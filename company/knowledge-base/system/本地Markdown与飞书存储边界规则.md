# 本地 Markdown 与飞书存储边界规则

> 状态：current
> 版本：0.1.0
> owner：CEO / Engineer
> last_updated：2026-07-14
> source_of_truth：company/knowledge-base/system/本地Markdown与飞书存储边界规则.md

这份文档用于约束 `MindSync` 在 `Codex + 本地仓库 + 飞书` 组合下的默认存储边界。

它回答的问题是：

- 哪些数据默认留在本地 Markdown
- 哪些数据默认放在飞书
- 同一类信息如果两边都存在，谁是主库
- `Codex` 在读写时应该优先信任哪一侧

## 1. 先定一个总原则

默认不要按“哪里更方便写”来决定存放位置，而是按“这份信息的职责”来决定。

- 本地 Markdown：负责严谨、沉淀、版本、批处理、可追溯
- 飞书：负责展示、协作、评论、流转、低门槛录入

一句话规则：

`源事实` 留本地，`协作界面` 放飞书。

## 2. 主库概念

同一个主题只能有一个 `source of truth`（唯一主库）。

可以存在：

- 本地主库 + 飞书展示版
- 飞书主库 + 本地索引页

不要长期并行维护“两边都算最终版本”的状态。否则会出现：

- `Codex` 不知道该信哪一份
- 人工改动互相覆盖
- 版本差异无法解释
- 周期性同步成本持续上升

## 3. 默认放本地 Markdown 的内容

以下内容默认以本地仓库为主库：

- 公司治理文档
- 项目级 `PROJECT.md`
- `spec / task / qa / delivery`
- 原始资料、访谈原文、OCR 原文、研究摘录
- Prompt、Agent 配置、自动化配置、脚本说明
- 会被 `Codex` 反复全文读取、改写、串联的知识库内容
- 需要 `Git` 历史、差异对比、回滚能力的文档
- 后续可能沉淀成模板、SOP、规则、知识条目的材料

这些内容适合本地的原因：

- 适合 `Git` 管理
- 适合大批量读取和重写
- 适合跨文件引用
- 适合保留证据链
- 适合后续机制化沉淀

## 4. 默认放飞书的内容

以下内容默认以飞书为主库：

- 给他人阅读的项目页、汇报页、对外说明页
- 会议纪要、讨论页、评审页
- 需要评论、@人、审批、共享的页面
- 需要多人手工维护的轻量表格、轻台账
- 访问便利性高于结构严谨性的页面
- 希望通过链接直接分发的页面

这些内容适合飞书的原因：

- 人类阅读体验更好
- 权限、分享、评论更方便
- 非技术成员进入成本更低
- 更适合作为协作工作台

## 5. 判断规则

如果一份内容满足下面任意两条，默认优先放本地：

- `Codex` 需要反复全文读取
- 需要保留完整历史版本
- 需要和多个本地文件交叉引用
- 后续要继续加工成知识库、模板或 SOP
- 属于证据、原文、研究材料，不能被随手改写

如果一份内容满足下面任意两条，默认优先放飞书：

- 主要是给人看，不是给机器做深加工
- 需要评论、协作、审批或转发
- 更新方式以零碎手工补充为主
- 链接直达比仓库结构更重要
- 维护者不止你一个，且多数人不在本地仓库里工作

## 6. 常见对象的默认归位

### 6.1 公司级与系统级材料

- `AGENTS.md`、`COMPANY.md`、治理文档：本地主库
- 系统设计、机制分析、协作规则：本地主库
- 面向外部协作者的阅读版说明：飞书展示版

### 6.2 项目执行材料

- `spec / task / qa / delivery`：本地主库
- 项目周报、阶段汇报、复盘摘要：飞书主库或飞书展示版
- 给客户或合作方看的项目介绍页：飞书主库

### 6.3 知识库与研究材料

- 原文、摘录、证据回填、术语定义：本地主库
- 经过筛选后的分享页、培训页、阅读导航页：飞书展示版

### 6.4 自动化与 Codex 协作材料

- Prompt、Skill、Agent 规则、自动化配置：本地主库
- 自动化输出给人看的日报、周报、看板页：飞书主库或飞书展示版

### 6.5 台账与表格

- 如果主要由你和 `Codex` 加工，且依赖结构化批处理：本地主库
- 如果主要由多人手填、查看、评论：飞书主库

## 7. 双边存在时的标准模式

### 模式 A：本地主库，飞书镜像

适用于：

- 方案文档
- SOP
- 知识库精选页
- 结构化研究结论

做法：

1. 先在本地完成正式版本
2. 如需共享，再同步到飞书
3. 飞书页头明确标注“主库在本地仓库”
4. 后续实质修改优先改本地，再决定是否回刷飞书

### 模式 B：飞书主库，本地索引

适用于：

- 周报
- 会议纪要
- 多人协作台账
- 审批或评论驱动页面

做法：

1. 飞书保存最终协作版本
2. 本地只保留索引、链接、摘要或导出物
3. 本地不要再维护一个“平行正式版”

## 8. Codex 的默认读写策略

当 `Codex` 能同时访问本地和飞书时，默认遵守以下顺序：

1. 先判断该类内容的主库在哪
2. 如果本地主库存在，优先读取本地
3. 如果飞书只是展示版，不以飞书文字覆盖本地主库
4. 如果飞书是主库，本地只维护链接、摘要或同步记录

如果当前没有明确定义主库，优先按下面方式处理：

- 规则、知识、配置、证据：默认判给本地
- 汇报、协作、评论、共享页：默认判给飞书

## 9. 不建议放飞书当主库的内容

以下内容不建议默认以飞书为唯一主库：

- 高复用 Prompt
- Agent 规则
- 自动化配置
- 需要长期 diff 的 SOP
- 研究原文与证据链
- 多文件相互引用的知识体系

原因不是“飞书不能放”，而是这些内容在飞书中通常会遇到：

- 历史差异不够清楚
- 结构化批处理成本更高
- 链接关系更弱
- 批量重构更难

## 10. 迁移判断

当一类内容原本在本地，现在考虑迁到飞书时，先问四个问题：

1. 它现在主要是给 `Codex` 用，还是给人看
2. 它需要版本追踪，还是需要评论协作
3. 它是证据与源材料，还是摘要与展示层
4. 它未来会沉淀成规则，还是停留在临时工作台

如果答案偏向前者，继续留本地。

如果答案偏向后者，可以迁到飞书。

## 11. 当前推荐默认策略

结合 `MindSync` 当前工作方式，推荐默认策略如下：

- 本地保留：
  - 公司治理文档
  - 项目 `PROJECT.md`
  - 原文资料与证据库
  - Prompt、Agent、自动化配置
  - 重要 `spec / task / qa / delivery`
  - 可复用 SOP 与知识沉淀
- 飞书保留：
  - 日常沟通页
  - 汇报页
  - 会议纪要
  - 面向他人的阅读版页面
  - 多人维护的轻量台账
  - 需要评论与审批的页面

## 12. 落地约束

后续若新增一个“本地与飞书都可能适合”的内容类型，默认执行：

1. 先指定唯一主库
2. 再决定另一侧是否只做镜像、摘要或索引
3. 在文档开头标注 `source_of_truth`
4. 不允许长期无定义地双向并行维护

如果一时判断不清，优先保守处理：

- 先把正式版本留在本地
- 飞书只放摘要版或共享版
- 等使用一段时间后，再决定是否把飞书提升为主库
