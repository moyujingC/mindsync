# AI Plugin 系统性讨论

> 版本：0.1.0
> owner：Research & Knowledge Lead

这份文档用于系统解释 `plugin` 在 AI 工具生态中的作用、边界、常见误区与治理方法。

这里的 `plugin` 泛指 AI 工具生态中的插件，不限定为某一个平台的专有实现。不同平台里的插件格式不同，但核心目标相似：把一组能力打包成可安装、可共享、可更新、可治理的能力包。

## 1. 一句话定义

`plugin` 是 AI 工具生态中的能力分发包。

它解决的核心问题不是“AI 应该怎么做事”，也不是“AI 怎么连接某个外部系统”，而是：

- 如何把一组能力打包
- 如何安装到 AI 工具里
- 如何跨项目或团队共享
- 如何升级、版本化和下架
- 如何避免能力命名冲突

如果 `skill` 像团队 SOP（标准作业流程），`MCP` 像 AI 连接外部系统的 USB-C 接口，那么 `plugin` 更像一个可安装的工具箱。

## 2. Plugin 可能包含什么

不同 AI 工具的 plugin 能力不完全一样，但常见内容包括：

- skills（技能 / 工作流说明）
- MCP servers（模型上下文协议服务端）
- MCP connectors（MCP 连接器）
- agents（代理 / 子代理定义）
- hooks（钩子 / 自动触发脚本）
- commands（命令）
- settings（默认配置）
- app connectors（应用连接器）
- templates（模板）
- scripts（脚本）
- assets（素材）

所以 plugin 不是一种单一能力。

它更像一个容器，把多种能力按平台规则组织起来。

## 3. Plugin 和其他概念的关系

### 3.1 Plugin 和 skill

skill 是流程层能力。

plugin 可以打包一个或多个 skill。

例如：

- 一个“内容团队插件”可以包含多个内容写作 skill
- 一个“工程团队插件”可以包含代码审查、CI 修复、发布检查 skill
- 一个“研究插件”可以包含文献检索、事实核查、研究综合 skill

plugin 负责分发，skill 负责指导 AI 怎么做。

### 3.2 Plugin 和 MCP

MCP 是连接协议。

plugin 可以打包 MCP server 或连接配置。

例如：

- 一个 GitHub plugin 可以内置 GitHub MCP connector
- 一个 Figma plugin 可以内置 Figma MCP server 的配置说明
- 一个内部数据插件可以打包 CRM MCP server 和对应使用 skill

plugin 负责安装和组织，MCP 负责连接外部系统。

### 3.3 Plugin 和 app connector

app connector（应用连接器）通常是连接某个具体 SaaS 或外部应用的能力。

它可能基于 MCP，也可能基于平台自己的 connector API。

plugin 可以把 app connector、使用说明和相关 skill 打包在一起。

### 3.4 Plugin 和 prompt

prompt（提示词）是一段直接给模型的指令。

plugin 可以包含 prompt 模板，但 plugin 不等于 prompt。

成熟插件通常不只是几段提示词，而是带有结构、权限、版本和依赖关系的能力包。

## 4. Plugin 解决什么问题

### 4.1 跨项目复用

如果某套能力只服务一个项目，放在项目本地配置里就够了。

如果它要被多个项目、多个角色、多个工作区使用，就适合做成 plugin。

例如：

- 公司统一代码审查流程
- 公司统一内容风格检查
- 公司统一 GitHub 工作流
- 公司统一研究事实核查流程

### 4.2 团队共享

plugin 可以让团队成员不必手动复制散落的配置。

团队只需要安装同一个 plugin，就能拿到同一组：

- skill
- agent
- connector
- hook
- 默认配置

这比在聊天里反复复制提示词更稳定。

### 4.3 版本管理

当能力变成 plugin 后，就可以被版本化：

- `0.1.0`：试用
- `0.2.0`：补充新 skill
- `1.0.0`：稳定发布

版本化的价值是：团队知道自己到底在用哪套能力。

### 4.4 命名空间隔离

插件通常会引入 namespace（命名空间）。

例如同样叫 `review` 的 skill，在不同 plugin 中可以区分为：

- `engineering:review`
- `content:review`
- `legal:review`

命名空间可以减少能力冲突，尤其适合大团队或多插件环境。

### 4.5 市场分发

plugin 可以进入 marketplace（插件市场）或组织内部 registry（注册表）。

这让能力可以被发现、安装、更新和评价。

但这也引入供应链风险，需要治理。

## 5. Plugin 不是什么

### 5.1 Plugin 不是质量保证

一个插件能被安装，不代表它质量高。

高 star、高下载量、被博主推荐，都不等于适合自己的团队。

plugin 只是分发形式，不自动保证：

- skill 写得好
- MCP 权限安全
- 工具调用可靠
- 输出符合你的团队标准

### 5.2 Plugin 不是越多越好

插件越多，AI 的可选能力越多。

但如果缺少治理，也会出现：

- 能力重叠
- 触发混乱
- 权限过宽
- 版本漂移
- 输出风格不稳定

插件市场很容易让人产生“装了就更强”的错觉。

实际更稳的做法是少量核心插件 + 明确边界 + 定期清理。

### 5.3 Plugin 不是 MCP 的替代品

plugin 可以包含 MCP，但不能替代 MCP 的协议职责。

如果目标是让 AI 标准化连接外部系统，核心仍然是 MCP 或对应 connector。

plugin 只是把这些连接能力打包和分发。

### 5.4 Plugin 不是 skill 的替代品

plugin 可以装很多能力，但如果没有 skill 告诉 AI 什么时候用、怎么用、输出什么，插件也可能只是能力堆叠。

真正稳定的团队插件，通常会同时包含：

- 连接能力
- 使用流程
- 质量门槛
- 示例任务
- 权限说明

## 6. 常见插件类型

### 6.1 工具连接型插件

目标是连接外部工具。

例子：

- GitHub 插件
- Google Drive 插件
- Jira 插件
- Figma 插件
- Sentry 插件

这类插件的核心价值是减少复制粘贴，让 AI 能直接读取或操作外部系统。

### 6.2 工作流型插件

目标是提供一组团队工作流。

例子：

- TDD 插件
- 代码审查插件
- 发布流程插件
- 内容生产插件
- 研究流程插件

这类插件的核心价值是把团队 SOP 变成可复用能力。

### 6.3 领域知识型插件

目标是为某个专业领域提供资料、工具和流程。

例子：

- 生命科学研究插件
- 金融分析插件
- 法务审查插件
- 前端设计插件

这类插件通常会打包多份 skill、参考资料和脚本。

### 6.4 组织治理型插件

目标是统一公司内部 AI 工作方式。

例子：

- 公司文档格式插件
- 公司交付流程插件
- 公司安全审查插件
- 公司知识库维护插件

这类插件最适合内部使用，不一定适合公开分发。

## 7. 插件市场的常见误区

### 7.1 高星不等于适配

一个公开插件很受欢迎，只说明它对很多人有吸引力。

但它可能默认：

- 英文工作流
- 某个技术栈
- 某种权限模型
- 某种团队流程
- 某种输出格式

这些假设不一定适合你的团队。

### 7.2 安装容易，治理困难

装插件通常很快。

但真正困难的是：

- 谁负责维护
- 谁审权限
- 谁判断升级
- 出问题如何回滚
- 哪些项目允许使用
- 哪些数据不能暴露

如果这些问题没解决，插件越多，系统越乱。

### 7.3 插件会改变 AI 的行为

插件可能带来新的 skill、工具、agent 或默认配置。

这会影响 AI：

- 能看到什么
- 能调用什么
- 会优先采用什么流程
- 输出时遵循什么模板

因此，插件不是中性的资源包，而是会改变 agent 行为的扩展层。

## 8. 插件的风险

### 8.1 权限风险

插件可能请求访问：

- 文件
- 邮箱
- 云盘
- Git 仓库
- issue 系统
- 客户数据
- 内部知识库

如果权限过宽，插件就可能成为数据泄露入口。

### 8.2 供应链风险

第三方插件可能：

- 依赖不安全包
- 更新后改变行为
- 被上游接管
- 通过脚本执行高危操作
- 暴露敏感数据

治理插件时，要像治理代码依赖一样严肃。

### 8.3 行为污染

插件里的 skill 或默认规则可能和团队规则冲突。

例如：

- 外部插件要求直接实现
- 公司规则要求先补 spec
- 外部插件默认英文输出
- 公司规则要求中文交付

这些冲突会让 AI 行为变得不稳定。

### 8.4 版本漂移

团队成员安装的插件版本不同，会导致同一任务产出不同。

治理要求：

- 固定核心插件版本
- 记录升级原因
- 升级前做最小回归
- 保留回滚路径

## 9. 团队如何筛选插件

安装一个插件前，至少问这些问题：

- 它解决的是高频问题吗
- 它是否和现有能力重叠
- 它会读取哪些数据
- 它会执行哪些动作
- 它是否有清晰 owner
- 它是否有版本和更新记录
- 它的默认流程是否符合团队规则
- 它是否可以只在特定项目启用
- 它是否需要配套 skill 约束使用方式

如果这些问题回答不清，不应直接进入核心工作流。

## 10. 团队如何自建插件

自建插件前，先不要急着打包。

推荐顺序是：

1. 先在单项目中试用 standalone（独立配置）
2. 跑真实任务
3. 稳定 skill 和工具边界
4. 写清权限和版本
5. 再打包成 plugin
6. 在少数项目试点
7. 通过后进入团队核心插件集

也就是说：

> 先验证能力，再插件化分发。

不要把还没稳定的流程直接做成 plugin。那只是把混乱扩散得更快。

## 11. 插件生命周期

一个团队插件最好有完整生命周期。

### 11.1 Candidate（候选）

只做调研和小范围试用。

不进入默认工作流。

### 11.2 Adapted（适配）

已经按团队术语、目录、权限和流程改写。

允许在少数项目中试跑。

### 11.3 Core（核心）

通过真实任务验证。

可以作为团队默认能力安装。

### 11.4 Deprecated（废弃）

不再推荐新任务使用。

需要给出替代插件或替代流程。

### 11.5 Removed（移除）

从默认能力集中删除。

保留历史记录，避免未来重复引入。

## 12. 核心结论

plugin 的本质不是“一个更强功能”，而是“把一组 AI 能力打包、分发、安装、更新和治理的方式”。

它最适合解决：

- 团队共享
- 跨项目复用
- 版本管理
- 能力组合
- 市场或内部 registry 分发

但 plugin 不自动保证质量，也不自动保证安全。

更稳的理解是：

> plugin 负责分发能力，skill 负责定义流程，MCP 负责连接外部系统。
