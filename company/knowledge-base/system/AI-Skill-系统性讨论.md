# AI Skill 系统性讨论

> 状态：current
> 版本：0.1.0
> owner：Research & Knowledge Lead
> last_updated：2026-05-03
> source_of_truth：company/knowledge-base/system/AI-Skill-系统性讨论.md

这份文档用于系统解释 `skill` 在 AI 团队中的作用、常见误区、设计原则与落地方法。

这里的 `skill` 指面向 AI agent 的能力封装：它可以包含触发描述、工作流程、质量标准、工具脚本、参考资料和模板。它不是普通提示词合集，也不是越多越好的插件仓库。

## 1. 一句话定义

`skill` 更像是给 AI 使用的团队 SOP（标准作业流程）+ 工具包。

它的目标不是让 AI 记住更多信息，而是让 AI 在特定任务里更稳定地：

- 判断什么时候该进入某个流程
- 按团队认可的方法工作
- 调用必要工具或资料
- 输出符合交付标准的结果

如果说普通 SOP 是写给人的流程说明，那么 skill 是写给 AI agent 的操作手册。

更准确地说：

> skill 是让 AI 更稳定地按团队 SOP 做事的能力封装。

## 2. Skill 不是什么

理解 skill 时，先排除几个误解。

### 2.1 Skill 不是万能插件

装了一个 skill，不代表 AI 就真的掌握了一门完整能力。

skill 只是提供方向、边界、工具和流程。AI 仍然需要根据当前任务、仓库、用户要求和上下文进行判断。

### 2.2 Skill 不是自动化程序

skill 不会自己定时运行，也不会自己主动执行任务。

通常流程是：

1. 用户提出任务
2. AI 判断是否触发某个 skill
3. AI 读取 skill 的说明
4. AI 根据说明读文件、写代码、运行脚本或生成内容

如果需要定时执行、监控、提醒、巡检，那更接近 automation（自动化）或 scheduler（调度器）的范畴。

### 2.3 Skill 不是知识库全文塞入

一个好的 skill 不应该把所有背景、教程、案例都塞进正文。

更好的结构是：

- SKILL.md 放核心流程
- references（参考资料）放详细知识
- scripts（脚本）放可执行动作
- assets（素材）放模板、图片、字体或示例文件

这样 AI 只在需要时读取具体资料，不会一开始就被大量无关信息淹没。

## 3. Skill 通常由什么构成

一个典型 skill 至少包含：

```text
skill-name/
├── SKILL.md
├── references/
├── scripts/
└── assets/
```

### 3.1 Metadata（元数据）

metadata 通常包括：

- `name`：skill 名称
- `description`：什么时候使用这个 skill

其中最关键的是 `description`。

它决定 AI 是否会触发这个 skill。description 写得太泛，skill 会频繁误触发；写得太窄，又可能该用时没用上。

### 3.2 Workflow（工作流程）

workflow 告诉 AI：

- 先判断什么
- 再读取什么
- 哪些步骤必须做
- 哪些步骤可以按情况省略
- 最后输出什么

这部分要写成“AI 能执行的流程”，不是写成给人看的长篇理念。

### 3.3 Quality Bar（质量标准）

quality bar 是交付门槛。

例如：

- 输出必须包含验收标准
- 不能虚构上游材料
- 修改代码后必须运行指定测试
- 文档必须包含 owner、状态、版本和 source_of_truth

没有 quality bar 的 skill，很容易变成风格建议，而不是稳定能力。

### 3.4 Bundled Resources（内置资源）

skill 可以带资源：

- scripts：可执行脚本，用于高重复、高确定性任务
- references：领域资料、API 文档、公司规范
- assets：模板、图片、字体、示例文件

这些资源的价值在于把“容易反复写错的动作”变成可复用资产。

## 4. Skill 为什么会显著影响 AI 输出

skill 对 AI 的影响主要来自四个方面。

### 4.1 它改变 AI 的任务理解方式

没有 skill 时，AI 只能从用户当前描述中推断任务。

有 skill 时，AI 会额外看到：

- 这个任务属于哪类场景
- 团队过去怎么处理这类任务
- 哪些边界不能越过
- 哪些交付格式是默认标准

这会明显影响 AI 对问题的建模方式。

### 4.2 它改变 AI 的行动顺序

比如同样是“帮我做一个产品方案”：

- 没有 skill 时，AI 可能直接写方案
- 有产品 framing skill 时，AI 可能先澄清用户、问题、范围、约束和验收标准

输出质量的差异，往往不来自“语言更漂亮”，而来自行动顺序更稳定。

### 4.3 它减少团队隐性规则的丢失

很多团队规则平时藏在人的脑子里：

- 这个项目不能改哪些目录
- 这个账号不能用什么表达方式
- 这个任务必须先补 spec
- 这个工具链必须先跑 smoke test（冒烟测试）

skill 的价值，是把这些隐性规则显性化，让 AI 不必每次都重新猜。

### 4.4 它把工具使用变成稳定路径

当 skill 内置脚本或工具说明时，AI 不只是“知道应该做什么”，还知道“具体怎么做”。

例如：

- PDF 处理 skill 可以告诉 AI 用哪个脚本旋转页面
- Playwright skill 可以告诉 AI 如何做浏览器验证
- CI skill 可以告诉 AI 如何读取失败日志和定位流水线问题

这会降低重复劳动和操作失误。

## 5. Skill 是不是越多越好

不是。

更准确地说：

> 有效 skill 越多越好；低质量、重叠、过时或触发不清的 skill 越多越糟。

原因很简单：skill 增加的是“可选项”，不一定增加“秩序”。

### 5.1 Context Window（上下文窗口）是有限资源

AI 每次工作时能同时看到的内容有限。

skill 的 metadata、说明、参考资料都会占用上下文窗口。上下文窗口可以理解为 AI 当前这次任务的工作台。

工作台上放太多无关材料，真正的任务材料、代码、用户要求和关键约束就会被挤掉。

### 5.2 Trigger（触发条件）会互相抢任务

如果多个 skill 都写着：

- 用于产品设计
- 用于战略分析
- 用于内容创作
- 用于代码实现

AI 就很难判断到底该用哪个。

结果是同一个任务今天走 A 流程，明天走 B 流程，行为开始不稳定。

### 5.3 规则可能互相冲突

一个 skill 要求“输出简洁”，另一个 skill 要求“完整展开”。

一个 skill 默认英文术语，另一个 skill 要求中文解释。

一个 skill 让 AI 直接实现，另一个 skill 要求先补 spec（规格说明）。

这些规则本身不一定错，但如果边界不清，就会让 AI 在冲突规则中来回摇摆。

### 5.4 外部 skill 往往带有隐性假设

很多从 GitHub 下载的高星 skill，会默认某些前提：

- 默认英文工作环境
- 默认某个技术栈
- 默认某种项目目录
- 默认某种团队协作方式
- 默认某种输出风格

这些假设放在原作者团队里可能成立，放到自己的 AI 团队里不一定成立。

直接照搬，本质上是把别人的 SOP 装进自己的组织。

### 5.5 维护成本会持续上升

skill 一多，就会出现：

- 旧版本没人删
- 重复 skill 没合并
- 半废弃 skill 仍然会触发
- 新旧规则同时存在
- 团队不知道哪个才是当前标准

AI 不会天然知道哪条规则才是最新、最权威、最适合当前团队。

## 6. 为什么短期看起来功能变多，长期会让 AI 行为变乱

短期看起来功能变多，是因为菜单变多了。

AI 似乎突然能做：

- 写 PRD（产品需求文档）
- 做竞品分析
- 生成代码
- 写营销文案
- 做浏览器测试
- 处理 PDF
- 生成图表

但长期变乱，是因为菜单没有治理。

典型表现包括：

- 同一类任务输出格式反复变化
- AI 经常触发不相关 skill
- 项目规则被外部 skill 覆盖
- 结果越来越像模板拼贴
- AI 花很多篇幅解释流程，却没有推进任务
- 不同 agent 对同一件事采用不同标准

可以把问题总结为：

> skill 变多以后，如果没有清晰边界、统一术语和版本治理，AI 不是更专业，而是在一堆互相打架的 SOP 中做选择。

## 7. 使用外部高星 skill 的常见误区

现在很多人会看 AI 博主分享的 GitHub 高星 skill 项目，然后批量下载使用。

这种做法的问题不是“外部 skill 没价值”，而是“没有经过组织适配”。

### 7.1 Star 不等于适配度

GitHub star 更多，通常说明：

- 标题吸引人
- 覆盖场景广
- 传播效果好
- 示例看起来强

但它不一定说明：

- 触发条件清楚
- 上下文节省
- 输出稳定
- 和你的项目兼容
- 维护及时

### 7.2 高星 skill 可以参考，但不能直接当组织规则

外部 skill 更适合作为素材库。

正确用法是：

1. 分析它解决什么问题
2. 找出它默认了哪些流程和技术栈
3. 删除和自己团队无关的部分
4. 改写成自己的术语、目录和交付标准
5. 用真实任务测试后再纳入 core skill（核心技能）

### 7.3 外部 skill 应该分级管理

建议用三种状态：

| 状态 | 含义 |
|---|---|
| `candidate` | 候选，只参考，不正式启用 |
| `adapted` | 已按团队流程改写，进入试用 |
| `core` | 真实任务验证通过，正式进入 AI 团队能力栈 |

未经改写和验证的外部 skill，不应直接进入 core。

## 8. 什么样的内容适合做成 skill

适合做 skill 的内容，通常同时满足几个条件。

### 8.1 高频

这个任务经常出现。

例如：

- 写产品规格
- 做代码审查
- 修 CI
- 生成内容选题
- 整理研究结论
- 做发布前验证

高频任务值得沉淀，因为每次少犯一点错，长期收益很大。

### 8.2 高风险

这个任务一旦做错，代价比较高。

例如：

- 发布流程
- 数据迁移
- 支付集成
- 权限系统
- 合规表达
- 用户数据处理

高风险任务需要更明确的 guardrail（护栏）。

### 8.3 高一致性要求

这个任务每次输出都应该稳定。

例如：

- spec 格式
- QA 报告
- delivery 记录
- commit message（提交信息）
- handoff（交接）材料

这类任务如果每次风格不同，后续协作会很痛苦。

### 8.4 容易被 AI 误解

如果一个任务人类觉得简单，但 AI 经常做偏，就适合做 skill。

例如：

- “把研究转成内容”不是让 AI 编外部知识
- “优化 UI”不是做营销风 hero page
- “修测试”不是跳过失败用例
- “写文档”不是堆长篇解释

skill 可以明确告诉 AI：这类任务真正的边界在哪里。

## 9. 什么内容不适合做成 skill

以下内容通常不适合直接做成 skill：

- 一次性临时任务
- 纯创意发散
- 没有稳定流程的判断
- 已经被现有 skill 覆盖的内容
- 只是个人偏好的表达习惯
- 大段教程或知识百科

如果只是为了“让 AI 知道更多”，通常不该新建 skill。

更好的方式可能是：

- 放到项目文档
- 放到知识库
- 放到 references
- 写进具体任务说明
- 更新现有 skill 的边界

## 10. 如何为自己的 AI 团队定制 skill 包

真正有效的 skill 包，不是从外面批量下载来的，而是从团队真实工作流中长出来的。

推荐流程如下。

### 10.1 第一步：先审计工作流，不先写 skill

让 Claude Code、Codex 或其他代码 agent 先读取团队已有材料：

- AGENTS.md
- 项目 PROJECT.md
- 公司治理文档
- 最近任务记录
- delivery 文档
- QA 文档
- 角色说明

然后让 AI 总结：

- 团队高频任务有哪些
- 哪些任务有稳定流程
- 哪些任务最容易出错
- 哪些输出需要统一格式
- 哪些规则属于公司级、项目级、角色级

这一步的目标是得到 skill map（技能地图），不是直接生成一堆 skill。

### 10.2 第二步：设计 Skill Map（技能地图）

一个 AI 团队的 skill 包可以分五层。

| 层级 | 作用 | 示例 |
|---|---|---|
| 基础协作层 | 统一语言、提交、文件修改、交付习惯 | Git 提交规则、文档元数据规则 |
| 任务路由层 | 判断任务归谁、走什么流程 | task-routing、artifact-readiness-check |
| 角色能力层 | 让不同 agent 按角色工作 | 产品、研究、内容、工程、QA |
| 项目专用层 | 说明项目目录、边界和禁区 | 某产品项目 skill |
| 工具执行层 | 处理具体工具或格式 | Figma、PDF、Playwright、CircleCI |

这张地图要回答：

- 每个 skill 管什么
- 不管什么
- 谁会用
- 和哪个 skill 相邻
- 是否存在重叠

### 10.3 第三步：每个 skill 只管一件事

坏 skill 经常长这样：

> 负责产品、战略、内容、增长、研究、执行和复盘。

它看起来强，实际很难触发准确。

好 skill 应该像这样：

> 当用户要把模糊产品想法收束成可执行规格说明时使用。输出包括目标用户、问题定义、范围边界、验收标准和下一步任务。

边界越清楚，AI 越容易稳定使用。

### 10.4 第四步：统一 skill 结构

建议每个 skill 至少包含：

```md
---
name: skill-name
description: 什么时候使用这个 skill。
---

# Skill Name

## When to Use
什么时候用。

## When Not to Use
什么时候不用。

## Required Inputs
需要哪些输入。

## Workflow
具体步骤。

## Output Format
输出格式。

## Quality Bar
质量标准。

## References
需要时再读取哪些资料。
```

这里最重要的是 `description`、`When to Use` 和 `When Not to Use`。

它们共同决定这个 skill 会不会被误用。

### 10.5 第五步：用真实任务做评测

不要只看 skill 写得是否漂亮。

要拿真实任务测试：

- 是否应该触发
- 是否真的触发
- 是否误触发
- 输出是否更稳定
- 是否减少返工
- 是否占用过多上下文
- 是否和其他 skill 冲突

评测应该使用真实任务样本，而不是专门为 skill 编造的完美测试题。

### 10.6 第六步：版本化和定期清理

skill 应该像代码一样治理：

- 有 owner（负责人）
- 有版本
- 有适用范围
- 有废弃机制
- 有真实任务回归样本
- 有定期清理节奏

如果一个 skill 三个月没有被正确触发过，要么它不重要，要么它的 description 写错了。

## 11. Claude Code 和 Codex 在定制 skill 包中的用法

Claude Code 和 Codex 这类工具，最适合扮演 skill 工程师，而不是单纯的提示词生成器。

### 11.1 用它们审计现有系统

可以让 AI 做：

- 读取仓库结构
- 总结项目边界
- 找出重复文档
- 识别高频任务
- 梳理 agent 角色分工
- 发现当前流程缺口

示例 prompt：

```text
请读取当前仓库的 AGENTS.md、项目说明、角色说明和最近任务文档。
帮我整理一张 AI 团队 skill 地图：
1. 高频任务
2. 适合沉淀成 skill 的节点
3. 不适合做 skill 的内容
4. 每个 skill 的触发条件和边界
```

### 11.2 用一个 AI 写，用另一个 AI 审

可以采用双角色：

- Codex 生成 skill 初稿
- Claude Code 审查是否过泛、重复、冲突或啰嗦
- Codex 根据审查意见修改
- 再用真实任务测试

审查 prompt：

```text
请以 skill reviewer 的身份检查这个 SKILL.md：
1. 触发条件是否过宽
2. 是否和已有 skill 重叠
3. 是否包含不必要的长篇解释
4. 是否缺少 When Not to Use
5. 是否能稳定指导 AI 完成任务
```

### 11.3 用 AI 改造外部 skill

不要直接照搬外部 skill。

可以让 AI 先分析：

```text
请分析这个外部 skill。
不要直接照搬。
请指出它默认了哪些团队流程、技术栈、语言习惯和交付标准。
然后把它改写成适合我们团队的版本。
```

改造后的 skill 要先进入 `adapted`，通过真实任务验证后再进入 `core`。

### 11.4 用 AI 建立回归样本

每个核心 skill 都应该保存几类测试样本：

- 应该触发的任务
- 不应该触发的任务
- 容易误触发的边界任务
- 过去出错过的真实任务

这些样本可以帮助你判断修改 skill 后是否引入了新问题。

## 12. 一套推荐的 AI 团队 skill 能力栈

对一个需要长期运行的 AI 团队来说，可以从下面这条链路开始：

```text
任务路由
-> 问题定义
-> 方案收束
-> 实施计划
-> 执行
-> 验证
-> 交付
-> 知识沉淀
```

对应 skill 类型可以是：

| 链路 | Skill 类型 | 目标 |
|---|---|---|
| 任务路由 | routing skill | 判断任务属于谁、走什么流程 |
| 问题定义 | framing skill | 把模糊请求变成清楚问题 |
| 方案收束 | spec skill | 形成可执行规格 |
| 实施计划 | planning skill | 拆任务、定边界、定验收 |
| 执行 | implementation skill | 按项目规则修改文件或运行工具 |
| 验证 | QA skill | 检查结果是否可交付 |
| 交付 | delivery skill | 记录改动、验证、风险和下一步 |
| 知识沉淀 | knowledge skill | 把一次性经验转成长期资产 |

这套结构的重点不是 skill 数量，而是链路闭环。

## 13. 好 skill 的判断清单

可以用下面清单判断一个 skill 是否值得保留。

### 13.1 触发清晰

- description 是否能说明“什么时候用”
- 是否写了 When Not to Use
- 是否避免了“什么都能用”的泛化描述

### 13.2 边界清楚

- 是否说明它不负责什么
- 是否和其他 skill 有明确分工
- 是否避免抢其他角色的任务

### 13.3 内容精简

- SKILL.md 是否只放核心流程
- 详细资料是否放到 references
- 是否删除了给人看的长篇解释

### 13.4 可执行

- 是否告诉 AI 具体做什么
- 是否有必要的输入和输出格式
- 是否包含质量门槛
- 高风险动作是否配有脚本或明确命令

### 13.5 可验证

- 是否有真实任务样本
- 是否能判断输出是否变好
- 是否能发现误触发和冲突

### 13.6 可维护

- 是否有 owner
- 是否有版本
- 是否知道何时废弃
- 是否能被团队其他成员理解

## 14. 最小落地方案

如果一个团队刚开始建设 skill 包，不建议一口气做很多。

可以先做 5 个核心 skill：

1. 任务路由 skill
2. 产品或需求收束 skill
3. 工程实现 skill
4. QA 验收 skill
5. 交付与知识沉淀 skill

然后选 10 个真实任务回放测试。

测试通过后，再逐步增加：

- 角色专用 skill
- 项目专用 skill
- 工具专用 skill
- 外部改造 skill

这样做的好处是：先跑通组织闭环，再扩展能力范围。

## 15. 核心结论

skill 的本质不是“更多提示词”，而是“把团队真实工作方式封装成 AI 可执行、可触发、可验证的能力”。

使用 skill 时，最重要的不是数量，而是：

- 是否来自真实工作流
- 是否触发准确
- 是否边界清晰
- 是否减少返工
- 是否能稳定提高交付质量
- 是否能被持续维护

外部高星 skill 有参考价值，但未经改写和验证，本质上只是别人的 SOP。

真正适合自己团队的 skill 包，应该从自己的项目、角色、任务、工具和交付标准里长出来。

最终目标不是拥有很多 skill，而是让 AI 团队形成一套稳定的操作系统：

> 任务能被正确路由，流程能被正确执行，结果能被清楚验证，经验能被长期沉淀。
