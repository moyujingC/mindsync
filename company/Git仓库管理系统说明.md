# Git 仓库管理系统说明

> 状态：current
> 版本：0.1.1
> owner：Engineer
> last_updated：2026-05-04
> source_of_truth：company/Git仓库管理系统说明.md

这份文档定义 `MindSync` 当前的公司级 Git 仓库管理系统。

这里说的“仓库管理系统”，不是指某个 Git 平台按钮怎么点，而是指公司内部当前采用的整套仓库组织方式，包括但不限于：

- `Monorepo`（单仓多项目）
- `git worktree`（Git 工作树）
- 分支与主干口径
- 公司级与项目级目录分层
- 历史仓库与当前主入口的关系
- 本地执行与服务器执行的仓库路径语义
- 提交纪律与自动提交辅助机制

这份文档的作用，是作为公司级总入口：

- 只保留整体口径
- 不重复项目映射细节
- 不重复 Monorepo 目录细节
- 不重复提交机制实现细节

## 1. 一句话定义

`mindsync` 当前采用的是：

- 一个公司级主仓库 `mindsync`
- 以 `Monorepo` 为主结构
- 以根工作区 `main` 作为单人开发默认主工作台
- 以 `git worktree` 作为按需启用的辅助机制，用于并行开发和执行链隔离
- 以公司治理文档作为长期规则源
- 以 `Paperclip` 作为运行时控制面，而不是仓库主入口

更直白一点说：

`mindsync` 是主系统，`main` 是默认工作台，`git worktree` 是按需加开的分工作台，`Paperclip` 是任务控制台。

## 2. 这套系统解决什么问题

如果没有这套仓库管理系统，信息和实现会散到很多地方：

- 多个历史仓库
- 临时 worktree
- 聊天记录
- shell 历史
- Paperclip 运行态对象
- 服务器上的共享 checkout

结果通常会变成：

- 不知道哪个公司级规则该改在哪里
- 不知道项目实现应该落在哪个目录
- 不知道某个 worktree 只是临时开发台，还是正式运行路径
- 不知道服务器上的 checkout 是主镜像区、巡检区，还是隔离执行区
- 不知道某个历史仓库是否还算正式主入口

这套管理系统的目标，就是把这些问题统一收口。

## 3. 当前采用的总结构

### 3.1 主仓库

当前公司级主仓库是：

- `mindsync`

它同时承担两层角色：

1. 公司内核仓库
2. 多项目 `Monorepo`

这意味着它不是“某个单一应用项目的代码仓库”，而是：

- 公司治理源
- 角色定义源
- 项目入口源
- 共享工具源
- 长期知识源

### 3.2 Monorepo 的定位

当前主仓采用 Monorepo 结构，但目录分层细节不在这里重复展开。

正式目录分层说明看：

- [MONOREPO.md](MONOREPO.md)

### 3.3 历史仓库的定位

当前默认口径是：

- 历史独立仓库只作为迁移来源或归档参考
- 不再作为正式主入口

也就是说，如果一个项目已经正式收束进 `mindsync/projects/`，那么后续默认应以 `mindsync` 为准，而不是继续把历史独立仓库当主线。

## 4. Git worktree 在这里扮演什么角色

`git worktree` 可以通俗理解为：

在同一个 Git 仓库主历史下，额外开出多个并行工作台，每个工作台可以对应不同分支、不同任务、不同执行链。

在 `墨予镜` 当前体系里，`git worktree` 主要承担三类角色：

### 4.1 本地多项目开发工作台

例如：

- `aimandala/dev`
- `relayhub/dev`
- `content-matrix/dev`
- `research-center/dev`
- `xinran-jobhunt/dev`

这些 worktree 的意义不是替代主仓，而是当根工作区不够用时，为不同项目提供稳定、独立、不互相打架的开发台。

### 4.2 运行时隔离工作台

例如服务器上的：

- `/opt/automation/worktrees/...`

它的意义是：

- 会写文件的自动化执行，不再共享同一个 checkout
- 每条任务或每类任务，尽量落到自己的隔离 worktree

### 4.3 本地自动执行的 runtime worktree

对部分本地自动执行场景，worktree 还承担：

- 给本地执行器提供稳定可运行 checkout
- 避免直接占用用户手工开发中的主工作区

## 5. 什么时候该用主仓，什么时候该用 worktree

### 5.1 主仓（main checkout）更适合做什么

主仓更适合承担：

- 公司治理文档维护
- 公司注册表与入口维护
- Automation、运行机制、系统说明这类总线级改动
- 单人开发阶段、一次只专注一个工程或任务时的项目实现与验证
- 最终收口后的稳定主干内容

在一人开发语境里，可以把这里理解得更直接一些：

- 如果你当前只有一条主任务线
- 如果根工作区没有被别的实验分支或运行时占住
- 如果你不需要并行隔离多个开发面

那么直接在根工作区对应的 `main` 上开发，就是默认推荐路径。

### 5.2 worktree 更适合做什么

worktree 更适合承担：

- 某个项目需要长期独立工作台时的连续开发
- 某条分支的实验、验证和迭代
- 与其他项目并行进行、不希望互相污染的开发任务
- 自动化执行链里的隔离写操作
- 需要同时保留多个 checkout（检出副本）而不想频繁 `stash`（临时收起改动）/ 切分支时

换句话说，`worktree` 不是“默认先进场”，而是“主工作区不够用时再启用”。

### 5.3 不该把 worktree 当成什么

不应把 worktree 当成：

- 另一个独立仓库
- 长期脱离主仓治理的平行世界
- 可以无纪律长期堆脏改的“临时垃圾场”

worktree 只是工作台，不是新公司。

## 6. 当前分支与 worktree 的正式口径

### 6.1 主干口径

当前根工作区默认对应：

- `main`

在当前一人开发模式下，`main` 的定位首先是：

- 默认主工作台
- 公司主干
- 治理主干
- Automation 和最终收口主干
- 当下单线程任务足够清晰时的直接开发分支

这里要特别避免一个常见误解：

- `main` 不是被禁止开发项目代码的“只读主台”
- `worktree` 也不是每做一个项目都必须先进的强制步骤

GitHub / Git 的正式理解应是：

- `main`
  - 默认先承担公司级文档、治理规则、Automation、共享脚本，以及单人开发场景下当前主任务的实现与验证
- 项目开发分支
  - 在需要隔离长期演进、多人并行、实验性迭代或部署链隔离时，再承担对应项目的日常开发与验证
- `worktree`
  - 只是这些分支在本地或服务器上的独立工作台，不改变分支本身的治理语义，也不是默认必选项

### 6.2 IDE 代理的分支权限

默认硬约束：

- `Codex`、`Claude Code` 等 IDE 代理不得主动创建分支
- 不得主动切换分支
- 不得主动创建新的本地 `git worktree`
- 不得因为任务较复杂、文件较多或推测需要隔离，就自行把工作搬到新分支

只有在用户明确说出类似下面意图时，代理才允许执行：

- “新建一个分支”
- “切到某个分支”
- “为这个任务开 worktree”
- “按项目 dev 分支推进”

否则默认动作必须是：

- 先确认当前 `git status`
- 在当前分支、当前 worktree 内完成修改
- 完成后只提交本轮负责文件

### 6.3 项目 worktree 口径

当前已经明确采用独立 worktree 的项目，可以固定对应自己的开发分支。

例如：

- `relayhub/dev`
- `aimandala/dev`
- `content-matrix/dev`
- `research-center/dev`
- `xinran-jobhunt/dev`

意思是：

- 当该项目确实需要独立工作台时，可以在自己的 worktree 上做连续开发与验证
- 如果当前只有一条主任务线，而且根工作区足够用，也允许直接在 `main` 上推进，不强制先切到项目 worktree
- 是否需要再合回主干，取决于你是否真的从项目分支 / project worktree（项目工作树）分出过独立演进线

当前推荐口径再往前收一层：

- `aimandala/dev`
  - 作为 `AI Mandala` 默认开发主线
- `relayhub/dev`
  - 作为 `RelayHub` 长期服务器测试分支和内部部署主线
- 其他项目
  - 采用 `<project>/dev` 作为长期开发分支时，也应明确写入各自项目入口文档

再补一条约束：

- `aimandala/dev`、`relayhub/dev`、`research-center/dev`、`content-matrix/dev`、`xinran-jobhunt/dev`
  - 都允许长期存在并高频迭代
  - 但它们是“可用的独立开发台”，不是“必须使用的唯一开发入口”
  - 只有当你真的在这些分支上形成独立演进时，才需要考虑它们与 `main` 的同步策略

原因很简单：

- 单人开发时，`main` 本身可以同时承担“当前施工区”和“当前稳定主线”
- 项目 `dev` 分支只是在你需要单独施工区时才发挥价值

因此不再把“所有项目高频开发都应该离开 `main`”当作默认前提，而是按实际复杂度决定是否分出去。

如果用户已经明确要求采用项目开发分支，任务分支可以从项目开发分支分出，例如：

- `feature/*`
- `fix/*`
- `codex/*`
- `chore/*`

但这条只在用户已经决定采用项目开发分支时成立。

如果任务当前就直接在 `main` 上推进，那么不必为了满足形式额外分出项目线；只有当隔离收益明显大于切换成本时，才建议分支或开 worktree。

注意：即便隔离收益明显，IDE 代理也只能提出建议，不能自行执行切分支或创建 worktree。

### 6.4 服务器 worktree 口径

服务器上的 `/opt/automation/worktrees` 不是“另一个项目目录”，而是：

- automation 节点的隔离执行区

只有符合服务器可写执行语义的任务，才允许落进去。

## 7. 公司级仓库边界

当前需要同时区分 4 种路径语义：

### 7.1 公司主仓路径

例如：

- `mindsync`

表示公司级主工作区和 Monorepo 根。

### 7.2 本地项目 worktree 路径

例如：

- `mindsync-worktrees/...`
- 或后续 runtime worktree 根

表示本地项目独立开发工作台。

## 8. GitHub / CI-CD 使用流程

GitHub Actions 不会识别“你是从哪个 `worktree` 推上去的”。

它只识别：

- `push`
- `pull_request`
- `workflow_dispatch`
- `schedule`
- 对应的 `branch`
- 对应的 `paths`

所以当前正式流程应围绕“分支职责”和“任务风险”设计，而不是围绕“worktree 数量”设计。

在 CI/CD（持续集成 / 持续交付）已经简化为 MVP 版本后，默认口径进一步收束为：

- 单人本地开发优先在 `main` 根工作区推进
- `main` 上的普通提交触发最小必要检查
- 只有服务器自动化、部署、smoke（冒烟验证）、runner 维护、auto-repair（自动修复）这类需要隔离执行的任务，才默认要求进入专门的 execution workspace
- 本地人工完成的普通研发任务，不因为 CI/CD 存在就强制拆出 project worktree 或自动化分支

### 8.1 公司治理 / Monorepo 治理

- 默认基于 `main` 推进
- 适合内容：
  - 公司级治理文档
  - 仓库协作规则
  - Automation 收口
  - 跨项目共享脚本与共享规范
- 完成后直接进入 `main`

### 8.2 AI Mandala

- 当前单人主线开发：
  - 默认可以直接在 `main` 根工作区推进
- 需要长期隔离或并行实验时：
  - 再使用 `aimandala/dev` 或其任务分支推进
- 如果确实使用了项目分支：
  - 任务分支先合回 `aimandala/dev`
  - 阶段性稳定后再由 `aimandala/dev` 合回 `main`
- 正式发布：
  - 由既定发布流程进入 `release`

### 8.3 RelayHub

- 当前单人主线开发：
  - 默认可以直接在 `main` 根工作区推进
- 需要长期服务器测试线、隔离实验或并行任务时：
  - 再使用 `relayhub/dev` 或其任务分支推进
- 内部试用与服务器测试：
  - 如果已经启用 `relayhub/dev`，统一收口到 `relayhub/dev`
  - 如果当前直接基于 `main` 推进，则按项目 runbook 明确从 `main` 部署或验证
- 当前不要求：
  - 先并回 `main` 才允许部署
- 当前也不要求：
  - 为 `RelayHub` 额外拆出仓库级 `release` 轨

### 8.4 分支之间的默认合并同步

当前默认采用“main 优先、项目分支按需回收”的策略：

- `main`
  - 作为单人开发时的默认主线和最小 CI/CD 检查入口
- `项目任务分支 -> 项目开发分支`
  - 只在已经启用项目开发分支时，作为日常收口路径
- `项目开发分支 -> main`
  - 只在项目分支形成独立演进后，作为阶段性、稳定点收口路径
- `main -> 项目开发分支`
  - 不做高频同步
  - 仅在项目明确依赖主干新治理、新共享脚本或分叉过大时回灌
- `main -> release`
  - 当前只保留给 `AI Mandala` 既有发布语义
- `relayhub/dev -> main`
  - 定期但不高频
  - 只在阶段能力稳定后回收

进一步收紧为：

- `research-center/dev -> main`
  - 只回灌已经确认要成为公司长期知识或共享方法的内容
- `content-matrix/dev -> main`
  - 只回灌公司级内容治理规则、正式入口和共享资产结构
- `xinran-jobhunt/dev -> main`
  - 只回灌对其他项目也成立的协作机制、模板或治理规则

默认不要把下列内容为了“保持同步”直接长期高频带回 `main`：

- 单一项目内部试验
- 频繁变化的过程稿
- 只服务某个项目当前阶段的临时脚本
- 还没有形成复用价值的研究草稿或内容草稿

但如果这些工作本来就是在 `main` 上完成的，就不存在额外“带回 main”的动作；此时关键是保持提交小、说明清楚、验证口径明确。

### 8.5 服务器主镜像区 / 巡检区

例如：

- `/opt/automation/app/mindsync`
- `/opt/automation/app/mindsync-heartbeat`

它们的语义不是“默认写入区”，而是：

- 主镜像参考区
- 巡检参考区

### 8.6 服务器隔离执行区

例如：

- `/opt/automation/worktrees`

它的语义是：

- 真正允许服务器写文件的隔离执行工作区

## 9. 提交纪律在这套系统里的位置

这套仓库管理系统不只关心“目录怎么摆”，还关心“改动怎么收口”。

当前统一纪律是：

1. 改完即提交
2. 适用于所有分支、所有本地 `git worktree`
3. 若当前工作区已有他人改动，只提交自己本轮负责文件
4. 不把长期脏工作区当默认工作方式

这条纪律的目的，是避免：

- worktree 越开越多，但没人知道哪个是干净的
- 分支越分越细，但没有稳定收口
- 本地、服务器、自动执行链都遗留半成品改动

自动提交辅助机制和提交边界的正式说明，仍以：

- [company/Git提交与自动提交规范.md](company/Git提交与自动提交规范.md)

为准。

## 10. 与 Paperclip 的关系

这里有一个很容易混淆的点：

`Paperclip` 可以管理 `workspace`，但它不是公司 Git 仓库管理系统本身。

更准确的分工是：

- `MindSync / 公司治理文档`
  - 定义公司级仓库口径
- `Git`
  - 承担真实版本历史、分支、worktree 和提交
- `Paperclip`
  - 承担运行时控制面、任务派发和 workspace 运行态映射

所以当你在面板里看到 workspace 时，不要自动等价成：

- 公司仓库结构已经合理
- execution workspace 一定真的落实
- worktree 一定被正确使用

面板配置只是运行态的一部分，不是全部真相。

## 11. 当前最常见的误区

### 11.1 把历史仓库继续当主入口

如果项目已经正式收束进 `mindsync`，就不应继续把历史独立仓库当默认主线。

### 11.2 把 worktree 当成独立仓库

worktree 是同一仓库的不同工作台，不是新仓库，不应自己发展出一套脱离主仓治理的规则。

### 11.3 把服务器主镜像区当默认写入区

`/opt/automation/app/mindsync` 这类路径不应继续被当成真实自动化写操作的默认落点。

### 11.4 把“开了 workspace”当成“仓库系统已经治理好”

不是。

仓库系统治理好，至少还要包括：

- 真实路径分层清楚
- worktree 语义清楚
- 提交纪律稳定
- 运行时不再漂移
