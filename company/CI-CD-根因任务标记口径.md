# CI/CD 根因任务标记口径

> 状态：current
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-04-17
> source_of_truth：company/CI-CD-根因任务标记口径.md

这份文档用于约束 `root_cause_task: true` 在 `墨予镜` 中的使用边界。

它的目标不是增加一个新的优先级标签，而是避免在“CI/CD / Deploy 只保留最新 3 次”的规则下，把真正仍需追踪的根因任务误当成历史噪音。

## 1. 一句话定义

只有当一条旧任务本身承担“根因跟踪主单”的职责时，才允许标记：

`root_cause_task: true`

否则默认一律保持：

`root_cause_task: false`

## 2. 什么情况可以标 `true`

必须同时尽量满足下面条件中的大多数，而不是只满足一条：

1. 这条任务不是某一次普通 run 的重复失败记录，而是对一类失败的根因承载。
2. 即使后面又产生了新的 run，当前团队仍然需要持续回看这条任务本身。
3. 这条任务里已经或即将沉淀：
   - 根因判断
   - 修复策略
   - 为什么后续 run 只是表象重复
4. 把它移出行动窗口后，会明显损失当前问题定位上下文。
5. 它是“唯一仍未闭环的结构性问题单”，而不是多个重复单中的任意一条。

## 3. 什么情况不应该标 `true`

下面这些情况默认都不应标：

1. 只是较早的一次失败 run。
2. 标题更老、评论更多，但并不是根因主单。
3. 只是因为优先级高、影响大。
4. 只是因为现在还没修完。
5. 同一流水线里已经有更新、更完整、更新鲜的承载任务。

## 4. 当前最适合标 `true` 的任务类型

当前更适合考虑标 `root_cause_task: true` 的，通常只有两类：

1. `CI基础设施异常`
   - 例如 runner、认证、宿主机、环境漂移、共享依赖故障
2. `失败汇总 / 根因汇总`
   - 明确承担多次失败的统一根因归并与后续跟踪

普通单次：

- `CI失败：<workflow> / <branch>`
- `❌ <workflow> · <sha> · <time>`
- `⚠️ deploy-dev · <sha> · <time>`

默认都不应因为“更老”而被升级成根因任务。

## 5. 标记前最小检查清单

在把某条任务改成 `root_cause_task: true` 之前，至少先检查：

1. 这条是不是当前唯一应该长期保留的主单？
2. 最新 3 次窗口里的任务，是否都只是它的重复症状？
3. 是否已经在描述中写出根因判断或明确写明“这里承载根因跟踪”？
4. 如果未来要换成另一条更新的主单，是否会把这个标记撤掉？

如果这四条答不清，就先不要标。

## 6. 推荐动作

当发现一类失败跨多个 run 持续重复时，优先动作不是给某条旧 run 直接打 `root_cause_task: true`，而是：

1. 先判断是否需要新建一条真正的“失败汇总 / 根因跟踪”任务。
2. 让那条汇总任务承担长期追踪职责。
3. 只有在没有更好主单、且现有旧任务已经事实上承担主单职责时，才给旧任务补 `root_cause_task: true`。

## 7. 一句话总结

`root_cause_task: true` 不是“这个任务很重要”，而是“这条任务是旧记录里唯一仍应留在当前窗口中的根因主单”。

## 8. 当前看板示例

下面是基于当前 `墨予镜` 看板状态给出的示例口径。

它们不是自动执行结果，而是用于帮助人工判断“什么像根因主单，什么不像”。

### 8.1 更适合考虑标 `true` 的示例

1. `CI基础设施异常：mindsync-ci-runner / main`
   - 原因：它更像 runner / 权限 / 宿主机 / 共享基础设施故障主单，而不是某一次普通 run 记录
2. `Aimandala-CI 失败汇总 / main`
   - 前提：它已经被当成同一提交下多类失败的统一归并入口，而不是只做一次性汇总展示

### 8.2 当前不建议标 `true` 的示例

下面这些更像普通历史 run，不应因为“更老”或“还没修完”就升级：

- `❌ mindsync-ci-runner · <sha> · <time> · main`
- `CI失败：Workflow-Quality / main`
- `CI失败：Knowledge-CI / main`
- `⚠️ deploy-dev · <sha> · <time> · main`

## 9. 可直接粘贴的描述片段

如果你决定把某条任务明确标成根因主单，可把下面片段补到该任务描述前部。

### 9.1 基础设施根因主单

适用于：

- runner
- 权限
- 宿主机
- 共享环境
- 基础设施链路

推荐片段：

```md
root_cause_task: true

根因主单说明：
- 这条任务承载当前这类 CI/CD 基础设施异常的统一根因跟踪。
- 后续同类 run 失败默认先视为该问题的重复症状，而不是新的独立根因。
- 在基础设施根因完成闭环前，本任务允许例外保留在“最新 3 次”窗口之外。
```

### 9.2 失败汇总 / 根因汇总主单

适用于：

- 失败汇总
- 多 job 归并
- 同一提交下的统一跟踪入口

推荐片段：

```md
root_cause_task: true

根因主单说明：
- 这条任务不是普通历史 run 记录，而是当前这组重复失败的统一跟踪主单。
- 后续同类失败若未出现新的独立根因，默认先回收为本任务的重复症状。
- 在新的主单替代它之前，本任务允许例外保留在“最新 3 次”窗口之外。
```

## 10. 当前建议结论

以下结论用于当前 `墨予镜` 看板窗口，不自动回写运行态，只作为人工操作建议。

### 10.1 建议标 `root_cause_task: true`

1. `CI基础设施异常：mindsync-ci-runner / main`
   - 建议：`标 true`
   - 原因：它明显更接近 runner / 权限 / 基础设施共享故障主单，而不是单次 run 记录
   - 操作建议：优先把“根因主单说明”片段补进描述，再由人工决定是否长期保留

### 10.2 条件性建议标 `root_cause_task: true`

1. `Aimandala-CI 失败汇总 / main`
   - 建议：`条件性标 true`
   - 条件：只有当它继续承担多次失败的统一归并、根因判断和后续跟踪时才标
   - 不满足条件时：保持 `false`，继续把它当普通汇总父任务，不当长期根因主单

### 10.3 当前不建议标 `root_cause_task: true`

下面这些类型当前都不建议标：

- `❌ <workflow> · <sha> · <time> · <branch>`
- `CI失败：<workflow> / <branch>`
- `⚠️ deploy-dev · <sha> · <time> · <branch>`

原因：

- 它们默认只是单次 run 或单次环境失败记录
- 即使影响大，也不自动等于根因主单
- 若要长期保留，应优先新建或指定一个真正的汇总 / 根因任务承接
