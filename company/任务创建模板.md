# 任务创建模板

> 状态：current
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-04-06
> source_of_truth：/Users/xinran/Downloads/dev/mindsync/company/任务创建模板.md

本模板用于 `知行工坊` 在 Paperclip 中创建新任务时的默认写法。

目标是减少三类常见问题：

- 任务类型一开始就模糊
- owner / artifact / 完成标准没写清
- 进入 review 时没写清本次在审什么

## 1. 使用原则

创建任务时，至少应写清：

1. `type:*`
2. `task_class`
3. `execution_route`
4. 所属 `project / goal`
5. 当前 owner 或 owner 约束
6. 预期 artifact
7. `done when`

若进入 `in_review`，再额外写清：

8. `review:*`
9. `review goal`

补充约定：

- `task_class: automation-execution`
  - 表示这条任务属于服务器端可写执行白名单
- `task_class: manual-review-required`
  - 表示这条任务默认需要人工审核，不应走服务器自动提交闭环
- `execution_route: server_automation`
  - 只用于 Automation / CI/CD / deploy / smoke / runner / maintenance 任务
- `execution_route: local_manual_review`
  - 普通研发、产品、UI、文案、业务逻辑和其他需要人工审核的任务默认走这条路径

## 2. Intake 模板

适用：

- 模糊想法
- 参考材料
- 待分诊问题
- 新方向线索

推荐模板：

```md
type:intake
task_class: manual-review-required
execution_route: local_manual_review
project:
goal:
source:

问题 / 输入：
- 

为什么值得看：
- 

当前未知项：
- 

下一步期望：
- 请先完成分诊，判断是否值得升级为 epic

done when:
- 形成明确分诊结论
- 明确是关闭、沉淀，还是升级为 epic
```

## 3. Epic 模板

适用：

- 正式推进的父任务
- 一个阶段目标
- 需要拆分的主题任务

推荐模板：

```md
type:epic
task_class: manual-review-required
execution_route: local_manual_review
project:
goal:
owner:
stage:

任务目标：
- 

本阶段边界：
- 做什么
- 不做什么

计划拆分：
- execution 1:
- execution 2:
- execution 3:

关键 artifact：
- 

风险 / 依赖：
- 

done when:
- 本阶段关键子任务完成
- 已形成阶段性结论或下一阶段计划
```

## 4. Execution 模板

适用：

- 明确 owner、明确产物、可直接开工的子任务

推荐模板：

```md
type:execution
task_class: manual-review-required
execution_route: local_manual_review
project:
goal:
parent:
owner:

任务目标：
- 

输入材料：
- 

预期 artifact：
- 

完成标准：
- 

约束：
- 

done when:
- 达到完成标准
- 产物已提交并可进入 review
```

## 5. Artifact / Review 模板

适用：

- spec 验收
- 报告验收
- 阶段门决策
- 方向审阅

推荐模板：

```md
type:artifact
task_class: manual-review-required
execution_route: local_manual_review
project:
goal:
parent:
owner:
review:deliverable

artifact:
- 

本次 review 在审什么：
- 

通过意味着什么：
- 

不通过时如何处理：
- 

done when:
- review 结论明确
- 已决定是 done、修订，还是进入下一阶段
```

## 6. 三类 review 快速模板

### 6.1 方向审阅

```md
review:direction
review goal:
- 请确认当前拆分与推进方向是否合理
- 此 review 只作用于父任务，不代表子任务验收完成
```

### 6.2 交付物验收

```md
review:deliverable
review goal:
- 请验收当前交付物是否达到阶段完成标准
- 若通过，可关闭当前子任务
```

### 6.3 决策审阅

```md
review:decision
review goal:
- 请作出继续 / 暂停 / 调整方向的决策
- 该结论将决定下一阶段任务创建
```

## 7. CEO / Orchestrator 默认动作

创建任务前，默认先判断：

1. 这是 `intake` 还是正式 `epic`
2. 是否已经足够清晰到可以直接建 `execution`
3. 是否已经有 artifact，因此应直接进入 `artifact-review`

如果答案仍不明确，优先：

- 先建 `intake`
- 或先发起讨论

不要直接把模糊想法建成 `execution`。

## 8. 一句话总结

先写清 `type`，再写清 `artifact` 和 `done when`，最后才改 `status`。

## 9. CI/CD 失败模板

### 9.1 CI / build 失败

推荐模板：

```md
type:execution
task_class: automation-execution
execution_route: server_automation
root_cause_task: false
project:
goal:
owner:

来源：
- workflow:
- job:
- step:
- commit:
- run:

任务目标：
- 恢复对应检查为绿色

输入材料：
- repro command:
- 日志摘要：

预期 artifact：
- 修复 diff / 修复分支 / PR

完成标准：
- 对应检查重新通过
- 根因和修复方式已回写

约束：
- 不直接修改主分支
- 服务器自动提交只允许进入 `automation/aimandala/<task-scope>` 固定自动化分支命名空间
- 若 issue 未 materialize 到 execution workspace，不得继续执行写操作
- 只允许在白名单范围内自动修复
```

补充约定：

- 默认写 `root_cause_task: false`
- 只有当该任务被明确认定为“根因任务”或“唯一仍未闭环的结构性问题”时，才改为 `root_cause_task: true`
- `root_cause_task: true` 的作用不是提高优先级，而是在 CI/CD “只看最新 3 次”的窗口规则下，允许该任务例外保留
- 如果没有这个显式标记，旧的 CI/CD 历史任务默认都会被视为超窗噪音

### 9.2 deploy / smoke 失败

推荐模板：

```md
type:artifact
root_cause_task: false
project:
goal:
owner:
review:deliverable

artifact:
- 环境恢复说明

来源：
- environment:
- workflow:
- step:
- commit:
- run:

本次 review 在审什么：
- 当前 deploy / smoke 风险是否已解除

通过意味着什么：
- 对应环境恢复为可放行状态

不通过时如何处理：
- 保持问题单打开并继续排障

done when:
- 风险已解除并有验证记录
```

补充约定：

- deploy / smoke 问题默认同样遵守“只关注最新 3 次”的窗口规则
- 只有明确承担根因跟踪职责的历史任务，才允许标记 `root_cause_task: true` 并例外保留
