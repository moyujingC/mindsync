# 标签与状态使用说明

> 状态：current
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-04-06
> source_of_truth：/Users/xinran/Downloads/dev/mindsync/company/标签与状态使用说明.md

这份文档说明 `墨予镜` 当前如何在实际运行中使用两类语义标记：

- 任务标签
- 文档状态

它的目标不是重复定义标签本身，而是解释：

1. 它们在系统里由谁来读
2. 它们会如何影响默认动作
3. 它们目前能做到什么，不能做到什么

## 1. 两类语义标记分别是什么

### 1.1 任务标签

任务标签主要包括：

- `type:intake`
- `type:epic`
- `type:execution`
- `type:artifact`
- `review:direction`
- `review:deliverable`
- `review:decision`

它们用于回答：

- 这条任务到底是什么
- 这次 review 到底在审什么

### 1.2 文档状态

文档状态主要包括：

- `draft`
- `in_review`
- `working`
- `current`
- `historical-reference`
- `archived`
- `superseded`

它们用于回答：

- 这份文档现在处于什么生命周期阶段
- 它是否应该被默认读取
- 它是规则、工作稿，还是历史案例

## 2. 系统是如何使用任务标签的

### 2.1 任务标签首先影响“解释方式”

当前阶段，任务标签最重要的作用不是驱动数据库，而是约束人和 agent 对任务的解释。

例如：

- `type:intake`
  - 默认动作应是分诊，而不是直接执行
- `type:epic`
  - 默认动作应是确认边界、拆分子任务
- `type:execution`
  - 默认动作应是确认 owner、artifact 和完成标准
- `type:artifact`
  - 默认动作应是围绕产物验收、沉淀或交接

### 2.2 任务标签会影响 CEO 的默认动作

在 `墨予镜` 中，CEO / Orchestrator 巡检任务时，默认顺序是：

1. 先判断它属于哪种 `type:*`
2. 再判断它是否该挂到某个父任务下
3. 最后才判断是否要改 `status`

这意味着：

- 标签优先于状态解释
- 状态不再独自承担全部语义

### 2.3 任务标签会影响任务创建模板

当前 [任务创建模板.md](/Users/xinran/Downloads/dev/mindsync/company/任务创建模板.md) 已按标签语义分为：

- intake 模板
- epic 模板
- execution 模板
- artifact / review 模板

因此任务标签已经开始影响：

- 新任务如何写
- 该补哪些字段
- 交付物如何定义
- review 目标如何表述

### 2.4 任务标签会影响巡检和整改

当前巡检脚本还主要依赖：

- 顶层 / 非顶层
- owner 有无
- `todo / in_progress / in_review`
- 最近活动时间
- `type:*` 与 `review:*` 标签

也就是说，它虽然还在用“派生语义层”判断问题，但已经开始把标签当成正式治理信号消费。

但一旦任务标签在运行中被稳定补齐，它会进一步提升：

- 待分诊识别更准
- 假进行中识别更准
- `in_review` 的解释更少歧义
- 存量任务整改更少依赖人工猜测

当前已经开始直接暴露的信号包括：

- 打开任务的 `type:*` 分布
- 打开任务的 `review:*` 分布
- 缺少 `type:*` 标签的打开任务
- 缺少 `review:*` 标签的审阅任务
- `review:*` 标签脱离 `in_review` 语境的任务
- 父任务已关闭但子任务仍打开的结构异常
- `activeRun=running` 但长期没有评论或状态回写的执行健康异常

### 2.5 任务标签目前还不能自动做什么

当前它们还没有原生接入到底层任务模型，因此还不能直接：

- 自动阻止错误状态流转
- 自动强制填写某些字段
- 自动驱动 Paperclip UI 原生分栏
- 自动从数据库层定义任务类型

当前阶段，它们首先是：

- 治理语义层
- 模板约束
- 巡检依据
- 解释边界

## 3. 系统是如何使用文档状态的

### 3.1 文档状态首先影响“是否默认读取”

文档状态最直接的作用，是决定它应不应该进入默认入口。

默认理解：

- `current`
  - 这是当前规则、当前入口或当前有效版本
- `draft`
  - 还在形成中，不能默认当硬约束
- `in_review`
  - 正在等待确认，引用时应谨慎
- `working`
  - 正在执行中的操作文档，可用于当前窗口，但不应视为长期规则
- `historical-reference`
  - 只作历史案例或复盘参考，不应默认当前化
- `archived`
  - 已归档，不再作为默认入口
- `superseded`
  - 已被新文档替代，应优先转到新文档

### 3.2 文档状态会影响入口设计

当前公司级入口文件默认只挂：

- `current` 级别的长期规则

而不会把：

- `working`
- `historical-reference`
- `archived`

当成公司级固定必读。

这就是为什么：

- 阶段性整改表被下沉到 `projects/research-center/delivery/`
- 历史纠偏文档被从项目固定必读中降级

### 3.3 文档状态会影响项目级阅读顺序

在项目层，`PROJECT.md` 应优先引用：

- 当前项目定位
- 当前研究结论
- 当前工作区入口

只有在明确需要追溯背景时，才去读：

- `historical-reference`

因此文档状态在项目层的作用，是把：

- “当前定义”
- “阶段性工作稿”
- “历史案例”

三者分开。

## 4. 这套标记目前由谁在使用

当前主要由四类主体在使用：

1. CEO / Orchestrator
   - 用于巡检、分诊和创建任务
2. 项目角色
   - 用于理解当前任务和文档应如何被解释
3. 审计脚本与治理脚本
   - 用于提高判断精度和整改一致性
4. 人工治理过程
   - 用于做文档分层、入口收束和历史材料降级

## 5. 当前阶段的真实边界

一句话说：

这些标签已经在治理层生效，但还没有完全成为 Paperclip 原生功能。

所以它们现在主要改变的是：

- 人的理解方式
- agent 的默认动作
- 巡检脚本的判断依据
- 文档入口的分层边界

而不是：

- 底层模型自动执行

## 5.1 `blocked` 的当前使用口径

当前 `blocked` 不应只表示“先放一放”。

在 `墨予镜` 中，`blocked` 默认应带出明确阻塞原因，例如：

- `infra_missing`
- `credential_missing`
- `workspace_drift`
- `human_action_required`

并且评论中应尽量补齐：

- 当前判断
- 已做动作
- 下一步动作
- 谁来解除阻塞
- 必要时的执行基线：`cwd / branch / sha / dirty`

## 6. 后续如何继续演进

建议按三步推进：

1. 先让标签在所有新任务和新文档中稳定使用
2. 再让巡检和整改默认依赖这些标签
3. 最后再判断是否值得进入 Paperclip 原生字段和 UI

## 7. 一句话总结

当前这套标签的价值，不是“系统自动做了什么”，而是“系统终于不再靠猜来理解任务和文档”。
