## 1. 问题定义

当前 `Paperclip` 面板里的 `project workspace`（项目工作区）主要还是服务器侧路径。

但现在系统已经明确拆成两条执行链：

- `server_automation`
- `local_manual_review`

这意味着同一个项目，通常不应只有一条“服务器 monorepo 路径”。

至少还要能表达：

- 服务器侧项目入口
- 本地 Mac 侧项目入口
- 如有需要，本地独立 `git worktree`（Git 工作树）入口

否则会持续出现两个问题：

1. 面板上看得到项目，但普通任务落不到本地正确目录
2. 项目已经采用独立 worktree 开发，但运行时仍只指向主 checkout

## 2. 目标

为 `墨予镜` 当前的 `Paperclip + Automation Platform + MindSync` 体系建立统一 workspace 分层口径。

本轮目标不是做所有执行器改造，而是先把“项目入口怎么表达”说清楚，并落到可维护的项目配置与工作区约定中。

## 3. 核心判断

### 3.1 一个项目至少区分两类 workspace

- `project workspace`
  - 项目的静态入口
  - 用于告诉运行时“这个项目默认关联哪个代码目录”
- `execution workspace`
  - 某次任务真正执行时 materialize（实例化）出来的目录
  - 可能来自项目主 workspace，也可能来自 `git worktree`

### 3.2 同一个项目可以有多个 project workspace

对当前体系，项目级至少允许并推荐表达：

- `server` workspace
  - 指向 automation 节点上的项目目录
- `local` workspace
  - 指向用户当前 Mac 上的项目目录
- `local worktree` workspace
  - 当项目已采用独立本地 worktree 开发时，指向该 worktree

### 3.3 不是所有 workspace 都应该是 primary

`primaryWorkspace`（主工作区）只代表默认项目入口，不代表所有任务都必须在这里执行。

对当前系统，更合理的理解是：

- `primaryWorkspace`
  - 作为项目默认入口与静态锚点
- `executionWorkspacePolicy`
  - 决定服务器侧任务如何实例化工作区
- `local_manual_review`
  - 由本地执行宿主根据项目约定进入本地 checkout 或本地 worktree

### 3.4 当前优先级高于“多机完美抽象”

本轮先服务真实开发路径，不追求抽象过度。

因此当前推荐口径是：

- 服务器侧：继续保留 server workspace
- 本地普通任务：补 local workspace
- 已明确长期独立开发的项目：直接补 local worktree workspace

## 5. 本轮验收标准

1. 公司级文档明确区分 `project workspace` 与 `execution workspace`
2. 已明确哪些项目需要 `server + local + local worktree`
3. `馨冉求职` 建立独立本地 worktree
4. 远程 `Paperclip` 运行时项目可挂多条 workspace，而不是只剩服务器路径

## 6. 非目标

本轮不直接完成：

- 所有 issue 自动按 host 智能切 workspace
- 本地执行器自动根据项目切换到特定 worktree
- 所有历史项目一次性补齐 execution policy
