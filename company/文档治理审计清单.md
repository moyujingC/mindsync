# 文档治理审计清单

这份清单是 `mindsync` 的长期文档治理工具。

它不记录某一次整改窗口的执行细节，而是用于后续每一轮人工或脚本化盘点时，按同一套问题检查仓库文档状态。

## 1. 使用边界

默认用于审计：

- 仓库根治理文档
- `company/`
- `projects/`
- `shared/` 中承担第一方规则、机制说明、模板职责的文档

默认不审计：

- `node_modules/`
- `.pytest_cache/`
- 构建产物、缓存目录、临时输出目录
- 第三方依赖自带 `README`
- 外部镜像资料与 vendor 文档

## 2. Canonical 审计

逐项检查：

- 是否仍有长期单一真理源带日期文件名
- 是否存在同一主题两份都承担默认入口职责的 canonical 文档
- `source_of_truth` 是否指向无日期 canonical 路径
- 旧日期文件是否已改为 `superseded` stub
- stub 是否明确写明 `superseded_by` 或跳转说明

## 3. 状态审计

逐项检查：

- 当前 `current` 是否过量
- `delivery/` 是否有大量一次性交付记录长期为 `current`
- `qa/` 中是否把验证记录、纸面验证、readiness check 长期保留为 `current`
- `tasks/` 中是否存在多个已完成计划仍保留 `current`
- `handoff/` 中是否存在已完成交接仍保留 `current`
- 周计划、周执行、窗口总结是否已经从 `current` 收紧到 `working` 或 `historical-reference`

## 4. 入口审计

逐项检查：

- `PROJECT.md` 是否明确区分长期 canonical、当前窗口材料、历史资料入口
- 目录 `README.md` 是否明确写出“放什么 / 不放什么”
- 默认阅读顺序是否仍然成立
- 是否还有默认入口直接指向 stub
- 是否还有“当前”“总览”“默认先看”表述误指向日期文件

## 5. 依赖链审计

逐项检查：

- 阶段文档的 `depends_on` 引长期真理源时，是否已切到 canonical
- 正文中的默认母文档链接是否已切到 canonical
- 仍保留的旧路径命中，是否主要来自 stub 元数据或纯历史叙述
- 是否还有阶段文档把旧日期 stub 当成默认依赖

## 6. 目录模板审计

逐项检查：

- `PROJECT.md` 是否覆盖统一模板字段
- 目录 `README.md` 是否覆盖统一模板字段
- canonical 母文档是否写清目标、边界、当前正式口径、同步规则
- 目录入口是否解释了“为什么这里很多日期文件，但不应全部 `current`”

## 7. 批次推进建议

若本轮需要继续整改，默认按以下顺序推进：

1. 先处理最明显的 `current` 误用
2. 再处理默认入口仍指向 stub 的问题
3. 再处理 `depends_on` 与正文默认链接
4. 最后再考虑是否需要升级新的 canonical 文档

## 8. 审计结论记录建议

每轮审计至少记录：

- 本轮审计范围
- 发现的问题类别
- 已修复项
- 暂缓项与原因
- 下一批建议对象
