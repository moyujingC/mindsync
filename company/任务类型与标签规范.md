# 任务类型与标签规范

> 状态：current
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-04-15
> source_of_truth：/Users/xinran/Downloads/dev/mindsync/company/任务类型与标签规范.md

本规范用于把 `墨予镜` 在 Paperclip 中的任务语义显式化。

目标不是给系统增加更多复杂名词，而是让：

- 新建任务时就知道它属于哪一层
- `status` 不再独自承担全部语义
- review 的用途能被显式区分
- CEO 与项目角色能用同一套规则判断下一步动作

## 1. 一条任务默认只回答两个问题

创建任务时，必须能明确回答：

1. 这条任务属于哪一种 `type:*`
2. 如果它进入 review，这次 review 属于哪一种 `review:*`

如果这两个问题答不出来，就不要急着派发执行。

## 2. `type:*` 标签族

### 2.1 `Intake`

含义：

- 原始输入
- 模糊想法
- 参考材料
- 待分诊问题

典型特征：

- 常常是顶层任务
- 可以没有明确 owner
- 不要求立即有完整交付物
- 首要动作是分诊，而不是开工

允许状态：

- `backlog`
- `todo`
- 必要时短暂 `in_review`

默认不建议：

- 长时间处于 `in_progress`
- 直接作为长期执行任务存在

### 2.2 `Epic`

含义：

- 已确认进入正式推进的父任务
- 一个阶段目标或主题任务

典型特征：

- 通常是顶层或高层父任务
- 应明确项目、goal 和阶段目标
- 应拆出多个 `Exec` 子任务

允许状态：

- `todo`
- `in_progress`
- `in_review`

默认要求：

- 必须有清晰的任务边界和阶段目标
- 不应只靠一条模糊描述长期悬挂

### 2.3 `Exec`

含义：

- 可执行子任务
- 已明确 owner、产物和完成标准的工作项

典型特征：

- 通常挂在某个 `Epic` 下
- 应尽量避免模糊描述
- 适合作为 agent 和人实际执行的主工作单元

允许状态：

- `todo`
- `in_progress`
- `in_review`
- `done`

默认要求：

- 有明确 owner
- 有明确产物
- 有明确完成标准

### 2.4 `Art`

含义：

- 围绕阶段产物、handoff、交付件展开的任务

典型特征：

- 重点不是重新探索方向
- 重点是围绕已有产物做整理、沉淀、交接或验收

允许状态：

- `todo`
- `in_progress`
- `in_review`
- `done`

默认要求：

- 产物本身必须已存在或即将形成
- 应明确本次任务对应的 artifact 是什么

## 3. `review:*` 标签族

`review:*` 只在任务进入 review 语境时使用。

### 3.1 `Dir`

适用场景：

- 父任务方向判断
- 拆分是否合理
- 路由是否合理

默认解释：

- 通过表示方向认可
- 不自动表示交付物已验收

### 3.2 `Deliv`

适用场景：

- spec 验收
- 报告验收
- 研究交付物验收

默认解释：

- 通过表示当前交付物可验收
- 若没有额外待批注，可进入收尾

### 3.3 `Decide`

适用场景：

- 是否立项
- 是否进入下一阶段
- 是否采用某个方案

默认解释：

- review 的产物必须是一条明确决策
- 决策后通常需要新建下一阶段任务或回写父任务

## 4. `priority:*` 与 `intervention:*` 标签族

`type:*` 解决“这条任务是什么”，`review:*` 解决“这次在审什么”，但它们还不能回答：

- 这条任务要不要优先看
- 这条任务是否值得人亲自介入

因此在 `墨予镜` 中，额外引入两组运行治理标签。

### 4.1 `priority:*`

默认建议只用三级，避免过度细分：

- `P0`
  - 需要尽快处理
  - 典型场景：主链路不可用、发布阻断、核心 CI/CD 持续红、支付/登录/数据安全风险、会扩大损失的问题
- `P1`
  - 高优先级，但不一定是立即止血
  - 典型场景：重要功能异常、关键质量回退、短期内会影响下一步推进的问题
- `P2`
  - 正常优先级
  - 典型场景：一般缺陷、局部优化、不会立刻阻断推进的问题

默认要求：

- 一条打开任务最多只保留一个 `priority:*`
- 如果没有明确理由，不要滥贴 `p0`
- 任务优先级变化时，应更新标签，而不是只在评论里口头说明

### 4.2 `Human`

适用场景：

- agent 已经定位问题，但无法闭环
- 需要你本人或明确的人类 owner 才能继续推进
- 需要人工做判断、授权、取舍、资源协调或外部操作

典型例子：

- 需要你决定是否回滚、是否放行、是否暂停某条链路
- 需要补凭证、补预算、补账号权限、手动登录第三方平台
- 需要人工判断业务风险、品牌风险、用户沟通口径
- 需要对 deploy / smoke / 发布风险单作出“继续放行 / 暂停放行 / 回滚处理”的人工决策

默认解释：

- 它不是“这条任务很重要”的同义词
- 它表示“这条任务如果没人亲自出手，agent 不应假装自己能闭环”

### 4.3 你当前最关心的筛选组合

如果你想在 Paperclip 看板里筛出“值得我优先亲自干预的问题”，默认看：

- `Human`
- 再叠加 `P0` 或 `P1`

也就是：

- `Human` + `P0`
- `Human` + `P1`

这组组合的含义是：

- 不只是问题重要
- 而且它确实需要你亲自介入，或者至少需要明确的人类动作解除阻塞

对于 `artifact / review` 类任务，再补一条默认判断：

- 若任务已是 `Art`
- 且带 `Deliv`
- 且优先级为 `P0`
- 且 review 本质是在判断“当前是否还能放行 / 是否要回滚 / 是否要继续暴露风险”

则默认也应补：

- `Human`

因为这类任务虽然不一定是“手动修机器”，但它已经进入“必须有人为当前风险负责并作出放行决策”的语境。

## 5. 标签和状态的关系

标签表达“任务是什么”，状态表达“任务现在处于哪个流程信号”。

默认不要用下面方式代替标签：

- 用 `todo` 表示“这其实只是想法”
- 用 `in_review` 表示“这次审的肯定是交付物”
- 用 `in_progress` 表示“虽然没 owner，但先挂着”

推荐理解：

- `type:*` 决定任务语义层级
- `review:*` 决定 review 的作用方式
- `priority:*` 决定处理优先级
- `intervention:*` 决定是否需要人工介入
- `status` 决定当前流程信号

## 6. 推荐组合

### 6.1 常见稳定组合

- `Intake` + `todo`
  - 待分诊输入
- `Epic` + `in_progress`
  - 正在推进的父任务
- `Exec` + `todo`
  - 已准备好开工的执行任务
- `Exec` + `in_progress`
  - 正在执行的子任务
- `Art` + `in_review` + `Deliv`
  - 正在等待验收的交付件
- `Epic` + `in_review` + `Dir`
  - 等待确认方向或拆分的父任务
- `Exec` + `P0` + `Human`
  - 高优先级且必须有人亲自解除阻塞的问题
- `Exec` + `blocked` + `Human`
  - agent 已无法继续推进，等待人类动作

### 6.2 不推荐组合

- `Intake` + 长期 `in_progress`
- 无 `type:*` 的顶层活跃任务
- `in_review` 但没有 `review:*` 或 review 目标说明
- 顶层 `Exec`
  - 除非明确说明为何不能挂到父任务下
- 同一任务同时存在多个 `priority:*`
- 仅贴 `Human`，却不说明谁来解除阻塞、为什么必须人工介入

## 7. 默认创建规则

### 7.1 用户给的是模糊想法

先建：

- `Intake`

不要直接建：

- `Exec`

### 7.2 已确定值得推进，但还需要拆分

先建：

- `Epic`

再从它下面拆：

- `Exec`

### 7.3 已明确 owner、产物和完成标准

直接建：

- `Exec`

## 8. CI/CD 失败的默认路由

### 8.1 CI / build 失败

默认建：

- `Exec`

默认说明应至少写清：

- 对应 workflow / job / step
- commit / run url
- repro command
- 日志摘要

默认优先级建议：

- 会阻断主分支合并、发布或关键验收时：`P0`
- 影响重要流程但存在临时绕路时：`P1`

默认不直接建：

- `Intake`

因为这类问题已经是明确的可执行修复任务。

### 8.2 deploy / smoke 失败

默认建：

- `Art`
- `Deliv`

原因：

- 它不只是“某段代码坏了”
- 更重要的是“当前交付链路是否还能被放行”

因此这类问题的审阅目标应聚焦：

- 风险是否已解除
- 当前环境是否恢复为可放行状态

如果需要你本人决定是否放行、回滚或继续暴露风险，应再补：

- `Human`

默认尤其适用于：

- `Art`
- `Deliv`
- `P0`
- 失败点在 deploy / smoke / 凭证准备 / 生产或 dev 发布入口

### 8.3 runner / 基础设施异常

默认建：

- `Exec`

说明中应显式标记它属于：

- `infra-runner-failure`

因为这类问题通常需要恢复 runner、网络、认证或宿主机服务，而不是直接做交付物验收。

如果 agent 无法自行恢复，且需要人工登录机器、补环境、补凭证或做运行时决策，应补：

- `Human`

### 8.4 已有产物，接下来主要是验收或审议

使用：

- `Art`

并补充：

- `Deliv`
- 或 `Decide`

## 9. 默认命名建议

推荐在描述或首条 comment 中直接写出：

- `type:`
- `review:`
- `priority:`
- `intervention:`
- `artifact:`
- `done when:`

例如：

`Exec`
`P1`
`Human`
`artifact: AI职业能力诊断服务 Spec v0.1`
`done when: 形成可审阅 spec 并进入 deliverable review`

## 10. 执行约束

在 `墨予镜` 中，默认要求是：

1. 顶层原始输入优先标记为 `Intake`
2. 正式推进的主题优先标记为 `Epic`
3. 执行活优先标记为 `Exec`
4. 进入 review 的任务必须写明 `review:*`
5. 没有标签时，CEO 在巡检中应优先补语义，而不是直接推进状态
6. 需要人工解除阻塞时，应补 `Human`
7. 明显有先后轻重时，应补一个且仅一个 `priority:*`

## 11. 一句话总结

`type:*` 解决“这条任务到底是什么”，`review:*` 解决“这次 review 到底在审什么”，`priority:*` 与 `intervention:*` 解决“现在该不该优先亲自介入”。
