# 任务类型与标签规范

> 状态：current
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-04-06
> source_of_truth：/Users/xinran/Downloads/dev/mindsync/company/任务类型与标签规范.md

本规范用于把 `墨予镜` 在 Paperclip 中的任务语义显式化。

目标不是给系统增加更多复杂名词，而是让：

- 新建任务时就知道它属于哪一层
- `status` 不再独自承担全部语义
- review 的用途能被显式区分
- CEO 与项目角色能用同一套规则判断下一步动作

## 1. 一条任务默认只回答两个问题

创建任务时，必须能明确回答：

1. 这条任务属于哪一种 `type:*`
2. 如果它进入 review，这次 review 属于哪一种 `review:*`

如果这两个问题答不出来，就不要急着派发执行。

## 2. `type:*` 标签族

### 2.1 `type:intake`

含义：

- 原始输入
- 模糊想法
- 参考材料
- 待分诊问题

典型特征：

- 常常是顶层任务
- 可以没有明确 owner
- 不要求立即有完整交付物
- 首要动作是分诊，而不是开工

允许状态：

- `backlog`
- `todo`
- 必要时短暂 `in_review`

默认不建议：

- 长时间处于 `in_progress`
- 直接作为长期执行任务存在

### 2.2 `type:epic`

含义：

- 已确认进入正式推进的父任务
- 一个阶段目标或主题任务

典型特征：

- 通常是顶层或高层父任务
- 应明确项目、goal 和阶段目标
- 应拆出多个 `type:execution` 子任务

允许状态：

- `todo`
- `in_progress`
- `in_review`

默认要求：

- 必须有清晰的任务边界和阶段目标
- 不应只靠一条模糊描述长期悬挂

### 2.3 `type:execution`

含义：

- 可执行子任务
- 已明确 owner、产物和完成标准的工作项

典型特征：

- 通常挂在某个 `type:epic` 下
- 应尽量避免模糊描述
- 适合作为 agent 和人实际执行的主工作单元

允许状态：

- `todo`
- `in_progress`
- `in_review`
- `done`

默认要求：

- 有明确 owner
- 有明确产物
- 有明确完成标准

### 2.4 `type:artifact`

含义：

- 围绕阶段产物、handoff、交付件展开的任务

典型特征：

- 重点不是重新探索方向
- 重点是围绕已有产物做整理、沉淀、交接或验收

允许状态：

- `todo`
- `in_progress`
- `in_review`
- `done`

默认要求：

- 产物本身必须已存在或即将形成
- 应明确本次任务对应的 artifact 是什么

## 3. `review:*` 标签族

`review:*` 只在任务进入 review 语境时使用。

### 3.1 `review:direction`

适用场景：

- 父任务方向判断
- 拆分是否合理
- 路由是否合理

默认解释：

- 通过表示方向认可
- 不自动表示交付物已验收

### 3.2 `review:deliverable`

适用场景：

- spec 验收
- 报告验收
- 研究交付物验收

默认解释：

- 通过表示当前交付物可验收
- 若没有额外待批注，可进入收尾

### 3.3 `review:decision`

适用场景：

- 是否立项
- 是否进入下一阶段
- 是否采用某个方案

默认解释：

- review 的产物必须是一条明确决策
- 决策后通常需要新建下一阶段任务或回写父任务

## 4. 标签和状态的关系

标签表达“任务是什么”，状态表达“任务现在处于哪个流程信号”。

默认不要用下面方式代替标签：

- 用 `todo` 表示“这其实只是想法”
- 用 `in_review` 表示“这次审的肯定是交付物”
- 用 `in_progress` 表示“虽然没 owner，但先挂着”

推荐理解：

- `type:*` 决定任务语义层级
- `review:*` 决定 review 的作用方式
- `status` 决定当前流程信号

## 5. 推荐组合

### 5.1 常见稳定组合

- `type:intake` + `todo`
  - 待分诊输入
- `type:epic` + `in_progress`
  - 正在推进的父任务
- `type:execution` + `todo`
  - 已准备好开工的执行任务
- `type:execution` + `in_progress`
  - 正在执行的子任务
- `type:artifact` + `in_review` + `review:deliverable`
  - 正在等待验收的交付件
- `type:epic` + `in_review` + `review:direction`
  - 等待确认方向或拆分的父任务

### 5.2 不推荐组合

- `type:intake` + 长期 `in_progress`
- 无 `type:*` 的顶层活跃任务
- `in_review` 但没有 `review:*` 或 review 目标说明
- 顶层 `type:execution`
  - 除非明确说明为何不能挂到父任务下

## 6. 默认创建规则

### 6.1 用户给的是模糊想法

先建：

- `type:intake`

不要直接建：

- `type:execution`

### 6.2 已确定值得推进，但还需要拆分

先建：

- `type:epic`

再从它下面拆：

- `type:execution`

### 6.3 已明确 owner、产物和完成标准

直接建：

- `type:execution`

## 7. CI/CD 失败的默认路由

### 7.1 CI / build 失败

默认建：

- `type:execution`

默认说明应至少写清：

- 对应 workflow / job / step
- commit / run url
- repro command
- 日志摘要

默认不直接建：

- `type:intake`

因为这类问题已经是明确的可执行修复任务。

### 7.2 deploy / smoke 失败

默认建：

- `type:artifact`
- `review:deliverable`

原因：

- 它不只是“某段代码坏了”
- 更重要的是“当前交付链路是否还能被放行”

因此这类问题的审阅目标应聚焦：

- 风险是否已解除
- 当前环境是否恢复为可放行状态

### 7.3 runner / 基础设施异常

默认建：

- `type:execution`

说明中应显式标记它属于：

- `infra-runner-failure`

因为这类问题通常需要恢复 runner、网络、认证或宿主机服务，而不是直接做交付物验收。

### 6.4 已有产物，接下来主要是验收或审议

使用：

- `type:artifact`

并补充：

- `review:deliverable`
- 或 `review:decision`

## 7. 默认命名建议

推荐在描述或首条 comment 中直接写出：

- `type:`
- `review:`
- `artifact:`
- `done when:`

例如：

`type:execution`
`artifact: AI职业能力诊断服务 Spec v0.1`
`done when: 形成可审阅 spec 并进入 deliverable review`

## 8. 执行约束

在 `墨予镜` 中，默认要求是：

1. 顶层原始输入优先标记为 `type:intake`
2. 正式推进的主题优先标记为 `type:epic`
3. 执行活优先标记为 `type:execution`
4. 进入 review 的任务必须写明 `review:*`
5. 没有标签时，CEO 在巡检中应优先补语义，而不是直接推进状态

## 9. 一句话总结

`type:*` 解决“这条任务到底是什么”，`review:*` 解决“这次 review 到底在审什么”。
