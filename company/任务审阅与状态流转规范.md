# 任务审阅与状态流转规范

> 状态：current
> 最后更新：2026-04-03
> 适用范围：`墨予镜` 在 Paperclip 中的日常使用

这份文档沉淀的是一次真实使用中暴露出来的经验：

- `in_review` 不是单一语义
- 父任务与子任务的审阅目标不同
- “通过”不等于“立即关单”
- 没有写清 review 意图时，用户和 agent 都容易误判

因此，这份文档的目标不是解释 Paperclip 的底层实现，而是给 `墨予镜` 一套更稳的使用约定。

## 1. 先记住一个核心原则

在 `墨予镜` 内部，任务状态只是流程信号，不直接代表语义本体。

真正重要的是三件事：

1. 当前这次 review 在审什么
2. 用户的反馈作用于哪个任务
3. 这个任务在什么条件下才允许进入 `done`

如果这三件事没有写清楚，就不要默认靠状态名去猜。

## 2. `in_review` 的三种语义

### 2.1 方向审阅

典型发生在父任务。

它的意思是：

- 当前的任务拆分是否合理
- 当前路由给谁是否合理
- 当前阶段推进方向是否正确

用户在这里回复“通过”，通常表达的是：

- 方向认可
- 拆分认可
- 可以继续往下推进

它默认**不表示**子任务已验收完成。

### 2.2 交付物验收

典型发生在子任务。

它的意思是：

- 这份报告是否合格
- 这份 spec 是否成立
- 这次研究 / 设计 / 实现是否达到当前阶段交付标准

用户在这里回复“通过”，才默认表示：

- 这个子任务交付物通过验收
- 该任务可以考虑收尾

### 2.3 决策审阅

典型发生在立项、重大取舍、阶段门判断。

它的意思是：

- 是否进入下一阶段
- 是否正式立项
- 是否采用某个方向

这类 review 的产物通常应该是：

- 一条明确决策
- 一条下一步指令
- 一个新的阶段任务或计划

## 3. `通过` 的默认解释规则

### 3.1 在父任务里说“通过”

默认只表示：

- 当前父任务语境下的方向、拆分、判断被认可

默认不表示：

- 所有关联子任务都完成
- 所有子任务都可以自动切到 `done`
- agent 可以代替用户关闭其他 review 中任务

### 3.2 在子任务里说“通过”

默认表示：

- 当前子任务交付物验收通过

但即便如此，若用户明确还要继续补批注、批改或追加指示，也不应立即关闭任务，而应先保留在 review 或转入一个明确的“待修订 / 待落实”状态语境。

## 4. 父任务与子任务的联动规则

### 4.1 允许的联动

1. 子任务完成后，父任务可以继续推进。
2. 父任务进入下一阶段时，可以创建新的后续子任务。
3. 父任务可以引用子任务结论作为决策依据。

### 4.2 不允许的联动

1. 用户在父任务里的反馈，默认不得直接关闭子任务。
2. agent 在处理父任务 heartbeat 时，不得自行替用户完成子任务验收。
3. 当子任务已经明确交回用户 review 时，其他 agent 不应擅自将其改为 `done`。

## 5. 在 `墨予镜` 中的推荐写法

为了减少误判，进入 `in_review` 时必须在评论或描述里明确写出 review 目标。

推荐直接写成下面三类模板之一。

### 5.1 方向审阅模板

`请审阅当前拆分方向是否合理；此 review 只作用于父任务，不代表子任务验收完成。`

### 5.2 交付物验收模板

`请验收本任务交付物是否达到当前阶段完成标准；若通过，可关闭本子任务。`

### 5.3 决策审阅模板

`请对当前阶段作出继续 / 暂停 / 调整方向的决策；该 review 结论将决定下一阶段任务创建。`

## 6. 用户实际操作建议

### 6.1 当 inbox 里同时有多个 `in_review`

不要只看状态名，先确认：

1. 这条是在审方向，还是在验收交付物
2. 这条是父任务，还是子任务
3. 你的回复是否只想影响当前任务

如果系统界面没有说明，就在回复里主动限定作用范围。

例如：

- `我认可这个拆分方向，仅表示当前父任务可以继续推进，不代表相关子任务已验收完成。`
- `我认可这份研究报告，当前交付物可视为通过。`

### 6.2 当你还想继续补批注

不要只写“通过”。

应直接写明：

- `原则上通过，但我还会补充批注，请先不要关单。`
- `报告通过验收，但请保留 review，等我把修改指示补完。`

## 7. Agent 使用约束

在 `墨予镜` 内部，对 agent 的默认要求是：

1. 不替用户扩展 review 作用范围。
2. 不把父任务认可自动解释成子任务完结。
3. 当 review 意图不清楚时，优先保守推进，不主动收束其他任务。
4. 若必须推进，先产出明确 artifact，再交由用户确认。

## 7.1 与 Paperclip execution policy 的当前映射原则

当前 `墨予镜` 已知上游存在 execution policy（执行审批策略）与多阶段 signoff（签核）能力，但本地默认仍以文档治理语义为主。

当前原则口径如下：

1. `review:direction`
   - 仍主要是本地治理语义
   - 暂不直接下沉成上游强审批流
2. `review:deliverable`
   - 是未来最值得映射 execution policy 的一类
   - 但当前仍先由本地 review 说明、验收口径和 handoff 控制
3. `review:decision`
   - 也是未来最值得映射 execution policy 的一类
   - 尤其适合“是否进入下一阶段”这类需要显式放行的场景
4. 只有出现下面情况，才值得进一步评估是否下沉到上游原生审批：
   - 跨阶段放行
   - 跨角色签核
   - 需要系统强约束阻断，而不是仅靠文档约定
5. 当前默认不做的事：
   - 不把所有 `in_review` 直接解释为应启用 execution policy
   - 不把本地 review 语义一次性迁成上游审批流
   - 不在没有正式 spec 前直接改造成多阶段审批链

## 8. `done` 的使用条件

一个任务只有在以下条件满足时，才建议进入 `done`：

1. 当前任务自己的 review 目标已经被满足。
2. 当前任务自己的交付物已经被明确验收。
3. 不存在用户已声明但尚未补充的批注、修订或下一步指示。

如果只是“方向认可”，更常见的正确动作是：

- 父任务继续 `in_progress`
- 子任务维持原状
- 或创建下一阶段任务

而不是直接把关联任务批量关单。

## 8.1 自动执行多次失败后的转人工

当任务由 `Engineer` 这类自动执行型 Agent 持续推进时，若出现“反复尝试但仍未突破”的情况，不应无限续跑。

当前推荐口径：

1. 连续失败达到 `3` 次，或累计运行超过 `90` 分钟，应优先考虑停止自动重试。
2. 若失败原因属于 `infra / auth / env / dependency / external service` 这类公共卡点，应直接解释为更适合人工介入，而不是继续追加模型尝试。
3. 进入人工接管时，任务更适合转为 `blocked`，而不是继续停留在模糊的 `in_progress`。
4. 转人工时，应显式附带：
   - 已尝试次数
   - 最后一次失败摘要
   - 建议用户先清除的公共卡点
5. 自动执行型 Agent 不应在已明确需要人工清障后继续燃烧 token。

这条规则的目标不是降低自动化比例，而是避免系统在“已知卡住”的主题上反复消耗预算。

## 9. 这份规范是怎么来的

本规范来自一次真实任务流转中的问题复盘：

- 用户在父任务里表达“通过”，本意是认可任务拆分方向
- agent 却在处理父任务时自行关闭了仍处于审阅中的子任务

后续已经分别在 Paperclip 开源项目中作为：

- 产品语义问题
- 审计 / 权限修复问题

进行追踪。

因此，这份文档既是使用规范，也是 `墨予镜` 当前阶段对 Paperclip 的本地防误用约束。
