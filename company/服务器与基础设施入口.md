这份文档是 `知行工坊` 公司层面的基础设施入口。

它的职责不是取代项目级 runbook，而是提供一个稳定的总入口，让任何 Agent 在需要登录服务器、核对运行时宿主机、定位 runner / Paperclip / 部署节点时，先知道应该去哪里找、先连哪台机器。

具体服务细节、环境变量、部署命令与验收口径，仍以对应项目的项目级运维文档为准。

相关运行时文档：

- [Paperclip-Agent-模型配置总表.md](company/Paperclip-Agent-模型配置总表.md)
  - 用于查看当前各 Agent 的运行时模型、adapter、base URL、鉴权方式、面板状态解读，以及 `Engineer` 的成本控制与转人工口径
- [company/projects/Automation/PROJECT.md](company/projects/Automation/PROJECT.md)
  - 用于查看公司级 `Automation Platform` 的能力边界，以及 `server_automation` 与 `local_manual_review` 两条执行链的正式口径

## 1. 使用原则

1. 先在这里确认“是哪一类机器、属于哪个项目、主入口文档是哪份”
2. 再进入对应项目 runbook 执行登录、部署、排障或验证
3. 不要把真实服务器信息只留在聊天记录、shell 历史或临时笔记里
4. 当服务器地址、登录方式、宿主角色发生变化时，应同时更新这里和对应项目 runbook
5. 对 automation 节点，公网 SSH key 是默认主入口；若失效，应按运维 bug 处理，而不是把 Tailscale SSH 升格为主路径

  - 不依赖交互式 HTTPS token
  - 当前目录分层应理解为：
    - `/opt/automation/app/mindsync`

    - `/opt/automation/app/mindsync-heartbeat`

  - Paperclip UI/API
  - Paperclip 主执行宿主
  - `mindsync-ci` self-hosted runner
  - `ci / deploy / nightly-smoke / auto-repair`
  - heartbeat 与 maintenance timer
- 当前运行语义：
  - `control plane host`
    - 当前继续是 automation 节点
  - `server execution host`
    - 当前继续是 automation 节点
    - 只承接 `server_automation`
  - `local execution host`
    - 对普通任务当前正式路径，固定是用户当前这台 Mac
  - 因此当前 automation 节点不是“只做调度”的控制面，但也不再应被默认解释为普通任务的唯一 `*_local` 宿主
  - 当前普通任务自动在 Mac 上跑的主链由本地执行器 + `launchd` 承接；automation 节点不再代跑这些本地 CLI
  - 但这不等于允许所有执行链共享同一个可写 checkout
    - heartbeat / maintenance 默认应使用巡检区
    - 会写文件的 agent / auto-repair 默认应进入隔离执行区
  - `一镜一梳` 当前默认 project policy 应固定为：
    - `executionWorkspacePolicy.enabled = true`
    - `defaultMode = isolated_workspace`
    - `allowIssueOverride = true`
    - `workspaceStrategy.type = git_worktree`
    - `workspaceStrategy.baseRef = main`
    - `workspaceStrategy.branchTemplate = {{issue.identifier}}-{{slug}}`
    - `workspaceStrategy.worktreeParentDir = /opt/automation/worktrees`
- 当前 comment 执行来源口径：
  - Paperclip 或 CI/CD 链路回写 comment 时，应显式带出 `adapter` 与 `host`
  - `host`
    - 默认表示真实执行宿主
    - 若为服务器侧执行链，推荐固定写法：`automation@150.158.9.95`
    - 若为普通任务本地单机试点，应明确写为用户当前 Mac 宿主，而不是继续伪装成 automation 服务器
  - `adapter`
    - 若为 Paperclip 服务器侧 agent，使用真实 adapter 名，如 `codex_local` / `claude_local` / `pi_local` / `hermes_local`
    - 若为 GitHub Actions 落在本机 self-hosted runner 上的执行链，使用稳定执行链名，而不是伪装成 Paperclip adapter
    - 当前固定命名：
      - `github-actions/self-hosted-runner:ci`
      - `github-actions/self-hosted-runner:deploy`
      - `github-actions/self-hosted-runner:nightly-smoke`
      - `github-actions/self-hosted-runner:auto-repair`
      - `github-actions/self-hosted-runner:runner-heartbeat`
- 当前明确口径：
  - `Idea Clarifier`
    - 主链路：`pi_local`
    - 兜底链路：`claude_local`
  - `Engineer / Test / QA`
    - 服务器侧 `codex_local` 已固定走 RelayHub
    - 当前客户端落地配置位置：
      - `/paperclip/.codex/config.toml`
      - `/paperclip/.codex/auth.json`
    - 当前正式入口：
      - `entry-paperclip-codex-local-server`
      - `relayhub-entry-paperclip-codex-local-server`
    - 当前正式基地址：
      - `https://relayhub.jingshu.cc/claude/v1`
    - Relay token 来源：
      - RelayHub 控制面的 `relay-config.json`
      - 不再把 token 写死在旧 console、临时 shell 或聊天记录里
  - `PaperClipAI *_local` 入口治理口径
    - 当前已按 adapter（适配器）收口成单入口
    - `claude_local / codex_local / pi_local / hermes_local` 各只保留一条正式 RelayHub entry
    - entry 名字里保留的 `server` 只是 canonical（规范）命名，不再表达 Mac / Server 可独立控模
    - 旧 `*-mac` alias 只保留短期兼容，不再作为控制面正式公开对象
  - 若服务器侧 `pi_local` 环境异常，不应只让 run 停在 failed；应自动切到 `claude_local` 保证任务继续推进
- 当前额外安全边界：
  - `codex_local` 不应默认继承非 Paperclip 显式批准的外部 connector（例如用户在其他 OpenAI / ChatGPT 应用界面里已连接的读写能力）
  - 若 automation 宿主或本地执行宿主无法技术上完全隔离这类外部已连接能力，应按高风险执行边界处理
  - 对邮箱、消息发送、外部系统写入这类 connector，当前默认不视为公司正式可用能力
  - 后续若要正式启用，应先在治理文档中单独立项说明，而不是先在运行时默认放开

    - 不应把 `Idea Clarifier` 或 `pi_local` 迁移到阿里云节点执行

## 4. 当前治理要求

1. 新增服务器时，必须先把入口补到本文件，再补项目 runbook
2. 真实 SSH 入口不得只写成 `<host>` 占位符
3. 如果某台机器使用专属 SSH key，应在公司层入口明确写出 key 路径
4. 如果某台机器同时有公网入口和 Tailscale 入口，应两者都记录，但标明推荐口径
