# 研发原则

> 状态：current
> 最后更新：2026-04-02

这份文档定义 `知行工坊` 的共享研发原则。

它不是某一个 Agent 的私有说明，而是公司级约束。所有涉及产品、研究、架构、实现、验证和文档治理的角色，都应遵守这里的原则。

## 1. 中文优先

默认工作语言为中文。

要求：

- 公司文档优先使用中文
- 知识沉淀优先使用中文
- 内容素材优先使用中文
- 引用源码、论文、官方文档时可保留英文原文

## 2. Harness Engineering

工程活动必须追求：

- 结构清晰
- 可维护
- 可验证
- 边界明确
- 长期可演进

这意味着：

- 不允许重要实现长期停留在临时拼凑状态
- 不允许核心系统依赖隐含约定
- 不允许架构决策只存在聊天记录里

## 3. SDD

Spec-Driven Development。

任何重要工作默认遵循：

1. 先定义问题
2. 再写 spec
3. 再拆 implementation plan
4. 再进入执行

没有 spec 的重要工作，不直接进入实现。

## 4. TDD

Test-Driven Development。

进入实现阶段前，必须先明确：

- 行为预期
- 验收标准
- 测试方式
- 边界情况

测试不一定都表现为自动化测试文件，但必须有清晰的验证机制。

## 5. Docs As System

文档不是附属品，而是公司系统的一部分。

要求：

- 每类信息有唯一权威位置
- 每次重要 handoff 都要产生结构化产物
- 研究、决策、spec、交付、复盘都可追溯
- 知识库由专人治理，但全公司共同供稿

## 6. Hypothesis Continuity

跨角色协作时，最容易丢失的不是文件，而是“当前到底在继承哪组判断”。

因此默认要求：

- 下游角色必须显式继承上游已有假设、分析和未决问题
- 下游角色可以反对上游结论，但必须写出反对依据与反证材料
- 不允许通过省略背景、偷换任务层级或静默改写范围来推进
- 局部实验不自动等于全局重定义

这条原则的目标不是压制不同意见，而是要求不同意见以可追溯的形式进入系统。

## 7. 共享原则的使用方式

这些原则不应该被每个 Agent 大段重复粘贴。

推荐做法：

- Agent 只在自己的 `AGENTS.md` 中引用这些原则
- 需要更强约束的角色，再补充与自己职责直接相关的解释
- 如果原则更新，以本文件为准

## 8. 审阅与状态流转

在 `知行工坊` 中，Paperclip 里的任务状态只能作为流程信号使用，不能代替语义建模。

尤其是：

- `in_review` 可能表示方向审阅，也可能表示交付物验收
- 父任务里的“通过”默认不等于子任务可以自动 `done`
- 当 review 目标不清楚时，应优先保守推进，不扩大反馈作用范围

具体使用约定见：

- [任务审阅与状态流转规范](../company/任务审阅与状态流转规范.md)

## 9. CI/CD 与自动修复边界

在 `知行工坊` 中，CI/CD 默认也受 `Harness Engineering + SDD + TDD` 约束。

当前 `Engineer` 与 `Test / QA` 在这条链路中的职责边界，见：

- [CI/CD 角色分工说明](../company/CI-CD-角色分工说明.md)

这意味着：

- CI 不是“跑个命令就算完”，而是项目质量门的一部分
- deploy / smoke 失败要进入正式任务系统，而不是只停留在日志里
- 自动修复只允许处理可重放、可验证、可回滚的问题

默认允许自动修复的范围：

- 单测失败
- 类型检查失败
- 构建失败
- 确定性脚本校验失败

默认不允许自动修复的范围：

- 生产部署失败
- 线上数据异常
- 运行时告警但根因不清
- 需要改服务器现场或密钥配置的故障

当不满足自动修复条件时，默认动作是：

- 建 bug / 风险任务
- 回写复现命令、日志摘要、建议 owner
- 等待人工处理或下一轮明确 handoff

## 10. Git 提交纪律

在 `知行工坊` 中，默认采用“改完即提交”。

这里的意思是：

- 只要当前角色已经完成一个可描述、可验证、可交接的最小改动闭环，就应立即提交
- 该规则适用于所有分支、所有 `git worktree`（Git 独立工作树）
- 不把“先留在工作区，等用户提醒后再提交”当作默认流程

执行要求：

1. 提交应尽量保持单一主题，避免把无关改动混入同一 commit
2. 若工作区已有他人未提交改动，只提交本轮负责文件，不擅自替他人收口
3. 若代理未手写 commit message，可使用仓库内自动生成最小提交说明的机制
4. 修改完成但未提交，默认视为交付未完成
