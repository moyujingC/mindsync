# 研发原则

> 状态：current
> 最后更新：2026-04-02

这份文档定义 `墨予镜` 的共享研发原则。

它不是某一个 Agent 的私有说明，而是公司级约束。所有涉及产品、研究、架构、实现、验证和文档治理的角色，都应遵守这里的原则。

## 1. 中文优先

默认工作语言为中文。

要求：

- 公司文档优先使用中文
- 知识沉淀优先使用中文
- 内容素材优先使用中文
- 引用源码、论文、官方文档时可保留英文原文

## 2. Harness Engineering

工程活动必须追求：

- 结构清晰
- 可维护
- 可验证
- 边界明确
- 长期可演进

这意味着：

- 不允许重要实现长期停留在临时拼凑状态
- 不允许核心系统依赖隐含约定
- 不允许架构决策只存在聊天记录里

## 3. SDD

Spec-Driven Development。

任何重要工作默认遵循：

1. 先定义问题
2. 再写 spec
3. 再拆 implementation plan
4. 再进入执行

没有 spec 的重要工作，不直接进入实现。

## 4. TDD

Test-Driven Development。

进入实现阶段前，必须先明确：

- 行为预期
- 验收标准
- 测试方式
- 边界情况

测试不一定都表现为自动化测试文件，但必须有清晰的验证机制。

## 5. Docs As System

文档不是附属品，而是公司系统的一部分。

要求：

- 每类信息有唯一权威位置
- 每次重要 handoff 都要产生结构化产物
- 研究、决策、spec、交付、复盘都可追溯
- 知识库由专人治理，但全公司共同供稿

## 6. Hypothesis Continuity

跨角色协作时，最容易丢失的不是文件，而是“当前到底在继承哪组判断”。

因此默认要求：

- 下游角色必须显式继承上游已有假设、分析和未决问题
- 下游角色可以反对上游结论，但必须写出反对依据与反证材料
- 不允许通过省略背景、偷换任务层级或静默改写范围来推进
- 局部实验不自动等于全局重定义

这条原则的目标不是压制不同意见，而是要求不同意见以可追溯的形式进入系统。

## 7. 共享原则的使用方式

这些原则不应该被每个 Agent 大段重复粘贴。

推荐做法：

- Agent 只在自己的 `AGENTS.md` 中引用这些原则
- 需要更强约束的角色，再补充与自己职责直接相关的解释
- 如果原则更新，以本文件为准

## 8. 审阅与状态流转

在 `墨予镜` 中，Paperclip 里的任务状态只能作为流程信号使用，不能代替语义建模。

尤其是：

- `in_review` 可能表示方向审阅，也可能表示交付物验收
- 父任务里的“通过”默认不等于子任务可以自动 `done`
- 当 review 目标不清楚时，应优先保守推进，不扩大反馈作用范围
