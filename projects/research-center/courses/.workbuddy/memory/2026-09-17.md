**已确定的框架结论**

- 每个节点应有 2–3 条出边：正常 / 可修复（回退边：重试或回滚）/ 不可修复（交给人）。
- 回退边必须有终止条件（次数、token/成本预算、时间），无守卫即为死循环。

**用户给出的 signal 节点初稿**

**诊断（待用户确认后定稿）**
1. 阻塞性歧义：三圈是人标注还是模型自己找？决定该节点是「识别」还是「检测」。
2. 输出是自然语言描述而非可解析契约 → 下游接不住，且无法自动校验 → 这正是「失败条件想不出来」的根因。
3. 建议结构化：Ring{index,cx,cy,r_inner,r_outer}（归一化 0–1）、Block{ring,angle_start,angle_end,color_hex,shape,area_ratio}；断言：circles==3 / r_outer 递增 / 单圈 Σarea_ratio∈[0.7,1.0]。
4. 技术建议：split 成 1a（OpenCV 提同心圆与颜色，确定性、无重试）+ 1b（LLM 做语义描述，有重试）。几何与颜色不交给 LLM 猜。
5. 重试陷阱：同图同 prompt 重跑易得同一错误答案，重试须换策略或换模型层。

### FDE 原型的定义 + 不可逆性复盘

**FDE 原型 = 窄而深的纵向切片**：功能广度约 5%（1 张图、1 个场景），但 100% 贯穿到用户看到。代码是写来扔的（硬编码、无抽象、无测试），价值在于它产出的「规格知识」，不在于代码本身。
- 判据：必须用真实数据 + 真实用户在场，否则只是 demo，不是原型。
- 推论：我们的第①步（d191 跑通、自己看）只是 demo；第②步（真实交付 3 单）才使它成为 FDE 原型。

**「工程质量/可替换性/防泄漏事后补不回来」这句说过头了，逐条修正**：
- 可替换性：接口补起来便宜，真正不可移植的是「prompt 针对特定模型的脾气调过」（格式、啰嗦程度、JSON 习惯）。抽象层可补，prompt 调校不可移植。
- 工程质量/证据链：基本补不回来。证据门要求生成时就把 observations 落盘并带 ID；事后无法给三周前的自由文本补 evidence_id，且旧模型输出不可复现（版本漂移、temperature、prompt 已改）。
- 防泄漏与避免锚定：**完全不可逆**。泄漏是事件不是属性——金标准一旦进过 prompt，该案例永久丧失评测资格；人一旦看过系统输出，判断就被锚定，无法「不知道」。

**结论（两版计划不互斥）**：真正不可逆的只有「泄漏 + 锚定」，而防护成本极低——约 1 小时：① 在跑系统之前，先独立写下对 d191 的预判（五行强弱 + 每圈主色 + 动势 + 反证，一页纸，单独存，不进任何 prompt）；② d191 金标准永不写入生成上下文。做完这两件事即可用重排版顺序，不可逆风险清零。

### 状态机三层职责划分（已与他对齐，写代码时照此分）

- **工作流代码 = 状态机**：节点、边、转移条件（含失败边与回退边）全归它。
- **Provider = 节点内的重试自环**，只有两个出口：成功 / 最终失败。它不知道别的节点存在。

**判据（不是看报错类型，是看结果）**：同样的请求原样再发一次，结果会不会变好？
- 会 → Provider 重试：超时、429 限流、5xx、连接中断、偶发 JSON 截断。
- 不会 → 工作流的失败边：标记线被当证据、漏圈、颜色判错、越界诊断表达、引用不存在的 evidence_id。

**灰色地带（真 bug 藏这）**：输出被 max_tokens 截断（表面像传输层，根因是「要太多」，须工作流拆请求）；模型拒答（重试一次，不行则换措辞＝换策略，属工作流）；持续 429（须工作流排队降速）。

**temperature 陷阱**：语义失败重试偶尔也能碰对，会让人误以为「重试有效」，实际只是概率且无法分辨哪次真对——绝不靠重试解决语义问题。

**本项目的关键结论**：曼陀罗解读里 99% 的失败是语义失败（右列），Provider 的 3 次重试几乎没用；真正要花力气的是工作流的失败边 + 校验节点 + 重试时换策略。

### LangGraph「黑盒」到底是什么 + 自研 vs 现成（他追问课程观点）

**黑盒的准确定义（两层，别混）**：
1. 不是「源码看不懂」（开源，随便读），是**控制流所有权的三方失焦**：你交出控制流→读不出执行顺序；模型被硬编码边钉死→走不了图外的路；框架持有控制流→默认不可观测（要 LangSmith）。断点打不进、state 不可 diff。
2. 课程那句「模型强了就别用」说的是**替代关系**：手写一条条件边 = 声明「我不信模型能判断下一步」。图的复杂度 ∝ 对模型的不信任度。模型变强后这些边不会自动变好，只会过时并拖住模型。

**采用率数据（纠偏他听到的「80%」）**：2026 年 LangGraph 生产采用率约 41–44%（LangChain 自家 State of Agent Engineering 41%；n=3200 的 State of AI Engineering 44%），**不是 80%**；且自研/内部定制占 16–41%，是第二主流。另：某第三方 benchmark 显示 LangGraph 成功率随复杂度衰减（简单 88%→中等 76%→复杂 62%），图越复杂收益越薄（该数据可信度一般，别当定论）。

**JD 的关键观察**：2026 真实 JD 里 LangGraph 几乎都带 "or comparable / or equivalent / or similar"（Worth AI、HPE、Mercanis 均如此）→ 它是「生产级 Agent 编排能力」的**代理指标**，不是硬门槛。但 ATS 按关键词筛，简历上必须出现该词，且要有真东西撑住。

**给他的选型判据**：
- 该用图：长时运行 + 断点续跑（跨进程 checkpoint）、人在回路 interrupt/审批、多分支并行 superstep 合并、时间旅行回放。
- 该自研：步骤固定且分支 ≤3、强合规需逐行可审计、要在面试里逐步讲清。
- **Miro 结论**：主路径 signal→wuxing→imbalance→state 固定 → 自研（30 行 while + 自己的 state dataclass）。唯一正当引入点 = 若要做「解读中断等待疗愈师确认再继续」，那是 interrupt + checkpoint；即便如此也可自己写 state 落盘 + 恢复。

2. **数字前置**：「Miro 解读链路端到端跑通，23 次运行产出双版本报告」而不是「…经历了 23 次运行」。
3. **拆段落式条目**：249 字的四条缺陷压成 85 字一条（保留 4 个可讲数字，砍掉根因分析——那是面试内容）。
4. **删内部术语**：文件名 / 函数名 / 内部状态名 / 决策编号 / 🅥 全部移出简历正文（它们属于面试口头材料）。
5. **V2 内容移到文末专节** `## 附：V2 跑通后并入正文（投递前整节删除）`——正文因此变成一份可直接投递的干净简历，待启用内容只多一次删除动作。这同时解决了母版 §6.4 提醒过的「内部备注」红线问题。
6. **未完成态改位置**：缺陷/局限不再占收尾位，仍保留为独立条目（差异化证据不丢）。
7. **合并古早经历**：2008–2019 的保险 + 自由职业 + 游戏研发合并为一个「保险与早期研发」条目、3 条子项。

**新增：格式规范写入治理文档**（`README-文件结构与同步规则.md` 第八节，原第八节顺延为第九）：
- 8.1 硬指标（正文 ≤3,000 字 / 单条 bullet ≤160 字 / 内部备注 0 处）+ 自检脚本
- 8.2 条目写法四条（数字前置 / 禁止段落式条目 / 加粗只用于能力标签与关键结论 / 未完成态不占强证明位）
- 8.3 分层表述（已跑通 / 已设计未实现 / 目标值，与认知卡 §0.6 第 4 条同源）
- 8.4 待启用内容的位置
- 8.5 自检脚本（改完必跑，含字数、超长条目、内部标记三项）
- 过程中我自己定的「单条 ≤110 字」阈值不现实，已按实测改为 ≤160 字。

**教训（写进规范，下次不用再返工）**：项目里的工程细节 ≠ 简历内容。写简历时先在项目文件里标记「这条是给面试讲的」还是「这条是给简历写的」；前者不进简历。
