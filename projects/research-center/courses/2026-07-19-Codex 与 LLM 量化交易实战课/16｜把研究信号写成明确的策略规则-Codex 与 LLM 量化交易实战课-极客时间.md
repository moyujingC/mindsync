第 15 讲我们验证了信号是否干净、稳定、可复测。这节课继续追问：它能不能变成引擎逐根执行的动作。“看多”不是 LONG，LONG 也不是已经成交。只有触发、仓位、退出、冷却、失效、停止、成本和成交假设都写清楚，研究信号才真正进入策略层。

在这一步里，Codex 不替研究者发明策略，而是把自然语言信号收束成可执行规则：检查策略函数，补齐触发和停止条件，运行规则测试，并确认模型文字没有绕过成本、仓位和失败条件。LLM 可以提供候选解释，最终交付必须落成可复查的策略契约。

本讲会用两条交叉类策略做对照：一条从价格窗口计算均线，一条依赖指标序列生成 MACD 金叉信号。两者的技术细节不同，但进入策略层前都要回答同一个问题：规则在每根 K 线上能不能给出一致、可复查、经得起失败检验的动作。

## 1\. 策略规则卡：先把研究语言降成契约

从信号进入策略层，第一步不是讨论“模型看多怎么交易”，而是确认信号能否被写成确定条件。回测引擎需要在每根 K 线上回答：现在是否入场，入多少，何时退出，遇到异常是否停止。

本讲的代码包括 src/backtest/rolling/strategies/、src/backtest/rolling/engine.py、tests/test\_qbot\_strategies.py 和 tests/test\_project.py，这些文件会在正文中逐步展开。

表 16-1 先给出策略规则卡的最小内容，也为后续代码实现提供审查边界。

| 规则项 | 记录内容 | 常见模糊表达 | 可执行写法 |
| --- | --- | --- | --- |
| 触发 | 指标、周期、阈值、交叉方向 | 趋势较好就买 | prev\_fast <= prev\_slow and fast\_ma > slow\_ma |
| 仓位 | 固定仓位、比例仓位或风险预算 | 适当买一点 | action=LONG 且分数达到阈值 |
| 退出 | 止损、止盈、反向信号、时间退出 | 不对就走 | 死叉、止损或最大持仓根数 |
| 冷却 | 连续交易后的等待根数 | 看情况再进 | N 根 K 线内不重复开仓 |
| 失效 | 数据缺失、异常波动、滑点过高 | 市场异常时停 | 缺字段或风险钩子阻断 |
| 停止条件 | 真实账户、自动下单、越权建议 | 直接执行 | 仅研究回测，不进入实盘 |

表 16-1　策略规则卡的最小内容

规则卡不是为了写得完整好看，而是为了让每一个模糊词都有落点。“趋势较好”必须落到某个指标、窗口和阈值；“适当买一点”必须落到动作和仓位口径；“不对就走”必须落到退出规则；“市场异常”必须落到失效或风险阻断。不能落到这些字段的句子，应留在研究假设里，不能进入回测实现。

### 1.1 可执行规则的审查口径

策略契约的关键不是字段数量，而是字段之间能不能闭合。触发条件要说明指标如何计算；仓位口径要说明当前空仓和已有持仓时如何处理；退出条件要说明是平仓、等待还是反手；冷却和失效条件要说明系统何时拒绝继续生成动作；停止条件要说明研究沙盒不能越界到真实交易。

| 审查问题 | 合格回答 | 不合格回答 |
| --- | --- | --- |
| 当前 K 线可见什么 | 只使用 idx 及以前的价格、指标和状态 | 用未来收益确认当前信号 |
| 动作从哪里来 | 由固定指标、阈值和交叉方向生成 | 由模型解释临时判断 |
| 分数有什么用 | 只作为入场阈值或排序依据 | 分数高就默认已经成交 |
| 已有持仓怎么办 | 继续持有、退出或阻断都有分支 | 新 LONG 重复开仓 |
| 失败如何记录 | 返回 WAIT、阻断原因或审计记录 | 跳过失败样本，只展示成功交易 |

表 16-2　策略规则卡的审查表

研究报告里的常见词汇还要翻译成动作枚举，不能把解释性语言直接交给引擎。

| 研究语言 | 策略层翻译 | 回测引擎实际需要 |
| --- | --- | --- |
| 看多 | action="LONG" 或 WEAK\_LONG | 动作枚举、分数、阈值 |
| 观望 | action="WAIT" | 不开仓、不加仓、可记录分数 |
| 转弱 | 死叉、负分或退出候选 | 是否平仓、是否反手、是否等待 |
| 风险大 | 风险规则或钩子阻断 | 阻断原因、规则编号、审计记录 |
| 暂停策略 | 停止条件或冷却期 | 暂停范围、持续时间、恢复条件 |

成熟回测框架虽然接口不同，但对策略规则的约束很接近。QuantConnect 的 Algorithm Framework 会把 insight、组合构建、执行和风控拆成不同模型；Backtrader 把策略逻辑放在逐 bar 调用的 next() 里，再通过 broker、commission 和 slippage 模型处理成交现实；Zipline / Zipline Reloaded 也把 commission 和 slippage 作为回测现实模型的一部分。把这些做法翻译到本专栏，就是三条硬规则：

信号不越级。研究信号只能先变成策略信号，不能直接变成成交记录。

执行另有模型。订单是否成交、以什么价格成交、承担多少成本，必须由成交和成本假设处理。

风控独立验收。仓位、止损、暂停和阻断不能藏在一句“模型看多”里，要有独立字段和失败记录。

这些资料不是为了把本讲写成框架比较，而是提醒一个工程事实：越成熟的回测系统，越不允许把研究解释、交易动作、成交现实和风险控制混成一层。策略规则卡正是这条分层原则的课程化表达。

### 1.2 ma\_crossover 规则卡样例

一张合格规则卡还要写清“谁负责判断”。Codex 可以把规则项落到代码和测试，不能替研究者决定“均线窗口为什么用 5/10 而不是 10/20”；回测引擎可以按规则执行，不能替研究者解释收益是否稳健；LLM 可以生成候选逻辑，不能绕过规则卡直接生成交易动作。

代码 16-1 是一份可直接复用的 ma\_crossover 规则卡样例。它不是策略结论，而是把研究信号固定成回测前的契约。其他 LLM 信号也应先改写成同样格式，再进入实现或检查。

这份规则卡有两个作用。对实现者来说，它限定了不能自由发挥的地方：死叉不能被解释成做空，窗口不足时不能补造信号。对复核者来说，它给出了检查入口：参数是否被改动，成交时点是否前视，成本假设是否和报告一致，测试是否覆盖触发条件。

规则卡没有写“预期收益”，这是刻意的。规则卡冻结的是研究动作，不是收益承诺；它回答“怎么执行”和“何时停止”，不回答“未来是否赚钱”。如果把收益目标写进规则卡，Codex 很容易被诱导去调窗口、改阈值或改样本，让规则适配目标结果。收益评估应留到回测和稳健性讲次，用固定规则去检验，而不是倒过来用收益改写规则。

macd\_crossover 是同一思想的第二个案例。它不直接从 close 序列计算短长均线，而是依赖 IndicatorSeries 中的 macd\_line 和 macd\_signal：当 MACD 线从下向上穿过信号线时生成 LONG，从上向下穿过时生成 WAIT，没有可用指标或没有交叉时保持等待。这个对照案例补充了三个判断点：

数据来源不同，契约字段不变。均线案例的输入是价格窗口，MACD 案例的输入是预先计算的指标序列，但两者都必须写清触发、退出、窗口不足和停止条件。

共享规则不等于共享策略。long\_only\_cross\_signal() 可以复用，但 ma\_crossover 和 macd\_crossover 的指标来源、参数空间和边界测试不同，不能只因为都叫“金叉”就混成一个策略。

等待状态是有效动作。MACD 指标缺失、当前索引越界或没有交叉时返回 WAIT，这不是“没有结果”，而是策略明确拒绝交易。能说清什么时候不交易，是规则卡最容易被忽略的价值。

因此，本讲不是只教一条均线规则，而是借两类交叉策略说明同一个工程原则：研究语言先降成契约，契约再进入策略函数，随后才进入回测证据链。

## 2\. 代码落点：把契约放进策略函数和状态机

规则卡写完后，我们进入代码层：确认每个字段都能在策略函数、引擎状态和测试里找到落点。仓库中已有 ma\_crossover、macd\_crossover、boll\_mean\_reversion、adx\_macd\_trend 等策略样本，它们都比“看多买入”更明确。这里重点查看共享规则、均线策略入口和 rolling 引擎的状态判断。

### 2.1 共享规则函数

代码 16-2 是 src/backtest/rolling/strategies/qbot\_rules.py 中的共享规则。crossed\_up 和 crossed\_down 是布尔条件，long\_only\_cross\_signal 把条件转成 LONG 或 WAIT。

def crossed\_up(prev\_a: float, prev\_b: float, cur\_a: float, cur\_b: float) -> bool:

return prev\_a <= prev\_b and cur\_a > cur\_b

def crossed\_down(prev\_a: float, prev\_b: float, cur\_a: float, cur\_b: float) -> bool:

return prev\_a >= prev\_b and cur\_a < cur\_b

def long\_only\_cross\_signal(

\*,

crossed\_up\_flag: bool,

crossed\_down\_flag: bool,

entry\_score: float = 50.0,

exit\_score: float = -50.0,

) -> Signal | None:

if crossed\_up\_flag:

return Signal(action="LONG", score=entry\_score)

if crossed\_down\_flag:

return Signal(action="WAIT", score=exit\_score)

return None

代码 16-2　Qbot 风格均线交叉规则

这里没有“看起来趋势不错”这样的自然语言。规则只有三种结果：金叉给 LONG，死叉给 WAIT，没有交叉就返回空，由策略入口继续处理。

这段共享规则还体现了一个重要边界：本仓库里的 ma\_crossover 是 long-only 规则。金叉进入多头，死叉回到等待或退出候选，并不自动做空。如果把“趋势转弱”直接写成 SHORT，就已经改变了策略定义。策略规则卡必须记录这种方向边界，否则后续回测会把两个不同策略混在一起比较。

同一共享规则也被 macd\_crossover 使用，但它的输入不是均线窗口，而是 macd\_lines\_at(indicators, idx) 返回的当前 MACD、当前 signal line、上一根 MACD 和上一根 signal line。这里有一个实战判断：如果 indicators is None，或者当前索引拿不到完整 MACD 线，策略必须返回 WAIT，不能根据价格走势临时补一个方向。这个分支看起来保守，却能防止“指标缺失时模型凭感觉补交易”的错误。

把两个案例并排看，规则卡还要多问三句：

指标是策略内部现算，还是由外部 IndicatorSeries 提供？

指标不可用时是等待、报错，还是阻断整次回测？

共用交叉函数后，策略自己的参数、阈值和测试是否仍然独立？

### 2.2 逐 K 线信号生成

共享规则只是第一层，真正进入回测前，还要确认它如何在每根 K 线上生成动作。代码 16-3 截取 src/backtest/rolling/strategies/ma\_crossover.py 的核心逻辑：先处理窗口不足，再只读取当前索引及以前的 K 线，最后把交叉条件交给共享规则。

def generate\_signal(self, candles, idx, params, indicators=None) -> Signal:

fast\_period = int(params.get("fast\_period", 10))

slow\_period = int(params.get("slow\_period", 30))

if idx < slow\_period:

return Signal(action="WAIT", score=0.0)

closes = \[float(candles\[i\]\["close"\]) for i in range(idx - slow\_period, idx + 1)\]

fast\_ma = sma\_at(closes, fast\_period)

slow\_ma = sma\_at(closes, slow\_period)

prev\_closes = \[float(candles\[i\]\["close"\]) for i in range(idx - slow\_period, idx)\]

prev\_fast = sma\_at(prev\_closes, fast\_period)

prev\_slow = sma\_at(prev\_closes, slow\_period)

cross\_signal = long\_only\_cross\_signal(

crossed\_up\_flag=crossed\_up(prev\_fast, prev\_slow, fast\_ma, slow\_ma),

crossed\_down\_flag=crossed\_down(prev\_fast, prev\_slow, fast\_ma, slow\_ma),

)

if cross\_signal is not None:

return cross\_signal

return Signal(

action="WAIT",

score=separation\_score(fast\_ma - slow\_ma, slow\_ma),

)

代码 16-3　ma\_crossover 的逐 K 线信号生成

这段代码有三层边界：

idx < slow\_period 时等待，避免指标窗口不足。

只读取当前索引及以前的 K 线。

交叉出现时才产生明确动作；没有交叉时，不靠语言解释补动作。

逐根 K 线执行的含义，是每一个 idx 只能看到 idx 及以前的数据。prev\_closes 判断上一根 K 线的均线关系，closes 判断当前 K 线的均线关系，两者共同构成交叉。这个写法看似啰嗦，却正是策略可信的来源：规则不是事后看完整走势再解释，而是在每个时点用当时可见的信息作出动作。

macd\_crossover 的逐 K 线流程更短，但审计点更集中：它先确认指标序列存在，再通过 macd\_lines\_at() 取得当前和上一根 MACD / 信号线，随后把交叉判断交给 macd\_cross\_flags() 和 long\_only\_cross\_signal()。如果没有指标、索引越界或指标值为空，策略返回 WAIT。这个案例说明，策略规则不一定都要自己计算指标，但必须说明外部指标不可用时的处理方式。

两个案例的实战差异可以这样记：

ma\_crossover 的风险主要在窗口边界，尤其是不能把最后一根 K 线误读成上一窗口。

macd\_crossover 的风险主要在指标依赖，尤其是不能在指标缺失时补造交易方向。

两者共同的规则边界是 long-only：金叉是入场候选，死叉是等待或退出候选，不自动变成做空。

### 2.3 信号、持仓与交易记录

回测引擎还会把 generate\_signal() 的输出继续放进状态机。generate\_signal() 返回的是 Signal(action, score)，它只说明“当前 K 线产生了什么候选意图”。rolling 引擎随后会先记录 candle signal，便于审计；再检查已有持仓是否需要退出；最后才检查空仓时是否允许入场。

表 16-5 把引擎里的对象层级拆成四层。

| 层级 | 例子 | 谁生成 | 不能替代什么 |
| --- | --- | --- | --- |
| 研究信号 | “趋势偏多” | 研究报告或 LLM 摘要 | 不能替代策略动作 |
| 策略信号 | Signal(action="LONG", score=50) | 策略规则函数 | 不能替代成交 |
| 持仓状态 | 空仓、持有多头、待退出 | 回测引擎状态机 | 不能替代收益结论 |
| 交易记录 | 入场价、出场价、PnL、原因 | 引擎和风控模块 | 不能证明未来有效 |

## 3\. Codex 实战：把模糊请求拆成可审计工作

策略规则一旦引入 Codex，委托边界要比普通开发任务更清楚。目标不是要求 Codex “优化策略”，而是让它在受限范围内完成可复查动作：读规则卡、定位代码、补测试、运行验证、交回证据。只要任务描述仍停留在“帮我把这个信号做成策略”，研究判断、实现细节和收益目标就容易混在一起。

### 3.1 一轮模糊请求拆成三轮工作

下面是一条不合格请求：

帮我把趋势偏多信号写成能赚钱的策略。

这句话至少有三个问题：没有固定触发条件，没有固定修改范围，也没有说明验证证据。更稳妥的做法是拆成三轮 Codex 工作。

规则整理轮。要求 Codex 只阅读研究信号和现有策略文件，输出规则卡草案，不改代码，不新增策略结论。

实现定位轮。要求 Codex 只在 src/backtest/rolling/strategies/ 和对应测试文件中找落点，说明哪些字段已经存在、哪些字段缺测试。

验证收口轮。要求 Codex 补最小测试或文档证据，运行指定命令，并把命令、退出码和关键输出写回交付说明。

代码 16-4 给出一段可以照做的委托提示词。它限制了修改范围，也要求 Codex 输出验证证据。

请把下面的研究信号整理成 ma\_crossover 的策略规则卡，并核对仓库实现。

范围：

\- 只检查 docs/v2/16-把研究信号写成明确的策略规则.md

\- 只读取 src/backtest/rolling/strategies/、src/backtest/rolling/engine.py、

tests/test\_qbot\_strategies.py、tests/test\_project.py

\- 不修改 vendor/

\- 不改变策略参数来追求收益

研究信号：

短均线重新站上长均线，趋势由弱转强。

交付：

1\. 输出触发、仓位、退出、冷却、失效、停止、成本、成交假设。

2\. 标出每个规则项对应的代码或测试文件。

3\. 如需改文档，只改本讲，不改代码。

4\. 运行指定 pytest 命令；未运行就明确写“未运行”。

代码 16-4　把模糊策略请求拆成可审计 Codex 委托

这段提示词的核心不是措辞，而是约束：它把“赚钱”从任务里拿掉，把交付改成规则、代码落点和验证证据。Codex 仍然可以建议缺口，但不能把收益目标倒灌进参数选择。

### 3.2 修改范围和证据输出

让 Codex 参与策略规则整理时，最容易失控的不是语法错误，而是范围漂移。一次合格委托应把下列边界写清楚：

只读范围。允许读取哪些策略、引擎、测试和文档文件。

可改范围。只改本讲文件，下一讲才进入代码实现。

禁止事项。不导入 vendor/，不新增真实交易动作，不为追求收益调参。

验证入口。指定窄口测试，例如 tests/test\_qbot\_strategies.py 和 tests/test\_project.py::test\_event\_driven\_engine\_uses\_on\_tick\_strategy。

证据格式。交付时写明命令、实际输出和没有覆盖的风险。

Codex 输出也应按证据链组织，而不是只给“已完成”。一个可接受的收口说明至少包括：改了哪些段落或文件；保留了哪些事实；运行了哪些命令；命令输出是什么；哪些结论仍不能声称。对策略课程而言，最后一项尤其重要：测试通过只说明规则接口和窗口边界正常，不能替代收益评估。

## 4\. 执行假设与结果复核：先固定口径，再看图表

规则可以逐根生成动作，并不意味着已经可以解释收益。策略规则进入回测前，至少固定四类假设：数据窗口、交易成本、成交规则和风险规则。否则同一条信号可以被解释出很多不同结果。这里把假设、图像复核和成本敏感性放在一起，是为了防止“规则能跑”被误读成“规则可靠”。

### 4.1 回测前固定四类假设

表 16-7 汇总策略规则进入回测前的假设清单。它们最好和规则卡一起冻结，因为数据窗口、成本、成交和风险会互相影响。

| 假设 | 固定内容 | 未固定的后果 |
| --- | --- | --- |
| 数据窗口 | 起止时间、频率、缺失处理 | 样本选择污染 |
| 成本 | 手续费、滑点、价差、资金费率 | 收益被高估 |
| 成交 | 开盘 / 收盘成交、下一根成交 | 前视偏差 |
| 风险 | 最大仓位、止损、暂停条件 | 回撤不可控 |

表 16-7　策略规则进入回测前的假设清单

成交规则尤其需要单独写明。很多初学者会把“本根 K 线收盘后得到信号”和“本根 K 线收盘价成交”混在一起。如果信号依赖本根收盘价，那么严格做法通常是下一根开盘或下一根可成交价执行。

| 成交口径 | 含义 | 主要风险 | 记录要求 |
| --- | --- | --- | --- |
| 当前收盘成交 | 信号和成交都使用本根收盘价 | 容易被误读为可实盘执行 | 标明为教学简化假设 |
| 下一根开盘成交 | 本根收盘生成信号，下一根开盘成交 | 更贴近可执行流程 | 记录延迟和跳空风险 |
| 下一根 VWAP/ 区间价 | 用下一根成交区间近似执行 | 依赖更细数据或假设 | 记录估算方法 |
| 无法成交 | 缺价格、停牌、滑点过高或风控阻断 | 交易路径中断 | 记录阻断原因 |

表 16-8　策略规则进入回测前的成交口径

成本、成交和风险假设，会改变同一条规则的执行路径。提高滑点可能改变止损触发，延迟成交可能改变持仓时间，风险钩子可能让某些高分信号不交易。只固定入场规则而不固定这些假设，回测就不是在检验策略，而是在检验一组未写明的执行口径。

## 总结

这节课我们把研究信号转换为策略规则，核心是把模糊判断固定为可执行、可复核、可阻断的条件。合格规则说明入场、离场、持仓、冷却、成本和失败状态，不能只把“趋势偏多”“模型看多”这类研究语言直接交给回测。

更严格地说，这节课我们完成的是一次语义降噪：把 LLM 或研究者的自然语言，降成规则函数能够执行的枚举、阈值、状态和假设。这个过程不追求让策略显得聪明，而是追求让策略在每根 K 线上都可判断、在每次失败时都可解释、在每次版本比较时都可复现。
