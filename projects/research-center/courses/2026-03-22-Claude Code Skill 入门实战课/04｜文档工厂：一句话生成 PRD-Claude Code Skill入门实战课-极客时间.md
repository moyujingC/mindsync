本节摘要

各位同学大家好！欢迎来到我们的 Claude Code Skill 实战系列课程的第 4 节。

大家有没有过这样的经历？脑子里突然蹦出一个特别棒的产品想法，但是要让这个想法变成一份能交给开发团队的 PRD 文档，却要花上好几天的时间？反复沟通、梳理流程、考虑各种异常情况……

如果大家经历过这种痛苦，那今天这节课请一定要认真看完。

我要给大家介绍的这个 Skill，就像是一个 24 小时待命的产品经理。只需要给它一个模糊的想法，它会主动帮你澄清需求、理清逻辑，最后输出一份专业到可以直接使用的 PRD 文档。

想知道它是怎么做到的吗？我们这就来一探究竟

## 痛点与价值

在正式开始前，先问大家一个问题：大家觉得写一份合格的 PRD 文档需要多长时间？

很多产品经理说，他们写一份完整的 PRD，往往需要 1 到 2 天。并且这还不包括反复修改的时间。

为什么需要花费这么多时间？因为 PRD 写作本质上不是“写文档”，而是一个思维梳理的过程。你需要：

- 把模糊的业务想法拆解成具体的用户故事
- 梳理核心业务流程和状态机
- 考虑各种异常边界情况
- 最后定义清晰的验收标准

更要命的是，很多产品想法在早期阶段是非常模糊的。可能只有一个念头：“我想做一个积分兑换功能。”

但是，积分怎么获取？怎么消费？要不要会员等级？积分会过期吗？这些问题没有逐一想清楚，PRD 文档就没办法开始往下编写。

而 PRD Skill 要解决的就是这个问题：在你只有一个模糊想法的时候，它会主动提问帮你澄清需求，然后自动生成结构完整、逻辑严密的 PRD 文档。

那么这个具体有哪些作用呢？

第一，时间节省。从 2-3 天缩短到 5 分钟。你只需要回答几个问题，剩下的文档生成全部自动化。

第二，质量保障。即使你不是专业的产品经理，生成的 PRD 也具备专业水准，涵盖了业务流程、状态机、边界场景等关键要素。

第三，快速迭代。当你有了一个新想法，可以快速生成多个版本的 PRD 进行对比，选择最优方案。

听起来是不是很神奇？接下来我向大家演示实际案例。

## 实战演示

首先进入 Claude Code。然后输入一句非常简单的需求：“创建 PRD 文档，做一个积分兑换功能”。

然后，神奇的事情发生了。

Skill 收到需求后，立刻识别到这是一个非常模糊的描述，缺少关键的业务细节。于是它开始主动提问。

第一轮问题，它问了 4 个核心业务问题：

1. 积分兑换的具体业务模式是什么？
2. 积分的主要获取来源是什么？
3. 目标业务场景和用户群体？
4. 核心业务目标是什么？

我依次回答：

- 积分兑换实物商品
- 消费获得积分 + 签到任务获得积分
- 餐饮零售行业 C 端用户
- 提升复购率和客单价

Skill 确认信息后，没有急着生成文档，而是继续追问第二轮细节。

第二轮问题，这次关注规则细节：

1. 积分是否有过期机制？
2. 是否需要会员等级体系？
3. 实物商品的配送方式？
4. 项目开发周期预期？

我回答：

- 永不过期
- 不需要会员等级
- 快递配送到家
- MVP 版本 2-3 周

收集完所有必要信息后，Skill 进入了文档生成阶段。

这就是生成的完整 PRD 文档！它包含了：

- 业务背景：清晰地说明了为什么需要这个功能
- 术语定义表：确保团队对关键概念理解一致
- 用户故事与验收标准：每个功能点都有明确的完成标准
- 功能清单：带优先级和迭代版本规划
- 业务流程图：使用 Mermaid 格式，可以直接渲染
- 状态机转换图：展示了订单状态的完整流转
- 边界场景分析：覆盖了 20 多种异常情况，比如断网提交、积分不足、库存不足等等
- 非功能需求：性能、安全、可观测性都有考虑
- 数据埋点清单：方便后续的数据分析

这就是一份可以直接交给开发团队的 PRD 文档。而我做的，只是回答了 8 个问题。

## 原理揭秘

你一定很好奇，这个 Skill 是怎么做到的？

其实，它的核心是结构化的思维链。它模拟了人类产品经理的思考过程。

看这张图：  
![](https://static001.geekbang.org/resource/image/4c/1b/4cfaa2c0653de56b1c862776e7faa01b.png?wh=610x416)

核心哲学层是整个 Skill 的灵魂。它定义了什么是“好的 PRD”——简洁、逻辑严密、考虑周全。

工作模式层是关键。注意这个理念：“Refine-Before-Write”——先澄清再写作。

PRD Skill 不会看到需求就立刻开始写文档，而是先评估需求的模糊度。如果信息不足，它会主动使用 AskUserQuestion 工具向你提问。

输出标准层定义了具体的 PRD 结构，包含 8 大模块，每个模块都有明确的写作规范。

## 避坑指南

当然，作为一个成熟的 Skill，PRD 生成器也有它的边界和局限。了解这些，能帮助你更好地使用它。

**场景一：需求极度模糊**  
在最开始提供需求的时候，需要提供基本的背景信息，如做一个健身记录的 APP。  
放置因为需求过于模糊，让 Claude Code 反复需求澄清阶段，影响最终生成的效率

**场景二：需求自相矛盾**  
如果你说“积分既要永不过期，又要限制有效期”，Skill 可能会尝试生成一份自相矛盾的 PRD。  
在需求澄清阶段时要避免提供自相矛盾的需求，保持前后状态一致，防止影响 PRD 文档生成质量

**场景三：领域知识不足**  
如果你的需求涉及非常专业的领域，比如金融、医疗领域。生成的 PRD 可能并不能符合实际标准，生成完成后，需要相关领域专家对文档进行 review，以确保内容的合法性与准确性。Skill 可以帮助梳理逻辑，但不能替代专业知识。

## 总结

这节课的学习到这里就结束了。

我们深知 PRD 撰写的核心痛点：不是写得慢，而是想得乱。本节课中，我们通过深度拆解 PRD Skill，将产品经理的“结构化思维链”注入 AI，实现了从“提问澄清”到“自动生成”的闭环。借助 Agent Skill 将原本数天的繁琐工作，浓缩成了 5 分钟的精准输出，确保生成的每一份文档都逻辑严密、无懈可击。
