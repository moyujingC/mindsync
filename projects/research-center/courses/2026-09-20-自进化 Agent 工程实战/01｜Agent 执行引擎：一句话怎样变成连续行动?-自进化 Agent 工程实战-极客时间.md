你好，我是 Tyler。

最近，使用 Codex、Claude Code、OpenCode 和 Hermes 这类工具的人越来越多。第一次打开它们时，你可能会觉得，这只是把聊天框搬进了终端：过去，我们把一段文字交给大模型；现在，我们把一个文件夹交给它。

用得久一些，你会发现，把文件夹交给 Harness 以后，原本需要你亲手完成的一连串操作，也跟着交了出去。

你不再需要逐份打开资料、挑出相关内容、复制给模型，再把回答保存回工作环境。只要把任务交给 Harness，它就可以直接在工作目录里查找资料、调用工具，并把结果保存下来。

可是，你只告诉了它要完成什么，并没有告诉它每一步应该怎么做。下面，我们从一个熟悉的夜晚开始，看看这样一项任务究竟是怎样被一步步完成的。

## 案例：告警调查任务中 Harness 做了什么

想象一下，这周轮到你 On-call。凌晨两点，值班电话响了。监控系统提示，支付服务的结账接口在过去五分钟里连续返回 HTTP 500，错误率已经超过告警阈值。

你打开电脑，找到告警详情和对应时段的日志，又把相关代码拉到本地。告警中带着一条失败请求的编号。你把这些材料放进同一个工作目录，然后把调查任务交给 Agent：

请根据告警、日志和代码，定位结账请求失败的最可能原因。

把调查结论写入 incident-report.md。

每项结论都要注明日志或代码位置。

没有证据的内容不要猜，也不要修改日志和代码。

如果你只是打开浏览器里的 ChatGPT 对话页面，这项工作仍然需要你不断在对话页面和本地环境之间传递材料。

你要先根据请求编号筛出相关日志，把错误堆栈交给模型；模型指出某个文件以后，你再打开代码，把相应片段继续送进去。等模型形成结论，你还要把回答整理成调查报告。少送进去一段日志，或者漏掉一份相关代码，模型也不会知道还有哪些证据留在对话之外。

有了 Harness，这些反复的资料传递和工具操作可以直接在任务环境中完成。

模型首先查看当前目录，确认有哪些材料可以使用。Harness 执行命令，把文件列表返回给模型。模型打开告警，从中取得失败请求编号，接着要求在日志中搜索这个编号。

搜索结果显示，请求 req-7f3a 因为 KeyError: 'currency' 返回了 HTTP 500，错误堆栈指向 src/checkout.py。

模型继续读取这份代码，发现程序直接访问了 payload\["currency"\]，而日志记录的请求数据中恰好没有 currency 字段。

两条原本分散的证据由此连接起来：日志说明程序在哪里失败，代码解释了为什么缺少这个字段会触发异常。

有了足够的证据以后，模型生成 incident-report.md，分别写入告警事实、日志证据、代码证据和最可能的原因。报告完成后，它重新读取文件，检查关键结论是否都能找到对应证据，然后结束任务。

整个过程中，你没有告诉它“先打开哪个文件，再搜索什么字段，然后读取哪段代码”。你只给出了目标。后面的步骤，是模型根据刚刚得到的结果一轮轮决定出来的。

## 一次任务在 Agent Harness 中的运行循环

把这个过程抽象一下，会发现它始终在重复同一个循环：

模型根据当前掌握的信息，决定下一步做什么；

Harness 在真实环境中执行这个动作；

环境产生新的结果，再由 Harness 返回给模型；

模型根据新的结果继续判断，直到任务完成。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/0d/1d/0d68158a50d5c5b82257c6af2d46841d.png)

这里还有一个很容易被误解的地方。站在你的角度，你只输入了一条指令，之后 Agent 就一路把任务做了下去。但从模型 API 的角度看，这并不是一次持续到任务结束的调用，而是许多次彼此独立的模型调用，被 Harness 串成了一项连续的任务。

模型决定“查看目录”以后，这一轮调用就结束了。Harness 执行命令，得到文件列表，再把结果带入下一轮模型调用。模型看到文件列表，决定搜索请求编号；Harness 执行搜索，再把日志结果带回来。后面的读取代码、生成报告和检查报告，也遵循同样的方式。

所以，看起来连续运行的是整个任务，底层实际发生的却是一轮又一轮模型调用。每一轮，模型都根据当前掌握的信息判断接下来做什么；Harness 负责执行这个动作，并把环境产生的新结果带入下一轮。

正是这样的反复交替，让 Agent 能够沿着刚刚获得的线索继续向前推进。这条不断运行的链，就是 Agent Loop。

因此，我们可以先用一个很简洁的式子理解 Agent：

Agent = Model + Harness

Agentic Model 负责理解当前状态、进行推理并决定下一步采取什么动作；Harness 负责维持任务循环，把这些决定落实到当前任务的资料、工具和真实环境中，再把执行结果带回来。

这也解释了为什么，同一项任务交给 Codex、Claude Code 或 OpenCode，最终可能走出不同的执行轨迹。这种差别既来自模型本身，也来自 Harness 如何组织上下文、加载哪些项目规则和工具，以及允许模型采取哪些动作。

到这里，第一个问题就有了答案：为什么只给 Agent 一个目标，它仍然能够沿着线索一步步把任务做下去？

因为它不需要一开始就知道完整的执行路径。每得到一个新的结果，模型都可以重新判断下一步，再由 Harness 真正执行这个动作，并把新的环境反馈带回来。

不过，这次故障调查的材料很少，可能十几分钟就能结束。如果事故涉及多个服务，需要持续几个小时，甚至在你离开屏幕以后仍然继续运行，问题就变成了——怎样才能让它持续工作，同时始终不偏离最初的目标？

## 责任交接：Harness 从人手上接过了哪些责任

假如影响范围还在扩大，刚才的调查就不会停在一份报告上。你还要参加故障沟通、确认业务损失，并和其他同事讨论止损方案。与此同时，Agent 正在继续梳理其他服务的日志。

你不可能一直盯着屏幕。当你离开以后，有些东西仍然必须留在系统里。

首先是目标。你不能只留下一句“继续调查”。后面的判断仍然要围绕“这次结账请求为什么失败”展开，不能顺手重构支付服务，也不能把所有历史告警重新分析一遍。任务持续的时间越长，目标边界就越重要。

第二是进度。几个小时的调查会经历很多次模型调用。哪些日志已经看过，哪些假设已经排除，哪份代码已经检查，报告写到了哪里，都不能只存在于某一轮模型刚刚生成的文字中。

Harness 需要通过会话记录、任务状态或其他持久化信息，把这些进度带入后续调用，让模型知道此前已经完成了什么，接下来还要继续做什么。

第三是行动边界。任务要求中的“不要修改日志和代码”表达了工程师的意图。真正进入无人值守状态以后，还要通过文件权限、隔离环境、工具策略和审批机制，把这条要求落实成系统能够执行的边界：哪些目录只能读取，哪些文件允许写入，哪些工具可以调用，哪些高风险动作必须等待批准。

最后是验收标准。Agent 宣布“调查完成”，并不意味着结果已经通过验收。报告中的关键结论仍然要能够指向日志或代码位置，事实、推断和待验证项也要保持区分。

Verifier 可以独立检查这些条件。运行轨迹则保留 Agent 看过哪些材料、调用过哪些工具、执行过哪些动作，方便工程师之后重新审查整个过程。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/8f/fa/8f73fddfffefa4752a28af3b98ea7ffa.png)

人的注意力退出以后，Harness 接过四项责任

目标、进度、行动边界和验收标准持续留在系统中，Agent 才能在工程师预先划定的范围内继续工作。这样的自治始终带着明确的控制边界。有了这些控制，你可以暂时把注意力转向其他事情，故障调查仍然能够继续推进。

## 为什么纠正过的问题，下次还会再犯？

可是，等任务真正结束以后，又会出现一个更麻烦的问题。

第二天早上，你回来审阅报告。

报告正确记录了 KeyError: 'currency'，也找到了直接访问这个字段的代码，却在结尾写下了一句：

上游客户端发布了错误版本。

现有证据只能证明请求中缺少 currency 字段，却不能证明这个字段为什么缺失。它可能来自客户端，也可能在中间服务中被丢失，还可能只是一次异常请求。你于是要求 Agent 修改报告：把已经确认的事实、根据现有证据作出的推断，以及仍待验证的问题分开。没有充分证据支持的可能性，不能写成已经确认的根因。

现在手里的这份报告是修好了，可下周再次出现类似故障时，新的 Agent 会不会犯同样的错误？这取决于刚才的纠正最终留在了哪里。如果它只存在于当前 Session，它改变的就只有这一份报告。新的 Session 不会因为你曾经纠正过一次，就自然学会区分事实、推断和待验证项。

Hermes Agent 在官网首页用一句话介绍自己——The Agent That Grows With You，也就是“与你共同成长的 Agent”。这里真正值得关注的是，“成长”究竟意味着什么。

一次任务结束以后，Harness 会留下对话、工具结果、运行轨迹和最终产物。这些内容共同构成一段任务经历。Hermes 的后台复盘可以重新读取这段经历，并从中提出 Memory 或 Skill 的候选修改。比如：

事故报告必须区分事实、推断和待验证项，并为关键结论注明证据位置。

这是一条简短、稳定，而且适用于后续任务的工作约定，更适合作为 MEMORY.md 的候选内容。

而刚才走通的整套调查方法，包括确定告警时间窗、根据请求编号检索日志、沿错误堆栈定位相关代码、建立证据链，以及控制结论边界，则更适合沉淀为一项可以重复使用的 Skill，在遇到类似任务时按需加载。

## 写进 Memory 和 Skill，就算成长了吗？

把经验写进 Memory 或 Skill，还不能开心太早，这只是能力演化的第一步。接下来的挑战是：这次修改真的会让 Agent 做得更好吗？

工程师可以先保留原来的版本，再启动一个新的 Session，让 Agent 加载修改后的 Memory 或 Skill，处理一份从未见过的故障材料。

一个位于任务执行链之外的只读 Verifier 再检查新的报告：日志引用是否正确，代码位置是否准确，事实和推断是否分开，任务过程中有没有突破原有的权限边界。

如果新的 Skill 只适用于刚才的样本，无法泛化到新的故障场景；或者虽然让调查速度更快，却带来了更多武断结论；又或者提高了任务成功率，却破坏了原有边界，那么这次修改就不应该成为长期能力。这时，工程师可以回滚到之前的版本。

于是，一条完整的能力演化链逐渐形成：任务执行留下经历，后台复盘提出候选，工程师审阅候选修改，新的 Session 在独立任务中加载新能力，Verifier 检查结果，最终再决定保留、发布还是回滚。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/3d/17/3d4a3dd2aa9ed4de71b2046187306117.png)

一次任务怎样形成可验证的成长闭环

这样一来，谁提出修改、谁检查结果、谁决定保留，都有了明确的责任主体。这也解释了为什么“记住”和“成长”之间还有一段距离。

过去的经历需要重新进入未来任务，并真正改变 Agent 的行为；这种变化还要接受新的任务检验，确认它能够适用于更多场景，同时没有破坏原有边界，才有资格成为长期保留下来的能力。

一个长期工作的 Agent 不能把遇到的每句话都永久保存，也不能把一次偶然成功直接变成所有未来任务的默认方法。它需要判断什么值得记住，什么值得沉淀成 Skill，还要通过新的任务不断检验，这些修改究竟是在积累能力，还是在积累错误。

当一个 On-call Agent 能够从自己的任务经验中沉淀出可靠的 Skill 以后，经验还可以继续向外传播。课程后面，我们会把能力验证放在 SkillClaw 的传播之前，再把已经通过验证的 Skill 分发给其他 Agent。

到那时，成长的范围就会从单次 Session，扩展到一个长期运行的 Agent，再进一步扩展到多个 Agent 共享的能力体系。

## 小结

学到这里，我们回头看一下这一讲发生了什么。

开篇时，我们用一次 On-call 故障调查理解了 Harness 的第一个价值。

过去需要工程师亲手完成的查找、读取、执行和保存操作，现在可以由 Harness 接手。模型根据当前信息判断下一步，Harness 在真实环境中执行，再把新的结果送回模型。一句话的任务要求，就这样经过一轮又一轮 Agent Loop，逐渐变成一份完整的调查报告。这解决的是第一件事，接管。

随后，你离开了屏幕。任务没有因此失去方向。目标、进度、行动边界和验收标准仍然留在系统中，Agent 可以继续工作，同时始终受到这些约束。这解决的是第二件事，自治。

最后，你发现 Agent 在报告中产生了过度推断。一次纠正如果只停留在当前 Session，只能修复当前结果。当任务经历能够被复盘，稳定的工作约定被写入 Memory，完整的方法被沉淀为 Skill，再经过独立任务、外部验收和版本治理，过去的经验才真正有机会改变未来的行为。这解决的是第三件事，进化。

接管、自治、进化。这三个词，也会成为接下来整门课展开的主线。

## 课后题

思考：当递归自我改进成为现实，工程师的职责还剩什么？

Anthropic Institute 在 2026 年的《When AI builds itself》中讨论了 Recursive Self-Improvement，也就是递归自我改进：AI 系统开始参与设计和开发自己的后继系统。

今天的 AI 已经能够承担越来越多实现、测试和评测工作。在一些开放任务中，人只需要给出目标和成功标准，模型就可以自行寻找实现方法，并根据结果继续调整。

如果这种能力继续向前发展，AI 有一天可能不仅能够完成研发任务，还能够持续改进自己的模型、工具、Memory、Skill，甚至 Harness 本身。

到了那时，一个更重要的问题会出现：当“怎么实现”越来越多地交给 AI，工程师究竟还需要决定什么？

练习：Headless 启动一次 Harness

大多数人第一次使用 Harness，都是从交互界面开始的。但当 Harness 进入定时任务、持续集成流水线或者业务服务以后，工程师还需要掌握另一种运行方式：直接从程序中启动它。

这种脱离人工交互界面的运行方式通常称为 Headless。这时，你不再坐在终端前逐句输入，而是由 Python 程序直接启动并驱动同一套 Harness。

打开 GitHub 中的实验 Notebook，从第一个单元格开始依次运行。Notebook 会自动安装实验所需组件。运行过程中，你只需要输入 GLM API Key。

实验首先展示告警、脱敏日志和一小段 Python 代码，然后通过 Codex App Server 创建 Thread，并启动一次调查 Turn。

运行过程中，请重点观察 Thread ID、Turn ID、工具事件以及最终生成的调查报告。任务结束以后，Notebook 会重新展示原始输入材料。你可以检查报告是否已经生成，同时确认告警、日志和代码是否保持原样。

观察这些现象时，可以重新思考本讲介绍的 Agent Loop：

每一次模型调用从哪里开始，又在哪里结束？工具动作发生在什么时候？新的工具结果又是怎样进入下一轮模型调用的？
