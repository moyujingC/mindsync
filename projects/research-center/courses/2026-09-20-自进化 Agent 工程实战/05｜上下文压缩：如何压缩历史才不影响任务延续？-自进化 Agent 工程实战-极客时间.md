上一讲结束以后，server-23 的调查仍在进行。到了凌晨四点，Agent 已经查过发布记录、应用日志、数据库指标和连接池配置，执行了几十条命令，Thread 中也积累了大量对话和工具结果。

任务还要继续，但模型的上下文窗口终究有限。历史不断增长以后，模型不可能在每一轮调用中，都重新读取从凌晨开始的全部内容。

因此，长任务运行到一定阶段，就必须让一部分历史退出当前 Context。真正困难的是该移走什么，又该留下什么。

信息的价值并不由出现时间决定。几百行刚刚返回的重复日志，可能没有提供任何新线索；很早以前确认的一条事实，却可能一直影响着当前判断。

当完整历史已经无法继续放进一次模型调用时，Harness 必须作出选择：哪些信息仍然支撑着当前任务，需要继续留在 Context 中；哪些材料可以暂时退出，等真正需要时再重新读取。

## 历史被压缩以后，调查还能接着做吗？

调查继续进行时，Codex 触发了一次 Context Compaction，也就是上下文压缩。

压缩完成以后，工程师问 Agent：

现在调查到哪里了？为什么暂时不能把应用发布写成根因？

Agent 回答：

当前仍在调查支付接口错误率上升。相同报错在应用发布以前已经出现，因此应用发布目前只能保留为调查线索。数据库连接等待与错误率在同一时段上升，还需要继续核对连接池配置和等待指标。

这段回答说明，压缩并没有打断调查。Agent 仍然知道当前目标、已经确认的事实、现阶段能够作出的判断，以及接下来准备核对什么。

工程师接着追问：

发布前那条报错，原始日志到底是怎么写的？

这一次，Agent 无法直接给出原文。它仍然知道应用发布以前出现过同类报错，也知道这项判断来自此前查过的日志，但那几行原始记录已经不在压缩后的 Context 中。为了准确回答，它需要重新打开日志，找到对应内容以后再引用。

这里可以看出，Compaction 的目标不是在更短的 Context 中浓缩此前出现过的一切。它保留的是继续完成任务所需要的状态，例如调查进行到哪里、哪些事实已经确认、当前结论的边界在哪里，以及下一步为什么要这样安排。

日志原文、精确数值和完整代码则属于另一类信息。它们仍然保存在日志系统、监控平台和代码仓库中，需要核对时再重新读取。

压缩以后，Agent 不必继续背着全部材料工作，但必须知道自己已经走到哪里，以及到达这里所依据的理由。

## 上下文更新后，什么不该随之改变？

压缩的目标不是把历史尽可能缩短。假如压缩以后只留下这样一句话：应用发布已经排除，继续调查数据库。

别看这段话很简洁，却改变了原来的调查状态。

因为此前确认的是，相同报错在应用发布以前已经出现。这个事实只能说明，现有证据不足以证明本次应用发布直接导致了故障。它没有证明发布与故障完全无关，也没有排除发布放大原有问题、改变请求路径或者触发其他条件的可能性。

“暂时不能认定”一旦被压缩成“已经排除”，判断的确定程度就被悄悄改变了。后续 Agent 可能因此关闭这条调查路径，不再检查与应用发布有关的新证据。

“继续调查数据库”同样存在问题。它保留了下一步动作，却丢掉了选择这一步的理由。

Agent 之所以开始检查数据库，是因为数据库连接等待与错误率在同一时段上升。这种时间上的共同变化，使数据库成为值得继续验证的方向。假如这个依据没有进入压缩后的 Context，后续 Agent 虽然知道应该查数据库，却不知道这项行动来自什么证据，也无法在新信息出现时重新评估它是否仍然合理。

因此，Compaction 需要保留的并不只是结论和待办事项。当前目标是什么，哪些事实已经确认，哪些内容仍然只是推断，现有证据能够支持到什么程度，为什么选择下一条调查路径，还有哪些问题尚未核对，这些信息共同构成了任务的当前状态。

与此同时，Context 也不需要继续容纳所有原始材料。

完整日志已经留在日志系统中，指标序列可以重新从监控平台读取，代码也能够从仓库再次打开。对于眼前的调查，Agent 需要记住的是“应用发布以前已经出现过同类错误”，以及这项事实可以到哪里核对。至于日志的逐字内容和某一分钟的具体指标，可以等真正需要时再取回。

## Codex 怎样做 Compaction？

请注意，虽然长任务中的 Context 可以不断压缩，但任务的目标、判断依据和未决问题不能在这个过程中发生漂移。对于这个问题，我们看看 Codex 是怎么做的。

Compaction 可以自动发生，也可以由客户端主动发起。Python SDK 的 Thread 提供了 thread.compact()，它最终会调用 App Server 的 thread/compact/start。

压缩发生在原来的 Thread 上，不会另外创建一条新的任务记录。客户端仍然使用同一个 threadId，并在其中收到 contextCompaction Item 的开始和完成通知。

这里需要区分两个容易混的概念：Thread 中已经发生过的完整过程，以及后续模型调用实际携带的 Context。

模型不再看到压缩以前的全部内容，不代表那些内容已经从系统中删除。Codex 当前的存储接口使用两个名称来区分这两部分：

StoredThreadHistory 用于读取已经持久化的 Thread 历史，为 resume、fork、rollback 和 memory 等操作提供基础。

StoredModelContext 关注的则是另一件事：当任务继续运行时，哪些记录需要重新进入模型当前使用的 Context。

这意味着，系统可以继续保留较完整的 Thread 历史，同时只把其中一部分交给后续模型调用。Compaction 改变的是模型当前看到的工作集，并不必然改写已经持久化的完整记录。

Codex 的 rollout trace 也为 Compaction 定义了对应的 checkpoint。

pub struct CompactionCheckpointTracePayload<'a> {

pub input\_history: &'a \[ResponseItem\],

pub replacement\_history: &'a \[ResponseItem\],

}

其中，input\_history 是本次进入压缩过程的历史，replacement\_history 是压缩完成以后，用来替代原有 Context 的内容。前者回答“这次压缩处理了什么”，后者决定“后面的模型还能看到什么”。

那么，新的 replacement\_history 是怎样生成的？

Codex 存在不同的 Compaction 路径。在仓库中保留的本地摘要式路径里，codex-rs/prompts/templates/compact/prompt.md 以这样一句话开头：

Create a handoff summary for another LLM that will resume the task.

这里使用的关键词是 handoff summary，也就是一份交给后续模型的任务交接摘要。

按原意整理，这段 Prompt 大致提出了以下要求：

为接下来继续任务的模型准备一份交接摘要。

保留当前进展和关键决定；

保留重要背景、约束和用户偏好；

说明尚未完成的工作以及下一步安排；

保留继续任务所需要的关键数据、示例和参考信息。

内容应当简洁、清楚，使后续模型能够直接接着工作。

发现了么？这段 Prompt 没有规定最近出现的内容必须优先保留，也没有要求尽可能复制历史原文。它采用的是任务导向的选择标准：后续模型还需要知道什么，才能在看不到完整历史的情况下继续完成工作。

放回 server-23 的调查中，几十条已经执行完毕的日志查询没有必要继续逐条出现。相同报错为什么削弱了应用发布作为直接根因的判断，数据库为什么成为新的调查方向，还有哪些指标尚未核对，则会继续影响后续行动，因此需要进入新的 Context。

不过，这段 Prompt 只对应本地摘要式 Compaction。Codex 还可以采用其他压缩路径，最终生成的 replacement\_history 未必表现为一份适合人直接阅读的摘要。

具体形式可以不同，但衡量标准不变。压缩后的上下文要能支撑模型继续完成原来的任务，而且不能因为信息被重新表达，就把事实变成推断、把可能性变成结论，或者把尚未验证的方向当成已经完成的决定。

## Compaction 后 Prompt Cache 会失效吗？

在同一项任务连续运行时，相邻两次模型调用经常共享很长的相同前缀。系统指令、项目规则、用户要求以及部分历史记录，可能在多轮调用中保持不变。

Prompt Cache 可以复用这些相同前缀已经完成的计算，从而减少重复计算带来的延迟和成本。

但命中缓存的内容仍然属于模型输入。它只是少算了一次，并没有从 Context 中消失。

Prompt Cache 解决的是：同一段内容再次出现时，能不能减少重复计算？

Context Compaction 解决的是：历史不断增长以后，后续模型还需要继续携带哪些内容？

即使二十万 Token 的历史几乎全部命中缓存，它仍然占据二十万 Token 的上下文空间。缓存可以降低处理重复前缀的成本，却无法让模型的 Context 无限增长。

Compaction 完成以后，后续调用会改用新的 replacement\_history。原来那段很长的前缀不再完整进入模型，因此压缩以前形成的缓存前缀未必还能继续以相同方式复用。

这不意味着 Prompt Cache 机制本身失效。任务在较短的新 Context 上继续运行以后，系统指令、项目规则和新的任务历史还会形成稳定前缀，后续调用仍然可以在这个基础上获得缓存收益。

因此，Prompt Cache 和 Compaction 并不是相互替代的两种方案。前者提高重复输入的计算效率，后者控制模型输入本身的增长。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/ce/7c/ce173fc3054d568ee3bcbe98bff4067c.png)

这里顺便看一下其他 Harness。它们都会遇到同一个问题：任务持续时间越来越长以后，不可能把从开始到现在的所有内容原样塞进每一次模型调用。区别主要在于三件事：什么时候触发压缩，压缩以后模型继续带着哪些内容工作，以及更早的历史还保不保留、以后怎样找回来。

![](https://static001.geekbang.org/resource/image/8f/eb/8f520c40a44f0360f7f16c2825db43eb.jpg)

Harness 的具体实现会随版本变化，但评估一套系统的长任务能力时，可以先问两个问题：

压缩完成以后，模型还能看到什么？

已经退出当前 Context 的旧内容保存在哪里，后面还能不能重新找到？

第一个问题决定任务能否连续。假如目标、关键事实、判断依据和未决问题没有进入新的 Context，Agent 即使继续运行，也可能已经偏离原来的任务。

第二个问题决定历史能否追溯。退出 Context 的日志、对话和工具结果如果仍然保存在 Thread 或外部系统中，Agent 后面就有机会重新检索；如果它们同时被彻底删除，压缩就可能造成不可恢复的信息损失。

## 小结

在古希腊传说中，忒修斯的船被后人长期保存。船上的木板腐朽以后，人们便一块块换掉。许多年过去，原来的木板已经全部被替换，它还是原来那艘船吗？

![](https://static001.geekbang.org/infoq/87/8793f74c0aaf06d434be39376ed4c9da.png)

长时间运行的 Agent 任务，也会遇到类似的问题。

回到凌晨四点的 server-23。调查已经产生了大量对话、命令和工具结果，模型无法继续在每一轮调用中携带全部历史。Compaction 因此需要重新组织 Context，把不会继续影响任务的内容移出当前工作集。

这次压缩不需要保留每一条查询命令和每一行重复日志，但必须保留调查目标、已经确认的事实、当前判断的边界、尚未解决的问题，以及下一步行动背后的理由。

需要精确引用的日志、指标和代码继续留在各自的原始系统中。压缩以前的 Thread 记录也可以继续保存在持久化存储里，只是不再默认进入每一次模型调用。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/c2/2b/c28a52c750cde0691cb578f33628c72b.png)

因此，Compaction 的核心不是删除历史，而是重新决定模型此刻需要带着哪些历史继续工作。衡量一次压缩是否成功，也不能只看 Token 减少了多少，还要看任务状态是否保持连续，判断有没有被改写，后续模型是否知道应该去哪里找回缺失的细节。

几个小时以后，工程师重新打开这条 Thread。夜里的调查记录仍然存在，生产环境却没有停在凌晨四点。

过去形成的调查状态可以继续使用，过去看到的现场还能直接相信吗？下一讲，我们就从这里继续。

## 课后题

### 观察题：压缩以后，哪些东西还在？

选择一条已经运行较长时间的故障调查 Thread。

压缩以前，让 Agent 说明当前调查到了哪里，为什么暂时不能成立某项判断，下一步准备做什么。同时找出一段以后可能需要精确引用的原始日志。

随后发起一次 Compaction，再次询问相同的问题，并要求 Agent 准确引用刚才那段日志。

如果所用 Harness 支持读取完整 Thread 历史，还可以继续检查压缩以前的消息和工具结果是否仍然存在。

观察时重点关注三个问题：压缩以后，模型保留了哪些任务状态；需要精确内容时，它是否会重新读取原始材料；已经退出当前 Context 的旧记录，能否通过 Thread 历史或其他检索方式重新找到。

### 思考题：压缩以后，什么必须留给模型？

一项任务连续运行几个小时以后，此前发生的一切无法继续原样进入模型 Context，但这些记录也没有必要全部从系统中删除。

如果由你设计这场 On-call 调查的 Compaction，哪些内容必须继续留在模型当前的 Context 中，哪些内容只需要保存在 Thread 历史里，哪些材料应当继续留在日志、代码和监控系统中？当后续 Agent 再次需要这些信息时，它应该通过什么线索找到它们？
