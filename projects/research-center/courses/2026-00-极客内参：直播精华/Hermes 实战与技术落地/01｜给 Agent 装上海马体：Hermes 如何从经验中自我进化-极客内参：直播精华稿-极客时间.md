各位同学，大家晚上好，我是王延飞。今天我们给大家一起来分享一下最近比较火的——从养龙虾（OpenClaw）到现在养马 Hermes，它有什么突出的能力？今天和大家一起来分享一下。我们今天所使用的 Hermes Agent 版本是相对比较新的，也就是 4 月 30 号的 12.00.12 版本。

今天和大家分享的内容主要分为五个部分。第一个部分，为什么我们现在会开始推崇这个“养马”Hermes？Hermes 解决了什么问题？其中最主要的问题是失忆——它拥有了一个长期记忆能力。不仅是长期记忆能力，还有一个自进化的能力。它会根据我们自己的交互习惯，我们平常的一些高频、重复性、周期性的任务，它会帮我们提炼成这样的 Skill，而不是说靠我们自己去抽取 SOP 再去形成 Skill。

我们会通过一个案例——大家日常接触比较多的销售数据总结提炼——来展示。之前是没有 Skill 的第一次，它会帮我们去形成一个 Skill。后来我们又增加了新的文件格式，比如我们平常使用的销售数据统计文件一般是 Excel 格式，可能有时候也会提供 CSV。我们知道很多做编程的同学也会用 CSV 做数据统计和报表。那如果我们突然给了它一种新的格式，它会不会帮我们去处理这个 Skill？能不能做一些自修正？我们会在第三部分去讲。

当然，讲这个前提我们也会讲得相对基础一点，因为照顾到很多同学可能还没有去养过马，刚体验完 OpenClaw 又来了个新东西。所以说我们会讲一下 Hermes 这个智能体你是怎么去部署的。今天我主要依赖于 Mac 环境，给大家做一个从 0 到 1 的演示。同时 Windows 版本、Linux 版本也给大家准备了一些文档，稍后这些文档在直播后会联系班班去要，我会统一把文档给到班班。

那我们部署完 Hermes，也体验到它的进化之后，它内部是怎么做的呢？我们就会讲一下它里面的一些关键性流程。这样的一些关键性的自进化流程，能不能在我们做一些企业级 Agent 的时候有一些可复用的设计原则？当然是有的，我们会在最后的第五部分给大家做一个提炼总结。

Agent 为什么会“失忆式工作”？Hermes / OpenClaw / Harness 的三角关系

我们先来看一下第一个部分。大家都会有一种焦虑：刚刚才把养龙虾搞明白，又来了一个 Hermes。其实 Hermes 这个工程在 2026 年 2 月份的时候已经开源了。我们知道 2 月份还是我们春节期间，那时候我们刚刚知道了龙虾和 Hermes，它们之间有什么关系呢？

![](https://static001.geekbang.org/resource/image/91/39/91c0049b06b162869f85a90ab004e139.png?wh=2048x632)

从目前来说，Hermes 整体的 Stars 数量还不如龙虾，到现在为止才 1000 多 K。但从另外一个数据来看——大模型 API 的中转站 OpenRouter 上，它有几周的时间是在霸榜的，大家对它的期待是比较高的，它的增速也非常快。那你说我之前还没有把养龙虾搞明白，现在能不能直接去学习 Hermes 呢？还是需要先看一下 OpenClaw 再看一下 Hermes？其实如果说你还没有接触过，那你可以直接去看 Hermes，它是不冲突的。如果说你原来已经接触了 OpenClaw，现在再来看 Hermes，它也提供了一键式迁移的方式，很方便。

我们今天也不是说让大家去追热点，我们也是去体验一下 Hermes 背后的 AI Agent 设计范式。因为我们只有理解它背后的设计逻辑，我们才能在后面新的产品形态出现的时候，把握到里面不变的东西。例如说之前在给大家分享 OpenClaw 的时候，我当时有一个断言：OpenClaw 一定不是最终的一个产品形态，但 OpenClaw 所代表的设计范式——特别是 Agent 这样的产品里面它所需要具备的能力——一定是未来的方向。

同样站在今天，Hermes 也是一样的。它也不是一个最终的产品形态，它只是一个现在比较时兴的产品，但它提供了一些设计范式，一定是我们未来的产品形态需要具备的。例如说现在 Hermes，它也继承了像 OpenClaw 里面我们之前提到的持久记忆、自主能力、本机主权这三大能力，它在这个基础上又提出了一个新的能力，就是自进化。我们稍后给大家具体去讲。

好，那我们讲自进化的时候就主要围绕着一个事情。我们在做智能体的时候其实经常会面临一个失忆的问题。智能体经常会失忆是为什么呢？因为大量的 AI Agent 有一个根本性的局限性：它是一个无状态的应用。我们经常会有这样的感受：花了半天时间去教会一个智能体，让它学习了项目规范、技术栈的偏好、我平常的一些经验，但是再给它进行第二轮交互的时候，它可能很多时候就忘光了。因为大部分智能体经常会存在这样的情况：会话结束之后就会清空上下文，再来第二个会话又从头来一次。就是因为没有持久的会话记忆。所以说 OpenClaw 会加一些 user、agent、memory 这样的文件，来存储用户对这个智能体的定义，以及它的一些上下文记忆，甚至会借助一些外部的存储。

![](https://static001.geekbang.org/resource/image/f6/60/f61e4211c4722f5a885cbc59f0214360.png?wh=2058x938)

这是一个方面。第二层面就是在 OpenClaw 里面，我们很多 Skill 是要去手动配置的，对不对？我们经常说安装完龙虾之后的第二步是干什么呢？要配置大模型 API，第三步就是要配置技能。配置技能就要根据自己的行为习惯：我是一个编程人员，我可能需要很多关于编码方面的 Skill，帮我去审核代码、帮我去写相关的开发文档；我是一个产品人的话，我需要你帮我去写市场调研的分析报告、抓取竞品分析、做 PPT。这样的 Skill 是需要我们靠自己从开发设计去找，并且是我们自己去提炼的。

而且还有一个问题：我们自己的操作经验和习惯会发生变化。这样的 Skill 它也是静态的。随着我自己对这个需求场景的变化——原来写 PPT 的时候可能需要这样的风格，后面需要另外一种风格——这个 Skill 还需要手动去调整。Skill 并不会根据我多次的交互自动进化，比如说我今天背景色用橙色，明天想换成红色，交互完之后 Skill 不会发生变化。这就是 OpenClaw 之前智能体的一个局限性：技能要靠人工维护。

进而引出来一个问题：原来我编程里面的 Skill 可能有很多不足。你原来先帮我去看一下代码再去修改代码，但是你经常上来就改，经常犯这样的错。我多次提醒你，你还是没有纠正过来。这些经验无法沉淀，你犯过的错还是会重复犯，没有做到“吃一堑长一智”，没有达到 Skill 的自进化。第四个层面就是它永远无法自适应我们用户习惯的变化。核心问题就是没有这样的技能经验的积累。

好，那我们再来看 OpenClaw、Hermes，还有最近大家经常提到的 Harness，它们之间有什么关系呢？

OpenClaw 大家都比较熟悉了，它主要解决了三大层面问题。一个是入口层，提供了一些即时通信工具，像微信、飞书、钉钉、企业微信、QQ。调度层有一个中间的 Gateway 网关，一端连接我们的即时通讯软件，另一端连接后面的 Node 节点。它解决消息从哪儿来——从一个用户非常熟悉的入口过来，到 Gateway 的时候做一些任务拆解、意图识别，再到路由转发，到 Node 节点。你是要直接操作你本地的文件？我们知道 OpenClaw 当时有一个非常惊艳的能力就是本地主权，可以直接操作我本地的文件。例如说我现在做了大量的 Hermes 的调研，你帮我去将这些文档汇总提炼一下，它都可以去操作你主机上的某个文件目录。甚至还可以联动到飞书，将平常做的会议纪要直接发给相关的同事。这也是我们在 OpenClaw 这个阶段经常用的能力。

那中间提到了 Harness，Harness 的区别在哪呢？Harness 其实更多的是一个工程设计的设计哲学。我们知道“Harness Engineering”这个概念，回过头来看，2026 年 2 月份的时候 OpenAI 曾经发布过一篇文章，披露了整个 Codex（OpenAI 里面的 AI Coding 工具）是怎么借助 Harness 这样的设计哲学，仅靠三个工程师在 5 个月的时间内提交了 1500 个 PR，整体代码都是靠 AI 去编写。Harness 其实不是一个具体的一个工具，它是一个设计范式。它将大模型提供的“智”的层面——也就是智力——纳管到一个工程体系的范畴。

我们经常在去年的时候给大家说，2025 年一定是进入了大模型工程化的阶段。工程化的阶段我们原来的想法可能是在传统 Web 时代里面要做 CI/CD、日志监控告警、记忆管理、会话管理、工具调用等等，这些都算大模型工程的范畴。但是这些工程其实还缺乏一种整体的范式，Harness 就是解决这个问题。例如说我们引入了大模型，怎么去解决它的真实性？让它提供的信息真实可靠。第二个，怎么去约束它的执行边界？第三个，怎么让它能接入我们的业务能力？这些能力都有了之后，它在运行过程中还是一个黑盒子的环境，这个黑盒环境我们怎么去观测调试？最后它最终的一个产出，我们怎么能够让它去进行可验证、可回归？

现在我们经常有个自嘲：我们现在的程序员经常成了“善后工程师”，对不对？经常让 AI 吭哧吭哧写了一大堆之后，我们人去上去调试、去修改。这就缺乏了两种情况：第一个就是我们做完的 Agent 缺乏一个可调试；第二就是它做完的结果，我们缺乏一个可验证。所以说整体的 Harness 就围绕一个事情：我不是要把大模型约束死、限制死、不让它发挥智能的能力，而是去引导它。

我们原来的方式是写大量的提示词工程，去写满这些规则，列举很多情况，写提示词的时候也会走大量传统软件开发里面的 if-else。那到了 Harness 里面，我们从想通过规则去控制大模型，变成去引导它。那 Harness 的边界在哪里呢？其实我们可以通过两个坐标轴来定位一下。这个坐标轴是阿里云他们开发社区提供的一个非常好的引荐。

![](https://static001.geekbang.org/resource/image/a7/67/a726f8de59880b64a8c4b72a07c50067.png?wh=1984x970)

第一个横轴（X 轴）表示执行流的路由，从静态到动态。纵轴（Y 轴）表示状态，有隐式状态和显式状态。我们看 X 轴，从静态到动态。原来我们可能是借助一些提示词或者借助 LangChain，提前写好了一些工作流程，预设好规则，这保证了确定性但是不够灵活。从静态到动态，是在可控性和灵活性中间取一个平衡。

我们去看静态：原来我们把大模型（23 年的时候）经常做一个 OpenAI API 的单次调用，你写好了提示词，拿到了一个确定性的结果。那时候有大量的提示词工程，特别是系统提示词。进入到 24 年有了 LangChain 这样的一个大模型开发框架，其实 LangChain 里面的思路也是 Chain，基于工作流的机制，将传统业务和大模型的结合通过工作流的方式。在我们智能体开发实战课程里面，第二周给大家讲在 LangChain 里面大概有几个流程：第一个是初始化状态，第二步是要去调用的模型，第三步是你是否要组装起来哪几步。LangChain 里面每个 Chain 就是一个节点，每个节点就是一个计算单元，每个计算单元之间的关系有串联式、路由分发式、并行式。所以它还是提前预设了一些规则，这是从可控性到灵活性之间的区别。

那我们到了动态的阶段，像 Harness，我们是靠模型的意图——“意图即服务”的机制，用户去问什么，我们就帮他去自主执行。那看纵轴，主要是看隐式状态和显式状态。怎么理解呢？就是系统的记忆你是放在提示词窗口里面去维持，还是放在外置的数据库里面？原来靠 OpenAI API 调用的话肯定是靠提示词做维护。到了 LangChain 之后，我们可以使用外置的数据库，像 PostgreSQL、SQLite 都可以。那到 Harness 里面也是一样，不仅是可以靠外部的数据库，同时还可以依赖像 OpenClaw 里面的一些外置数据文件——Markdown 格式的文件。Harness 里面同样有这样的数据文件，就是 memory 和 user 这两个文件。

那其实说到 Harness，我们怎么区分它是不是一个好的做法？这个问题就是：我们要试图在单次对话的上下文里面解决所有的问题，你是靠软约束还是靠硬规则？

好，那我们再回过头来看 Hermes。一个好的 Hermes 应该长什么样？它应该有一些前置的验证。如果说单次的单元测试失败之后，它会将这个日志抓给 Agent，在 Agent 里面做一些重试、修复 bug，来调整目标达到期望值。同时它也能够去维护一个状态文档，避免任务跨天或者智能体宕机时能够快速恢复。其次我们也会加一些用户的审批节点，能够做一些关键的审核，避免破坏用户核心的数据。总结三个点：第一它能够验证，第二有自己的状态维护文档，第三有审批机制。

Hermes 也是国外的一个团队开发的，它的核心定位是：我不仅要解决工具怎么去用、记忆怎么去存放，最主要的还有两个能力——用户在扣我的多轮交互过程中，用户的操作经验是怎么沉淀下来的？而不是每次交互都无法积累，下次对话还是按照原来的思路。用户提供了新的想法、新的操作思路，我怎么去把这个思路做完善，或者改变思路让它变得更趋向于用户的期待？

所以整个 Hermes 的创始人当时就将 Hermes Agent 定义成一个类似于 Coding Agent 和 Generative Agent 的中间产品形态，或者说混合产品形态。它既是一个编码的智能体，也是一个通用的智能体，既能处理结构化的开发任务（因为开发环境的输入输出相对清晰），又能处理更加复杂的日常通用任务。所以它的整体设计是：AI Agent 应该从交互里面去学习，随着交互越来越多，Skill 也会变得越来越贴近用户的预期，能够去反思、去进化。这个地方的关键点就是它能够进行自进化、持续改进。

![](https://static001.geekbang.org/resource/image/be/fd/be11909ef91e54a6555f758f0b2702fd.png?wh=2004x982)

那么这样来看 OpenClaw 和 Hermes 的区别，最关键的区别就是在这个第三个地方：自学习、自进化。OpenClaw 所需要的技能都是我们要从开源社区拿下来，或者自己将传统工作流程做提炼总结。但 Hermes 不需要了：你直接跟我交互，我会根据交互过程来判断。如果是简单任务我就不帮你写 Skill 了。如果交互过程中有非常复杂的逻辑，反复操作、反复失败，调用了大量的工具，我发现这个问题比较复杂；另外用户交互的次数目前设置的是 10 次，凡是一个会话交互 10 次以上，我就会将它沉淀成一个 Skill。所以说它能够自动去创建一个 Skill。而且随着用户交互越来越多，第一版的 Skill 肯定不符合用户预期，我还能自己去调整、去完善。

还有，它们现在的记忆系统有一个四层的机制，我们会在后面做讲解。另外，OpenClaw 里面大概提供了 7 个文件，有 soul、agent、memory、user 等等，分门别类地去存放面向用户、面向智能体、面向整个系统的预设角色定义。但是 Hermes 这个地方其实只提供了两个：user 和 memory，并且这两个文件在你安装完 Hermes 之后是没有的，它是随着你的交互越来越多，不断地去增删。这就是我们回到核心：它具备自进化的能力。

动手实战——跑通 Hermes Agent（macOS + 飞书接入）

好，那我们接下来就进入第二个部分，我们来实战一下怎么去跑通一个 Hermes Agent。

首先我们需要装。目前官方提供的方式就是 Linux 和 Mac 是最为友好的。如果说大家在安装的时候尽量去选择 Linux 或者 Mac 这样的操作系统，Windows 你可以使用虚拟机去搭建一个 Ubuntu 这样的操作系统，或者使用 Windows 里面自带的 WSL 2。对 Python 的版本要求大概是 3.10 以上。内存的话和 OpenClaw 也一样，它本来就是一个本地化的应用，对内存的要求也不是很高，大概 4G 的内存基本上足够。网络的话尽量是能够访问 GitHub，能够科学上网，因为有些依赖的安装还是需要的。

其次现在大模型 API 的话，DeepSeek V4 的能力也足够强，稍后给大家演示的话就可以使用 DeepSeek V4 这个大模型 API。

你安装完 Brew 之后，我们接下来到第二步，我们需要 Python 3.10 以上的版本，我们会通过 Brew 去安装 Python，安装它需要的 NodeJS 环境，还有需要 Git 和 uv（Python 里面的类库包管理工具）。你可以通过这个方式装。这个地方我都已经装过了，稍后给大家直接打印出来版本看一下。

我们可以直接打印版本，大家看一下，验证一下当前环境。我们有 Python 的版本是 3.11.5，pip 是 26.1，nodejs 是 25.9，还有 Git，还有 uv 0.11.8。

我们到下面这一步，我们就直接通过一行命令就可以直接去安装 Hermes。这行命令直接安装。安装完之后我这里面已经安装过了，安装完之后我们就可以直接通过 hermes version 去打印出来我们的版本。Hermes 的版本是 0.12.0，是 26 年 4 月 30 号，还是相对比较新的一个版本。

安装完之后你可以做一些检查，看一下整体有没有地方安装失败的。有一个诊断 hermes doctor，和 OpenClaw 里面是一样的。这个诊断的内容其实也比较简单，它会判断一下你所依赖的 Python 环境、所需依赖的包都有没有。我们看到它可能用了一些 OpenAI 的 SDK，因为它很多与大模型的交互还是要靠 OpenAI 的 SDK，还有它自己的 Terminal 终端、Python 的一些环境变量、YAML 的处理。

那我们接下来就来进入到它的配置环节。配置引导也是类似于我们安装完 OpenClaw 之后，接下来第二步就是要配置。我们进入它有两种配置方式：一种是快捷方式，一种是全量的自定义方式。快捷方式的话主要是你去配置一下提供商模型，还有你的消息渠道。

Hermes 核心思路——给 Agent 装上“海马体”，通过案例演示自进化

这是我们刚给大家演示的怎么去接入飞书平台。刚大家提到了几个关键点：添加事件的时候一定要去选择长连接，把消息接收的事件一定要加上去；然后是在 Hermes 里面通过 hermes gateway setup 去直接配置飞书的 App ID 和 App Secret。当然你也可以直接去编辑配置文件。我们刚刚说的它有大量的环境变量，我们可以直接去看，~/.hermes/.env 这个文件里面就有大量的信息。我的飞书的 App ID、模型的 API Key（DeepSeek）、飞书的 Secret 等等，你可以直接去改这个配置文件，改完给它重启一下就行。改完之后你可以通过 hermes gateway restart 直接进行重启。

那么接下来去演示一下我们今天最主要讲解的 Hermes 里面的海马体。海马体是我们人大脑里面去负责将短期记忆转化成长期记忆的一个关键的生物机制。我们原来的传统智能体没有海马体，任务执行完之后就忘记了。下次的任务，我们中间给它多次的交互——不管是原来的 Skill，我们对这个 Skill 提供了一些新的操作习惯——它依然是没有记住，依然要从零开始。

那现在 Hermes 有了海马体，在交互过程中我们会沉淀。它会对我们的交互习惯进行总结，沉淀成 Skill，并且还会对 Skill 进行改进。它背后主要依赖的几个机制就是：Memory（能够记住用户的一些偏好），Skill（创建、修改，将经验固化）。它背后一个关键性的机制就是 Nudge Engine，一个做后台异步复盘总结的系统机制。

我们接下来就选择一个场景：销售周报数据的清洗。我们先给大家看一下这个销售数据。我们会在桌面上放置一些测试数据。我们先给它提供前三周的数据（16 周、17 周和 18 周的数据文件）。这个数据文件有几个特点。

第一个特点：存在一些格式上的问题。比如说列名存在多余的空格；第二个它有合并的单元格，我们在做统计的时候就不太好统计；第三个它的日期有四种日期格式。这是第一个提供的素材。

第二个素材：第 17 周的数据相比第 16 周，16 周的数据有 4 列，17 周有 5 列，多了一列“渠道”这样的数据。

再看第 18 周的数据：它加了一些不符合销售额这个类型的非法字段。我们期待的是一个数值，它这个地方直接填入了中文。

我们每周都需要将数据进行批量的清洗。那我们首先就通过智能体来问它。我是一个数据分析、财务分析的人员，每周一都需要做这件事：将某个文件夹下所有的周数据进行批量清洗，并且合并成一个月度报表。每个文件我需要怎么处理呢？你要做列名的 strip（去除空格），门店列要做补齐（因为合并了单元格），日期有多种类型需要统一成一个日期格式。如果其他文件里面多出来一列，你要在合并的时候去补齐它；如果没有这个渠道，你就标“未知”。然后标注当前是一个月里面几个周的信息。合并完之后，你还要给我做两个汇总：一个是按周汇总，一个是门店排行。我每周大概都需要重复做。

你其实这个地方是个很明确的指令，你帮我去总结成一个 Skill。因为在执行过程中，很多时候我们现在用的 DeepSeek V4 这个模型比较强，它可能一把就过了，觉得任务比较简单，就不会自动去提炼成 Skill。所以我们这个地方可以这样说：你能不能帮我去……如果你想要将这个重复性的任务指定成一个 Skill，不想让它依靠模型自己的判断机制，那你就直接加上一个显式的指令：“执行完之后帮我去总结成一个 Skill”。这也是可以的。

你看它接下来这个过程：它首先去搜索文件，接下来通过 Python 的环境去执行，找到了这三个文件。它说相关的依赖包都已经安装了，它使用脚本加 Terminal 的方式去执行。它生成了一个脚本文件，你也可以去观察后台的日志。它发现了有些门店的标签显示为数据行，然后去做修正。这个地方耗时了 3 分钟，它迭代的次数上限应该是 90 次，当前已经迭代了 16 次，正在接受流式消息推送。诶，你看它现在说这三个 sheet 说明相关的月度汇总表应该是创建好了。它现在去将其保存为 skill。当然这个地方是我们显式指定了要提炼成 skill，它也会有一些自动判别的机制，我们稍后做源码解析的时候会拆解一下。里面有关键的几个判断机制，例如用户交互次数多少次才会创建 skill，触发了多少次 create skill 的调用。

你看它最终去创建了一个 skill，通过 skill manage 这个机制去创建。我们来看一下，打开这个文件。输出文件已经保存好了。我们有了这样的输出文件，看一下我们大概需要 3 个 sheet。第一个就是将我们原来有些地方 4 列、有些地方 5 列统一合并成了 4 列，日期格式统一按照我们的预期，还有按周汇总和门店排行也同时给到了我们。

这是我们期待的结果。那它有没有把这个 skill 提炼好呢？我们可以这样去问：“你这个 skill 放在哪里了？”其实我知道这个 skill 是在 ~/.hermes/skills 里面。大家可能经常会遇到问题：它生成的 skill 放哪里了？你可以直接去问它，它会告诉你。诶，你看它说这个 skill 是在 hermes/skills/productivity。我们直接通过我们的 cursor 去看一下，~/.hermes/skills/productivity 下面就有一个 weekly-sales-clean 的文件夹。我们看一下这个时间是在今天 8:21、8:22 创建的，是我们今天创建的。里面的内容是啥？我们带大家看一下。这个就是我们之前写 skill 的方式，有一个 name、description，description 里面有触发机制。你看这个 trigger：“清洗本周销售数据”，它就可以直接去调用这个 skill。它要清洗的数据文件是什么？它要去匹配规则。它里面的依赖怎么去做？它自己提炼出来一个 Python 脚本。

![](https://static001.geekbang.org/resource/image/38/00/382bd474be7ae27afb037901bc511300.png?wh=1136x962)

我们进行第二个 session。现在我们里面其实只有三个文件：16 周、17 周、18 周。我们接下来再加一周的数据，加一下第 19 周的数据。我们现在新加了一个文件数据，它的处理速度能不能快一点呢？它刚刚其实告诉我们了，你接下来后面怎么处理，直接说“清洗本周销售数据”就可以了。它已经给我们提供好了后续的指令。那我现在加了第 19 周的数据，它能够帮我们去自动化处理吗？第一个 session 我们是通过提示词把它提炼成了 skill。第二个 session 第二次会话我们能够让它快速去复用已有的 skill 对不对？你看它现在就执行得非常快，不到一分钟的时间。

我们看一下这个 skill 的能力。我们刚才是 16 周到 18 周，你重新打开这个文件，这是 8:26 生成的结果。我们发现这里面已经有了 19 周的内容。这是符合当前 skill 预期的内容。

但我们刚也看到了这个 skill 只能处理 Excel 的文件格式。那么很多时候数据报表我们也可能用 CSV 的文件格式去保存，对不对？那我们再来加一个 CSV。CSV 文件格式第 20 周的数据，我是通过 CSV 来保存的。我们来去看一下。同样我说“清洗本周销售数据”。首先正常情况下它是不会去发现我新增的 CSV 文件格式的，这是非常正常的，因为这个 skill 里面它就说这个状态文件没有变化。那么接下来我就要提示它：“我这里面新增了 week20 周的数据文件，格式是 CSV。”你发现它接下来会——它发现这个脚本目前只匹配了 Excel 的文件格式，它也来看一下这个 CSV，那么它就要去更新这个 skill。

我们要注意这个地方，它会发生变化，它自己会改变。你看它同时也发现了这个文件里面，因为 CSV 保存经常是 GBK 的编码，不是一个 UTF-8 的编码。它会对此进行一个修正。首先是通过 GBK 去读取这个编码，读取完之后再去修改这个 skill。我们来看一下这个文档，重新打开一下看看。脚本里面其实我们已经看到是已经支持了这个东西，它已经支持了新增 CSV。那么让它再去做一下清洗本周销售数据，应该它已经是自动化地做好了这些事情。我们来看一下，它已经执行过了。再看一下这个数据，这个地方就有 20 周的数据了。

这个地方就给大家演示了几个它的自进化机制。第一个 session，我们传统的一个习惯：我已经写好了一些规则和提示词，你帮我去按照我的预期做这样的事情。它这个地方会自动去提炼 skill，但是为了保证演示效果，我们强制让它“你给我写个 skill”。第二个 session，它就会直接去复用已有的 skill，快速完成任务。第三个，我加了一个新的数据格式，它原来只支持 Excel，现在加了 CSV，它可能识别不了，因为 skill 是静态的。我告知它我现在有一个新格式是 CSV，它就会自动调整之前创建好的 skill，将 CSV 这样的内容做总结和修正。当然我们也会发现这个 SKILL.md 的内容其实没有修正好，它只是把 Python 脚本里面的内容做了修正。因为它最主要的执行逻辑还是靠脚本。你看这个 Markdown 文件也会同步修改——它已经加了一个注意事项：按文件名匹配规则，支持 Excel 和 CSV。

源码解剖——自进化闭环怎么跑起来？

那我们接下来就看自进化它是怎么去完成的。其实主要是有几个核心的逻辑。它背后有一个异步执行的复盘，主要是靠 Nudge Engine。它主要有一个 memory，怎么去触发这个 memory？还有怎么去触发 skill？

![](https://static001.geekbang.org/resource/image/4c/13/4c3a1d89e21f46e4c28dce5420cd7613.png?wh=1968x978)

有几个关键性的触发机制。一个是靠用户交互的 turn 次数，还有一些设置的内存上限。skill 的触发是靠工具迭代的次数。其次就是靠一些在主 Agent 对话里面你直接命中的创建条件，例如说我们直接说“你帮我去总结成一个 skill”。那它自动创建 skill 的几个判断机制包括：任务的复杂度、任务遇错报错后怎么克服、用户的纠正方案、发现不平常的流程、用户明确的指令要求创建。

我们去通过一些源码带大家去看这个事情。大家可以拉取 Hermes 的代码，有个关键文件是 run\_agent.py。在这个文件里面，大概在 1703 行的时候你会看到 memory\_nudge\_interval，它就已经明确了有 10 轮的交互会触发 memory 自动提取记忆。那 skill 的触发我们搜一个关键词 skill\_nudge\_interval，再往上 1 万多行的地方，你会看到追踪工具调用的 iteration，为 skill nudge 做一个技术重置。skill manager 它是否真正要去用的时候，这里面的一些判断逻辑就是：memory 是靠用户 turn 的计数，skill 是靠工具调用的次数（tool calling）来触发和 skill 创建的触发。

![](https://static001.geekbang.org/resource/image/23/e3/236a32954bc015ce95c430cc9d6dd8e3.png?wh=1968x978)

它后台主要是依靠一个关键性的能力：\_spawn\_background\_review 机制。这个代码定义了 Nudge Engine，是后台最主要的异步执行的任务。它会分发一个后台的线程来审核交互，看是否作为记忆或 skill 去存放。它会创建一个完整的 AI Agent 的子分支，使用相同的模型工具和上下文。作为主要的 session，它 review 的提示词是追加到用户的下一轮交互里面的。它里面有关键性的几个判断，比如限制了模型调用的次数——工具调用的最大迭代次数大概是 16 次，它就会决定我们要不要去做 skill 的创建。MAX iterations 就是复盘 16 次工具调用的预算，给它足够去读取上下文的信息，去写这个 skill 的 Markdown 文件以及它的脚本依赖。

这就是其中几个关键性的代码判断。关于记忆，它不仅有一些静态的记忆，现在 memory 和 user 是有限制的，避免发散性过高，另外它提取用户摘要保存 90 天，进行压缩，按需加载。

架构升华——5 条可复用的企业级 Agent 设计原则

整体来说 Hermes Agent 对我们做企业级 Agent 有哪些启发呢？

![](https://static001.geekbang.org/resource/image/0e/33/0e657e3b348f103f5a16764d1e64d333.png?wh=2046x966)

第一点，约束即资产。Hermes 的 memory 字符限制大概是 2200 个字符，user 是 1375 个字符。它不是把所有的记忆都存放，因为你记了所有的内容等于什么都没记。有了长度限制，就会迫使智能体记一些关键性的内容。

第二点，声明式 Agent。声明式的概念最开始我在做 K8s 的时候经常提。举个简单的例子：夏天室内要降温，传统风扇是一档一档按，调高一档、二档、三档。但到了空调的方式，我直接设定温度到 25 度，它就会根据当前室内环境判断要降温还是升温。这就是声明式：设定一个条件，程序向某一个期待的结果运行，而不是命令式（给一个指令做一个变化）。对我们的启发是做智能体的时候，命令式的话我们会说“最终你要将结果用中文给我回复”，声明式的话我们就说清楚用户的背景：“用户是一个中文母语使用者”，它每次的输出结果就会偏向于中文。

第三点，渐进式加载。在我们最开始做 Agent Skill 的时候大家就已经比较熟悉了，就是渐进式披露。

第四点，前台响应，后台学习。我们刚给大家看的 run\_agent 主要入口里面有很多异步性的总结复盘任务，像 fork\_agent 等等。

第五点，边界而非规则。我们现在特别担心像龙虾那样有很多越权行为。我们是把所有的禁止性指令都列举上来吗？比如“你不能删除文件、不能修改数据库、不能操作邮箱、不能打开飞书”——这样的穷举非常多。正确的做法是定义好安全边界。不是说允不允许，而是遇到需要打开邮件、打开即时通讯软件、操作本地文件的时候，先去问我，采用审批机制。

整体来说企业级 Agent 的整体架构设计有接入层、编排层、执行层、记忆层、学习层。我们整体课程里面也讲了编排和执行层，还有记忆层。今天讲到的 Hermes 智能体的自动创建和修复，它后面依靠了一个后台异步复盘。里面有一些关键性的参数，大家有兴趣可以多看一下它的源码设计。源码也不用自己直接去看，直接扔给 Codex，让它帮你去提炼总结。
