## 一、开场：分享的起点是一个现实信号

大家好，我是尹会生，最近一段时间，我跟随公司的售前顾问走访了大量企业，覆盖北京和深圳两地，行业横跨新能源制造和互联网。这些企业的反应让我产生了一个强烈的触动——它们都在向我传达同一个信号：模型越来越强了。

前天，Anthropic 发布了他们最新的旗舰模型，能力几乎令人叹为观止。关注我朋友圈的同学应该看到我发的一条内容——我们拿两年前那个经典的测试题"一串英文里到底有多少个字母 r"，用最新的 Anthropic 模型来测，结果被嘲笑了。当然，这是个段子，但它侧面说明了一件事：模型的能力，真的在飞速进化。

这个趋势对程序员意味着什么？以前我们很多人靠大模型赚钱、建立护城河，是因为模型还不够聪明，很多技术细节它解决不好，所以人的价值还很充分。但随着模型越来越聪明，我们编码的能力空间被逐渐挤压。以前可以说"我会 coding，别人不会"，但今天大模型也能 coding，而且写得很好——我们自己的生存空间就被压缩了。

带着这个问题，我走访了这些企业，他们提出了两个高度一致的核心问题。

第一个问题：现在的技术人员和非技术人员，其实都已经掌握了 Codex、Claude Code 等工具，公司里的 token 也不限量随便用。技术与非技术之间的能力差距被极大缩短了。那作为程序员，我怎么继续保持领先地位？

第二个问题：很多人用 AI Agent 写了一些工具，但工具往往只是搭出来一个 demo。怎么把这个 demo 变成能交付的、有企业价值的、能进入企业流程的工具？

这两个问题，就是今天整个分享的灵感来源。

## 二、今天的核心命题：开源把能力拉平了，工程化才会把价值重新拉开

今天的分享，我想给大家交代三件事情：

成长路线图：为什么企业已经开始不为"聪明的 Agent"买单？我们的方向该往哪里走？

工程化解决什么：工程化的本质是什么，它到底能解决哪些问题？

该补哪些技能：接下来我们该补 Prompt、上下文工程，还是系统能力？怎么补？

需要提前说明的是，今天这一个小时，我不会带大家抄代码、照搬实现——那样做反而会让大家退回到"知识点堆叠"的状态。我更想用这一个小时讲清楚一件事：如何用工程化的视角去写方案、做汇报、进行 Agent 的选型。

## 三、行业现状：为什么做 Agent 的人越来越多，真正吃到红利的人却越来越少？

### 3.1 Demo 泛滥，但企业买的不是"炫酷"

过去一年，整个 AI 圈里最多的是什么？是 demo。各种各样的 demo 满天飞。今天有人做了个自动写代码的 Agent，明天有人做了个自动拆需求的 Agent，后天又出来一个自动调工具、自动改文件的 Agent——视频都拍得很炫，能力也都很强。

但问题来了：企业真的需要一个炫酷的 Agent 吗？

我在走访中了解到，有很多 CEO 给我的反馈是这样的：我们之前在企业内部组织过 AI 大赛，产生了很多优秀的 Agent，当时有不少人拿了奖。但把这些 Agent 放回到组织里的时候，我发现只有它的创造者能用好，别人用就用不好。而且，这个 Agent 只能加快"使用 Agent 的那一段时间"——

大家知道，在软件研发里，真正写代码的时间只占整个软件开发周期的 10%。一个 Agent 做出来，充其量把这 10% 压缩成了 5%、3%。但写完代码还要 check，这部分时间反而增长了。结果整体算下来，用了 Agent 之后反而总耗时更长了。

这就是很多同学现在的真实感受：Agent 写的东西越快、写的东西越多，自己反而越累。

更要命的是，客户可能觉得这个 Agent 看起来很聪明——但聪明就会让他们长期付费吗？不一定。还有一些程序员用 Agent 写贪吃蛇、写小游戏，大家心里其实都清楚：这些真的能给企业带来竞争力吗？答案是否定的。

### 3.2 能力被开源拉平之后，我们需要什么？

为什么越来越多的人会做 Agent，真正吃到商业红利的人反而变少了？

我自己的判断是：因为开源把我们的能力给拉平了。

以前你不会写代码，现在 AI 帮你写了，能力上被拉平了。但这意味着我们需要一个新的东西，把每个人的能力重新拉开差距。

真正的大变化，不会发生在模型排行榜上，也不会发生在产品演示视频里。真正发生变化的地方，是企业预算，是能不能把 Agent 真正丢进企业流程，是整个组织架构和责任链有没有因此发生变化。

以前大家都研究：怎么接模型、怎么挂工具、怎么写工作流——这是上一代人的技能。但今天，在 OpenClaude（即开源的 Claude Code CLI）出来之后，整个世界已经变了。商业世界只会为三件事买单：

稳定交付结果：你开发的 Agent 能不能稳定运行，并且交付稳定的结果？

风险控制成本：能不能提前做风险控制？（比如 Agent 一跑，数据库数据就没了——这是真实风险）

局部能力沉淀为组织能力：你做的 Agent 能不能让整个组织吸收和复制，而不只是你自己能用？

## 四、核心结论：淘汰程序员的不是 Agent，而是"没有工程化视角"

说到这里，我们就回到了今天的核心主题。

未来真正被淘汰的程序员，既不是被 Agent 淘汰，也不是像很多人武断下结论说的"会 AI 的淘汰不会 AI 的"——本质上，是有没有工程化视角。

以前衡量一个程序员是否厉害，靠的是什么？代码写得快、别人不会的我会——这些构成了竞争优势。今天这条路已经走不通了。AI 都能写代码了，而且写得不错。

那我们的价值体现在哪里？绝对不是再多写几百行代码。未来更值钱的，是能把工程这件事给干好。

怎么是"工程化"？单提一个指标没法衡量，我们不妨把"工程化指标"拆开来看，它会变成这些东西：

谁能定义整个 Agent 的运行边界

谁能在运行时做流程治理

谁能设计整套指标、管好整个上下文

谁能控制 Agent 的风险

最终，谁能把经验封装成可用的系统

所以，程序员的竞争方式已经不再是卷代码写的速度了，而是一次更难、更有价值的跃迁：把工程化的事情做好。

## 五、两个视角理解 AI 工程化：技术视角 vs 企业视角

理解工程化，有两个视角可以切入。

技术视角：我们懂技术，知道 Agent Loop 是什么，知道上下文怎么写，知道怎么存数据库，知道怎么做容器化。

企业视角：这个技术如果要落地到特定的业务上，我们怎么考核这个 AI 的能力？

回到我们以前熟悉的前后端开发，感觉是什么？如果想要存一个数字，我就要考虑：存的时候要不要做缓存？怎么设计并发？——这些是以前的考虑方式。换到现在，我们用 AI 的新坐标系来重新考量同样的问题。这就是我理解的工程化。

## 六、工具越完备，竞争为什么反而越惨烈？

有一个问题很值得大家思考：以前工具没完备的时候，我们研究什么？我们研究设计模式、研究微服务——这些东西提升的是架构上的技能门槛。

现在这些东西，Codex 大部分都能替代了。按道理，模型越来越强，工具越来越全，我应该越来越轻松才对——但很多人的感受恰恰相反：工具越完备，自己越来越累。

为什么？

因为以前体现我们价值的是：我知道这个东西需要写循环，别人不知道。今天这个优势消失了，AI 都知道了。所以我们来做软件工程，要考虑的是别人考虑不到的事情。

这里我抛一个结论：因为工具越来越完备，能力的复制也越来越容易。能力复制越容易，客户就只为一件事买单——结果的确定性。

这也是 AI 工程化和以前软件工程最大的区别所在：以前工程比较难，你和别人有信息差，这个信息差很难弥补。今天信息差已经很小了，更重要的是：你知道这个 Agent 怎么运行，能让它更加稳定。

今天我要再明确一个判断：今天最便宜的是"能做出来"，最昂贵的是"交付出去之后还能稳定跑"。

代码本身不再值钱了。以前叫"Talk is cheap， show me the code"，今天变了——"Code is cheap， show me the mind"。你怎么思考这个代码、怎么让它交付之后稳定运行，才是真正的价值。

## 七、企业真正的付费逻辑：不为"聪明"买单，只为"确定性"买单

走访企业的过程中，我发现企业不再因为"智能"而兴奋了，他们开始问这些问题：

在权限受控的前提下，Agent 能不能稳定修改核心代码库？

模型意外输出中断或者报错时，系统能不能自动回滚？

状态的突变追踪、中间执行链和审计责任怎么合理划分？

当多个 Agent 并行协作时，高昂的上下文 token 成本该怎么治理？

企业最怕的不是 AI 不聪明。AI 可以傻一点、慢一点，但最怕的是 AI 很聪明、结果却不可控，或者不可衡量。

这话听起来可能颠覆大家的认知，但这就是我走访了这么多企业之后，最强烈的感受。

### 7.1 "接入"不等于"价值落地"

很多企业在做 AI 项目时，最大的误区就是：把 AI 接入等同于 AI 落地。

你们公司是不是这样——把大模型套个壳，只要接入到系统，就宣布"我们系统带 AI 了，AI 落地了"，然后发 paper、发新闻？比如把模型接入到工单系统、客服系统，接知识库，接研发流程，感觉接完之后价值自然就体现了？

但真体现了吗？

以前，能把模型接进去本身是一件很兴奋的事，因为难。但今天，把 OpenClaude 接到飞书里、自动总结聊天记录——这件事太容易了。采集全网信息、总结成特定内容、做成舆情采集系统——现在大家觉得这些东西太简单了。

于是就出现了一个很奇怪的现象：接进去了，但到底带来了多大价值，大家回答不清楚，也说不清楚到底创造了什么价值。

接进去了，不代表你的软件有价值。

### 7.2 业务价值：你必须能回答这五个问题

如果真的想要让你的 Agent 跟业务结合，你需要能回答这五个问题：

这个 Agent 有没有真正解决我们的业务瓶颈？

它彻底改变了哪一段关键流程的成本结构？

它真实提升的是收入、效率、质量，还是组织的韧性？

如果它发生异常失效，损失在哪里？由谁负责兜底？

它成功的度量标准是什么？拒绝服务的硬阈值又是多少？

很多技术团队在把 AI 接进工具的时候，压根没法回答这些问题。我把这个现象叫做"自我感动"——模型本来很聪明，开发的界面也很流畅，工作流也很完整，演示也很顺利，但我们整个业务不依赖它，因为业务部门要的不是"智能感"，要的是确定的结果。

虽然现在是概率编程，但业务仍然需要确定的结果。业务对研发的要求是什么？不关心 Agent 会不会用多步推理，也不关心把 30 分钟压到了 5 分钟——关心的是：这些原本离散在人的经验里的东西，能不能抽象出来，变成标准化的能力。

有时候企业不会为"模型做了什么"买单，企业只会为"你的结果变成了什么"买单

## 八、衡量 Agent 的五类核心指标：拒绝被 Demo 愚弄

既然要面向业务价值，那我们怎么衡量一个 Agent 是不是真的工程化的，而不只是一个 demo？

我把衡量指标分成五类：

### 8.1 结果指标（Outcome）

这是最核心的指标。Agent 做完这件事之后，业务的结果有没有发生变化？比如：工单的关闭率、代码修复的成功率、需求拆解的准确率、客户的满意程度、知识库的命中率。

如果没有结果指标，这个 AI 就是 demo。

### 8.2 效率指标（Efficiency）

注意，效率指标不一定和结果指标同时成立。有些 AI 工具是用来提效的，有些不是。

举个例子：我之前做过一些和法律相关的 AI，它的作用是纠错——把法律文本里人挑不出来的错误挑出来。这个工具不提效，甚至会让单次处理时间变长，但它的价值在于提升质量。

另外，效率指标非常容易被误判。很多人把"GPT 回答速度很快"当成"整体效率很高"，这是错的。真正要看的是整段流程有没有缩短。

我经常用一个比喻：从广东飞北京，最快的办法是坐飞机。但坐飞机之前要打车去机场，落地之后还要打车。很多人解决"怎么更快"的方法，是在打车的时候拼命催司机——但飞机的起飞时间和最长的飞行段根本没变。把最新的 Agent 工具用上了，看起来某一段加速了，但整体时间没有变短。

真正的效率指标应该看什么？从需求澄清开始： 需求澄清周期有没有变短？研发交付周期有没有变短？测试回归等待时间有没有下降？客服从接单到结案的总耗时有没有减少？

### 8.3 成本指标（Cost）

成本不只是模型的调用费用。更完整的成本模型包括：

缓存的命中率（这个非常重要，后面会专门展开）

工具链的运维成本

上下文的冗余

人工兜底成本

失败的试错成本

集成的维护成本

企业看到的是这些成本叠加在一起之后，单位业务结果的成本有没有降。

### 8.4 风险与合规指标（Risk & Compliance）

包括误操作率、回滚次数、合规情况等。这里不展开，但这些是企业非常关心的硬性指标。

### 8.5 组织吸收与复制指标（Adoption & Replay）

这是企业级 Agent 最核心的组织指标。比如：我这个比较容易出错的项目，能不能规模化沉淀成标准的 SOP？这个 SOP 跨团队能不能正常使用？

企业最怕的不是 AI 不聪明，最怕的是 AI 很聪明、结果不可控或不可衡量。

## 九、个人提效 vs 组织提效：为什么一个人用 Agent 很爽，一家公司却不爽？

这是一个值得认真思考的问题。

很多人对 Agent 的最初体验，是把它当玩具——先让它写个简单代码，再挑战写个复杂的，发现居然可以，于是开始用它实现以前自己没实现好的东西。结果就是：晚上玩着 Agent，天亮了，第二天扛着黑眼圈去上班。一个人玩 Agent 很爽，但一旦把这个 Agent 搬到自己的工作里，就不爽了。

为什么？

答案是：个人提效靠的是体验，组织提效靠的是治理。

很多人关于 Agent 的讨论，其实还停留在个人层面——程序员说能让我写代码写得更快，产品经理说写 PRD 写得更快，运营说整理资料整理得更快。这些提效都是真实的，是个人的外挂。但它不是整个企业组织升级的方式，因为个人提效和组织提效是有区别的。

个人提效：核心在于体验，只要顺着自己的习惯工作就行了，知道上下文从哪开始、结果怎么用，甚至可以手动兜底、手动忽略某些错误——你不用考虑这些异常。

组织提效：要考虑的东西就复杂得多了——

这个 Agent 部署之后，怎么分发？

权限授予了之后怎么收回？

工具怎么被约束？怎么验证？

失败了怎么回退？

成本怎么追踪？

带了实习生，实习生怎么接手这个系统？

听起来头疼了？这就是重点。

个人层面用 Agent，主要追求的是"能用"；组织层面，追求的是"能治理"。所谓的工程化，其实就是治理。而大部分情况下，接受 Agent 之后，一直缺的都是治理。

如果把一个个人层面做得很好的 Agent 直接搬到整个组织里，中间造成的一个小混乱，会被放大成很大的系统混乱。个人的 Agent 是外挂，组织的 Agent 是生产系统。所以：

组织 Agent 需要工程化的能力

个人 Agent 需要技巧，追求的是体验

大家把这件事分开，就知道自己要往哪方面努力了。

## 十、可以模仿的标杆：Claude Code 的工程化启示

知道了工程化的重要性，有没有可以模仿的对象？

现在有两个非常好的参考：一个是"被动泄露"的 Claude Code 源代码（我只能这么说了），另一个是 Codex 的 CLI，也是开源的。这两个都是大家可以去学习的非常好的工具。

大家可以通过 AI 来分析它们的代码，完善自己的代码。重要的是，研究 Claude Code 的目的不是为了把它做一点什么输出、写本书之类的，更多是看：人家写这个 Claude Code 的时候，是怎么来设置它的约束条件的？

这里我提醒大家，有一个概念即将成为核心词——叫做 Harness（控制面）。相信很多人最开始听到这个词，感觉莫名其妙，不知道它是什么、有什么用。所以今天我们要先把"企业要什么、我们自己做的是什么"这个问题讲清楚，之后再来看怎么实现它的约束。

## 十一、Agent 是一个操作系统的雏形

在正式进入 Harness 之前，我要先给大家建立一个认知：AI 编码 Agent 不是传统的 CLI（命令行工具），它是一个在分发状态下能够运行的极其复杂的系统。

你可以把它理解为：未来它一定是一个操作系统。

操作系统是什么？把它拆开，它就是：能计算、能存储、能临时存储、能持久存储的一整套调度系统。

今天的 Claude Code，其实已经具备了操作系统的雏形：

能计算：它能生成代码

能记录上下文：上下文就相当于内存

能持久化存储：就相当于硬盘

System Prompt：相当于主板

它就是一整套操作系统的概念。大家记住：它未来就是一个操作系统。

传统 CLI 的特点是：发布之后，整个行为就写死了。但 Agent 不一样——在被用户使用的时候，整个行为仍然是一个动态的过程。模型可以决定：我到底调哪个工具，传哪个参数，什么时候继续，什么时候停止。这就是 Agent 和传统 CLI 最大的区别。

如果想学工程化，当下最好的参考就是 Claude Code。 但在学之前，我们得先解决一个问题：模型的行为可能完全是由代码决定的，我们怎么确定它在运行的时候是可控的？

这时候就要引出一个核心概念：Harness。

## 十二、Harness：约束模型行为的控制面

### 12.1 什么是 Harness？

Harness 这个词，被很多人传得神乎其神——但说白了，用普通话讲，它做的就是这几件事：

告诉大模型它自己是谁

它什么能做、什么不能做

遇到不同的场景时怎么做

如果有多件事，优先做什么

最后输出长什么样

运行的时候什么时候停、什么时候来问你

做得不好的时候怎么回退

就这几件事，简单吗？说普通话很简单，但这个简单的东西被大家传得那么神秘，其实就是名字起得比较吓人。

更精确地说：Harness 决定的是方向，模型决定的是上限。

用一个比喻：给汽车加了一车油，是发动机决定汽车能跑多快（这是模型）；而地图、走哪条比较宽敞的路、怎么进行防御性驾驶——往哪走，这才是 Harness。

用更通俗的说法：Harness 就是给大模型套上一套缰绳，或者是火车的轨道，或者是电动汽车的护栏。它不是让我们的 Agent 更加自由，恰恰相反——给 Agent 划定边界，它反而能更加高效。

一个必须颠覆的偏见是：Harness 不是写几行精妙的 System Prompt，它是从系统工程上拦截不安全行为的控制面。

### 12.2 Harness 的三层分层架构

很多人把 Harness 理解成一整块东西，其实它是有分层的。就像我们学网络的时候，不了解的人说"只要能连上、能通就行了"，但行内人会去研究分层——Harness 也是一样。

Harness 分三层：

第一层：宏观 Harness（全局控制）

管的是整体的系统运行控制，包括：系统提示词、角色设定、全局规则、安全规则、行为边界、上下文的注入方式。

宏观层解决的问题是：这个模型在整个系统里扮演的是谁？遵守什么角色？优先干点啥？

第二层：微观 Harness（工具调用）

管的是工具调用这件事。告诉模型：我有什么样的工具，什么时候该用、什么时候不该用，用的时候到底该怎么用，用完之后最后该怎么组织。

可以理解成系统提示词决定的是模型的"人格"，工具的提示词决定的是模型的"手法"。宏观 Harness 决定全局方向（战略层），微观 Harness 管的是局部动作（战术层）。

第三层：运行时 Harness（最工程化的一层）

这是最容易被低估的一层，也是最工程化的一层。它决定的是：

运行时的状态管理

运行时的权限校验

并发调度的设置

上下文的压缩

token 的预算

缓存

回滚

这些东西不是模型本身的能力，但它们决定模型最后运行的时候会不会失败。

### 12.3 研究 Claude Code 的真正目的

Claude Code 里有大量的约束条件。它写出来的代码那么优秀，而你直接跟大模型对话写出来的代码没那么优秀——差别在哪？就是在于哪些约束条件让这个模型更加优秀。这是大家研究 Harness 的主要目的。

Harness 的几个重要趋势：

从"编写提示词"走向"设计控制面"——核心护城河不再是对自然语言 Prompt 的技巧，而是构建系统架构层的代码防火墙、拦截钩子和行为约束状态机。

从"全局单体大 Prompt"走向"分层精细 Harness"——超级冗长的全局 Prompt 会让模型难以聚焦，未来方向是大量小体积、高内聚的分层 Harness 组件。

从"提示与引导"走向"强行约束系统行为"——放弃"请尽量安全"这类无约束力的提示，改由底层的沙箱层、文件路径限制钩子来硬性切断不安全动作。

Harness 跃升为企业级系统的绝对控制总线——随着企业对数据安全与合规零容忍，Harness 将超越具体的 LLM 模型，沉淀为企业级 Agent 部署的必要基础设施。

## 十三、Claude Code 的工程化分层：八层架构全解析

如果想学工程化，当下最好的参考对象就是 Claude Code。现在我们把它的分层方式直接给到大家。

大家可以利用手边的大模型，以及"被动泄露"的 Claude Code 源代码，去分析这套分层方式，看看能不能给你带来新的体验和启发。

我先抛一个很多人忽视的起点：Claude Code 的第一层，并不是模型的调用。

为什么这么说？因为很多人做出来的 Agent 看上去能跑，但把代码一打开，就是一大堆脚本拼在一起——这类 Agent 本质上是"功能的集合"。而 Claude Code 做的是"运行时"——它不是把工具堆叠上去，而是先定义好：运行的时候怎么把模型、工具、上下文、状态和界面都放在运行时里边协同工作。放进去之后，它还是先去做分层。

这就像我们学网络的时候，传输层进行传输控制，会话层进行 session 连接，应用层进行应用程序通信——网络协议栈在里面一定是分层去考虑的。Claude Code 的工程化设计也是如此。

下面我们逐层拆解。

### 第一层：运行时层（Runtime）

Agent 真正的难点，不是调用一次模型 API，而是让模型在你的系统里持续稳健工作。

Claude Code 的第一层是运行时层，其核心是 Agent Loop——整个 Agent 的主循环。Agent 和传统 CLI 最大的区别正在于此：CLI 发布之后行为就写死了；但 Agent 在被用户使用的时候，整个行为仍然是一个动态的过程，模型可以决定调哪个工具、传哪个参数、什么时候继续、什么时候停止。

运行时层的内部分层如下：

应用逻辑层（Application Logic Layer）：包含主要的 Agent Loop、工具系统、系统提示词，以及终端对应的 UI 交互。

宿主控制层（Host Control Layer）：比如 Claude Code 是基于 Node.js 运行的，这一层提供沙箱、运行快照、灰度控制等能力——这是宿主环境的运行控制层。

外部接入层（External Layer）：当上一层的能力不足时，向下穿透到这一层，比如模型的 API、MCP 服务器、外部的 skill 等工具。

这个穿透方式让人联想到操作系统的开发——应用层想用操作系统里的资源，通过 system call 找到内核态的工具；system call 比较原始，所以在上层再封装一个 library，让应用层更方便调用。Claude Code 的感觉与之非常相似。

系统允许模型知道什么、允许模型看见什么、允许模型决定什么——这才是运行时层真正做的事。

### 第二层：状态层（State）

第二层关注的是状态。

如果没有做好状态管理，Agent 运行久了之后，会退化成一大堆回调、一大堆临时变量——系统会出现各种不可预期的退化。Claude Code 的第二层，理解的就是运行状态的保持，就跟 HTTP 协议是一样的道理：传输的时候要确认账号是否登录、是什么界面、如果没登录要跳转到哪里——这个状态一致性，贯穿整个运行过程。

Claude Code 归入状态中轴的运行时状态，包含以下几类：

权限防御模式（Security/Permission Mode）：全局 Hook 及一键拦截规则状态

任务核心注册表（Active Task Registry）：当前正被模型展开的多步执行栈状态

MCP 连接池状态（Active MCP Server Connections）：所有外部服务的握手健康度

推测执行与预测缓存（Speculative Execution Queue）：在并发状态下对分支任务的探测

多维度会话开销（Session-level Token Accounting）：严防 token 消耗突破单会话额度

有了统一的状态中轴，Agent 才能回答一个关键问题：我当前运行到了哪个环节？这个任务有没有注册？上下文有没有协调？

任何不可见、不可撤销的状态突变，都是生产级 Agent 系统的灾难根源。 Claude Code 绝不在多轮模型调用里盲目传递状态，而是让状态成为一等实体，无论是权限锁的变化，还是推测执行的结果，都写入全局总线，随时向控制层广播。

### 第三层：工具契约层（Tool Contract）

第三层关注的是工具调用，但重点不在于工具有多少，而在于工具的契约。

这里有一个很重要的认知：工具越多，不代表系统越强。工具越多意味着上下文被占用得越多，当工具过多的时候，系统就可能出现各种问题。

Claude Code 本身有 40 多个内建工具，它是怎么设计工具调用的契约的？它在前面就设置好了调用的约束，这些约束通过 JSON Schema 来做校验——就是填空题：把所有内容按照指定的格式填进去，符合语义了就映射成对应的工具；不符合的话，就跳过这个工具，不使用它。

无契约、依赖随缘提示补丁的 Tool Calling，会导致模型频繁产生调用幻觉。任何工具如果其职责模糊、入参不确定，在自动化循环里就必定引爆死循环。

强契约必须能回答这三个问题：

明确的职责边界（Deterministic Scope）：这个工具到底解决什么问题？能控制在哪些确定的路径目录中？

触发条件白名单（Explicit Triggers）：在什么状态下允许大模型发起调用？在什么异常下严禁模型进行尝试？

类型自签名的输入 / 输出（Strongly Typed Schema）：不允许入参是无规则的 JSON，强制通过底层运行时拦截并提供类型纠错。

### 第四层：并发安全层（Concurrency Safety）

第四层关注的是并发，但要注意：并发能力不是代表你一次可以做多少事，而是在并发的时候，真正哪些事情可以并行安全地完成。

举个例子：假设我有两个 API 调用，都是对数据库做读操作——这两个操作能不能并发？当然可以。三个、四个、更多的读操作，也都可以并发。再比如一个读操作加一个全文检索操作——也可以并发。

但如果是编辑操作和写入操作呢？那就必须串行了。

更复杂的情况：让 Claude Code 执行一个 Bash 命令，能并发吗？天然不能。因为 Bash 里的命令不是原子化的，它天生就不能并发。

Claude Code 的处理逻辑是：首先让模型对操作做归类——只读操作可以并发，状态突变的写动作必须严防死守，Bash 命令则智能分类后默认拦截并单线程执行。

并发控制还有两个至高无上的防护原则：

原则一：先严格验证，再确定分类。 当模型传入的参数本身没有通过 Schema 安全检验之前，该工具调用绝不可能获得并发准入，所有校验层完全运行于独立的控制面。

原则二：异常即不安全（Fail-Safe Defaults）。 如果并发安全状态机在判定"某动作是否可以并发"时自身发生了任何报错、逻辑不确定或超时，系统会放弃乐观锁，自动回滚为最保守的单线程阻塞执行模式。

你看，一个再庞大的 Agent，把它拆到最后都变成特别简单的东西——这些基础又基础的能力。多 Agent 的价值不是来自于并发数量本身，而是能不能让并发成立——工程化在里边的作用，就是让你的并发能够成立。

### 第五层：权限治理层（Permission Governance）

第五层是权限治理。有一个规律大家必须记住：

能力越强，如果没有权限治理，风险放大的速度会比价值释放的速度更快。

模型能力越强，一旦权限没控制好，风险放大的速度会远远超过它产生的价值。

Claude Code 的权限治理分四个层次：

系统级拦截（Hook Filters）：处于核心控制总线，动态阻断或修改任何涉及系统底层的越界动作，决策选项包含 allow、deny、ask。

工具内部细颗粒度校验：当工具触发时，对输入的敏感数据深度自检，禁止外部 API 向有破坏性质的文件执行不规则参数写入。

强规则配置文件过滤：用户预定义的安全黑白名单规则。硬性铁律：任何试图加速判断的 Hook allow，绝不能覆盖用户显式配置的 deny 规则。

关键人机确认网关：对高风险动作（如删除核心分支、执行未在白名单的 Bash 命令）强制中断并唤醒控制台交互，必须取得人工实体确认授权。

所谓的纵深防御（Defense-in-depth）：系统绝不单点迷信任何一次判决，而是靠层层网关重叠把关。

权限系统的主要目的，是保证模型不会跨过企业的底线。这也是它真正带来价值的地方。

### 第六层：上下文层（Context Engineering）

第六层关注的是上下文。

这里我要给大家一个准确的认知，纠正一个常见的误区：真正的上下文不是记忆。

很多人把上下文理解为"让模型记住什么"。但上下文更准确的定义是：系统允许花多少钱来记住这些东西。

对应到你的电脑来说，上下文就是内存。内存不是硬盘——内存是易失性的，断电就没了。所以你一定不要把上下文当成持久化记忆来用。

为什么上下文需要专门的工程？因为模型现在虽然很聪明了，但还解决不了以下几个问题：

输入太多的问题

状态乱了的问题

系统没有存取预算的问题

举个实际的例子：做一次大模型对话，可能一次 grep 查找就搜索到了 80K 的文本，接着再 cat 读一个 200K 的文件，再加上 5 个业务日志文件……假设你的上下文是 500K，一下子就超了。上下文窗口不是无限的，更多时候我们要看的是它的时间成本。

Claude Code 的上下文治理范式有三个关键策略：

动态差异快照（Diff Snapshots Only）：不全盘吐出所有源码文件，仅剪裁出修改上下文和相关 AST 的差异变更节点，可以节省 80% 的 token。

垃圾回收机制（GC for Context）：对长时间未被触发的冗余工具输出和推理堆栈进行运行时垃圾回收，重置上下文权重。

预置阈值强熔断（Strict Cost Ceiling）：单会话设计最高 token 保护额度，一键触及硬红线时系统终止，杜绝大模型狂暴套娃调用。

盲目的上下文扩容，是高耗时、高价格与低稳定性的死角。

### 第七层：缓存优化层（Cache Optimization）

第七层是缓存。这一层很多人以前不重视，但现在越来越重要了。

以前不看缓存，是因为模型确实足够便宜；现在越来越看重缓存，一个是财务问题，一个是架构问题。

我要给大家一个可能颠覆认知的结论：缓存策略不是补充特性，它直接决定你的商业 Agent 在市场上能不能活下去、能不能盈利。

为什么这么说？因为如果能命中缓存，成本可以达到正常调用的 1/5 甚至更少。如果没命中，这里面就不只是技术问题了——你的产品可能就没有毛利了。所以对于今天的程序员，自己写的 Agent 有没有命中缓存，是非常重要的一件事。

Claude Code 设计了极其精细的三层内容缓存划分：

第一层：完全静态全局层（Global Cache） 跨会话、绝对稳定的通用系统提示、不可变的基础依赖结构和核心内置协议。全局缓存持久存在，实现最底层的基础 token 节约。

第二层：组织机构级共享层（Org-Level Cache） 在多租户或团队协作下相对稳定的组织私有知识语义、代码工程范式，以及共享的基础工具声明结构。跨用户复用。

第三层：动态内容零缓存（Zero-Cache for Dynamics） 凡是处于高频变动的分支文件状态、单次推理的会话级输入，坚决隔离出缓存机制，绝不污染全局稳定高速缓存。

模型每一次对海量静态工程库和依赖环境的重复解析阅读，都是一次纯粹的财务失血。如果无法在工程层面拦截相同的输入流，任何企图对外提供 SaaS 或 API 的商业 Agent 团队，都将面临毁灭性的财务负担。

### 第八层：多 Agent 协作调度层（Multi-Agent Scheduling）

第八层是多 Agent 协作，这也是当下越来越火的方向——workbody、各类协作 Agent 框架都在快速崛起。

多 Agent 真正的难点在哪？一定不在数量上。难点在于：怎么让几个 Agent 之间高效共享和同步状态。

进入复杂协作的时候，多 Agent 会暴露两个特别大的问题：

第一：任务边界不清晰。 你指定的任务可能就不清晰。Agent 的任务经常和团队、和任务是放在一起的——任务有普通的 to-do，有带阻塞的，有被阻塞的，有依赖别人的，有被别人依赖的，有马上执行的。在生成的时候就要考虑谁先谁后的问题。

第二：状态出现冲突。 很多人说"我把这个角色规划得很好，它不会冲突"——但这里忽略了一点：Agent 经常和团队、任务是一体两面的，角色划分再好，状态同步不到位，冲突一样会发生。

Claude Code 解决这个问题的方式叫做 DAG（有向无环路图）。它先把所有任务排成一张图，再基于这张图来完成整体任务，从而解决并发冲突的问题。

真正工业级的多智能体并驱，绝非让它们通过自由对话商量，而是靠底层的刚性状态机进行高频、精准地调度。 在大规模生产部署下，任由 Agent 之间通过自然语言自由聊天讨论，除了耗尽 token、制造通讯冗余和时延灾难之外，别无他用。工业级的调度器，在任务展开前就彻底编码了冲突路径。

### 八层架构总结

这八个层面，是我强制给它划分出来的。如果你自己划分，可能是更多层，也可能是更少层，但这几层刚好符合工程化的划分理念——从运行状态，到解决某个细节问题，再到联合起来解决多 Agent 的问题。这些解决方式，统称为工程化。

工程化解决完这些问题之后，我们的目标就已经不再是为了解决个人体验感的 Agent 了，我们解决的是组织的 Agent。

## 十四、从 Demo 到工程化：用五类指标衡量你做的 Agent

这里给大家一个实用的自检方法——你可以拿这些指标来衡量一下自己做的 Agent 到底是 demo 还是工程化的。

Demo 的特征：它展示的是高光时刻。所有的问题都被考虑得非常顺利，只展示最核心的能力，挑最适合展示的地方、最理想的输入、最容易体现智能感的场景。

工程化 Agent 的特征：我们在表现的过程中，看它的平均表现——有没有长尾的异常，它的边际成本是多少，在组织里是不是可复制的。

评估你的 Agent 到底是 Demo 还是工程化的，最核心的一个指标是： 做完这件事之后，业务结果有没有发生变化？

如果没有结果指标（比如工单关闭率、代码修复成功率、需求拆解准确率、客户满意度、知识库命中率），这个 AI 就是 demo。

## 十五、组织升级：个人 Agent 进化之后，组织必须重写分工

### 15.1 企业真正要建设的不是"万能 Agent"

到现在为止，大家应该已经看清楚了：现在企业为什么样的 Agent 买单，我们应该写什么样的 Agent。

企业真正要建设的，并不是那种什么都能做的万能 Agent，而是能够把人、Agent、标准 SOP、以及数据反馈建立成一个复合单元的东西——这就是 ReAct 模式（Reasoning + Acting）：在这个模式当中，我们把人融进去了，把标准业务流程融进去了。

这四个部分缺一不可：

人：用来定义目标，给 Agent 赋予指定的权限，做最后的裁决

Agent：负责执行、检索、分析、编排

SOP：把整个行业的经验做成可调用的 skill

数据反馈：告诉整个系统哪部分有效、哪部分失效，失效后该回退还是重做

这个框架给员工配上 Agent，有效性会比单独给一个 AI 账号高很多。

### 15.2 大炮不能直接配给骑兵

如果每个员工都拥有极强的个人 Agent，组织会自动变强吗？

绝不会。个人能力的极速增强，只会率先引爆组织架构的失衡。

当单个员工的产出速度、反馈半径被智能体放大十倍，而传统的跨部门协作流程、管理审批和业务交付依然运行在工业时代——失衡和内耗就不可避免。唯有彻底重写协作契约和边界，组织才能完成进化。

组织分工的重构，需要发生在三个层面：

岗位重构（Job Reconstruction）：彻底废除低水平、纯手工配置的工作岗位，向"人充当高阶评判与审核人，Agent 充当主力执行者"的全新技能模型过渡。

协作重构（Collaboration Reconstruction）：部门间的沟通从低效的会议和对齐，升格为直接交付可运行的 Agent 工作流与具有强契约特性的标准结构化协议数据。

管理重构（Management Reconstruction）：考核标准不再模糊，转向完全基于 token 成本投产比、FTR（首通通过率）、及自动异常响应频率的量化体系。

### 15.3 怎么判断一个组织真的进化了，而不只是采购了新工具

工具普及不等于组织进化。大家一定要记住这一点：你的公司买了无限量的 token，让你用 Claude Code、用 Codex——这不是进化，这是工具普及。

什么才是真正的组织进化？整个流程已经被重构了。

进化的标志通常有以下几个：

SOP 真正不是文档，已经被结构化地变成 skill 来执行了——操作手册和工作指令集不再是束之高阁的 Wiki，而是彻底序列化并注入系统的底层契约声明，成为 Agent Loop 能够开箱即用的指令协议。

业务知识不再只在聊天记录里，已经把上下文真正给到大模型了——变成了企业的知识资产，散落在员工本地 Excel、微信聊天记录和个人脑子里的操作边界，通过 MCP 和系统状态中轴归拢，永久沉淀，跨人复用。

Human-in-the-Loop 真正做到了谁输入、谁判断、谁执行、谁验收，分得更清楚了——岗位间的耦合和责任判定完全数字化、可视化。

AI 项目已经被纳入整个经营的指标分析，而不只是做个看板——每一个单节点带来的 token 费用和人力置换，在财务毛利层面形成刚性证明。

跨部门的协作，你的模型能不能跑通了——企业真正的升级，是能够像编排系统一样把它编排进去，让它真正运作起来。

终极信号：当跨部门、跨层级沟通时，大家讨论的主题不再是"大模型能不能写这段代码"，而是"这套基于 Harness 拦截机制的智能体系进入核心业务后，如何被严格治理、如何精准度量、以及如何进行无损复制"——这才叫真正进化了。

## 十六、什么才算企业级的 Agent 解决方案？

能对外交付的企业级 Agent，需要满足八个硬性条件：

前四个（业务侧）：

业务闭环：Agent 能不能解决企业的业务闭环？不充当答非所问的闲聊外挂，确保单节点业务流进入系统后能自动输出标准格式的确定性商业结果。

系统集成：能不能解决系统的集成？通过高吞吐的 MCP 和底层 RPC，深层无缝咬合既有的 CI/CD、CRM 及复杂权限中轴，消灭信息孤岛。

流程嵌入：能不能把这个流程绕进去？Agent 不是孤岛，它作为原子级的精密齿轮被嵌入企业现有大型软件管道中，完美适配全局工作流控制。

角色清晰：这个角色是不是足够清晰？拥有黑白分明的分工，杜绝大模型无边界推理，人是最终的审核、判定与责任主体，Agent 是高效执行器。

后四个（工程侧）：

安全可控：纵深防御，Hook 拦截机制与安全沙箱对高危突变写动作进行死守，遇未知异常一键自动完成状态回滚。

成本可算：将 token、缓存与会话生命周期作为一等财务资源治理，单节点业务流预算严密隔离，拒绝黑盒天价账单。

效果可评估：全流程指标覆盖——首通通过率（FTR）、人机介入比、异常频率和 token 命中率，一切用数据和平均表现说话。

能力可复制：废除依赖员工个人经验的游击提效，通过控制面和 SOP，将单人提效无损、成规模地分发和复制到企业。

## 十七、Agent 的终局不是聊天框，而是组织操作系统

说到这里，我们的结论已经很清晰了：

Agent 的终局绝对不是聊天框，而是组织操作系统。

大家不要再追求说"我们跑了最新的什么模型"——而是能不能把组织、业务和 Agent 编排到一起。编排到一起之后，企业的竞争力和组织的竞争力才能真正提升；你写的 Agent 才真正能变得有用；企业里的 AI 才真正有用。

未来企业的护城河不是拥有哪个模型，而是：换任何一个模型，这个工具都能运行得很好。

举一个大家都通俗易懂的例子：Claude Code 这个工具，大家都拿来写代码，但我们追求的不是它背后一定跑 Claude 模型——把它换成 DeepSeek，依然可以跑得很好。这才说明你的 Agent 写得非常有用，也是最简单的一个衡量办法。

未来企业最坚不可摧的护城河，绝对不是拥有某个大模型的 API 访问权，而是拥有吸收任何模型并将其转化为自身系统确定性产出的"组织操作系统"。模型正在以惊人的速度迭代，价格每天都在崩塌。谁能更早建立起刚性的 Harness 控制总线、成体系地重构岗位与协作契约，谁就能在这个模型商品化时代将智能吸纳为坚不可摧的企业私有资产。

## 十八、程序员成长路径：四个阶段打怪升级

说了这么多关于企业和组织的事，最后回到程序员自身——我们该怎么升级？

程序员未来的成长路径可以分为四个阶段：

### 第一阶段：把 Agent 当个人效率外挂（Individual Power）

学会使用大模型和各种 Codex 工具，关注个人日常编写代码、写周报的本地提效，局限于"体验"维度。这是起点，也是很多人现在所处的位置。

### 第二阶段：把 Agent 封装成团队可复用能力（Team Enablement）

将个人零散的代码技巧和操作经验编写为标准的提示词模板，封装成团队能够跨电脑、跨网络复用的轻量化功能组件。这需要的是：把这些工具的脚手架、测评流程、代码规范等等，都拆解给到 Agent 平台上。

### 第三阶段：接入业务流程并建立硬性考核机制（Business Embed）

不局限于工具属性，将其像齿轮一样咬合进公司的 CI/CD、看板和数据管道中，建立起 FTR、成本毛利和权限等全面可评估指标。把体系化做成解决方案，做成企业解决方案。

### 第四阶段：构建企业级解决方案与组织操作系统（Enterprise OS）

彻底接管企业的最核心流程。定义高内聚的人机分工四元生产单元，以高可用的控制总线（Harness）保障企业资产的确定性。你还可以把这个 Agent 接入到其他公司的业务，对外提供解决方案。

未来最值钱的程序员，绝非写代码最快的人，而是最会定义系统边界、契约与指标的人。

## 十九、程序员如何续命：五个不轻言退的战术抓手

最后回到这次分享的标题：程序员怎么续命？

程序员未来最值钱的能力，绝非编写更多行代码，而是把模型能力工程化，把工程能力组织化。

模型终究只是原子能力。真正的胜负手，是你能否用一整套不轻言退缩的控制面板约束它，在多并发、重权限合规、严控毛利的前提下，像精密的传统软件一样，稳定跑完每一笔企业核心业务的交易与动作闭环。

具体来说，有五个战术抓手：

把经验彻底协议化：废除模糊 Prompt，将个人 SOP 结构化为可调用 API 契约。把经验做成 SOP。

把工具强类型规约：通过严格参数格式校验过滤大模型不稳定的 Tool Calling。把工具做成契约，慢慢变成你自己的 skill。

把安全纵深堆叠：在应用逻辑层和沙箱容器层建立多重拦截 Hook 哨卡。你的系统运行时要是可治理的。

把成本一等治理：建立多级精细内容缓存，拒绝黑盒 token 天价失血。把个人能力转化成组织能力。

把局部智能系统化：让人、智能体与传统大型软件工作流闭合，对商业结果负责。把局部的最优解变成企业的解决方案。

## 二十、结语：代码写速度不再是核心竞争力

就像以前有 IDE 和 Vim 的时代变迁一样——没有 IDE 之前，大部分人用 Vim 写代码，谁能知道哪些函数、谁会查某个调用里有多少参数，这可能是个牛人。有了 IDE 之后，这份能力就不再有效了。AI 也是一样：有了 AI 之后，我去写通用代码的能力就不再是稀缺能力了。

怎么做？当模型放在这儿的时候，同时借助模型能力提升自己的工程化能力，用工程化能力提升组织能力，再用组织能力打造 Agent 产品——这是 Agent 走向商业化的过程，也是我们自己去提升的过程。

这个过程的三个自我评估：

对自己的技术重新评估一下——把以前的 demo 拿出来看看，它是不是真的 demo？

对企业项目重新评估一下——看看自己做的东西有没有以上提到的这些工程化属性。

对自身价值重新评估一下——我们是不是需要去学一些业务建模、系统工程，学怎么来组织和设计这样的系统，怎么来做这个交付的治理？

程序员的竞争力依然不弱，依然非常有竞争力——只是竞争的方式变了：从以前高级地写代码，变成我怎么来定义这个工具该怎么去用，怎么来定义 Harness，怎么定义软件工程。这才是未来大家的核心能力。
