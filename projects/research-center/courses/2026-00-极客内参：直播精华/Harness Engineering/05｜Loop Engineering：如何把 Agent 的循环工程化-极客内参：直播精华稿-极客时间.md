大家好，非常开心又回到极客时间给大家分享。今天我们分享的主题是 Loop Engineering，如何把 Agent 的循环工程化。这个是我思考了一段时间的主题，因为我感觉 Loop Engineering 这个提法有些重复，和 Harness Engineering 有重叠。没关系，我们从 Loop Engineering 背后还是能够体会到很深的工程内涵，甚至还有哲学内涵。

我们在讲解 Loop Engineering 的设计和实现的过程中，实际上是搭建一整套 Agent，尤其是执行型 Agent 的工程闭环系统的过程。今天我们仍然是以干货设计为主，从一个假想的微信小程序入手，我把它叫“到店吧”。

以前的小程序都是我们自己点，你要什么选单，比较自己喜欢的商品，下单，确认。现在我们让 Agent 给我们推荐，我就一句话，给我找到附近的比较人气旺的外卖，想吃水饺，你就跟它一说，这个 Agent 自己负责给你去从微信小程序生态中寻找发现。微信在未来三五个月、一两年之内遍地都是的小程序生态里，其实开放了 Agent 平台和生态，以后它的小程序都是一大堆的 Agent Service，或者一系列的 Skills，供你随时调用。

![](https://static001.geekbang.org/infoq/2b/2b3f75f7f96530271543b1cf8b0ca2fb.png)

## Loop Engineering 到底是什么

今天的分享认知负载比较大，因为概念、名词比较多。我先说 Loop Engineering 到底是什么，把概念说得明确一些，让大家都在一个平面上去理解问题。

![](https://static001.geekbang.org/infoq/d7/d756e34e5c57c7d45acdbdc478c90639.png)

我们先从工程师的新能力象限说起。这非常重要。我的最大的读者群，上来都会问，朋友你是什么技术方向？一半的人说，佳哥，我是 Java 后端。Java 后端现在进入了 Agent 时代，学习 Agent 的朋友最多。我们从能力象限的角度，是要往哪个方向过渡？

![](https://static001.geekbang.org/infoq/81/815e97b9496af33988f649bfabaab9a3.png)

传统的硬技能该保留的保留，代码、软件工程、调试、架构的权衡，这些站在过去程序设计理论基础上的东西，仍然在这个时代相当重要。从竖轴上看，你是逐渐从写代码过渡到搭建系统的能力。传统的软技能永远需要，现在更需要，需求的理解、业务的建模、团队的沟通，这些是我们现在最强的护城河。我不怕一个 AI 来跟咱们这样聊天，它没有我聊得好，这种沟通能力是我们要死死把握的。

横轴是从执行到设计的技能，也非常重要。我们从一个程序的编写者，要逐渐过渡到程序的设计者以及系统的设计者。这个部分特别强调规约的表达、验证的设计，尤其是评价体系的搭建。以前我搭建一套 Evaluation 体系，只是给自己测评用。现在我搭建出来的 Evaluation 体系，不仅给我用，给团队用，更重要的是给未来越来越聪明的 Agent 来用。所以这就是为什么我要强调 SDD（规范驱动开发），强调验证的设计，强调 TDD 测试驱动的开发，强调 Evaluation 体系的搭建，它是一举多得。

![](https://static001.geekbang.org/infoq/cc/cc780a487692167e4f320583eab84cf7.png)

那我们再从几本经典著作说起，这几本书也是我最近一段时间思考 Loop Engineering，看这些老书，发现它是有哲学底座的。到底为什么我们现在越强调让 Agent 自主循环 Loop，能够出现越来越多的智能涌现？

![](https://static001.geekbang.org/infoq/fa/fa0620cb473930127797b971330900a7.png)

第一本是凯文·凯利写的《失控》，他所说的造物九律，九个自然规律，其实就是和 Loop Engineering 和 Agent 的循环每天所做的事相当类似。沿着这条思想脉络，还有侯世达写的《哥德尔、艾舍尔、巴赫》（GEB），提出来怪圈和智能的涌现是怎么一回事。最后一本是《有限与无限的游戏》，帮助我们思考这个循环的边界在哪里。

### 从热词演进看 Loop Engineering 的定位

好，那 Loop Engineering 到底是什么？实际上我认为它仍然是 Prompt Engineering，但有一个区别，就是它的关注点在变化。

![](https://static001.geekbang.org/infoq/66/66834d6a54a5ea3e95dc7edc60d98141.png)

当我们做 Prompt Engineering 的时候，关注的是对模型一次调用的结果。经过 Context Engineering，也就是对上下文窗口的提炼和构造，落到设计模式里叫感知模式的设计，你把模型最需要的东西传递给它。那么到了 Loop 和 Harness Engineering 这个层次，你关注的是整个循环，多次调用，不断重复调用模型，要求在自我重复迭代很多次之后达到一个好的结果。

用一句话讲透 Loop Engineering：你不再一句句手动写每一个 Prompt，而是写一个程序，或者说设计一套循环，让这套循环替你去 Prompt。以前是自己一步步干，现在是 Agent 有一个目标，它就在行动、观察、判断，再继续行动，什么时候收手，在循环的过程中停止。

![](https://static001.geekbang.org/infoq/5d/5dd50fb950b29753f2eb2ac7045f26b6.png)

所以主语变了。以前是我做 Prompt，模型给我答案。现在是整个系统做 Loop，我得到一个结果，我不再手动调试任何 Prompt，我只是去设计不断给模型 Prompt 的循环。

![](https://static001.geekbang.org/infoq/fc/fc317981238ff7573bba7b4a1bcff72f.png)

这个过程中价值的单位也发生了改变。以前什么东西有价值？模型给我的回答结果有价值。现在我不太在意模型一次是不是做对，它可以做错，关键在于我能不能通过循环定位问题。从错到对，不断循环完成任务的轨迹，变得比一次答对更重要。

![](https://static001.geekbang.org/infoq/b2/b23913cf27ad6b8de3755f05c2a8097f.png)

因此我认为 Loop Engineering 其实就是我们一路以来所说的工程化本身。它从第一天开始就没有创造新概念，它就是 Harness Engineering，也就是我们一直给大家讲的 Agent 设计模式：怎么操控上下文、怎么调用工具、怎么管理记忆、怎么做对模型的治理、怎么把 Agent 变成一个很强、很可控、能够上线交付的系统。

![](https://static001.geekbang.org/infoq/88/889f052f60a101a07c23a2bf34bbf86f.png)

所以 Loop Engineering 就是 Agent 设计模式的工程化落地过程。模型早就不再是瓶颈，瓶颈在于这个循环的设计。

![](https://static001.geekbang.org/infoq/b3/b34ecf9a8c87ec0b19f9798515e0d215.png)

那我们如果用一个到店吧 Agent 的循环做例子，假设微信小程序生态允许我们做这种设计，通过一个循环，从用户说一句话开始，意图识别把我这一句话收敛成控制信号，后边的 Agentic 工作流就开始调度，编排着整个循环。调度器需要调用工具，调用微信能够给我的服务，这个过程中都需要有很清楚的参数的机械状态平面去记录。你还有有向无环图的传递，把步骤都设计出来。还有审核门和支付门护栏，什么时候需要用户确认付钱，该停就停，把循环交给人。你还有一系列可观测的玻璃罩系统。这个过程周而复始地进行，直到完成。

![](https://static001.geekbang.org/infoq/f8/f8be5a8a7c61b97030d84725f7405006.png)

### 《失控》的造物九律与 Agent 循环

说到这里，为什么《失控》这本书里提出来的判断越来越精准？凯文·凯利在 1994 年写的这本书，他说人造物越来越像生命体，生命体变得越来越工程化。

![](https://static001.geekbang.org/infoq/4b/4b654b17be9e69312539f02344d52a6e.png)

他提出的造物九律，和 Loop Engineering 逐条对应。

第一是分布式状态，到了 Agent 时代我们有多 Agent、子代理分布式的状态。

第二是自下而上的控制，其实就是我们所说的机械平面的自治和固定工作流的编排。

第三是递增的收益，就是复利效应。比如你的企业积累的技能越多，Agent 就越强。

第四是生命体会模块化往上生长。

第五是边缘部分越来越大，创新常常不在中心地带产生，越是有动荡、放的部分，系统就越有生命力。

![](https://static001.geekbang.org/infoq/e6/e674416c8a80006b798c3684d7ab63d8.png)

第六是礼待错误，要尊重错误、重视错误。我们设计模式里有一个特别的模式叫失败日记。当 Loop Engineering 过程中出错了，这些错误就是你未来避免类似错误发生的必要条件。Agent 要对错误有一个非常开放的态度去记录、去容纳，把错误放在一个位置，什么时候还要召回这个错误，能够避免第二次重犯。

第七是不要求最优，目标众多，不追求单一的最优解，因为单一的最优解往往很脆弱，这是一个反脆弱的思想。

第八是持续的不均衡状态，生命系统的活力在变化、张力、扰动中存在。因此我们的思维要逐渐从设计固定系统变成设计一个不停 Loop 演进的 Agent 生态。

第九是变自生变，变化本身来自于变化。

我通过不断积累技能、沉淀技能，下一轮的 Loop 就变了，跑在我之前积累的 Skills 上面再去重新 Loop 就不一样了。我每 Loop 多一次，我的企业、我个人就多了一个 Skill。比如说我们科研单位正在开发科研智能体，现在很简单，有一套系统、一套规矩，所有科研人员跟着这套规矩做科研，所有对话都在系统中发生，所有结果都被记录。大家说没什么好处，我还是干昨天那些事。但不要小看这个过程，三个月之后，几千个科研人员每天的科研对话，系统就可以开始沉淀，提炼 Skills，系统加上科研人员就可能越来越会做科研。从第一天积累也是很重要的，不积累，两年之后还是从零开始。

## 从一个用户旅程开始

好，那现在我们就开始。用户需要做的很简单，他说好了，今天订两个人的火锅，细节不管，150 块钱之内就行。这就是小程序收到的全部内容。

![](https://static001.geekbang.org/infoq/cf/cf9c01443b4025fa0284233d1f098355.png)

这句话背后一套旅程就开始了，先帮他找到合适的门店，比较套餐看哪个划算，下单、支付，最后出票。这就是我们所说的执行型 Agent 的承诺，它要跑通一套真实的任务。

![](https://static001.geekbang.org/infoq/7c/7c30095d7d85b50f4508f63893bff9d3.png)

所以这是第一个关键概念，执行型 Agent 不是对话聊天型的 Agent，不是内容生成型的 Agent。什么是内容生成型 Agent？给我做个报告，没有对错，它怎么 Loop、怎么多次之后，反正给你一个东西，你打 10 分就是 10 分，打 8 分就是 8 分，那个东西没有标准。但是执行型 Agent，如果我下了单，它给我付错了钱，我是要投诉的、要索赔的。所以这种东西跟让它给我做个研究报告完全不同。

![](https://static001.geekbang.org/infoq/21/21eabc047e6426a15d5171947c197ae6.png)

最小闭环就是一个 ReAct，想、做、看，做不好再想、再做、再看，直到完成了就搞定。这就是我们做 Demo 做到这个程度就可以了。但是在真正的执行型任务上，没有一个产品能够通过这样一个最小 ReAct 循环就完成，这是不可能的。

![](https://static001.geekbang.org/infoq/06/0630854783984b52818c3696c9efc551.png)

在真正的产品中，这种循环会崩盘在多个节点。模型跨步漏步、参数漂移、虚假成功。Agent 有时候也是讨好型人格，它内部已经失败了，不知所措了，最后跟你说已经成功完成了，等着吃饭吧。也有可能死循环，一直调 API 一直调不到，停不下来。上下文爆炸、失控的情况都有可能出现。这种循环如果没有控制，你其实是在把整个程序的设计交给运气。

![](https://static001.geekbang.org/infoq/3f/3f2a412d6f93cd24d518eff225420847.png)

这就是执行型 Agent 的难度。内容生成型的你可以不去调试，做得不好再给一些额外 Prompt，它下一次真的做得更好。但执行型 Agent 的结果更重要。

![](https://static001.geekbang.org/infoq/0c/0c4df3fb503a9ac582b08c731bf403c9.png)

解决方案就是把工程化循环在每一个环节需要明确管控的地方，全部进行治理。该感知的东西要给，该记忆的失败日志要记，行动轨迹要存档，每一步的思考和行动调用工具的过程都要用可观测性呈现出来，每一步机械状态的进展都要记录下来。治理和停止条件，出错怎么 Rollback，死循环怎么停止，都需要详细设计。

## 认知地基与设计地图

这个过程需要把控制平面和叙事平面拆分开，这就是我们所说的二元论。

![](https://static001.geekbang.org/infoq/4c/4cd63d43858ec1a3e7bf858ed509db2e.png)

叙事平面是自然语言、语义、人话的东西，存储在一个地方。控制平面是离散信号，要么对要么错，要么是订单 ID 要么是其他订单的 ID，控制程序分支往哪个方向走。以前做系统架构你可能只有机械控制平面，不需要考虑叙事。这完全是在 Agent 大模型时代出来之后才有的。

未来的架构是叙事平面和控制平面二者的有机结合。叙事平面负责发散，负责很多未来的可能性，我在这个平面进行 Loop 才有意义，它不断变化，因为是自然语言的叙事、大模型思考推理的结果。控制平面负责收敛，把你说的一大堆东西收敛到离散信号里去驱动，你要调哪个美团的订单服务，得真正把东西给人家买了。

![](https://static001.geekbang.org/infoq/36/36bfe7847c13d7e30e2ab885cc4ed996.png)

再衍生出来第三个平面，调度平面，就是 Workspace、Orchestrator，各个节点的状态，工作流程执行到哪里了。一个 Agentic Workflow 的循环是通过叙事平面、控制平面、调度平面三个平面相互配合，才能够产生完整的 Loop 结果。

![](https://static001.geekbang.org/infoq/60/60c6e560787ae943676867f897da2304.png)

再说到 Agent 设计双轴框架，通过认知功能和执行拓扑进行组织。这是 Loop Engineering 整体框架中的一套共同语言。在设计每一个 Loop 工程节点的时候，我都需要思考可以复用什么方面的设计模式。

比如说失败日记模式，当我订餐给我订来了某个店，我很生气，除了他家啥都行。Agent 没错，但我给了差评。这个失败相当有特色，针对我这个 ID，以后下单的时候千万查一查附近的鼎泰丰，口碑再好也排除出去。这就是一次成功的经验记录。

再比如治理模式，到店吧小程序付款需要用户确认，走到审批门模式。产品经理可以递要求说不可超过两次审批门，因为我就是为了跟它说我要吃包子，20 分钟后吃到，不要让我再点超过 3 次。在这个约束下，设计 Loop 的人就说，人审批不可以超过 3 次，付钱时加一个审批，确认买包子可能加一个，最多两次。

## 把 Loop 工程化

基础理论讲完了，储备知识搞定了，我们就进入工程。现在要设计到店吧这个 App，在每一个层次中都需要设计什么？

![](https://static001.geekbang.org/infoq/f0/f073a77e65efe99efbf5b0f3bfc10472.png)

这是它的循环全貌，四层运行时。用户入口层，从小程序发起委托。协议层，把入口委托承载了，开始做意图识别、小程序 MCP 连接、Skill 选择和策略路由。能力层，包括各种 Skills、MCP、原子接口、原子组件，结构化的数据和可以跟用户 UI 渲染的卡片。状态治理层，编排器、Workspace、DAG 图、机械状态平面储存、Payment 和可观测性 Tracing。

![](https://static001.geekbang.org/infoq/32/32b15869678f0a3c03ee15b0ad59d0ec.png)

首先看循环入口，怎么把"订火锅 150 块钱"转成机器语言。我需要把它收敛成离散的控制信号。一句话做收敛，Task 是 BuyFood，FoodCategory 是火锅，Budget 是 150，Time 是今晚 6 点到 9 点，Confidence Level 0.93。你实现了从模糊自然语言到精确意图识别的收敛过程。

![](https://static001.geekbang.org/infoq/15/15d5e84d08b3e037e5ad0b447705fb68.png)

意图网关路由判定搞定了之后，就到了 ReAct 推理行动的第一步。然后是调度大脑 Orchestrator 的设计。用户消息先到 MessageHandler，收消息、展示结果，不负责业务解决。Orchestrator 是真正干活的人，拿到意图识别给出来的控制信号，交给 ReAct 去做事、编排下游链路。如果某一步做错了，Orchestrator 不会从头再来，它对流程都有记录，会按状态机回滚到最后的断点再重试。

![](https://static001.geekbang.org/infoq/44/44b4b41cb0a1f0a4b52ed1cfabfbf1ae.png)

在这个过程中最重要的核心思路，就是机械状态平面的设计。每一个 ID 和任务数据结构都要清晰地存储在状态平面中，供审核、供调用。User ID、Store ID、电话、地址、SKU ID、Cart、Coupon ID、Payment Session、Order ID、Ticket，这些全都是最重要的机械状态信息，每一个都不可以出错。

记住，参数的记录和传递不能完全交给模型。确定性的值必须由程序进行机械掌控。每一个参数都需要有可审计的来源，这个叫 Provenance 坐标。所有的参数哪来的？订单 ID 谁生成的？什么时候生成的？传给哪个小程序了？越是在 Agent 时代，我们让它自己一直 Loop，这些可以留下的痕迹，对于 Agent 到底做了什么、怎么做的、调用了谁，是非常重要的审核来源。

![](https://static001.geekbang.org/infoq/50/501207c921f4e81f174bd660d7ba6363.png)

任务状态机也是关键。每一个委托都是一次有状态的节点，能够被追踪、被回退、可以验收。某一步失败需要回退多少，这些都需要在设计工作流时设计出来。到了一定程度输出一个原子卡片，门店卡片、套餐对比、订单确认。如果产品经理说不能让用户确认太多次，就把几个原子卡片集成起来，用户点一下就行。

这里有一个设计思想：让计划活在代码里，让创意活在上下文里。到店吧这个小程序，我更愿意让它生活在代码里，因为最重要的事，别把人家订单搞错了，不要让人家买包子你回来给人家饺子。但科研场景就不同，可以给更多灵活性，让它更多生活在上下文和积累的 Skills 里，有可能发现更多新的灵感和东西。

![](https://static001.geekbang.org/infoq/fe/feda2c2f9cb1c0efea7e521698664c68.png)

循环的护栏就是这些，该支付的时候必须有用户确认，加一个支付的审批门。

![](https://static001.geekbang.org/infoq/92/9217461b90e43d05adf01e0f7e3960a6.png)

最后是全程轨迹观测，要透明。一次对话，LLM 调用了什么，意图网关路由走到哪个值，选店、选套餐、选优惠的环节，调用的是哪个 Skill、哪个 MCP，推理和行动的结果是什么，一共几步，工具调用怎么个情况，全部一清二楚。这是给开发人员的可观测的玻璃罩。

![](https://static001.geekbang.org/infoq/79/79e1fd104b538d88a3ed157565d90533.png)

梁博老师有一个很好的比喻。我们有一个手表，正面是客户看到的清清楚楚的结果，给你一个包子，套餐就是 20 元。但把手表翻过来，背面是一大堆齿轮和机械步骤，很多工具啮合在一起，非常复杂。这就是循环的每一步到底怎么走的。用户看到很清晰的界面，这是手表正面。我们程序员看到的东西，是大模型的思考平面、控制平面、ID 和工具调用的各个环节，全部都在玻璃罩后面呈现。

## Loop 的边界与灵魂

![](https://static001.geekbang.org/infoq/4f/4f8ce0b48cb50f5f9bb63074b6972dd3.png)

Loop 的安全边界要有数。什么东西工具可以读，什么写操作要注意隐私、支付、模型不确定性的东西。

![](https://static001.geekbang.org/infoq/7e/7e8be509107ba53e892cdbb98ee64fda.png)

Loop Engineering 的另一个灵魂，就是你 Loop 的边界在哪里？边界和停止条件是循环本身的一部分。支付场景的边界比研究场景严格得多。研究场景越发散越好，灵感来自于系统的不确定性和动荡。但做支付、做企业级 SaaS，就没有这么多灵活性。

说到 GEB 这本书，它的主题是怎么样通过无意义的符号涌现出意义和"我"。人工智能大模型不就是通过一圈一圈的循环神经网络、Transformer 不停迭代，涌现出来了一些让我们觉得是强人工智能的意义嘛。

![](https://static001.geekbang.org/infoq/b0/b0f82ce20ee92c9d45781556836e9181.png)

怪圈理论告诉我们，不要在循环过程中自己给自己打分。对循环本身的验证，必须来自于循环的外部。在 Agent 场景中，可以通过机械平面的真值去验证，用户真实地去验证，或者换成另一个模型去验证，用 Claude 和 GPT 相互校验，因为它们是通过不同数据训练出来的，品味和想法还确实可以互相提高。

《有限与无限的游戏》把世界上一切活动分成两种游戏。一种是在边界内玩，有限游戏，有规矩，有终点。一种是边界外边玩，无限游戏，规则由自己定义，没有终点，可以一直玩下去。这本书的精华就这么一句话：有限的游戏是在边界内玩，无限的游戏玩的就是边界。

换成我们这一单火锅，一单火锅就是一个有限的游戏，你只能在他附近有限的选择中选最好的一次。但如果把这个东西看成一个循环的生态，它就是一个无限的游戏。你的 Agent 越来越了解主人今天想吃啥、明天想吃啥、后天不想吃啥、啥时候吃火锅吃烦了。这个 Loop 不需要局限在这一单火锅本身，下一单呢？那就是另一个事了。如果你认为这是一个无限的游戏，你的 Agent 可以变得越来越聪明，到最后都不用主人说，它知道每天下午 6:30 自动给他订火锅。

![](https://static001.geekbang.org/infoq/44/44d5d712dff221bde45717a44a76581c.png)

哪些场景值得上比较重的循环？看你是执行型还是内容型，是单步 Agent 还是长程任务组合。执行型乘以长程组合，两个轴都过了才值得。

![](https://static001.geekbang.org/infoq/25/25c78a5177bcc8fc05f22f93ed01cdc4.png)

总结一下今天的几个重点判断：Loop Engineering 就是 Harness，就是工程化本身。先分执行型和内容型。模型的思考是叙事平面，机械的执行是控制平面，机械状态平面的数据准确性、Provenance 是重中之重。计划活在代码里，不是由上下文束缚。要有清晰的有向无环图。边界和停止条件是循环本身的一部分。用无限游戏的心态去设计有限游戏的边界。
