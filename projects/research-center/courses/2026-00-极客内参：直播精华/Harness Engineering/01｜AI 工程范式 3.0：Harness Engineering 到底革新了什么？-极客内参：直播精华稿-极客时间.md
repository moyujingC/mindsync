AI 工程范式 3.0——Harness engineering，这个题目可以说是 2026 年 AI 工程领域最重要的一个概念。那么今天直播的内容，应该也是未来指导我们未来两到三年做 Agent 系统架构设计的一个思维导图。

先从一个问题开始，我们看一看，就是说为什么我们进入了 Harness 时代？

真实的事故：Agent 的“隐形风险”

我们用一个真实场景说明问题，让一个 Agent 修复线上 Bug。它精准定位了异常，修复了代码，还贴心地更新了所有配置文件，最后部署到生产环境。一切测试通过，看起来完美（大家都这样做）。

但问题在于，它把 staging 环境的测试数据库地址写进了生产配置。所有测试仍然通过，而生产系统的真实流量就这样流入了测试数据库，我们毫不知情。在 Agent 时代，Agent 在后台做了什么，我们往往并不清楚。

所以，Agent 最大的风险不是"出错"导致测试失败，而是它看起来一切正常，但方向完全错了。

这不是危言耸听。就在前几天，Claude Code 的源码泄露事件——仅仅因为一个.map 文件被打包进 NPM 包并进入生产环境，51 万行就被完整还原。

这些事件启发我们未来设计 Agent 系统时，不能只追求模型更聪明，更要思考如何为 Agent 设计外部的约束与治理体系。

Harness 的本质：不是限制聪明，而是限制聪明的使用方式

“吾生也有涯，而知也无涯。”

（我在准备这个直播的时候脑海始终萦绕这句话）

在这个时代，知识的边界几乎被消除，Agent 的能力可以无穷无尽。但 Agent 力量的来源不仅仅是能力本身，更重要的是你如何为它设计外部的 Harness 系统。

Harness 不是限制 Agent 变聪明，而是限制这份聪明如何被使用、落到哪里。你需要一整套系统，包括权限、约束、检查、隔离、审批、环境、边界，所有这些东西都要系统化地组织起来。

去年没有人谈论这件事，因为 Agent 还没走到这一步。今年我们必须讨论所有在模型和 Agent 外围的生态，即 Harness Engineering。更深一层的思考时，真正危险的不是“你知道某件事有风险”，而是“你根本不知道这里有风险”。

做 Harness 不是靠一个人的能力来做一个完善的系统，而是大家齐心合力地去驾驭这个 agent，一起打造一套约束系统，能够防住一些你不知道、我也不知道、但 Agent 知道的东西。是不是我们应该朝着这个方向去设计这个系统？

【彩蛋】Hermes ：不是虚假爆款，和 OpenClaw 一样都是很有用的 Agent 发展方向

近期 Hermes（“爱马仕”翻译法为法语发音，亦指天神赫尔墨斯）引起广泛关注。我认为它并非虚假爆款，而是真实且会持续深化的发展方向，与 OpenClaw 一样，都是极具价值的 Agent 发展方向。

本质区别

Claude Code 的 Harness：需要手动配置，包括编写 Claude.md、定义 Skill、配置 Hooks、设置 headless 模式等。过去一两个月我们主要在做这些工作。

Hermes 的 Harness：能够自我进化。在完成复杂任务的过程中，自动提取 Skill、自动优化 Prompt，使 Harness 随用户协同进化。

在使用 Claude Code 时，不知道你是否有和我相同的体验？我常主动要求它总结固定模式并生成 Skill。例如，处理书稿时发现第一章有固定开头模式（如使用成语），便让 Claude Code 分析是否存在可复用的写作模式。有时它会建议不生成 Skill，因为需要保留人类的创造力，天马行空一些。这种互动是相互激活的。

对于 Hermes，我后面也会试一下，在不主动要求的情况下，经过一段时间的协作，它能否自动总结出 Skill、了解我的习惯并实现自动进化。本质上，Hermes 是一个自进化的 Agent，大家也可以自己去玩一玩。

Hermes 具有程序性记忆：

声明性记忆：人写的（如 CLAUDE.md）

程序性记忆：AI 自动生成 skills。任务完成后自动触发 skill 创建，下次遇到类似问题直接加载该 skill。

思想比实现更重要（也是未来行动营里带大家强化训练的）。

#### Harness 架构是如何设计的？它解决了什么落地卡点？

##### 初识 Harness

Harness 是包裹大语言模型的运行时基础设施，管理工具调度、上下文、安全状态、持久化、会话连续性等。大语言模型仅负责推理决策，其余均为 Harness 职责。

![](https://static001.geekbang.org/resource/image/46/0b/4612c5fc9cd7471a549542e7708c670b.png?wh=1918x1046)

公式表达：Agent = Harness + Model

与现有框架的区别如下 。

框架（Framework）：如 LANGGRAPH、Deep Agents、AutoGEN、Meta GPT 等，提供搭建系统的库和结构方向。

运行时系统（Runtime System）：Harness 是真正的运行时系统，可用各种框架实现（Python、TypeScript 等）。

好的 Harness 系统就是要考虑很全面，因为我把所有的东西都交给 Harness 了，这也是企业级系统设计需要重视的地方。第一步是完成任务最重要，那么下一步我们完成任务完成得是不是漂亮，是不是安全，其实才是最重要的。

做个比喻，你的模型或者 Agent 就是一匹烈马，我们思考未来两到三年所思考的就是怎么去驾驭它，把它驾驭得更好。一匹马有人骑得一般，有人会骑得非常精彩，区别就在于 Harness 设计。

##### Harness 核心组件

![](https://static001.geekbang.org/resource/image/fd/36/fd898202842e323f45f628d1e8bcf236.png?wh=2334x770)

最核心的是第一个 Agentic Loop，你也可以参考 Claude code，它是如何完成这个组件的。工具系统也可以参考 Claude。它就是基于搜索、查询、查找、读写等原子操作，不依赖向量数据库构建与索引系统，就是暴力搜索然后解决问题（速度很快）。上下文管理也很重要 ，我们稍后展开，先认识到它的重要性。

如果你看我们的 Claude Code 工程化实战这个课程，你会发现到处都是权限控制，它覆盖在每一个组件的方方面面，因为权限控制是重中之重。

LangGraph 框架就采用状态图实现状态管理。我记得有个词， Time Travel ，从这个状态恢复到之前的情况。你自己从头搭，那这些持状态持久化，你就要自己全部自己实现手工实现。那么如果有 LangGraph 这种框架，你就可以快速的实现这种对话历史工具，结果会话恢复的状态持久化。而事件钩子就是工具执行前后的自动化的一些拦截。

##### 少即是美与结构化思维

一个核心的设计哲学是：很多时候简单就是美。我们有时会觉得一个系统拥有几百个工具看起来很厉害，但需要反思——如果工具数量超出了头脑的认知负荷，这个系统就不够“美丽”。像 Claude Code 这样的 Agent 系统都没有几百个工具，那我们在做系统设计时是否应该停下来思考？并不是说几百个工具一定错误，而是要考虑是否需要组合、重新组织（Organize），让它变得更清晰。

我们都喜欢简单清晰的结构。Claude Code 反复做同一类事情，结果却能神奇地完成任务。例如，我可以告诉它。“这是一个新主题，不要从我的知识库里搜索，去上网查。”它就会执行 Web Search。

最优的工具数量，就是边际效应递减曲线的平衡点——不多不少，过犹不及。Claude Code 源码带来的重要启示是：大约 15~20 个工具，模型的"选择焦虑"就会下降。

结构化思维：当我们面对一个新系统或一套学习资料时，不要试图设置 200 个章节。先归纳成七八章，每章再细化成几个小节，有条有理地组织起来。这种结构化思维避免了焦虑，这方法也适用于公司管理——十几个部门互相协作，比 200 个部门的大公司病要好得多。

##### 上下文管理

进入 Harness Engineering 时代，Context Engineering 仍然是最关键的能力。它的本质仍然是 Prompt Engineering。我的专栏课程群有同学分享了一个有趣的漫画：一个强盗说“我来了，我是 Harness”，摘下面具，里面写着大大的“Prompt”。这揭示了一个事实：最重要的东西仍然是你对模型说了什么，决定了输出质量。

所有人都拥有最强的模型（如 Claude Code），但为什么有的人能迅速让 Claude Code 抓取精华、探讨出优质内容？因为其 Context Engineering 和 Prompt 做得好，能够精准打中模型的点，引导其深入思考：“这个不行，不是我们想要的，继续想”“我不满意你刚才的陈述”“你看我积累了这么多内容，我们从中发现更多精华”。这就是我和 Claude 切磋的方式。

##### 问题：是否有上下文管理的方法和技巧？

答案，有解。你可以等待模型自动压缩上下文，但关键是要理解它自动压缩时做了什么，然后你也要做同样的事情。

核心做法（参考 Claude Code 的自动压缩逻辑）：

保留最近的消息（完整消息，最重要）

压缩早期的消息（生成摘要，因为早期消息可能不再需要）

重新注入系统提示词（注意：CLAUDE.md 不是系统提示词。系统提示词包括：你有哪些 tools、你有哪些 skills。工具定义每次都要告诉大模型，因为它“金鱼记忆”，每次都会忘记）

如果你不想让模型自动压缩，而是主动压缩过长的上下文，就必须做以上三件事——保留、压缩、重新注入。不能随意压缩，要做好上下文管理。

##### Memory 系统：显式记忆与隐式记忆

Hermes（赫尔墨斯 / 爱马仕）——今天的刷屏词。Hermes 是负责沟通的神，也是商业使者，寓意 Agent 能够自己进化、越来越会做事。我们希望 Agent 能像 Hermes 一样帮助完成大量沟通和日常助手工作。

我认为，深度交互仍然最重要。我每天使用最多的 Agent 仍然是 ChatGPT 这类对话型模型——每产生一个思路都去问“你觉得怎么样？”，经常质疑“你还有没有其他角度？”。大模型能带给普通人的是“平庸的优秀”，而批判性思考能让我们超越它：“你还有盲点，有些东西你没想到，不要止步于此。”

两种记忆系统说明如下。

显式记忆：项目级的规定和约定，写在 CLAUDE.md 中。例如：React 组件用一套规则，Python 用 Python 规则，Go 用 Go 规则。因为 CLAUDE.md 每次会话都会传递，需要渐进式加载——通过 rules 配置让模型按需访问 react-rules.md、python-rules.md 等。

隐式记忆：claude-memory 目录（后来补充）。Agent 自动存储的用户偏好和反馈。需要主动告诉它“把这个写入 memory”，否则它不会记录。这个系统文件夹相当于帮你记日记，你可以定期 review 是否仍有意义。如果项目或个人偏好改变（比如从黑背景 PPT 改为白背景），需要调整 memory 中的内容。

##### Hooks：条件反射式的强制机制

Hooks（钩子）类似于 Python 中的 callback 函数——当某个事件被触发时回调执行特定任务。

工具执行前触发：适合做拦截、修改、权限检查

工具执行后触发：适合做校验、审计（已执行完，拦截无效，仅检查）

Stop 结束时触发：做汇报、清理

重要区别：

Skills：概率性调用（可能 99% 会调用，但不保证 100%）。例如写 PPT 的 skill，模型有时会自己生成一套 PPT 而不调用该 skill。

Hooks：强制性，一旦设定必须执行（例如“检查是否 push 了不该 push 的文件到 GitHub”）。在 Harness 系统中，Hooks 至关重要，因为我们要“给野马套上缰绳”——自动做 formatting、lint 检查、测试校验。

刚刚说的这些东西从 Harness 架构角度看都是重要的，因为我们是在做系统，不是在做玩具，这些东西能够帮助到我们系统设计的方方面面。这是系统演进带来的变革。

#### 软件工程三时代演进：从固定到分布到概率

第一代：固定逻辑（单体软件工程）

计算机 1+1=2，固定

面向对象、设计模式

业务架构搭建

第二代：分布式逻辑（互联网 / 移动互联网高并发时代）

每个 Server 是固定逻辑，但 100 个 Server 的集群需要考虑灾备、扩容（如双十一）

代表：Google MapReduce 论文，海量数据切分到不同 Server 处理再汇总

核心问题：稳定性

参考书籍：李智慧《大型网站架构设计》

第三代：概率逻辑（Agent 时代）

大模型是概率机器（例如 9.1 和 9.12 谁大可能答错）

系统不再可信任（非固定，非稳定分布）

新增思维：概率思维

优秀架构师的要求：同时掌握面向对象、分布式高并发、概率时代三者的透彻理解。

Permissions：安全围栏与精细粒度控制

核心矛盾：希望 Agent 自主，但又要防止失控。Permissions 就是解法。

Bypass Permissions：在测试系统（如训练模型）中，可以 bypass 权限检查，避免反复回答“可以吗？允许吗？”的问题。在 VSCode 中设置 plan mode 和 bypass permissions 即可。

精细粒度控制：allow/deny 具体行为，拆分成细粒度的规则。可以设置 sudo 及下属权限。

目的：不是限制能力，而是定义行为边界（例如“可以订机票，但不能泄露个人信息”）。

Harness Framework vs. Orchestrator

Framework（如 LangChain、OpenAI SDK）：帮助写代码、定义流程、调用接口，适合确定性工作流。

Harness（如 Claude Code、OpenClaw）：运行时的基础设施，包含循环、工具、上下文、规划等。

##### Claude Code 和 OpenClaw 为什么都是 Harness 的优秀实现？

Claude Code（标杆）

单人深度交互，纵深型

启发思维和智慧，适合工程师设计项目

业界的绝对标杆

OpenClaw

不是为单人编码场景设计，而是为平台级 Agent 服务设计

外向型、广度型

架构层级：

采集层（抓数据、形成知识）

交互层（对话式查询，连接多个 Bot）

分发层（帮做运营，发到飞书、邮件）

目标：帮你搞运营、运维，不指望带来深度思考

个人感受：Claude Code 纵深，OpenClaw 广度。两者配合——核心用 Claude，外围用 OpenClaw 做运营运维（这也是我们在《多 Agent 设计与工程化行动营》里对两者的运用思路）。

#### Agent 时代的工程师，需要掌握哪些核心能力？（Harness Engineer 核心能力栈）

核心能力栈（Harness 时代需要学会的）：

规范设计

工具编排

循环治理

上下文工程

质量保证

成本控制（Token 计量、预算熔断、模型降级）

专门强调一下，在 Harness 系统中，可观测性很重要：每个环节用了多少 Token，循环了几轮，调用了哪些工具，Token 花费多少。以前只管完成任务，现在要管——不能一天消耗太多 Token。这些能力目前很少有人掌握，先学会就能在团队中鹤立鸡群。
