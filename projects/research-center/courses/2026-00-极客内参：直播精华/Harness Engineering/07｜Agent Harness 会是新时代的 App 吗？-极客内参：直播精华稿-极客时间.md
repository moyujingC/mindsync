过去几年，AI 技术持续演进。真正值得关心的，不只是模型又变强了多少，而是它将如何改变我们使用电脑、构造软件以及组织业务的方式。

如果你要问我： 最近一段时间里面，或者在最近几年里面，随着 AI 这些技术的发展，让我感觉到最震撼？或者说让我感觉到“大人，时代变了”这种感觉的是什么？

其实是今年 6 月份，正好是老黄在台北宣发他的新款芯片。他讲有一个桌面级的 GPU 可以跑全量的大模型的工具，他最终的理想其实是和微软有一个战略合作项目，会把他所有的大模型做到操作系统的内核当中去。在老黄的畅想里，我们未来的电脑的形态可能就是操作系统，中间有一个大模型。

一个很有冲击力的设想是：未来，大模型可能进入操作系统内核，成为所有功能的统一入口。用户不必先找到并打开某个 App，只要直接说出自己的目标，系统就能调用相应的 MCP、工具或技能完成任务。比如，你在工作时想喝咖啡，只需告诉 Agent“帮我下一单”，它就可以完成选购、下单等操作。类似的能力已经在逐步出现。

这意味着，我们长期习惯的“操作系统 + App”两层结构可能发生变化。过去，无论手机还是电脑，操作系统负责管理资源，App 负责承载具体功能，由此形成了今天软件行业最基本的商业模式。

## 一、Agent = LLM + Harness

可一旦大模型成为操作系统里的通用入口，用户就可能不再需要为每一种功能安装独立应用，而是通过 Agent 直接表达意图，让它自主完成任务。首先受到挑战的，正是以 App 为中心的软件形态。

理解这种变化，可以从一个公式开始：

Agent = LLM + Harness。

大模型天然擅长理解、思考和推理，但仅有思考能力还不足以完成复杂任务。它需要 Harness 帮助自己接收上下文、规划行动、调用工具、观察结果、保存状态，并在必要时进行校正。只有这两部分结合起来，Agent 才能从“会回答问题的模型”变成“能够持续完成任务的系统”。

传统应用也可以写成一个相似的公式：

App = Runtime + Business Logic。

传统软件把运行时环境和业务逻辑结合起来：运行时负责执行，业务逻辑规定软件在不同条件下应该做什么。把两个公式对应起来，就会发现，大模型正在扮演一种通用 Runtime，而 Harness 承担了相当一部分业务逻辑、软件架构和软件设计的职责。

## 二、LLM 作为通用运行时，带来两项关键变化

## 应用逻辑被大幅简化

传统软件需要程序员把业务规则翻译成代码，并用顺序、分支、循环等结构精确表达。每一条路径、每一种异常、每一次流程变化，都可能对应一段定制逻辑。

当大模型成为通用运行时后，很多过去必须显式编码的分支与循环，可以由模型根据语义和现场信息动态推断。开发者不必为每种情况都提前写死处理路径，应用中的大量定制逻辑因此有机会被简化。

这并不是说代码会完全消失，而是说，软件不再只能依靠确定性的代码描述行为。自然语言指令、上下文、工具和验收标准，也可以成为软件行为的一部分。

## 固定工作流变成动态工作流

传统 App 的流程通常在开发时就已经固化。一个用于在线买咖啡的应用，很难自然地转变成处理其他任务的工具，因为它的页面、数据结构和业务路径都围绕特定场景构建。

以大模型为通用运行时后，工作流可以随着目标和环境动态变化。模型能根据用户意图选择步骤、调整顺序，甚至在执行过程中依据反馈改变策略。

过去三十年，软件行业一直在解决“如何更快、更准确地响应变化”这个问题；敏捷开发等方法，本质上也是为了提高软件适应变化的能力。现在，大模型把这种适应能力进一步带到了运行时：变化不一定要等到下一轮开发，有些调整可以在任务执行过程中发生。

因此，大模型作为通用运行时的意义，不只是让应用开发更快，而是同时降低定制逻辑的负担，并让工作流从预先固化走向动态生成。

## 三、Harness 既是软件架构，也是软件设计

传统软件工程通常区分两个问题：软件架构关心如何正确地实现功能，软件设计关心如何实现正确的功能。围绕这两个问题，行业积累了架构模式、企业架构、领域驱动设计等大量方法。

到了大模型时代，Harness 同时覆盖了这两个层面。为了避免概念混淆，我们可以把它分成内部 Harness 和外部 Harness。

## 内部 Harness：趋同的 Agent 架构

过去，人们习惯把 Claude Code、Codex 等系统统称为 Agent。现在越来越多产品开始强调 Agent Harness，因为单独的模型或 Agent 循环并不能覆盖完整的业务逻辑和软件设计。

内部 Harness，也可以称为内建 Harness，指的是 Agent 最核心的运行架构。它围绕 Agent Loop 展开，其来源可以追溯到 ReAct：模型先推理下一步该做什么，再采取行动，观察行动结果，然后继续推理。

早期的 Reasoning + Acting 还不够。为了让任务能够持续推进，系统又加入观察与自我校正：每次行动的结果会成为下一轮推理的输入，模型据此调整方向，逐步逼近目标。于是，Reasoning、Acting、Observing 和 Self-correction 共同构成了今天 Harness 的基础循环。

这个架构还在演化。例如，一些新框架开始加入 Self-improving 或 RSI（Recursive Self-Improving，递归式自我改进），让系统不仅能完成任务，还能调整自己的执行流程。但无论具体能力如何扩展，它们大多仍然围绕一个持续迭代的 Agent Loop 展开。

![](https://static001.geekbang.org/infoq/e2/e2d9f1456e3399452b1575e6f1a62bc4.png)

与传统软件百花齐放的架构模式相比，Agent 时代的软件架构正在高度趋同。多数场景不必重新发明一套循环；真正需要设计的是，我们如何利用这套通用架构完成具体业务。

## 外部 Harness：决定系统如何工作

如果把内部 Harness 看成一种公共运行时或操作系统 API，那么外部 Harness 就是我们影响 Agent 行为的方式。它承担软件设计的角色，主要由四个子系统组成：指令系统、工具与技能、环境系统、状态系统。

## 四、外部 Harness 的四个核心子系统

## 1\. 指令系统：既要告诉它怎么做，也要说明什么算完成

最简单的指令系统可以只是一条提示词。例如：“生成一张图片，包含 1、2、3、4、5 五个要素。”这种对行动方向的说明，可以理解为前馈控制（Feed-forward）：它向模型提供目标、要求和操作指引，主要影响推理过程。

只有任务指引往往不够，还需要反馈控制，也就是检查结果是否符合要求。上面的提示可以进一步写成两部分：先描述要生成什么，再列出必须满足的关键特征。后一部分相当于验收条件（Acceptance Criteria），作用于自我校正环节。

因此，一个有效的指令系统通常同时包含“任务说明”和“验收标准”。它不是简单地把需求说得更长，而是建立一个可执行、可检查的闭环。

## 2\. 工具与技能：让模型能够行动和观察

大模型本身不能完成所有现实操作。网页搜索、数据库查询、文件读写、格式转换、调用服务器接口，都需要通过 Tool、Skill 或 MCP 等方式实现。

工具与技能一方面负责行动：例如调用接口下单、运行脚本、转换文档；另一方面也负责观察：系统要确认文件是否成功生成、格式是否有效、接口是否返回了预期结果，同样需要读取和检查工具。

所以，工具不仅是 Agent 的“手”，也是它的一部分“眼睛”。没有工具与技能，模型即使能规划，也很难把规划变成可验证的结果。

## 3\. 环境系统：决定能力能否真正运行

工具必须运行在具体环境中。比如，用 Python 调用一个 HTTP API，需要相应的解释器、依赖库、网络和权限；处理文档也需要对应的软件和文件系统。环境配置不正确，工具再丰富也无法可靠执行。

传统开发中，运行环境常被当作工程基础设施；在 Agent 系统里，它直接决定模型可用的行动边界，因此本身就是 Harness 的一部分。

## 4\. 状态系统：让多步任务能够衔接

复杂任务往往需要跨多个步骤传递信息。不同技能之间并不会天然共享所有数据，因此必须人为提供状态系统。它可以很简单，只是一组文件；也可以是数据库或其他结构化存储。

工具执行的结果、当前进度、中间产物和关键决策，都可以保存在状态系统中。Agent 再通过读取这些状态判断任务进行到哪里、下一步应该做什么。对许多实际场景而言，文件系统已经足够有效；关键不在于技术多复杂，而在于状态是否清晰、可读取、可验证。

把四个子系统合在一起，就能看到完整关系：指令系统影响推理和自我校正，工具与技能承担行动和观察，环境提供执行条件，状态负责保存过程与结果。过去需要通过代码和编程实现的许多功能，今天可以通过这些系统共同塑造 Agent 的行为。

## 五、真正值得投入的，是外部 Harness

未来相当一部分场景，只需要使用成熟的内部 Harness。因为 Agent 的核心架构已经趋同，大多数开发者没有必要重复手搓一套 Agent Loop。除非业务极其特殊，需要新的架构承载，否则内部 Harness 的差异很难构成软件的核心竞争力。

不同框架当然会有差别。有的加入 RSI，有的优化上下文管理，有的通过精简系统提示词降低 Token 消耗。这些优化有价值，但通常只是成本、性能或执行效率上的改善，不等于业务价值上的差异。

软件真正的差异，从来不只来自架构，而来自它解决了什么问题、如何解决问题。Agent 时代也是如此。更值得关注的是：指令系统如何写，状态如何组织，工具与技能如何设计，环境如何搭建。也就是说，开发者应该把注意力从重复构造内部 Harness，重新转向外部 Harness 所代表的软件设计。

软件始终是为业务服务的。通用架构出现以后，我们更应该追问：用户真正需要什么？怎样把经验和要求变成 Agent 能理解、能执行、能验收的系统？这才是未来软件的核心差异。

## 六、面对不确定性，软件设计要从质量管理出发

基于大模型的软件与传统软件有一个根本差异：它是非确定性的。同样的提示词，在没有命中缓存等特殊情况下，模型可能给出不同答案。但许多业务流程又需要相对稳定、可靠的结果。

因此，Agent 软件开发的第一要务，是把质量内建到构造过程中。我们不能只要求系统“能用”，还要让它的输出从时好时坏，逐步稳定在可以接受的范围。换句话说，构建 Agent 系统可以被理解为对大模型输出进行持续的质量管理。

最基础的方法是 PDCA，也就是 Plan、Do、Check、Action。一个原本无序的任务，通过计划、执行、检查和改进形成反馈循环，质量就有机会持续提升。早期 Harness 常采用多 Agent 分工：一个负责计划，一个负责执行，一个负责检查。本质上，这就是把 PDCA 引入模型输出，让任务变得更可控。

不过，PDCA 不是无限拆分任务。一个管理者可以不断把任务拆成更小的任务，却不一定因此得到更高质量。拆到一定程度后，真正的瓶颈不再是计划颗粒度，而是具体工作的 Know-how。

以做菜为例，把流程分成备料、切菜、热油和炒制，可以让协作更顺畅；但如果执行者不知道鸡丁切多大、葱取哪一段、火候如何控制，再细的任务清单也无法替代经验。软件开发同样如此：当任务已经拆到具体操作，系统需要的是能够指导现场执行的知识。

## 七、用“双层循环”表达 Agent 时代的软件设计

Know-how 可以被封装进上下文。对于一项具体任务，系统先提供操作说明和关键经验，这是一种前馈控制；执行之后，再根据结果进行检查和反馈。如果未达到要求，就依据前馈信息调整方向，重新执行。

例如，任务是编写一个 API 测试，仅仅写下“完成 API 测试”并不够。Agent 还需要知道如何启动服务器、怎样模拟请求、如何完成调用、什么结果算通过。上下文工程（Context Engineering）的价值，正是为具体任务提供这些有效上下文和反馈机制。

把项目层面的 PDCA 与任务层面的前馈—反馈结合起来，就形成了双层循环：

外层循环管理宏观任务，负责任务分解、进度推进和整体检查；内层循环管理每一项任务的具体执行，通过上下文注入 Know-how，并对结果逐步校正。

仍以做宫保鸡丁为例，外层循环决定先备菜、再炒制、最后装盘；内层循环则处理每一步的具体标准，例如鸡丁切多大、花生米炒到什么程度、葱的哪些部分要保留。它很像专业厨房：主厨把控整体进度，各个岗位掌握具体工序。

映射到软件开发，外层是任务列表和项目进度，内层是每类任务最有效的执行上下文。随着模型能力增强、上下文变长，单个任务可以覆盖的范围也会越来越大，因此不必为每个微小动作都创造独立流程。对许多简单场景，三到五类内层任务已经足够。

重要的不是机械地套用两层结构，而是软件设计的表达方式发生了改变。过去，我们主要用确定性的流程、分支和代码描述业务；现在，可以用外层的宏观流程，加上内层的上下文与反馈，表达一个能够动态执行的软件系统。

## 八、Harness 可能成为新的软件范式，也可能成为通用技能

Harness 的意义，不只是多了一种 Agent 框架。它可能成为一种新的软件模型：以大模型作为通用运行时，以内部 Harness 提供趋同的执行架构，以外部 Harness 表达业务目标、操作知识、工具能力、运行环境和状态。

过去二三十年的软件工程，大多建立在人编写代码、把知识转换成确定性逻辑的基础上。Harness 提供了一种更直接的表达方式：软件架构由通用 Agent Loop 承担，软件设计则通过指令、上下文、工具、环境和反馈机制组织起来。

这并不意味着过去积累的工程经验失效。恰恰相反，如何理解系统、拆解任务、管理质量、提炼 Know-how，仍然是关键。变化在于，许多具体编码技能的门槛会被大模型降低，而准确表达需求、构造反馈、设计工作系统的重要性会进一步上升。软件从业者真正需要迁移的，不只是工具，而是自己的关注点。

更进一步，Harness 也可能不再是程序员独占的技能。当自然语言能够直接表达需求，每个人都有机会根据自己的工作方式构造软件。它让个人电脑更接近 Alan Kay 所设想的形态：用户看到的工作台并非不可改变的成品，而是可以随时调整、重新组合的个人环境。

过去，即使 Smalltalk 已经非常接近自然语言，它仍是一门编程语言，仍有使用门槛。今天，大模型让人们有可能用真正的自然语言描述目标，再由 Harness 把目标转化为任务、行动和反馈。未来，如果大模型进一步进入操作系统，人们使用电脑和手机的方式，或许不再是寻找一个现成 App，而是为当下需求快速构造一个合适的 Harness。

所以，Agent Harness 会不会成为新时代的 App？更准确地说，它可能不是另一个等待用户打开的 App，而是重构 App 的方式：让固定功能转向动态能力，让软件从预先交付的产品，变成可以按需生成和持续调整的工作系统。

这也是 Harness 最值得关注的地方。它既在重写软件的架构和设计，也可能逐渐成为每个人使用数字世界的一项通用能力。
