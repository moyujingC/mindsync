## Day 1 复盘：学 Agent 开发，要先抓住五项长期能力

大家晚上好我是尹会生，直播开始我先不直接讲新东西，而是先复盘了 Day 1 的内容。为什么要复盘？我给出了三个理由，这三个理由其实也回答了「学 Agent 该把时间花在哪里」的问题。这其实是每次开课我最想先讲清的事。

第一个理由是「学一些学完之后不会被马上淘汰的能力」。技术栈会迭代、名词会换，但有些底层能力是跨周期的。我把它们归结为 Agent 开发的五大核心能力——上下文工程、外部工具调用、长程任务循环（Agent Loop）、持久化记忆、测评与治理。

第二个理由是这五项能力是 Agent 达成业务目标的关键控制点。我打了一个很直观的比方：开车从北京到上海，关键控制点无非是走对路、识别路牌、操作汽车这三件事，对应到 Agent 上就是理解问题、调用工具、把多步任务推进到底的能力。这五项就是 Agent 跑起来必须的「路、路牌、方向盘」。

第三个理由是这五项能力是「可长期复用、可支撑复杂场景」的资产。无论前端还是后端，只要打算往 Agent 方向转，这五项能力都能直接平移过来，不会因为技术迭代被快速淘汰。

![](https://static001.geekbang.org/infoq/86/865bba0681f50d1769d8c80da8895ec7.png)

整个五大能力地图不是五个孤岛，而是一个能跑起来的闭环。上下文工程负责「让模型看见该看见的」，工具与协议负责「让模型能动手」，Agent Loop 与状态机负责「让模型不会跑偏」，RAG 与记忆系统负责「让模型能想起业务」，评测与治理负责「让模型不会越用越糟」。这五个模块相互联动，再加上一层贯穿全程的 Harness Loop（治理循环），整个系统就稳了。

![](https://static001.geekbang.org/infoq/9f/9f543d0fcde736e7834864051bf25a38.png)

光看地图太抽象，我把每个能力都拆到了「做工程时真正会卡住」的颗粒度。比如上下文工程，核心是「设计模型每一步看见什么、忽略什么、相信什么」，不是把所有信息都塞给模型——那会触发成本爆炸、注意力稀释、缓存失效三类典型问题。具体的上下文应该按优先级排布：稳定系统规则放最上面，接下来是工具定义、任务目标、结构化摘要、动态观察，过期信息放在最下面并且要主动过滤。

工具设计也是同理。我用一个非常鲜明的对比说清楚「放羊模式」和「动作空间」的区别：如果把一百米长的 API 列表全开放给 Agent，模型会一脸茫然；正确的做法是把工具封装成有约束的能力集合，比如邮件场景下要拆成 draft\_email、preview、send\_email\_after\_confirmation、error\_diagnosis\_tool 这几个语义清晰、职责单一的步骤，每一步都带「护栏、急停、确认」机制。这种思路在 MCP（Model Context Protocol，模型上下文协议）出现后被进一步标准化。

![](https://static001.geekbang.org/infoq/71/714719a767a596f1f2679a4d8e8e95c1.png)

Agent Loop 跑得久了会出现四类典型问题：上下文膨胀（用「状态化」解决）、目标漂移（用「周期性目标校验」解决）、死循环（用「Loop Guard」含最大步数与重复检测解决）、多 Agent 协作扯皮（用「隔离 / 仲裁 / 终止」三原则解决）。我特别强调：「真正的自主，是在边界内持续推进。」没有边界，再聪明的模型也跑不远。

![](https://static001.geekbang.org/infoq/a4/a4710f34909891e71fc851b2b7dbb38f.png)

记忆系统则有一个反常识的结论：「真正高级的记忆系统不是记得多，而是会遗忘。」RAG 的核心是「召回可信而非召回更多」，分块、向量检索、重排序三步走，配合版本冲突、权限校验、引用溯源、拒答策略四套保障机制；Memory 则分短期、长期、程序性三类，分别处理会话状态、用户偏好与流程经验。

![](https://static001.geekbang.org/infoq/a4/a472a6529ccd38ad18ac8c17e4f0d23b.png)

最后是评测。我直接抛出一句「没有评测的 Agent 都是玄学」——Demo 看结果，生产看轨迹。一个任务跑完，要看任务成功率、过程质量、成本效率、安全合规四个核心指标。一个专业的 Agent 工程师必须能回答六个问题：表现是否稳定、边界条件是否明确、失败能否自动恢复、改版后是否退化、成本是否可控、关键时刻用户能否接管。这六个问题是判断 Agent「能不能上线」的硬门槛。

![](https://static001.geekbang.org/infoq/18/18b92f03dbb6cde0d21bc21cd7538b01.png)

讲完五大能力地图，我做了一件有意思的事——发起了一场现场调研。第一个问题：认为 Agent 研发有前途的扣 1。响应很多。第二个问题：平常关注 Agent 新闻动态的扣 2。也有不少。第三个问题：看到好用的技能或大模型，会立刻在自己电脑上跑一遍的扣 3。结果 1 和 2 都有，3 几乎没人扣。

这个数据很扎心，但它揭示了一个真问题：知道的人多、动手的人极少。而 Agent 这个领域，恰恰是「必须跑起来才能真正学会」的领域。

## Python 选型、转岗路径与「不要为了 Agent 而 Agent」

接下来切入一个非常实际的问题：Agent 开发到底用哪门语言？我给出的答案是 Python，而且给出了非常工程化的解释：并不是 Python 在 AI 时代有什么神秘加成，核心原因是搞大模型的人多数不擅长构建稳定的 SaaS 软件，他们把精力投入到了大模型技术本身，那「把想法落地成可运行软件」这件事就需要一门足够简单、第三方库足够丰富的语言。Python 刚好符合这两个条件。Go、Java 这些语言门槛更高，所以被自然排除。我自己也是被这个问题困扰过来的，所以这次想先把判断逻辑讲透。

「那为什么后端转 Agent 开发吃香？」我回答得很直白：后端工程师在长期工作中已经处理过大量生产级 Bug、业务落地经验，这些能力在 Agent 落地阶段是直接复用的，不需要重新学。换句话说，Agent 开发并不是新大陆，而是后端开发能力的「一次再分发」。

但对前端和其他非后端开发者来说，是不是就没机会了？也不是。我给出了非常具体的前置补足路径，分三块：

第一块是 Python 本身。完全不需要买教材从零学起。学习目标是「读得懂代码逻辑、判断代码写得是好是坏」就够。我打了一个比方：现在你就像一个 Team Leader，招了一个实习生帮你写代码，你不需要自己会写，但你必须能判断他写的东西能不能跑、能不能解决业务问题。前端工程师本来就具备「代码品味」这种判断能力，只需要切换编程语言。

第二块是关系型数据库。学习范围严格界定在「基础运行机制 + 增删改查」，不要深入去学数据库底层理论、性能调优、分布式这些深水区。落地时大模型可以直接生成 SQL，你只要能校验逻辑合理性即可。

第三块是报错处理。后端同学遇到报错，脑子里是有「常见错误模式库」的，前端同学没有。所以前端同学遇到陌生报错时，要多问模型一嘴：这个错误的常见原因是什么、后端通常怎么解决。逐步积累后端相关的报错经验就行，不需要刻意系统学习。

![](https://static001.geekbang.org/infoq/b8/b8bee2e3838a1a6594de4e8457deea66.png)

我还特别强调了一句听起来像段子但其实非常务实的话：「不要为了 Agent 而 Agent。」如果业务只是规则匹配，根本不需要意图识别、动态工具调用、长程任务拆解，那就老老实实用传统代码，不要强行 Agent 化。规则匹配场景下，Agent 不仅慢，准确率还跑不过普通算术匹配。判断业务是否需要 Agent 化，要看是否需要反思、调用工具、查知识库、循环迭代找目标这五大类核心能力——任何一个不需要，就别硬上。

## 专用 Agent 落地的两条路径：从会议室预定到法务多 Agent

复盘完基础，我抛出了一个对很多新手「祛魅」的观点：现在大家都不做通用 Agent 了。为什么？因为大模型的通用理解能力还撑不起「一个 Agent 解决所有问题」这种野心。我原话非常直接：「AI 的能力太差了，你做通用 Agent 的时候，他理解不了。」这算是我这一年来最深的体感之一。

所以现在行业的主流方向是做专用 Agent——单行业、单岗位的垂类 Agent。比如医疗咨询有蚂蚁阿福、生活陪伴有豆包、办公场景有 Workbody、咖啡点单有瑞幸。每个 Agent 只解决一类问题，理解难度大幅下降，成功率显著提升。

但「专用 Agent 不是凭空造一个新东西」，它是把 AI 能力叠加在传统后端能力上。我用两个现场案例把这条路讲透了。

第一个案例是会议室预定 Agent。完整流程是：用户提需求 → Agent 理解问题 → 调用静态知识库查询「有哪些可容纳 30 人、有智慧屏的会议室」→ 调用动态工具校验这些会议室的占用状态 → 先临时占用资源 → 弹窗让真人最终确认 → 通知用户结果。

![](https://static001.geekbang.org/infoq/78/7899f1fc43e4bed25cb9f33f4de360c4.png)

这个流程看似简单，但拆开看会发现：理解问题对应上下文工程，调用知识库对应 RAG，调用工具对应工具调用，临时占用对应工程化能力，人工确认对应安全边界，结果通知对应记忆系统。一个看似简单的会议室预定，把五大核心能力全部跑了一遍。

第二个案例是法务多 Agent 审核系统。我展示了一个类似定期循环的批量处理系统：把高风险、中风险、低风险的合同审核任务拆分成三个独立 Agent 并行执行。每个 Agent 调用知识库比对上下文识别风险，能自动处理的就直接形成报告，无法处理的转给法务人员人工判断。整个系统是一个队列化的多线程实现，前端界面负责把关键信息和证据清晰地呈现给法务。

![](https://static001.geekbang.org/infoq/fe/fed431eea5320acbaace667acd66a0cc.png)

这两个案例传递的核心信息是：企业级 Agent 没有什么神秘，它就是把传统的后端能力（接口调用、并发处理、队列化、数据库操作）和 AI 能力（意图理解、知识库检索、工具调用）组合起来。后端工程师转 Agent 之所以占便宜，就是因为这些传统能力不需要重新学。

## 把通用 Agent 改造为专用 Agent：Skill 封装是核心

接下来的内容是整场直播最有「操作价值」的部分。我用一个完整案例——瑞幸咖啡点单——把「怎么把一个通用 Agent 改造成专用 Agent」讲透了。瑞幸的厉害之处在于它同时提供了三种接口：CLI、MCP、Skill，分别面向不同人群。这一节我会把这一年我积累的判断都放出来。

![](https://static001.geekbang.org/infoq/4a/4a65ce1e4681c63f041d98a6ede99c8d.png)

CLI（命令行接口）面向工程师、运维、数据同学。它的特点是参数化调用、执行过程透明可控、每一步都能精确看到。在 Linux 服务器、无界面环境下也能跑。但门槛高，得记命令、记参数、流程琐碎。

MCP（模型上下文协议）面向掌握业务流程的开发者。你只要提供必要的配置信息（服务器地址、Token 等），剩下的工具调用过程由通用 Agent 自动引导完成。本质上，MCP 是给 Agent 加的外部工具，通过 Streamable HTTP 这类协议和业务系统通信。

![](https://static001.geekbang.org/infoq/d7/d7d212b52775e244ce18d738fd4fd608.png)

Skill 是面向普通用户最高级的一种封装。把固定业务流程、调用逻辑、异常处理全部写进 Skill 里，用户只需要输入自然语言需求就行。我用一个 PPT 生成 Skill 做了对比演示：把模板、主题色、布局规则、执行步骤全部封装进 Skill，用户只要指定风格、页数、核心内容，就能自动生成符合要求的 PPT。

![](https://static001.geekbang.org/infoq/03/035c925db178b1571324daebfdeee6c2.png)

这三个接口不是冗余，而是分层。CLI 让能力强的工程师精确控制每一步，MCP 让懂流程的开发者快速接入，Skill 让普通用户零门槛使用。Skill 背后真正执行的还是 MCP 服务器，但它把工作流封装进去了——比如瑞幸的 Skill 里写死了「先查门店、再搜商品、确认意图、预览订单、创建、开始执行」的完整流程，人工只需在关键节点确认。

我特别点出了 Skill 适合封装的场景判断公式：高频、高价值、高一致性、容易出错的事。展开来说，重复频次高、复用价值大、流程一致性强、出错代价高的事务，最适合做成 Skill。相反，低频的、创造性强的、边界模糊的内容，不要硬塞进 Skill。

Skill 开发的完整流程，我把它拆成了 8 步：创建最小化版本（名字 + 描述）、设定目标、明确用户输入、定义工作流、明确输出、加入工程化条件、加入测试脚本、灰度上线。简单 Skill 套流程就行，复杂 Skill（比如 PPT 生成）需要把模板、主题、布局做成可调用的 assistant 和 reference 文件。

![](https://static001.geekbang.org/infoq/26/26172423180589209ec5e86d579adb03.png)

我在演示完瑞幸案例之后，现场又用 Codex 演示了一个完整的点咖啡流程。打开 Codex，配置 DeepSeek 模型，把 My Coffee 的 MCP 配置贴进去，Agent 自动加载工具，搜索附近门店、确认商品、生成订单、弹出支付二维码。整个过程完全自然语言驱动。再换成 Workbody 安装 My Coffee Skill 做对比，步骤数大幅减少，因为 Skill 把工作流都封装好了，用户只关心「我想要什么」。

![](https://static001.geekbang.org/infoq/38/38de7033c76e534df7e125bbb0c327da.png)

讲到这里，直播的实操部分基本完成。但我很快把话题拉到了更深的地方：把通用 Agent 改造成专用 Agent 是相对容易的事，真正难的是「生产级 Agent 的深水区」。

上下文工程是首要难点。上下文不是越多越好，要排优先级：用户原始目标、当前任务进度、已执行工具的结果、相关业务数据、Harness、系统策略、安全边界、Agent 自身状态（比如剩余 Token 预算）。排得不对就会出现成本爆炸、注意力稀释、缓存失败三类问题。Token 用到 75% 时会自动压缩，关键指令如果被压掉了，Agent 就会跑偏。

工具设计则要回答四个问题：工具的语义描述是否清晰、参数类型与范围是否明确、是否可幂等（重复调用结果是否一致）、哪些高风险操作必须人工确认。我特别举了瑞幸点单的例子：下单和支付被刻意拆开，因为下单可以自动化做十次，但支付必须一次性人工确认，避免「付十次款」的灾难。

![](https://static001.geekbang.org/infoq/71/714719a767a596f1f2679a4d8e8e95c1.png)

Agent Loop 跑长任务时会出现三类问题：上下文膨胀导致核心目标被冲掉，需要把目标保护好；目标漂移导致 Agent 对中间过程过度关注、偏离最终任务，需要周期性校验；死循环需要设置最大步数阈值和重复检测机制。日志记录也要全链路做，否则出问题排查不动。

多 Agent 协作的核心难点是「信息隔离」：通用框架类信息（用了什么框架、目标是什么）可以同步，但每个 Agent 的独立执行策略必须互相隔离——否则就会出现「生成 Agent 用 A 策略、审查 Agent 也用 A 策略、bug 漏判」的问题。我举了一个很接地气的例子：解一元二次方程时，验证的人不能按原方法再算一遍，要逆推，所以生成策略不能同步给审查 Agent。另一个常用技巧是让 GPT 生成、Claude 审查，靠不同模型本身的能力差异来制造「隔离」。

记忆和评测相对容易理解但工程量巨大。记忆分短期（当前会话状态）、长期（用户偏好、项目约定）、程序性（流程经验、失败模式），分别对应不同的存储方案。评测则要覆盖任务成功率、工具调用准确率、执行路径合理性、成本可控性、安全合规等多个维度，定期检测劣化并迭代优化。

![](https://static001.geekbang.org/infoq/a4/a472a6529ccd38ad18ac8c17e4f0d23b.png) ![](https://static001.geekbang.org/infoq/18/18b92f03dbb6cde0d21bc21cd7538b01.png)

## 作品集、答疑共识与收尾

讲完深水区后，我给出了一个非常实用的「作品集」建议——这是给所有正在准备转型 Agent 开发的人的一份行动清单。这份清单我每年都会更新一遍，但核心五条一直没变过。

第一个是工具型任务 Agent，比如瑞幸点单。核心标签是「工具、Schema、权限分级、错误恢复」。实现路径是通用 Agent + 业务 MCP + 前端展示页面，整个工程量不大，但能完整跑通业务闭环。

第二个是企业知识库 Agent。核心标签是「RAG pipeline、引用溯源、评测集」。用户提问时调用 RAG 检索、带上引用出处、补充问题引导改写。

第三个是 Coding Agent 助手。核心标签是「代码搜索、最小修改、测试闭环、轨迹日志、回归验证」。这种 Agent 对工程化要求最高，因为代码改错了代价大。

第四个是多 Agent 审查工作流。核心标签是「规划、执行、审查、仲裁、终止条件」。这是工业界最常见的协作模式，能跑通就有完整的工程示范价值。

第五个是 Agent 评测与观测平台。核心标签是「任务成功率、轨迹分析、成本统计、失败归因、版本对比」。这个项目的难度不是技术，而是对业务的深度理解。

![](https://static001.geekbang.org/infoq/94/947c712e51a4fb697308719a857b2f14.png)

我特别强调，这五个项目的难度梯度是从「能跑通」到「能上线」，覆盖了一个 Agent 工程师完整的能力证明链。完成它们之后，无论面试还是项目落地，都有了「从 Demo 到生产」完整链路的能力证据。

整场直播最后的部分，我挑出了观众在群里和直播间里问得最多的几个问题，给出了非常清晰的统一答复。

关于 Function Calling 和 MCP 的选型：判断标准有两个——如果工具是全局通用的、自己公司提供的，用 Function Calling；如果工具是第三方提供、需要遵循协议规范和密钥验证，用 MCP。

关于异步与阻塞：耗时超过 1 分钟的工具调用必须异步，Workflow 和 Codex 都支持 fork 能力开新分支不阻塞当前会话。如果期望「等结果回来再继续」，可以设成阻塞模式新建会话并行处理。本质上都是 Function Calling，只是 MCP 在协议层面更规范。

关于多 Agent 通信：常见方法有四种——父 Agent 初始化时复制指定上下文到子 Agent；A2A 协议点对点通信；共享状态数据库写入后各 Agent 定期检查；定期状态校验。当前多 Agent 生态还不成熟，很多机制需要结合具体业务场景定制开发，没有开箱即用的方案。

关于前端转岗：核心难在两点——多数 Agent 用 Python 开发，前端要多学一门语言；后端常用的接口调试、业务拆解、数据库增删改查、向量数据库、RBAC / ABAC 权限体系这些能力，前端都需要重新学。这是后端能力更吃香的根本原因。

关于通用 Agent 是不是要自己写代码：通常不需要。千问、Workbody、Codex 生成的通用 Agent 本身就是一个完整的 Agent 能力载体。只有当需要定制化扩展（比如网页展示、特殊业务接口）时，才需要自己写代码。

关于生产级 Agent 的开发方式：全部从零开始。现在的 Agent 开发并不需要框架，因为每个模块本身难度不高，用框架反而会增加复杂度。Codex CLI 和 Claude 的开源代码都是直接可用的学习样本。

![](https://static001.geekbang.org/infoq/bc/bcb8f943c5b756c12d36aa24548de7be.png)

直播也快到尾声了，总结一下：

第一句是关于岗位价值的直白解释：「Agent 做完之后确实比平常的程序放大了企业非常多的能力，那自然你的薪水就水涨船高。」这不是鸡汤，是岗位价值的真实计算公式——能力放大多少倍，薪资就放大多少倍。

第二句是贯穿整场的提醒：「不要为了 Agent 而 Agent。」这是对所有开发者的核心告诫：技术是用来解决业务问题的，不是用来证明自己懂技术的。

学 Agent，本质上是学「如何让 AI 真正干活」，而不是「如何让 AI 陪你聊天」。把通用 Agent 装上业务 Skill、把深水区的工程问题一个个解决、把零散能力沉淀成完整作品，这就是从「会看」到「会跑」再到「会上线」的完整路径。剩下的，就是动手。
