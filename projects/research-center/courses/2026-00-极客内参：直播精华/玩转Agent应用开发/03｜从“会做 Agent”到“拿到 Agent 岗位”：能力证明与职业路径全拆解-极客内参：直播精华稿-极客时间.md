## 学了 AI，为什么还是拿不到 AI 岗位

## 三个不容回避的事实

大家好我是尹会生，连着三天直播做下来，最让我有感触的，是这群程序员身上共同的焦虑。找工作这件事，其他岗位的同事可能稍微吃香一些——产品能讲清业务价值，运营能讲清转化漏斗，市场能讲清获客成本。但对程序员来说，简历上的核心竞争力，过去是「我输出代码」，而现在这件最引以为傲的事，恰恰被 AI 替代了。

这就引出今天的第一趴：为什么很多人学了 AI，依然拿不到 AI 的岗位？我把它总结成三个事实。

事实一：你拿的是旧地图，找的是新大陆。 上一个时代程序员的核心竞争力是「手写代码 + 算法八股 + 设计模式」。这一轮企业真正在招的 Agent 开发工程师，核心要求已经完全不同。我前两天在直播间打开 BOSS 直聘，随便挑几个 Agent 应用开发工程师的岗位 JD 给你们看：第一个写的是「熟练应用 Codex、熟练应用 Claude Code 等主流 AI 编程工具进行代码生成、重构、测试和调试」；第二个是「AI Native 的开发习惯，熟练使用 Claude Code、Cursor 等 AI 辅助编程」；第三个是字节的，要求你先写评估、再写验收、做仿真测试集，对业务指标有理解、然后做技术前瞻。

你看到了吗？这些岗位的 JD 共同点是——不要求你手写代码快。它要求的是你能用 AI Native 的方式工作：让 AI 生成代码，你来校验代码、评估代码、组织代码。

事实二：风口一直在变，不会等你。 这件事我们其实都经历过。Python 出来的时候，写代码效率比 Java 高，一批 Java 工程师转去补 Python，找到了薪水相对不错的工作。后来容器化、Docker、K8s、Service Mesh 时代来了，Go 语言成了风口——很多上一波去字节面试的同学，是学了 Go 才踩上了这波红利。再后来呢，Python 热度回落、Go 也回归常态。所以你看，风口是不断变化的。市场上在大量招 Go 的时候，你还在坚守 Java，薪水就不会涨。风口这件事，识别比努力重要，跟上比死磕重要。

事实三：从零手写代码和分析现成大项目，这两种能力都不再是值得投入的努力方向。 直播间里有同学问我：老师你的课程，到底是从零教我写代码，还是给我一个现成项目让我分析？这两种我都不教。原因是企业不再看重纯编码能力。AI 写代码比我们快，写错了我让他改、改到他写对为止——这个时间本来也是我们自己手写一遍的代码时间，AI 已经能跑三遍、四遍了。所以你重点要做的不是「写得多快」，而是「怎么校验 AI 写的代码、怎么评估 AI 写得好不好」。

## 围绕岗位要求，重新锚定努力方向

知道了这三件事，我们才能去谈努力的方向。跟着岗位走，而不是跟着别人说。我把方法论压缩成三句话：

第一，打开 BOSS 直聘人工筛目标岗位 JD。 不要用 AI 帮你筛——你要用自己的眼睛一条条看。假设你想应聘 Agent 开发工程师，就直接选它，把地区、薪资、经验要求都选好。然后看 JD 到底要什么：AI 工具能力占多少、工程化能力占多少、业务理解占多少、传统后端技术栈占多少。

第二，把 JD 拆成「工具能干」和「人必须干」两类。 工具能干的事，是左边的薪水——大家都会用 Codex、大家都会用 Claude Code，这个层面是基线。人必须干的事，是右边的薪水——这个工具干不了的部分：你怎么把 AI 写出的代码放进工程里、怎么评估、怎么上线、怎么兜底出错。右边这一栏，才是你拿高薪的原因。

第三，把不变的东西圈出来，作为重点学习内容。 用户需求在变、Agent 产品形态在变、工具 API 在变——但有些东西是跨周期不变的：模型 API 的选型与异常处理、Agent Loop 的工程化结构、工具的 Schema 与权限分级、可观测与回滚机制。这些不变的事，才是值得花时间去钻研的。

把上面三件事做完，你大概就能回答一个问题了：我现在投入努力的方向，到底是旧地图，还是新大陆？

## 正确的努力方向：从手写最小 Agent Loop 开始

## 为什么先手写一个 Agent Loop

很多 AI 相关课程一上来就直接教你 LangChain、LangGraph、Pro AI 这些框架。这些框架当然重要，但我更想强调另一件事：先手写一个最小的 Agent Loop。

为什么？因为只有自己写的时候，你才知道这个循环里到底有什么。业务承接在哪一步、模型在哪一步选择行动、解析哪些工具、执行哪些工具、记录哪些结果、在哪一步更新状态、怎么判断继续还是结束——这些决策点，亲手撸一遍，你才能讲出它们之间的边界。你不写一遍，面试官一问你就会露馅。

写完最小循环后，再把工程化能力叠上去：工具的 Schema 定义、错误恢复、加日志、加预算、加上下文压缩、人工确认、加评测。这些都做完之后，再拿 LangGraph 的节点、边、状态图重写一遍——这才是高效的学习方式。

![](https://static001.geekbang.org/infoq/4c/4c673d0b7814ac8d5190af3b482b9d02.png)

## 瑞幸点一杯冰美式：一个真实的 Agent Loop

为了让大家有体感，我用一个具体的业务——瑞幸点咖啡——把 Agent Loop 拆开来讲一遍。

用户走进瑞幸，跟手机上的瑞幸 App 说「给我点一杯冰美式」。这个过程里，Agent Loop 至少要回答这些问题：用户想点哪家门店？门店是否在营业？冰美式有没有货？规格、温度、糖度怎么选？有没有可用的优惠券？用户是否需要二次确认？支付这个动作是 Agent 自动完成还是让用户点确认？下单失败之后怎么恢复？

你看，这就是一个完整的 Agent Loop。它涉及不同类型的工具：读菜单是只读工具，提交订单是写入工具，支付是高风险工具——这一类必须设计成让用户来确认。把这些东西讲给面试官听，他就知道你真的做过。

更关键的是，Agent 产品设计的核心，是知道 AI 的能力边界。AI 擅长模式匹配、擅长生成文本，但它做不了高风险决策。所以人机结合要融进业务——这是你体现人价值的地方。

![](https://static001.geekbang.org/infoq/0c/0c87ea3965189260d6cb445b12a495cf.png)

## Coding Agent：一个完整闭环的例子

如果说瑞幸的例子还偏轻量，那 Coding Agent 是更值得放进简历的实战。

面试官问你「做过 Coding Agent 吗」，千万别只说「能帮我写个函数」——这样答基本没戏。也别说「整个 Coding Agent 80% 都是我手写的」——这在 2026 年的面试里也不加分。原因很简单：Agent 本身是相对简单的循环，复杂度远不如 SaaS 系统，真正有价值的是完整的执行轨迹与上下文设计。

一个能拿得出手的 Coding Agent，应该有这些能力：读需求、搜代码库、找到相似风格模块、最小化完成修改、自动完成测试、高危指令触发人工确认、根据错误提供修复方案、输出变更声明。它不破坏用户已有的改动，每一步都记录在执行轨迹里。

它的上下文也不是单一提示词，而是一组东西：代码仓库结构、Git 状态、测试输出、文件 diff、开发规范、用户给的具体指令。这些上下文是静态的摆前、动态的摆后——静态信息（项目结构、规范）放在提示词前面，动态信息（Git 状态、测试输出）放在后面。这套设计逻辑讲出来，面试官才信你是真的做过。

对应的工具也不是点咖啡的简化版，而是一整套：代码搜索、读文件、编辑文件、执行命令、查看图片（你截个图让它修 UI）、运行测试。评测时，核心问题是回答质量——这些功能是不是都跑通了。

## 企业知识库与多 Agent：两个绕不开的工程化课题

## 企业知识库 Agent：不只是 RAG

聊完工具型 Agent，再讲一个每个后端工程师都会遇到的场景——企业知识库。

企业知识库的基础能力有四样：版本控制、文档冲突处理、权限过滤、跨文档综合。在这四样之上，还有一个很多人忽略的能力——反 Prompt Injection。这是企业级知识库和「玩具版 RAG」最大的分水岭。

![](https://static001.geekbang.org/infoq/90/90d1d693a3a2ad3d9941fdd0b17cf2aa.png)

更值得提醒的是面试考点的变化。前几年面试官问的是 RAG 的标准流程：文档切分、向量化、检索、重排、生成答案。这一套现在属于「默认你会」，不会再问。今天面试官关心的是：RAG 怎么跟业务结合。 你做的知识库是给客服用、给销售用、给研发用，还是给合规用？不同的业务结合点，决定了你怎么裁剪 RAG 流程，怎么设计权限模型，怎么做引用溯源，怎么做版本回滚。

## 多 Agent 协作：不是堆角色

最后讲多 Agent 协作。这两年因为 OpenClaw 火过一阵，市面上流传过一种「三省六部制」的拆法——把 Agent 拆成尚书省、子 Agent、审验机构等角色。这种拆法跑起来就是一片混乱，Token 烧得飞起，输出结果反而不如单个 Agent。

问题在哪？拆 Agent 不是为了拆得多，而是为了拆得清楚。 面试官真正问的是这五件事：

为什么拆？拆的工程理由是什么？

拆完之后，每个 Agent 脑子里知道什么？

哪些信息需要在 Agent 之间共享？哪些必须隔离？

哪些 Agent 可以并行？哪些必须串行？

风险如何评估？冲突如何仲裁？什么时候该强制终止？

![](https://static001.geekbang.org/infoq/99/99cb6575c37c3276bd9229a0c1ee04ae.png)

多 Agent 协作的工程原则只有三条，违反任何一条就会崩：

第一条，隔离优于共享。Agent 之间如果共享同一个上下文，Token 消耗会指数级爆炸，调试也基本不可能。正确的做法是给每个 Agent 自己的上下文窗口，必要时通过显式消息传递。

第二条，仲裁优于争论。两个 Agent 意见不一致时，不要让它们来回辩论——辩论会烧 Token，也不会有结论。让一个 Supervisor Agent 做仲裁，或者用规则引擎决策。

第三条，终止优于空转。任何一个 Agent 如果跑超过 N 步还没有收敛，必须强制终止并报告失败。空转比失败更糟糕——空转会烧光预算，且没有任何可观测的失败原因。

记住这三句话——隔离、仲裁、终止——比记住任何框架的 API 都有用。

## 一套为后端工程师量身设计的 Agent 课程

## 课程的整体结构：6 大阶段，14 周

讲完学习方向和工程化课题，接下来讲讲我们的课程体系。我们从 2024 年做 ACP 大模型课、2025 年做工程化课，到 2026 年做 Agent 课程，这是我们设计的第三套课程体系，每一套都对应一个技术周期。

这套 Agent 课程按项目路径推进，分为 6 大阶段，对应三大方向：

方向一，工具型任务 Agent。 包括 LLM 统一调用服务、Agent 工具调用基础设施。

方向二，Codebase Agent + Codebase RAG。 包括 Agent Loop 框架、代码库索引与混合检索、项目级记忆。

方向三，多 Agent + 生产化方式。 包括 Supervisor 协作、自动化评测、Docker 部署、可观测性、灰度发布。

关于课程为什么 8 月中才开、为什么录播 + 直播混合、为什么不做成纯直播——这三个问题直播间问得最多，这里统一回答。

为什么 8 月中才开课？ 不是偷懒，是技术不成熟。今年 2 月份 OpenClaw 出来的时候，Agent 一度大火，很多人说已经实现了 AGI、所有工作都能迁移过去。但那时候 OpenClaw 没有 harness、没有 graph、没有工程化配套——它就是一个不计安全、不计成本、只算执行结果的 Agent 雏形。这种状态下出课程，出来一个月就过期。我当时判断不能出。果不其然，OpenClaw 火了一两个月后第三个月就被干掉了，热度回落。活下来的是 OpenClaw 底层的 Pi Framework——那个框架把整个 Agent Loop 写进一个 370 多行的 TS 文件里，非常适合跟着 AI 一起分析。OpenClaw 是 Loop Engineering 的一个雏形，但还不是终态——知识体系不完整的时候，强行做训练营是对学员不负责任。

为什么录播 + 直播混合？ 因为我写代码、跑 AI 生成的时候，没办法跟弹幕互动——AI 生成 5 分钟的代码，不可能让直播间几百人坐着等 5 分钟。所以演示部分做成录播，连续、可暂停、可回看、可跟着练。每周安排一场直播，集中答疑——8 年老工程师提的问题和 1 年小白提的问题不一样，大家在同一个进度上互相互补。这种形式跟以前「全程直播」或「全程录播」都不一样，是为 Agent 学习专门设计的。

关于课程更新。前面提到课程是 7 章、14 周完成主体，全年配套 40 小时技术更新。这 40 小时不是匀速释放，是「有新热点才更新，没新热点就不动」。如果一个月内 AI 领域没有任何新东西出来，就不用为了更新而更新——大家工作已经够忙，没必要每周花时间在没有新东西的内容上。等新东西出来，我们就把新技术加进训练营，说明它跟之前的技术怎么结合、哪些旧技术已经被迭代掉。这是对抗「学了过期」焦虑最实在的做法。

第一个阶段是 LLM 统一模型调用服务。这一章不是教你怎么调一个 hello world，而是教你在企业里真正会遇到的事：怎么选 chat completion 还是 response API？怎么统计 Token、Cost、Latency？怎么处理异常？怎么在多个模型之间做路由？这些事是大模型本身不会主动告诉你的——大模型可以告诉你「我是谁」，但不会告诉你「企业在生产中怎么用我」。

第二个阶段是 Agent 工具调用基础设施。包括 ToolRegistry 工具注册中心、ToolSchema 工具元数据定义、JSON Schema / Pydantic 参数校验、Function Calling 集成、权限校验与风险分级、工具调用审计、超时 / 重试 / 降级机制、MCP Client 接入、工具调用 Trace 记录。这一章是后续所有 Agent 项目的底座。

![](https://static001.geekbang.org/infoq/90/909d1648e249a340c6e961e7d002a7fa.png)

第三个阶段是 Codebase Agent——也就是 Coding Agent 的工程化实现。涉及 Agent Loop 循环执行框架、Planning 任务规划、搜索 / 读取 / 修改文件能力、执行测试与读取失败日志、自动修复错误、Human-in-the-loop 人工确认机制、Sandbox 安全执行环境、任务状态管理与 Checkpoint。这一章配套的项目是「Coding Agent 助手」。

第四个阶段是 Codebase RAG & Memory。包括代码库索引与文档解析分块、向量检索 + 关键词检索 + 混合检索、Rerank 重排序、项目级记忆（目录结构、技术栈、构建命令）、长文件压缩与工具结果压缩、任务摘要与恢复、引用来源追溯、Context Debug Report。

![](https://static001.geekbang.org/infoq/de/de014e114c82c8b225cf9c10ffca58e8.png)

第五个阶段是 Multi-Agent & Eval。包括 Supervisor Agent 监督协作、Architecture/Test/Security/Performance/Report 多角色 Agent 分工、Skill 注册与检索机制、Benchmark 管理与自动化评测、LLM-as-Judge 评估、人工评测流程、Trace Analysis、回归测试与 Agent 版本对比。这一章配套的项目是「多 Agent 审查工作流」。

第六个阶段是 Production Ready——把前五个阶段的项目推到生产。包括 Docker Compose 部署方案、Model Gateway 模型网关、Redis/PostgreSQL/VectorDB 基础设施、Trace/Metrics/Monitoring 可观测性、Replay 回放调试、Prompt/Model/RAG/Tool 版本管理、Feature Flag 功能开关、灰度发布与回滚、成本治理、上线 Runbook。

![](https://static001.geekbang.org/infoq/94/947c712e51a4fb697308719a857b2f14.png)

整套课程 7 章、14 周完成主体更新，全年配套 40 小时技术更新——只要业内出现新的技术热点，我们就把它加进课程、同时说明它跟之前的技术怎么结合、哪些旧技术已经被迭代掉。

## 编程语言与工具选型：怎么挑适合自己的

关于编程语言。课程代码以 Python 为主，核心是借代码讲设计逻辑——你没学过 Python 也能大概看懂。实在看不懂，就用 AI 把 Python 代码翻译成你熟悉的 Java。但有些现成项目是固定语言的：Codex 和 Claude Code 的开源版本是 TypeScript；K8S 相关会涉及一部分 Golang；Service Mesh 相关可能涉及 Java。这些是工具本身的限制，不是我们能改的。

关于开发工具。我把常用的工具分成三类，这三类承担的是完全不同的功能，不要混着用。

Codex：本身就是一个完整的 Agent，能调用工具、能循环、能反思。它是你做项目的主力——从 2026 年的实际项目落地看，Codex 已经成为企业内部 Agent 项目的首选。

VS Code 这一组（Cursor、Trae、Coder 等）：是集成开发环境（IDE），提供与代码交互的便利界面，Agent 反思、Skill 使用、工具调用的可视化主要靠它。但 IDE 本身不是 Agent，它不会主动调用工具。

OpenClaw 这一组（Workbuddy、Codebuddy 等）：是另一种 Agent，工具丰富、反思能力强，非程序员的 Agent 用户更多用这一类。但它对工程化能力的要求更高，适合做复杂任务的编排。

三者的边界是这样的：Codex = Agent 本身；VS Code = 与代码交互的 IDE；OpenClaw = 偏反思能力的 Agent。 这三类工具并不互斥——一个项目里你完全可以用 Codex 跑 Agent、用 VS Code 调试代码、用 OpenClaw 做复杂任务规划。

工具可以自选，但有两件事要注意。 第一，用 Codex 不要点太快确认操作——它会误删内容，特别是对代码库的批量操作。第二，Claude Code 账号封号严重，很多企业已经从 Claude Code 转到 Codex 或者其他同类工具，面试基本不再考 Claude Code 的具体 API。如果你之前用 Claude Code 比较多，把能力迁移到 Codex 上是更划算的选择——Kimi Code、QodeX、CodeR 等同类工具的能力也都在快速补齐。总之，掌握一类 Agent 工具的能力边界，比熟悉某一个具体工具的 API 重要得多。

## 把焦虑变成作品：行动比认知更重要

## 不要做大而全的 Agent

直播间里有同学问：课程里是不是会教把 long-term memory、multi-agent、background task、自由配置 MCP 全部塞到一个 Agent 里？

这个我要特别说一下——不要这么做。行业里有一类误区：觉得 Agent 越全越好、塞的能力越多越值钱。这是错的。

Agent 平台从 OpenClaw 火起来之后，已经走过了一轮「大而全」的弯路——大企业喊着要做 Agent 平台、做一半新功能出来了、平台被推翻、推翻之后再做、再被推翻。今天能活下来的 Agent，都是纵向切割的、聚焦在具体业务上的小型 Agent。

![](https://static001.geekbang.org/infoq/9e/9ece89e2f1c1e9a912a9dc9c56d87520.png)

正确做法是：切入业务的核心点，做一个 100 行代码能解决具体问题的小 Agent。比如运营关心小红书投流，那就做一个专门做小红书投流的 Agent——它可能只涉及上下文压缩，那上下文压缩就是这个 Agent 的核心，别的能力都不需要。做小红书投流的 Agent 不需要做沙盒环境、不需要自由配置 MCP——那是另一个 Agent 的事。

每一个 Agent 就是一个项目，不要试图把所有能力塞进同一个 Agent。 当你真正需要把它们组合起来的时候，你需要的是一个平台——而平台这种东西，业内已经有成熟的开源方案了，不要自己去重写一套。

## 技术更新快 ≠ 是好事

直播间还有同学担心：现在学完 Agent，半年后又出新范式了怎么办？

范式不会出那么快，至少这半年内不会再出新的范式。 但工具会用得很快。

这里要纠正一个常见误解：技术更新快不是好事。 它的真实含义是——这个技术还不成熟。只有不成熟的技术才会更新这么快。技术成熟了，反而稳定下来——比如 Web 开发框架，前几年百花齐放，这两年已经收敛到几个头部。

所以面对快速变化的技术，正确的态度是：先把能跑、能用、能在面试里讲清楚的项目做出来，把焦虑变成作品。 至于还没稳定的新技术，等它稳定了再学不迟。先动手，先做出来，比什么都重要。

## 写在最后：给正在准备转岗的你

如果你还没做过任何 Agent，我建议从 Codex 开始——把 Codex 本身当做一个通用 Agent，往里面加 Skill、加工具、调用国内大模型，把这些先玩熟。等你熟悉了 Agent 的工作方式，再去转岗、再去面试，你的简历上就有东西可以讲了。

最后再回答几个高频问题，让准备转岗的你有更完整的预期。

关于年龄。 早两年 Agent 岗位的招聘要求是「清一色 00 后」——这是当时的现状，但现在已经放宽了。原因是纯 00 后写出来的代码缺乏工程化能力、错误处理能力，很多项目上线后出了问题，又得找有经验的工程师救火。现在企业更愿意招有 1-5 年后端经验、且愿意学 Agent 的人。你对照 BOSS 直聘的岗位 JD 看一下：5 年以上后端、1 年以上大模型应用开发，是目前的主流配置。

关于 Agent 工程师和 FDE 的区别。 Agent 工程师更强调软件交付的工程能力——能写 Agent、能上线、能维护。FDE（Forward Deployed Engineer）除了工程能力之外，还要求顾问能力——能跟客户一起梳理业务场景、把业务拆成 Agent 任务。FDE 的课程极客时间已经上线，由曹老师主讲，但如果你目标是快速就业，先聚焦 Agent 工程师更划算。

关于二三线城市的竞争力。 这个问题我前段时间去西安参加腾讯云社区活动时专门看过——当地不少中小型公司已经把 OpenClaw 用得很溜，做短视频剪辑、做出海翻译、做图片生成。这些中小公司对 Agent 工程师的需求很大、给得起合理薪资、且不像大厂那么卷。如果你在郑州、西安、合肥这类城市，Agent 反而比传统后端更容易找到差异化机会。

关于学历与就业。 实事求是地讲，Agent 工程师岗位目前学历是简历初筛的硬门槛——HR 在不了解你的时候，学历是他最直接的筛选维度。但能力足够突出时，学历卡不住你。最聪明的做法是：在正式投入学习之前，先投几份简历试水——看看目标岗位对你的学历、经验、城市有没有硬性要求，再决定学习的投入度。

Agent 工程师这条路，未来两年会越来越值钱。问题是：你愿不愿意现在就开始动手。
