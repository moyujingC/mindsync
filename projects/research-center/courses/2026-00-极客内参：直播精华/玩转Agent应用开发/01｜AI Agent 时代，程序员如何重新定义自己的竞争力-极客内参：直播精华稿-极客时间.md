为什么第二次转型拖了这么久？其实跟 Agent 的发展节奏有关。AI 这个领域更新太快了，你可能 20 天、30 天，新技术就迭代变化了。之前我们说学 Loop Engine、做 Loop 工程师，这刚火没到 5 周，现在大家又在说"Loop 已死，Graph 归来"。新技术还没等学会呢，可能就已经过时了。

所以我一直在等，等那些真正能沉淀下来、能让大家长期受益的技术。最近我发现很多技术确实慢慢成熟了，可以作为大家找工作和转行的真正跳板——于是就有了这门新的 AI Agent 全栈工程师训练营。

## 为什么今天的程序员必须重新定义竞争力

先抛第一个问题：为什么今天的程序员必须重新定义自己的竞争力？

我们研究院做技术研究的时候发现一个共识——2025 年是 AI Agent 落地的元年。这个概念不是我定义的，腾讯研究院、阿里研究院都得出了类似的结论。

为什么是今年？因为 Agent 新增了两个关键维度，导致整个行业发生了质变。

第一个维度：传统基础能力在扩张。 以前的 Agent 大家怎么用？都在用 Dify、扣子那些东西。说它是 Agent 吧也算，但本质上还是工作流——把你传统的工作用工作流再做一遍，遇到需要意图识别的地方就让大模型来做，需要人介入审批的地方就人来审批，其他和传统工作流一模一样。

去年跟着我学 AI 工程化的同学其实领先了一步——在大家还在搞 RAG、搞提示词的时候，他们就已经成功转型成 Agent 工程师了，也拿到了高薪。

但今年你会发现，很多企业面试的时候不考这些了，变了。为啥？因为整个智能体出现了两个最大的变化。第一个就是传统基础能力多了规划、记忆、工具调用和执行这四点。如果今天听完明天就要去面试，你可以跟面试官讲一讲现代智能体和以前有什么区别，就说这四点。

第二个新增的核心能力叫反馈式学习。 Agent 可以在持续的行动中沉淀经验，实现自我能力迭代。这个能力是未来 Agent 即将要用的。大家可以往这两方面去考虑，这也是未来 Agent 人才发展的两个最重大趋势。

![](https://static001.geekbang.org/infoq/55/552abba077a95bee39f27376aad09892.png)

说了这么多趋势，那 Agent 现在到底落地了哪些场景？如果你时间紧张，我直接给你答案——三个场景，你可以完全去考虑：

第一个叫内部提效场景。 典型应用就是 AI 生成代码和 AI 数据分析。给你一份数据：腾讯现在已经 90% 以上的程序员日常使用 Workbuddy 做 AI 编码工具，其中 50% 的新增代码都是由 Codebuddy 生成的，Bug 率降低了 30%。这数据是从腾讯研究院来的。

第二个是客户服务类。 比如知识库搭建、智能客服、保险理赔计算。一些汽车厂商的知识库搭建周期，以前是 30 人天，现在压缩到 5 人天，构建效率提升了 83%。权威机构调研显示，未来 12 个月大概会有 82% 的企业计划引入 AI Agent 客服。

第三个是企业增长类。 比如腾讯、字节这些互联网公司，主要用于广告素材生成和销售素材管理。腾讯的广告工具"妙思"，可以一键生成商用级的 AI 广告片，现在已经落地了。

这三个场景就是未来确定落地的方向，你今天可以把我的话录下来，三个月以后再回来找我验证。

![](https://static001.geekbang.org/infoq/32/327d47417e4f946e7b6a32f8e66300d0.png)

如果你说"我看不了那么远，我就想在公司内部学 Agent 往哪方面学"，我仍然给你三条路：

第一条路：组织和个体的角色重建。 未来很多组织里，人是负责校对和承担最终责任的，Agent 变成执行目标任务的。长期来讲，人会变成 Agent 的老板——智能体的管理者。调用多个智能体完成任务，由人来背最后的责任。我只包一年的判断啊，第二年极有可能出现的情况是——你的老板是 Agent，你向一个 Agent 汇报你做了什么样的审核工作。那个时候就蛮悲观了，但路还有很长，起码一年之内你可以先去做 Agent 的老板。

第二个方向：AI Agent 的协作落地。 现在越来越多的调度 Agent 会打通企业现有的 CRM 和存量系统。比如酒店场景里，用户说"送水""送拖鞋"，都可以由 Agent 调用物联网和后台系统完成全流程服务。前几天我去参加 WAIC 上海的机器人大会，也发现了这样的趋势。

第三个方向：Agent 的基础设施建设。 Agent 能不能做专属的支付系统？Agent 之间的协作协议，比如 MCP、A to A？Agent 运行的监控——投入多少成本、产出多少价值、ROI 怎么算？很多企业都开始做这些事了，这些都属于基础设施建设。

![](https://static001.geekbang.org/infoq/70/70ca782edd61db25268949dd51dd8361.png)

说到这儿，不知道大家有没有发现一个问题——刚才我说的这些，有的同学说"这不就是我现在在做的事吗"，也有人说"似懂非懂，感觉对企业挺有用，但跟我差点意思"。

为什么会有这种感觉？因为之前我们做的很多 Agent 更像是一个 Demo，只是一个演示。Demo 的时候你会发现，普通人也能做，懂开发的人也能做，做出来的结果差不多。

我给你举个例子。我们职场人和小学、初中毕业的小朋友，一起去拼七巧板、搭积木。你会发现，在有限的时间内、积木难度很小的时候，搭出来的结果其实相差不大。为什么？因为目标过于简单了。

但是当目标足够复杂、要应对真正的企业级工作的时候，你会发现懂编程的人和不懂编程的人，对后台业务的理解，差距是非常大的。

就像有人开发信源系统，拿 Web Coding 来做——需求给我，只要长得符合审美、结果说得过去，网站就上线。上线之后用户量一多，网站崩了，才后知后觉去查瓶颈、查并发。

但对于有软件开发经验的人来说，这些问题我们在做之前就优先考虑进去了。做前端的先选 Vue 还是 React，做后端的先选 Spring 框架、选数据库、选微服务架构，然后架构师开始抽象逻辑、设计模式、类的抽象——提前规划，规划完再开发。很多没有开发经验的人想不到这一步，只有碰到事情才临时反应。

为了解决这个问题，今年兴起了一个词——Harness，有没有听过？就是驾驭工程。拿大模型编程的时候，你在后面不断约束它，跑偏了拉回来，再跑偏再拉回来——与其运行中不断约束，不如提前定义好前进的方向和规则。

你看，这些东西对于普通人来讲很难想到，甚至很多已经在这个圈里的大模型开发工程师也没想到，只是遇到的问题多了，才想到用什么方式能确定性地解决这类问题。什么东西是确定性的？工程化是确定性的，架构是确定性的，设计模式是确定性的。这些是不是又回到了我们程序员熟悉的战场？

所以我说，这就是我们程序员的机会。为什么以前没有？因为以前不重视 Harness。为什么以前不重视？因为以前的结果过于简单了——简单到提示词里写几个 if-else 就能解决，根本用不到程序员的思维，所以不是我们的机会。

而现在，已经开始进入一个新的时代，才真正用到我们程序员的能力。就像直播间里同学说的"换汤不换药"——学的仍然是打磨自己的确定性工程能力，只是把它应用到新的领域去。

也有同学说，随着模型的增强，Harness 会不会走向消亡？没错。你看现在还有人提 Harness 吗？没了，都提 Loop 了。等你下周再看，还有人提 Loop 吗？没了，都提 Graph Engineering 了。这些概念在不断消亡。

但这个消亡是真的消失了吗？大家想想。大模型出来之前，我们积累的那些底层逻辑、框架知识——不管你接什么业务，程序员嘛，你今天干掉我，我换个新岗位，俩仨月就熟悉新业务了，我会的是 Spring 框架。现在很少有人提 Spring 了，那它消亡了吗？没有，它已经沉淀成你最基础的能力了。

再举几个例子，Hadoop 还有人提吗？微服务还有人提吗？Service Mesh 还有人提吗？都没人提了。但这些东西消亡了吗？没有，包括 Kerberos、Docker 这些，都已经被我们用在真正的底层了——已经落地了，不再需要研究花活了，所以这些词就听不到了。

Harness 也是一样——要么被基础模型吸收，要么慢慢固化到 Agent OS 操作系统层。就像以前做内核开发的时候，我们要学怎么申请内存、释放内存、合理利用内存，Windows 和 Linux 还不一样，到安卓又不一样，得学三套。现在还有人提吗？没有了，为什么？因为操作系统这一层已经给你包装得特别好了，你只需要调几个参数就搞定了。

所以 Harness 现在还要不要学？还是要学的。很多词不再提了，你要看清楚——它到底是被业务淘汰了，还是已经变成基础设施了。

再比如 Function Calling（函数调用），现在也没人提了，那这个要不要花大精力去学？不需要了。为什么？因为它是真的被淘汰了——已经变成模型开发商必须写好的东西了。我们现在真正用的是 MCP、CLI、Skills 这些东西，不用再去学 Function Calling 了。

有同学问，Agent 和 AgentOS 到底啥区别？

Agent 其实是一个统称——LLM 大模型加上 context 上下文，再加上工具，这就是 Agent 的概念。

AgentOS 呢？就是另一种提法——我的 Agent 能够自己管理上下文、自动管理工具，就像一个操作系统一样，你不用关心底层调的大模型是什么样的，也不用关心上下文和工具，就是把这一层做得特别好。就像我们用的 Windows、iOS，都叫操作系统，你平常会关心系统里怎么运行、怎么做上下文切换吗？不会的，我们最多关心上面装的那些 App。

所以 Agent 和 AgentOS 是两个层面。Codex 其实就是 Agent，它的目标就是 AgentOS。

## 岗位拆解：企业到底要什么样的 Agent 开发工程师

好，背景讲得差不多了，接下来给大家做岗位拆解。为什么要拆解岗位？因为我一个主要工作就是为大家打造体系化的 Agent 全栈训练营，另外我也经常在大会上做技术布道，岗位解读也是我工作的一部分。

![](https://static001.geekbang.org/infoq/8d/8d9f555d3b8c7419446915f08139630b.png)

先给大家看几个典型的岗位，你们可以去 BOSS 直聘上搜，会看到比我更详细的。我挑的只是我认为比较典型的，当然也有可能我被算法蒙蔽了，所以大家自己去搜最直观。

第一个岗位，AI 应用开发工程师。你看认知要求，跟以前不一样了。以前的要求是什么？熟悉 LangChain、LangGraph、LlamaIndex、Coze 这些大模型开发框架，在这个基础上用 Web Coding 或者 AI Coding 做过真正的项目。

现在呢？我给你讲一个真实的事情。前段时间我去参加腾讯的社群活动，在西安，陕西省政府邀请我们一起做的。当时遇到了 Workbuddy 的产品负责人，我就直接问了——你们整个 Workbuddy 系统是怎么开发出来的？有多少是 AI 写的代码，有多少是人写的？

他告诉我，最开始第一版 Workbuddy 脱胎于 OpenClaw，当时人员很少、项目紧张，三十几个研发几乎就是拿 AI Coding 的方式写的，主要是为了抢占第一时间把产品发出去。

但是发出去之后，产品分成了 To C 和 To B 两个方向。To B 的时候，用户各种各样的业务需求进去，通过 AI Coding 不断打补丁，终于扛不住了——Bug 每天 30 个人都处理不过来。当时他们说 90% 都是 AI Coding 写的代码，我当时也没点赞，心想这早晚要爆炸的。

![](https://static001.geekbang.org/infoq/5e/5ea59a363fdc0363c6a732a61e77bb58.png)

后来他们怎么做的？继续招人，然后人工把之前 AI Coding 写的代码大部分重构了一遍。大概隔了三个月左右的第二次大会，我再问他们的时候，他们已经有 150 个研发了。AI 写的代码占多少呢？大概 80% 左右，但这些代码已经不是直接提交了——AI 写完之后，由人来做审核，再去提交。

我说那这些占到你整体代码的多少呢？他说，以前占 80%、90% 的那些代码，技术栈成熟之后只占整体的 30% 左右。整体 AI 写的代码量被压缩到很低。

我问他们踩过最大的坑是什么？他说最开始找很多业务同学写代码，这些代码在业务上只满足特定需求，业务稍微一变化就不可复用了，需要批量修改大量代码，引入大量 Bug——不是改一个函数那么简单，是大范围的修改，就会引入大范围的 Bug。

所以你会发现，现在很多招 Agent 应用开发的岗位，要求已经变成了——至少有 3 到 5 年的后端开发经验。

大家懂了吧？为什么我今天说，有后端开发经验的人，今天是吃到红利的人。

再往下看，之前的系统是 Python 开发的，所以你会看到 Python、Flask、FastAPI 这些主流的 Web 开发框架，以前用的是 LangGraph 这样的大模型开发框架。同时还要熟悉传统的 MySQL、Redis，以及至少一个向量数据库——因为有 RAG 嘛。能够习惯使用 AI 工具提升研发效率。

这个写得真的非常实在了。

![](https://static001.geekbang.org/infoq/dd/dd58dc020da5b155b00dd409a1535e30.png)

第二个岗位，负责多智能体设计，薪资 30 到 40K。更多偏向知识体系建设，包括 RAG、Wiki、知识沉淀，整个优化也是关于向量检索、文本切块、召回——其实就是一个标准的 Agent 后面套了一个 RAG。要求 1 到 3 年的开发经验。

要知道，3 年的 AI 开发经验在市场上是极其少见的。大众真正接触大模型应用开发，最多也就三年半。这个要求蛮高的，但你会发现它依然要求——软件开发相关经验，有成熟商业系统的开发经验。仍然离不开传统的开发能力。

第三个也是差不多的，本科计算机专业，至少熟悉一门编程语言，熟练掌握数据结构和算法，才是 RAG。

还有一个，扎实的后台研发经验，Golang 优先，其次是 Java，再其次是 Python，熟悉 MySQL——你看还是传统那一套。只是在这一套基础上，要求掌握 Harness、主流的 MCP，要求架构设计经验，加分项是有 LangGraph 的二开经验。

为什么我特意提二开经验？因为我看到很多公司优先招有二开经验的人，所以我在设计课程的时候特意做了一个创新——不是我一个人讲，而是让大家和框架的开发者直接对话。我觉得这个对大家就业比较有帮助。

好，岗位就展示到这里。大家如果相中哪家公司、想从事什么岗位、对应期望的薪水，自己去 BOSS 直聘上搜，我搜的不算数。

有前端同学问，前端转后端没有后端经验怎么办？

我觉得是这样的——强调的"后端经验"到底是个啥东西？第一，大家对编程这件事要比普通人理解得深。比如来了一个简单业务，产品经理拆分完之后，假设没有架构师，你要把它抽象成多少个类？哪些类要实例化？类的方法怎么设计？这些东西很多程序员是受过训练的。

前端工程师其实接触过 Vue 等框架，也是比其他人有优势的。但为什么强调后端开发？因为真正写 Agent 的时候，还是需要懂一点后端开发能力的。比如你入职的公司用 Python 写 Agent，你不懂 Python，那生成出来的代码，你怎么作为最后把门的人来验证对不对？没有办法验证的。

就像一个审美不好的人，你怎么验证 AI 画的画是好是坏？对音乐一窍不通的人，你怎么知道 AI 写的音乐是好是坏？你说 AI 可以自己校验啊——那校验完的结果，你也得看得懂吧？

所以如果大家觉得 Agent 应用开发真的是未来，我建议你不妨借助大模型去学一门简单的编程语言，比如 Python。

你可能会说，等 Agent 把火蔓延到前端开发、用 TypeScript 或 JavaScript 写 Agent 变成主流，我再学不行吗？我觉得你要等很久，在等的过程中，时机就已经错过了。这是我掏心窝子的一点建议。

你可以拿大模型来学 Python。还有什么呢？以后开发的 Agent 早早晚晚得操作你的数据库——不管是关系型的、非关系型的、向量型的、时序的，不同行业有不同的数据库。数据库这个事你也可以提前学起来，只要从事软件开发，永远都会用到。

而且像 Python 这种脚本语言，学起来没那么麻烦，特别是有大模型辅助，你跟它边对话边学，两周、三周就能学会。现在写 Agent 又不要求你一行一行写 Python，只是大概能看懂、出了语法错误大模型能帮你修、业务能力测不过去大模型也能帮你修——但是最后兜底的还得是你自己，这个绕不过去。

至少要学个 Python，至少要学个数据库。其他的东西可能随着大模型的发展变得不那么重要，但作为软件工程师，这是必须得学的。

## 三大错觉与五个能力模型

好，岗位拆解完了。在学 Agent 开发的时候，大家经常会有三个错觉，我想跟大家说一下。

![](https://static001.geekbang.org/infoq/70/70960fc2ba192f2fdcb48a8b1751e47c.png)

第一个错觉：造词。 硅谷最擅长的就是造词。今天说 Harness 已死、Loop 当道，明天又说 Loop 已死、Graph 为王。造词有坏处也有好处，要辩证地看。

坏处是什么呢？很多新词你可以学也可以不学。比如现在的 GraphRAG，我觉得你就可以只观望，不要深入学。为什么？它涉及到多 Agent 互相通信之间该不该传状态、该不该运行到下一个节点、该不该回退——这些还在研究阶段，大家进去太早了。甚至它定义的图还是有回路、有环路的图，你把它定义成图也行，定义成其他结构也行，明天可能本体论又把它推翻了，说所有 Agent 都是实体，是实体和实体之间的关系。

所以有些词大家了解就行，不用深究。但有些词是为了我们更方便地进行技术人之间的沟通，那些是应该掌握的。比如工厂模式，我一提这个词大家就知道怎么回事，这就是造词的好处——快速技术对齐。

硅谷造的这些词，你应该知道，但哪些重点掌握、哪些不用重点掌握，要好好辨析。

第二个错觉：技术迭代太快，不知道该学啥。 我的建议是，要看这个技术有没有真正为业务服务、有没有真正为基础设施服务。就这两点。如果没有，那这个技术也只是观望——不能马上为业务带来提效的、不能马上为你的基础知识基础框架带来增效的，就不要去学。

比如最近 KV Cache 又被提出来了，它到底能不能帮我们节省 token？我发现是可以的，那这种情况下 KV Cache 你就可以去学。就是这个意思。

第三个错觉：只要学得慢就不用学。 我知道第三个你们经常听过，我把它放在"错觉"这，你们也知道不应该这么干。但很多时候就是——"学了那么多道理，依然过不好这一生"的感觉。

不是不用学，而是哪些需要深入学、哪些了解概念就行，要分清楚。学得慢就不学了，不学后面大模型就学会了嘛，学会了之后你的技术就跟不上了。当然，有一些技术努力的方向本身就是错的，那你可以不学。

辨析着来，这三个错觉不要完全相信。

![](https://static001.geekbang.org/infoq/dd/ddde5a92115e822aebe3fb6bb5636c38.png)

好，接下来讲五个核心能力地图。刚才铺垫了这么多，你再来看这五个能力，会不会有不同的感受？

以前大家理解 Agent 可能是一个感性的状态——能自己思考、能自己办事、能调工具、能操作现实世界。但现在，我们可以把一个概念拆成不同的小部分，专注理解这些部分，再组合在一起，就是你所能理解的 Agent 全部。

第一个能力：上下文工程。 很多人认为 Agent 的上限是由模型决定的，我看到直播间里也有很多人这么说。但我自己的判断是——在给企业交付的真实应用里，Agent 的上限首先是由上下文决定的。

因为模型想要做决策，就只能基于它看到的信息做决策。这个大家能懂吧？信息看不到，做决策那叫什么？那叫幻觉。它看不见需求文档，看不到系统状态，看不到工具结果，看不到历史偏好，那做的结果就是错的。所以上下文才是决定模型能不能干好事的关键，现在受到非常大的重视。

第二个能力：工具。 当你的模型能力撞墙的时候，一定要有 Agent 的手脚——也就是工具。工具如果设计得比较粗糙，那感觉就像带着拳击手套做外科手术——工具太糙了，调用回来的结果虽然填充了上下文，但没用。

这时候就要考虑，是不是把工具的 Schema 设置得更细一点？MCP 协议是不是设置得更合理一点？有人问 Agent 会不会泄密——那你的权限边界要设置好。还有，以前封装函数的时候，在支付系统中我们会考虑幂等设计，你现在设计大模型的工具，有没有考虑过？这些都是生产级 Agent 的基本功。

![](https://static001.geekbang.org/infoq/ca/ca435cdcdd37600cf655c2d300e67af7.png)

第三个能力：Agent Loop 和状态机。 我们希望 Agent 能够长程运行，那 Loop 和状态机就是非常关键的东西。自己设计的 Agent 如果是多步执行的，就得管理好最终目标是什么，怎么观察状态，出错了怎么重试。

你一直循环肯定不行——写循环或者嵌套循环，最重要的是写啥？绝对不是写循环本身，是什么？终止条件嘛！还有什么时候需要人工接管？你看，这就是懂后端的人往 Agent 开发上迁移的时候，只要有人点透这一层，迁移得非常快。

第四个能力：RAG 和记忆系统。 以前 RAG 和记忆系统是单独的系统，我甚至还拿它单独卖过钱——做个软件、写个界面就拿去卖。现在不行了，时代变了，RAG 已经变成 Agent 的一个扩展工具了——一部分扩展工具和协议，一部分扩展上下文。

大家都听过"长上下文出来了，RAG 已死"这种话吧？都快听腻了。但长上下文不是万能的，真正的知识系统要解决什么？检索、压缩、引用、更新、冲突、遗忘——这些东西都要解决。这些都是 RAG 的事情，是上下文的补充。你就想，Windows 发展这么多年了，不还有虚拟内存吗？Windows 都解决不了的问题，你让一个 Agent 来解决？不要扯了。

第五个能力：评测系统。 很多写 Agent 的人，最开始入行的往往不是专业的。比如 OpenClaw，你回去问问他们有没有测评？没有测评，Agent 永远停留在"我感觉还行"的程度。因为没有评测、没有治理，所以 Agent 始终没办法上线，在线上风险源是极大的。

这五个能力集成在一起，我们还可以在上面加约束条件——最好的办法就是在设计这五个子系统之上，提前把 Harness 设计在里面，然后形成现在的 Loop Engineering。

我把它称为 Harness 的 Loop——在大模型外面包一层工程的 Harness。整个大的是一个循环，在循环外面再包一层工程化的 Harness，这样就可以做到：输入是可控的，过程是可监测的，行动的时候是可约束的，结果可以评测，出现失败的时候还可以恢复。

这就是我们希望 Agent 能够达到的能力。大家可以对照一下自己以前做的 Agent 到底是啥样的。

## 传统工程师的优势与企业级平台

那再回来，传统工程师有啥优势呢？你看看这些词，你们熟不熟？这些词其实都是现在 Agent 特别缺的。

![](https://static001.geekbang.org/infoq/5d/5d564d602fb4a083bd0b48ffe9107c2b.png)

很多人说"我在公司的大赛上 Demo 拿了一等奖"——你看他敢不敢放回你的生产系统上？为啥不敢？缺啥？

API 和它的鉴权，有没有？没有。

数据的一致性，有没有？也没有。

处理并发的时候，任务的多队列、异步、可恢复，有没有？也没有。

评测和回归测试，有没有？也没有。

出事故了能不能限流、能不能降级？有没有？还是没有。

所以我说，现在搭好的 Agent，最缺的就是我们程序员和业务坐在一起，给之前的"AI"装上一个工程骨架。这才是真正的 Agent 工程师。

我预感到了这样一个情况，给企业做咨询的时候也发现了大量这样的需求，所以才想推动这件事——把传统工程师的技能和 Agent 能力放在一起，给大家创造一个新的就业路径。

![](https://static001.geekbang.org/infoq/4c/4c60e2d00308adf79b9dc64092f04d3b.png)

那企业级的 Agent 平台应该包括哪些组件呢？你把刚才说的东西和现在拼在一起就知道了。

最小的 Agent 内核是什么？接收用户的目标，构建上下文，然后选择行动，解析工具，执行工具，记录更新状态，判断完成了没有，然后再回来——这不就是 Agent Loop 嘛。整个这个过程就是原来的 Agent 那一套。

然后加上工程化的这一套——工具的 Schema、日志、上下文的预算和压缩、Token 的预算、人工确认、评测——这些加起来就形成一个比较成熟的 Agent 了。

![](https://static001.geekbang.org/infoq/1f/1f69187ad1449d2e42bc0c893bebc08f.png)

我给大家看两个真实的企业级系统截图，是从人家交付的系统里截出来的，我不好告诉大家是什么系统。

第一个，"帮我查一下最近我审批的流程都到哪了"。对于用户的问题，它首先先去理解，理解完之后识别用户的意图——用户的问题是关于什么的。然后去搜索知识库，找到最近几天发起的审批，包括会议审批等等，当前审批人是谁，整个流程状态如何。

你会发现整个界面是不是就和以前对话的界面一样了？前端工程师在这就特别吃亏——大家更关心的是你能不能理解问题、能不能识别意图、能不能搜索知识库，前端界面好不好看反而不那么重要了。我这个界面已经丑得我都没法看了，但人家觉得还凑合，能不能再优化、时间再短一点——他更关心的是这个事。

![](https://static001.geekbang.org/infoq/fc/fcf85a013dda6525933f15fa741042f2.png)

第二个例子，"我想要去定会议室，需要有智慧屏"。推理、理解问题、找知识库，找到哪些会议室有智慧屏，然后唤起会议室预订系统，看对应的时间有没有空。推荐完之后，由你手工来做提交——这个我没有让它完全自动化，后边讲课程的时候再跟大家讲为什么。

还有这种运营看板的——"最近四周我的运营看板是什么情况？先给我结论。"结论之后是关键的图表、关键的 UV，就这些东西。还有法律方面的，模拟 OpenClaw 来做的，高风险、中风险、低风险，嵌套的都是业务流，右侧是近期的证据，上面是整体的过程。

为什么设计成这种方式？这么丑是为啥？因为很多非技术的人，包括领导层，他们最开始接受的 AI 就是 OpenClaw 这种对话窗口。你给他交付一个经过前端精心设计的高级 Agent，他们会发现用不懂。所以当下设计的东西，更多的都是这种界面——左侧是对应的功能，中间是对话，展示相应的结果，下边拿对话来进行查询。

世界变化得比较快，我们只能先跟随着往前跑。

## 转型路径：如何进入 Agent 开发方向

最后一个主题，关于转型路径。其实把前面分析好之后，大家就会发现转型路径已经非常清楚了。

![](https://static001.geekbang.org/infoq/18/18c3466e0a8129a2684bcdfd86cdf17b.png)

哪些东西是大家可以长期积累的？我在课程当中会把每一个部分做重点剖析。但直播间里也有很多自学能力很强的同学，所以我也把路径告诉你们。

通过自学的方式也可以，跟着我来做跟练的方式也可以。最终我们希望在国内有更多的 Agent 应用开发工程师——行业变得越来越大的时候，大家的薪水才会水涨船高。自学能力强的人先一步找到工作，体现出专业开发工程师的价值，把薪水撑得更高；后面跟学跟练的同学也会有非常好的就业前景。这个东西没有什么可保密的。

整个学习路径我规划了 5 个阶段，但未来是不是 5 个阶段我不保证——我的课程里还安排了不低于 40 个小时的全年更新，就是为了防止 AI 变化太快，随着新技术的产生、新趋势的出现，我们不断扩展，可能会有第六级台阶。

第一个阶段：基础概念。 要求大家理解 Agent = 大语言模型 + Context + Tool 这样的机制，理解 ReAct Loop，理解工作流和自主 Agent 的区别。只有真正理解了基础概念，你在上面才能真正用好它。对于开发工程师来讲，就像理解 TCP 协议、HTTP 协议才能做好网络编程，你自己写的东西才能变成给别人用的接口，而不是一直调别人的接口。这就是基础。

第二个阶段：工具调用。 理解了基础概念之后，接下来就是扩展能力——能不能掌握工具的调用？包括 Function Calling、JSON Schema、工具的权限、错误恢复等等。

第三个阶段：上下文工程。 怎么管理、压缩、检索上下文，这是 Agent 能力上限的关键。

第四个阶段：知识库和记忆系统。 怎么做引用溯源？怎么做记忆的分层？构建好知识之后，能不能构建一个完整的记忆系统？构建不了能不能临摹一个、抄一个？

第五个阶段：生产化和可观测性。 怎么建立测评集？怎么规划轨迹日志？可观测性、成本治理、部署、监控和降级——这些东西要搞定。

![](https://static001.geekbang.org/infoq/ad/ada48cd4f754f5d4f33c08454be4974a.png)

为啥要搞定这些？因为 B 站或者很多零碎视频教大家的都是——怎么搭好一个 RAG、怎么安装一个 Skill、怎么调用工具、怎么把上下文加进去、怎么把 RAG 加进去。但实际上大家面试的时候，你会发现他不考你这些东西。

为什么？因为这些东西都是模型正常运行情况下的事。正常情况下模型能正常运行，我作为公司为什么要招一个人来专门做开发？大家理解这个概念吧？所有东西都能正常运行，我为什么不买一个 OpenClaw 让它跑在公司里就行了呢？

不是这样的。正常的工作、面试、商业项目里，我们要解决的是那些有可能出问题的东西。

我给大家列几个真实的面试题，是我其他学员面试的时候遇到的，我搜集了一些：

设计一个企业的知识库 Agent，怎么做权限控制和引用溯源？

调用工具的时候准确率只有 70%，怎么提升？

跑长程任务的时候上下文爆了，怎么处理？

多 Agent 协作的时候怎么解决冲突？怎么做仲裁？

怎么来做 Agent 的评测？

怎么防提示词注入？

跑了一个 GPT-5 的大模型，又跑了一个 GPT-4 的小模型，大模型正常用，小模型在 Coding Agent 的时候用来改每一个会话的名字。小模型挂了之后会话名字很长，怎么发现这个问题？怎么把 GPT-4 降级成其他系统？换了其他模型之后怎么做好提示词的适配？

考的都是这些问题。所以大家自学的时候也要注意——不要只学概念，要学当它们出现异常或者不正常的时候，我们该怎么解决。这些东西才是真正有用的。

![](https://static001.geekbang.org/infoq/bf/bf26b3caeb48dcef6ffc43c2142fece4.png)

最后，因为时间的关系，今天也超了快半个小时了，我给大家一个态度上的总结。

我希望带大家走的是 Harness Loop 这样一条路。一边是学概率推理的大模型怎么组建 Agent，另一边是大家现在已经掌握的工程系统化的确定性能力。通过 Harness 和 Loop 的机制，我们在两者之间建立一个桥梁。

在这个桥梁上，我们来看看怎么对大模型做约束（Harness）、怎么做校验、怎么做记录、怎么回滚、怎么评测——把大家现有的后端经验慢慢迁移到大模型的开发上。让模型提供可能性，工程提供可靠性，来做这种生产级的 Agent。

这就是我最终想要在课程里给大家交付的一点东西。

![](https://static001.geekbang.org/infoq/de/de66c5b10d7d1ba96f6d9723c2c138a5.png)

好，今天的分享就到这里。希望大家都能有所收获。我们明天见，拜拜。
