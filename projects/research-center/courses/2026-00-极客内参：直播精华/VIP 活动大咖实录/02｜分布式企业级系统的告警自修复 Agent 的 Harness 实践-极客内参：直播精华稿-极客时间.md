## 从一次深夜告警说起：企业为什么需要"数字值班同事"

非常开心收到会生老师的邀请，今天来聊一聊关于企业级 Agent 在真实场景中落地时遇到的那些问题。今天要分享的，是一个叫 Eva 的项目——分布式企业级系统的告警自修复 Agent 的 Harness 实践。

在正式开始之前，想先做个简单的调研：在场的有多少是"码农"同学？举下手我看一下。不错，有一半左右。再问一下，有多少是专门做后端开发的？跟刚才一样是吧，基本都做过，也挺好。因为"告警"这件事，在程序员群体里头，主要还是后端同学接触得比较多，但现在的边界其实已经很模糊了，做前端、做全栈的也都会涉及到这一块。

那就先做一下简单的自我介绍吧。我的名字叫郭美青，英文名是 Andy。几个标签大家可以记一下：第一个是"互联网第一代全栈开发工程师"——我最早是做 Java 出身的，比较早，后来又改做前端，再后来做全栈，再后来做 AI，反正什么都做过。第二个标签是"前腾讯资深架构师"——在腾讯那段时间积累了不少企业级系统的心得。第三个标签就是我现在所在的百川智能——我也是负责 AI Agent 方面的一些研发工作。也给自己贴了几个小标签：AI 的思考者、实践者和布道师，因为我也经常在自己的公众号里头去分享一些一线真实的实践经验。最后一个标签，去年写了一本书，是 MCP 领域最早的一本书，叫《AI Agent 互联网新纪元：一本书讲透 MCP》。

闲言少叙，回到正题。

既然是讲企业级系统在生产环境中的 Agent 实践，那我们首先要对齐一个概念：到底什么样的产品才算"企业级"？或者说，一个典型的企业级产品的架构大概长什么样？这里我以我们自己线上的一款产品为例，做了一些脱敏之后的样子：

![](https://static001.geekbang.org/infoq/b1/b13565ad634b51d7b0c175fcbcadfd2e.png)

可以看到，前端是多端的——Web 浏览器、iOS、安卓、小程序、还有一些 Admin 管理后台。中间有一层 BFF 层，也叫 Gateway 层，是个网关。后端是一个完整的微服务架构，涉及很多独立部署的服务。每一个服务上线之后，都会产生一些运营日志，比如说告警日志，这些都会统一打到可观测日志总线上。

但这样的架构之下，企业里头通常会有多个代码仓库、多支团队协同维护，不是一个团队把所有事情都干完。所以这是比较典型的一种 toC 企业级系统的样子，toB 的话端上会少一点，可能只有一个管理后台。

既然是讲治理、讲日志和告警的治理，那有几个概念需要先跟大家对齐。第一个就是 SLS——做后端的同学应该比较了解，这是阿里云的日志产品，左边这张图就是。它解决的问题就是集中去采集应用里的日志、集中存储、集中查询，就是这么个产品。

第二个概念是告警治理。线上的服务在运行中会有各种边界 case，可能产生告警。常见的做法是基于规则、基于消息规则去做告警——把 error 日志打到飞书群或者企微群里头，相关的同学每天都要盯着群去看告警消息。比如说，群里有"PC 服务端异常"这种消息，里面会有一些关键信息，其中一个就是 TraceId——它就是一次请求从端到端所有日志共用的同一个 ID。

所以所谓的告警治理，其实就是通过规则处罚、去重降噪、分级路由，把真正需要处理的问题分发给真正需要看到的人。这就是告警治理。

接下来一个问题就来了：在 Eva 出现之前，一次典型的线上告警治理大概是一个什么样的流程呢？这里给大家一个画面感。

在 AI 出现之前，在 Agent 出现之前，大多数团队——包括大厂里头的实践——基本上都是这样：

深夜：收到线上系统的告警，可能是群里头告警，也可能是直接发短信、打电话。→ 找 TraceId：负责人跑到群里一看，找到告警消息，拿到那个 TraceId。→ 跳 SLS 查日志：去日志库里头查，看这个 error 日志上下文是什么样的情况。→ 跳板机 + IDE：拿到上下文之后，去代码仓库里头去排查，到底是哪一行代码出了问题。→ 跨团队 @：有时候前端排查到调后端接口出问题，会把后端同学叫醒说"这是你们的问题"；有时候后端查下来也会甩给前端说"这是前端的问题"。→ 群里回一句：最后回个"已修复"。

![](https://static001.geekbang.org/infoq/f2/f29c0acf511f08a28eb653567c62d34b.png)

是不是非常有画面感？晚上基本上很多 C 端产品的值班工程师都睡不好觉，尤其是涉及到重要的时间节点。

那我们来算一笔账。首先，假设一个产品对应到前端和后端的规模，至少在 10 人以上。大厂可能更多，但小企业可能两三个前端、三四个前端、五六个后端这样的配备。

在这样的一个人员规模下，我们每天可能要在告警处理上花至少 1 个小时，一周就是 5 个小时。如果我们能把这个时间压缩到 0.5 个小时——也就是说一周我只需要花半个小时去 review 一下线上的故障方案，剩下自己就解决了——按照企业为员工支付的成本（按 3000 元 / 天的标准，含五险一金）来估算，每年能节省小 80 万。

![](https://static001.geekbang.org/infoq/b2/b2f81f43f5feacf1868c506694532bdd.png)

但这还只是开发工程师花在告警处理上的成本。做过开发的都知道，你本来在专心写一个需求，突然老板甩过来一个问题，你立刻就要停下手上的工作，开始排查——心流的状态是被打断的。而且恢复这个状态要花更多时间。所以实际成本一定比这个还要高。

那能不能造一个 Agent、一个数字人来解决这个问题呢？晚上就不用再去盯着或者接收告警，除非有极端情况才需要人去处理。

我畅想了一个画面：比如晚上再次遇到告警的时候，Agent 首先自己去分析，分析完以后知道影响面是什么，然后基于代码仓库去排查问题，排查完直接改代码，直接提交，直接提一个 Merge Request。开发同学要干的事情就是 review 一下代码、验收一下，看看他分析得对不对——这跟我们没有做这个之前用 AI Coding 解决问题的流程是一致的。

第二个画面：第二天早上，收到一份头一天的日报——昨天有 35 条告警、7 次任务、整体健康度是什么样子的、有哪些 todo。Agent 越用越聪明，因为每一次用 AI Coding 也会发现，它分析完了以后最终你并没有采纳，而是用了自己的方法去解决——那为什么你不采纳？是因为发现了某个问题，下次同样的问题就能避免。

第三个画面是长跑的画面：每周收一份周报，上周累计解决 30+ 个问题、采纳率从 60% 提升到 95%……这个数字同事不是只在救火，他是在帮团队积累经验。

那能不能让一个"数字人"真的来替我们值班？——能。这就是我们今天要讲的 Eva。

## 把脏活累活做扎实：五道硬门槛

落地真正难的，从不是模型，而是工程的脏活累活。 我们造这个 Agent 的过程，遇到了五道硬门槛：

第一道：Agent 架构怎么设计——到底是用重型多 Agent 编排框架，还是自研 Planner + Tool Loop，还是用 CLI 子进程 + Agent SDK？

第二道：上下文治理 A：日志规范——线上跑着几十个服务，每个服务命名都不统一，Agent 怎么知道该查哪个日志库？

第三道：上下文治理 B：代码 ↔ 日志的映射——多仓多服务下，Agent 怎么知道这条告警应该去哪个代码仓库排查？

第四道：告警聚合与去重——一次请求可能产生 N 条告警，全部丢给 Agent 是巨大的浪费。

第五道：把排障 SOP 写成 Skill——这是最关键的一步，但也是最容易被低估的一步。

挑战 1：Agent 架构选型——自主性 vs 确定性的取舍。 第一条就遇到了取舍——Agent 架构到底怎么选？我们当时面临三条路线：

第一条路是重型多 Agent 编排框架，比如 LangGraph 这种。一上来就要规划任务、规划状态机、写 DAG，听起来很美，但企业级场景里大多数告警处理都是"查日志 → 改代码 → 提 PR"这种相对线性的流程，重型编排反而把简单事情复杂化。

第二条路是自研 Planner + Tool Loop，自己写一个规划器，中间去调各种工具。听起来很可控，但企业级最贵的是什么？是时间。自己造一套规划器，光测试稳定性就要花好几个月。

第三条路是直接基于 Agent SDK，写一个 CLI 子进程 + 一个 Skill。这是最轻的——没有重型编排，没有自研框架，就是一个简单的循环：给它一个提示词，告诉它这是什么告警、什么上下文、应该按什么 SOP 去排查，循环跑完就结束。

我们最终选了第三条。

![](https://static001.geekbang.org/infoq/d0/d04e850af419d90c508bfbb4f67c0c57.png)

为什么？因为对企业级产品来说，90% 都是工程代码——拉代码、查日志、跑测试、提 PR——这些动作不需要 AI 自由发挥，写死反而更可靠、更便宜、更可预期。只有那 10% 的环节——分析、定位、排查、写报告——才是 AI 的真正主战场。

所以我们的架构是：

DETERMINISTIC 90%（确定性的工程代码） → AI Coding CLI spawn 子进程（AUTONOMY 10%，让 AI 自由发挥） → DETERMINISTIC 90%（又是确定性的工程代码）

这是一个非常重要的取舍——企业级 Agent，确定性 > 自主性。

挑战 2：上下文治理 A——分布式日志规范治理。 第二条门槛，就是上下文治理。在企业里头，决定你这个 Agent 能不能落地的，往往不是中间那个 AI Loop，而是前面这一堆工程的脏活——你能不能让上下文是受控的，而不是野生的。

我们先解决第一个问题：日志的规范。

线上跑着几十个服务，每个服务都在打日志。但这些日志的格式千奇百怪——有的服务叫"traceId"，有的叫"trace\_id"，有的叫"TRACEID"，有的把 TraceId 放在第一列，有的放在 JSON 的某个字段里。如果不做规范化，Agent 拿到一堆日志，根本不知道哪个 ID 是关键 ID。

我们的做法是：每个服务在自己的代码仓库里声明自己的字段。这个声明文件就放在仓库根目录，里头写清楚"我的服务名是什么、我的 TraceId 字段叫什么、我的 Error 字段叫什么、我的 Time 字段叫什么"。然后有一个统一的 TraceId Normalizer，在 Agent 拿到日志的时候，先过一遍 Normalizer，把所有格式都归一化。

![](https://static001.geekbang.org/infoq/3e/3e4c272cb4cf1cd206a0d0f84716e162.png)

Before 的时候，Agent 要自己识别、自己试错；After 的时候，Agent 拿到的是结构化的、字段明确的数据。这一个改动，上下文 Token 直接下降 58%——因为不用再让 AI 去猜字段名了。

挑战 3：上下文治理 B——MultiRepo 与日志库的映射。 第二个上下文问题更麻烦——多仓多服务下，告警来了，Agent 怎么知道该去哪个代码仓库排查？

我们的产品有几十个服务、几十个代码仓库。每个服务都有自己的告警规则，都可能产生 error 日志。如果什么都让 Agent 自己去探索——把所有的日志都丢给它，把所有的代码仓库都开给它——AI 能力再强，他也能解决问题，但问题在于成本。时间成本、Token 成本，还有排查问题的准确率都会下降。

所以我们定义了一个规范：在每个仓库的根目录下面有一个.aliyunrc 文件。这个文件里头写清楚：这个服务的名称是什么、对应到阿里云的 LogStore 是哪个、对应到的代码仓库路径是什么、这个服务是谁维护的（人员邮箱、账号名称）。这是一个 mapping 的规范化配置文件。

![](https://static001.geekbang.org/infoq/e4/e4c3c1abf75dbfbe9fe6ed153c8d989e.png)

这个配置文件在每个项目下都有。如果我作为其中某个服务模块的开发者，要去推动其他人采用这个规范，其实很简单——我只需要给他提个 PR，剩下的事情他只需要考虑要不要 merge 进去就行了。这个规范对代码仓库没有任何其他影响，所以推广起来非常顺滑。

接下来，当 Agent 拿到一条告警时，它先去查.aliyunrc，找到对应的代码仓库和对应的日志库，然后去那一个仓库去排查——而不是在所有仓库里头乱搜。

挑战 4：告警聚合与去重——精准度与成本的取舍。 第三个工程问题，是告警的聚合与去重。

先说去重。线上的告警并不是所有告警都要第一时间处理。只有优先级最高的告警——比如页面打不开了——你必须 5 分钟内恢复。但中间有大量 P1 级别的告警，影响面有限，可能只是用户看到一些不同的提示，主流功能都还能用。这种告警优先级没那么高，不需要开发同学第一时间停下手上更重要的工作去处理。

但线上的告警不会因为你没处理就停下来——它会频繁地告。如果每一次告警都丢给 AI 重新处理一遍，这是巨大的浪费。

我们做了去重之后，告警的去重率是 61%——相当于每天有一半以上的告警都不需要处理，因为已经处理过了。

![](https://static001.geekbang.org/infoq/5c/5c921c0645cf0608326ea508a84f0941.png)

再说聚合。请求先到前端，再到后端，再到更底层的服务，每一个服务都有告警规则、都会把告警打到 Agent 上。如果 Agent 一接收到一个消息就去处理，这是一个 TraceId 产生的 N 条告警——你可能要等一个时间窗口，把这些 TraceId 相同的日志全部聚合在一起，整合到一次告警里，再统一打给 Agent。这是为了降低调用 Agent 的频率、降低成本。

去重和聚合这两个问题，不是真正在做这个项目的人是想不到的——只有真正做了才会有体感。

挑战 5：把"排障 SOP"写成 Skill。 前面四个挑战，都是在解决确定性问题——通过工程代码、通过各种又脏又累的活，把问题都搞定。

接下来最关键的一步：怎么让 Agent 高效地解决问题？ 分析、定位、改代码、提 PR、写报告——这一步才是 AI 真正发挥价值的地方。

这里就涉及到一个取舍——这个流程，到底拆成一个 Skill 还是多个 Skill？怎么拆才是最好的？

我们当时考虑过拆成多个：分析是一个 Skill，写代码是一个 Skill，写报告是一个 Skill。但后来想了一下：

这个过程——从收到告警日志、丢给 AI、把代码仓库 clone 到服务器本地、跑一个 Claude Code 的分析和修复任务、分析完成之后提交、生成一份报告——这不就是我们每天在 Cursor 里头、在 Claude Code 里头干的事吗？说白了就是一个简单的 Loop——我给它一个上下文，写个提示词告诉它：你去通过什么样的排查 SOP 去解决并且修复，修复完了以后你自己去做单元测试、自动化测试来验收，只有通过了，你才能去提 PR。

所以后来我们就定义成一个 Skill——因为这样足够简单，不用去考虑 Skill 串联、上下文共享等额外复杂性。

这个 Skill 我们起名叫 Error Analysis for Eva。

![](https://static001.geekbang.org/infoq/e3/e3821c90cc1bc7cc66bb113c51bd39fe.png)

它蒸馏了我们工程师对于线上告警治理的经验和流程。核心 Know-how 一共四个：

第一，日志坐标直达。告警只给你当时那一个 error 日志，但你要分析出原因，需要这个 error 的上下游非 error 日志。Agent 拿到一堆日志后，要能直接定位到对应的日志库——不需要试错、不需要探索。刚开始没做好的时候，AI 会自己去试错，一会儿找这个、一会儿找那个，中间就需要人的经验去判断。我们在 Skill 里把"什么类型的告警应该去查哪个日志库"直接写死。

第二，Query 有策略、有预算。SLS 有两种搜索方式——结构化搜索和全文搜索，到底用哪一种？哪一种更高效、成本更低、效果更好？日志通常只需要查一段时间窗口，不需要把范围扩得很大——所以默认是 2 小时，更短也可以压缩。另外只查这个 error 的关键路径，不要把所有上下文都拉下来——一个 TraceId 拉下来可能上兆。

第三，跨服务追根因。你只收到一个告警，去查下游代码仓库的时候，AI 自己也会犯错。我们通过一些 API Pattern、通过一些工程的确定性方式，给到 AI 一些经验——这个服务如果明确调了某个接口，那个接口就属于那个服务的，我干嘛让它自己去探索？直接告诉它"只要日志里出现了这个 API Pattern，你就直接去找那个库"。

第四，上下文与修改受控。有些时候 AI 会过度设计——它只需要改一个符、做一个小改动就行了，但它给两个仓库提了 PR；或者它做了一些"顺手重构"，改了一堆不该改的地方。Skill 里要把这些都约束住——Agent 只改它该改的，不许顺手动其他东西。

这些坑我们都踩过：上下文爆炸（Token 暴增）、模型过度修改（无效修改率曾高达 71%）、同类的故障重复做推理、长上下文失控……

![](https://static001.geekbang.org/infoq/54/54126e18ea3beeb65fd267b40030e053.png)

最后，怎么评估这个 Skill 到底好不好用？我们用历史告警回放的方法——回放了 120 条历史告警，让 Agent 重新跑一遍，统计指标：

6.2 分钟：中位分析耗时

0.42x：单任务 Token 成本（是原来的 42%）

3%：无效代码修改率（从 71% 降下来的）

根因定位的正确率、报告的可读性、修复是否可被接受——这三个是核心。一定要有真实的数据来反馈、来优化——不能只靠试两个 Case 觉得跑通就结项了。

## 让数字同事能进化：记忆、Skills 沉淀与拟人化

这五道门槛都解决完了之后，整个流程就跑起来了，效果也还可以。但这就够了吗？

告警接住了、原因分析出来了、修复也提上去了。但一个"数字同事"，不该只会救火。

我们后来又做了几个事情：让 Eva 越用越懂业务、让她的 Skill 能自我进化、让她变得有"人格"——不至于让人对告警产生疲劳。

记忆·进化·定时任务。 我们做三件事：记忆、进化、定时任务。

记忆：LessonsRepository。 早期的时候，AI 修复的成功率并没有那么高，大概只有 60% 多。我们 review 过几个失败的 Case，发现 AI 经常犯某几类错误。这个时候，我们会给 AI 一些 feedback——"你这次问题分析得不对，应该是 XXX"。这些 feedback 最终要能让模型学到、并且持续用到。

![](https://static001.geekbang.org/infoq/6e/6efaa34feff94ccb39fadd32e1c92b9a.png)

我们做了一个 Lesson Injector——把人反馈的 lesson 抽象出来，变成一个记忆，每次有选择地注入到 prompt 里。注入策略是分级的：critical 级别的全量注入；其他类型的限长 3000 字以内；按 scope\_level + importance 分级匹配。这样下次遇到相似的告警，类似的 lesson 就会被自动召回并注入。

进化：Skill 搜索 pattern 自沉淀。 早期 Skill 在跑的时候，会花很多轮次去查日志、跨库查询。模型在生成 SLS MCP 工具调用参数的时候，经常会有错误或试错——调了三次才调对。这个过程其实有一个东西可以沉淀：它的搜索 pattern。一旦成功过一次，下次就没有必要再从零去探索了。所以我们在 Skill 里单独定义了一个目录，Agent 每完成一次成功解决问题，就要反思这次搜索环节哪些是对的，下次哪个又是好的——把这些 pattern 直接内化到 Skill 文件里。

这就形成了一个经验回流的闭环：

告警 → Lesson Injector → Agent → Lessons Repository → 下次相似告警召回并注入。

Agent 越用，搜索效率越来越高。

定时任务：日报、周报。 每天发日报、每周发周报——这是人类创造出来的优秀实践，把它交给 Agent 是顺理成章的事。

复利效应。从一开始上线的采纳率 65%，到现在 W28 采纳率 95%——不是某一个 Skill 突然变聪明了，是所有的机制在时间维度上产生了复利。

拟人化：对抗"告警疲劳"的入口。 人是需要反馈和情绪的——你做了一个东西如果它有"性格"，你会更愿意跟它交互。

![](https://static001.geekbang.org/infoq/f7/f7cdb2750bc4fa6b9828ec5b57d55cbe.png)

我们给 Eva 定义了 8 种情绪——开心、赞赏、困惑、鄙视、大驾、害羞、崇拜、飞吻。它根据当前的修复情况——修得顺不顺、这个问题好久没修了还是刚修过——自动去选不同的表情和文案。

比如某天线上一切平稳，告警不多，Eva 就会在飞书群里发一条：

"今天的系统，依旧在线发光。✨"

而不是冷冰冰地贴一条消息。这是一个很拟人化的东西——也是对抗告警疲劳的入口：你对着一堆冷冰冰的告警消息，时间久了就会麻木；但如果告警来自一个"数字同事"，她会有情绪、会吐槽、会开心——人和人之间的连接感，反过来又提升了人对告警的关注度。

## 让人始终握着方向盘：Human in the Loop 与效果评测

到这里，Eva 已经能接住告警、分析原因、提交修复了。但生产级的产品，线上的用户量很大，出个故障就是一堆投诉。我们其实早就在基础设施层面做到了让 AI 自己修复、自己上线——但我们没敢这么做。

因为生产环境容不得半点马虎。

所以人必须在这个流程里头始终握着方向盘。

Human in the Loop：Review、Merge、反馈。 我们的流程是这样的：

Agent 修复完（commit 到独立分支） → Human: Code Review → Merge / Rollback → Human: 反馈 → 回流 Lessons。

![](https://static001.geekbang.org/infoq/f0/f0646b7bba4a765962b60d35d0373214.png)

每次修复都必经人工 Review。即便 Agent 的方案看起来没问题，最终的 Merge 动作必须由人完成——这就像自动驾驶的 L4、L5 再先进，方向盘后面也始终要有人。

日报、周报。人只需要去关心到底有哪些问题其实时间长了还没有解决，而是需要解决但是没有解决的。

反馈驱动进化。Review 的过程中，人会给出"采纳 / 不采纳"的判断——如果判断是"不采纳"，会附上具体原因："这个问题不是这个服务的，是另一个服务的""这个改动有更好的实现方式"……这些反馈会回流到 Lessons Repository，成为下一次的经验。

半年下来，我们做到了一些数据：

HUMAN · 采纳率 = 95%（W28）——从 W1 的 65% 涨到 W28 的 95%。

周人均告警治理时长：从 5h 压缩到 0.5h——早就已经超额完成了。

任务完成率：最近一个月做到 3 个 9（99.9%）。

修复采纳率：95%。

效果评测：指标、方式、成本。 具体怎么评测？分三层。

![](https://static001.geekbang.org/infoq/58/58cedee90f7e885d209ae1264c90c8c8.png)

第一层：核心指标。

任务完成率 99.9%——Agent 接到的告警里，99.9% 都能闭环到底（要么提交 PR 要么给出可执行的修复建议）。

修复采纳率 95%——Agent 提交的 PR 里，95% 被人采纳合并。

周人均告警治理时长：从每周 5 小时压缩到 0.5 小时。

年化成本：5.3 万（Token + 服务器）对比原本要花的 87.8 万（人力时间成本），一年省下 82 万。

单任务平均处理时长：5 分 39 秒——比人工处理快 5-10 倍。

第二层：报告预览 + 人工评价闭环。

每一份 Agent 提交的分析报告都带一个 HITL 入口——人可以一键反馈"诊断正确 / 不正确"。如果"不正确"，需要填写最终修复意见。这些反馈全部回流到 Lessons。

![](https://static001.geekbang.org/infoq/1a/1a2ea811bc58a3ef09fb0aba97c50f19.png) ![](https://static001.geekbang.org/infoq/6a/6ae1ede859b9e513ba031f7b8c63b150.png)

第三层：成本视角。

很多人会问"这个 Agent 自己也要花钱啊，跑这么多 token 是不是亏了？"——我们来算账：

一年 Token + 服务器成本：5.3 万。

原本一年需要的人力时间成本：87.8 万。

净省 82 万。

Token 成本之所以能压这么低，关键就在于我们没有在 Skill 那一层让 AI 自由探索——中间你不断地发现问题、不断地去优化迭代，把确定性的东西变成脚本、变成规则、变成约束。所以 Agent 自己花的钱也少，把人的时间释放出来了。

Eva 的日常：两个研发同学真正会打开的入口。 给大家看一下 Eva 在日常的界面。研发同学真正会打开的入口就两个：

飞书群：告警来了 Eva 就在群里反馈（修复完成卡片、问题分析、下一步建议）。

监控台：日报、周报、HITL 反馈，都在这个入口完成。

后台还有两个 Eva 会"天天路过"的界面：监控中心（Agent 运行状态、今日告警、系统总览、近 7 天趋势）、分析报告·人评页（每一份报告都带一个 HITL 入口）。

## 6 条思考：跑通比完美更重要

最后，简单总结一些思考。

第一，跑通 >> 架构完美。 一开始很多生产级的产品并不是一开始就设计得很完美的——都是说"我要先用 AI 时代最快速的方式看到效果"。有了这个结果之后，再去说服老板、去做汇报、拿到更好的资源和预算。不要一上来就设计一个非常完美的架构——能不能用 3 天时间搞定问题，这是第一个问题。所以我们没有自己造轮子、也没有基于开源框架，我们直接基于一个很底层的 Agent SDK，直接写了一个提示词、写了一个 Skill，这个事情就搞定了。

第二，确定性 > 自主性。 这个项目里头 90% 都是工程代码——只在中间的"分析、排查、写报告"环节用到了 AI，那才是模型自由发挥的地方。大量的确定性地方不要直接让 AI 去干——AI 虽然能干，但要付出成本：时间成本、试错成本。所以企业级的 Agent，确定性一定是更重要的。真正能到 90% 验收就不错了，确定性大于自主性。

第三，上下文治理是一个入场券。 很多 Agent，大家眼睛都盯着中间那个 Loop，但实际上决定你这个产品能不能落地的，往往不是那个 Loop——而是前面工程的治理和后面确定性的东西，你有没有让它受控，而不仅仅是"跑通"。所以上下文治理是入场券。

第四，让"她"能进化。 智能时代、AI 时代有一个非常大的不一样——它是可以进化的。如果大家在自己的工作中去造 Agent，一定要让它能够进化起来——脑子里要有一个进化的思路。经验回流、Skill 版本化、HITL 反馈闭环——这些机制要让 Agent 越用越聪明。

第五，成本视角 + Agent 思维。 我们平时的工作里头其实有大量的场景可以用 Agent 去解决。怎么能够从 0 到 1 起步、想到这个问题、迈出第一步，用 AI 真正用 3 天的 AI Coding 时间、花费可能不到一次 7 天的用量，能把这个问题真正落下来？决定性的因素是：你有没有养成用成本的视角去看问题？有没有养成用 Agent 的思维去思考解决方案？ 这是一个思维的问题。

第六，Skill 一定要靠真实反馈来进化。 不能只靠"试两个 Case、发现它跑通了就结项了"。一个真正的企业级产品需要长期维护，而长期维护又需要它是可控的维护。在这个过程中，到底好与不好，不是说拿两个 Case 出来秀一下就 OK——要真正用真实的业务反馈来驱动你这个 Skill 不断的迭代和优化。

好，那这就是我今天的分享。Eva 不是一个人在救火，她是和团队一起在长跑。 感兴趣的可以扫一下我的公众号（郭美青聊 AI），我会经常去分享一些关于企业级 AI 的真实思考。
