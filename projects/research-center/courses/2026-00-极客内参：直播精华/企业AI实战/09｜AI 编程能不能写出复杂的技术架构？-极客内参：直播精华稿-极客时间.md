## 开源、基础架构与 AI 编程

先从一个很朴素的问题说起：你怎么判断一个程序员厉害？

我想很多人的第一反应是开源做得好，是个开源大佬。

开源和复杂基础架构，一直是社区的主阵地。Kafka、Redis、Kibana，这些都是从社区里长出来的。但基础架构发展到今天，越来越成熟，也意味着门槛越来越高。一个复杂技术人员要打磨五年、十年，甚至十几年。要经过大量的编码、补测试用例、解决边界场景。一个团队要花几年时间才能做出点东西，个人几乎碰不了这个领域。

AI 编程出来以后，这件事变了。

一个人或者一个小团队，也能完成一个高质量的复杂基础架构组件。所以我说，AI 编程和技术架构、开源不冲突，反而能加速你成为有社区影响力的人。找工作、个人影响力、薪资回报，最终都会落到你身上。

从这个角度看，AI 编程对个人的收益是巨大的。不管是构建影响力，还是做出自己的作品，它都是以后程序员的必备技能。我的体感很直接：没掌握这个技能，后面大概率会掉队。

AI 编程把产出的成本降下来了，把一个人的生产力提上去了。小团队真的能做复杂的基础架构组件。你看上节课讲的 Loop 编程，再往前讲的企业级 Agent，一个人或者两三个人就能做。

对你来说，最大的收益是什么？想办法把 AI 编程用好，去拿到开源的收益。而开源本身，也是你练 AI 编程最好的载体和验证场。

核心论点很明确：基础软件当然可以用 AI 写，而且应该用。但你不能把它当成全自动开发，而是要把它当一个好用的工具、一个得力的助手。

![](https://static001.geekbang.org/resource/image/24/f4/248b19fa54fd6f42a7a62699f9e1f1f4.png)

听上去好像是一条路，但真动手的时候，你会遇到各种各样的门槛。AI 很好用，但门槛还在，只是门槛变了。编码本身的门槛降了，但你的工作量转移到了别的地方：怎么找到一个好项目？怎么找到项目里真正的问题？这个问题是不是社区真正关心的？他们愿不愿意合并你的 PR？

这些考验的是你的判断力和系统能力。

如果你指望 AI 全自动把你变成一个大佬，基本不可能。基础架构里的错误路径、性能取舍，模型给不了你答案，你得有自己的判断力。但把它当一个超强助手，完全现实。我们这两个项目——RobustMQ 和 MQ9 就是这么做的。方向和架构我们来定，产出交给 AI，效率提升非常明显。这是 AI 编程的核心。

所以你只要把 AI 驾驭好，哪怕是社区这种大型 Rust 技术组件，AI 也能交出很好的结果。区别就在于你能不能驾驭它，能不能让它做到你要的结果。

## 三层分工：哪些交给 AI，哪些不能

说到这里肯定有个问题：哪些内容可以交给 AI？哪些不能？

我们的做法是分为三层，每一层分工不同。分好层以后，用起来就没有心理负担，你知道它错在哪里、哪里不致命。

第一层：不容错的核心层。

比如存储系统的并发控制、通信协议。这部分不能错，涉及性能、稳定性、可靠性，一定是人来主导设计，AI 只能做辅助、做执行。

第二层：可以快速实现的样板重复层。

测试用例补齐、统一内部接口开发、文档补齐、重构这些都可以让 AI 去搞。比如 RobustMQ 的官网主页，完全是 AI 做的，做得很好，我们非常满意。

第三层：必须验证的收敛层。

Review、测试、混沌测试，这些是人来做最终验收的。

![](https://static001.geekbang.org/resource/image/bb/ea/bbbf18933543de802c34d222081d2fea.png)

那不能交给 AI 的部分是什么？

架构是灵魂。你设计一个分布式基础架构组件，整个系统架构是灵魂，核心代码是整个架构里最核心的东西。

架构和设计。这是项目的灵魂，比如你怎么设计架构？设计思想是什么？开发节奏是什么？

存储层并发控制和协议的实现。这部分涉及后面的性能和可靠性。

性能关键路径和疑难问题的修复。

架构是你自己设计的，存储层并发协议的可靠性是你搞定的，性能也是你搞定的，整个项目的价值就有了。就像搭房子，你把四周的框架搭好，AI 去把墙里的砖补好，它做得特别快。

但 AI 写出来的代码会有问题——比如 Rust 里到处 clone、原子操作和锁的使用不当、异常处理不到位。这部分我们会通过 Harness 去限制它，不让它瞎写。

总结一下就是：AI 可以写出能用的代码，但基础设施需要的是优雅的代码。

有的项目只要能用就行，有的项目需要优雅。你要能区分哪些项目写到能用就好，哪些要追求优雅。千万不要觉得社区组件可以随便写，为了开发速度让 AI 写核心代码，后面一定会重构，那就是时间的代价。这不是能力问题，这是责任问题。

## 反向用法：不让它写，让它查

分享一个反向的用法：不让 AI 写代码，让它查代码。

AI 的用法远不止写代码。你自己写一部分，让 AI 去 review——查边界条件、panic 风险、资源释放、内存泄漏。这三类场景可以直接做成 Skill 或 Harness，每次跑完自动检查。

![](https://static001.geekbang.org/resource/image/83/c0/83d4005970e5e064d0d87d30ee1832c0.png)

甚至可以双模型互查：A 模型写，B 模型检查。我们在社区经常这么干——让 AI 写一版，我看完觉得没问题，再换个模型好好审一遍。为什么这招好用？核心代码的所有权和理解在你手上，你又多了一个不知疲倦、守规矩的 review 角色。

还有一个更值钱的用法：让 AI 当质疑者。我可以让 AI 扮演一个持怀疑态度的资深基础设施工程师，来质疑已有的设计理念、愿景和定位。比如对 MQ9 提最尖锐的问题：这是真实需求吗？壁垒是什么？注册中心怎么做？通信怎么做？我们会用多种角色来评审同一篇设计，比如技术架构专家、算法专家、一线开发者，各自挑刺，产出的建议再融会贯通。

## 真实项目：RobustMQ

它的定位是用 Rust 写的多协议统一消息引擎，一个 AI 时代的统一基础设施。单二进制，没有任何外部依赖，自己实现存储层。云原生支持 MQTT、Kafka、AMQP、MQ9 等五个协议。

当前进度是所有协议都已经打通，MQ9 第一版内核也已经实现了，目前到了 0.4.12 版本。下半年我们主要聚焦在 MQTT、Kafka 以及 MQ9 上。MQ9 会支持语义拦截和审计，Kafka 协议会探索 S3 存储。

整条路的野心很大，但你去看我们的代码，会发现代码特别干净。因为 AI 只是辅助，我们没有纯依靠它。我们一直有两个克制：克制地用 AI，克制地规划方向。比如主架构怎么设计？协议怎么设计？存储层和通信层怎么做？这些都是我们自己来的。

在开源项目里，我认为一个好的开源项目，一定不能外包给 AI。

RobustMQ 的逻辑是打通物联网设备到大数据平台到 AI Agent，用一份存储、多协议去打通这条数据链路。

![](https://static001.geekbang.org/resource/image/3c/41/3ca4e78fyy513228b435aa4b70fcc941.png)

这里有一个关键取舍：RobustMQ 不会发明新的协议。MQTT、Kafka、NATS、AMQP 这些协议，都已经内化在大模型的语料里面了。如果我们在 AI 辅助下把它们写出来，大家可以直接用，不用培养生态。发明一套新的抽象是很危险的，因为没人懂，生态起不来，AI 也不会写。

所以今天要讲的 MQ9，是建立在 NATS 协议之上的，我们也不建新的协议指令，任何 NATS 客户端都能直连。NATS 是文本协议，对 AI 原生也友好。AI 之间要通信，让它们知道协议是什么、能发消息。NATS 是成熟协议，有很多现成的 SDK。在 AI 时代，我们要做好取舍：不用新协议，也不在通信层面做新的抽象。

为什么这么做？在 AI 时代，模型能不能看懂你怎么用，本身就是一种生态优势。不要以为新造一个轮子就是好轮子，很多轮子能流传到今天，说明它已经是好轮子了，只是有些方式不太适合当下。你要想办法弥补它，而不是直接全盘干掉。

## AI 驱动的混沌测试体系

最能说明问题的是我们用 AI 搭了一套混沌测试体系的经历。

开源组件最怕什么？没人测，出了问题质量下降、口碑变差。我们就几个人推进社区项目，怎么保证质量？答案是 AI。

我们基于 Hermes Agent 和大模型驱动了一整套混沌测试闭环：自动部署集群、注入故障、跑多语言 SDK 测试、分析日志、生成报告。全程没有硬编码执行流程，也没有 Python 人工调度，用 Markdown 描述要做什么，大模型自己驱动一切。

这套系统完全是用 Claude Code 实现的，做了 26 个场景（MQTT 3 个、MQ9 3 个），分为基础故障、客户端异常、组合场景三类。每天凌晨、每两天、每周都会自动跑。

开发这套混沌测试组件，我们只花了一周多。

## MQ9：Agent 的通信层

先想一个场景：你电脑上装了 OpenClaw，同事电脑上也有一个，你要跟它们通信、分发任务，怎么做？都在线的话，HTTP、RPC 都没问题。但对方下线了怎么办？断电了怎么办？故障了怎么办？你还要发任务、失败要重试、中间结果要回传。通信会变得很复杂，尤其是多对多的时候，HTTP 撑不住，你需要消息队列。

但 Kafka、RocketMQ、RabbitMQ 这些，又不是为"流量很小但 Agent 特别多"设计的。这不是传统的吞吐问题。

现有的方案有几种：HTTP 同步调用、SSE 流传输、Webhook，还有挪用 Kafka 和 NATS。前三种解决不了上面的问题，Kafka 和 NATS 能解决，但传统 MQ 的抽象里没有 Agent 的身份。 Kafka 和 NATS 解决的是服务与服务之间的通信，服务数量基本固定，不会爆炸式增长。但 Agent 的增长数量无法预测，甚至每分钟都在增加。这就是传统消息队列的不足，也是我们做 MQ9 的原因。

## 从管道到邮箱

MQ9 是 AI Agent 的通信层。我们给每一个 Agent 分配一个邮箱。有了邮箱这个概念，通信就一句话的事：我直接把邮件发给你，你好了回我一封，按顺序看就行。

技术层面，它是一个协议无关的可靠消息管道，一个持久化的邮箱，自带注册中心，Agent 之间能相互发现、相互发邮件，支持 N 对 N 拓扑。一旦用了邮箱模型，N 个 Agent 跟 N 个 Agent 之间的通信，就变得非常丝滑。所以 MQ9 不是 NATS，也不是 Kafka，它是一个消息邮箱。协议和存储层是我们自己设计的，轻量级 SDK 封装交给 AI 来搞。

![](https://static001.geekbang.org/resource/image/57/8e/571371860a746c128f4d90fd83dfdf8e.png)

有句话这么说：如果说 Memory 填的是记忆层，MQ9 填的就是消息层。其中最关键的区别在于传统 MQ 是管道，MQ9 是邮箱。

管道没有名没有姓，核心指标是吞吐和顺序性：发到 topic，谁拿到算谁的。传统 MQ 按管道方向设计：大数据管道、通信管道。

MQ9 是专门给 Agent 设计的。一个邮箱属于某个 Agent，邮箱地址就是它的身份。A 发给 B，就是给 B 发邮件，B 收到以后回复。每个邮箱既有命名的意义，也有消息的语义。

设计出发点很朴素：Agent 之间通信应该像发邮件一样简单。邮件系统已经跑了几十年，人与人之间通信从邮箱到微信，底层都是同一个模型。

MQ9 想做的就是给每个 Agent 一个身份，把这个身份当邮箱地址，相互之间通信，底层持久化，保证一定能收到、按顺序收到。这解决的是 Agent 之间可靠通信的问题。

我们在 NATS 基础上，用它的 PUB/SUB 模式规则来设计：创建邮箱、发送邮件、收取邮件，同时支持 Agent 的注册、解绑、发现、上报。同时也有一些刻意不做的取舍：不做幂等，有多层 TTL，消息不分片，单条消息有大小限制，邮箱地址就是 Agent 的凭证。优先级分高、中、低三层，每层内消息有序。邮件重复发了就重复了，看最新的就行，数据会过期。

## Agent 注册与发现

那么 Agent 怎么找到 Agent？这就是注册中心的能力。

Agent 上线的时候注册上来，带着身份注册，告诉注册中心我有什么能力。另一个 Agent 要做翻译，它就去找具备翻译能力的 Agent，找到地址，给它发邮件。它做完事情以后把邮件返回。这就是 Agent 之间的注册与发现。

我们支持按 key、按 tag、全文检索、语义检索。底层这个检索引擎，核心也是自己写，在 AI 的辅助下完成。我们基于 LanceDB 做向量和关键词索引，用 FASTMO 这个 Rust 库生成向量数据，自己实现检索引擎的几个模块。

LanceDB 的选型我们也是通过 AI 帮我们快速做决策的，当然我们有自己的判断，不是什么都给 AI，只是设计和使用过程中和 AI 协作得比较多。

## MQ9 的价值与边界

MQ9 的价值有三个标准：

轻。有了 MQ9 以后，A2A（Agent to Agent）的通信从 60 行代码变成 15 行，半小时就能闭环。

不丢消息。即使对方 Agent 不在线，你也可以把消息发到它的邮箱地址里，它上线就能拿到。

和 A2A SDK 百分百兼容。基于 A2A 开发 SDK，AI 都能搞定，不用绑定协议，整个协议会和 Kafka、RobustMQ 一样共存。

MQ9 的边界也很清楚：做 Agent 的相互发现，做可靠传输，做监控追踪。它是一个协议中立的基础设施，是 Agent 通信这块的基础设施。它本身不做协议、不做编排、不做框架，只解决一个问题：Agent 通信。

## 变的是端点，是假设

背后的判断其实很简单：变的是那条假设，就是端点。

以前通信两侧是设备，收发一个字节，坏了就换一个。现在端点是智能体，是一个聪明的端点。以前是写死的、固定的服务。

假设变了，设计理念就跟着变。传统消息队列的瓶颈是每个通道搬多少数据，也就是吞吐性能。但 Agent 出来以后，挑战变成了怎么管理海量的端点、海量的 Agent，解决大量 Agent 快速上线下线的问题。而且这些 Agent 流量又很小。以前几个 topic，要扛几个 G 的通信；现在几千万个 topic，只有几百兆流量。

特性不一样，基础设施的设计就得变。这些判断 AI 做不了，要靠你的经验和判断力。

假设变了，发现、可靠、追踪、管控，这些职责最终都会让基础设施发生大的变化。这也是我一贯的观点：基础架构这块肯定会有大变化，肯定会有新的设计和实现。

![](https://static001.geekbang.org/resource/image/77/73/77920cc5dd83524afd9a29c7e4f1f073.png)

MQ9 要做齐就四件事。前两件是地基，后两件才是真的难。第一是发现，就是 Agent 能找到 Agent。第二是邮箱模型，也就是持久化的邮箱模型，离线也能收到消息。最后两个是全链路追踪和语义拦截与审计。Broker 要理解 Agent 之间通信的内容，理解它要做什么事情，然后把它约束好。

## 个人的机会在哪里

三个结论：

AI 编程可以把产出的成本降下来，这也是最大的，大家都能理解。

小团队也能碰复杂的基础架构组件，完全没问题，只要你能把 AI 编程学起来。

开源是增加项目经验和个人竞争力的最佳载体和实验场。

AI Coding 的时代，人多不一定是优势。真正的稀缺是什么？不是技能，不是怎么做，而是你能不能把一个事情想清楚、定义清楚，你有没有把这件事做出来的欲望和努力。

如果你今天在做独立开发者，自己一个人做项目，或者想打造自己的影响力——这件事是没问题的。我们已经在跑了，用 AI 编程做一个大型的社区开源项目，有不错的影响力。我想告诉你的是，这条路是通的，只要你愿意。

### 四个现实的切入路径

个人怎么切入？有四个现实的路径：

先读懂一个。 把一个成熟组件的核心链路，在 AI 辅助下读通。

从场景库入手。 给某个开源社区组件写混沌测试场景。门槛很低，不影响核心流程，但价值很高，能保证整个社区项目的稳定性。这属于脏活累活，大家不愿意干，但又很有价值。从场景入手给开源项目做贡献，是很好的起点。

接生态的活。 SDK、集成插件，模式最清晰，也最容易出成果。

最后再碰内核。 有了上下文，再去啃硬骨头。从简单的事情慢慢做到内核，从普通贡献者成为 PMC，完全可通。在 AI 辅助下是可通的。如果你一上来就写内核，很多人都会被拒掉。这是一个现实的路径。

## 最后：五个结论

最后咱们用五个结论来收个尾：

复杂的技术基础架构是能用 AI 去写的，而且应该去用。但你不能把它当成全自动开发的工具，而应该把它当成一个高效的助手。

整个开发过程中要分为三层：核心层人来主导，实现层 AI 承担大头，收敛层人做最终验收。

反向做法很值钱：不让它写核心，让它查边界条件、当质疑者、做多角色评审。

MQ9 不是一个新的 MQ，而是把心智模型从管道换成了收件箱。身份和状态优先于吞吐，它解决的是新范式下的问题。

很多场景变的是端点，也就是假设。以前的端点是微服务里那些固定的服务，现在变成了智能体。端点变了，整个基础设施的设计就会发生新的改变。
