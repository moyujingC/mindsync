## 前言：大模型开发的“玄学”现场与工程师的觉醒

大家晚上好！我是尹会生，很高兴能再次在极客时间的直播间跟大家分享。我最近的身份有所转变。过去我可能更像是一个纯粹的创业者，每天埋头在公司里帮客户交付各种各样的 Agent；而现在，我更希望以一名老师的身份，把这套成体系的工程化方法论带给大家。

与其让我一个人在那儿吭哧吭哧地搞这种“古法手工编程”去交付 Agent，不如教会大家怎么把模型稳稳地交给企业。因为我发现，一个人交付的效率终究是有限的，但如果我们能培养出一批懂工程的大模型应用工程师，那整个 AI 落地的进程就会快得多。

过去这两年，大家做大模型肯定都有个共同的体感：这玩意儿太像“玄学”了，做起来全靠“猜”。你在网页端测试模型时，它显得特别聪明，上知天文下知地理；但只要一接入你的业务系统，它就开始“变脸”：不是答非所问，就是记不住刚才说的话，甚至还会一本正经地胡说八道。很多人会觉得是模型不行，但实际上，问题往往不在 Agent 框架本身，而是因为我们把它给“喂”笨了，甚至亲手把它给“练废”了。

![](https://static001.geekbang.org/resource/image/ef/31/eff753bfd1622ce056c83fc854d4ed31.png?wh=2386x1326)

## 从“上限能力”博弈转向“下限能力”保障

在过去很长一段时间里，大家都在薅大模型的“上限能力”。什么是上限？简单来说就是看哪个模型最新、跑分最高。比如 Claude Code 出了 V3、V3.5，或者 OpenAI 又更新了。大家一听说有新模型，马上就转过去，因为上限越高，模型确实越聪明，写出来的代码虽然可能还是“屎山”，但起码能跑通，Bug 也会少一点。这就支撑了大家过去很长一段时间的那套“氛围感编程（Vibe Coding）”的逻辑——只要模型够强，我就能偷懒。

但最近，很多成熟的程序员和企业开始“悟”了。前两天我在西安跟 WorkBody 的团队聊天，他们以前 90% 的业务靠 AI 编排和 Web Coding，但最近他们开始疯狂招募具备三年以上经验、精通微服务、中间件和数据库的资深工程师。

为什么？因为大家发现，做软件不能只看上限。上限决定了代码“能不能写出来”，而下限才决定了这东西“能不能商用”。如果你生成一张图，最好的时候能打 90 分，但最差的时候只有 20 分，那这个产品是没法推向市场的，用户得不停地“抽奖”。但如果我们能通过工程手段，把下限提升到 60-70 分，虽然不一定惊艳，但起码每一张图都是合格的。

这就是我们今天要聊的主题：为什么很多 Agent 达不到这个合格的下限？这就是因为我们没有意识到，模型本身是需要“驾驭”的。如果你把大模型比喻成一匹野马，那么我们所做的一切工程化努力，就是为了给它套上那副沉稳的缰绳（Harness）。

![](https://static001.geekbang.org/resource/image/20/52/209a6afff0ecffe0497ddyyc693e7a52.png?wh=2344x1268)

## 姿势一：给它喂“垃圾食品” —— 缺乏清洗的 RAG 知识库

第一个让 Agent 变笨的姿势，就是给它喂“垃圾食品”。这在 RAG（检索增强生成）系统里表现得最明显，也是大家最常踩的坑。

### 1.1 垃圾进，垃圾出的惨痛教训

很多人觉得 RAG 没什么技术含量，不就是找个向量数据库，把 PDF 往里一扔，接个 Embedding 就完事了吗？我以前也是这么想的，结果在第一笔政府项目上就吃了大亏，差点做亏本了。

那时候我们还没用上现在的 Dify。我们把系统搭好，丢给那些政府部门用，人家啪一下把成堆的文档往里一塞，然后就开始问问题。结果呢？模型要么说找不到，要么回一段乱码。我们技术支持被薅到现场才发现，那些原始文档里带有大量乱码、OCR 错误、格式错乱。

如果你不做数据清洗，模型检索出来的全是垃圾碎片，哪怕你用的是满血版的 DeepSeek 或 GPT-4，它也回不出正确答案。后来我们学了网易 QAnything 的思路，先分大块，再分细的小块，加上多粒度切分和重排（Rerank），效果才算救回来。所以大家一定要记住：相似和相关是两回事。 “雷峰”和“雷峰塔”向量相似度可能 70%，但你要是没做本体论和实体识别，模型就敢给你乱回。

### 1.2 LLM Wiki：Karpathy 的自进化知识库

现在自媒体都在炒作“RAG 已死”，说 Karpathy 提出了 LLM Wiki。其实没那么玄乎，它跟 RAG 更多是互补关系。

向量 RAG 像 Ctrl+F：适合查个短文本、FAQ、搜个电商商品。

LLM Wiki 像个会做笔记的研究员：它让 LLM 先把散乱的文章、论文“编译”成结构化的 Wiki，有概念分类，有反向链接。它虽然慢一点、贵一点，但它理解了文档的结构。

如果你现在做的是那种 20 页以上的长文档分析，或者需要精准定位到某个复杂的表格，我建议你看看 LLM Wiki。我们在实践中甚至会玩“组合拳”：先拿 RAG 快筛缩小范围，再拿 LLM Wiki 做精查，这样既快又准。

![](https://static001.geekbang.org/resource/image/2d/3b/2d16bdc09776265e0b9205f390a5ca3b.png?wh=2378x1314)

## 姿势二：写“意识流”Prompt —— 没有版本管理的提示词

很多人的 Prompt 写得跟许愿池投币一样，全靠“感觉”。

### 2.1 告别 Vibe Coding，走向 SPEC Coding

有些开发者把几千字的 Prompt 直接塞在 Java 的 String 变量里，没有结构，也没有 Git 管理。你今天改了一个无关紧要的字，或者模型版本稍微一迭代，Agent 就不听话了。这哪是编程啊？这就是“氛围感编程”。

我们现在提倡 SPEC Coding。大家去面试，如果人家让你写个排序算法，你得背快排，因为那能涨工资；但实际干活，你得调用成熟的库。写提示词也是一样，必须有严谨的预制结构：

Role（角色）：在初始化时定死，明确边界。

Context（上下文）：动态注入实时业务数据。

Constraints（约束）：明确告诉它什么是不准干的（比如禁止回复政治敏感信息）。

Workflow（工作流）：引导它分步骤思考，避免“意识流”回复。

Output Spec（输出规范）：强制要求 JSON 等结构化格式，方便系统解析。

大家看现在的 Claude Code 或者 Hermes（我爱叫它“爱马仕”），它们好用的秘密就藏在这些结构化的系统提示词里。比如 Hermes 最大的特点就是能把你模糊不清的指令进行任务分解（Decomposition）。如果你不学这套 SPEC 模式，你的 Prompt 永远停留在“撞大运”的阶段。

![](https://static001.geekbang.org/resource/image/09/b4/0988ea33ac1d897f826f758276c10db4.png?wh=2330x1252)

## 姿势三：让它“裸奔”上网 —— 工具调用没有约束

把工具调用权完全交给 LLM，就像把银行账户交给一个完全没有自控力的熊孩子。

3.1 概率模型的不确定性陷阱

大模型本质上是概率模型，它的行为是不稳定的。如果你的智能体具备删除数据库、发送邮件、调用外部 API 的权限，而你没有给它加任何约束，它哪天要是由于幻觉陷入了死循环，一秒钟就能烧掉你几个月的奖金，甚至搞垮你的生产系统。

### 3.2 加装“智能锁”：API 网关与运行时沙箱

我们要用工程手段把风险管住，通常有 6 个关键做法：

强类型契约：调用的参数必须做 JSON Schema 强校验。

工具代理层：别让 Agent 直接碰数据库。

人在回路 (Human-in-the-loop)：高危操作必须暂停，等待管理员确认。

资源配额与熔断：限制调用次数和 Token 消耗。

容器沙箱：Agent 执行代码必须在 Docker、Wasm 等隔离环境中。

双向过滤：调用前查注入，调用后查敏感信息脱敏。

这种对模型进行分门别类控制的体系，就是 Harness 工程。它就像给野马套上了最稳固的笼头，让每一声“驾”都收到预期的反馈。

![](https://static001.geekbang.org/resource/image/67/48/67bcfba7af4d23772290a2a21339d748.png?wh=2362x1308)

## 姿势四：只有“七秒记忆” —— 混乱的上下文工程

大家玩大模型久了，肯定觉得它们记忆力跟金鱼一样。如果你不管理上下文，把 128k 的窗口全塞满，它不仅响应慢，还会产生“脑雾”。

### 4.1 内存整理的“概率陷阱”

大模型的上下文就像内存。当我们对话越来越多，内存快满的时候，系统会自动整理。但大模型不知道哪些信息重要啊，它全靠概率去“脑补”。结果可能把你最重要的第一轮设定的业务规则给压缩掉了。

这时候你会发现，原本养得好好的“龙虾”，聊到第五轮突然就不认人了。所以我们要学 JVM 调优一样，去搞上下文工程。核心方法有三种：

Reduction（压缩）：移除重复信息，只保留索引。

Isolation（隔离）：分而治之，大任务拆解为子智能体，减小各自的上下文。

Offloading（卸载）：上下文仅保留轻量引用，重数据放在外部冷存储。

只有让智能体只拿到最关键的信息，它的效果才能保持稳定，而不是忽好忽坏。

![](https://static001.geekbang.org/resource/image/39/61/39681de39126e54a7a47cd1f2f6ee961.png?wh=2368x1298)

## 姿势五：全靠“人工 Eyeball” —— 没有自动评估

这是最让我感到无奈的。很多人做完一个 Agent，自己跑去跟它聊两句，觉得“嘿，回得还行”，然后就直接上线了。结果用户一用，反馈全是差评。

### 5.1 别让大模型“奉承”你

如果你直接问大模型“我这个回答好不好”，它甚至会奉承你。前两天我看到个笑话，有人拿某包 AI 识别毒蘑菇，模型说这蘑菇鲜美适合做汤，结果人家中毒了。中毒后再去问，模型才改口说“对不起这蘑菇有毒”。这种事后补救在商业环境下是致命的。

我们需要建立严谨的评估工程。建立 Golden Dataset（黄金测试集），把用户最可能问的坑、以前真人客服的准确回复全都整理出来。然后利用 LLM-as-a-Judge，让更高阶的模型去客观打分。只有量化了，你的优化才有方向。

![](https://static001.geekbang.org/resource/image/a6/ff/a6ba63e69bb94d980a273314a73fa3ff.png?wh=2366x1272)

## 姿势六：让它“单打独斗” —— 缺乏状态机与流程编排

很多人迷信“一个全能 Prompt 解决所有问题”，结果模型自由度太高，跑着跑着就发散了。尤其是在处理“订票 + 改签 + 入库”这种复杂任务时，单一模型往往表现得逻辑混乱。

### 6.1 状态机：给野马套上缰绳

在工业场景，Agent 的自由度必须被限制。我们现在用 LangGraph 这种工具去做工作流编排，本质上是用“确定性的代码逻辑（DAG）”去约束“不确定性的模型推理”。

为什么要搞多 Agent 协作？因为每一个 Agent 的人设不能崩。你不能让一个 Agent 既当产品经理又当程序员，它会精神分裂的。把任务拆解成研究、需求、规划、开发、验证五个步骤，每个步骤由专人（Sub-Agent）负责，这就是多智能体协同的精髓。

这就涉及到了我们的 Harness Workflow。我们要把任务拆解成可控的小步骤，确保每一步都在预设的轨道上运行。这就像是企业的部门分工，财务不管研发的事，研发不管市场的事。

![](https://static001.geekbang.org/resource/image/37/2f/3742dc43a66183a4ce04d7a3ee1c192f.png?wh=1280x685)

## 姿势七：出了错就“重启试试” —— 看不清整条链路

这是最后一种让 Agent 废掉的姿势：闭眼开车。Agent 报错了，你看着一堆乱七八糟的 JSON，完全不知道是哪个环节出了问题。是在检索时找错了文档？还是在推理时逻辑断了？

### 7.1 全链路可观测性：接入 LangSmith

出错的时候，简单的重试往往解决不了业务逻辑错误。最好的办法是接入 LangSmith 这种 Trace 工具，把思维链（CoT）、Token 消耗、工具调用的入参出参全都看个透。

你要像监控分布式系统一样监控你的 Agent。每一个转折点、每一条检索出来的原文、每一次 API 的响应耗时，都要有迹可循。只有这样，你才能从“写 Prompt 的”转变成真正的“大模型应用工程师”。

![](https://static001.geekbang.org/resource/image/3f/9f/3f38ace2ce251317529fd2e8805ae09f.png?wh=2354x1280)

## 结语：从“写 Prompt 的”升级为“大模型应用工程师”

在 AI 瞬息万变的今天，开发者需要的不再仅仅是撰写 Prompt 的技巧。撰写 Prompt 只是入门，它类似于我们在开发中的“Hello World”。真正的价值在于你如何运用严谨的工程思维，通过数据处理、安全网关、状态机编排和评测系统，去驯服那些不确定的模型。

虽然现在新名词特别多，什么 Harness、mcp、skill、LLM Wiki，但其实“换汤不换药”。以前我们做传统软件开发时叫内存管理，现在叫上下文；以前叫调 API，现在叫 Function Calling。我们作为懂 Java、懂数据库、懂 Python 的成熟工程师，最大的优势就在于我们有工程底蕴，我们知道怎么让系统“稳”。

不管你最终选不选择加入我们的实战营，我都建议大家去梳理一下这些知识点。在这个时代，单纯靠“感觉”写 AI 已经行不通了。让我们一起用工程化的铠甲，为大模型 Agent 构建起坚实的商业底座。
