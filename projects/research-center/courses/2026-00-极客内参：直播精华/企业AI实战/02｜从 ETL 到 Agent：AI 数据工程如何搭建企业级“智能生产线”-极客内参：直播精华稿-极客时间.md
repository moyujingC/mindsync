### 为什么我们要重新定义数据工程？

大家晚上好，又见面了！欢迎来今晚的直播间，我是曾丹。

在正式开始分享之前，我想先花一分钟聊聊为什么这次直播我把标题起成“从 ETL 到 Agent：AI 数据工程如何搭建企业级“智能生产线””。如果你在企业里做过数据，大概率经历过这样一个阶段：我们花了多年时间，把企业数据管道从手写脚本升级到 Airflow，从传统数仓演进到 Lakehouse，从简单的报表做到实时指标。但最终的交付物，无非就是三样东西：一张表、一个指标、一个报表。这套工程范式，我们称之为 ETL。过去 20 年，它支撑了全球几乎所有大型企业的数据决策。

但在过去一年半里，我在为企业做咨询、做内部培训以及跟很多一线团队做实战复盘时，频繁听到同一种声音：“我们的数据是 Ready 的，模型也是 Ready 的，但为什么就是做不出生产级别的 AI 应用？”

深挖下去你会发现，这不仅是模型的问题，也不是数据质量的问题，它其实是一个“系统供给”的问题。我们过去为“人”设计的数据系统，和我们今天要给“模型”用的数据系统，压根就不是一回事情。我们需要重新搭建一条生产线，我在这门课里面给大家取了一个响亮的名字：AI 数据工厂。

今天的分享，我们将围绕 6 个关键词展开：Data Foundation（数据底座）、Contract（数据契约）、Context（上下文工程）、Skills/Tools（技能与工具层）、Harness（运行时）以及 Eval/Governance（评测与治理）。这六层结构是我在企业一线落地总结出的一套参考架构，同时也是我们《AI 数据工程实战营》整门课的骨架。

今天我们不卖焦虑，不讲空话。我会用最新的公开数据和技术动向，把“为什么要重做这件事情”讲透。今天不讲模型训练，也不比较 GPT 和 Claude 谁最强，我们讲的是：企业如何把 AI 做成一个可生产、可评测、可治理的系统。

### 第一部分：为什么现在必须重讲 AI 数据工程？

1.1 瓶颈迁移：从“模型接入”转向“系统供给”

请大家关注 PPT 左侧的几个数字。

第一个数字是 8 倍 与 320 倍。这是 OpenAI 在 2025 年 12 月发布的《The State of Enterprise AI，2025 Report》中的真实数据。调研显示，过去一年 ChatGPT Enterprise 的周消息增长量增长了 8 倍，但每个组织的推理 Token 消耗量却增长了 320 倍。注意，不是 3 倍，是 320 倍！

这两个数字的含义完全不同：8 倍说明“人在更多地使用 AI”；而 320 倍说明“企业不再只是和 AI 聊天了”，而是把 AI 嵌入到生产流程里，去跑更多复杂的多步推理任务。换句话说，AI 已经从一个“聊天玩具”变成了企业的“生产基础设施”，这是一种质变。

第二个数字是 88%。麦肯锡在 2025 年 11 月的报告中指出，88% 的组织已经在至少一个业务场景中常规性地使用 AI 了。在今天，“我们在用 AI”这句话已经不再是差异化的优势，而变成了像“我们上云了”一样的常态。

真正的残酷在于第三个数字：只有 23% 的企业在业务流程中做到了规模化应用，而能把收益反映在营收利润上的，仅占 6%。

这意味着竞争焦点已经从“谁先接上大模型”转向了“谁先把 AI 做成可生产、可评测、可治理的系统”。接模型在今天几乎是零门槛的，调个 API 下午就能跑起来。但要变生产力，门槛在模型周边的系统工程。正如 OpenAI 报告中定义的“Frontier Workers”，那些走在前面的员工，其 AI 消耗量是中位数的 6 倍。拉开差距的，是把 AI 做成系统的能力。

![](https://static001.geekbang.org/resource/image/13/f6/13a73ff5yy6560306cfc677064d077f6.png?wh=2204x1234)

1.2 范式转换：数据消费者从“人”变成了“模型”

从传统的 ETL 到现在的 Agent，到底变了些什么？核心在于：数据消费者已经从“人”变成了“模型”。

旧范式（ETL → 报表）：交付物是表、指标和批处理任务。消费者是运营人员、分析师、老板。只要报表准时、准确、稳定就行。

新范式（Context → Agent）：交付物是上下文（Context）、能力（Skills）和反馈（Feedback）。模型不看固定报表，它是动态检索、工具调用、按需加载。你不能提前把数据都聚合好，你必须具备“访问能力”，让模型在需要的时候自己去拿。

这种转变带来一个致命问题：静默失败（Silent Failure）。过去表变了，发个邮件通知分析师改代码就行。但下游的模型不会读邮件，一旦 Schema 变了，它会默默地给出看似合理但完全错误的答案。它不报错，它在“悄悄地变差”，这比直接报错更危险。

举个比喻：过去的数据工厂像食品工厂，把原材料做成罐头放在货架上；现在的 AI 数据工程像食品供应链，你不知道客户最后要做哪道菜，你必须保证他要什么、什么时候要，你都能第一时间给到。

![](https://static001.geekbang.org/resource/image/1f/32/1f821c8707efe56ayye3ef70ed96b132.png?wh=2200x1234)

1.3 选型逻辑：RAG、Workflow 还是 Agent？

过去半年我见过太多企业一上来就说要做 Agent。我总是劝他们先做最简单可行的方案，因为复杂度是有成本的。

1\. RAG（解决“知道什么”）：解决 FAQ、知识问答、政策解释。胜负手在于检索质量和来源可信（比如客服想知道保修几年，员工想查报销上限）。

2\. Workflow（解决“按流程做什么”）：流程清晰可控，比如工单分流、对账检查。AI 的作用是替代原本需要人判断的节点。

3\. Agent（解决“在不确定中完成任务”）：涉及跨系统调查、采购建议、故障定位。关键在于规划能力（拆解子任务）、工具调用和异常处理。

我的建议原则：能用 RAG 解决的，不要上 Workflow；能用 Workflow 的，不要上 Agent。 为什么？第一是成本：Agent 链路越长，Token 消耗越大，延迟越高；第二是可评测性：RAG 只有命中率和相关性指标，Agent 的成功路径可能有几十条，极难判断好坏；第三是可控性：Agent 自由度越高，越容易出现越权访问、信息泄露等大事故。Anthropic 的官方文档也强调过：从能工作的最简单事情开始。

![](https://static001.geekbang.org/resource/image/8d/bf/8dcbe7041bd0dbea4ff2f8806e2ab3bf.png?wh=2200x1234)

### 第二部分：企业级 AI 数据工厂的六层架构

这张图囊括了整门课的全貌。我们要搭的不是一条 Pipeline，而是一座工厂。

2.1 架构全貌

\- L1：数据底座（Data Foundation）：原材料层。包括结构化数据（DB/ 数仓）、非结构化数据（文档 / 音视频）和 SaaS 接口（飞书 / 钉钉）。

\- L2：数据契约（Contract）与语义层：规格说明书。定义指标、权限、版本和兼容性，防止静默失败。

\- L3：上下文层（Context Layer）：核心加工车间。负责文本切片（Chunking）、索引构建、检索、内存管理和状态维护。

\- L4：工具与技能层（Skills / Tools）：业务能力封装。把如“订单异常诊断”这样的逻辑封装成可复用、可调用的模块。

\- L5：编排与运行时（Harness）：驯马具。决定 Agent 怎么运行，包括循环、重试、检查点（Checkpoint）和人工审批（HITL）。

\- L6：评测与治理（Eval / Governance）：发布门禁。决定系统能不能上线，包括调用链路追踪、审计和回滚。

![](https://static001.geekbang.org/resource/image/66/ea/66837449c6443726ea29fe47e23a52ea.png?wh=2204x1238)

2.2 核心能力 1：数据契约（Contract）

AI 链路最怕的不是报错，而是 Schema 漂移带来的“悄悄变差”。

我讲一个真实的故事：之前我们做一个 RAG 企业客服，准确率调到了 95%。某天突然掉到 60%，排查了两个礼拜，才发现上游把“客户等级”从“VIP/ 高级 / 一般”改成了枚举值“T1/T2/T3”。上游觉得这是个小优化，没通知任何人。下游模型匹配不到等级，就开始自己编、瞎掰，导致大量合理但错误的回答。

数据契约就是把数据模型当成 API 管。在构建阶段（Build-time）就要暴露漂移，不让变更流到生产中。一定要通过 CI/CD 强制执行，而不是靠人约束。

![](https://static001.geekbang.org/resource/image/14/cc/1469d9fddc81d063c78314d1be2161cc.png?wh=2184x1202)

2.3 核心能力 2：上下文工程（Context Engineering）

业内共识：Context Engineering（上下文工程）正在取代 Prompt Engineering（提示词工程）。

2025 年 6 月，Shopify 的 CEO 和 OpenAI 前首席科学家安神（Karpathy）同时发表观点：上下文工程是一门精妙的艺术。提示词工程关心的是“我跟模型说什么”，而上下文工程关心的是“模型看到了什么”。

在 128K 甚至更长的上下文窗口里，Prompt 只是极小的一部分。真正的上下文包含：系统角色、检索到的数据、工具描述、记忆（短期 / 长期 / 状态）、范例（Few-shot）和消息状态。

设计原则：

1\. 做减法：不是越多越好，塞得越多注意力越分散，模型越容易出错（即上下文腐烂 Context Rot）。

2\. 分层组织：System 层、Tool 层、Memory 层职责清晰。

3\. 预算管理（Attention Budget）：主动压缩、裁剪、摘要，把关键信息提前。安神曾类比：模型是 CPU，上下文窗口就是内存，我们要像操作系统一样管理内存。

![](https://static001.geekbang.org/resource/image/19/e1/194fedd77772bf68b41d8dce5e7d5fe1.png?wh=2188x1210)

2.4 核心能力 3 & 4：Skills 资产化与 Harness 运行时

Skills（技能） 是 2025 年底火起来的概念。Anthropic 推出了 Agent Skills 标准。Skills 就像文件夹，里面有元数据（Metadata）、指令集、工具适配器和输出规范。

核心设计是“按需加载”：Agent 一开始只加载 metadata，只有匹配到任务时才加载完整内容。这解决了“企业知识无限而窗口有限”的矛盾。Skills 是企业真正的独门秘籍，因为它凝聚了业务场景的 SOP。

Harness 决定智能体怎么工作。安神（Karpathy）现在管理着 10-20 个 Code Agent 帮他干活，离不开 Harness。

它包含：状态管理、预算控制（Budget）、重试、检查点、上下文压缩和人工介入（HITL）。

\- Budget 救命：有团队没设预算，一个晚上烧了 3000 多美金 API 费。

\- HITL 生产必备：高风险决策（涉及资金、采购、删除）必须人审批。

![](https://static001.geekbang.org/resource/image/56/76/56a48ff92ab2eac46642c84f334d0e76.png?wh=2204x1234) ![](https://static001.geekbang.org/resource/image/6d/fb/6d0876171acee8b84b0032e37d5a87fb.png?wh=2188x1208)

### 第三部分：生产化落地——评测、治理与启动

3.1 评测闭环：从氛围检查（Vibe Checks）到质量门禁

没有评测的 AI 系统本质上只是玩具。

评测要分三层：

1\. 组件评测：单测检索召回率（Recall@K）、SQL 生成准确率、工具选择准确率。

2\. 任务评测：核心业务任务的成功率、业务 KPI 改善、人工满意度。

3\. 线上监控：答错反馈、Token 成本、响应延迟（P99）、人工接管率。

最关键的是建立 Quality Gate（发布门禁）。发布新版前，如果检索命中率低于阈值（比如 85%），或者工具误调用率高于 2%，就不允许发布。这让发布变成了严谨的工程操作，而不是“赌一把”。

![](https://static001.geekbang.org/resource/image/7b/45/7bf926edc147b6ebd9c1ac6459f69945.png?wh=2202x1232)

3.2 治理与安全：AI 事故的防火墙

麦肯锡报告显示，51% 的企业在 AI 落地中遇到过事故。治理必须在设计时内嵌。

六个支柱：最小权限（能只读绝不给删）、审计回放（Agent 行为不确定，必须能重现场）、策略前置、发布门禁、工具边界和 HITL 兜底。

3.3 启动策略：别等“完美数据”

很多企业说“等我们数据治理好了再做 AI”，这是误区。

只有 6% 的成功案例是在数据完全 Ready 时启动的。90% 以上是在非结构化脏数据上做的。

新思路：先把上下文层（Context）搭出来，让数据“找得到、拿得出、连得上”。利用大模型本身去处理数据质量（如实体抽取、语义归一），效率比人工高 10 倍。

![](https://static001.geekbang.org/resource/image/ef/c4/ef31965e4533aa1a33yy199438a46dc4.png?wh=2200x1226)

### 第四部分：案例实战、趋势与路线图

4.1 零售采购 Agent：从分析走向闭环

这是一个真实案例：某跨境零售企业通过采购 Agent 降低了 40% 的资源浪费。

过去，买手每天要看库存、销售、天气、报价，做上百个决策。传统 AI 只给预测，买手往往因为忙而不看。新方案直接跳过推荐，让 Agent 自动下单，只在超额或异常时让人介入。

判断 Agent 的四个维度：高频、高价值、可验证结果、错误可恢复。 满足这四条，就基本可以冲了！

![](https://static001.geekbang.org/resource/image/84/c6/84ace0afc2db6a06451b9827666beec6.png?wh=2192x1216)

4.2 半导体多源查询：跨系统的数据考古

半导体行业文档分散在 5-6 个 Repo（规格书、测试库、实验记录等）。工程师查个 Bug 需要“考古” 40 小时。

Multi-Agent 解法：给每个数据源挂一个专家 Agent，通过协调 Agent 拆解分发。这证明了：先把“访问层”做出来，比追求彻底的“数据集中化”更有价值。 同时，Google 推出的 A2A（Agent-to-Agent）协议正在解决不同框架间 Agent 通信的标准问题。

![](https://static001.geekbang.org/resource/image/f3/0c/f302f9a97861e32414c2fyyd6ec8d10c.png?wh=2170x1194)

4.3 未来三年的判断与落地路线图

竞争优势转向专有数据与 Skills 库：基础模型差距在缩小，护城河是你独有的数据、封装出来的 Skills 和那套工程系统。

Agent 工程标准化：MCP 协议将成为 AI 的 USB 接口，实现跨平台复用。

最稀缺的人才：系统串联者。能把数据、模型、工程、业务和治理拼在一起的人，是未来五年最值钱的角色。

落地时间表：

0-90 天（打地基）：单场景 RAG 启动，建立最小评测集。

3-6 个月（跑流程）：高价值流程 Workflow 化，核心逻辑 Skill 化，建立回放机制。

6-12 个月（放自治）：在可恢复场景引入 Agent，Harness 平台化，治理门禁机制化。

![](https://static001.geekbang.org/resource/image/45/cf/45760f84bb1e52ec5b1ce189ea8f45cf.png?wh=2168x1198)

### 结语：做 AI 生产系统的设计者

企业不缺大模型，缺的是一座 AI 数据工厂。

大模型本身只是一个原生态的东西，要让它变成生产力，需要的是一套标准化的软件工程。我们这门课的目标，就是让你不再只是一个调 API 的人，而是成为一名 AI 生产系统的设计者。
