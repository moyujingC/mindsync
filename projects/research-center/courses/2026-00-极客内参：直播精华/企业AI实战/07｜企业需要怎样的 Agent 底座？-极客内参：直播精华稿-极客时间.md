哈喽，大家好，我是 Robert。

今天的主题是企业需要怎样的 Agent 底座。内容分为两部分：一部分是对大厂在 Agent 底座方向的技术路线拆解，另一部分是 AgentOS 的架构拆解。

## 行业格局：大厂在做什么

今晚的直播分为四段。第一部分讲行业，看看现在大厂在 Agent 底座都在做什么，各家的路线差异在哪里。第二部分讲如果我们要自建 Agent 底座，必要性在哪里：为什么企业需要自己的底座，为什么不用大厂的。第三部分是如果要搭建一套自己的 Agent 底座，怎么设计实现，以及怎样用 AI 来提速。最后一部分是作为开发者，我们应该怎么培养自己的能力，怎么去了解 Agent 底座应该具备哪些能力、应该怎么设计，怎么让自己得到成长。

一句话总结：先看清楚大厂在这一层要什么，再看这套底座是怎么搭起来的，以及 AI 编程能帮到我们什么、不能做什么，最后回到你和我之间应该怎么练。

好，我们先来讲行业。

2026 年，企业级 Agent 平台已经是必争之地。你会发现 GitHub 社区每天的热榜都是各种 AI 应用、各种 Agent 相关的、Skill 相关的。各大云厂商也在开源各种各样的 AI Agent 开发平台、模型、底座、开发框架。比如华为的 AgentOS，阿里的悟空，字节的 Coze，它们都希望在 Agent 平台这个方向做一些事情。

![](https://static001.geekbang.org/resource/image/20/f8/2002d91954de083a909fd5f9edaf46f8.png)

这些大厂从以前做模型，慢慢在整个 ToB 的方向，不想再只卖模型了，想卖底座。相当于在它的平台上把底座搭起来，你就可以买它，最后上下游比如 PaaS、SaaS 这些应用就能卖出去。Agent 底座的功能，就是把 Agent 的运行、编排、治理打包成平台去卖。

业界的分歧在哪里呢？云厂商是从它的基础设施——比如容器、虚拟机这些 IaaS 平台往上去做；有一些应用厂商，比如模型提供商，可能从应用层往下去做框架。还有一些独立的企业做框架，方向是不一样的。

大厂的整个投入方向，基本就等于未来三年技术标准的走向。你会发现业界各种各样的框架、底座，比如 Dify 这样的开发平台，随着 Agent 越来越多，支撑多个 Agent 或大量 Agent 运行的平台，后面会成为刚需。

### 六家大厂的位置

我们来看整个行业格局，六家的位置：

华为 AgentOS：从基础设施往上做，基础是云 + 算力 + 模型。

阿里 AgentScope：一个开源框架，你可以通过这个框架开发自己的 Agent，底层已经把 Runtime、基础的 Notify 这些都做好了。

阿里悟空：企业级 Agent 平台，可以让 Agent 在上面跑。

AWS Agent Core：一个托管的底座，帮你把 Runtime、Gateway、沙箱这些都做好，让你的 Agent 能跑在上面。

百度 AgentBuilder：在各自的生态内搭建，让你快速开发 Agent、让 Agent 运行在它的平台上。

![](https://static001.geekbang.org/resource/image/43/75/43a6f07c0dc3dc4f65c25e317ff06275.png)

各家产品的侧重点不一样，虽然看起来都是给 Agent 当运行底座或开发框架，但方向不同。

这里有两种读法：越靠近基础设施、越倾向托管的平台，比如 AWS Agent Core，强调的是可控免运维，你把 Agent 运行上去，就能稳定地跑，免运维。它不管你开发当中的事情，代码怎么写它不管。

而像阿里 AgentScope，强调的是开发框架。它把 Agent 里面的一些功能组件都内置了，你可以快速地通过代码写出你的 Agent，不用写很多底层的东西。但是你写出来之后，运行在哪里？运行在你自己的平台上。框架这种东西强调的是低门槛，以及你可以基于框架去组建各种各样的场景。

各大云厂商的角度归总一下其实不复杂：一种是开发框架，让你把 Agent 快速开发出来——提供公共组件、运行时、可观测这些能力；另一种是当你有了 Agent 之后，能在我的平台上快速跑起来，不用花费那么多精力。这就是框架和底座的区别，也是各大云厂商都会往这个方向去做的原因。

### 两个典型样本：AgentScope 和 Agent Core

两个非常典型的样本：一个是阿里的 AgentScope，一个是 AWS 的 Agent Core。

AgentScope 是开源框架，整个代码的编写和部署都在你手上。框架里包括整体的开发框架、Runtime、Studio 的一些监控之类的，覆盖的其实是开发部署到监控的全流程。它面向的是你怎么样去开发 Agent。

Agent Core 是云托管平台，你不用管自己的基础设施。最主要的包括 Runtime 的隔离。对于 Agent 来讲，因为它有了底层的模型，调用模型的话，你可以理解它是一个有自驱力的智能体。这时候它的隔离就非常非常重要，不然可能突破你的整个隔离体系，形成安全风险。状态隔离很重要，比如身份验证、可观测、评估审计。这些跟代码无关，你只要 new 一个 Agent 就跑在上面，这就是底座。

你会发现，不管是 AgentScope 还是 Agent Core，它们要解决的问题其实是高度重叠的：Agent 运行的 Runtime、Provider、工具、记忆、长期记忆、短期记忆、可观测体系、审计。

甚至你在业界很多产品，或者你们公司——假设你们公司有很多 Agent，要把这些 Agent 管理好，你会怎么往上抽象？对于程序员来讲，无非就是公用部分提出来，大家独立的部分跑在上面，各自开发自己独立的部分。这就是程序员的思维。

这其实也就是 Agent 框架、AgentOS 这个发展方向的原因：大家会把一些公用的东西抽出来，比如运行、记忆、状态隔离这些。大家都在做这个事情，不同产品的差别主要在交付方式这一块。

交付方式不一样，服务的人群就不太一样。底座是让 Agent 跑起来，主要给运营用，研发把 Agent 开发好，给运营，运营布上去。框架主要是给开发用。这个比喻可能没那么贴切，但大概是这么个意思。

### 百花齐放的阶段

业界有各种各样的做法，各种各样的叫法：Agent 平台、Agent OS、Agent 框架。回过头来看，你会发现好像这些组件，比如我们以前的小龙虾 OpenClaw，后面的 Hermes Agent，近期可以在 Claude Code 或者 Cursor 上面跑的 Skill，功能都差不多。

![](https://static001.geekbang.org/resource/image/0b/5e/0bb8b5eb7c3f69yyf1a1ebdd6838f65e.png)

虽然做的事情都很像，叫法不一样，但问题在于没有形成统一的标准。举个更简单的例子，Apache 现在就没有 Agent 方向的项目，不管是底座也好，框架也好，没有一个项目来让大家形成共识。

所以很多 Agent 相关的项目会很火、会爆火，但你今天真的要去用的话，你会发现找不到一个非常满意的、标准的项目。研究这类项目的时候会发现，平台也有、OS 也有、框架也有，还有各种开发框架，Dify、Cursor，都分不清谁是谁、每个东西是干什么的。

这并不是说这些不好，我想表达的是现在属于百花齐放的阶段。等过了这个阶段，我理解 Agent 的底座、框架，就会慢慢形成一个标准的大型项目。比如现在很多都是 Python 体系的，后面 Java 体系的东西也都会有。那时候叫法就会倾向于统一，甚至以后的 Agent 开发都会形成一个叫 Agent Spring 的东西，就跟我们以前微服务开发一样。这些都会有的，只是现在还比较早期。

### 两种打法：自下而上 vs 自上而下

业界主要有两种打法，在底座或者说 OS 这个方向。

![](https://static001.geekbang.org/resource/image/66/40/66b498814a670e9c8b76181a2075f640.png)

一种是自下而上做底座。 从算力、模型、运行时这一层，在大模型之上构建 Harness，给 Agent 开发运行的一套 Harness 体系。比如你今天开发一个 Agent，你肯定要给 Agent 做审计。最简单的例子，假设你有 10 个 Agent，每个都做审计，那如果你在整个底座上面已经具备了审计能力，你这块就不用做了。其他也是类似的，从下往上把公共部分做掉，这一层就是底座。

另一种是自上而下做管理。 比如现在最火的 Dify，从上层，从 Workflow 的角度、Provider 的角度去做应用的编排，通过模板去组织整套流程。“组织”这个词本身也是 Workflow 的一个概念。它强调的是低门槛、快速部署、场景多、很灵活。

不管自下而上还是自上而下，解决的其实是不同方向的问题，但又是一类的问题是怎么样让我们的整个开发流程也好，财务流程、管理流程也好，能够自动化起来、智能化起来。

如果要到研发人员这个程度，你可以走左边的路线，在底座上构建自己的 Agent；也可以在上面，基于 Dify 之类的、用 Coze 之类的去搭建自己的工作流。它其实并不冲突，看各家的技术储备和具体情况。

就跟我们以前做微服务一样，微服务有 Java 生态，Spring 那套做的也很好；后面也有 Golang 的生态，Golang 微服务也火了很多。服务发现也好，Nacos 也好，Keepalived 也好，每个方向都会有多种产品。本质上并不冲突，解决的是整个生态里面不同的问题，解决的是 Agent 怎么样更好地把事情做好的问题。

## 为什么要自建 Agent 底座

好，接下来有一个问题：前面有这么多平台，我们为什么还要自建？

其实平台这么多跟自建，并不冲突。到了今天，每家厂商都会有自研的东西，即使业界有标品。从更普适性的角度来讲，行业已经不再是自建或选购二选一的逻辑了，行业共识就是混合。

通用的一些流程，我们会用平台的产品，甚至通用流程都不用，就看每家情况。差异化流程一定是要自己掌握，一定不会交给平台。

有个判断标准很实在：假设这个 Agent 本身算不算你的竞争力？算的话，就自己掌握住编排、数据、选模型的选择权。

怎么理解？举个简单例子，你是个创业公司，你的核心能力就是 Agent。比如你做一个内容相关的，内容的生成、格式、规范这些都是通过你的 Agent 来运行的，那这个 Agent 就是你的竞争能力，你就应该全部自己把握。

另外一个现实的约束就是规模：包括调用量、复杂度到一定程度，就是成本核算的问题。所以问题不是要不要自建，而是从整个产业行业的角度来讲，很多组件其实是必须的，并没有标准说一定要用平台的。一部分会自己建，建成什么样，看各家的形态。而且业界并没有很强的标准，所以 Agent 的开发也好、Agent 的相关面试也好，都是百花齐放的。

### 私有化需求

现在一些传统的 ToB 企业，有私有化的需求。比如国企、大型央企，有私有化的需求。私有化需求里面包括：

数据主权：企业的私有数据，包括数据库、会话记录，不会出企业，不允许输出企业。

审计合规：数据调用、每一条决策链路要可追溯。

多 Agent 治理：模型选择自由，或者只能用私有模型。

这些都需要你的底座是私有化部署的。一句话：平台能给我们能力，但可能给不了我们整个的控制权以及私有化的需求。

![](https://static001.geekbang.org/resource/image/e8/47/e889fbb8bbaac371db87b971e2717747.png)

### 什么交平台、什么自己掌握

通用的流程，包括标准问答、一次性无差别的场景，这些都会交给平台。自己掌握的，是和我们自己核心业务耦合的编排、工具，以及私有数据、权限、审计链路，这些都要自己掌握。

实践上的建议就是：用平台跑通一些场景的验证，自建底座承载我们的业务应用服务。平台和自己开发并不冲突。

## AgentOS 架构拆解

好，到这里我们进入第三部分，整个架构的部分。

既然业界有平台、有底座、也有 Agent 的 OS，那在 AgentOS 里面，我们的整个企业级 Agent 底座是什么样的？

![](https://static001.geekbang.org/resource/image/29/ff/29551be080f3939b55f0e32ec7d1d1ff.png)

它是运行和管理 AI Agent 的一个底座系统，向上给各种 Agent 提供统一的运行环境。有了很多 Agent 以后，很多共用的部分就向下，接入模型、渠道、工具、记忆、身份、审计相关的，这就是前面讲的下沉，做底座做下沉。

从开发的角度，我们想办法把这些下沉的东西做好，上层就开发各类 Agent。做好我们应该做哪些部分？从整个 Agent 的架构来讲，主要就是五个：模型、渠道、记忆、身份和审计。

一句话理解：我这么多 Agent 怎么样能够低成本、快速地运行和管理起来？企业级 AgentOS 解决的就是这个问题。

抽象到开发维度：那么多 Agent，那么多公用的部分，我怎么把它下沉？下沉的时候有两个问题：第一，我要怎么开发这个下沉的部分，相当于开发一个让多个 Agent 运行的运行时；第二，Agent 是怎么和 AgentOS 去对接的，怎么运行在这个底座上面。

Agent Runtime 面向的是单个进程的执行环境，Agent OS 面向的是管理一群进程、调入资源、提供共享服务的那一层。就跟我们用操作系统上面跑很多个程序是一样的，你在上面写程序，可以调用操作系统的各种系统调用。这就是一个 AgentOS。

### 底座解决的五件事

![](https://static001.geekbang.org/resource/image/d1/06/d18861f36c71f4534cddeb23151d1406.png)

底座主要解决五件事情：

第一件，Agent 生命周期管理。 包括 Agent 的注册、启动、监控、销毁。每个 Agent 都有独立的 Prompt、模型、工具、渠道、记忆。关键词叫“独立”：你在这个底座上面，每个 Agent 的信息应该是要独立的。

第二件，统一的对外渠道。 比如对接企微、飞书、钉钉、Slack 等等，这些对外的统一渠道接入。

第三件，统一的对内接入。 比如 Provider、工具、企业系统，通过 MCP 去访问企业的 IT 系统以及企业内部知识库。

第四件，统一的记忆。 跨会话的长期记忆系统、可复用的 Skill、长期短期记忆的跨 Agent 知识沉淀、向上一层的知识库，记忆里面怎么把它复用起来。在整个 Agent 开发当中，记忆这一层是最难最难的。你包括整个对话的上下文压缩、对话处理、记忆的提炼、它怎么在你的 Prompt 里面传给大模型、怎么减少 Token，这都是很细节的问题。

第五件，工具调用和沙箱。 Agent 运行起来，有哪些工具可以调，这些工具在哪些沙箱里面运行。

这五个事情，我们怎么样把它下沉到底座里面？这就是接下来要讲的事情。

### OryxOS：企业级 AI 编程实战营的第一个项目

整个训练营我们讲的就是怎么样构建这个 AgentOS 的底座。我们会实现的包括：

Provider：怎么样和模型交互，以及 ReAct 怎么样构建一个自循环。

Memory：记忆怎么样从对话里面保存下来。

Tools：整个操作系统执行的时候，有哪些动作可以执行，包括运行时的 Sandbox。

Notify：对外通知相关的组件。

安全审计：以及分布式多节点运行的相关组件。

右边这张图看起来很复杂，这就是我们训练营里面第一个项目要做的 OryxOS。它本身就是一个给多个 Agent 运行的底座。

![](https://static001.geekbang.org/resource/image/f0/2d/f0e06c2ce9e302434a4e3eaf9702862d.png)

它最典型的模式，你可以理解在底座里面会支持 Reactor、Prompt Builder、Tools、Provider，然后基于 Memory 相关的，比如基于 SQLite 或文件系统，或者一些外挂数据库，实现跨节点、跨机器的记忆。

这一块做好了以后，我们可以通过一个 MD、一个统一的格式去定义一个 Agent。这时候对你来讲，你开发一个 Agent，只要去写好你的需求就可以了。

比如你的需求是“每天的数据校对”、“数据审核”，你要开发一个服务，你的审核怎么做？比如一个商品上来以后，你要审核它是不是违规，类似这种应用。或者客服、财务每日的对账、财务每天的信息整理的一个 Agent，你就直接用一个 MD 去把它定义好，你都不用开发。

你把 MD 整理好以后，下面的整个底座会在调度下，自动化地去调用下面的每一个组件。每一个组件完了以后，它就会快速地去建一个 Agent。

本质上对我们来讲，AgentOS 希望的就是我们把底层的公用部分全部开发好，在上层我们用尽量更轻的角度：比如只写少量的代码，只写一些 MD 或文字类的描述，它就能执行。相对复杂的 Agent，我们可以写一些脚本来辅助执行。

你写一个 Agent 不会涉及到底层这部分的开发，你都不会感知到底层的部分，因为底层全部会做好。这就是我们训练营第一个项目要做的事情。

我们在做的事情，其实和前面这些大厂要做的东西有点像了。

群里大家一直在问：我们做这个项目和 AgentScope 是不是很像？跟它们的区别、还有跟 Agent Core 的区别是啥？

这里我想告诉你，这个底座有两层意义：

第一层是 \*\* 教学意义：\*\* 让大家知道如果做一个大厂在做的 Agent 的运行底座，它应该要做哪些事情？你是怎么用 AI 编程把它实现的？怎么样从零实现？怎么样打造一个分布式的 Agent OS？

第二层是 \*\* 企业意义：\*\* 如果做好了，它有真实的意义，因为业界也需要这么个东西。

不管是从学习的角度，还是从简历、项目经验来看，它都是一个不错的项目。这就是我们要做的 OryxOS 整个底座。

### 能力拆解：五大组件

下面我们来拆解一下整体的 AgentOS 能力。

第一个是 LM Provider 抽象。 这一层的逻辑主要是调模型，把调模型这个事情，还有提示词的构建、提示词和记忆的融合。比如我给我的一个 Session 里面，我给上下文给一个提示词，比如“我昨天点了瑞幸咖啡”，它就会记下来。

Provider 的作用是，如果底层“点了一杯咖啡”这件事，让哪一个模型去帮我思考？本质上它是可以和多个模型去交互的。核心在于你怎么样去对接模型，能够允许你自由切换模型。这就是模型 Provider 的抽象。

第二个是 ReAct。 ReAct 本身做的其实是一个循环。它的输入是你想要做什么事情，这是你的提示词，我要做什么事情。这时候我会转给 ReAct 这个循环，然后它就会调上一层的 Provider，得到结果以后，去判断是要结束，还是要执行某个工具。

ReAct 这一层技术包括很多东西，比如你问“我今天穿什么衣服”，模型可能做两件事：查一下温度，查一下近期的潮流，可能有两次循环。但如果它两次循环做不完，一直循环就会卡死，所以要设置最大轮数。如果上下文太多，记忆当中的内容太多，上下文长度太长，导致超出长度以后就失败，所以要有失败和退出的策略。

还有在这个循环里面，我们的观测是成功还是失败？消耗了多少 Token？整个 Memory 的使用率是多少？是不是已经会从记忆里面去提炼东西出来？这些东西都是需要想的。

第三个是 Tools。 假设在下一层你又有了 Tool。你开发了很多 Tool，包括函数调用、MCP。这时候你怎么样通过你的提示，让模型、让 Agent 去执行某些具体的调用。底座在这时候就应该知道我有哪些工具，这些工具要被注册到整个底座里面，能够被上层的 Agent 去发现。包括参数校验、权限配额、调用的痕迹、审计。

第四个是记忆。 大家都知道小龙虾 OpenClaw，以及 Hermes Agent。Hermes Agent 对于 OpenClaw 的一个竞争优势就是说，它是一个会进化的 Agent。可进化是什么意思呢？其实就有记忆。一个 Agent 有记忆，它就能进化。我以前踩过的坑我不再踩，你以前让我做的事情我记得。你就会觉得它变聪明了。

在整个 Agent 里面，记忆是非常非常重要的，记忆层要包含：

短期记忆 / 会话级别记忆：当前会话是上下文窗口里面的记忆。记忆的长度有没有限制？是不是需要检查摘要？

长期记忆：比如跨会话的偏好。假设你个人在这台机器上运行了多个会话，多个会话之间是不是应该都记住你？因为唯一标识不应该是会话，而是这个环境、这个主体。

知识库：你有很多知识、构建了很多知识库、很多文档，它是不是也要理解这些文档？你告诉他一个事情，他能从文档里面知道你后台要怎么做。

可复用流程：很多复用流程可以沉淀成 Skill，跨 Agent 可以共享。

第五个是 Open Service 和渠道接入。 比如对外的 IM、邮件的 Open，如果每个 Agent 都要做，那你可以统一给它做了。渠道层就会抹平差异，你直接调一个 call 就行了，什么都不用管。如果你用框架，你还需要调函数自己去组织。

### 插件化设计：让底座长期演进

接下来我们讲几个功能设计的点。

第一个是插件化。

Provider 插件：底层可以通过配置或动态地去换模型，上层不用感知。会有模型自动切换，有些贵的模型和便宜的模型，有些模型不能用了，有些业务就一定要用贵的模型，它可以指定模型。所以整个插件化设计非常重要，你可以动态去换模型。

工具插件化：我们整个工具非常多——OryxOS 在第一期我们开发 32 个工具，这些工具完全是可以插件化的。你可以理解在代码里面可能就一个 Interface，多个实现。我们通过插件化设计去实现很多的工具拓展。

记忆插件化：记忆这块的插件化就很有意思了。如果你真正写过 Memory 这块模块的时候，你会发现，比如 Claude Code 在本地运行，它主要两种记忆：一种是通过 MD、本地的文件系统来实现的；还有一种是内存相关的，只有在这一次对话过程当中才会记下来。另外，当我们要做一个分布式的 OS 的时候，它是需要存在远程的组件里面的，比如 PostgreSQL 或者一些向量数据库，所以整个 Memory 存储也要插件化。

插件化的核心在于接口定义，做好 Interface、做好动态加载，让底座可以直接通过一个上层的函数去调用。

![](https://static001.geekbang.org/resource/image/7a/01/7acfccf25854b0fyy3d7022ab6f73f01.png)

第二个是多租户隔离、权限、沙箱、审计。

多租户隔离：不同部门、不同 Agent，它们的记忆、会话、调用工具，完全是不一样的，你不应该互用。配额、审计这些都互不干扰。

权限配额：谁调用了哪些工具、每天几次，这些都得考虑，非常细节。

沙箱：A 部门允许操作这个资源，B 部门不允许；A 部门允许网络访问这个地址，B 部门不允许，这是工具沙箱的用处。

全链路审计：你需要接入到整个公司的审计系统，甚至需要拦截。

如果你只是开发自己玩的 Agent 的话，这四点你基本不会考虑，但这四点也成了企业级服务的一个绝对门槛。

## AI 编程能帮我们做什么

这时候你会遇到一个问题：我们是企业级 AI 编程，这么大的一个项目，AI 能帮我们到什么程度呢？

我直接说结论：这类底座的核心代码绝大部分可以用 AI 写出来。

这门课要教的是怎么样用 AI 写出来，怎么样设计好、怎么样让 AI 写。内容我们就先不讲，但是这里有个关键点：AI 到底能帮你到什么程度？

我们要记住：AI 不擅长的是在模糊当中做决策，很多架构决策需要你来把握。它擅长的是在清晰约束下做一些高强度的产出。

所以你会发现，在整个训练营的题里面，提示词不是很重要，或者说我会把我的提示词并没有那么规范、那么简单、那么标准。我们很多做的其实是：开始怎么把事情想好，怎么拆好，怎么定我们的契约，怎么分块交付，怎么去构建 Harness、验证我们的运行结果。

第一点是约束，第二块是拆分，第三步是验证。只要你不是做那种数据库、消息队列、时序库或者缓存这种非常底层的应用，我觉得上层的一些应用、技术架构的东西，AI 都可以跑非常好。关键你怎么设计好、怎么样做好约束、怎么样去拆分、怎么样让它跑得更好。

### 契约先行

契约先行是什么意思呢？简单理解就是你要做好约束。那么要约束哪些东西呢？

领域模型接口：跨模块的核心领域模型。比如一个 Agent、一次会话、一次工具调用长什么样子？它的接口的入参出参是什么？

代码规范：安全审计、安全扫描、代码格式。比如 Java 的包格式，你是用阿里巴巴规范还是 Google 的规范？

### 分块交付

每一块为什么要分块交付？你可能会觉得分块交付和 Loop 编程好像有点冲突，其实本质上不冲突。

假设你有个项目，一个项目有 10 个部分，你把 10 个部分拆出来，每个部分做好输入的约束。这块要做什么事情，它的交互接口、产出什么，做好约束，它不允许碰什么，拿不准就停。这时候你一次只交给 AI 一块，跑完全程，再进入到下一块。优势是全程可控，出错可定位。人的位置在于定义输入和验收，审一些关键的边界。执行过程当中我们基本可以不用在场。

### 判官可跑：没有验证 AI 只会自信地错

判官可跑，这是做验证。没有验证 AI 只会自信地错。什么意思？你让 AI 跑个事情，你没有验证，它也不知道它错了还是对了。

这就是 Harness。你会去建一些自动化的测试、类型编译、检查、安全扫描，你可能每轮都问它“你到底做对了没”。你要找到验证 AI 执行结果的方法，它才能把事情都做对。

## 开发者应该怎么成长

最后，Agent 底层未来三年会怎么走呢？有几个观点你可以参考：

一些协议会收敛，包括一些工具、数据的结果会逐步标准化，比如像现在的 MCP 那样子。

底座会下沉成为基础设施，像今天的消息队列、注册中心、数据库一样，会成为企业标配一层。

\*\* 竞争点从能不能跑变成治理成本，\*\* 包括审计、权限、审核、多模型调度这些东西的成本怎么样？它的智能化怎么样？它的安全程度怎么样？

以前我们三大件是什么？操作系统、中间件、数据库，这是三个大方向。后面可能会加一个 Agent 底座的方向，可能就和现在的 K8S 一样，是类似的样子。但目前这块的标准还没定死，底座也还没成型。最近很多招聘全都是 Agent 相关的岗位，大家其实都在做同样的事情，这也是为什么协议会收敛的原因。当整个企业都在做这些事情了以后，你会发现很多基础设施就会涌现出来，公用的东西就会涌现出来。

### 什么会贬值，什么会留下

自然贬值的技能是把清晰需求翻译成代码的熟练度、记住 API 用法、会使用某个工具。

更值钱的是判断力。这点我们不重复，讲的特别多：模糊问题怎么样变成清晰的规格，你的架构判断、技术选型，你怎么去设计才是对的，为结果负责。

这也就是为什么现在很多有经验的工程师真正在一线干活了。其实有经验的工程师不是吃老本的，他一定是在一线干活、真正去社区做东西、而且做出有价值的东西的人。这时候你会发现判断力真的很值钱。

### 你要怎么补

作为一个研发，你要怎么去跟上时代，补充自己的技能呢？主要有四个方向：

规格能力：怎么样把模糊需求验证成一个统一的规格。

架构判断能力：你会做一个选型对照，你会知道为什么用这个而不用那个。

验证设计：你怎么样让 AI 写代码的时候，能够设计出让它跑得很好的一些 Harness，而不是只是追求代码的数量。

校验方法：契约先行，怎么样去规范项目，验收的整个结果。

说实话，现在到今天，大家缺的不是一个内容，缺的其实就是你怎么样找到一个真的项目，从头到尾去做一遍。

一个大项目给你的其实包括：最基础的基础能力、架构取舍和验证；一个作品和开源身份。三者是相互放大的一个作用。能力是你做的出来，作品能够让你被人看见，开源身份是让你长期有效的。

所以在这个项目，我们第一个项目要做的就这么个东西。
