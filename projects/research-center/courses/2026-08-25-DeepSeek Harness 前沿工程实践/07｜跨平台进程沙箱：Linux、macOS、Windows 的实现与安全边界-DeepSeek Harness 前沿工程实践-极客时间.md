你好，我是张嘉熙。

上一讲结尾我们把“程序执行本身的隔离”留成了另一道题。这一讲我们就来讲它，不过得先打个预防针：上一讲的 worker 线程只是“围住”，算不上安全边界，这一讲的进程沙箱同样不是强隔离。

但开头得先破一个误解。说到“沙箱”，很多人脑子里浮现的是 Docker、虚拟机。不过这俩压根不是一回事：虚拟机自带内核，是真的“另一个世界”；Docker 用的仍是宿主内核，只是拿 namespace 把进程树、挂载点、网络这些视图隔开了，内核还是共享的那一个。

而 dsh 的进程沙箱比 Docker 还要再弱一档。官方对它的概括是：把同世界的子进程 argv（也就是要跑的那条命令）包进一层文件效果策略。同世界是说它与宿主共享文件系统和内核，没被挪进另一个世界；文件效果划的是管辖边界：它只管对文件系统的改动，在这个范围内具体约束的就是能往哪儿写。重点在子进程：被约束的是一个个被启动起来的子进程，不是一个被造出来的隔离环境。

本讲沿一条线走：先看清它到底管什么，再看怎么用（给命令前面加半截）、策略怎么定、三个平台拿什么实现，最后回答边界有多牢靠。

关于环境：本讲新增三个包——@deepseek-ai/dsh-sandbox（seam 定义）、@deepseek-ai/dsh-sandbox-local（本地实现）、@deepseek-ai/dsh-sandbox-policy（策略解析），已加入本项目的 package.json，npm install --legacy-peer-deps 装上即可。

关于示例平台：这一讲的运行输出来自 macOS。在 Linux 上你会看到 bwrap 或 Landlock，在 Windows 上会看到 ACL runner——机制不同，结论一致。想在一台机器上看全三个平台的表现，跑 npm run start:ch07:platforms。

### 沙箱管什么，不管什么

它只管对文件系统的改动，约束程度分三种模式：

| 模式 | 能往哪儿写 | 典型用途 |
| --- | --- | --- |
| read-only | 只有 /dev/null 这一个必需的“下水道” | 只读探索、搜索、跑构建检查 |
| workspace-write | 再加上工作区根目录，以及提供方承诺的临时区 | 正常的编码任务 |
| danger-full-access | 不限制 | 显式提权后的重试 |

表格里冒出个新词——提供方。沙箱是分两层做的：一层只定规矩（要包装 argv、要报告执行结果，至于怎么做它不管），真正把规矩变成现实的，是另一个包，就是本讲开头装的 @deepseek-ai/dsh-sandbox-local。用哪个 runner、怎么包装 argv、执行得怎么样，全由它说了算；消费方只拿结果，不关心内部。所以表里说的“提供方承诺的临时区”，就是它答应给你的那块可写地方。

表头里的“能往哪儿写”是广义的写：创建、删除、重命名、改属性，凡是让文件系统发生变化的操作都算，不只是往文件里写数据。删个文件、给文件改个时间戳，一样受这张表约束。

danger-full-access 的意思就是不套沙箱，命令原样启动，想写哪儿就写哪儿，中间没有任何一层包装。技术上说，它根本不会走到 ctx.sandbox（沙箱能力的那道接口，后面你会一直见到它）。

这里值得停一下：在 dsh 里，“不套沙箱”只有一条来路，就是策略被显式指定成了这个模式（比如用户批准了一次提权重试）。它不是“沙箱没配好、干脆裸跑”的兜底路径，真到沙箱不可用时，提供方会直接抛异常，也就是后面要讲的“失败关闭”。所以每一次没套沙箱的执行，都能在策略里追溯到出处。

而不在这个词汇表里的东西，得记牢：

不管网络：沙箱里的进程照样能联网、照样能往外发数据。

不管进程可见性：它能看见宿主的其他进程。

也不管读：它只拦写、不拦读——宿主上的密钥、登录凭据，进程照样读得到。

换句话说，这是一个文件效果围栏，不是一个通用沙箱。把它当后者用，就会在“为什么它没拦住网络请求”上栽跟头。

### 沙箱怎么用：命令一个字不改，前面加半截

用法就一句话：

const confined = ctx.sandbox.confine(argv, policy)

argv 就是一条命令拆成的数组，第一个元素是要运行的那个程序（严格说是程序名，比如 bash，真正的文件路径由系统去查），后面是传给它的参数。注意它不是 shell 字符串：要跑 shell，得传 \['bash', '-c', command\]，而不是 'bash -c...'。这句约束看着琐碎，其实是安全前提：一旦传字符串，谁来解释、边界在哪儿就全乱了。第二个参数 policy 是第一节说的模式加工作区根目录，它怎么定，下一节单独讲。

三步串起来：

const policy = { mode: 'read-only', workspaceRoot: process.cwd() }

const confined = ctx.sandbox.confine(\['bash', '-c', 'echo hi > /tmp/out.txt'\], policy)

const result = spawnSync(confined.argv\[0\], confined.argv.slice(1)) \*

包装后的 argv 是这个样子：

sandbox-exec -p \<profile> -- bash -c <命令>\</profile>

从左到右认识一下这几个部分：

sandbox-exec：这一层的 runner，在 macOS 上正是沙箱机制 Seatbelt 的命令行工具。

\-p：告诉它：策略以字符串的形式直接跟在后面。

\<profile>\</profile>：那段策略本身。下面马上把它单独打出来看。

\--：分隔符，前面归沙箱，后面才是真正要跑的命令。

bash -c <命令>：你原本要跑的那条命令，一个字没动，只是被挪到了后面。

返回值有四样东西，每样都有用（先认个词：runner，平台上真正去包装、启动命令的那个程序，Linux 是 bwrap、macOS 是 sandbox-exec，后面细讲）：

| 字段 | 含义 |
| --- | --- |
| argv | 包装后的 argv——拿它去启动进程，替换掉你原本要跑的那条命令 |
| enforcement | 这个提供方能把策略执行到什么程度——full 是全都管得住，partial 是只管得住一部分 |
| denialSignatures | 该提供方的"拒绝方言"（被拒时 stderr 里会出现什么字样） |
| runnerFailureRules | 判定"runner 自己坏了"的结构化证据 |

跑 npm run start:ch07，脚本会连着跑五组对照。这里挑三组讲：①② 分别看“拦得住吗”和“放宽到哪儿”，⑤ 看“不套会怎样”，剩下 ③④ 的结论顺着这两组就能推出来，脚本里都跑得到，就不占篇幅了。

先看第 ① 组：read-only 模式下往家目录写文件（家目录在工作区外，属于“不该被写”的地方）：

\--- ① read-only：往工作区外写 ---

退出码: 1 | stderr: bash: /Users/.../\_dsh\_should\_not\_exist.txt: Operation not permitted

被拒了。凭什么拒？答案就在上面那行 argv 里，跟在 -p 后面的 \<profile>\</profile> 就是那段策略。把它单独打出来、去掉 JSON 转义，是这样：

(version 1) (allow default) (deny file-write\*) (allow file-write\* (literal "/dev/null"))

这三句话就是 read-only 的全部语义：默认允许，只拒绝写，且只放行 /dev/null 这一个字面路径。留这么一个“下水道”，是让命令能照常往里丢弃输出，不至于因为没地方写而报错。

第 ② 组换成 workspace-write，profile 末尾多出一段白名单，额外放行三个可写位置（同样去掉了 JSON 转义；$WORKSPACE、$TMPDIR 是脚本把真实长路径换成的别名）：

(allow file-write\* (subpath "$WORKSPACE") (subpath "/private/tmp") (subpath "$TMPDIR"))

三个位置各是什么：

$WORKSPACE 是工作区根目录，你要改的代码在这儿；

$TMPDIR 是这次调用拿到的私有临时目录；

/private/tmp：注意，你写的是 /tmp，但 Seatbelt（就是前面那个 sandbox-exec）匹配的是解析后的路径，而 /tmp 在 macOS 上只是 /private/tmp 的符号链接。

最后这条值得停一下：正因如此，每个根目录都要先解析出实际路径、再整理字面写法；否则白名单写了一堆，实际一个也没匹配上。

注：中间 ③④ 两组正如上面所说的能推出来：③ 是 workspace-write 下往工作区外写、照样被拒，白名单只放行上面这三处；④ 是 read-only 下只读命令、不被拦，只拒写、不拒读。

最后看第 ⑤ 组，不套沙箱的对照组，和 ① 同一个命令，退出码 0，文件真的写出了：

退出码: 0 （对比 ① 的 1：没被拦住，文件真的写出了）

五组看下来就一句：拦住这次写入的，不是什么隔离环境，就是命令前面被加上的那半截——sandbox-exec -p \<profile> --\</profile>。你原本那条命令一个字没改，只是前面多了这一串，写入就被管住了。

### 沙箱策略怎么定：每次各算各的

前面为了看清机制，policy 是我手写的。真实调用里它由 ctx.sandboxPolicy.resolve() 解析出来，而且每调用一次就解析一次，解析出的策略只属于这一次调用，不会被提供方存成状态。上一节我们已经讲过，策略有两项内容：模式和工作区根目录。

先看模式。它从哪来？优先级从高到低是：

显式批准的模式覆盖，比如用户批准了一次提权重试，那次调用就用更宽的模式；

会话最近一条 sandbox/mode 事件，这一轮会话被切到了什么模式；

部署配置的默认值，没人特别指定时的兜底。

工作区根目录也在这里定：有会话时，取发起这次调用的会话的工作目录，也就是进程当前所在的那个目录；没有会话时，比如脚本直接发起的调用，没有会话信息可用，就退回部署时配好的默认目录。

注：Windows 上还要多切一层：工作区的写入授权按工作区共享、长期保留，而每个“会话 / 工作区”另外拿到一个随机的私有临时目录——于是共享同一工作区的多个会话能共享写权限，却不继承彼此的临时目录权限。

定下来之后还要把它解析成实际路径，原因和上一节那个 /tmp 一模一样：路径里一旦有软链接，字面写法和实际到达的地方就不是一回事。比如当前目录是 /ws/link/..，其中 link 指向别处：按字面消掉.. 得到 /ws，可进程真正 chdir 进去的是 link 指向的目录，再往上退一级，落到的是另一个地方。所以先把软链接解开、看它真正指向哪儿，再消掉字面上的..——这样这个根目录标识的才是进程真正会到达的目录。

这跟上一节 /tmp 变成 /private/tmp 是同一套路径解析，只是用处不同：那边是让白名单对得上进程真正去写的那个位置，这边是让工作区根目录正好是进程真正会去的那个目录。

每次调用各算各的，带来一个很实用的性质：两个消费方可以在同一瞬间套着不同的策略跑。bash 用 read-only，而另一个 agent 需要往自己的状态目录写东西——两者同时向同一个提供方要不同的边界，提供方不需要为谁改变状态。获批的提权重试也一样，它不是“把提供方放宽”，而是用更宽的策略发起一次新调用。

### 三个平台，四套机制

同一个 confine 调用，在不同平台上走的是完全不同的 runner，runner 是平台上那个真正去包装、启动命令的程序；而这一节我们来看它背后的机制，也就是平台究竟靠什么手段把写入拦下来。注意平台与机制不是一一对应的：Linux 独占两套，一主一备，所以才叫三个平台、四套机制。

Linux：bwrap 主用，不行则退到 Landlock（两个候选按序探测，结论在 provider 生命周期内缓存）

bwrap 是“隔离式”：用 Linux 的 mount namespace 给进程单独挂一套目录视图，把该保护的位置换成只读挂载，路径一个没变，写进去的动作会被内核挡下。打个比方：把你放进一间和真房间一模一样的样板间，家具摆设都在，抽屉却全封死了；你以为在自己家，其实什么都放不进去。

Landlock 是“检查式”：bwrap 的备胎。它不另建视图，进程看到的还是真实文件系统，只是内核在每次文件访问时按规则集逐条查一遍，不合规则就拒绝。打个比方：房间还是那间房，但每扇门都装了刷卡机——你走原来的走廊、开原来的门，每开一扇都要刷一次卡，刷不过就“嘀”一声弹开。老版本的内核接口（ABI）管不全所有动作，也报 partial。

macOS：sandbox-exec

Seatbelt 是“清单式”：sandbox-exec -p 把一段 allow/deny 规则（profile）交给 macOS 内核的策略引擎，由内核照单判定——默认允许、只拒写、只放行 /dev/null。打个比方：给进程配一个照单办事的管家，清单上写着"可以读、不准写、废纸只能扔这个桶"；进程每做一件事，管家就对着清单核一遍，没写的不让做。

Windows：ACL 受限令牌 runner

受限令牌是“令牌式”：它既不改视图也不逐次检查，而是给进程换一个降级后的身份，restricting SID 只列出能写的目录，内核查 ACL（访问控制列表，每个文件上都挂着一张“谁能在它上面做什么”的表）时只认这个受限身份。打个比方：把工牌换成打折版，上面只印着“能进这几间房”，别处一律刷不开。只是启动时 Everyone 必须保留，等于工牌上还盖了个通用章，有些门它照样开得开——所以它报的是 partial。

四套机制，四种拦法——换视图、每次查、照单判、换身份。手段差别这么大，落点却是同一个：把“拦住写入”这件事交给内核去做，dsh 自己只负责把命令正确地包好、送过去。

跑 npm run start:ch07:platforms，脚本会依次扮演三个平台，各跑一遍完整链路，用哪个 runner、能执行到什么程度、被拒时 stderr 里冒什么话，都能清清楚楚看到：

| 平台（process.platform 的取值） | runner | enforcement | 方言 |
| --- | --- | --- | --- |
| macOS（darwin） | sandbox-exec | full | operation not permitted |
| Linux（linux） | 抛 SANDBOX\_UNAVAILABLE | — | — |
| Windows（win32） | node runner.js | partial | access is denied 等 |

注意，linux 那行别读反了：抛异常不是 Linux 沙箱坏了，而是这台演示机是 macOS，上面压根没有 Linux 的 runner（bwrap、Landlock 都不存在）。换一台真装了 bubblewrap 的 Linux，就会看到 bwrap 被选中、enforcement 为 full，这就是前面说的失败关闭：没有可用提供方就抛异常，绝不裸跑。

脚本能在一台机器上把三个平台都跑一遍，靠的是 internals.platform 这个测试钩子临时换掉 process.platform；真机上用不着这一手。表里 darwin 是 macOS 在 Node.js 中的平台标识，win32 是 Windows 的历史叫法，64 位 Windows 返回的也是它。

三个平台摆在一起，差异一目了然：runner 不同、enforcement 不同、被拒时 stderr 里的字样也不同。可对消费方来说，这些差异根本看不见，它只认 ctx.sandbox 这一份契约，平台差异全被提供方吃掉了。这，就是 seam（能力接口）的价值：换一个提供方实现，消费方一行代码都不用改。

### 安全边界：把拦住写入交给操作系统

最后我们来回答最关键的问题：这个边界到底有多牢靠？ 答案藏在它的设计理念里——dsh 自己并不拦，而是把命令交给操作系统内核：

dsh 沙箱：把命令交给内核（它自己并不拦），再报告执行到什么程度

│

↓ 真正拦住写入的是

操作系统内核：bwrap / Landlock / Seatbelt / ACL

│

↓ 安全上限取决于

这些机制各自的设计、成熟度、历史漏洞

安全上限最终由这些内核机制决定，dsh 插不了手，说到底还是开头那句官方概括里的同世界：沙箱进程与宿主共享文件系统和内核，dsh 没有在两者之间砌墙，只是把命令交到了内核手上。

既然拦住写入这件事交给了内核，dsh 自己要扛的，就只剩这次交接的两端：

交不出去时（失败关闭，fail closed）：没有可用的内核机制就抛异常，绝不把命令裸着跑出去。官方的措辞很硬，对受限策略而言，把命令悄悄不加约束地放过去永远不合法（silent unconfined passthrough is never legal）。

交出去之后（报告执行到什么程度）：Windows 因受限令牌必须保留 Everyone、NTFS 硬链接会让路径指向同一文件，内核只能做到这个程度，就报 partial，不夸大；老版本的 Landlock 接口也是这样——它管得住的动作不全。

但它防不住网络、进程可见性、任何非文件的效果，以及显式切到 danger-full-access 之后的一切。所以它的定位很清楚：隔离交给操作系统，dsh 自己只保证转交正确、报告准确。

### 本讲小结

今天这一讲，我们把“进程沙箱到底是个什么边界”这个问题，从头到尾拆开了。

我们看清了进程沙箱与宿主共享内核和文件系统，只管对文件系统的改动；confine 按每次调用解析出的策略把命令包一层，四个机制各有一套拦法（Linux 的 bwrap 换视图、Landlock 每次查，macOS 的 Seatbelt 照单判，Windows 的受限令牌换身份），消费方只认契约不认平台；而它的边界有多牢靠，最终取决于它委托的内核机制——没提供方就抛异常不裸跑，管不全就报 partial，把管不住什么说得明明白白。

这背后真正的变化是你不再把"沙箱"想象成一个隔离的世界，而是把它看成一层按每次调用施加的文件效果策略；让“管到什么程度”由提供方报上来（就是那个 enforcement），而不是由调用方一厢情愿地假定。

这，就是进程沙箱的本质——把隔离交给操作系统，自己只问“这次调用的文件效果，我能承诺管住多少”，管不住的部分绝不假装管住了。

到这里，从 Tool 接入能力、seam 让实现可替换、流水线上的守卫，一直到进程沙箱的执行边界，能力这条线终于完整了。但所有这些调用都发生在一次会话里：模型怎么知道前面发生过什么、长任务的状态存在哪儿、中途断了怎么接着跑？下一讲，我们回到这条主线，聊聊会话。
