# L02｜把仓库规则写进 AGENTS.md

> 来源：`PPT/L02-PPT.pdf`（25 页，已提取文字）；`PPT/L02-辅导资料｜…pdf` 为截图型查询手册，未 OCR。
> 仓库讲义：`CodexFDE/docs/courses/L02/`。

## 一句话

把「已经查清的项目事实」写成长期规则，让下一次协作继承；写完后用同一份真实请求做前后对照复验。

## 核心案例：两个字段，两个问题

任务：给查询结果写中文说明（只交方案，不改代码）。

- `evidence_complete=true` → 程序检查：已导入记录满足完整性条件
- `acceptance=pending_human_review` → 人工决定：仍在等待人工审核

**不能合并成「人工验收通过」**。完整性查询只是读取导入记录，人工接受不是自动检查的结论。

## 筛选：这句话要不要成为长期规则

1. 换个任务仍然适用？
2. 再问一句：**不知道它，协作者会做错哪个决定？** 说不清就先别加。

推导一条规则的实例：①查到事实（检查与人审是两件事）→ ②找到误解（把"完整"翻成"验收通过"）→ ③确定要保护的含义（两项事实分别表达）→ 写成候选规则。

## 三种写法对照

- 坏①「保证状态正确」→ 方案写成"已验收通过"，混淆两事。
- 坏②「禁止修改任何状态显示」→ 连保留原意的翻译也被禁。
- 好「记录完整与人工审核分别显示；允许改中文，不能代填审核结论」。

## 目录职责的写法

规则写「路径 + 职责 + 边界」，例如：工作台记录与 ERP 业务状态分开维护。目录职责让协作者找到正确的修改位置；**用自己的仓库实际路径，不照搬示例目录**。

## 与 Codex 的协作要点

- 职责边界：AGENTS.md / Prompt / Skill / Hook / MCP 各管什么。
- 具体 Prompt 结构：目标 + 入口 + 边界 + 交付；无法核实的内容标「未验证」；续问只补变化；长日志存文件、回复给摘要。
- 「只读」限制写入、「输出详细程度」影响呈现——不能据此推断 token 下降，也不能省略必要验证。

## 复验流程（每一步都产生可检查的材料）

1. 查项目事实 → 事实表 + 自己的判断
2. 保存前测 → 请求 N + 真实回答 N0
3. 起草规则 → 候选规则 + 取舍
4. 审查并写入 → AGENTS.md 前后差异
5. 新会话复验 → 真实回答 N1 + 边界题

比较维度：含义是否正确、合法工作能否继续、是否增加无关操作。**前后都正确就如实记录，不制造差异。**

- 合理提议要推进，不是只会全部拒绝——全部拒绝不能证明规则写得好。
- 实际报错案例：`blockng` 拼错 → `invalid choice`，退出码 2（参数解析失败），不能写"检查通过"。

## 迁移题（业务判断）

客户："先加库存，审批明天补。"——**采购申请已建立 ≠ 人工审批完成**。可以申请走流程入库的材料，但不能把申请当审批。

## 交付物

AGENTS.md（核心规则）+ 学习记录（规则前后版本、真实请求与回答、个人取舍与反馈、修订与未验证项）。通过标准：新会话能读取约束；错误命令或越界修改能被明确拒绝或纠正。
