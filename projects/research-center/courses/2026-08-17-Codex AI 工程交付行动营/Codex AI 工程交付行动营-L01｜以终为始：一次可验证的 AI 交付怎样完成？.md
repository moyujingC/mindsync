> 来源：`PPT/L01-PPT.pdf`（40 页，已提取文字）；`PPT/L01-辅导资料｜…pdf` 为截图型查询手册，未 OCR。

## 一句话

先看课程最终作品（个人工作台 + FlowERP 双产物），再倒推第一版做什么：先做「记录能力」，让一次开发能查找、能复查。

## 工作台是什么

- 自己日常使用的研发应用：把**项目、需求、Codex 的执行、检查结果、验收决定**组织在一起。
- 分工：**人**提出目标、确认范围、核对结果；**Codex** 读代码、写测试、修改排错；**工作台**保存任务与要求、安排执行与检查、汇总实际记录，等待人的决定。
- 两套应用各自有数据：先用 Codex 开发工作台本身；L04 起才通过工作台组织 Codex 修改 FlowERP。

## 为什么需要工作台（三个重复交接的痛点）

1. 每次接手都要找上下文 → 任务编号 + 需求快照 + 多次运行记录。
2. 每次都要核对执行范围 → 把确认的范围与检查入口交给执行流程。
3. 失败后很难接着处理 → 保留失败输出、待办和人的决定。

## L01 的范围判断

- 从**使用条件**推导设计，不从架构名词开始：个人、本地、任务量不大 → 记录优先（SQLite + 命令行够用；多人并发/审计需求出现再重新比较）。
- L01 = 可运行第一块：五个命令保存项目与任务、追加运行记录、关闭后查回。**L04 才补齐执行与检查**。
- 没有记录，后续无法判断：Codex 按什么改、检查哪一版、失败后从哪继续。

## 关键术语（PPT 速查页）

- Spec / Diff：需求说明 / 查看代码修改前后差异
- ID / 需求快照：任务固定编号 / 创建任务时保存的需求副本
- 红灯 / 绿灯：测试失败 / 通过（都要看实际输出）
- 持久化 / 写集：关掉程序数据仍在 / 本次允许修改哪些文件
- 命令证据 / 自举：保存命令和运行结果 / 用新工作台记录自己的开发

## 交付要求（L01 行动卡核心）

- **开发前签字**：保存原始问题、Codex 建议、个人取舍，确认需求说明。
- **实现并重新测试**：提交需求说明、实现前的失败测试（红灯）、五个操作、允许范围内的代码修改、同一测试通过记录（绿灯）。
- **复核后签字**：同伴或教师检查；写明通过/退回/暂时无法判断及理由；没收到反馈就写「待复核」。
- 参考仓库通过测试 ≠ 你已完成：要交自己练习目录的代码、真实运行结果、个人判断。

## 能力路线图

L01 记录工具 → L02–L03 规则与需求输入（AGENTS.md、Spec 模板与解析器）→ L04 工作台 V0（限范围 + 最小检查，首次交付库存导出）→ L05–L16 持续交付 FlowERP，业务问题反过来推动工作台升级。
