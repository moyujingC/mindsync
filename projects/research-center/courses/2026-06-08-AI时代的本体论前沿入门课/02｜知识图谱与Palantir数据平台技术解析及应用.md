

现在，最原始、最严苛的部分已经说完了，那是最理想的预测。但实际上，那太乌托邦了。所以大家觉得还是要解决工程问题，那怎么办？就做弱化。所以就有了知识图谱，它和前者不一样。前者是规则严密的规则系统，但图谱是实用主义的类型标签系统。注意，它是面向实用主义的，很像一个标签系统，就是打标：实体类型是什么，关系类型是什么，简单连标签。它也没有那么多限制。

顺着这个点，我们来看一下图谱是怎么做的弱化和自动化。首先，图谱被称为连接万物的智慧大脑。它是用图结构来展示和表示现实世界中实体、概念及其关系的语义网络。通过将信息转化为机器可理解的形式，实现数据的深度关联和智能推理，是构建人工智能应用的重要基石。所以它能做什么？数据的关联，打破数据孤岛。这就是现在很多做数据治理的喜欢的：搞一个知识图谱，把各个ERP系统里的东西全整合出来，搞成一个全景的知识视图。然后基于这个东西能做什么？能做智能搜索。

例如百度百科、企查查等。你可以进行搜索，如路径搜索等，也能支持一些查询，例如KPQ。KPQ当时主打的点是，之前需要从网页中寻找答案，这很困难。现在不如直接给出答案，比如“姚明的老婆是谁？”，直接回答是叶莉。如今大模型来了，就不再需要这样做了。

此外，它还能做决策分析，揭示海量数据背后隐藏的模式、潜在关联和发展趋势。因为它是一个图，所以可以进行关联挖掘，例如最短路径、全路径分析。基于此，可以查找所有路径，应用六度人脉理论，发现潜在关联。例如在量化场景中，有大量转账数据，就可以进行分析，发现发展趋势等。

OK，有了这些能力后，我们看一下它的定义：定义是以实体、属性、关系为核心的语义结构化网络。它主要由两类元素构成：节点和边。节点表示实体或概念，边表示实体间的特定关系。它最早源于2012年，已经是14年前的技术了。为了解决传统信息管理中关键词匹配的局限性，赋予了它关联能力，并成为其核心技术。

设定目标是为大规模、不完美且极具动态性的复杂数据构建一个清晰、可伸缩的骨架。注意这个“可伸缩”，和前面的“语义”就不一样了，它是可伸缩的。概念、概念类型、关系类型，可以不必那么严苛。

三大设计目标：

1. 高效存储：例如 Neo4j 等图数据库。
2. 赋能业务场景：如搜索引擎、推荐系统、问答系统。
3. 高可扩展性和灵活性。

典型应用：

- **搜索引擎**：如 Google Knowledge Graph。
- **个性化推荐**：例如日常点餐，构建商品图谱。你点了麻辣烫，它可能给你推荐钵钵鸡。图用于构建个性化推荐系统，推荐方式有很多，比如基于千维嵌入（embedding）去做推荐，还是基于关联关系去构建。
- **知识管理**：旨在解决信息孤岛问题，这也是设计目标之一。

存储架构主要有两种：

- **属性图**：这是大家常用的数据库类型，例如 Neo4j、JanusGraph、Nebula Graph 或 TigerGraph。其核心是表达能力强的属性图，边上也可以有属性，可以添加各种信息。它还配备了一些工具，例如 Neo4j Browser 可以帮助进行可视化。

所以这也是为什么导致大家都觉得，图谱其实就是个可视化，其实不是的，它能解决关联关系的问题。

另一个是RDF，它继承了以往的那一套，比如像Stardog等，标准化程度极高，支持丰富的推理能力。所以大家会发现，有人说Neo4j可以做推理，这是不准确的。Neo4j没有推理机，它只能做一些路径查询等。

核心组成也和以往一样：实体、关系、属性。

- **实体**：与之前的“类”类似，不是具体的人，而是如电影、公司这样的类别。
- **关系**：实体和实体之间存在的各种关系，比如导演关系、创始人关系。
- **属性**：用于描述实体本身的特征，例如《满江红》的上映时间、字节跳动的成立时间。

大家发现了什么？现在的图谱很多到这就结束了。约束呢？没有了，规则那些也没有了。这就是现在真实生产中的情况，只剩这些东西了。因此它没有推理能力，所以很容易混乱。

那么它能做什么？我们看一下它的应用：路径发现。这就是我们今天所遇到的图谱。例如，问“李白”，我可以把这张图找出来，这体现了可解释性和可观测性。像这种路径发现，例如“李三”和“锐”之间的关系，我把“李三”和“锐”分别作为头节点和尾节点，拉一条边去找最短路径或全路径，就能发现一些潜在的关联。

包括帕兰提尔，它也是这一类的。刚才提到的很多做情报的公安系统也是这么做的。还有像这种多跳推理，例如“窦靖童的爸爸的前妻的前夫是谁？”当然，现在用大模型可以直接得出答案。但在2022年之前，大家只能通过这种方式去做。窦靖童在这，她的爸爸是窦唯，窦唯的前妻是王菲，王菲的前夫是李亚鹏。所以你会发现，最终得到的就是李亚鹏。这其实也是当前大家通常津津乐道的图谱“推理”，其本质就是路径游走。

还有可视化交互，比如公安知识图谱，大家能看到点与点之间的关联。看电视剧时，大家发现破案时都喜欢画这种图。这能帮助进行线索挖掘。因果图其实也能做，比如银行加息会导致什么，然后一连串地推演。专利也可以改成图。另外，像一些情报检索，加上地理空间的可视化，也可以做事件的演化追踪和知识的交互问答。把这些功能给到用户，大家就很喜欢，因为它是可解释的，能做问答。

说完这类之后，我们再看。既然它能做这些，我们怎么去做呢？有几种定义是工业界的和学术界的。

工业界的话，它其实就是类型的标签化系统，是轻量级结构。学术界的定义就是对比外部本体，定义其完备性等。其特点是重逻辑体系、强约束条件，同时成本高。

它的主要特点就是弱约束、非强逻辑。弱约束就是不强制严格的约束规则，在保证数据可用的前提下即可。例如，不要求所有人物实体都必须填写出生日期属性。大家做图不也这么干吗？避免因数据不全导致实体无法入库，也不会有严格的校验规则，直接存入即可。做法很直接。

另一个特点是允许缺失。例如，允许实体属性为空，不要求每个字段必须有数据，以适应真实世界数据的不完备性。比如对于某个属性，它不包含这个数值。并且，它容忍这些矛盾。如果出现矛盾，比如有A和B两个冲突值，可以直接搞个版本控制，拉一条边，加个标注位说明其有效性即可。所以它其实就是对本体的弱约束和非强逻辑的这样一种实现。

所以，它本质上是一种轻量级的建模，包括实体类型的建模。

**类型体系**

- **实体类型**：允许一个实体拥有多个类型标签，例如“person”和“student”。
- **关系类型**：如“directed by”或“acted in”，可以有向或无向，基数可以是一对一、一对多或多对多。
- **属性类型**：包括文本、数值、日期等类型规范，并允许存在枚举值。属性可以缺失，不强制所有字段都有数据。

**特点**

- 允许缺失属性值。
- 容忍数据间的矛盾。
- 结构灵活，可以打破层级限制来建模。

**实践** 在定义拓扑 schema 时，尤其是借助大模型，可以采用自底向上的方式自动进行知识抽取和归纳。例如：

1. 使用大模型进行 schema induction，自动识别实体并为其打上标签。
2. 基于这些标签，再做进一步的归类和组织。

它的核心优势是自动化程度高，能适应新领域，无需预设 schema 就能完成这些工作。

另一层是人工规则和高层 schema 设计，这与以往的本体或 schema 设计很相似，即人工定义高层类别，然后自动抽取、整理和优化。它能提升 schema 的质量，融入领域知识，也能构建层级体系。其实施方法是定义类别，并归类抽取结果。因此，与以往方法的区别在于，以往依赖于人工操作，而引入大模型后，可以交由模型自动进行规约等操作。

接下来是具体的构建流程：

1. 明确领域知识图谱的目标：是要用于搜索问答，还是用于决策分析？应用领域决定了概念的选取和专业术语的定义。用户目标是大众用户还是领域分析师？能力范围的边界是什么？产出是详细的需求文档，包括核心目标应用领域和边界范围。
2. 定义核心概念：识别核心类，定义核心关系，构建分类体系，并定义关键属性。

然后，形式化表示可以用这类工具完成。但在实际图谱构建时，我们往往不使用专门的构建工具，有时直接使用 Excel 或 Markdown 也可以，只要机器能够处理，写配置文件或样例也行。

另一个重点是，构建完成后需要进行评估和完善。因为本体构建不是一蹴而就的，它是一个持续优化的闭环过程，需要进行：

- 一致性检查
- 完整性评估
- 可扩展性评估
- 专家评审
- 收集真实场景的反馈

然而，在实际的知识图谱构建项目中，很多人过于工程化，常常将评估和完善这一步直接忽略。

图谱构建完成后，接下来是考虑如何应用它。整体流程如下：

1. **数据准备**：收集结构化、半结构化和非结构化数据。
2. **实时信息抽取**：进行命名实体识别（NER）、关系抽取等。
3. **实体链接**
4. **实体归纳**（有时实体归纳的结果会反哺到抽取步骤，形成约束）
5. **数据融合**
6. **存储**

在数据接入环节，涉及数据映射，包括：

- 数据源的选择
- 选定结构化数据（如 CSV、Excel），这与以往的做法是一致的。

首先是抽取实体类型，将每一行记录转化为图谱中的一个节点。其次是属性映射，将原本的数据字段映射为图谱实体的属性。此外，抽取还涉及外部关联和业务逻辑。关于数据加载，例如映射：假设有一个“Employees”表，包含职工的ID、姓名和部门名称。同时，定义了图谱schema，其类型“Employee”具有ID和Name属性。“Employee”与“Department”之间存在“works_in”关系。这样，就可以将这两张表连接起来。需要注意的是，这里是两张表的连接，后续的数据关联（如“printing on”）也是一种连接方式。数据映射解决的是数据层面的转换问题。

对于非结构化数据的抽取，通常直接使用命名实体识别（NER）或关系抽取（RE）技术进行处理。实体链接和数据加载则通常使用自然语言处理（NLP）方法或前沿的深度学习技术来实现。

数据准备与映射涉及多种数据源格式：

- 结构化数据：MySQL、文件格式、关系型数据库。
- 半结构化数据：外部资源、HTML。
- 链接数据：JSON-LD。
- 非结构化数据：例如文本文档。

核心挑战是如何将不同数据源整合到一起，因此需要进行数据抽取。通常的做法是：

- 对于结构化数据，使用ETL工具进行实例映射。数据表中的每一行记录对应图谱中的一个实体实例，例如电影表的一行记录对应知识图谱中的电影实例。
- 属性映射是指每一列对应一个属性或对象属性。
- 关系映射则是通过外键和关联字段建立关系，例如通过ID关联到其实体。

可以看到，这本质上是在构建一张宽表。后续的步骤也需要先将数据集成起来，形成一张宽表，然后再进行处理。

数据清洗包括处理缺失值、去除重复记录、统一数据格式（例如统一为标准四位数年份）。数据对齐则涉及对多元异构数据进行同名字段的合并和标准化，例如将“导演”和“director”统一为“导演”。

对于非结构化数据，处理包括：

- 预处理
- 非结构化数据抽取
- 关系抽取
- 事件抽取（事件要素包括时间、地点等）

可以使用NLTK、NLP技术、传统的API接口，或BERT、GPT等模型，以及一些自动化抽取工具，包括当前用于抽取的大模型。

这也是我们经常提到的。实体链接也很重要，必须进行实体对齐。例如，文本中识别出的实体提及“卡梅隆”和“詹姆斯·卡梅隆”，指的都是同一个人。又如，“苹果”可能指水果，也可能指科技公司，这需要进行链接对齐。

此外，消歧也是当前数据治理和语义处理中需要投入大量精力的环节。其核心流程主要分为三步：

1. **候选生成**：检索所有可能的实体。例如“苹果”，可以关联到水果或公司两个不同的实体。
2. **相似度计算**：将实体描述或属性转化为embedding，分别计算相似度并进行排序，选择最高的。
3. **实体链接**：选择相似度最高的候选实体进行链接。

这个过程很像RAG，但其中的核心挑战在于相似度阈值难以设定。如果待链接的实体只有一个模糊的提及，缺乏上下文，相似度计算可能不合理。因此，实体链接的核心价值在于消除非结构化数据的模糊性，确保提取的信息能准确融入知识图谱，避免产生错误的关联。

这就是其纠错和校正的关键。大家之所以在谈论知识图谱时感到困难、甚至想回避，正是因为“歧义性”问题解决得不好，它本质上是为了突破非结构化数据的局限。

数据融合主要包括两个层面：

1. **实例融合**：例如，将“豆瓣”和“危机”融合成一个统一的实体。这类似于将两套业务系统中的两张表合并成一张，核心方法依赖于相似度计算或实体链接。
2. **属性融合**：同一实体在不同来源中可能存在属性冲突，例如评分分别是4.9和5.0，该如何选择？可采用的策略包括：
    - 依据信任度加权平均
    - 建立信任度分布词典
    - 遵循多数表决原则
    - 优先选择最新数据

数据融合不仅是知识图谱需要处理的问题，也是ETL和数据治理中的常见环节。

另一个关键点是知识的存储与查询。完成图谱构建后，通常需要高效的支持查询、推理和图分析的能力。因此，在技术选型时，必须考察所选存储方案是否自带这些能力。

这时也会有，比如目前最流行的 Neo4j。它的生态很活跃，适合中小规模图。第二就是 JanusGraph，它是开源的图，支持 PB 级。还有亚马逊的 Neptune。其核心动作就是大家会说，我也开源过那个医疗的图谱，大家不要反应慢。所以这时大家习惯用分布式的方式去做批量导入。批量导入是纯存储侧。

完成这个之后，我们去看质量的评估和升级。大家搞完本体、搞完数据治理之后，肯定会问一个问题：怎么去评价我这个图？这时大家就要拉指标，去确定评估的体系是什么。

一般来说会有两个点：

- **完整性**：是否覆盖了既定的知识范围？怎么去定义这个知识范围？是不是需要人工去设定指标？是否存在大量缺失的实体或者关系？怎么去判定是否有缺失？需要抽检，而抽检方法又是一套逻辑。
- **准确性**：是否正确？存在错误的事实比例是多少？能接受多少？可以抽检一下，然后去计算准确率。

另外两个点是**一致性**和**时效性**。

一致性是指数据中是否存在逻辑矛盾，是否需要进行检查。时效性则关注数据是否为最新。这些都是需要评估的方面。这也是为什么很多人虽然落地了本体论和数据治理，但不敢声称其质量很好，因为这一块需要高度人工的方式进行校验。

评估就像评估大模型一样，做起来容易，但如何做好、评估得完备，才是关键。此外，评估不是一次性的，评估后还需要持续优化。这时就需要不断地升级和优化。就像现在很多知识图谱（KG）在做进化一样，进化可能出错，因此需要加以约束。

具体怎么做？有以下几点：

- **数据补全和扩充**：针对缺失的关键信息，可以通过众包协作、全网爬虫、引入新的权威数据等方式进行补充。
- **错误清洗**：通过人工审核和自动规则进行纠正。
- **模型优化**：持续改进相关模型。

但这一块工作你会发现它一直在循环，何时是个头呢？这又需要人工主观地设定一个截止标准。所以大家会发现，图谱构建本质上就是在做数据工作，解决的其实还是数据治理的问题，因此过程会比较繁琐。

因此，图谱的构建其实是一个持续升级的过程，它需要不断的维护和更新，以保证知识的质量和价值。

评估升级很重要，包括数据融合等，做的都是数据治理的事情。我们看下一个案例：构建一个电影图谱。

构建电影图谱有三步： 第一，设定目标：构建一个小型电影图谱，打通电影、人物、类型三者之间的数据孤岛，最终实现对导演是谁、演员演过什么、电影评分等问题的智能查询。

第二，明确需求。构建图谱或做 RAG 时，效果好坏取决于索引（知识结构）构建得好不好。支持的具体问答包括：

- 某部电影的导演是谁？
- 某个演员出演了什么电影？
- 某部电影的评分是什么？

需求限定后，定义关键词类，包括电影类、人物类、类型类。然后构建核心关系：

- 人物 “acts in” 电影
- 电影 “has genre” 类型 同时补充核心属性，如电影年份等，以支持筛选等操作。

第三，做数据准备。

我去做数据准备，这时我们使用的是结构化的图谱，具体来说是 CSV 格式的标准电影数据。CSV 作为主要结构，每一行包含以下字段：id、title、release year、rating、director、actors、genres。此外还有一些非结构化数据，例如摘要文本。下一步是将其整合到图谱中。具体步骤如下：

**步骤三：处理结构化数据**

- 读取CSV的每一行。
- 为导演、演员、类型分别创建对应的“Person”和“Genre”实体，并生成唯一ID。
- 补充实体属性（如电影年份）。
- 构建核心关系。

**关系构建**本质上是一个映射过程。具体来说，它首先将名称（例如人名、电影名）规范化为标准格式，这有助于后续的数据对齐。

此外，还有几个非结构化数据源需要处理，例如用于知识增强或AR融合的数据。这是一个典型的多源数据融合场景，因为这些非结构化源中可能缺少明确的“主演”、“导演”等指导关系。处理方法是：继承从结构化数据中已抽取出的模式（如电影、导演的关系类型），然后用其去非结构化源中进行实体与关系的抽取。

**步骤四：导入与存储**

- 将清洗和映射后的结构化数据批量导入，并使用图数据库存储。

至此你会发现，由于前期已完成数据映射，此时的数据可以高效地进行对齐和整合。

对，就是行和列如何映射的问题。所以它能支持一些问答，例如：

- “谁导演了《泰坦尼克号》？” 可以写一个查询：匹配电影标题为“泰坦尼克号”，然后找到导演（一个Person实体），返回该Person的名字。
- “他出演了哪些电影？” 匹配Person的名字为“莱昂纳多”，然后找到他参演的电影，返回电影的标题和年份。

以及所有评分相关的查询。

所以，当我们把图谱构建好，将多元异构的数据整合之后，能做什么？我就可以通过清晰的本体构建和精准的数据映射，将非结构化文本转化成可推理、可关联查询的电影图谱，从而回答这些问题。

OK，完成之后，我们再看推理的实际应用。主要有两种：一种是基于统计规律，一种是近似推理。

- 近似推理的方法其实就是路径排序，就像“sharding pass”，这本质上是图数据库内置的、基于规则的推理链路，以及简单的传递机制（自己写if-else也可以实现）。
- 我们看路径排序算法，就是基于路径上这些关系进行推理。

它也可以推断出这个东西，对吧？它能做链接预测，也能做关系预测。

另一种方法是使用 TransE，这是一种基于嵌入的推理方法。其核心是使用一个三元组 (h, r, t)，通过欧式距离，让 head 加上 relation 约等于 tail，来计算距离函数。例如，使用 L1 或 L2 范数，使得它们在向量空间中彼此不断接近。这样，我们就可以得到所有实体、关系和 tail 的嵌入向量，从而利用它进行一些便利的操作，比如 TransE、TransR 等。

你会发现，为什么它会变成一些……那是因为现在很多系统需要处理更复杂的情况。例如，一个人参与了多部电影，如果区分不开，就需要引入一些纯的、拉维度的特征，这样就能处理了。

此外，还有像简单的传递规则，例如我们可以写规则：如果 A 是 B 的父亲，那么……我们可以去查找、匹配，也可以做逻辑判断，从而发现其中的关联。

5. **权限治理层**

大宽表是最理想的情况，因为只需要按行按列去取数据即可。

第二点，拿到数据后需要做转换。这需要连接器、转换器、流/批调度（例如增量/全量同步），以及数据集版本分支管理。

第三层是本体建模层，包括：

- 对象类型
- 链接类型
- 行动类型
- 接口和函数

注意，这里有两个大家熟悉的概念：语义网的Web Ontology和知识图谱，它们都有对象、属性等，但唯独没有“行动”和“接口/函数”。这就是所谓的动态本体。动态本体意味着对象可以绑定一些行动，而这些行动可以执行一些函数。这样，一张表是否就能自动实现数据上的自动变化？数据本身就能轮转、转动。

完成这几层后，到这里只是定义了逻辑和函数，它本身并不能执行。不能执行怎么办？这时就需要更上层的东西，即使用Agent来实现执行。

这个东西也可以理解成是一些业务规则。一些低代码平台的 Agent 也能自己去做动态推演、图的可视化等。基于此，才能实现动态的业务执行闭环。

当整个闭环完成后，你会发现它还需要治理，因为万一执行出错了怎么办？这就是它的四层架构。

拆开来看：

1. **数据采集层**：解决企业内外所有数据源，打破数据孤岛。它有很多连接器，如 SaaS、数仓等，支持多样化的数据接入，灵活支持批量与实时两种模式，还有零拷贝虚拟化。例如 Oracle、Snowflake、Salesforce、SAP、Kafka 等。为什么不要拷贝？就是能直接连接就连接，这样可以减少本地备份的压力。其核心点是广泛连接数据源，因此这一块会有很多数据接入上的工作。
2. **执行转换层**：需要将数据变成统一可信的，因此需要做标准化的清洗。这里有一些核心组件，以及版本管理等。例如，有些数据源格式不同，就需要一个中间层将其映射到大宽表。这一层需要有质量保证，因为数据每次请求或同步都可能变动，需要确保它不容易出错。另外就是全链路的追溯，需要记录完整的数据血缘关系，让数据来源清晰透明，便于问题排查和合规审计。

另一个是结果的可重现性，这属于可观测性的范畴。同时，每一步集成转化都是可审计的。

集成转化这一侧，因为与前述内容有重复，此处略过。集成的系统包括SaaS应用、关系型数据库、数据仓库、消息队列以及标准格式数据等。

整个集成过程，有时也需要在ID环境中进行探索分析和转换，其核心是解决人工代码操控的问题。

它有三种集成模式：

1. **第一种模式**：平台作为消费者。不采集原系统数据，直接对接，只获取加工后的宽表，跳过原始数据。后续仅负责本体（Ontology）建模和AIP决策。这样做的优势是，原始数据接口高度一致，可以避免形成新的数据孤岛。劣势是受限于中台提供的数据接口类型。适用场景是已有自己的中台体系，并非需要推倒重来。
2. **第二种模式**：并行双轨。
3. **第三种模式**：承担中台职能。

由此可见，它并不想替代公司现有的业务系统，这是其设计精髓之一。

关于并行双轨模式，即数据中台与各系统独立采集数据并行。两者互不干扰，但这将造成资源浪费与接口不一致的问题。另一种是让其直接承担中台职能。

此模式实施成本和周期较高，适合原有数据状态尚不成熟的场景，可以从头开始长期推进。

具体来说： 第一种：普拉提亚作为消费方。数据中台主导采集数据，普拉提亚消费加工后的数据。例如，供应商门户数据经数据中台处理（经过ODS、DW、DWS等环节），输出后供其执行。其继续使用报表，不重复采集。 第二种：并行双轨。原系统数据分走两道，其中一条路径通向BI。之所以需要BI，是因为普拉提亚这类平台所做的本就是数据分析相关的事务。现在已有许多公司从拆分出BI模块入手，转而宣称自己正以本体论的方式构建平台团队。 当然，也可以让其直接统一管理数据资产，避免数据冲突。 第三种：直接让其承担中台职能。由其直接对接数据源，进行数据存储、转换，并存储为数据对象，供现有系统使用。

普拉提亚存什么？它存副本，也存源数据。

选型建议：

- 如果数据中台已成熟，选择模式一，避免数据孤岛。
- 如果需要并行双轨，则选择模式二。

核心问题是，无论数据从哪两个路径进入，都必须保证数据接口一致。一旦接口不一致，数据就无法流转。这也是前面提到的，数据语义必须保持一致。

完成这部分后，我们考虑本体建模层。它的核心是构建一个统一的、面向业务的企业数据模型，将技术化的表和字段转化为业务人员能够直接理解和交互的实体概念，打破技术与业务之间的语言壁垒。

其核心概念有几个：

- **ObjectType**：即类和实体类型。
- **关系**：关系类型。
- **动作**：可执行的业务操作，例如创建订单或触发通知。它需要绑定到具体的业务对象上，例如绑定到产品，那么在产品上创建订单的动作就可以直接触发。
- **函数**：用于计算。例如，可以联合两张表进行计算，像“客户购买了某个产品”这样的业务逻辑。

例如，客户要购买产品并支付费用，这时就需要关联产品和客户信息。客户属于哪个等级（如黑金或白金）、享有何种折扣，以及产品对应的折扣是什么，计算后即可得出最终价格。这个过程可以通过函数来实现，类似于我们的计算逻辑。

其核心价值在于统一语义层、构建视图，并由业务驱动定义。

**对象类型**定义了业务领域的核心实体类型，是构成节点的基础。例如，客户、产品、订单都是对象类型。通过这种方式，可以将散落在不同数据源中的客户表、产品表、订单表关联起来，构建一个统一的全局业务视图。其实现方式是通过映射整合一个或多个底层数据源，并为每个对象分配一个唯一标识。

**关系类型**用于定义不同业务对象间的关系，例如订单与库存的关系。它将孤立的实体链接成一张结构化的业务图，避免了复杂的多表关联查询。这与图数据库的概念很相似。

**动作类型**定义了可在对象类型上执行的操作，描述了系统能够对外界触发的响应行为，例如更新库存或创建订单。

发送通知。例如，当 agent 检测到库存低于安全阈值时，可以自动调用这个动作来更新系统数据。那么这个动作是否需要操作某个对象？它必须操作一个 object type。但这里有一个关键点：这个 action type 必须由某个事件触发和激活，需要一个动机。所以这时你会发现，它可以变得有点像 action 里的 function call，或者说，有点像小型 SOP 这样一个触发节点。这其实就是编排。

另一个是 function。function 实际上就是动作类型，它能直接通过函数实现，例如封装可复用的计算逻辑，处理 object 和 type 的属性和关联关系的复杂运算。过去常见的例子，如计算客户生命周期价值、订单实时税费计算等。能发现什么？因为有了 function，属性可以变为动态的。

比如说一个人的出生日期，或者小孩子的年纪，它们每天都在变。但你不能天天去改。这时，实际上我不需要去改它，它就变成一个派生属性。我可以直接定义一个函数，让它随着查询时计算出来。这个孩子到目前的年龄甚至能精确到秒。 这种实现可以通过作为对象的虚拟字段对外提供服务，为上层业务提供了统一的计算能力。所以，函数能力赋予了属性，以及多个实体或对象之间的属性值的动态计算能力。

而 Action type，变成了 Agent 的一个触发入口。所以，它就变成了一个动态本体。

**应用/运营层的核心目标**： 基于统一的数据模型，快速构建面向决策的系统。

**实现方式**：

- 低代码平台、Workshop、拖拉拽。
- Slate：面向开发者，基于 Actor 方式开发。
- 推理模型：需要规则引擎、推理引擎来配置业务规则。
- 智能体：通过配置人工操作的界面，它有一个执行引擎和一个调度引擎。调度引擎可以用 IM 去做调度。这有点像 Workflow，是执行这类任务的东西。 这个其实就是应用层。

接下来，详细看一下推理引擎和 AI Agent。

推理引擎（AIP Logic 推理引擎）可以结合业务规则等构建一个决策图（Decision Graph），进而得出业务结论。它支持可视化构建器（Builder），允许用户自行编辑和配置规则。此外，它支持原生集成，可以集成一些通用的模型。

AI Agent 本质上是一个自主闭环的工作流，即感知、分析、决策、行动等环节。另一个重点是低代码平台，如 Workshop 和 Slate。它们可以绑定对象、链接和动作，实现开箱即用。Slate 还提供了一些外部开发框架，可用于渲染等。这些属于工具层。

此外，还有权限和治理层。因为前面提到的功能都能执行，所以执行过程需要可观测、可审计。解决方案是增加权限和治理层，包括：

- SSO 身份集成
- RBAC 基于角色的访问控制
- 属性级权限授权

正是通过这些机制，才能确保入口的精细化，并控制 Agent 的行为变化。

另一个重点是数据质量和可观测体系，包括：

- 全链路数据质量监控
- 关键数据部分的标记
- 全量可审计的日志

这些都是需要实施的。

Pantheon Frangy 最重要的一个点就是它的数据管理和数据血缘。

数据管理方面，因为它面向的是数据操纵，所以必须进行版本管理。每次 Pantheon 运行后，都会生成一个新的不可变的数据版本。因此，每次数据更新都是基于原则性的，每一次更改都要被记录和追踪。

数据血缘方面，每一个数据，它的来源、依赖关系等所有信息都应该被记录。你可以进行回滚，并且进行依赖管理。具体来说，在进行数据集计算时，所有触发的动作及其依赖都需要被存储。

基于这个基础，我们再来看一些具体案例。

几个场景：

- **供应链应用场景**：某个业务企业想利用 Frangy 来做供应链计划管理，包括实时监控库存、士气评估、全流程状态，并建立敏捷的异常响应机制，从而有效降低供应链风险。
- **实施步骤**：
    1. 数据采集：从 ERP、WMS、MES 等系统获取数据。
    2. 模型构建：构建关联关系模型。
    3. 决策：部署 AI 以实时监控指标，当出现延误时，自动生成解决方案。

这是优化场景。我们细分来看具体怎么做。

第一，数据采集。从ERP系统、MES生产计划产线、物流平台、财务系统采集数据，也包括一些外部情报。然后进行数据集成。

数据清洗与整合：

- 清洗数据不一致的问题。
- 进行数据标准化。
- 整合数据，形成数据资产。

在具体定义数据资产时，会涉及以下供应链数据整合步骤：

拆分步骤：

1. **定义核心业务对象**：供应商、零部件、采购订单、货运。
2. **定义对象关系**：
    - Link type: 供应商供应零部件。
    - Link type: 包含关联。
    - Link types for fields: 关联。
3. **定义函数**：
    - 计算供应商的平均交付周期。
    - 计算零部件的供应频次和偏差。
4. **定义动作**：
    - Action: 创建采购订单，触发创建新订单流程。
    - Action: 自动向供应商发送预警通知。

以上是本体建模部分，定义了这些元素。

角色应用构建了一个规则引擎，其核心逻辑配置如下（因为它本身有规则引擎）：

- **规则**：如果任何供应商的交付评分大于70，且该供应商是关键物料的唯一来源，则系统触发动作为寻找替代供应商创建需求。

其实就是规则引擎。它在上面构建了一个风险看板，进行全量、分布可视化监控。点击任意关键节点可以及时查看详情。一旦供应商出现风险情况，系统直接突出结论，并驱动相关人员去协作。这就是决策和应用。

决策完成后，这些信息会产生新的变化。新的变化需要落盘，即决策回写。触发这个流程后，系统会调用推送风险、生成订单等动作，并通过调用ERP API自动完成数据写入，减少人工操作。

这形成了一个闭环：动作触发定制化决策，决策需要落盘。此时牵一发而动全身，一个数据变化，所有关联数据也随之更新。这解决了数据一致性和实时更新的问题，能做到实时响应、降本省力，并实现智能预警。

自动化是AI应用的主流方向之一。

另一个例子是精细化库存管理。某零售企业拥有海量SKU，传统的库存管理方式难以做到精细化，导致部分商品积压占用大量资金，而部分商品因缺货导致销量损失。这时就需要系统自动、实时地识别滞销商品，以控制成本。

以下是精细化库存管理的具体实现流程：

上述问题中的人工低效和缺乏数据驱动，可以通过自动化来解决，称为智能库存管理。系统实现实时监控与预警，建立SKU监控模型，实现秒级告警和自动化决策，以达到释放资金的目的。

具体步骤如下：

1. **数据接入**：由中台系统集成所有相关数据源，包括库存记录、零件信息、出库单、生产工单、入库单等。
2. **指标建模**：对上述数据进行加工处理后，定义核心分析指标，例如周转率。计算公式为：周转率 = （相关数值之和）/差值。
3. **监控告警**：基于定义的指标（如周转率），系统建立实时监控模型。一旦触发预设规则（例如库存达到警戒值），即刻生成告警。
4. **自动化决策**：监控模型触发后，系统自动进行决策推演。例如，当库存需求下行且故障值达到某种设定比例时，系统会推荐相应的处理方式（如促销、调拨）。
5. **闭环回写**：决策完成后，结果会回写至业务系统（如ERP），并同步更新到数据中台，确保数据一致性。

这套方案解决的问题包括：实时监控与预警、自动化智能决策、释放资金以及优化绩效。

从具体技术细节来看，其核心是建模与计算：

- **定义核心对象**：将产品（Product）定义为核心业务对象，包含如 plant、plan_g 等相关属性。
- **逻辑封装**：将上述业务逻辑（如周转率计算、决策规则）进行封装。
- **虚拟属性挂载**：将封装后的逻辑作为产品（Product）对象的虚拟属性进行挂载，使其可以被直接调用。

然后构建产品画像、基本信息、决策分析等。其核心其实是两点：定义对象，然后定义一个 function 字段，能够自动实时地进行计算。

然后是决策。AI 逻辑被触发规则，这里有一个触发条件（trigger），例如它小于等于5，然后执行相应的规则（ruler）。或者，触发条件是它，规则是它。这些是预先写好的规则，用于监控和执行逻辑。

设定自动查询，可以建立线性监控，或者像原型（prototype）一样，数据驱动。还有自动计算，然后匹配规则，自动执行，自动形成决策流程。

所以这时你会发现，Plantia 的价值翻倍了。
