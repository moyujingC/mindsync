你好，我是产品二姐。

回顾过去两年 AI 的发展，你的脑海里肯定会冒出不少名词，比如某个新模型超越科学家了，Harness 能驾驭一切了，Skills、龙虾泛滥了，爱马仕可以自我进化了……真是让人应接不暇。不过，如果你和我一起静下心来理清事件脉络，就会发现：驱动事件背后的本质，并没有变化。

在第一章，我会用两节课带大家一起梳理这些名词，通过一张“演进地图”，把过去两年 AI 在模型层、工程层、产品层发生的关键变化串起来。让你看清每一层各自会往哪里走，三层之间是如何互相推动的，这能帮助你在课程后续的内容中保持清晰的学习方向；更重要的是，未来你再看到任何一个 AI 产品、任何一个技术名词，都能在这张地图上衍生出它的位置，快速理解它为什么能诞生，以及对你的工作意味着什么。

在我的上一个专栏 《成为 AGI 产品经理》 中，我把 AI 产品架构分了四层：

算法、算力、数据层

模型层

应用工程层

产品层

![](https://static001.geekbang.org/resource/image/74/db/745d77e5ec7fac402ed89dcefec6a0db.png?wh=4366x2518)

其中第一层算法、算力、数据层，更多的是对模型厂商的影响。对于大多数应用型的产品，这一层不需要深入掌握，我们就不展开讲，重点看上面三层。

我把这三层在近两年的演进总结为三个词：

更聪明是指模型层能处理更高难度的任务了。

更持久是指工程层能支撑更长时间的任务了。

更自主是指产品层从只能聊天的 Chatbot，变成了能独立干活的 Agent。

第一节课我们先来看模型层和应用工程层的演进。

## 第一层：模型层——不断挑战难度极限

对于 AI 应用来说，模型 token 就像是石油资源，油质越高，管道越多，才能支撑起各种各样的 AI 应用。

我用一张图表示这两年模型的变化。

![](https://static001.geekbang.org/resource/image/26/e8/266c0cbfb211a451dfbf362b3619bee8.jpg?wh=15918x7392)

在图中可以看到，模型有三个发展趋势：

第一，从“单纯的知识理解”变成了“超长步骤推理”。这里的推理不是数学里的推导，而是逻辑多跳推理，比如执行 A 任务，要完成 B 任务，而完成 B 任务，又要完成 C 任务，因此完成 A 任务，也要完成 C 任务。在最近（2026 年 4 月）发布的 Claude Mythos preview 中，长上下文多跳推理能力已经达到了 98% 左右的准确率，这个比率已经可以完成大多数的日常白领类任务。

![](https://static001.geekbang.org/resource/image/2f/1a/2f7112e8bf10117d4bcd58950b85c41a.png?wh=1474x956)

模型层的这个演进，对产品经理写提示词产生了一个重要影响，那就是类似“让我们一步步来”这样的 CoT（Chain-of-thought）已经不需要放在提示词里了，模型自带了推理思考。

第二，从单一的语言理解，变成了原生多模态。单一的语言是不足以传递信息的，视觉、听觉中都蕴含了大量信息，且有助于语言能力的提升。类似的，模型原生带视觉、听觉理解就自然而然成为趋势。在 Mythos preview 版本中，对复杂科学图表的理解能力也达到了接近 90% 的水平。

![](https://static001.geekbang.org/resource/image/2e/10/2e462fda5533f2f4753f8b2a60083210.png?wh=1322x1016)

这一点对产品经理的影响是：图像、语音理解原来需要多个模型，现在只需要一个模型。比如某个纸质收据识别系统，原来需要先让图像模型提取信息，然后使用大语言模型根据规则识别，那么现在可能只需要把图片和规则同时给一个多模态模型，就能完全识别了。步骤更少，会让响应速度变快，性能也会更稳定。

第三，编程能力完美地弥补了 LLM 的不确定性。大多数人把 AI 编程工作当做一个生产力工具产品来理解，但在我看来它的地位几乎和语言模型是一样的。从历史上来说，编程能力由 AI- 符号主义 一派发展而来，大语言模型是 AI- 神经网络派 的演变结果，可以说，今天的 AI 编程能力是符号主义与神经网络的完美融合，成为了 AI 应用的生产设备。

在 Mythos 的评测中，一般工程能力已经达到 93.9%，但是在真实活跃仓库与多模态的测试中，分别是 77.8% 与 59%，仍然有很大提升空间。

![](https://static001.geekbang.org/resource/image/4e/c6/4e75996860c31de103690abedcc763c6.png?wh=1918x1258)

编程能力对软件开发带来的影响不亚于第一次工业革命机器对手工业的冲击。产品经理直接 Vibe Coding 编程，开发工程师使用 AI 工具发现产品需求，这样的角色融合是必然趋势，但在到达那个完全融合的状态前，软件工程正在经历“组织在混沌中变革”的情况。

别担心，在这一门课中，我们既有针对“一人公司”的创业型产品经理的内容，也有针对这种“组织变革期”的协同型产品经理的内容。让大家对二者都有清晰的了解。

看完这三个趋势后，各家模型都不断地在这三方面持续精进，他们各有长短。下面是我个人长期经验总结得出的模型擅长方向，供你参考：

![](https://static001.geekbang.org/resource/image/b3/da/b337895f5324a4ca335f56050e3275da.png?wh=2568x1170)

不过，模型的飞速迭代，并不足以推动 AI 变革往前走。曾经有一个观点说：模型即产品，意思是只要模型足够强，产品包装这一层没有存在的必要。我并不认同这个观点。因为产品是针对一群人共同的需求做了一层抽象，如果人人都把模型当产品，模型每时每刻都会在重复造轮子。从人类追求经济的本性来讲，模型 + 产品必定共存，相互促进。

那么，过去两年，应用层、产品层又发生了怎样的变化呢？

## 第二层：应用工程层——从“靠运气”到“靠系统”

我把这两年应用工程层的演进用三句话概括，那就是：

第一阶段 Prompt Engineering，开发产品靠运气

第二阶段 Context Engineering，开发产品靠设计

第三阶段 Harness Engineering，开发产品靠系统

我们逐一细看。

第一阶段（2022 年 -2023 年）：Prompt Engineering，靠运气。

两年前的模型对于同一提示词，会输出完全不一样的东西。因此需要我们在提示词里给出各种条件、限制，反复调整多次，才能勉强碰对，那时我们把 Prompt 称为“咒语”“抽卡”，真的是碰运气。

第二阶段：Context Engineering（2024 年），靠设计。

到 2024 年底，用户对 Agent 的要求越来越高，使得 Agent 的四大件：行动、反思、工具使用、记忆，越来越复杂，上下文也越来越长，造成了“上下文腐烂”现象。

为了应对这种情况，Context Engineering 应运而生，它的理念就是：从冗长的信息中，只选出最相关的信息发给模型。

那么，如何才能选出最相关的信息呢？在 2025 年 9 月 Anthropic 发布的博客中，它清晰地对比了 Context Engineering 和 Prompt Engineering。

![](https://static001.geekbang.org/resource/image/d6/d0/d691ce2503fd1dd71b6f39ecd46ef6d0.png?wh=2292x1290)

在这张图里，我们可以看到，Prompt Engineering 阶段，上下文只有系统提示词与用户指令。到了 Context Engineering，上下文越来越长，会包含：

长期记忆：包括以文档的形式存在的知识库、Memory 文件；

程序性的提示词：包括系统提示词、领域专业提示词；

短期记忆：历史对话；

工具说明：基于 MCP 的工具体系。

Context Engineering 就是把这些上下文很好地管理起来，然后只把最相关的内容发给大语言模型，应对“上下文腐烂”的问题。

举个例子，Agent 在执行复杂任务时，首先做计划，分多个 Agent 完成多个任务。每个任务执行完成后，系统并不会把任务完成过程中所有的上下文发给模型，而只把子任务的输入、输出结果发给 Agent。这样，就能保证 Agent 在执行这个任务时把上下文控制在一定长度内。

而要达到只发相关上下文的效果，就必须对记忆、工具进行管理，比如任务计划、各个子任务的输入、过程、输出都需要分别管理，这就是当时的上下文工程，2025 年 3 月出来的 Manus 就是当时最典型的上下文管理模式。你看，这是不是从靠运气走向了靠设计呢？

然而很快，工程师们就感受到了 Context Engineering 的局限，那就是：每次执行任务都是单向执行，Agent 没有形成自我闭环反馈，比如生成一份股票的深度研究报告，Agent 会做计划、执行，执行完成后就直接交给用户。在执行过程中任务很难被中断，及时进行纠正。其次，Agent 对执行结果也没有进行自我评估。

能不能让 Agent 自己执行完任务，自己检查呢？这时候 Harness Engineering 就诞生了。

第三阶段：Harness Engineering（2025），靠系统。

Harness 一词原意是缰绳和马鞍，寓意 AI 这匹马很强大，但没有缰绳和马鞍，它就只会乱跑；而开发者，就是构建这些缰绳和马鞍的骑手。

2026 年 2 月，OpenAI 在博客中描述他们用 Codex 构建了一个超百万行代码的生产级产品。这个过程中，工程师们不写代码，只负责构建让 AI 可以可靠写代码的系统——Harness Engineering。

如果说 Context Engineering 能让 Agent 完成一个复杂任务，那么 Harness Engineering 能让 Agent 开发一个系统工程。

你可以把 Harness Engineering 想象成一个工厂车间，让我们跟随 Agent 的视角“参观”这个车间。

首先，当 Agent 来到车间门口，就会看到门口墙上赫然在列的车间介绍、工作制度、规范。这对应的是项目的各种文档，包括需求、架构设计、技术选型、测试规范。

打开大门，Agent 看到的是一张车间地图和一排工具架，放置着所有 Agent 可以使用的工具。这里，车间地图对应的是项目文档结构，工具代表着 MCP 与 Skills。

随后 Agent 进入车间大厅，迎面看到数字大屏，上面写着项目进度（包括当前已完成、进行中、待完成任务），每个任务都有详细记录。这对应着每项任务 Session 管理。

这时有人给 Agent 递来文件，上面写着任务说明和验收标准，这就是它要马上执行的任务。于是 Agent 便开始执行任务，过程中他可以随时参考车间地图查找所需资料，并在工具墙上按需取用工具。

在执行任务过程中，如果系统发现这个任务太大，Agent 的记忆存储空间不够了或不能独立完成，则会自动压缩记忆或者拆解出新的任务。这种记忆压缩、拆解新任务的标准对应的是一些自动触发机制，比如一旦上下文长度到了某个级别就触发压缩，或者新任务拆解。

任务完成后，Agent 就会把任务结果发给对应的质检系统。如果不合格要打回去重做，直到完成为止。这对应的是评估标准。

![](https://static001.geekbang.org/resource/image/93/50/9317f1567df8952eab845d8e3fd7b850.png?wh=4580x2162)

所以，Harness Engineering 本质上是为了给 Agent 工作提供一个安全、高效的场域。

对于产品经理来说，你可以有两种方式来应用 Harness：

一种方式是：在 Vibe Coding 任何一个项目的时候，使用 Harness Engineering 来开发产品，你可以主动构建这个项目的工作规范、评估体系等。

另一种方式是： 把 Harness Engineering 的思想融入到 AI 产品中，Harness Engineering 就像核心系统提示词一样，保障你的 AI 产品能高效、安全的运行。比如 Claude Code 就是一款自带部分 Harness Engineering 思想的产品。

如果你还觉得抽象，别担心，我们在后面的课程中还会讲具体的 Harness Engineering 实战案例，到时候你会有更深的体会。

这里我们也不妨展望一下，Harness Engineering 之后又会是什么呢？

我认为它最终会成为面向 Agent 的操作系统，Agent 只有在这个操作系统中，才能高效完成自己的任务。而 Harness Engineering 的记忆管理、工具管理、任务管理，不正是 Windows 这类操作系统的文件系统、App 工具、任务管理吗？

Harness Engineering 未来如何发展，让我们拭目以待。

## 总结

到这里，我们回顾了过去两年在模型侧、工程侧的演进地图以及对 AI 产品经理的影响。总结一下就是：

模型层会继续在超长步骤推理、多模态上精进，而模型编程能力已经补足了语言模型输出不确定的短板。产品经理不再需要耗费大量精力评测、选择模型。

应用层从 Prompt Engineering 到 Harness Engineering，从不确定的碰运气，走向更加安全规范的系统工程，产品经理既可以在 Vibe Coding 的场景中使用 Harness Engineering，提高编程效率，又可以把它嵌入到自己的产品中。

随着这两方面的进步，一个 Agent 可以执行的任务时长呈指数级上升。根据全球著名的 AI 评估机构 METR 给出的 Agent 可自主执行的任务时长，从 2023 年 2 分钟，已经提升到今天的 8 小时。注意，这个图里的纵坐标是用 2 的幂次来标注的。

![](https://static001.geekbang.org/resource/image/32/84/329a2297e33c07efb3ec6cfc7d218f84.png?wh=1569x893)

这就意味着，Agent 可以做的事情会越来越多，这也正是产品层可以大展身手的时候。下一节课，我们就来讲述在产品层，过去两年爆款产品的迭代路径，什么样的产品会在技术进步的大浪中存活下来，为我们该做什么样产品提供思路。
