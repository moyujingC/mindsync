你好，我是产品二姐。

到这儿，我们已经走到第三章的最后一公里了。也就是支撑 Agent 核心行动力的最后一个要素：多 Agent 协同。

![](https://static001.geekbang.org/resource/image/34/1f/34aa72179fb1c3614c03557fc23ab61f.png?wh=1708x976)

在过去两年，多 Agent 协同的演进用一句话说就是：从静态流水线走向了动态规划，从中心化走向了分布式。

怎么理解呢？ 我用人类在工作场景的协同方式来类比，一下子就明白了。

最开始，智能体刚刚被提出的时候，多 Agent 协同就像是固定在工业流水线上的工人，Agent 具备技能，但是协同方是上下固定的。

后来，Agent 成为一种资源，开发者构建了很多 Agents，然后主 Agent 可以把一个需求拆成不同任务，派发给合适的 SubAgent。甚至主 Agent 自己会构建 SubAgent。这就像层级划分明确的中心化军队组织，只有最高领袖知道各个子部门在干什么，各个子部门之间是不知道彼此存在，没有沟通的。这种模式被称为 Orchestrator-Subagent 模式，目前这个模式已经可以被生产级使用了。

再后来，模型能力增强。开发者希望每个 Agent 都能发挥自主能力，主动根据其他 Agent 的任务进度，主动领取任务，而不是派发。这就像是一个敏捷团队， 没有层级关系，有一个 Scrum Master 或项目管理员 Agent 负责协同，而且成员 Agent 之间可以直接沟通，主动认领并推进任务。这种模式最灵活，但也最难管理。目前仅在 Claude Code 这类顶级 Agent 当中有实验性的应用，还没有被广泛使用，但它一定是未来不可或缺的 Agent 协同模式。

需要说明的是，这三种模式不是递进关系，而是各司其职，各有用处。就像今天人类社会中，三种协作模式依然是并行存在的。

这节课，我们就看看这三种协作模式的适用场景，以及不同协作模式下 Agent 应该如何定义、上下文如何管理。

学完之后，就可以为你的业务场景选择合适的协同模式，为我们后续的实战做好准备。

## 模式一：工业流水线

工业流水线是最朴素、也是最早出现的 Agent 协同方式。比如，我们曾经做的一个股票分析应用，就是下图这样的流水线：

![](https://static001.geekbang.org/resource/image/a6/36/a6641ec57585004ee49fd3295d0cc536.png?wh=2626x1278)

股票分析流水线

先让基本面、情绪面、技术面三个 Agent 分别做分析，把结果汇总到一起。

然后交给一个看涨方 Agent vs 看跌方辩论 Agent 去辩论交锋。

辩论完再交给综合 Agent、交易员 Agent、风险员 Agent 进行判断，给出分析结果。

这里说的 Agent，本质上就是对应一段提示词。比如那个技术面分析 Agent，它的提示词可能长这样：

你是一名专业的股票技术面分析师。请根据我给你的这只股票近 6 个月的日 K 线数据，完成下面几件事：判断当前处在什么趋势阶段（上升 / 下降 / 震荡）；解读 5 日、20 日、60 日均线的多空排列；识别 MACD、RSI 有没有出现背离或超买超卖信号；标出近期的关键支撑位和压力位。输出时，先给一句话结论（偏多 / 偏空 / 中性），再用 3-5 条要点说明依据。

这就是流水线式的协同方式，它的上下文管理也很简单：上一个节点的输出，作为下一个节点的上下文。以现在的眼光来看，它都不能称为 Agent，而在 2024 年，能完成这种静态工作流的输出，也同样被称为 Agent，可见 AI 进步有多快。

不过，这种流水线的方式，要求提前就知道完整的步骤，在早期大语言模型幻觉频频的时候，能有效控制任务不跑偏。但现实中很多任务是走一步看一步的，随着大语言模型的进步，指令遵循能力增强，Agent 就能充分相信模型，开始处理更多任务。

于是，Agent 协同的第二种模式开始成熟。

## 模式二：中心化协同

第二种范式是 Orchestrator-Subagent，直译过来就是编排者与子代理协同模式，我把它翻译为“中心化协同”更方便理解。

它的结构是：有一个主 Agent 当“主管”，它只做协同，会根据当前任务的进展，随时决定是否拆出子任务、派给一个个 SubAgent 去做，SubAgent 干完把结果汇报给主管，主管再综合，如下图。

![](https://static001.geekbang.org/resource/image/52/ed/5258fae4b889e100a80b31403a53d3ed.png?wh=1814x1435)

中心化协同模式

还是用刚刚股票分析的例子。比如当用户看到五粮液股票的分析报告后，还想把五粮液和泸州老窖、山西汾酒财报做对比分析，而系统中并没有预制这个对比的 workflow。那么这时候就需要让 Agent 派出 2 个财报分析 SubAgent，分别分析泸州老窖、山西汾酒财报的情况，汇总给主 Agent 后，由主 Agent 做对比。这就是中心化模式的多 Agent 协同方式。

这里你可能会问：如果我写一个财报分析 Skill，让它依次完成泸州老窖、山西汾酒的财报分析，不也能搞定这个任务吗？没错，能搞定。

两种方式的不同在于：如果用 Skill，就是主 Agent 自己去读泸州老窖、山西汾酒的财报，主 Agent 的上下文窗口会有原始文字，也会有泸州老窖、山西汾酒的财报，如果财报数据很多，主 Agent 就容易发生记忆爆炸，引发不必要的干扰信息。

而用多 Agent 协作，每个 SubAgent 都拥有一个全新的、独立的上下文窗口，只有主 Agent 派给它的任务里定义了上下文，子 Agent 返回给主 Agent 也是最终的结果，而不包含它完成任务所需要的过程。

所以多 Agent 协同有一个非常重要的作用，就是高效管理 Agent 的上下文，通过跨 Agent 之间的任务拆分，可以完成更长、更复杂的任务。我把使用 Skill 和使用 SubAgent 的上下文管理用下图做对比，可以更明确说明这一点。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/10/64/10382b8bc2c79f9e0d621237d72d3e64.png)

不过，有一种 Agent 会继承主 Agent 的全部上下文，那就是 Forked Agent。我们在 07、08 讲聊记忆管理的时候，曾经提到 Claude Code 会 fork 一个 Agent 来进行 memory 的记忆提取和记忆压缩，这是一个比较特殊的 SubAgent。除此之外，大部分 SubAgent 拿到的上下文都是经过主 Agent 裁剪、精简之后的。

那么这种中心化模式的多 Agent 协同是如何实现的呢？本质上，主 Agent 派生 SubAgent 就是把 Agent 当做工具一样随时调用。执行任务的时候，主 Agent 会拿到所有的工具列表，其中包含 Agent 这个工具，判断是否需要使用 Agent 工具。如果需要，就生成相应的上下文（比如 Agent 系统提示词，需要完成的任务等），生成 Agent。

当然，你也可以预备好专属的 Agent 供主 Agent 随时调用。遵循工具的渐进式披露的原则，定义 Agent 的 Markdown 文件头部也是用一段 YAML 声明它的身份，正文就是它的“岗位说明书”。下面就是一个简单的 Agent 定义方式：

name: code-reviewer

description: 审查代码质量与最佳实践

tools: Read, Glob, Grep

model: sonnet

你是一位代码审查员。被调用时，分析代码并就质量、

安全、最佳实践给出具体、可执行的反馈。

需要注意的是，Agent 这个工具有一个很关键的约束：Agent 不能再派生 SubAgent，也就是 Agent 不能再调用 Agent 这种工具。这样设计，是为了防止 Agent 无限套娃， 引起上下文混乱。如果某个任务确实需要“嵌套委派”，就可以再回到主对话里，由主 Agent 再去调用 Agent 工具，而不是让子 Agent 自己使用 Agent 工具。

这个限制就是中心化模式的本质——所有的协同权，都牢牢握在主 Agent 这一个“中心”手里。 这既是它简单可控的原因，但也是它的天花板：当任务复杂时，多个子任务相互依赖彼此，都要经过主 Agent，就会给上下文管理带来极大挑战。于是 Agent 协同方式又往前迈了一步——分布式协同。

## 模式三：分布式协同

分布式模式，在 Claude Code 里叫 Agent teams（智能体团队）。这是三种范式里最难管理的一种，目前也只有少数 Agent 系统真正采用，在 Claude Code 里它还是实验性功能，默认是关闭的。但它仍然是未来多 Agent 协同的重要方式，需要我们了解。

在人类社会中，这种模式在软件研发场景中最常见，所以你完全可以把 Agent 团队想象成一个敏捷团队。在分布式模式中，团队成员不再只向主管汇报，而是可以直接互相沟通，所有队友们共享一份任务清单、自己认领工作，并且直接互相通信。

![](https://static001.geekbang.org/resource/image/a5/0a/a5b751edf78f18cb71c2d2b32289fc0a.png?wh=2448x1615)

分布式协同模式

这种工作场域你听起来是不是有点像我们在 02 讲 提到的遵循 Harnerss Engineering 构建 Agent 车间？没错，Harnerss Engineering 本身就是实现 Agent 分布式协同的前提。

这种模式下有四个要素，我把它们分别对应敏捷开发团队的概念中，是这样的：

团队 Lead：对应 Scrum master，主要负责项目管理、协调事务。注意这里的 lead 和 teammates 并不是层级关系。

Teammates：对应团队的前端、后端、产品等人员，完成具体任务。

共享任务清单：对应的是敏捷团队的白板，团队成员在这里可以看到自己的任务，也可以看到别人的任务进度，依据不同任务的依赖关系，自己主动认领任务等。

信箱：对应的是团队的每日站会，会上大家可以快速和其他成员沟通彼此的任务进度，依赖项。只不过在 Agents 的虚拟世界中，这种沟通不是以每天的频率在进行，而是无时无刻不在进行。

分布式协同看上去很美好，但落地起来会有以下挑战，虽然我们可以参考 Claude Code 的落地方式，但目前还没有成熟的框架支持，如果要应用在实际业务中，需要谨慎考虑。

这些挑战主要有：

成员之间可能会发生冲突。比如成员 A、B 同时修改一个文件，彼此覆盖。在 Claude Code 中，它提供了类似 GitHub 代码库的这种管理方式，每个成员拉一个 branch，最后再合并。

Token 消耗量大。因为每个 Agent 都有自己的独立的上下文，比如白板任务信息，主 Agent 对应的共享信息等，如果用中心化的模式，这些 Token 是不会出现在 SubAgent 当中的。

沟通成本过高。分布式协同需要每个团队成员都和所有其他成员沟通，会增加 token 消耗，也会增加冲突发生的可能性。

到这里，Agent 协同的三种方式就讲完了。那自己的业务中到底该选哪一种模式呢？

## 如何选择协同模式？

选择协同模式有三个决定因素：

任务复杂度：如果流程固定，就用 workflow 的方式解决。无固定流程的首先考虑中心化模式，如果中心化模式遇到瓶颈，（比如主 Agent 的上下文经常触及上下文局限），再考虑分布式模式。

可容错程度：可容错程度较低，比如金融交易、监管合规的，依然推荐用流水线 workflow。可容错程度一般的，比如客服辅助、内容生产、数据分析这类有人类兜底的任务可以考虑用中心化模式；可容错程度较高，且确实需要发散思维的，比如代码工作、科学研究等，可以考虑分布式模式。

Token 预算量：多 Agent 系统烧的 token，大约是单 Agent 的 10 到 15 倍。

但请记住，随着模型与工程能力不断提升，Agent 的能力范围会进一步扩大，而业务诉求也会跟着变化。当下，中心化模式的采纳率正在变高，分布式协同模式也正在完善中。对应到你自己的业务中也是如此在演进，比如一个电商客服系统，演进路径可能是这样的：

第一阶段：加意图路由，将客户常见的订单状态、商品问题、投诉放在多个 workflow 中分别解决，这是工业流水线模式。

第二阶段：配置多个 Agent，比如营销 Agent、销售 Agent、售后 Agent，每个 Agent 配备不同的工具的只读权限，由主 Agent 判断并识别调用正确 Agent 解答客户问题。 同时加上一个评估 Agent，类似 forked Agent，监督所有 Agent 的进程，做质量保证和持续改进。这是中心化协同模式。

第三阶段：进化成协调库存、支付、物流的多 Agent 系统，各个 Agent 的权限也逐渐扩大，完成完整的客户服务。这就是分布式协同模式。

所以，一个 Agent 系统，它从来不是一步到位的，而是从最简单的方案开始，伴随着整个行业的成长，踏实、稳步前行！

## 总结

最后，我们来总结一下。这节课我们看了多 Agent 协同的三种范式，加上这一章前几节的内容，我们把 Agent 四大能力——行动、记忆、工具使用、多 Agent 协同，通过“庖丁解牛”式的学习，把这两年的演进全部都过了一遍。

我用开篇词里的这张图来总结一下，相信此刻的你再看这张图，已经将其中的概念了然于胸。 让我们一起做一个简单的回顾。

![](https://static001.geekbang.org/resource/image/a8/f1/a8050de2dfd19631d7b6511907107ff1.png?wh=2728x2524)

Agent的演进

行动能力：从最初论文里的 ReAct 循环——推理→行动→观察，进化到今天工业级的应用中。靠的是更强的模型能力以及后面三种能力的外围工程。

记忆管理：从早期微调（fine-tuning）、脆弱的上下文管理、RAG 走到今天的 Memory 文件、高效的上下文管理、LLM Wiki 来管理记忆。本质上是随时随地将 Agent 的记忆进行保鲜、压缩、整理。

工具管理：从 Function Calling 这种手写函数进化到 MCP 这样的标准写法；安全防护也从简单，走向多层、细粒度的权限管控。

多 Agent 协同：从人工预设的静态流水线，走到中心化的动态派发，再到分布式的自主协作。从工人到军队再到敏捷团队。

也正是这四大能力齐头并进，驱动着 Agent 从能用一步步迈向好用。

而作为产品经理，我们也准备好了开发新一代 Agent 的兵器库，下一章触类旁通就是要学以致用。我们会把这些拆解出来的思想，真正迁移到你自己的金融、营销、内容业务里去，做出属于你的产品。
