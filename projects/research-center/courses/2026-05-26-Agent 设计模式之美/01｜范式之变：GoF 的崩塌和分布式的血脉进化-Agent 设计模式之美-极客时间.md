## 第一代 GoF 23 模式，用了 20 年的设计词汇

1994 年，四位计算机科学家（Erich Gamma / Richard Helm / Ralph Johnson / John Vlissides，简称 GoF 四人帮）合写了一本书叫《 Design Patterns: Elements of Reusable Object-Oriented Software 》（ 设计模式：可复用面向对象软件的基础 ）。书中给面向对象编程立起了 23 个可复用模式，成为了软件工程历史上影响最深的书之一。

![](https://static001.geekbang.org/resource/image/bd/83/bd931a5aa8b88b6c54e8ffd6ab057c83.jpg?wh=808x626)

设计模式

GoF 的 23 种设计模式，本质上就是 23 种写程序时常见问题的经典解法。简单来说有三类。

创建型：怎么把对象“造出来”更灵活。

结构型：怎么把对象“拼起来”更合理。

行为型：怎么让对象之间“配合工作”更顺畅。

![](https://static001.geekbang.org/resource/image/56/41/56327a350c10fdae54739c2f9760d441.jpg?wh=4003x3147)

这 23 个模式不是凭空发明的。往上追溯，模式语言这个概念来自 1977 年建筑学家 Christopher Alexander 的《A Pattern Language》。Alexander 当年在做城市规划，发现“好的城市不是设计出来的，是从一组反复出现的好模式涌现出来的”，他把这套思路写成了一本厚书。GoF 把 Alexander 的“建筑模式语言”搬到了软件工程，建立起这 23 个面向对象的可复用模式。

![](https://static001.geekbang.org/resource/image/ab/95/ab985a9aedfd9eb8c4674c28ef0dca95.jpg?wh=2364x956)

无论建筑还是 IT 工程，好的设计都是从一组反复出现的好模式涌现出来的

GoF 23 模式的工程价值是什么？具体来说，无非是做好这两件事。

第一件事，提供共同词汇。Singleton、Factory、Observer、Strategy 这套词汇我们用了 20 年。它让我们能在 5 分钟里跟同事讨论一个系统的结构，让我们审查代码时能说“这里该用 Strategy 不该用 Switch”，让架构图能用一句“这是 Observer 模式”代替三页文档。

第二件事，把编码工程经验抽象出来 ，这 23 个模式都是从工业实战里萃取出来的好实践，我们不需要重新发明轮子。

但 GoF 23 模式有一个共同的底层假设：它假设单进程 / 共享内存 / 同步调用 / 确定性失败。所有对象在一个进程里跑，状态在共享内存里改，函数调用同步返回，失败就抛 Exception。这套假设在 1994 年成立、在 2000 年还成立，到了 2010 年代分布式系统开始大规模铺开，这套词汇突然不够用了。

## 第二代 2010 年代 分布式系统模式

2010 年代我们经历了一次大规模的工程范式之变，我们从单机走到了集群。Microservices / Kubernetes / Service Mesh 一波接一波，GoF 的每一条底层假设都受到冲击。

共享内存 → 网络分区 (节点之间不能瞬间看到对方状态)

同步调用 → 异步消息 (调用方等不到响应可能就是消息丢了)

单点失败 → 部分失败 (一个集群里 30% 节点挂了系统仍要工作)

确定性 → CAP 三选二 (Consistency / Availability / Partition tolerance 不能全要)

GoF 的 Observer 在分布式里失效了，你想给 1000 个 subscriber 同步推 event？网络不允许。你想用 Singleton 管全局配置？跨集群没有全局。整套词汇得重新建立。因此，接下来的 10 年涌出了一批新模式，也就是第二代设计模式——分布式系统模式。为了便于你阅读，我选了 9 个最经典的做成了表格。

![](https://static001.geekbang.org/resource/image/3b/c9/3bd56150095a82df468360cd3b70b6c9.jpg?wh=4449x3784)

这 9 个分布式模式的共同特征是什么呢？它们都把“不确定性”作为首要关注点来处理。GoF 假设失败是 Exception，分布式假设失败是 default，每一个模式都是在不确定性下保证系统行为可靠的工程纪律。

做过 5 年以上微服务的同学，这 9 个模式应该都熟。如果还不熟，推荐 Michael Nygard 的《 Release It!》，它是分布式工程模式的奠基书，地位类似 GoF 之于面向对象时代。

OK，到这里我们有了第一代 GoF 23 模式 + 第二代分布式 9 个核心模式，目前为止我们一共有了 32 个旧模式。这些就是 2024 年 LLM、Agent 出现之前，我们在系统中做工程决策时用到的主流词汇。

## 第三代 Agent 模式，解决“模型怎样被约束地行动”

第三代 Agent 模式所要解决的，已经不再是传统意义上“代码如何组织”或“服务如何协作”的问题，而是“模型怎样被约束地行动”。

很多人一谈 Agent 就容易把它讲得很玄，但如果把它放回整个软件工程的演进脉络里看，其实它并不神秘，它只是把系统的核心难题又往前推进了一层：第一代的核心是对象协作，第二代的核心是服务协作，而第三代的核心则变成了模型协作。

![](https://static001.geekbang.org/resource/image/b1/a6/b14b5e985890276918d39e5eeb5cb4a6.jpg?wh=4500x3938)

表面上看，这似乎只是词汇的变化，但背后的工程含义其实非常深刻，过去我们写的是逻辑，系统按预先写好的逻辑执行；后来我们设计的是边界，让服务在预设边界内彼此调用；而现在，我们面对的是一个会在运行时自己决定“看什么、想什么、调什么、做什么”的系统部件。

因此，Agent 时代最深的变化，并不是又多了一个 AI API，也不是又多了一个工具协议，而是决策的位置发生了迁移：在 GoF 模式里，关键结构决策默认由人在设计阶段做出；而在 Agent 系统里，大量关键决策开始转移到运行时，由模型在不确定环境中动态生成。

一旦这一点发生，旧模式就不会彻底失效，但会开始失重。它们依然存在，依然有价值，却已经不足以完整解释我们今天面对的新问题。

## 模式崩塌：GoF 模式在 Agent 时代如何断裂

2024 年 LLM agent 大规模铺开之后，GoF 和分布式的某些假设依然有效，但很多常用的模式各自以不同方式断裂。

我们拿 GoF 里四个广为人知的模式来看。

### Singleton 断裂，因为状态不再全局共享

经典 Singleton 保证全局只一个实例，一个数据库连接池、一个配置管理器、一个 Logger。基础假设是状态持久共享，所有调用者看到同一份内存里的同一份数据。

![](https://static001.geekbang.org/resource/image/c9/2f/c98cbe81d9f416d50b919ce287daec2f.jpg?wh=1664x1348)

Agent 的状态受上下文窗口所限，有 token 上限，且每次对话都会被重置。你想在里面放一个“全局配置管理器”，第一次对话能塞进去；用户聊到一定 token 上下文在压缩的过程中万一你的全局配置消失了，Agent 就没法找回。再开启一段新对话时，它压根没见过你的全局配置（你也许还以为，我之前和他说过了呀😀）。

这里需要的不是 Singleton，是分层记忆架构，工作记忆 / 短期记忆 / 长期记忆 / 程序性记忆四层，将是第三模块“记忆 - 沉淀之美”整章要讨论的内容。

### Factory 断裂，因为动作空间在编译期是开放的

经典 Factory 从固定分类造对象——createSedan() / createSUV() / createTruck()。基础假设是产品类型在编译时已知。

![](https://static001.geekbang.org/resource/image/5f/45/5f05b9dca4964f52689e38380yyb3a45.jpg?wh=1664x1348)

Agent 的“产品”是动作，而动作空间根本不是编译期的。MCP 协议 (Model Context Protocol) 让 Agent 在运行时动态发现新工具，你今天部署的 Agent 明天可能就接到一个昨天不存在的 MCP server。createTool(ToolType.GREP) 这种写法在 Agent 世界里根本写不出来，因为下一个工具叫什么名字、签名长什么样，写代码的时候不知道。

这里需要的是语义工具路由 (semantic tool routing)，让 Agent 根据自然语言意图，动态匹配 MCP registry 里的工具描述。我们会在 20 讲探讨工具调度（Tool Dispatch ）时把它讲透。

### Observer 断裂，因为同步推送会自爆

经典 Observer 同步通知所有订阅者，状态变化触发回调，所有 subscribers 立刻收到。基础假设是推送可靠且廉价。

![](https://static001.geekbang.org/resource/image/ba/12/bacd4aedf4624e83be3a72c2ff314b12.jpg?wh=1536x1228)

让 Agent 浏览一个网页，DOM 节点几百个，你要是把 DOM 树全推给它做 Observer，上下文窗口很快就爆。让 Agent 监控一个 logstream，一秒一万条 log，每条都推送过来，还没等 Agent 想任何事情，token 已经烧完了。分布式系统当年是通过消息队列 + 最终一致性解决了类似问题。

Agent 系统比这个还要再进一步，它可以主动感知 (active perception)，Agent 自己决定看什么、什么时候看、看多深。第二模块“感知世界之美”会进一步深入剖析。

### Strategy 断裂，因为人不再选策略

这个最有代表性，单独拎出来讲。

经典 Strategy 长这样：calculator.setStrategy(new VIPPricing())，开发者在编码时决定用哪个策略。Strategy 模式的整个工程价值，就在于让策略切换从硬编码变成参数化。但切换决策本身仍然在开发者手里。

![](https://static001.geekbang.org/resource/image/81/1c/819843b62f63eeb6c3e339ec48c2351c.jpg?wh=1536x1105)

回到刚才那个 15 分钟修 5xx 的例子。Claude Code 修这个 bug 走了 7 步：grep 定位、读文件、形成假设、跑测试、被打脸、改假设、再写代码。这 7 步里没有任何一次 setStrategy() 调用。每一步的策略选择都是 LLM 在运行时根据“我现在看到了什么”自己做的：

看到 cache.py 第 47 行的 lock 用法可疑，切到 race condition ；

假设“测试失败，但不是 timing 的问题”（也就是和操作次序无关），切到 stale data ；

假设需要看更多 caller，切到 grep mode ；

寻找所有 cache.get 调用点 。

如果是在 GoF 时代，每一个箭头切换都得是一个 setStrategy() 调用、一个开发者 design time 写好的分支。而在 Agent 世界里，每个箭头都是 LLM 在运行时自己画出来的。Strategy 模式没消失。它被搬到了 Agent 脑子里，由 LLM 在每一步动态切换。

### 根因：决策权从开发者搬到大模型

把这四种断裂放在一起看，根因是同一个：

GoF 所有模式假设架构师在设计时做出所有结构性决策。Agent 系统要求由系统本身在运行时、不确定性情况下做出决策。

GoF 是编译期决策 + 运行时执行；Agent 时代是运行时决策 + 运行时执行——决策权从开发者手里搬到了 LLM 手上。这个搬家就足以让 GoF 整个 23 模式集体失重。

落到代码层面，这四种“搬家”就长成下面这样，你可以把它印一份贴电脑上：

GoF Singleton → MemoryArchitecture (03 记忆模块 · 4 层记忆)

GoF Factory → SemanticToolRouter (04 行动模块 · 工具调用和MCP语义匹配)

GoF Observer → ActivePerception (02 感知模块 · agent 自己决定看什么)

GoF Strategy → LLM 在 reason() 里每一步自己挑

这门课讲的 28 个新模式，每一个都在回答这个问题：当决策权在 LLM 手上时，工程师该怎么搭框架，才能让 LLM 的决策稳定 / 可审计 / 可复用。

## 血脉进化：分布式模式在 Agent 时代继续演进

从第二代到第三代，旧模式没有消失，它们被推进了一层。模式的三代演化图并不是在做“新旧替换表”——Saga 换成什么，Bulkhead 换成什么。真正准确的说法是：第二代模式处理的是服务世界的不确定性，第三代模式处理的是模型决策的不确定性。问题还在，但承载问题的对象变了。

你可以这样理解这条血脉。“长事务补偿”到了 Agent 时代，会进化成“规划—执行”。

为什么？因为 Agent 的任务本来就不是一步完成。模型先拆任务，再执行步骤，执行中失败了，还得根据当前状态重新规划。以前补偿的是数据库状态，现在补偿的是任务推进路径。

这些进化你同样可以参考下表。

![](https://static001.geekbang.org/resource/image/e2/42/e2e51f22e9e60cfeebf56cf25c2feb42.jpg?wh=4449x3511)

第二代和第三代之间是推进的关系，不是断裂。旧模式没有过时，旧模式是被“抬高了一个层次”。但为什么到这里，很多人还是会觉得传统模式不够用了？因为真正崩的不是某一个具体模式，而是“系统默认可控”这个前提。

## 模式演进的根因：三种不确定性

如果说 GoF 的前提是确定性执行，分布式的前提是不可靠网络， 那么 Agent 时代的新前提，就是高强度的不确定性。

![](https://static001.geekbang.org/resource/image/e9/c4/e91b995134b1c7f2c94a6967ca4a14c4.jpg?wh=3964x1924)

第一种 输出不确定 (Output uncertainty)

同一个 prompt，模型跑十次，可能给十种不同答案。你过去以为 retry 会得到同样结果，传统软件的 retry 假设幂等，失败重跑应该得同样结果。但在 LLM 上，LLM 调用的重试可能得到完全不一样的答案，引出新的行为分支。这就让熔断器（Circuit Breaker）、幂等键（Idempotency-Key）这些经典工程模式整套要重新装一遍。

第二种 行为不确定 (Behavioral uncertainty)

Agent 不只是给你一个答案，它还会自己决定要不要调用工具、先调用哪个工具、要不要问澄清问题、要不要继续展开思考。它的行为轨迹，不再是代码里写死的流程图。一个 ReAct Agent 在 Reasoning 和 Acting 之间循环切换，循环长度、循环内容、每一步具体做什么，都不是 设计阶段就能预测的。

第三种 环境不确定 (Environmental uncertainty)

Agent 操作的世界本身在变。一个浏览网页的 Agent，今天看到的页面布局明天可能变了；一个写代码的 Agent，它上次读过的 Codebase 这次可能已经被同事改过。世界不会停下来等 Agent。

传统软件工程把不确定性当边缘情况来处理，try-catch 一下、retry 几次、超时报错。大家会觉得我加个 retry、schema 校验，后者加个 timeout 就稳了。这思路是 try-catch 思路，它治不了 Agent 系统。

Agent 工程必须把不确定性当作默认运行条件。也就是说，要从一开始就默认系统会漂、会偏、会重复、会失控，在这个前提下设计结构，不能等出了问题再打补丁。

一旦你接受这一点，后面的核心判断就顺理成章了。

## 真正的新地基：Harness

地基（前提）变了，软件工程系统的重心也就不同了。当系统的关键决策越来越多地在运行时由模型作出时，工程师的工作重心就发生了迁移。过去我们主要是在写功能逻辑，现在我们越来越多是在设计边界条件。

也就是说，工程师定义的范围扩展了。除了“系统做什么”，还要定义：

模型在什么上下文下思考；

模型能看到哪些信息；

模型能调哪些工具；

模型在什么条件下必须停下来；

模型做错以后，系统如何把它拉回来；

模型做过什么，谁来留痕，谁来审计。

这一整层，不是 prompt。这一整层，就是 Harness。

Harness 在模型思考之前、之中、之后，给它立边界、留痕迹、做审计。它不替代模型思考。

请你记住后面这句重要的工程判断，这个思想也会在后面课程里反复、充分体现。

Agent 架构，就是在不确定性之下设计有界资源的分配。

Agent architecture is the design of bounded resource allocation under uncertainty.

更口语一点说，就是：模型负责花钱，Harness 负责管账。\*

![](https://static001.geekbang.org/resource/image/4f/76/4f7813fc978ab21820f5484d1c05a376.jpg?wh=3155x1559)

为什么是“花钱”和“管账”？

到了 Agent 世界里，token 是钱，context 是钱，工具调用是钱，wall-clock 是钱，用户信任是钱，不可逆动作的风险也是钱。模型天然擅长生成可能性，但它不天然擅长节制。它会花，会试，会探索，会走弯路。真正的问题是它花到哪里、花多少、什么时候该停——模型会花是默认前提。于是 Harness 的意义就出现了：它不负责创造智能，它负责约束智能的开销与后果。

![](https://static001.geekbang.org/resource/image/96/af/9697d298c3132c33e94c6b2eac1e1eaf.png?wh=1408x768)

这时候你会发现，前面那一大串从 GoF 到分布式再到 Agent 的演进，终于合上了，终于闭环了：

GoF 教我们组织代码；

分布式模式教我们驯服网络；

Agent 时代则逼着我们去驯服模型的运行时决策。

而驯服这件事，靠的就是整套 Harness 工程。

Harness 是新一代工程师的最高杠杆工程。因为 Agent 时代最值钱的，不再只是“让模型会做事”，而是“让模型持续稳定地做对事”。

![](https://static001.geekbang.org/resource/image/5c/2b/5c73e5d6313819828d739eeb2bfca72b.png?wh=1536x1024)

发现一个错误，如果你只是改 prompt，那往往只是让它“这次别犯”。 但如果你去改 Harness，你是在设计一种机制，让它“以后都别这么犯”。

这就是工程和调参最大的分界线。

调 prompt，是局部修补。

做 Harness，是把局部错误上升为系统纪律。

所以我越来越相信，新一代工程师最重要的能力，是能把企业的流程、知识、权限、风险、审计，沉淀成一套 Agent 可以消化、可以复用、可以持续迭代的 Harness 结构。写几个只存在于 PPT 展示、看起来很炫的 Agent demo 谁都能做，再包一层 Workflow 也算不上真正的工程能力。你做的是企业未来的智能操作系统外壳。

## 双轴正交框架的提出：这一代的“GoF 词汇”

到这里我们已经完全看清，第三代 Agent 模式正在涌现，时代呼唤新的范式。而这门课要建立的就是 Agent 时代的“GoF 词汇”。

如果今天面对的只是几个新技巧，那我们完全没必要再立一整套模式词汇。但问题在于，Agent 时代的模式已经不是 GoF 那种“对象怎么构造、怎么组合、怎么协作”的问题了。它的核心张力变成了另一件事：资源花在什么地方以及资源是怎么被花出去的。

所以我最后决定，不沿用 GoF 的“创建型、结构型、行为型”三分法，也不跟着分布式时代“来什么问题，解决什么问题”那种见招拆招的模式构建套路，我提出一套更适合 Agent 的坐标系。

第一条轴，叫认知功能。 也就是 Agent 到底在做什么：感知、记忆、推理、行动、反思、协作、治理。

另一条轴，叫执行拓扑。 也就是这些能力到底是怎样流动起来的：链式、路由、并行、编排、循环、层级。

前者回答的是：资源花在哪里。后者回答的是：资源怎么花出去。

这就是为什么我说，后面这 28 个 Agent 模式构成了 Agent 时代新的“共同词汇”，给我们一套可以共同讨论 Agent 工程问题的语言。就像 GoF 当年给面向对象时代立起语言一样，我希望这一套双轴框架，能够给 Agent 时代的工程设计立起一张真正能用的地图。

## 总结一下

今天这一讲最重要的，是记住一条完整的血脉。具体的定义，以后可以查、可以补。

第一代 GoF 模式，解决的是代码对象怎么组织。

第二代分布式模式，解决的是系统在不可靠网络中怎么存活。

第三代 Agent 模式，解决的是模型在高不确定环境中怎样被约束地行动。

第二代不是把第一代推翻，第三代也不是把第二代推翻。它们是一道道往上推进的问题升级。对象协作之后，是服务协作；服务协作之后，是模型协作。

真正让第三代成立的，是系统决策位置的迁移。从开发者的设计时，搬到了模型的运行时。多一个 LLM API 还不至于。一旦决策权搬家，模式就必须跟着搬家。而一旦模式开始搬家，工程师的最高杠杆也跟着搬家，从写功能搬到了设计 Harness。

但 28 个新模式不能像 GoF 那样按创建、结构、行为分 3 类，因为 Agent 模式的核心张力不在“做什么对象操作”，是“花什么资源 × 怎么花”。

所以，这门课后面要讲的 28 个模式，归根结底都在回答同一个问题：当模型开始在运行时自己做决定，工程师该怎样搭一个框架，让这些决定仍然稳定、可审计、可复用、可进化？这，就是 Agent 设计模式真正要回答的命题。
