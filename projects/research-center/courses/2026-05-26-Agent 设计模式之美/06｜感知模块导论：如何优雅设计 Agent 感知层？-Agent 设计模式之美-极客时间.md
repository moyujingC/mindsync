你好，我是黄佳。欢迎进入第一个模式组——感知模式。

正题开始之前，请你先思考个重要问题：归根结底，感知和记忆都是 Context Engineering 的一部分，那么为什么要拆成感知和记忆两个模式组？如果你已经在生产实践中建设自己的 Agent，那么你哪些时候是在设计感知？哪些时候是在设计记忆？

没有标准答案，只是想启发你的思考。因为有时候我也觉得二者的边界有些模糊。但是把它理得更清晰，显然有助于我们思考得更深。希望讲完感知模式组和记忆模式组之后，我们建立更深入的认知。

这一模块讨论一个看似简单、但在生产系统里极其关键的问题：怎样让 Agent 看对东西。

传统软件没有这道工序。函数的输入是被 schema 严格定义的，调用方传什么就处理什么，工程师不用操心“该让谁进”。Agent 不一样，它的输入是 prompt 这种自由文本，谁进 prompt、谁不进、按什么顺序进、压缩到什么粒度，全是工程师的设计决策。每一个进入 prompt 的 token 都在花预算：attention 预算、KV cache 空间、API 计费。Perception 就是在管这笔预算。

![](https://static001.geekbang.org/resource/image/a8/y6/a83fd39b76d3b9c9bd095d00d5287yy6.jpg?wh=1448x1086)

很多时候，模型已经足够强，prompt 也写得很认真，Agent 给出的答案看起来通顺、引用具体、逻辑自洽，但最后一核对，事实是错的。把 trace 拉出来看，问题往往不在推理阶段，而在最前面：它一开始就没有看到关键材料。

在 Agent 系统里，感知不是一个外围模块，它其实决定了后面所有推理的上限。模型并不是在真实世界里推理，它是在你喂给它的那一小块上下文里推理。它看不到的事实，对它来说就不存在；它看到的噪声太多，也会稀释真正重要的证据。一个中等模型读干净的 30K token，很多时候比最强模型淹在 180K 噪声里更可靠。差距不一定来自模型能力，而是来自它到底看到了什么。

## 感知是 PRA 循环里的入口闸

除了双轴框架那张图，这门课贯穿始终的另一张图是 PRA 循环：Perception、Reasoning、Action，也就是感知、推理、行动。

行动负责把决策变成对外部世界的影响。感知站在另一头，负责把外部世界压缩成模型能处理的上下文。而推理只能加工已经进入上下文的材料，它不能凭空补回没看见的事实。

![](https://static001.geekbang.org/resource/image/8a/e9/8a8bbc33c9e0f39d375df726a2a5eae9.jpg?wh=9280x5572)

很多失败案例的根因都是：

“Agent 不知道 X”的真相，往往是“X 明明存在，但没有进入它的视野”。

这也是为什么长上下文不能简单理解成“仓库越塞越全”。Liu 等人在 TACL 2024 的论文《 Lost in the Middle 》里发现，模型使用长上下文时，对开头和结尾的信息更敏感，中间位置的关键信息更容易被忽略。窗口变长以后，问题不会自动消失，很多时候只是把“没检索到”变成了“检索到了但没用上”。

Anthropic 在 《Effective Context Engineering for AI Agents》 里告诉我们，上下文工程是“在恰当的时刻把恰当的信息放进上下文窗口的精细工艺”。同时也把感知工程师的工作定义为找出“使下一次推理质量最大化的最小高信号 token 集合”。佳哥觉得这个定义对于我们的工作非常有指导意义，所以特别强调一下。

这里可以用一个很简单的例子理解。假设用户问：

这个订单能不能退款？

一个粗糙的感知系统，可能会这样做：

context = search\_docs(query="退款", top\_k=50)

answer = llm(question, context)

看起来很合理。多找一点资料，给模型更多上下文。但问题是，top\_k=50 里可能混着旧版退款政策、无关 FAQ、历史客服话术、其他品类规则。模型不是没能力，而是被放进了一个很脏的信息现场。

更好的感知，不是“多塞”，而是先判断这次推理真正需要什么：

context = \[

order.status,

order.delivered\_at,

user.refund\_history,

current\_refund\_policy,

sku.refund\_exceptions

\]

answer = llm(question, context)

这就是最小高信号 token 集合的意思，不是把所有和“退款”沾边的材料都塞进去，而是把这次判断真正需要的证据放进去。感知工程解决的不是一个简单的“检索多少条”的问题，而是三个更架构化的问题：

什么信息有资格进入上下文？

什么信息应该被压缩、排序或丢弃？

什么信息必须在模型推理前就被结构化出来？

这样再回到 PRA 循环里就很清楚了：Reasoning 的质量，不只取决于模型怎么想，也取决于 Perception 先把一个什么样的世界交给了它。

所以，感知不是普通的预处理步骤。它更像 Agent 系统里的入口闸：哪些事实能进来，按什么顺序进来，以什么颗粒度进来，决定了后面的 Reasoning 有没有可靠材料可用。到了生产系统里，这件事和数据建模、API 设计、容量规划一样，都是架构问题。

## 感知模式组中的四种模式

感知模式组包含如下图所示的四种模式，我们的讲解顺序是上下文分诊 Context Triage、语义压缩 Semantic Compaction、渐进发现 Progressive Discovery 以及多模态融合 Multi-Modal Fusion。

![](https://static001.geekbang.org/resource/image/20/8f/209e319f00c52dddf231cafff593118f.jpg?wh=3500x2461) ![](https://static001.geekbang.org/resource/image/0b/11/0b1b5f81611626d8326a2dc05ce9aa11.jpg?wh=9184x4509)

四讲的顺序可以概括为四个字：选 → 压 → 探 → 融。

![](https://static001.geekbang.org/resource/image/e6/8e/e6b05f9deaac2a02913b2164d068148e.jpg?wh=3202x2349)

第一讲，上下文分诊（Context Triage）。解决的是哪些信息应该进入上下文。不是所有文件、日志、规则都该一股脑儿塞给模型，而是要按 P0/P1/P2/P3 分级，把最关键的信息放到最该出现的位置。

第二讲，语义压缩（Semantic Compaction）。解决的是“进了上下文之后，怎么瘦身”。长任务跑到几十轮之后，对话历史、tool 结果、错误日志都会膨胀，必须压缩，但不能把关键证据压没。

第三讲，渐进发现（Progressive Discovery）。解决的是“我一开始不知道相关信息在哪里”。面对一个陌生代码仓库，Agent 不能把 2000 个文件全读一遍，而要像工程师一样，先广扫，再精读，再沿着调用链深入。

第四讲，多模态融合（Multi-Modal Fusion）。解决的是“图片、表格、日志、PDF、SQL 这些异类信息怎么进入 Agent”。有些内容应该保留为图片，有些内容应该转成文本，有些内容应该先过滤再进入主 Context。

在 2025 到 2026 年间（这真是 Agent 设计沉淀成型的黄金一年），工业界围绕 Agent 如何“看见世界”，其实有很多争论，都可以放进我们的感知模式组里面来探讨。

第一，RAG 还是 Agentic Search？

信息是应该提前建索引、接到任务后检索 top-K，还是让 Agent 像工程师一样，自己搜索、读文件、沿着线索深入？

第二，窗口越大越好吗？

上下文窗口越来越长，但长窗口不等于可以不筛选。问题不是“能不能塞进去”，而是“塞进去之后模型还能不能稳定用好”。

第三，多模态内容保留为图，还是转成文本？

图片、表格、PDF、截图、日志进入 Agent 之前，到底该保留原样，还是先转成结构化文本？这取决于核心信号在空间关系里，还是在文字内容里。

第四，分诊靠人写，还是算法自动？

哪些信息优先进入上下文，是靠人写规则、靠算法自动判断，还是靠 schema 和权限系统强约束？不同场景会有不同答案。

这四个问题你也许有答案，也许还没有答案。接下来的四讲，其实正是围绕它们展开：

上下文分诊，回答什么信息该进来、什么该挡在外面。

语义压缩，回答信息进来之后，怎么变短但不丢关键证据。

渐进发现，回答一开始不知道信息在哪时，Agent 该怎么逐步找。

多模态融合，回答图片、表格、PDF、SQL、日志这些异类信息该怎么进入上下文。

学完这四讲，你会发现所谓“Agent 感知世界”，不是简单地把资料喂给模型，而是在设计一套信息流秩序：什么先看，什么后看，什么压缩，什么保留，什么按需再取。

## Perception Trace：给 Agent 的眼睛装一块仪表盘

在进入四个具体的感知模式之前，我们还要知道一个贯穿整个模块的重要概念：Perception Trace（感知追踪）。

因为很多团队调 Agent 时有一个共同习惯：结果错了，就改 Prompt；再错，就换模型。

但现在我们知道，很多问题既不是 Prompt 的问题，也不是模型的问题，而是 Agent 根本没看到关键材料。

如果没有 Perception Trace，你很难发现这一点。因为最终回答里看不出来 Agent 当时看到了什么、没看到什么。你只能看到结果，却看不到信息是如何进入上下文的。

Perception Trace 要记录的不是模型最后说了什么，而是模型在开始推理之前经历了什么：

读了哪些文件

检索到了哪些内容

选中了哪些片段

丢弃了哪些材料

压缩了哪些历史

调用了哪些发现动作

关键证据最终落在上下文什么位置

如果用户问：订单为什么不能退款？而最终答案错了。这时候普通日志只能看到：

answer = "该订单已超过退款期限"

而 Perception Trace 能告诉你：

检索命中：47 条

进入 context：6 条

被丢弃：41 条

关键证据：

refund\_policy\_v3.md

→ 被排序到第 38 位

→ 未进入 context

实际进入：

refund\_policy\_v1.md

此时核心问题就会暴露的比较清晰。上下文分诊、语义压缩、渐进发现和多模态融合四个模式都在做不同的信息处理动作。但它们最终都会留下同一种痕迹，就是信息从哪里来、为什么进来、为什么被压缩、为什么被丢弃，以及为什么被重新取回。

这些痕迹合在一起，就是 Perception Trace。后面几讲里，我们还会陆续介绍：budget\_usage、dropped\_count、compression\_ratio、p3\_hit\_rate…… 等等不同的感知指标，这些指标本质上都是 Perception Trace 的不同切面。

Perception Trace 就是 Agent 的行车记录仪，虽然它不能让 Agent 更聪明，但它能让工程师知道 Agent 当时到底看见了什么。

## 感知工程不是新瓶装新酒

很多工程师听到“感知工程”，会以为这是 LLM 时代才有的新东西。其实不是，它和我们熟悉的很多工程纪律是同源的。这里的底层问题是在资源有限的情况下，怎么把最有用的信息，放到离计算最近的位置。

数据库查询优化早就在做这件事。我们不会把一张上亿行的表全拉回应用层，再用代码慢慢过滤。工程师会用 WHERE、JOIN、LIMIT，尽量在数据库层就筛掉无关数据，只把真正需要的结果送到应用层。

上下文分诊也是同一个逻辑。Agent 不应该把整个代码仓库、全部文档、所有日志都塞进上下文窗口，而应该先判断：这次推理真正需要哪些信息？哪些必须马上给模型？哪些只是备用，先放在工具或文件系统后面。

再看操作系统的虚拟内存。RAM 很贵，所以只放热数据；磁盘便宜，所以放冷数据。系统不会把所有文件都加载到内存里，而是根据访问频率和任务需要，把最可能用到的东西放到最近的位置。

Agent 的上下文窗口也可以这样理解：P0/P1 优先级的信息相当于热数据，应该直接进入上下文；P2 优先级信息可以压缩后进入；P3 级别的信息就不需要一开始就占窗口，留在数据库、文件系统、搜索工具后面，等模型真的需要时再取。

CDN 缓存也是同一种工程思想。热门内容靠近用户，冷门内容留在源站。这样不是因为源站没用，而是因为每一种信息都有自己的访问成本。Agent 系统里也是一样：高频、稳定、关键的信息，应该离模型更近；低频、长尾、可能无关的信息，不应该一开始就占用 prompt。

甚至编辑工作也在做类似的事。一个成熟的内容编辑，不会把所有采访录音、背景资料、参考文献都原封不动塞进文章里，不加筛选。他会判断哪些是主线，哪些是证据，哪些只是背景，哪些虽然有趣、但会干扰读者理解。感知工程在做的，也是在替模型完成这一步：先把信息整理成一个适合推理的现场。

所以，感知工程不是一套完全陌生的新方法。它本质上是在 LLM 这个新载体上，重新实现数据库、操作系统、缓存系统早就积累过的经验。区别只在于，过去我们优化的是查询计划、内存页面、缓存命中率；现在我们优化的是上下文窗口、attention 预算和推理质量。

离模型越近的信息越贵，所以不能谁都进来。感知工程，就是在决定谁有资格进入模型的工作记忆（也就是认知上下文）。

## 总结一下

上面所有内容其实都回到同一个问题：你的 Agent 到底怎样感知世界？

这个问题并不是 LLM 时代凭空冒出来的。Karpathy 曾有个类比：LLM 像 CPU，上下文窗口像 RAM，文件系统像磁盘。沿着这个类比看，感知就不是 prompt 前面的一点预处理，而是一条完整的信息流 pipeline。

信息从哪里来，经过哪一层筛选，哪些进入上下文，哪些被压缩，哪些被丢弃，哪些留在工具和文件系统后面按需再取——这些决定合在一起，构成了 Agent 眼里的世界。

感知层的错误很容易一路传导到后面。如果某个版本之后，Agent 效果突然下降。团队一开始以为是模型变了，或者 prompt 改坏了，于是反复调 prompt、换模型、改系统指令。但最后 trace 拉出来才发现，真正的问题在更上游：数据源格式变了，原来的分诊规则没有跟上，导致每次都会漏掉一部分关键文件。

这就是感知追踪（Perception Trace）的意义。它通过对信息流的记录让我们知道 Harness 选了啥，Agent 读了啥，关键证据最后落在了上下文的什么位置。后面几讲中我们会介绍一系列的“感知指标”，把“感知决策”变成一个可观察、可度量、可调试的工程对象。

对于 Agent 的感知，原则是：少背 Prompt 术语，多看信息流。

Anthropic 在 2026 年的《 Agentic Coding Trends Report 》里把上下文工程称为 AI 时代开发者最重要的技能转型之一。这个判断背后，其实就是同一个逻辑：未来开发者不只是写代码、写 prompt，还要设计 Agent 的信息流。

最后再强调一次：感知不是预处理，是核心架构问题。它和数据建模、API 设计、容量规划是一个量级的事情。你把它当配菜，Agent 就会在看似聪明的输出里不断漏信号；你把它当主菜，系统才有机会跑得稳、跑得准，也跑得便宜。
