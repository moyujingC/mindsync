在上一讲里，我们顺着机械臂抓取杯子的全过程，把物理世界中的“单帧数据”拆解成了三样核心要素：相机画面、本体实测姿态与期望动作指令。很多刚接触具身智能算法的同学，常常会产生一个想当然的乐观想法：

“既然数据字典已经定义好了，我只要用 Python 写个循环把每一帧数据存下来，是不是就可以直接启动 GPU 开始训练了？”

真实工程的检验，往往会在第一步就暴露出严峻问题：真正跑训练时，最隐蔽、最难查的故障，往往出在数据读取时的时序错位上！

如果在数据加载管道（Data Pipeline）中，读取程序因为索引偏差，把画面与动作指令哪怕仅仅错开了 0.03 秒（一帧），模型在底层学到的物理因果就会完全颠倒：

比如在画面中，夹爪甚至还没有靠近杯身，读出来的动作标签却已经提前发出了闭合指令；

或者杯子在第 50 帧被意外碰歪了，但模型读出来的动作却依然沿着碰歪前的旧轨迹前进。

真机测试时，如果机械臂总是提前合爪，或者动作时快时慢，有人会先改模型结构，或者调整训练时每次更新模型的幅度，这个参数叫学习率。这些调整不一定能解决问题。如果程序把某一时刻的画面配给了另一个时刻的动作，模型学到的对应关系从一开始就是错的。这时应先检查画面、关节状态和动作是否来自同一时刻，再考虑调模型。那么从哪查起呢？

上一讲我们解析的那一帧数据，在磁盘存储中并不是孤立的一个文件。具身智能常用的开源规范 LeRobot Dataset v3.0，采用了一套规范的存储架构：视觉画面被压缩为 MP4 视频流，关节角度与动作指令被保存在结构化数据表中，再通过元数据索引表，把画面帧和关节数值在同一时间线上对应起来。

这一讲，我们沿着 LeRobot 读取数据的过程，重点看两个问题：

给定一条示范中的某一帧，程序怎样从数值表和视频中找到同一时刻的关节状态、动作目标和画面。

弄清这条查找路径后，画面与动作错位时，就能判断应该先核对帧号、时间，还是文件索引。

掌握这套存储与对齐机制，后续在训练和真机部署中排查数据问题时，你才能清楚查出每一行数字和每一帧画面到底是从哪里来的。

## 画面和数字为什么不放在同一个文件里

打开 LeRobot 数据集的磁盘存储目录，你会看到结构清晰的三个核心文件夹：

连续视觉视频库 videos/

结构化时序数值表 data/

硬件与时序索引配置 meta/

很多从纯软件转入具身智能的同学会好奇：为什么不把同一时刻的图片和关节角度直接打包在同一个文件里，而非要拆开存放在三个不同的目录中？

根本原因在于：视觉图像与硬件数值在数据体积、压缩方式和读取方式上有着截然不同的特点。

画面数据体积大且连续：如果把每一帧图片都以非压缩的原始数组保存，几十次示范就会占用数十 GB 的存储空间，导致数据加载时磁盘读取速度严重跟不上，因此图像必须通过视频编码器，压缩为体积更小、更适合流式读取的 MP4 视频文件。

传感器数值轻量且要求快速随机读取：电机的 6 维实测姿态与动作指令都是紧凑的浮点数，模型训练时需要频繁对不同关节进行列切片和批量采样，因此数值数据通常保存在高性能列式存储文件——Parquet（.parquet 后缀）中。

元数据目录记录全局对应关系：meta/ 目录下的 JSON 文件，则记录着每个关节的物理名称、顺序、每次示范在视频中的精确起止时刻，以及在数值表中的起始行号。

这三套文件在读取时分工非常明确。在后续实验中遇到动作异常、文件读取报错或画面与动作不匹配时，可以对照下表快速确定排查方向：

| 到哪里找 | 主要保存什么 | 在这次抓取中回答什么 |
| --- | --- | --- |
| data：数值表 | 每个时刻的状态、动作等记录。 | 当时关节在哪里，操作者给了什么目标？ |
| videos：录像 | 各路相机的连续画面。 | 同一时刻，杯子和夹爪是什么位置？ |
| meta：说明与位置记录 | 字段含义、每次操作从哪到哪，以及数据和视频的位置。 | 这次操作从哪里取，数字和画面怎样对应？ |

在具身数据管理中，有一条重要原则：videos/、data/、meta/ 这三部分必须作为一个整体配套保存，缺一不可！

有些初学者在整理或交接数据集时，误以为只要把体积最大的视频和数值表复制过去就行，忽略了看似简单的 meta/ 目录。这样做会导致严重的后果：虽然数值表依然能用 Pandas 打开，视频播放器也能正常播放画面，但整个数据集已经失去了时间索引与起止边界。读取程序不知道每条示范从哪一秒开始、关节按什么顺序排列，也就无法拼装出可信的训练样本。

下面的全系统对齐架构图，展示了这三部分在底层的配合方式：数值大表与流式视频之所以能在任意时刻准确对应，全靠 meta/ 中记录的物理时间戳与行号指针把两者连接起来。如果元数据中的起始时间出现偏差，程序虽然不会报错，但输入给模型的画面与动作指令就会发生错位。

人眼看连续画面时，很容易认出哪些动作属于同一次操作。但数据读取程序无法从画面里理解操作流程，必须依赖 meta/ 目录中记录的位置信息，去指定文件的指定时刻提取数据。

## 文件名里的编号，不是第几次抓取

假设我们在实验台上，用 SO-101 机械臂连续录制了 50 次杯子抓取示范。初学者直觉上的做法往往是：录一次存一个视频文件，从 01.mp4 一直存到 50.mp4。

在示范次数很少时，这种方式直观易懂。但在实际工程中，一个任务通常包含数百甚至上千次示范，而且每台机械臂通常配备 2~3 路相机。如果每一次示范的每个相机视角都单独保存为一个物理文件，磁盘目录下很快就会产生数以万计的小文件。在模型训练启动多进程数据加载时，频繁打开和关闭大量小文件，会导致严重的磁盘读取瓶颈，拖慢训练速度。

为了解决这个问题，LeRobot Dataset v3.0 规范采用了大文件流式打包机制：数据记录程序会把连续多次的示范过程，顺序追加写入同一个长视频文件（例如 file-000.mp4）和同一张连续数值表中；同时在 meta/ 索引表中，精确记录每一次示范分别是从该视频的第几秒开始、到第几秒结束，以及在数值表中占据了哪几行。

这就带来了一个必须明确的认知：视频文件名中的编号，并不代表这是第几次抓取示范。例如在 file-000.mp4 这个长视频里，可能按顺序包含了第 1 次到第 15 次全部的抓取任务。在 v3.0 规范中，区分不同示范任务的唯一标准，始终是 meta/episodes 中的回合索引 episode\_index。

此外，你在数据集目录中看到的 chunk-000、chunk-001 等文件夹名称，只是文件系统的分卷目录（用于防止单个目录下文件过多影响操作性能）；这一目录分卷，与模型在时序上一次预测的动作块，是完全不同的概念，两者切勿混淆。

## 用行号和视频时间，把同一帧找出来

现在，我们代入具体的工程数值，推导数据加载器在底层是如何把画面与传感器数值从两个独立文件中准确提取出来的。

假设当前训练程序需要提取某次示范中，任务内部相对第 84 步的那一帧数据。在 Python 代码中索引从 0 开始计数，因此该帧在任务内部的局部索引为 frame\_index = 83。

数据加载程序首先查阅 meta/episodes 元数据表，获取该次示范在文件中的物理位置：

数值大表起始全局行号 dataset\_from\_index：假设查出本次示范在全局数值大表中从第 1800 行开始记录；

视频流起始播放时间戳 from\_timestamp：假设查出本次示范在对应的长视频中，是从第 60.0 秒 开始切入的；

相机录制帧率 fps：查阅 meta/info.json 确认该相机的硬件采样频率为每秒 30 帧（30 FPS）。（注：这里的 1800、60.0 和 30 均为方便计算的示例数字，实际排查时请以自己的元数据文件为准）。

拿到这些基础参数后，数据加载程序分别执行两路查找：

第一步：定位关节状态与动作指令（行号计算）。

计算公式为：全局绝对行号 = 示范起始行号 + 任务内部相对帧号。代入数值：1800 + 83 = 1883 行。数据加载程序直接根据行号索引，读取 Parquet 数值表第 1883 行，即可取出该时刻的从臂实测角度 observation.state 以及动作目标 action。

第二步：定位与解码对应相机画面（时间戳计算）。

计算过程分两步：首先计算相对帧号对应的时间跨度：83 帧 ÷ 30 FPS ≈ 2.767 秒；接着加上本次示范在长视频中的起始时间戳：60.0 秒 + 2.767 秒 ≈ 62.767 秒。视频解码器直接跳转到视频文件的 62.767 秒处，解码提取出该瞬间的相机图像。

我们设想一种错误情况：如果数据加载的代码在编写时，截取视频画面时忘记加上起始偏移量 60.0 秒，而是直接拿 2.767 秒 去视频中截取图像——程序在运行时不会抛出任何报错，解码出来的也是一张清晰完整的图像，但这张图像实际上是前一次示范甚至更早之前的历史画面！当这张旧画面与第 1883 行的新动作指令被当成同一时刻的训练样本时，模型就会把错位关系学进去。

下面这段 Python 伪代码，展示了 LeRobot 数据集在底层提取单帧样本的基本逻辑。当有多路相机时，每路相机都有独立的时间戳指针，代码中以单路相机做简明演示：

def get\_dataset\_item(dataset, episode\_index: int, frame\_index: int) -> dict:

"""

遵循 LeRobot Dataset v3.0 规范的样本跨文件绝对寻址与对齐核心逻辑（教学伪代码）

输入参数：

dataset: 数据集实例，包含对数值大表、视频流解压器与元数据的引用

episode\_index: 目标示范的全局回合编号（例如定位第 12 次录制）

frame\_index: 本次抓取任务内部的时间步局部帧号（例如第 83 步）

输出：

时间与物理因果严格对齐的标准单帧训练样本字典

"""

episode\_meta = dataset.meta\_episodes\[episode\_index\]

global\_row\_offset = episode\_meta\["dataset\_from\_index"\]

video\_start\_time = episode\_meta\["from\_timestamp"\]

fps = episode\_meta\["fps"\]

global\_row\_idx = global\_row\_offset + frame\_index

state = dataset.table\["observation.state"\]\[global\_row\_idx\]

action = dataset.table\["action"\]\[global\_row\_idx\]

frame\_timestamp = video\_start\_time + (frame\_index / float(fps))

image = dataset.video\_loader.get\_frame\_at\_timestamp(

video\_path=episode\_meta\["video\_path"\],

timestamp=frame\_timestamp

)

return {

"image": image,

"state": state,

"action": action,

"episode\_index": episode\_index,

"frame\_index": frame\_index

}

在实际的数据集中，任务指令文本通常不会在每行数据中重复保存，而是以整数编号存放在数值表中，程序再通过元数据字典映射为“把桌面上的杯子放入纸盒”等文字说明。

在配置多台相机时需要格外注意：安装在固定机架上的全局主相机，与安装在机械臂末端的手腕相机，在长视频中的起始时间戳通常是各自独立的！即使它们记录的是同一次抓取任务，也不能假设各路视频都在完全相同的一秒切入。

对照下方的时钟对齐图，理解两个关键位置：一个是数值大表从哪一行开始切入，另一个是对应相机的长视频从哪一秒开始切入。只要这两个物理锚点准确，再加上帧号相对偏移，就能准确还原出当时的现场状态。

![](https://static001.geekbang.org/resource/image/98/29/9887eccc102e7df2bac2c86fdda50e29.png)

在日常训练中，上述寻址计算通常由数据加载底层代码自动完成。我们之所以要清楚推导 1883 行与 62.77 秒的换算过程，是为了在真机测试遇到异常动作时，能够直接根据帧号反查当时的物理现场。

例如，当发现机械臂在靠近杯子时提前抓空，我们可以根据发生异常的帧号，换算出对应的视频秒数与数值表绝对行号，调出原始数据进行核对：

画面里的夹爪是否已经对准了杯身？

这一行数值表里的 action 动作目标，写的是张开还是闭合？

全局行号是否存在越界，是否读到了下一次示范的数据？

能够将具体的动作表现追溯到明确的秒数、行号与数值，问题排查就有了确凿的依据，避免无目的地反复重试训练。

## 画面和数字单独看都正常，为什么还可能配错

我们来看一个实际排查中常见的故障：模型在真机上运行时，夹爪总是在还没靠近杯口时就提前闭合。抽检训练集数据时，截取出的相机图片清晰正常，导出的电机角度数值也在合理范围内。如果只检查到这一步就停止，很可能忽略了“假对齐”的问题：图片和数值单独看都正常，但在时序上可能被配到了不同的时刻。

排查这种问题，建议分两步进行：

第一步：排查数据读取寻址是否发生偏移。在原始录制视频中，找到夹爪接触杯壁的那一瞬间画面；再用数据加载代码，读取对应时刻的单帧样本，确认读取出的图片是否与视频画面完全一致。如果对不上，通常是元数据 meta/episodes 中的 from\_timestamp 记录有偏差，或者示范起止行号计算有误。

第二步：排查硬件采集时钟是否发生漂移。如果读取代码提取出的画面完全正确，数值表记录此时夹爪正在合拢，但画面里的夹爪却处于完全张开状态，这说明在硬件录制阶段，相机取图线程与电机数据读取线程之间就存在时间不同步。

同时需要注意：电机的控制指令发出后，机械臂转动到位需要一定的时间，存在物理延迟。因此，不能将电机的当前状态与下发的目标角度混为一谈。通过分步排查，才能明确究竟是数据读取时算错了时间点，还是录制阶段硬件时间戳本身就存在偏差。

此外，我们在第 06 讲中强调过：即使两份数据集的关节数组长度相同（都是 6 维浮点数），相同位置的数字也不一定代表同一个电机。例如在 A 数据集里第 1 个数代表底座旋转，而在 B 数据集里第 1 个数可能代表手腕关节；单位也可能一个是弧度制，另一个是角度制。

在合并不同批次的数据集前，必须打开 meta/info.json 逐项核对：关节名称、排列顺序、物理单位，以及控制指令采用的是绝对目标还是相对增量；以及在 meta/stats.json 中是否保存着数据归一化所用的均值与标准差。如果加载了不匹配的统计参数表，模型输出就会被还原为错误的物理角度。明确两者的分工：硬件对应关系查 meta/info.json，数据归一化换算查 meta/stats.json。

## 连续取动作时，不要读进下一次操作

提取完单帧数据后，下一步需要处理连续动作块的读取。

策略模型在训练时，通常需要接收未来连续多步的动作序列。如果数据截取逻辑没有设置边界保护，就容易产生跨任务的数据混淆。

我们来看一个具体的例子：假设某次抓取示范在数值表中从第 1800 行开始记录，总共有 150 帧数据，因此本次示范的最后一行索引是：1800 + 150 − 1 = 1949 行。如果训练采样时刚好抽到了第 148 步（索引 frame\_index = 147），并要求向后连续截取 8 个时间步的动作块。

如果代码没有设置示范结束边界的保护，切片逻辑就会顺序读取第 1947 到 1954 行：

前面的第 1947、1948、1949 行属于本次抓取的真实动作；

但随后的第 1950 到 1954 行，已经超出了本次示范的范围，读取到了下一次示范的开头内容。

下一次示范，通常是操作人员把杯子摆回原位后重新开始的。如果把下一次开头的动作拼接在当前示范的结尾，模型就会学到一种不合常理的动作序列：杯子抓到一半，机械臂突然快速跳回初始位置重新下探。

为了防止这种跨任务的数据混淆，数据读取管道需要执行边界截断与合规补齐（Padding）：

当向后截取的动作序列，超出了本次示范的结束边界时，停止读取后续数据；

将本次示范最后一步的真实动作（第 1949 行）复制填充到剩余的空缺槽位中；

在掩码列表（如 action\_is\_pad）中，把这些填充位置标记为 True，告知训练损失函数在计算梯度时忽略这些填充位。

补齐与跨任务拼接，在张量形状上都能凑够 8 步动作，但两者的意义完全不同：前者保持了单次任务的物理边界，后者则引入了错误的动作因果。检查数据加载逻辑时，不仅要看输出张量的形状，还要核实末尾数据的来源以及掩码是否被正确使用。

## 别人的文件不是这套格式时，先用一次操作试转

在实际工程中，我们常常会收到外部团队交付的数据，或者使用开源生态中的非标记录。处理这些数据时，一个常见的误区是：只要能把文件读进内存，把字段名改成 LeRobot 的格式就算转换完成了。

以 LeRobot 本身的文件格式演进为例：早期版本采用单次示范分散存储的方式，而 v3.0 版本转向了多次示范打包的存储结构。两者的区别不只是文件后缀不同，元数据索引的寻址逻辑也完全不同。单靠修改文件扩展名或版本号字符串，并不能自动解决数据对齐的问题。

转换外部数据时，建议按这个流程核对：先保留原始数据作为备份，不要直接在原文件上修改。先拿一条示范试着转成 LeRobot 格式，在这条示范里挑三个好认的瞬间——夹爪开始下探、夹爪碰到物体、物体被抬离桌面。逐帧对比转换前后：画面、关节角度、时间戳是否对上同一时刻。核对通过了，再批量转换全部数据。

下方的结构变化示意图，展示了两种存储方式的差异：分散存储会产生大量小文件，而大文件流式存储则把定位信息的职责交给了元数据索引表。元数据中的时间戳如果记录不准，就会直接影响后续的动作对齐。

![](https://static001.geekbang.org/resource/image/2e/94/2e165d5141a0e5c88de33d9731731094.png)

在日常开发与跨平台协作中，你还会遇到其他主流的机器人数据格式：

LeRobot 与 Google RLDS 格式：均已按照任务回合（Episode）将视觉画面、关节姿态与动作指令整理在一起，通常可以直接对接主流具身策略模型的训练流程；RLDS 是 Google 生态常用的回合数据格式，与 LeRobot 的目录划分不同，但两者按操作组织的思路是一致的。

HDF5 格式（.h5 /.hdf5 后缀）：属于通用的多维科学计算数据容器。使用 HDF5 数据前，必须首先查明文档：图像保存的是原始压缩二进制流，还是解压后的数组？动作数据在导出前是否已经提前做过了归一化处理？

ROS / ROS2 原生数据包（.bag /.db3 后缀）：记录的是机器人各传感器在系统总线上各自发布的异步原始消息流。由于摄像头拍照的节奏，和电机驱动板的读角度、执行目标的节奏通常对不齐，直接拿来训练容易导致动作紊乱；使用前必须按各路传感器的时间戳，在相邻采样点之间均匀补齐中间时刻的数值，再重新采样成固定频率的回合格式。

拿到任何外部格式的数据集时，核心标准始终一致：确认能否从这份数据中，准确还原出同一次示范在同一时刻的真实画面与真实动作。如果这一步做不到，数据文件体积再大也无法直接用于训练。

如果拿到其他系统导出的数据，切忌仅仅根据文件后缀盲目编写脚本。建议按照以下顺序排查：

先查时间对齐：先挑选一条记录，检查能否按单次操作对应上同一时刻的视觉画面、关节位置与动作指令。如果对不上，往往不是格式问题，而是各路传感器的时间戳起点没有对齐。

区分处理失误与采集缺失：保留原始文件至关重要。如果是转换代码算错了时间起点，修正代码后可以重新配对；但如果在录制现场本身就因为卡顿丢掉了关键动作画面，无论怎么转换格式，也无法凭空恢复缺失的数据。先分清是脚本转换错误，还是现场录制缺失，再决定是重新转换数据，还是回到实验台重新录制。

## 小结

这一讲我们梳理了具身智能多模态数据在磁盘上的存储与读取逻辑：读取程序，是根据元数据中记录的任务起止位置，一方面从数值表中按行号查找关节姿态与动作指令，另一方面从长视频中按时间戳截取对应时刻的画面。

当面对多个示范保存在同一个长视频中的结构时，核心是认清元数据中的 episode\_index、起始行号与视频时间戳，不要把视频文件的编号误当成示范序号。

建议你亲手核对一次单帧数据的读取：挑选一段具体的示范，计算某一步在数值表中的行号以及在视频中的时间点，调出画面与角度数据进行核对。掌握这条查找逻辑，遇到数据错位或时钟不同步等问题时，就能顺着行号和时间戳快速找到原因。

完成了数据存储与格式对齐之后，接下来的关键问题是：看记录下来的操作示范，判断动作质量是否符合训练要求？如果操作过程中机械臂出现了停顿、抖动或碰歪物体的情况，哪些数据可以保留、哪些必须作废？下一讲，我们将进入遥操作数据采集现场，讨论如何建立规范的示范质量判定标准。
