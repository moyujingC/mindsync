### 414. 如果面试官问“什么才算真正的 Agent”，你怎么回答？ > 📘 **对应课程**：基础 01 深挖 > 概念层面，真正的 Agent 不是“会聊天的模型”，而是能在目标约束下理解任务、使用工具、读取外部观察结果、更新状态并决定下一步的系统。普通 LLM 应用偏单轮生成，Chatbot 偏对话体验，Agent 则强调行动能力和执行循环。 工程层面，Agent 至少要把模型、消息、工具、上下文、状态、停止条件、错误处理和人工边界组织起来。工具不是装饰，必须有参数 schema、权限校验和安全返回；执行循环也不能无限跑，要有 final answer、iteration limit、tool error fallback 和 human handoff。 项目关联上，小哲电商客服 Agent 不是直接让模型回答所有客服问题。它把稳定知识交给 RAG，把实时订单物流交给 Tool，把退款退货交给 Workflow / HITL，把 Trace 和 Evaluation 作为证据链。这样才能从“答得像客服”变成“按业务边界处理客服”。 边界上，不能说 Agent 可以替代所有后端逻辑，也不能说用了工具就天然安全。高风险写操作、权限判断、审批责任和资金动作仍然要由确定性系统、业务接口和人工确认兜住。 ### 415. 为什么模型与消息结构是 Agent 的底座？ > 📘 **对应课程**：基础 02 深挖 > 概念层面，消息结构把输入从一整段字符串拆成有角色的上下文。SystemMessage 定义角色、任务和边界，HumanMessage 表示用户本轮诉求，AIMessage 表示模型回答或工具调用意图，ToolMessage 把工具结果交回模型。 工程层面，消息结构能让系统稳定追踪 tool_call_id、usage_metadata、response_metadata 和多轮历史。工具结果如果被当作用户输入，模型会误解来源；历史消息无限传入，会造成成本和上下文污染；忽略 tool_call_id，会导致工具调用和工具返回对不上。 项目关联上，小哲项目早期就用 messages 区分公司边界、用户诉求和模型回复。后面 RAG 片段、Tool Observation、Runtime Context 和公开 Trace 都依赖来源清楚的消息结构，否则很难解释一段回答到底依据什么。 边界上，SystemMessage 不是保险箱。它能提高模型遵守规则的概率，但不能替代业务事实查询、工具权限、人工审批和运行验证。 ### 416. Agent loop 为什么必须有停止条件和人工边界？ > 📘 **对应课程**：基础 03 深挖 > 概念层面，Agent loop 是“模型判断 -> 工具调用 -> 观察结果 -> 再判断或回答”的循环。它让模型不再只生成文本，而是可以围绕任务逐步行动。 工程层面，循环必须有停止条件：模型已经能回答、达到最大迭代次数、工具失败进入兜底、触发人工接管。没有停止条件会导致无限调用工具；没有错误处理会把接口异常包装成业务结论；没有人工边界会让高风险动作被模型继续推进。 项目关联上，小哲电商中物流查询可以走一次 Tool Observation 后回答；退款问题不能只靠循环多跑几步，而要切入 Workflow / HITL。工具结果也不能直接当最终回答，需要模型在客服口径和风险边界下组织自然语言。 边界上，Agent loop 不是让模型自由做所有决定。工具、权限、审批、停止条件和可观测性必须一起设计。 ### 417. 为什么项目开始前要先画 Agent 场景地图？ > 📘 **对应课程**：基础 04 深挖 > 概念层面，场景地图是把业务问题按数据来源、动作风险和处理方式分类。它通常把任务分成直接回答、查知识库、查工具、人工确认、不适合 Agent 几类。 工程层面，分类依据不是关键词，而是背后的事实来源和风险边界。稳定知识走 RAG，实时事实走 Tool，高风险动作走 HITL，不适合自动化的动作拒绝或转人工。这样后续路由、工具目录、权限设计和 eval case 才有统一边界。 项目关联上，小哲电商里“发票多久开”是 RAG，“订单到哪了”是 Tool，“直接退款”是 Workflow / HITL，“查别人订单”是权限拒绝。这个地图后来会落成 TaskPlanner / RoutePlan。 边界上，不要把所有客服问题当成一类，也不要一开始就设计多 Agent。先把任务类型和风险级别分清，系统会更稳。 ### 418. Prompt 角色边界应该如何设计，为什么它不是唯一安全机制？ > 📘 **对应课程**：基础 05 深挖 > 概念层面，Prompt 角色边界定义模型是谁、服务谁、事实优先级是什么、哪些话不能说、信息不足时怎么处理。它不是营销文案，而是模型行为边界的一部分。 工程层面，SystemMessage 应放角色、任务、禁止事项、事实来源和拒答规则，HumanMessage 只放用户问题。高风险承诺要分支处理：不直接承诺退款、赔付、发货时间或活动核销，而是说明限制、查事实或转人工。 项目关联上，小哲客服 Agent 的 Prompt 要说明自己是小哲电商公司的客服 Agent，不能承诺优惠、退款、物流和赔偿结果。后续 Prompt Registry 会把这些边界拆成可维护片段。 边界上，Prompt 不能替代权限系统、业务接口和 HITL。用户可以诱导模型，RAG 或工具文本也可能带脏指令，所以真正安全要靠 Prompt、上下文隔离、工具权限和业务流程共同完成。 ### 419. 上下文工程为什么不是“把信息塞全”？ > 📘 **对应课程**：基础 06 深挖 > 概念层面，上下文工程是选择、排序、压缩、隔离和标注模型当前能看到的信息。它要解决的是“模型看到了什么、没看到什么、哪些信息可信、哪些信息可能污染回答”。 工程层面，Model context、Tool context、State、Runtime context 各有边界。工具结果不能原样塞给模型，隐私信息不能随意传递，旧上下文不能覆盖新事实，所有历史也不能无限追加。 项目关联上，小哲项目到中后期会同时有历史消息、RAG 片段、Tool Observation、Workflow State、Runtime Context 和安全结果。Context Builder 要按来源、可信度、优先级和预算重新组织它们。 边界上，上下文不足会让模型猜，上下文过多会让模型混乱。上下文工程追求的是“足够且可信”，不是“越多越好”。 ### 420. 结构化输出为什么是系统契约，而不是格式美化？ > 📘 **对应课程**：基础 07 深挖 > 概念层面，结构化输出把自然语言变成可校验、可处理的数据，例如 intent、risk_level、next_action、citations、tool_calls、workflow 状态。它让系统不再依赖人工读一段回答来判断状态。 工程层面，schema 要定义字段名、类型、枚举、必填项和描述。模型输出不符合 schema 时要进入校验错误、重试、降级或人工处理，不能直接驱动业务程序。 项目关联上，小哲项目中用 IntentResult 把“咨询退款还是投诉”变成结构化意图，后续 RoutePlan、ApprovalRequest、EvalReport 都是同类思想：让模型参与判断，但输出必须落回系统契约。 边界上，结构化输出只是“系统读懂了模型判断”，不等于业务动作已经完成。`refund_request` 不代表退款批准，`complaint` 不代表已转人工。 ### 421. Streaming 在 Agent 系统里应该展示什么？ > 📘 **对应课程**：基础 08 深挖 > 概念层面，Streaming 不只是逐字显示回复，还包括 Agent 进度流。`messages` 更偏 token 流，`updates` 更偏节点状态变化，`custom` 可以展示工具内部进度。 工程层面，客服工作台需要知道 Agent 正在检索知识、调用工具、等待审批还是进入降级。过程流要控制可见内容，不能暴露工具参数、系统提示词、权限信息或内部错误栈。 项目关联上，小哲 前端工作台后期展示的不是“回答正在生成”这么简单，而是 `tool_calls`、citations、workflow、trace、cost 等观察信号。它帮助你证明路径正确。 边界上，Streaming 不是性能优化。它解决的是体验和可观察过程，但所有未校验内容都不能过早当作最终业务结论展示。 ### 422. Tool Calling 的面试重点不只是会写 `@tool`，还要讲什么？ > 📘 **对应课程**：基础 09 深挖 > 概念层面，Tool Calling 让模型提出工具调用请求，通过外部工具获取实时事实或执行受控计算。它是 Agent 从“回答”走向“行动”的关键能力。 工程层面，要讲工具名、description、docstring、参数 schema、Pydantic / JSON Schema、ToolRuntime、ToolNode、tools_condition、返回值和错误处理。工具名要清晰，描述要写边界，schema 要告诉模型能传什么，也告诉后端要检查什么。 项目关联上，小哲订单物流、库存价格、售后状态都必须走工具。模型可以生成 tool_calls，但执行层要用 Runtime Context 校验当前用户和订单归属。 边界上，Tool Calling 不能替代权限、审批、审计和错误处理。写操作、高风险动作和敏感数据访问必须收紧。 ### 423. 工具错误处理为什么要设计成业务可理解的返回？ > 📘 **对应课程**：基础 10 深挖 > 概念层面，工具错误不是单一异常，而是参数错误、业务对象不存在、接口超时、权限不足、规则不允许等不同情况。不同错误要进入不同分支。 工程层面，可预期业务错误要转成结构化结果或模型可理解的错误 observation，而不是把 HTTP stack trace、数据库错误、内部接口地址返回给用户。`ToolNode(handle_tool_errors=...)` 可以兜底，但不能替代业务错误设计。 项目关联上，小哲物流工具超时应触发降级，订单不存在应提示用户核对订单号，权限不足应拒绝查询，退款写动作失败不能盲目重试。 边界上，不要把所有失败都说成“系统繁忙”。错误越清晰，Agent 越能决定 ask_user、retry、deny、fallback 还是 transfer_to_human。 ### 424. ToolRuntime、State、Context、Store 为什么不能混用？ > 📘 **对应课程**：基础 11 深挖 > 概念层面，ToolRuntime 让工具访问运行时能力；State 是图运行中的可变共享数据，Context 是本次运行传入的不可变配置，Store 是跨会话长期保存的数据。 工程层面，State 适合保存本次流程中的订单、节点历史和中间结果；Context 适合保存 user_id、tenant_id、channel 等运行参数；Store 适合保存长期偏好，但要有隐私控制。ToolRuntime 不应该暴露给模型。 项目关联上，小哲工具调用时可以从 Context 拿当前用户身份，从 State 看流程状态，从 Store 查低风险偏好。但不能把敏感长期偏好直接塞进短期消息，也不能让模型自己编 runtime 字段。 边界上，混用会导致权限错位、隐私泄露和流程状态污染。要主动讲清三者生命周期和可见范围。 ### 425. `create_agent` 能帮你到哪一步，不能帮你到哪一步？ > 📘 **对应课程**：基础 12 深挖 > 概念层面，`create_agent` 把 model、tools、system_prompt 组装成一个最小 Agent，让模型能判断是否调用工具并组织回答。 工程层面，它适合快速跑通模型和工具闭环，也能返回 messages 供观察。但完整业务系统还需要鉴权、错误处理、数据映射、安全边界、RAG、Workflow、Trace、Evaluation 和成本治理。 项目关联上，小哲早期可以用 `create_agent` 处理订单查询类轻路径，但退款和审批不能直接交给最小 Agent。后期高风险流程要进入 LangGraph / HITL。 边界上，system_prompt 不要写动态事实，工具描述不要含糊，不能只看最终回答而忽略中间工具消息。 ### 426. 为什么 RAG 不是“外挂知识库”这么简单？ > 📘 **对应课程**：基础 13 深挖 > 概念层面，RAG 是检索增强生成：把外部知识切成文档、embedding 或索引后，根据问题检索相关片段，再让模型基于片段回答。 工程层面，RAG 要处理数据加载、chunk、metadata、retriever、引用、更新和低置信兜底。它和长 Prompt 的区别在于按需检索、来源可追踪、知识可更新。 项目关联上，小哲售后政策、FAQ、活动规则适合 RAG；订单、物流、库存不适合 RAG，因为它们是实时事实。 边界上，RAG 不是不会幻觉的保证。不保留来源、知识库长期不更新、检索命中错误，都会让回答出问题。 ### 427. 文档切片和 metadata 怎样影响最终回答？ > 📘 **对应课程**：基础 14 深挖 > 概念层面，切片把长文档拆成可检索单元，metadata 给每段知识贴来源、章节、版本、品类、时间等标签。 工程层面，chunk size 决定单片长度，overlap 保留跨边界语义。机械按字数切所有文档容易把条件和结论拆开；丢失来源会导致 citation 不可用；新旧版本混在一起会让模型引用过期规则。 项目关联上，小哲售后知识要按“签收后 7 天无理由退货”“质量问题售后”“赠品缺失”等业务章节先切，再用长度兜底，metadata 标明 policy_type、effective_status 和 source。 边界上，切片参数没有万能值。要用固定问题集验证召回是否真的更准。 ### 428. RAG 防幻觉的核心机制有哪些？ > 📘 **对应课程**：基础 15 深挖 > 概念层面，RAG 防幻觉不是让模型“更听话”，而是让回答必须基于检索资料，并在资料不足时承认不确定。 工程层面，要有 citations、top-k 控制、score threshold、低置信兜底、冲突资料处理和间接 Prompt Injection 防护。引用不能只写“根据资料”，要能回到具体来源。 项目关联上，小哲活动叠券、售后退货、发票规则这类证据型问题必须有 citation；没有命中时要明确没有可靠依据或转人工。 边界上，top-k 不是越大越好，引用也不代表一定正确。引用只说明“有依据”，还要看依据是否适用于当前条件。 ### 429. Agentic RAG、Hybrid RAG 和普通 RAG 怎么区分？ > 📘 **对应课程**：基础 16 深挖 > 概念层面，普通 2-step RAG 是固定检索再生成；Hybrid RAG 在固定流程中结合向量、关键词、规则路由；Agentic RAG 让 Agent 决定何时检索、是否改写、是否继续检索。 工程层面，Agentic RAG 会增加节点、分支、判断和错误路径，需要文档相关性判断、查询改写、检索工具和 trace 支撑。它不是所有知识问答的默认选择。 项目关联上，小哲项目先从基础 RAG、query rewrite、rerank、Hybrid RAG 逐步升级，再在复杂问题里引入更智能的检索决策。 边界上，简单 FAQ 不要过度 Agentic。只有问题需要判断、追问、改写和多步检索时，再考虑更复杂链路。 ### 430. 短期记忆为什么必须有 thread 隔离？ > 📘 **对应课程**：基础 17 深挖 > 概念层面，短期记忆让 Agent 在同一会话里接住上下文，例如“刚才那个订单”“这款商品”。thread 是短期记忆的隔离单位。 工程层面，checkpointer 保存 thread 状态；消息历史要裁剪和摘要，不能无限传给模型；短期记忆不是长期用户画像。 项目关联上，小哲 Session Memory 可以保存最近订单、最近商品、最近意图，辅助消歧。但物流状态、退款资格、审批状态仍要重新查工具或 workflow。 边界上，所有用户共享同一个历史是严重隐私错误；把所有历史永久塞给模型会带来成本、污染和权限风险。 ### 431. 长期记忆为什么先讲隐私边界？ > 📘 **对应课程**：基础 18 深挖 > 概念层面，长期记忆保存跨会话信息，例如用户偏好、稳定事实或经验记录。它比短期记忆影响更久，因此隐私风险更高。 工程层面，长期记忆通常用 Store、namespace、key 存储。写入前要判断是否必要、是否低风险、是否用户授权、是否可修改删除、是否会影响高风险决策。 项目关联上，小哲可以保存“偏好通勤耳机、预算 300 到 800”这类低风险偏好，但不能随意保存身份证、支付凭证、投诉敏感内容或高风险售后判断。 边界上，长期记忆不是越多越好。跨用户 namespace 设计错误、没有删除机制、把聊天历史全当长期记忆，都会造成隐私和合规风险。 ### 432. Runtime Context 为什么要和 model context 分开？ > 📘 **对应课程**：基础 19 深挖 > 概念层面，Runtime Context 是应用层在本次运行传入的可信上下文，例如 user_id、tenant_id、channel、role。Model context 是模型可见的消息和提示词。 工程层面，runtime context 可以通过 context_schema 和 ToolRuntime.context 给工具使用。敏感身份和权限字段不应让模型自由生成，也不应全部写进 system prompt。 项目关联上，小哲查询订单时必须用 Runtime Context 里的当前用户判断归属，而不是用户说“我是 U9999”。模型可以看到脱敏摘要，但工具执行用完整可信字段。 边界上，Runtime Context 不是权限系统本身，但它是权限校验的输入。真正的权限判断还要在业务后端执行。 ### 433. 为什么复杂流程要用 LangGraph，而不是继续堆 Agent loop？ > 📘 **对应课程**：基础 20 深挖 > 概念层面，LangGraph 用状态机表达可控、可恢复的 Agent 流程。它关注状态、节点、边、分支、持久化和人工确认。 工程层面，复杂客服流程往往有明确顺序：查订单、查政策、判断资格、人工确认、恢复提交。用图能让每一步可测试、可观察、可恢复。 项目关联上，小哲退款、退货和审批恢复都属于强顺序、高风险流程。自由 Agent 适合轻路径探索，不适合掌控资金和权益动作。 边界上，不是所有问题都要 LangGraph。简单问答、单次工具查询不一定需要图，避免把系统做重。 ### 434. State、Node、Edge、Reducer 和 Command 分别解决什么？ > 📘 **对应课程**：基础 21 深挖 > 概念层面，State 是图的共享数据结构，Node 做一步处理，Edge 决定执行顺序，条件边决定分支，Reducer 合并状态更新，Command 可以同时更新状态并路由。 工程层面，节点应该职责单一，边表达流程逻辑，状态只保存跨节点需要的数据。并发或多节点写同一字段时需要 reducer，避免覆盖。 项目关联上，小哲售后流程里，State 保存订单、政策、风险和审批状态；节点分别查订单、查规则、判断资格；条件边根据状态决定继续、拒绝或等待人工。 边界上，不要把聊天历史、临时变量、隐藏推理全部塞进 State。公开 workflow 状态是流程事实，不是模型思维链。 ### 435. Functional API 和 Graph API 的面试取舍怎么讲？ > 📘 **对应课程**：基础 22 深挖 > 概念层面，Functional API 用 `@entrypoint` 和 `@task` 组织函数式工作流，Graph API 用节点和边表达流程图。 工程层面，`@task` 可持久化独立步骤，resume 可以避免重复执行已完成工作；但任务必须可序列化，非幂等副作用要谨慎。需要清晰流程图、节点边界和复杂路由时，Graph API 更直观。 项目关联上，小哲退款审批这类流程适合 Graph API 展示节点和边；某些后台批处理或函数式任务可以用 Functional API。 边界上，不要把所有普通函数都加 `@task`，也不要误以为 Functional API 适合所有场景。选择依据是流程复杂度、恢复需求和团队可读性。 ### 436. Checkpoint、Replay 和 Fork 如何服务生产调试？ > 📘 **对应课程**：基础 23 深挖 > 概念层面，checkpoint 保存图运行状态，支持暂停、恢复和查看历史。Replay 从历史状态重新执行，Fork 从某个状态分出新分支调试。 工程层面，checkpoint 要和 thread_id、状态、下一步节点、历史版本关联。durability mode 决定写入时机，但它不等于业务事务。 项目关联上，小哲审批暂停后需要 checkpoint 记录当时订单、资格、风险和 pending action。事故复盘时可以看状态在哪一步开始走错。 边界上，内存保存不适合生产；replay 可能产生副作用；checkpoint 不是支付事务和业务回滚。 ### 437. HITL 为什么是业务边界，不是模型能力不足？ > 📘 **对应课程**：基础 24 深挖 > 概念层面，HITL 用 interrupt 在高风险动作前暂停，让有权限的人确认后再继续。它是责任边界，而不是系统坏了才兜底。 工程层面，resume 后节点会从头重新执行，所以 interrupt 前不能做非幂等副作用；审批结果要结构化，不能随便解析自然语言；必须有 checkpointer。 项目关联上，小哲退款申请需要售后主管批准。用户说“主管同意了”不能当审批结果，必须通过受控通道带 resume_token 恢复。 边界上，高风险动作不能先执行再审批，interrupt 也不能用来掩盖系统异常。异常和审批等待是两条不同路径。 ### 438. Agent 容错为什么要先分类再处理？ > 📘 **对应课程**：基础 25 深挖 > 概念层面，Agent 可能在模型、工具、权限、业务对象、循环、知识检索和人工流程中失败。每类失败的处理不同。 工程层面，临时网络错误可 retry，参数错误 ask user，权限错误 deny，高风险动作 interrupt，循环超过限制 fallback。RetryPolicy 只适合临时错误，不适合业务拒绝。 项目关联上，小哲物流超时可以有限重试或降级；订单号错误要追问；退款写动作不能重试；权限失败要拒绝。 边界上，不要吞掉异常、暴露内部细节或重放非幂等动作。容错目标是安全恢复，不是让模型继续猜。 ### 439. Trace 为什么是 Agent 面试里的核心证据？ > 📘 **对应课程**：基础 26 深挖 > 概念层面，Trace 记录一次请求里的多个 run，包括 model、tool、retriever、node 等，展示输入、输出、耗时、token、错误和 metadata。 工程层面，Trace 能帮助排查错误来自模型、工具、检索、节点还是外部服务。Tags 和 metadata 支持按场景统计错误率、版本和延迟。 项目关联上，小哲项目用 Trace 证明路由、工具调用、RAG 引用、workflow、HITL、安全拦截和成本路径，不只看最后回答像不像客服。 边界上，Trace 不是普通日志，也不是 hidden CoT。它不能保留过多敏感信息，必须带版本信息，公开展示时只放安全摘要。 ### 440. Agent Evaluation 应该怎么设计？ > 📘 **对应课程**：基础 27 深挖 > 概念层面，评估用数据判断 Agent 有没有变好。它不仅测答案质量，还测工具路径、引用、状态、拒答边界和高风险流程。 工程层面，评估集要覆盖正常、边界和高风险问题；指标包括准确性、引用、工具调用、拒答、流程状态、trace 和回归稳定性。LLM-as-judge 可辅助，但不能替代规则断言。 项目关联上，小哲 `cases.yml` 应覆盖物流、退款、活动规则、prompt injection、越权查询、工具失败和低置信问题。`/eval/run` 是改 Prompt、改工具和改 RAG 后的门禁。 边界上，不要只手测成功样例，不要只看平均分。平均分可能掩盖退款、隐私和越权这类严重错误。 ### 441. MCP 接入外部工具前为什么先讲安全边界？ > 📘 **对应课程**：基础 28 深挖 > 概念层面，MCP 标准化 tools、resources、prompts 的接入，让不同客户端和 Agent 更容易复用外部能力。 工程层面，MCP server 暴露能力前要定义认证、授权、参数校验、PII 处理、审计日志、错误返回和高风险工具审批。客户端、Agent、server 任何一层都不能单独被信任。 项目关联上，小哲后期把物流、库存、退款进度等能力做成 MCP-style 目录时，也要绑定 Resource 边界和 Prompt 口径。 边界上，MCP 是接入协议，不是自动安全通道。安全边界不能只靠提示词，必须有代码级权限和工具级校验。 ### 442. Claude Code 工程化心智模型和业务 Agent 有什么关系？ > 📘 **对应课程**：基础 29 深挖 > 概念层面，Claude Code 展示了工程任务中的 agentic loop：理解目标、读取项目上下文、制定计划、调用工具、修改或分析、验证结果、汇报总结。 工程层面，它强调 context window、permissions、checkpoints、resume / fork 和验证闭环。复杂系统里，跳过上下文探索会导致错误修改，没有验证闭环就无法证明任务完成。 项目关联上，小哲客服 Agent 的开发同样需要先读现有架构、找业务边界、改代码、跑测试、看 trace 和总结剩余风险。它不是一次性生成代码，而是受控协作。 边界上，checkpoint 不是业务回滚，Claude Code 也不是更强聊天窗口。它的价值在工具、上下文和验证闭环。 ### 443. 项目记忆适合保存什么，不适合保存什么？ > 📘 **对应课程**：基础 30 深挖 > 概念层面，项目记忆保存长期工程规则、业务边界、测试命令、架构说明和用户偏好，帮助 Agent 在多次任务中保持一致。 工程层面，可以用类似 CLAUDE.md、rules、auto memory、Skills 组织项目上下文。Compaction 可以压缩长上下文，但必须保留关键约定和验证要求。 项目关联上，小哲项目记忆可以记录“退款高风险动作必须 HITL”“修改工具后要验证订单查询和拒答边界”“使用小哲电商公司品牌口径”。 边界上，不能把实时事实、敏感信息、密钥和用户隐私写入项目记忆，也不能把项目记忆当成无需验证的强制当前事实。 ### 444. 工具权限、沙箱和 Prompt Injection 的关系是什么？ > 📘 **对应课程**：基础 31 深挖 > 概念层面，工具让 Agent 有行动能力，权限和沙箱限制它能做什么、在哪里做、是否需要人工确认。Prompt Injection 发生在模型理解层，沙箱发生在工具执行层。 工程层面，Permission rules 要区分 allow、deny 和细粒度控制；Permission mode 决定是否自动执行或人工确认；沙箱限制文件系统、网络和子进程访问。 项目关联上，小哲订单查询、退款申请、管理后台修改属于不同风险级别。模型不能填写 user_id 或 role，退款和权限变更必须有审批和审计。 边界上，沙箱不能识别所有恶意指令，也不能替代业务权限。它能降低工具执行破坏范围，但高风险动作仍需要审批。 ### 445. Hooks、Skills、MCP 为什么要分层，而不是都写进 Prompt？ > 📘 **对应课程**：基础 32 深挖 > 概念层面，Prompt 管模型行为边界，Skills 封装专门任务能力，MCP 连接外部工具和数据源，Hooks 在生命周期事件中做拦截和自动化治理。 工程层面，Hooks 可以在 SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop 等事件上做输入检查、工具前审批、结果处理、错误拦截和完成审计。 项目关联上，小哲工具治理适合用 Hooks 做脱敏、降级、审计和成本记录；工具复用适合 MCP-style 目录；课程生成和面试辅助可以做成 Skill。 边界上，不能用 Prompt 代替工具、用 Skill 代替权限、用 MCP 代替业务流程，也不能把必须执行的安全规则写成可选 Skill。 ### 446. 什么时候该拆 Subagents，什么时候不该拆？ > 📘 **对应课程**：基础 33 深挖 > 概念层面，Subagents 适合职责清晰、上下文独立、工具权限不同、可委派的任务。它不是为了显得高级而拆。 工程层面，主 Agent 要决定是否委派，子 Agent 要有结构化输入输出、独立权限、上下文隔离、trace 汇总和失败回收。Subgraph 和 Subagent 也不完全等同：前者偏图内部结构，后者偏协作角色。 项目关联上，小哲未来可以把知识质检、售后审核、运营活动规则维护、客服质检拆成不同助手，但前提是职责、权限和归因链路清楚。 边界上，多 Agent 会增加调试难度、成本和权限面。所有子 Agent 共享同一套工具、输出不验证、用多 Agent 掩盖流程不清晰，都会让系统更不可靠。
