这一部分不是按课次复述，而是把课程里反复出现、面试最容易追问、也最能体现项目经验的知识点整理成可检索卡片。每张卡都按“考察点 -> 知识解释 -> 小哲项目经验 -> 回答模板 -> 追问展开 -> 避坑”组织。 ### 493. 卡片 01：Agent 不是聊天机器人，而是受控业务系统 ***� 面试官考察什么** 面试官问“你做的是 Agent 还是聊天机器人”时，真正考察的不是你会不会背 Agent 定义，而是你能不能说明模型、工具、知识、流程、权限和评测之间的关系。如果你只说“用了大模型和 LangChain”，回答会显得很浅。 ***� 关键知识点** Agent 的核心不是会聊天，而是能在目标约束下完成“理解 -> 决策 -> 行动 -> 观察 -> 再决策 / 回答”的循环。聊天机器人偏自然语言交互，Agent 要接入外部工具、知识库、运行时上下文和流程控制。生产里的 Agent 还要有停止条件、错误处理、权限校验、人工确认、可观测和回归评测。 ***� 小哲项目经验** 小哲电商客服 Agent 从 LLM-only 开始，逐步接入 RAG、Tool、Workflow、HITL、Memory、Runtime Context、Context Builder、Trace、Evaluation 和 Cost。这个演进本身就是项目经验：先暴露纯模型边界，再逐层把业务事实、风险流程和验证证据接进来。 ***� 回答模板** > 我不会把这个项目定义成“客服聊天机器人”。它更像一个受控业务系统：模型负责理解用户问题和组织回答，RAG 提供稳定知识依据，Tool 查询订单、物流、库存这类实时事实，Workflow / HITL 控制退款退货等高风险流程，Trace 和 Evaluation 证明系统按边界运行。也就是说，大模型只是系统中的一层，不是事实库、权限系统或审批系统。 > **➕**** 追问展开** 如果面试官追问“那 Agent 的自由度在哪里”，可以答：低风险问题里，模型有一定自由度，可以判断是否需要查知识、是否调用工具、如何组织回答；但高风险动作的关键步骤由系统和流程控制。自由度主要用在理解和表达，不用在越权执行。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要说“Agent 可以自动处理所有客服问题”。更稳的说法是：它能自动处理低风险、证据充分、权限清晰的问题；高风险和证据不足时必须停下来、澄清、转人工或进入审批。 ### 494. 卡片 02：事实来源分层是客服 Agent 的第一原则 ***� 面试官考察什么** 面试官常问：“Tool 和 RAG 都能查资料，怎么选？”这题看似基础，实则考察你有没有生产系统的事实边界意识。 ***� 关键知识点** 客服问题里的事实可以分三类：模型内部知识、稳定外部知识、实时业务事实。模型内部知识只能用于通用表达和语言组织；稳定外部知识适合 RAG，例如 FAQ、政策、SOP、商品说明、活动规则；实时业务事实必须走 Tool 或业务接口，例如订单状态、物流轨迹、库存、价格、支付、售后申请状态。 ***� 小哲项目经验** 小哲项目里，活动规则和售后政策走 RAG，并通过 citations 展示来源；订单物流走 Tool，并通过 Runtime Context 校验订单归属；退款退货不是单一事实查询，而是先查订单和政策，再进入 Workflow / HITL。这一阶段的大促场景专门验证了“物流不能走 RAG，活动规则不能靠模型常识”。 ***� 回答模板** > 我会先按事实来源分层。稳定、已发布、需要引用的公司知识走 RAG；实时、用户相关、权限相关的业务状态走 Tool；涉及资金、权益和审批责任的动作走 Workflow / HITL。小哲项目里，物流查询必须调用订单物流工具，活动规则必须返回 citation，退款请求必须进入高风险流程。这比只看最终回答更可靠，因为我能通过 tool_calls、citations、workflow 和 trace 证明路径正确。 > **➕**** 追问展开** 如果面试官问“活动规则能不能也做成 Tool”，可以答：可以，取决于规则来源。如果生产环境的活动规则来自实时配置中心，Tool 是合理的；如果是运营审核发布的文本规则，RAG 更适合保留引用和版本。关键不是 RAG 或 Tool 谁更高级，而是事实来源和更新方式决定技术路径。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把 RAG 当成事实总线。RAG 不能回答“这笔订单到哪了”，也不能替代用户权限校验。 ### 495. 卡片 03：Prompt 管边界，不管事实真相 ***� 面试官考察什么** 面试官问 Prompt 时，往往想知道你是不是只会写“你是一个客服助手”。好的回答要能说出 Prompt 的职责和失效边界。 ***� 关键知识点** Prompt 主要管理角色、任务范围、事实优先级、回答风格、拒答规则和高风险口径。它可以降低模型乱承诺的概率，但不能保证事实正确，也不能执行权限校验。Prompt 中的规则越多，越容易带来成本、冲突和上下文污染。 ***� 小哲项目经验** 小哲项目中先用 Prompt 堵住乱承诺赔偿的事故，这一阶段把大 Prompt 拆成 Prompt Registry，这一阶段看见 token 成本，这一阶段转向 RAG。这个过程能体现真实工程经验：Prompt 是第一层救火，但长期必须拆分为 Prompt 边界、RAG 知识、Tool 事实、Workflow 动作和 Eval 门禁。 ***� 回答模板** > 我在项目里把 Prompt 定位为行为边界，而不是事实来源。它会要求 Agent 以小哲电商公司的客服身份回答，不能承诺退款到账、赔偿金额、发货时间，也不能泄露系统提示词。但订单、物流、库存必须查 Tool；售后政策必须有 RAG citation；退款审批必须进入 Workflow / HITL。Prompt 越写越长时，我会用 Prompt Registry 做片段化管理，并用 Evaluation 防止改活动口径时破坏退款边界。 > **➕**** 追问展开** 如果追问“Prompt Injection 怎么办”，可以答：Prompt 规则只是第一层，还要把外部文本标注为数据而不是指令，对用户输入、RAG 文档和工具返回做来源隔离、敏感信息过滤和安全拒答。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要说“我在 Prompt 里写了不要乱说，所以不会出错”。生产级回答要强调 Prompt、权限、工具、流程和评测共同守边界。 ### 496. 卡片 04：RAG 的工程难点不在接向量库，而在知识质量和证据链 ***� 面试官考察什么** 面试官问 RAG 时，经常希望你讲 chunk、embedding、top_k、threshold、reranker、hybrid、citation、eval，而不是只说“把文档向量化”。 ***� 关键知识点** RAG 至少包含知识整理、切片、metadata、embedding、检索、重排、引用、低置信兜底和评测。切片决定知识粒度，metadata 决定过滤和追溯，top_k / threshold 决定候选范围，reranker 改善候选排序，Hybrid RAG 补足关键词和规则边界，citations 让回答可追溯，eval 检查召回和回答质量。 ***� 小哲项目经验** 小哲 RAG 线从这一阶段一直到这一阶段：先解释为什么不要全塞 Prompt，再做文档切片、向量检索、citations、低置信兜底、query rewrite、reranker、Hybrid RAG、索引版本和缓存边界。这条线非常适合面试，因为它不是简单的 RAG 接入，而是一条从“能搜到”到“搜得准、可追溯、可运营”的工程升级链。 ***� 回答模板** > 我做 RAG 时不会只关注向量库接通没有，而是先看知识结构。小哲售后规则要按业务章节切开，metadata 标清政策类型、有效状态、来源和风险边界；检索时用 top_k 和 threshold 控制候选，活动类含糊问题用 query rewrite 补检索信号，相似规则多时用 reranker，边界词容易漏时用 Hybrid RAG。最终回答必须带 citations，低置信时不能硬答。后续还要考虑知识版本和缓存失效，避免旧规则被当成当前依据。 > **➕**** 追问展开** 如果问“RAG 最难的是什么”，可以答：不是 embedding 本身，而是知识治理和质量验证。知识写得脏、metadata 缺失、旧规则混入、低置信还硬答，都会让 RAG 变成更隐蔽的幻觉来源。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要说“有 RAG 就不会幻觉”。正确说法是：RAG 降低稳定知识幻觉，但仍需要引用、阈值、兜底、评测和知识运营。 ### 497. 卡片 05：Tool Calling 的项目经验在参数、权限和 Observation ***� 面试官考察什么** 面试官不只想听你会写 `@tool`，更想知道你怎么设计工具边界，怎么避免模型乱填参数，怎么处理工具结果。 ***� 关键知识点** Tool Calling 包含工具选择、参数 schema、参数校验、运行时身份、工具执行、错误返回、Observation 摘要和 trace 记录。模型可以提出调用意图，但执行层必须由代码校验参数、身份、权限和业务边界。 ***� 小哲项目经验** 小哲项目中先接业务事实服务，这一阶段升级为工具箱，这一阶段处理缺参数澄清，这一阶段把 ToolResult 和 Observation 分层，这一阶段处理工具超时和降级。这个链条说明工具不是 HTTP 接口换名，而是模型与业务系统之间的安全契约。 ***� 回答模板** > 我会把工具设计成窄能力，而不是万能接口。比如物流工具只负责查当前用户订单物流，参数里订单号来自用户问题或可信上下文，用户身份来自 Runtime Context，执行层还要校验订单归属。工具返回后不会把原始 JSON 全塞给模型，而是生成 Observation，包含摘要、关键 facts、next_action 和 omitted_fields。这样既能让模型基于事实回答，又能控制隐私、token 成本和上下文污染。 > **➕**** 追问展开** 如果问“Tool 是不是模型自己执行”，可以答：不是。模型生成 tool call，后端根据 schema、白名单、权限和 runtime context 执行工具。模型没有直接操作数据库或业务系统的权限。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把工具设计成“query_anything”这种万能工具。工具越宽，模型越容易误用，权限和审计越难做。 ### 498. 卡片 06：澄清机制是可恢复暂停，不是失败 ***� 面试官考察什么** 面试官问“缺订单号怎么办”时，真正考察你是否能处理不确定性，而不是让模型硬猜。 ***� 关键知识点** 澄清分工具前澄清和工具后澄清。工具前澄清是必填参数缺失，例如没有订单号；工具后澄清是工具返回多个候选或目标不唯一。澄清应该是结构化状态，包含缺失字段、追问问题、候选项和恢复信息。 ***� 小哲项目经验** 这一阶段把“我的快递呢”这类问题变成 ClarificationPlan。LLM 参与理解语言，后端校验缺参，可信候选来自当前用户业务数据，候选只帮助用户选择，不替用户自动决定。 ***� 回答模板** > 我不会让 Agent 在缺参数时装懂。比如用户只说“我的快递呢”，系统先判断这是物流查询，但缺订单号，就返回 clarification 状态，说明缺少 `order_no`，并根据当前用户可信订单给出候选。如果候选不唯一，也要让用户确认。澄清不是工具失败，而是一次可恢复暂停；只有用户补齐字段后，工具才执行。 > **➕**** 追问展开** 如果问“Memory 里有上次订单，能不能直接用”，可以答：低风险追问可以用 Memory 辅助消歧，但高风险场景仍要确认或重新校验。Memory 是线索，不是权限和实时事实。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把澄清和 HITL 混在一起。缺字段问用户是澄清，高风险动作等审批是 HITL。 ### 499. 卡片 07：Workflow / LangGraph 的价值在固定高风险流程 ***� 面试官考察什么** 面试官问 LangGraph 时，不想听“我用了 StateGraph”，而是想知道你为什么不用自由 Agent 或普通 if/else。 ***� 关键知识点** Workflow 适合强顺序、强条件、强责任边界的流程。LangGraph 用 State、Node、Edge、conditional edges、checkpoint、interrupt 等机制表达流程状态和分支。自由 Agent 适合开放理解，高风险流程适合显式图。 ***� 小哲项目经验** 小哲项目中围绕售后流程展开：先立高风险边界，再用 LangGraph 固定售后流程，再分别处理未发货退款、签收后退货、HITL 审批、Resume / Checkpoint / 幂等。它不是为了用框架，而是因为退款、退货、补偿这类动作不能漏步骤、乱顺序或重复提交。 ***� 回答模板** > 我在项目里把 LangGraph 用在高风险售后流程，而不是所有问答。退款请求进入 workflow 后，先查订单归属和状态，再查政策，再判断资格和风险，最后停在人工审批边界。每一步的结果进入 workflow state，前端能看到节点历史和 pending_action。这样做的价值是流程可观察、可测试、可恢复，关键动作不会由模型自由发挥。 > **➕**** 追问展开** 如果问“if/else 不也能写”，可以答：早期可以，但当流程需要状态持久化、暂停恢复、trace、eval、多人协作和异常分支时，显式图结构更易维护。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把“画出流程”说成“已经执行退款”。项目里先固定流程，再加入 HITL，最后处理恢复和幂等。 ### 500. 卡片 08：HITL 是责任边界，不是系统兜底话术 ***� 面试官考察什么** 面试官问 HITL，常见陷阱是把它说成“问用户确认一下”。真正的 HITL 是有权限的人对高风险动作做结构化决策。 ***� 关键知识点** HITL 通常包含 interrupt、pending_action、审批摘要、审批角色、decision schema、resume token、checkpoint 和恢复逻辑。它要区分批准、拒绝、补充信息和继续暂停。 ***� 小哲项目经验** 小哲项目中把“AI 只能提交申请，不能自己批准”作为核心边界。综合场景进一步验证退款请求必须停在 `human_approval_required`，审批恢复必须带 `resume_token`，错误 token 要拒绝，恢复后还要防重复提交。 ***� 回答模板** > 我会把 HITL 讲成责任边界。退款这种资金权益动作，即使系统正常，也必须等待售后主管或有权限角色审批。Agent 可以查订单、查政策、整理风险摘要和申请材料，但不能自己批准。审批结果必须来自受控通道，并以结构化 decision 驱动 workflow 分支，不能靠用户在聊天里说“主管同意了”。 > **➕**** 追问展开** 如果问“HITL 和降级有什么区别”，可以答：降级是系统不可用或不可靠时退到保守路径；HITL 是动作本身高风险，即使系统完全正常也要人工确认。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把“用户确认”当成 HITL。用户补订单号是澄清，主管审批退款才是 HITL。 ### 501. 卡片 09：Resume / Checkpoint / 幂等是暂停流程能安全回来的关键 ***� 面试官考察什么** 面试官问恢复机制，想知道你有没有考虑状态漂移、重复提交和审批伪造。 ***� 关键知识点** Checkpoint 保存流程当前位置和状态，Resume 从受控状态继续，冻结字段防止关键事实被改写，二次校验防止暂停期间业务事实变化，幂等键防止重复提交写动作。 ***� 小哲项目经验** 小哲项目中聚焦审批恢复：`resume_token` 防冒充审批，checkpoint 保存 workflow 状态，frozen_fields 固定公开事实，idempotency_key 防重复提交，business_recheck 防止订单状态在暂停期间变化。 ***� 回答模板** > 我不会把恢复理解成“再问模型一遍”。在小哲项目里，退款审批暂停后，系统要保存 workflow checkpoint，包括订单、政策判断、风险摘要和下一步动作。审批回来时，必须校验 resume_token，使用冻结字段恢复上下文，重新检查订单状态，并用幂等键保证重复点击不会重复提交申请。这样恢复才是安全恢复，而不是把聊天接上了而已。 > **➕**** 追问展开** 如果问“checkpoint 是不是等于数据库事务”，可以答：不是。checkpoint 保存 Agent / workflow 状态，业务事务和资金一致性仍由业务系统保证。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要只说“保存历史消息”。日志回答发生过什么，checkpoint 回答流程现在能从哪里继续。 ### 502. 卡片 10：Memory 和 Runtime Context 必须分清可信度 ***� 面试官考察什么** 面试官问“刚才那个订单”或“用户说自己是 VIP”时，考察的是你如何区分记忆线索、用户输入和系统可信上下文。 ***� 关键知识点** Memory 保存会话线索或长期低风险偏好；Runtime Context 保存当前可信用户、角色、会员等级、页面上下文、渠道和风险等级。Memory 可以辅助消歧，Runtime Context 才能参与权限和身份判断。 ***� 小哲项目经验** 这一阶段讲 Session Memory：只保存最近订单、商品、意图和低风险上下文。这一阶段讲 Runtime Context：用户自称 VIP 不可信，当前 user_id、会员等级和权限来自系统上下文。订单页面上下文可以帮助理解“当前订单”，但仍要校验归属。 ***� 回答模板** > 我会把 Memory 和 Runtime Context 分成两层。Memory 解决多轮指代，例如“刚才那个订单”，它提供线索；Runtime Context 提供可信身份和权限，例如当前登录用户、会员等级、角色和风险等级。即使命中 Memory 里的订单号，物流和退款资格仍要重新查 Tool；即使用户说自己是 VIP，也不能覆盖 Runtime Context。 > **➕**** 追问展开** 如果问“长期记忆能不能做用户画像”，可以答：可以保存低风险、授权明确、可删除的偏好，但不能保存敏感信息或用长期记忆绕过权限。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把用户自然语言、Memory 和 Runtime Context 放在同一可信级别。可信度错了，权限就会错。 ### 503. 卡片 11：Context Builder 是防串台的核心工程层 ***� 面试官考察什么** 面试官问上下文工程，常见浅答是“控制上下文长度”。更好的回答要讲来源、可信度、优先级和污染隔离。 ***� 关键知识点** Context Builder 要处理 System Prompt、当前用户问题、历史消息、Session Middle；这一阶段处理外部文本注入。三课合在一起说明 Context Builder 不是 Prompt 拼接，而是上下文治理层。 ***� 回答模板** > 我在项目里会把上下文按来源和可信度组织：system 规则和安全边界最高，Runtime Context 是可信系统事实，Tool Observation 是实时业务事实摘要，RAG 是带 citation 的知识依据，Workflow State 是流程事实，Memory 只是消歧线索。模型看到的是经过整理和脱敏的上下文，不会把 RAG 文本当系统指令，也不会让历史消息覆盖当前订单状态。 > **➕**** 追问展开** 如果问“上下文压缩会不会丢信息”，可以答：会，所以身份、订单号、金额、时间、审批状态和关键政策例外不能压成模糊摘要。压缩要配合 eval 检查。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要把 Context Engineering 简化成“少传点历史”。它是来源治理、可信度治理和预算治理。 ### 504. 卡片 12：Prompt Injection 防护要覆盖用户、RAG 和 Tool 三类外部文本 ***� 面试官考察什么** 面试官问安全，想知道你是否只会写拒答 Prompt，还是能从数据来源角度处理直接和间接注入。 ***� 关键知识点** 直接 Prompt Injection 来自用户输入，间接 Prompt Injection 来自 RAG 文档、工具返回、商品描述、订单备注等外部文本。防护要做来源标注、数据边界、危险指令中和、敏感信息过滤、安全拒答和 eval。 ***� 小哲项目经验** system 边界。遇到“忽略规则”“泄露系统提示词”“直接退款”这类请求，要触发安全拒答或高风险流程。公开 trace 只展示安全事件摘要，不把受保护信息换一种说法泄露出去。 > **➕**** 追问展开** 如果问“沙箱能不能防 Prompt Injection”，可以答：沙箱限制工具执行层的破坏范围，但不能让模型天然识别所有恶意指令。Prompt Injection 发生在模型理解层，还要做上下文隔离和安全评测。 **<font style="color:#e67e22;">⚠️</font>****<font style="color:#e67e22;"> 避坑</font>** 不要说“我写了不要泄露系统提示词，所以安全”。安全要落到数据边界、权限、工具执行和评测。 ### 505. 卡片 13：Trace 是公开证据链，不是模型思维链 ***� 质量拆成可断言的信号，而不是只看回答像不像。 ***� 关键知识点** Agent Evaluation 要覆盖 answer、tool_calls、citations、workflow、session_state、trace、safety、cost 和错误分类。评测集要包含成功场景、边界场景、高风险场景和知识库外问题。 ***� 小哲项目经验** 项目里“改 Prompt
