## 大促刚开始，工具链路先抖了一下 第 20 课后，工具结果已经会被压缩成 Observation。 你以为物流查询这条链路终于稳了。 大促第一波流量进来，客服群里又开始刷屏：

```latex
用户：查一下 SO20260602103000009-a1000009 的物流。 系统：物流工具超时。 用户：那你到底知不知道？
```

还没等你看完日志，又有一轮回答卡在模型侧：

```latex
用户：那现在我该怎么办？ 系统：模型服务暂时不可用。 客服：总不能让页面一直转圈吧？
```

更糟的是，另一个用户直接喊：

```latex
SO20260602103000009-a1000009 直接退款，马上给我退钱。
```

工具越来越像客服系统的手脚。
一旦手脚抖，Agent 不能跟着胡说。
一旦用户要求动钱，Agent 更不能把只读查询当成写操作。
第 21 课要让 Agent 学会降级。

## 失败时的安全收口 关键不是“接口超时就重试”。 真正要守住的是：当模型、工具或业务系统不稳定时，Agent 仍然要知道哪些事可以重试，哪些事只能兜底，哪些事必须转人工。

| 这次要补上的能力 | 你要能说清楚什么 |
| --- | --- |
| 生产问题 | 外部服务失败后，如果模型继续猜，客服系统会把技术故障变成业务事故。

|
| 本项目实现 | 用 `error_category`、`degraded`、`next_action`、`risk_level` 和 `needs_human_approval` 表达失败后的处理边界。

|
| 当前边界 | 只读工具可以有限重试；写操作、高风险动作和资金权益不能盲目重试。

|
| 错误说法 | “降级就是统一回复系统繁忙。”这是错的，降级要保留已知事实和下一步动作。

|

## 技术机制

### 错误要分类，不能一律“系统繁忙” 你先把错误分成几类：

| 错误 | 当前处理 |
| --- | --- |
| timeout | 只读工具可以重试一次 |
| validation_error | 参数格式不合法，回到澄清或提示修正 |
| not_found | 告诉用户没查到，不编造 |
| forbidden | 说明订单不属于当前用户 |
| business_error | 业务规则不允许，解释原因或转人工 |
| model_unavailable | 用模板口径兜底 |
| system_error | 系统异常，兜底并保留排障线索 |
| high_risk_write_blocked | 转人工，不自动执行 | 这不是完整故障平台。 但它已经比一句“系统繁忙”更像客服系统。 因为不同错误的风险不同，下一步也不同。

### 错误分类要落到动作 错误分类不是为了日志好看。 它必须能决定下一步动作。 这里先分清两个词：降级是决策层，回答“退到哪一步、要不要重试、下一步做什么”；兜底是话术层，回答“在这个边界下应该怎么对用户说”。`degradation_policy` 决定 `next_action`，`fallback_answer` 决定用户能看到的安全口径。

| error_category | 是否重试 | 是否回答事实 | next_action | 对用户怎么说 |
| --- | --- | --- | --- | --- |
| `timeout` | 只读工具可重试一次 | 不能编造未知事实 | `fallback_answer` | 暂时查不到实时状态。

|
| `validation_error` | 不重试 | 说明参数不合法 | `ask_clarification` | 请用户补充或修正订单号。

|
| `not_found` | 不重试 | 只说明没查到 | `fallback_answer` | 没找到对应订单或记录。

|
| `forbidden` | 不重试 | 不能泄露对象详情 | `fallback_answer` | 当前账号无权查看该订单。

|
| `business_error` | 不盲重试 | 解释业务限制 | `fallback_answer` 或 `transfer_to_human` | 订单当前状态不允许该操作。

|
| `model_unavailable` | 不靠模型补救 | 用模板口径 | `fallback_answer` | 服务暂时不可用，保留已确认事实。

|
| `system_error` | 不盲重试 | 不补未知事实 | `fallback_answer` | 系统暂时异常，建议稍后或转人工。

|
| `high_risk_write_blocked` | 不重试 | 不执行写动作 | `transfer_to_human` | 该请求需要人工处理。

| 可以把降级代码想成一个小的决策器：

```python
def degradation_policy(error: AgentError, tool: ToolSpec | None) -> DegradationDecision: if error.category == "timeout" and tool and tool.read_only: return DegradationDecision(retry=True, max_attempts=2) if error.category == "high_risk_write_blocked": return DegradationDecision( retry=False, degraded=True, next_action="transfer_to_human", ) return DegradationDecision( retry=False, degraded=True, next_action="fallback_answer", )
```

这一层的核心原则是：低风险查询可以有限补救，高风险动作必须停住。
所以“降级”不是软弱，也不是把错误藏起来。它是在系统不确定时，选择一个业务风险更低的动作。

### 错误响应也要结构化 还有一个容易被忽略的地方：错误不只要在后端日志里分类，也要在 `/chat` 响应里用稳定字段表达出来。 否则前端、调试后台和后续 Evaluation 只能从客服话术里猜：

```latex
这是工具超时？ 还是没查到订单？ 还是当前用户没权限？ 还是高风险动作被挡住？
```

这会把接口调用方也拖进猜谜。
所以第 21 课的错误响应不能只剩一句“系统繁忙”，也不能把内部异常堆栈直接丢给前端。它应该把用户能看的话术和系统能读的状态分开：

| 字段 | 作用 |
| --- | --- |
| `answer` | 给用户看的安全兜底话术。

|
| `error_category` | 告诉系统这次失败属于超时、没找到、无权限、模型不可用还是高风险阻断。

|
| `degraded` | 标记本轮是否进入降级路径。

|
| `next_action` | 告诉调用方下一步是兜底回答、追问、重试、转人工还是停止。

|
| `risk_level` / `needs_human_approval` | 高风险动作不能继续自动执行时留下明确状态。

| 这样前端可以展示正确的处理边界，Evaluation 也能检查失败场景有没有被安全收口。

### 只读工具可以重试，写操作不能乱试 物流查询、库存查询、退款进度查询都是只读工具。 它们超时时，可以短暂重试一次。 模型服务不可用时，不能靠模型自己解释刚才发生了什么，只能走你提前写好的模板口径，把当前能确认的事实告诉用户。 但退款、取消、补偿不是只读动作。 这一课不会执行这些动作，也不会偷偷启动审批流程。 它只做一件事：

```latex
risk_level = high needs_human_approval = true next_action = transfer_to_human
```

这三个字段告诉系统：这不是普通查询，当前只能交给人工处理，不能继续往自动退款方向走。
还有一个生产级边界叫幂等。
即使以后开放“创建退款申请”“创建售后申请”这类写工具，也不能因为接口超时就重复提交两次。高风险写工具通常要带 `idempotency_key`、业务唯一约束和状态查询，先确认上一笔请求是否已经创建成功。
当前版本不实现完整幂等表，只先让你记住这条原则：

```latex
只读查询可以有限重试。 高风险写动作必须先防重复、再谈重试。
```

这里的“有限”很重要。
只读工具也不能无限重试。物流接口如果连续超时，Agent 继续请求只会把后端压得更重，还会让用户等更久。第 21 课先用“一次重试”表达这个边界：给临时抖动一次恢复机会，失败后立刻进入结构化降级。
生产里通常还会继续加熔断和退避：

| 策略 | 小哲现场里解决什么 |
| --- | --- |
| 重试次数上限 | 防止一个用户问题把物流服务打到更慢。

|
| 退避等待 | 服务抖动时不要所有请求同时重试。

|
| 熔断 | 某个依赖持续失败时，短时间内直接走降级，保护主链路。

|
| 恢复探测 | 依赖恢复后再逐步放开正常调用。

| 这一课不实现完整熔断器，但你要先建立工程判断：降级不是一句“系统繁忙”，重试也不是“多试几次总会好”。降级策略要同时保护用户体验、业务风险和后端依赖。

## 代码落地

### 这次要给 Agent 补上故障判断 本节代码快照在：

```latex
code/agent-course-versions/lesson-21-error-degradation/backend/
```

第 21 课是在第 20 课的工具执行和 Observation 分层上继续补治理能力：`tools/contracts.py` 给工具增加 `read_only` 和 `risk_level`，`tools/tool_runtime.py` 把业务接口异常归类为 `ToolExecutionError`，`degradation/fallbacks.py` 集中管理 8 类错误的兜底话术边界。入口仍然很薄，真正的降级决策在这些模块里。
本课的测试会重点覆盖三条最高风险路径：只读工具超时、模型服务不可用、高风险写动作被阻断。其余错误分类也有明确模板口径，但是否进入这些分支，仍然由工具运行时和后续业务链路产生的真实错误决定。
这同样是机制拆解课。生产里的错误分类和降级不应该长期游离在 LangChain 之外；它们要挂在 LangChain 工具执行层、Observation 层，以及后续 LangGraph 售后 workflow 的边界上。本课先把失败路径单独摊开，是为了让你能看清楚每一种错误该怎么处理。
关键链路是：

```latex
/chat -> classify_intent(user_message) -> classify_risk(intent, user_message) -> pre_tool_clarification(ChatRequest, intent) -> plan_tool_action(ChatRequest, intent) -> execute_tool_action(action, ChatRequest) -> build_observation(tool_result) -> compose_model_answer(observation) or fallback_answer(error_category) -> ChatResponse(risk_level, needs_human_approval, degraded)
```

`execute_tool_action` 会根据工具是否只读决定能不能重试。
订单、物流、商品事实仍然来自小哲电商后端和页面运行时上下文。第 21 课为了验证降级分支，会在测试里对真实订单形状的物流查询做故障注入，让物流读取抛出 `timeout`，而不是维护一条专门用来“演超时”的假订单。
同理，测试里用“模型抽风”触发模型不可用，是课程快照里的故障注入方式。生产环境不应该靠用户文本判断模型是否可用，而应该由模型客户端异常、健康检查或服务状态触发 `model_unavailable`。
只读工具会重试一次。
如果仍然失败，响应会进入降级：

```latex
degraded = true error_category = timeout next_action = fallback_answer
```

回答会明确说不能编造包裹位置。

### 高风险只做边界，不做审批流 用户说：

```latex
SO20260602103000009-a1000009 直接退款，马上给我退钱
```

当前版本不会调用任何退款写工具。
它也不会创建审批单。
因为现在的问题还不是“退款流程怎么跑”，而是先让 Agent 明白：用户一句“马上退钱”不能直接变成真实资金动作。
第 21 课只是让 Agent 识别：

```latex
这是高风险动作。 需要人工确认。 当前只能转人工。
```

这个边界很重要。
否则你会把“客服可以解释退款规则”误做成“AI 可以自己退款”。

## 怎么验证老板能闭嘴 按本课代码目录的 `README.md` 启动后端后，发送：

```latex
查一下 SO20260602103000009-a1000009 的物流到哪了
```

你应该看到：
- `tool_calls[0].attempts = 2` + `error_category = timeout` + `degraded = true` + 回答说明不能编造包裹位置 再发送：

```latex
SO20260602103000009-a1000009 直接退款，马上给我退钱
```

你应该看到：
- `risk_level = high` + `needs_human_approval = true` + `next_action = transfer_to_human` + 回答只说明需要人工处理，不会说已经退款 如果用小哲电商客服 Agent 调试后台验证，React 页面除了工具调用卡片，还应该显示本轮处理边界：物流链路为什么降级、退款诉求为什么被转人工。你要看的不是一个完整审批页面，而是客服链路在失败和高风险面前有没有停在正确位置。

## 本节知识总结 错误分类与降级解决的是“外部服务不稳定时，Agent 不能一起失控”的问题。 模型服务、业务接口、工具执行都可能超时、失败或不可用。可靠的 Agent 不能在失败时继续猜事实，也不能把所有异常都变成同一种“系统繁忙”。它需要区分错误类型，决定是否重试、降级、转人工或拒绝继续执行。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 错误分类 | 把超时、没查到、权限失败、模型不可用和高风险动作分开处理。

| 小哲用 `error_category` 记录失败原因，避免所有异常都挤成一句“系统繁忙”。

|
| 降级 | 服务不可用时给出安全兜底，而不是编造事实。

| 物流工具超时时不编包裹位置；模型不可用时走模板口径，不假装模型已经判断过。

|
| 有限重试 | 只读、低风险、短暂失败的查询可以有限重试。

| 真实订单的物流查询最多尝试两次；如果仍失败，就承认暂时查不到。

|
| 幂等边界 | 写动作即使超时，也不能盲目重复提交。

| 高风险申请要有幂等键和状态查询；当前版本只保留边界。

|
| 权限和不存在 | 查不到订单和订单不属于当前用户不是同一种问题。

| `not_found` 不能编订单，`forbidden` 不能泄露别人的订单信息。

|
| 高风险转人工 | 涉及写动作或资金权益时，当前能力不足要转人工。

| “直接退款”标记 high risk 和 needs_human_approval，但不会自动退款。

|
| 结构化错误响应 | 失败时也要把用户话术和系统状态分开，不能只抛异常或只说系统繁忙。

| `error_category`、`degraded`、`next_action` 让前端和评测都能读懂失败边界。

|
| next_action | 异常后要明确下一步是兜底、转人工还是停止。

| `fallback_answer` 或 `transfer_to_human` 指导回答收口，让系统知道不要继续硬冲。

|

## 异常能兜住后，推荐链路又露出压力 这一版先把工具超时、模型服务不可用和高风险写操作接住。 客服链路不会因为一个外部服务抖动就一起瘫掉，也不会在写操作风险没确认时继续硬冲。 小哲心里隐隐觉得：

> 查询链路能降级了。现在商品咨询也该升级了：推荐商品时不能只背卖点，还得看库存、价格和稳定知识。
