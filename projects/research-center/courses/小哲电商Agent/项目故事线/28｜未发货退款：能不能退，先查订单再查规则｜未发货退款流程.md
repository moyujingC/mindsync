这次事故背后的 Agent 问题 未发货退款不是一句话判断。 它至少要按固定顺序拿到三类证据： | 证据 | 作用 | | --- | --- | | 订单状态 | 是否已支付、是否仍处于待发货 | | 物流状态 | 是否还没有出库、揽收或运输 | | 退款政策 | 小哲电商公司是否允许发起未发货退款申请 | 第 28 课只开放这一条路径： ```latex unshipped_refund ``` 签收后退货先不做。 这样你能让代码成熟度和课程进度保持一致：这一课只把未发货退款讲透。 分支不是为了分类好看。 它决定后面要读哪些事实、检查哪些条件、能不能进入申请前准备。未发货退款关注的是支付状态、订单状态和物流是否未发出；签收后退货关注的是签收时间、商品属性和退货原因。 如果系统只保存一个笼统的 `refund_request`，后续节点就很容易拿错规则。正确做法是先把意图落到明确的 workflow type，再让后面的节点按这个类型读事实、查政策和判断资格。 ## 代码落地 ### 当前 Agent 的实现边界 本节代码快照在： ```latex code/agent-course-versions/lesson-28-unshipped-refund-workflow/backend/ ``` 这一课没有把所有售后都做完，而是在第 27 课 `workflows/after_sale_workflow.py` 的固定节点上收窄一条路径：只开放未发货退款。`policies/after_sale_policy.py` 继续判断资格，`agents/customer_service_agent.py` 只把“可准备申请”的状态公开给用户。 关键链路是： ```latex /chat -> AfterSaleWorkflow.run(request) -> classify_after_sale_intent -> load_order -> load_logistics -> retrieve_policy -> check_eligibility -> stop_before_submission -> ChatResponse(workflow.pending_action = prepare_refund_application) ``` 当订单符合条件时，`workflow.pending_action` 会变成： ```latex prepare_refund_application ``` 注意，它不是 `refund_success`。 它只是“可以准备退款申请”。 ### 核心代码拆解 第 28 课沿用第 27 课的 StateGraph，但 `_classify_after_sale_intent` 只把退款诉求映射成： ```latex workflow_type = unshipped_refund ``` 如果用户说的是签收后退货，这一版会停在边界说明。 这不是偷懒，而是课程边界：签收后退货需要时间、商品和原因判断，下一课再打开。 真正的未发货退款判断在 `assess_refund_boundary`： ```latex order_status == PENDING_SHIPMENT payment_status == PAID logistics_status == NOT_SHIPPED ``` 三个条件同时满足，才返回： ```latex eligibility_status = eligible_for_application ``` 如果业务系统显示订单已经发货在途，比如 `SO20260602103000009-a1000009`，即使用户说“取消订单并退款”，也会返回 `not_eligible`。 这里有一个顺序边界：先查事实，再套规则。 用户说“还没发货”只能当线索，不能当事实。只有订单系统和物流系统都确认还没有发货，未发货退款政策才有适用空间。 如果顺序反过来，先拿“未发货退款政策”去安慰用户，再发现物流已经揽收，系统就会把客服话术和业务事实打架的问题留到最后。 ## 怎么验证未发货退款流程跑对 按本课代码目录的 `README.md` 启动后端后，发送： ```latex SO20260601090000008-a1000008 还没发货，直接给我退款 ``` 你应该看到： + `workflow.workflow_type = unshipped_refund` + `workflow.pending_action = prepare_refund_application` + `after_sale_assessment.eligibility_status = eligible_for_application` + 订单状态是 `PENDING_SHIPMENT` + 物流状态是 `NOT_SHIPPED` + citation 指向未发货退款 SOP + 没有 `approval_id` + 没有 `resume_token` 再发送： ```latex SO20260603110000010-a1000010 已签收，我要退货 ``` 这一版会告诉你：签收后退货下一课处理。 ## 本节知识总结 流程分支解决的是“同一个用户诉求背后可能是不同业务路径”的问题。 用户都说“我要退款”，但未发货退款、已发货拦截、签收后退货、质量问题售后，背后的事实、规则、风险和处理方式都不一样。Agent 不能只识别到“退款意图”就给结论，它必须先把请求落到正确分支上。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | 未发货退款流程 | 对同类诉求拆出具体业务分支，每个分支有自己的判断条件。 | 已支付、待发货、未揽收才进入未发货退款准备申请。 | | Workflow Type | 先确定当前属于哪条售后分支，再让后续节点读取对应事实和政策。 | `unshipped_refund` 决定本课只检查未发货退款条件，不混入签收退货规则。 | | 业务事实先于规则 | 先确认当前事实，再查适用规则；事实不清时不能套政策。 | 小哲先查订单和物流，再看售后政策，不先凭用户描述判断。 | | 状态校验 | 流程必须校验关键状态，防止用户描述和系统事实不一致。 | 物流状态能防止用户把已出库订单说成未发货。 | | 准备申请 | “可准备申请”只是进入下一步，不等于动作已经成功执行。 | `prepare_refund_application` 表示可准备退款申请，不表示退款成功。 | | 能力克制 | 当前分支只实现当前能力，不把后续审批、恢复或其他路径伪装成已完成。 | 本课不提前实现签收后退货、HITL 和恢复。 | ##
