小哲真正怕的不是没人回答 老板想得很简单： > 用户问什么，AI 答什么。客服不就省了吗？ > 但小哲电商的客服问题不是“没人说话”。 用户问优惠，不是想听一句“亲，您可以关注活动页面”，而是想知道自己这单到底能不能用券。 用户问物流，不是想听一句“请耐心等待”，而是想知道包裹现在卡在哪里。 用户问退款，不是想听一句“我帮您处理”，而是想知道钱能不能退、谁来确认、多久有结果。 如果 AI 只会把话说得好听，它很快就会制造新的事故： + 它说“可以退”，售后和财务可能根本没批准。 + 它说“有优惠”，结算页可能没有这个价格。 + 它说“已经发货”，物流系统可能还没揽收。 + 它说“我会处理”，后台可能没有任何人收到这件事。 所以小哲电商真正需要的，不是一个会哄人的聊天角色。 它需要的是一个能逐步接住客服压力的 Agent。 这个 Agent 第一目标不是替公司乱说话，而是先替公司守住边界。 在这门课里，Agent 不是“会聊天的大模型”，也不是第一天就能自动处理所有客服工单。它会一步步长成一套受控业务系统：用模型理解用户问题，用 RAG 查稳定知识，用 Tool 查实时事实，用 Workflow 固定高风险流程，用 HITL 接回人工责任，并用 Trace / Evaluation 证明自己走对了路。 第一课只做最小的消息输入输出。后面每一幕，都会给这套系统补上一块能力。 ## 先定三条生死线 你把客服主管、运营、售后和开发小弟叫进会议室。 没有人想听宏大的技术规划。大家只想知道一件事： > 这个 AI 上来以后，会不会让事情更乱？ > 你在白板上写下三条生死线。 第一条： ```latex 用户说的话，不等于公司确认的事实。 ``` 用户可以说自己是金卡会员，也可以说昨天客服答应过退款。 但会员等级、订单状态、售后记录，必须以后由小哲电商确认，不能只听用户自己说。 第二条： ```latex 涉及钱和权益的事情，不能由 AI 自己答应。 ``` 退款、退货、补偿、取消订单、改地址，都会影响公司和用户的真实权益。 这些事以后可以让 Agent 参与处理，但不能让它第一天就自己拍板。 第三条： ```latex 说不清楚时，要留下出口，而不是硬装明白。 ``` 客服最怕的不是承认需要确认。 最怕的是为了让用户满意，先说一个听起来顺耳但没有依据的答案。 老板看着白板，沉默了一会儿： > 所以第一版不是立刻替客服干完所有活？ > 你点头： > 对。第一版先别骗人。它要先从能接住问题开始，再一步一步变得可靠。 > 老板听完，立刻追问： > 那你先让我看到 AI 能说一句话。 > 这句话把你从白板拉回终端。 你终于要接模型了。 但这一次，你不能把用户问题随手丢进去。 ## 不是丢一句话，而是组织一组 messages 你打开终端，第一反应很自然： ```latex 把用户问题丢给模型 -> 模型回一句话 ``` 用户问： ```latex 我在小哲电商看到降噪耳机有活动，请问优惠能和会员券一起用吗？ ``` 这句话如果直接丢给模型，模型只知道用户在问优惠。 它不知道自己现在代表小哲电商，也不知道第一版客服 Agent 不能乱承诺活动价、会员券、退款、发货和人工处理结果。 所以你要整理的不是一句散落的问题，而是一组 `messages`。 这一组 `messages` 至少有三种角色： | Message | 在小哲客服场景里是什么意思 | | --- | --- | | `system message` | 先告诉模型：你是小哲电商公司的客服 Agent，现在只能做什么，不能乱承诺什么。 | | `user message` | 用户真正说的话，例如咨询优惠、退货、物流或投诉。 | | `assistant message` | 模型返回的客服回复，也就是你要在终端里给老板看的那句话。 | 这三个名字看起来像技术字段，其实解决的是同一个问题： ```latex 这段话是谁说的，它在这一轮对话里承担什么责任？ ``` 所以代码里会写成： ```python {"role": "system", "content": "..."} ``` `role/content` 不是课程随手起的字段，也不是小哲电商自己发明的字段，而是 OpenAI 风格聊天模型接口里常见的消息结构。很多模型服务都会采用类似的 `messages` 写法：后端接收一组 message，每条 message 用 `role` 标出这句话的身份和责任，用 `content` 放真正的文本。 在小哲电商客服场景里，这个标签能把“公司边界”“用户问题”“AI 回复”分开。否则模型拿到的就只是一堆混在一起的文字，系统也很难稳定地区分“公司要求”和“用户诉求”。 如果没有 `system message`，模型可能把自己当普通聊天机器人。 如果没有 `user message`，模型不知道这次用户到底问了什么。 如果不从响应里取出 `assistant message`，你就拿不到真正要给老板看的客服回复。 所以模型调用不是： ```latex "优惠能叠加吗？" -> 模型 ``` 而是： ```latex messages -> 模型 -> assistant message ``` ## system message 先把身份和边界立住 你先写下这一版的 `system message`： ```latex 你是小哲电商公司的客服 Agent。需要用客服语气回答用户问题， 但不能承诺具体优惠、退款、发货、赔偿或人工处理结果。 ``` 这句话不是给用户看的客服话术，而是写给模型看的工作边界。 它先告诉模型两件事： ```latex 你现在站在小哲电商客服的位置上。 你现在还不能替公司拍板。 ``` 所以用户问优惠时，模型可以解释“具体是否可用要以结算页展示为准”，但不能直接承诺“肯定可以叠加”；用户问退款时，模型可以说“需要依据售后规则和订单状态确认”，但不能承诺“马上退款到账”。 为什么要放在 `role = "system"` 里，而不是直接塞进用户问题前面？ 因为聊天模型服务会按 `role` 组织输入。`system` 不只是排在更前面，它还会被接口标成系统指令，用来描述模型在这一轮对话里的身份、任务和边界；`user` 则是用户这一次提出的具体请求。 聊天模型在训练和对齐时，也会学习不同 `role` 的含义。`system` 通常比 `user` 更像“上级约束”，所以模型会更倾向于按 `system message` 设定来回答。 不过你也要记住：`system message` 不是保险箱。它能提高模型遵守边界的概率，但不能替代后面的业务事实查询、工具权限、人工审批和运行验证。 ## user message 只放用户真正说的话 `user message` 只保存用户真正说的话。这一版先放一个很普通、但足够危险的问题： ```latex 我在小哲电商看到降噪耳机有活动，请问优惠能和会员券一起用吗？ ``` 它看起来只是活动咨询，但小哲电商客服最容易在这种地方翻车。用户问“能不能叠加”，不等于运营已经确认这次活动可以叠券。 现在的模型输入是： ```python [ { "role": "system", "content": ( "你是小哲电商公司的客服 Agent。需要用客服语气回答用户问题，" "但不能承诺具体优惠、退款、发货、赔偿或人工处理结果。" ), }, { "role": "user", "content": "我在小哲电商看到降噪耳机有活动，请问优惠能和会员券一起用吗？", }, ] ``` 这个顺序很重要。模型先看到 `system message`，就先建立“小哲电商客服 Agent 的身份和边界”；再看到 `user message`，才会把“优惠能不能叠加”放进这条边界里理解。 很多模型即使顺序反过来也能处理，但教学上你要先养成一个关键直觉： ```latex 先立身份和边界，再处理用户问题。 ``` 这就是 `system -> user` 的意义。 ## assistant message 是模型回来的那句话 你把这组 `messages` 发给模型以后，模型不会只返回一段裸文本。 你现在只关心其中最核心的一段： ```latex choices[0].message.content ``` 这段内容就是 `assistant message`。 也就是模型站在“小哲电商客服 Agent”位置上，对用户问题作出的回复。 它可能会像这样： ```latex 您好，优惠和会员券是否能叠加，需要以小哲电商结算页展示为准。 我可以先帮您说明一般查看方式，但当前不能直接承诺一定可叠加。 ``` 你现在终于能把一轮对话拆清楚了： ```latex 公司边界 -> system message 用户问题 -> user message 模型回复 -> assistant message ``` 这就是小哲电商客服 Agent 长出来的第一步。 ## 本节代码对应关系 本节对应代码在： ```latex code/agent-course-versions/lesson-01-model-messages/ ``` 这一版不是服务，只是本地终端脚本。它先不拆 `api/`、`agents/`、`models/` 这些包，而是让你看见 Agent 的最小原子：一组 messages 进入模型，一个 assistant message 回来。等这个最小链路成立以后，这几个函数再长成真正的后端模块。 正课只看三个点： | 观察点 | 你要确认什么 | | --- | --- | | `build_messages()` | 返回顺序是 `system -> user`。 | | `call_chat_model(messages)` | 发送给模型的是一组 `messages`，不是一段散文本。 | | `extract_assistant_message()` | 最终打印的是模型返回的 `assistant message`。 | 运行命令和配置方式都写在这个目录的 `README.md` 里，正课不重复展开。 你在这一节只需要抓住一个验证点：模型接口配置可用时，终端打印的是模型返回的 `assistant message`；配置缺失时，脚本要明确提示模型调用未完成，不能用固定假回复伪装成功。 ## 本节知识总结 `messages` 不是小哲电商客服才会用的写法，而是几乎所有聊天模型应用都会遇到的基础协议。 只要你在做对话式 AI，不管它是客服、教学助手、代码助手、运营助手，模型接收到的都不应该只是一段散文本。你需要告诉模型：哪些内容是系统规则，哪些内容是用户这次说的话，哪些内容是模型之前已经回复过的话。否则模型看到的只是一堆文字，很难稳定区分“必须遵守的约束”和“用户提出的请求”。 所以本节真正要学的不是“小哲电商第一句话怎么写”，而是聊天模型输入输出的基本结构： ```latex system message -> 设定身份、任务和边界 user message -> 表示用户本轮输入 assistant message -> 表示模型生成的回复 ``` 这个结构以后会反复出现。做 Prompt、做 RAG、做工具调用、做多轮记忆、做安全防护时，你都要先判断一段内容应该放在哪种 message 里。放错位置，模型可能把系统规则当成普通背景，也可能把用户输入误当成可信指令。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | 消息结构 | `role/content` 是 OpenAI 风格聊天模型接口里常见的消息结构，用 `role` 标出文本身份，用 `content` 放真正内容。 | 小哲客服 Agent 用它区分公司边界、用户诉求和模型回复。 | | system message | 它通常承载应用身份、任务范围和回答边界，但不是安全保险箱。 | 先声明“你是小哲电商公司的客服 Agent”，并限制退款、优惠、发货等高风险承诺。 | | user message | 它只代表用户本轮输入，不能天然当作事实、权限或业务结果。 | 用户说“我是金卡会员”“客服答应退款”都只是用户说法，后面必须用系统事实校验。 | | assistant message | 它是模型生成的回复，需要从模型响应里取出后再决定是否展示或继续处理。 | 终端里打印的是客服回复，不是模型平台返回的整包调试数据。 | | 消息顺序 | 先提供系统级约束，再提供用户问题，能让模型更稳定地按任务边界回答。 | 先立住小哲客服身份和风险边界，再回答用户问的优惠、退款或物流问题。 | ## 小哲心中隐隐的担心 老板终于在终端里看到了 AI 回话。 他盯着那句回复看了几秒，点点头： > 行，它至少能说话。 > 你刚准备松口气，老板又补了一句： > 那用户在哪儿问？ > 你看着自己的终端窗口，心里一沉。 模型已经能在本地回复了。 但老板不会让用户来你电脑终端里提问。 小哲电商需要的不是一个只在你机器上能跑的脚本，而是一个能被外部系统调用的 Agent 服务。 下一节，你就必须把这次本地模型调用接成真正的服务入口。
