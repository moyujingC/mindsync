## 都叫退货，三笔订单不是一回事 第 28 课把未发货退款跑清楚了。 但售后队列里更麻烦的单子开始堆起来：

```latex
SO20260603110000010-a1000010 已签收，七天无理由退货。 SO20260525093000011-a1000011 已签收，也要退。 SO20260605103000005-a1000005 是定制商品，但用户说不喜欢，要退。
```

用户都在说“退货”。
但这三笔订单完全不是一回事。
售后主管看着你：

> 签收后退货不能只看“已签收”。要看签收多久了、商品能不能退、原因是否符合政策。

> 这一课，你要把签收后退货单独接进工作流。

## 这次事故背后的 Agent 问题 签收后退货比未发货退款多了几层判断。

| 判断项 | 为什么重要 |
| --- | --- |
| 签收时间 | 七天无理由有时间窗口 |
| 商品属性 | 定制、拆封影响二次销售等商品可能不可退 |
| 退货原因 | 无理由、质量问题、错发漏发对应不同政策 |
| 售后政策 | 最终仍要落到小哲电商公司的 SOP | 所以第 29 课打开第二条 workflow 路径：

```latex
received_return
```

这条路仍然沿用 StateGraph，但资格判断更细。
签收后退货最容易被模型讲成一句“七天无理由可以退”。
但真实判断不能只看一句政策口号。它要把用户原因、商品属性和系统时间放到同一个判断里：

| 信息 | 不能只靠什么 |
| --- | --- |
| 签收时间 | 不能只靠用户说“刚收到” |
| 商品属性 | 不能只靠商品名猜是否可退 |
| 退货原因 | 不能只靠情绪词判断是不是质量问题 |
| 政策依据 | 不能只引用一条宽泛规则，忽略例外条件 | 所以这一课的重点不是“多查几个字段”，而是让 workflow 能处理政策例外。

## 代码落地

### 当前 Agent 的实现边界 本节代码快照在：

```latex
code/agent-course-versions/lesson-29-received-return-workflow/backend/
```

这一课延续第 28 课的 `workflows/after_sale_workflow.py`，但 workflow 不再只认识未发货退款。签收后退货的签收时间、商品可退属性、退货原因和政策依据仍然放在 `policies/after_sale_policy.py` 判断，Agent 只读取 workflow 结果并解释边界。
关键链路是：

```latex
/chat -> AfterSaleWorkflow.run(request) -> classify_after_sale_intent -> load_order -> load_logistics -> retrieve_policy -> check_eligibility -> stop_before_submission -> ChatResponse(workflow.pending_action = prepare_return_application)
```

如果订单满足条件，`pending_action` 会变成：

```latex
prepare_return_application
```

这仍然只是“准备退货申请”。
不是退货成功，也不是人工审批通过。

### 核心代码拆解 第 29 课会用业务系统里的真实订单事实覆盖两类边界：

```latex
SO20260525093000011-a1000011 -> 已签收，但超过 7 天 SO20260605103000005-a1000005 -> 已签收，但商品不支持无理由退货
```

`assess_refund_boundary` 在 return 路径下会多做三件事：

```latex
signed_days(order) order["returnable"] 退货原因和政策依据
```

其中 `signed_days` 使用课程固定日期 `2026-06-07` 做确定性判断，课堂演示不会因为真实日期变化而漂移。
符合条件时，`evidence_checklist` 会比未发货退款多出：

```latex
签收时间 商品可退属性 退货原因
```

这能让你在调试后台或接口响应里清楚看到：Agent 不是因为“用户说要退货”就放行，而是把签收后退货需要的证据都检查过。
退货原因也要被结构化理解。
“不喜欢”“七天无理由”“质量问题”“发错货”会落到不同政策路径。课程这一版先用固定规则演示最小闭环；真实系统里还会把原因枚举、商品品类、售后记录、图片凭证和质检结论放进同一条状态链。
但无论规则多复杂，边界都一样：用户原因只是输入，系统事实和政策例外才决定能否进入申请。

## 怎么验证退货判断没有跳步 按本课代码目录的 `README.md` 启动后端后，发送：

```latex
SO20260603110000010-a1000010 已签收，七天无理由退货
```

你应该看到：
- `workflow.workflow_type = received_return` + `workflow.pending_action = prepare_return_application` + `after_sale_assessment.eligibility_status = eligible_for_application` + `evidence_checklist` 包含签收时间、商品可退属性、退货原因 + citation 指向签收后退货 SOP + 没有审批和恢复字段 再发送：

```latex
SO20260525093000011-a1000011 已签收，我要七天无理由退货
```

你应该看到它因为超过 7 天而不能进入退货申请。

## 本节知识总结 条件组合判断解决的是“单个标签不够决定业务动作”的问题。 很多高风险流程不是看一个字段就能判断。你需要同时看时间、状态、对象属性、用户原因、政策例外和权限边界。只要少看一个条件，Agent 就可能把不该放行的请求放行，或者把本该继续处理的问题挡掉。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 签收后退货流程 | 同一个退款意图下，签收后退货要单独进入更细分的路径。

| `received_return` 路径和未发货退款分开判断。

|
| 时间窗口 | 高风险资格常常依赖时间窗口，必须用系统事实计算。

| `signed_days` 判断是否超过 7 天。

|
| 对象属性 | 商品、账户、合同或订单属性会影响能否继续处理。

| `returnable` 防止定制商品被错误放行。

|
| 原因与政策 | 用户原因要映射到明确政策，不能只靠情绪或话术判断。

| 退货原因要落到小哲售后 SOP。

|
| 政策例外 | 宽泛规则必须和例外条件一起判断。

| 七天无理由也要同时看签收时间、商品是否可退和是否影响二次销售。

|
| 申请边界 | 资格通过或申请准备完成，不等于审批通过或动作执行完成。

| `prepare_return_application` 不是退货审批通过。

|
