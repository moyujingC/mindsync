原始工具结果可能太长、太脏、含内部字段或敏感信息，直接塞给模型会污染上下文。 | | 本项目实现 | `build_observation` 从 `ToolResult` 提取安全事实、摘要、`omitted_fields` 和 `next_action`。 | | 当前边界 | Observation 是给 Agent 和观察台看的安全事实摘要，不等于完整业务接口响应。 | | 错误说法 | “工具结果是真实数据，所以全部给模型最可靠。”这是错的。 | ## ToolResult 是内部结果，Observation 才是给 Agent 的观察 你可以先这样分： | 名称 | 谁看 | 放什么 | | --- | --- | --- | | ToolResult | 后端内部 | 工具原始返回、状态、错误码 | | Observation | Agent 和调试视图 | 摘要、关键事实、下一步动作 | `ToolResult` 可以很大。 它可能包含完整物流时间线、内部调试字段、供应商备注。 但 `Observation` 必须克制： + 一句话摘要。 + 当前回答必需的事实。 + 哪些字段被省略。 + `next_action`。 这一层压缩不是为了好看。 它是在保护模型上下文，也是在保护业务内部信息。 还有一个容易漏的点：`ToolResult` 例子一：物流工具查到太多轨迹 用户问： ```latex 查一下 SO20260602103000009-a1000009 的物流到哪了 ``` 物流工具可能拿到这样的原始结果： ```latex 订单号 = SO20260602103000009-a1000009 物流状态 = 已发货 承运方 = 小哲速运 运单号 = XZKD202605310088 完整轨迹 = 18 条完整轨迹 最新节点 = 已到达上海分拨中心 预计送达 = 2026-06-02 18:00 前 异常原因 = 无 仓库路由 = 华东仓 -> 上海分拨 -> 城配站 成本中心 = EC-SH-OPS-02 供应商备注 = 大促优先件，异常需联系仓配主管 内部诊断 = 接口耗时、重试次数、上游节点 ID ``` 如果你把这一整包原样交给模型，模型有三个风险： + 上下文被 18 条轨迹和诊断字段撑长。 + 回答里可能漏出运单号、成本中心、供应商备注。 + 模型可能把内部排查信息当成用户可见结论。 真正进入 Observation 的应该更克制： ```latex summary = 订单 SO20260602103000009-a1000009 最新物流：已到达上海转运中心，预计明日派送。 facts.order_id = SO20260602103000009-a1000009 facts.logistics_status = 已发货 facts.latest_event = 已到达上海分拨中心 facts.estimated_delivery = 2026-06-02 18:00 前 omitted_fields = 完整轨迹、运单号、仓库路由、成本中心、供应商备注、内部诊断 next_action = answer_user ``` 这不是“少说一点”。 这是把客服回答需要的事实留下，把内部字段挡在模型上下文外面。 ### 例子二：订单工具返回了用户隐私 还有一种更危险。 用户说： ```latex 我 6 月那笔订单是哪一单？ ``` 候选订单工具为了让后端能排查问题，可能拿到完整订单： ```latex 订单号 商品摘要 订单状态 支付金额 收货人姓名 收货手机号 收货地址 发票抬头 订单备注 客服内部备注 风控标签 ``` 但这轮 Agent 只需要让用户确认“你说的是哪一单”。 所以 Observation 里不该出现完整地址、手机号、发票抬头和风控标签。它只需要保留可选择的安全摘要： ```latex summary = 查到 2 笔 5 月订单，需要你确认要查询哪一笔。 candidates = [ {订单号: SO20260602103000009-a1000009, 状态: 已发货, 摘要: 65W GaN 快充充电器，实付 129 元}, {订单号: SO20260603110000010-a1000010, 状态: 已签收, 摘要: 降噪蓝牙耳机，实付 599 元} ] omitted_fields = 收货人姓名、收货手机号、收货地址、发票抬头、客服内部备注、风控标签 next_action = ask_clarification ``` 注意这里的 `next_action` 不是 `answer_user`。 因为工具查到了结果，但目标还不唯一。系统应该让用户选订单，而不是让模型替用户猜。 ### 例子三：商品工具返回了运营内部字段 再看商品咨询。 用户问： ```latex 那个降噪耳机现在还有货吗？适合通勤吗？ ``` 商品工具可能拿到： ```latex 产品编号 商品名称 售价 库存 活动信息 商品卖点 商品描述 供应商名称 毛利率 采购成本 活动预算 售后限制 场景标签 ``` 用户真正需要的是库存、价格、活动和适用场景。 Observation 可以变成： ```latex summary = 降噪蓝牙耳机当前有货，活动价 399 元，主打通勤降噪和长续航。 facts.product_id = P1001 facts.name = 降噪蓝牙耳机 facts.price = 399 facts.stock = 126 facts.suitable_scene = 通勤、地铁、办公室 omitted_fields = 供应商名称、毛利率、采购成本、活动预算、售后限制、长商品描述 next_action = answer_user ``` 如果后面第 22 课要把商品工具和 RAG 知识一起用，这个 Observation 也更好拼接：工具负责实时库存价格，RAG 负责稳定商品知识和活动规则依据。两边都短、干净、可追踪，回答才不会变成一锅接口字段汤。 ## 代码落地 ### 这一版 Agent 怎么改 本节代码快照在： ```latex code/agent-course-versions/lesson-20-tool-result-observation/backend/ ``` 第 20 课没有把 Observation 写回入口文件，而是在原有 `tools/tool_runtime.py` 旁边新增 `observability/observation.py`。工具执行层负责拿到内部 `ToolResult`，Observation 层负责把原始 payload 压缩成可进入回答上下文的摘要、关键 facts、`omitted_fields` 和 `next_action`。`models/answer_client.py` 只把压缩后的安全 Observation 交给真实模型生成最终回复，`agents/customer_service_agent.py` 只编排这条链路。 这仍然是在拆 LangChain Tool Calling 周边的关键机制。第 18 课已经解决“模型怎么提出 tool call”，本课专门看 tool call 执行之后，原始业务返回怎样先变成干净的 Observation，再进入模型上下文和用户回答。它不是另起一条长期手写 Agent 主链路，而是在把生产链路里的 Observation 层拆开讲。 关键链路是： ```latex /chat -> pre_tool_clarification(ChatRequest, intent) -> plan_tool_action(ChatRequest, intent) -> execute_tool_action(action, current_user_id) -> build_observation(tool_result) -> compose_grounded_answer(observation) -> ChatResponse(tool_calls, next_action) ``` `execute_tool_action` 返回内部 `ToolResult`。 这一版的 `ToolResult` 不是本地假数据表拼出来的，而是来自小哲电商后端接口和页面运行时上下文。比如订单列表页会把当前用户的候选订单带给 Agent，订单详情、物流详情和商品信息仍然通过只读业务接口查询。 它可能包含： ```latex order logistics product currentUserOrders ``` `build_observation` 会把它压缩成： ```latex summary facts omitted_fields next_action ``` 比如物流查询最终只保留： ```latex order_id logistics_status latest_event estimated_delivery ``` 完整物流事件、物流单号、当前用户完整订单列表、商品详情长文案和促销内部字段不会完整进入响应。 ### Observation 不是把结果变短这么简单 很多人第一次做工具调用，会把 Observation 理解成“把 ToolResult 摘短一点”。 这还不够。 Observation 至少要同时完成四件事： | 动作 | 为什么要做 | | --- | --- | | 筛选 | 只保留回答当前问题需要的字段。 | | 脱敏 | 去掉手机号、地址、内部备注、供应商字段。 | | 结构化 | 让后续回答、Trace、Eval 都能读同一组事实。 | | 留痕 | 记录哪些字段被省略，方便排查为什么没展示。 | 最小代码可以这样理解： ```python def build_observation(result: ToolResult) -> Observation: latest_event = result.data["logistics"]["events"][0] facts = { "order_id": result.data["order_id"], "logistics_status": result.data["logistics"]["status"], "latest_event": latest_event["description"], "estimated_delivery": result.data["logistics"].get("estimatedDelivery"), } return Observation( status=result.status, summary=f"订单 {facts['order_id']} 最新物流：{facts['latest_event']}", facts=facts, omitted_fields=["events", "trackingNo", "order.items"], next_action="answer_user", ) ``` 这段代码里最重要的不是字符串怎么拼，而是字段分流： + `facts` 是允许进入回答上下文的事实。 + `omitted_fields` 是明确不进入模型上下文的内部字段。 + `summary` 是给模型和调试视图看的短摘要。 + `next_action` 告诉系统拿到 Observation 后该怎么收口。 这样做以后，模型看到的是干净事实，不是整包接口返回。`build_answer()` 只保留为模型不可用、缺参数或没有 Observation 时的安全回退；正常路径里，用户看到的最终回答来自真实模型，但它只能依据压缩后的 Observation。 还有一层经常被漏掉：Observation 不是只管“少给模型看点东西”，还要先确认哪些事实可以被保守地放进回答上下文。 | 检查 | 小哲项目里的例子 | 不通过时怎么处理 | | --- | --- | --- | | 类型 | `logistics_status` 应该是可回答的公开状态，不是内部调试文本。 | 当前先不把异常内容包装成确定状态，回答时保守说明。 | | 完整性 | 只有订单状态，没有独立物流轨迹。 | 只保留已有事实，回答里说明暂未查到物流轨迹。 | | 合理性 | 退款进度不能同时是“已关闭”和“待审批”。 | 不合成一个看似完整的进度，改用保守摘要。 | | 权限 | 返回的订单必须属于当前 `runtime_user_id`。 | 不展示对象详情，按无权限收口。 | 比如物流结果里只有订单号和订单状态，没有独立物流轨迹。这个结果不能因为“已经调用过工具”就被包装成“快递正在运输中”。调试后台应该能看到工具调用发生了，也能看到 Observation 只形成了有限事实：订单是什么状态、缺了哪些物流字段。这样 Evaluation 才能检查：工具路径走过，不代表事实已经完整。 ### next_action 让系统知道下一步该做什么 第 20 课开始出现 `next_action`。 它先告诉当前这轮工具链路下一步怎么收口： | next_action | 含义 | | --- | --- | | answer_user | 工具结果够用，可以回答用户 | | ask_clarification | 参数不够，要先澄清 | | fallback_answer | 工具没拿到可用事实，只能兜底说明 | 当前事故先抓住一个关键点：工具结果拿回来以后，系统要知道是回答用户、继续追问，还是走兜底说明。 ## 怎么验证老板能闭嘴 这一课要验证的是：Agent 回答用户时只拿到压缩后的 Observation，而不是整包内部 ToolResult。 你发送： ```latex 查一下 SO20260602103000009-a1000009 的物流到哪了 ``` 你要观察到： + `tool_calls[0].observation.summary` 是压缩后的物流摘要。 + `tool_calls[0].observation.facts.latest_event` 来自真实物流接口的最新节点。 + `tool_calls[0].observation.omitted_fields` 记录了哪些内部字段没有进入模型上下文。 + `next_action = answer_user`。 如果用小哲电商客服 Agent 调试后台验证，页面展示的应该是 Observation 卡片，而不是原始 ToolResult。你应该能看到摘要、关键 facts、`omitted_fields` 和 `next_action`，但看不到完整物流事件、物流单号、订单明细或商品长文案。 ## 本节知识总结 ToolResult 与 Observation 的分离解决的是“工具结果不能原样进入模型”的问题。 工具返回的原始结果通常包含大量内部字段、诊断信息、供应商备注、成本中心或完整时间线。它们对系统排查有用，但不一定适合进入模型上下文，更不一定适合展示给用户。 通用做法是把原始 ToolResult 压缩成安全 Observation：只保留回答所需事实、公开摘要、遗漏字段说明和下一步动作。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | ToolResult | 工具原始返回，可能包含内部字段和完整诊断信息。 | 小哲物流工具可能返回完整物流轨迹、供应商备注、内部诊断字段。 | | ToolResult 契约 |
