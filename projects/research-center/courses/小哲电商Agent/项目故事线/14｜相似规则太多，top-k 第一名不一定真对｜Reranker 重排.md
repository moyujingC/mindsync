``` ## 技术机制 ### top-k 是候选，不是最终判决 前面几课里，top-k 很容易被读成“最相关的 k 条”。 但在生产检索链路里，它更像第一轮候选名单。 第一轮向量检索关心的是： ```latex 这段文字和用户问题像不像。 ``` 第 14 课要补的 reranker 关心的是： ```latex 在这些相似片段里，哪一段更适合作为最终依据。 ``` 放到小哲电商的事故里，reranker 要看更多细节： | 判断信号 | 为什么重要 | | --- | --- | | 当前规则还是历史复盘 | 过期活动不能当客服口径 | | 是否命中优惠券叠加条件 | 用户问的正是能不能叠券 | | 是否提到结算页约束 | 当前规则明确要求以结算页为准 | | 是否属于活动规则 | 商品介绍不能替代活动口径 | 这不是让模型再回答一遍。 它是在回答之前，先把候选证据排好队。 ### reranker 到底在重排什么 你可以先把第 10 课的向量检索想成“先粗找一批像的”。 向量检索会把用户问题和知识片段分别压成向量，再比较两个向量的距离。这样做很适合从很多知识里快速找候选，但它有一个天然弱点：它更擅长判断整体语义像不像，不一定擅长判断细粒度条件谁更适合当前问题。 比如下面两段都很像用户的问题： | 候选片段 | 为什么向量会觉得像 | 为什么最终依据不同 | | --- | --- | --- | | 2025 年耳机清仓活动 | 有耳机、活动、优惠券、叠加 | 这是历史活动，不能当当前客服口径 | | 2026 春季音频节规则 | 有耳机、当前活动、会员价、优惠券、结算页 | 正好回答当前能不能叠券 | 所以 reranker 不是重新去知识库里搜索。 它拿到的是已经召回出来的候选池，然后把“用户问题”和“每一个候选片段”放在一起重新判断： ```latex 用户问题 + 候选 A -> A 作为依据有多合适 用户问题 + 候选 B -> B 作为依据有多合适 用户问题 + 候选 C -> C 作为依据有多合适 ``` 很多真正的 reranker 模型会用这种成对判断方式。它不像 embedding 那样提前把问题和文档各自压成固定向量，而是让模型同时看到 query 和 document，再判断两者是否匹配。这个方向通常叫 cross-encoder reranker。 你不需要在这一课先背模型名。 你只要抓住工程含义： ```latex embedding 初召回：便宜、快，负责从很多知识里找候选。 reranker 精排：更细，负责在少量候选里判断谁更适合当前问题。 ``` 第 14 课直接接入商用 reranker，让专门的精排模型判断每个候选片段能不能作为当前问题的依据。这样更贴近生产：向量检索负责粗召回，reranker 负责精排，本地规则不再作为默认排序主路径。 ### reranker 不能解决什么 这也是为什么 reranker 只能救“正确片段已经进候选池，但排序不稳”的问题。 如果正确规则一开始完全没被召回，候选池里根本没有它，reranker 就没有东西可以重排。这个边界会自然引出第 15 课的 Hybrid RAG。 ## 代码落地 ### 商用 reranker 放在哪里 第 14 课把入口统一放在 `rerank_candidates`，它负责把召回后的候选池交给真实 `/rerank` 服务。 完整实现里的 `code/agent-backend/app/rag/knowledge_base.py` 已经接了商业 reranker。它的位置不是 `/chat` 一开始，也不是答案生成之后，而是在这里： ```latex 向量召回 -> score_threshold / 领域词过滤 -> 商用 reranker 精排候选池 -> build_citations(...) -> 把最终证据放进回答上下文 ``` 配置从环境变量来： ```plain AGENT_RAG_RERANK_ENABLED=true AGENT_RAG_RERANK_MODEL=Qwen/Qwen3-Reranker-8B AGENT_RAG_RERANK_BASE_URL=https://api.siliconflow.cn/v1 AGENT_RAG_RERANK_API_KEY=你的模型平台 Key AGENT_RAG_RERANK_INSTRUCTION=Given a customer-service query for XiaoZhe E-commerce, rank passages that directly support the answer higher... ``` 第 14 课按商用 reranker 主路径来讲。你需要把 `AGENT_RAG_RERANK_ENABLED` 设为 `true`，并提供可用的模型平台配置，才能走真实精排服务。 如果没有单独设置 `AGENT_RAG_RERANK_API_KEY`，代码会复用 `AGENT_OPENAI_API_KEY`。这表示聊天模型、Embedding 模型和 reranker 可以先共用同一个模型平台 Key；真正上线时，也可以给 reranker 单独配 Key、限流和预算。 商业 reranker 的请求体长这样： ```python payload = { "model": self.model, "query": query, "documents": [hit.content for hit in hits], "top_n": min(top_k, len(hits)), "return_documents": False, "instruction": self.instruction, } ``` 然后向 reranker 服务发请求： ```python response = client.post( f"{self.base_url}/rerank", headers={ "Authorization": f"Bearer {self.api_key}", "Content-Type": "application/json", }, json=payload, ) ``` 这里最关键的是三个字段： | 字段 | 含义 | 小哲项目里的边界 | | --- | --- | --- | | `query` | 当前检索问题，可以是改写后的检索表达。 | 用来判断相关性，不是系统 Prompt。 | | `documents` | 已经召回并过滤过的候选片段内容。 | 不是全量知识库，只是候选池。 | | `top_n` | 希望 reranker 返回前几条。 | 控制 citations 数量和上下文成本。 | reranker 返回结果时，通常会带回候选下标和相关性分数。 代码按 `index` 找回原来的 `KnowledgeHit`，再把 `relevance_score` 写成新的分数： ```latex 返回 index=2, relevance_score=0.91 -> 找回 hits[2] -> 更新 score -> 保留 source、title、snippet、metadata ``` 这样做有两个好处。 第一，reranker 只负责排序分数，不负责改写知识来源。citation 仍然来自原来的知识片段，证据链不会断。 第二，外部 reranker 没配置或调用失败时，系统会用本地规则重排做兜底补丁。它不是主方案，只是保证客服 Agent 不会因为精排服务超时，就把整个 RAG 回答链路打挂。 ### reranker 要不要写提示词 要分情况。 Reranker 不是聊天模型，它不会生成客服回答，所以你不要给它写“你是小哲电商公司的客服，请礼貌回答用户”这种系统 Prompt。 但很多商用 reranker 支持任务 instruction。这个 instruction 的作用不是让模型回答问题，而是告诉它“按什么标准判断 query 和 document 是否相关”。 小哲电商公司这种客服 RAG，排序标准不是通用语义相似就够了。你更希望 reranker 知道： + 用户问的是小哲电商公司的客服、售后、物流、发票、优惠、商品知识。 + 能直接回答当前问题的政策排前面。 + 售后场景不匹配的片段要降权，比如“签收后退货”不要被“未发货退款”覆盖。 + 实时订单、库存、价格、退款状态不能靠知识库判断，这类片段不能替代 Tool 事实。 + 历史活动、商品说明、FAQ 和正式政策要按当前问题的证据价值排序。 如果你接入的 reranker 支持 instruction，可以把任务说明写成类似这样： ```latex Given a customer-service query for XiaoZhe E-commerce, rank the candidate passages by how directly they support the answer. Prefer current policy, FAQ, shipping, after-sale, invoice, promotion, and product knowledge passages that match the user's exact business condition. Down-rank passages with mismatched after-sale scenes, historical activities, or content that cannot answer the current query. Do not treat realtime order status, inventory, price, payment, refund result, or approval outcome as knowledge-base facts. ``` 然后再把用户检索表达和候选片段交给 reranker： ```latex Query: 签收三天了不想要了还能退吗？ Document: 签收后 7 天内，在商品完好、不影响二次销售、配件齐全的情况下，通常可以申请退货。 ``` 不过这里有一个工程坑：**不同 reranker 的 instruction 写法不一样**。 有的服务只接受 `query` 和 `documents` 字段；有的支持单独的 `instruction` 字段；有的要求你把 instruction 拼进 query；有的模型文档会给固定模板。你不能把某个模型的 `<Instruct> / <Query> / <Document>` 格式当成所有 reranker 的通用标准。 所以更稳的做法是： 1. 先按模型服务文档接通最小请求。 2. 再确认它是否支持 instruction。 3. 如果支持，就把“小哲电商客服检索任务”的排序标准写进去。 4. 用 eval case 对比 instruction 前后的 citation 排序。 5. 只把稳定提升的 instruction 固化到配置里。 当前完整实现使用的是 `Qwen/Qwen3-Reranker-8B`，硅基流动 `/rerank` 接口也支持 `instruction` 字段，所以会直接把 `AGENT_RAG_RERANK_INSTRUCTION` 传给 reranker。这样做不是让 reranker 生成回答，而是让它把“相关性”理解成小哲电商客服证据标准。 rerank_reasons: list[str] = [] ``` `vector_score` 保留初召回分数，`rerank_score` 记录商用 reranker 返回的相关性分数，`rerank_reasons` 可以记录你在调试层补充的解释，例如命中了当前规则、历史活动被排到后面、结算页边界被识别出来。这样你不是只看到“排到第一了”，而是能解释它为什么可能排到第一。 商用 ranked_hits.append(hit.with_score(score)) ``` 这段代码的重点不是 `with_score` 这个写法，而是两个工程边界：第一，reranker 返回的是候选的排序结果，不是新知识；第二，citation 仍然必须来自原来的 `hit`，不能让外部模型重新生成证据来源。 ### 怎么判断问题出在召回、重排还是最终引用 第 14 这一课要让老板看到：正确规则不是因为“碰巧排第一”，而是经过候选合并和重排后被选中。 你发送： ```latex 那个耳机活动还能叠券吗？ ``` 你要观察到： + 初召回里仍可能出现历史耳机活动，这说明相似规则确实会撞车。 + 重排后，当前春季音频节规则被放到最前面。 + 重排原因能说清楚：历史活动被降权，当前规则、优惠券叠加条件和结算页约束被加权。 + 最终 citations 来自重排后的片段，而不是初召回里看起来最像的第一条。 ### 易混淆问题：历史活动可以出现但不能成为依据 历史耳机清仓活动不一定完全不能被召回。它和当前活动确实相似，所以出现在候选池里是合理的。 真正要验证的是： ```latex 相似历史规则可以进候选池，但不能压过当前规则成为最终依据。 ``` 你可以在调试状态里看 `rerank_reasons`：历史活动应该出现“历史活动降权”，当前活动应该出现“当前规则加权”或“结算页约束匹配”。 ### 边界问题：低置信时仍然不能硬答 再问一个和小哲知识库无关的问题： ```latex 小哲电商能不能帮我订机票？ ``` 这时你要观察到： + `citations` 为空。 + `confidence_level` 是 `low`。 + 回答承认没有足够可靠的小哲电商规则依据。 这说明第 14 课虽然新增了重排，但没有破坏第 12 课已经立住的低置信兜底边界。 ## 本节知识总结 Reranker 解决的是“候选已经找到了，但排序还不够准”的问题。 向量检索负责把相似候选找出来，但 top-k 第一名不一定就是最能回答当前问题的依据。尤其在活动规则、售后条款、商品说明很相似时，初召回常常会把当前规则、历史规则、相似场景一起带回来。
