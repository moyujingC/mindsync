代码落地 ### 当前 Agent 的实现边界 本课复用第 41 课综合演练版： ```latex code/agent-course-versions/lesson-41-final-rehearsal/backend/ ``` 本课专属交付材料： ```latex code/agent-course-versions/lesson-45-production-delivery-boundary/production_delivery_checklist.json ``` 验证链路是： ```latex delivery checklist -> 必须列出上线范围、验收证据、灰度、回滚、非目标 /eval/run -> 大促 9 条 case 全部通过 -> 其中 3 条 resume case 验证审批恢复边界 -> 退款 case 仍然保留 human_approval_required ``` ### 工程经验与设计取舍 第 45 课最大的取舍，是不把课程项目包装成“已经生产完美上线”。 更稳的项目表达是： ```latex 具备有限灰度上线条件。 ``` 但不能说： ```latex 完全无人值守、所有退款自动处理、所有活动规则自动更新。 ``` 小哲电商客服 Agent 当前能支持有限范围： + 常见 FAQ 和活动规则问答。 + 登录用户自己的订单物流查询。 + 退款申请资格判断和人工审批流。 + 异常、低置信和安全请求的转人工。 + Trace、Eval、Cost 作为上线验收证据。 它还不能替代售后主管、财务系统、知识运营后台或线上监控平台。 ### 核心材料拆解 `production_delivery_checklist.json` 里最重要的是三块。 第一块是上线决策： ```latex limited_gray_release_ready ``` 它说明当前是有限灰度，不是全量无人值守。 第二块是验收证据： ```latex tool_calls citations session_state.workflow trace_event_v1 eval_report_v1 cost_summary_v1 ``` 你要用这些证据证明系统走过正确路径。 第三块是非目标： ```latex real_money_refund_execution auto_approval_without_hitl full_finops_billing knowledge_ops_platform ``` 上线边界写得清楚，才不会把没有做的能力说成已经交付。 ## 怎么验证上线边界已经写清楚 按第 41 课后端的 `README.md` 触发评测后，你应该看到： ```latex eval_report_v1 passed = 6 failed = 0 ``` 再看交付清单： + 灰度入口是登录客服相关入口。 + 退款审批必须有售后主管。 + 回滚触发包含 eval 失败、工具错误、安全边界破坏和成本预警。 + fallback 是 `transfer_to_human`。 + 明确不做真实资金退款和无 HITL 自动审批。 你可以对老板说： ```latex 可以做有限灰度，但不是无边界全自动上线。 ``` ## 项目复盘追问 **追问：你怎么判断这个 Agent 能交付？** 回答：我先限定上线范围，再用固定 eval 和结构化证据做验收。Tool、RAG、Workflow、Trace、Cost 都有可检查字段；退款、高风险动作和异常场景都有转人工或人工审批边界。 **追问：如果上线后出事故怎么办？** 回答：先回滚到人工或旧流程，再用 trace 定位路径，用 eval case 固化事故，用反馈闭环归因到 Prompt、RAG、Tool、Context 或 Workflow，修复后再回归。 **追问：你这个项目最像生产系统的地方是什么？** 回答：不是页面效果，而是把上线边界写清楚：哪些场景可自动处理，哪些必须人工，哪些证据能验收，哪些能力还没有做。 ## 本节知识总结 生产交付解决的是“能跑”和“能上线”之间的差距。 一个 Agent 在演示环境能回答问题，不代表它可以无边界上线。上线前要说清楚适用范围、禁用范围、灰度策略、回滚条件、转人工路径和验收证据。 生产交付不是把功能包装得更漂亮，而是把责任边界写清楚，让业务、研发、运营和审核都知道系统能做什么、不能做什么、出问题时怎么退。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | 生产交付 | 从功能能跑变成范围、边界、证据和责任都清楚。 | 小哲客服 Agent 要说明哪些场景可灰度、哪些不能自动处理。 | | 灰度上线 | 先限定用户、场景、风险等级和流量范围。 | 小哲先在有限客服场景里试运行。 | | 回滚 | eval、工具、安全或成本异常时要能退回人工或旧流程。 | 小哲出现异常时退回人工客服或旧客服流程。 | | 转人工 | 降级、低置信和高风险流程要有明确兜底。 | 服务抽风、知识没命中、退款审批都能转人工。 | | 验收证据 | 上线验收要看可复查证据，而不是只看演示回答。 | `tool_calls`、`citations`、workflow、trace、eval、cost 都是验收材料。 | ## 上线边界不等于全量生产承诺 本课不创建真实发布平台。 不做自动灰度控制器。 不接入真实客服工单或告警系统。 不承诺 Agent 可以无人值守处理资金动作。 它只解决： ```latex 把小哲电商客服 Agent 从能跑，整理成可有限灰度、可验收、可回滚、可说明边界的交付方案。 ``` ## 小哲心中隐隐的担心 老板听完上线边界，没有再拍桌子。 他突然换了个表情： ```latex 那以后还能不能更强？ ``` 你知道，这个问题不能继续往主线里塞功能。 下一课，你要拿出升级路线图，讲清哪些方向值得做，哪些只是现在先不做。
