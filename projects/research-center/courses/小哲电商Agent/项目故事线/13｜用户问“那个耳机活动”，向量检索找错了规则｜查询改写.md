## 第四幕开始时的 Agent 形态 到第四幕开始时，Agent 已经有基础 RAG：能切片、能向量检索、能给 citations，也知道低置信时不能硬编。但它只是“能召回”，还不一定“召得准、排得对、更新得稳”。 这一幕只升级稳定知识检索质量：查询改写、Reranker、Hybrid RAG、索引更新和缓存。它仍然不把 RAG 当成订单、库存或审批系统。

## 运营拿来一张很短的截图 第三幕结束时，你已经让小哲电商客服 Agent 有了基础 RAG。 它能找知识、能返回 citations，也能在低置信时承认“依据不足”。老板终于不再一看到 AI 回答就问“它是不是编的”。 但运营同事很快又把截图递过来。 用户只问了一句：

```latex
那个耳机活动还能叠券吗？
```

上一版 Agent 确实去知识库里找了，也确实返回了引用。问题是，它把 2025 年真无线耳机清仓活动排到了前面。
运营当场急了：

> 用户说的是现在商品页上的降噪耳机活动，不是去年那个清仓活动。

> 老板看着你：

> 你不是说有向量检索了吗？怎么用户说“那个”，它就把旧规则翻出来了？

> 这次不是 citations 不见了，也不是完全没命中。
> 这次是用户说得太口语，检索问题太含糊。

## 用户原话不等于检索问题 第 12 课的 Agent 已经能判断低置信，也知道没有依据不能硬编。 但它还有一个默认假设：

```latex
用户怎么问，系统就拿这句话直接去检索。
```

这个假设在清晰问题里还行。
比如：

```latex
金卡会员买降噪耳机，会员价还能叠加优惠券吗？
```

这里有会员、商品、优惠券、叠加，向量检索能抓住不少信号。
可真实客服问题经常不是这样。用户会说：
- 那个耳机活动。
- 这个券还能不能用。
- 上次你们页面写的优惠。
- 我买那个蓝牙的，能叠吗。
这些话对人来说有上下文，对检索来说却缺了关键字段。
所以这一课你要把一件事拆开：

```latex
用户原话：保留给回答和客服语气。 检索问题：改写成更适合找知识的查询。
```

这个动作就是查询改写。

## 代码落地

### 这一版 Agent 怎么改 本节代码快照在：

```latex
code/agent-course-versions/lesson-13-query-rewrite/backend/
```

它沿用第 12 课已经出现的 RAG citations 和低置信兜底，只在检索前新增 `rewrite_retrieval_query`。
这一版的模块边界是：

| `knowledge_chunks.json` | 本课检索知识片段 | 这里开始换成 `knowledge_chunks.json`，不是说第 09、10 课的 Markdown 切片管线被废掉了。第 13 课要把注意力放在“同一批知识，原始 query 和改写 query 命中有什么不同”，所以先使用固定知识片段，减少知识切片本身带来的变量。 关键链路是：

```latex
/chat -> classify_intent(user_message) -> retrieve_knowledge(original_query) -> rewrite_retrieval_query(ChatRequest, intent) -> retrieve_knowledge(rewritten_query) -> build_citations(reliable_hits) -> render_rag_messages(...) -> call_chat_model(messages) -> ChatResponse
```

你可以看到，这一版没有改 `/chat` 请求格式。
阈值也跟前一幕不完全一样：`RETRIEVAL_SCORE_THRESHOLD = 0.2` 负责放宽候选入口，让原始问题和改写问题都能暴露相似候选；`LOW_CONFIDENCE_THRESHOLD = 0.5` 负责挡住知识库外问题的弱相关命中。它们是为本课固定知识片段和查询改写案例校准的演示值，不是从 0.28 / 0.68 推导出来的通用公式。
新增的是一段内部检索状态：

```python
class QueryRewrite(BaseModel): original_query: str rewritten_query: str applied: bool added_terms: list[str] reason: str
```

### 查询改写具体是怎么做的 小哲这版没有把查询改写做成一个神秘的模型黑盒，而是先用一段可观察的规则实现，让你看清楚它到底改了什么。 它的设计思路分成四层。 第一层，先把“用户怎么说”和“知识库怎么写”对齐。 用户说“叠券”，知识库里更可能写“叠加优惠券”；用户说“耳麦”，知识库里可能统一叫“耳机”。如果这些词不先对齐，后面补再多信息，检索也可能抓不到真正相关的规则。 第二层，先判断问题属于哪类场景，再决定补什么词。 查询改写不是所有问题都加同一批词。用户问活动叠券，应该补活动规则词；用户问退货，就应该补签收时间、退货条件、凭证，而不是硬塞“春季音频节”。 第三层，只补“检索需要的线索”，不替用户下业务结论。 “那个耳机活动还能叠券吗”缺的是当前活动、具体商品、会员价、优惠券叠加、结算页这些检索线索。系统可以补这些词，但不能在改写阶段直接写成“不能叠券”，因为那已经是答案，必须等知识命中和 citations 来支撑。 第四层，保留可排查证据。 改写结果不能只藏在后端日志里。第 13 课把 `original_query`、`rewritten_query`、`applied`、`added_terms` 和 `reason` 都放进内部检索状态，这样调试后台能看见：原话是什么、系统补了什么、为什么补、补完以后命中了哪条规则。 所以这次的目标不是“让问题看起来更完整”，而是让检索从一句含糊原话：

```latex
耳机活动还能叠加 优惠券吗？
```

变成一条带有关键线索的检索问题：

```latex
耳机活动还能叠加 优惠券吗 当前 2026 春季音频节 降噪耳机 会员价 优惠券 叠加 结算页 金卡
```

理解了这个设计，再看代码就很直接。
第一步是把用户原话做一次轻量归一化：

```python
NORMALIZATION_RULES = [ ("那个", "", "去掉缺少上下文的指代词“那个”"), ("耳麦", "耳机", "把用户口语“耳麦”对齐为知识库常用词“耳机”"), ("叠券", "叠加 优惠券", "把用户口语“叠券”展开为“叠加 优惠券”"), ("会员券", "优惠券", "把“会员券”归一到知识库里的“优惠券”"), ] def normalize_query(text: str) -> str: normalized = text.lower() for source, target, _reason in NORMALIZATION_RULES: normalized = normalized.replace(source, target) return normalized
```

这张表不只是做替换，也给后面的 `reason` 提供证据来源。第 13 课不是让后端写死一句“因为用户说得口语”，而是让后端记录本轮到底命中了哪些归一化规则。
第二步是先判断意图。第 13 课里，`classify_intent(user_message)` 会把包含“优惠、活动、会员价、券、满减、折扣”的问题识别成 `promotion_consult`。
第三步才进入核心函数：

```python
def rewrite_retrieval_query(request: ChatRequest, intent: Intent) -> QueryRewrite: normalized = normalize_query(request.user_message) added_terms: list[str] = [] rewrite_reasons: list[str] = [] if intent == "promotion_consult" and "耳机" in normalized: add_rewrite_terms(added_terms, ["当前", "2026", "春季音频节"]) rewrite_reasons.append("促销咨询提到耳机，补齐当前活动时间和活动名") add_rewrite_terms(added_terms, ["降噪耳机"]) rewrite_reasons.append("补齐知识库里的具体商品类目“降噪耳机”") add_rewrite_terms(added_terms, ["会员价", "优惠券", "叠加", "结算页"]) rewrite_reasons.append("补齐会员价、优惠券叠加和结算页边界") if request.runtime_member_level == "gold": add_rewrite_terms(added_terms, ["金卡"]) rewrite_reasons.append("运行时上下文显示当前用户是金卡会员")
```

这里的判断条件只有两个：

```latex
这是促销咨询。 归一化后的问题里提到了耳机。
```

满足以后，系统才把当前活动、年份、活动名、商品类型、会员价、优惠券、叠加关系、结算页边界补进检索问题。
如果调试后台当前用户是金卡会员，还会把“金卡”补进去。这个词不是凭空猜出来的，而是来自请求里的 `runtime_member_level`。也就是说，改写可以使用可信运行时上下文，但不能把用户没有说、系统也不知道的业务结论编进去。
同时，`reason` 不是某个分支里写死的一句话，而是由归一化命中、意图分支、补充词组和运行时上下文组合出来的说明。这样调试后台看到的“改写原因”，才对应这一轮请求真实发生了什么。
最后一步是拼出真正送去检索的文本：

```python
rewritten = ' '.join((part for part in [normalized, *added_terms] if part)).strip()
```

后面的答案仍然必须来自检索命中的知识块和 citations。
这一版的改写规则是透明的规则实现，方便你从代码里看见每个补词为什么出现。生产环境可以把这层升级成模型生成候选改写、词典维护、用户画像补全或多查询融合，但无论怎么升级，都要保留两条底线：不覆盖用户原话，不让改写结果直接变成业务结论。

### 原始问题要先留一份对照 代码里保留了一个对比：

```latex
retrieve_knowledge(original_query) retrieve_knowledge(rewritten_query)
```

第一次检索是为了让你看见上一版为什么会翻车。
原始问题只有“耳机、活动、叠券”这些词，2025 年旧活动也很像，所以它容易抢到第一名。
第二次检索才是这一版真正用于回答的结果。
它拿 `rewritten_query` 去找知识，当前的 2026 春季音频节规则会排到前面，citations 也来自这批可靠命中。
这就是查询改写在小哲项目里的工程位置：

```latex
不要让用户原话直接承担检索所需的全部精确信息。
```

## 怎么验证老板能闭嘴 这一课的验证不靠再解释一遍“向量检索已经接上了”，而是让同一个含糊问题在调试后台里露出前后对比。 你向 `/chat` 发送：

```latex
那个耳机活动还能叠券吗？
```

你要看到的证据是：
- 系统保留了用户原话，也记录了改写后的检索问题。
- 原始问题容易把旧耳机活动排到前面，这说明上一版翻车不是凭空编出来的。
- 改写后，当前春季音频节规则排到前面，引用来源也跟着指向当前规则。
- 回答仍然以小哲电商活动规则和结算页为边界，不把“能不能叠券”说成模型自己的判断。

## 本节知识总结 查询改写解决的是“用户原话不一定适合直接检索”的问题。 用户提问通常是口语化、含糊、有省略的。他会说“那个活动”“还能叠吗”“和之前一样吗”，但知识库里写的是正式规则名、商品类目、活动时间、权益条件和结算边界。检索系统如果直接拿用户原话去找，很容易被旧规则、相似商品或宽泛 FAQ 带偏。 查询改写的通用价值，是在不改变用户真实意图的前提下，把检索所需的关键信息补完整，让系统更容易找到正确依据。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 查询改写 | 把口语化、含糊、省略的用户问题改写成更适合检索的查询。

| “那个耳机活动还能叠券吗”被补成当前活动、降噪耳机、会员价、优惠券叠加等检索线索。

|
| 原始问题保留 | 改写不能覆盖用户原话，原始问题要保留，方便对照和排查。

| 小哲同时记录 `original_query` 和 `rewritten_query`。

|
| 检索意图补全 | 改写要补检索所需的实体、场景、时间、商品和规则词。

## 问题问清楚后，排序压力露出来了 这一版解决的是口语化、含糊问题带来的检索偏差。 但问题问清楚以后，多个相似规则会更容易一起被召回。 比如当前春季音频节、历史耳机活动、会员券说明都和“耳机活动叠券”有关。检索能把它们找回来，但 top-k 第一名不一定就是最终该用的那条。 小哲心里隐隐觉得：

> 把问题问清楚了，还不代表相似规则能排对。下一次翻车，可能不在 query，而在排序。
> >
