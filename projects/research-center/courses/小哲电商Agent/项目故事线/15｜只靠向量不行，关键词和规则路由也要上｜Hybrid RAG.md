# 只靠向量不行，关键词和规则路由也要上｜Hybrid RAG

## 售后主管说：这不是相似度问题，是漏了 第 14 课的 reranker 让活动规则排序稳了不少。 只要候选池里有正确规则，它就能把当前规则、过期规则、商品说明重新排队。 但售后主管很快丢来一个新问题：

```latex
耳机赠品少了，包装盒也压坏了，还能处理售后吗？
```

上一版 Agent 找到了“签收后 7 天无理由退货”，也找到了“质量问题售后”。
这两段都不是完全无关。
可售后主管说：

> 用户说的是赠品和包装盒缺失，不是普通无理由，也不是质量坏了。我们有专门的配件缺失规则。

> 你去看知识库，确实有一段：

```latex
耳机配件或赠品缺失售后
```

它的关键字是“配件、赠品、包装盒、压坏、凭证”。
问题在于：用户问题很短，向量相似度可能更偏向更常见、更长、更泛的售后规则。
这次不是排序没排好。
是正确规则差点没进候选池。

## 先分清：这次坏在候选池 第 14 课解决的是排序问题。 候选池里已经有正确规则，只是它没有排到最前面，所以你加了 reranker。 但这一次不一样。 如果“耳机配件或赠品缺失售后”一开始没有进候选池，后面再聪明的 reranker 也排不出它。 这就是第 15 课要补的缺口：

```latex
不是把候选排得更好。 而是让正确候选先被找回来。
```

Hybrid RAG 的重点不是“多加一个检索方法看起来更高级”。
它解决的是：单一路径容易有盲区，所以要让几条召回路径互相补位。
在小哲电商这类客服 Agent 里，常见盲区有三种：

| 盲区 | 事故表现 | 这一课怎么补 |
| --- | --- | --- |
| 场景混了 | 售后问题召回到活动规则或商品说明 | 先做规则路由，限制知识范围 |
| 关键词太具体 | “赠品”“包装盒”“7 天”这类边界词被语义相似度冲淡 | 增加 BM25 关键词召回 |
| 候选来源重复或冲突 | 向量和 BM25 各找回一批，需要合并去重 | 合并分数和来源，再选最终引用 | 所以这一课的 Hybrid RAG 可以先理解成一句话：

```latex
先判断该去哪个货架找，再同时用语义和 BM25 关键词找，最后把两份候选合成一份证据。
```

这一课先不急着展开完整 Agent 路由。
你只要先记住一件事：Hybrid RAG 不是用户问题一来就直接搜全库，而是先有一个检索计划。
这个计划至少要回答三个问题：

| 问题 | 小哲项目里的直觉 |
| --- | --- |
| 这轮该不该查知识库？

| 物流实时状态不该无脑查 RAG，售后政策和 FAQ 才需要依据。

|
| 应该去哪个知识范围里找？

| 售后问题优先查售后政策，不让活动规则和商品说明抢进来。

|
| 用户原话需要补哪些检索信号？

| “赠品少了”要补上“配件、包装盒、凭证、售后规则”等边界词。

| 后面等业务 Tool 和完整 Agent 路由出现后，这个“检索计划”还会继续接到更大的执行链路里。现在先把知识库内部这一步讲清楚。

## 技术机制

### 检索前先做规则路由 以前你只有一个笼统动作：

```latex
retrieve_knowledge(user_message)
```

这会让所有知识都站在同一个入口前竞争。
用户说“耳机赠品少了，包装盒也压坏了”，活动规则、商品说明、无理由退货、质量问题售后都可能带着“耳机”“退货”“包装”这些词挤进来。
但客服真正需要的是售后规则里的“配件与赠品缺失”。
所以现在要先做 pre-retrieval：

```latex
用户问题 -> 判断知识场景 -> 限制召回范围 -> 补齐检索关键词 -> 再做向量召回和 BM25 关键词召回
```

在小哲电商项目里，场景可以先粗分成：

| 场景 | 召回重点 |
| --- | --- |
| promotion | 活动、会员价、优惠券、叠加、结算页 |
| after_sale | 签收、退货、配件、赠品、包装盒、凭证 |
| shipping | 发货、物流、快递、现货、预售 |
| product | 商品介绍、型号、卖点 | 这里的“规则路由”不是业务工具路由。 它不会去查订单、退款、库存或物流。 它只是知识库内部的路由：

```latex
这句话更像在问哪一类稳定规则？
```

它还是知识库检索，只是先告诉检索系统：这轮应该优先在哪类稳定规则里找。

### BM25 关键词召回：把规则边界词拉回来 规则路由解决“去哪个范围找”。 接下来还要解决“用什么线索找”。 向量检索擅长找“意思相近”。用户说“耳机赠品少了”，它可能找回“售后”“退货”“质量问题”这些整体语义相近的片段。 但售后规则里有很多词不是靠意思近就够的。 它们本身就是边界条件：
- 赠品。
- 配件。
- 包装盒。
- 凭证。
- 结算页。
- 7 天。
这些词不是普通描述，而是客服判断能不能处理的规则边界。
如果用户说了“包装盒压坏”，你不希望系统只理解成“商品坏了”。
你希望它直接把“包装盒”“压坏”当成强信号，去抓那条专门规则。
所以这一课加上 BM25 关键词召回。
BM25 是传统搜索里很常用的一类关键词检索方法。
它不负责理解“这句话整体是什么意思”。
它更关心：

```latex
用户问题里的词，哪些出现在了这段知识里？ 这些词有多能区分当前规则？
```

你可以先不用背公式。
先把 BM25 理解成三层打分直觉：

```latex
1. 词命中了，就加分。 2. 越少见、越能区分具体规则的词，加分越高。 3. 一个词重复太多次，不会无限加分。
```

至于 BM25 后面的具体分数怎么计算，这一课不用展开推公式。
生产环境里通常也不会自己手写 BM25 算法，而是直接调用现成检索库或搜索引擎。
常见选择包括：

| 场景 | 可以用什么 |
| --- | --- |
| Python 教学或小规模实验 | `rank-bm25` 这类轻量库 |
| 后端全文检索 | Elasticsearch、OpenSearch、Lucene |
| 混合检索框架 | LangChain、LlamaIndex 里的 BM25 retriever 或 lexical retriever | 你在这一课要先理解的是：

```latex
BM25 分数可以交给现成库算。 工程上真正要想清楚的是：BM25 召回出来的候选，怎么和向量召回候选合并。
```

比如这次用户说：

```latex
耳机赠品少了，包装盒也压坏了
```

“耳机”很有用，但它太常见了。商品介绍、活动规则、售后规则里都可能出现“耳机”。
“赠品”“包装盒”“压坏”更关键，因为它们不是每条售后规则都有，反而能直接指向“配件与赠品缺失”这类规则。
所以 BM25 这一路不是在问：

```latex
这段话和用户问题整体像不像？
```

它问的是：

```latex
命中了哪些更能区分答案边界的词？
```

这就是它适合放进 Hybrid RAG 的原因。
向量召回负责找语义相近的候选。
BM25 召回负责把规则边界词拉进候选池。
如果用户把“赠品缺失”说成“少了一个赠品”，向量召回可能找到泛泛售后规则。
但 BM25 看到“赠品”“少了”“包装盒”“压坏”，会把含有这些关键词的配件缺失规则强行拉回来。
第 15 课代码的向量路已经接入 OpenAI 兼容 embedding，用 cosine similarity 计算 `vector_score`。
但 BM25 关键词路没有接入外部 BM25 库，而是把这个思想压成了一个很轻的本地实现。
`rare_terms` 里的词，比如“赠品”“包装盒”“压坏”，命中一次给更高分；普通词命中一次给普通分。
它没有实现完整 BM25 的文档长度归一化、词频饱和、全库逆文档频率这些细节。
但它保留了关键词召回最重要的工程目的：

```latex
BM25 不是为了替代向量召回。 它是为了把那些很短、很硬、很能决定规则边界的词拉进候选池。
```

“包装盒”“赠品”“压坏”比“耳机”“活动”更能定位具体售后规则。
于是同一个问题会被拆成两路去找：

```latex
向量召回：这段规则和用户问题整体像不像？ BM25 召回：这段规则有没有命中关键边界词？
```

向量召回负责宽一点，避免用户换个说法就找不到。
BM25 关键词召回负责硬一点，避免关键规则词被泛泛语义盖过去。
这两个不是互相替代。
它们是在同一个售后范围里，从不同角度把候选抓回来。

### Hybrid RAG 到底混合了什么 现在可以把 Hybrid RAG 拆成四步看：

```latex
1. pre_retrieval_plan 判断 scene，得到 allowed_topics 和 keyword_terms 2. vector_retrieve 在 allowed_topics 里找语义相近的候选 3. keyword_retrieve 在 allowed_topics 里做 BM25 关键词召回，找命中规则关键词的候选 4. merge_hybrid_hits 合并同一个 chunk 的来源、关键词和分数，选出最终引用
```

用这次事故跑一遍，大概是这样：

```latex
用户问题： 耳机赠品少了，包装盒也压坏了，还能处理售后吗？ pre_retrieval_plan: scene = after_sale allowed_topics = ["after_sale"] keyword_terms = ["配件", "赠品", "少了", "包装盒", "压坏", "凭证", "售后"] vector_retrieve: 可能找回无理由退货、质量问题、配件缺失这些售后候选 keyword_retrieve: 会用 BM25 关键词支路强命中“赠品”“包装盒”“压坏”，把配件或赠品缺失规则抓回来 merge_hybrid_hits: 发现“耳机配件或赠品缺失售后”同时有售后场景、关键词来源和当前规则加分
```

最后进入回答上下文的，不是“所有看起来相似的片段”，而是合并后的可靠引用。
这就是 Hybrid RAG 的工程含义：

```latex
先缩小正确范围，再扩大召回方式，最后收敛成可引用证据。
```

## 这一版 Agent 怎么改 本节代码快照在：

```latex
code/agent-course-versions/lesson-15-hybrid-rag/backend/
```

这一版的模块边界是：

| 文件 | 作用 |
| --- | --- |
| `main.py` | 应用启动和路由挂载 |
| `api/schemas.py` | `RetrievalPlan`、`KnowledgeHit`、`Citation`、请求和响应结构 |
| `api/routes.py` | `/health`、`/capabilities`、`/chat` |
| `agents/customer_service_agent.py` | pre-retrieval、Hybrid RAG、citations 和回答编排 |
| `embeddings/client.py` | OpenAI 兼容 embedding 客户端和文本向量缓存 |
| `rag/knowledge_base.py` | `knowledge_chunks.json` 读取 |
| `rag/planning.py` | 场景识别、`allowed_topics`、`keyword_terms` |
| `rag/hybrid_retrieval.py` | `vector_retrieve`、`keyword_retrieve`、`merge_hybrid_hits` |
| `rag/prompting.py` | Hybrid RAG Prompt 和 citations |
| `models/llm_client.py` | OpenAI 兼容聊天模型调用 |
| `config/settings.py` | 路径、top_k、embedding 默认配置、低置信阈值和统一课程环境 |
| `knowledge_chunks.json` | 本课检索知识片段 | 关键链路是：

```latex
/chat -> classify_intent(user_message) -> pre_retrieval_plan(ChatRequest, intent) -> vector_retrieve(plan) -> keyword_retrieve(plan) -> merge_hybrid_hits(plan, vector_hits, keyword_hits) -> build_citations(reliable_hits) -> generate_stable_rag_answer(messages) -> ChatResponse
```

这一课为了聚焦 Hybrid RAG，`intent` 先沿用轻量规则分类；第 04 课的小模型兜底分类和后续 RoutePlan 机制不在本课展开。这里的 `scene` 是检索场景，不是完整业务决策。
你可以这样区分：`intent` 回答“用户想做什么”，比如退款、咨询活动；`scene` 回答“该去哪类知识里找依据”，比如售后政策、活动规则。一个退款意图通常会落到售后场景，但 `scene` 不代表系统已经决定要执行退款动作。
本课的 `LOW_CONFIDENCE_THRESHOLD = 0.34` 也要放在 Hybrid RAG 里理解。分数已经混合了向量召回、关键词召回、路由加权和有效期加权，不能继续沿用第 13/14 课只看向量或重排分数时的 0.5。这里的阈值是为了让“多路证据合并后的可靠命中”留下来，同时挡住没有足够证据的问题。
`pre_retrieval_plan` 会生成：
- `scene` + `allowed_topics` + `rewritten_query` + `keyword_terms` 这四个字段分别回答四个问题：

| 字段 | 回答的问题 | 例子 |
| --- | --- | --- |
| `scene` | 这轮更像哪类知识问题？

| `after_sale` |
| `allowed_topics` | 哪些知识片段允许参与召回？

| `["after_sale"]` |
| `rewritten_query` | 原问题要补哪些检索信号？

| 补上“售后规则、配件、赠品、包装盒、凭证” |
| `keyword_terms` | 哪些词要按规则边界强匹配？

| “赠品、包装盒、压坏、凭证” | 当用户问“赠品少了、包装盒压坏”，它会把场景判断成 `after_sale`，并把召回范围限制在售后知识。 这能避免活动规则、商品介绍和物流 FAQ 抢进来。 `retrieve_knowledge` 的分工也更清楚：

```latex
pre_retrieval_plan 负责决定怎么找。 vector_retrieve 负责找语义相近的候选。 keyword_retrieve 负责承载 BM25 关键词召回，抓规则关键词。 merge_hybrid_hits 负责合并和排序。
```

`keyword_retrieve` 里的 `raw_score / 8` 是课程版的轻量归一化，不是 BM25 公式本身。它只是把多个关键词命中的累计分数压回 0 到 1 之间，方便和向量分数放在同一个调试视图里比较。真实项目通常会用搜索引擎或 BM25 库返回自己的相关性分数，再通过固定问题集重新校准。
`merge_hybrid_hits` 先取 `max(vector_score, keyword_score)`，不是因为两路结果必须互相同意，而是为了保留“任一路召回强证据”。向量抓住语义、关键词抓住边界词，二者是互补关系；后面的场景和有效期加权再告诉你：这个强证据是否落在本轮允许的业务范围里。
如果把这套能力放回后续 Tool Calling 阶段，citations 还应该记录 `retrieval_stage`：

| 阶段 | 含义 |
| --- | --- |
| `pre_retrieval` | 后端根据路由结果主动预检索出来的依据。

|
| `tool_retrieval` | Agent 执行中调用 `retrieve_knowledge` 二次补查得到的依据。

| 这样调试后台和 trace 才能看懂：这条知识是系统提前兜住的，还是 Agent 运行中发现缺依据后补查的。 注意这里的 `vector_retrieve` 已经负责真实 embedding 向量召回；`keyword_retrieve` 才是本课为了讲清 BM25 角色而保留的轻量关键词实现。生产环境通常会把向量存进专门的向量库，把 BM25 交给搜索引擎，但链路边界不变：

```latex
向量召回负责语义候选。 BM25 关键词召回负责边界词候选。 规则路由负责先把检索范围收住。
```

## 怎么验证老板能闭嘴 这一课要验证的是“正确规则有没有被召回进候选池”，不是只看最终回答顺不顺。 你发送：

```latex
耳机赠品少了，包装盒也压坏了，还能处理售后吗？
```

你要观察到：
- 检索计划先把问题判断成售后场景，而不是活动、商品或物流。
- 召回范围被限制在售后知识里，避免商品介绍和活动规则抢进来。
- “配件或赠品缺失”这条规则能进入可靠引用，而不是被泛泛的七天无理由退货盖过去。
- 命中来源里能看出 BM25 关键词召回发挥了作用：包装盒、赠品、压坏这些词本身就是规则边界。

## 本节知识总结 Hybrid RAG 解决的是“单一检索方式各有盲区”的问题。 向量检索擅长处理语义相近，但可能漏掉规则关键词、编号、边界条件和长尾说法。BM25 关键词检索擅长抓明确词汇和稀有边界词，但不理解近义表达。规则路由能先限定场景，避免无关知识抢进候选池。 混合检索的通用价值，是让不同召回方式互相补短板：先判断场景，再用向量找语义相似，用关键词抓规则边界，最后合并、去重、排序。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| Hybrid RAG | 组合向量、BM25 关键词和规则路由，减少单一检索方式的漏召回。

| 小哲把售后问题限制在售后知识里，再合并向量和 BM25 关键词命中。

|
| 预检索计划 | 检索前先判断场景、允许范围、改写查询和关键词。

| `pre_retrieval_plan` 生成 scene、allowed_topics、rewritten_query 和 keyword_terms。

|
| 向量召回 | 负责找语义相近的候选。

| 用户换说法时仍能找回相近售后规则。

|
| BM25 关键词召回 | 负责抓规则词、边界词和长尾业务词。

| “赠品”“包装盒”“压坏”帮助命中配件或赠品缺失规则。

|
| 合并排序 | 多路召回后要去重、合并分数、保留来源证据。

| 小哲能看到命中是来自 vector、keyword 还是合并结果。

|
