课之后，小哲电商客服 Agent 已经有工具箱了。 它能调用 `get_order_logistics` 查物流，也能调用 `get_product_inventory` 查库存。 老板刚夸完你两句，客服群里又炸了。 用户发来一句： ```latex 我的快递到哪了？ ``` Agent 一看，这是物流问题。 但它没有订单号。 更糟的是，这个用户名下有两笔订单： ```latex 已经知道用户大概要做什么，但继续执行还缺一个关键条件，所以先暂停本轮动作，向用户追问具体字段，或者让用户从可信候选里选一个。 ```latex 用户意图大致清楚 -> 关键参数缺失或对象有歧义 -> 不猜、不调用高风险工具 -> 问用户补充或选择 -> 用户补齐后继续执行 ``` 比如“查一下我的物流”已经能判断是物流查询，但缺订单号；“查我 6 月那笔订单”可能查出多笔候选，也不能让模型自己选。 这就是澄清：用一次可恢复的追问，把不确定性变成明确参数。 这一课开始，澄清不再只靠本地关键词规则。LLM 会先介入，输出一个结构化的 `ClarificationPlan`：它判断用户大概想做什么、可能要用哪个工具、已经说了哪些参数、还缺哪些参数，以及应该怎么追问。 但 LLM 不是最终裁判。它只提出计划草案，后端仍然要用工具契约、当前登录用户和真实业务结果重新校验。 ### 不确定性处理要先停住 关键不是“缺订单号时问一句”。 你要建立一个更重要的判断：Agent 缺信息时，不能为了显得聪明而继续执行。生产系统里，停下来澄清往往比快速给错答案更可靠。 | 这次要补上的能力 | 你要能说清楚什么 | | --- | --- | | 生产问题 | 用户问题经常缺参数或有歧义，乱选订单会查错对象，甚至泄露隐私。 | | 本项目实现 | LLM 先输出 `ClarificationPlan`；`pre_tool_clarification` 按 ToolSpec 复核缺参；`post_tool_clarification` 在工具返回多个候选后要求用户确认。 | | 当前边界 | 澄清是可恢复状态，不是工具失败；候选只辅助用户选择，不替用户自动决定。 | | 错误说法 | “当前用户只有几个订单，Agent 选一个最可能的就行。”这是错的，尤其不能用于退款、退货和补偿。 | ### 工具调用前先问清楚 工具调用不是越快越好。 真正的客服系统里，缺关键参数时应该先停下来；如果用户给了月份这类低风险条件，也只能先查候选，再让用户确认目标。 这里让 LLM 参与，是因为真实用户不会都按规则说话。有人说“五月买的那个音箱”，有人说“上次那单退款到哪了”，本地关键词很快就会变成一堆补丁。LLM 更适合先把自然语言整理成结构化草案。 你可以先把工具调用前澄清理解成： ```latex 用户问题 -> LLM 输出 ClarificationPlan -> 后端按 ToolSpec 检查必填参数 -> 参数缺失 -> 先澄清，不调用工具 ``` 这一课的关键不是让 Agent 更会聊天，也不是让模型自己决定一切。 关键是让模型负责理解语言，让后端负责守住执行边界，不把不确定当确定。 ### 工具调用后也要确认唯一目标 还有一种澄清发生在工具调用之后。 这时系统不是完全缺参数，而是用户给了一个可以查询的范围，但工具返回的结果仍然不唯一。 比如用户说： ```latex 查一下我 6 月那笔订单 ``` 这里的“6 月”已经足够让系统做一次低风险候选查询。Agent 可以调用 `search_current_user_orders`，但这个工具查到的是候选订单，不是最终目标订单。 如果返回了多笔订单，系统不能把第一笔当成用户要查的订单，也不能让模型根据商品名、状态或历史聊天猜一个“最可能”的结果。 所以工具调用后澄清的链路是： ```latex 用户给了可查询范围 -> 先调用候选查询工具 -> 工具返回多个候选对象 -> 保留本轮 tool_calls -> 返回 clarification，让用户确认目标 ``` 它和工具调用前澄清的区别在于：工具调用前澄清是“参数不够，先不查”；工具调用后澄清是“已经查到候选，但目标还不唯一”。 两者的共同边界是：候选只能来自当前用户的可信业务数据，不能来自模型猜测；候选只能帮助用户选择，不能替用户选择。 ## 代码落地 ### 这一版 Agent 怎么改 本节代码快照在： ```latex code/agent-course-versions/lesson-19-tool-clarification/backend/ ``` 第 19 课继续沿用第 18 课的工具契约和执行层，但把“澄清规划”单独拆出来：`models/clarification_planner.py` 调用 LLM 生成 `ClarificationPlan` 草案，`tools/planning.py` 负责重新校验工具名、必填参数和当前用户上下文，`tools/tool_runtime.py` 只执行已经通过校验的只读工具。工具结果可用时，`models/answer_client.py` 再把 `ClarificationPlan`、Tool Action 和 Observation 交给真实模型生成最终回复。这样你能看清楚：模型负责理解和表达，后端负责约束和执行。 这里是机制拆解：第 18 课已经让实时事实查询进入 LangChain Tool Calling，本课为了讲清楚“缺参数不能硬调工具、候选结果不能让模型代选”，把 LangChain 工具循环中的澄清判断单独摊开。后续完整链路不是放弃 LangChain，而是把这层澄清和校验接回 LangChain 工具执行链路。 关键链路是： ```latex /chat -> ClarificationPlannerModelClient.plan_clarification() -> ClarificationPlan(intent, tool_name, known_arguments, missing_required) -> pre_tool_clarification(ChatRequest, ClarificationPlan) -> plan_tool_action(ClarificationPlan) -> execute_tool_action(action, ChatRequest) -> post_tool_clarification(action, observation) -> compose_grounded_answer(plan, action, observation) -> ChatResponse(clarification, tool_calls) ``` `ClarificationPlan` 是模型的计划草案，不是可直接执行的命令。`pre_tool_clarification` 会在工具执行前按 ToolSpec 重新检查必填参数。`post_tool_clarification` 会在工具已经返回候选结果之后，再判断是否还需要用户确认目标。 先看工具调用前澄清，可以拆成五步： | 步骤 | 系统做什么 | | --- | --- | | 1. 生成计划草案 | LLM 输出意图、候选工具、已知参数、缺失字段和追问草案。 | | 2. 找到工具契约 | 后端根据候选工具拿到 `ToolSpec`，看这个工具需要哪些必填参数。 | | 3. 过滤已知参数 | 只保留工具允许的字段，丢弃模型输出的 `user_id` 等越界参数。 | | 4. 复核缺什么 | 如果必填参数缺失，先不生成 Tool Action。 | | 5. 返回澄清状态 | 返回 `clarification_field`、追问问题和可信候选，同时保持 `tool_calls = []`。 | 当用户没说订单号时，它返回： ```latex clarification_field = order_id candidates = 电商后端校验过的当前用户真实订单 ``` 这时 `tool_calls` 是空的。 因为 Agent 还没有足够参数，不能先查一个看起来最像的订单。 当用户补充： ```latex 查 SO20260603110000010-a1000010 的退款进度 ``` Agent 才会继续生成工具 Action，并执行 `get_refund_status`。 如果用户没有直接给订单号，但给了一个可安全查询的范围： ```latex 查一下我 6 月那笔订单 ``` Agent 会先调用 `search_current_user_orders`，只查询当前用户名下 6 月的候选订单。这个工具调用会保留在 `tool_calls` 里；如果返回多笔候选，`post_tool_clarification` 再返回 `clarification_field = order_id`，要求用户确认具体订单。 ### 缺参数要分三种情况 “缺订单号”不是唯一的澄清场景。 工具调用前，你至少要分清三种状态： | 状态 | 例子 | 系统动作 | | --- | --- | --- | | 参数完整 | “查 SO20260602103000009-a1000009 的物流” | 继续生成 Tool Action。 | | 参数缺失但可提供候选 | “我的物流到哪了”且当前用户有多个订单 | 返回候选，让用户选择。 | | 参数缺失且没有候选 | “我的退款怎么样”但当前用户没有可查售后单 | 说明缺少必要信息，不调用工具。 | 所以 `pre_tool_clarification` 不是简单判断字符串里有没有订单号。 它要结合 LLM 计划、ToolSpec 和当前用户事实： ```python def pre_tool_clarification(request: ChatRequest, plan: ClarificationPlan) -> Clarification | None: spec = TOOL_SPECS[plan.tool_name] missing = find_missing_required_fields(spec, plan.known_arguments) if "order_id" not in missing: return None candidates = list_current_user_orders(request.runtime_user_id) return Clarification( clarification_field="order_id", question="你要查哪一个订单？", candidates=candidates, ) ``` 这里有两个边界要守住。 第一，候选只来自当前登录用户的业务数据，不从模型记忆里猜。 第二，候选只帮助用户补全参数，不代表系统替用户选择。 如果当前用户名下只有一个订单，也不建议在高风险场景里自动选中。物流查询可以更宽松，但退款、退货、补偿这类动作要更保守，因为选错对象的代价更高。 如果澄清规划模型不可用，本课不会回退到旧规则路径继续猜。系统会明确告诉你澄清规划不可用，并且不生成 Tool Action。这是为了让这一课的主线保持清楚：澄清机制从这里开始由 LLM 参与规划，后端负责校验和执行边界。最终回答模型不可用时，系统才回退到 `build_answer()` 的安全话术。 ### 候选订单也要来自当前用户 候选列表不是从历史聊天里猜出来的。 它来自当前用户的本地确定性业务数据。 这能守住两个边界： + 只能展示当前登录用户名下的候选订单。 + 候选只是帮助用户澄清，不代表系统自动替用户选择。 这一课只讲 `clarification_field` 和 `candidates`。 后面你会看到 `next_action`，但现在还不需要它。 ### 工具执行后也可能需要澄清 前面已经讲过工具调用后澄清：工具已经执行了，结果却不够唯一。 比如用户说“查一下我 6 月那笔订单”，系统按时间查到了多笔候选订单。此时不能让模型自己选第一笔，也不能把候选当成已确认订单保存。 正确做法是保留本轮已经发生的工具记录，把已知条件和候选项作为结构化 `clarification` 返回。真实产品里，上层应用可以把它做成文本追问或候选选择，但本课不展开前端交互，重点只看 Agent 有没有停止硬猜。 本课代码里的对应链路是： ```latex 用户说“6 月那笔订单” -> LLM 规划 search_current_user_orders -> 后端校验月份参数 -> execute_tool_action 返回 candidate_orders -> post_tool_clarification 把候选订单转成 clarification.candidates -> ChatResponse 同时包含 tool_calls 和 clarification ``` | 类型 | 发生时间 | 系统动作 | | --- | --- | --- | | 工具前澄清 | 必填参数还没凑齐 |
