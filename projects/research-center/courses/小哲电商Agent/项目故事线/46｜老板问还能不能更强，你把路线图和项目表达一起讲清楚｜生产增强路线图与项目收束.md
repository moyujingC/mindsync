生产增强路线图 老板问“还能不能更强”时，他不一定在问模型参数。 他更可能在问： ```latex 活动规则谁维护？ 售后政策改了怎么发布？ 用户差评怎么变成下一轮改进？ 运营主管怎么知道 Agent 哪些问题答得不稳？ 大促成本和人工兜底怎么一起管？ ``` 所以路线图先从运营侧拆开。 | 运营环节 | 生产环境中怎么做 | 为什么重要 | | --- | --- | --- | | 活动规则运营 | 做活动规则录入、适用人群、起止时间、互斥关系、发布状态和回滚记录。 | 活动规则变化快，必须可审核、可追溯。 | | 售后政策运营 | 把退款、退货、补偿、会员权益做成可审核、可生效、可追溯的政策版本。 | 政策影响资金和承诺边界，不能靠口头通知进模型上下文。 | | 知识质检 | 让运营看到 citation 缺失、低置信兜底、用户追问失败和人工修正建议。 | 低置信不是结束，而是知识缺口回流入口。 | | 反馈闭环 | 把差评、客服质检、主管改写和事故复盘沉淀成新 case、知识修订和 Prompt/RAG/Tool 改进任务。 | 反馈要变成可复盘任务，而不是聊天记录里的一句抱怨。 | | 成本与人效运营 | 统计轻路径、重路径、转人工、缓存命中和高频 FAQ 的成本与人效变化。 | 成本治理要和风险分层一起设计，不能为了省钱绕过审批。 | | 权限与审计 | 区分客服、运营、售后主管、管理员能看什么、改什么、发布什么。 | 权限设计不清会暴露内部 SOP、隐私或高风险操作。 | 这样讲，路线图就不再是“再接几个高级组件”。 它变成了小哲电商公司生产运营体系的升级清单。 ## 别把高级词混成一锅 高级路线图里最容易出问题的不是“不知道这些词”，而是把它们讲成同一种增强。 你要把它们分成四类： | 类别 | 包含方向 | 主要解决什么 | | --- | --- | --- | | 知识治理 | 知识运营后台、多知识库权限 | 知识谁能改、谁能看、怎么发布和回滚。 | | 检索基础设施 | RAG Fusion、BM25 / ES、ANN | 召回更全、精确匹配更稳、大规模检索更快。 | | 成本与稳定性 | 缓存、路径分层、热门问题优化 | 高频请求更便宜，但不绕开风险边界。 | | 组织与学习闭环 | Feedback Loop、RLHF 边界、Subagents | 事故如何回填，角色如何分工，哪些属于模型训练。 | 几个词尤其容易误讲。 `RAG Fusion` 不是简单“多查几次”。它通常是用多个 query 或多个召回器拿到候选，再做合并、去重和重排。它解决的是召回覆盖问题，但会增加检索和 rerank 成本。 `BM25 / ES` 不是向量检索的低级替代品。它擅长商品名、政策编号、活动词、订单状态这类关键词精确匹配，适合和向量检索组成 Hybrid RAG。 `ANN` 不是一个新业务能力。它是向量检索规模变大后的近似最近邻索引方案，主要在延迟、召回、内存和索引更新之间做取舍。 `Feedback Loop` 是运营和工程之间的闭环。用户差评、客服质检、主管改写和 trace 证据先变成可复盘的 case，再推动知识、Prompt、RAG、Tool 或流程改进。 `RLHF` 也不是“把用户差评加进 Prompt”。小哲当前做的是反馈闭环：收集事故、归因、回填 case、做回归。RLHF 属于模型训练范畴，需要偏好数据、训练流程和评估体系。 `Subagents` 不是把一个 Agent 拆得越多越高级。只有当质检、知识运营、退款审核这些职责真的稳定、权限边界清楚、归因链路能打通时，拆分才有价值。 ## 把项目讲成工程能力 路线图讲完，老板的问题就变成： ```latex 那你怎么把这个项目讲清楚？ ``` 这不是普通结课感言。 真正要落住的是：你能不能把一个 Agent 项目讲成生产级工程能力，而不是讲成“我调了 Prompt、接了 RAG、用了 Tool”。 如果项目介绍里只说： ```latex 我做过一个电商客服 Agent，用了 RAG 和 Tool。 ``` 这句话太轻。 更像项目的表达是： ```latex 我设计并实现了一个小哲电商客服 Agent，支持稳定知识 RAG、实时业务 Tool、售后 Workflow/HITL、审批恢复、Trace 可观测、Evaluation 回归、失败归因、成本治理和安全降级。 ``` 这句话里每个词都能被项目文件和运行证据支撑。 你还要能把整套知识架构压成一张工程图： ```latex 用户问题 -> /chat 会话入口 -> Intent / Risk / Context 判断 -> 稳定知识走 RAG -> 实时事实走 Tool -> 高风险动作走 Workflow / HITL -> 回答前做 Context Builder / Safety -> 全程留下 Trace -> 用 Eval 和 Feedback Loop 回归 -> 用 Cost Summary 看成本和路径 ``` 这张图里每一层都有自己的责任： | 层次 | 解决的问题 | 不能替代什么 | | --- | --- | --- | | `/chat` 入口 | 接住会话、用户身份和响应结构。 | 不能替代业务判断。 | | Intent / Risk | 判断问题类型和风险级别。 | 不能替代真实权限校验。 | | RAG | 找稳定知识依据。 | 不能回答实时订单状态。 | | Tool | 查实时业务事实。 | 不能自动执行高风险写动作。 | | Workflow / HITL | 管退款、审批、恢复这类受控流程。 | 不能省略人工审批边界。 | | Context / Safety | 组织上下文、隔离脏指令和敏感信息。 | 不能把隐藏推理暴露出去。 | | Trace / Eval | 证明发生了什么，防止改一处炸一片。 | 不能只靠主观感觉判断质量。 | | Cost | 看路径、token 和缓存是否合理。 | 不能为了省钱跳过风控。 | 这样讲，项目就不再是“我用了几个大模型名词”。 它变成了一套可解释的业务 Agent 架构。 ## 简历表达怎么写 你可以把简历亮点写成这样： | 简历亮点 | 背后的项目证据 | | --- | --- | | 实时事实和稳定知识分层 | 物流走 Tool，活动/会员规则走 RAG | | 高风险售后流程受控 | 退款进入 Workflow/HITL，审批恢复用 checkpoint 和幂等 | | 行为可观测可回归 | `trace_event_v1`、`eval_report_v1`、固定 cases | | 失败可归因 | 用户反馈绑定 trace/eval 并回填 case | | 成本可治理 | `cost_summary_v1` 区分轻路径、重路径、缓存和 Observation 压缩 | | 安全边界明确 | Prompt Injection、低置信、降级和转人工边界清楚 | 不要写成“熟悉大模型客服”。 要写成你解决了什么工程问题。 前面的场景课已经把能问的技术追问放在验证过程中问掉了。 最后一课不再补题，而是把这些场景证据收成一套完整工程能力：你能解释系统为什么这样拆，风险为什么这样控，证据为什么能证明它可靠，后续路线为什么值得这样排。 ## 配套材料 材料目录： ```latex code/agent-course-versions/lesson-46-advanced-roadmap/ ``` 材料文件： ```latex advanced_roadmap.json project_wrap_up.json ``` 本课不新增 Agent 后端。 `advanced_roadmap.json` 整理生产增强方向、适用场景、优先级和取舍。 `project_wrap_up.json` 整理简历表达、完整工程能力、项目亮点、成长路线和全课总结。 ## 个人成长路线 这门课的成长路线，其实也是你做 Agent 项目的成长路线。 第一步，能把模型调用接成服务。 第二步，知道 Prompt 只能约束口径，不能替代业务事实。 第三步，能用 RAG 处理稳定知识，用 Tool 处理实时事实。 第四步，知道高风险动作必须进入 Workflow/HITL。 第五步，能处理 Memory、Runtime Context、Context Builder 和安全隔离。 第六步，能用 Trace、Eval、失败归因和 Cost 证明系统行为。 第七步，能把生产边界和增强路线图讲清楚。 这时候，你讲的就不是“我会调模型”。 你讲的是： ```latex 我能把 Agent 放进一个真实业务系统里，并让它可控、可查、可评、可交付。 ``` ## 全课总结 小哲电商客服 Agent 一开始只是一个会聊天的模型。 它会说话，但不知道公司规则。 它能接 `/chat`，但状态还很粗。 它靠 Prompt 救火，但越写越重。 它用 RAG 找稳定知识，又学会 citation 和低置信兜底。 它接入 Tool 查询订单、物流、库存这些实时事实。 它把退款、退货、补偿这些高风险动作交给 Workflow/HITL。 它学会 Memory、Runtime Context、Context Builder 和安全隔离。 它留下 Trace，跑 Evaluation，做失败归因，控制成本。 最后，它进入大促总演习，能把 Tool、RAG、Workflow、HITL、Trace、Eval、Cost 和安全边界连成一条完整证据链。 这就是小哲电商 Agent 生死局真正要你带走的东西： ```latex Agent 不是会聊天就能进业务。 Agent 要能接入业务、查询事实、处理流程、接受审批、留下证据、评测回归、控制成本、说明边界。 ``` ## 本节知识总结 生产增强路线图和项目表达解决的是“项目做完后，怎么继续规划，又怎么讲得站得住”。 一个 Agent 项目做完主线后，后续增强方向会很多：知识运营、检索基础设施、多知识库权限、缓存、成本治理、反馈学习、Subagents。路线图不是把热门名词堆上去，而是说明每个方向解决什么问题、什么时候值得做、代价是什么。 简历和项目答辩里，真正有价值的也不是罗列 RAG、Tool、LangGraph、Trace、Eval 这些名词，而是讲清楚：业务问题是什么，你怎么拆系统，关键风险怎么处理，用什么证据证明它可靠，哪些边界没有夸大。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | 高级路线图 | 只讲方向、适用场景、优先级和取舍，不把高级词当主线堆料。 | 小哲把知识运营、RAG 增强、反馈闭环和 Subagents 放进生产增强路线图。 | | 项目表达 | 用业务问题、工程拆分、关键难点和验证证据讲项目。 | 小哲项目从客服事故讲到 RAG、Tool、Workflow、Trace、Eval 和 Cost。 | | 简历表达 | 简历亮点要有工程问题和项目证据支撑。 | 实时事实分层、高风险流程、可观测、可回归、成本治理和安全边界。 | | 完整工程能力 | 能把入口、事实、流程、上下文、安全、观测、评测和成本串成系统。 | 小哲能说明 RAG/Tool 分工、HITL 边界、Trace/Eval 证据、Cost 治理和安全降级。 | | 成长路线 | 能从模型调用讲到可交付 Agent 系统，说明工程成熟度。 | 主线从能聊天，走到能查事实、控流程、可观测、可评测、可交付。 | | 全课收束 | 收束时要说明能力边界，不把项目包装成无边界的万能客服。 | 小哲 Agent 能说明边界和灰度条件，不声称无人值守处理所有客服问题。 | 到这里，小哲电商客服 Agent 的主线收束。 老板看完路线图和项目表达，沉默了一会儿。 他终于意识到，小哲不是“会调模型的开发”，而是已经摸到了小哲电商公司下一阶段客服 Agent 的核心科技：业务事实怎么接、风险流程怎么控、知识怎么治理、事故怎么回归、上线边界怎么写。 于是老板没有再说“加点工资”。 他换了一种说法： ```latex 股票和期权，你选一个。 ``` 小哲笑了笑。 你也终于知道，下一次再遇到一个真实业务 Agent 项目，你不是从“会不会调 Prompt”开始。 你会先问： ```latex 业务事实在哪里？ 风险边界在哪里？ 证据链在哪里？ 出了事故怎么回归？ 上线边界怎么写清楚？ ```
