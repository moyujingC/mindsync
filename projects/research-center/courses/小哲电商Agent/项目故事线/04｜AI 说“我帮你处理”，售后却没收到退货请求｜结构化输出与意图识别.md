所以这一次先别急着做完整退货流程，也别急着自动建售后单。 小哲电商 Agent 现在最需要补的是第一块分拣牌： ```latex 这句话是不是退货退款类问题？ ``` ## 这一版只先做一件事 前面你已经把 `/chat` 接进来了。 上一版你让第一版 AI 客服站上了前台，也看到了它会乱承诺、乱接业务话题。 这一轮改造只做第一步： ```latex 自然语言回答 -> 粗意图标签 ``` 也就是让系统先知道： + 这是普通聊天？ + 这是活动咨询？ + 这是商品咨询？ + 这是订单或物流查询？ + 这是退款售后？ + 这是投诉？ + 还是暂时看不懂？ 先做到这个程度就够了。 售后主管现在缺的不是一套自动退货流程，而是一个最基础的信号： ```latex 这条消息应该先进入售后退款这一类。 ``` 只要这个信号没有返回，客服网关就没法分拣，售后队列也不知道该接住这件事。至于下一步怎么处理、风险高不高、缺不缺订单信息，要等系统真的能识别出“这是退货退款类消息”之后再继续往下做。 ## 自然语言回复不能替系统分拣 看这三句客服回复： ```latex 我帮你看一下。 我可以协助你处理。 这边会尽快为你跟进。 ``` 它们听起来都很像客服话术。 但对系统来说，它们几乎没有可执行价值。 因为系统不知道： ```latex 这是问优惠？问订单？要退款？还是在投诉？ ``` 你不能让客服网关去解析“我会帮您处理”这几个字，然后自己猜是不是退款。这样做迟早会被模型换一种说法搞崩。 所以我们先给 `/chat` 响应加一个最小结构化字段： ```latex intent：用户这句话的大类 ``` 这不是完整流程编排。 它只是让系统从“只能看一句客服话术”进化到“至少知道这是一条退货退款类消息”。 ## 这一次响应多了什么 前面你已经用 Pydantic 的 `BaseModel` 固定了 `/chat` 请求和响应格式。Pydantic schema 是用 Python 类写出来的数据结构约定。你可以先把它理解成一张“字段说明书”：它规定结果里有哪些字段、字段是什么类型、哪些取值是允许的。 现在同一套方式要继续用在意图分拣结果上：让客服网关读到稳定的字段，而不是一段随模型说法变化的文字。 最早的 `/chat` 响应只证明入口能通： ```python class ChatResponse(BaseModel): session_id: str answer: str reasoning_summary: list[str] session_state: dict[str, Any] ``` 从这一版开始，响应旁边多一个粗意图结果： ```python class ChatResponse(BaseModel): session_id: str answer: str intent: Intent intent_result: IntentResult reasoning_summary: list[str] session_state: dict[str, Any] ``` 这里先只新增两个字段： | 字段 | 系统怎么用 | | --- | --- | | `intent` | 给这条用户消息打一个大类标签，例如退款、投诉、订单查询。 | | `intent_result` | 保存这次粗分拣的细节，例如来自规则还是分类模型、置信度是多少、为什么这么分。 | 现在先不要急着让 Agent 判断“该怎么处理”。这次事故先暴露了一个更靠前的问题：用户已经发出退货退款诉求，但系统没有可读标签，客服网关就不知道该把它分到售后退款这一类。 所以这一版先把 `intent` 稳定返回。系统先知道“这是退货退款类消息”，后面才能继续判断能不能退、要不要补订单号、要交给谁处理。 ## 先把标签格式定死 你当然可以让模型或规则随便写一个标签： ```json { "意图": "用户可能想退一下吧" } ``` 这看起来也像结构化，但系统没法稳定消费。 今天叫“退款”，明天叫“售后”，后天叫“用户不满意”，客服网关和调试后台都会跟着变。 所以这里要先把“意图结果的结构”定死。 这个固定格式，在代码里就是一个 Pydantic schema。请求或响应不符合这张说明书时，系统就能尽早发现，而不是把乱七八糟的标签继续传给客服网关。 所以小哲电商 Agent 需要一个很小的 Pydantic schema： ```python Intent = Literal[ "general_chat", "promotion_consult", "product_consult", "order_query", "refund_request", "complaint", "unknown", ] IntentSource = Literal["rules", "classifier", "rules_fallback"] class IntentResult(BaseModel): intent: Intent source: IntentSource confidence: float matched_keywords: list[str] = Field(default_factory=list) explanation: str ``` 这已经够了。 `intent` 保证标签只能从固定枚举里选。 这里还有一个很实用的工程经验：让模型生成的字段值，尽量直接带真实语义。 比如意图识别不要设计成这样： ```latex 1 = 退货退款 2 = 活动咨询 3 = 投诉 ``` 这种数字编码对程序当然也能用，但它把业务含义藏在另一张映射表里。模型、日志、调试后台、评测 case 和下游规则都要记住“1 到底代表什么”。一旦有人改了映射，或者模型生成了一个不在映射表里的数字，排查会很别扭。 所以本课直接用： ```latex refund_request promotion_consult complaint ``` 这些值读起来就知道业务含义。模型被要求从这些语义化候选里选，调试后台也能直接显示 `intent=refund_request`，测试用例也能直接断言这条消息进了售后退款类。即使后面数据库或 BI 系统需要数字编码，也应该在系统内部再做转换，而不是让模型直接生成没有业务语义的 `1`、`2`、`3`。 `source` 说明这次标签来自规则还是分类模型。 `confidence` 是这次粗判断的置信度，方便系统区分“高确定性分拣”和“不太确定的兜底判断”。 `matched_keywords` 方便你排查这次为什么会被分到这一类。 `explanation` 给小哲自己看，说明这只是粗判断，不是业务结论。 你会发现，这里仍然没有处理动作。 现在的小哲电商 Agent 还只是第一版分拣器。它先把 `intent` 稳定住，比提前写一堆看起来很完整、实际却没有业务依据的字段更重要。 ## 当前代码的实现入口 当前代码快照在： ```latex code/agent-course-versions/lesson-04-intent-structured-output/backend/ ``` 相比最早的聊天入口，这一版新增了粗意图识别： | 文件 | 作用 | | --- | --- | | `main.py` | FastAPI 应用装配和启动入口 | | `api/schemas.py` | `IntentResult`、`ChatRequest`、`ChatResponse` 契约 | | `api/routes.py` | `/chat` 薄入口 | | `agents/customer_service_agent.py` | 规则优先、小模型兜底，并把结构化意图交给最终回答模型 | | `models/classifier_client.py` | 分类模型 messages 构造、JSON 解析和兜底调用 | | `models/answer_client.py` | 基于 `IntentResult` 调用真实大模型生成克制客服回复 | | `config/settings.py` | 课程共享配置读取 | 这一版还是只放 Agent 后端。相比第 03 课，它新增的是 `models/classifier_client.py`、`models/answer_client.py` 和响应里的 `IntentResult`：自然语言先被变成系统可读的意图，再把这个结构化意图作为最终回答模型的事实边界。 调试后台依旧是外部调用方。你启动这一版 Agent 后端后，让小哲电商客服 Agent 调试后台指向当前服务，就能看到 `/chat` 响应里多了结构化意图。 ## 核心代码拆解 这一版的关键链路是： ```latex /chat -> ChatRequest -> classify_intent(user_message) -> plan_intent_by_rules(user_message) -> classify_intent_with_model(user_message) -> IntentResult -> build_answer(intent_result) 生成安全回退文本 -> compose_grounded_answer(user_message, intent_result) -> ChatResponse ``` 你要按这个顺序读代码。 现在不是在做完整客服决策器，而是在做第一版分拣器。它只负责把用户问题放进一个粗意图里。 先看意图结果。系统真正消费的不是一段客服话术，而是这个结构： ```python class IntentResult(BaseModel): intent: Intent source: IntentSource confidence: float matched_keywords: list[str] = Field(default_factory=list) explanation: str ``` `intent` 是标签，`source` 说明来源，`confidence` 表示确定程度，`matched_keywords` 和 `explanation` 留给排查。 再看规则层： ```python INTENT_RULES: list[tuple[Intent, list[str], str]] = [ ( "complaint", ["投诉", "举报", "赔偿", "曝光", "315", "别踢皮球"], "用户表达了投诉、赔偿或强烈不满，规则高置信标记为投诉类消息。", ), ( "refund_request", ["退款", "退货", "取消订单", "坏了", "无法开机", "质量问题"], "用户在询问退款、退货或质量问题，规则高置信标记为售后退款类消息。", ), ... ] ``` 这里不是“关键词全包”，也不是“所有问题都交给大模型猜”。小哲电商采用的是和项目主线一致的思路： ```latex 规则优先 -> 高置信直接返回 规则不确定 -> 小模型兜底分类 ``` 订单物流、退款、投诉、优惠、商品咨询这类高确定性场景，不需要每次都让模型自由判断。规则能稳稳命中时，系统直接返回 `source="rules"` 和较高 `confidence`。 分类和回答拆开，是为了让系统更容易控。分类只判断“这句话属于哪类问题”，可以用更轻的模型；回答负责把分类结果说成客服能给用户看的话，需要更自然、更克制。以后排查时，分错类和说错话也能分开看，不会混成一个“模型没答好”的黑盒。 规则顺序也有一点讲究。投诉类放在退款类前面，是因为用户可能会说： ```latex 我要退款，你们再不处理我就投诉。 ``` 这句话里既有退款，也有投诉。第一版分拣器虽然很粗，但至少要先把强烈不满标出来。注意，这里只是标成 `complaint`，还没有把消息交给人工队列。 再看命中逻辑： ```python def plan_intent_by_rules(user_message: str) -> IntentResult | None: ... for intent, keywords, explanation in INTENT_RULES: matched = first_matched_keywords(message, keywords) if matched: return IntentResult( intent=intent, source="rules", confidence=0.95, matched_keywords=matched, explanation=explanation, ) ``` 这段代码做的事情很直白：按顺序检查规则，找到关键词，高置信命中就返回一个 `IntentResult`。 如果规则没有高置信命中，才进入小模型兜底： ```python model_result = classify_intent_with_model(user_message) if model_result: return model_result ``` 这个小模型不是客服执行器。它只负责补一个结构化标签： ```latex intent confidence explanation ``` 它不能执行工具，不能批准退款，不能把“想退货”直接变成售后单。 如果分类模型不可用或输出不符合 schema，这一版才退回 `unknown`。这里也不要急着追问用户；如果信息不够，系统以后再学会追问，现在先承认当前版本看不懂。 ## 怎么让大模型只识别 intent 规则兜不住的问题，通常不是完全陌生，而是表达更绕。 比如用户说： ```latex 金卡买这个会不会更划算一点？ ``` 这句话没有直接出现“优惠”“活动”“折扣”这些规则关键词，但你能看出来它大概率在问会员权益或价格优惠。 这类问题适合交给小模型做兜底分类。 但这里的关键不是问大模型“你觉得用户想干嘛”，而是把它约束成一个很窄的分类器： ```latex 只判断 intent 只从固定候选里选 只输出 JSON 输出后再由后端 schema 校验 ``` 本课代码里，小模型入口是： ```python def classify_intent_with_model(user_message: str, ...) -> IntentResult | None: ... ``` 它用的模型名来自课程共享配置 `AGENT_CLASSIFIER_MODEL`。 正课里不用展开模型平台配置，你只要看清这条边界： ```latex 分类模型可以参与判断，但不能执行工具、不能批准退款、不能临时发明标签。 ``` 发给分类模型的 messages 大致是这样： ```python [ { "role": "system", "content": ( "你是小哲电商客服 Agent 的轻量意图分类器。" "只输出 JSON，不要输出 Markdown。" "你只能判断用户消息的大类，不能执行工具、不能批准退款、不能承诺售后动作。" ), }, { "role": "user", "content": ( "请把下面用户消息分成一个粗意图。\n" f"允许的 intent 只能是：{allowed_intents}\n" "输出 JSON 格式：{\"intent\": string, \"confidence\": number, \"explanation\": string}\n\n" f"用户消息：{user_message}" ), }, ] ``` 这里有三个设计点。 第一，`system` 明确把模型关进“轻量意图分类器”这个角色里。它不能把 `refund_request` 理解成“已经可以退款”。 第二，候选标签来自固定枚举： ```python allowed_intents = ", ".join(Intent.__args__) ``` 模型只能在系统认识的标签里选，不能临时发明“用户有点烦躁想售后一下”。 第三，Prompt 约束不是最终保证。 模型可能在 JSON 外面多写一句话，也可能把 JSON 包进代码块，甚至写出 schema 里没有的 intent。所以工程链路必须继续往后走： ```latex Prompt 约束格式 -> 解析模型文本 -> Pydantic schema 校验 -> 不合法就兜底 unknown ``` 代码不是拿到模型文本就直接信，而是先解析 JSON，再构造 `IntentResult`： ```python payload = parse_classifier_json(content) if payload is not None: return IntentResult(...) ``` 如果 `intent` 不在枚举里，或者 `confidence` 不是合法数字，Pydantic 会挡住它。`parse_classifier_json` 则负责处理 JSON 外包代码块这类常见格式毛边。 如果配置缺失、模型超时、输出不是合法 JSON，当前版本会退回： ```latex source = "rules_fallback" intent = "unknown" ``` 这比硬塞进某个类别更安全。 分拣系统最怕的是： ```latex 看起来有结果，其实分错队列。 ``` 回答生成也要配合这个边界。第 04 课不是只用模板回复，`build_answer()` 先生成安全回退文本，然后 `models/answer_client.py` 会把用户消息、`IntentResult` 和课程边界交给真实大模型，让模型基于结构化意图组织客服话术： ```python def build_answer(intent_result: IntentResult) -> str: if intent_result.intent == "refund_request": return "我已经先把这条消息识别为退款或售后类问题。当前版本还没有接入售后规则和订单状态，不能直接判断是否可退。" ``` 这段文本不是主路径的“假客服回答”，而是模型不可用时的安全回退。你可以把这里理解成双保险：每次请求先准备好 `build_answer()` 这张安全网，再尝试让 `compose_grounded_answer()` 生成更自然的客服回答；如果模型配置缺失、超时或返回空，安全网接住这一轮。正常配置真实模型后，最终回答来自 `compose_grounded_answer()`，但模型只能根据 `IntentResult` 和课程边界说话：它可以解释“这类问题已经被识别出来”，不能承诺“退款已经处理”。 最后看主流程： ```python intent_result = classify_intent(request.user_message) deterministic_answer = build_answer(intent_result) model_answer = compose_grounded_answer( user_message=request.user_message, deterministic_answer=deterministic_answer, intent_result=intent_result, ) answer = model_answer.answer return ChatResponse( session_id=request.session_id, answer=answer, intent=intent_result.intent, intent_result=intent_result, reasoning_summary=reasoning_summary, session_state=session_state, ) ``` 这里继续把用户可见回答和系统可读状态分开： ```latex 用户看到 answer 系统读取 intent 和 intent_result 调试后台读取 session_state.model_answer ``` 不要让系统从 `answer` 里猜意图。 也不要让用户话术承担系统状态。 `session_state` 仍然只保存这一轮运行状态，其中最重要的是 `next_gap`： ```python "agent_version": "lesson-04-intent-structured-output", "message_count": message_count, "runtime_context": {...}, "next_gap": "系统知道消息大类，不代表已经知道下一步该怎么处理。" ``` 它提醒你：这一版只会分拣，还不会安排下一步。 这个缺口不是靠多塞几个空字段解决的，而是要等系统真的接入售后规则和订单事实后再补。 ## 怎么验证老板能闭嘴 这一版要让系统第一次看到的东西很简单：不是 AI 说得好不好听，而是退货退款诉求能不能被标成 `refund_request`，投诉诉求能不能被标成 `complaint`。 现在验证的不是“回答一定正确”，也不是“流程已经能跑”。 现在只验证一件事： > 系统能不能把退货退款诉求标成可读的 `refund_request`。 > 你要看到： 1. `POST /chat` 返回 `200`。 2. 响应体包含 `intent` 和 `intent_result`。 3. 退款类问题会标成 `refund_request`。 4. 投诉类问题会标成 `complaint`。 5. 响应体只包含当前版本真正能解释清楚的字段，不提前摆出还不会用的处理动作。 6. 售后主管不用再从一句“我会帮您处理”里猜这是不是退货退款。 老板这次终于能看到： > AI 不只是会说话，系统也能知道这是一条售后退款类消息。 > 但你心里很清楚，这还不够。 系统知道“这是退款问题”，不代表它知道“能不能退”。 系统知道“这是投诉”，不代表它已经能转人工。 ## 本节知识总结 结构化输出是所有 AI 应用从“能聊天”走向“能被系统使用”的关键一步。 自然语言适合给人看，但系统不能稳定消费自然语言。今天模型说“我可以帮您看看退款问题”，明天它可能说“这边会协助您核实售后诉求”。人能看懂这两句话差不多，程序却很难可靠判断它们是不是同一类业务信号。 所以当 AI 的输出要进入业务流程、自动分拣、数据看板、工具调用或后续决策时，就要把一部分结果做成结构化字段。 结构化输出的通用链路是： ```latex 先定义字段和允许取值 再约束模型或规则只产出这些字段 然后用 schema 校验 最后为失败情况准备兜底 ``` 这不是为了让返回结果看起来更“工程化”，而是为了让 AI 结果可以被其他系统稳定读取。没有结构化输出，后续系统只能从回答话术里猜；有了结构化输出，系统才能明确读取 `intent=refund_request`、`confidence=0.95`、`source=rules` 这样的信号。 但结构化输出也有边界。分类标签只说明“这句话像哪类问题”，不说明“这件事已经处理完成”。`refund_request` 不是退款批准，`complaint` 不是已经转人工，`order_query` 也不是已经查到了订单。 | 知识点 | 核心概念 |
