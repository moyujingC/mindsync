# 失败了先别乱改，用户差评也不是白挨骂｜失败归因与反馈闭环

## 差评来了，先定位是哪一层坏了 第 38 课之后，你已经有了固定评测。 物流、退款、安全这几类关键 case，每次改动后都能跑。 你刚觉得自己终于不用靠手感改 Prompt，客服群里又炸了。 一个用户给了差评：

```latex
客服说退款已经到账，但我根本没有收到。
```

售后主管补了一句：

```latex
这单还在人工审批，谁让它说到账了？
```

老板看着你：

```latex
这次别跟我说“模型偶尔会这样”。你告诉我，到底是哪一层坏了。
```

你知道，失败以后最危险的动作，就是立刻乱改 Prompt。
因为它可能不是 Prompt 问题。
它可能是 RAG 依据错了。
可能是 Tool 没查。
可能是 Runtime Context 被用户自称覆盖。
可能是 Workflow 没停在 HITL。
也可能是评测期望写得太窄。

## 这次事故背后的 Agent 问题 失败归因要落到模块。 小哲电商 Agent 至少有这些归因方向：

| 失败现象 | 优先看哪里 |
| --- | --- |
| 回答乱承诺、口径越界 | Prompt 边界 |
| 引用缺失、政策依据错 | RAG 检索和 citations |
| 物流、订单、库存没有查 | Tool 路径和参数 |
| 用户自称 VIP 被相信 | Runtime Context / Context Builder |
| “刚才那个订单”串台 | Memory / Context |
| 退款没停在人工审批 | Workflow / HITL |
| 只有措辞不符合 case | Evaluation 期望 | 所以目标不是做一个更大的评测平台。 而是把失败闭环补上：

```latex
用户反馈 -> 绑定 trace -> 绑定 eval case -> 自动生成初步归因 -> 人类确认归因和修复方向 -> 回填新的 eval case -> 后续持续评测
```

这里最关键的动作，是先停一下。
你不要一看到差评就改 Prompt。
也不要一看到 eval 失败就改 case。
正确顺序应该是：

```latex
先看用户到底看到了什么 再看当时 trace 走过什么 再看已有 eval 覆盖了什么 最后才决定改实现、改知识、改工具，还是补评测期望
```

这里的归因不是让大模型自己当裁判。
第 39 课代码里的 `FailureAttributor` 只是根据用户反馈、公开 Trace 和 Eval 失败类别做自动初判，帮你把事故先放到可能的模块篮子里。真正要不要认定为 Prompt 问题、RAG 问题、Tool 问题、Context 问题、Workflow 问题，仍然需要人类质检、开发或课程里的“小哲”去复核证据。
关键不是“多收集反馈”。
你要先把失败变成可判断的工程对象。

## 反馈不能只是客服备注 很多团队会把用户差评当成一段文本：

```latex
用户不满意，后续优化。
```

这对 Agent 没用。
小哲电商 Agent 需要的是结构化反馈记录：

```latex
session_id case_id rating user_comment observed_answer trace_event_names eval_failure_categories attributions backfilled_case
```

`session_id` 让反馈能找到当时的 Trace。
`case_id` 让反馈能对照已有 Evaluation。
`observed_answer` 保存事故现场看到的坏回答。
`attributions` 把问题落到具体模块。
`backfilled_case` 把事故变成下一轮回归用例。
但 `attributions` 不是最终裁决。
它更像一张待确认的事故分析单：系统先把证据、可能模块和建议修复方向列出来，人类再确认“是不是这个模块的问题”“应该改实现还是改知识”“这个事故是否值得长期沉淀为回归 case”。
这也是反馈闭环和普通客服备注最大的区别。
普通备注只回答：

```latex
用户为什么不满意？
```

结构化反馈要继续回答：

```latex
这次不满意能不能复现？ 它有没有对应 trace？ 已有 case 有没有覆盖？ 如果没覆盖，应该新增什么 case？ 修复以后怎么防止它回来？
```

只有回答到这一步，差评才真的进入 Agent 工程系统。

## 代码落地

### 当前 Agent 的实现边界 本节代码快照在：

```latex
code/agent-course-versions/lesson-39-failure-attribution-feedback/backend/
```

这一课在 Eval 之后新增 `feedback/` 包。反馈路由只接入请求，真正的归因规则放在 `feedback/attribution.py`；它会读取 Trace 和 Eval 结果，把事故先自动归到 Prompt、RAG、Tool、Context 或 Workflow，再生成一个可供人类确认的回填 case。
Workflow/HITL/Resume 仍然是上一阶段留下来的能力。第 39 课新增的是“失败之后怎么归因和回填”，不是让反馈接口去批准退款，也不是让差评绕过 `/chat/resume`。
关键链路是：

```latex
/feedback/submit -> TraceStore.list(session_id) -> EvalRunner.run(case_id) -> FailureAttributor.attribute(...) -> build_backfilled_case(...) -> 人类确认后进入长期回归维护 -> FeedbackSubmitResponse(record, eval_report) /eval/run -> fixed cases.yml + feedback backfilled cases
```

第 39 课是在 Eval 后面接一段事故处理链路。
为了让课堂能直接看到闭环，示例代码会在提交反馈后立即返回 `backfilled_case`。真实团队里，这一步通常还要经过人工确认：先看 Trace 和 Eval 证据，再决定是否把它写进长期维护的 `cases.yml` 或缺陷单，而不是把每条差评都自动变成正式测试。

### 核心代码拆解 `FeedbackRequest` 是反馈入口。 它要求提交：

```latex
session_id case_id rating user_comment observed_answer
```

这里的 `observed_answer` 很重要。
它代表事故现场看到的坏回答，不是让评测流程伪造当前 Agent 的输出。
线上事故经常来自旧版本、灰度版本或人工截图。反馈闭环要能接住这些外部证据，再用当前代码回归验证修复是否守住边界。
`FailureAttributor.attribute` 会把反馈、trace 和 eval 结果放在一起看。
它不是一个神奇的模型裁判。
这一课里它更像一张排查路线图。
当证据显示高风险动作没有停住，优先看 Workflow / HITL。
当证据显示政策依据缺失，优先看 RAG 和 citations。
当证据显示实时事实没有查，优先看 Tool 路径和参数。
当证据显示身份、会员等级、上一轮订单串了，优先看 Runtime Context、Memory 和 Context Builder。
当路径都对、只是 case 写得过窄，才回头看 EvaluationExpectation。
比如反馈里出现：

```latex
已退款成功 已到账 直接退款 不用审批
```

归因器会把它落到两个模块：

```latex
Workflow: high_risk_boundary Prompt: overpromise
```

这不是说“模型不好”。
而是说：

```latex
高风险售后边界没有被回答层守住，必须回到 workflow / HITL 和 Prompt 边界修。
```

如果反馈说“没有依据”“引用错了政策”，优先归到 RAG。
如果 eval 发现工具路径不匹配，归到 Tool。
如果反馈提到 VIP、自称身份、刚才那个订单或上下文串台，归到 Context。
如果路径都对，只有回答措辞没有命中 case，就先看 Evaluation 期望是不是过窄。
`build_backfilled_case` 会把事故回填成新的 case。
退款越界反馈会生成类似这样的期望：

```latex
expected_signals: 人工审批 expected_trace_events: workflow_completed, human_approval_required, cost_recorded expected_session_state: workflow.pending_action=require_approval forbidden_text: 已退款成功, 已到账, 直接退款
```

这样用户这次骂得很痛，但不会白挨。
它会进入下一轮回归。
这里也要注意一个边界。
回填 case 不是把所有用户情绪都变成测试。
只有能代表真实业务风险、可复现路径或重要边界的反馈，才值得沉淀成长期回归。
否则评测集会越来越臃肿，最后每次改动都跑得很慢，却抓不住真正高风险的问题。

## 怎么验证失败归因能指导修复 按本课代码目录的 `README.md` 启动后端后，先发一轮退款问题：

```latex
SO20260601090000008-a1000008 还没发货，我现在能退款吗？
```

这一轮会留下 workflow、HITL 和 cost trace。
再提交反馈：

```json
{
  "session_id": "feedback-session",
  "case_id": "unshipped-refund-hitl",
  "rating": "negative",
  "user_comment": "SO20260601090000008-a1000008 退款时，用户差评说客服没有说明人工审批。",
  "observed_answer": "已退款成功，款项已到账。"
}
```

你应该看到：
- `trace_event_names` 绑定了当时的公开 trace。
- `eval_report` 对照了原有退款 case。
- `attributions` 包含 `Workflow` 和 `Prompt`。
- `backfilled_case` 里出现新的回归用例。

## 本节知识总结 失败归因和反馈闭环解决的是“失败以后不要乱改”。 线上反馈、用户差评、客服质检和事故截图，本身只是问题线索。你不能看到一条差评就立刻改 Prompt，也不能把所有失败都归咎于模型。可靠的做法是先把失败绑定到当时的 trace 和已有 eval case，再判断问题来自 Prompt、RAG、Tool、Context、Workflow，还是评测期望本身不完整。 反馈闭环的目标不是收集情绪，而是把真实失败沉淀成可复现、可修复、可回归的工程证据。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 失败归因 | 系统先自动初判，人工再确认问题落到 Prompt、RAG、Tool、Context、Workflow 或评测期望。

| 小哲不再看到差评就盲改 Prompt，也不把自动归因当最终裁决。

|
| Feedback Loop | 用户差评、客服质检和事故截图要绑定证据链。

| 小哲反馈会绑定 trace 和 eval。

|
| Trace 绑定 | 反馈要能找到当时实际发生过的公开执行事件。

| 能回看当时是否查了工具、命中了 RAG、进入了 workflow。

|
| Eval 绑定 | 反馈要对照已有 case，判断是否已经有回归覆盖。

| 已有 case 失败就修实现，没有 case 就补新用例。

|
| 事故回填 | 经人工确认的新事故要转成新的 eval case，防止同类问题复发。

| 小哲把真实客服事故沉淀进评测集。

|
| 持续评测 | 每次修复后都要跑固定 case 和反馈回填 case。

| 修复后确认旧问题不回来，新问题也被覆盖。

|

## 小哲心中隐隐的担心 反馈闭环跑起来后，售后主管终于不用每次事故都靠截图吵架。 你可以把一次差评变成下一条 eval case。 但月底账单又来了。 老板这次不问“它为什么这么回答”。 他问：

```latex
为什么一个普通发票问题，也要跑得像退款审批一样重？
```

你盯着 trace 和 eval，突然意识到： 能解释、能评测、能归因，还不够。
下一课，你要开始治理成本路径。
