## 第七幕开始时的 Agent 形态 到第七幕开始时，Agent 已经能分清 RAG、Tool 和高风险入口，也能用 RoutePlan 把退款请求送到受控路径门口。但“送到门口”不等于流程已经安全执行。 这一幕只处理高风险售后流程：动作边界、LangGraph Workflow、退款/退货判断、HITL、Resume、Checkpoint 和幂等。它不会让模型自己批准资金、补偿或权益动作。

## 售后主管追问：高风险不是一句转人工 第六幕结束时，你已经把工具链路和入口路由管得像模像样。 订单能查，物流能查，库存也能查。工具调用前后有 Hooks，工具定义也开始从 MCP 风格目录里统一出来，TaskPlanner 也能先给出 RoutePlan。老板看着调试后台里的工具卡片，终于有点放心。 然后一个用户进来，甩下一句话：

```latex
SO20260602103000009-a1000009 直接给我退，马上退款。
```

上一版 Agent 很警觉，它知道这是高风险动作，会把请求路由到受控售后路径。
但售后主管问了你一个更扎心的问题：

> 你说它高风险，那它到底能不能退？凭什么不能退？它看过订单状态、物流状态和售后政策了吗？

> 你突然发现，第 25 课只解决了“先把高风险路由出来”。
> 它还没有解决“高风险诉求应该怎么判断”。

## 这次事故背后的 Agent 问题 退款不是一句自然语言命令。 一个订单能不能发起退款，至少要看四类事实：

| 要看什么 | 为什么必须看 |
| --- | --- |
| 订单状态 | 订单是否已支付、是否已出库、是否已发货 |
| 物流状态 | 未发货退款和已发货/已签收售后不是同一条路 |
| 售后规则 | 小哲电商公司的 SOP 才是判断依据，不是模型口感 |
| 政策依据 | 回答要能说出依据，不能只说“我觉得可以” | 所以第 26 课先做一件事：

```latex
把高风险动作挡在资格判断边界上。
```

Agent 可以查事实，可以解释依据，可以判断“是否可发起申请”。
但它不能退款、不能取消订单、不能补偿，也不能假装审批已经完成。
这里要先把动作分层。
查订单、查物流、查政策，属于读操作。它们会影响回答质量，但不会改变业务状态。
提交退款申请、取消订单、发补偿券、批准退款，属于写操作或高风险决策。它们会改变订单、资金、权益或后续履约。
所以小哲不能只写一句“高风险动作要谨慎”。系统要知道：

| 动作类型 | 可以自动做吗 | 边界 |
| --- | --- | --- |
| 查询事实 | 可以 | 但必须校验当前登录用户和订单归属 |
| 判断资格 | 可以 | 只能判断“是否可申请”，不能说“已完成” |
| 提交申请 | 后续课程才开放 | 需要进入受控 workflow 和审批边界 |
| 批准/执行 | 不能由模型决定 | 必须由人工或受控业务系统处理 | 这张表的意义是：风险不是靠一句口头提醒控制的，而是靠接口、状态和动作范围控制的。

## 代码落地

### 当前 Agent 的实现边界 本节代码快照在：

```latex
code/agent-course-versions/lesson-26-high-risk-action-boundary/backend/
```

第 26 课在前面工具分层之外新增 `policies/after_sale_policy.py`。这个模块只做售后政策检索和高风险资格判断，不提交退款、不取消订单、不补偿；`tools/tool_runtime.py` 仍然负责订单、物流和工具调用证据。
关键链路是：

```latex
/chat -> classify_intent(user_message) -> extract_order_id(user_message) -> get_order_detail(order_id, runtime_user_id) -> get_order_logistics(order_id) -> retrieve_after_sale_policy(action_type) -> check_after_sale_boundary(order, logistics, policy) -> ChatResponse(after_sale_assessment, tool_calls, citations)
```

这一版沿用了前面已经讲过的三类能力：
- Tool：读取订单和物流这些实时事实。
- RAG / citations：提供售后政策依据。
- 高风险标记：返回 `risk_level` 和 `needs_human_approval`。
但它没有启动售后工作流。
它只是把“直接退款”变成一份可检查的 `after_sale_assessment`。
这里的 `needs_human_approval = true` 只是一个风险标记，意思是“后续如果要提交申请，必须进入人工审批边界”。它不是审批动作，也不会创建审批单；第 30 课才会把资格通过的售后申请整理成 `ApprovalRequest`。

### 核心代码拆解 请求先进 `ChatRequest`。 这里最重要的字段不是用户说了什么，而是：

```latex
runtime_user_id user_message
```

`runtime_user_id` 是调用方确认的当前登录用户。订单归属必须靠它校验，不能靠用户在消息里说“这是我的订单”。
`classify_intent` 会把“退款、退钱、取消订单”识别成 `refund_request`。接着 `extract_order_id` 抽出真实订单号，例如 `SO20260602103000009-a1000009`。
如果没有订单号，Agent 不查工具，直接返回：

```latex
next_action = ask_clarification
```

因为高风险售后不能在缺关键参数时继续。
有订单号时，`load_order` 先查订单详情，并校验订单归属。归属不匹配时，流程直接停住。
订单通过后，`load_logistics` 读取物流状态。未发货退款必须确认订单还没有出库、发货或签收。
然后 `retrieve_policy` 返回小哲电商公司的售后政策 citation。
最后 `assess_refund_boundary` 汇总成：

```latex
after_sale_assessment -> eligibility_status -> evidence_checklist -> policy_basis -> reasons -> blocked_write_actions
```

这里的 `blocked_write_actions` 很关键。
它明确告诉系统：这一课阻断 `create_refund`、`approve_refund`、`cancel_order`、`create_compensation`。
也就是说，即使资格判断结果是 `eligible_for_application`，它也只是“可以发起申请”，不是“退款成功”。
这一点在响应契约里必须写清楚。
如果后端只返回一段自然语言“可以退”，前端、日志和后续节点都可能误解成已经放开退款动作。`after_sale_assessment` 需要同时返回资格、证据、政策依据和被阻断的写动作，才能让调用方知道：当前系统完成的是判断，不是执行。

## 怎么验证高风险边界真的生效 按本课代码目录的 `README.md` 启动后端后，发送：

```latex
SO20260602103000009-a1000009 直接给我退，马上退款
```

你应该看到：
- `intent = refund_request` + `risk_level = high` + `needs_human_approval = true` + `after_sale_assessment.eligibility_status = eligible_for_application` + `tool_calls` 里依次出现订单、物流、政策、边界判断 + 响应里没有 `workflow` + 响应里没有 `resume_token` 再发送：

```latex
SO20260602103000009-a1000009 取消订单并退款
```

如果业务系统和页面上下文显示 `SO20260602103000009-a1000009` 已经发货在途，它就不能走未发货退款。

## 本节知识总结 高风险动作边界是 Agent 从“回答问题”走向“影响真实世界”时必须先立住的概念。 只要一个动作会影响资金、权益、账户、订单、合同、权限或用户隐私，它就不能因为用户一句话或模型一句话直接执行。Agent 可以参与收集信息、判断条件、准备申请和解释进度，但执行动作前必须有明确的资格判断、权限校验和责任边界。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 高风险动作边界 | 影响资金、权益、订单、权限或隐私的动作，不能由自然语言直接触发执行。

| 退款、退货、取消订单、补偿不能因为用户一句“直接给我退”就执行。

|
| 读写动作分离 | 查询和判断可以自动化，改变业务状态的动作必须有额外边界。

| 查订单、查物流、查政策可以自动跑；退款、取消、补偿不能直接执行。

|
| 资格判断 | 高风险动作前要先查事实、查规则、查权限，再决定是否能进入申请。

| 小哲必须同时看订单状态、物流状态和售后政策。

|
| 可信身份 | 动作对象必须绑定系统确认身份，不能相信用户自述。

| 订单归属看 `runtime_user_id`，不信用户在聊天里自称是谁。

|
| 政策依据 | 判断要能追到规则依据，不能让模型凭常识或客服语气决定。

| 售后规则通过 citations 返回，退款资格不能靠模型感觉。

|
| 写动作阻断 | 当前版本不能执行的写动作要明确列出，避免调用方误以为已经放开。

| `blocked_write_actions` 标出当前不允许执行的退款、取消、补偿等动作。

|
| 人工审批标记 | 需要人工审批不等于已经进入审批流，更不等于审批通过。

| 第 26 课只返回 `needs_human_approval`；第 30 课才创建待审批申请。

|
