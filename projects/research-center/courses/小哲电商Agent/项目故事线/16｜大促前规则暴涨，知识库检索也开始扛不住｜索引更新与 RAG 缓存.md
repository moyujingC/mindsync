## 运营说：明天大促，今晚再加三百条规则 第 15 课之后，小哲电商客服 Agent 的 RAG 已经比第三幕稳多了。 口语化问题先改写。 相似规则先重排。 长尾售后词用 Hybrid RAG 抓回来。 你刚想喘口气，运营同事拿着表格走过来：

> 明天大促，今晚还有三百条活动规则、商品口径、会员权益要加。

> 老板补了一句：

> 明早客服高峰前必须生效。

> 你突然意识到，RAG 质量不只是“检索算法准不准”。
> 还有两个很现实的问题：

```latex
知识变多后，索引怎么更新？ 同样的问题重复出现，检索能不能少算一点？
```

这就是第 16 课的事故。
知识库不再是几段规则，而是会持续运营的系统。

## 知识运营判断 关键不是单纯让检索更快。 你要学会判断：当知识从几段示例文档变成小哲电商公司持续更新的活动、售后、FAQ 和商品口径时，RAG 就不再只是一次检索调用，而是一个需要版本、更新、失效和边界的知识运营链路。 所以本课要落住四个能力：

| 这次要补上的能力 | 你要能说清楚什么 |
| --- | --- |
| 生产问题 | 大促前知识暴涨，旧索引、旧缓存和新规则混在一起会导致错答。

|
| 本项目实现 | 用 `KnowledgeIndex`、`fingerprint`、`index_version` 和 RAG cache 记录当前知识版本。

|
| 当前边界 | 只缓存稳定知识的检索结果，不缓存最终客服话术，不缓存订单物流等实时事实。

|
| 错误说法 | “RAG 缓存就是把用户问题和答案存起来，下次直接返回。”这是错的。

|

## 技术机制

### 索引不是一次性文件 前面的课程里，知识 chunk 放在 `knowledge_chunks.json`，程序启动后读取它。 这对教学和小规模演示够用。 但运营每天改规则时，你需要开始有索引意识。 索引可以先理解成：

```latex
把知识提前整理成更方便检索的结构。
```

在真实系统里，向量库会维护 embedding、ANN 索引、metadata 和过滤条件。
这里先抓住索引更新的直觉：

| 问题 | 工程动作 |
| --- | --- |
| 全量规则变了 | 重建索引 |
| 少量规则新增或修改 | 增量更新索引 |
| 旧索引还在缓存里 | 用索引版本隔离 |
| 同样稳定知识被反复问 | 缓存检索结果 | 第 16 课的代码会生成一个轻量 `KnowledgeIndex`。 它包含：

- `version` + `fingerprint` + `chunk_count` + `chunks_by_id` + `inverted_index` `fingerprint` 根据当前知识内容计算。知识一变，索引版本就变。
这能避免旧规则命中结果在缓存里继续被当成新依据。

### 向量不是临时算完就丢 第 10 课为了看清 embedding 和相似度，用的是进程内向量缓存。生产环境不能停在这里。 真正上线时，embedding 生成出来的向量通常会写进向量数据库或搜索索引。向量库里不能只存一串浮点数，还要同时保存能追溯和过滤的字段：

```latex
chunk_id source_path / section metadata knowledge_version embedding_model embedding_dimension content_hash
```

这样做是为了避免两个常见事故。
第一，知识更新了，但向量库里还留着旧 chunk。用户问新活动，系统却命中旧活动向量。
第二，embedding 模型换了，旧向量和新向量维度或分布不同，却被放在同一个索引里一起算相似度。
所以生产里通常会把“知识原文”和“向量索引”分开看：知识后台或文档仓库是主数据源，向量库是可重建的检索索引。发布新知识版本时，要么增量 upsert 受影响的 chunk 并删除废弃 chunk，要么按版本建新 collection / namespace，验证通过后再切流量。
简单说，向量库不是一个神秘黑盒，而是一份带版本的检索索引。它必须能回答：这条向量来自哪段知识、用哪个 embedding 模型生成、属于哪一版知识、什么时候应该失效。

### RAG 缓存只能缓存稳定知识 大促期间，很多用户会反复问：

```latex
那个耳机活动还能叠券吗？
```

这种稳定规则问题，检索结果可以缓存。
但缓存要守住边界。
你不能缓存用户的最终自然语言回答，因为同一句回答可能受会员等级、上下文和客服口吻影响。
你更不能缓存实时业务问题。
比如：

```latex
我的订单物流到哪了？
```

知识库里有“现货商品 24 小时内发货”的 FAQ，但它查不到这位用户的包裹正在路上哪个城市。
所以这一课的缓存只做一件事：

```latex
缓存稳定知识的检索结果，不缓存最终回答，不缓存实时业务问题。
```

### 缓存 key 要带上索引版本 这里最容易误解的是：缓存不是简单把“用户问题 -> 命中片段”存起来。 如果缓存 key 只用用户问题，运营凌晨改了活动规则，第二天用户再问同一句话，系统可能继续拿旧规则回答。 所以第 16 课的缓存 key 至少要包含三类信息：

| key 组成 | 作用 |
| --- | --- |
| `index_version` | 确认命中结果来自哪一版知识索引。

|
| `intent` | 区分活动、售后、商品 FAQ 等不同检索域。

|
| `normalized_query` | 用归一化后的检索问题减少重复缓存。

| 可以把它理解成：

```latex
同一句问题 + 同一类意图 + 同一版知识索引 -> 才允许复用这次检索结果
```

一旦 `fingerprint` 变了，`index_version` 也变了，旧缓存就自然不再命中。
这就是为什么课程里强调“索引版本”和“缓存边界”要一起讲。缓存本身不是问题，问题是缓存有没有知道自己依赖哪一版知识。
再看实时问题：

```latex
我的 SO20260602103000009-a1000009 到哪了？
```

就算用户连续问两次，答案也可能随着物流节点变化。它不能进入 RAG 缓存。这里要记住一个判断标准：

| 问题类型 | 能否缓存 RAG 检索结果 | 原因 |
| --- | --- | --- |
| 活动规则、售后政策、商品 FAQ | 可以 | 依赖稳定知识，且受索引版本控制。

|
| 订单物流、库存、退款进度 | 不可以 | 依赖当前业务状态，知识库不是事实来源。

|
| 最终客服话术 | 不建议 | 可能受上下文、身份、语气和风险边界影响。

|

## 这一版 Agent 怎么改 本节代码快照在：

```latex
code/agent-course-versions/lesson-16-index-cache/backend/
```

这一版的模块边界是：

| 文件 | 作用 |
| --- | --- |
| `main.py` | 应用启动和路由挂载 |
| `api/schemas.py` | `KnowledgeIndex`、`RetrievalCacheEntry`、`RetrievalPlan`、请求和响应结构 |
| `api/routes.py` | `/health`、`/capabilities`、`/chat` |
| `agents/customer_service_agent.py` | 索引确认、Hybrid RAG、缓存边界和回答编排 |
| `embeddings/client.py` | 沿用第 15 课的 embedding 客户端和文本向量缓存 |
| `rag/knowledge_base.py` | `knowledge_chunks.json` 读取 |
| `rag/planning.py` | 场景识别、实时业务问题识别、检索计划 |
| `rag/index_cache.py` | 索引构建、版本、重建、检索缓存策略 |
| `rag/hybrid_retrieval.py` | 基于 `KnowledgeIndex` 的 Hybrid RAG 和缓存读写 |
| `rag/prompting.py` | 带索引版本的 RAG Prompt 和 citations |
| `models/llm_client.py` | OpenAI 兼容聊天模型调用 |
| `config/settings.py` | 路径、top_k、embedding 默认配置、低置信阈值和统一课程环境 |
| `knowledge_chunks.json` | 本课检索知识片段 | 第 16 课不是重新写一套向量召回。它沿用第 15 课的真实 embedding 向量召回和 BM25 关键词召回，只是在外面补上知识索引版本和检索缓存。 关键链路是：

```latex
/chat -> get_knowledge_index() -> classify_intent(user_message) -> pre_retrieval_plan(ChatRequest, intent) -> cache_policy_for(plan) -> retrieve_knowledge(plan, index) -> build_citations(reliable_hits) -> generate_stable_rag_answer(messages) -> ChatResponse
```

这一课为了聚焦索引更新与 RAG 缓存，`intent` 先沿用轻量规则分类；第 04 课的小模型兜底分类和后续 RoutePlan 机制不在本课展开。这里的 `scene` 是检索场景，不是完整业务决策。
`get_knowledge_index` 会在需要时构建索引。
`rebuild_knowledge_index` 会重建索引并清空 RAG 检索缓存。
`cache_policy_for` 会判断这轮能不能缓存。
稳定活动、售后、商品 FAQ 可以缓存检索结果。
订单物流、库存、退款进度这种实时问题不能缓存成知识库答案。
这一版的 `is_realtime_business_query` 只是过渡判断，用少量关键词把明显实时的问题挡在 RAG 缓存外。它还不是第 17 课的业务事实服务，也不会真正查询订单、库存或退款进度；它的职责只有一个：不要把当前状态问题缓存成稳定知识答案。
响应里的 `session_state.rag.index` 会记录当前索引版本，`session_state.rag.cache` 会记录：
- `cacheable` + `cache_hit` + `cache_key` + `scope` + `reason` 这让你能看见：系统这轮到底是重新检索，还是复用了同一索引版本下的检索结果。

## 怎么验证老板能闭嘴 这一课要让老板看到两件事：稳定知识可以复用检索结果，实时事实不能被知识库缓存糊弄。 你连续发送两次：

```latex
那个耳机活动还能叠券吗？
```

第一次，系统应该重新检索：

```latex
cache_hit = false
```

第二次，同一个稳定规则问题可以命中检索缓存：

```latex
cache_hit = true
```

但两次最终回答仍然会经过模型组织，因为缓存只保存检索结果，不缓存客服回答。
再发送：

```latex
我的订单物流到哪了？
```

你要观察到：
- 系统识别出这是实时业务事实缺口。
- 稳定知识 citations 不能替代这一单的物流状态。
- 这一轮不能使用 RAG 检索缓存来生成结论。
- 回答会说明这个问题需要查询小哲电商业务系统，而不是让知识库猜快递节点。

## 本节知识总结 索引更新和检索缓存解决的是“知识规模变大后，RAG 怎么稳定又不浪费”的问题。 知识库变大以后，每轮都重新解析、切片、检索会变慢；但如果缓存不看知识版本，又可能拿到旧规则。真正可用的 RAG 缓存必须和索引版本绑定，并且只缓存适合缓存的稳定知识检索结果。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 知识索引 | 把知识切片、metadata 和检索结构整理成可复用索引。

| 小哲用 `get_knowledge_index` 管理当前知识索引。

|
| 索引版本 | 索引要有版本，知识更新后才能判断缓存是否失效。

| `session_state.rag.index` 记录当前索引版本。

|
| 重建索引 | 知识更新时需要重建索引，并清理依赖旧索引的缓存。

| `rebuild_knowledge_index` 会重建索引并清空 RAG 检索缓存。

|
| 检索缓存 | 高频稳定知识问题可以缓存检索结果，减少重复检索。

| 同一个耳机活动问题第二次可命中 cache。

|
| 缓存边界 | 缓存只适合稳定知识，不适合实时状态和最终自然语言回答。

| 订单物流、库存、退款进度不能被 RAG 缓存当成事实结论。

|

### 上线前还要替换什么 索引版本和 RAG 缓存解决的是知识链路里的一个关键问题：知识更新后，Agent 不能继续拿旧索引和旧缓存回答。 但真正上线时，RAG 还不能只靠几份文件和本地索引撑住。小哲电商公司需要把这条链路接到企业里的知识运营、权限、搜索和监控系统。 你可以把当前这版理解成一套工程骨架：

```latex
已发布知识 -> 切片和 metadata -> 索引版本 -> 检索 -> citations -> 缓存失效
```

上线时要替换和补齐的是这些生产能力：

| 能力 | 为什么需要 | 上线时怎么落地 |
| --- | --- | --- |
| 知识审核、发布、灰度和回滚 | Agent 不能读取草稿、过期活动或未审核规则。

| 接知识运营后台，只有已发布版本进入索引，发布后触发重建和缓存失效。

|
| 多知识库和权限过滤 | 客户可见 FAQ、内部 SOP、法务口径不能混在一起暴露。

| 按用户身份、渠道和知识可见范围做过滤，citations 也只能指向允许展示的来源。

|
| Elasticsearch / OpenSearch | 商品名、活动名、政策编号、赠品和包装盒这类硬关键词需要精确匹配。

| 用搜索引擎承接 BM25、中文分词、字段过滤，再和向量召回一起进入 Hybrid RAG。

|
| RAG Fusion | 用户一句话可能对应活动、商品、售后多个检索角度，单条 query 有时会漏掉关键规则。

| 先用 eval 证明单 query 确实漏召回，再扩展多条 query；召回结果必须合并去重、重排，并监控误召回、延迟和成本。

|
| ANN 和在线监控 | 知识库变大后，要同时控制召回质量、延迟和成本。

| 监控命中率、低置信率、无 citation 回答、缓存命中率和知识版本分布。

| RAG Fusion 不应该被理解成“多查几次就更准”。它会扩大候选池，确实可能补回漏掉的规则；但在售后场景里，相邻规则很多，多 query 也可能把无理由退货、质量问题、赠品缺失和活动优惠一起拉进来。上线时只有在评测样例证明“漏召回比误召回更严重”时，才值得打开，并且要让 reranker、阈值和 forbidden citation 一起守住边界。 这段边界不是为了把功能说少，而是为了上线时不把“能跑的 RAG demo”误当成完整知识平台。真正可靠的客服 Agent，必须知道自己读的是哪一版知识、哪些知识能给当前用户看、命中质量有没有变差，以及缓存什么时候必须失效。

## 第四幕收尾：知识库再强，也查不到实时事实 这一版把索引更新和 RAG 缓存的边界讲清楚了。 稳定活动、售后规则、商品 FAQ 可以通过索引和缓存变得更稳。 但用户不会只问稳定知识。 第四幕到这里，知识库检索已经越来越靠谱。可用户开始问：
- 我的订单到哪了？
- 这个商品还有库存吗？
- 退款进度怎么样？
- 快递是不是已经揽收？
这些问题不是知识库能回答的稳定规则。
所以第 16 课遇到这类问题时，会通过 `realtime_gap` 返回一条保守说明。这不是最终客服能力，而是下一幕接入实时业务事实之前的安全占位：宁可承认“现在不能查”，也不要让知识库或模型猜一个当前状态。
小哲心里隐隐觉得：

> 知识库再强，也查不到正在路上的快递。下一幕，Agent 必须开始使用业务工具。
> >
