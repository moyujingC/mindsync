## 第五幕开始时的 Agent 形态 到第五幕开始时，Agent 已经能用 RAG 回答稳定规则，也能通过引用证明依据。但它仍然查不到“这一单现在到哪了”“这个 SKU 现在有没有货”这类会变化的业务事实。 这一幕只把实时事实接进来：业务接口、Tool Calling、澄清、Observation、错误降级，以及 Tool + RAG 联合回答。高风险退款审批还不会在这一幕自动执行。

## 老板盯着一条物流投诉 第 16 课结束时，小哲电商客服 Agent 的 RAG 已经靠谱了不少。 活动规则能引用。 售后说明能找到依据。 知识索引也知道什么时候该重建，什么时候能缓存稳定规则。 你刚想把第四幕的事故报告收起来，老板把一条用户投诉拍到你面前：

```latex
用户：我的 SO20260602103000009-a1000009 到哪了？ AI：您的包裹预计今天下午送达，请耐心等待。 用户：快递页面明明显示还在上海转运中心，你们 AI 又在编？
```

这一次不是 RAG 没命中。
知识库里确实有“现货商品通常 24 小时内发货”的规则。
但它回答不了这一单的包裹现在在哪个城市。
你突然明白：稳定规则和实时事实不是一类东西。

## 技术机制

### 知识库再强，也查不到正在路上的快递 RAG 适合回答小哲电商公司的稳定知识：

| 问题 | 适合来源 |
| --- | --- |
| 会员价能不能叠券 | 活动规则知识库 |
| 签收后几天能退 | 售后政策知识库 |
| 现货通常多久发货 | 发货时效 FAQ | 但用户现在开始问：

| 问题 | 必须查询 |
| --- | --- |
| 我的订单到哪了 | 订单与物流系统 |
| 这件商品现在还有库存吗 | 商品库存系统 |
| 退款进度怎么样 | 售后单或退款系统 | 这些事实会变。 它们跟“当前登录用户”有关，也跟当前时间有关。 如果 Agent 继续从知识库里猜，就是把“通常会怎样”说成“你这一单现在怎样”。 客服事故就是这样来的。

### 事实来源分层 关键不是多接一个“物流接口”。 你要先建立生产级客服 Agent 的第一条硬分界：

```latex
稳定知识可以走 RAG。 实时业务事实必须查业务系统。
```

这条分界以后会反复出现。商品库存、订单状态、退款进度、会员等级、审批状态，都不能靠模型语言能力或知识库通用规则猜出来。

| 这次要补上的能力 | 你要能说清楚什么 |
| --- | --- |
| 生产问题 | 用户问的是“我这一单现在怎样”，知识库只能回答“一般规则是什么”。

|
| 本项目实现 | `detect_business_fact_need` 识别实时事实需求，`BusinessFactService.lookup` 查询当前用户的业务事实。

|
| 当前边界 | 本课建立只读事实接入层：识别实时事实需求、绑定当前用户、读取订单 / 物流 / 库存事实，并把结果放入 `session_state.business_facts`。

|
| 错误说法 | “RAG 里放了发货规则，所以可以回答任意订单物流。”这是错的。

|

### 业务事实服务不是临时查询脚本 能查到物流，只是第一步。 业务事实层还要让上层 Agent 知道：这条事实够不够用、能不能给用户看、出了错该怎么处理。

| 设计点 | 为什么不能省 |
| --- | --- |
| 字段要够 | 订单不能只返回订单号和金额，还要有支付、发货、签收、售后状态；商品不能只返回名称，还要有价格、库存、上下架和售后限制。

|
| 新鲜度要清楚 | 库存、退款资格和物流状态更新频率不同，哪些可以短缓存，哪些必须实时查，要由业务系统说清。

|
| 权限要前置 | 订单、地址、手机号、支付状态属于敏感业务信息，即使 Agent 会做身份校验，业务接口也不能默认开放。

|
| 异常要结构化 | 订单不存在、无权限、物流未创建、第三方超时，不能都返回“失败”，否则 Agent 只能统一兜底。

|
| 审计要留下 | 谁查了哪笔订单、返回了什么状态、是否命中异常，后面排障和风控都要追得回去。

|

## 代码落地

### 先把业务事实服务接进 Agent 这一步先从业务事实入口开始。你让开发小弟把小哲电商公司的订单、物流和商品事实服务整理出来，然后在 Agent 后端里接入当前版本的事实来源。 本节代码快照在：

```latex
code/agent-course-versions/lesson-17-realtime-business-facts/backend/
```

这一版代码不再把所有逻辑塞进 `main.py`。`main.py` 只负责启动 FastAPI；请求/响应模型在 `api/schemas.py`，路由在 `api/routes.py`，课程配置在 `config/settings.py`。第 16 课已经完成的 `models/llm_client.py`、`rag/`、`knowledge_chunks.json` 继续保留，用来回答稳定规则问题；实时事实路径新增 `models/answer_client.py`，让真实大模型基于业务接口返回的事实组织最终客服回复。小哲电商后端只读接口在 `integrations/ecommerce_client.py`，当前用户上下文整理在 `tools/runtime_context.py`，实时事实判断在 `tools/planning.py`，真正的事实接入层在 `services/business_facts.py`，Agent 编排在 `agents/customer_service_agent.py`。
你可以把第 17 课看成“从 RAG 走向业务系统”的第一层生产结构：稳定知识继续走第 16 课的 RAG 和模型回答；实时订单、物流、库存、退款进度才从 RAG 分流到业务系统。也就是说，这一课新增业务事实能力，但不丢掉上一幕已经完成的稳定知识问答能力。
代码里会看到两个 `classify_intent`。`rag.planning.classify_intent` 服务稳定知识检索，关心该去售后、活动、商品还是物流 FAQ 里找依据；`tools.planning.classify_intent` 服务实时事实路径，只判断订单、物流、退款进度、库存价格这类是否需要业务系统。它们名字相同，但职责不同，不是要让两套分类规则互相替代。
关键链路是：

```latex
/chat -> detect_business_fact_need(ChatRequest) -> 实时事实：BusinessFactService.lookup(need, ChatRequest) -> 可信事实：compose_grounded_answer(facts) -> 稳定知识：Hybrid RAG + index cache -> generate_stable_rag_answer() -> ChatResponse
```

`detect_business_fact_need` 先判断用户问的是不是实时事实。
用户问 `SO20260602103000009-a1000009` 物流时，它会生成：

```latex
kind = logistics requires_realtime = true order_id = SO20260602103000009-a1000009
```

`BusinessFactService.lookup` 再用 `runtime_user_id` 做身份边界。
订单属于当前登录用户，才能把订单和物流事实交给 Agent 回答。
订单不属于当前用户，就不能因为用户在聊天框里写了一个订单号，系统就泄露别人的物流信息。

### 事实需求识别先回答：该不该查业务系统 这里先做的是“事实需求识别”：判断这个问题是不是必须查业务系统。 这一步不是为了炫技，而是为了避免 Agent 把两类问题混在一起：

| 问题 | 本课处理方式 | 为什么重要 |
| --- | --- | --- |
| 这是不是实时事实 | `detect_business_fact_need` 判断物流、订单、库存这类当前状态问题。

| 防止把实时状态误交给 RAG 或模型常识。

|
| 需要哪条业务线索 | 从问题里抽取 `order_id` 或商品关键词。

| 防止把“通常规则”说成“这一单现在怎样”。

|
| 当前用户能不能读取 | `BusinessFactService.lookup` 使用 `runtime_user_id` 校验归属。

| 防止用户在聊天框里写别人的订单号就拿到详情。

|
| 查不到或无权限怎么表达 | 返回 `found`、`user_matched`、`summary` 这类结构化事实结果。

| 让上层回答能安全说明原因，而不是统一兜底。

| 你可以先把第 17 课看成 RAG 到业务系统之间的分界层。 RAG 以前只回答“公司规则通常是什么”，现在 Agent 第一次意识到：

```latex
这个问题不是缺知识，而是缺当前业务事实。
```

最小判断逻辑可以这样理解：

```python
def detect_business_fact_need(message: str) -> BusinessFactNeed: order_id = extract_order_id(message) if order_id and contains_any(message, ["物流", "快递", "到哪"]): return BusinessFactNeed( kind="logistics", requires_realtime=True, order_id=order_id, ) return BusinessFactNeed(kind="none", requires_realtime=False)
```

这段逻辑的重点不是正则有多聪明，而是分类边界清楚：
- 用户问“通常多久发货”，可以查 FAQ 或 RAG。
- 用户问“我的 SO20260602103000009-a1000009 到哪了”，必须查订单物流事实。
- 用户没有给订单号时，不要猜订单，系统先说明需要补充订单信息。
- 用户给了别人的订单号，也不能泄露，执行层要用 `runtime_user_id` 再校验归属。
当前 `extract_order_id` 仍是课程版的轻量解析：优先识别小哲订单号，也保留一个较宽的回退匹配，方便你在调试时看到“参数线索如何进入事实查询”。生产系统不能只靠这条正则，应该用订单号格式、渠道上下文、候选订单列表和后续 Tool Calling 澄清一起收口，避免把 SKU、用户名或其它编号误当订单号。

## 实时事实先接住，回答才有底 第 17 课先把事实源接上，再让最终回答回到真实模型。 它会返回 `session_state.business_facts`，让你看到本轮查的是哪类事实、有没有命中、是否匹配当前用户。 它也会返回 `session_state.model_answer`，让你看到本轮最终回答是否由模型基于可信事实生成。 `model_answer` 只记录最终回答来源：是否调用了模型、模型名、是否触发兜底，以及来自稳定 RAG 还是实时事实。实时事实路径会先整理可信事实，再交给模型组织客服口吻；订单不存在、越权或事实不可用时，则跳过模型，直接用安全话术。 这一步解决的是：

```latex
订单物流这类实时状态，必须来自业务事实服务，不能靠模型猜。
```

做到这里，Agent 已经不再把实时物流当成普通知识问答，也不再用固定模板假装客服完成了回答。
它有了一个可复用的事实入口：
- 事实来源是业务系统或事实服务，不是 RAG 命中的发货规则。
- 身份来自 `runtime_user_id`，不是用户在聊天框里的自我声明。
- 结果有 `found`、`user_matched`、`summary`，不是一段无法判断来源的自由文本。
- 最终回答由真实模型基于这些事实组织；订单不存在、越权或模型不可用时才回退到安全话术。
- 调试后台重点看 `session_state.business_facts`，确认这一轮到底查了什么事实。
这就是本课完整目标：先把实时事实来源接稳，而不是继续让模型用话术补业务空洞。

### 这版直接查事实服务，有什么缺点 你也要知道：这个写法只是当前演进阶段，不是工具体系的终点。 现在的链路是后端用规则判断“要不要查实时事实”，再直接调用 `BusinessFactService.lookup`。它适合让你先看清楚事实分层，但如果业务接口越来越多，就会露出几个问题：

| 当前做法 | 生产风险 |
| --- | --- |
| 识别逻辑写在后端规则里。

| 订单、物流、库存、退款、优惠、会员等级都加进来以后，判断逻辑容易变成一堆难维护的分支。

|
| 查询能力没有统一的工具契约。

| 每个接口需要什么参数、哪些参数由系统注入、哪些字段能返回给模型，容易分散在不同代码里。

|
| 缺参、错参和无权限处理不够统一。

| 用户没给订单号、给错订单号、拿别人的订单号时，系统容易每条链路各写一套兜底。

|
| 调试证据只看到 `business_facts`。

| 你能知道查到了什么事实，但还看不到“为什么选择这个能力、参数是什么、执行结果如何回到 Agent”的完整调用链。

|
| LLM 不参与选择可用能力。

| 当前版本只能按固定规则查事实，不能让 Agent 根据工具说明在多个业务能力之间做受控选择。

| 所以生产上更好的做法，通常会把这些业务事实能力整理成 Tool Calling：工具有名字、参数契约、权限边界和结构化返回；模型可以在受控范围内选择工具，但真正执行、鉴权和审计仍然由后端工具层负责。第 18 课会顺着这条线继续往下走。 现在你先把最关键的分工立住：

```latex
RAG 负责稳定知识。 业务事实服务负责实时状态。
```

## 怎么验证老板能闭嘴 这一课要验证的是：订单物流回答来自业务事实服务，而不是来自知识库里的“通常发货时效”。 你发送：

```latex
帮我查一下 SO20260602103000009-a1000009 的物流到哪了
```

当前用户是订单所属用户时，业务事实里应该能看到电商后端返回的最新物流或订单状态：

```latex
来自真实订单/物流事实的状态摘要
```

如果把当前用户换成另一个账号时，同一个订单号不能返回物流详情，回答会说明订单不属于当前登录用户。
如果用小哲电商客服 Agent 调试后台验证，这一课重点看 `session_state.business_facts`。它会告诉你这一轮查的是物流事实、命中的实时状态是什么，以及订单是否匹配当前登录用户。

## 本节知识总结 实时业务事实解决的是“知识库再强，也查不到当前状态”的问题。 RAG 适合稳定规则和文档知识，但订单状态、物流节点、库存数量、退款进度这类信息会随时间变化。它们必须来自业务系统或实时事实服务，不能由模型根据常识猜，也不能用知识库里的通用说明替代。

| 知识点 | 核心概念 | 小哲项目里的落点 |
| --- | --- | --- |
| 实时事实 | 当前状态类问题必须查业务系统，不能靠模型或稳定知识库猜。

| 物流位置来自小哲业务事实服务。

|
| 事实需求识别 | Agent 要先判断问题是否需要实时事实。

| `detect_business_fact_need` 识别 logistics、order_id 和 requires_realtime。

|
| 身份边界 | 查询实时事实必须绑定当前可信用户身份。

| `runtime_user_id` 决定订单是否属于当前用户。

|
| RAG / 实时事实分工 | 稳定规则走 RAG，当前状态走业务事实服务。

| 活动规则查知识，SO20260602103000009-a1000009 物流查业务事实。

|
| 业务事实层 | 实时事实接口要有字段、新鲜度、权限、异常和审计边界。

| 订单、物流、商品事实不是临时脚本，而是小哲业务系统提供的可信事实。

|
| 事实证据 | 查询结果要作为结构化状态返回，便于调试和排障。

| `session_state.business_facts` 展示命中、事实类型和用户匹配结果。

|

## 事实能查了，回答边界才站住了 这一版让 Agent 第一次拿到了实时业务事实。 现在回答 `SO20260602103000009-a1000009` 到哪了，不再靠“现货商品通常 24 小时内发货”这种稳定规则，也不靠模型猜一个快递节点。 它必须能说清楚三件事：
- 事实从哪里来。
- 这条事实是不是当前登录用户有权读取。
- 查到或查不到时，系统状态里留下了什么证据。
小哲心里隐隐觉得：

> 不是所有问题都是知识问题。凡是问“我这一单现在怎样”，先找可信业务事实，再组织客服回答。
