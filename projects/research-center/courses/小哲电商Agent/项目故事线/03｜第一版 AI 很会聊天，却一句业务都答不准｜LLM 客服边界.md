AI 回得很顺，但你越听越紧张 运营先问： ```latex 我是金卡会员，今天买降噪耳机能叠加优惠券吗？ ``` AI 很快回了一段客服味很足的话： > 金卡会员通常可以享受专属权益，优惠券是否可叠加需要以活动页面规则为准，建议您下单前查看结算页优惠展示。 > 这段话听起来没什么问题。 但运营皱了一下眉： > 今天这个活动是“会员价不能叠券”。它没查规则，只是在说通用话术。 > 售后主管接着问： ```latex 我上周买的耳机坏了，想退货退款，你们别踢皮球。 ``` AI 又回得很快： > 很抱歉给您带来不好的体验，我会尽力协助您处理退货退款问题，请您提供订单信息以便核实。 > 老板点点头： > 这不挺像客服的吗？ > 售后主管直接把工单页面打开： > 像客服不等于接了售后。它不知道退货条件，不知道订单状态，也没有给系统创建任何请求。用户听到“协助处理”，会以为我们已经接了。 > 最后客服主管问物流： ```latex 我的订单三天没动了，什么时候能到？ ``` AI 还是能答： > 物流可能受到仓库处理、天气或快递节点更新延迟影响，请您耐心等待，我会帮您关注。 > 客服主管看着你： > 它没有查物流。用户现在要的是准确节点，不是“可能延迟”。 > 这时你终于能把问题讲清楚了： > 第一版 AI 客服会聊天，但没有业务事实。它的回答越顺，越容易让人误以为它真的知道。 > ## 它现在只有回答，没有行动和观察 如果以后要把这个客服做成真正可靠的 Agent，它不能只会把话说顺。 面对一个业务问题，它至少要补上三个环节： | 环节 | 在小哲客服里意味着什么 | | --- | --- | | 公开决策摘要 | 告诉调试后台这一轮为什么需要查活动、查物流或查售后，但不展示隐藏推理。 | | 业务动作 | 选择后续要查哪类业务事实，并组织安全参数。 | | 观察事实 | 把工具或知识来源返回的结果整理成可用、可追溯、可脱敏的事实。 | 这一课先不用背 ReAct，也不用急着把 Reason / Action / Observation 这些词记成公式。 你现在只是用它看清一个缺口： ```latex 这一版 AI 客服只有 Answer。 它没有真正的 Action。 也没有来自业务系统的 Observation。 ``` 等后面真正接 Tool Calling 时，我们再把这种“先判断、再行动、再观察、再回答”的模式和 ReAct 对上。 所以运营问活动时，它没有去查活动规则。 用户问物流时，它没有去查快递节点。 售后主管问退款时，它没有去查订单状态和售后条件。 它能给出客服味的回答，但回答前面没有“行动”，回答背后也没有“观察事实”。 ## 这一课先让问题暴露出来 你没有马上去接知识库，也没有马上去写售后流程。 因为现在最重要的不是把系统一口气修完，而是让老板、运营、售后和你自己都看清楚第一版 LLM 客服的边界。 这一版只做一件事： ```latex 保留 /chat 服务，让模型以小哲电商客服身份回答真实业务问题。 ``` 也就是说，你现在不是重新发明接口。 接口形态仍然是： ```latex POST /chat ``` 请求里仍然有： ```latex session_id runtime_user_id runtime_member_level runtime_risk_level user_message ``` 响应仍然沿用上一课的最小结构。这一课只新增一个你需要看的字段： ```latex reasoning_summary ``` 现在的小哲电商 Agent 只是第一版 LLM 客服。它开始站在业务问题面前说话，但它返回的仍然是最小聊天响应，还没有连接小哲电商自己的业务事实。 ## 当前代码的实现入口 当前代码快照在： ```latex code/agent-course-versions/lesson-03-llm-customer-boundary/backend/ ``` 它只放 Agent 后端。 小哲电商客服 Agent 调试后台仍然是外部调用方。你启动这一课后端后，让调试后台指向当前 Agent 地址，就能看到同一个聊天入口现在会把真实业务问题交给第一版 AI 客服回答。 本课核心文件是： | 文件 | 作用 | | --- | --- | | `main.py` | FastAPI 应用装配和启动入口 | | `api/schemas.py` | `/chat` 请求响应格式和公开摘要字段 | | `api/routes.py` | `/chat` 薄入口 | | `agents/customer_service_agent.py` | 第一版 LLM 客服和 messages 构造 | | `models/llm_client.py` | 大模型聊天接口调用 | | `config/settings.py` | 课程共享配置读取 | | `agent_capabilities.json` | 告诉调试后台当前只开放聊天和公开执行摘要 | 这一课没有新增路由种类，而是在第 02 课的 `agents/` 和 `models/` 上加客服身份与业务边界：Agent 开始用小哲电商客服口吻回答，但仍然不接订单、物流、活动规则这些事实来源。你要按这条链路读代码： ```latex /chat -> ChatRequest -> Lesson03Agent.chat -> build_customer_service_messages -> call_chat_model -> ChatResponse ``` 这条链路很短，但它把第 03 课的事故压得很清楚： ```latex 业务问题已经进模型了，但业务事实还没进系统。 ``` ## `/chat` 入口没有变 先看路由层： ```python @app.post("/chat", response_model=ChatResponse) def chat(request: ChatRequest) -> ChatResponse: return agent.chat(request) ``` 第 02 课已经把 `/chat` 定成了小哲电商调用 Agent 的门。 第 03 课不改门。 这件事很重要。 如果每一课都换入口，调用方会跟着乱。用户商城、客服网关、调试后台应该继续把问题发到 `/chat`，真正变化的是 `/chat` 后面这一版 Agent 能做什么。 所以第 03 课的变化不在路由层，而在 `Lesson03Agent.chat` 里面。 请求格式沿用上一课。第 03 课会把真实业务问题交给模型回答，但它还没有接活动、订单、物流和退款规则；这一课要暴露的问题正是：业务问题已经进来了，业务事实还没有进系统。 ## 第一版客服 messages 是怎么拼出来的 这一版新增的核心函数是： ```python def build_customer_service_messages(request: ChatRequest) -> list[dict[str, str]]: ... ``` 它做两件事。 第一，告诉模型现在的身份： ```latex 你是小哲电商公司的第一版 AI 客服。 ``` 第二，只把用户这次问的问题整理成模型输入。 它不是把模型变成业务系统。 它只是让模型知道： + 当前谁在问。 + 用户这次具体问了什么。 + 当前回答没有经过活动规则、订单物流或退款条件核验。 这正是第 03 课要让你看到的边界。 就算用户自己说“我是金卡会员”，模型也不能把这句话当成系统确认的会员事实，更不知道今天活动是否允许叠券。 就算模型听到“订单三天没动”，它也不知道快递节点在哪里。 就算模型看到“耳机坏了想退款”，它也不知道订单是否超过售后期、商品是否符合退货条件。 所以这一步不是完整 Prompt 工程。它只是第一版客服身份和用户问题的包装。 ## 模型调用单独封装 `Lesson03Agent.chat` 不直接写 HTTP 请求，而是调用： ```python answer = call_chat_model(messages) ``` 这样主流程只关心一件事： ```latex messages -> answer ``` 模型平台、Base URL、模型名、API Key 这些运行配置，统一从： ```latex code/agent-course-versions/course.env ``` 读取。 所有 lesson 后端统一复用同一份课程配置和运行手册准备好的 Python 环境，环境变量从 `code/agent-course-versions/course.env` 读取。 运行时，`call_chat_model` 会调用模型接口。 ## 先盯住事实来源 这一课最重要的知识点，不是接口字段多了几个。 你要先把一个客服 Agent 的底层问题看清楚： ```latex 回答从哪里来的？ ``` 如果回答来自模型自己的语言能力，它可以很流畅。 但小哲电商真正需要的客服回答，不能只来自语言能力。 运营问活动叠券时，正确答案应该来自小哲电商当天的活动规则。模型知道“金卡会员通常有权益”，不等于知道今天降噪耳机活动能不能叠券。 用户问物流三天没动时，正确答案应该来自订单和快递节点。模型知道“物流可能延迟”，不等于知道这个包裹卡在仓库、揽收点还是运输途中。 用户问耳机坏了能不能退款时，正确答案应该来自订单状态、售后规则和商品条件。模型知道“我可以协助您处理”，不等于知道这单有没有超过售后期、是否符合退货条件、售后系统有没有记录。 这就是第 03 课要让你记住的边界： ```latex 客服语气不是事实来源。 会员等级不是活动规则。 用户描述不是订单状态。 一句“我帮你处理”不是售后受理记录。 ``` `build_customer_service_messages` 能做的事情，是把客服身份和用户问题整理好，让模型知道自己正在以小哲电商客服的口吻说话。 但它不能把不存在的事实变出来。 这一课不会把 `runtime_member_level`、`runtime_user_id` 提前塞进模型输入。它们仍然保存在 `session_state.runtime_context`，给调试后台和后续系统看。真正把运行时上下文变成可控输入，是后面 Runtime Context 这条线要解决的事。第 03 课先守住一个更基础的边界：用户原话不是系统事实，客服语气也不是业务依据。 `system message` 能提醒模型不要乱承诺，却不能替小哲电商查询活动、物流和售后。 所以这一版最危险的地方，不是它完全不会答。 恰恰相反，是它太会答了。 一个完全不会答的系统，老板和运营会立刻停掉；一个能把客服话术说顺的系统，很容易让人误以为它已经拿到了业务事实。 ## 这一版停在什么位置 试运行会结束后，你没有把这版 AI 客服说成“可上线”。 你把当前版本的边界写在调试后台旁边： + 能接业务问题。 + 能生成客服回答。 + 能在公开摘要里说清楚没有查过业务事实。 + 不能让系统消费出分类结果。 + 不能查订单、查物流、查活动。 + 不能承诺退货、退款、赔偿或人工处理。 这不是功能清单，而是事故结论。 老板看到的是 AI 会说话；你必须让团队看到的是：它现在没有事实来源，也没有能给业务系统消费的结果。 ## 调试后台怎么锁住这一课的边界 这一版调试不是为了证明模型回答一定正确。 恰恰相反，它要证明： > 这版还没有能力保证业务回答正确。 > 你主要看两件事。 第一，能力声明里只开放当前能力。 `/capabilities` 会告诉调试后台：这一版只适合观察最小聊天链路和公开执行摘要，调试后台不应该把当前响应还没有数据支撑的面板当成已经可用。 第二，`/chat` 响应不能提前出现后续能力字段。 响应里还不应该出现： ```latex intent intent_result citations tool_calls ``` 这样调用方不会误以为它已经拿到了分类结果、引用来源或业务处理记录。 同时你还要看同一个 `session_id` 下的 `message_count` 是否继续递增。 如果你用调试后台验证，还要确认业务问题确实进入了当前 Agent 的 `/chat`，并且 `reasoning_summary` 明确提示当前回答没有经过活动规则、订单物流或退款条件核验。 如果模型回答得很像客服，你更应该警惕。 因为这正是这一课要暴露的问题： > 话术顺，不等于事实对。 > 这才是第 03 课该保护的边界。 ## 本节知识总结 LLM-only 应用最容易让人误会的地方，是它“会说”。 大模型擅长根据已有语言模式组织回答。它可以把语气说得自然、把步骤说得完整、把安慰说得像真人。但在业务系统里，回答好听不是最重要的，回答背后的事实来源才是最重要的。 你以后做任何 Agent，都要先问一个通用问题： ```latex 这句话的依据来自哪里？ ``` 如果依据只是模型语言能力，那它适合写说明、做草稿、给建议，但不能直接变成库存状态、订单结论、审批结果、退款承诺或医疗、法律、金融等高风险结论。只要问题依赖外部世界的当前事实，模型就必须接入对应的信息来源。 常见事实来源可以分成几类： | 事实来源 | 通常解决什么问题 | | --- | --- | | 稳定知识 | 政策、SOP、产品说明、FAQ、操作手册。 | | 实时系统 | 订单状态、物流节点、库存价格、账户权限、审批进度。 | | 工具调用 | 查询、计算、创建任务、提交申请、触发流程。 | | 人工确认 | 高风险、争议大、权限敏感或需要责任人审批的动作。 | 这就是 LLM-only 边界：模型可以生成语言，但不能凭语言能力替代外部事实。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | LLM-only 边界 | 只有模型回答、没有检索、工具或业务系统事实时，结果只能当语言生成，不能当业务结论。 | 第一版 AI 客服能说得像客服，但还不知道活动、订单、物流和退款事实。 | | 事实来源 | 业务回答要能追到依据：稳定知识、实时系统、工具结果或人工确认。 | 活动规则来自知识或运营系统，物流来自快递节点，退款资格来自订单和售后规则。 | | 用户说法与系统事实 | 用户输入是待处理信息，不是可信事实来源。 | 用户说“我是金卡会员”不能替代 `runtime_member_level`，更不能替代订单或售后查询。 | | 消息组织的边界 | messages 能组织身份和上下文，但不能凭空生成外部世界的真实状态。 | `system message` 能提醒别乱承诺，却不能查到今天活动是否允许叠券。 | | 流畅回答风险 | 自然、完整、客服味强的回答，反而容易让人误以为系统已经查证。 | 老板看到 AI 会说话，可能误以为它已经能接客服；这正是本课事故。 | ## 小哲心里真正害怕的事 试用会结束后，老板没有立刻骂你。 这反而更让你不安。 老板看着 AI 客服的几段回复，嘀咕了一句： > 其实普通用户也看不出来它有没有查规则吧？ > 你知道这才是最危险的地方。 如果 AI 回得很差，大家会马上停掉。 但它回得很像客服。 运营不盯着规则，它可能把活动说错。 售后不盯着工单，它可能让用户以为退款已经在处理。 客服主管不盯着物流，它可能用一堆安慰话术盖住真正的问题。 第一版 AI 客服已经证明了一件事： ```latex 能聊天，不等于能接客服。 ``` 但小哲心里还有另一层不安。 就算你下一步把回答写得更谨慎，让 AI 不再轻易承诺“可以退款”“一定能叠券”“物流马上到”，系统还是只拿到一段自然语言。 自然语言对用户有用，但对客服网关、售后队列和运营排查来说还不够。 因为系统读不懂这段话到底代表什么业务请求。 下一次事故会更具体。 用户说要退货退款，AI 说： > 我帮您处理。 > 用户听完会以为小哲电商已经接住了这件事。 但售后主管的系统里，没有任何退货请求，也没有任何能分到售后队列的信号。 那时你会发现，第 03 课暴露的是“回答没有事实来源”，第 04 课要继续解决的是“系统不能只收到一段好听的回答”。 小哲电商的系统必须读懂：这句话到底是普通咨询、退款请求，还是投诉。
