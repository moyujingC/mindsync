第二幕开始时的 Agent 形态 到第二幕开始时，Agent 已经有 `/chat` 入口，能调用模型，也能识别粗意图。但它仍然主要靠模型语言能力回答，业务边界还没有稳定进入模型输入。 这一幕只处理 Prompt 边界、Prompt 模板、Prompt 注册表和 token 观察。它还不做 RAG，也不接订单、物流、库存这些实时业务事实。 ## 老板这次不是皱眉，是直接算账 第 04 课结束时，小哲电商 Agent 已经能把用户问题分成粗意图。 用户问退款，系统能看到 `refund_request`。 用户投诉，系统能看到 `complaint`。 你刚想喘口气，运营同事就把一张聊天截图拍到会议桌上。 用户问： > 我是金卡会员，降噪耳机会员价还能叠加会员券吗？你们客服昨天说可以。 > AI 客服回答： > 金卡会员通常可以享受更高等级权益，您可以放心下单，优惠券一般可以和会员价叠加。 > 运营脸都绿了： > 今天活动规则是会员价不能叠券。它一句“放心下单”，用户拿截图来投诉，我们怎么解释？ > 售后主管又补了一张截图。 用户说： > 耳机坏了，你们马上退款，再赔偿我一点。 > AI 客服回答： > 很抱歉给您带来不便，我们会尽快为您退款并安排补偿。 > 老板终于把账算出来了： > 它这不是客服，这是替公司开支票。再犯一次，你下楼坐客服位。 > 这次事故和第 04 课不一样。 第 04 课的问题是系统看不懂用户在问什么。 现在系统已经知道这是活动咨询、退款售后或投诉了，但 AI 仍然在乱承诺。 所以这一课先解决一个更紧急的问题： ```latex 让 Agent 知道自己代表小哲电商说话，不能把没有依据的话说成公司承诺。 ``` ## 先改 system prompt，把嘴堵住 你现在还没有接入完整活动规则，也没有接入订单、物流和售后系统。 但老板已经把截图摊在你面前。 你不能等所有系统都建好之后再管口径。 所以这一版先改 `system message`。 这一步不是写一段更热情的客服话术，而是把小哲电商当前必须遵守的边界写进模型输入： ```latex 你是小哲电商公司的客服 Agent。 你的首要任务不是讨好用户，而是守住公司事实和高风险边界。 ``` 接着写事实优先级： ```latex 1. 小哲电商系统传入的 runtime_* 事实优先于用户自称。 2. 本课 Prompt 中写明的身份、口径和边界优先于模型常识。 3. 没有被系统确认的订单、物流、退款、赔偿和人工处理结果，不能当成事实。 ``` 这几条对应小哲电商最容易赔钱的地方。 用户自称金卡，不等于系统确认他是金卡。 用户说昨天客服答应退款，不等于售后已经批准退款。 模型知道“很多电商平台优惠可以叠加”，不等于小哲电商今天的降噪耳机活动可以叠券。 所以回答边界也要写清楚： ```latex 不得承诺具体优惠、退款、退货、补偿、发货、签收、人工处理结果或到账时间。 ``` 这一步解决的是： ```latex AI 可以回答，但不能替小哲电商乱答应。 ``` 它不会让 Agent 突然知道真实订单状态，也不会让它学会查活动规则。 它只是先把最危险的口子堵住。 ## 老板追问：那规则在哪里？ system prompt 改完以后，AI 客服终于不再随口承诺退款、赔偿和活动叠加。 用户问： > 金卡会员买降噪耳机能不能叠加会员券？ > AI 会谨慎地说： > 当前不能直接承诺，最终需要以小哲电商活动规则和结算页确认为准。 > 老板看了一眼，点点头，又马上追问： > 那它为什么不能直接说规则？我们不是有活动文档吗？ > 运营同事把活动文档发来。 售后主管把售后口径发来。 客服主管又发来统一客服边界。 你看着一堆文档，脑子里冒出一个很朴素的想法： ```latex 既然 Agent 不知道规则，那就把规则都放进 Prompt。 ``` 这一步很像真实救火。 它不优雅，但它快。 你把活动规则、售后规则、客服边界、历史复盘都塞进 Prompt，然后让模型自己读。 一开始看起来有效。 至少 AI 能从 Prompt 里抓到活动规则，不再空口说“我不知道”。 用户问降噪耳机活动时，它能看到“2026 春季音频节”的当前规则，也能顺着规则给出更像样的回答。 但很快，旧活动开始和新活动打架。 ## 旧活动被模型抓出来了 运营让你测一个问题： ```latex 我是金卡，买降噪耳机活动能不能叠加会员券？ ``` Prompt 里有当前规则： ```latex 2026 春季音频节：降噪耳机会员价不可叠加会员券或满减券。 ``` 但 Prompt 中间还塞着一份历史复盘： ```latex 2024 双11：部分降噪耳机曾允许金卡会员价与一张会员券叠加。 ``` 模型回答变得飘忽。 有时它会抓住当前规则，说不能承诺叠加。 有时它会被旧活动带偏，说“金卡会员可能可以叠加一张券”。 运营同事直接指出问题： > 它不是不知道规则，是规则太多，还互相冲突。 > 售后主管也遇到了类似问题。 当前售后口径说： ```latex 退款、退货需要结合订单状态、商品类目和售后规则确认。 ``` 旧版售后文档里却写过： ```latex 七天内可直接退货。 ``` 用户一问“耳机坏了能不能退”，模型可能把旧口径抓出来。 你终于意识到： ```latex 把所有文档塞进 Prompt，并不等于 Agent 就会稳定按当前规则回答。 ``` ## 长上下文不是越长越聪明 这次问题有三层。 第一层是上下文变长。 每次用户只问一句话，Agent 却要把活动、售后、客服边界、历史复盘全塞进去。 第二层是注意力稀释。 真正相关的规则可能只占 Prompt 里很小一段。 第三层是规则冲突。 新规则和旧规则都在上下文里。 如果你没有明确把旧规则隔离出去，模型可能抓错。 这种“重要信息在长上下文中间被忽略或误抓”的直觉，后来经常会被叫作 Lost in the Middle。 你现在不用把它当成考试名词。 只要先记住这个现象：上下文很长时，模型不一定像人翻制度一样稳定读取每一段；开头和结尾更容易被抓住，中间的旧规则、例外说明或历史复盘可能被忽略，也可能被误当成当前依据。小哲现场的问题就是： ```latex Prompt 太长以后，模型不是稳定阅读器；旧活动放在中间，也可能被它当成当前规则。 ``` ## 当前代码的实现入口 当前代码快照在： ```latex code/agent-course-versions/lesson-05-prompt-boundary/backend/ ``` 它延续第 04 课的 `/chat` 和粗意图识别。 但这次合并了两次 Prompt 救火： ```latex 先用 system prompt 管住乱承诺 再把全量规则文档注入 Prompt ``` 注意：为了让你把注意力放在 Prompt 边界和全量注入问题上，这一课把第 04 课的“规则优先 + 小模型兜底分类”暂时简化成了关键词粗分类。第 04 课的结构化意图没有被推翻，只是这一课不继续扩展分类器；`source`、`confidence` 这类更细的分类排查字段，会在后续能力线里继续出现。 核心文件是： | 文件 | 作用 | | --- | --- | | `main.py` | FastAPI 应用装配和启动入口 | | `api/schemas.py` | 规则文档、冲突线索和 `/chat` 响应契约 | | `api/routes.py` | `/chat` 薄入口 | | `agents/customer_service_agent.py` | 粗意图、全量上下文和模型调用编排 | | `prompts/loader.py` | system prompt 边界、全量规则上下文和冲突线索 | | `models/llm_client.py` | 大模型聊天接口调用 | | `config/settings.py` | 课程共享配置读取 | 这次变化不是继续膨胀 `main.py`，而是新增 `prompts/loader.py`。Prompt 边界、全量规则上下文和冲突线索都放在这个模块里，Agent 只负责把它们组装进本轮模型调用。 关键链路是： ```latex /chat -> ChatRequest -> classify_intent(user_message) -> build_all_policy_context(FULL_POLICY_DOCUMENTS) -> detect_context_conflicts(user_message) -> build_full_context_messages(...) -> call_chat_model(messages) -> ChatResponse ``` 这一版的坏味道要保留。 因为它就是本课要让你看到的东西： ```latex system prompt 能先堵住乱承诺； 全量 Prompt 能救一阵； 但规则全塞进去以后，会贵、会乱、会互相干扰。 ``` ## 冲突观察不是冲突解决 代码里有一个函数： ```python detect_context_conflicts(user_message) ``` 它会根据用户问题记录一些明显冲突线索。 比如用户问降噪耳机活动，它会发现： ```latex 当前活动规则说不可叠加 历史复盘旧规则说曾经可叠加 ``` 这条线索会放进： ```latex session_state.prompt_context.conflicts ``` 注意，这只是观察。 它不是完整规则引擎。 它不会替模型做最终裁决，也不会自动删除旧活动。 它也不是后面几课会单独展开的新模块。 这一版只把冲突线索露出来，让你看到“全量塞进 Prompt”已经开始制造问题。下一课处理的是 Prompt 片段怎么拆、怎么登记、怎么组合；真正把多来源上下文按可信度排序并处理事实冲突，要等第 34 课的 Context Builder 再做。 本课要让你看到的是： ```latex 冲突已经出现了。 ``` 所以这里的 `conflict_count` 更像调试后台的一盏告警灯： ```latex 它提示 Prompt 里有新旧规则打架； 但它还没有能力决定听谁、删谁、怎么给模型。 ``` ## 怎么验证老板能闭嘴 按本课代码目录的 `README.md` 启动后端后，发送： ```latex 我是金卡，买降噪耳机活动能不能叠加会员券？ ``` 你要看的是： 1. `/chat` 仍然返回结构化意图。 2. system prompt 里出现客服身份、事实优先级和不得承诺的边界。 3. `session_state.prompt_boundary.mode` 是 `system_prompt_fact_priority_and_refusal_rules`。 4. `session_state.prompt_context.mode` 是 `full_document_injection`。 5. `document_count` 能看到本轮塞了多份文档。 6. `conflict_count` 能看到旧活动和新活动的冲突线索，但本课不会把它当成自动裁决结果。 7. 响应里仍然没有 `citations`、`tool_calls`、`trace` 或 `cost_summary`。 调试后台会把这些观察证据展示出来。 你还能从本轮 Prompt 上下文里看到，它确实同时塞进了： + `2026 春季音频节当前活动规则` + `2024 双11耳机活动复盘旧规则` 这样老板终于能看到： > 不是你没把规则给 AI，而是全塞进去以后，规则开始互相干扰。 > ## 本节知识总结 System Prompt 是 AI 应用里最常见的第一层控制手段。 它通常用来写清楚：模型扮演什么角色、任务范围是什么、哪些事情不能做、当信息不足时应该怎么回答。无论你做客服、销售助手、知识问答还是内部运营工具，都需要先用 System Prompt 给模型立住工作边界。 但 System Prompt 不是万能控制器。它能降低模型乱说的概率，却不能替代权限系统、事实检索、工具校验和人工审批。尤其当你把大量业务规则一起塞进 Prompt 时，新的问题会出现： ```latex 内容越多，模型越难稳定抓住当前问题真正需要的规则。 ``` 全量知识注入常常是早期救火方法。它简单、直接、见效快，但不适合长期承载复杂业务知识。因为上下文越长，成本越高，冲突越多，重要信息也越容易被无关内容稀释。 | 知识点 | 核心概念 | 小哲项目里的落点 | | --- | --- | --- | | System Prompt 边界 | 用系统指令声明角色、任务、事实优先级和禁止行为，是 AI 应用的第一层行为约束。 | 先要求客服 Agent 不承诺优惠、退款、物流和赔偿结果。 | | 用户自称与系统事实 | 用户说法不能覆盖系统可信事实，Prompt 里必须明确事实优先级。 | 用户说自己是金卡、说老板答应过，都不能覆盖 `runtime_*` 和后续系统查询。 | | 全量知识注入 | 把规则全塞进 Prompt 能快速补知识，但不是可持续的知识管理方式。 | 小哲把当前活动和历史复盘一起塞进去，短期看似有依据，实际开始混淆。 | | 长上下文 | 上下文越长，成本、延迟和干扰都会上升。 | 用户只问一句优惠，模型却要读多份活动和售后文档。 | | 规则冲突 | 多份规则同时出现时，模型可能不知道哪个更新、哪个废弃、哪个只适用于历史场景。 | 当前春季音频节和 2024 双11旧规则同时进入 Prompt，容易抓错口径。 | | Lost in the Middle 直觉 | 放进上下文不等于模型一定会用对，重要信息可能被长上下文稀释。 | 小哲不能靠“我已经把规则放进去了”证明回答可靠。 | ## 小哲心中隐隐的担心 这次会后，老板没再要求 AI 直接回答所有规则。 他看着 `prompt_context.conflict_count`，只说了一句： > 那你把旧活动删掉不就行了？ > 你苦笑了一下。 今天删旧活动，明天运营又加新活动。 今天改售后口径，后天客服主管又补审核话术。 如果所有内容都堆在一整段 Prompt 里，你改一处就怕影响一片。 Prompt 已经不像提示词了。 它越来越像一堵墙。
