# 长期记忆：保存跨会话信息之前，先划清隐私边界

本节总览图：这张图从左到右画出 `用户会话 -> 候选记忆 -> 隐私和价值判断 -> store(namespace, key, value) -> 后续会话读取`。判断节点分出“不保存敏感信息”“保存可撤回偏好”“写入业务数据库而非记忆”的分支，强调长期记忆不是自动记录所有对话。

## 课程目标

学完这一节，你应该能说清：
- 长期记忆和短期记忆的区别。
- LangGraph store 如何保存跨会话 JSON 文档。
- namespace 和 key 的作用。
- 工具如何通过 `runtime.store` 读写长期记忆。
- 哪些用户信息不应该随意保存。
- 电商场景中长期记忆的合理边界。

---

## 1. 为什么需要长期记忆 短期记忆只解决同一会话。长期记忆解决跨会话：

```latex
用户上周说喜欢顺丰配送 用户经常买数码配件 用户希望发票抬头默认为某公司
```

下次用户再来时，系统可以在合规和授权范围内提供更贴合的服务。
但长期记忆风险也更高。不能因为技术上能保存，就把所有对话都永久记录。
和第 17 课一样，这里的“长期”不是简单指保存时间更久，而是指**召回范围跨越单个 thread**。长期记忆可以被后续不同会话读取，通常用 store、namespace 和 key 组织；短期记忆则是同一 `thread_id` 里的 graph state。

---

## 2. 长期记忆如何存储 官方文档说明，长期记忆基于 LangGraph store，以 JSON 文档形式保存，并按 namespace 和 key 组织。

```latex
namespace = ("users", user_id, "preferences") key = "delivery" value = {"preferred_carrier": "SF Express"}
```

Store namespace key 图：这张图画出 store 像文件柜，第一层 namespace 包含 users、shops、orgs；users 下按 user_id 分区；每个分区里有多个 key，如 preferences、invoice、style。每个 key 对应 JSON value 和 metadata。图中强调 namespace 用于隔离用户和业务域。

---

## 3. 用 InMemoryStore 理解读写

```python
from langgraph.store.memory import InMemoryStore store = InMemoryStore() namespace = ("users", "user_123", "preferences") store.put(namespace, "delivery", {"preferred_carrier": "SF"}) item = store.get(namespace, "delivery") print(item.value)
```

`InMemoryStore` 只适合学习和测试。生产环境要使用数据库支持的 store，并考虑备份、删除、权限和审计。

---

## 4. 工具通过 runtime.store 访问长期记忆

```python
from dataclasses import dataclass from langchain.tools import tool, ToolRuntime @dataclass class Context: user_id: str @tool def get_delivery_preference(runtime: ToolRuntime[Context]) -> str: """读取用户配送偏好。""" item = runtime.store.get(("users", runtime.context.user_id, "preferences"), "delivery") if item is None: return "没有记录配送偏好。" return f"用户偏好配送方式：{item.value}"
```

模型不需要知道 store 怎么读写。工具负责把长期记忆转成安全、必要的信息。
官方概念里，长期记忆还可以按用途分成用户事实、偏好集合、经验记录、流程规则等类型。基础课不展开这些分类，你先掌握 store、namespace、key 和隐私边界。

---

## 5. 什么不该保存 长期记忆要经过隐私和业务价值判断。 不建议随意保存：
- 身份证号、银行卡、完整地址。
- 用户临时情绪表达。
- 未经确认的敏感偏好。
- 可能造成歧视或不公平服务的信息。
- 和服务无关的私人内容。
可以考虑保存：
- 用户明确授权的偏好。
- 可撤回的通知设置。
- 常用发票抬头，前提是有业务合规设计。
- 店铺或组织级配置。

## 6. 长期记忆写入前的判断

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396392267-99db5d2a-a8ad-41a2-82a6-385a74da81b7.png" title="null" crop="0,0,1,1" id="jxQ3D" class="ne-image">

长期记忆写入决策图：这张图从 `候选信息` 开始，依次经过四个判断：是否与服务相关、是否敏感、是否需要用户确认、是否有保留期限。通过后进入 store；不通过则丢弃或写入受控业务系统。图中要强调“用户说过”不等于“可以永久保存”。
推荐写入规则：

```latex
只有当信息与服务相关、用户明确表达稳定偏好、且不包含敏感内容时，才写入长期记忆。
```

## 7. 可运行 Demo：保存偏好

```python
from langgraph.store.memory import InMemoryStore store = InMemoryStore() def save_preference(user_id: str, key: str, value: dict) -> None: namespace = ("users", user_id, "preferences") store.put(namespace, key, value) def get_preference(user_id: str, key: str) -> dict | None: namespace = ("users", user_id, "preferences") item = store.get(namespace, key) return None if item is None else item.value save_preference("user_123", "delivery", {"preferred_carrier": "SF"}) print(get_preference("user_123", "delivery"))
```

观察点：
- namespace 隔离用户。
- key 表示具体记忆项。
- value 是 JSON 风格数据。
- demo 不包含敏感个人信息。

## 8. 常见错误

### 错误一：把聊天历史全部当长期记忆 长期记忆应该是筛选后的信息，不是完整对话归档。

### 错误二：没有删除和修改机制 用户偏好会变化，长期记忆必须能更新和删除。

### 错误三：跨用户 namespace 设计错误 长期记忆串用户比短期记忆串话更严重。

---

## 9. 本节知识框架总结

```latex
长期记忆 -> 跨 thread / 跨会话召回 -> LangGraph store -> namespace / key / value -> runtime.store 在工具中读写 -> 可以承载用户事实、偏好集合、经验或流程规则等类型 -> 保存前做隐私和价值判断 -> 支持更新、删除、隔离和审计
```

## 10. 本节小结 你需要记住：
1. 长期记忆跨 thread / 跨会话召回，短期记忆只在 thread 内。
2. store 用 namespace 和 key 组织 JSON 记忆。
3. 工具可以通过 `runtime.store` 安全读写。
4. 长期记忆不是越多越好，隐私边界优先。
5. 生产环境要考虑授权、删除、审计和数据保留期限。

4. 写出长期记忆写入前的三条规则。
