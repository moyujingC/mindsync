课程目标 学完这一节，你应该能说清： + 为什么工具参数 schema 是工具可靠性的第一道边界。 + 什么时候用简单类型，什么时候用 Pydantic。 + 工具可以返回字符串、对象和 `Command`。 + 工具异常应该如何转成模型能理解的信息。 + `ToolNode(handle_tool_errors=...)` 能解决什么问题。 + 订单号错误、订单不存在、接口超时这类问题应该如何设计失败路径。 --- ## 1. 为什么工具“能调用”还不够 第 9 课里，你已经看到最小工具： ```python @tool def get_order_logistics(order_no: str) -> str: """根据订单号查询物流信息。""" ... ``` 但生产场景不会这么简单。用户可能输入： ```latex 帮我查一下订单 订单号是 abc 查 20260001 和 20260002 我不是这个订单的收货人，也帮我查一下 ``` 工具层要处理： + 参数是否完整。 + 参数格式是否正确。 + 多个参数如何表达。 + 查询失败如何返回。 + 是否允许当前用户查询。 + 返回给模型的是人类可读文本还是结构化对象。 工具设计的目标不是“函数不报错”，而是： ```latex 正常路径清楚，失败路径也清楚。 ``` --- ## 2. 简单参数和复杂参数 简单工具可以直接用函数签名： ```python from langchain.tools import tool @tool def get_order_status(order_no: str) -> str: """根据订单号查询订单状态。""" return f"订单 {order_no} 已发货。" ``` 复杂工具建议用 Pydantic schema： ```python from typing import Literal from pydantic import BaseModel, Field from langchain.tools import tool class OrderSearchInput(BaseModel): order_no: str = Field(description="订单号，例如 20260001") include_logistics: bool = Field(default=True, description="是否包含物流信息") detail_level: Literal["summary", "full"] = Field( default="summary", description="返回摘要还是完整详情", ) @tool(args_schema=OrderSearchInput) def search_order(order_no: str, include_logistics: bool = True, detail_level: str = "summary") -> dict: """查询订单状态，可选择是否包含物流信息。""" orders = { "20260001": { "order_no": "20260001", "status": "SHIPPED", "payment_status": "PAID", "items": ["降噪耳机 Pro"], "logistics": { "carrier": "顺丰速运", "latest_event": "包裹已到达上海转运中心", }, }, "20260002": { "order_no": "20260002", "status": "PAID", "payment_status": "PAID", "items": ["机械键盘 K3"], "logistics": None, }, } order = orders.get(order_no) if order is None: return { "found": False, "message": f"没有查询到订单 {order_no}", } result = { "found": True, "order_no": order["order_no"], "status": order["status"], } if include_logistics: result["logistics"] = order["logistics"] if detail_level == "full": result["payment_status"] = order["payment_status"] result["items"] = order["items"] return result ``` Pydantic 的价值不只是“写起来规范”，还包括： + 字段描述帮助模型填参数。 + 默认值减少不必要追问。 + 枚举限制减少无效输入。 + 类型让调用前校验更明确。 --- ## 3. 参数 schema 要站在模型视角设计 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396373345-7eb3de1e-b03e-44e4-b093-8149c8d59201.png" title="null" crop="0,0,1,1" id="tO9IP" class="ne-image"> 工具参数 Schema 设计图：这张图左侧是用户自然语言，箭头指向模型提取参数；中间是工具 schema，列出字段名、类型、描述、默认值和枚举；右侧是工具函数执行。图中要用红色标注含糊字段名如 `x`、`flag` 会导致模型难以填参，用绿色标注 `order_no`、`include_logistics` 这类语义明确字段。 不推荐： ```python @tool def query(x: str, flag: bool) -> dict: """查询。""" ... ``` 推荐： ```python @tool def get_order_detail(order_no: str, include_logistics: bool = True) -> dict: """根据订单号查询订单详情，可选择是否包含物流信息。""" ... ``` 工具 schema 是模型看到的接口。你要把它当成给模型用的 API 文档来写。 --- ## 4. 工具返回字符串 字符串返回最简单，适合模型直接阅读： ```python @tool def get_refund_policy() -> str: """查询普通商品退货政策。""" return "普通商品支持签收后 7 天无理由退货，特殊商品除外。" ``` 优点： + 简单。 + 容易让模型生成自然语言回答。 缺点： + 程序不容易继续处理字段。 + 不适合复杂业务判断。 --- ## 5. 工具返回对象 对象返回适合后续程序继续处理： ```python @tool def get_order_detail(order_no: str) -> dict: """根据订单号查询订单详情。""" return { "order_no": order_no, "status": "SHIPPED", "paid_amount": 399, "currency": "CNY", "can_refund": None, "risk_notes": ["退款结论需要结合售后政策判断"], } ``` 对象返回的好处是字段清晰，但也要注意： + 不要返回内部敏感字段。 + 不要把数据库原始记录完整丢给模型。 + 字段名要稳定。 + 时间、金额、状态码最好同时有业务含义说明。 --- ## 6. `Command` 返回：工具更新状态 除了返回字符串和对象，工具也可以返回 `Command`。 这里的状态，指的是 LangGraph 运行时维护的 `State`，也就是当前流程里保存的数据。 比如用户说： ```latex 我想退订单 20260001 里的耳机。 ``` 工具查到订单后，后续流程可能还要继续判断： + 当前订单号是什么。 + 当前商品是什么。 + 是否已经签收。 + 是否可能进入退款流程。 + 是否需要人工确认。 如果工具只是返回一段文字，模型可以读懂，但后续节点不一定方便继续使用这些字段。 所以可以这样理解三种返回： | 返回方式 | 主要作用 | 适合场景 | | --- | --- | --- | | 字符串 | 把一段文字结果交给模型 | 简单政策说明、简单查询结果 | | 对象 | 返回结构化字段，模型和程序都能读 | 订单详情、物流状态、售后判断结果 | | `Command` | 返回结果的同时，要求 LangGraph 更新当前 `State` | 工具结果会影响后续节点和流程分支 | 基础阶段你先记住： ```latex 字符串：主要是返回一段可读文本。 对象：主要是返回结构化查询结果。 Command：不仅返回结果，还要修改 LangGraph 的 State。 ``` 一个简化例子： ```python from langchain.tools import tool from langgraph.types import Command @tool def select_order_for_refund(order_no: str) -> Command: """选择一个订单进入售后判断流程。""" return Command( update={ "current_order_no": order_no, "refund_flow_started": True, } ) ``` 这段代码的意思不是“把订单号告诉模型就结束”，而是告诉 LangGraph： ```latex 请把 current_order_no 写入当前 State， 并标记 refund_flow_started 为 True， 后续节点可以基于这些状态继续执行。 ``` 不要一开始就滥用 `Command`。如果只是查询订单状态，返回字符串或对象就够了。只有当工具结果需要影响后续流程状态时，才考虑返回 `Command`。 --- ## 7. 错误处理路径 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396373510-ce20c6d2-fe4e-4e7a-a481-e5a371940304.png" title="null" crop="0,0,1,1" id="eHjlJ" class="ne-image"> 工具错误处理路径图：这张图从 `工具调用` 分成四条错误路径：参数错误、业务不存在、外部服务失败、权限不足。每条路径先进入“内部异常或错误码”，再进入“对模型安全的错误消息”，最后回到模型生成面向用户的说明。图中要强调不要把 HTTP stack trace、数据库错误、内部接口地址直接暴露给用户。 错误不要只考虑 Python 异常。电商工具常见错误包括： | 错误 | 示例 | 面向模型的返回 | | --- | --- | --- | | 参数错误 | 订单号为空或格式错误 | “订单号格式不正确，请用户提供正确订单号” | | 业务不存在 | 查不到订单 | “未找到该订单，请核对订单号” | | 权限不足 | 用户查别人的订单 | “当前用户无权查询该订单” | | 服务失败 | 物流接口超时 | “物流系统暂时不可用，请稍后重试或转人工” | --- ## 8. `ToolNode(handle_tool_errors=...)` 在 LangGraph 工作流中，`ToolNode` 可以统一执行工具，也可以处理工具错误： ```python from langgraph.prebuilt import ToolNode tool_node = ToolNode( tools=[get_order_detail], handle_tool_errors=True, ) ``` 你也可以提供固定错误消息： ```python tool_node = ToolNode( tools=[get_order_detail], handle_tool_errors="工具调用失败，请检查输入或稍后再试。", ) ``` 这适合基础错误兜底。但业务系统里，你仍然应该尽量在工具内部把可预期错误转成清晰的业务错误。 --- ## 9. 可运行 Demo：参数校验和错误返回 ```python from pydantic import BaseModel, Field from langchain.tools import tool class OrderLookupInput(BaseModel): order_no: str = Field(description="订单号，只能包含数字，例如 20260001") @tool(args_schema=OrderLookupInput) def get_order_status(order_no: str) -> dict: """根据订单号查询订单状态。订单号必须是数字。""" if not order_no.isdigit(): return { "ok": False, "error_type": "INVALID_ORDER_NO", "message": "订单号格式不正确，请用户提供数字订单号。", } if order_no != "20260001": return { "ok": False, "error_type": "ORDER_NOT_FOUND", "message": "未找到该订单，请用户核对订单号。", } return { "ok": True, "order_no": order_no, "status": "SHIPPED", "latest_logistics": "包裹已到达上海转运中心。", } print(get_order_status.invoke({"order_no": "abc"})) print(get_order_status.invoke({"order_no": "20260002"})) print(get_order_status.invoke({"order_no": "20260001"})) ``` 观察点： + 参数错误没有抛出内部异常。 + 订单不存在和订单正常返回结构一致，都有 `ok` 字段。 + 错误消息是给模型理解的业务消息。 + 没有暴露内部数据库、HTTP 或代码异常。 --- ## 10. 本节知识框架总结 ```latex 工具可靠性 -> 参数 schema -> Pydantic / JSON Schema -> 字段名和描述面向模型设计 -> 返回 string / object / Command -> 可预期业务错误转成结构化结果 -> ToolNode(handle_tool_errors=...) 做兜底 -> 错误消息要安全、明确、可继续对话 ``` ## 11. 本节小结 你需要记住： 1. 工具不是只要能调用就够了，参数和错误路径同样重要。 2. 复杂参数优先用 Pydantic schema。 3. 返回对象时不要把内部原始记录完整暴露给模型。 4. 工具错误要转成模型和用户都能理解的业务信息。 5. `ToolNode` 的错误处理是兜底，不替代业务错误设计。 课后练习： 1. 为 `get_order_logistics` 增加订单号格式校验。 2. 设计 `ORDER_NOT_FOUND`、`LOGISTICS_TIMEOUT` 两类错误返回。 3. 把字符串返回改成结构化对象返回。 4. 思考哪些字段不应该返回给模型。
