# 上下文工程：把正确的信息放进模型当前能看到的位置

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396368458-8503f0b8-b1f3-444e-bfa2-a1af9061c4ce.png" title="null" crop="0,0,1,1" id="RBiAo" class="ne-image">

本节总览图：这张图从左到右画出 `用户问题 -> 可用信息池 -> 上下文选择 -> model context -> 模型回复`。可用信息池包含消息历史、订单状态、商品资料、政策片段、工具结果和用户偏好；上下文选择节点要画出“保留相关信息、丢弃无关信息、压缩过长历史”的动作，强调模型只能基于当前调用看到的上下文回答。

## 课程目标

学完这一节，你应该能说清：
- 什么是 context engineering。
- 为什么上下文不是越多越好。
- model context、tool context、state、runtime context 有什么区别。
- 什么是上下文窗口和上下文污染。
- 如何为一次回答选择最小必要上下文。
- 如何用 `wrap_model_call` 做调用前的临时上下文调整。
- 电商客服回答为什么需要精选订单、商品和政策信息。

---

## 1. 为什么需要上下文工程 模型不是直接连接你的数据库、文件系统和历史会话。每一次调用模型时，它只能看到你传进去的上下文。 比如用户问：

```latex
这个还能退吗？
```

这句话本身信息不足。你可能需要知道：
- “这个”指的是哪件商品。
- 订单是否已签收。
- 签收时间距现在多久。
- 商品是否属于特殊品类。
- 当前售后政策怎么写。
- 用户前面是否说过商品有质量问题。
但你不能把所有订单、所有商品、全部聊天历史、完整售后手册都塞给模型。上下文太多会带来成本、延迟和干扰。
上下文工程要解决的是：

```latex
本轮回答到底需要哪些信息？ 这些信息应该以什么形式放进模型？ 哪些信息不该放进去？
```

---

## 2. 官方视角：Agent 失败常常是上下文失败 LangChain 官方文档把 context engineering 放在 Agent 设计的重要位置。Agent 失败不一定是模型不聪明，也可能是：
- 缺少必要事实。
- 工具太多，模型不知道选哪个。
- 消息历史太长，重点被淹没。
- 过期信息和最新信息冲突。
- 系统提示词没有表达当前任务边界。
- 工具结果没有被整理成模型能理解的形式。
所以你不能只问“模型行不行”，还要问：

```latex
模型当前看到的上下文是否足够、准确、干净、相关？
```

## 3. 上下文不是一种东西

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396368158-1de0cffc-60c7-4f07-ae24-e639272434ad.png" title="null" crop="0,0,1,1" id="FWMee" class="ne-image">

上下文类型关系图：这张图中心是 `Agent run`，四周分别连接 `Model context`、`Tool context`、`State`、`Runtime context`。`Model context` 指向模型调用，包含 messages、system prompt、tools、response format；`Tool context` 指向工具函数，包含工具参数、runtime、store；`State` 标注会被保存并跨节点传递；`Runtime context` 标注本次运行的 user_id、tenant_id、channel 等不可变配置。
基础阶段先掌握四个概念：

| 概念 | 含义 | 电商例子 |
| --- | --- | --- |
| Model context | 本次模型调用能看到的信息 | 当前问题、精选历史、订单摘要、政策片段 |
| Tool context | 工具执行时能访问的信息 | 工具参数、当前用户、店铺配置 |
| State | 会话或图运行中的短期状态 | 消息列表、已查询订单结果 |
| Runtime context | 本次运行传入的外部上下文 | user_id、渠道、门店、权限 | 这一节重点讲 model context：模型当前能看到什么。

---

## 4. 上下文窗口和上下文污染 上下文窗口是模型一次调用能处理的最大输入范围。窗口越大，不代表你就应该塞越多。 常见问题有两类：

### 信息不足 用户问“能退吗”，上下文里没有订单签收时间和售后政策。模型只能猜。

### 信息污染 上下文里同时放了旧政策和新政策，或者把其他用户的订单信息放进来。模型可能引用错误事实，甚至造成隐私问题。 上下文工程的目标不是“把信息塞满”，而是：

```latex
让模型看到完成当前任务所需的最少、最新、最相关信息。
```

---

## 5. Model context 里可以控制什么 LangChain 文档中，model context 可以包含：
- system prompt + messages + tools + model + response format 这意味着你可以在调用模型前动态决定：
- 这轮使用哪版系统提示词。
- 保留哪些消息历史。
- 注入哪些订单或商品摘要。
- 暴露哪些工具。
- 是否要求结构化输出。
- 是否使用更强或更便宜的模型。
电商客服里，一个常见策略是：

```latex
普通商品咨询：商品资料 + 少量历史 订单物流查询：订单号 + 物流摘要 + 禁止编造规则 售后争议：售后政策 + 订单状态 + 人工确认边界
```

## 6. 临时上下文和持久状态的区别

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396369575-4935891d-cff5-48d0-949a-d0958415f43d.png" title="null" crop="0,0,1,1" id="bhyQU" class="ne-image">

临时上下文与持久状态图：这张图左侧是 `state["messages"]`，箭头进入 `wrap_model_call`；中间节点临时插入订单摘要或政策片段，箭头指向 `model context`；另一条虚线返回 `state`，标注“临时插入不一定写回 state”。图中要强调本轮模型看到的信息和长期保存的信息不是一回事。
官方文档强调，可以在模型调用前做 transient updates，也就是只修改本次模型看到的内容，不一定改变保存的 state。
这很重要。比如你可以把订单摘要临时插入本轮模型上下文：

```latex
订单 20260001：已发货，顺丰，最新节点：上海转运中心
```

但不一定要把这段摘要永久写入消息历史。否则后续对话越来越长，还可能残留过期状态。

## 7. 最小 demo：选择必要上下文 下面的 demo 不调用真实模型，先用 Python 展示“精选上下文”的思路。

```python
def build_context(user_question: str, order_summary: str | None, policy_snippet: str | None) -> list[tuple[str, str]]: system_prompt = ( "你是电商客服助手。回答必须基于提供的订单、商品或政策信息。" "如果上下文不足，请说明缺少什么信息。" ) context_parts = [] if order_summary and any(word in user_question for word in ["订单", "物流", "退", "售后"]): context_parts.append(f"订单信息：{order_summary}") if policy_snippet and any(word in user_question for word in ["退", "换", "保修", "售后"]): context_parts.append(f"政策信息：{policy_snippet}") if context_parts: system_prompt += "\n\n当前可用上下文：\n" + "\n".join(context_parts) return [ ("system", system_prompt), ("user", user_question), ] messages = build_context( user_question="这个耳机签收 10 天了，还能退吗？", order_summary="订单 20260002，商品：降噪耳机，签收时间：2026-05-01。", policy_snippet="普通数码配件支持 7 天无理由退货；质量问题按售后检测结果处理。", ) for role, content in messages: print(role, "=>", content)
```

观察点：
- 普通咨询不会注入订单信息。
- 售后问题会注入订单摘要和政策片段。
- 注入的是摘要，不是完整数据库记录。
- 如果缺少必要信息，系统提示词要求模型说明缺口。

## 8. 常见错误

### 错误一：把所有历史都塞进去 多轮会话越长，模型越容易被早期无关信息干扰。你需要裁剪、摘要或只保留任务相关信息。

### 错误二：把工具结果原样塞给模型 工具返回可能很长，也可能包含内部字段。推荐先转成模型需要的业务摘要。

### 错误三：把隐私信息当上下文随意传递 用户手机号、地址、身份证、支付信息等敏感数据要最小化使用。不要为了“模型更聪明”把不必要的隐私数据放进上下文。

### 错误四：让旧上下文覆盖新事实 如果物流状态更新了，旧的物流摘要不应该继续影响回答。要明确事实的更新时间。

---

## 9. 本节知识框架总结

```latex
上下文工程 -> 模型只能看到当前调用传入的信息 -> 上下文不是越多越好 -> model context 包含 prompt、messages、tools、model、response format -> tool context、state、runtime context 各有边界 -> 临时上下文不等于持久状态 -> 目标是最少、最新、最相关的信息
```

## 10. 本节小结 你需要记住：
1. Agent 很多错误来自上下文设计错误。
2. 上下文工程的核心是选择，而不是堆叠。
3. 模型当前看到的内容和系统长期保存的状态不是一回事。
4. 电商客服回答要注入订单、商品、政策等必要事实，但要避免无关历史和隐私泄露。
5. 好的上下文应该让模型知道“有什么事实、缺什么事实、哪些不能猜”。
课后练习：
1. 为“订单还没到”设计本轮最小上下文。

3. 写出哪些信息不应该放进模型上下文。
4. 比较“全量聊天历史”和“精选摘要”对回答质量的影响。
