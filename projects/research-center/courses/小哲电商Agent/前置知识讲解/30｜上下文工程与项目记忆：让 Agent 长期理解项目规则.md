Context window 是模型当前能看到的工作区 Claude Code 的 context window 可以包含： + 当前用户请求。 + 对话历史。 + 工具调用结果。 + 项目说明文件。 + 规则文件。 + Skills 的说明。 + MCP 工具描述。 + 子 Agent 返回结果。 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396400819-9f41e444-aafc-4e68-905b-059028ba4d00.png" title="null" crop="0,0,1,1" id="ky6z5" class="ne-image"> Context window 组成图：这张图画一个有限容量的矩形框表示 `context window`。框内分区放入 `current prompt`、`conversation history`、`tool results`、`project memory`、`rules`、`skill descriptions`、`MCP tool schemas`。框外画 `large codebase`、`full database`、`all policies`，用箭头标出它们只能被检索或按需加载，不能全部常驻上下文。 这和前面课程讲过的上下文概念可以对应起来： | 类型 | 解决的问题 | | --- | --- | | Model context | 模型当前能看到什么 | | Tool context | 工具执行时需要什么外部信息 | | State | 同一流程内保存什么状态 | | Runtime context | 本次运行固定传入什么身份和配置 | | Project memory | 长期项目规则和协作约定 | Claude Code 的项目记忆重点解决的是最后一类。 --- ## 3. CLAUDE.md 适合保存什么 官方 memory 文档介绍了 CLAUDE.md。你可以把它理解为项目级长期说明。 适合写入： + 项目启动方式。 + 常用测试命令。 + 代码风格。 + 目录结构说明。 + 重要业务规则。 + 安全边界。 + 不要修改的内容。 + 交付前检查清单。 不适合写入： + 临时对话。 + 大段源码。 + 所有接口返回样例。 + 经常变化的运行数据。 + 需要权限控制的敏感信息。 在业务 Agent 项目中，你可以设计类似 `AGENT.md` 的文件，告诉 Agent： ```latex 订单、物流、售后政策必须通过工具或知识库获取。 退款、发券、改地址属于高风险动作，需要人工确认。 回答用户时不能编造政策和订单状态。 ``` CLAUDE.md 是上下文，不是强制配置。它能引导模型，但不能替代权限系统。 常见作用域可以这样理解： | 作用域 | 常见位置 | 适合内容 | | --- | --- | --- | | 组织级 | 由管理员管理的位置 | 公司安全策略、统一代码规范 | | 项目级 | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 项目架构、测试命令、业务边界 | | 用户级 | `~/.claude/CLAUDE.md` | 个人偏好和常用工具习惯 | | 本地项目级 | `./CLAUDE.local.md` | 个人本地配置，不应提交到仓库 | 官方文档还说明，Claude Code 会从当前工作目录向上查找 CLAUDE.md 和 CLAUDE.local.md，并把它们拼接进上下文。越靠近当前工作目录的说明越具体，也越容易影响当前任务。 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396400171-658bfed4-1381-4548-b997-097f51ac76f8.png" title="null" crop="0,0,1,1" id="o8JSn" class="ne-image"> CLAUDE.md 加载顺序图：这张图画一棵目录树，从仓库根目录到子目录。箭头从上层目录的 `CLAUDE.md` 指向子目录的 `CLAUDE.md`，再指向 `CLAUDE.local.md`。旁边标注这些内容会被拼接进入 context window，而不是覆盖式配置；更具体的目录说明通常更贴近当前任务。 --- ## 4. Rules、auto memory 和 Skills Claude Code 文档中，CLAUDE.md 不是唯一的上下文机制。 下面这些名字指的是 Claude Code 当前官方文档里的上下文和记忆机制，不是业务 Agent 框架里的通用 API。具体可用性仍要以你安装的 Claude Code 版本和客户端形态为准。 | 机制 | 适合保存什么 | | --- | --- | | CLAUDE.md | 项目级长期说明和协作约定 | | `.claude/rules/` | 更细粒度、可按路径组织的规则 | | Auto memory | Claude Code 自动记录的偏好和长期信息 | | Skills | 某类任务的专门流程、脚本和参考资料 | <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396401311-517459d7-2a7b-4f63-ae64-87cf51eb8b51.png" title="null" crop="0,0,1,1" id="b1M4j" class="ne-image"> 记忆机制对比图：这张图按层级画出 `CLAUDE.md`、`.claude/rules/`、`auto memory`、`skills`。`CLAUDE.md` 连接到整个项目；`rules` 连接到特定目录或文件类型；`auto memory` 连接到用户偏好；`skills` 连接到特定任务类型。图中用不同颜色区分“长期常驻规则”和“按需触发能力”。 这给业务 Agent 一个重要启发： ```latex 不要把所有规则都写进一个巨大 prompt。 ``` 应该按用途分层： + 固定角色和安全口径放系统提示词。 + 项目级约定放项目记忆。 + 售后政策放知识库。 + 订单实时状态用工具查。 + 特定复杂流程用 LangGraph 显式编排。 CLAUDE.md 还支持用 `@path` 导入额外文件： ```markdown 见 @README.md 了解项目概览。 测试流程见 @docs/testing.md。 安全规则见 @docs/security.md。 ``` 但被导入内容仍然会占用上下文。售后政策全文不应该通过项目记忆导入，而应该进入知识库，由 RAG 按需检索。 对于大项目，官方文档建议用 `.claude/rules/` 组织更细粒度的规则。规则文件可以按目录或文件类型生效： ```markdown --- paths: - "agent-backend/**/*.py" --- # Backend Agent Rules - 工具函数必须有明确类型标注。 - 涉及用户身份的字段必须来自 runtime context。 - 高风险动作必须经过审批节点。 ``` 这类路径规则适合后端代码规则、前端组件规则、测试文件规则和安全相关目录规则。 --- ## 5. Compaction：上下文变长后的压缩 长任务会消耗上下文窗口。当上下文接近上限时，系统可能需要压缩历史信息。 压缩的目标是保留关键事实，丢弃低价值细节。但压缩也可能带来风险： + 细节丢失。 + 约束被弱化。 + 决策原因不清楚。 + 工具结果只剩摘要。 所以你应该把关键规则放在稳定位置，而不是只放在聊天历史里。 对于业务 Agent 来说： + 售后政策应该在知识库。 + 用户身份应该在 runtime context。 + 流程状态应该在 graph state。 + 审批结果应该持久化。 + 临时对话可以被摘要。 --- ## 6. 小 demo：设计项目记忆文件 下面是一个简化版 `AGENT.md` 示例： ```markdown # 电商客服 Agent 项目说明 ## 业务边界 - 订单状态必须通过订单工具查询。 - 售后政策必须通过知识库检索。 - 不允许编造物流节点、退款结果或赔付承诺。 ## 高风险动作 - 退款、发券、修改地址、取消订单必须人工确认。 - user_id、tenant_id、role 只能来自运行时上下文，不能由模型填写。 ## 验证要求 - 修改工具、Prompt 或知识库后，需要至少验证订单查询、售后问答和拒答边界。 ``` 这个文件不是 prompt 的替代品，而是项目级长期上下文。 --- ## 7. 常见错误 ### 错误一：把所有内容塞进系统提示词 系统提示词过长会难维护，也容易挤占模型上下文。 ### 错误二：把实时事实写进项目记忆 订单状态、库存、物流节点是实时数据，应该用工具查询。 ### 错误三：把敏感信息写入记忆 用户手机号、地址、身份证、token 不应该进入长期项目记忆。 ### 错误四：把项目记忆当成强制规则 项目记忆只是上下文。禁止读取 `.env`、禁止调用退款工具这类硬约束，必须通过权限、Hook、guardrail 或后端校验实现。 --- ## 8. 本节知识框架总结 ```latex 上下文工程 -> context window 是模型当前工作区 -> 上下文有限，需要分层管理 -> CLAUDE.md 保存项目级长期规则 -> rules 保存更细粒度规则 -> auto memory 保存长期偏好 -> skills 保存特定任务能力 -> compaction 会压缩历史但可能丢失细节 -> 业务 Agent 要区分项目记忆、会话记忆、运行时上下文和实时工具数据 ``` ## 9. 本节小结 你需要记住： 1. 上下文工程不是堆内容，而是选择和组织信息。 2. 长期项目规则应该稳定保存，不要只依赖聊天历史。 3. 实时事实应该通过工具或 RAG 获取。 4. 敏感数据不应该写进长期记忆。 5. Claude Code 的记忆设计可以帮助你设计业务 Agent 的上下文分层。 课后练习： 1. 为电商客服 Agent 写一份 10 行以内的项目记忆说明。 2. 标出哪些信息应该放知识库，哪些应该放工具，哪些应该放 runtime context。 3. 说明为什么订单状态不应该写入长期记忆。
