RAG 的基本流程 RAG 通常包含两个阶段。 索引阶段： ```latex 原始资料 -> 加载为 Document -> 切成 chunk -> 生成 embedding -> 存入 vector store ``` 回答阶段： ```latex 用户问题 -> 检索相关 chunk -> 放入模型上下文 -> 生成回答 ``` <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396376300-b9cadb53-7c84-4a92-9794-c769d496049e.png" title="null" crop="0,0,1,1" id="CIgsL" class="ne-image"> RAG 双阶段流程图：这张图上下分两层。上层是索引阶段，从政策文档、商品说明进入 Document loader，再到 text splitter、embedding、vector store；下层是问答阶段，从 user query 到 query embedding、retriever、top-k chunks、chat model、final answer。上下两层通过 vector store 连接。 --- ## 3. 核心组件 | 组件 | 作用 | 电商例子 | | --- | --- | --- | | `Document` | 文本和元数据的标准单元 | 一段售后政策及来源 | | Text splitter | 把大文档切成小片段 | 按章节切商品说明 | | Embeddings | 把文本变成向量 | “退货”与“退款”语义接近 | | Vector store | 存储和搜索向量 | 商品政策知识库 | | Retriever | 根据问题返回相关文档 | 查“耳机保修”相关片段 | 这些组件是模块化的。你可以替换 embedding 模型或向量数据库，而不必重写整个问答逻辑。 --- ## 4. RAG 和长 Prompt 的区别 长 prompt 的做法是把大量资料直接塞给模型： ```latex 用户问题 + 完整售后政策 + 完整商品手册 + 完整活动规则 ``` RAG 的做法是先检索： ```latex 用户问题 -> 找最相关的几段资料 -> 只把这些片段给模型 ``` 长 prompt 的问题： + 成本高。 + 延迟高。 + 容易超过上下文窗口。 + 相关信息被无关内容淹没。 + 资料更新后难维护。 RAG 的优势： + 只注入相关资料。 + 可保留来源。 + 更容易更新知识库。 + 可控制召回数量和质量。 --- ## 5. RAG 架构类型 LangChain retrieval 文档提到几类常见架构： | 架构 | 特点 | | --- | --- | | 2-step RAG | 固定流程：先检索，再生成 | | Agentic RAG | Agent 判断什么时候检索、如何检索 | | Hybrid RAG | 在固定流程和 Agent 决策之间加入查询改写、相关性判断等中间步骤 | 基础阶段先掌握 2-step RAG。Agentic RAG 会在第 16 课展开。 --- ## 6. 最小 Demo：用内存列表模拟检索 这个 demo 不依赖向量数据库，只用关键词模拟 RAG 流程，帮助你看清机制。 ```python POLICIES = [ { "source": "after_sale_policy_v1", "text": "普通数码配件支持签收后 7 天无理由退货，质量问题按售后检测结果处理。", }, { "source": "invoice_policy_v1", "text": "电子发票开具后如抬头错误，可在 30 天内申请重开。", }, ] def retrieve(query: str) -> list[dict]: keywords = ["退", "售后", "发票", "抬头"] return [ doc for doc in POLICIES if any(keyword in query and keyword in doc["text"] for keyword in keywords) ] question = "耳机签收 8 天了还能无理由退吗？" docs = retrieve(question) print("检索结果：") for doc in docs: print(doc["source"], doc["text"]) ``` 观察点： + 模型回答前先拿到相关政策。 + 检索结果带有来源。 + 如果没有检索结果，就不应该编造政策。 --- ## 7. 常见错误 ### 错误一：把 RAG 当成“不会幻觉”的保证 RAG 能降低幻觉，但不能保证模型永远正确。检索错了、切片错了、上下文写错了，回答仍然会错。 ### 错误二：不保留来源 没有来源，客服无法追溯答案依据。RAG 文档必须保留 metadata。 ### 错误三：知识库长期不更新 RAG 依赖外部知识。如果活动规则变了但知识库没更新，模型仍然会基于旧资料回答。 --- ## 8. 本节知识框架总结 ```latex RAG -> Retrieval：检索相关资料 -> Generation：基于资料生成回答 -> Document / chunk / embedding / vector store / retriever -> 索引阶段和回答阶段分开 -> 2-step RAG / Agentic RAG / Hybrid RAG -> 保留来源，处理低召回和旧资料 ``` ## 9. 本节小结 你需要记住： 1. RAG 用外部知识弥补模型知识过期和不了解内部资料的问题。 2. RAG 不是把所有资料塞进 prompt，而是先检索相关片段。 3. `Document`、chunk、embedding、vector store、retriever 是核心链路。 4. RAG 降低幻觉，但仍需要来源、更新和评估。 课后练习： 1. 列出电商客服需要进入知识库的 5 类资料。 2. 写出“售后政策问答”的 RAG 流程。 3. 思考哪些问题不应该走 RAG，而应该查业务系统。 4. 解释 RAG 和 Tool Calling 的区别。
