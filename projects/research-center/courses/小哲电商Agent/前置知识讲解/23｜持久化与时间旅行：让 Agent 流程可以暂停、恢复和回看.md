Checkpoint 保存什么 checkpoint 可以理解为某一步执行后的状态快照。它通常关联： + 当前 state。 + thread config。 + checkpoint id。 + 上一步和下一步信息。 + 节点写入记录。 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396395190-16f1d1f0-0ff0-401b-bffb-9a1717fefa82.png" title="null" crop="0,0,1,1" id="qE6Fz" class="ne-image"> checkpoint 结构图：这张图中心是 checkpoint，向外连接 `state values`、`config(thread_id/checkpoint_id)`、`metadata`、`next nodes`、`tasks`。旁边画一条 thread 中的 checkpoint 序列，说明同一 thread 会产生多个 checkpoint。 --- ## 3. 最小持久化写法 ```python from langgraph.checkpoint.memory import InMemorySaver checkpointer = InMemorySaver() graph = builder.compile(checkpointer=checkpointer) config = {"configurable": {"thread_id": "customer_001"}} graph.invoke({"question": "订单能退吗？"}, config) ``` `InMemorySaver` 适合学习。生产环境要使用数据库支持的 checkpointer。 --- ## 4. Durability Modes：checkpoint 写入时机 启用 checkpointer 之后，LangGraph 就具备 durable execution 的基础。但还有一个问题： ```latex checkpoint 应该什么时候真正写入持久化存储？ ``` 写得越及时，崩溃恢复能力越强；写得越少，运行开销越低。LangGraph 官方提供三种 durability modes，用来在性能和持久性之间做取舍。 调用图时可以指定： ```python for chunk in graph.stream( {"question": "订单能退吗？"}, config, durability="sync", ): print(chunk) ``` 三种模式从低持久性到高持久性如下： | 模式 | 写入时机 | 优点 | 风险 | 适合场景 | | --- | --- | --- | --- | --- | | `"exit"` | 图执行退出时保存，包括成功、报错或 interrupt 退出 | 性能最好，长流程中间开销低 | 进程在中途崩溃时，中间状态可能没有保存 | 学习、低风险流程、可重跑任务 | | `"async"` | 下一步执行时异步保存上一步变化 | 性能和持久性折中 | 进程刚好崩溃时，少量 checkpoint 可能还没写入 | 大多数普通在线流程 | | `"sync"` | 下一步开始前同步保存当前 checkpoint | 每一步写入最可靠 | 性能开销更高 | 高风险审批、资金相关、不可轻易重跑的流程 | <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396396181-676ddd08-8a13-4d76-824d-ab7efb80cc74.png" title="null" crop="0,0,1,1" id="LieAi" class="ne-image"> Durability Modes 对比图：这张图横向画出一个 graph execution：`step 1 -> step 2 -> step 3 -> exit`。在三条并行泳道中分别展示 `"exit"`、`"async"`、`"sync"` 的 checkpoint 写入位置。`"exit"` 只在末尾写入；`"async"` 在下一步执行时异步写入上一步；`"sync"` 在进入下一步前先同步写入。图中要用标注说明：越靠近 `"sync"`，崩溃恢复越可靠，但性能开销越高。 注意：durability mode 只控制 checkpoint 的写入时机，不解决所有可靠性问题。 它不能替代： + retry。 + timeout。 + 数据库事务。 + 外部 API 的幂等设计。 + 高风险动作前的人工确认。 如果节点里调用了退款、发券、发短信这类外部副作用，即使用 `"sync"`，也仍然要设计幂等键、状态检查和审计记录。 --- ## 5. 查看当前状态和历史 ```python current_state = graph.get_state(config) history = list(graph.get_state_history(config)) ``` 你可以用这些信息回答： + 当前流程停在哪。 + 每一步 state 如何变化。 + 哪个节点写入了哪个字段。 + 是否存在错误或 interrupt。 --- ## 6. Replay 和 Fork LangGraph 时间旅行支持两类常见操作： | 操作 | 含义 | | --- | --- | | Replay | 从过去 checkpoint 重新执行后续节点 | | Fork | 从过去 checkpoint 修改状态，创建新分支继续执行 | Replay 适合复现问题。Fork 适合实验不同输入或修正某个中间状态。 注意：replay 会重新执行 checkpoint 之后的节点，包括 LLM 调用和外部 API，结果可能和第一次不同。 --- ## 7. 时间旅行调试图 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396396177-94bf6d6a-9df2-42cf-95cf-4588fd3e21f9.png" title="null" crop="0,0,1,1" id="qHLJz" class="ne-image"> 时间旅行调试图：这张图画一条执行历史 `A -> B -> C -> D`，在 B 后方标出“错误从这里开始”。Replay 路径从 B 重新执行 C 和 D；Fork 路径从 B 修改 state 为 B'，再执行 C' 和 D'。图中要标注旧分支和新分支互不覆盖。 --- ## 8. 常见错误 ### 错误一：没有 thread_id 没有稳定 thread_id，就很难把多轮状态和 checkpoint 关联起来。 ### 错误二：生产环境使用内存保存 服务重启后内存状态会丢失。生产要用持久化存储。 ### 错误三：以为 replay 不会产生副作用 后续节点会重新执行。外部 API、发短信、退款等副作用必须谨慎设计幂等。 ### 错误四：以为 `durability="sync"` 等于业务事务 `"sync"` 只是保证 checkpoint 在继续下一步前同步写入。它不能保证外部系统调用一定成功，也不能自动回滚已经发生的副作用。 --- ## 9. 本节知识框架总结 ```latex 持久化 -> checkpointer 保存 checkpoint -> thread_id 关联一条运行历史 -> durability modes 控制 checkpoint 写入时机 -> exit 性能最好但中途崩溃恢复弱 -> async 在性能和持久性之间折中 -> sync 持久性最强但开销更高 -> get_state 查看当前状态 -> get_state_history 查看历史 -> replay 重新执行后续节点 -> fork 修改旧状态并创建新分支 -> 外部副作用要考虑幂等 ``` ## 10. 本节小结 你需要记住： 1. 持久化让 Agent 可以恢复和调试。 2. checkpoint 是状态快照，不只是日志。 3. durability mode 决定 checkpoint 的写入时机。 4. 时间旅行适合复现和调试复杂流程。 5. replay 可能重新触发外部调用，副作用要谨慎。 课后练习： 1. 为一个售后流程设计 thread_id。 2. 说明 checkpoint 和普通日志的区别。 3. 比较 `"exit"`、`"async"`、`"sync"` 三种 durability mode。 4. 举例说明 replay 可能造成的副作用。 5. 画出一个 fork 调试场景。
