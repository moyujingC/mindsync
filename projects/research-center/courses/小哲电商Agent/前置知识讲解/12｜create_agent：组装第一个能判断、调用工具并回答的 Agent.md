课程目标 学完这一节，你应该能说清： + `create_agent` 解决什么问题。 + `model`、`tools`、`system_prompt` 是最小 Agent 的核心参数。 + 如何用 `invoke` 跑一次 Agent。 + 返回结果里的 `messages` 如何理解。 + 模型什么时候直接回答，什么时候调用工具。 + 最小 Agent 和完整业务系统之间的边界。 --- ## 1. 为什么需要 create_agent 如果你只调用模型： ```python model.invoke("帮我查订单 20260001 的物流") ``` 模型只能根据已有语言知识回答，无法自动查询业务系统。 如果你有工具，但没有 Agent 循环，你还要自己写： ```latex 模型是否需要工具？ 调用哪个工具？ 参数是什么？ 工具结果如何回给模型？ 是否需要继续调用？ 什么时候结束？ ``` `create_agent` 解决的是常见 Agent 闭环的组装问题： ```latex 模型 + 工具 + 系统提示词 + 执行循环 ``` --- ## 2. 最小 Agent 的三个核心输入 <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396375661-76a28b21-18cd-4459-a36a-9dae736ed9d9.png" title="null" crop="0,0,1,1" id="a9ivK" class="ne-image"> create_agent 输入结构图：这张图中心是 `create_agent`，左侧三条箭头分别来自 `model`、`tools`、`system_prompt`。`model` 标注负责理解和生成，`tools` 标注负责外部事实和动作，`system_prompt` 标注负责角色和边界。右侧输出 `agent`，下面连接 `invoke` 和 `stream`。 最小写法： ```python from langchain.agents import create_agent agent = create_agent( model=model, tools=[get_order_status], system_prompt="你是电商客服助手。订单状态必须通过工具查询。", ) ``` 三个输入分别是： | 参数 | 作用 | | --- | --- | | `model` | 负责推理、生成、决定是否调用工具 | | `tools` | 外部能力列表 | | `system_prompt` | 角色、规则、边界 | --- ## 3. 可运行 Demo：订单查询 Agent 前提： + 已配置 `AGENT_OPENAI_API_KEY` + 已配置 `AGENT_OPENAI_BASE_URL` + 已配置 `AGENT_OPENAI_MODEL` ```python import os from langchain.agents import create_agent from langchain.tools import tool from langchain_openai import ChatOpenAI @tool def get_order_status(order_no: str) -> dict: """根据订单号查询订单状态。适合回答订单是否发货、当前处理状态等问题。""" if order_no != "20260001": return { "ok": False, "message": "未找到该订单，请用户核对订单号。", } return { "ok": True, "order_no": order_no, "status": "SHIPPED", "latest_event": "订单已出库，等待揽收。", } model = ChatOpenAI( model=os.environ["AGENT_OPENAI_MODEL"], api_key=os.environ["AGENT_OPENAI_API_KEY"], base_url=os.environ["AGENT_OPENAI_BASE_URL"], temperature=0, ) agent = create_agent( model=model, tools=[get_order_status], system_prompt=( "你是电商客服助手。" "订单状态必须通过工具查询，不能编造。" "如果用户没有提供订单号，请要求补充订单号。" ), ) result = agent.invoke({ "messages": [ {"role": "user", "content": "帮我查一下订单 20260001 的状态"} ] }) print(result["messages"][-1].content) ``` 观察点： + 模型是否调用 `get_order_status`。 + 工具参数是否是 `20260001`。 + 最终回答是否基于工具结果。 + 模型是否避免编造未返回的信息。 --- ## 4. 返回结果里的 messages Agent 返回的不只是一段最终文本。通常你会看到一个 `messages` 列表，里面可能包含： ```latex HumanMessage AIMessage(tool_calls=[...]) ToolMessage(...) AIMessage(final answer) ``` <img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396375708-88a94190-05eb-4348-8e85-0996942aa780.png" title="null" crop="0,0,1,1" id="EHu32" class="ne-image"> Agent messages 时间线图：这张图从上到下画消息时间线：`HumanMessage` 用户提问，`AIMessage` 携带 tool_calls，`ToolMessage` 携带工具返回，最后 `AIMessage` 携带最终回答。每条消息旁标注是谁生成的、用途是什么、是否面向最终用户展示。 最终用户通常只看最后一条 `AIMessage`，但调试 Agent 时，你应该查看完整消息列表。 --- ## 5. 不需要工具的问题 同一个 Agent 不应该每轮都调用工具。 输入： ```latex 你是谁？ ``` 预期： + 不调用订单工具。 + 直接说明自己是电商客服助手。 这说明 Agent 的价值不是“强制调用工具”，而是： ```latex 模型根据当前问题判断是否需要外部能力。 ``` --- ## 6. system_prompt 不能替代工具 错误写法： ```python system_prompt = "你是电商客服。订单 20260001 已发货。" ``` 这会把动态业务事实写死在提示词里。订单状态会变化，不能长期写在 system prompt。 推荐： ```python system_prompt = "你是电商客服。订单状态必须通过工具查询，不能编造。" ``` 动态事实应该来自工具或检索结果，系统提示词负责规则和边界。 --- ## 7. 最小 Agent 和完整业务系统的边界 这一节的 demo 只是验证 `create_agent` 的最小闭环。完整业务系统还需要： + 用户身份和权限。 + 真实订单接口。 + 错误处理。 + 日志和 trace。 + 人工确认。 + 安全边界。 + 前端体验。 不要把一个 demo 误认为完整系统。基础课先让你理解机制，项目课会围绕完整项目展开。 --- ## 8. 下一步：实时数据之外，知识资料怎么办 学到这里，你已经能用 `create_agent` 组装一个可以判断问题、调用工具、读取工具结果并生成回答的最小 Agent。 但这会自然引出另一个问题： ```latex 工具很适合查订单、库存、物流这类实时业务数据。 那商品说明、售后政策、发票规则、活动条款这类知识资料怎么办？ ``` 你当然可以把“查询政策”“查询商品说明”也写成工具。这个思路没有错，但如果资料很多、更新频繁、需要按语义查找，单纯写几个固定查询函数会很快遇到问题： + 政策文档很多，不可能全部写进 system prompt。 + 商品资料会变化，不能依赖模型记忆。 + 用户问法很口语，不能只靠关键词精确匹配。 + 回答需要保留来源，方便客服追溯。 + 知识库没有答案时，模型应该说不确定，而不是编造。 所以工具解决的是“Agent 如何连接外部能力”，但知识资料还需要另一套机制： ```latex 先从外部知识库检索相关资料， 再让模型基于这些资料回答。 ``` 这就是下一课 RAG 要解决的问题。 --- ## 9. 常见错误 ### 错误一：工具描述太含糊 工具 docstring 决定模型什么时候调用工具。不要只写“查询信息”。 ### 错误二：system_prompt 写动态事实 订单、库存、物流、售后状态都应该查系统，不应该写死。 ### 错误三：只看最终回答，不看中间消息 调试 Agent 时必须看 tool call、工具参数和 ToolMessage。 --- ## 10. 本节知识框架总结 ```latex create_agent -> model：推理和生成 -> tools：外部能力 -> system_prompt：角色和边界 -> invoke：运行一次 -> messages：完整执行轨迹 -> 模型判断是否调用工具 -> 最小 demo 不等于完整业务系统 -> 实时数据通常走工具，知识资料会引出 RAG ``` ## 11. 本节小结 你需要记住： 1. `create_agent` 是组装常见 Agent 闭环的入口。 2. 最小 Agent 至少需要模型、工具和系统提示词。 3. 动态业务事实必须通过工具或检索获得。 4. 返回结果里的 `messages` 是理解 Agent 行为的关键。 5. Demo 只验证机制，不代表完整项目。 6. 当问题从实时业务数据扩展到大量知识资料时，就需要引入 RAG。 课后练习： 1. 添加一个 `get_product_stock(product_id: str)` 工具。 2. 让 Agent 回答“这款商品还有库存吗？”。 3. 测试“你是谁？”是否不调用工具。 4. 打印完整 `messages`，标出 HumanMessage、AIMessage 和 ToolMessage。
