# Agent 场景地图：先判断任务边界，再决定是否使用 Agent

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396365956-a6df820e-dfac-4b0c-b3dd-2cf11be99b2b.png" width="1672" title="null" crop="0,0,1,1" id="klsVc" class="ne-image">

本节总览图：这张图从左到右画出 `业务问题 -> 任务分类 -> 技术处理方式 -> 风险边界`。`任务分类` 分成五类：直接回答、查知识库、查工具、人工确认、不适合 Agent。每一类箭头分别指向不同处理方式：模型直接生成、RAG 检索、Tool Calling、Human-in-the-loop、规则系统或拒绝处理。图中要强调：不是所有业务问题都应该交给 Agent 自动执行。

## 什么是场景地图 场景地图不是技术架构图，也不是完整的业务流程图。 它更像一张“任务分类图”：把真实业务中会遇到的问题，按照处理方式和风险边界先分清楚。比如哪些问题可以让模型直接回答，哪些问题必须查知识库，哪些问题必须调用业务系统，哪些问题需要人工确认，哪些问题根本不应该交给 Agent 自动处理。 所以，场景地图解决的不是“代码怎么写”，而是先回答一个更前置的问题：

```latex
这个业务问题应该由谁处理，用什么能力处理，边界在哪里？
```

只有先把场景地图画清楚，后面设计 Prompt、RAG、工具、记忆和 LangGraph 流程才不会跑偏。

## 课程目标

学完这一节，你应该能说清：
- 为什么做 Agent 之前要先画场景地图。
- 什么任务适合直接模型回答。
- 什么任务应该查知识库。
- 什么任务必须查工具或业务系统。
- 什么任务需要人工确认。
- 什么任务不适合交给 Agent 自动处理。
- 为什么确定性规则、业务系统和 Agent 应该配合，而不是互相替代。

## 1. 为什么要先做场景地图 很多人第一次做 Agent 时，会直接想：

```latex
我要做一个客服 Agent，什么问题都让它回答。
```

这个想法风险很高。
因为同样是客服问题，背后的处理方式可能完全不同。
例如：

| 用户问题 | 背后真正需要什么 |
| --- | --- |
| “这款耳机适合通勤吗？” | 商品知识和推荐表达 |
| “订单20260001到哪了？” | 实时订单和物流事实 |
| “用了两天有电流声，可以退吗？” | 售后政策、订单状态、可能人工判断 |
| “帮我直接退款” | 高风险动作、权限和审批 |
| “把所有客户手机号导出来” | 敏感数据，通常不应处理 | 如果你不先做场景分类，就容易把所有问题都塞给模型。结果是：

- 模型编造实时事实。
- 工具调用过度。
- 高风险动作缺少审批。
- 简单规则被复杂化。
- 隐私和权限边界失控。
所以做 Agent 前，第一步不是写代码，而是画出场景地图。

## 2. 官方理念：模型应该和外部数据、计算协作 LangChain 官网在介绍框架理念时强调过一个核心判断。这里保留英文原文作为对照：

```latex
LLMs are even better when you combine them with external sources of data.
```

对应中文可以理解为：

```latex
当你把大语言模型和外部数据源结合起来时，它会变得更有用。
```

也就是说，模型本身很强，但它不应该独自承担所有任务。课程里会说明相关官网链接，但不会要求你直接阅读本地整理出来的官方文档文件。
官方文档还强调，模型不只用于 text generation，也可以用于编排更复杂的流程，让应用与外部数据和计算交互。
这给我们一个设计原则：

```latex
模型负责理解和编排 外部系统负责事实和动作 规则系统负责确定性约束 人工负责高风险判断
```

Agent 的价值不是替代所有系统，而是把这些能力组织起来。

## 3. 五类任务边界

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396366368-bc2e5b1b-5b39-49ea-b29d-e55399753d7d.png" title="null" crop="0,0,1,1" id="Gv0Zz" class="ne-image">

五类任务边界图：这张图画一个从低风险到高风险的横轴，依次放置 `直接回答`、`查知识库`、`查工具`、`人工确认`、`不适合 Agent` 五类任务。每类下面标出判断条件、典型输入和处理方式。箭头从左到右表示自动化风险逐步升高，越往右越需要规则、权限、审批或拒绝。
本节使用五类任务来判断场景：

```latex
直接回答 查知识库 查工具 人工确认 不适合 Agent
```

这五类不是技术名词，而是设计 Agent 时的任务分流方式。

### 直接回答 适合模型直接回答的问题通常满足：
- 不需要实时业务事实。
- 不涉及用户隐私。
- 不涉及实际业务动作。
- 可以基于一般知识、已给上下文或公开信息回答。
例子：

```latex
请用更礼貌的语气改写这段客服回复。
```

这种任务可以直接让模型生成。

### 查知识库 适合查知识库的问题通常满足：
- 答案来自文档、政策、说明书或 FAQ。
- 资料可能变化，不能完全依赖模型记忆。
- 需要引用来源或保持口径一致。
例子：

```latex
这个耳机支持多久质保？
```

这类问题适合 RAG 或知识库检索。

### 查工具 适合查工具的问题通常满足：
- 答案来自实时业务系统。
- 需要订单、库存、物流、发票、售后状态等事实。
- 模型不能凭空知道。
例子：

```latex
订单20260001现在到哪了？
```

这类问题必须通过工具或业务接口查询。

### 人工确认 需要人工确认的问题通常满足：
- 影响资金、权益、权限或用户承诺。
- 模型可以辅助判断，但不能直接执行。
- 需要审批、确认或人工复核。
例子：

```latex
这个客户投诉很多次，直接补偿一张 100 元优惠券吧。
```

Agent 可以整理信息、给出建议，但不能无审批发券。

### 不适合 Agent 不适合 Agent 的任务通常满足：
- 明显违规。
- 请求敏感数据。
- 要求绕过权限。
- 没有必要使用模型。
- 后果不可控。
例子：

```latex
把所有客户手机号导出来给我。
```

这类任务应该拒绝或走严格权限流程，而不是交给 Agent 自动处理。

## 4. 确定性系统和 Agent 的关系

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396366292-cbee2ce6-78d9-41bb-a6d4-0272e92ab7e6.png" title="null" crop="0,0,1,1" id="igXOX" class="ne-image">

确定性系统与 Agent 分工图：这张图左侧画 `确定性系统`，包含规则、数据库、权限、审批和交易接口；右侧画 `Agent`，包含自然语言理解、工具选择、信息整合和回复生成。箭头从 Agent 指向确定性系统表示查询或申请动作，箭头从确定性系统回到 Agent 表示返回事实、规则结果或审批状态。图中要标明 Agent 不直接替代规则和交易系统。
Agent 不应该替代确定性系统。
确定性系统适合：
- 判断订单是否存在。
- 判断是否超过退货期。
- 判断库存数量。
- 判断用户是否有权限。
- 执行退款、改地址、发票开具等业务动作。
Agent 适合：
- 理解用户自然语言。
- 判断应该查哪个信息源。
- 把多个系统返回的信息组织成回答。
- 在信息不足时追问。
- 在风险升高时转人工。
例如退货规则：

```latex
签收后 7 天内可无理由退货
```

这个判断不应该让模型自由发挥。应该由规则系统或后端函数判断。模型可以做的是：

```latex
解释规则、追问必要信息、调用规则判断工具、把结果说清楚。
```

## 5. 风险越高，自动化越要收紧 电商业务里，任务风险可以粗略分成三档。

| 风险 | 例子 | 建议处理 |
| --- | --- | --- |
| 低风险 | 改写话术、解释商品参数 | 可直接模型回答或查知识库 |
| 中风险 | 查订单、查物流、查售后状态 | 必须查工具，不能编造 |
| 高风险 | 退款、赔付、发券、改地址 | 需要确认、权限、审批和审计 | 这条规则非常重要：

```latex
低风险可以自动回答，中风险必须查事实，高风险必须有边界。
```

Agent 设计的成熟度，不是看它能自动做多少事，而是看它知道什么时候不能自动做。

## 6. 场景分类练习 下面给出几个业务场景。你先不要看答案，先判断它们分别属于哪一类：
- 直接回答 + 查知识库 + 查工具 + 人工确认 + 不适合 Agent 题目：

| 编号 | 用户问题 | 你的判断 |
| --- | --- | --- |
| 1 | 帮我把这段客服回复改得更礼貌 |
| | 2 | 这款耳机适合通勤吗？

|
| | 3 | 这款耳机支持多久质保？

|
| | 4 | 订单20260001到哪了？

|
| | 5 | 订单20260002有没有开发票？

|
| | 6 | 我用了两天有电流声，可以退吗？

|
| | 7 | 直接给这个客户退款 |
| | 8 | 给客户发一张 100 元优惠券 |
| | 9 | 把所有客户手机号导出来 |
| | 10 | 帮我查一下库存还剩多少 |
| | 11 | 这个活动规则怎么解释？

|
| | 12 | 帮我删除这个用户的差评 |
| 参考答案：

| 编号 | 建议分类 | 判断理由 |
| --- | --- | --- |
| 1 | 直接回答 | 只是改写话术，不需要实时事实，也不涉及业务动作。

|
| 2 | 直接回答 / 查知识库 | 如果只是根据已知商品信息做表达，可以直接回答；如果需要准确参数，应该查商品知识库。

|
| 3 | 查知识库 | 质保属于政策或商品说明，应该来自文档资料。

|
| 4 | 查工具 | 物流状态是实时业务事实，必须查订单或物流系统。

|
| 5 | 查工具 | 发票状态来自订单、发票系统，模型不能凭空回答。

|
| 6 | 查知识库 + 查工具，可能人工确认 | 需要售后政策，也可能需要订单状态、签收时间和人工判断。

|
| 7 | 人工确认 | 退款影响资金，不能由 Agent 直接执行。

|
| 8 | 人工确认 | 发券影响权益和成本，需要权限、审批和审计。

|
| 9 | 不适合 Agent | 批量导出手机号涉及敏感数据和权限风险。

|
| 10 | 查工具 | 库存是实时业务事实，必须查库存系统。

|
| 11 | 查知识库 | 活动规则来自运营文档或规则说明。

|
| 12 | 不适合 Agent | 删除差评涉及平台规则、权限和合规风险，不能让 Agent 自动处理。

| 观察点：

- 分类依据不是关键词本身，而是背后的数据来源、业务动作和风险边界。
- 同一句话可能不只属于一类，比如“可以退吗”往往同时涉及政策、订单事实和人工判断。
- 后续真正的 Agent 可以让模型辅助分类，但边界规则不能只靠模型自由发挥。
- 场景地图的价值，是在写代码前先把“该自动化什么、不该自动化什么”想清楚。

## 8. 常见错误

### 错误 1：把“客服问题”都当成一类 客服问题只是入口，不是任务类型。 同样从客服入口进来的问题，可能分别需要模型、知识库、工具、人工审批或拒绝。

### 错误 2：让模型回答实时事实 订单、物流、库存、发票、售后状态都必须来自业务系统。模型不能编。

### 错误 3：让 Agent 直接执行高风险动作 退款、赔付、发券、改地址都涉及权益或资金。Agent 可以整理材料和建议，但不能绕过确认和审批。

### 错误 4：把简单规则复杂化 如果后端用一条确定性规则就能判断，不要为了“智能”强行让模型判断。

### 错误 5：一开始就设计多 Agent 本节只讨论单个任务如何分类。多 Agent 是后续架构问题，不是第一步。

## 9. 本节知识框架总结

```latex
Agent 场景地图 -> 先看任务，不先看技术 -> 直接回答：模型生成 -> 查知识库：RAG / 检索 -> 查工具：业务系统事实 -> 人工确认：资金、权益、承诺、权限 -> 不适合 Agent：违规、越权、敏感、无必要 -> 确定性系统负责规则和动作 -> Agent 负责理解、选择、整合和交互
```

## 10. 本节小结 你需要记住：
1. 做 Agent 前先做场景地图。
2. 任务分类比模型选择更早。
3. 低风险问题可以直接回答。
4. 文档政策类问题应该查知识库。
5. 实时业务事实必须查工具。
6. 高风险动作必须有人、权限和审计。
7. 不适合 Agent 的任务要拒绝或走严格流程。
8. Agent 和确定性系统是协作关系，不是替代关系。
