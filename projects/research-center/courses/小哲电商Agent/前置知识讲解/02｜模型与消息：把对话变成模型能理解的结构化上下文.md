# 模型与消息：把对话变成模型能理解的结构化上下文

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396362663-daee86c2-467a-4a79-92e3-506dbcf393ff.png" width="1672" title="null" crop="0,0,1,1" id="CmDnN" class="ne-image">

本节总览图：这张图从左到右画出 `messages 列表 -> Chat model -> AIMessage`。`messages 列表` 内按顺序包含 `SystemMessage`、`HumanMessage`、可选历史 `AIMessage`、可选 `ToolMessage`；`AIMessage` 输出框中拆出 `content`、`tool_calls`、`usage_metadata`、`response_metadata`。如果 `tool_calls` 不为空，箭头进入工具执行，再以 `ToolMessage` 回写到 messages 列表。

## 课程目标

学完这一节，你应该能说清：
- Chat model 在 LangChain 和 Agent 中扮演什么角色。
- 为什么简单任务可以传字符串，复杂 Agent 更适合传 messages。
- `SystemMessage`、`HumanMessage`、`AIMessage`、`ToolMessage` 分别表示什么。
- `AIMessage.tool_calls`、`usage_metadata`、`response_metadata` 有什么用。
- 为什么 `ToolMessage.tool_call_id` 必须和 `AIMessage.tool_calls` 对应。
- 消息历史为什么不能无限增长。

## 1. 为什么需要理解模型与消息 很多初学者第一次调用大模型时，会把所有内容写成一个字符串：

```python
prompt = '你是客服。用户问：订单20260001到哪了？请回答。'
```

这种方式可以跑，但不适合复杂 Agent。
电商客服对话里，系统至少要区分：
- 哪些是系统规则。
- 哪些是用户说的话。
- 哪些是模型上一轮回复。
- 哪些是工具返回的订单或物流结果。
- 哪些 metadata 用来调试、计费和追踪。
如果全部拼成一个字符串，模型可能还能看懂，但程序很难可靠管理。
更好的方式是把对话组织成 messages：

```latex
SystemMessage：你是电商客服，不能编造订单状态 HumanMessage：订单20260001到哪了？ AIMessage：我要调用 get_order_logistics ToolMessage：订单已发货，预计明天送达 AIMessage：我查到订单已发货……
```

这就是消息体系的价值：**把对话、工具调用和运行信息变成结构化上下文。**

## 2. 官方对模型的定位

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396362724-9e605cac-c4d7-47e1-ad6b-2623080004c6.png" width="1672" title="null" crop="0,0,1,1" id="ibDmn" class="ne-image">

模型在 Agent 中的位置图：这张图把 `Chat model` 放在 Agent 中央，左侧输入 `user message`、`system instruction` 和 `history`，右侧有两个出口：`直接生成 AIMessage.content` 和 `生成 AIMessage.tool_calls`。工具结果以 `ToolMessage` 从右侧回流到模型，模型再输出最终回答。图中要强调模型负责决策，工具负责事实。
LangChain 官方 `models.md` 说明，LLM 可以解释和生成文本，也支持越来越多扩展能力，例如：
- Tool calling。
- Structured output。
- Multimodal input / output。
- Reasoning。
在 Agent 中，模型是 reasoning engine，也就是推理和决策核心。
模型负责：
- 理解用户输入。
- 判断是否需要工具。
- 决定调用哪个工具。
- 解释工具返回结果。
- 判断什么时候给最终回答。
所以模型不是 Agent 的全部，但它是 Agent 的决策中心。

## 3. 独立模型调用和 Agent 里的模型调用 LangChain 官方文档说，模型可以有两种使用方式：

```latex
Standalone：直接调用模型，完成生成、分类、抽取等任务 With agents：模型作为 Agent 的推理核心，参与工具选择和执行循环
```

电商例子：

| 使用方式 | 适合任务 | 是否需要工具 |
| --- | --- | --- |
| Standalone | 改写客服话术、总结投诉、抽取咨询字段 | 不一定 |
| With agents | 查询订单、查售后政策、组合多个信息源回答 | 通常需要 | 不要所有场景都上 Agent。 如果只是把一段售后政策总结成三句话，直接调用模型就够了。

## 4. 初始化 Chat model LangChain 官方推荐的最简单方式是 `init_chat_model`。

```python
from langchain.chat_models import init_chat_model model = init_chat_model("openai:gpt-4.1-mini")
```

也可以使用具体模型类，例如 OpenAI 兼容接口：

```python
import os from langchain_openai import ChatOpenAI model = ChatOpenAI( model=os.environ["AGENT_OPENAI_MODEL"], api_key=os.environ["AGENT_OPENAI_API_KEY"], base_url=os.environ["AGENT_OPENAI_BASE_URL"], temperature=0, )
```

两种写法的区别：
- `init_chat_model` 更适合教学和跨 provider 示例。
- 具体模型类更适合项目里配置 `base_url`、`timeout`、`temperature` 等参数。
本节重点不是模型供应商，而是模型如何接收 messages 并返回 `AIMessage`。

## 5. 字符串输入什么时候够用 LangChain messages 官方文档说明，简单任务可以直接传字符串。

```python
response = model.invoke('帮我写一句礼貌的客服回复。')
```

适合这种写法的场景：
- 单次生成。
- 不需要对话历史。
- 不需要系统角色。
- 不需要工具调用。
- 不需要多模态内容。
例如：

```latex
把“没货了”改写成更礼貌的客服回复。
```

这是一个独立任务，不一定需要 messages。

## 6. `invoke`、`ainvoke`、`stream`、`astream` 是什么 在 LangChain 里，很多组件都可以被“运行”，比如 model、tool、retriever、agent、graph。它们经常会使用同一套调用方法。 最常见的是 `invoke`：

```python
response = model.invoke('帮我写一句礼貌的客服回复。')
```

它表示：把输入交给这个组件，同步运行一次，并等待最终结果返回。
常见调用方式可以先这样理解：

| 方法 | 含义 | 常见场景 |
| --- | --- | --- |
| `invoke` | 同步运行一次，等待最终结果 | 脚本、Notebook、基础 Demo |
| `ainvoke` | 异步运行一次，需要 `await` | FastAPI、异步后端服务 |
| `stream` | 同步流式运行，边执行边返回片段或事件 | 命令行、同步调试 |
| `astream` | 异步流式运行，边执行边返回片段或事件 | Web 后端流式响应 | 现在你只需要记住：

```latex
invoke 是“运行一次并拿最终结果”。 stream 是“运行时持续拿中间输出”。 前面加 a，表示 async，需要在异步代码里 await 或 async for。
```

后面看到 `agent.invoke(...)`、`tool.invoke(...)`、`graph.invoke(...)` 时，本质也是同一类调用方式，只是被运行的对象不同。

## 7. Messages 什么时候必须用 一旦进入多轮对话或 Agent，就应该使用 messages。 官方文档建议在这些情况下使用 message prompts：
- 管理多轮对话。
- 包含 system instructions。
- 处理多模态内容。
- 需要工具调用。
电商场景中，下面这种对话就应该使用 messages：

```latex
用户：我想买一款出差用的耳机。 AI：你更关注降噪还是续航？ 用户：续航。 AI：推荐长续航款。 用户：这款现在还有货吗？
```

最后一句“这款”必须依赖历史消息才能理解。

## 8. Message 的三个组成部分

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396362685-06ab8c34-6e16-4fa6-bf0f-6f8041f97b81.png" title="null" crop="0,0,1,1" id="zUnUz" class="ne-image">

Message 结构图：这张图画一个通用 `Message` 对象，内部拆成 `role`、`content`、`metadata` 三块。下方分四个子类型：`SystemMessage` 的 role 是 system，`HumanMessage` 的 role 是 user，`AIMessage` 的 role 是 assistant 且可能包含 tool_calls，`ToolMessage` 的 role 是 tool 且必须包含 tool_call_id。箭头表示这些消息按时间顺序组成 messages 列表。
LangChain 官方文档说明，message 通常包含：

| 组成部分 | 作用 |
| --- | --- |
| Role | 标识消息类型，例如 system、user、assistant、tool |
| Content | 实际内容，例如文本、图片、工具结果 |
| Metadata | 附加信息，例如 message id、token usage、response metadata | 不要把 message 只理解成“聊天文本”。 在 Agent 里，message 同时承载上下文、工具调用、工具结果和调试信息。

## 9. SystemMessage：定义角色和边界 `SystemMessage` 用来告诉模型应该如何表现。 电商客服例子：

```python
from langchain.messages import SystemMessage system_message = SystemMessage( "你是电商客服助手。" "订单、物流、库存、退款和赔付结论必须基于工具或政策。" "不能编造库存、发货时间、退款承诺或优惠。" )
```

它适合放：
- 角色身份。
- 回复语气。
- 业务边界。
- 安全规则。
- 不能做的事情。
不要把用户问题写进 SystemMessage。
用户问题应该放进 HumanMessage。

---

## 10. HumanMessage：表示用户输入 `HumanMessage` 表示用户当前输入。

```python
from langchain.messages import HumanMessage human_message = HumanMessage("订单20260001到哪了？")
```

它适合放：
- 用户问题。
- 用户补充信息。
- 用户上传内容的说明。
错误写法：

```python
SystemMessage('用户问：订单20260001到哪了？')
```

推荐写法：

```python
SystemMessage("你是电商客服助手，不能编造订单状态。") HumanMessage("订单20260001到哪了？")
```

角色清楚，后续维护才清楚。

---

## 11. AIMessage：模型输出，不只是文本 `AIMessage` 表示模型调用后的结果。 普通文本回复：

```python
from langchain.messages import AIMessage ai_message = AIMessage("请提供订单号，我帮你查询物流状态。")
```

但在 Agent 里，`AIMessage` 还可能包含 tool calls。

```python
AIMessage(content=[], tool_calls=[{'name': 'get_order_logistics', 'args': {'order_no': '20260001'}, 'id': 'call_001'}])
```

这表示模型不是在回答用户，而是在说：

```latex
我需要调用 get_order_logistics，参数是 order_no=20260001。
```

真正执行工具的是应用程序或 LangChain 运行时。

## 12. ToolMessage：把工具结果交回模型

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396364293-277dc395-2896-4621-98a8-bfa1a0752f14.png" title="null" crop="0,0,1,1" id="ZW0Fo" class="ne-image">

工具消息对应关系图：这张图左侧画一个 `AIMessage.tool_calls` 列表，里面有 `call_001: get_order_logistics` 和 `call_002: search_products` 两个工具调用；右侧画两个 `ToolMessage`，分别用 `tool_call_id=call_001` 和 `tool_call_id=call_002` 对应回左侧。箭头要一一连接，说明一次多个工具调用时，运行时依靠 id 匹配结果，不能只靠顺序或工具名。
当模型发出 tool call 后，程序执行工具，并把结果包装成 `ToolMessage`。

```python
from langchain.messages import ToolMessage tool_message = ToolMessage( content="订单已发货，物流单号 SF123456，预计明天送达。", tool_call_id="call_001", )
```

`tool_call_id` 很重要。
它必须对应前面 `AIMessage.tool_calls` 里的 `id`。
为什么？
因为模型可能一次请求多个工具：

```latex
查订单详情 查物流状态 查售后政策
```

系统必须知道每个工具结果对应哪个 tool call。

---

## 13. ToolMessage 的 content 和 artifact 官方文档还提到，`ToolMessage` 可以包含 `artifact`。 可以这样理解：
- `content`：会交给模型看的内容。
- `artifact`：程序后续要用，但不一定需要塞进模型上下文的原始数据。
例如检索商品资料时：

```python
from langchain.messages import ToolMessage tool_message = ToolMessage( content="这款耳机支持主动降噪，续航约 40 小时。", tool_call_id="call_002", name="search_products", artifact={ "product_id": "P1001", "source": "product_guide.md", "score": 0.87, }, )
```

模型只需要看 `content` 来回答用户。
程序可以用 `artifact` 在前端展示引用来源、商品 ID 或检索分数。

## 14. usage_metadata 和 response_metadata

<img src="https://cdn.nlark.com/yuque/0/2026/png/28539630/1783396362545-2dac6550-e86f-4573-a5fa-022d47f89ca0.png" title="null" crop="0,0,1,1" id="VfwBE" class="ne-image">

消息 Metadata 调试图：这张图把 `AIMessage` 放在左侧，拆出四个 metadata 分支：`usage_metadata -> 成本分析`，`response_metadata -> 模型返回状态和 finish reason`，`id -> trace 关联`，`tool_calls -> 工具调用调试`。右侧汇总到 `observability / eval / debugging`，说明 metadata 不参与普通回答内容，但会支撑排错和评估。
`AIMessage` 里可能带有 metadata。
常见字段：

| 字段 | 作用 |
| --- | --- |
| `usage_metadata` | token 使用量、输入输出 token 统计 |
| `response_metadata` | provider 返回的模型、finish reason、请求信息 |
| `id` | 消息 ID，方便追踪 |
| `tool_calls` | 模型请求调用的工具 | 电商客服系统为什么需要这些？

- 成本分析：一次回答用了多少 token。
- 质量排查：模型为什么提前结束。
- Trace：某次投诉回答对应哪个模型调用。
- 调试：模型到底有没有生成 tool call。
不要把 metadata 当成无关细节。企业 Agent 后续评估和观测都会依赖它。

## 15. Dictionary 格式 LangChain 也支持 OpenAI chat completions 风格的字典消息：

```python
messages = [ {"role": "system", "content": "你是电商客服助手。"}, {"role": "user", "content": "订单20260001到哪了？"}, ] response = model.invoke(messages)
```

这种写法简洁，适合 API 层或快速示例。
但教学中仍建议先理解标准 message 对象：

```python
SystemMessage(...) HumanMessage(...) AIMessage(...) ToolMessage(...)
```

因为对象形式更容易看清每类消息的职责。

## 16. 可运行 Demo：直接调用模型 如果已经配置好模型环境，可以运行：

```python
import os from langchain.messages import HumanMessage, SystemMessage from langchain_openai import ChatOpenAI model = ChatOpenAI( model=os.environ["AGENT_OPENAI_MODEL"], api_key=os.environ["AGENT_OPENAI_API_KEY"], base_url=os.environ["AGENT_OPENAI_BASE_URL"], temperature=0, ) messages = [ SystemMessage( "你是电商客服助手。" "如果涉及订单、物流、库存、退款和赔付，不能编造事实。" ), HumanMessage("这款蓝牙耳机适合出差使用吗？"), ] response = model.invoke(messages) print(type(response)) print(response.content) print(response.usage_metadata)
```

观察点：
- `response` 的类型是否是 `AIMessage`。
- `response.content` 是否是模型回复。
- `usage_metadata` 是否包含 token 用量。
- 没有工具时，模型是否避免编造实时库存或订单状态。

## 17. 可运行 Demo：手动构造一次工具消息链 下面不需要真实模型，重点是理解消息顺序。

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage messages = [ SystemMessage("你是电商客服助手。订单物流必须基于工具结果回答。"), HumanMessage("订单20260001到哪了？"), AIMessage( content=[], tool_calls=[ { "name": "get_order_logistics", "args": {"order_no": "20260001"}, "id": "call_001", } ], ), ToolMessage( content="订单已发货，物流单号 SF123456，预计明天送达。", tool_call_id="call_001", name="get_order_logistics", artifact={"carrier": "SF", "tracking_no": "SF123456"}, ), AIMessage("我查到订单20260001已发货，物流单号 SF123456，预计明天送达。"), ] for message in messages: print(type(message).__name__, "=>", message.content)
```

观察点：
- 工具调用请求出现在 `AIMessage.tool_calls`。
- 工具执行结果放在 `ToolMessage`。
- `ToolMessage.tool_call_id` 和 `AIMessage.tool_calls[0]["id"]` 对应。
- 最终回答才是给用户看的文本。

## 18. 常见错误

### 错误 1：所有内容都拼成字符串 不推荐：

```python
prompt = ' 你是客服。 用户：订单20260001到哪了？ 工具结果：已发货。 请回答。 '
```

推荐：

```python
messages = [SystemMessage('你是客服。'), HumanMessage('订单20260001到哪了？'), ToolMessage(content='已发货。', tool_call_id='call_001')]
```

结构化消息更利于工具调用、追踪、裁剪和调试。

### 错误 2：把工具结果当成用户输入 不推荐：

```python
HumanMessage('工具返回：订单已发货。')
```

推荐：

```python
ToolMessage(content='订单已发货。', tool_call_id='call_001')
```

工具结果不是用户说的话。

### 错误 3：忽略 `tool_call_id` 如果 `ToolMessage` 没有关联 tool call，模型和运行时就很难判断这个结果对应哪个工具请求。

### 错误 4：把所有历史消息无限传给模型 消息越多，成本越高，响应越慢，也越容易引入无关信息。 后续上下文工程和短期记忆会专门讲如何裁剪、摘要和选择上下文。

## 19. 本节知识框架总结

```latex
Models and Messages -> 模型是 Agent 的推理核心 -> 简单任务可以直接传字符串 -> 多轮对话和 Agent 应使用 messages -> Message = role + content + metadata -> SystemMessage 定义规则 -> HumanMessage 表示用户输入 -> AIMessage 表示模型输出，也可能包含 tool_calls -> ToolMessage 表示工具结果 -> tool_call_id 连接工具请求和工具结果 -> usage_metadata / response_metadata 用于成本、调试和观测
```

## 20. 本节小结 你需要记住：
1. Chat model 接收消息，返回 `AIMessage`。
2. 字符串 prompt 适合简单单轮任务。
3. Agent 更适合使用结构化 messages。
4. `SystemMessage` 不是用户问题，而是系统规则。
5. `ToolMessage` 不是用户输入，而是工具执行结果。
6. `AIMessage.tool_calls` 表示模型想调用工具，不是最终回答。
7. metadata 是后续 trace、评估、成本分析的重要基础。

3. 解释为什么 `ToolMessage.tool_call_id` 必须和前面的 tool call id 对应。
4. 想一个你熟悉的业务场景，列出 system、human、AI、tool 四类消息分别放什么。
