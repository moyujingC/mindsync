你好，我是徐昊，欢迎继续学习驾驭工程。

今天我们继续识别驾驭工程（Harness Engineering）中常见的坏味道（Bad Smell），并掌握对应的重构手法。

有一个很常见的场景。你让 Agent 把 100 条客户反馈按问题类型分类，并标注严重程度。Agent 很快回复“做好了”，表格格式漂亮，分类清晰。但是你发现它只处理了四五十条，有很多都被跳过了。而被跳过的恰好是那些表述含糊、需要仔细判断的反馈。这就是坏味道虚假胜利（False Victory）。

## Bad Smell：虚假胜利

虚假胜利背后的成因是惰性生成（Lazy Generation）。所谓惰性生成是指大模型过早终止任务，系统性回避需要更多推理的复杂部分，只处理容易的部分，然后对整个任务自信宣布完成。这是最近（2026 年 7 月）才发现的，一个普遍存在于大模型中的行为模式。

比如研究者给 Agent 一个网络搜索任务：“列出 2022-2024 年所有 AngryBirds 动画剧集”。大部分 Agent 在多轮检索后，只找到了有直接网页引用的 2 集，而需要跨越多个页面检索的 5 集都没能找到，就宣布任务成功了。

再比如研究者让 Agent 为 Apache Commons CLI 的 DefaultParser 类生成测试，并要求“最大化代码覆盖率”，最终 Agent 为 DefaultParser 生成并验证了 5 个测试，覆盖率约 42%，分支覆盖率仅 31% 就宣布任务结束了。

惰性生成有三个很明显的特征。

第一是容易的部分做，而且做得很快。Agent 处理那些信息明确、路径清晰的数据时效率很高；

第二是复杂的部分跳过，但不告诉你跳过了。对于需要更多推理的任务，Agent 可能会完全跳过。然而它并不会说“还有多少条没有做”；

第三，对整个任务宣布“做完了”，Agent 把自己完成的部分当作全部，自信地交付。你验收时才发现并没有完全完成。

惰性生成不是随机的偷懒，它有模型层面的原因。首先是位置偏差（Positional Bias），LLM 对上下文开头和结尾内容的注意力权重最高，而中间部分注意力权重越低，Agent 越倾向于忽略。然后是难度回避。Agent 面对没有把握或是需要更多计算资源的任务，它会系统性地选择跳过，然后宣布完成，以降低对于算力的要求。

你可能会问，既然我们设定了终止条件，大模型怎么没有发现虚假胜利呢？

首先是因为当被要求评估自己产出的工作时，Agent 倾向于自信地夸赞这份工作。有很多学术论文已经证明，神经网络系统性过度自信，模型报告的置信度显著高于实际准确率。Anthropic 在今年（2026）的研究中发现，当 Agent 被要求自己评估时，它会系统性地给出过度正面的评价。因此，哪怕已经设定终止条件，Agent 倾向于赞同自己已经做完的结论，而不是尝试推翻它。

然后，当生成和评估都由同一个 Agent 执行时，生成时的上下文、假设、盲点全部原样保留到评估阶段，Agent 也只能严格地确认自己之前的判断。很难发现之前的盲点。这就是因认知统一带来的评估失效。

## Solution：分离执行与验证

消除虚假胜利的手法叫分离执行与验证（Separate Execution from Verification）。核心原则是把“干活的人”和“检查的人”分开：生成者只负责产出，验证者独立判断是否完成。

根据前面的描述，我们知道产生虚假胜利的一个原因是认知统一。判断自己是否完成，本质上是一种自我评估。让同一个 Agent 批判自己的工作，几乎是不可能的。把验证者独立出来，让它用挑剔的眼光检查生成者的产出，反而容易做到。一旦验证者的反馈存在，生成者就有了具体可以迭代的对象。

实现这个分离最简单的方式是在状态系统中记录进度。生成者执行任务时，不能只在对话里说“我在做了”，而是要把进度落到状态文件里：处理了多少条、跳过了哪些、为什么跳过。这些记录必须是原始数据，因为原始数据是客观事实。然后验证者再根据记录到状态系统中的信息，判断进度。把数据和判断分开，正是把“干活的人”和“检查的人”分开的第一步。

验证者独立读取这些状态，根据预设规则判断是否满足完成条件。判断权从生成者手中转移到了验证者手中。Agent 不再有权说“我做完了”，它只能写“已处理 30 条，跳过 70 条”。验证者读完状态后决定是否通过这个转变的意义在于：Agent 的“我感觉做完了”不再算数，取而代之的是“状态文件里的进度是否满足预设条件”这个客观判定。虚假胜利赖以生存的自我评估，在这里被彻底绕开了。

如果验证部分仍然通过 Agent 来判断进度文件的内容是否达标，还可能会存在认知统一的问题（虽然概率已经低了很多）。一个简单的办法是把验证环节变成一段脚本或是代码。既然进度是以结构化数据记录在状态文件里的，脚本就可以直接读取并判断。比如检查“已处理数量是否等于总数量”“覆盖率数值是否不低于阈值”“跳过的条目是否都带有原因”。这类判断是确定性的，同样的输入永远产生同样的输出，Agent 的表述再漂亮也无法影响结果。

更重要的是，脚本判断可以在每次 Agent 宣布完成时自动触发，把判断逻辑写成脚本，就等于把验收标准变成了可重复执行的测试套件，Agent 的“我觉得达标了”在脚本面前没有立足之地。

## 什么时候该做这个重构

最直接的信号是，你抽查时持续发现工作量数据不符合。要求处理 100 条数据，最后只能提交 80 条数据。或者要求每天背 30 个单词，但是只提供 10 几个。这就是最明显的信号。还有一个可疑的行为是，Agent 完成任务的速度异常的快。任务越复杂，完成得越快，越值得警惕。

惰性生成的本质是跳过需要深挖的部分，一个需要综合多份资料的任务，Agent 不到一分钟就交稿了，那它大概率只处理了最容易的那部分。

## 如何重构

分三步。

第一步：把完成条件定义为可验证的指标。非 IT 场景写“100 条全部处理，每条有分类和严重程度标注”；IT 场景写“测试覆盖率不低于 90%，端到端全部通过”。每个条件都必须能用“是 / 否”来判定，避免“写得很好”这类主观描述。

第二步：要求 Agent 记录进度，而不是汇报结果。Agent 不能说“做完了”，它只能写“已处理 30 条，跳过 70 条”，以及跳过了哪些、为什么跳过。进度记录必须是原始数据，不是自我评价。写“分支覆盖率 31%”，不写“覆盖率达标了”。写“已处理 30 条，跳过 70 条”，不写“处理得很好”。每个进度条目都是‘是 / 否’，验证者不需要解读，只需要对照预设条件逐条打勾。

第三步：让验证者读取进度并判断。验证者可以是自动化脚本、检查清单、另一个人，甚至另一个被调校得挑剔的 Agent。关键是把完成判断从 Agent 手中拿走。在 AGENTS.md 中声明职责边界：“你负责执行任务并在状态系统中记录进度。完成判断由验证者根据进度数据决定。你不能自行宣布任务完成。”

## 最佳实践：一个例子

其实我们早就见过避免虚假胜利的例子。回到第 3 讲那个西班牙语背单词的 Harness。当时我们在 AGENTS.md 中定义了完成条件和进度查询方式。

#

三个工具的掌握率都超过 90%，就算全部完成。

#

| 问什么 | 从哪里看 |

|--------|---------|

| 词汇背了多少了？ | state/vocab/progress.json |

| 今天有哪些到期要复习的？ | 各任务的 progress.json |

完成条件写得很清楚，进度也有地方查。但这里仍然有问题：谁来判断掌握率达标了？在原来的设计里，是 Agent 自己读 progress.json，自己判断“超过 90% 了”，然后宣布完成。这就给虚假胜利留了空子。

因此，我们可以通过引入独立的检查器，彻底消除滋生虚假胜利的可能性。可以使用如下的提示词：

进度检查脚本提示词

请编写一个进度检查脚本 check\_progress.py。

脚本需要满足以下要求：

1\. 读取 state/vocab/progress.json、state/conjugation/progress.json、state/numbers/progress.json 三个进度文件

2\. 对每个工具检查两个指标：

掌握率（stats.mastery\_rate）是否达到 90%

到期未复习的卡片数（stats.due\_cards）是否为 0

3\. 输出结果：

三个工具全部达标时输出 PASS，并列出每个工具的掌握率

有未达标时输出 FAIL，明确指出哪个工具、哪个指标不达标、当前值是多少

4\. 脚本只依赖 Python 标准库，只用 progress.json 中的数值字段做判断，

不读取也不解析任何对话内容或 LLM 生成的主观描述

检查规则：

掌握率 = stats.mastery\_rate 字段

到期未复习 = stats.due\_cards 字段

三个工具全部达标才算通过，任何一项不达标都输出 FAIL

然后修改 AGENTS.md。

#

三个工具的掌握率都超过 90%，就算全部完成。

#

每次学习会话结束后：

1\. 更新各任务的 progress.json，只记录原始数据：新词学了几个、测试正确率、到期复习卡片数、已复习卡片数

2\. 运行 python check\_progress.py 检查进度

3\. 只有脚本输出 PASS，本次会话才算完成

4\. 脚本输出 FAIL 时，根据脚本指出的具体指标继续学习，直到脚本输出 PASS 为止

5\. 禁止自行宣布完成。完成与否以脚本输出为准

这样我们就通过分离执行与检查，彻底杜绝了虚假胜利的可能性。

## 小结

![](https://static001.geekbang.org/resource/image/8b/3f/8bf24b23924bf4a350542f4bfd18f73f.jpg)

虚假胜利的本质是惰性生成：Agent 系统性回避需要更多推理的复杂部分，只处理容易的部分，然后对整个任务自信宣布完成。它有三个特征：容易的做且做得快、复杂的跳过但不告诉你、对整个任务宣布完成。

惰性生成有模型层面的原因：位置偏差让 Agent 偏向处理上下文开头和结尾的数据，难度回避让 Agent 用跳过代替尝试。

终止条件失效的原因有两个：过度自信让 Agent 在自我评估时系统性给出正面评价；认知统一让生成时的盲点原样保留到评估阶段，它只会确认自己之前的判断，发现不了遗漏。

消除虚假胜利的核心手法是分离执行与验证：让生成者只负责产出，验证者独立判断是否完成。实现方式是记录进度而非汇报结果，进度必须是原始数据，验证者根据进度决定是否通过。

验证者可以是脚本：判断逻辑写成代码就是可重复执行的验收测试，确定性的检查让 Agent 的自我评价没有立足之地。
