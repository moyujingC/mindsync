今天我们来看一下驾驭工程（Harness Engineering）中常见的坏味道（Bad Smell），以及对应的重构手法。

## Bad Smell：上下文焦虑

使用 Agent 的时候，会出现这样一个现象。一个任务在执行的初始，它仔细核对需求，做完一步检查一步。但是当执行到后期的时候，上下文占用接近窗口上限，大模型便不再细致，做完一步就直接宣布完成，给出的结果也明显比前期粗糙。任务没有改变，大模型的能力也没有改变，只是上下文窗口快满了，它就开始急着收尾。

这就是坏味道上下文焦虑（Context Anxiety）。上下文焦虑指的是，Agent 在接近上下文限制时表现出的行为退化：匆忙完成、跳过验证步骤、选择简单方案而不是最优方案。

为什么会出现这样的行为？需要先说明一点：这是模型本身的缺陷，不是我们能通过指令修正的行为习惯。同一个任务，有的模型在上下文接近上限时焦虑行为非常强烈，换一个模型就大大减弱，甚至几乎消失——缺陷在模型内部，只是我们可以用外部手段去治理它的后果。

至于模型内部为什么会这样，目前还没有定论，但有两个比较可信的推测。

第一个推测是，当大模型接近窗口上限时，为了防止任务在执行中超出上下文的限制，它倾向于尽早结束任务。但是这种情况并非只在上下文将被填满时出现。因为大模型对上下文余量的感知不是对实际占用率的测量，而是一种来自训练经验的内在“感觉"”，而不是真实的使用情况。比如，一个标称一百万上下文的模型，偶尔会在会话进行到大约二十万，感觉上下文快满了，从而匆忙的结束任务。

第二个推测是，随着上下文越来越长，早期内容在模型注意力中的权重会越来越低，模型对“任务还没完成、还有哪些约束”的感知逐渐变弱，收尾的倾向就会压过继续干下去的倾向。它并不是忘记了这些内容，而是它们不再像新内容那样持续提醒它。当“该结束了”的感觉占上风，它就跳过验证、选简单方案，把能省的步骤都省掉，早点收工。

无论成因是哪一个，外在表现都一样。在资源压力下，模型从“把任务做完”的策略切换到“尽快结束”的策略。还要注意一点：这种快到上限才开始敷衍的行为，和我们之前讲过的惰性生成不同。惰性生成是生成者在没有外部验证时系统性回避复杂部分；上下文焦虑是资源压力触发的，同一个模型在上下文充足时表现完全正常。

## Solution：双层循环架构

由于上下文焦虑是模型的内在行为，我们无法通过外在的提示词修正。就算我们把上下文实际的状况告诉大模型，也无法缓解它的焦虑。应对上下文焦虑，解决方案其实非常简单——严格按照双层循环架构，就能系统性避免上下文焦虑。这是因为双层循环天然给上下文制造了边界。

外层循环通过 PDCA 循环管控任务的分解与进度追踪，把长任务切成一个个里程碑。内层循环负责具体的执行，它的职责范围被外层限制在当前子任务上。一个子任务做完，这个内层循环的使命就结束了，它不需要背着整个任务的历史继续跑下去。那么双层循环的分界天然就不会放任上下文一路积累到上限。

上下文焦虑的起点，恰恰是上下文失去边界。把整个任务塞进一个会话，一个内层循环从头跑到尾，没有周期、没有存档、没有可以重置的边界，上下文一路涨到接近上限，焦虑就开始了。所以与其说焦虑是模型单方面的缺陷，不如说它是让模型在没有边界的会话里跑了太久。双层循环正是那个把长任务切成有界片段的框架，严格执行它，焦虑就没有开始的土壤。

但是正如我们前面所说，哪怕上下文充分，上下文焦虑还是偶有发生。那么我们还有一个应对方法，就是在执行 Harness 的过程中，持续留存上下文的信息。当出现上下文焦虑时，不需要从头重复整个流程，而可以从最近一次进度开始重做。

那么，针对这个方案我们还需要做哪些额外的调整呢？外层循环要加 checkpoint，内层循环要守两条纪律。我们分别来看。

### 外层循环：加入 checkpoint

外层循环要增加一个环节，叫 checkpoint（检查点）。PDCA 每转一圈，也就是每个子任务或者环节结束的时候，把当前上下文做压缩保存，以备不时之需。checkpoint 作用是给任务打存档点，无论后面发生什么，当前状态都在文件里，随时可以继续。即使某次会话真的撑到上限被系统截断，损失也只是一个周期内的对话，而不是整个任务的上下文。

这样设计并不是说每次压缩都会直接替换当前正在使用的上下文。每个周期结束时生成的摘要，是写给 checkpoint 文件的存档，当前会话继续按原样运行，不会被中途改写。如果一切正常，这个会话可以一直用下去，不影响后续对话。

真正需要替换上下文的时候，是发现质量开始下降，模型进入焦虑状态时。这时候可以由人干预，结束当前会话或清空当前上下文，指定 Agent 按照某个 checkpoint 继续执行。上下文的恢复由外层循环按节奏发起，发起者可以是人，也可以是 Harness 的内建机制，比如多少轮次之后，主动清空并重置上下文。

具体动作是，周期结束时先验证这个阶段的目标是否真的完成。然后做压缩，把这一周期的对话分成两类，分别处理。一类是过程性内容，讨论的过程、试错的中间步骤、检索到的资料细节、已经确认不再相关的旧信息，这类压成摘要就够了。另一类是必须完整保留的内容，压缩时不能只留摘要，要原样写进 checkpoint 文件：

进度：任务做到哪一步了，哪些阶段已经完成

关键决策以及为什么这么决策：决策理由丢了，后面的会话就无法理解为什么要这么做，要么推翻既定的决策，要么把已经犯过的错再犯一遍

验证记录：什么通过了验证、什么失败了、失败的原因是什么，这决定下一步能不能信任已有的结果

未决事项：接下来要做什么，还有哪些悬而未决的问题

为什么这么分？因为压缩一定会丢信息，我们要保证丢掉的只是过程，而不是依据。过程细节丢了不影响继续，决策理由、验证记录、未决事项丢了，那么一旦出现上下文焦虑，就很难恢复。而不得不从头执行。

### 内层循环：上下文预算

严格的双层循环让内层循环每次面对的都是有界子任务，对上下文的要求大大降低，但这不意味着内层循环不会遇到上下文焦虑。一次子任务如果涉及大量信息，比如要读大文件、查多份资料，内层循环的上下文同样会逼近上限，模型同样会跳过验证、草草收尾。而且这种焦虑更难被发现：长对话里的焦虑有"前期仔细、后期敷衍"的明显对照，内层循环短而独立，一个子任务草草做完，看起来只是结果粗糙了一点，很难意识到是上下文出了问题。

所以内层循环要做的是严格执行上下文预算：筛选、分层、按需加载以及压缩。这是我们处理资料时就用过的思路，内层循环的执行过程同样适用。

落到具体动作上：读取大文件或长文档之前，先检索定位，只读与当前任务相关的段落；入口只放索引和摘要，需要细节时再按需深入，而不是把整份资料一次读进来；给单次读取设定预算，比如最多三千 token。这样内层循环的上下文里永远只有当前步骤用得上的内容，占用被压在低位，也就没有机会逼近上限。

但上下文预算不是总能严格执行的。有些子任务本身就要求同时对照大量资料，信息无法按需切分；有些资料没有可靠的索引，想定位也无从定位。

这种情况下，与其让内层循环硬扛，不如用 subagent 进一步切分上下文：把需要大量上下文的子任务再拆出去，交给一个拥有独立上下文的 subagent 执行，它自己读取所需的资料，完成后只把结果的摘要带回主循环，主循环依然保持低占用。subagent 的本质，是把一个装不下的上下文切分成几块，每一块都有自己的边界，各自都不会逼近上限。

## 什么时候该做这个重构

上下文焦虑的重构不需要等到发现问题再做，它应该是默认实践，从一开始就构造进双层循环里。

原因有两个。第一，上下文焦虑随时可能发生，它不挑任务规模。任何会话，只要上下文占用涨了上去（读了一份大文件、查了一堆资料、对话进行得够久）就可能触发，没有哪个任务能保证自己不会走到那一步。

第二，一旦发生，代价很高。焦虑的典型表现是跳过验证、草草收尾，产出的结果不可信，往往需要重新执行已经做过的步骤来确认，之前的 token 白花了，还要再花一遍。更麻烦的是它很难当场察觉，等发现质量不对的时候，不可信的结果已经积累了一批。

所以从两个角度看，这套做法都应该是默认的。从进度控制的角度，checkpoint 让任务随时有存档点，无论发生什么都可以从最近的存档续跑，进度不会归零；从防止返工的角度，内层纪律让每个子任务都在余量充足时完成，结果可信，不需要事后回头重做。而成本都很低：压缩一个周期、写一次存档、读文件前先检索定位，换来的却是任务不会因为焦虑而前功尽弃。

## 如何重构

重构分两层：外层把 checkpoint 构造进循环，内层参照上下文预算的手法管好执行中的上下文。我们这里主要讲一下外层循环的重构。内层循环上下文预算的重构手法我们在 14 讲已经讲过了，这里就不再赘述了。

外层循环的重构，是在 PDCA 的 Check 环节加入对上下文的 checkpoint。原本的 Check 环节只检查一件事：这个周期的目标有没有达成。现在要让它在检查目标的同时，也检查并处理上下文。重构后的 Check 环节就多做了一件事，压缩这一周期的进度、关键决策及理由、验证记录、未决事项必须原样保留，连同摘要一起写入 checkpoint 文件。

重构的方法也很简单，在 AGENTS.md 中 check 的环节增加一句话即可。当然，对于不同的任务，提示词的侧重点（写入 checkpoint 文件的内容）可能有所不同。

关键决策及理由、验证记录、未决事项必须原样保留，连同摘要一起写入 checkpoint 文件。

## 小结

![](https://static001.geekbang.org/infoq/0c/0cceb3ed6e43b2de0262c40edb432875.jpeg)

上下文焦虑坏味道的本质：Agent 在接近上下文限制时表现出的行为退化——匆忙完成、跳过验证步骤、选择简单方案。这是模型自身的缺陷，缺陷在模型内部，外部手段能做的只是治理它的后果。

成因有两个可信的推测：模型对余量的感知来自训练经验的内在“感觉”，不是对实际占用率的测量，它接近的是它以为的上限；随着上下文变长，早期内容在注意力中的权重下降，收尾的倾向压过继续干下去的倾向。表现是模型从“把任务做完”切换到“尽快结束”。

与惰性生成的区分：惰性生成没有外部验证时随时可能发生，上下文焦虑只在资源压力下触发，用同一个任务测试余量充足时是否正常即可区分。

重构手法是双层循环架构：严格执行双层循环就给上下文造出了边界。外层在 PDCA 的 Check 环节加入对上下文的 checkpoint，定期压缩并落盘，进度、关键决策及理由、验证记录、未决事项原样保留，需要时在会话之外重置；内层严格执行上下文预算，筛选、分层、按需加载、压缩，装不下的上下文用 subagent 进一步切分。

这套做法应该是默认实践：焦虑随时可能发生，一旦出现往往要重做已完成的步骤、浪费大量 token；从进度控制（随时可从存档续跑）和防止返工（子任务结果可信）两个角度看，成本都远低于收益。
