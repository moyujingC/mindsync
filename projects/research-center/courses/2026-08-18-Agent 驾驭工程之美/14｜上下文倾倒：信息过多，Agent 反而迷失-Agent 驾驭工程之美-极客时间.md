你好，我是徐昊，欢迎继续学习驾驭工程。

今天我们来看一下驾驭工程（Harness Engineering）中常见的坏味道（Bad Smell），以及对应的重构手法。

## Bad Smell：上下文倾倒

当我们想让 Agent 输出更好的结果时，会倾向于把能找到的资料都给它。我们总是觉得信息越多，Agent 了解得越充分，结果就越好。但实际效果往往相反，信息越多，Agent 往往越抓不住重点。

比如让 Agent 写一份行业调研报告，为了让它充分了解所需要调研的场景，把几十篇参考资料、过往所有聊天记录、公司制度文件全部塞给它。结果它抓不住重点，报告里塞满了不相干的内容，你所需要的关键分析反而没有。

编码场景里也一样。我们总是期待把整个代码库、所有文档、全部历史对话都喂给 Agent，它就能够精准地帮助我们完成想要的功能。但通常往往是 Agent 耗费了大量时间检索代码库，交叉比对各种文档。要求修改 UI 上的一个按钮，把部署文档也读了一遍，最后还是改得七零八落。

这就是坏味道上下文倾倒（Context Dumping）。上下文倾倒指的是，把能给的资料不加筛选全部塞给 Agent，大模型在海量细节中迷失，最终丧失注意力，输出的结果平平。

至于产生这个坏味道的成因，也是我们在其他坏味道里提到的两个关键点，第一个是上下文窗口有限，第二个是注意力稀释。

Agent 的上下文窗口不是无限大的，它是有限的预算。不加筛选地塞入所有信息，窗口很快被无关内容填满，真正重要的信息被挤到边缘，随着对话进行被截断或压缩，模型根本发现不了关键信息。即使窗口足够大，信息越多，模型对不同信息块的注意力就越分散，对于指令的响应质量也会下降。无法有效集中大模型的注意力，就无法产生高质量的结果。

为什么我们会倾向于上下文倾倒？那还是因为上一轮使用 Agent 的最佳实践叫上下文工程（Context Engineering），工程不知道怎么弄，上下文尽可能多给，估计已经是下意识的反应了吧。

## Solution：上下文预算

消除上下文倾倒的手法叫上下文预算（Context Budgeting）。核心思想是把上下文看作珍贵的资源，窗口是有限的，注意力是有限的，每一段信息都要花钱。那么我们就可以按照投资回报率（ROI）的角度，去思考如何规划上下文以及注意力的使用。而不是把大模型的上下文当作档案柜，什么信息都往里面填入。

构建有效性的上下文预算有很多种办法，我们最常看到的就有四种：筛选、分层、按需加载和压缩。下面让我们分别来看看。

![](https://static001.geekbang.org/infoq/c7/c74d872ad8f51d8d45871fa4ff997a51.png)

### 筛选

上下文预算最简单也最困难的做法就是筛选。也就是不把全部信息都放入上下文。给 Agent 之前，先想一想这段信息不给，Agent 会做错决策吗？如果不会，就不给。

相关性是筛选的唯一标准。写调研报告，只有和主题直接相关的资料才进上下文；改 UI 按钮的话，只有涉及的那个模块的代码才给它。

这听起来很容易，但做起来很难。这对于小型任务来说，或许还是有效的策略。但如果在任务本身就需要大量的上下文信息，比如在多个代码仓中协调修改完成某个功能，信息就很难取舍。

然后这个方法对人有较高的认知负载，能够在诸多信息中筛选出需要的信息，本身就是一个挑战。

### 分层

筛选回答的是“给不给”，分层回答的是“怎么组织”。把上下文按照不同的生命周期分层处理。比如，按照项目层、任务层和执行层分解就是一个常用的策略。在项目层中，放置项目背景、架构约束等。在任务层中，放置不同的任务的流程控制，和具体上下文。然后在执行层放可用工具、约束条件、前馈反馈等。

这样就可以通过不同的子 Agent（subagent）或者技能（skills）获取对应的上下文信息，保证获取的上下文都与当前任务紧密相关。

分层比起筛选要容易很多，也自然很多。特别是我们使用双层循环模型构造 Harness 的时候，外层循环和内层循环本身就有不同的关注点，所需要的上下文也不相同了。不过遇到大规模的任务，比如根据某个主题写研究论文之类需要很多参考资料的任务，分层可能仍然无法解决上下文倾倒的问题。

### 按需加载

筛选决定“给不给”，分层决定“放哪层”，按需加载决定“什么时候给”。不是一次性把所有层的上下文都加载，而是走一步加载一步。入口只放核心规则和路径指引，具体内容通过引用按需读取。这也就是课程前面讲过的渐进式信息披露（Progressive Disclosure）。

按需加载的核心做法，不是把会用到的资料提前塞给 Agent，而是为这些资料建立索引。比如写调研报告，入口给的不是几十篇资料的全文，而是一份资料清单：市场概况有哪些参考，竞争对手又看哪些等等。

索引和内容分离的好处有两个。首先是减少上下文的使用，上下文里只占一份索引的空间，而不是全部资料的篇幅。其次是 Agent 每次读到的都是当前任务真正需要的部分，也有利于注意力的集中。

但建立索引也有自己的难点。索引必须足够准确，资料清单写错了主题，Agent 就会读错资料。索引还需要维护，资料更新了，索引的描述要跟着更新，否则 Agent 按旧索引取到的就是过时内容。

### 压缩

筛选决定“给不给”，按需加载决定“什么时候给”，压缩决定“以什么形式给”。信息不是只能原样给。长资料可以变成摘要，完整文档可以只给相关片段，日志可以只给结论。Agent 不需要原文的时候，给它摘要就够了；需要原文的时候，再通过引用去读。

压缩和按需加载是天然搭配。索引里放的可以不是全文，而是每份资料的一句话摘要。Agent 先读摘要判断要不要深挖，需要细节了再去读原文。这样入口的索引更小，Agent 的第一次判断也更快：大部分资料读个摘要就知道和自己无关。

但压缩也有自己的代价。第一，压缩会丢信息。摘要是对原文的取舍，丢掉的细节可能正是 Agent 决策需要的。所以压缩要区分内容：可以压缩的是参考资料、日志、历史对话，不能压缩的是约束、验收标准这类关键信息。第二，压缩本身可能出错。摘要由模型生成，模型概括错了，Agent 就会基于错误的摘要做决策，这比不给信息更危险。所以越是重要的资料，越要保留原文。

## 什么时候该做这个重构

最直接的信号是 Agent 处理任务的时间很长，而查看执行过程，会发现有大量的信息查找动作。它花了大把时间检索代码库、交叉比对各种文档、反复确认某个资料里到底写了什么，真正动手做事的比例反而很低。就像一个人走进一间堆满杂物的房间，找东西比干活花的时间还长。

特别是 Agent 在处理无关内容。写报告时去研究不相干的资料，改按钮时把部署文档也读了一遍。它分不清哪些和当前任务有关，只好把能查的都查一遍。

这时候我们就需要怀疑，如果我们还提供了大量的参考文档或是代码，就要考虑是否遇到了上下文倾倒。

## 如何重构

前面提到的四种方法可以组合使用。筛选决定什么进，分层决定放哪层，按需加载决定什么时候进，压缩决定以什么形式进。核心只有一个：上下文是有限的，要把每一份预算花在真正相关的信息上。

这是一个需要点想象力的重构手段。我个人的建议是从按需加载开始。

通常这样的方法，能给一个大致的方向，当然具体有效的索引还要看具体任务才能确定。然后接下来我会尝试使用压缩，比如与其给参考文档，比如让大模型先把所有的文档总结一下。与其给整个代码库，不如提炼 API 契约（API Contract）和 UI 组件树（UI Component tree），这样总是能得到更好的结果。至少可以提高检索的速度。

在压缩之后，可以考虑分层。信息压缩之后，再分层就容易很多了。

最后的最后，可以进行筛选，这个比较费人，大家量力而行。

## 小结

![](https://static001.geekbang.org/infoq/b7/b7ce45e08797e8ab2b5cef1dba8994e2.png)

上下文倾倒坏味道的本质：把能给的资料不加筛选全部塞给 Agent，信息越多表现越差，大模型在海量细节中迷失，最终丧失注意力。

两个成因：上下文窗口有限（关键信息被挤出窗口）和注意力稀释（关键指令被噪声淹没），根源是上下文工程的惯性，下意识地认为信息多给总没错。

诊断信号：Agent 处理任务的时间很长，执行过程里有大量的信息查找动作；它分不清哪些资料和当前任务有关，只好把能查的都查一遍。

重构手法是上下文预算：把上下文看作珍贵的资源，窗口和注意力都是有限的，每一段信息都要花钱，按 ROI 的角度规划上下文的使用。

四种方法各有分工：筛选决定“给不给”，分层决定“怎么组织”，按需加载决定“什么时候给”（为资料建立索引），压缩决定“以什么形式给”。

重构顺序建议：从按需加载开始建立索引，再用压缩提炼摘要，之后分层，最后筛选，量力而行。当信息量与表现成反比时，就要考虑上下文倾倒。
