你好，我是徐昊，欢迎继续学习驾驭工程。

上一讲我们介绍了驾驭工程的双层循环模型：外层通过 PDCA 管控整个任务的流程分解与追踪，内层操控循环（Steering Loop）负责为具体的子任务提供前馈控制（Guides）和反馈控制（Sensors）。操控循环通过前馈和反馈，驾驭 Agent 的自我纠正（Self-correction）循环，提高 Agent 的输出质量。

双层循环模型是一个概念模型（Conceptual Model），它的主要作用是帮助我们设计 Harness，指导我们如何拆解要做的工作，哪些映射到 PDCA 的流程上去，哪些映射为子任务。也就是能为我们提供如何实现 Harness 的思路。 但是要真正实现 Harness，仅有思路是不够的，我们还要了解 Agent 的内部结构，以及 Harness 由哪些子系统构成。

## Agent 的内置 Harness

对于任何完整的 Agent 系统，不管是 OpenClaw、Claude Code 还是 Hermes，其内部核心都是自我纠正循环（Self-Correction Loop）。而自我纠正循环实际上是推理行动循环（ReAct / Reasoning Action Loop）的一个特殊形式。

推理行动循环是 Agent 执行任务的主循环。它遵循“推理 - 行动 - 观察”的三步模式：Agent 先根据当前上下文推理下一步该做什么，然后执行一个具体的动作，比如调用工具、生成文本或查询知识库，接着观察动作的结果，再根据新的观察继续推理，直到任务完成或达到终止条件。没有推理行动循环，Agent 就是一个静态的文本生成器。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/8a/33/8acbccbbdcd1582f80fc159e2c136a33.png)

自我纠正循环则是将推理行动循环中的观察改为自我纠正。每次迭代后运行，检查当前输出是否满足预定的质量标准：格式对不对、约束是否满足、数据是否完整。如果发现问题，就会触发修正动作，重新生成、补充信息或是询问用户，然后再回到“推理 - 行动”继续执行。因而自我纠正循环的模式为“推理 - 行动 - 观察 - 自我纠正”。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/96/02/96896fd969c1a4703c43f6e03baf8c02.png)

自我纠正循环实际上也是个戴明环（PDCA），“推理 - 行动”是 PD，而“观察 - 自我纠正”是 CA。所以我们也把自我纠正循环称作 Agent 的内置 Harness 机制（Built-in Harness），是我们要驾驭的主要对象。

当然，不同的 Agent 系统还可能包含更多的循环，比如，Hermes 就包含自我改进循环（Self-Improving Loop）。更多的循环意味着，内置 Harness 机制不同，为驾驭工程提供了更多的可驾驭对象。我们目前主要关注自我纠正循环就可以了。

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/8e/95/8e815ec46f7245d4caada660aeaeb395.png)

## 推断型控制与计算型控制

除了驾驭内置的 Harness 之外，我们驾驭的对象还有大模型本身。而今天，大模型的能力只有两个：推理能力和工具调用能力（Function calling）。

在第 1 讲编写周报这样的任务中，反馈控制“周报是否有至少 2 个亮点？亮点是否有数据？阻塞项是否有责任人？”是依赖于大模型本身来完成。这样的控制叫做推断型（Inferential）控制。

推断型控制依赖大模型的推理能力，结果是非确定性的。比如“评估这封邮件的语气是否合适”“判断这个方案的风险是否充分”“分析这段文字的逻辑是否自洽”这些判断需要理解语义和上下文，适合交给大模型来处理。

但是有一些任务需要更强的确定性。比如帮助客户预定机票，就需要通过指定渠道获取机票价格。这样的操作通常依靠代码（API 调用）而不是大模型的理解能力来实现，因此叫做计算型（Computational） 控制。

计算型控制通过确定的规则或代码来执行，计算型控制通过大模型的工具调用能力实现。不需要大模型参与判断。比如“验证链接是否返回 200”“确保字数不少于 300”。这些规则是确定的，每次执行结果都一样，不会因为模型状态而波动。

把计算型的检查交给工具，把推断型的判断交给大模型，对大模型的驾驭才会更有效率。用大模型去执行“确保字数不少于 300” 这种任务，既浪费成本又不可靠。大模型可能因为上下文偏移而漏数。反过来，把需要语义理解的任务硬编码成规则，既写不出来也维护不了。

对于内置 Harness 机制的驾驭，可以通过文本指令达成，但是计算型控制则不行。文本指令擅长描述“做什么”和“怎么做”，但它无法执行确定的计算，这些工作需要能实际执行操作的系统。这就是为什么一个完整的 Harness 通常由四个子系统构成，而不是只是一份 AGENTS.md。

## Harness 的四个子系统

构成 Harness 的四个子系统是：指令（Instructions）、工具与技能（Tools & Skills）、环境（Environment）和状态（State）。Harness 的四个子系统为 Agent 提供了运行所需的一切：

指令（Instructions）：告诉 Agent 做什么 。

工具与技能（Tools & Skills）：给 Agent 做事的途径。

环境（Environment）：Agent 运行的真实条件。

状态（State）：让 Agent 记住过去。

下面让我们来仔细看一看。

### 指令（Instructions）

指令子系统是 Harness 的核心载体，它包含前馈控制和反馈控制，并直接作用于自我纠正循环。

前馈控制：指令告诉 Agent 当前任务的目标、可用工具、约束条件、输出格式。Agent 在推理每一步时都依赖这份指令来判断下一步该做什么。

反馈控制：指令中嵌入的检查规则和验证标准，决定了 Agent 在完成一次输出后如何自我评估。比如，指令里写了“每个亮点必须附带数据”，Agent 的自我纠正环节就会在提交前扫描内容、识别缺失、自动补充。

你可能会问，指令子系统不就是一份更详细的提示词吗？的确，从某种意义来说，的确如此。但是在 Agent 内部指令子系统的优先级高于单次提示词（Prompt）。用户在对话中输入的内容位优先级低于指令子系统。当两者冲突时，指令子系统会覆盖用户输入。

这意味着你写在 AGENTS.md 里的规则是“不可违反的硬约束”，用户可以在对话中追加需求，但不能覆盖 AGENTS.md 中定义的核心规则。这种优先级设计保证了指令子系统作为前馈控制的权威性：Agent 在任何情况下都会优先遵守结构化指令，而不是被偶然的提示词带偏。

这也是指令子系统又被称作 Agent 宪法（Constitution）的原因。

### 工具与技能（Tools & Skills）

正如我们前面说的，工具调用是大模型的核心能力之一。大模型通过输出特定的结构化数据，告诉外部系统执行某个操作。这使得大模型不再局限于训练数据，而是能与其他系统交互，比如获取机票价格、或是操作你的电脑。

技能则是一组指令、工具和验证规则的封装，可以像插件一样被 Agent 加载和使用。技能和工具最大的不同在于，技能中往往包含独立的工作流程和 Harness。如果工具是 Agent 的手和脚，那技能就是 Agent 的 App。工具让 Agent 能做一件事，技能让 Agent 知道在什么场景下该采用什么流程来处理。工具与技能子系统是在 Harness 中引入计算型控制的核心机制。

### 环境（Environment）

环境子系统主要指保证 Agent 能够正常运行所需的软件与配置。比如，我们让 Agent 帮助我们修图，那么一些基础的图像操作库就是必不可少的。特别是当我们使用别人提供的工具与技能时，也需要考虑这些工具与技能所需的环境。

除此之外，环境子系统对于反馈控制格外重要。因为反馈控制的结果只有在一致的环境中才有意义。自动化 测试要在正确的版本下跑，Lint 检查要使用一致的验证规则。如果环境每次都不一样，反馈信号就不可信。反馈信号不可信，那么 Agent 输出的结果也就不会稳定。

所以，环境子系统的核心就是可复现性（Repeatability），无论是对于 Agent 功能的复现还是对于反馈控制的可复现，都是重要的考量。

### 状态（State）

状态子系统是前馈控制和反馈控制之间的桥梁，它让 Agent 记住之前发生了什么，现在进行到哪一步，下一步该做什么。

没有状态子系统，Agent 每次启动都是一张白纸。上一讲拆解周报例子时，AGENTS.md 里要求 Agent “阅读最近 8 周的周报”，这就是在利用状态子系统来保持连续性。同时，状态让转向控制有了依据：没有状态，Agent 无法知道哪里出了问题，也就无法在做出有针对性的调整。

状态的形式可以很简单。比如，在 reports/ 目录下保存周报，就是一个简单有效的状态系统。也可以很复杂，比如使用各种数据库。状态系统的设计要根据具体任务来取舍。

## 四个子系统与内置 Harness

在了解了 Agent 的内置 Harness 机制，以及构成 Harness 的四个子系统之后，我们对于 Harness 是如何工作的，就有了一个全景式的了解。如下图所示：

![](https://static001.geekbang.org/editor-compose/resourceimage/compose/b0/15/b05deed819217c7c9f7a6bde1aaaf015.png)

简而言之，指令子系统负责驾驭 Agent 的内置 Harness，状态子系统为 Agent 提供连贯的记忆，工具与技能子系统和环境子系统则支撑计算型控制的执行。四个子系统把操控循环从抽象概念变成了可操作的工程组件，也就是驾驭工程的核心要点。

当你理解了这层关系，再回头看上一讲的周报例子，就能清楚地看到每一个指令和检查分别属于哪个子系统。AGENTS.md 里的结构定义是指令子系统，自动检查是反馈子系统，reports 目录中的历史周报是状态子系统。由于没有用到计算型控制，我们并没有关注工具子系统和环境子系统。当然，严格意义来说，Agent 读取历史周报是通过工具调用实现的，也就是使用了 Agent 内置的工具子系统。

## 小结

上一讲的双层循环模型是驾驭工程的概念模型，为了我们真正实现 Harness，还需要熟悉 Agent 的内置 Harness 机制。

Harness 的四个子系统为 Agent 提供了运行所需的一切。

![](https://static001.geekbang.org/resource/image/88/d7/88e9d947c184fd7e68b7f8e8d58697d7.jpg)

指令（前馈与反馈控制）、工具与技能（计算型控制）、环境（保证可复现性）、状态（保持连续性）。通过四个子系统，我们把驾驭工程从概念变成了可操作的方法。
