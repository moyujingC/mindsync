今天我们来看一下驾驭工程（Harness Engineering）中常见的坏味道（Bad Smell），以及对应的重构手法。

我们知道在构建 Harness 的时候，一个核心设计原则是将仓库本身作为系统的唯一事实来源（Single Source of Truth），即仓库即规范（Repository as Spec）。但是汇聚到仓库中的知识，可能存在不同来源，如何保持他们与真实情况同步就成了一个问题，这个问题我们称为信息散落。

## Bad Smell：信息散落

信息散落指的是知识被纳入仓库后，因为更新不及时，导致仓库里的信息不再是事实本身，而是事实的旧版本。这比没有文档更糟糕。

没有文档的时候，Agent 至少知道自己在猜，它的输出带有不确定性，你会检查。 有文档但过时的时候，Agent 自信地执行错误的信息，而且这份自信来自你建立的仓库。你验收时看到 Agent 精准地实现了错误的目标，执行到位，方向全错。你花时间建立的知识体系，因为没有更新，反而成了误导 Agent 的源头。

这种问题的根源在于：仓库里的信息是静态的，而现实是动态的。单词表在更新、外部依赖在升级、业务规则在变化。仓库和现实之间的差距每天都在扩大。你第一天写进仓库的信息是准确的，一个月后可能就过时了一半。你需要不断维护仓库，确保信息与时俱进，否则仓库就会从帮手变成误导的来源。你不主动缩小这个差距，Agent 就会基于过时的信息做出决策。

比如，在背单词的场景中，可能你花时间整理了一份 500 个单词的词表，几周后发现太难了，从词表中移除了 20 个太难的单词，增加了 30 个更基础的同义词。但仓库里的词表还是最初的 500 个 Agent 继续安排那些已移除的单词的复习，浪费了你的时间。

在软件开发的场景中更为常见。团队开了个会，讨论修改了 API 接口格式，修改了团队 Wiki。但仓库里的 API 规范没有更新。由 Agent 生成的代码仍然遵循仓库中陈旧的知识，继续生产已经不符合要求的代码。

## Solution：管理知识依赖

消除这个坏味道的手法叫管理知识依赖。当信息发生变化时，第一时间更新仓库中的对应文档，而不是让修正只停留在讨论中。

你可能觉得这听起来很简单，不就是改了东西要更新文档吗？但在实际工作中，这件事很少被认真执行。这主要是因为在 Agent 系统之外，我们都有日常的工作流程。比如，电子邮件、会议、线下讨论等等。经过讨论形成的决议，也都有其各自的存储方式。这就使得将这些知识固化回仓库中，变成了一个额外的行为。而这种额外的行为，就容易被忽略，或是遗忘。

此时，在现实世界中，需求或者实现方式的契约已经发生改变。但对 Agent 来说，文档就是它的全部信息来源。文档不更新，Agent 就不知道变化。

因此，我们需要设计一套机制，让 Agent 能够自动更新信息源，或者是提醒我们从不同的来源同步信息。

如果有软件开发背景的读者，可以类比软件开发中的依赖管理。任何一个项目都会依赖其他的软件包，无论是 npm、jar 还是什么格式，我们通常会使用 Dependabot 或是 Renovate 这样的工具把相关依赖升级到最新的版本。

而在仓库中的信息，实际上都是一条知识依赖。它依赖某个外部信息源（团队 Wiki、会议决议、邮件、第三方文档等等）。当那个外部信息源变化时，就像是依赖库发布了新版本，那么我们自然要及时地更新它。

## 什么时候该做这个重构

在我看来，这应该是默认最佳实践。任何时候只要 Harness 依赖外部信息源，都应该建立主动更新的机制。只要仓库的信息来自外部，就有过时的风险。不要等到 Agent 基于过时信息做出错误决策后才去修复，而应该从一开始就把知识依赖的管理机制作为 Harness 的标配。

## 如何重构

如果项目中需要参考的上下文，都有其知识来源，那么可以建立一个 SOURCE.md 的文体，表明其来源。比如，如下的项目结构：

project/

├── AGENTS.md

├── docs/

│ ├── api-spec.md

│ ├── database-guide.md

│ ├── deploy-checklist.md

│ └── architecture.md

└── skills/

那么我们可以构造一个 SOURCE.md 文件：

本仓库中以下文档的内容来自外部信息源：

| 仓库文件 | 外部来源 | 更新时机 |

|--------------------------|-----------------------------------------------------|--------------|

| docs/api-spec.md | Confluence Wiki (https://wiki.team.com/api-spec) | 每周一 |

| docs/database-guide.md | DBA 团队 Notion (https://notion.team.com/dba-guide) | 按需 |

| docs/deploy-checklist.md | CI 流水线说明 (https://ci.team.com/deploy-docs) | 每次 CI 更新 |

| docs/architecture.md | 架构决策记录 ADR (https://github.com/team/adr) | 每次 PR 合并 |

然后我们可以要求 Agent 帮我们构造一个技能（Skill）帮助我们从对应的来源，获取更新，比如：

请根据以下 SOURCE.md 中的信息源映射，创建一个名为 sync-sources 的 Skill。

Skill 需要满足以下要求：

1\. 读取 SOURCE.md 获取所有信息源映射

2\. 对每个外部来源，通过 URL 或 API 拉取最新内容

3\. 对比拉取的内容和当前 docs/ 下的文件，如有差异则自动更新

4\. 更新后提交一个 PR，注明哪些文件已更新以及更新的内容摘要

5\. 对于标注为"按需"的来源，每次运行时提示用户是否需要更新

6\. 支持通过命令行手动触发，也支持配置为定时任务（cron）

请生成 SKILL.md 文件，包含完整的技能描述、触发条件、执行步骤和工具声明。

但如果是类似于背单词这样的 Harness，单词表并没有一个明确的来源，那么我们可以 AGENTS.md 中，增加提醒环节：

单词列表更新检查

每次会话开始时，先执行以下步骤：

1\. 询问用户：「单词列表是否有更新？如果有，请提供要添加或移除的单词。」

2\. 如果用户提供了更新内容，执行以下操作：

\- 更新 vocab/word-list.md（或对应的词表文件）

\- 更新 vocab drill的计划

\- 告知用户词表已更新

3\. 如果用户说没有更新，继续正常流程

实际效果就是每次你跟 Agent 说“开始背单词”时，Agent 会先回你一句：

「好的，开始今天的复习。顺便问一下，单词列表有更新吗？比如最近有没有发现哪些词太难需要移除，或者有哪些新词想加进来？」

此时，如果你说“帮我把 xxxx 移除，加上 yyyy”，Agent 会更新词表文件，然后按新词表开始复习。下次新会话，它仍然会先问一遍。这样我们就能始终保证单词表是最新的内容。

## 最佳实践

除了手动建立 SOURCE.md 和提醒机制外，你也可以使用 OpenWiki 这样的工具来做知识管理。OpenWiki 是一个专门为 Agent 建立本地知识库的 CLI 工具，由 LangChain 开发。它已经内置了连接器可以从 Gmail、Slack、Notion、X/Twitter、Web Search、Git 仓库等来源更新信息。Agent 每次启动时读取这个本地知识库，就能获取到散落在各处的全部上下文。

你可以把 OpenWiki 理解为一个自动化的知识依赖管理器。它替你完成 SOURCE.md 的建立和定时 Skill 的编写，只需要配置一次连接器。无论你是技术用户还是非技术用户，配置好之后就不再需要手动维护。对于已经存在大量外部信息源的项目，比如同时依赖 Confluence、Notion、Slack 等多个平台的项目，引入 OpenWiki 比从零搭建 SOURCE.md 加定时 Skill 的效率高得多。

如果你的项目信息源较少，只有一两个外部来源，用 SOURCE.md 加一个简单的定时 Skill 也足够。选择哪种方式取决于你的信息源数量和变化频率：少量稳定的信息源用手动方案，多而频繁变化的信息源用 OpenWiki。

两个方案并不互斥，你可以先用 SOURCE.md 快速建立依赖清单，等后期信息源增多再切换到 OpenWiki。

关键是无论选择哪种方式，都要让知识依赖管理成为 Harness 的标配，而不是靠记忆力去维护。知识依赖管理不是可选项，它应该是 Harness 的一部分。

## 小结

![](https://static001.geekbang.org/resource/image/03/6a/03dd43171dbb8dbbb36a26fdfb39a26a.jpg)

信息散落的本质是知识进入仓库后没有及时更新，导致仓库里的信息从事实来源变成了事实的旧版本。过时的文档比没有文档更危险，因为 Agent 信任它，会自信地执行错误的方案。

知识依赖管理就是给每个信息源建立映射和更新机制：有 URL 或 API 的用 SOURCE.md 加定时 Skill 自动拉取，没有固定来源的在 AGENTS.md 中加入提醒让 Agent 主动询问用户。

工具生态已经成熟：OpenWiki 内置 Gmail、Slack、Notion、X/Twitter 等多平台连接器，自动吸入信息并维护 AGENTS.md 入口。代码模式适合软件项目，个人模式适合背单词等非 IT 场景 。

无论选择手动方案还是 OpenWiki，核心原则不变：设计主动机制代替人的记忆，依赖外部信息就有更新义务。知识依赖管理是 Harness 的标配组件。

## 思考题

找出仓库里一份可能已经过时的文档，为它建一条知识依赖（外部来源 + 更新时机），然后选一个方案落地：SOURCE.md 加定时 Skill，还是在 AGENTS.md 里加提醒。
