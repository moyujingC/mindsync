今天我们来看一下驾驭工程（Harness Engineering）中常见的坏味道（Bad Smell），以及对应的重构手法。

## Bad Smell：模式复制漂移

在通过 Agent 辅助软件开发的时候，我们经常会遇到这样一个问题：希望在不修改存量代码的前提下，使用新的架构模式实现新的功能。比如，存量代码的写法是在 controller 里直接写业务逻辑，通过 SQL Mapper 直接调数据库。而现在我们希望提取服务，对业务逻辑进行封装。再比如，我们希望使用内存数据库，然后真实启动 Spring Boot 应用，通过 API 层对服务进行测试，而不是通过 Mock 分层逐步去测试每一层的组件。

当我们用约束和反馈把 Harness 搭建起来，约定的写法写进了 AGENTS.md，就会自然产生一个期待：Agent 接下来构建新功能时，会按照我们给定的约定来构造。但实际跑起来常常不是这样。它新写出来的代码，形状和仓库里既有的旧模式一模一样。大量的逻辑仍然留存在 controller 里，测试还是一层一层地测，并没有组合到 API 层面进行测试。

这就是坏味道模式复制漂移（Pattern Copy Drift）。仓库里既有的产物，本身就是 Agent 的学习材料。它会把自己读到的模式复制下去，也不管这个模式是不是团队正打算消灭的。

最开始发现这个问题的是 OpenAI，他们在一个为期五个月的编码实验中观察到，Codex 会复制仓库里已经存在的模式。哪怕团队最初每周五花掉 20% 的工程时间手动清理这些“AI 滑坡”，Agent 仍然会坚持从代码仓库中学习现有模式。

为什么会产生这样的现象呢？有很多原因。

第一是因为代码模型在训练目标上，是给定上下文预测下一段代码。这个目标奖励的是“接得像”，不是“判断得对”。写得和仓库里周围的代码一个样，在训练目标上是得分的。写出一个和仓库里谁都不像、但符合你新约定的实现，反而不得分。更微妙的是，跟着上下文走本身就是一种能力，而且随着模型规模增强，大模型会放弃自己预训练里的先验，转去跟随上下文里的示例。范例给的是什么，它就跟什么。仓库里满是旧模式，它就跟旧模式。

第二是因为当指令与范例产生冲突时，范例常常获得更高的权重。在一个专门研究指令与归纳冲突的实验中，研究人员发现：先给模型一条明确的指令，再给它若干个示范行为，随着示范数量增加，模型会从遵守指令逐渐转向跟随示范。那么，你写在 AGENTS.md 里的约定是几条，仓库里的旧模式是几十上百个示范，这是一场数量悬殊的对抗。模型会倾向于跟随示范。

第三是因为 Agent 写代码的时候，不是从头开始，而是在现有代码基础上增添修改。那么通常第一步是检索当前实现，然后再按相关度排序。通常排在前列的，正是那些实现同类功能的旧代码。然后，Agent 就会依据这个上下文，继续增改。

多方因素综合作用，使得代码仓里的旧模式往往会比 Agent.md 中提供的新模式，更容易被 Agent 采纳。

## Solution：模式基线化

消除模式复制漂移的手法叫模式基线化（Pattern Baseline）。这个坏味道的根源在于，仓库里的旧样例在数量上有压倒性优势，把指令对 Agent 的控制压了下去。所以不能只是加强指令，而要处理样例本身。一方面给出值得参考的正向范例，让它知道该照着谁写；另一方面让旧样例不再是可选项，把它标成待修改的技术债；旧样例一时清理不完，就把它们记入基线，只能逐步减少不能增加。这个手法通常要分四步实现：正向范例、确立架构约束、确立存量基线以及持续清理。

### 正向范例

如前面所述，范例是 Agent 做判断的主导信号。那么我们首先要给出新写法的样子。针对要解决的问题，提供一份参考实现（reference implementation）。比如，新的测试方式，或是 controller 实现的方法。

参考实现放在仓库里固定的位置，然后在 AGENT.md 中给出指引。比如：

my-harness/

├── references/

│ ├── testing/

│ │ └── api/ ← API测试的参考实现

└── AGENTS.md

这里我建议使用单独的参考文件，而不要指定项目中实际的代码。这是因为项目中的代码可能会被改动，那就失去了参考的意义。使用独立的参考实现，受实际开发任务的影响更小。如果暂时写不出范例，还有一个替代办法，找一个独立的外部参照，比如，另一个已经改好的仓库，或是一份示范工程。

无论如何，引入新模式的范例，都是最重要的第一步。因为一旦范例定下来之后，它就是仓库里“什么算标准”的唯一答案，

### 确立架构约束

正向范例给出了“该照着谁写”。接下来处理另一边，让“照着旧样例写”失败。也就是一旦新生成的代码采用了旧有的架构风格，那么就让它失败。这一步叫确立架构约束。当然我们需要提供必要的前馈，让 Agent 理解要如何去写代码，但是更重要的是，提供自动化的反馈，帮助 Agent 高效准确地发现反模式。

我们构造反馈的方式，可以是自定义的 linter，或是像 ArchUnit 这样的工具，帮助我们来做检查：

class ArchitectureTest {

private static final JavaClasses classes =

new ClassFileImporter().importPackages("com.acme");

@Test

void controller\_should\_not\_access\_db\_directly() {

noClasses().that().resideInAPackage("..controller..")

.should().dependOnClassesThat().resideInAPackage("..mapper..")

.because("业务逻辑必须落在 service，controller 只做参数校验和转发")

.check(classes);

}

@Test

void API\_test\_should\_not\_use\_mock() {

noClasses().that().haveSimpleNameEndingWith("ApiTest")

.should().dependOnClassesThat().resideInAPackage("org.mockito..")

.because("API 测试必须真实启动应用，从接口层验证行为")

.check(classes);

}

}

确立架构约束有一条原则：强制不变量，不微观管理实现。可以要求“数据必须在边界处解析”，但不用规定用哪个库；可以要求“业务逻辑不得出现在 controller”，但不规定 service 的方法怎么切。不然反而会束缚 Agent 解决问题的能力。

### 建立基线

范例放好了，架构约束也定好了，下一步是把仓库中的存量代码，标记为技术债，而不是可供参考的上下文。

架构约束一旦上线，存量代码几乎处处违规：controller 里调用 mapper 的有几十上百处，测试里 Mock 分层的是全部。如果选择让 Agent 彻底重构存量代码，可能会存在改坏了的风险，特别是测试不全的情况下。另外，也会花费大量的词元（token），在没有带来额外收益的前提下，这笔钱可能花得不值。

那么，更有效的做法是建立基线。也就是明确承认现状不完美，但不接受变得更差。常用的做法是，首先运行一次架构约束，规则命中的现存违规会被全部记录进基线文件；然后 Agent 修改代码，持续通过架构约束检查，如果有新增的违规，会立马停止当前工作，转而修复架构违规。这样，就能避免在代码仓中新增违规，也就是“不接受变得更差”。

这其实是我们在软件工程中相当常用的一个方式，比如要提升测试覆盖率，那么以当前现状作为基线，只许提升，不能降低。只不过现在用来规范 Agent 的行为了。

### 持续清理

基线解决的是“不允许变得更差”，它不负责变好。存量如果只冻着不动，改造就停在原地。新代码守规矩，旧代码还是老样子。持续清理是指，任何一次改动，只要碰到了存量代码，就在这次改动里把它按照新模式重新实现。

这并不需要额外的努力，因为一旦 Agent 改到存量代码，作为反馈的架构约束就会告诉它，现在的修改并不符合新的模式。作为前馈的架构模式就会告诉它应该怎么修改当前实现。那么，旧模式自然而然就被清理掉了。

## 什么时候该做这个重构

最直接的信号，是新写的代码和打算改造的老代码长得一模一样。另一个信号是，在 PR 评审里同一条评论在多个 PR 上重复出现，比如“这里不该这么写”等等。

其实只要 Agent 还在读仓库、还在往仓库里写，模式复制漂移就一直在发生，区别只是仓库中占据主导的模式是需要丢弃的，还是希望采用的。遗留系统改造是它的高发场景，因为仓库里旧样例的存量最大，Agent 把它们当成标准的概率也最高。但其实只要存在重构或是改写，都会出现模式复制漂移。

## 如何重构

重构的手法就是前面那四步，不再重复：正向范例、确立架构约束、建立基线、持续清理。这里只补两件落地时容易卡住的事。

第一件是顺序。四步之间有依赖关系。先有范例，约束才拦得对，因为只堵旧的不给新的，Agent 无路可走时会就近找一个能抄的；先有约束，基线才有东西可记，没有检查就无从知道现存违规有多少；先有基线，约束才敢上线，存量处处违规的时候，Agent 根本干不了活。

第二件是架构约束的构建比看起来麻烦。麻烦在于你写规则的时候是在跟仓库的现状较劲，哪些反模式要拦、边界划在哪里、判定条件怎么写才不误伤。而 ArchUnit 之类的工具和一般的业务开发逻辑也不尽相同，那么此时多用知识固化就好了，不用自己死磕。甚至可以让大模型，根据提供的参考实现，为你提供对应的 ArchUnit 代码。虽然这么做大部分情况下得不到完整的架构约束，但至少是一个良好的开始。

## 小结

![](https://static001.geekbang.org/infoq/6e/6efa4683cb75e5b7042dbc5d45ad8aed.png)

模式复制漂移的定义：仓库里既有的产物本身就是 Agent 的学习材料，它会把读到的模式复制下去，不管这个模式是否一致、是否正要淘汰，也不管是不是团队正打算消灭的。于是坏模式被反复确认、跨会话放大。

成因有三条：训练目标是给定上下文预测下一段代码，奖励的是“接得像”而不是“判断得对”，跟着上下文走本身就是能力；指令与范例冲突时范例权重更高，你的约定是几条，仓库里的旧模式是几十上百个示范；它写代码前先检索同类实现，按相关度排序，排在前列的正是旧代码。

重构手法是模式基线化，分四步：正向范例（给出新写法的样子，放在仓库固定位置并在 AGENTS.md 里指路）、确立架构约束（把约定变成会失败的自动化检查，反馈优先）、建立基线（现存违规冻结，只许减少不许增加）、持续清理（改到哪清到哪）。

前两步的分工是：范例告诉它该照着谁写，约束让照着旧的写就失败。一个给方向，一个给边界。少了范例，约束拦得住越界却给不出方向；少了约束，方向推不过仓库里的多数派。

判断要点是看架构而不是等症状：新写的代码和要改造的老代码长得一模一样，或者同一句评审意见在多个 PR 上重复出现，就是信号。只要 Agent 还在读仓库、还在往仓库里写，复制就一直在发生，遗留系统改造是高发场景。

架构约束不必一次设计出来，用知识固化一轮轮长：每次 Agent 犯一个新的架构错误，或者评审里出现一条新的重复意见，就问一句“这条能不能变成一条检查”。能机械判定的补进约束，需要人判断的补进约定或范例。
