上一篇创建 Task Lens 时，我们用了默认的 DeepSeek 配置。那条路径最短，但不是唯一选择。

DeepSeek Harness 把“模型是谁”和“Agent 怎么工作”分成了两层。模型通过“提供方（Provider）” 接入，Agent 预设负责组装工具、提示词和运行方式。换一个提供方，相当于给同一套工作环境换了一个大脑；终端、文件编辑和计划能力不会因此凭空消失，也不会自动增加。

这一篇不追求把所有模型服务都配置一遍。我们只走通三条有代表性的路径：默认 DeepSeek 、内置提供方和自定义提供方，然后让它们回答同一个问题。

## 先准备一条固定的测试任务

打开 Task Lens 工作区，新建会话，发送：

请只读分析当前项目，不要修改文件，也不要运行安装命令。

请回答：

1\. 项目现在实现了什么；

2\. 哪个模块最值得优先改进；

3\. 给出一个可以在半小时内完成的改进方案；

4\. 说明需要修改哪些文件；

5\. 给出明确的验收方法。

最后用“理解准确性、方案可执行性、潜在风险”三个小标题总结。

这条任务有意限制为只读。我们的目标是比较模型，不想让三个会话真的改出三套代码。固定提示词也很重要：如果问题本身一直变化，最后就无法判断差别来自模型还是来自任务。

建议记录四项：首次响应时间、是否正确理解项目、方案是否能落地、有没有擅自调用无关工具。无需做复杂打分，简单写几句感受就够了。

## 路径一：默认 DeepSeek

进入“设置 → 模型”，最上方通常可以看到 DeepSeek 卡片。这里的默认配置只要求一个 API Key，保存后即可在模型选择器里使用 DeepSeek 模型。

![](https://static001.geekbang.org/infoq/ca/cad23b360a7dacc2857d903c2bb882a5.png)

它与其他 Provider 最大的不同，是 Harness 已经自带针对 DeepSeek 接口的适配。普通用户不需要填写 Base URL、API 协议和模型清单。

保存凭证后，回到新会话页面选择 DeepSeek 模型，再运行刚才的固定任务。

如果请求失败，先看错误类型。MISSING\_CREDENTIAL 通常表示凭证没有保存，或所引用的环境变量不存在；UNKNOWN\_MODEL 表示会话选择的模型不在当前配置中。网络错误、余额不足和服务限流则需要在 Provider（提供方） 端处理。

这里顺便强调一个容易忽略的细节：模型选择会记录进会话日志。一个已经开始运行的会话，不会因为你修改了默认模型，就在下一条消息时自动切换。做对比实验时，最稳妥的办法始终是新建会话，并在发送第一条消息前确认模型。

## 路径二：添加内置提供方（Provider）

还是在模型设置页，点击“添加提供方”。

![](https://static001.geekbang.org/infoq/22/227329d880b739927a39c628f7fb89c4.png)

这里展示的是 DeepSeek Harness 已经内置的模型服务目录，例如 OpenAI、Anthropic，以及其他内置 Provider。

所谓“内置”，不是说这些模型免费附送，也不是说不需要账号，而是 Provider 的端点、协议和模型目录已经由内置 catalog 描述。你选择 Provider、填写凭证并保存，DeepSeek Harness 就知道怎样与它通信。

选择一个你本来就有账号和 API Key 的 Provider，按照提示填写好对应的 API 密钥然后点击“保存”即可，这里不需要手动添加模型，该内置提供方的可用模型会自动出现在对话框的可选模型列表里。

不要为了完成教程临时购买另一家服务。如果暂时没有第二个 Provider，可以先读完操作思路，等以后真正需要时再配置。

添加好之后，可以再次新建一个会话，然后发送同样的任务提示词，对比不同模型的效果。

## 路径三：添加自定义提供方（Provider）

自定义提供方适合三类情况：公司内部模型网关、本地或自托管模型服务，以及不在内置提供方列表中的兼容接口。

点击“添加自定义提供方”后，表单会要求填写 Provider ID、显示名称、API 地址、API 协议、凭证和至少一个模型。

![](https://static001.geekbang.org/infoq/74/74c0071be171af0e18c8eaa30f0dbee1.png)

### Provider ID 要慎重

Provider ID 是内部使用的稳定标识，只能使用小写形式。请求、会话、默认模型和凭证引用都会使用它。显示名称以后可以改，Provider ID 则不适合重命名；如果确实要换，只能新建一个 Provider，再删除旧的。

我建议把 Provider ID 写成能长期辨认的名字，例如 company-gateway 或 local-vllm，而不是 test1。

### API 地址与协议必须匹配

如果你不确定，优先查服务方的正式文档，而不是不断更换协议碰运气。

### 不要想当然地打开图像输入

手动添加的模型默认按纯文本处理，因为 DeepSeek Harness 无法从一个普通接口自动推断模型是否支持图像。如果接口确实支持视觉输入，需要在 $DSH\_HOME/settings.yaml 中为模型声明 input: \[text, image\]。

这个声明只是告诉 DeepSeek Harness“我确认接口支持”，不会替你验证。如果模型实际上不接受图像，请求仍会被 Provider 拒绝。

保存自定义 Provider 后，新建第三个会话，选择对应模型，再运行固定任务。

## 怎样比较才有意义

模型对比很容易滑向排行榜思维：谁写得长、谁听起来聪明、谁就是最好。但在 Harness 里，我更愿意把模型放进具体工作流里看。

可以用下面这张表记录：

| 观察项 | 默认 DeepSeek | 内置 Provider | 自定义 Provider |
| --- | --- | --- | --- |
| 是否正确识别项目功能 |  |  |  |
| 是否遵守只读要求 |  |  |  |
| 改进方案是否能落地 |  |  |  |
| 是否指出真实风险 |  |  |  |
| 首次响应体感 |  |  |  |
| 工具调用是否稳定 |  |  |  |

如果某个模型在纯文字回答中更强，却经常生成错误工具参数，它未必适合长时间 Agent 任务。反过来，一个回答不花哨、但能稳定读文件、运行测试和修正错误的模型，可能更适合作为默认工作模型。

## 我的选择方法

日常小改动，我先看速度、稳定性和成本；复杂设计或疑难错误，我会换到推理能力更强的模型。

不必追求“一次选出永久默认模型”。DeepSeek Harness 的优势本来就是把模型与其他层拆开。同一套项目维护预设，可以在不同 Provider 之间复用；同一个 Provider，也可以根据任务切换不同模型。

下一节我们保持模型不变，改换 Agent 预设。这样就能看清：当“大脑”没换、工作方式变化时，同一个项目任务会怎样被执行。
