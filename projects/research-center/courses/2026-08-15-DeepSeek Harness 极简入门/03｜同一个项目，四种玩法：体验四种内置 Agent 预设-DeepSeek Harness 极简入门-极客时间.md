模型决定谁来思考，Agent 预设则决定它以什么方式工作。

在 DeepSeek Harness 中，Agent 预设不是一句“你是一名资深程序员”那么简单。它是一套按会话组装的插件组合，决定工具、提示词和能力。当前内置四种预设：标准模式、PTC 模式、极简模式和创造模式。

这一篇不靠定义记忆。我们给 Task Lens 安排四个小任务，每种预设做一件最擅长的事。

## 开始前先留好基线

确认上一篇的 Task Lens 测试仍然通过。如果你使用了 Git，先检查工作区是干净的（用 git status 命令查看）。每个预设最好使用独立会话；涉及修改的任务完成后，可以用 Git 恢复修改前的状态（使用 git restore. 命令），再进入下一个实验。

四种预设最好先使用同一个模型。否则同时更换模型和预设，结果好坏就很难归因。

## 标准模式：日常工作的默认选择

标准模式是功能完整的编码 Agent。文件编辑、Shell、文件和网页检索、Skills、计划、目标、子 Agent 与工作流，都在它的能力范围里。

我们让它做一个典型维护任务：

请为 Task Lens 增加

开启时只输出 todo、doing、done 和 total 的数量，不显示任务明细。

请先检查现有实现和测试，给出计划；确认方案后修改代码、补充测试和 README，最后运行完整测试。不要安装第三方依赖。

这个任务需要读代码、改文件、补测试、运行命令，正适合标准模式。观察它是否先检查现有参数解析，而不是直接重写整个程序；是否把测试和文档当成完成条件；测试失败后能否继续修正。

标准模式的价值不是每个任务都要把所有工具用一遍，而是常用能力已经备齐。大多数日常编码、文档整理和项目分析，都应该从这里开始。

## PTC 模式：不是多一套工具，而是换一种调用方式

PTC 模式值得多花一些篇幅说一下。先说结论：PTC 模式与标准模式拥有的能力基本相同，区别不在“能做什么”，而在“模型怎样组织和调用工具”。

标准模式使用原生工具调用。模型直接看到 grep、read、bash、edit 等工具，每得到一轮结果，就重新思考并决定下一步。PTC 模式则主要向模型提供一个 run\_code 工具和一份 Code Mode SDK。模型会写一段临时的 TypeScript 程序，在程序里调用原来的工具。

可以简单理解为：

标准模式：模型亲自一步步指挥工具。

PTC 模式：模型先写一个小程序，让程序批量组织和调用这些工具。

这里有一个容易混淆的地方：标准模式也可以并行调用工具。如果模型已经知道要读取哪四个文件，它可以一次并行发起四次读取。

真正的区别是：如果“读哪些文件”必须先看搜索结果才能确定，标准模式通常要让搜索结果先回到模型，再由模型发起下一批读取；PTC 模式可以在同一段程序里处理搜索结果、生成文件列表并继续调用工具，不必再次请求模型。

以“找出项目中所有使用 status 的文件并整理影响清单”为例，两种模式的执行过程大致是：

标准模式：

模型 → grep → 结果回到模型 → 决定读取哪些文件

→ 多次 read → 结果回到模型 → 整理清单

PTC 模式：

模型 → run\_code

├─ grep 搜索

├─ 提取并去重文件路径

├─ 并行 read

├─ 分类和汇总

└─ 返回整理后的结果

→ 模型输出清单

原来的 Task Lens 案例只有少量搜索和读取，所以两种模式看起来差别不大。要真正观察 PTC，可以把任务改成一次“状态一致性审计”：

请使用 PTC 模式检查 Task Lens 项目中的状态定义是否一致，暂时不要修改文件。

请尽量在一次 run\_code 中完成：

1\. 搜索项目中所有提到 todo、doing、done、blocked 和 status 的位置；

2\. 从搜索结果中提取并去重文件路径；

3\. 并行读取相关文件，只保留判断所需的内容；

4\. 按“源码、测试、示例数据、README”分类；

5\. 检查每种状态是否同时出现在校验、统计、筛选、测试和文档中；

6\. 返回一张一致性矩阵，列出缺失项及对应文件。

最后根据程序返回的结果，给出新增 blocked 状态的影响清单。

运行时可以打开执行观察。标准模式通常会显示多轮由模型直接发起的 grep、read 等调用；PTC 模式会出现一个外层 run\_code，里面再发生多次工具子调用。内层调用仍然经过原有的权限、审批和执行链路，并不会绕过安全控制。

PTC 也不一定更快。只改一个文件时，写程序反而可能增加成本；当任务包含“先得到一个列表，再逐项处理、筛选、分类和汇总”时，它才更容易体现优势。

一句话总结：

标准模式让模型一步步使用工具；PTC 模式让模型先写程序，再由程序批量使用工具。能力基本不变，变化的是工具编排方式。

## 极简模式：看看模型离开“豪华工具箱”还能做什么

极简模式只提供两个模型工具：持久 Bash 和 str\_replace\_editor。它主要用于最小环境下的模型基准测试，而不是追求舒服的日常体验。

我们给它一个范围很小、答案明确的任务：

请检查 Task Lens 的测试，为“传入未知 status 时应返回非零退出码”补充一个测试并实现对应行为。

只修改必要文件，不安装依赖。完成后运行测试并报告结果。

这个任务的有趣之处不在功能本身，而在观察模型怎样使用有限工具。它不能依赖标准模式里的计划、网页检索或专门的文件发现工具，只能通过持久 Bash 查看环境，再用编辑器修改文件。

极简模式很适合做模型对比：同一套工具、同一条任务、同一个项目，结果更容易反映模型自身的编码和工具使用能力。但如果你正在赶一个真实需求，就不必为了“纯粹”主动放弃更好用的能力。

还有一点要注意：极简不等于只读，也不等于低风险。Bash 和文件编辑器已经足以改坏一个项目，工作区和审批边界仍然重要。

## 创造模式：观察并改造 DeepSeek Harness 自身

创造模式具备标准模式的全部能力，同时加入了运行时检查、插件实验和预设创作指导。它是四种内置预设之一，也是用 Agent 创作自定义预设的入口。

这次先不让它创建预设，只做观察：

请检查当前 Agent 运行时，说明这个会话加载了哪些与文件、终端、网页、计划和子 Agent 有关的插件或服务。

请区分：

1\. 模型可直接调用的工具；

2\. 为工具提供底层能力的服务；

3\. 负责会话、权限或运行控制的基础设施。

只做检查和解释，不要挂载、卸载或修改插件。

这个任务能帮你看见“一切皆插件”不是宣传语。一个文件工具背后可能有文件系统服务和权限策略；终端工具背后有持久 PTY 与进程能力；会话记录、Agent 循环也不是不可触碰的核心黑箱。

创造模式还允许在内存中试验插件。这里我们先克制一点，因为真正创建“项目维护助手”是下一篇的主题。第一次进入创造模式，先学会查看，再学会改造。

## 四种预设怎么选

可以先用一张简单表判断：

| 任务 | 优先预设 | 原因 |
| --- | --- | --- |
| 日常开发、文档、排错 | 标准模式 | 能力完整，过程直观 |
| 大量重复检索或多步工具组合 | PTC 模式 | 可用 TypeScript 组合操作 |
| 模型工具使用能力评估 | 极简模式 | 工具环境小，变量更少 |
| 检查运行时、试验插件、创建预设 | 创造模式 | 提供自省与创作能力 |

这不是硬规则。同一个任务常常有不止一种做法。选择预设时，我通常问三个问题。

第一，任务是不是以日常完成为目标？是的话先用标准模式。

第二，工具操作是不是大量、重复且可程序化？是的话考虑 PTC。

第三，我是在解决业务问题，还是在研究 Agent 本身？后者才需要极简或创造模式。

## 不要频繁在同一会话里来回切

预设可以按会话选择，也可以重新组合到现有会话。但学习阶段我建议一个实验开一个新会话。不同预设提供的工具和提示词不一样，频繁切换会让历史上下文与当前能力错位，也不利于比较。

如果某个预设要长期使用，可以在“设置 → Agent 预设”中选择相应的模式将其设为默认模式。内置预设可以查看和复制，不能把系统自带的那份直接当作个人草稿随意覆盖。

## 这四次实验真正告诉了我们什么

同一个模型，在标准模式里像全功能项目助手，在 PTC 模式里更像会编排工具的程序员，在极简模式里只剩基础操作，在创造模式里则开始观察和改造自己的运行环境。

所以，评价一个 Agent 不能只看模型。模型、Agent 预设、插件和权限共同决定了最后的行为。

下一节我们会正式使用创造模式，把标准模式复制和调整为一个专门维护 Task Lens 的自定义预设，我们将从“选择预设”开始迈向“设计预设”。
