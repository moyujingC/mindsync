这一节我们只做一件事：从零启动 DeepSeek Harness，并让它创建一个可以运行、可以测试的小项目。

过程中你会接触模型、工作区、会话、Agent 预设和审批，但暂时不用记住它们的定义。先看它们怎样一起完成任务，后面再逐层拆开。

## 开始之前，先检查 Node.js 版本

运行如下命令检查：

node

npm

如果 Node 版本过低，推荐使用 nvm 安装 Node 22。不同操作系统的具体安装方法可参考：https://nodejs.org/zh-cn/download

## 启动 Web UI

先打开终端，进入你准备用来练习的空目录。例如，我会新建一个名为 task-lens 的目录，然后在这个目录中启动 Harness。

mkdir task-lens

cd task-lens

npx @deepseek-ai/dsh web

第一次运行需要下载包，速度取决于网络环境。启动完成后，终端会显示 Web UI 的地址，默认是：

http:

在浏览器中打开它。这里的 127.0.0.1 表示页面运行在本机，不是已经发布到互联网的在线服务。关闭启动它的终端进程，Web UI 也会停止。

如果 3080 端口被其他程序占用，可以指定另一个端口：

npx @deepseek-ai/dsh web

在这一步，最常见的两个问题是找不到 npx，或者 Node.js 版本太旧。前者通常说明 Node.js 没有正确安装，后者则需要升级 Node.js。切记，不要在网上随便找一个同名的 deepseek-harness 包替代；本教程使用的是官方包 @deepseek-ai/dsh。

## 先配置默认 DeepSeek 模型

首次打开 DeepSeek Harness 的 Web 界面时，程序会引导你添加 API Key。如下图所示：

![](https://static001.geekbang.org/infoq/83/8331733de55e4d9a6c7dc0a3ba71f640.png)

如果没有自动出现引导，也可以在网页左下角点击“设置”，进入“模型”，找到 DeepSeek 卡片，填入 DeepSeek API Key 并保存。

![](https://static001.geekbang.org/infoq/ef/ef43123cfb92951f7706f23d142fbd5f.png)

这里有两点需要注意。

第一，保存后的 Key 是只写凭证。界面会告诉你凭证已经配置，但不会把原始密钥重新展示出来。

第二，默认模型主要影响新会话。一个已经向模型发过请求的会话，会在自己的日志里保留当时使用的模型。你在设置里换了默认模型，不等于旧会话会悄悄换“脑子”。

## 把空目录变成工作区

回到主界面，点击“选择工作区”，添加刚才创建的 task-lens 目录，然后选中它。

![](https://static001.geekbang.org/infoq/72/7213ee4cef1d691bdbb8d50d5ce93a30.png)

工作区不是一个装饰性的项目标签。它决定了这次会话围绕哪个目录理解文件，也构成了权限控制的重要边界。我们特意使用空目录，就是为了让第一次写入没有历史包袱。

选中工作区后，新建一个会话，并确认 Agent 预设是“标准模式”（在“选择工作区”的按钮旁边可以选择各种模式）。标准模式是功能最完整的内置预设模式，适合第一次体验。它具备文件编辑、Shell、文件和网页检索、Skills、计划、目标、子 Agent 与工作流等能力。

## 让 Agent 创建 Task Lens

把下面这段任务发给 Agent：

请在当前空工作区创建一个名为 Task Lens 的零依赖 Node.js 命令行项目。

要求：

1\. 使用 ES Modules，不安装第三方依赖；

2\. 从 data/tasks.json 读取任务；

3\. 每个任务包含 title 和 status，status 只能是 todo、doing、done；

4\. 默认输出各状态的任务数量和总数；

5\. 支持 --status 参数，只显示指定状态的任务；

6\. 使用 Node.js 内置 test 模块编写测试；

7\. package.json 至少提供 start 和 test 两个脚本；

8\. README 写清楚安装、运行和测试方法。

请先给出简短计划，再创建文件并运行测试。不要安装任何依赖。完成后总结创建了哪些文件、测试是否通过。

这段提示词并没有规定每个文件该怎么写，但给出了边界、功能和验收方法。对 Agent 来说，“做一个任务统计工具”过于宽泛；加上零依赖、数据格式、命令参数和测试要求，它才知道怎样算完成。

我尤其建议保留“先给出简短计划”和“不要安装任何依赖”这两句。前者让你在它动手前发现理解偏差，后者可以避免一个很小的练习项目被塞进一大堆不必要的包。

## 看懂执行过程

标准模式下，Agent 通常会先浏览工作区，确认目录确实为空，然后创建 package.json、README.md、data/tasks.json、源码文件和测试文件。接着它会运行测试，失败时再继续修改。

你会在会话里看到几种不同内容：

普通文字：Agent 对计划、进度和结果的说明；

文件工具：读取、创建或修改文件；

Shell 或终端：运行 npm test、启动程序或检查目录；

审批请求：某项操作需要你的明确授权；

结果卡片：命令输出、测试结果和工具返回值。

不要只盯着最后一句“任务完成”。至少检查三件事。

第一，文件是否真的创建在 task-lens 工作区里。如果路径跑到了上一级目录，先停止任务再检查工作区选择。

第二，测试命令是否真实运行。Agent 说“测试应该可以通过”和终端里出现通过结果不是一回事。

第三，README 描述是否和实际命令一致。AI 生成项目很常见的问题不是代码完全不能跑，而是文档里多写了一个不存在的参数。

## 审批时看什么

在这个案例里，合理的动作包括创建工作区内文件、运行 Node.js 和执行测试。因为我们明确要求零依赖，所以如果它申请运行 npm install，就要先拒绝并追问原因。

我判断审批请求时通常看四个信息：

操作对象是不是当前工作区；

命令是否和任务直接相关；

是否包含删除、覆盖或联网行为；

如果失败，能不能轻松恢复。

## 手动验收项目

Agent 完成后，不要立即进入下一篇。先在自己的终端里运行：

npm test

npm start

npm start

你应该看到测试通过、默认统计结果，以及 status 为 done 的任务统计结果。不同模型生成的输出格式可能不同，只要满足提示词里的验收条件即可。

再打开项目文件，确认大致包含：

task-lens/

├── data/

│ └── tasks.json

├── src/

│ └──...

├── test/

│ └──...

├── package.json

└── README.md

如果没有通过，不必自己马上修。把真实错误原样交回同一会话，例如：

我手动运行 npm test 后仍有失败。请读取真实测试输出，定位根因，只修改与失败相关的文件。修复后重新运行测试，不要通过删除测试来绕过问题。

这比“还是不行，再试试”有效得多。后者没有给 Agent 新信息，只会让它重新猜一次。

## 这次任务里发生了什么

现在我们可以回头看几个概念了。

模型负责理解你的要求、决定下一步并生成内容；标准预设决定这次 Agent 拥有一套完整的编码工作方式；文件、Shell、计划和会话记录等插件提供具体能力；工作区和权限策略限制它能把这些能力用到哪里。

这几层组合起来，才是你刚才使用的 Agent。

普通聊天模型也能给你一段 Task Lens 代码，但需要你手动拆文件、运行测试、把报错贴回去。Harness 做的事情，是把模型放进一个可以观察环境、使用工具并持续推进任务的运行系统里。

## 留一个干净的起点

如果你安装了 Git，可以在这里做第一次提交：

git init

git add.

git commit -m "chore: create task lens baseline"

后面我们会让不同模型和不同 Agent 预设模式修改同一个项目。有了 Git 版本记录，就能分清哪些变化来自哪次实验。
