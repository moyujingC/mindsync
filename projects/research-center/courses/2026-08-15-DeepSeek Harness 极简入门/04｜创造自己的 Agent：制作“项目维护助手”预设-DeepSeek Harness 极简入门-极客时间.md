四种内置预设已经覆盖了常见工作方式，但它们面向的是一般任务。真正把 DeepSeek Harness 用顺手之后，你多半会想固定一套自己的习惯：修改前先读项目规则，复杂任务先列计划，能不用网络就不用网络，写完代码必须跑测试，高风险操作必须停下来问人。

这些要求可以每次都写进提示词，但更好的办法是把它做成自定义 Agent 预设。

这一篇我们将使用创造模式，给 Task Lens 做一个“项目维护助手”。它不追求能力最多，而是追求行为稳定、边界清楚、可以重复使用。

## 先写清楚它的工作合同

创建预设之前，我会先写一份很短的工作合同。没有这一步，创造模式很容易变成“帮我做一个厉害的 Agent”，最后得到一堆听起来强大、实际没有验收标准的配置。

我们的项目维护助手应该做到：

开始修改前先阅读 README、项目结构和现有测试；

任务超过两个步骤时先建立计划；

优先使用工作区内信息，只有遇到版本、外部接口或最新资料时才搜索网页；

不安装依赖，除非用户明确允许；

不删除文件，不修改工作区之外内容；

完成代码修改后必须运行相关测试；

测试失败时先定位根因，不通过删测试绕过；

最终报告包含改动文件、测试结果、剩余风险。

这份合同既决定提示词，也决定插件和权限。比如它需要 Shell 来运行测试，需要 Plan 来管理多步任务，可能需要网页搜索，但不应该默认拥有无边界的写权限。

## 两条创建路径

打开“设置 → Agent 预设”，可以看到四种内置预设。有两种创建方式。

第一种是复制现有预设。选择“复制：标准模式”，输入新的预设 ID、名称和说明。复制后得到的是一份完整快照，这种方式适合你已经知道要改哪些插件的情况。

![](https://static001.geekbang.org/infoq/a7/a7c365f807a5e962b12f24d6823e9539.png)

第二种方法，点击“用「创造模式」创作自定义预设”。点击之后，当前设置页会自动关闭，进入一个已经选择好创造模式的新会话。你可以直接描述目标，让 Agent 检查当前运行时、提出组合方案并帮助创建。

## 把需求交给创造模式

选择 Task Lens 工作区，进入创造模式会话，发送如下内容：

我想创建一个个人自定义 Agent 预设，名称叫“项目维护助手”，建议 ID 使用 project-maintainer。

用途：维护小型代码项目。

行为要求：

1\. 开始前阅读 README、项目结构和现有测试；

2\. 超过两个步骤的任务先创建并维护计划；

3\. 优先使用工作区信息，只有需要外部最新资料时才搜索网页；

4\. 未经明确允许，不安装依赖、不删除文件、不修改工作区之外内容；

5\. 修改代码后运行相关测试；

6\. 不允许通过删除测试绕过失败；

7\. 最终报告改动文件、测试结果和剩余风险。

请先检查当前运行时和标准模式的插件组装，给出预设设计方案。先不要创建，等我确认。

“先不要创建”很重要。创造模式能检查和试验运行时，也能写入预设文件。在它真正动手之前，我们要先看方案是否符合工作合同。在这个过程中，对话框会弹出一些选项或授权审批让你选择，根据你的实际想法来选择对应的选项即可，如下图所示（每个人弹出的内容会不一样）：

![](https://static001.geekbang.org/infoq/a9/a930f3e9fc43076f035d1959b6df9f9b.png) ![](https://static001.geekbang.org/infoq/25/259db2a54e651e1e95557d1ac3bc12e1.png) ![](https://static001.geekbang.org/infoq/c7/c7c7e47933084b65affeacbff4161cc5.png)

一个合理的方案应该回答：以哪个内置预设为基础、保留哪些工具、是否包含 Plan、Skills、网页能力、子 Agent 和工作流、采用什么权限边界。它还应该说明哪些约束来自提示词，哪些需要靠工具和权限实现。

如果 Agent 只是把我们的七条要求换一种说法重复一遍，没有谈插件组装，就继续追问：

请把设计拆成三层说明：

1\. 预设需要挂载的插件与工具；

2\. 写入 persona 或系统提示的行为约束；

3\. 不能只靠提示词、必须由权限或沙箱保证的边界。

## 提示词不是权限系统

这是设计自定义预设时最值得记住的一点。

“请不要修改工作区之外文件”是一条行为指令，模型通常会遵守，但它不是强制隔离。如果工具本身拥有更大的访问范围，模型仍有犯错的可能。真正的边界应该由工作区、权限预设、沙箱和审批策略共同保证。

反过来也一样。沙箱可以阻止越界写入，却不会让 Agent 自动养成“先读测试再改代码”的习惯。工作流程更适合写进 persona（人设） 或 Skill。

好的预设会同时使用软约束和硬边界，而不是把一切希望寄托在一段系统提示词上。

## 让创造模式在内存中试验

确认方案后，不必马上保存。可以先让 Agent 在当前运行时中试验：

方案可以继续。请先在内存中试验建议的插件组合，检查必要服务是否存在、插件依赖是否满足，以及是否能提供文件编辑、Shell、Plan、Skills 和按需网页搜索。不要卸载当前会话赖以运行的核心服务。

这一步的目的不是追求“热插拔”的炫技，而是提前发现缺失依赖和错误配置。比如一个模型工具只是 Consumer，背后还需要对应的 Service Provider；只装工具外壳，没有底层服务，运行时依然不可用。

要求 Agent 报告试验结果，包括成功挂载项、未满足依赖和回滚情况。临时实验结束后，应当把运行时恢复到稳定状态。

## 正式创建预设

试验通过后，再授权它创建：

请根据确认后的方案创建 project-maintainer 预设。创建完成后：

1\. 检查预设元数据和组装文件；

2\. 验证预设能够被列表发现；

3\. 不要修改内置预设；

4\. 告诉我怎样在新会话中选择它。

个人自定义预设会保存在 DeepSeek Harness 的个人预设目录中，如下图所示，而不是写进 Task Lens 仓库。这样它可以被不同工作区复用。

![](https://static001.geekbang.org/infoq/dd/ddd468ff1ed21b19c021b4de8bcdbb9c.png)

内置预设可以查看和复制，但不应该直接覆盖。复制得到的预设是一份快照：以后 DeepSeek Harness 升级了标准模式，你的副本不会自动吸收所有变化。这既保证个人配置稳定，也意味着需要自己维护。

## 用一条固定任务测试它

创建完成后，结束创造模式会话，新建会话并选择“项目维护助手”。发送：

请为 Task Lens 评估新增 blocked 状态的影响。

先阅读项目和测试，建立计划，只输出影响分析和实施步骤，暂时不要修改文件。分析必须覆盖代码、测试、示例数据和 README。

我们刻意要求“暂时不要修改”。测试自定义预设时，先验证行为，再验证产出。观察它是否：

主动阅读 README 和测试；

在多步骤任务中建立计划；

没有为了显得能干而立刻改文件；

没有在本地信息足够时滥用网页搜索；

报告范围覆盖合同要求。

如果行为不符合预期，不要马上追加十条更强硬的提示。先查看它的执行轨迹，确认它实际加载了哪个预设、看到了哪些提示、有哪些工具。问题可能来自 persona，也可能是插件未挂载、权限过宽或会话选错预设。

## 什么时候该改，什么时候该另做一份

“项目维护助手”适合通用代码维护。如果以后需要一个只读审查 Agent，我更倾向于复制一份新预设，而不是给现有预设增加大量条件分支。

一个预设只解决一类核心问题，通常比“万能预设”更容易预测。命名时也尽量表达用途，例如 read-only-reviewer、docs-researcher、release-checker，而不是 my-agent-v7-final。

下一篇我们进入设置页，具体调校三个开放给用户的插件配置区域：终端、Agent 循环和网页搜索。随后再体验 Skills、Plan、Subagent、Sandbox 和 Session 等几类代表性预装插件。
