前面几篇一直在拆解 DeepSeek Harness：先换模型，再换预设，然后创建自己的预设，最后调插件。现在我们把这些不同的层重新合起来。

我们的最终任务是给 Task Lens 增加第四种状态 blocked。这不是一个很难的功能，但它会同时影响数据校验、统计、筛选、测试、示例数据和 README，正好适合检验 Agent 能否持续完成一组有关联的工作。

这一篇最重要的不是代码结果，而是完整走一遍决策过程：为什么选这个模型、为什么用这个预设、需要哪些插件、怎样设置边界、最后如何验收。

## 开始前恢复干净状态

先运行：

npm test

git status

如果前面四种预设实验留下了未提交修改，先决定保留还是恢复。不要让最终任务从一个自己都说不清的状态开始。

建议做一次基线提交：

git add.

git commit -m "chore: prepare blocked status exercise"

没有使用 Git 也没关系，但至少复制一份项目目录。能随时恢复，是让 Agent 放手工作的前提之一。

## 先做配置决策

### 模型

选择前面测试中工具调用稳定、理解项目准确的模型。这个任务规模小，不需要仅仅为了“更强”切到最昂贵的模型。模型选择器中确认 Provider 与模型名称，并新建会话。

### Agent 预设

选择上一篇创建的“项目维护助手”。如果自定义预设还不稳定，可以退回标准模式，但要把工作合同写进任务。不要为了最终实战改用 PTC；这次工作的核心是多轮分析、修改和测试，并没有大量重复工具调用。

### 插件

需要文件读写、普通 Shell、Plan 和 Session。网页搜索不是必需能力，因为 blocked 是 Task Lens 的本地业务定义，不依赖最新外部资料。Subagent 也没有必要，这个项目太小，委派反而增加协调成本。

这恰好验证了插件选择原则：拥有网页搜索不代表每次都要搜，拥有子 Agent 也不代表每次都要委派。

### 权限

允许写入当前工作区，保留命令审批或工作区写入策略；不授予工作区之外写入，不允许安装依赖，不允许删除文件。

终端命令超时保持一个能覆盖完整测试的合理值。Agent 循环的并行工具调用数保持默认即可，不需要为了小项目专门拉高。

## 提交完整任务

把下面的任务交给“项目维护助手”：

请为 Task Lens 增加第四种任务状态 blocked。

背景：blocked 表示任务当前无法继续，需要等待外部条件。它应当和 todo、doing、done 一样参与统计和筛选。

工作要求：

1\. 先阅读 README、源码、测试和示例数据；

2\. 建立并维护一份执行计划；

3\. 找出所有受影响位置后再修改；

4\. 更新状态校验、汇总输出和

5\. 在示例数据中加入至少一个 blocked 任务；

6\. 为统计、筛选和非法状态补充或更新测试；

7\. 更新 README 中的状态说明和命令示例；

8\. 不安装第三方依赖，不删除现有测试；

9\. 完成后运行完整测试。

验收标准：

\- npm test 全部通过；

\- npm start 的汇总中出现 blocked；

\- npm start

\- 未知状态仍应返回非零退出码；

\- 最终报告列出改动文件、测试结果和剩余风险。

如果发现要求与现有实现冲突，先说明冲突并等待确认，不要自行改变验收标准。

这是一条比较完整的任务指令，但并不啰嗦。背景解释业务含义，工作要求规定范围，验收标准定义完成。最后一句给异常情况留了出口，避免 Agent 为了继续运行而悄悄改题。

## 第一轮只看计划

项目维护助手应该先读取项目，再建立计划。计划至少覆盖代码、测试、数据和文档。

此时先检查它有没有遗漏：

状态白名单或校验逻辑；

默认统计对象；

\--status 参数校验；

测试夹具或内联数据；

README 的状态列表和示例输出。

如果计划只说“修改源码、更新测试”，还不够具体。可以要求它把受影响文件与对应修改列出来，再批准执行。

不要替 Agent 逐行设计实现。我们要验证的是预设能不能自主完成任务，不是把所有决定都拿回来自己做。

## 观察执行，而不是盯着动画

任务开始后，关注几个真正有意义的节点。

### 它是否遵守范围

合理操作应集中在 Task Lens 工作区。出现安装依赖、访问无关目录或大范围重写时，先拒绝并询问原因。

### 它是否使用真实反馈

第一次测试失败很正常。关键是 Agent 有没有读取真实错误，再针对根因修改。如果它反复运行同一命令却没有新分析，Agent 循环可能正在做无效工作，应及时中断。

### 它是否维护计划

计划不是开场仪式。调查完成、代码完成、测试完成时，状态应该更新。如果事实发生变化，计划也应该调整。

### 它有没有滥用插件

这个任务不需要网页搜索。若 Agent 搜索“blocked 状态最佳实践”，并不能帮助理解本地验收标准。除非项目引用了外部规范，否则应让它回到工作区。

子 Agent 同样不是必需。如果预设仍然委派了简单文件读取，说明组合可能过于积极，后续可以调整 persona 或工具指导。

## 手动验收，不接受“应该通过”

Agent 报告完成后，在自己的终端中运行：

npm test

npm start

npm start

npm start

前三条应该正常完成，最后一条应该给出清楚错误并返回非零退出码。

然后检查 Git 差异：

git diff

git diff

我会特别看这几个问题：

是否为了加一个状态重构了大量无关代码；

测试是否真的验证输出，而不是只验证进程没崩；

示例数据和 README 是否一致；

错误路径是否仍然保留；

有没有把生成文件、临时日志或凭证提交进项目。

如果测试通过但实现过度复杂，可以继续同一会话要求精简，不过要保持验收标准不变。不要只说“优化一下”，而要指出具体问题，例如“这次改动新增了两层不必要抽象，请在不改变行为和测试的前提下简化”。

## 用 Trajectory 复盘一次

最终结果合格后，打开 Trajectory。顺着时间检查：

会话使用的 Provider、模型和 Agent 预设；

系统提示和项目上下文是否正确加载；

Agent 先读取了哪些文件；

计划在什么时候建立和更新；

哪些工具调用并行执行；

测试失败后如何进入下一步；

是否发生不必要搜索或重复读取；

最终报告依据哪些真实结果生成。

这一步会把“我觉得 Agent 挺聪明”变成可检查的事实。预设设计的问题，往往从最终答案看不出来，却会在轨迹里暴露：重复读取、无意义委派、过早修改、测试失败后盲目重试，都是常见信号。

如果想比较另一个实现方案，可以从修改开始前的边界分叉会话，让分支尝试不同设计。不要在已经完成的会话末尾说“全部推倒再来”，那会让上下文同时保留两套互相冲突的历史。

## 回到最初的三个问题

完成这个案例后，DeepSeek Harness 的三层配置应该已经连起来了。

模型 Provider 决定“谁来思考”。默认 DeepSeek 最方便直接，内置 Provider 也可以节省很多配置工作，自定义 Provider 则适合连接第三方的模型服务。

Agent 预设决定“以什么方式工作”。标准模式适合日常任务，PTC 适合程序化组合工具，极简模式适合评估，创造模式用来观察运行时并制作自己的预设。

插件决定“拥有和依赖哪些能力”。Shell 运行测试，Agent 循环推动多步工作，Plan 保存执行状态，Session 记录事实，Sandbox 和审批守住边界。网页搜索与 Subagent 在这次任务中没有被使用，这同样是一个正确的配置结果。

## 接下来怎么用到自己的项目

把 Task Lens 换成真实项目时，不要直接复制最终任务里的所有要求。先做一次只读分析，让 Agent 了解项目结构、测试命令、贡献规范和风险边界，再调整“项目维护助手”。

大项目可能需要更长的命令超时、更严格的输出控制、项目专属 Skill，或者把调研和实现委派给不同子 Agent。企业项目还要考虑网络策略、凭证、审计和自定义 Provider。

但配置顺序不应该改变：

先定义任务和验收标准；

再选择合适模型；

决定 Agent 的工作方式；

只启用必要插件；

用权限和沙箱限制真实边界；

最后通过结果与轨迹验收。

如果你已经能解释每一步为什么这样选，而不只是记住按钮在哪里，这套快速入门就算完成了。
