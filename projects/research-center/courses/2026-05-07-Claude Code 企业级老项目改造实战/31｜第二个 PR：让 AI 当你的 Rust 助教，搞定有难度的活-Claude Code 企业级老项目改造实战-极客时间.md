你好，我是 Robert。

上一讲跑通了 SignYourName，你的名字进了 RobustMQ 项目的贡献者列表。但那是心理胜利，不是真本事。第一个 PR 证明你能在不属于你的代码上交付，第二个 PR 才证明你能在不熟的栈上做出真正的工程贡献。

这一讲就做这件事。我们会在 30 讲那个 Rust 项目上完成两件事：第二个 PR 加一个真实功能 + 第一个 issue 报告一个真实问题。两件事跑完，你就正式成为这个项目的 Contributor。

这里多说一句，为什么选 Rust 项目？Rust 是 AI 时代仍然有学习门槛的语言，所有权、生命周期、async，这些机制不是看一眼就能上手的。但有 AI 当助教，门槛就被压下去了。你不熟没关系，AI 解释机制，你做判断。这一讲想让你看到的就是这种工作姿势：不熟的栈，不再是 blocker。

提醒一句，这一讲所有动作都在 30 讲那个项目上跑，但载体你可以换。你跟着这一讲的方法论，在你筛中的任何项目上都能复刻这套流程。

## 先用 24 讲的方法摸清项目

动手之前先摸项目。24 讲那套四维度框架直接套，它是什么、它能做什么、它怎么扩展、它内部怎么跑。

但这次的任务不一样了。24 讲的任务是做一个新系统，这次的任务是找一个能上手的 issue。任务变了，问 AI 的角度也要变。

我用一段提示词跑完顶层认知：

我在项目仓库目录下。我已经成功提了第一个 PR(SignYourName),

现在要做第二个 PR,目标是给这个项目提交一个有真实工程价值的小贡献。

请你按这四个维度给我一份针对"找 issue"任务的项目地图:

1\. 模块划分。这个项目的代码大致分成几块?每块负责什么?

2\. 测试组织。单测放在哪、集成测试放在哪、怎么跑?

3\. 贡献热点。最近三个月哪几个模块改动最多?活跃 contributor 主要在

哪些模块?(扫 git log 看)

4\. 适合新人的入口。看 issues 里 good first issue / help wanted 标签

下,有没有可以上手的方向?CONTRIBUTING.md 有什么对新人的硬约束?

不要给我一份完整架构文档,只给我对找 issue 有帮助的那部分。

提示词的关键是“针对找 issue 任务的项目地图”。AI 不知道你要干嘛的话，会给你一份干巴巴的架构介绍。告诉 AI 你的目的，它会过滤出对你有用的部分。带任务问，这条 24 讲建立的姿势，这一讲再用一次。

跑完这一段，我对项目内部心里有数了：协议层、存储层、metadata、CLI 工具，大概四块。最近活跃的是协议层和 CLI。good first issue 标签下有几个待领的小活，CONTRIBUTING.md 要求所有新增代码必须带测试。

地图有了，接下来是从这张地图上挑一个我能干的 issue。

## 让 AI 帮我筛 issue

挑 issue 不是凭直觉，是按标准。这一讲的 issue 筛选标准有三条：

改动量不大。第二个 PR 不是搞大型重构，目标是做完一件能合并的小事。改动量控制在 50-200 行代码 + 测试。

AI 能自己改。issue 描述清楚 + 改动是局部的，AI 看完代码上下文能写出来。避开那种需要深度业务理解或者跨多个模块协调的 issue。

我能 review。AI 写完代码我能看懂、能判断对错、能跟维护者讨论。不要选自己看完都不知道在改什么的 issue，你会签字提 PR，但你的简历上挂的是这条 commit 的话，出问题就是你的责任。

把这三条标准丢给 AI（还在同一个仓库目录下的 Claude Code session 里继续跑，前面那份项目地图它还记得）：

基于刚才那份项目地图,帮我从这个项目的 issue 列表里筛 5 个候选,

作为我的第二个 PR 目标。

筛选标准:

1\. 改动量不大,代码 + 测试加起来 50-200 行

2\. 描述清楚,改动是局部的(单文件或单模块内)

3\. 不需要深度业务理解,我能 review 得了 AI 写的代码

每个候选告诉我:

\- issue 编号和标题

\- 它在哪个模块

\- 我做这个 PR 大概要干什么(一两句话)

\- 为什么它符合上面三条标准

\- 风险点在哪(比如有没有可能改完发现规模超出预期)

5 个候选给我排个优先级,从最稳到最有挑战。

Claude Code 跑完给了我一份候选清单。我看了一遍，挑了一个改动量合适的 issue：Issue #1605: 把 admin-server 里 shard/list 和 segment/list 两个查询类 API 从 POST 改为 GET。改 4 个文件，逻辑不变，语义对齐 REST。

为什么挑这个？它有真实工程价值（说清楚这个改动满足什么用户需求）、改动是局部的（说清楚在哪个模块、影响范围）、Rust 经验要求适中（说清楚用到哪些 Rust 特性，但不至于硬到看不懂）、我能 review（我虽然对 Rust 不熟，但相关模式能看懂)。

## 让 AI 改 + 测试 + 提 PR

挑好 issue，后面就是 30 讲那个工作流的复刻。fork + clone + 一段长提示词，AI 跑完剩下的全部。

如果你 30 讲已经 fork 过这个项目，直接在原来那个本地仓库目录下继续。如果还没 fork，先 fork + clone。然后在 fork 后的本地仓库目录下打开 Claude Code，丢下面这段提示词。

我没有手敲过一行代码，但这一次提示词比 30 讲长，因为这次是真改代码，不是改 Markdown。

我要给这个项目提一个 PR,实现 issue

\`shard/list\` 和 \`segment/list\` 两个查询类端点,从 POST 改为 GET。

查询类接口本来就该用 GET,这是 REST 语义的一次回归。

请你帮我把整套流程跑完。每一步执行前告诉我你要做什么,执行后告诉

我结果。任何报错或不确定的地方立刻停下来问我,不要自己瞎修。

这段提示词的关键设计：

先 plan 后改，AI 不能拿到 issue 就闷头写，得先把 plan 给我审核，我同意才动。这是 27 讲提示词驱动写代码那一讲建立的硬规则。

关键改动逐段解释 + 所有权 / async 简短解释，这是 AI 当 Rust 助教的具体形态，它不只是写代码，是边写边教我。

不为了炫技用复杂 idiom，这一条是防止 AI 写出 Rust 高手风格的代码，会导致我看不懂、review 不了。

所有 warning 清掉不留 allow 绕过，这是开源项目的硬要求，不能用 #\[allow(...)\] 偷懒。

Claude Code 跑完，大概是这个过程：

它先读了 issue + 相关代码，给我一份 4 条 plan：第一，在 admin-server 的 router 文件里把两个端点的.post(...) 改成.get(...)；第二，handler 函数签名从 Json(req) 改成 Query(req)；第三，client 端调用方对应改.post() 为.get()，且把请求 body 改成 query string；第四，跑现有测试，有失败再补对应的测试更新。我看完同意，它开始写代码。

写到 handler 那段，它停下来跟我解释：axum 的 Json extractor 把请求 body 反序列化成 struct，只能配 POST/PUT；Query extractor 把 URL query string 反序列化，配 GET。这是 axum 的类型驱动 Web 框架 idiom，不是 Rust 语言层面的事，但你不知道这一点会卡半天。这一段就是 Rust 助教的价值，我自己写不会想到这个细节，AI 写出来还告诉我为什么这么写。

写到 ShardListReq 那段，它停下来提醒：这个 struct 里有一个 Vec\<String> 字段，axum 默认的 Query extractor 不支持多值参数（同名 query string 出现多次会被覆盖）。我问它“那怎么办，要不要把 Vec 改成逗号分隔的 String 然后手动 split”，它解释：项目已经引入了 axum-extra 这个 crate，它的 Query 扩展支持 multi-value，直接用 axum\_extra::extract::Query 替换 axum::extract::Query 就行，不用动业务代码。我学到一个 idiom，而且确认了它符合项目风格。

测试它跑现有的集成测试，跑 cargo nextest run --package admin-server（项目用 nextest 不是默认 cargo test，这是 Makefile 里发现的项目惯例），有 2 个 case 失败。它停下来给我看错误信息，问我要不要让它修。我看了一眼，是测试还在用.post() 调端点，因为路由改成 GET 了，这两个 case 拿到的是 405 Method Not Allowed。它把测试里的.post(body) 改成.get().query(...)，重跑，绿了。

cargo fmt + cargo clippy 各跑一遍，clippy 报了一个 needless\_borrow warning，在 client 改造的地方多了一个引用符号。它没用 #\[allow\] 绕过，直接改代码消掉。

最后 commit + push + 用 gh CLI 提了 PR。整个过程大概 50 分钟，大部分时间在等 cargo build 和 cargo nextest。

这里需要注意的是，在 5 到 6 之间，需要停一下，你需要 review 代码。这里需要提醒的是，给开源项目提交的代码一定需要我们 reveiw，这也是对开源负责任的体现。

## 让 AI 找一个不复杂的漏洞，提 issue

PR 提了不算结束。这一讲我要让你做的另一件事是：提一个高质量 issue。

为什么 issue 也算 contributor 行为？开源项目里很多核心维护者会告诉你，一个写得清楚、可复现、有定位价值的 bug 报告，价值不比一个 PR 小。PR 可能因为方向不对被砍，但 issue 是输入信息，几乎不会被拒。很多 Maintainer 反而更欢迎高质量 issue，因为 PR 代码质量良莠不齐，issue 至少不污染代码库。

Contributor 不只是改代码的人，是给项目带来价值的人。一个清晰的 bug 报告，就是价值。

让 AI 扫代码找候选漏洞。我倾向找性能问题，AI 扫静态代码最擅长找这类问题：不必要的 clone、async 处的潜在死锁、热路径上的锁竞争、内存分配的低效模式。

还在仓库目录下的 Claude Code 里继续跑（同一个 session 跑完最稳，AI 对项目代码的上下文还在）：

帮我扫一遍这个项目的代码,找潜在的性能问题。重点看:

1\. 不必要的.clone() 或.to\_owned(),特别是热路径上(协议处理、存储读写)。

2\. async 函数里持有 std::sync::Mutex(应该用 tokio::sync::Mutex 或者重构掉)。

3\. 锁的粒度太粗,把不该锁住的代码包进去了。

4\. 在循环里反复分配 Vec/String/HashMap 这种可以预分配的场景。

5\. Stream / iterator 用法低效,比如 collect 之后又遍历的可以直接 chain。

不要找编译器和 clippy 已经能查出来的(那些项目自己会跑)。

找那种需要看上下文才能发现的真问题。

给我 5 个候选,每个说清楚:

\- 文件路径和行号

\- 问题描述(具体哪段代码 + 为什么是问题)

\- 影响范围(只有 corner case 才会触发,还是日常路径上)

\- 修复思路(不要写代码,讲清楚改动方向就行)

提示词关键是“不要找 clippy 已经查出来的”，那些是项目自己跑 CI 就能消灭的，提了也没价值。要找需要上下文判断的真问题。

AI 跑完给了 5 个候选。我看完挑了最有算法价值的那一个：mqtt-broker/src/core/topic\_rewrite.rs:54-70 的 convert\_rewrite\_topic 函数，在外层遍历所有 topic 的循环里，每个 topic 都重新过滤一次全量 rules，生成一个临时 Vec<&MqttTopicRewriteRule>。生产环境 topic 几万的场景下，算法复杂度是 O(topics × rules)，应该降到 O(topics + rules)。

这个候选符合高质量 issue 的标准：在日常路径上（规则重算时遍历全量 topic）、影响清晰（算法复杂度可量化）、有具体定位（文件 + 行号 + 函数名）、修复方向明确（循环外按 tenant 建分组 map，内层 O(1) 查表）。

挑这个不是挑最简单的。AI 推荐的 5 个里有几个是“多余的 collect”、“多余的 clone”那种 1 行就能改的代码风格问题，那种东西维护者反应通常是“直接 PR 删一行就行，提 issue 干嘛”，不算高质量 issue。算法层面有改进、修复需要讨论方向、需要测试验证的问题，才值得走 issue 流程。

让 AI 帮我把这个候选写成一个高质量 issue：

基于上面那个 topic\_rewrite O(n²) 过滤的性能问题,帮我写一个

GitHub issue。

要求:

1\. 标题简洁,一句话概括问题(<80 字符)

2\. 正文按这几节:

\- Description:问题是什么,3-5 句话,讲清楚 O(topics × rules) 这个

复杂度问题

\- Reproduction:怎么复现(rules 数量 + topics 数量足够大,触发规则

重算路径就能观察到延迟)

\- Impact:影响什么场景、严重程度,生产环境 topic 数量级是几万的话

量化一下延迟

\- Suggested fix:可能的修复方向(不要写代码,讲思路:循环外按

tenant 把 rules 分组成 HashMap,内层改成查表)

\- Environment:项目版本、Rust 版本、OS

3\. 语气是普通工程师,不是 LinkedIn 帖子,不是问问题,是报告问题

4\. 显式说"我可以在确认方向后跟一个 PR",给维护者一个信号:

我不只是路过的伸手党

最后那一条很关键。“显式说我可以跟 PR”是高质量 issue 的标志，它告诉 Maintainer 你不是只想刷 contribution 数字，你愿意接着把这件事做完。很多时候 Maintainer 看到这一句就会主动来 review 和讨论，因为他们知道这个 issue 不是石沉大海。算法改进类问题尤其适合走 issue 先讨论，因为修复方向（分组 map vs 索引化 vs 缓存化）有几种合理选择，先在 issue 里对齐方向，再开 PR，效率比直接提 PR 让 Maintainer 选方向高得多。

AI 写完一份 issue，我审核一遍，提到了项目仓库。

## 成为 Contributor 的那一刻

第二个 PR 合并，第一个 issue 提了。打开你的 GitHub 个人页面，那个项目的仓库下，你的贡献从一条 SignYourName commit 变成了：1 个有功能价值的 PR + 1 个有定位价值的 issue + 1 条 SignYourName commit。

这不是数字游戏。这是 Contributor 身份的真实开始。简历上你可以写：X 项目 contributor，贡献了一个 Y 功能 + 一个性能 issue 报告。这一行简历的分量，远大于“熟练使用 Rust 5 年”。因为它公开可点击验证、不可伪造、AI 写不出来。

更重要的是，这套流程在一个项目上跑通了，以后任何项目都能复刻，接下来就是选下一个项目继续做。

第一个 PR 是心理胜利，第二个 PR 是真本事。真本事一旦做成第一次，后面就是肌肉记忆。

## 小结

这一讲做了两件事：第二个 PR 加了一个真实功能，第一个 issue 报告了一个真实问题。两件事加起来，你正式成为这个项目的 Contributor。

让 AI 当 Rust 助教这个姿势，是这一讲想留给你最重要的工作方法。AI 不是替你写代码，是边写边教你，逐段解释关键改动、提醒所有权和 async 的细节、推荐项目风格的 idiom、把不熟的栈的门槛压下去。你不熟没关系，AI 解释机制，你做判断。

Contributor 不只是改代码的人。一个清晰的 bug 报告，价值不比一个 PR 小。提 issue 是 Contributor 行为，提带“我可以跟 PR”信号的 issue，是更高级的 Contributor 行为。

现在整套打法你已经有了：24 讲四维度摸项目、30 讲三道题筛项目、这一讲三条标准筛 issue + 长提示词跑 PR + 扫漏洞提 issue。这一讲所有提示词都在 fork 后的项目仓库目录下打开 Claude Code 跑。AI 在仓库里有完整的代码访问能力，提示词才能驱动完整的开发流程。接下来就是选下一个感兴趣的项目，在那个项目目录下把这套流程再跑一遍。
