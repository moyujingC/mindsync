## 背景： 加什么样的自动化测试

简单讲一下背景，RobustMQ 是一个多协议消息中间件，支持 MQTT 这个主流协议和创新 mq9 协议，定位生产级使用。作为一个开源的消息中间件项目，用户使用时的第一个问题不是功能够不够，而是敢不敢用：消息会不会丢、节点挂了能不能恢复、客户端 SDK 换个版本还能不能正常连。这些问题靠单元测试和常规集成测试覆盖不到，必须在真实的混乱条件下持续验证。所以现有测试有盲区。

单元测试和基础集成测试只能覆盖核心逻辑的正确性，但协议兼容性没有持续验证机制、故障场景没有系统化覆盖、长时间运行问题暴露不出来、组合场景几乎没碰。问题发现周期以月计，等用户踩坑反馈再修，节奏太慢，跟不上早期项目的迭代速度。所以需要有一个自动化的 7×24 不间断的自动化混沌测试。

所以这个需求最开始就一句话：

用 AI Agent 给 RobustMQ 实现一套 7×24 不间断跑混沌测试的系统，自动起集群、自动注入故障、自动调多语言 SDK 跑测试、自动收集日志、自动出报告。

这句话听起来已经很具体了：5 个功能动词、1 个时间约束、1 个技术取向。看起来直接拆任务就能干。但接到这种需求当天就开始写代码的人，没一个交付得好。这句话里藏的事比说的多得多。

举几个它没说的：

测什么协议、覆盖哪些 SDK 语言和版本？

故障注入到底是 kill 进程，还是网络延迟，还是磁盘填满？

测试报告给谁看？对内还是对外公开？

多语言 SDK 是预先写好的脚本，还是让 AI 现写？

频率怎么定？所有场景都跑一样频率，还是分级？

这些事每一件都有几种合理选择，每种选择都会影响后面的技术方案长什么样。不先把它们拍清楚，直接进技术设计，后面会出现的情况是：写到一半发现某个假设不对、回头改方案、改完又发现另一处不对。绕一圈，几天就过去了。

所以接到一句话需求，第一件事不是拆方案，是先把需求本身拆完整。

“先别谈具体技术框架”。把问题域和方案分开，这是这一讲的核心动作。如果不强调，AI 立刻就会往 Hermes 上跳。

### 我反问的几个点

场景的优先级没分。AI 列了几十个场景，但没说“哪些每次必跑、哪些每天跑、哪些每周跑”。混沌测试持续运行，频率分级是必须的，不然要么资源跑爆，要么覆盖度不够。

测试报告的公开度没定。报告对内给团队看，还是对外公开？这件事直接决定数据存在哪、有没有 Dashboard、要不要做信息脱敏。一句话需求里没说，完整设计里这条得有。

SDK 矩阵没系统化。AI 列了“多语言 SDK”，但具体覆盖哪些语言、每种语言哪几个版本、版本之间怎么切换，没讲。协议兼容性测试的核心就是这个矩阵，矩阵不清楚，测试就跑不出可信结果。

我把这三条直接抛给 Claude Code：

你这版有几处空洞：

1\. 场景优先级没分。混沌测试持续跑，得有 P0/P1/P2 这种分级，

按触发频率匹配。补一下。

2\. 测试报告对内还是对外？这件事影响存储、Dashboard、脱敏一系列设计。

给我两三个选项，我来拍。

3\. SDK 矩阵不够系统。具体覆盖哪些语言、每种语言哪几个版本、

怎么切换版本，展开。

别又冒新选择，把这版补完整。

这一步是反问，不是追问。反问是“你这里漏了，补上”；追问是“你前面那段再讲讲”。AI 不会主动告诉你它漏了什么，得你自己有一份“完整设计文档该长什么样”的预期，拿这份预期去比对它给的版本，差了什么就反问什么。预期从哪来？从你工作经验里来。

Claude Code 跑完，三处全补上。

场景库分级给了 P0 / P1 / P2：P0 是基础功能的最低保障线，任何 P0 失败立即报警；P1 是故障场景和多语言基础覆盖；P2 是组合场景和完整 SDK 矩阵。

Claude Code 给了一份相当扎实的初版方案。

Skill 套件设计：

7 个工具函数全部映射成同一个 Skill 套件 robustmq-chaos-test 下的 Tools。核心理由是它们共享同一个上下文（场景描述、集群状态、测试进度），由 Agent 串联调用最自然。如果拆成 7 个独立 Skill，跨 Skill 的上下文管理会成为新的负担。

目录结构：

~/.hermes/skills/robustmq-chaos-test/

├── SKILL.md

├── tools/

│ ├── cluster.py

│ ├── chaos.py

│ ├── client.py

│ ├── observability.py

│ └── report.py

├── scenarios/

│ ├── mqtt/

│ └── mq9/

├── templates/

│ └── report.md.j2

└── config.yml

SKILL.md 是 Agent 真正读到的“场景描述”。它告诉 Agent 这个 Skill 是干什么的、有哪些 Tool 可用、什么时候该用哪个、报告应该长什么样。

关键 Tool 的设计：

cluster\_start 不引入 Docker，直接 spawn 多个 RobustMQ 进程。每个节点用独立端口和数据目录，数据目录用临时目录，cluster\_stop 时清理。这一条决策极简，单机环境跑混沌测试，Docker 反而增加复杂度。

inject\_fault 以 Chaosd（Chaos Mesh 单机版）为主，tc / kill 等系统命令为补充。Chaosd 提供 HTTP API，函数封装调用，参数对齐 Chaosd schema。

run\_client 多语言 SDK 调度的关键设计是，服务器上预装多语言运行时和版本管理工具（pyenv / gvm / rustup / sdkman / nvm），Skill 里通过版本管理工具切换，不用 Docker。单机环境足够，启动快。

push\_report 直接 git clone / commit / push 到 GitHub 公开仓库，不调 GitHub API，比 API 调用更简单可控。

### 我反问的几个点

这版方案比第一次翻译那一版成熟得多。AI 自己已经会“列选项 + 给建议”，不再被动等我拍。但我看完依然觉得几处可以收紧。

Skill 套件粒度有歧义。AI 说放一个套件下，理由是共享上下文。但如果未来要扩展 Claude Code 深度分析 Skill，它跟 chaos-test 共享上下文吗？这个边界得讲清楚，不然以后再加一个 Skill 又要回头重构。

故障注入选型留白太多。AI 给了 Chaosd 主 + tc 补，但没说什么时候该用哪个。“极简场景用 tc” 这一句太模糊，工程师看了不知道判断标准。

GitHub 凭据怎么管没说。push\_report 要写仓库，凭据放哪、怎么轮换、Skill 里怎么读到，这些是 7×24 系统最容易翻车的地方。

把这三条直接抛给 Claude Code：

你这版有几处可以再收紧：

1\. Skill 套件粒度：这次放一个套件下没问题，但未来加 Claude Code 深度

分析 Skill 时，边界怎么划？给个原则。

2\. 故障注入 Chaosd vs tc 的选择标准模糊。给个判断：什么场景用哪个。

3\. GitHub 凭据怎么管？Deploy Key 还是 PAT？放哪？Skill 里怎么读？

补这三条，别又冒新决策。把这版收紧。

提示词最后那句“别又冒新决策，把这版收紧”很关键。第一次翻译的两轮都在展开，每一轮都让 AI 列新选项。但第二次翻译已经到方案阶段，不能再发散，只能收敛。如果不点这句，AI 又会一边补、一边给你冒新决策点，方案永远定不下来。

### AI 把方案收紧了

Claude Code 跑完，三条全接住，而且没冒新决策。

Skill 边界原则：一个 Skill 套件等于一个独立的工作流。chaos-test 是“跑混沌测试”这个工作流；未来 Claude Code 深度分析是“分析失败报告”这个独立工作流，两者通过共享报告仓库联动，但 Skill 内部隔离，不共享 tools 目录。这一条让未来扩展有了明确的切线。

故障注入选型标准：Chaosd 用于所有需要精确控制的故障（进程级 kill 信号、网络精确延迟分布、磁盘 I/O 限速、时钟穿越）；tc / kill 用于极简快验证场景，临时拉起验证一下逻辑就行。判断标准是“故障是否需要被精确测量和回放”，需要就用 Chaosd，只是验证可达性就用系统命令。

GitHub 凭据：用 Deploy Key，只授写权限到 test-reports 单一仓库。私钥放在服务器 ~/.ssh/test-reports-deploy，Skill 里通过 GIT\_SSH\_COMMAND 环境变量指定使用这个 key 做 git push，不进 Hermes 的.env，也不进版本库。这一条接住了 24 讲那条硬规则：7×24 无人值守最容易翻车的就是凭据和 allowlist。

这一轮收得很紧，没冒新决策，该补的全补上。

### 完整方案文档成型了

最后一步，让 Claude Code 把所有讨论整合成一份和设计文档对称的完整技术方案文档。提示词显式列出：对照表 + 7 个 Tool 实现要点 + 场景库分级 + 触发机制 + GitHub 凭据 + 关键决策。不点这些 AI 会漏，因为它默认从最近对话回忆，而不是把整个反问链路重新组织。跑出来的文档里最值钱的是这几个东西。

Skill 套件目录结构：8 行树形结构。看着简单，但每一行都对应一条决策：tools/ 多个文件而不是一个，scenarios/ 按协议分目录，templates/ 用 Jinja2，config.yml 和 SKILL.md 分开。每条都有理由，不是随便排的。

关键决策记录：8 条，每条带选定方案和理由。

这张表是后面所有开发的硬约束。cluster\_start 怎么实现来自“单机 + 不用 Docker”；run\_client 怎么实现来自“本地版本管理”；push\_report 怎么实现来自“git push 用 Deploy Key”。

实施步骤按依赖顺序拆，先环境准备，再搭 Skill 骨架，然后按 Tool 依赖顺序实现（cluster → observability → run\_client → inject\_fault → push\_report），再写场景库，最后跑通完整闭环和报告系统。每一步产出都能独立验证，卡在哪一步立刻能定位。

到这里，第二次翻译做完了。手上拿着的不再是“在 Hermes 上做一个混沌测试系统”这种模糊方向，是一份可以分配给具体工程师按依赖顺序开干的方案。

## 拿到这两份文档之后

走完两次翻译，我手上有两份真实的文档。一份是完整设计文档，讲清楚为什么做、做什么、按什么思路。一份是完整方案文档，讲清楚怎么具体落到 Hermes 上。

这两份文档之间有一条清晰的因果链。设计文档里“协议兼容性是核心命题”直接决定了方案文档里 run\_client Tool 的多语言矩阵设计。设计文档里“测试记录完全公开建立社区信任”直接决定了方案文档里 push\_report 提交到 GitHub 公开仓库 + Quality Dashboard 静态读取的设计。设计文档里“P0 / P1 / P2 场景分级”直接决定了方案文档里 cron.yml 那 4 条不同频率的触发配置。

这条因果链是这两份文档真正的价值。不是文档本身有多漂亮，而是后续每一行代码、每一个配置、每一个判断，都能追溯到上游某条需求决策。开发过程中如果有人问“为什么 run\_client 要支持 SDK 版本切换”，答案不是“我觉得这样好”，是“因为设计文档里的协议兼容性目标这么定的”。如果某天需要改协议兼容性策略，你也能立刻知道下游有哪些 Tool 会受影响。

接下来开发的时候，这两份文档就是单一事实源。不是开发完成后再补的文档，是开发过程中的硬约束。任何代码偏离了文档的决定，要么改代码，要么改文档，然后回来重新对齐。

## 小结

这一讲教的就是接到一句话需求那一阵子该做什么。一句话需求很危险，因为它藏的事比说的多。

接到这种需求，第一件事是把它翻译两次。

第一次翻译是从一句话到完整设计文档，让 AI 帮你穷举该拍的事，你来拍方向。产物和技术栈无关，讲清楚为什么做、做什么、不做什么、按什么思路。

第二次翻译才把完整设计落到具体技术栈上，跑出一份能开干的方案文档。产出 Skill 设计、Tool 实现、场景库、触发配置这些可以动手的东西。

第二次翻译有个容易被忽视的环节：先反问“路径选对了吗”。第一次翻译产物里的执行路径，可能是 AI 顺着你的提问随手给的，不是认真比较过的最优路径。这一步反问，就是把 24 讲建立的工具认知拿出来用，你刚摸过的那个开源项目，可能已经把方案里 80% 的工程都做了，你不用自己撸。

每次翻译都不是 AI 一次性出方案，而是反问到 AI 收敛为止。AI 的价值是穷举该拍的事，你的价值是拍方向。提示词不需要很长，预设你已经想到的，余地留给 AI 去补，几句话写得清楚就够了。

写完两份文档，第一件事其实是放下。第二天早上再看一遍，你常常会发现某个决策当时拍得太草率，趁还没动手赶紧改回来。真正动手前，留一晚给方案沉淀，这条经验比方法论本身值钱。

所以接到需求当天就开始写代码的人，没一个交付得好。理由不是“先写文档显得专业”，而是写文档的过程本身就是把需求里所有藏着的事拍清楚的过程。不拍清楚就动手，等于把代码当成需求的探索工具，代价是改代码远比改文档贵。

## 思考题

回想你最近一次接到一句话需求的经历，比如做个监控系统、加个权限模块、接个支付通道。如果用这一讲的“两次翻译”打法重做一遍，你的第二次翻译里那个“路径选对了吗”的反问，会反问什么？有没有一个你已经摸过、但当时没想到要用上的工具？
