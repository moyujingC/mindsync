你好，我是张嘉熙。

随着这门课程正式画上句号，我终于可以松一口气，告别那些想方设法挤时间更新的日子。现在，我终于可以安安静静地坐下来，和大家聊聊我的一些心里话。

作为一名身处 AI 时代的软件工程师，我太理解大家眼下的焦虑了。坦白讲，在过去的几年里，我也焦虑过无数次。但有意思的是，每当我去体验最新最强的 LLM，每当我尝试将 Agent 真正塞进企业严苛的生产环境中时，层出不穷的现实问题总能让我瞬间冷静下来。

## 软灵魂，需要硬骨骼

在真实世界里，我们绝不可能把企业核心资产的控制权，完全赌在纯文本概率采样的随机输出上。我们需要用软件工程的硬骨骼，去约束 LLM 这颗多变的软灵魂。

但不可否认，随着大模型理解复杂指令和自主拆解任务的能力越来越恐怖，“工程硬编码”与“模型自主性”的边界正在发生微妙的位移。这逼着我们重新审视整个技术栈的未来：如果模型无限变强，未来还需要专门的 Agent 框架吗？会不会有一天，像 Embabel 这样的框架真的会变得多余？

LangChain 创始人 Harrison Chase 在今年的一次访谈中说：“框架才是未来，模型终将走向商品化。” 他的逻辑很朴素——模型会越来越聪明，但再聪明的模型也需要一个可靠的“外壳”，让它看清边界在哪、能调什么工具、怎样才算完工。这不是在限制模型，而是让模型澎湃的力量落在可控的通路上。

你发现了吗？框架存在的真正价值，不是把模型束缚得更紧，而是在该放手时让它肆意发挥，在不该用时果断收权。

需要 LLM 做语义理解或决策的地方，让它充分施展；而像 GOAP 规划、类型检查、权限校验这些不需要 LLM 介入的硬性环节，就老老实实交给确定性工程。这条清晰的权责线，正是 Embabel 真正想画出的工程边界。

## 70 年前的工程控制论

有意思的是，这种“工程控制”的思想，早在 70 年前就有人系统性地研究过。

1954 年，钱学森被软禁在美国，被迫放弃火箭研究的他，写下了一部巨著——《工程控制论》。他当时只想回答一个问题：如何让火箭、卫星这些由无数不确定零部件构成的复杂系统，变得稳定、可控、可预测？

钱老在书中给出了一个醍醐灌顶的洞察：系统的可靠性，并不取决于零部件是否完美，而是取决于整个控制架构的设计。

如果我们把随时可能幻觉、失控的 LLM 视作那个“不完美的零部件”，那么整个系统的确定性，就必须依靠一套精密的外部反馈回路来锚定。历史在这一刻完成了闭环——70 年前钱老用来驯服火箭的控制思想，恰恰成为了今天我们降服大模型幻觉的终极武器。

顺着这条控制论的脉络，到了 2026 年的今天，AI 落地最前沿不可避免地衍生出了两个新词：Harness Engineering 与 Loop Engineering。

这些概念听起来玄学，本质无非是用系统设计去“搭台子”和“建闭环”。通过定边界、给工具、自纠错，硬生生把 AI 从一个“只会聊天的抽象工具”，驯化成一个“能自主干活、自动纠错的靠谱员工”。

## 人类往哪儿站？

可如果控制架构把台子搭好了，闭环也跑通了，人又该往哪站？Andrej Karpathy 今年在一场访谈里说了一句直击本质的话：“你可以外包你的思考，但不能外包你的理解。”

他坦言，自己现在天天跟 Agent 打交道，却发现系统真正的瓶颈不再是 AI 那头，而是人类自己这头。当执行和纠错都被工程闭环彻底接管，你必须更清晰地想明白：究竟要做什么？为什么值得做？怎么高屋建瓴地去指挥？

在高度自动化控制的 Agent 时代，人类指挥 AI 的能力上限，最终取决于你对业务 & 技术理解的深度。

AI 可以做越来越多的事，但它永远无法替代你对业务逻辑的洞察、对系统可靠性的信仰、对工程结构的精准判断。这些理解不可能速成，它需要时间的沉淀，需要你亲手踩过一个个坑，需要你完整经历过一个系统从“跑得通”到“敢上线”的全过程。

这就是我们这些 Java 老兵在 AI 时代的护城河，而 Embabel，就是我们指挥 Agent 的最佳武器。

## 带走年轻的思想

客观来讲，Embabel 目前还是一个很年轻的框架。它用户还不够多，文档还在完善，目前还没推出 1.0 版本。跟 CrewAI、LangGraph 这些成名已久的成熟框架相比，它就像个刚出生的孩子。

听到这里，你可能会想：花时间学它，是不是有点傻？

我的答案是：恰恰相反。

正因为它足够年轻，它敢于成为世界上最好的 Agent 框架。在它身上，你能直观地看到设计者最原始的工程思考——为什么要死磕强类型？为什么创新性地默认用 GOAP 规划而不是放任 LLM 思考？

在这门课里，你学的其实不是这个框架本身，而是一种对抗不确定性的思维方式：当 AI 靠不住的时候，你靠什么让系统变可靠？

这是未来十年，每一个做 AI 工程化落地的人都必须面对的核心命题。无论你将来换用什么流行框架，这种“确定性工程”的能力和思想你都可以带走。

## 换个战场，继续冲锋

所以，如果你也是那个在 AI 浪潮中感到惶惑的开发者，我想坚定地对你说：你的看家本领没有贬值，你只是换了一个战场。AI Agent 要想真正跨过门槛进入生产环境，必须经过我们最熟悉的这道工程关。

如果你愿意跟着我迈出下一步，我有一个很小的建议：请把课程最后的保险 Agent 案例丢掉，换成你目前业务中的一个真实场景。不需要设计得多复杂，哪怕只是一个工单的自动化分类，或者一个垂直领域的 SQL 查询助手。当你发现框架还是那个框架，但面对的问题变成了你自己的“屎山代码”和业务痛点时，你对“工程化”的理解瞬间就会深一层。

这门课程虽然结束了，但我会一直在评论区等你。

如果你把案例成功改造成了自己的业务场景，欢迎回来分享你的喜悦；如果你在落地时踩到了意料之外的新坑，也欢迎回来狠狠吐槽。

这条 AI 工程化的路，我们谁都不是孤军奋战。

课程结束，工程开始。各位，路上见！
