## 1. 本轮问题与边界

本轮只回答一个问题：现有课程中，哪些方法能够成为曼陀罗解读产品重构的设计输入？

不做：

- 不逐章复述或制作泛读笔记。
- 不把课程中使用的 Java、Go、Spring、Embabel、Claude Code 等具体工具直接定为本项目技术栈。
- 不提前决定 To C / To B 的功能清单、数据模型、部署方式或排期。
- 不把课程观点写成疗愈专业结论、合规结论或已验证的用户需求。

后续方案必须逐条标注采用、降级采用或不采用本文件的哪张输入卡；未被本文件覆盖的设计仍可提出，但要另标明来源或本轮决策依据。

## 3. 设计输入卡

### I-01：先定问题、范围和验收，避免 AI 把空白处擅自补满

**课程提炼。** 在开始开发前，要先定义用户、核心问题、做什么、不做什么、部署/运维预期和验收标准。范围可以分为“必须做、降级简化、暂不做”，不宜只写做与不做两档。[S1][S2]

**对本项目的输入。** 后续不能以“重做曼陀罗智能体”作为规格标题下唯一的需求。至少要拆成：共用解读引擎、To C 自我觉察体验、To B 疗愈师个案工作台，并分别写出本期不做的能力。

**不能直接推出。** 课程没有证明疗愈师真正需要哪些页面、报告形式或付费方式；这些必须通过访谈和试点确认。

**第二阶段待定。** 三份 spec 是否共享一个主规格；各自的最小闭环、非目标和放行条件是什么。

### I-02：先建业务对象与状态，再让 Agent 参与工作流

**课程提炼。** 复杂业务中，业务对象不应只是散落的文本或键值对。对象、关系、允许的状态变化和业务规则构成 Agent 理解及调用系统的共同契约；模型输入和输出也应有可校验的结构。[S3]

**对本项目的输入。** 后续架构必须先讨论共同对象，而不是先讨论页面：`来访者 / 疗愈师 / 个案 / 画作 / 议题 / 解读草稿 / 审核意见 / 已确认报告 / 会谈记录 / 反馈`。To C 只接触自己的画作和报告；To B 才拥有个案、审核和交付动作。

**不能直接推出。** 不等于必须采用 Java 或某个领域驱动设计框架；Python 的数据模型、数据库约束和 API Schema 也可以实现同样的契约。

**第二阶段待定。** 对象清单、对象归属、状态机、哪些对象可被模型读取、哪些只能由人修改。

### I-03：先规范输入；不确定时提问，不应直接解释

**课程提炼。** 自然语言输入经常省略对象、时间、意图和判断标准。Agent 应先将输入转为结构化任务，识别缺失或歧义，再通过澄清问题补齐，而不是把猜测当成事实。[S4]

**对本项目的输入。** 共用解读引擎的首步应包括输入检查：画作是否可用、三圈标记是否可靠、用户/疗愈师提供的议题是否足够、哪些内容只是一种推断。To B 场景还应产生“建议向来访者追问什么”的草稿，而不是替疗愈师下结论。

**不能直接推出。** 不代表每份输入都要经过多轮对话；一开始应先用少量必填字段和明确的“信息不足”返回，避免把入门流程做得过重。

**第二阶段待定。** 输入 Schema、澄清阈值、可继续/需补充/拒绝处理的条件，以及对两类用户的提问文案。

### I-04：个案上下文、会话与长期记录必须分开管理

**课程提炼。** 多用户或多来源并发时，不能共享一段全局对话历史；每个 Session（会话）都应有隔离的上下文。短期工作记忆、长期记忆和持久化记录也要分层，避免历史内容不加选择地进入模型。[S5]

**对本项目的输入。** To B 的每次生成和追问必须限定到 `组织/疗愈师 -> 个案 -> 本次会谈或报告版本`；To C 则限定到 `用户 -> 本次画作/报告`。历史报告不能默认进入新个案或新报告的提示词。

**不能直接推出。** 课程的 Session 示例不是隐私合规方案，不能替代数据加密、访问控制、用户同意、保留期和删除机制。

**第二阶段待定。** 隔离键、上下文装配清单、可跨会话带入的资料、默认保留期、删除与导出流程。

### I-05：知识要能追溯到来源；检索只是受控获取方式

**课程提炼。** RAG（检索增强生成）的价值在于把私有或专业知识纳入回答，并保留证据链；模型不应只凭内部记忆输出。知识条目需要考虑分块、元数据、适用范围和引用方式。[S6]

**对本项目的输入。** 现有疗愈体系知识库应继续作为受控知识源。后续解读草稿至少应能区分“画面观察”“知识依据”“模型推断”“待人工确认”，并能回链到知识包版本或来源索引。

**不能直接推出。** 不等于一期必须接向量数据库，也不等于所有疗愈材料都应直接提供给模型。先确定知识包、引用和版本协议，再决定是否需要检索基础设施。

**第二阶段待定。** 知识来源等级、运行时选择逻辑、报告内的证据呈现、无足够依据时的安全降级。

### I-06：模型能提议动作，但不能绕过业务准入

**课程提炼。** 工具“语义上选对”与“此刻被允许执行”是两件事。受控执行应区分工具可见范围、调用资格、最新状态检查、次数限制、审批和异常证据；被拒绝与已经执行后失败也要分开记录。[S7]

**对本项目的输入。** To B 的 AI 只生成 `解读草稿 / 待追问问题 / 练习建议 / 报告导出草稿`，不能自行把内容发送给来访者、修改个案事实或代表疗愈师作判断。疗愈师确认、修改、退回或拒绝，才是交付状态改变的入口。

**不能直接推出。** 初期不需要建设通用工具平台或复杂工作流引擎。这个原则首先落在少量高风险动作的状态机和审核记录上。

**第二阶段待定。** 哪些动作仅生成草稿、哪些需要疗愈师确认、是否需要二次确认、每种拒绝/失败如何留痕。

### I-07：安全是多层边界，不是一段免责声明

**课程提炼。** 生产型 Agent 的安全至少覆盖输入与输出内容校验、身份认证与动作授权，以及执行次数/成本等失控保护；任何单层机制都不足以覆盖注入、越权和循环风险。[S8][S9]

**对本项目的输入。** 共用引擎要继续维持“不做诊断、治疗承诺、财务建议或重大现实决策”的边界；To B 还要新增“角色和个案权限”边界。风险内容的处理需明确为拒绝、提示寻求专业帮助、停止生成或交由疗愈师处理，不能只依赖提示词。

**不能直接推出。** 课程例子中的高危命令拦截不能直接套用到疗愈场景；具体风险规则、危机干预边界和法务要求仍需专业人士确认。

**第二阶段待定。** 风险分类表、输入/输出安全检查、身份和个案授权、人工转介边界、最大轮次和预算限制。

### I-08：最小可观测性要从首版保留，而不是上线后猜故障

**课程提炼。** 第一版可以不引入完整的分布式追踪或复杂日志平台，但应使用结构化日志和贯穿请求的 trace ID（追踪标识），记录关键调用的模型、耗时、成功/失败和错误码；指标、健康检查和告警阈值要与实际使用场景相匹配。[S10][S11]

**对本项目的输入。** 每次解读生成、追问、审核和导出都应有一次运行记录，最小字段包括：请求 ID、个案/报告 ID 的脱敏引用、模型与提示词/知识包版本、耗时、Token/成本、质量门结果、失败类型、疗愈师修改或拒绝情况。

**不能直接推出。** 不等于首版要接 Grafana、Prometheus、OpenTelemetry 全家桶；先定义记录字段和查询目标，再按试点规模选择工具。

**第二阶段待定。** 运行记录 Schema、哪些字段可留存、谁可查看、试点阶段看哪些指标、何时升级监控基础设施。

### I-09：评测既要看最终报告，也要看每个关键子步骤

**课程提炼。** Agent 评测不应只依赖“感觉不错”。复杂任务可拆成子目标并分别验证，结合最终成功率、延迟、成本和工具调用正确性；模型、提示词或工具变化后，应与历史基线对比。测试还应覆盖单元、集成和端到端三个层次。[S12][S13]

**对本项目的输入。** 共用引擎需要一套去隐私评测集，分别检查：视觉观察是否基于画面、知识依据是否匹配、是否标出不确定性、是否触发安全边界、草稿是否方便疗愈师修改。To B 还要度量“疗愈师接受/修改/拒绝了什么”。

**不能直接推出。** 不能用一个总分替代疗愈师审阅，也不能让 LLM 自动评分成为唯一放行条件；人工 rubric 必须先定义。

**第二阶段待定。** 样本来源与脱敏规则、评分维度、通过阈值、人工复核角色、哪些改动触发回归。

### I-10：To B 的价值要在真实流程中验证，并回流为可复用能力

**课程提炼。** FDE（前向部署工程师）式交付不以“做出了一个定制功能”为终点，而以真实业务结果和现场经验能否沉淀回产品为判断。客户需要提供业务参与、真实但受控的数据和协作条件；第二个类似场景应更容易交付。[S14][S15]

**对本项目的输入。** 疗愈师工作台第一期应找少量设计伙伴，围绕单一真实流程试跑，例如“收到画作与议题 -> 会谈前形成可审核草稿 -> 疗愈师修改 -> 形成会谈材料 -> 记录反馈”。每次试点必须留下产品回流卡：哪些是某位疗愈师的个例，哪些可配置，哪些可变为通用能力。

**不能直接推出。** 不能因为服务对象是疗愈师，就宣称已经完成企业级交付；没有真实试点、使用记录和反馈时，仍只是内部原型。

**第二阶段待定。** 设计伙伴准入条件、试点流程、业务指标、反馈记录格式、产品回流判定规则和隐私授权方式。

## 4. 当前可进入方案讨论的结论

以下是本轮课程支持、可以带入第二阶段讨论的最小判断：

1. To C 与 To B 应共享受控的解读引擎、知识依据、质量门、运行记录和评测基线；不应共享身份、个案权限、审核工作流和交付界面。
2. 后续先讨论业务对象、输入/输出合同、状态与人机边界，再讨论模型、框架或页面。
3. To B 的第一版应把 AI 定位为“可编辑草稿生成者”，把疗愈师确认设为不可绕过的交付门。
4. 生产基础层的最低优先级应包含：隔离、结构化记录、质量/安全检查、评测基线和运行追踪；高级监控、复杂多 Agent、通用工作流平台暂不预设为一期必需项。
5. 任何 To B 通用能力都要通过设计伙伴试点确认，并记录是否使下一个相似个案更容易处理。

## 5. 仍缺少的输入

课程无法替代以下材料，第二阶段开始前或过程中需要单独补齐：

- 疗愈师与来访者的实际工作流、痛点和用词：需要访谈或设计伙伴试点。
- 心理健康、疗愈服务、隐私与危机情形的专业/合规边界：需要具备相应资质的专业人士审阅，不能由课程或模型代替。
- 当前 To C 代码的真实运行状态、数据存储与已上线能力：需要代码/部署核查，不能只看历史文档。
- 模型、存储、认证、异步任务和监控的具体技术选择：需要在架构阶段结合团队能力、预算、数据敏感度和试点规模决策。
