## 1. 先给结论：测试不是一个动作，而是四道不同的门

对“曼陀罗智能体”这类有模型输出、隐私风险和业务分层的产品，不能只问“有没有测试”。每次改动都要分清它要经过哪几道门：

| 质量门 | 要防住的失败 | 适合的验证方式 | 运行时机 |
| --- | --- | --- | --- |
| 代码合同 | API、权限、状态、金额、输入输出结构被改坏 | 单元测试、类型检查、契约断言 | 每次提交 / PR（合并请求） |
| 工作流 | 上传到报告、审核到交付等主路径断裂 | 集成测试、少量 Mock（模拟替身）链路 | 每次 PR；关键改动必跑 |
| 智能体质量 | 画面依据缺失、越界、Lite / Pro 混淆、知识引用错误 | 固定样例 + 明确评分规则 + 人工复核 | 相关提示词、知识、模型变更时 |
| 可交付性 | 服务没有真正启动、部署后接口不可用 | 构建、容器健康检查、部署后 smoke（冒烟检查） | 合并后、部署后、定时 |

`测试通过` 只说明某一层通过，不能推导出产品已经安全、报告质量已经合格，或生产环境已经可用。

## 2. 课程输入卡

### T-01：先画核心链路和风险地图，再决定测什么

**课程提炼。** 测试的起点不是覆盖率百分比或“每个文件都有测试”，而是找出核心业务链路，按链路检查当前是否有兜底；随后列出缺口，并给每个缺口指定合适的测试类型。[S1][S2]

**对本项目的输入。** 第二阶段的首份 QA 基线应先列出四类分层主链：

1. To C Lite：输入 -> 生成 -> 质量门 -> 用户读取。
2. To C Pro：Lite 权益 / 升级授权 -> 深度生成 -> 可读取报告。
3. To B 新进疗愈师：材料输入 -> AI 草稿 -> 追问建议 -> 疗愈师修改。
4. To B 稳定执业疗愈师：个案材料 -> 草稿 -> 审核 -> 受控交付 / 留痕。

每条链路标出：数据边界、角色权限、外部模型调用、失败降级、不可绕过的人机门。这比追求“测试数量”更有用。

**不能直接推出。** 当前已有测试数量、通过记录或覆盖率不能证明上述四条未来链路已经覆盖；To B 尚未进入现有产品范围，必须在规格确认后重建其 QA 基线。

### T-02：纯逻辑用单元测试；真实协作用集成测试

**课程提炼。** 单元测试适合纯业务逻辑、状态流转、权限判断和边界条件；依赖数据库、HTTP、外部模型协议或多个组件协作的功能，更适合以集成测试验证。过度 Mock 会得到“假数据下全绿”，却漏掉真实协议、排序或持久化问题。[S3][S4]

**对本项目的输入。** 新解读引擎可把以下能力做成确定性单测：

- Lite / Pro 与两类疗愈师工作流的权限和状态变化。
- 输入 Schema（数据结构契约）校验、风险分类、质量门规则、知识包版本选择。
- 报告草稿不可直接交付、疗愈师确认后才可交付的状态机。

而“请求进入 API -> 读取受控知识 -> 调用替身模型 -> 写入运行记录 / 报告版本”的主链，应以集成测试覆盖。不要为每个 FastAPI 控制器（Controller）写只验证 Mock 是否被调用的测试。

**不能直接推出。** 集成测试不等同于真实模型质量测试；模型可用、返回格式正确，也不等于报告的观察依据和专业边界合格。

### T-03：用 TDD 约束实现，但先写清行为而不是让 AI 猜断言

**课程提炼。** TDD（测试驱动开发）可按 Red-Green-Refactor（先让测试失败、最小实现通过、再重构）推进。测试先给出可执行的行为边界，能防止 AI 生成“看起来完整”的错误代码；外部依赖可通过依赖注入和替身隔离。[S5]

**对本项目的输入。** 对第二阶段确认的每个高风险规则，先写行为例子再实现，例如：

```text
给定：疗愈师仅有个案 A 的访问权
当：请求读取个案 B 的草稿或报告
则：服务拒绝，且不返回 B 的任何内容。
```

或者：

```text
给定：AI 草稿没有疗愈师审核
当：尝试标记为“已交付”
则：状态变化被拒绝，并留下拒绝原因。
```

这里的测试是规格的可执行版本，不只是实现后的补丁。

**不能直接推出。** TDD 不适合把开放式报告写作压缩成逐字匹配；模型文本应使用结构、证据、越界和人工评分等可解释标准评估。

### T-04：改造已有能力前，先用 Characterization Test 锁住当前行为

**课程提炼。** Characterization Test（特征测试）记录旧系统“实际做了什么”，而不是根据想象断言“它应该做什么”。它最适合在重构前保护已有的可用行为；优先级高于为简单 CRUD（增删改查）堆单元测试。[S2]

**对本项目的输入。** 若后续重做现有 To C 解读链路，应先把仍需保留的行为固定为测试或样例基线：

- Lite 与 Pro 的访问 / 授权边界。
- 质量门不通过时不交付报告。
- 追问场景对诊断、危机、重大决策请求的拦截。
- 当前报告的最小结构与可读取性。

先锁住这些，再替换 Agent 编排、知识装配或后端模块。这样重构失败时能区分“故意改变规格”还是“无意回归”。

**不能直接推出。** 现有旧行为并非全部应保留；每条特征测试都要由后续 spec 标注为保留、修改或删除，不能让历史实现反过来决定新产品。

### T-05：智能体评测应有固定样例、可执行验收和人工评分

**课程提炼。** Agent 不应只靠“对话感觉还行”验收。对每个评测样例，要有受控输入、可复现运行、机器可检查的验证项和可比较的结果；提示词、工具或模型变更后与历史基线对比。[S6]

**对本项目的输入。** 现有 `model-evals/` 已保存样例、阶段输出、质量门和报告产物；第二阶段应把它升级为共享解读引擎的评测基线：

- 使用获得授权或彻底脱敏的画作 / 个案材料；每个样例记录知识包和提示词版本。
- 机器硬门：输入完整性、引用存在、无禁止措辞、无未审核交付、Lite / Pro 层级匹配。
- 人工评分表：画面观察是否可追溯、推断是否标出不确定性、是否尊重边界、疗愈师是否便于修改。
- 失败分类：视觉依据、知识匹配、提示词 / 模板、权限 / 流程、安全门、运行稳定性。

**不能直接推出。** 课程和现有样例都不能替疗愈专业人士给出临床、危机干预或合规放行；任何“安全”评分也不是执业资格结论。

### T-06：真实模型 E2E 只跑少数主链，放在预发布或手动门

**课程提炼。** 真实模型端到端测试会消耗 Token（模型调用额度）、等待外部服务，并受非确定性影响。它应只覆盖 1-2 条高价值闭环，放在预发布、夜间或人工触发环节；日常 CI 主要跑快速、可重复的单元和集成测试。[S4]

**对本项目的输入。** 推荐分工如下：

| 触发场景 | 应运行的内容 | 不应依赖的内容 |
| --- | --- | --- |
| 每次 PR | 静态检查、单元、替身集成、知识结构检查 | 真实模型、真实用户资料、真实支付 |
| 合并后 / 夜间 | 部署后健康检查、匿名化 smoke、必要时一个固定 Lite 样例 | 大批量真实模型报告 |
| 预发布 / 人工 | 1 个 Lite + 1 个 Pro 固定样例、人工评分、成本与耗时记录 | 仅靠自动总分放行 |
| To B 设计伙伴试点 | 经过授权的个案草稿、疗愈师审核和修改记录 | 把任何个案内容自动交付给来访者 |

**不能直接推出。** 夜间 smoke 成功不代表业务数据隔离、支付、权限或真实用户体验已经验证。

### T-07：CI 先标准化本地命令，再自动化“检查 -> 测试 -> 构建”

**课程提炼。** CI（持续集成）的价值是每次变更自动执行一致的检查、测试和构建。前提是本地已有稳定、可复现的命令；Dockerfile（容器构建文件）、Makefile 或任务脚本、健康检查和环境配置模板是可交付性的基础。[S7][S8]

**对本项目的输入。** 当前 `aimandala-ci.yml` 已执行前端 lint / format / Vitest / coverage / typecheck / build，后端 Pytest，以及知识校验和知识评测。第二阶段不应推倒重写，而应将新增的测试命令分配到现有质量门：

- 共用引擎：单元、集成、评测 fixture（固定样例）。
- To C：Lite / Pro 权益、报告读取与输入失败路径。
- To B：个案隔离、草稿审核状态机、审计记录。
- 部署：健康检查、最小匿名 smoke、构建产物。

每个命令都要能在本地一条命令复现，失败输出要指出复现命令和失败类别。

**不能直接推出。** 有 workflow 文件不代表 CI 当前一直成功或 runner（自托管执行机）可用；这需要在进入实施时按提交和运行记录重新核验。

### T-08：部署验证分成“能启动”与“能完成受控业务动作”

**课程提炼。** 健康检查可以验证服务活着，但不能证明业务链路可用。部署方案应先明确环境、外部服务、配置和回滚边界；部署后还要运行与产品主路径相符的 smoke。[S8][S9]

**对本项目的输入。** To C 的 smoke 至少区分：

1. `basic`：前端可访问、后端 `/health` 正常、配置缺失时安全失败。
2. `deep`：匿名 fixture 输入可以获得通过质量门的 Lite 报告，并能按授权读回。

To B 后续至少再增加：不同疗愈师之间不能跨个案读取，以及“草稿未审核不能交付”。这些必须在隔离测试环境运行，不使用真实来访者数据。

**不能直接推出。** 这里没有授权自动发布生产；部署目标、回滚机制、密钥管理和数据保留策略仍需架构 / 运维阶段确定。

## 3. 当前资产与下一步缺口

### 已有且可复用

| 资产 | 当前事实 | 第二阶段的用法 |
| --- | --- | --- |
| 后端 Pytest | 已覆盖运行时、API、质量门、追问和回归脚本的多类单测 | 整理为“核心逻辑”和“替身集成”两类执行入口 |
| 前端 Vitest 与静态检查 | 已在 CI 中运行 lint、格式、测试、coverage、类型检查和构建 | 以 Lite / Pro 权益和报告读取为优先补 UI 行为测试 |
| 真实样例回归 | 已有 Lite / Pro 样例、质量门和人工复核待办 | 升级为共享引擎的版本化评测集，不用单一总分取代人工判断 |
| 知识质量门 | CI 已运行知识校验与知识评测 | 把知识来源 / 版本和报告引用一致性纳入评测契约 |
| CI、部署与夜间 smoke | 活跃 `aimandala-ci`、部署链与夜间 basic / deep smoke 已存在 | 新能力接入既有质量门，不新建平行“第二套 CI” |

### 需要在第二阶段补齐

1. **核心链路风险地图**：现有测试按模块较多，尚未用未来四类用户链路统一标记 P0（必须）/ P1（应有）/ P2（可延后）。
2. **显式测试分层**：当前 `tests/unit/` 中包含 API / 智能体编排性质的测试；需要按运行成本、外部依赖和断言对象明确“单元 / 替身集成 / 真实 E2E”。
3. **To B 的权限与交付测试**：现有 To C 范围无法替代个案隔离、疗愈师审核、审计日志的测试。
4. **人工评测协议**：现有样例已有评分维度与待人工复核，但还需要为两类疗愈师的“可编辑性、可追问性、工作流适配”补评分标准。
5. **覆盖率的正确使用**：CI 会生成前端 coverage，但当前不应先设一个漂亮百分比门槛；先让 P0 链路有明确兜底，再根据风险设阈值。
6. **生产验证证据**：本文件未核验当前 GitHub Actions、真实部署或夜间 smoke 的最新运行状态；实施阶段需要重新检查。

## 4. 第二阶段可采用的最小测试策略

在产品规格确认后，建议将每个需求条目写成下面五行，而不是只写“补测试”：

```text
用户层级：Lite / Pro / 新进疗愈师 / 稳定执业疗愈师
行为：谁在什么前提下可以做什么，系统返回或改变什么状态
风险：越权、越界表达、错误交付、成本失控、数据泄露等
验证：单元 / 替身集成 / 评测 / 真实 E2E / smoke 中的哪一种或哪几种
放行：自动硬门、人工复核、预发布或设计伙伴确认分别是什么
```

这样测试不再是开发结束时的“补作业”，而是需求本身的一部分。
