# 心理疗愈 AI 产品观察室：AI 技术架构内容接入方案

> 日期：2026-06-06  
> 用途：给“心理疗愈 AI 产品观察室”后续内容开发使用。  
> 边界：这是公开网站可展示的内容框架，不包含 Aimandala 的内部实现策略。  

## 1. 为什么要补这一层

当前观察室已经能回答：

- 产品面向什么用户场景
- AI 在体验中扮演什么角色
- 用户为什么会使用
- 风险边界在哪里
- 商业模式是否成立

但对 AI 产品创业来说，这还不够。两个产品在界面上都像“AI 陪你聊天”，底层实现难度可能完全不同。

例如：

- 一个可能只是通用 LLM（大语言模型）加一段 prompt（提示词）。
- 一个可能有长期记忆、风险识别、知识库检索、语音实时流和人工转介。
- 一个可能是嵌在临床机构工作流里的 AI 文档系统，用户并不会直接把它体验成聊天产品。

所以观察室需要新增一层：

**AI 技术架构拆解。**

它回答的问题从“用户看见了什么”继续往下走：

**这个体验可能由哪些 AI 与工程模块支撑，哪些部分是真正有实现门槛的，哪些说法还需要继续核验。**

## 3. 技术信息证据等级

心理健康相关 AI 产品很容易出现技术营销词，例如 foundation model、agent、RAG、fine-tuning、clinical-grade AI。观察室不能把这些词直接当事实使用。

后续技术拆解统一使用 5 个证据等级：

| 等级 | 名称 | 使用条件 | 公开写法 |
| --- | --- | --- | --- |
| A | 官方确认 | 官网、技术博客、论文、帮助文档、公开合作方资料明确写出 | “官方披露……” |
| B | 可信公开来源 | 媒体采访、公开报道、招聘 JD、App Store 描述多源一致 | “公开资料显示……” |
| C | 功能推断 | 产品功能强烈暗示某类架构，但没有明确技术栈 | “从体验上推测，可能需要……” |
| D | 行业通用实现 | 不是该产品事实，只是同类产品常见做法 | “同类产品通常会……” |
| E | 待核验 | 来源单一、营销化强、无法交叉验证 | 不作为公开事实引用 |

公开网站建议只使用 A / B / C。

D 可以放在“技术学习卡”里，但必须说清楚这是通用实现路径，不是某个产品的真实技术栈。

E 只保留在内部研究线索里，不放到公开页面的结论区。

## 4. AI 技术架构 8 维

### 4.1 输入 / 输出模态

要看产品处理什么输入，以及产出什么结果。

常见输入：

- 文字
- 语音
- 图片
- 问卷 / 量表
- 日记
- 临床会话录音
- 行为数据

常见输出：

- 对话回复
- 语音回复
- 日记追问
- 报告
- 行动计划
- 临床记录
- 风险提醒
- 结构化数据

技术判断点：

- 纯文字产品的实现门槛相对低。
- 语音产品会增加 ASR（语音识别）、TTS（语音合成）、打断检测、延迟控制。
- 图片 / 报告解读产品需要处理“证据和解释是否对应”。
- 临床会话产品需要处理转写质量、合规审计和 EHR（电子健康记录系统）集成。

### 4.2 模型策略

要看产品到底依赖哪类模型能力。

可观察问题：

- 是通用 LLM 封装，还是垂直模型？
- 是否声称有 foundation model（基础模型）？
- 是否有 fine-tuning（微调）或专门训练？
- 是否多模型协同？
- 是否有风险分类模型、摘要模型、主回复模型、审查模型等分层？

公开写法要克制：

- 没有官方证据时，不写“它使用 GPT-4o / Claude / Llama”。
- 可以写“这类体验通常需要具备情绪语气控制、长上下文和安全分类能力的模型层”。

### 4.3 上下文与记忆

心理产品里的记忆不是越多越好。

要看：

- 只记当前会话，还是跨会话长期记忆？
- 记忆是用户可见、可编辑、可删除的吗？
- 记忆保存的是原文、摘要、标签、向量，还是结构化画像？
- 记忆是否用于个性化推荐或模型训练？

公开判断：

> 心理类产品的长期记忆必须可控、可解释、可删除。否则它可能从“个性化”滑向“黑箱化心理画像”。

### 4.4 知识与 RAG

RAG 是 Retrieval-Augmented Generation（检索增强生成），简单说就是：

> 模型回答前，先从知识库或用户资料里检索相关内容，再生成回答。

要看：

- 是否有心理学知识库、教练知识库、课程库或临床知识库？
- 检索的是通用专业内容，还是用户自己的历史内容？
- 输出是否能回到来源？
- 知识库是否由专业人士审核？

公开判断：

> 对心理产品来说，RAG 的价值不只是“回答更准”，更重要的是让 AI 的解释有证据、有边界、可追溯。

### 4.5 编排与工作流

要看 AI 是自由聊天，还是被放进稳定流程里。

典型链路：

```text
用户输入
  -> 意图 / 风险分类
  -> 上下文检索
  -> 主回复生成
  -> 安全审查
  -> 输出 / 转介 / 记录
```

要问：

- 是否先分类，再生成？
- 是否根据风险等级切换回应策略？
- 是否有状态机或 agent（智能体）编排？
- 是否把对话拆成倾听、澄清、总结、建议、转介等阶段？

公开判断：

> 在心理产品里，工作流编排往往比模型本身更重要。强模型自由发挥，不如普通模型在稳定边界内工作。

### 4.6 安全护栏

安全护栏不是页脚免责声明。

要看：

- 是否识别自伤、他伤、急性危机、未成年人、医疗诊断等高风险场景？
- 风险识别发生在输入前、生成中，还是输出后？
- 是规则、分类模型、LLM judge（大模型评审）、多模型复核，还是人工介入？
- 触发风险后产品做什么：拒答、降级、转介、提示紧急资源，还是继续对话？
- 是否保留审计日志？

公开判断：

> 心理类 AI 的安全性，不在于它能不能说温柔的话，而在于高风险输入出现时，它是否稳定地少做事、做对事。

### 4.7 数据、安全与合规

要看：

- 数据是否加密？
- 用户能否导出、删除自己的数据？
- 产品是否说明数据是否用于训练？
- 是否涉及 HIPAA、SOC2、GDPR、PIPEDA 等合规声明？
- 企业场景下，个人数据和组织数据如何隔离？
- 临床场景下，AI 生成内容如何被治疗师审核？

公开写法：

> 官方称其符合某某标准；观察室未做独立合规审计。

不要替产品做合规背书。

### 4.8 评估与可观测性

要看产品如何知道 AI 做得好不好。

普通 AI 产品可能只看用户满意度，但心理产品还要看：

- 是否过度建议
- 是否误判危机
- 是否制造依赖
- 是否给出错误心理解释
- 是否在高风险场景稳定转介
- 是否有人工抽检、红队测试、用户反馈闭环或临床评估

公开判断：

> 心理类 AI 不能只优化“用户觉得被理解”。它还必须评估边界是否稳定、风险是否被识别、解释是否过度。

## 5. 四类技术架构原型

### 5.1 聊天陪伴型

代表样本：

- Ash
- Pi
- Sonia
- Noah

典型链路：

```text
文字 / 语音输入
  -> 情绪与风险识别
  -> 用户上下文检索
  -> 共情对话生成
  -> 安全审查
  -> 文本 / 语音输出
```

技术难点：

- 长期记忆
- 低延迟语音
- 情绪语气控制
- 危机检测
- 输出安全审查

主要风险：

- 用户把 AI 当治疗师。
- 长期记忆强化依赖。
- 拟人化语音提高关系强度，也提高安全责任。

### 5.2 AI 日记 / 自我探索型

代表样本：

- Rosebud
- Layers

典型链路：

```text
日记 / 语音记录
  -> 事件、情绪、想法、需求抽取
  -> 用户历史主题检索
  -> 个性化追问
  -> 周期性模式总结
  -> 用户可读洞察
```

技术难点：

- 非结构化输入抽取
- 长期主题建模
- 反思问题生成
- 周报 / 月报总结
- 记忆可见、可控、可删除

主要风险：

- 把用户过早标签化。
- 把暂时情绪写成长期人格判断。
- 用户不知道 AI 到底记住了什么。

### 5.3 AI 教练 / 行为改变型

代表样本：

- Rocky.ai
- CoachHub AIMY
- Flourish Science

典型链路：

```text
目标 / 场景输入
  -> 教练流程选择
  -> 结构化追问
  -> 行动计划生成
  -> 跟踪提醒
  -> 组织 / 教练侧反馈
```

技术难点：

- 目标状态管理
- 教练流程模板
- 角色扮演 / 模拟训练
- 企业数据隔离
- 组织层聚合报告

主要风险：

- coaching（教练）和 therapy（治疗）边界混淆。
- 企业看到不该看的个人心理数据。
- AI 生成行动建议后责任归属不清。

### 5.4 临床 / 机构工作流型

代表样本：

- Eleos Health

典型链路：

```text
临床会话 / 机构数据
  -> 转写
  -> 临床要点抽取
  -> progress note 生成
  -> 治疗师审核
  -> EHR 写入
  -> 合规审计
```

技术难点：

- ASR 转写质量
- 临床实体抽取
- 模板化文档生成
- EHR 集成
- 审计日志
- HIPAA / SOC2 等合规

主要风险：

- AI 错误进入临床记录。
- 治疗师过度依赖自动摘要。
- 机构、治疗师、AI 供应商之间责任边界不清。

### 5.5 多模态报告解读型

代表样本：

- 星云星空的部分能力
- 图片 / 测评 / 报告解读类心理产品

典型链路：

```text
图片 / 测评 / 用户叙述
  -> 多模态特征抽取
  -> 证据定位
  -> 知识库检索
  -> 报告生成
  -> 安全审查
  -> 陪读 / 追问
```

技术难点：

- 图像证据与文本解释绑定
- 知识库引用
- 报告结构化
- 不做诊断的表达边界
- 用户追问时保持证据一致

主要风险：

- AI 看图后自由发挥。
- 把单次作品解释成稳定人格。
- 报告语言过度确定，造成用户自我标签化。

## 7. 四个重点样本的公开写法草稿

### 7.1 Ash / Slingshot AI

证据等级：

- A / B / C 混合。公司对外有“心理健康研究实验室”“心理学基础模型”等叙事，但具体训练数据、模型结构和安全评估仍需继续核验。

技术架构判断：

- 更接近“聊天陪伴型 + 垂直模型叙事”。

可能实现路径：

- 文字 / 语音对话入口。
- 长上下文或长期记忆系统。
- 情绪和危机风险识别。
- 主回复生成。
- 输出安全审查。

技术风险：

- “心理学基础模型”如果缺少独立评估，容易成为营销叙事。
- 长期记忆会提高陪伴感，也会提高依赖风险。
- 如果语音交互很拟真，用户更容易把它理解成治疗关系。

待核验问题：

- 是否公开披露模型训练方式？
- 是否有临床专家参与安全评估？
- 是否说明用户数据是否用于训练？
- 危机场景下的降级策略是否可观察？

### 7.2 Rosebud

证据等级：

- B / C。官网和产品描述能确认 AI journaling、pattern discovery、reflection prompts 等体验；底层模型、向量数据库、具体 RAG 实现不应当作已证事实。

技术架构判断：

- 更接近“AI 日记 / 自我探索型”。

可能实现路径：

- 文本 / 语音日记输入。
- 情绪、事件、主题抽取。
- 历史日记主题检索。
- 个性化追问生成。
- 周期性模式总结。

技术风险：

- 长期记忆如果不可见，用户很难判断 AI 如何理解自己。
- 模式总结容易从“反思线索”滑向“人格标签”。
- 日记数据敏感度高，隐私说明必须清晰。

待核验问题：

- 用户能否查看、编辑、删除 AI 记住的内容？
- 是否说明数据是否用于模型训练？
- pattern discovery 的结果是否可追溯到具体日记片段？
- 高风险日记内容是否触发转介或危机资源提示？

### 7.3 Rocky.ai

证据等级：

- B / C。公开资料能确认它是 AI coaching platform，并覆盖企业、组织、教练和个人成长场景；“多智能体”“数字孪生”等技术说法需要逐条核验来源。

技术架构判断：

- 更接近“AI 教练 / 行为改变型 + 平台化工作流”。

可能实现路径：

- 用户目标 / 场景输入。
- 教练流程模板选择。
- 结构化追问。
- 行动计划生成。
- 进展跟踪。
- 企业或教练侧配置与白标分发。

技术风险：

- 教练场景很容易越界到心理治疗。
- 企业客户需要严格的数据隔离，否则员工不会信任。
- 白标平台如果配置权过大，可能让不同客户生成不稳定的心理支持体验。

待核验问题：

- 是否公开说明不同组织之间的数据隔离方式？
- 是否有 coaching / therapy 边界提示？
- 教练方法论是否由专业机构或教练审核？
- 组织侧能看到哪些个人数据？

### 7.4 Eleos Health

证据等级：

- A / B。Eleos Health 对外明确是面向行为健康机构的 AI system of action，公开资料中也有临床工作流、文档、质量管理、合规和系统集成相关信息。具体模型性能、客户效果数字仍需来源核验。

技术架构判断：

- 更接近“临床 / 机构工作流型”。

可能实现路径：

- 临床会话录音或机构数据输入。
- ASR 转写。
- 临床要点抽取。
- progress note 生成。
- 治疗师审核。
- EHR 写入。
- 合规审计与质量管理。

技术风险：

- AI 生成内容进入临床记录，错误成本高。
- 治疗师审核如果流于形式，责任边界会变模糊。
- EHR 集成和合规审计是商业门槛，也是实施负担。

待核验问题：

- 哪些内容由 AI 自动生成，哪些必须由治疗师确认？
- 是否公开说明 EHR 集成范围？
- 是否披露质量评估或临床安全评估方法？
- 机构客户如何审计 AI 生成记录？

## 9. 公开站点不做什么

公开观察室不要做：

1. 不公开 Aimandala 的内部实现策略。
2. 不把推断技术栈写成产品事实。
3. 不强行给每个产品画完整系统架构图。
4. 不把所有产品都解释成 RAG、Agent、微调。
5. 不替任何产品做医疗合规背书。
6. 不把“像治疗师”当成产品优点。

## 10. 最终内容口径

后续观察室对每个重点产品，应同时给出两条链路：

```text
产品体验链路：
用户场景 -> 交互入口 -> AI 角色 -> 用户价值 -> 风险边界

技术实现链路：
输入模态 -> 模型策略 -> 记忆 / 知识 -> 工作流编排 -> 安全护栏 -> 评估与合规
```

这两条链路合在一起，才是对 AI 心理疗愈产品更完整的拆解。
