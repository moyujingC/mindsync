# 心理疗愈 AI 产品观察室：AI 技术架构拆解补充

> 日期：2026-06-06  
> 背景：当前观察室主要从产品设计、用户体验、商业模式和安全边界拆解产品，但对 AI 技术架构、工程实现和可复制路径拆解不足。  
> 目标：补一套“可公开、可核验、不过度臆测”的 AI 技术架构拆解框架，并明确它如何服务 Aimandala 的内部技术判断。  

## 1. 结论

需要给观察室补一个独立的“技术架构层”。

现在的 7 维方法论是：

1. 场景
2. 关系
3. 输入
4. 干预
5. 记忆
6. 边界
7. 商业

这套框架适合看产品体验，但对 AI 产品创业来说还不够。后续每个重点产品至少还应该回答：

1. 它使用什么输入和输出模态？
2. 它像是通用 LLM 封装、垂直模型、微调模型，还是多模型工作流？
3. 它如何处理上下文、记忆和用户数据？
4. 它有没有 RAG（检索增强生成）、知识库或结构化心理学流程？
5. 它的安全护栏在哪里？是提示词、模型、规则、人工审核，还是多层系统？
6. 它与外部系统如何集成？例如 EHR、HR 系统、教练平台、App Store、语音服务。
7. 它如何评估输出质量、安全性和长期效果？

一句话：

**产品拆解回答“用户看见了什么”；技术架构拆解回答“这个体验可能是怎么被做出来的，以及哪些部分不可轻易复制”。**

## 2. 为什么必须补技术架构层

### 2.1 只看产品体验会误判壁垒

两个产品都可能表现为“AI 陪用户聊天”，但底层差异很大：

- 一个可能只是通用 LLM + 一段系统提示词。
- 一个可能有长期记忆、风险分类器、心理学知识库、语音实时流、人工转介机制。
- 一个可能是机构工作流系统，AI 只是其中一个生成模块。

如果不拆技术层，很容易把“界面相似”误判成“实现难度相似”。

### 2.2 对 Aimandala 的反哺需要技术判断

Aimandala 不只是内容产品，它涉及：

- 图像输入
- 曼陀罗知识库
- 报告生成
- 报告陪读
- avatar persona
- 安全边界
- 用户数据和隐私

所以外部产品研究不能只停在“这个体验很温柔”“这个产品边界感好”。还要问：

- 这个体验需要什么模型能力？
- 是否需要长期记忆？
- 是否需要向量知识库？
- 是否需要多模型审查？
- 哪些地方可以先用规则和流程解决，不必上复杂模型？
- 哪些能力一旦做错，会直接带来安全风险？

### 2.3 公开站点需要避免技术臆测

原始产品拆解文档里已经有不少技术架构描述，例如：

- GPT-4o / Claude / Llama
- Pinecone / Weaviate / Chroma
- RAG
- SFT / RLHF
- ASR / TTS
- 多模型路由
- 危机检测模型
- EHR 集成
- HIPAA / SOC2

但其中相当一部分是“根据功能推测”的技术栈，不一定来自官方资料。

因此公开站点必须加证据等级。

## 3. 技术信息证据等级

后续任何技术拆解都必须标注证据等级。

| 等级 | 名称 | 使用条件 | 公开表达方式 |
| --- | --- | --- | --- |
| A | 官方确认 | 官网、文档、论文、技术博客、公开访谈明确写出 | “官方披露……” |
| B | 可信公开来源 | 媒体采访、投资人文章、App Store 描述、公司招聘 JD 多源一致 | “公开资料显示……” |
| C | 功能推断 | 产品功能强烈暗示某类架构，但没有明确技术栈 | “从体验上推测，可能需要……” |
| D | 行业通用实现 | 不是该产品事实，只是同类产品常见实现路径 | “同类产品通常会……” |
| E | 待核验 | 来源单一、营销化强、无法交叉验证 | “暂不作为事实引用” |

公开观察室最多使用 A/B/C。

D 可以放在“可实现路径”或“技术学习卡”里，但不能写成产品事实。

E 只作为内部研究线索。

## 4. 技术架构拆解维度

建议在原 7 维方法之外，新增一套“AI 技术架构 8 维”。

### 4.1 输入 / 输出模态

要问：

- 输入是文字、语音、图片、视频、量表、行为数据，还是临床会话？
- 输出是文本回复、语音、报告、练习、摘要、风险提醒，还是结构化数据？
- 是否需要实时流式交互？

典型影响：

- 文字输入最简单。
- 语音输入会增加 ASR（语音识别）、TTS（语音合成）、打断检测、延迟控制。
- 图片输入会增加视觉模型、证据定位和解释一致性。
- 临床会话输入会增加转写、摘要、合规和审计。

### 4.2 模型策略

要问：

- 是通用 LLM 封装，还是垂直模型？
- 是否声称有 foundation model（基础模型）、fine-tuning（微调）、SFT（监督微调）、RLHF（基于人类反馈的强化学习）？
- 是否多模型协同？
- 是否本地模型、云端模型，还是混合架构？

公开表达建议：

- 官方确认前，不要写“使用 GPT-4o / Claude / Llama”。
- 可以写“这类体验通常需要具备情绪语气控制、长上下文和安全分类能力的模型层”。

### 4.3 上下文与记忆

要问：

- 只记当前会话，还是跨会话长期记忆？
- 记忆是用户可见、可编辑、可删除的吗？
- 记忆是摘要、标签、向量检索、结构化画像，还是原文片段？
- 记忆是否用于训练或个性化推荐？

对心理产品的关键判断：

**记忆不是越多越好。心理类产品里的记忆必须可控、可解释、可删除。**

### 4.4 知识与 RAG

RAG 是 Retrieval-Augmented Generation（检索增强生成），简单说就是：模型回答前，先从知识库或用户资料里检索相关内容，再生成回答。

要问：

- 产品是否有心理学知识库、教练知识库、课程库或临床知识库？
- 检索的是通用内容，还是用户自己的历史内容？
- 生成内容是否引用来源？
- 知识库是否经过专业审核？

对 Aimandala 的启发：

曼陀罗报告更适合“证据型 RAG”：回答要回到本次画作、用户输入和知识库条目，避免泛泛心理解释。

### 4.5 编排与工作流

要问：

- 是单轮 prompt，还是多步骤工作流？
- 是否有 agent（智能体）或状态机？
- 是否先分类，再生成，再安全审查？
- 是否把对话拆成倾听、澄清、总结、建议、转介等阶段？

典型架构：

```text
用户输入
  -> 意图 / 风险分类
  -> 上下文检索
  -> 主回复生成
  -> 安全审查
  -> 输出 / 转介 / 记录
```

对心理产品而言，编排比模型本身更重要。一个普通模型放进清晰流程里，往往比一个强模型自由发挥更安全。

### 4.6 安全护栏

要问：

- 是否有自伤、他伤、危机、未成年人、医疗诊断等风险识别？
- 风险识别在输入前、中、后哪一层发生？
- 是规则、分类模型、LLM judge、多模型复核，还是人工介入？
- 触发风险后产品做什么：拒答、降级、转介、报警、联系人工？
- 是否保留审计日志？

公开观察室应重点看：

- 安全边界有没有写在产品流程里。
- 是否只是页脚免责声明。
- 危机触发后的行为是否稳定。

### 4.7 数据、安全与合规

要问：

- 数据是否加密？
- 用户能否导出、删除自己的数据？
- 是否说明数据是否用于训练？
- 是否提到 HIPAA、SOC2、GDPR、PIPEDA 等合规？
- 企业场景下，员工个人数据和组织聚合数据如何隔离？
- 临床场景下，治疗师和机构如何审计 AI 生成内容？

公开站点不要替产品背书“合规”，除非有官方材料。

更稳的表达：

> 官方称其符合某某标准；本站未做独立合规审计。

### 4.8 评估与可观测性

要问：

- 产品如何评估回答质量？
- 如何评估安全性？
- 是否有用户反馈闭环？
- 是否有临床评估、A/B 测试、人工标注、红队测试？
- 是否公开过错误率、危机识别指标、留存数据、效果数据？

对创业者的关键点：

心理产品不能只评估“用户满意”。还要评估：

- 是否过度建议
- 是否误判危机
- 是否制造依赖
- 是否产生错误心理解释
- 是否在高风险场景下稳定转介

## 5. 四类产品的技术架构原型

### 5.1 聊天陪伴型

代表：

- Ash
- Pi
- Sonia
- Noah

典型架构：

```text
文字 / 语音输入
  -> 情绪 / 风险识别
  -> 用户上下文检索
  -> 共情对话生成
  -> 安全审查
  -> 文本 / 语音输出
```

重点技术问题：

- 低延迟语音
- 长期记忆
- 情绪语气控制
- 危机检测
- 输出安全审查

最大风险：

- 用户把它当治疗师。
- 长期记忆制造依赖。
- 语音拟真提高关系强度和安全责任。

### 5.2 AI 日记 / 自我探索型

代表：

- Rosebud
- Layers

典型架构：

```text
日记 / 语音记录
  -> 事件、情绪、想法、需求抽取
  -> 用户历史主题检索
  -> 个性化追问
  -> 周期性模式总结
  -> 用户可读洞察
```

重点技术问题：

- 非结构化输入抽取
- 长期主题建模
- 反思 prompt 生成
- 周报 / 月报总结
- 用户记忆可控性

最大风险：

- 把用户过早标签化。
- 记忆黑箱化。
- 把暂时情绪总结成长期人格判断。

### 5.3 AI 教练 / 行为改变型

代表：

- Rocky.ai
- CoachHub AIMY
- Flourish Science

典型架构：

```text
目标 / 场景输入
  -> 教练框架选择
  -> 对话式追问
  -> 行动计划生成
  -> 跟踪提醒
  -> 组织 / 教练侧反馈
```

重点技术问题：

- 目标状态管理
- 教练流程模板
- 角色扮演 / 模拟训练
- 企业数据隔离
- 组织层聚合报告

最大风险：

- coaching 和 therapy 边界混淆。
- 企业看到不该看的个人心理数据。
- AI 生成行动建议但缺少责任归属。

### 5.4 临床 / 机构工作流型

代表：

- Eleos Health

典型架构：

```text
临床会话 / 机构数据
  -> 转写
  -> 临床要点抽取
  -> progress note 生成
  -> 治疗师审核
  -> EHR / 机构系统写入
  -> 合规审计
```

重点技术问题：

- ASR 转写质量
- 临床实体抽取
- 模板化文档生成
- EHR 集成
- 审计日志
- HIPAA / SOC2 等合规

最大风险：

- AI 错误写入临床记录。
- 治疗师过度依赖自动摘要。
- 责任边界不清。

### 5.5 多模态报告解读型

代表：

- Aimandala 未来相关能力
- 星云星空部分能力
- 其他图像 / 测评 / 报告解读产品

典型架构：

```text
图片 / 测评 / 用户叙述
  -> 多模态特征抽取
  -> 证据定位
  -> 知识库检索
  -> 报告生成
  -> 安全审查
  -> 陪读 / 追问
```

重点技术问题：

- 图像证据与文本解释绑定
- 知识库引用
- 报告结构化
- 不做诊断的表达边界
- 用户追问时保持证据一致

对 Aimandala 的直接启发：

Aimandala 不应只做“AI 看图说话”，而应形成：

```text
图像证据
  -> 知识解释
  -> 用户议题
  -> 安全边界
  -> 陪读追问
```

## 8. 对 Aimandala 的技术反哺

技术层反哺应聚焦几个问题。

### 8.1 图像证据绑定

外部报告解读型产品容易泛化。Aimandala 应要求：

- 每个重要解释尽量回到图像证据。
- 区分“画面观察”和“心理解释”。
- 不把单张图解释成稳定人格或临床判断。

### 8.2 知识库与 RAG

Aimandala 更适合先做知识库增强，微调模型可以放到后续阶段再判断。

优先级：

1. 结构化曼陀罗知识库
2. 检索引用
3. 报告模板
4. 安全表达规则
5. 再考虑微调或专门模型

### 8.3 Avatar persona

Persona 应由产品层控制，不应完全交给模型自由发挥。

建议：

- 固定角色边界：报告陪读者，不是治疗师。
- 固定语气规则：温柔、克制、回到证据。
- 固定拒答边界：诊断、治疗、危机干预、重大人生决策。

### 8.4 安全护栏

Aimandala 至少需要三层安全：

1. 输入风险识别  
   用户是否表达自伤、他伤、精神病性症状、重大危机。

2. 生成前约束  
   限制模型输出诊断、确定性结论和过度建议。

3. 输出后审查  
   检查是否出现医疗化表达、恐吓式解释、过度人格化判断。

### 8.5 评估体系

不能只看报告是否“好看”。

至少评估：

- 是否回到图像证据
- 是否区分观察和推测
- 是否避免诊断化
- 是否有温度但不制造依赖
- 是否给出低风险、可行动的反思问题
- 是否在危机场景下稳定转介

## 10. 不做范围

这次补技术架构时，不做：

1. 不把所有推测写成事实。
2. 不强行给每个产品画完整系统架构图。
3. 不公开 Aimandala 的内部实现细节。
4. 不做“技术栈炫技”。
5. 不把心理产品简化成 RAG、Agent、微调这几个流行词。
6. 不在没有证据时写具体供应商，例如 GPT-4o、Pinecone、ElevenLabs。

## 11. 最终口径
