这份文档定义 `AI 岗位 JD 与企业 AI 转型需求研究` 的第一版标注框架与样本选择规则。

目标不是先做一个复杂数据库，而是先用统一字段把 JD（Job Description，职位描述）稳定转成可研究、可比较、可复盘的结构化样本。

## 1. 目标

第一版只解决三件事：

1. 让每条 JD 都能按同一套字段被记录。
2. 让后续分析可以围绕“企业问题”和“组织需求”展开，而不是只围绕岗位名称。
3. 让求职、内容、咨询和产品反哺共用同一份上游样本。

当前不解决：

- 自动化抓取
- 大规模爬取
- 完整 BI（Business Intelligence，商业分析）看板
- 复杂标签系统

## 2. 使用范围

当前适用于：

- 招聘平台上的 AI 相关岗位 JD
- 企业官网岗位页面
- 招聘海报或岗位长图中的职位说明
- 可转写为结构化文本的招聘内容

当前优先覆盖的岗位类型：

- AI 转型咨询
- AI 产品经理
- AI 解决方案 / 行业解决方案
- AI 项目负责人 / AI 业务负责人
- AI 独立开发 / AI 应用开发
- AI 运营 / AI 增长 / AI 赋能培训

## 3. 设计原则

### 3.1 先标“企业要解决的问题”，再标“岗位叫什么”

岗位名称常常不稳定，甚至带有明显热点包装。

因此第一判断层不是：

- 这是 AI 产品经理

而是：

- 企业想借这个岗位解决什么问题

### 3.2 JD 是组织需求文本，不是标准人才画像

JD 往往混合了：

- 真实需求
- 模糊期待
- 内部认知不足
- 招聘模板复用
- 对热点概念的拼接

这些混乱本身就是研究信号，不能在标注时被抹平。

### 3.3 先保留判断过程，再追求精细分类

第一版更重要的是：

- 字段一致
- 判断可解释
- 样本可回看

而不是一开始就做出过细、过满的标签树。

## 4. 单条 JD 的最小字段

每条 JD 至少记录以下字段。

### 4.1 样本基础信息

- `sample_id`
  - 建议格式：`JD-YYYYMMDD-序号`
- `captured_at`
  - 记录采集日期
- `source_platform`
  - 例如：Boss、猎聘、脉脉、企业官网、公众号
- `source_link`
  - 若无公开链接，说明来源形式
- `raw_title`
  - 原始岗位名称
- `company_name`
- `industry`
  - 若不明确，可先写“待判断”
- `city_or_region`
- `salary_range`
  - 写原文，不强制换算
- `employment_type`
  - 全职 / 兼职 / 顾问 / 项目制 / 实习 / 待判断

### 4.2 企业背景与组织语境

- `company_stage`
  - 初创早期 / 成长期 / 成熟期 / 大公司新业务 / 待判断
- `business_context`
  - 公司当前在做什么，JD 所属业务线是什么
- `reporting_line`
  - 向谁汇报；若没写，标“未披露”
- `team_context`
  - 是否能看出已有 AI 团队、产品团队、业务团队或培训团队

### 4.3 需求问题定义

- `primary_problem`
  - 这家公司最想解决的主问题，只写一个
- `secondary_problems`
  - 次要问题，可写 `1-3` 个
- `problem_category`
  - 效率提效 / 产品创新 / 方案售前 / 行业交付 / 组织赋能 / 增长获客 / 培训教育 / 战略试探 / 其他
- `demand_maturity`
  - 认知试探期 / 局部提效期 / 业务嵌入期 / 组织改造期 / 待判断

### 4.4 岗位任务包

- `responsibility_summary`
  - 用 `3-5` 句概括真实任务包
- `responsibility_modules`
  - 可多选：
  - 需求调研
  - AI 工具选型
  - 流程改造
  - 产品设计
  - 原型验证
  - 项目推进
  - 客户沟通
  - 方案撰写
  - 培训赋能
  - 内容输出
  - 数据分析
  - 增长运营
  - 商业化探索

### 4.5 能力结构

- `core_capabilities`
  - JD 明确要求的核心能力
- `mixed_capability_signals`
  - 观察这条 JD 混合了哪些本应分开的能力，例如：
  - 产品 + 咨询
  - 方案 + 销售
  - 培训 + 运营
  - 项目管理 + 开发
- `technical_depth_required`
  - 高 / 中 / 低 / 模糊
- `business_depth_required`
  - 高 / 中 / 低 / 模糊
- `communication_weight`
  - 高 / 中 / 低 / 模糊

### 4.6 交付预期

- `deliverable_signals`
  - 这家公司希望这个岗位最终交什么
- `success_metric_signals`
  - JD 中若出现结果导向表述，记录下来
- `time_horizon`
  - 短期试水 / 中期落地 / 长期能力建设 / 模糊

### 4.7 风险与认知信号

- `ai_cognition_level`
  - 清晰 / 一般 / 模糊 / 明显混乱
- `risk_signals`
  - 常见风险包括：
  - 职责过载
  - AI 理解停留在概念层
  - 把单人岗位当组织改造替代品
  - 技术与业务预期脱节
  - 想要“全能型 AI 人”
- `confidence_level`
  - 这份标注的判断把握：高 / 中 / 低
- `notes`
  - 记录不确定点和后续补充线索

### 4.8 下游转译字段

- `jobhunt_relevance`
  - 对当前求职是否高相关：高 / 中 / 低
- `content_value`
  - 是否值得转成内容选题：高 / 中 / 低
- `consulting_value`
  - 是否值得转成咨询切口：高 / 中 / 低
- `product_feedback_value`
  - 是否值得反哺产品判断：高 / 中 / 低

## 5. 第一版标准枚举解释

### 5.1 `demand_maturity` 判定

- `认知试探期`
  - 关键词通常是：探索、关注、研究、尝试、跟踪趋势
  - 说明企业还没形成稳定落地路径
- `局部提效期`
  - 已开始把 AI 用于单点流程、部门效率或某个具体岗位
- `业务嵌入期`
  - 已要求岗位推动产品、交付或业务环节里的 AI 应用
- `组织改造期`
  - 已出现跨部门、流程重塑、培训体系、组织协同等信号

### 5.2 `ai_cognition_level` 判定

- `清晰`
  - 能看出明确问题、明确职责和较合理的交付预期
- `一般`
  - 有方向，但仍有部分概念混杂
- `模糊`
  - 目标、角色和结果不够清楚
- `明显混乱`
  - 职责堆叠严重，几乎看不出真实岗位边界

## 6. 样本选择规则

### 6.1 首批样本量

第一轮建议收 `20-30` 条。

数量目的不是统计显著性，而是先跑出：

- 字段是否够用
- 标签是否顺手
- 需求模式是否开始浮现

### 6.2 行业分布

首批样本尽量覆盖：

- 软件 / SaaS（软件即服务）
- 教育 / 培训
- 电商 / 消费
- 企业服务
- 制造 / 传统行业数字化
- 医疗 / 金融等强行业场景

如果短期收不到完整行业覆盖，可以先保证至少 `4` 类行业。

### 6.3 公司阶段分布

首批样本尽量覆盖：

- 初创公司
- 成长期公司
- 大公司新业务

不要全部来自一种公司类型，否则很容易把单一组织阶段误当成市场共性。

### 6.4 岗位类型分布

首批样本不要只收“AI 产品经理”。

至少覆盖：

- 咨询型
- 产品型
- 方案 / 交付型
- 运营 / 培训型
- 开发 / builder（构建者）型

### 6.5 样本剔除规则

以下样本默认不进入首批正式分析：

- 明显重复发布、内容完全一致的 JD
- 只有职位名，没有职责正文
- 明显中介转发且缺少原始岗位信息
- 无法确认是否真的和 AI 相关的泛岗位

### 6.6 保留规则

即使 JD 写得很差，也不意味着没有价值。

以下样本反而应优先保留：

- 职责混杂严重
- 要求极不合理
- AI 概念使用明显错位
- 把多岗位任务压成一个岗位

因为这些内容对研究“企业 AI 认知阶段”很有价值。

## 7. 标注流程

每条样本按下面顺序处理：

1. 保存原文或截图依据。
2. 填基础信息，不做解释。
3. 提炼企业主问题和岗位任务包。
4. 判断需求阶段与 AI 认知水平。
5. 标记混合能力和风险信号。
6. 评估对求职、内容、咨询、产品的下游价值。
7. 记录不确定点，避免强行下结论。

## 8. 第一轮输出要求

首批 `20-30` 条标注完成后，至少要产出：

1. 一份样本概览表
2. 一版需求模式初步归类
3. 一版高频风险信号清单
4. 一版内容选题池
5. 一版咨询切口候选清单

## 9. 暂不处理的扩展项

本轮先不做：

- 自动化采集脚本
- 复杂评分模型
- 可视化面板
- 多人协作审核机制
- 行业趋势结论对外发布版本

这些动作要等第一轮手工标注证明框架有效后再决定。
