这份文档定义 `墨予镜` 当前阶段如何处理 repo skill 与本机运行时 skill 的关系。

## 1. 背景

- 当前 skill 的治理源已经明确落在：
  - `/Users/xinran/Downloads/dev/mindsync/projects/research-center/skills/`
- 角色 prompt 也已经完成基础 skill 引用接入
- 但 Paperclip 面板显示的 skill，实际读取的是运行时已挂载 skill，而不是仓库里被角色引用的 skill

因此当前需要一套现实可用的处理策略。

## 2. 当前策略

### 2.1 治理源

- 统一以 repo 中的 skill 目录为 source of truth：
  - `projects/research-center/skills/<skill-slug>/`

### 2.2 运行时镜像

- Claude 本机运行时需要的 skill，通过轻量同步挂到：
  - `~/.claude/skills/`

### 2.3 当前不做的事

- 不把这件事误写成 Paperclip 已原生支持 company-managed skills runtime
- 不为了当前单人单机阶段，先改 Paperclip 内核
- 不把 `~/.claude/skills/` 当成正式治理源

## 3. 为什么采用这个方案

- 当前只有单人、单机、单开发环境
- 目标是让 skill 真正可运行，而不是先做平台级治理
- 如果现在为了挂 skill 改 Paperclip 内核，会把 `mindsync` 与 `paperclip` 两条线耦合起来
- 未来如果要支持公司级 skill 管理，更适合单独在 `paperclip` 仓库以 PR 形式推进

## 4. 使用方式

推荐使用：

- `/Users/xinran/Downloads/dev/mindsync/shared/tools/sync-local-skills.sh`

默认支持：

- `status`
  - 查看 repo skill 与本机挂载状态
- `install`
  - 将 repo skill 以软链接形式挂到 `~/.claude/skills/`
- `remove`
  - 仅移除由该脚本创建的链接，不删除 repo skill 本体
- `list`
  - 查看首批计划挂载的 skill

## 5. 边界说明

- 这个方案解决的是：
  - 本机运行时可用
- 它不等于：
  - Paperclip 面板必然立刻显示为 company-managed skill
- 如果未来要让 skill 进入 Paperclip 公司技能库，应另开任务，在 `paperclip` 仓库推进

## 6. 一句话结论

当前 `墨予镜` 的正式策略是：repo 负责治理，`~/.claude/skills/` 负责本机运行时挂载；先保证单机可用，再等待或单独推进 Paperclip 内核侧支持。
