这份文档定义 `墨予镜` 第一版 skill 协议。

它的目标不是一次性设计一套复杂运行时，而是先为后续 skill 补齐：

- 最小目录协议
- 最小元数据协议
- 通用输出约束
- 通用 handoff 约束
- 通用与角色专属的分层方式

## 1. 设计目标

`墨予镜` 的 skill 应解决的问题，不是“让角色更会说”，而是：

- 让可重复的方法变成可复用资产
- 让不同 Agent 在相同任务类型下有稳定工作方式
- 让 handoff 不再依赖临场发挥
- 让研究、产品、架构、测试、内容之间更容易形成闭环

## 2. 协议范围

本协议当前只定义：

- skill 的目录结构
- `SKILL.md` 的推荐 frontmatter
- skill 的适用场景
- skill 的输入输出约束

本协议当前不定义：

- 真实运行时 loader
- 自动权限系统
- 远程 skill 注册
- 复杂 marketplace

## 3. 目录协议

每个 skill 使用目录格式：

```text
<skill-slug>/
  SKILL.md
  templates/
  references/
  assets/
```

最小必需文件：

- `SKILL.md`

按需增加：

- `templates/`
  - 模板文件，例如 brief、checklist、handoff 模板
- `references/`
  - 必要参考材料
- `assets/`
  - 辅助资源

## 4. 建议放置位置

第一版先采用项目内协议，不急着做全局安装器。

建议位置：

- 公司通用 skill：
  - `shared/skills/<skill-slug>/`
- 研究中心主导的通用方法 skill：
  - `projects/research-center/skills/<skill-slug>/`
- 明确只服务单项目的 skill：
  - `projects/<project-slug>/skills/<skill-slug>/`

## 5. `SKILL.md` 最小 frontmatter

建议最少包含以下字段：

```yaml
---
name: research-brief
description: 把研究任务收束成正式 brief
owner: Research & Knowledge Lead
status: draft
version: 0.1.0
skill_type: shared
applies_to:
  - research_knowledge
  - ceo
when_to_use: >
  当任务需要先明确研究对象、研究问题、范围、服务对象和交付物时使用。
inputs:
  - 任务背景
  - 研究对象
  - 服务对象
outputs:
  - 研究 brief
handoff_to:
  - Research & Knowledge Lead
  - Product Spec Lead
  - Architect
---
```

## 6. 字段说明

- `name`
  - skill 名称，建议与目录 slug 一致
- `description`
  - 一句话说明 skill 做什么
- `owner`
  - 默认 owner 角色
- `status`
  - `draft` / `in_review` / `current` / `archived`
- `version`
  - 轻量语义版本
- `skill_type`
  - `shared` / `role-specific` / `project-specific`
- `applies_to`
  - 适用角色
- `when_to_use`
  - 何时应调用该 skill
- `inputs`
  - 最小输入
- `outputs`
  - 最小输出
- `handoff_to`
  - 默认下游角色

## 7. Skill 正文结构

`SKILL.md` 正文建议采用固定结构：

1. 目标
2. 适用场景
3. 不适用场景
4. 必读上下文
5. 执行步骤
6. 输出格式
7. 质量检查项
8. handoff 规则

## 8. 输出要求

每个 skill 至少应明确：

- 产出什么 artifact
- artifact 放在哪
- artifact 最小字段是什么
- 下一步交给谁

默认要求 skill 产出不能只是聊天回答，而应尽量对应：

- `research/`
- `specs/`
- `tasks/`
- `qa/`
- `delivery/`
- `kb/`

中的正式或半正式产物。

## 9. Skill 分类

### 9.1 通用 skill

适合多个角色共享的方法型 skill。

示例：

- `task-routing`
- `handoff-packaging`
- `artifact-readiness-check`

### 9.2 角色专属 skill

适合某一类角色反复执行的专门方法。

示例：

- `business-diagnosis`
- `product-framing-spec`
- `architecture-boundary-plan`
- `qa-gate-review`

### 9.3 项目专属 skill

只服务某个项目语境，不适合抽成公司通用能力。

示例：

- 某产品 onboarding spec skill
- 某品牌内容转译 skill

## 11. 首批 skill 的完成标准

首批 skill 不要求一开始就支持复杂自动化，但至少要满足：

1. 有稳定目录
2. 有 `SKILL.md`
3. 有明确输入输出
4. 有对应模板或 checklist
5. 能独立被某个 Agent 调用
6. 调用后能形成可 handoff 产物

## 12. 不要做成什么样

不要把 skill 做成：

- 另一份冗长角色 prompt
- 只有原则、没有动作
- 只有说明、没有产物要求
- 只有灵感、没有适用边界
- 只有“何时使用”，没有“完成标准”

## 13. 下一步建议

基于本协议，建议优先落地以下三个样例：

1. `research-brief`
2. `handoff-packaging`
3. `product-framing-spec`

原因：

- 这三者能直接连起研究中心、CEO、产品定义三段工作流
- 也是当前 `墨予镜` 最容易出现不稳定的接口位置

## 14. 一句话结论

`墨予镜` 的 skill 不应只是“提示词片段”，而应是带有适用边界、输入输出、artifact 落点和 handoff 规则的方法单元。
