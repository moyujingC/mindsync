这份文档定义一个跨项目、跨角色可复用的事实核查质量门能力。

它不是 `研究中心` 私有流程，而是公司级共享能力。

## 1. 目标

这套能力要解决的问题是：

1. 让包含事实主张的草案，在进入 review、handoff、知识库或决策前先过核查。
2. 防止“像真的但没有稳定出处”的内容继续往下游流动。
3. 让核查成为可复用的共享能力，而不是某个项目里的一次性提醒。

## 2. 能力定位

建议将该能力定义为共享 skill：

- skill 名称：
  - `fact-check-gate`

它的职责不是生成内容，而是：

- 拆分事实主张
- 检查来源覆盖
- 标记高风险表述
- 给出放行、条件放行或退回结论

## 3. 触发规则

满足以下任一条件时，默认触发 `fact-check-gate`：

- 草案中包含数字、比例、市场规模、增长率
- 草案中包含案例细节、机构报告结论、行业事实
- 草案准备进入创作者 / 用户 review
- 草案准备进入知识库
- 草案准备 handoff 给下游角色继续使用
- 草案准备作为商业、产品或策略判断输入

默认不触发的场景：

- 纯 brainstorming
- 纯观点发散，尚未形成事实型草案
- 明确不用于 downstream 决策、review、handoff 或知识沉淀的临时笔记

## 4. 标准链路位置

`fact-check-gate` 应插在“草案”和“正式使用”之间：

`draft -> fact-check-gate -> review/use/handoff/ingest`

典型挂接方式：

- 研究中心：
  - `research-draft -> fact-check-gate -> review -> knowledge-ingest`
- 商业可行性研究：
  - `biz-report-draft -> fact-check-gate -> review -> decision/handoff`
- 竞品调查：
  - `competitor-analysis-draft -> fact-check-gate -> review -> spec/strategy`
- 对外内容稿：
  - `content-draft -> fact-check-gate -> review -> publish/handoff`

## 5. 输入输出

### 5.1 输入

- 当前草案
- 原始来源材料
- 如有，已有综合结论或上游摘要

### 5.2 输出

- `fact-check-note`
- 核查结论：
  - `pass`
  - `pass_with_conditions`
  - `fail`

## 6. 放行规则

- `pass`
  - 允许进入下一阶段
- `pass_with_conditions`
  - 必须先完成指定修改，再进入下一阶段
- `fail`
  - 退回草案修改，不得进入下一阶段

## 7. 与现有 skill 的关系

- `research-synthesis`
  - 负责综合结论，不负责事实放行
- `knowledge-ingest`
  - 只接收已经过核查和 review 的内容
- `qa-gate-review`
  - 仍用于实现、spec、架构等质量门；不替代事实核查质量门
- `artifact-readiness-check`
  - 负责阶段就绪性；不替代事实主张核查

## 8. 最小落地方式

当前先做轻量版：

1. 沉淀 `fact-check-gate` skill
2. 统一 `fact-check-note` 模板
3. 在研究中心、商业研究、竞品调查链路里显式挂入
4. 后续再评估 NotebookLM、插件或自动化接入

## 9. 当前结论

`fact-check-gate` 应作为公司级共享质量门能力存在。

它不是所有任务都要跑的一刀切流程，但凡是“包含事实主张、且会继续被使用的草案”，都应先过这一关。
