这份文档用于把 `墨予镜` 第一阶段 skill 体系，收束成一个可对外表达、可服务化试水、但不误装成成熟产品的平台打包方案。

## 1. 背景

- 当前资产现状：
  - 第一阶段 skill 体系已完成统一接入最小闭环
  - 已有 6 条真实试跑链路
  - 已有协议、模板、案例索引、QA 结果和阶段性综合判断
- 当前关键判断：
  - 这套体系值得继续推进
  - 但不适合直接包装成独立产品或 marketplace

## 2. 对外打包目标

- 目标一：
  - 形成一套可对外讲清楚的方法论表达
- 目标二：
  - 形成一套可服务化交付的最小方法包
- 目标三：
  - 为未来产品化保留结构化资产，而不是现在就过度产品包装

## 3. 外部受众与场景

### 3.1 外部受众

- 想搭建一人公司 AI 协作系统的创作者
- 需要稳定 artifact 与 handoff 的小团队
- 已有多个 Agent，但方法层混乱的 AI 产品团队

### 3.2 对外场景

- 内容场景：
  - build in public
  - 方法论文章
  - 开源样本研究后的原创判断
- 服务场景：
  - 帮团队梳理多 Agent 工作流
  - 帮团队设计 handoff、artifact 和 QA 闸门
  - 帮团队把 prompt 层问题升级为方法层问题
- 产品前置场景：
  - 收集外部团队对模板、案例和方法包的真实反馈

## 4. 对外最小能力包

### 4.1 可直接对外表达的部分

- 为什么问题不只是 prompt，而是方法层缺失
- skill 作为可复用工作流单元的价值
- artifact、handoff、QA 在 Agent 协作中的作用
- 从研究到内容、产品、架构、QA 的链路样例

### 4.2 可服务化交付的部分

- 一套最小 skill 设计方法
- 一套 handoff 与 artifact 模板包
- 一套阶段门与 QA 最小清单
- 一套真实试跑案例拆解

### 4.3 当前不对外承诺的部分

- 自动发现 loader
- marketplace
- 通用 runtime 平台
- 适配所有团队的开箱即用系统

## 5. 打包结构建议

### 5.1 内容打包

- 一篇总论：
  - 为什么我最后补的是 skill，不是更多角色 prompt
- 一篇方法文：
  - 如何把多 Agent 协作从聊天推进成 artifact 系统
- 一篇案例文：
  - `墨予镜` 如何用 6 条真实链路把方法跑实

### 5.2 服务打包

- 服务名称建议：
  - AI 协作方法系统梳理
  - 多 Agent artifact 与 handoff 设计
- 服务交付建议：
  - 诊断现状
  - 识别缺失的 skill / handoff / QA
  - 定义最小模板与阶段门
  - 交付一套定制化方法包

### 5.3 产品前置打包

- 不先做完整产品
- 先收集：
  - 哪类团队最需要
  - 哪些模板最常被复用
  - 哪些方法包最愿意付费

## 6. 验收标准

- 外部看完后能理解：
  - 这不是 prompt 集合，而是方法体系
- 服务对象拿到后能理解：
  - 能交付什么
  - 不能交付什么
- 内部继续推进时能复用：
  - 现有案例
  - 现有模板
  - 现有 QA 标准

## 7. 下一步 handoff

- 建议交给谁：
  - `Content Lead`
  - `Business Lead`
- 需要产出什么：
  - 一份内容侧表达包
  - 一份服务化 offer 草案

## 8. 一句话结论

当前 `墨予镜` skill 体系最合理的对外打包方式，不是直接产品化，而是先把它整理成可讲、可交付、可验证的方法与服务包。
