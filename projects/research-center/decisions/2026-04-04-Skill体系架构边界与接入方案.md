这份文档把第一阶段 skill 体系的产品定义继续收束成可执行的架构边界。

目标不是设计复杂运行时，而是明确：

- 第一阶段 skill 系统由哪些结构组成
- 哪些能力只是文档协议，哪些已经进入接入层
- 后续统一接入时，工程和 QA 分别要拿到什么输入

## 1. 背景

- 项目：
  - `研究中心`
- spec 来源：
  - [Claude Code 启发下的 Skill 体系产品定义 / SPEC](/Users/xinran/Downloads/dev/mindsync/projects/research-center/specs/2026-04-04-Claude-Code启发下的Skill体系产品定义-SPEC.md)
- 继承锚点：
  - 第一阶段目标是为现有多 Agent 协作补上方法层，不是重做公司运行时
  - 当前 skill 已在 `projects/research-center/skills/` 下形成首批目录和模板

## 2. 技术边界

### 2.1 模块边界

- 模块一：Skill 定义层
  - 位置：
    - `projects/research-center/skills/<skill-slug>/`
  - 职责：
    - 保存 `SKILL.md`
    - 保存模板、示例和辅助参考
  - 当前形态：
    - 文档协议 + 可人工调用的方法对象

- 模块二：Skill 治理层
  - 位置：
    - `projects/research-center/skills/README.md`
    - `projects/research-center/skills/技能统一索引.md`
    - `projects/research-center/skills/技能编写与维护规范.md`
    - `projects/research-center/skills/技能评审清单.md`
  - 职责：
    - 统一索引
    - 规范字段
    - 评审和维护规则

- 模块三：角色引用层
  - 位置：
    - `agents/*/AGENTS.md`
  - 职责：
    - 只声明角色优先使用哪些 skill
    - 不复制 skill 细节
  - 约束：
    - 保持最小接入，不让角色 prompt 再次膨胀

- 模块四：试跑与验证层
  - 位置：
    - `projects/research-center/delivery/`
    - 对应真实产物目录，如 `company/projects/...` 或 `projects/...`
  - 职责：
    - 记录 skill 是否能支撑真实任务
    - 沉淀案例，反向修订 skill

- 模块五：后续统一接入层
  - 第一阶段定义：
    - 尚未实现真实 loader
  - 当前允许的最小实现：
    - 人工按目录引用和模板执行
    - 在角色 prompt 中声明优先 skill
    - 通过试跑记录验证可用性

### 2.2 数据边界

- Skill 主数据：
  - `SKILL.md` frontmatter 与正文
- Skill 辅助数据：
  - 模板、示例产物、评审清单、统一索引
- 运行态引用数据：
  - 各角色 `AGENTS.md` 内的 skill 引用
- 验证数据：
  - 真实试跑产生的 `spec`、`delivery`、品牌上游输入等 artifact

### 2.3 不做范围

- 不实现自动扫描和动态注入 loader
- 不实现远程 skill registry
- 不实现复杂的执行权限白名单
- 不实现独立 skill marketplace UI
- 不把 `projects/research-center/skills` 立即迁移为全局 `shared/skills`

## 3. 关键架构判断

### 3.1 先把 Skill 当成治理对象，而不是运行时对象

- 第一阶段最核心的是：
  - 让 skill 成为可审阅、可版本化、可试跑的文档化能力单元
- 不是：
  - 先做一个能自动调用一切的运行时系统

这保证当前架构复杂度和 `墨予镜` 的组织阶段匹配。

### 3.2 角色 prompt 只做入口，不做能力承载主体

- skill 细节留在 `projects/research-center/skills/`
- `agents/*/AGENTS.md` 只保留：
  - 何时优先用哪个 skill
  - skill 的职责边界

这样后续更新方法时，只需维护 skill 本体，不必反复改角色 prompt。

### 3.3 试跑记录是第一阶段的重要验证接口

- 第一阶段没有自动化 loader 时：
  - `delivery/` 中的试跑记录就是“能力是否成立”的主要验证面
- 因此架构上必须把：
  - skill 本体
  - 真实任务产物
  - 试跑复盘
  三者视为一个闭环

## 4. 风险

- 风险一：
  - skill 目录存在，但很多 skill 仍停留在说明层，缺少真实产物案例
- 风险二：
  - 角色 prompt 中的 skill 引用和 skill 本体可能逐步失配
- 风险三：
  - 如果试跑链路太少，后续统一接入时会放大隐含缺口
- 风险四：
  - 研究中心承担过多协议 owner 职责后，若没有评审节奏，skill 质量会再次分化

## 5. 实现前提

- 需要持续补齐：
  - 每个关键 skill 的示例产物或试跑案例
- 需要建立：
  - 第二轮、第三轮试跑记录，覆盖产品、架构、QA 等不同链路
- 需要确认：
  - 后续统一接入的最小目标到底是“统一引用规范”还是“半自动 loader”
- 需要在实现前保持：
  - `projects/research-center/skills/` 作为第一阶段单一事实源

## 6. 对 Engineer 的 handoff

- 给 `Engineer`：
  - 如果进入统一接入实现，先做轻量接入层，而不是运行时重构
  - 第一优先事项应是：
    - 统一索引可读性
    - 角色引用一致性检查
    - skill 示例与模板的目录约束
  - 不要先做复杂执行引擎

## 7. 对 Test / QA 的 handoff

- 给 `Test / QA`：
  - 验证重点不是代码功能，而是：
    - skill 是否能稳定产 artifact
    - handoff 字段是否完整
    - 试跑链路是否可复现
    - 角色与 skill 是否存在职责越界

## 8. 允许变化与禁止改写

- 本轮允许变化：
  - 统一接入的实现顺序
  - skill 治理层文档的组织方式
  - 未来是否把部分 skill 迁到 `shared/skills`
- 本轮禁止改写：
  - 第一阶段“轻量接入、重试跑”的架构策略
  - skill 本体与角色引用分层
  - 以真实 artifact 作为第一阶段验证主接口

## 9. 一句话结论

第一阶段最合理的 skill 架构，不是先追求自动调用，而是先把 skill、角色引用和试跑验证组织成一个低复杂度但可持续收敛的闭环。
