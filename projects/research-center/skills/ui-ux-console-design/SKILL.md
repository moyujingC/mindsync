# UI UX Console Design

## 目标

把控制台前端从“功能拼起来了”收束成“结构清楚、状态稳、操作敢用、后续好扩展”的正式后台界面。

这里的重点不是做炫技视觉，而是把以下几件事同时讲清楚：

- 用户现在在看什么
- 这个页面最重要的动作是什么
- 数据异常、为空、加载中时会发生什么
- 哪些配置是长期真理源，哪些只是一次性接线
- 用户改完一个值后，系统会立刻影响什么

## 适用场景

- 新建或重做控制台前端
- Vite SPA 想升级为更稳的正式前端骨架
- 页面已经能跑，但信息层级混乱
- 页面白屏、空白、错误态缺失，导致不敢上线
- 模型、入口、密钥、门禁卡之类配置很多，但用户看不懂主次关系
- 需要给第三方系统提供“一次性接入模板”

## 不适用场景

- 纯营销页、品牌故事页、落地页
- 只改一个按钮文案或一个颜色值
- 当前问题本质上是接口没通、数据没准备好，而不是 UI 结构问题
- 只想做视觉探索，不需要落地到真实页面和交互合同

## 必读上下文

1. 对应项目 `PROJECT.md`
2. 当前页面涉及的 `spec / task / qa`
3. 真实接口合同、字段语义、异常返回
4. 现有页面截图、录屏或运行页面
5. 若是控制台：至少明确
   - 默认首页是谁
   - 主导航有哪些项
   - 页面级主操作是什么

## 执行步骤

1. 先判定页面类型。
   - 它是“总览页”、“列表页”、“详情页”、“设置页”，还是“一次性接入页”。
   - 不要让一个页面同时承担过多角色。

2. 写清主任务。
   - 用户进这个页面第一件事要完成什么。
   - 次要信息只能服务主任务，不能抢层级。

3. 梳理信息层级。
   - 顶层：页面标题、页面解释、主操作。
   - 中层：核心卡片、表格、表单。
   - 底层：高级信息、调试信息、补充说明。

4. 明确状态系统。
   - loading（加载中）
   - empty（空状态）
   - error（错误态）
   - success（保存成功）
   - pending（提交中）
   页面不能只设计“成功且有数据”的理想态。

5. 明确配置真理源。
   - 哪些值应该长期在控制台里维护。
   - 哪些值只是一眼能看懂的解析结果。
   - 哪些值只是一次性接线配置，不应要求用户反复修改。

6. 把术语翻译成人话。
   - 英文专有名词旁边补中文解释。
   - 对系统级配置写清“它是做什么的，不是什么”。
   - 例如：
     - `relay token`：RelayHub 的门禁卡，不是模型厂商密钥。
     - `reasoningEffort`：模型思考深浅档位。

7. 给出可实现的组件策略。
   - 优先卡片、表格、表单、状态标签。
   - 大页面拆成稳定区块，不让一个接口失败拖垮整页。
   - 列表页优先考虑搜索、筛选、状态标签、行内编辑边界。

8. 补齐一次性接入模板。
   - 若页面要指导外部系统接入，必须给可复制的固定模板。
   - 模板至少包含：
     - URL
     - model / alias
     - 鉴权方式
     - 使用哪个协议端点

9. 收口为实现约束。
   - 哪些交互必须做
   - 哪些本轮不做
   - 哪些错误先显式报错，不做自动兜底

## 输出格式

建议基于：

- `templates/控制台页面设计模板.md`
- `templates/控制台页面快速检查清单.md`

最小输出至少包括：

- 页面目标
- 页面类型
- 主任务
- 信息层级
- 状态设计
- 关键字段的人话解释
- 本轮主操作
- 不做范围

## 质量检查项

- 首页是否一眼看得出“现在最该看什么”
- 页面是否把“配置真理源”和“解析结果”区分清楚
- 是否补齐了加载、空态、错误态，而不是只画正常态
- 是否避免全屏大段说明文字压过主要操作
- 表格和卡片是否真的服务决策，而不是堆字段
- 技术名词旁边是否给了通俗解释
- 用户看完一次性接入模板后，是否能直接去配置，而不用再翻 runbook
- 单个区块失败时，整页是否仍能继续使用

## Handoff 规则

- 若任务还停留在“我们想做得更好看”，先回到 `product-framing-spec`
- 若已经明确页面目标和范围，再交给 `Engineer`
- 若涉及前后端边界和接口补齐，可并行交给 `Architect`
- 完成实现后，应交给 `QA` 做：
  - 空态检查
  - 错误态检查
  - 直达链接与刷新检查
  - 关键表单保存反馈检查

## 默认设计原则

- 优先做正式后台，不优先做花哨特效
- 优先让用户敢改配置，而不是先追求视觉戏剧性
- 优先减少“页面空白时不知道发生了什么”
- 优先让同一类信息用同一类组件承载
- 优先让每个页面只承担一个主任务

## 常见错误

- 把首页做成“什么都有”，结果没有重点
- 把关键解释埋进很深的弹窗或文档
- 只有成功态，没有空态和错误态
- 页面依赖某一个接口成功，否则整页白屏
- 把运行时真理源分散在两个面板中维护
- 表单能编辑很多值，但用户不知道哪些值才是长期该改的
