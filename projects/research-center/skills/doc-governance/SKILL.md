# Doc Governance

定期检查并修复文档系统中的冗余、重复、矛盾问题。

## 核心原则

**规则层（DOCS_GOVERNANCE.md）定义"应该怎样"，skill 层负责"怎么检查并修复"。**

## 目标

确保文档系统满足 AI-Ready 的六个特征：

| 特征 | 含义 |
|------|------|
| **不冗余** | 一个事实只在一处 |
| **不重复** | 职责清晰，不交叉 |
| **不矛盾** | 有权威链和新鲜度声明 |
| **可执行** | 有明确的验收条件和边界约束 |
| **有边界** | 声明依赖和上下文，不让 AI 猜 |
| **可发现** | 有 AI 专用导航索引，不让 AI 翻目录 |

## 检查类型

### 1. 冗余检查

**问题**：文档里积累了"过程"而非"结论"

**检查规则**：
- 同一主题的多次讨论、修改记录、备选方案是否只保留最终结论
- 带 TODO、计划、考虑中 超过 3 个月的文档是否已决策或删除
- 过长的 sprint log、变更历史是否移入 archive

**识别模式**：
```
高风险关键词（需检查）：
- "讨论中"、"考虑中"、"待定"
- "备选方案 A/B/C"
- 超过 5 次的修改记录堆叠
- 划掉的内容保留过多
```

**修复建议**：
- 删除过程，保留结论
- 过程内容移入 `in-progress/` 或 `archive/`
- 结论升格为 canonical 文档

### 2. 重复检查

**问题**：多个文件讨论同一件事，AI 不知道信哪个

**检查规则**：
- 同一模块是否在多个文档里重复描述
- 同一决策是否在多个地方记录
- spec 和 README 是否有职责重叠

**识别模式**：
```
重复信号：
- 两个文件都解释"这个模块怎么工作"
- 同一个 API 在多处描述参数
- 同一段代码说明在不同文档出现多次
```

**修复建议**：
- 确定唯一权威位置
- 其他位置引用权威文档，或删除
- 用 `source_of_truth` 和 `supersedes` 声明关系

### 3. 矛盾检查

**问题**：不同文档说的情况冲突

**权威链（从高到低）**：
```
1. 实际代码          → 真相之源
2. specs/           → 模块契约（由代码验证）
3. progress.md      → 当前状态摘要
4. decisions/       → 为什么这么做的理由
5. README           → 入门指南
6. research/        → 参考材料（可能有偏差）
```

**检查规则**：
- spec 描述与代码实际行为是否一致
- README 说依赖 X，实际用的是不是 Y
- ADR 说决定用 A，spec 里是不是 B

**修复建议**：
- 以权威链更高的为准
- 更新/删除低权威的矛盾文档
- 标注文档新鲜度（`last_verified`）

### 4. 状态检查

**检查规则（基于 DOCS_GOVERNANCE.md）**：
- 是否有周计划、交付记录、readiness check 长期占用 `current`
- 带日期的阶段文档是否仍承担长期入口职责
- `tasks/`、`qa/`、`delivery/` 默认状态是否正确

**常见问题**：
- `current` 用于一次性交付记录
- 周执行清单长期标为 `current`
- 已完成的 handoff 仍维持 `current`

**修复建议**：
- 一次性文档降为 `working` 或 `historical-reference`
- 长期入口文档升级为无日期 canonical

### 5. 可发现性检查

**检查规则**：
- `docs/README.md` 或 `PROJECT.md` 是否有 AI 导航索引
- 关键文档是否能通过索引快速找到
- 是否存在深层目录里的重要信息被遗忘

## 执行步骤

### 步骤 1：确定检查范围

```
默认：全仓库扫描
可选：指定目录（如 company/、projects/aimandala/）
```

### 步骤 2：选择检查类型

```
--check all      # 全部检查（默认）
--check redundancy  # 仅冗余
--check duplicate   # 仅重复
--check conflict    # 仅矛盾
--check status      # 仅状态
```

### 步骤 3：执行扫描

对每个检查类型，执行相应检查逻辑，收集问题清单。

### 步骤 4：生成治理报告

输出格式：
```markdown
# 文档治理报告
> 日期：YYYY-MM-DD
> 范围：xxx
> 检查类型：xxx

## 问题汇总
- 问题数：N

## 问题详情

### 1. [冗余] 文件名
- 位置：xxx
- 问题：xxx
- 建议：xxx

### 2. [重复] 文件名
- 位置：xxx
- 问题：xxx
- 建议：xxx

...

## 可执行操作
```

### 步骤 5：用户确认后执行修复

建议逐项确认修复，而非自动执行全部。

## 输出格式

### 治理报告模板

见 `templates/治理报告-模板.md`

### 问题清单字段

| 字段 | 说明 |
|------|------|
| `类型` | redundancy / duplicate / conflict / status |
| `文件` | 路径 |
| `问题` | 具体描述 |
| `严重度` | 高 / 中 / 低 |
| `建议` | 具体修复建议 |
| `可执行操作` | 修复命令或操作步骤 |

## 治理节奏

### 按需触发（事件驱动）

| 触发时机 | 动作 |
|---------|------|
| 发现文档矛盾 | 调用 skill 诊断并修复 |
| 代码重大变更 | 调用 skill 同步检查 spec |
| 新决策确定 | 调用 skill 更新 decisions |

### 定时触发（可选）

| 频率 | 内容 |
|------|------|
| 每周一次（轻量） | 状态扫描 + 冗余检查 |
| 每月一次（完整） | 全部检查 + 完整审计 |

## 与其他 Skill 的边界

| Skill | 职责 | 边界 |
|-------|------|------|
| `DOCS_GOVERNANCE.md` | 定义规则 | 只负责"是什么"，不管"怎么查" |
| `qa-gate-review` | 交付前质量门 | 只在交付节点触发 |
| `artifact-readiness-check` | 阶段切换检查 | 只在阶段切换时触发 |
| `doc-governance`（本 skill） | 定期健康检查 | 按需/定时，全局扫描 |

## 质量检查项

治理完成后，检查是否满足：

- [ ] 冗余问题已清理或移入 archive
- [ ] 重复文档已合并或声明权威关系
- [ ] 矛盾问题已确认并修复
- [ ] 状态误用已更正
- [ ] AI 导航索引完整
- [ ] 治理报告已生成并存档

## 示例调用

### 1. 发现矛盾时的调用

```
发现 specs/ 和 README 对同一 API 描述不一致，使用 doc-governance 检查矛盾并修复。
```

### 2. 定期治理的调用

```
执行本周期的文档治理，检查全仓库的冗余、重复、矛盾问题。
```

### 3. 代码变更后的调用

```
代码变更影响了模块契约，使用 doc-governance 同步检查并更新 spec。
```
