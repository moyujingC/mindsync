这份文档用于统一 `墨予镜` skill 的编写口径，避免后续 skill 越补越散、格式不一、边界混乱。

## 1. 命名规范

### 1.1 目录名

统一使用英文 kebab-case：

- `research-brief`
- `handoff-packaging`
- `product-framing-spec`

不要使用：

- 中文目录名
- 空格
- 下划线风格混用

### 1.2 Skill 名称

`SKILL.md` 中的 `name` 应与目录名保持一致。

## 2. 结构规范

每个 skill 至少包含：

```text
<skill-slug>/
  SKILL.md
```

建议默认加：

```text
<skill-slug>/
  SKILL.md
  templates/
```

只有在确实需要时再补：

- `references/`
- `assets/`

## 3. Frontmatter 规范

建议最少包含：

- `name`
- `description`
- `owner`
- `status`
- `version`
- `skill_type`
- `applies_to`
- `when_to_use`
- `inputs`
- `outputs`
- `handoff_to`

如果某个字段当前写不清，不要硬补假内容。

## 4. 正文结构规范

默认使用以下结构：

1. 目标
2. 适用场景
3. 不适用场景
4. 必读上下文
5. 执行步骤
6. 输出格式
7. 质量检查项
8. Handoff 规则

除非有充分理由，不要跳过这些段落。

## 5. 内容边界规范

skill 不应写成：

- 角色自我介绍
- 冗长价值观复述
- 大段重复公司原则
- 纯灵感笔记

skill 应写成：

- 一个可重复的方法单元
- 一个明确的动作流程
- 一个可导向 artifact 的执行协议

## 6. 模板规范

如果 skill 会稳定产出正式 artifact，建议提供模板。

模板命名建议：

- `研究任务-brief-模板.md`
- `HANDOFF-模板.md`
- `产品定义-SPEC-模板.md`

模板目标不是替代判断，而是降低遗漏字段的风险。

## 7. 版本与状态规范

### 7.1 状态

- `draft`
  - 首次创建，尚未验证
- `in_review`
  - 已准备接入或试运行
- `current`
  - 已被正式采用
- `archived`
  - 不再推荐使用

### 7.2 版本

- 首版默认为 `0.1.0`
- 小修订可升到 `0.1.1`
- 结构调整可升到 `0.2.0`

## 8. 维护原则

### 8.1 优先改 skill，不优先改角色 prompt

如果问题本质是方法不稳定，应优先修 skill。

### 8.2 一个 skill 只解决一类问题

不要把多个阶段的工作都塞进同一个 skill。

### 8.3 优先让下游更容易接棒

skill 的价值不只在本阶段提效，也在于让 handoff 更稳定。

## 9. 当前建议

后续新增 skill 时，默认先检查：

1. 是否已存在相近 skill
2. 能否通过补模板或补边界解决，而不是新增目录
3. 是否真的具备跨多次复用价值
