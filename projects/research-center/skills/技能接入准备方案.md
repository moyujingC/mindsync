这份文档不直接修改角色 prompt，而是为“最后一次性接入”做准备。

它重点回答：

1. 每个角色最应该接哪些 skill
2. 接入时应以什么最小改动方式完成
3. 哪些 skill 应该作为默认方法，哪些只在特定任务下调用

## 1. 接入原则

### 1.1 少改 prompt，多挂 skill

接入时不应把 skill 内容重新抄回角色 prompt。

应采用：

- 角色 prompt 保留职责边界
- 角色 prompt 只补“默认优先调用哪些 skill”
- skill 继续作为独立方法单元维护

### 1.2 先挂高频 skill，后挂补充 skill

不要一口气把所有 skill 都挂进每个角色。

优先接入：

- 高频
- 跨任务
- 直接影响 handoff 质量

### 1.3 默认 skill 不等于每次都要调用

接入描述要避免写成：

- “每次都调用”

而应写成：

- “遇到某类任务时优先使用”

## 2. 每个角色的建议接入 Skill

## 2.1 CEO / Orchestrator

建议接入：

- `task-routing`
- `artifact-readiness-check`
- `handoff-packaging`

接入位置建议：

- 放在“默认工作流判断”之前或之后
- 单独新增一段：
  - `你优先使用的 skill`

建议写法：

- 当任务刚进入系统时，优先用 `task-routing` 判断工作流和 owner
- 当任务准备进入下一阶段时，优先用 `artifact-readiness-check`
- 当任务需要交给下一角色时，优先用 `handoff-packaging`

## 2.2 Research & Knowledge Lead

建议接入：

- `research-brief`
- `knowledge-ingest`
- `insight-handoff`
- `handoff-packaging`

接入位置建议：

- 放在“默认输入来源”和“默认输出”之间

建议写法：

- 当任务尚未收束成正式研究对象时，优先用 `research-brief`
- 当研究完成后，优先用 `knowledge-ingest`
- 当研究要交给产品、架构或内容时，优先用 `insight-handoff` 或 `handoff-packaging`

## 2.3 Product Spec Lead

建议接入：

- `product-framing-spec`
- `artifact-readiness-check`
- `handoff-packaging`

接入位置建议：

- 放在“默认工作方式”或“阶段门责任”前

建议写法：

- 当任务处于产品定义阶段时，优先用 `product-framing-spec`
- 当准备 handoff 给 `Architect` 或 `Engineer` 时，先用 `artifact-readiness-check`
- 正式交接时优先用 `handoff-packaging`

## 2.4 Business Lead

建议接入：

- `business-diagnosis`
- `handoff-packaging`

接入位置建议：

- 用 skill 替代现有 `dbskill` 口径的主要调用说明

建议写法：

- 在不能直接调用 `dbskill` 的环境下，默认优先使用 `business-diagnosis`
- 当商业判断要交给产品或内容时，优先用 `handoff-packaging`

## 2.5 Architect

建议接入：

- `architecture-boundary-plan`
- `artifact-readiness-check`
- `handoff-packaging`

接入位置建议：

- 放在“阶段门责任”前后

## 2.6 Test / QA

建议接入：

- `qa-gate-review`
- `artifact-readiness-check`

接入位置建议：

- 放在“默认输出”或“阶段门责任”前

## 2.7 Content Lead

建议接入：

- `content-grounded-transform`
- `handoff-packaging`

接入位置建议：

- 放在“默认输入来源”之后

建议写法：

- 当任务需要把真实研究或项目素材转为内容角度时，优先用 `content-grounded-transform`
- 当内容上游输入不足时，用 `handoff-packaging` 明确回退需求

## 3. 不建议现在接入的做法

以下做法当前不建议采用：

- 在每个角色里列全量 11 个 skill
- 把 `SKILL.md` 的全文嵌进 `AGENTS.md`
- 要求每次任务都显式点名 skill
- 还没接入就修改 skill 协议本身

## 4. 一次性接入顺序建议

建议分三批接入，但在同一次提交里完成：

### 4.1 第一层：公司总控

- `CEO`

原因：

- 先让任务路由、阶段判断、handoff 打包稳定

### 4.2 第二层：核心生产链

- `Research & Knowledge Lead`
- `Product Spec Lead`
- `Architect`
- `Test / QA`

原因：

- 这四个角色构成研究到实现再到验收的主链路

### 4.3 第三层：两端增强

- `Business Lead`
- `Content Lead`

原因：

- 它们很重要，但放到前两层之后更容易按同一口径接入

## 5. 建议的最小改动模板

角色 prompt 中建议新增统一小节：

```md
## 你优先使用的 skill

当任务属于以下情况时，优先使用：

- `skill-a`
  - 用于……
- `skill-b`
  - 用于……
```

这样能做到：

- 改动小
- 角色职责不被冲散
- skill 入口清楚

## 6. 接入完成后的检查

一次性接入后，应检查：

1. 每个角色是否只挂了最相关的 skill
2. 是否仍然保持角色边界清楚
3. 是否没有把 skill 再写回 prompt 本体
4. 是否形成一条完整主链：
   - route -> research/product -> architecture -> qa -> handoff/content

## 7. 一句话结论

最后一次性接入时，目标不是让 prompt 变长，而是让每个角色知道自己在什么任务下优先调用哪几个 skill。
