# AI 应用需要同时设计人类界面和 Agent 界面

## 当前结论

AI 应用的产品设计不能只考虑人类用户怎么使用，也要考虑其他 AI 应用、Agent（智能体）、Workflow（工作流）或自动化系统怎么理解和调用它。

传统软件的界面主要是 Human Interface（人类界面）：用户怎么看、怎么点、怎么输入、怎么确认、怎么接管。

AI 应用还需要 Agent Interface（智能体界面）：外部 Agent 怎么发现能力、理解输入输出、判断权限边界、读取状态、处理失败、复用结果。

所以 AI 应用的 UI/UE（界面与用户体验）不再只是视觉和交互问题，它会反过来塑造 Agent、Workflow、Skill、Plugin、MCP 的设计边界。

## 核心结构

### 1. AI 应用有两类使用者

第一类是人类用户。

他们通过页面、按钮、表单、聊天框、工作台、预览区和确认弹窗使用产品。

人类用户需要的是：

- 看得懂当前发生了什么
- 知道自己该输入什么
- 能确认 AI 的关键判断
- 能修改、回退、重生成
- 能在风险动作前接管
- 能看到进度、失败和结果状态

第二类是 AI 使用者。

这里的 AI 使用者可能是：

- 外部 Agent
- 本产品内部 Agent
- 其他 Workflow
- 某个 Skill
- 自动化脚本
- 通过 MCP 接入的外部 AI 应用

AI 使用者需要的是：

- 能发现这个应用有哪些能力
- 能读懂每个能力的输入、输出和限制
- 能知道哪些动作需要人类授权
- 能读取当前状态和历史结果
- 能识别结果是否 stale（已失效但仍可见）
- 能处理错误、重试和回滚
- 能把结果交给下游能力继续使用

### 2. 人类界面和 Agent 界面是同一个产品的两层接口

AI 应用不能只设计“人怎么点页面”，也不能只设计“Agent 怎么调 API”。

成熟的 AI 应用需要同时具备两层接口：

- UI/UE：给人类用户看的界面
- Capability Contract：给 Agent 调用的能力契约

这里的 Capability Contract（能力契约）至少应说明：

- 能力名称
- 能力目标
- 输入参数
- 输出结构
- 状态流转
- 权限要求
- 失败模式
- stale 条件
- 可否自动执行
- 是否需要人类确认

如果产品只做 UI，Agent 很难稳定调用。

如果产品只做 API 或 MCP，人类用户又很难理解、确认和接管。

### 3. UI/UE 会反过来影响 AI 能力组织方式

不同 UI 形态，会自然引出不同的能力组织方式。

聊天框适合开放目标，容易引出 Agent。

表单和向导适合确定输入，容易引出 Workflow。

命令面板和能力列表适合复用任务，容易引出 Skill。

插件市场、授权页和工具连接页适合外部能力管理，容易引出 Plugin。

多工具工作台、跨应用调用和外部上下文接入，容易需要 MCP。

因此，UI/UE 不是能力的外壳，而是能力边界的一部分。

用户能看见什么、确认什么、修改什么、授权什么、回退什么，会决定：

- Agent 能不能自主推进
- Workflow 能不能稳定运行
- Skill 能不能被理解和复用
- Plugin 能不能安全安装和管理
- MCP 暴露出去的能力是否足够清晰

### 4. AI 应用原型不只是页面跳转原型

传统产品做原型，常见目标是验证页面结构和用户路径。

AI 应用做原型，还要验证人和 AI 怎么分工。

一个合格的 AI 应用原型，至少要回答：

- 用户在哪里表达目标？
- 用户在哪里补充上下文？
- AI 在哪里给出判断？
- 哪些判断需要用户确认？
- 哪些步骤可以自动执行？
- 哪些动作必须等待授权？
- 结果如何展示？
- 失败如何解释？
- stale 结果如何提示？
- 用户如何修改、回退、重跑？
- 外部 Agent 如何调用同一能力？

所以 AI 应用的原型不是纯 UI 原型，而是“人机分工原型”。

### 5. 推荐的 AI 应用迭代顺序

较稳的开发顺序不是简单的“先 UI，再后端能力”。

更合适的是一条双螺旋：

```text
最小任务场景
  -> UI/UE 原型
  -> AI 能力拆分
  -> 假数据交互验证
  -> 最小真实 AI 闭环
  -> 状态与能力契约沉淀
  -> 再反推 UI 和能力架构
```

具体步骤：

1. 先定义最小用户任务。
   - 例如：导入一篇文章，生成 3 张可用知识卡。

2. 做 UI/UE 原型。
   - 重点不是页面好不好看，而是验证用户如何表达目标、交出上下文、确认 AI 判断、修改结果、接管风险动作。

3. 根据原型反推能力拆分。
   - 哪些是 Workflow？
   - 哪些是 Skill？
   - 哪些需要 Agent？
   - 哪些只是 Tool？
   - 哪些未来需要 Plugin 或 MCP？

4. 先用假数据跑通交互。
   - 按钮能点。
   - 状态能变。
   - 结果能展示。
   - 用户能修改、重生成和导出。

5. 再接入最小真实 AI 闭环。
   - 不一次接完整链路。
   - 先做一个纵切面，例如：文章导入 -> 拆解 -> 生成一张图 -> 用户选择 / 重生成 / 导出。

6. 最后沉淀 Skill 架构、状态机、stale 机制和依赖矩阵。
   - 架构文档应服务已经跑通的闭环，而不是在闭环还不稳时过早铺满。

### 6. 内容视觉工坊 V2 的启发

内容视觉工坊 V2 的推进混乱，主要不是单个页面或单个能力的问题，而是几个层级同时推进：

- Figma/code bundle 原型
- 工作台 UI
- 真实出图接口
- 内容拆解
- Skill 架构
- 状态清点
- 多页面联动
- stale 和绑定关系

这些都重要，但如果没有先收束到一个最小主链路，就容易变成页面、状态、能力、接口一起拉扯。

当前更稳的主链路应先收束为：

```text
导入文章
  -> AI 拆解
  -> 用户确认卡片计划
  -> 生成知识卡
  -> 用户选择 / 重生成
  -> 导出
```

其他页面和能力可以先降级为未来入口或假数据演示。

只有当这条主链路稳定后，再逐步补：

- 金句卡
- 封面生成
- 正文配图
- 公众号排版
- 风格资产
- 同步记录
- 外部 Agent 调用入口
