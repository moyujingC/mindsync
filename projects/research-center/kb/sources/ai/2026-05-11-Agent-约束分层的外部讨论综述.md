## 摘要

这组来源说明，外部确实已经在讨论“不要只靠 prompt，而要靠更强的流程和控制机制”，但他们使用的术语并不完全一致。

目前比较稳定的三条讨论线是：

- `guardrails`
  - 强调输入、输出、工具调用等边界上的检查与阻断
- `control plane`
  - 强调多 Agent 系统的部署、治理、权限、监控和生命周期管理
- `programmable rails`
  - 强调把运行时行为约束写成独立于模型的可编程规则

这些讨论共同支持一个方向：Agent 的可靠性不能只靠更长的 prompt。真正可靠的系统，需要把一部分约束下沉到工作流边界、工具调用边界和运行时治理层。

但这些来源并没有直接给出一套统一的“知识层 / prompt / runbook / 控制层”标准框架。更准确的说法是：目前外部已经有很多相邻概念，而我们现在整理出的分层模型，是对这些讨论的工程化收束。

## 关键摘录

- OpenAI Agents SDK 明确区分了：
  - input guardrails
  - output guardrails
  - tool guardrails
  - 并说明 tool guardrails 会在每次工具调用时执行
- OpenAI《A practical guide to building agents》明确把 guardrails 说成 layered defense mechanism（分层防御机制），并强调 guardrails 需要和认证、授权、访问控制一起工作
- IBM 对 agent control plane 的定义是：负责 deploy（部署）、operate（运行）、monitor（监控）和 govern（治理）Agent 的系统；它位于 data plane（数据平面）之上，在动作执行前负责 route（路由）、permission（权限）和 policy（策略）
- Datadog 把 guardrails 放进生产系统视角，强调不仅要拦输入和输出，还要覆盖 tool misuse（工具滥用）、sensitive data protection（敏感数据保护）、anomaly protection（异常保护）和 MCP protection
- NeMo Guardrails 论文把 rails 定义成独立于底层模型、可解释、可编程的运行时约束，并强调它不是单纯依赖训练期 alignment（对齐）

## 初步判断

这组来源对 `research-center` 很有价值，因为它们能帮助我们确认：当前把 Agent 约束理解为“比 prompt 更高一层的方法问题”，不是自说自话，而是和外部主流工程讨论同向。

它适合服务几个方向：

- 沉淀 `Agent`、`runbook`、`guardrails`、`control plane` 的概念边界
- 支撑“为什么不能只靠长 prompt”的系统性表达
- 帮 `mindsync` 和 `aimandala` 判断哪些规则还停留在文档层，哪些已经进入控制层
- 后续写关于 Agent 生产化、可观测性、治理和可靠性的 wiki 页

当前最重要的边界是：

- 外部更多在讲 `guardrails` 和 `control plane`
- `runbook` 作为独立关键词并不是所有来源都强调
- 因此后续如果要形成正式 wiki，不应强行声称“所有人都认同 prompt / runbook / gate 这套三分法”
- 更稳妥的做法是：把 `runbook` 视为我们对“流程层”的一个高可用表达，再和外部的 `guardrails / control plane / programmable rails` 建立映射

## 可提取 atoms

- 外部主流讨论已经普遍承认：Agent 可靠性不能只靠 prompt。
- `guardrails` 常被放在输入、输出和工具调用边界上理解。
- `control plane` 讨论的重点不是单个 Agent 提示词，而是多 Agent 系统的治理、授权、路由和观测。
- `programmable rails` 提供了一种把约束从模型内部对齐转向运行时可编程规则的表达方式。
- `runbook` 不是所有外部来源的统一术语，但可以作为“流程层”的本地工程表达。
- `knowledge / prompt / runbook / control` 这类分层框架更像对多种外部讨论的工程化收束，而不是现成标准术语。
