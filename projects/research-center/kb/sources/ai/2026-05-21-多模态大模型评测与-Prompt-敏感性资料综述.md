## 摘要

这组来源围绕一个问题展开：多模态大模型评测时，prompt（提示词）本身会不会影响模型能力判断，以及是否应该为不同模型定制 prompt 后再比较。

从目前资料看，较稳的判断是：多模态任务里，prompt 对评测结果的影响比纯文本任务更明显。原因包括视觉识别误差、图像区域关注差异、文字和图像之间的指代歧义、输出格式约束不同，以及模型在 OCR（光学字符识别）、空间关系、图表理解、UI 截图理解等能力上的偏好差异。

TP-Eval 和 Promptception 更直接地支持“不同多模态模型对 prompt 的敏感性不同”这个方向。NVIDIA、OpenAI、Anthropic 和 Google 的文档更偏工程实践，帮助把这种敏感性转成可操作的 prompt 设计和 eval（评测）设计。Hamel Husain 的文章虽然不是多模态专项，但适合补充工程 eval 的基本方法：样本集、错误分析、人工标注、回归测试和真实业务场景验证。

中文材料目前分三类：

- 官方中文：Anthropic Claude Vision、Google Vertex AI 多模态提示文档。
- 中文论文摘要或评述：TP-Eval、Promptception 的 Moonlight / ChatPaper 条目。
- 中文横评或体系综述：智源 FlagEval、302.AI、53AI。

## 关键摘录

- TP-Eval 的核心价值在于提出：通过为多模态 LLM（Large Language Model，大语言模型）定制 prompt，可以更充分释放模型在评测任务中的表现，减少统一 prompt 带来的低估。
- Promptception 的核心价值在于系统研究大型多模态模型对 prompt 变化的敏感性，适合用来支撑“统一 prompt 不能完全代表模型真实上限”的判断。
- NVIDIA 文章适合学习 VLM（Vision-Language Model，视觉语言模型）在图像和视频理解任务中的 prompt 写法，包括如何描述任务、输入范围和输出要求。
- OpenAI Cookbook 的 Image Evals 更适合理解多模态 eval 为什么需要拆分硬约束、视觉质量、语义一致性和失败模式，而不是只看一次模型回答。
- Anthropic 和 Google 的官方中文文档可以作为实际写多模态 prompt 的基础参考，尤其适合整理模型输入限制、图文顺序、图像质量和任务说明方式。
- Hamel Husain 的 eval 文章适合作为通用工程方法参考：不要只在 prompt playground（提示词调试台）里判断模型，要用真实样本集和错误分析来做持续评估。
- 中文横评材料适合观察行业怎么比较多模态模型，但需要区分体验型横评和可复现评测。

## 初步判断

这组来源适合支撑 `research-center` 后续沉淀一组关于“多模态 prompt 调试与评测设计”的知识：

- 多模态 prompt 调试应先做 baseline probing（基线探测），了解模型默认看图方式和稳定漏点。
- 正式评测可以分成两层：
  - 统一 prompt 下的基础能力评测；
  - 模型适配 prompt 下的最佳可用效果评测。
- 最终选型不应只看“哪个模型在统一 prompt 下最高分”，还应比较：
  - 适配后上限；
  - prompt 维护成本；
  - 失败模式；
  - OCR、空间关系、图表、UI 等任务子能力；
  - 业务样本上的稳定性。

当前边界也要写清：

- 为每个模型定制 prompt 可以更接近业务真实使用方式，但会引入调试成本和公平性问题。
- 如果给某个模型明显更多调参时间，评测结果会混入 prompt 工程能力。
- 因此后续做正式评测时，应同时记录 prompt 版本、调试轮次、样本集、失败样本和人工判分口径。
- 中文评述不能替代原论文；正式引用论文结论时仍应回到论文页或原文。

## 可提取 atoms

- 多模态大模型评测比纯文本评测更容易受到 prompt 表达、图文顺序和视觉关注范围影响。
- 只用统一 prompt 横评多模态模型，可能测到的是 prompt 与模型的匹配度，而不完全是模型能力。
- 模型适配 prompt 可以接近真实业务上限，但会降低横评公平性，需要记录调试成本。
- 多模态模型选型应同时比较统一 prompt 表现、适配后表现、失败模式和维护成本。
- 多模态 prompt 调试可以先做 baseline probing，再逐步加入关注范围、判断标准和输出格式。
- 中文论文评述适合快速学习，但正式知识沉淀应优先回指论文、官方文档或一手工程文章。
