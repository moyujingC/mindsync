# NotebookLM-MCP 基线事实核查试跑方案

这份文档用于定义如何把 `NotebookLM-MCP` 作为当前阶段的事实核查 baseline 方案来试跑。

目标不是立即替代所有现有流程，而是用最低测试成本回答两个问题：

1. `NotebookLM-MCP` 作为核查引擎，实际效果是否已经足够好
2. 我们还需要自己手搓哪些流程层能力

## 1. 当前决策

当前默认路线不是：

- 直接从零手搓完整核查系统

而是：

- 先用 `NotebookLM-MCP` 做 baseline
- 再用少量真实任务做效果验证
- 只补它没有覆盖好的流程层能力

## 2. 试跑目标

本轮试跑只验证三件事：

1. 它是否能稳定发现草案中的高风险事实主张
2. 它是否能明显减少你在 review 阶段抓到的“无出处硬事实”
3. 它的使用成本是否低到值得纳入正式链路

## 3. baseline 定位

在当前方案中，`NotebookLM-MCP` 的角色是：

- 核查引擎
- 来源约束问答层
- `fact-check-note` 的上游输入

它不负责：

- 最终 review
- 最终入库判定
- 研究草案的最终改写
- 知识库结构化沉淀

因此当前链路固定为：

`draft -> NotebookLM-MCP 核查 -> fact-check-note -> review -> knowledge-ingest`

## 4. 第一批试跑任务

第一批只选 3 类任务，每类 1 个真实样本：

1. 商业可行性研究
   - 目标：验证对市场规模、增长率、商业案例这类硬事实的核查效果
2. 产品竞品调查
   - 目标：验证对产品能力、竞品对比、案例引用的核查效果
3. 研究中心内容草案
   - 目标：验证对对外表达、趋势判断和数据句子的核查效果

当前不建议一开始就大规模铺开。

## 5. 每个样本的固定输入

每个试跑样本都应准备同一套输入：

1. `draft`
   - 当前草案
2. `source-pack`
   - 原始网页 / PDF / 文档文本
   - 原始链接
   - 如有，研究摘要或综合结论
3. `fact-check-note`
   - 使用既有模板回填

要求：

- 不允许只把草案丢进去
- 必须保证 source-pack 可追溯
- 若 source-pack 不完整，本轮结果默认不计入有效样本

## 6. 每个样本的执行步骤

### 第一步：准备 source-pack

整理：

- 原始来源链接
- 网页/PDF/文档文本
- 当前草案
- 如有，研究摘要

### 第二步：用 NotebookLM-MCP 执行核查

围绕以下问题输出结果：

1. 这份草案里有哪些明确事实主张
2. 每条主张分别由哪些来源支撑
3. 哪些句子没有直接来源覆盖
4. 哪些数字、比例、市场规模属于高风险表述
5. 哪些内容应改成趋势判断而不是硬事实

### 第三步：整理为 `fact-check-note`

必须回填：

- 事实主张
- 状态
  - `verified / plausible / needs_source / do_not_publish`
- 依据来源
- 处理动作

### 第四步：回改草案

按 `fact-check-note` 回改：

- `verified`
  - 保留
- `plausible`
  - 改弱表达
- `needs_source`
  - 删除或改写
- `do_not_publish`
  - 必删

### 第五步：进入你的 review

只有在核查回改完成后，才允许进入 review。

## 7. 统一评估指标

每个样本都按同一套指标记录。

### 7.1 效果指标

- 你在 review 阶段额外抓出的无出处硬事实数量
- 你在 review 阶段指出的高风险句子数量
- 草案被退回重写的次数
- 从草案到可入库/可继续使用的轮次

### 7.2 成本指标

- 准备 source-pack 的时间
- 跑一轮 NotebookLM-MCP 的时间
- 整理 `fact-check-note` 的时间
- 回改草案的时间

### 7.3 主观指标

- 你对最终稿可信度的主观评价
  - 高 / 中 / 低
- 你对这条链是否“省心”的评价
  - 高 / 中 / 低

## 8. Go / No-Go 判断

跑完第一批 3 个样本后，再决定是否继续深投入。

### 8.1 Go 条件

满足以下多数条件时，可继续推进：

- review 阶段的硬事实问题明显下降
- 退回次数减少
- 每轮试跑的人力成本可接受
- 你主观上认为“比直接 review 更省心”

### 8.2 No-Go 条件

满足以下任一条件时，应暂停扩大使用：

- source-pack 准备成本过高
- 核查结果经常抓不到关键问题
- 你 review 时仍反复抓到明显硬伤
- 整条链比直接 review 更慢且收益不明显

## 9. 如果 baseline 效果一般，下一步怎么做

如果 `NotebookLM-MCP` 只能解决一部分问题，不要立即重做整套系统。

优先只补三类流程层能力：

1. 更严格的 `fact-check-gate` prompt 与判定规则
2. 更清晰的 `fact-check-note` 与 `review-note` 模板
3. 更硬的放行规则
   - 未通过核查不得进入 review
   - 未通过 review 不得进入知识库

## 10. 当前最小结论

当前最值得做的不是“重造一个 NotebookLM”，而是：

- 先让 `NotebookLM-MCP` 成为 baseline 核查引擎
- 用真实任务验证效果
- 再只补它缺失的流程层能力

这会比直接完整手搓一套方案更省测试成本，也更容易得出可信结论。
