## 1.1 扩写策略

详情页内容偏少时，不建议只把段落写长。更好的做法是把每个项目拆成“读者能快速扫读的证据层”：

- 一屏讲清项目：项目是什么、我是谁、为什么值得看。
- 二屏讲清问题：原始场景、用户痛点、复杂度在哪里。
- 三屏讲清方法：我如何拆问题、定边界、做取舍。
- 四屏讲清系统：用流程图、模块图或对照表展示工作流。
- 五屏讲清结果：已有产物、当前状态、可验证输出。
- 六屏讲清迁移：这个项目对应 AI 产品经理 / AI 转型咨询顾问的哪类能力。
- 页尾讲清边界：主动说明不夸大的部分，反而增强可信度。

视觉上可以把每个详情页做成 6 到 8 个区块，而不是一页短介绍。Figma Make 里可用“横向信息条 + 双栏正文 + 三列卡片 + 流程图 + 边界提示”组合起来，避免页面像简历条目。

## 2. 详情页一：一镜一梳

### Hero

标题：
一镜一梳

副标题：
曼陀罗绘画 AI 解读与自我探索产品

一句话定位：
一个面向 To C 用户的曼陀罗绘画上传与 AI 解读 Web MVP，围绕画作上传、三圈识别、Lite / Pro 报告、付费升级和报告追问构建最小产品闭环。

角色：
创始人 / AI 产品负责人 / 独立开发推进者

时间：
2025 - 至今

标签：
AI 产品、Web MVP、多模态、Prompt Pack、质量门、报告追问

### 页面展开建议

建议做成 8 个区块：

1. Hero：项目定位和角色。
2. 起点：从人工解读耗时和非标准化问题讲起。
3. 产品主路径：上传画作到报告追问的用户路径。
4. AI 工作流：Vision Pass 和 Reasoning Pass。
5. 产品分层：Lite / Pro 的设计取舍。
6. 质量与安全：质量门、追问边界、非医疗表达。
7. 当前产物：已形成的 MVP 主线、报告链路、项目工作区。
8. 能力映射：对应 AI 产品经理和 AI 转型咨询顾问。

适合页面首屏的短文案：

我做的不是一个简单的“AI 看图解读”工具，而是把曼陀罗绘画这个高信任、强体验、难标准化的服务场景，拆成可以被用户自助使用、可以被系统持续迭代、也能被边界控制的 AI 产品主线。

### Context：为什么做

曼陀罗绘画解读是一种高信任、非标准化、强依赖咨询师经验的服务。人工解读通常需要大量时间，且解读质量会受到咨询师经验、表达方式和当次状态影响。

我在一线疗愈学习与个案实践中发现，真正难的不是让 AI “看懂一张图”，而是把图像观察、领域知识、用户议题、表达边界和安全提醒组织成一条稳定的产品链路。

这个项目的起点是一个真实问题：如何把原本偏人工、偏经验性的曼陀罗解读，转成一个用户可自助体验、结果可复用、边界可控制的 AI 产品。

### What I Did：我做了什么

- 定义 To C Web MVP 主路径：上传画作、补充必要描述、生成 Lite 报告、从 Lite 升级 Pro、查看 Pro 内容、围绕当前报告继续追问、查看历史记录。
- 设计 Lite / Pro 产品分层：Lite 面向首次体验用户，Pro 从 Lite 后升级，不提供独立购买入口。
- 拆分报告生成链路：将视觉观察、领域知识、用户意图和输出规范分层处理，避免报告变成简单的“看图说话”。
- 设计报告追问边界：追问只围绕本次画作和本次报告，不做长期陪伴，不做心理咨询，不替代医疗或人生决策。
- 将产品迁入 MindSync（知行工坊）Monorepo 正式工作区，持续完善项目入口、产品规范、知识层、报告契约和交付文档。

### System / Workflow：核心工作流

当前报告生成主线采用两段式思路：

1. Vision Pass：基于用户原画作、三圈标记图和基础知识包，生成可复用的视觉基准。
2. Reasoning Pass：基于视觉基准、主题 prompt pack、输出规范和用户意图，生成 Lite / Pro 报告。

这个设计解决三个问题：

- 同一幅画先形成统一视觉基准，减少不同报告之间的观察矛盾。
- 视觉观察与主题推理分层，方便未来复用同一画作生成不同议题报告。
- 通过输出规范和质量门控制越界表达，保留报告的陪读感和流派感。

### Product Path：用户路径可视化

页面中建议放一个 7 步横向流程：

1. 进入手机端 Web 产品
2. 上传曼陀罗图片
3. 补充少量必要描述
4. 生成一镜 Lite 报告
5. 从 Lite 入口升级一梳 Pro
6. 查看 Pro 报告内容
7. 围绕本次报告向曼曼继续追问

每一步可以配一句设计意图：

- 上传：降低首次体验门槛。
- 描述：补齐图像无法直接判断的主观信息。
- Lite：先给用户一个低门槛反馈。
- Pro：只在用户已经看到价值后再升级。
- 追问：围绕当前报告陪读，不扩展成长期咨询关系。

### Product Decisions：关键取舍

| 取舍点 | 我的选择 | 原因 |
| --- | --- | --- |
| To C / To B / Studio 同时做 | 当前只聚焦 To C Web MVP | 先验证用户主路径，避免产品线发散 |
| Lite 和 Pro 是否独立售卖 | Pro 只从 Lite 后升级 | 让用户先获得低门槛体验，再决定是否深入 |
| 报告是否直接一次生成 | 拆成视觉基准和主题推理 | 降低同一画作多次解读时的观察矛盾 |
| Avatar 是否长期陪伴 | 只围绕本次画作和本次报告 | 控制高信任场景的依赖和越界风险 |
| 是否强调疗愈效果 | 强调自我探索和参考性报告 | 避免医疗化、诊断化表达 |

### Artifact：可以展示的产物

详情页可以展示这些“作品证据”，即使不放真实截图，也可以用抽象 UI 卡片表达：

- To C MVP 用户路径图

### My Role：角色拆解

这个项目中，我不是只承担一个单点角色，而是在早期阶段同时承担四类工作：

- 产品负责人：定义用户路径、产品分层、MVP 范围和付费升级逻辑。
- AI 工作流设计者：拆分视觉观察、知识调用、报告生成和质量检查。
- 独立开发推进者：把产品迁入正式项目工作区，持续推进实现入口和交付文档。
- 高信任场景边界设计者：明确报告追问、avatar persona 和非医疗表达边界。

### Outcome：当前结果

- 已形成清晰的 To C MVP 主线。
- 已梳理 Lite / Pro 报告、付费升级、报告追问和历史记录的产品边界。
- 已形成报告生成 agent、prompt pack、视觉基准复用和质量门设计。
- 已建立正式项目工作区，用文档和项目入口支撑后续持续迭代。

可以在页面里把结果写成三列：

- 产品结果：To C MVP 主路径、Lite / Pro 分层、报告追问入口。
- 系统结果：两段式报告生成链路、prompt pack、质量门。
- 治理结果：项目进入 MindSync（知行工坊）Monorepo，有项目入口、规范和后续迭代路径。

### Relevance：它证明什么

这个项目体现的是我从真实一线服务痛点出发，定义 AI 产品、控制 MVP 范围、设计 AI 工作流和安全边界的能力。

对应 AI 产品经理岗位，它证明我不只会写需求，还能理解技术链路、报告质量、用户路径和上线边界之间的关系。

### Boundary：表达边界

不把它写成心理治疗工具、医疗诊断产品或成熟商业化平台。更稳妥的表达是：

## 3. 详情页二：知行工坊

### Hero

标题：
知行工坊

副标题：
AI 一人公司 Monorepo / 公司工作空间

一句话定位：
一套中文语境下的 AI 一人公司工作系统，用 Monorepo 管理公司治理、项目入口、角色定义、知识库、共享工具和阶段 artifact。

角色：
系统设计者 / 一人公司工作空间搭建者 / Agent 协作机制推进者

时间：

### 页面展开建议

建议做成 7 个区块：

1. Hero：AI 一人公司工作系统。
2. 问题：AI 协作下的信息散落、任务断层、上下文丢失。
3. 系统结构：agents / company / projects / shared / knowledge-base。
4. 工作流：spec、task、QA、delivery、handoff。
5. 运行方式：Paperclip、本地 Codex / Claude Code、文档回写。
6. 当前承载对象：AI 产品、研究、内容、求职材料。
7. 岗位价值：AI 工作流、知识治理、复杂系统产品化。

适合页面首屏的短文案：

我把 AI 协作中最容易散掉的东西放回一个长期系统里：角色、项目、规则、知识、任务和交付物。知行工坊不是一个单点工具，而是一套让一人公司能持续和 AI 协作的工作空间。

### Context：为什么做

当 AI 真正参与长期工作后，问题不再只是“怎么写一个 prompt”，而是信息、任务、角色和项目如何持续保持可追踪。

在多项目并行时，如果所有信息都散落在聊天记录、临时文档和运行时工具里，Agent 很难稳定接手上下文，人也很难判断当前项目到底处于什么阶段。

知行工坊要解决的是一人公司在 AI 协作下的长期运转问题：让公司治理、项目实现、角色分工和知识沉淀有统一入口。

### What I Did：我做了什么

- 设计并落地 MindSync（知行工坊）Monorepo / 公司工作空间。
- 建立 company、projects、agents、shared、knowledge-base 五层结构。
- 建立项目注册表、公司蓝图、研发原则、任务状态流转规则和文档治理入口。
- 将 AI 产品、研究、内容、求职材料等项目纳入统一工作区。
- 基于 Paperclip、本地 Codex / Claude Code 和 artifact-based handoff，设计多角色 Agent 协作方式。
- 将 spec、task、QA、delivery 等阶段产物纳入项目推进闭环。

### System / Workflow：系统结构

五层结构：

1. agents：角色定义，回答谁负责做什么。
2. company：公司治理规则、注册表、蓝图和公司级入口。
3. projects：项目工作区、项目实现和项目级文档。
4. shared：共享脚本、模板和跨项目工具。
5. company/knowledge-base：长期复用知识沉淀。

工作方式：

- 用项目入口文件降低 Agent 接手成本。
- 用公司级规则控制项目边界。
- 用阶段 artifact 管理需求、实现、验证和交付。
- 用知识库把一次性研究沉淀为长期可复用资产。

### Workflow：任务如何在系统里流转

页面中建议用一个“从需求到交付”的流程：

1. 输入：用户想法、项目问题、研究材料或业务判断。
2. Framing：先判断任务属于产品、能力、品牌还是治理。
3. Spec：把模糊目标写成边界清楚的需求或问题定义。
4. Task：拆成可执行任务，明确 owner、状态和验收方式。
5. Implementation：在对应项目工作区内实现，不混入公司级文档。
6. QA：用验证记录确认是否满足目标。
7. Delivery：交付说明沉淀为后续角色可接手的 artifact。
8. Knowledge：长期有效的判断进入知识库。

### System Decisions：关键设计选择

| 设计问题 | 我的选择 | 解决的问题 |
| --- | --- | --- |
| 公司规则和项目实现放在哪里 | company 和 projects 分层 | 避免公司治理和项目源码混在一起 |
| Agent 如何接手上下文 | 每个项目有稳定入口文件 | 减少重复解释和聊天依赖 |
| 任务如何避免只停留在聊天里 | spec / task / QA / delivery artifact | 让工作过程可追踪、可复盘、可交接 |
| 多项目如何保持边界 | 项目注册表和项目工作区 | 避免把品牌、产品、能力混为一谈 |
| 知识如何复用 | knowledge-base 长期沉淀 | 把一次性研究变成可调用资产 |

### Artifact：可以展示的产物

详情页可以放这些模块：

- Monorepo 五层结构图
- 项目注册表截图或抽象示意
- Agent 角色边界示意

- “聊天记录 -> artifact -> knowledge” 转化示意

### My Role：角色拆解

- 工作流设计：把需求讨论、实现、验证和交付整理为可执行链路。

- 知识治理：把研究、项目经验和规则沉淀为长期可复用的文档系统。

### Outcome：当前结果

- 已形成公司级入口和多项目工作区。
- 已承载 AI 产品、研究中心、内容体系和求职项目等对象。

页面里可以用“系统已经能承载什么”来替代夸张结果：

### Relevance：它证明什么

这个项目证明我能把模糊的长期工作拆成系统结构、角色边界和可执行流程。

对应 AI 产品经理岗位，它体现信息架构、工作流产品思维、复杂系统拆解和工程协作理解。

### Boundary：表达边界

不把它写成成熟商业化 SaaS、企业级多人平台或完全自动化公司。更稳妥的表达是：

自用 AI 一人公司工作系统；Monorepo 实践；一人公司操作系统原型。

## 4. 详情页三：曼陀罗疗愈知识库

### Hero

标题：
曼陀罗疗愈知识库

副标题：
从一线解读经验沉淀出的结构化知识体系

一句话定位：
围绕曼陀罗绘画解读场景，将三圈结构、五行对应、颜色与主题观察、解读边界和报告表达沉淀为可复用的知识层。

角色：
体系构建者 / 内容结构化负责人

时间：
2025 - 至今

标签：
知识工程、曼陀罗解读、结构化梳理、AI 知识层、报告标准

### 页面展开建议

建议做成 7 个区块：

1. Hero：结构化曼陀罗知识层。
2. 问题：只有大模型通用理解时，报告容易泛化。
3. 知识结构：三圈、五行、颜色、主题、表达边界。
4. 从经验到知识：一线解读如何变成模块。
5. 从知识到报告：知识层如何进入 Lite / Pro 生成链路。
6. 质量控制：视觉证据、三圈带读、非诊断表达。
7. 能力价值：领域知识建模和 AI 输出质量控制。

适合页面首屏的短文案：

这个知识库的价值，不是把资料堆起来，而是把原本依赖个人经验的曼陀罗解读，整理成 AI 可以调用、产品可以复用、报告可以保持稳定风格的知识层。

### Context：为什么做

AI 曼陀罗产品不能只依赖大模型的通用理解。曼陀罗解读涉及颜色、结构、象征、用户议题和表达方式，如果没有稳定知识层，报告就容易变得泛泛、跳跃或缺乏流派感。

知识库的作用，是把一线个案经验、学习材料和产品输出要求整理成可被产品复用的结构，让 AI 报告不只是“生成一段文案”，而是遵循明确的观察路径和表达边界。

### What I Did：我做了什么

- 将曼陀罗解读中的三圈结构、五行理论、颜色观察和主题表达整理为产品可用的知识模块。
- 从人工解读经验中提炼常见观察维度，服务 Lite / Pro 报告生成。
- 设计报告输出规范，帮助 AI 在观察、解释、建议和边界提醒之间保持稳定结构。
- 配合 prompt pack 和质量门，把知识层纳入报告生成链路。
- 保持疗愈表达边界，避免把自我探索报告写成心理诊断或确定性判断。

### System / Workflow：知识层如何进入产品

知识层不是单独展示的资料库，而是进入 AI 报告生成链路：

1. 用户上传画作并补充必要描述。
2. 系统形成画作视觉基准。
3. 报告生成阶段调用相关知识模块。
4. 输出 Lite / Pro 分层报告。
5. 质量门检查报告是否越界、是否保留视觉证据、是否符合三圈带读逻辑。

这个结构让知识库既服务内容质量，也服务产品稳定性。

### Knowledge Structure：知识模块建议展示

页面可以用 5 个知识模块卡片：

1. 三圈结构：外圈、中圈、内圈分别承载不同观察层次。
2. 五行对应：用东方五行理论提供颜色和主题的解释框架。
3. 视觉证据：颜色、面积、位置、密度、边界和重复元素。
4. 主题表达：把观察转成用户能理解的语言，而不是直接下判断。
5. 安全边界：避免诊断化、绝对化、恐吓式或过度承诺表达。

### Method：从经验到知识层

可以把“人工经验产品化”的过程写成四步：

1. 记录：保留人工解读中的常见观察维度和表达方式。
2. 抽象：把个案语言拆成结构、颜色、主题、建议和边界。
3. 标准化：形成报告章节、字段和输出规范。
4. 接入：把知识模块放入 prompt pack 和质量门。

### Output Standard：报告质量标准

详情页中建议放一组“好报告应该满足什么”的标准：

- 有视觉证据：不是空泛判断，要能回到画面中的颜色、结构和位置。
- 有陪读感：像带用户读懂自己的画，而不是冷冰冰检测结果。
- 有结构：从观察到解释，再到建议和提醒。
- 有边界：避免医疗诊断、心理治疗承诺和决定性建议。
- 可复用：同一套结构能支持 Lite / Pro 分层报告。

- 五行与颜色主题映射示意
- 报告章节结构

- 质量门检查清单
- “人工经验 -> 结构化知识 -> AI 报告”的转化图

### Outcome：当前结果

- 已形成曼陀罗产品知识层的核心方向。
- 已明确三圈结构、五行对应、报告输出规范和质量门的关系。

页面里可以把结果分为三层：

- 工程层：进入 prompt pack、报告契约和质量门，而不是停留在散文资料。
