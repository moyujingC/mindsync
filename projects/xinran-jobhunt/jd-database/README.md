# JD 数据库

这个目录是 `馨冉求职` 的岗位输入层。

目标很直接：把你发来的岗位截图，先转成文字版 JD，再把分析附在后面，逐步积累出一批可比较的岗位样本。

## 目录

- `index.yaml`
  - 岗位总索引，方便快速筛选和汇总
- `taxonomy.yaml`
  - 岗位分类法，统一主轨道、子桶和交叉观察维度
- `jobs/`
  - 每个岗位一份独立记录
- `templates/`
  - 模板文件

## 你怎么用

你只需要做一件事：

- 看到喜欢的岗位，截图发给我

我会负责：

1. 从截图里提取岗位信息
2. 新建一个单独岗位文档到 `jobs/`
3. 更新 `index.yaml`
4. 先写文字版 JD
5. 再把岗位分析接在文字版后面
6. 如果你同时给了 BOSS 竞争力分析截图，也会一起写进该岗位文档
7. 默认把状态写成 `applied`，并补 `applied_at`

## 单个岗位文档结构

每个岗位都单独成一个文档，固定按这个顺序写：

1. frontmatter 元数据
2. 岗位摘要
3. 文字版 JD
4. BOSS 竞争力分析（如果有）
5. 结构化拆解
6. 分析判断
7. 提高匹配度需要补足的能力
8. 简历优化建议
9. 市场信号与暂不执行动作
10. 投递发送消息

这样做有两个好处：

- 后续可以直接做横向对比
- 暂时不把单条 JD 过早绑定到某一版简历

如果某条岗位带有 BOSS 竞争力分析，我们后续会额外追踪两件事：

- 平台给低分的具体位置
- 这条岗位真实上更像哪一种职责桶

这样后面才分得清：

- 是简历表达确实缺东西
- 还是平台算法把岗位分错类了
- 还是岗位本来就是混合画像

## 岗位文档命名规则

建议格式：

```text
YYYY-MM-DD-公司-岗位.md
```

例如：

```text
2026-06-08-字节跳动-AI Builder产品实习生.md
```

如果岗位名里有不适合做文件名的符号，保留主要中文和英文词，去掉多余符号即可。

## 状态字段约定

- 当前这套录入工作流统一使用 `applied`
- `application_status` 表示投递状态，当前默认写 `applied`
- `recruitment_status` 表示招聘状态，默认写 `open`；如果后续确认停招，可手动改成 `closed`
- `applied_at` 默认写录入当天；如果用户明确给出真实投递日期，再按真实日期覆盖
- 历史文档中出现过 `new / parsed / analyzed / archived`，现已统一收敛到 `applied`

## 轨道字段约定

- `ai-pm`
- `ai-consulting`
- `fde`

## 我们后面怎么用这些数据

单条岗位用于：

- 记录真实市场样本
- 判断岗位类型和要求结构
- 看单条岗位的进入门槛和信号
- 判断如果要继续提高匹配度，应补哪类能力和证据
- 沉淀针对该岗位的简历优化方向
- 在文档最后保留一条可直接复制发送的投递消息

多条岗位累积后用于：

- 提炼高频关键词
- 看市场对你的真实要求
- 找出三条求职方向各自的主流要求
- 判断三份可投简历该如何分工
- 再决定是否需要改简历、作品集和自我介绍

## 当前阶段约束

当前阶段先做 JD 积累，不直接针对单个岗位改简历。

原因很简单：

- 招聘平台只能维护少量自定义简历版本
- 逐岗定制的维护成本太高
- 先积累样本，再做共性分析，更适合当前策略

## BOSS 截图建议

如果是 BOSS 上的岗位，后续尽量一次给两类截图：

1. `JD 正文`
2. `竞争力分析`

这样数据库会多一层非常有价值的信息：

- 岗位真实要求是什么
- 平台算法是怎么低估或高估你的

后面做综合分析时，价值会比只有 JD 更高。
