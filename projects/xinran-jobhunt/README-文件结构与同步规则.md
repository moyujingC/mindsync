## 三、阶段评估报告规则

1. 达到共性信号、有效沟通、方向变化或新证据等触发条件时，新建 `delivery/YYYY-MM-DD-求职材料阶段性评估.md`。
2. 阶段报告属于 `support / stage-review`，只承担改前基线、质量判断、改写范围、改后复评和残余风险，不进入 active 投递来源。
3. 报告状态按 `working → current → in_review → historical-reference` 流转，只使用仓库治理规范已有状态。
4. 新一轮必须新建日期文件；旧报告和 [历史评估归档](delivery/2026-08-06-简历评估与改写建议归档/README.md) 不继续滚动修改。
5. 报告发现事实变化时，必须先回写 `职业经历全量报告.md`，不能把报告本身当成新增简历事实的依据。
6. 归档前必须记录 P0 关闭情况、改后复评、QA 结论和残余风险。

## 四、同步规则（事实 → 论点 → 投递材料）

事实或口径变化时，按固定顺序改，一次提交完成：

1. 先改 `职业经历全量报告.md`（事实唯一来源）。**改动即替换**：直接改写对应条目并删除被替代的旧值，不新增"校准 / 增量 / 更新后"章节，不保留旧版本。
2. 涉及能力主张、证据排序或选岗口径 → 改 `三岗位认知卡.md`。
3. 涉及平台在线字段 → 同步 `在线简历母版.md`。
4. 涉及附件投递 → 同步受影响的 `工程版 / FDE 版 / 产品版` 分职位简历。
5. 只影响面试表达或作品展示 → 更新自我介绍、作品集或问答材料，不反向污染事实源。

禁止在某一份简历里单独发明项目事实。

## 五、日常投递轻量流程

看到一个岗位时，不先改简历，只做三步：

1. **判方向**：AI 应用工程师用 `工程版`；FDE / AI 解决方案用 `FDE 版`；AI 产品经理用 `产品版`。
2. **判是否值得定制**：只有目标公司重要、JD 高匹配、HR/猎头明确反馈、或 JD 暴露当前简历硬缺口时，才定制。
3. **最多改 3 处**：标题 / 求职意向、个人优势前 2-3 行、一个项目 bullet 或项目排序。单条 JD 不重写事实源和全套简历。

（以下为检查项）

1. 是否用了正确方向的 active 简历：`工程版 / FDE 版 / 产品版`。
2. 文件名和求职意向是否一致。
3. 电话、邮箱、城市、链接是否正确。
4. 是否出现期望薪资。
5. 是否还有“写作说明 / 投递前删除 / 选岗提醒 / 内部备注”。
6. 支付口径是否为：**内测兑换码模式运行中，在线支付接入中**。
7. 是否出现禁用旧口径：育碧 / Ubisoft、成熟商业化平台、已接入支付系统、医疗诊断、心理治疗。
8. 所有强数字是否能解释来源和统计口径。
9. 项目描述是否通过替换测试：把项目名与业务名词换成任意其他场景后仍成立的描述，属泛化表述，须删改（判据见 [简历评分标准](简历评分标准.md) 1.8 与 [AI产品经理岗位能力补充](AI产品经理岗位能力补充-2026-09-15.md) 第 8 节）。

## 八、附件简历格式规范（2026-09-17 定，源自一次「可读性极差」返工）

> 触发原因：2026-09-17 按 V2 口径重写后，三份附件简历正文膨胀到约 6,900–7,000 字（约 4.9 页），条目写成段落，并混入 `_build_claims()`、`needs_human`、🅥、WF-0x、§4.2 这类内部术语。同时违反 [简历评分标准](简历评分标准.md) 第 4 节「长度与格式：1-2 页；无内部备注；无格式噪声」与「未完成态不占据强证明位」。以下为定稿规范。

### 8.1 硬指标

| 项 | 标准 | 自检 |
| --- | --- | --- |
| 正文篇幅 | ≤3,000 字（≈2 页，按 1400 字/页估算） | 见 8.5 脚本 |
| 单条 bullet | ≤160 字，最多 2 行；超 160 必须拆条或砍细节 | 见 8.5 脚本 |
| 内部备注 | 0 处 | 正则扫 `🅥 / § / D-0\d\d / WF-0\d / 反引号` |

实测（2026-09-17 改写后）：工程版 2,766 字 / FDE 版 3,352 字 / 产品版 3,344 字。

### 8.2 条目写法

1. **数字前置**：可量化结果放在条目前半句（「报告问答 18 问实测锚定 97.8%、安全越界 0 条」而不是「…做了评测」）。
2. **禁止段落式条目**：一个 bullet 里不许塞 ①②③④ 四级内容。真讲不完就拆成两条，或把细节留给面试。
3. **加粗只用于两类**：条目的能力标签（`**设计先行**`）与关键结论（`**一个从不拒绝的校验等于没有校验**`）。不整句加粗。
4. **未完成态不占强证明位**：缺陷、局限、待办放在所属段落的**最后一条**，不用作收尾亮点。想让它当差异化证据，就在「个人优势」里单独起一条，别占项目条目的收尾位置。

### 8.3 分层表述（与认知卡 §0.6 第 4 条同一规则）

写任何 Miro 相关句子前先判定层级，并让文字与层级一致：

- **已跑通**：可给代码与数字（双版本报告、输入预处理黄金集 18/18、报告问答 18 问实测）
- **已设计未实现**：只能写「设计 / Spec / 计划」，不得暗示已实现（问答 Agent 的 6 工具、三层记忆、权限分级）
- **目标值**：必须显式标注「（目标值，待试点回填）」（采纳率 / 编辑率 / 问答使用率 / 交付完成率）

**三层混写是本项目最大的翻车风险**：面试官追问一句「这个数字怎么来的」就会当场崩。

### 8.4 待启用内容的位置

V2 才成立的内容（问答 Agent 最小集 + 来源标注 + 中期记忆）一律放文末专节 `## 附：V2 跑通后并入正文（投递前整节删除）`，**不夹在正文中**。这样正文本身就是一份可直接投递的干净简历，待启用内容只多一次删除动作。
