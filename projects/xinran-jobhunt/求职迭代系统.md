本文定义 `馨冉求职` 的材料迭代闭环。它不替代 [投递期材料迭代工作流](投递期材料迭代工作流.md)，而是在本轮简历评估后，把简历、BOSS、作品集、面试逐字稿、JD 数据库和面试反馈串成一个系统。

## 1. 系统目标

求职材料不再按“临时改一份简历”运行，而是按以下闭环迭代：

> 事实源 → 岗位认知卡 → 公共表达原则 → 分岗位简历 → BOSS 在线字段 → 作品集证据 → 面试逐字稿 → 投递 / 面试反馈 → 下一轮更新。

每次改动先判断影响层级，避免：

- 为单条 JD 大改全套材料。
- 在某一份简历里单独发明事实。
- 把面试口播问题误改成事实问题。
- 把作品集详情塞回简历首屏。
- 因焦虑继续扩张版本。

## 2. 材料层级

| 层级 | 文件 | 职责 | 何时更新 |
|---|---|---|---|
| 事实层 | [职业经历全量报告](职业经历全量报告.md) | 事实、数字、时间线、口径唯一来源 | 出现新事实或旧事实校准 |
| 论点层 | [三岗位认知卡](三岗位认知卡.md) | 三岗位能力主张和证据排序 | 岗位策略或证据排序变化 |
| 公共规则层 | [求职材料公共问题与改写原则](求职材料公共问题与改写原则.md) | 所有材料共享的表达原则 | 多份材料出现同类问题 |
| 附件简历层 | 工程版 / FDE 版 / 产品版 | 分岗位约面材料 | 阶段性共性信号触发 |
| 平台入口层 | [总在线简历-BOSS版](总在线简历-BOSS版.md) | 列表页、初筛、打招呼语 | 平台反馈或方向优先级变化 |
| 作品集层 | [个人职业叙事作品集网站](个人职业叙事作品集网站/README.md) | 项目证据、截图、详情、案例 | 面试追问缺证据 |
| 面试表达层 | [面试逐字稿打磨系统](面试逐字稿打磨系统.md)、[三岗位2分钟自我介绍](三岗位2分钟自我介绍.md) | 开场、追问、FAQ、逐字稿 | 口播卡住或面试反馈出现 |
| 反馈输入层 | JD 数据库 / delivery | JD、HR、猎头、面试反馈 | 每次值得复用的输入出现 |

## 3. 输入分类与处理

### 3.1 单条 JD

默认不改主简历。只做：

1. 判方向：工程版、FDE 版、产品版。
2. 判断是否值得定制。
3. 如需定制，最多改标题、个人优势前 2-3 行、一个项目 bullet 或项目排序。

### 3.2 高频 JD 信号

3-5 条以上 JD 反复出现同类要求时，进入阶段性材料迭代。

常见信号：

- Agent / Workflow / Multi-Agent。
- RAG / 知识库 / 数据治理。
- PoC / MVP / Demo / 原型验证。
- 客户现场 / 方案设计 / 交付。
- 评测 / Guardrails / 安全边界。
- 培训赋能 / SOP / 组织推广。

### 3.3 HR / 猎头反馈

先判断反馈属于哪类：

| 反馈 | 处理 |
|---|---|
| 看不懂岗位定位 | 改 BOSS 首屏或附件简历开头 |
| 质疑经历跨度 | 改公共主线和面试 FAQ |
| 质疑商业化 | 改商业化口径，补数据或降级为内测验证 |
| 质疑技术深度 | 补工程版技术断面和面试 FAQ |
| 质疑客户交付 | 补 FDE 版 PoC / MVP / 验收表达 |
| 对某项目很感兴趣 | 补作品集详情页和项目深挖稿 |

### 3.4 面试反馈

每次面试后至少记录：

1. 对方最关心什么。
2. 哪段表达有效，哪段卡住。
3. 哪份材料需要改。

处理原则：

- 只是口播卡住：改面试逐字稿。
- 缺项目证据：补作品集。
- 简历表达误导：改对应简历。
- 事实不清或数字更新：先改事实源。
- 岗位明显错配：记录，不改材料。

## 4. 修改决策树

```text
出现新输入
  ↓
是否是事实变化？
  是 → 职业经历全量报告 → 影响论点则同步认知卡 → 同步材料
  否 ↓
是否是多次出现的共性问题？
  是 → 公共问题文档 / 分岗位评估文档 → 阶段性改材料
  否 ↓
是否影响当前投递动作？
  是 → 最多定制 3 处
  否 ↓
是否影响面试表达？
  是 → 面试逐字稿 / FAQ / 作品集
  否 → 记录到 JD 数据库或 delivery，暂不改
```

## 5. 本轮评估后的系统改造任务

### 5.1 公共部分

优先执行 [求职材料公共问题与改写原则](求职材料公共问题与改写原则.md)：

- 删除正式简历内部备注。
- 校验时间线。
- 确认模型名称。
- 统一“一镜一梳”的通用表达。
- 降级商业化强表述。
- 压缩 MindSync 个人系统表达。

### 5.2 分岗位简历

按以下文档改：

- [AI 应用工程师简历评估与改写建议](AI应用工程师简历评估与改写建议.md)
- [FDE / AI 解决方案工程师简历评估与改写建议](FDE-AI解决方案工程师简历评估与改写建议.md)
- [AI 产品经理简历评估与改写建议](AI产品经理简历评估与改写建议.md)
- [BOSS 在线简历评估与改写建议](BOSS在线简历评估与改写建议.md)

### 5.3 面试逐字稿

按 [面试逐字稿打磨系统](面试逐字稿打磨系统.md) 拆成：

- 15 秒一句话版。
- 45 秒电话版。
- 90 秒面试版。
- 2 分钟深聊版。
- 风险 FAQ。
- 项目深挖逐字稿。

优先做 FDE 版，因为当前第一主攻是 FDE / AI 解决方案工程师。

## 6. 每周节奏

### 6.1 日常投递

- 不为每条 JD 大改材料。
- 只使用当前 active 简历。
- 投递前执行 60 秒红线检查。
- 有复用价值的 JD 和反馈进入数据库或 delivery。

### 6.2 周评

每周做一次：

1. 汇总 JD 高频词。
2. 汇总 HR / 猎头 / 面试反馈。
3. 判断是否触发公共部分或分岗位简历迭代。
4. 检查作品集是否缺承接页。
5. 更新面试 FAQ。
6. 冻结下一周主攻方向和材料版本。

## 7. 版本控制原则

- 不继续扩张新的简历版本。
- 当前只维护工程版、FDE 版、产品版和 BOSS 唯一在线版。
- 评估文档是工作依据，不直接投递。
- 面试逐字稿是表达训练材料，不作为简历事实源。
- 作品集承接详情，不反向塞爆简历。

## 8. 完成定义

本系统跑顺的标志：

1. 所有正式投递简历无内部备注。
2. 三份简历共享同一职业主线，但岗位表达不同。
3. BOSS 首屏短、清楚、方向不发散。
4. 面试开场有 45 秒和 90 秒版本，不再只背 2 分钟稿。
5. 常见质疑有 FAQ，而不是塞进开场介绍。
6. 每次面试后能明确判断该改事实源、简历、作品集还是逐字稿。
7. 每周只基于共性信号改材料，不因单条 JD 频繁重写。
