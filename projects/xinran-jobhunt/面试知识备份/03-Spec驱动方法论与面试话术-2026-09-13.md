## 0. 一句话定位

**"Spec 驱动"走了三阶段：伪 spec（聊天+补文档）→ 强制流程（多文档多阶段）→ 单一真相源（一份 spec，写完即交 AI）。**

面试官问"你怎么用 AI 写代码"时，这段方法论进化比任何工具名都更能证明你对 AI 编程协作模式的理解深度。

## 0.5 方法论来源（课程查证，2026-09-13）

**主来源**：《极客时间 · 企业级 AI 编程实战营》（2026-07 开营，11 周训练营，本地目录 `courses/2026-07-16-年企业级AI编程实战营/`）

核心方法：**Spec-Kit 四阶段工作流** `/specify → /plan → /tasks → /implement`。

课程的核心对比（直接对应我的 V1/V3 实践）：

| 课程讲的 | 我的实践对照 |
|---|---|
| **普通姿势**：把需求直接扔给 AI，来回改，最后不确定能不能用 | = 我的 V1（伪 spec，对话写代码） |
| **驾驭姿势**：先 spec，再 plan，再 implement，每一步可控，结果可预期 | = 我的 V3（单一真相源 spec，写完即交 AI） |
| **驾驭的定义**：主动权在你手里，AI 在你的框架下执行 | = 我的"spec 一旦定稿，写代码就是 AI 的事" |
| 规范不是一次性的指令，是一套体系；AI 没有长期记忆，单次指令只解决单次质量 | = 我的"单一真相源"动机（V2 来回跳/旧文档干扰的根因） |

**补充来源**：《极客时间 · Claude Code 企业级全链路开发实战》（`courses/2026-04-01-.../`）第 02 集《规范驱动开发（SDD）：让 AI 永远在轨道上》——SDD 定义、四步闭环、规范质量标准（约束 AI 最容易跑偏的四个地方：命名风格 / 返回格式 / 接口路径 / 错误码）。

**我的增量（课程没讲、我实践中深化、面试亮点）**：
1. **概念债**：课程讲"规范约束 AI"，我补了反方向——spec 打磨也约束我自己，强迫把没想清楚的事理清楚，未决事项显性化进待办
2. **只留一份 spec**：课程是"一套体系"，我实践出"单人 + AI 场景下维护一套多文档体系成本过高"——收敛为一份 spec + 内容分层，从根上消除过期文档干扰
3. **写 spec 前可以聊天**：对话是打磨 spec 的手段，不是写代码的手段——边界划分

## 1. 四层 Spec 结构（我的方法论）

> 来源口径：**"这是我在 AI 编程实践中总结的四层 Spec 结构"**——基于 SDD 通用实践提炼整理，不是某一本教材或某一门课的标准分法。面试/文章/简历中主动说明"实战总结"，比声称权威理论更有说服力。

**核心逻辑**：从上到下，从"是什么"到"怎么做"到"怎么验证"，逐层细化。

| 层 | 回答什么 | 核心要点 | 来源依据 |
|---|---|---|---|
| **设计层** | 是什么 / 不是什么 / 边界 | 先定范围再动手；AI 特别喜欢加功能 → 特别强调 **Hard Boundaries（绝对不做的事）** | PRD + 软件设计文档传统实践；Hard Boundaries 提炼自 OpenSpec、Spec-Kit 等 SDD 工具最佳实践 |
| **控制层** | 状态机 / 流转规则 | **AI 编程场景下最关键、最易被忽略的一层**。给人写的 spec 不需要写细状态机（人会处理异常）；给 AI 写的 spec 必须把状态流转写死，否则它只处理正常流程 | 状态机设计模式 + 驾驭工程"操控循环"概念 |
| **工程层** | 技术选型 / 目录结构 / 依赖约束 | 重点反过来——不是"用什么"，而是**"不要什么"**（AI 特别喜欢加依赖、整最佳实践全家桶） | 传统技术设计文档 + 大量 AI 编程实战观察 |
| **验收层** | 测试用例 / 验收标准 | 把 TDD 顺序从"先写测试再写代码"变为"**先写验收标准再让 AI 写代码**"；spec 必须可验证，否则等于没写 | TDD + SDD 核心主张 |

**面试表达（60 秒版）**：

> 我的 spec 分四层。设计层定"是什么、不是什么"，特别强调 Hard Boundaries——因为 AI 特别喜欢加功能，不写死边界它就会自由发挥。控制层是状态机和流转规则，这是我认为最关键的一层：给人写的 spec 不需要写死状态机，因为人会自己处理异常；但给 AI 写的 spec 必须把流转写死，否则它只处理正常流程，遇到边界就乱。工程层重点不是"用什么"而是"不要什么"，因为 AI 喜欢加依赖、整全家桶。验收层是把 TDD 的顺序反过来——先写验收标准再让 AI 写代码，spec 必须可验证，否则等于没写。

**防追问**：

| 追问 | 口径 |
|---|---|
| 四层结构有权威出处吗？ | 是我在 AI 编程实践中基于 SDD 通用实践总结的，不是教材标准分法；不同人有不同分法，但核心逻辑一致：从是什么到怎么做到怎么验证 |
| 控制层为什么最关键？ | 给人写的 spec 不需要状态机（人会处理异常）；给 AI 的 spec 不写死流转，它只会走正常流程，异常和边界全靠你提前写死 |
| Hard Boundaries 举例？ | Miro spec 里写死"MVP 不做上传交互、不做三圈设定、不做 UI 优先"——AI 就不会去"顺手"实现 |
| 和 TDD 什么关系？ | 顺序反转：TDD 是先写测试再写代码；SDD 是先写验收标准再让 AI 写代码——验收标准就是给 AI 的测试用例 |
| 工程层"不要什么"举例？ | 约束依赖：不整全家桶、不加多余库；目录结构写死，AI 不会自己发明分层 |

## 2. Monorepo 约定的查证结果（2026-09-13 实地核验）

**用户记忆**：Monorepo 约定走 "spec、QA、task、delivery" 流程。

**查证结果**：约定在 `/Users/xinran/Downloads/dev/mindsync/AGENTS.md`，准确名称是**重要工作默认阶段门（6 阶段）**：

```text
1. spec 或问题定义
2. task / implementation plan
3. qa basis
4. implementation
5. verification
6. delivery
```

配套约定（面试可引用）：

- **双轨制**：重要工作走 `Harness Engineering + SDD + TDD`；轻量工作允许直接改、直接交付（不强制 artifact）
- **TDD 默认执行**：进入实现前至少写清 目标行为 / 验收标准 / 边界情况 / 验证方式
- **缺失 artifact 的默认动作**：不"边做边补"、不把零散聊天长期当唯一依据、先补最小 spec/task/qa basis、回退给对应 owner
- **完成实现后**：补 qa 验证记录、delivery 交付说明、残留风险、下一阶段 handoff 对象
- **文档生命周期**：区分"当前有效入口"与"历史参考（historical-reference）"；仓库里存在 `日期文档缺状态-人工复核批次`、`仓库文档生命周期清单` 等治理文档——**说明"过期文档干扰"是这个体系的真实痛点，不是你的个人感受**

## 3. Spec 驱动三阶段（核心叙事）

### 阶段一（V1）：伪 spec 驱动——把"单一真相源"放在 spec 里，但代码总是先于 spec

- **做法**：用聊天方式写代码，一开始就想把单一真相源放在 spec 文档里，自认为是 spec 驱动
- **实际发生**：代码经常已经写好、spec 文档还没有；代码更新后反过来补 spec——**spec 永远是滞后的，单一真相源名存实亡**
- **教训**：单一真相源不是"放一份文档在那里"，而是"文档必须先于代码、且始终与代码同步"。滞后的 spec 比没有 spec 更危险（它给你虚假的确定性）

### 阶段二（V2）：强制流程——复杂任务先写 spec，走 spec→task→qa basis→implementation→verification→delivery

- **做法**：在 Monorepo 里强制自己按阶段门走，复杂任务必须先写 spec
- **实际发生**（三个真问题）：
  1. **来回跳**：很多工作不是线性走完 6 阶段，而是在 spec/QA/task 之间来回跳——讨论中改需求、验证中发现 spec 错了、补 spec 又触发新任务
  2. **过期文档干扰**：spec 带日期，文件夹里堆积大量过期 spec，违背"单一真相源"，且旧文档会干扰判断
  3. **形式大于内容**：为了"符合流程"而产出的 artifact 未必真想清楚，反而增加维护负担
- **教训**：**流程的价值在于"想清楚再动手"，不在于"产出多少份 artifact"**。多文档多阶段在单人 + AI 场景下，管理成本超过了约束收益

### 阶段三（V3）：单一真相源——只保留一份 spec

- **做法**：
  1. 只保留一份 spec（不是一份文档，是一个"当前真相"的收口点）——**从根上维护住单一真相源**
  2. 研究 spec 的**内容分层**（不是分文档，是文档内部按层级组织）
  3. **spec 完成前可以用聊天/对话完善它**（对话是打磨 spec 的手段）
  4. **spec 一旦定稿，写代码就完全交给 AI（Codex），中间不再插手**
- **三个收益**：
  1. **AI 编程效率高**：指令精确、边界清楚，AI 不需要在对话里反复猜
  2. **避免"概念债"**：以前很多设计稀里糊涂就让 AI 执行；现在认真打磨 spec 迫使把所有没想清楚的事理清楚
  3. **未决事项显性化**：现在不需要理清的事情，也会写清楚安排进待办——不留隐藏假设

## 4. 面试话术（Spec 驱动 90 秒版）

> 我用 AI 编程经历了三个阶段。最早我以为"把单一真相源放进 spec 就是 spec 驱动"，但实际是聊天写代码、spec 永远滞后于代码——那是伪 spec。第二个版本我强制自己走完整流程（spec→task→QA→delivery），但发现很多工作在这几个环节之间来回跳，而且日期化的 spec 文档堆了一文件夹，过期文档反而干扰判断，违背了单一真相源。到第三个版本我想透了：**我只需要一份 spec，它内部做内容分层，写 spec 之前可以随便聊，但 spec 一旦定稿，写代码就完全是 AI 的事**。这带来两个好处：一是 AI 编程效率大幅提升，因为指令精确；二是倒逼我把概念想清楚——以前很多设计是稀里糊涂就让 AI 执行，现在 spec 打磨的过程就是消除"概念债"的过程。

## 5. 面试防追问清单

| 追问 | 口径 |
|---|---|
| 伪 spec 和真 spec 区别？ | 伪 spec：代码先于文档，spec 滞后、是补丁；真 spec：spec 先于代码，是唯一真相，写完即交 AI |
| 为什么 V2 流程会来回跳？ | 单人 + AI 场景下，讨论中需求在变、验证暴露 spec 错误；多文档多阶段的管理成本超过约束收益 |
| 日期化 spec 的问题？ | 过期文档与现行文档混在一起，违背单一真相源，且会干扰后续判断；只留一份 spec 从根上消除 |
| 一份 spec 怎么组织内容？ | 内容分层（意图/契约/边界/验收/待办），不是分文档；对话是打磨手段，定稿后不再中途插手 |
| "概念债"具体指什么？ | 设计没想清楚就让 AI 执行，AI 产出的是"看似合理但不知为什么"的代码；spec 打磨强制想清楚，未决事项显性化进待办 |
| 和 TDD 的关系？ | Monorepo 约定重要工作走 SDD+TDD：spec 写清目标行为/验收标准/边界/验证方式，实现前测试口径已定 |
| 单人为什么还需要 spec？ | 不是给团队看的，是给自己和 AI 的契约：AI 执行不失控，我复盘有依据 |
