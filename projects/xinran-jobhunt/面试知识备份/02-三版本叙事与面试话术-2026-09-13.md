## 0. 一句话定位

**用三个版本的迭代，讲一个"从 Demo 级到生产级、从对话写代码到 Spec 驱动"的成长故事。**

面试官真正想看到的不是"你做过曼陀罗解读"，而是：你如何用 AI 编程做项目、如何从失败中迭代、如何判断什么重要、如何把项目做成可测试可治理的生产级系统——这三个版本恰好完整覆盖了这条曲线。

## 2. 五条体感 → 技术对照 → 学到什么（面试素材核心）

> 使用方式：每条都是"体感（我发现了什么）→ 原因（为什么）→ 行动（V3 怎么改）"三段式，面试时可以单条展开，也可以串成完整故事。

### 体感一：V1 把时间花在了 UI 上，核心反而花得少

- **体感**：V1 是我第一次用 AI 编程做项目，多年没写代码，靠的是以前传统的软件开发工程经验。结果把大量时间投入了 UI 界面和看似优先级不高的工作，核心的"解读报告生成"花的时间很少——甚至没有拆解环节。
- **技术对照**：V1 有完整的前端（studio / frontend / FigmaCode 主题体系），报告生成是 InsightAgent 的"模板 + 单次 LLM 调用"。
- **学到什么**：**先验证核心能力，再补外围**。大模型能不能把"那件事"做好，应该在 MVP 第一周就回答；UI 是最后一公里，不是第一公里。
- **V3 行动**：MVP 不做上传交互、不做三圈设定等次要功能，聚焦两件事：① 知识库 ② 搭建并跑通 agent。

### 体感二：V2 拆了很多环节，效果反而还不如 V1

- **体感**：V2 我把解读拆成很多很多环节，但无论怎么改，报告效果反而不如 V1（直观对比体感）。后来才决定"不拆中间环节"，改端到端直出。
- **技术对照**：V2 spec 明确记录"不恢复旧 16 stage、不把中间层做成重 JSON 机器"——早期拆解的尝试被废弃；`single_pass_e2e`（单阶段端到端直出）作为 AB 变体上线。
- **为什么拆了反而差（面试防追问）**：
  1. 中间 JSON 环节会丢失/压缩信息，误差逐环累积（前一步的错被后一步放大）；
  2. 模型被中间结构束缚，失去整体判断（写章节时看不到全图）；
  3. 环节越多，prompt 工程成本越高，且每个环节的错误都难归因。
- **学到什么**：**拆解环节 ≠ 提升质量**。是否拆环节应由"质量实测"决定，而不是由"架构洁癖"决定。
- **V3 行动**：V3 的 5 步固定编排（信号→五行→状态→议题→报告）是为了**可观测性**（每步留 trace 供复盘），不是重 JSON 机器；且用黄金集数据（F1 0.821）验证质量，而不是靠体感。

### 体感三：V2 上线后不知道怎么测试，测试特别累，不敢上线运营

- **体感**：功能勉强做完，但报告没有让我踏实测试的方法，哪怕做了本地联调面板也觉得累。
- **技术对照**：V1 质量评估是人工逐节打分（质量评估报告 v1.6.2），V2 有 AB 实验脚本但无系统化黄金集——**每次改 prompt 都要人工重读报告**。
- **学到什么**：**没有自动评估，就没有迭代速度**。不能"凭感觉"判断改好改坏。
- **V3 行动**：自动黄金集评估闭环（11 个案例、状态命中 F1、章节完整率、成本基线 15.6k token/48.7s、一致率），每次改动跑批出数字。

### 体感四：AI 移植 UI 失败，1:1 像素复制做不到，最后重新做了一遍

- **体感**：想把 V1 做好的 UI 移植到 V2，AI 移植后把界面改得面目全非，无法像素级复刻；最后 V2 的 UI 等于重新做了一遍。
- **为什么（面试防追问）**：AI 擅长"从零按精确指令生成"，不擅长"在既有代码上做像素级修改"——修改任务里，模型要理解旧代码的隐含设计意图（间距、层级、状态），指令稍不精确就整体跑偏。
- **学到什么**：**给 AI 的指令要像给工程师的 spec 一样精确**；"重新做一次"往往比"让 AI 移植"更快，因为重新做的指令可以写得非常准确。
- **V3 行动**：彻底 Spec 驱动（SDD）——不靠对话写代码，靠 spec 让 coding agent 执行；同时 MVP 直接砍掉 UI 优先级。

### 体感五：Monorepo 下以为只需移植，实际 AI 移植比重做更慢

- **体感**：V2 采用 monorepo 组织，以为 V1 很多事已实现只需移植；但 AI 做移植时上下文断裂、依赖错位，反而比重新做慢。
- **学到什么**：对 AI 编程而言，"迁移"是高成本操作（要理解两套工程的上下文）；**明确给出目标结构，让 AI 直接按目标写，比让它迁移快**。
- **V3 行动**：新工程从零按 spec 搭建，不迁移旧代码；旧版资产只以"知识内容"形式迁入 markdown 知识库。

## 3. 认知跃迁（面试叙事的高潮）

三版本背后的三条认知升级，建议作为故事的"落点"：

1. **Demo 级 → 生产级**：做到 V2 我才意识到，之前都是 Demo 级——能跑、能看，但不能测试、不能治理、不敢上线。于是专门去学了企业级/生产级做法（FDE 体系、Agent 设计模式、Spec 驱动开发）。
2. **个人工具 → 多租户产品**：一开始纠结要不要做生产级（自己用就像个人工具）；后来想通——**如果我是疗愈师，跑通流程后不可能一对一给其他疗愈师交付，所以一定是多租户产品，知识库由平台方（我）维护**。多租户 → 必然有企业级需求（知识治理、权限、评估、监控）。
3. **对话写代码 → Spec 驱动**：V1/V2 用对话写代码，代码是"失控"的（AI 自由发挥，无法约束）；V3 改为 Spec 驱动——先把设计想透，再用 spec 让 coding agent 快速执行。

## 4. 简历写入建议（FDE 版优先）

### 4.1 项目经历段（建议结构）

```
曼陀罗疗愈 AI 工作台（Miro）｜架构设计 + 工程实现 ｜ 2026-09 至今
- 面向疗愈师的多租户 AI 解读平台：知识库平台方维护，报告生成全自动、可评估
- 本体论驱动知识库：23 个状态本体、8 类文档、10.2 万字符，全量注入 + 来源过滤
- 生成链路：workflow（5 步固定编排）+ Agent 反思内核（规则硬检 + LLM 软审 ≤2 轮）
- 评估闭环：自动黄金集 11 例，状态命中 F1 0.821、章节完整率 100%、成本基线 15.6k token
- 知识治理闭环：新状态发现 → 冲突检测 → 疗愈师人在环审核 → 入库（版本化）
- 迭代史（V1 商业化 → V2 端到端直出 → V3 生产级）：用三版演进证明"评估驱动重构"
```

### 4.2 面试叙事主线（90 秒版）

> 第一版我验证了需求（商业化跑通），但把时间花在 UI 上、核心没拆环节、靠体感判断质量；
> 第二版我拆了环节发现质量反降，于是改回端到端直出，但同时暴露了两个真问题——报告没法自动测试、AI 移植 UI 失败；
> 这两个问题让我意识到之前是 Demo 级，去学了生产级做法（FDE / Spec 驱动 / 本体论）；
> 第三版我把判断想透了：做成多租户疗愈师产品（知识库平台维护），MVP 砍 UI，聚焦知识库 + agent，用本体论组织知识、用 spec 驱动开发、用自动黄金集保证可测试可迭代。

### 4.3 简历避坑

- **不要**并列罗列三个项目的功能清单（像做了三个 demo）；
- **要**用"V1 验证什么 → V2 发现什么 → V3 解决什么"的演进逻辑写成一个连续故事；
- 数字优先（F1、token、章节数、案例数、版本数），体感翻译成可验证事实。

## 5. 面试防追问清单

| 追问 | 口径 |
|---|---|
| 为什么拆环节质量反而下降？ | 中间 JSON 信息损耗 + 误差累积 + 模型被结构束缚；拆不拆由实测决定 |
| 你怎么证明"直出质量高"？ | V2 AB 实验 + V3 黄金集基线（F1 0.821）双重证据 |
| 什么是生产级？你怎么定义？ | 可测试（自动评估）、可治理（知识入库流程）、可观测（trace）、可追溯（版本化）、有安全护栏 |
| 为什么不用检索注入？ | 旧版检索注入有质检阈值 0.7 降级，实测全量灌质量最高；10.2 万字符在窗口内，检索降级为规模开关 |
| 本体论用在哪？ | 知识组织：23 个状态本体 + 状态间关系；让疗愈知识从"散文档"变成"可推演的结构" |
| 为什么 MVP 砍 UI？ | 核心问题是"大模型能不能做好解读"，先验证核心再补外围；UI 是最后一公里 |
| 多租户体现在哪？ | 知识库平台维护（版本化+人在环审核）、评估闭环、安全护栏、来源过滤——为多疗愈师使用设计 |
| AI 编程的协作方式？ | Spec 驱动 vs 对话驱动：对话代码失控（V1/V2 教训），spec 让 coding agent 精确执行（V3） |
