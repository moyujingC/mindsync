# JD 简历优化建议汇总

> 日期：2026-07-13
> 来源：`projects/xinran-jobhunt/jd-database/jobs/*.md`
> 范围：75 份有效 JD 的 `## 简历优化建议`
> 用途：把单条岗位建议收束成后续在线简历、三版岗位简历、作品集和面试材料的修改依据

## 0. 结论

所有 JD 的简历优化建议高度集中在同一个方向：

> 不要再把 AI 经历写成“会使用 AI 工具”，要写成“能从业务场景出发，拆需求、设计 AI 工作流 / Agent / 知识库方案，用原型或 Demo 验证，再通过质量门、数据反馈和跨团队协作推进落地”。

这次汇总不直接触发简历修改。按投递期工作流，单条 JD 不改主材料；只有跨多条 JD 重复出现的信号才进入材料审核。

当前可以进入材料审核的高频信号：

- `业务场景拆解 + AI 工作流 / 产品方案 + 落地推进`
- `跨团队沟通 + 需求拆解 + 原型验证 + 持续迭代`
- `Agent / RAG / 知识库 / Prompt / 质量门`
- `AI Coding / Claude Code / Codex / 快速原型`
- `FDE / AI 转型咨询 / 客户方案 / 交付闭环`

当前必须先补证据再写进简历的信号：

- 强行业经验，例如医疗、金融、制造、游戏、电商、旅行等
- 强工程经验，例如 Python、后端、部署、模型评测、API / SDK、DevTools
- 大规模指标，例如 DAU、增长、商业化收入、组织级 adoption、企业级上线数据
- 大厂 / 头部平台 / 管理岗 / 算法岗等身份型标签

当前不能硬包装的边界：

- 不把未真实承担过的研发、算法、行业专家职责写成已有经验
- 不因单条 JD 改动在线简历母版主定位
- 不牺牲 `AI 产品经理 / AI 转型咨询顾问 / FDE` 三条主线一致性
- 不把探索型 Demo 写成稳定商业化产品
- 不把个人工具使用写成企业级平台上线

## 1. 统计口径

本次读取 `jobs/` 下所有 Markdown JD，排除 `README.md`。

- 有效 JD：75 份
- 读取章节：`## 简历优化建议`
- 读取子段：`### 立刻可优化的表达`、`### 需要新增证据后再写进简历的内容`、`### 不建议为了这条岗位硬改的内容`
- 抽取条目：`立刻可优化` 225 条，`需要新增证据` 232 条，`不建议硬改` 225 条

高频词不是简单词云，而是用于判断材料动作。部分历史 JD 使用了模板化建议，因此这里按“重复主题”归并，不逐条堆叠。

## 2. 立刻可优化的表达

### 2.1 把 AI 工具使用升级成业务落地表达

这是最高频建议，重复出现在 52 份 JD 中。

当前问题：

- 如果只写“熟悉 AI 工具 / 高频使用 AI 工具”，招聘方看不出产品能力。
- 很多岗位关心的不是会不会用工具，而是能否把真实业务任务变成 AI 产品方案。

建议改写方向：

- 从 `会使用 AI 工具` 改成 `能把业务场景拆成 AI 工作流、产品方案和落地步骤`
- 从 `熟悉 Agent / RAG` 改成 `能判断 Agent / RAG 适合解决哪类业务问题，并设计流程、边界和验收口径`
- 从 `做过 AI 项目` 改成 `围绕真实任务完成需求拆解、原型验证、反馈迭代和交付沉淀`

可进入在线简历母版和三版简历的关键词：

- 业务场景拆解
- AI 工作流
- Agent 产品方案
- 知识库 / RAG
- 质量门
- 原型验证
- 反馈闭环
- 跨团队推进
- 交付沉淀

### 2.2 强化跨团队、需求拆解、原型验证和持续迭代

这也是 52 份 JD 反复出现的建议。

岗位共同筛选逻辑：

- AI PM 不只是写 PRD，还要和算法、工程、设计、运营、客户或业务团队一起推进。
- AI 转型咨询和 FDE 更看重从问题到方案、PoC、交付和复盘的闭环。
- Builder 型岗位要求能快速做出可体验的原型，而不是只停留在方案文档。

简历建议表达：

- `负责从业务问题识别、需求拆解、方案设计到原型验证的完整推进`
- `能协同产品、研发、设计、运营或业务方，将 AI 能力转成可落地工作流`
- `通过用户反馈、任务验证和质量门持续迭代 AI 产品体验`

### 2.3 显性保留 Agent / RAG / 知识库 / Prompt / 质量门

这些词已经不是单条岗位偏好，而是横跨 AI 产品、FDE、AI 咨询、企业 AI、AI Native 岗位的稳定信号。

建议处理：

- 在线简历母版：保留完整关键词，方便 BOSS / 猎聘检索。
- AI 产品经理版：重点讲 Agent 产品定义、原型验证、用户反馈和产品边界。
- AI 转型咨询顾问版：重点讲业务流程诊断、知识库、SOP、组织采用和落地路径。
- FDE 版：重点讲客户场景、PoC、RAG、系统集成、验收和交付闭环。

注意：不要堆词。每个关键词最好绑定一个真实项目动作。

### 2.4 AI Coding / 产品工程要从“工具使用”写成“验证能力”

近期 JD 明显增加 `AI Coding`、`Claude Code`、`Codex`、`Cursor`、`Builder`、`Demo`、`原型` 信号。

建议改写方向：

- `高频使用 Codex / Claude Code 完成真实开发和文档任务`
- `基于 AI Coding 工具快速搭建产品原型、验证交互和工作流`
- `能从真实任务中复盘模型失败类型、上下文组织方式和质量门`

当前可以写：

- 高频使用 AI Coding 工具
- 能用 AI 辅助做原型验证
- 能沉淀 Prompt / Context / 质量门
- 能把开发任务转成可复用工作流

当前不要写：

- 完整 DevTools 产品负责人
- 模型评测体系负责人
- 成熟开发者生态商业化经验
- 长期专职工程师履历，除非有真实证据支撑

## 3. 需要补证据后再写进简历

### 3.1 行业经验不能泛化

很多 JD 都建议补行业证据，但不能直接写成已有经验。

需要谨慎的行业：

- 金融 / 保险 / 证券：合规、风控、数据安全、客户经营
- 医疗 / 生命科学：患者管理、医疗合规、复杂流程、可信输出
- 制造 / 汽车 / 供应链：生产流程、质量、排程、设备、供应链系统
- 游戏 / 内容 / 社交：用户增长、留存、内容供给、互动体验
- 旅行 / 教育 / 儿童：垂直用户洞察、内容经验、场景使用频次

简历处理原则：

- 有真实经历的，写成可迁移能力，例如高信任咨询、流程诊断、用户洞察。
- 没有真实经历的，只放到面试准备或岗位分析，不直接写进行业履历。
- 对行业岗位，只能写“能快速进入业务场景并拆解 AI 应用机会”，不能写“具备该行业产品经验”。

### 3.2 工程和模型能力需要分层表达

JD 频繁要求 Python、后端、API、部署、模型评测、LangChain、RAG、Function Calling、DevTools 等能力。

建议分三层处理：

- 已有可写：技术背景、工程协作、AI Coding、工作流设计、RAG / Agent 应用理解。
- 需要补证据后写：本地部署、后端接口、模型评测、API / SDK 产品、开发者工具产品。
- 不应包装：算法训练、模型调优负责人、生产级平台工程负责人。

适合当前简历的表达：

- `具备技术背景，能与工程团队讨论 AI 应用落地路径、数据结构、工具调用和质量边界`
- `熟悉 Agent / RAG / Prompt / 工作流等应用层机制，能转化为产品方案和验收口径`

不适合当前直接写的表达：

- `负责模型训练和调优`
- `主导后端架构设计`
- `负责企业级模型部署`
- `搭建完整开发者生态`

### 3.3 指标和商业化要保守

不少 JD 提到用户增长、商业化、ROI、提效指标、使用人数、上线效果。

当前可以补的证据：

- 项目阶段产物数量
- 工作流覆盖的任务类型
- 交付文档、质量门、复盘记录
- 用户反馈或访谈样本
- 原型验证过程

当前不能硬写：

- 百万 DAU
- 成熟商业化收入
- 大规模企业上线
- 组织级 adoption 数据
- 明确 ROI，除非有真实记录

## 4. 不建议硬改的内容

### 4.1 不为单条 JD 改主定位

重复最多的边界是：不要因为单条 JD 改动在线简历母版主定位。

当前主线仍然是：

- AI 产品经理
- AI 转型咨询顾问
- FDE / AI 解决方案工程师

单条岗位如果偏旅行、儿童教育、医疗、游戏、电商、供应链、AI 售前、模型评测，只能作为定向沟通和面试准备，不应把主简历改成该行业专家。

### 4.2 不把未承担过的角色写成已有经验

这些表达风险高：

- 算法工程师
- 模型训练负责人
- 后端研发负责人
- 医疗产品经理
- 金融 AI 产品负责人
- DevTools 商业化负责人
- 大厂增长负责人
- 组织级 AI 转型负责人

更稳妥的表达：

- `具备技术理解和工程协作能力`
- `能把业务场景转译为 AI 产品方案`
- `能设计工作流、知识库、质量门和验收口径`
- `能用 AI Coding 工具快速验证产品想法`

### 4.3 不牺牲三条主线一致性

JD 建议里反复提醒，不要为了某个岗位把经历写散。

三条主线的统一底层能力应保持一致：

- 业务问题拆解
- AI 产品方案设计
- Agent / RAG / Workflow 应用理解
- 原型验证
- 跨团队推进
- 质量门和反馈闭环
- 交付文档和复盘

差异只体现在排序：

- AI 产品经理版：产品定义、用户任务、原型、体验、迭代。
- AI 转型咨询顾问版：业务诊断、流程改造、SOP、知识库、组织采用。
- FDE 版：客户现场、PoC、系统集成、交付、验收、技术边界。

## 5. 建议进入材料审核的修改点

### 5.1 在线简历母版

建议审核是否补强前三行：

```text
AI 产品经理 / AI 转型咨询 / FDE 复合背景，擅长从业务场景拆解 AI 工作流、Agent / RAG 方案和原型验证路径。长期使用 Codex、Claude Code 等 AI Coding 工具推进真实任务，能沉淀 Prompt、质量门、交付文档和反馈闭环。
```

注意：这只是候选表达，写入前要对照字数和现有版本，不要直接替换全部个人优势。

在线简历母版承担平台检索和第一眼匹配，应该比 PDF 简历更完整地覆盖关键词。它不需要像单个岗位定制版那样极窄，但前三行必须让 HR 看到你不是泛 AI 爱好者。

建议保留的词：

- AI 产品经理
- AI 转型咨询
- FDE / AI 解决方案
- Agent / RAG / 知识库
- AI 工作流
- Prompt / Context / 质量门
- Codex / Claude Code / AI Coding
- 业务场景拆解
- 原型验证
- 跨团队推进

建议减少的词：

- `熟悉 AI 工具`
- `关注 AI 发展`
- `学习能力强`
- `对 AI 有兴趣`
- `有较强沟通能力`

这些词不是不能出现，而是不能单独出现。它们要跟具体动作绑定，例如“用 AI Coding 工具验证产品原型”“把客户问题拆成知识库和工作流”“通过质量门控制输出稳定性”。

### 5.2 AI 产品经理版

建议强化：

- Agent / AI Native 产品定义
- 用户任务和真实反馈
- AI Coding 原型验证
- 产品边界和质量门
- 数据反馈和持续迭代

避免：

- 只写工具名
- 只写愿景
- 把自己包装成算法 PM

AI 产品经理版最应该承接这些 JD 信号：

- `AI Native / Agent 产品定义`：强调你能判断什么任务适合 Agent，什么只是普通自动化。
- `用户任务 / 使用反馈`：强调从真实使用场景出发，而不是只写功能清单。
- `原型和 Demo`：强调用 Codex、Claude Code、Cursor 或低代码工具快速验证。
- `评测和质量门`：强调 AI 产品不是一次性生成，而是要定义输出标准、失败兜底和迭代口径。
- `跨团队协作`：强调和研发、设计、运营、业务方一起推进，而不是只写 PRD。

可以转成简历句子的方向：

- `围绕真实业务任务设计 AI 工作流和 Agent 产品方案，覆盖需求拆解、原型验证、质量门和反馈迭代。`
- `长期使用 Codex / Claude Code 等 AI Coding 工具进行产品原型和工作流验证，能从模型失败类型中反推产品边界。`
- `能够将 Agent、RAG、Prompt、工具调用等能力转成用户可感知的产品流程。`

需要谨慎的方向：

- 不写“主导模型训练”。
- 不写“负责算法调优”。
- 不写“拥有大规模 C 端增长成果”，除非有真实数据。
- 不把曼陀罗 AI 项目包装成成熟医疗、教育或心理诊疗产品。

### 5.3 AI 转型咨询顾问版

建议强化：

- 业务流程诊断
- SOP / 知识库 / 组织赋能
- AI 工具采用路径
- 客户或业务方沟通
- 从方案到落地的最小闭环

避免：

- 泛泛写“帮助企业 AI 转型”
- 没有对象、流程和交付物
- 夸大成大型企业转型负责人

AI 转型咨询顾问版最应该承接这些 JD 信号：

- `业务诊断`：能进入客户或内部业务场景，识别流程问题、知识断点和可自动化环节。
- `方案设计`：把问题拆成 AI 工作流、知识库、SOP、角色分工和落地路径。
- `培训赋能`：把工具使用转成团队可复用的流程，而不是自己单点提效。
- `交付物`：PRD、流程图、SOP、Prompt Pack、知识库结构、验收标准、复盘报告。
- `组织采用`：关注团队是否真的用起来，能否形成迭代机制。

可以转成简历句子的方向：

- `将复杂业务问题拆解为流程、知识库、AI 工作流和可执行 SOP，形成可复用的交付文档。`
- `面向业务团队设计 AI 工具采用路径，覆盖场景选择、Prompt 模板、质量标准和使用反馈。`
- `结合咨询、业务诊断和 AI 产品实践，推动从问题定义到试点验证的最小闭环。`

需要谨慎的方向：

- 不写“服务过大型企业 AI 转型”，除非有真实客户和项目。
- 不写“组织级 adoption 数据”，除非有使用人数、部门范围或持续周期。
- 不把个人工作系统写成客户已上线系统。
- 不把房产咨询经历直接写成企业咨询，应该写成“客户需求诊断、方案设计和 SOP 沉淀的可迁移能力”。

### 5.4 FDE 版

建议强化：

- 客户场景转译
- PoC / Demo / 原型
- RAG / Agent / 工具调用
- 技术边界和工程协作
- 验收、风险和交付复盘

避免：

- 假装自己是纯研发
- 把 AI 工具使用写成生产级部署经验
- 缺少业务现场和交付对象

FDE 版最应该承接这些 JD 信号：

- `客户现场 / 业务现场`：能和业务方一起把问题翻译成系统需求。
- `PoC / Demo / 原型`：能快速做出验证件，而不是只停在方案文档。
- `RAG / Agent / 工具调用`：能理解应用层实现路径，和工程团队讨论边界。
- `验收和风险`：能定义什么叫做可用、什么情况失败、怎么回滚或人工兜底。
- `交付复盘`：能把一次交付沉淀成后续可复用的文档、模板和流程。

可以转成简历句子的方向：

- `具备技术背景和业务沟通经验，能将客户问题转译为 AI 应用方案、PoC 和验收口径。`
- `熟悉 Agent / RAG / Prompt / 工作流等应用层机制，能与工程团队协同判断实现路径和风险边界。`
- `通过原型、质量门和交付文档推动 AI 应用从概念验证进入可复用流程。`

需要谨慎的方向：

- 不写“生产级部署负责人”。
- 不写“后端架构负责人”。
- 不写“模型平台工程师”。
- 不把 AI Coding 使用经验等同于完整工程交付经验。

### 5.5 作品集

作品集比简历更适合承接证据。

建议补 3 类材料：

- `AI 工作流案例页`：从真实任务到流程、Prompt、质量门、交付结果。
- `Agent / RAG 方案页`：展示如何判断场景、设计知识库和工具调用边界。
- `AI Coding 原型页`：展示 Codex / Claude Code 如何支持快速验证和复盘失败类型。

建议每个作品集页面都用同一个证据结构：

- 背景：真实任务或业务问题是什么。
- 目标：要降低什么成本、提高什么效率、减少什么不确定性。
- 方案：用了哪些 AI 能力，例如 Agent、RAG、Prompt、工作流、AI Coding。
- 过程：如何做需求拆解、原型、质量门、反馈迭代。
- 结果：形成了什么可展示产物，例如页面、报告、SOP、Prompt Pack、流程图、验收标准。
- 边界：哪些还只是探索，哪些已经可复用，哪些不能夸大。

作品集优先补证据，不急着做视觉包装。当前 JD 暴露出的主要问题不是“看起来不漂亮”，而是“招聘方需要看到你确实能把 AI 能力落到任务、流程和交付物里”。

## 6. 按岗位线拆解

样本集中在 AI Native、Agent、内容 / 游戏 / 社交 / 电商、AI Coding、用户体验、产品原型、数据反馈。

这条线希望你证明：

- 能定义 AI 产品，不只是用 AI。
- 能从用户任务出发判断产品机会。
- 能做原型、Demo、PRD、反馈迭代。
- 能理解 Agent、RAG、Prompt、模型行为和产品边界。
- 能把 AI Coding 作为验证工具，而不是把工具名堆在简历里。

简历上应该前置：

- 曼陀罗 AI 产品：作为 AI 产品从体验、报告、边界和质量门出发的证据。
- MindSync / AI 工作系统：作为 AI Native、Agent 工作流和 AI Coding 实践证据。
- 游戏 / 工程经历：作为产品工程、交互理解和开发协作证据。

简历上不应前置：

- 保险销售经历本身。
- 过长的房产业务细节。
- 泛泛的“内容创作能力”，除非投内容 / 社交 / 旅行相关岗位。

### 6.2 AI 转型咨询顾问线

样本集中在企业 AI、行业数字化、售前、AI 战略规划、业务流程重构、组织赋能、培训、SOP、客户沟通。

- `组织采用`：AI 布道师、AI 应用推广、AI 应用业务伙伴。
- `高信任行业`：金融、医疗、制造、供应链、汽车。

这条线希望你证明：

- 能听懂业务问题，而不是只讲模型。
- 能把业务流程拆成 AI 工具采用路径。
- 能输出清晰交付物，帮助团队真正使用。
- 能和客户、业务、研发、管理层沟通。
- 能识别哪些需求适合 AI，哪些只是管理或流程问题。

简历上应该前置：

- 房产咨询体系：转译为客户需求诊断、方案设计、SOP、风险控制。

简历上不应前置：

- “大型企业 AI 转型负责人”这种身份。
- 没有证据的 ROI / 降本增效数字。
- 对具体行业的专家身份，例如制造业专家、医疗产品专家、金融科技专家。

### 6.3 FDE / AI 解决方案线

样本集中在客户现场、PoC、系统集成、RAG、Agent、工程协作、交付、部署边界、验收。

- 生产级后端架构能力。
- 本地部署、模型调优、平台工程经验，除非有明确项目。

## 7. 按简历模块拆解

### 7.1 个人优势 / 自我评价

这一段要解决“你到底是什么人”的问题。

建议结构：

- 第一层：三岗位定位。AI 产品经理 / AI 转型咨询 / FDE。
- 第二层：底层能力。业务问题拆解、AI 工作流、Agent / RAG、原型验证、质量门。
- 第三层：证据来源。曼陀罗 AI 产品、MindSync 工作系统、咨询 / 工程 / 创业复合经历。

不要在这里展开过多行业细节。行业细节会让定位发散，除非你投的是定向版本。

### 7.2 核心技能

核心技能建议分组，不要堆一串词。

建议分组：

- AI 产品与 Agent：Agent、RAG、Prompt、工作流、质量门、AI Native、AI Coding。
- 产品与交付：需求拆解、PRD、原型验证、用户反馈、验收标准、复盘。
- 业务与咨询：业务诊断、客户沟通、方案设计、SOP、知识库、组织赋能。
- 技术协作：工程理解、API / 工具调用理解、Codex、Claude Code、Cursor、低代码原型。

谨慎放入：

- Python
- 后端
- 模型部署
- 模型评测
- DevTools
- 商业化增长

这些可以在面试或作品集中解释，简历里没有证据时不要放太靠前。

### 7.3 工作经历

工作经历要把过去的非 AI 经历转译成现在 JD 看得懂的能力。

房产咨询经历：

- 可写成客户需求诊断、风险识别、定制化方案、SOP、经纪人培训。
- 不要写成泛销售。
- 适合 AI 转型咨询和 FDE 线。

自由职业 / 工程经历：

- 可写成需求沟通、技术实现、交付复盘、跨角色协作。
- 不要写成平台级工程负责人。
- 适合 FDE 和 AI Coding / Builder 岗。

创业 / 一人公司经历：

- 可写成产品定义、任务系统、AI 工作流、知识库、质量门、自动化协作。
- 不要写成大型组织级系统上线。
- 适合三条线共用。

### 7.4 项目经历

项目经历要把每个项目变成“岗位证据”。

曼陀罗 AI 产品：

- 适合证明 AI 产品定义、用户体验、报告生成、内容边界、质量门。
- 谨慎避免医疗化、诊疗化、心理治疗化。

MindSync / AI 工作系统：

- 适合证明 Agent 工作流、知识治理、Prompt Pack、任务路由、质量门、交付文档。
- 谨慎避免企业级商用化夸大。

房产咨询体系：

- 适合证明业务诊断、方案设计、客户沟通、SOP、培训赋能。
- 谨慎避免写成 AI 项目，除非明确讲“可迁移能力”。

游戏 / 工程项目：

- 适合证明产品工程、复杂系统理解、跨团队协作、原型实现。
- 谨慎避免写成 AI Coding 产品经验，除非补足当前 AI 工具实践。

### 7.5 作品集入口

作品集入口在简历里不应只是链接。最好给一句“看什么”。

建议表达：

- `作品集包含 AI 产品案例、AI 工作流系统、业务诊断方案和工程交付项目，可展开查看 Agent / RAG / AI Coding / 质量门相关证据。`

如果字数有限，可以拆成：

- `作品集：AI 产品、Agent 工作流、业务诊断和工程交付案例。`

## 8. 证据缺口清单

### 8.1 高优先级补证据

这些证据一旦补上，会同时服务多条 JD：

- AI 工作流案例：真实任务、流程图、Prompt、质量门、输出样例、复盘。
- Agent / RAG 方案案例：场景判断、知识来源、检索逻辑、工具调用、失败边界。
- AI Coding 案例：用 Codex / Claude Code 从需求到原型、调试、验证的过程。
- 质量门案例：如何判断 AI 输出可用、不可用、需要人工复核。
- 业务诊断案例：从客户或业务问题到方案、SOP、交付物。

### 8.2 中优先级补证据

这些用于定向岗位，不必先改主简历：

- 金融 / 保险 AI 场景：合规、客户经营、风险提示、知识库。
- 制造 / 供应链 AI 场景：质量、排程、设备、采购、知识管理。
- 内容 / 游戏 / 社交 AI 场景：角色、互动、内容生产、用户反馈。
- 旅行 AI 场景：行程规划、攻略生成、偏好建模、旅行社交。
- AI 售前场景：客户问答、方案演示、PoC 边界、投标支持。

### 8.3 暂不补证据

这些当前投入产出比不高：

- 大规模 DAU / 增长指标。
- 成熟商业化收入。
- 模型训练和调优。
- 后端架构设计。
- 医疗诊疗产品。
- 大型企业组织级 AI 转型。

它们不是永远不重要，而是当前没有足够事实基础，硬补会伤害可信度。

## 9. 原始建议归并样例

### 9.1 高频模板建议

大量 JD 的建议可以归并为三句话：

- `把个人 AI 工具使用表达升级为“业务场景拆解 + 工作流 / 产品方案 + 落地推进”的描述。`
- `强调跨团队沟通、需求拆解、原型验证和持续迭代，减少泛泛的兴趣或学习表述。`
- `只有真实做过或能现场讲清的技术 / 行业模块，才写进简历。`

这三句话代表当前 JD 数据库的主信号：市场不缺会说 AI 的人，缺能把 AI 放进真实任务并推进落地的人。

### 9.2 岗位关键词建议

不同岗位给出的关键词并不一样，应该分桶处理。

AI Native / Builder：

- AI Native
- Builder
- AI Coding
- Vibe Coding
- 产品原型
- Claude Code / Codex / Cursor
- 快速 Demo

Agent / 工作流：

- Agent
- Multi-Agent
- RAG
- 知识库
- 工具调用
- Prompt
- Context
- 质量门

FDE / 解决方案：

- 客户现场
- PoC
- Demo
- 解决方案
- 系统集成
- 验收标准
- 交付复盘

AI 转型咨询：

- 业务诊断
- 流程重构
- SOP
- 组织赋能
- 培训推广
- 知识库
- AI 工具采用

行业型岗位：

- 金融、医疗、制造、供应链、游戏、内容、电商、旅行等关键词只在定向沟通中使用。
- 主简历里不建议把这些行业都铺开，否则会显得没有主线。

### 9.3 风险边界建议

原始 JD 里反复出现的风险边界可以归并为：

- 不要因为单条 JD 改主简历。
- 不要虚构行业经验。
- 不要虚构工程深度。
- 不要虚构大厂 / 大规模 / 商业化成果。
- 不要把个人工具使用写成企业级平台上线。
- 不要把探索型 Demo 写成成熟产品。
- 不要让三条主线互相打架。

这些边界应该继续保留，因为当前求职材料最需要的是可信度。很多岗位可以通过“可迁移能力 + 诚实边界 + 作品集证据”进入沟通，不需要把每条 JD 都伪装成完全匹配。
