## 使用说明

**STAR 格式**：

- **S（Situation / 情境）**：当时是什么背景 / 情况
- **T（Task / 任务）**：你面临的任务是什么 / 你的角色是什么
- **A（Action / 行动）**：你具体做了什么
- **R（Result / 结果）**：带来了什么结果，尽量量化或说明当前状态

**准备原则**：

- 每个故事能回答 2-3 个不同问题。
- 同一故事可以从不同角度切入。
- 边界提醒用于避免失当表达。
- AI 项目不夸大商业化，不写成医疗 / 心理诊断产品或成熟企业级平台。

## 案例 1：从裁员到技术成熟

**适合问题**：

- 你是怎么成长起来的？
- 你怎么面对不确定性？
- 你为什么能快速进入新领域？

### STAR 展开

**S（情境）**：
2008 年金融危机期间，我入职上海昱泉国际做游戏程序员。入职不到一年，公司 90% 员工被裁员，我也在其中。

**T（任务）**：
作为刚入行不久的新人，面临失业压力，需要在两个月内找到新工作。

**A（行动）**：

- 在家期间没有停止技术积累，持续保持代码编写和新技术学习。
- 主动联系前同事表达求职意向。
- 两个月后，前同事主动内推至维塔士，当时游戏外包行业的头部公司。

**R（结果）**：

- 成功入职维塔士，参与《席德梅尔的海盗》WII 移植等项目。
- 技术底座在那段时间快速建立，包括跨模块开发、Scrum 协作、快速学习和技术文档能力。

**边界提醒**：

- 重点是经历低谷后快速恢复的韧性。
- 不需要把第一段写得过重。

## 案例 2：从程序员到项目经理

**适合问题**：

- 为什么你不只适合执行，也适合推进协作？
- 你如何理解技术和业务之间的翻译问题？
- 你在技术转型的过程中学到了什么？

### STAR 展开

**S（情境）**：
在维塔士做了三年开发后，我对“纯写代码”的局限性有了清晰感知。代码写得好不好是一回事，项目能不能按时、按质量交付是另一回事。

**T（任务）**：
2012 年加入上海笑游，担任项目经理，需要为 MMORPG 项目搭建完整的工程流程体系。

**A（行动）**：

- 调研团队现状，设计适合当时项目的流程方案。
- 搭建 Bug Tracker、版本发布系统和项目流程。
- 推动程序、美术、策划、测试之间的协作和节奏管理。

**R（结果）**：

- 项目流程更可控，版本发布从依赖人工经验变成更稳定的流程。
- 技术背景让我在跟程序员沟通时有更强判断力，也能把技术约束翻译给非技术角色。

**边界提醒**：

- 重点是推进与协作，不是管理头衔大小。
- 可以强调技术背景如何帮助项目判断。

## 案例 3：定制化咨询方案并负责落地

**适合问题**：

- 你如何理解客户需求？
- 你如何在非标场景下结构化问题？
- 你为什么适合做复杂决策支持型工作？

### STAR 展开

**S（情境）**：
2019 年底到 2024 年底，我在上海优诺优诺做房产咨询工作室。当时房产市场信息复杂，客户往往不知道自己真正想要什么。很多人带着“要买大房子”或“要卖高价”的想法来找我，但真实需求往往是“在有限预算内平衡居住体验、资产安全和家庭决策”。

**T（任务）**：
在非标场景下，帮客户梳理真实需求，设计匹配的购房 / 售房方案，并负责落地执行。

**A（行动）**：

1. **需求映照**：不直接给答案，而是用真实市场数据映照客户想法，帮客户看到自己没看到的取舍。
2. **方案设计**：结合资金状况、居住需求、资产安全、市场周期等因素，设计不止一套方案并讲清利弊。
3. **落地执行**：匹配执行人力和行业资源，全程跟踪交易节点，处理突发状况。
4. **长期关系**：交易完成后继续维护关系，依靠专业输出和客户信任获得转介绍。

**R（结果）**：

- 2 经纪人 + 2 助理的产出约等于传统 20 人门店年营收，约 200 万 / 年，成本更低。
- 70% 客户来源于转介绍。
- 工作室不做传统中介撮合，而是以客户利益优先的单边代理模式运营。

**边界提醒**：

- 不要写成传统中介撮合，重点是单边代理和客户价值。
- 不要夸大团队规模，强调效率和方案质量。
- 这段经历的核心是方案设计和执行落地，不是销售业绩。

## 案例 4：独立经纪人孵化体系

**适合问题**：

- 你有搭平台 / 系统化思维的经验吗？
- 你如何设计让新人快速成长的体系？
- 你怎么处理合伙人关系？

### STAR 展开

**S（情境）**：
在优诺优诺运营过程中，我意识到传统房产经纪人成长周期长、流失率高，很多新人 1-2 年都出不来。我们开始思考：能不能设计一套让新人更快进入专业状态的体系。

**T（任务）**：
设计并落地一套经纪人孵化体系，让零基础新人能在约 6 个月内变得专业全面。

**A（行动）**：

1. **分佣模式设计**：设计让经纪人和工作室利益一致的分佣机制。
2. **培训体系建立**：梳理市场分析、需求洞察、交易流程、风控要点等核心知识模块。
3. **资源支持**：整合法务、财务和行业资源，为新人提供起步支持。
4. **长期陪跑**：不只是培训，还持续陪跑，帮助新人度过真实客户沟通和交易节点。

**R（结果）**：

- 零基础新人转行成为独立房产经纪人，成长周期可缩短到约 6 个月。
- 累计孵化 30+ 经纪人，其中部分转行成功，部分转为长期合作关系。
- 这套体系成为工作室的重要能力之一。

**边界提醒**：

- 不要写成大规模管理，重点是小而精的体系。
- 不要夸大商业化结果，强调体系化和陪跑能力。

## 案例 5：从疗愈服务痛点长出 AI 产品

**适合问题**：

- 你为什么会进入 AI 方向？
- 你如何从一线问题走到产品定义？
- 你做 AI 产品不是跟风的依据是什么？

### STAR 展开

**S（情境）**：
2025 年我开始做曼陀罗绘画、家族系统排列等疗愈相关学习和个案实践。这个场景很高信任、很非标准化，服务质量和个人精力高度相关。小红书半个月就能变现，说明需求真实，但如果每个客户都深度人工解读，交付很快会遇到精力瓶颈。

**T（任务）**：
找到一种方式，在不牺牲服务边界和用户体验的前提下，把人工曼陀罗解读流程产品化，提高交付效率。

**A（行动）**：

1. **问题抽象**：从人工解读过程中抽象出可产品化的共性路径：上传画作、识别三圈、生成报告、围绕报告追问。
2. **MVP 收束**：将 AI-Mandala 定义为 To C Web MVP，先聚焦 mobile-web，不扩张 To B、Studio 或完整 App。
3. **报告链路设计**：参与设计 two-pass e2e 报告生成链路，先生成可复用视觉基准，再结合 prompt pack 和输出规范生成 Lite / Pro 报告。
4. **安全边界设计**：明确报告和追问不做心理诊断、医疗建议、投资建议、长期陪伴或重大人生决策。

**R（结果）**：

- AI-Mandala 已形成 To C Web MVP 产品规范和主路径：上传画作、三圈识别、Lite / Pro 报告、付费升级和报告追问。
- 项目从“AI + 疗愈想法”推进为有产品路径、报告链路、质量门和安全边界的 AI 产品实践。
- 该项目证明我能从真实服务痛点出发，定义 AI 产品，而不是只学习 AI 工具。

**边界提醒**：

- 不要把疗愈服务说成医疗、心理治疗或诊断。
- 不要夸大 AI-Mandala 商业化结果。
- 核心是从一线痛点走到产品定义和边界设计。

## 案例 6：设计 MindSync 公司系统

**适合问题**：

- 你如何做系统化思考？
- 为什么你不满足于只解决单点问题？
- 你如何把知识、流程、交付和协作沉淀成长期资产？

### STAR 展开

**S（情境）**：
在同时推进 AI 产品、疗愈实践、内容、研究和求职材料时，我发现信息很容易散落在聊天记录、运行时系统、历史仓库和临时文档里。如果没有稳定入口，AI agent 每次进入项目都像第一次进入现场。

**T（任务）**：
设计并落地一套 AI 一人公司工作系统，把多项目、多角色、知识和执行收束成可管理、可追踪、可交接的整体。

**A（行动）**：

1. **结构设计**：将系统拆成 `agents / company / projects / shared / knowledge-base` 五层，分别承接角色定义、公司治理、项目工作区、共享工具和长期知识。
2. **项目治理**：通过项目注册表管理 product、capability、brand 等对象，保证项目入口和对象边界清楚。
3. **artifact 流程**：将 spec、task、QA、delivery、handoff 等阶段产物固定到项目中，减少只依赖聊天记录的风险。
4. **运行时分工**：区分 MindSync 与 Paperclip，MindSync 承担治理源、文档源、实现源和知识源，Paperclip 承担运行时控制面和任务状态面。

**R（结果）**：

- MindSync 已作为公司内核 + 多项目工作区 Monorepo 使用。
- 支撑 AI-Mandala、RelayHub、馨冉求职等多个项目并行推进。
- 这套系统把 AI 协作从“对话输出”推进到“可追踪、可交接、可验证的工作流”。

**边界提醒**：

- 不要夸大为成熟企业级平台或商业化 SaaS。
- 更适合讲成 AI 一人公司工作系统 / Monorepo 实践。
- 重点是系统化思维和持续沉淀能力。

## 案例 7：RelayHub 模型治理与评测能力

**适合问题**：

- 你如何理解 AI 应用落地中的模型治理？
- 你如何区分开发实验和生产边界？
- 你是否只懂业务，还是也理解 AI 工具链和模型接入？

### STAR 展开

**S（情境）**：
在同时使用多个模型、第三方中转、国产模型和不同 AI 编码工具时，我发现模型使用很容易混在一起：个人开发、产品生产和评测优化如果不区分，会带来隐私、成本、质量和稳定性风险。

**T（任务）**：
定义一套公司级共享模型能力，让个人开发、产品生产和旁路评测各自有清楚边界，并能支持后续模型选择、评测和优化决策。

**A（行动）**：

1. **运行形态拆分**：将 RelayHub v1 拆成 `dev-relay`、`prod-relay/<product>` 和 `eval-sidecar` 三类运行形态。
2. **生产边界定义**：明确心理疗愈应用生产版只允许国产模型，第三方中转不进入生产用户数据主链路，不默认记录正文级敏感数据。
3. **能力边界收束**：v1 只承接 provider 抽象、统一 API 入口、基础鉴权、模型映射、流式透传和 usage / 延迟 / 错误 / TTFT 等基础指标，不做复杂自动路由和企业级管理后台。
4. **控制台信息架构**：围绕 Dashboard、Environments、Providers、Routes、Usage、Eval、Policies、Runs、Settings 组织信息，让控制台服务决策而不是只展示日志。

**R（结果）**：

- RelayHub v1 形成产品与架构定义。
- 明确了开发实验、生产治理和旁路评测三类环境边界。
- 形成对模型接入、评测、成本、隐私和生产风险的系统化判断。

**边界提醒**：

- 不要写成完整 AI Gateway。
- 不要写成已承载大规模生产流量。
- 不要写成已完成智能路由、自动切流或企业级管理后台。
- 重点是模型治理能力和 AI 落地边界意识。
