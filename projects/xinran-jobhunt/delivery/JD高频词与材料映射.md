## 0. 数据口径

本次重建以 `JD 数据库` 为主，不再只依据每日筛选报告做阶段性判断。

- 扫描范围：`jd-database/jobs/` 中 75 份有效 JD。

- 读取字段：frontmatter 中的 `keywords`、`primary_track`、`match_score`、`company`、`role_title`、`captured_at`。
- 读取正文：每份 JD 的 `## 关键词提炼`，按 `业务关键词 / AI 关键词 / 工具关键词 / 行业关键词` 四类处理。

- 输出方式：不做简单词云，按“信号簇”归并同义词，再判断材料动作。

## 1. 当前总判断

JD 数据库里的真实岗位正在集中筛选一种复合能力：能理解 Agent / RAG / 大模型产品机制，能用 AI Coding 和原型工具快速验证想法，能把客户或业务场景转成 PoC、Demo、工作流、知识库和评测口径，并能用 Harness Engineering 把输入、上下文、工具、输出契约、质量门和交付回写组织成稳定工作流。

对馨冉来说，当前材料表达的主线应收束为：

> 从真实业务任务出发，拆解可被 AI 改造的流程，设计 Agent / RAG / Workflow 方案，用 Vibe Coding / 原型 / Demo 快速验证，再用 Harness Engineering、质量门、评测口径、用户反馈和交付文档形成可复用的产品与方案能力。

本次重建不直接触发主材料修改。它只给出哪些信号已经进入“稳定高频”、哪些信号需要人工审核、哪些信号继续观察。

## 3. 业务关键词

- 岗位含义：招聘方希望候选人能把业务问题翻译成 AI 方案，而不是只讲模型或工具。
- 馨冉匹配点：房产咨询里的高信任需求诊断、自由职业工程交付、MindSync 中的任务拆解和交付回写。

## 8. 材料修改触发规则

### 8.1 进入材料审核

出现以下任一情况，进入人工审核：

- 同一信号跨 3-5 条正式 JD 重复出现，并且当前材料没有明确承接。
- 同一信号在 2-3 天内连续出现在新 JD、猎头反馈或面试反馈中。
- HR 或猎头明确说某个表达影响推荐。
- 面试中反复追问某个项目，但简历或作品集没有证据承接。
- 平台竞争力分析持续低估某项能力，且岗位本身确实匹配。

### 8.2 暂不改主材料

出现以下情况，先放入观察：

- 只有单条 JD 提到的个性化要求。
- 来源只是摘要页、聚合页或猎头列表，完整 JD 未核实。
- 岗位明显偏算法、高管、纯销售或传统项目管理。
- 修改会造成项目事实夸大。
- 信号只适合某个高门槛岗位，不适合当前整体投递口径。

| 医疗 / 心理诊疗产品经验 | 曼陀罗不能包装成医疗或心理治疗 | 写自我探索、内容解读、高信任边界 |
| 成熟 DevTools 产品负责人 | 有 AI Coding 使用和工程背景，但缺开发者产品商业化证据 | 写产品工程和 AI Coding 实践 |
| 深度开源社区维护者 | 当前只有 1 个已知开源贡献，自动化贡献项目还在积累期 | 写具体 PR / commit / issue 协作和自动化贡献系统，不写“维护大型开源社区” |
| 飞书产品专家 / 飞书管理员 | 有飞书协作使用和数据分布事实，但不是飞书产品或管理员经验 | 写本地 Markdown + 飞书协作边界、知识库和流程工具理解，不写飞书后台管理经验 |
| 生产级平台架构负责人 | 有部署和云服务器使用，但不是大型平台架构 | 写 Web 产品部署、CI/CD、服务器运维 |

### 12.4 两个主项目的能力承接

| 项目 | 主要证明能力 | 不要承担的能力 |
|---|---|---|
| 曼陀罗绘画 AI 解读产品 | AI 产品 0 到 1、商业化产品路径、AI Builder、Vibe Coding、CI/CD、云服务器部署、知识库、AI 报告生成、质量门、安全边界 | Harness Engineering 主证明、医疗诊疗、成熟规模化商业化 |
| MindSync / 一人公司 AI 工作系统 | AI Native 工作系统、Harness Engineering、SDD、TDD、Agent 工作流、知识治理、任务状态、交付回写、内容生产 AI 工作流、求职材料工作流、多项目治理 | 成熟企业 SaaS、多人企业平台、完全自动化公司 |

当前材料最容易漏掉的是：`AI Builder / AI Native`、`Harness Engineering`、`SDD / TDD`、`CI/CD / 云服务器部署`、`内容生产 AI 工作流`、`状态 / stale / 失败处理`、`开源项目贡献证据`、`本地 Markdown + 飞书协作边界`、`小型 evals 证据`。前七项已有事实基础，适合进入项目经历；`开源` 当前只能写 1 个已举证贡献和自动化贡献项目，`飞书` 应写协作边界而不是产品专家，`evals` 需要先补一个小样。
