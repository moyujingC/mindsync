## 2. 作品一：曼陀罗绘画 AI 解读产品

### 2.1 项目一句话

这是面向 To C 用户的曼陀罗绘画上传与解读 Web MVP，围绕上传画作、三圈识别、Lite / Pro 报告、付费升级和报告追问构建最小产品闭环。

### 2.2 背景问题

曼陀罗解读属于高信任、感性、非标准化的服务场景。人工解读耗时高，公域获客与深度交付之间容易出现精力瓶颈。

项目需要解决的问题不是“让 AI 给结论”，而是：

- 如何让用户上传画作后得到一份可阅读、温和、不过界的报告。
- 如何把人工解读流程变成产品路径。
- 如何在 AI 输出中保留画面证据、三圈带读和安全边界。

### 2.3 我的角色

负责产品定义、MVP 范围控制、用户主路径设计、AI 报告生成链路设计和安全边界梳理。

### 2.4 我做了什么

- 定义 To C 主路径：上传画作 → 生成 Lite 报告 → 从 Lite 升级 Pro → 查看 Pro 权益 → 围绕本次报告继续追问。
- 控制 MVP 范围：当前聚焦 mobile-web 和 To C 主产品，不同时扩张 To B、Studio、V3 实验线和完整 App。
- 设计 Lite / Pro 权益关系：Lite 作为首次体验入口，Pro 只能从 Lite 后升级，不提供独立购买入口。
- 参与设计报告生成链路：先生成可复用视觉基准，再结合 prompt pack、议题规则和输出规范生成报告。
- 定义“曼曼”报告陪读和追问边界：只围绕本次画作和本次报告，不做长期陪伴、心理咨询、医疗诊断或重大决策建议。

### 2.5 当前状态

- 已形成 To C Web MVP 产品规范。
- 当前用户端主入口为手机端 Web。
- 当前主路径覆盖上传、Lite / Pro 报告、Pro 升级、报告追问和历史记录。
- 解读智能体架构采用 two-pass e2e：Vision Pass 生成可复用视觉基准，Reasoning Pass 生成议题报告。

### 2.6 证明的能力

- 从真实服务痛点定义 AI 产品。
- 控制 MVP 范围。
- 用户主路径和付费路径设计。
- Agent / prompt pack / quality gate 工作流设计。
- 高信任场景中的 AI 输出边界意识。

### 2.7 可展示材料 / 来源

- `projects/aimandala/docs/specs/ToC-MVP-产品规范.md`
- `projects/aimandala/docs/architecture/解读智能层-曼陀罗解读智能体架构.md`
- `projects/aimandala/docs/specs/2026-05-30-曼曼-avatar报告陪读与追问-handoff.md`

### 2.8 表达边界

不表达为：

- 医疗、心理诊断或心理治疗产品。
- 已经大规模商业化。
- 已服务大量用户。
- 已完成完整 To B / Studio / App 产品。

## 3. 作品二：一人公司的 AI 工作系统

### 3.1 项目一句话

这是自建的一人公司 AI 工作系统，以 Monorepo 管理公司治理、项目入口、角色定义、知识库、共享工具和阶段 artifact，支撑多个项目并行推进。

### 3.2 背景问题

同时推进 AI 产品、研究、内容、求职材料和系统建设时，信息很容易散落在聊天记录、运行时系统、历史仓库和临时操作里。

如果没有稳定结构，会出现：

- 规则找不到。
- 项目入口不稳定。
- Agent 每次都像第一次进入现场。
- 交付物无法追踪和复用。

### 3.3 我的角色

负责系统设计、信息架构、项目注册表、文档治理、角色边界和 AI 协作流程设计。

### 3.4 我做了什么

- 将系统拆分为 `agents / company / projects / shared / knowledge-base` 五层。
- 用项目注册表管理 product、capability、brand 等对象。
- 将 spec、task、QA、delivery、handoff 等阶段 artifact 固化到项目中。
- 区分该系统与运行时环境的职责：该系统是治理源、文档源、实现源和知识源，运行时环境是控制面和任务状态面。
- 用 Docs as System 的方式，让 AI 协作不只停留在聊天输出，而能沉淀为可交接、可验证、可回写的工作流。

### 3.5 当前状态

- 已作为公司内核 + 多项目工作区 Monorepo 使用。
- 已承载公司治理、角色定义、项目入口、共享工具和长期知识库。
- 已用于 曼陀罗绘画 AI 解读产品、馨冉求职等多个项目的持续推进。

### 3.6 证明的能力

- 复杂系统拆解。
- AI 协作流程设计。
- 知识治理。
- 多项目管理。
- 文档即系统。
- 把模糊任务转成可分派、可验证、可交接的工作流。

### 3.7 可展示材料 / 来源

- `AGENTS.md`
- `COMPANY.md`
- `MONOREPO.md`
- `company/knowledge-base/system/一人公司的 AI 工作系统-设计机制分析.md`

### 3.8 表达边界

不表达为：

- 成熟企业级 SaaS。
- 已商业化客户系统。
- 大团队协作平台。
- 完全自动化 Agent 公司。

## 4. 作品三：房产定制化方案与经纪人孵化体系

### 4.1 项目一句话

在房产咨询工作室中，以单边代理和客户利益优先为原则，为客户提供定制化房产方案，并将一线服务经验沉淀为经纪人孵化和培训体系。

### 4.2 背景问题

房产交易是高金额、高风险、高信任的复杂决策。客户表面上常说“想买大房子”或“想卖高价”，但真实问题往往涉及家庭关系、资金安全、资产配置、居住体验、市场周期和交易风险。

### 4.3 我的角色

创始合伙人、一线业务打样者、咨询方案设计者和后期经纪人孵化体系参与者。

### 4.4 我做了什么

- 用真实市场数据映照客户需求，帮助客户识别表层诉求背后的真实取舍。
- 为客户设计买房、卖房、信贷、装修、售前美化、民宿运营、出租管家等方案。
- 负责落地推进，整合执行人力、行业资源、交易节点和风险控制。
- 后期参与建立经纪人孵化体系，提供分佣模式、知识库、SOP、法务财税和长期陪跑支持。

### 4.5 结果

- 2 经纪人 + 2 助理产出约等于传统 20 人门店年营收，约 200 万 / 年，且成本更低。
- 70% 客户来源于转介绍。
- 累计孵化 30+ 经纪人。
- 零基础新人成长周期可缩短到约 6 个月。

### 4.6 证明的能力

- 高信任需求洞察。
- 定制化方案设计。
- 复杂流程推进。
- 资源整合和风控。
- 培训体系和知识沉淀。
- AI 转型咨询岗位所需的业务理解与落地陪跑能力。

### 4.7 可展示材料 / 来源

- `projects/xinran-jobhunt/职业经历全量报告.md`
- `projects/xinran-jobhunt/specs/2026-04-27-职业叙事基础档-SPEC.md`
- `projects/xinran-jobhunt/delivery/2026-04-29-核心STAR案例库.md`

### 4.8 表达边界

不表达为：

- 传统中介撮合。
- 大规模组织管理。
- 标准化 SaaS 产品。
- 管理几十人团队。

## 5. 作品四：主机游戏开发项目

### 5.1 项目一句话

在维塔士参与主机游戏移植、自研引擎和跨平台 AAA 项目开发，涉及 Wii、PS3、Xbox 360 等平台。

### 5.2 背景问题

AI 产品经理不能只写需求文档。判断技术可行性、理解工程约束、评估交付风险、和技术团队有效沟通，都需要真实的工程经验打底。

这三个项目分别代表了三种不同的工程难度：把经典 PC 游戏适配到体感主机、在自研引擎上做平台优化、以及跨五个平台同时交付一款 AAA 动作冒险游戏。

### 5.3 我的角色

游戏开发工程师，在跨职能团队中与策划、美术、测试协作。

### 5.4 我做了什么

- **《席德梅尔的海盗》Wii 移植**：该项目由 2K China 与维塔士联合开发、2K Games 发行。参与将 PC 策略 / 动作冒险体验适配到 Wii 平台，涉及 UI 适配、迷你游戏交互、游戏逻辑和 Wii Remote 体感操作调整。
- **达芬奇引擎 Wii 版开发与优化**：参与公司自研游戏引擎在 Wii 平台上的适配和优化，接触主机平台引擎开发、渲染管线、工具链和跨平台工程问题。
- **《Generator Rex: Agent of Providence》跨平台 AAA 项目**：该项目由维塔士内部团队完整开发、Activision 发行，支持 PS3、Xbox 360、Wii、3DS、DS 五个平台。参与多平台动作冒险游戏开发，涉及 UI、战斗、渲染、网络同步、游戏逻辑、特效、美术工具等多个模块。
- 持续撰写技术文档，与策划、美术、测试协作。

### 5.5 技术栈与平台

- 语言：C++、Python、C#
- 平台：Xbox 360、PS3、Wii
- 开发方式：Scrum，约 6-7 程序员 + 2 策划 + 多美术

### 5.6 证明的能力

- 真实工程实现经验，能理解技术方案、模块边界和开发成本。
- 跨平台适配和引擎开发经验，理解不同平台的工程约束。
- 跨模块协作：UI、游戏逻辑、渲染、网络同步、工具链都在实际项目中接触过。
- 在跨职能团队中持续协作和撰写技术文档的习惯。
- 这些经验后来成为判断 AI 产品工程可行性、工作流设计和交付风险的基础。

### 5.7 表达边界

不表达为：

- 现在还是活跃的游戏开发工程师。
- 独自负责整个项目或技术方案。
- 与当前 AI 方向无关的纯技术炫耀。

重点是：这段经历让你能和技术团队平等对话，能理解工程约束，能把技术判断带入 AI 产品决策。
