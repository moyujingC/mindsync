## 2. 项目一逐字稿：AI 曼陀罗解读 Web MVP

### 对方问：Tell me about a recent AI project.

```text
One recent project is an AI mandala interpretation web MVP.

It started from a real service problem. Manual interpretation takes a lot of time, is difficult to standardize, and depends heavily on the experience of the practitioner. I wanted to see whether we could turn this service into a product workflow that is more consistent, more testable, and safer for users.

The user journey is simple: a user uploads an artwork, the system recognizes the three-circle structure, generates a Lite report or a more detailed Pro report, and then allows follow-up questions about that same report. We also keep the report history.

My role is product lead and development driver. I define the user flow, the scope, the report structure, the AI output rules, evaluation logic, and acceptance criteria. I also work hands-on with AI-assisted development for implementation and integration.

On the AI side, I designed a two-pass workflow. In the first pass, we create visual grounding for the artwork. In the second pass, we combine that grounding with user intent, a topic-specific prompt pack, and output rules to generate the report.

The reason for this design is that we do not want the model to produce different or conflicting observations about the same artwork in different reports. The visual grounding gives us a more stable base, and the second pass focuses on explanation and user-facing language.

Because this is a high-trust scenario, quality and safety are very important. I designed output contracts, fixed samples, golden reports, quality checks, and human-review boundaries. We define what the AI can generate, what needs human judgment, and what should be handed off rather than answered by the system.

**The main lesson for me is that an AI solution is not just a model call. It needs a clear workflow, clear output criteria, safety boundaries, and a way to validate quality over time.**
```

### 对方追问：What was the most difficult part?

```text
The most difficult part was not generating text. The difficult part was making the output stable, useful, and safe.

In a high-trust scenario, an answer can sound convincing even when it is too general or goes beyond what the system should say. So I separated visual grounding from reasoning, added output rules and quality checks, and defined cases that require human judgment.

This made the workflow easier to test and easier to improve over time.
```

### 对方追问：What did you personally implement?

```text
I personally drive the product and delivery workflow. I define the scope, the user journey, the prompt and output requirements, the evaluation approach, and the acceptance criteria.

I also use AI-assisted development for implementation, integration, debugging, documentation, and verification. I am careful to distinguish what I have personally implemented from what I have designed or validated. For deeper infrastructure or algorithm topics, I will be transparent about my current level of hands-on experience.
```

## 3. 项目二逐字稿：AI 一人公司工作系统

### 对方问：How do you use AI coding tools in practice?

```text
The second project is an AI work system that I built for my own company. It is also my practical environment for using AI coding tools in a structured way.

The problem was that long-running AI work can easily become fragmented. Important context stays in chat, project rules are scattered, and it becomes hard for people or AI agents to take over a task reliably.

I built a monorepo structure with five layers: agents, company rules, projects, shared tools, and a knowledge base. Each project has a clear entry point. We use structured artifacts for specification, task planning, QA, delivery, and handoff.

In practice, I use Codex and Claude Code for implementation, debugging, documentation, and verification. But the key is not only generating code. Before an important change, I define the target behavior, task boundary, acceptance criteria, edge cases, and verification method. After implementation, I review the changes and keep QA and delivery records.

For example, AI output can start from a discussion, but it should not remain as an isolated chat response. When appropriate, it becomes a project file, a test or verification record, a delivery note, or reusable knowledge.

**My practical understanding is that AI coding becomes more reliable when the model has a stable operating environment, not only a single prompt.** That environment includes project context, role instructions, specifications, task boundaries, quality checks, and a clear way to verify results.

This is an internal working system, not a finished enterprise SaaS product. But it is a real test bed where I practice making AI-assisted work more traceable, controllable, and reusable.
```

### 对方追问：How is this related to SDD or Harness Engineering?

```text
The core idea is very close. For important work, I do not begin with an open-ended prompt. I first clarify the problem, expected behavior, boundaries, acceptance criteria, edge cases, and verification method.

Then I give the AI a structured context: project entry points, role instructions, relevant documents, and the task boundary. After the change, I verify the result and keep a record.

I have practical experience with this specification-driven way of working. I would be transparent that I have not yet led a large enterprise-wide rollout of a specific SDD platform. But I can show how I use these ideas in real project work to reduce ambiguity and improve reliability.
```

### 对方追问：How do you ensure quality when using AI-generated code?

```text
I do not treat AI-generated code as automatically correct. First, I make the expected behavior and acceptance criteria clear. Then I review the implementation, check the main path and edge cases, and run the relevant verification.

The level of automated testing varies by project. For important changes, I use test-first thinking: what should happen, what can go wrong, and how will we verify the result? I am continuing to strengthen the automated-testing side, while keeping quality checks and delivery records in the workflow.
```

## 4. 客户场景与交付能力逐字稿

### 对方问：Do you have customer-facing or delivery experience?

```text
Yes. Before my recent AI work, I co-founded a real-estate consulting business focused on complex and high-value client decisions.

The work was not simply selling a product. We needed to understand the client's goals, budget, constraints, risks, financing situation, and the different people involved in the process. Then we designed a workable plan and coordinated clients, owners, banks, renovation teams, and other partners.

Over time, we turned repeated frontline experience into SOPs, knowledge bases, risk checklists, and training materials. We also built a training system for new agents.

With two agents and two assistants, the business generated around RMB 2 million in annual revenue. We served more than 150 high-net-worth clients, and about 70 percent came from referrals.

This is relevant to FDE work because I am comfortable starting with an unclear customer problem. I know that a useful solution has to fit the real workflow, ownership, data and risk constraints, not just look good in a demo.
```

### 对方问：What would you do when a customer request is unclear?

```text
I would not start by choosing a tool. First, I would clarify the business goal, the current workflow, the users, the available data, the main constraints, and the success criteria.

Then I would identify one small but valuable use case. I would propose a pilot with a clear scope, owner, timeline, risk boundary, and acceptance criteria.

After the pilot, I would review the result with the customer: what worked, what did not work, what data or process issue remains, and whether the solution should be expanded, adjusted, or stopped.

This approach helps the team learn quickly without overcommitting at the beginning.
```

## 8. 朗读标记与练习顺序

### 朗读规则

- `/` 表示可以停半秒：`First, I clarify the goal / then I define the scope.`
- 加粗句是每段最该记住的一句；只要这句和前后 1 句说出来，就能继续对话。
- 专有词说不顺时，直接用简单词替代：`specification-driven development` 可以说成 `a structured way of working`；`acceptance criteria` 可以说成 `clear checks for success`。

### 今晚练习顺序

1. 先朗读第 1 节三遍，目标 90 秒以内。
2. 朗读第 2、3 节，每节各两遍；不要追求一字不差。
3. 只练第 5 节四个问题，每题 30 到 45 秒。
4. 最后朗读第 7 节，把它当作不会英语时的“安全按钮”。
