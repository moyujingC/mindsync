# 求职材料公共问题与改写原则

> 状态：working
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-08-05

本文沉淀本轮 Agent 集群评估后的公共结论，用于先改所有简历、BOSS 在线字段和面试表达中的共有问题。它不新增事实，只定义表达和裁剪原则。

## 1. 总体判断

当前求职材料的素材质量高，主线成立：

- 早期 9 年工程研发，能理解系统、代码、部署和工程协作。
- 中期 7 年高信任服务创业，能处理复杂客户、真实约束、风险边界和付费结果。
- 近 2 年 AI 应用实践，已上线可演示产品，具备模型链路、评测、安全边界和商业化意识。

公共问题不是“没有东西写”，而是“写得太满、解释欲太强、个人项目色彩偏重、证据还不够外部化”。正式投递材料应从“完整证明我很强”转成“招聘方快速判断我适合这个岗位”。

## 2. 统一职业主线

所有版本应统一使用同一条底层主线：

> 长期处理复杂、非标准问题：早期用工程能力完成商业项目交付，中期在高信任客户现场做需求诊断和服务标准化，近两年把专家经验和业务流程转化为可运行、可评测、可交付的 AI 应用。

面试口播可压缩为：

> 我的主线是把复杂、非标准的问题拆成可交付、可复用、可验证的系统。

这条主线分别映射到三类岗位。这里的映射只决定简历、BOSS 和面试表达中的“翻译方式”，不反向决定 [三岗位认知卡](三岗位认知卡.md) 的岗位本质、能力主张和证据排序；若后续发现这里与认知卡冲突，应先回到认知卡重新确认，再同步更新本文。

| 方向 | 主线翻译 |
|---|---|
| AI 应用工程师 | 把复杂 AI 产品链路实现为可运行、可测试、可部署、可排障的系统 |
| FDE / AI 解决方案工程师 | 把客户现场的模糊问题拆成可验证 PoC、可交付 MVP、清晰边界和可复用方案 |
| AI 产品经理 | 把真实用户问题转化为可上线产品路径、可验证 MVP、AI 输出评测机制和商业化反馈闭环 |

## 3. 所有正式投递材料的 P0 修改

### 3.1 删除内部写作说明

正式简历、BOSS 字段、对外材料不得出现：

- 写作依据
- 裁剪原则
- 口径自查
- 可读性原则
- “未成交不包装”
- “所有数字均可解释统计口径”
- “投递前删除”
- “本人反馈后修订”

这些内容适合内部协作，不适合招聘方阅读。外部看到会降低正式感，并触发“包装口径”的警觉。

### 3.2 校验时间线

当前多份材料中存在需要统一解释的时间线：

- 一人公司 / AI 产品独立开发者：2025.01 - 至今。
- MindSync：2026.01 - 至今。
- 一镜一梳工程化三阶段：2026.02 / 2026.03 / 2026.04 至今。

如果 2025.01 是真实起点，需在事实源中明确 2025 年承担的是学习、服务实践、需求验证、产品探索，避免招聘方误解为“2025 开始做产品，但 2026 才有项目”。

### 3.3 确认模型名称

“DeepSeek V4”需要校验是否为官方或平台可核验名称。若不是，应改成平台展示名或更保守的“DeepSeek 系列推理模型”。模型名不准确会直接损伤工程可信度。

### 3.4 不把“在线支付接入中”放在首屏强证明位置

“在线支付接入中”是真实状态，但在招聘材料首屏里属于未完成状态，容易削弱上线确定性。公共字段优先写：

> 已完成 Lite / Pro 分层定价与内测兑换码验证，当前重点验证报告价值感、用户理解成本和后续付费转化路径。

如需保留支付状态，放项目状态或面试口径中，不放个人优势第一屏。

## 4. 争议词的统一处理

### 4.1 “曼陀罗 / 疗愈 / 家族系统排列”

这些词真实，但在泛 AI 岗位中有误读风险。处理原则：

| 场景 | 写法 |
|---|---|
| 泛 AI 工程 / FDE / 产品 | 多模态图像理解 + 个性化报告生成产品 |
| 需要解释真实场景时 | 面向用户手绘图像输入的 AI 辅助解读工具 |
| 垂直疗愈 / 内容 / 陪伴岗位 | 可保留曼陀罗和疗愈，但必须同步强调非医疗、非诊断、安全边界 |
| 教育培训栏 | 泛 AI 版本可删除“家族系统排列”，垂直版本按需保留 |

推荐通用句：

> 一镜一梳本质是一次“专家经验 AI 产品化”实践：将人工解读中的观察、推理、边界判断和追问反馈拆成可执行链路，用 AI 报告承接标准化交付。

### 4.2 “一人公司 / 独立开发者 / 产品负责人”

这些词有差异化，也有组织适配风险。所有版本都应增加“可进入组织协作”的信号。

推荐句：

> 过往同时具备一人产品闭环、4 人创业团队经营、12 人研发团队管理和开源社区协作经验，能在小团队中承担产品 / 交付牵引角色，也能围绕公司业务目标与工程、运营、创始人高频协作。

### 4.3 MindSync / Monorepo / Agent / commit 数字

MindSync 是资产，但在简历中容易喧宾夺主。处理原则：

- 少写“五层 Monorepo、9 个职能 Agent、2200+ commits、70+ 天复盘”。
- 多写“如何支撑需求、任务、验证、交付、复盘的可追踪流程”。
- commit 数字不作为主结果，最多作为辅助证据。

推荐句：

> 搭建 AI 辅助研发与文档治理流程，将需求、规格、任务、质检、验证和交付沉淀为可追踪文档流，减少 AI 协作中的上下文断裂和质量不可追踪问题。

## 5. 证据补强清单

下一轮全套材料最缺的是“小而硬”的外部化证据。

优先补：

- 内测用户数。
- 生成报告份数。
- 兑换码使用数。
- 执业疗愈师试用人数。
- 有效反馈条数。
- 基于反馈完成的迭代轮次。
- 小红书线索 / 咨询 / 服务转化数量。
- AI 辅助前后人工解读耗时变化。
- golden case 覆盖类别和评测维度。
- 单份报告 token 成本或生成耗时。
- 模型失败 / 降级触发的判断标准。

没有成熟商业数据时，不要包装成商业闭环，应写“内测验证阶段”。

## 6. 材料分工

| 材料 | 职责 | 不承担 |
|---|---|---|
| 职业经历全量报告 | 事实源 | 不写招聘话术 |
| 三岗位认知卡 | 岗位论点和证据排序 | 不直接投递 |
| 附件简历 | 岗位匹配和约面 | 不讲完整作品集 |
| BOSS 在线简历 | 列表页吸引和初筛匹配 | 不压缩全部履历 |
| 作品集 | 承接证据、截图、项目详情 | 不替代简历 |
| 面试逐字稿 | 引导面试官追问强项 | 不在开场解释所有风险 |

## 7. 本轮公共改写优先级

1. 删除所有正式简历顶部内部备注。
2. 统一职业主线，把“经历跨度大”改写成“复杂问题系统化”。
3. 将“一镜一梳”统一翻译为“多模态 AI 解读产品 / 专家经验 AI 产品化”。
4. 将“商业化验证”降级为“商业化路径设计 + 内测验证”，除非补充真实付费数据。
5. 压缩 MindSync 和 commit 数字，转成“AI 协作交付流程”。
6. 为工程版补系统结构、评测维度、生产运行证据。
7. 为 FDE 版补客户现场、PoC / MVP、验收口径。
8. 为产品版补用户验证、团队协作、迁移能力。
9. 将面试材料拆成 15 秒、45 秒、90 秒、2 分钟四层，不再只维护 2 分钟稿。
