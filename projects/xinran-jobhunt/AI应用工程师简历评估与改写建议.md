## 1. 总体判断

AI 应用工程师简历已经区别于普通“AI 使用者”或“课程 Demo 候选人”。它呈现的是：

> AI 原生独立产品开发者 + 早年工程背景 + 高信任服务业务经验。

最适合投递 AI 应用工程师、大模型应用工程师、Agent 应用工程师、AI 产品工程师、全栈 AI Engineer、早期 AI 产品团队技术合伙型岗位。

不适合直接投算法工程师、大模型训练工程师、大模型平台工程师、纯后端高并发岗位、标准 Java / Python 中高级后端岗。

当前最大问题是：工程可信度证据还不够均衡。AI 项目写得强，但系统结构、评测指标、生产运行、Agent 机制等可核验细节需要补足。

## 2. 会不会约面

| 岗位类型 | 约面概率 | 判断 |
|---|---:|---|
| AI 应用工程师 | 高 | 有真实上线产品和完整链路 |
| 大模型应用工程师 | 中高 | 需补 prompt / 评测 / 成本 / 上下文工程 |
| Agent 应用工程师 | 中高 | 需澄清 Agent 执行机制，不只写角色提示词 |
| AI 产品工程师 | 高 | 业务 + 工程 + AI 组合强 |
| 传统后端工程师 | 中低 | 近年企业团队工程证据不足 |
| 算法 / 平台 / MLOps | 低 | 岗位主要求不匹配 |

## 3. 最大优势

最大优势是：

> 不是只会调用模型，而是能围绕真实业务场景，把多模型链路、评测、降级、安全边界、部署和产品闭环完整做出来。

强证据：

- 上线产品 web.jingshu.cc。
- 完整链路：上传、识别、报告、追问、历史记录、部署。
- 多模型链路：视觉模型 + 推理模型 + 兜底模型。
- 模型选型：GLM 经 9 张测试图 × 3 轮稳定性评测后淘汰。
- 质量控制：5 组 golden case、16 阶段离线原型。
- 生产化信号：Nginx + HTTPS、COS 私有存储、签名 URL、CI、冒烟测试。
- 公开工程物证：paperclipai/paperclip 5 个 PR。

## 4. 最大风险

### 4.1 强词缺少机制

当前简历中有不少强表达：

- 生产级防御工程
- 每晚自动冒烟测试与自动修复
- Monorepo 五层结构
- 9 个职能 Agent
- 六阶段交付门
- 16 阶段解读智能体
- 标准测试集
- 输出安全边界

这些词需要机制支撑。技术面试官会追问：

- 自动修复具体修什么？
- 冒烟测试覆盖哪些路径？
- golden case 如何判定通过？
- 降级触发条件是什么？
- 安全拦截是 prompt、规则还是模型分类？
- 是否有日志、告警、错误率、生成耗时、token 成本？

如果答不硬，强词会反噬可信度。

### 4.2 工作经历和项目经历重复

一镜一梳、MindSync、paperclip 在工作经历和项目经历里重复展开。应分工：

- 工作经历：角色、职责、结果。
- 项目经历：技术难点、系统结构、模型链路、评测和生产化。

### 4.3 职业画像不够聚焦

工程版应让工程画像最强。房产、保险、创业经历只保留迁移价值：需求诊断、风险边界、SOP、知识库、客户理解。

## 5. P0 修改项

1. 删除顶部内部写作说明。
2. 校验 2025.01 与 2026 项目阶段之间的时间线。
3. 确认“DeepSeek V4”是否为官方或平台可核验名称。
4. 若使用“生产级”“自动修复”等强词，补机制或降级表达。

## 6. 技术栈改写建议

当前技术栈结构可保留，但需更工程化。

### 6.1 AI 应用层

补充或确认：

- Prompt 版本管理。
- 结构化输出约束。
- 多模型路由。
- 失败重试。
- 降级兜底。
- 内容安全规则。
- 离线评测集。
- 回归测试脚本。
- 调用日志留痕。
- 成本与延迟监控。

### 6.2 后端与数据层

需要明确：

- 数据库是什么。
- 用户和历史报告如何存储。
- 兑换码 / 订单 / 支付状态如何设计。
- 鉴权和权限如何处理。
- 异步任务是否存在。
- 日志和异常如何定位。

如果当前未实现，不要包装成生产级 SaaS，只写已完成边界。

### 6.3 部署与运维

“腾讯云三机分工”和“自动冒烟测试与自动修复”需解释：

- 三台机器分别承担什么职责。
- 冒烟测试覆盖上传、生成、追问、历史记录中的哪些链路。
- 自动修复是重启、自恢复、回滚、配置修复，还是 AI 编码修复。

## 7. 一镜一梳项目应补的工程证据

建议项目经历增加 1-2 条技术断面：

- 系统结构：React / Vite 前端、FastAPI 后端、COS 私有存储、签名 URL、视觉模型、推理模型、兜底模型、Nginx + HTTPS、GitHub Actions。
- 评测结构：9 张图 × 3 轮稳定性评测，5 组 golden case 覆盖画面清晰、复杂符号、信息不足、高风险表达、议题强约束等类型。
- 运行证据：累计生成报告数、平均生成耗时、降级触发条件、冒烟测试覆盖路径。

## 8. Agent 表达边界

工程版必须区分两类 Agent：

| 对象 | 建议表达 |
|---|---|
| 一镜一梳报告生成 Agent | 多阶段生成链路 / 报告生成工作流，重点写输入输出、阶段留痕、失败处理 |
| MindSync 职能 Agent | AI 辅助研发协作角色，重点写任务边界、交付门、文档治理，不包装成自动化服务进程 |

不要让“9 个职能 Agent”被误解为可执行多 Agent 产品架构，除非能讲清工具调用、状态管理、失败恢复和人工接管机制。

## 9. 面试追问清单

工程面试需准备：

1. 当前真实用户数和报告生成量。
2. 后端数据存储与历史记录结构。
3. 图片上传、私有存储和签名 URL 安全策略。
4. 模型调用失败如何重试和降级。
5. 9 张测试图如何选择，GLM 为什么淘汰。
6. golden case 通过标准是什么。
7. 16 阶段智能体每阶段输入输出是什么。
8. 自动冒烟测试覆盖什么。
9. AI 生成代码如何 review，如何防止回归。
10. 近两年代码能力如何恢复，AI 辅助与手写代码比例如何。

## 10. 最终结论

工程版有约面潜力，尤其适合 AI 应用和 Agent 应用方向。下一版应减少“个人系统”和非工程叙事，补足系统结构、评测指标、生产运行和 Agent 机制，让它更像一份强 AI 应用工程简历，而不是 AI 产品型独立开发者说明书。
