# JD 数据库 SPEC

> status: current
> date: 2026-06-08
> owner: Codex / Xinran
> scope: projects/xinran-jobhunt

## 1. 背景

当前 `馨冉求职` 项目已经有三版目标简历，但还缺一个稳定的岗位输入层。

真实使用场景是：

- 你在招聘 App 里看到喜欢的岗位
- 直接截图发给我
- 我先把截图里的 JD（Job Description，岗位描述）转成文字版
- 再把分析写在同一个文档后面
- 先积累岗位样本，之后再做综合分析

## 2. 目标

建立一个轻量、可直接维护的 JD 数据库，满足下面四件事：

1. 持续收集感兴趣岗位
2. 统一记录岗位关键信息和判断
3. 保证每个岗位都有独立文字版文档
4. 从多条岗位中提炼市场主流需求

## 3. 非目标

当前不做：

- 招聘平台自动爬取
- OCR 自动识别流水线
- Web 后台或数据库服务
- 投递管理台账
- 针对单个岗位立即改简历

这些能力后续如果真有频次，再单独升级。

## 4. 方案

采用文件化数据库：

- `jd-database/index.yaml`
  - 作为岗位总索引
- `jd-database/jobs/*.md`
  - 每个岗位一个独立文档，前半段是文字版 JD，后半段是分析
- `jd-database/templates/*.md`
  - 录入和分析模板

## 5. 单条岗位卡最小字段

每条岗位至少记录：

- `job_id`
- `captured_at`
- `company`
- `role_title`
- `city`
- `source_platform`
- `status`
- `match_score`
- `keywords`
- `must_have`
- `nice_to_have`
- `risks`

## 6. 观察轨道

当前默认只标记三条主观察轨道：

- `ai-pm`：AI 产品经理
- `ai-consulting`：AI 转型咨询顾问
- `fde`：FDE

如果一个岗位跨两条轨道，岗位文档里保留：

- `primary_track`
- `secondary_track`

但 `index.yaml` 里仍只写主轨道，避免统计口径发散。

## 7. 截图输入工作流

当你发岗位截图时，按下面流程处理：

1. 我先读取截图内容，补全岗位文本
2. 新建一条独立岗位文档
3. 更新 `index.yaml`
4. 把分析写在同一个文档后半段
5. 等样本达到一定量后，再做阶段性综合分析

## 8. 验收标准

本轮交付完成后，应满足：

1. 项目里有独立 JD 数据库目录
2. 有可复用模板，而不是临时口头格式
3. 有总索引，方便后续汇总
4. 单个岗位文档遵循“文字版在前，分析在后”
5. 不改动你当前正在编辑的简历文件
