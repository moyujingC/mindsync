## 1. 用途

这份底稿用于更新求职材料中的 AI 项目表达。它不是作品集正文，也不是简历正文，而是事实基线。

## 2. 总表达原则

最稳的求职主线是：

> 有工程底座和复杂服务场景经验，能从真实问题出发，把高信任、非标准化、不确定的场景收束成 AI 产品、工作流或治理系统。

写法上优先强调：

- 问题定义
- 产品边界
- AI 工作流
- 质量门与安全边界
- 从 MVP 到可验证主路径
- 文档治理和系统化沉淀

避免强调：

- 大规模商业化
- 医疗 / 心理诊断
- 成熟企业级平台
- 大团队生产系统
- 未验证的自动化能力

## 3. AI-Mandala / 一镜一梳

### 3.1 来源文件

- `projects/aimandala/docs/specs/ToC-MVP-产品规范.md`
- `projects/aimandala/docs/architecture/解读智能层-曼陀罗解读智能体架构.md`
- `projects/aimandala/docs/specs/2026-05-30-曼曼-avatar报告陪读与追问-handoff.md`

### 3.2 当前状态

AI-Mandala / 一镜一梳已经从“想法 / 即将上线”推进为一条更清晰的 To C Web MVP 主线。

当前 MVP 只覆盖 To C 用户主路径：

1. 用户进入手机端 Web 产品。
2. 用户上传曼陀罗图片，并补充少量必要描述。
3. 系统生成 Lite 报告。
4. 用户查看 Lite 报告。
5. 用户可从 Lite 报告入口升级 Pro。
6. Pro 支付成功后查看 Pro 权益内容。
7. 用户可围绕当前报告向曼曼继续追问。
8. 用户可查看历史记录。

当前产品层级：

- 一镜 Lite 版：面向首次体验用户，当前入口价格 9.9 元。
- 一梳 Pro 版：只能从 Lite 后升级，当前升级价 29 元，不提供独立购买入口。

当前正式 API 主线为 V2。

### 3.3 可公开表达

可以写：

> AI-Mandala / 一镜一梳是面向 To C 用户的曼陀罗绘画上传与解读 Web MVP，围绕上传画作、三圈识别、Lite / Pro 报告、付费升级和报告追问构建最小产品闭环。

更偏简历写法：

> 主导 AI-Mandala Web MVP 的产品收束，将曼陀罗绘画上传、三圈识别、Lite / Pro 报告、付费升级和报告追问整理为可验证的 To C 用户主路径。

### 3.4 技术 / 工作流亮点

新版曼陀罗解读智能体采用“端到端 + 提示词缓存 + 可复用视觉基准”的主线。

当前正式生产默认链路为 `two_pass_e2e`：

1. Vision Pass：基于用户原画作、三圈标记图和基础知识包生成可复用视觉基准 `visual_draft`。
2. Reasoning Pass：基于视觉基准、财富 prompt pack、输出规范和用户意图生成 Lite / Pro 报告。

这个设计的价值：

- 同一幅画只有一个画作级视觉基准。
- 未来同一画作生成多个议题报告时，可以复用同一视觉基准。
- 避免不同议题报告对同一画作的视觉观察互相矛盾。
- 保留报告的带读感和流派感，而不是变成系统检测结果。

Prompt pack 设计原则：

- 稳定前缀版本化。
- 用户图片、用户问题、本次视觉草稿不进入稳定前缀。
- 通过顺序固定提高缓存命中率。
- 质量门检查是否越界、是否保留视觉证据和三圈带读。

### 3.5 曼曼 avatar / 报告追问边界

曼曼适合表达为：

> Aimandala 的报告陪读与追问 avatar，负责帮助用户读懂本次曼陀罗报告，并在本次画作与本次报告范围内回答追问。

产品边界：

- 只围绕本次画作和本次报告。
- 不做长期陪伴。
- 不做心理咨询。
- 不做财务或人生决策。
- Persona 负责表达层，不能替代事实观察、安全判断和质量门。

### 3.6 适合证明的能力

- 从一线服务痛点中定义 AI 产品。
- 收束 MVP 范围。
- 设计复杂高信任场景的 AI 输出边界。
- 设计报告生成 agent 工作流。
- 用质量门和安全边界控制 AI 输出风险。
- 在感性体验和工程可验证之间做取舍。

### 3.7 不可夸大边界

不要写：

- 已大规模上线。
- 已服务大量用户。
- 已完成完整商业化验证。
- 医疗诊断 / 心理治疗 / 心理咨询产品。
- 完整 To B / Studio / App 产品已经交付。

推荐边界写法：

> Web MVP 主线 / 上线准备 / 可验证产品闭环 / 报告链路重构中。

## 4. MindSync

### 4.1 来源文件

- `AGENTS.md`
- `COMPANY.md`
- `MONOREPO.md`
- `company/knowledge-base/system/MindSync-设计机制分析.md`

### 4.2 当前状态

MindSync 是公司内核 + 多项目工作区 Monorepo，不是单一应用仓库。

它同时承载：

- 公司治理
- 角色定义
- 项目入口
- 共享工具
- 长期知识库

MindSync 与 Paperclip 的关系：

- MindSync：治理源、文档源、实现源、知识源。
- Paperclip：运行时控制面、任务派发与回写面、执行状态面。

### 4.3 可公开表达

可以写：

> 自建 MindSync AI 一人公司工作系统，以 Monorepo 管理公司治理、项目入口、角色定义、知识库、共享工具和阶段 artifact，支撑 AI 产品、研究、内容和求职材料等多项目并行。

更克制写法：

> 搭建自用 AI 工作系统 MindSync，用文档即系统的方式管理多项目、角色分工、知识沉淀和任务流转，支撑 AI 产品和个人转型项目持续推进。

### 4.4 系统结构亮点

MindSync 五层结构：

1. `agents/`：角色定义，回答“谁负责做什么”。
2. `company/`：公司治理规则、注册表、蓝图、公司级入口。
3. `projects/`：项目工作区、项目实现、项目级文档。
4. `shared/`：共享脚本、模板和跨项目工具。
5. `company/knowledge-base/`：长期复用知识沉淀。

它解决的问题：

- 信息不再散落在聊天记录、运行时和历史仓库。
- Agent 进入项目时有稳定入口。
- 项目从 spec、task、QA 到 delivery 有可追踪 artifact。
- 多项目可以在同一系统内保持边界和状态。

### 4.5 适合证明的能力

- 系统化思维。
- AI 协作流程设计。
- 知识治理。
- 多项目管理。
- 文档即系统。
- 把模糊任务转成可分派、可验证、可回写的工作流。

### 4.6 不可夸大边界

不要写：

- 成熟商业化 SaaS。
- 企业级多人协作平台。
- 已销售给客户的 AI Agent 平台。
- 完全自动化公司。

推荐边界写法：

> 自用 AI 工作系统 / Monorepo 实践 / 一人公司操作系统原型。

## 5. RelayHub

### 5.1 来源文件

- `projects/relayhub/specs/2026-04-16-RelayHub-v1-架构与产品定义.md`
- `projects/relayhub/specs/2026-04-16-RelayHub-v1-控制台信息架构草图.md`
- `projects/relayhub/delivery/2026-04-18-v1-relayhub-console-release-节点静态试用入口-交付说明.md`

### 5.2 当前状态

RelayHub 是公司级共享模型能力项目，不是泛化“大而全”的 AI Gateway。

v1 由一个共享底座承载三类运行形态：

1. `dev-relay`：面向个人开发工作流，为 Claude Code、Codex 等客户端提供统一模型接入入口，用于比较第三方中转与国产模型在真实编码代理任务中的效果。
2. `prod-relay/<product>`：面向具体产品的正式生产流量，承担统一鉴权、路由、隐私治理、供应商收口与成本观测。
3. `eval-sidecar`：面向旁路评测、评分板、日报、探活和优化建议，不与生产主链路强耦合。

### 5.3 可公开表达

可以写：

> 设计 RelayHub 公司级模型接入与评测能力，将个人开发 relay、产品生产 relay 和旁路 eval 拆分为三类运行形态，统一沉淀 provider 接入、路由、观测、评测与优化建议边界。

更简历化：

> 参与定义 RelayHub v1 产品与架构边界，区分开发实验、产品生产和旁路评测三类模型使用场景，避免开发配置、生产数据和评测逻辑混用。

### 5.4 共享底座能力

v1 共享底座至少包括：

- provider 抽象与统一 API 入口。
- 基础鉴权。
- 模型到 provider 的配置映射。
- 流式透传能力。
- usage、延迟、错误、状态码、TTFT 等基础指标采集。
- 运行模式切换：`dev-relay`、`prod-relay/<product>`、`eval-sidecar`。

v1 明确不要求：

- 复杂自动路由。
- 智能切流。
- 正文缓存。
- 企业级管理后台。

### 5.5 生产边界

心理疗愈应用生产版 relay 的硬边界：

- 只允许国产模型。
- 第三方中转不进入生产用户数据主链路。
- 不默认记录正文级敏感数据。

这个边界适合写成 AI 落地中的风险意识，而不是技术炫技。

### 5.6 适合证明的能力

- AI 模型接入治理。
- 开发、生产、评测边界分离。
- 模型选择、测评和降本优化意识。
- 对隐私、合规、成本、质量之间关系的判断。
- AI 基础设施类产品的信息架构能力。

### 5.7 不可夸大边界

不要写：

- 已上线完整 AI Gateway。
- 已承载大规模生产流量。
- 已实现智能路由 / 自动切流。
- 已完成企业级管理后台。
- 成熟 MLOps 平台。

推荐边界写法：

> v1 capability 设计 / console trial / 只读 provider 试点 / 内部开发主路径收口。
