## 1. 报价原则

报价不是按工具名、模型名或聊天时长计算。

报价必须同时考虑：

- 客户要解决的业务问题。
- 影响收入、成交、交付、等待时间、错误成本或经验复用的程度。
- 流程和资料是否清楚。
- 买单人、使用人、资料方、验收人是否对齐。
- 交付物是否能写清。
- 不包含事项是否能写清。
- 是否需要合作方。
- 是否会形成可复用资产。
- 是否会导致低价重交付。

可用表达：

```text
这个报价不是按“用了哪个 AI 工具”算的。
我会按本次范围、资料复杂度、交付物深度，以及它对你们业务的价值来定。
```

客户觉得贵时，先缩小范围，不直接降价。

报价必须先拆成两类工作：

| 类型 | 解决的问题 | 是否可由自己直接报价 |
| --- | --- | --- |
| 策略诊断 | 判断客户处于哪个阶段、哪些场景值得做、边界怎么定 | 可以在范围清楚时直接报价 |
| 执行交付 | 搭建、开发、系统接入、课程规模化、生产级治理 | 需要先确认合作方、客户输入和验收方式 |

客户还没说清流程、资料、负责人和验收标准时，只报价策略诊断，不报价执行交付。

## 2. 报价前置条件

报价前必须确认以下信息。

| 检查项 | 必须回答的问题 |
| --- | --- |
| 服务对象 | 本次交付对象是一条流程、一批资料、一个岗位，还是一次团队工作坊？ |
| 业务问题 | 客户现在最慢、最乱、最容易返工或最影响业务的点是什么？ |
| 价值判断 | 它影响收入、成交、交付、客户体验、风险、新人上手，还是老板管理？ |
| 流程基础 | 当前人工流程是否已经走清楚？输入、处理、输出、审核点是否明确？ |
| 资料基础 | 资料是否电子化、结构化、可提供、可脱敏、可校对？ |
| 使用人 | 谁每天使用或执行？是否参与过需求确认？ |
| 买单人 | 谁决定付费？是否理解本次范围？ |
| 资料方 | 谁提供资料、账号、样本、历史记录或系统截图？ |
| 验收人 | 谁判断有没有价值？判断标准是什么？ |
| 安全边界 | 是否涉及隐私、商业机密、账号、cookie、API Key、客户数据或高监管行业？ |
| 合作方 | 是否需要工程、设计、法务、财税、行业专家或培训助教参与？ |
| 维护边界 | 是否包含维护期？维护和新增需求如何区分？ |
| 复用资产 | 本次能否抽取流程模板、问题清单、行业术语、验收口径或 demo 素材？ |
| 回款风险 | 付款节点、审批周期、开票主体和尾款条件是否清楚？ |

如果这些问题回答不出来，不报价完整交付。可选动作：

- 补一次访谈。
- 只报价小诊断。
- 只报价资料盘点。
- 只报价试点定义。
- 明确拒绝或转介绍。

## 3. 报价结构：SOW / SOP / SLA

凡是进入付费诊断、工作坊、陪跑或合作交付，报价单至少要写清轻量 `SOW / SOP / SLA`。

| 结构 | 中文含义 | 报价时必须写清 |
| --- | --- | --- |
| SOW | Statement of Work，工作范围说明 | 做什么、不做什么、交付物、资料范围、使用场景 |
| SOP | Standard Operating Procedure，交付流程 | 客户输入、服务动作、关键节点、反馈方式、验收流程 |
| SLA | Service Level Agreement，服务响应约定 | 响应方式、响应时间、维护期、答疑次数、紧急事项边界 |

简化模板：

```text
SOW：本次只处理【一条流程 / 一批资料 / 一次工作坊】，不包含【系统搭建 / 长期维护 / 新增需求】。
SOP：甲方先提供资料和访谈对象，乙方完成诊断 / 交付物，双方按约定时间复盘。
SLA：服务期内按约定渠道响应，超出范围的新需求另行报价。
```

没有 SOW / SOP / SLA 的报价，容易变成无限答疑、免费方案或边界不清的执行项目。

## 4. 不同服务的报价边界

### 4.1 免费诊断

用途：

- 判断场景是否适合。
- 建立信任。
- 发现真实流程。
- 判断客户付费意愿。

边界：

- 时长通常控制在 15-30 分钟。
- 不输出完整方案。
- 不配置工具。
- 不搭自动化。
- 不写详细提示词。
- 不做长期答疑。

表达：

```text
这次先帮你判断适不适合做，不输出完整方案。
如果确认值得做，再进入付费诊断或小实验。
```

### 4.2 小诊断

适合：

- 一条流程。
- 一个岗位场景。
- 一批小规模资料。
- 一次资源方客户样本判断。

包含候选：

- 当前问题摘要。
- 流程拆解。
- 访谈纪要。
- 高频 / 结构化 / 可评判 / 人工兜底判断。
- AI 可介入节点。
- 不建议自动化节点。
- 7 天小实验建议。
- 下一步是否值得继续。

不包含：

- 实际搭建系统。
- 多轮陪跑。
- 跨部门调研。
- 本地部署。
- 敏感数据处理。
- 收入、效率或经营结果承诺。

### 4.3 资料 / 知识库前置整理

适合：

- 资料多、散、乱。
- 资料还没有电子化、结构化或校对过。
- 客户想做知识库或内部 AI 助手，但基础不清楚。

包含候选：

- 资料盘点。
- 入库前资料状态判断。
- 分类结构。
- 命名规则。
- 标签规则。
- 可入库 / 暂不入库清单。
- 需要客户人工校对的问题清单。
- 模板建议。
- AI 使用入口建议。

不包含：

- 企业级知识库系统。
- 内部 AI 助手上线。
- 大规模数据清洗。
- 大批量 OCR 和人工校对，除非单独报价。
- 权限治理。
- 万级以上资料的全量治理。
- 去重、版本识别、相似聚类和文档画像。
- 正式依据、背景材料、归档材料的可信度分层。
- 长期维护。

边界表达：

```text
知识库不是把资料丢进去就结束。
如果资料还没有电子化、结构化或校对过，
第一阶段只能先做入库前盘点和整理，
不能直接承诺问答效果。
```

如果客户资料已经进入千级或万级规模，普通资料整理报价不能覆盖生产级治理。应单独报价：

- 文档抽样方案。
- 资料准入机制。
- 去重和版本识别规则。
- 文档画像字段。
- 可信度和使用价值分层。
- 评测 badcase 归因。
- 客户内部资料责任人协同。

### 4.4 知识库 PoC（概念验证）

知识库 PoC 只用于验证一个真实场景的资料、检索和使用闭环，不能按“搭一个企业知识库”整体报价。

报价单、交付清单与合同必须使用同一组范围字段：

| 范围字段 | 必须写清 |
| --- | --- |
| 场景 | 哪个岗位在什么时刻查询或问答；不覆盖哪些场景 |
| 资料 | 代表资料范围、数量、格式、可入库资格与版本责任人 |
| 测试 | 测试问题数量、须引用的问题、拒答 / 转人工规则和反馈方式 |
| 使用 | 使用人数、使用入口、验收人和反馈责任人 |
| 维护 | PoC 期间的资料更新、错误修正、答疑次数和截止日期 |
| 费用 | 平台、模型、解析、存储和第三方费用由谁承担 |
| 排除项 | 全量迁移、复杂权限、源系统同步、生产运维、准确率或经营结果保证 |

进入条件：已完成资料诊断；有一个明确场景、使用人、验收人、代表资料、资料责任人、人工兜底和测试问题。

验收候选：在约定样本与测试环境中，使用人能完成约定检索 / 问答；答案提供来源入口或明确拒答；至少完成一轮 badcase（失败样例）分类和修正。PoC 后是否扩展，取决于反馈与治理责任，不由 demo 演示效果自动决定。

以下情况不使用 PoC 小单报价：真实多人使用、跨部门资料、敏感数据、源系统同步、自动写入或需要审计日志。此类需求应单列生产设计和合作交付范围。

### 4.5 小实验 / 工作坊

进入条件：

- 已完成诊断。
- 有明确流程。
- 客户能提供资料。
- 有使用人和反馈人。
- 成功标准可定义。
- 客户接受“先让至少一名成员跑通”的最低成功标准。

包含候选：

- 一次 2-4 小时工作坊。
- 一条流程的实验版。
- 示例提示词或模板。
- 操作说明。
- 交付前 5-10 分钟演示视频。
- 复盘会议。

不包含：

- 完整企业 AI 落地方案。
- 课前跨部门调研。
- 系统搭建。
- 客户资料整理和知识库治理。
- 保证全员掌握。
- 保证流量、成交或经营结果。
- 无限期答疑。
- 把半自动流程包装成全自动系统。
- 超出约定流程的新需求。

### 4.6 企业内训 / 小分享

企业内训和小分享主要解决认知对齐、共同语言和场景启发。

包含候选：

- 课前一次需求确认。
- 围绕一个岗位、流程或行业场景的分享。
- 现场案例启发或 demo。
- 简版问题收集。
- 会后诊断邀请。

不默认包含：

- 完整方案设计。
- 多部门访谈。
- 工作流搭建。
- 资料清洗、整理或入库。
- 课后长期答疑。
- 学员全员掌握或业务结果承诺。

如果客户要求培训后直接输出方案、SOP 或系统原型，应拆成工作坊、诊断或小实验单独报价。

### 4.7 工作流 / 自动化试点

进入条件：

- 手动流程已经完整走过一遍。
- 每一步输入、输出、账号、系统和人工判断点清楚。
- 客户愿意提供测试账号、脱敏数据或安全测试环境。
- 成功标准不是“点了按钮”，而是业务结果能被独立验证。
- 有人工兜底人，能处理失败、审核、重试和平台变化。

必须单独写入报价的前置成本：

- 流程影子跟跑。
- 资料准备。
- 测试账号或测试数据准备。
- 试运行。
- 审核和反馈。
- 异常处理。
- 第三方平台变化风险。

不承诺：

- 搜索排名。
- 线索数量。
- 转化率。
- GMV。
- 平台长期稳定性。
- 自动化零失败。

### 4.8 demo / POC / 试点 / 生产级报价边界

demo、POC、试点和生产级必须分开报价，不能用 demo 报价覆盖生产级责任。

| 层级 | 报价可包含 | 必须排除或单独报价 |
| --- | --- | --- |
| demo | 模拟样板、脱敏样板、录屏演示、流程可能性展示 | 稳定使用、全量准确、真实生产数据、长期维护 |
| POC | 约定样本、测试环境、一次验证记录、人工审核点 | 全量上线、多部门推广、生产环境 SLA |
| 试点 | 小范围真实使用、反馈记录、异常记录、有限调整 | 无人值守、全员铺开、长期运维 |
| 生产级 | 需要另行定义权限、日志、监控、回滚、维护、费用和责任 | 不包含在培训、诊断、工作坊、小实验默认报价中 |

进入生产级前，以下成本必须单独估算：

- 第三方工具、模型、token、账号、服务器或 API 费用。
- 权限、账号、数据、日志和监控配置。
- 测试环境、测试数据和验收样本准备。
- 异常处理、回滚、停用和人工兜底机制。
- 维护期、响应方式、故障处理和新增需求边界。
- 合作方工程、部署、运维或安全评估费用。

客户要求自动写入、自动发送、自动发布、自动操作客户系统或长期无人值守时，默认不属于普通自动化试点，必须重新报价。

### 4.9 月度支持 / 企业试点

当前只作为远期观察，不作为公开价格表。

进入条件：

- 已有真实付费交付。
- 客户愿意持续提供反馈。
- 服务边界可以写清。
- 不会变成无限答疑。

可能包含：

- 月度 AI 工具更新。
- 场景复盘。
- 小流程迭代。
- 管理层汇报。
- 新场景判断。

## 5. 价格数字的使用规则

当前不把外部材料中的高客单数字写成正式价格表。

可使用的是价格结构：

- 引流品：低门槛，换来样本、信任和后续沟通。
- 利润品：围绕诊断、工作坊、试点、陪跑收费。
- 明星品：作为远期能力展示和价格锚点。

候选价格只用于内部验证：

| 服务 | 候选区间 | 使用规则 |
| --- | --- | --- |
| 小诊断 | `999-1999 元` | 只在范围极窄、交付物清楚时测试 |
| 资料 / 知识库前置整理 | `1999-4999 元起` | 视资料数量、混乱程度、清洗和校对成本调整 |
| 小实验 / 工作坊 | `3000-10000 元起` | 诊断后再报，不作为首推价格表 |
| 小团队 AI 工作流实战工作坊 | `3000-5000 元` | 仅作为第一阶段候选口径，需真实反馈验证 |

任何价格都必须回到当前阶段验证结果，不因外部材料提到高价就直接抬价。

## 6. 不承诺事项

所有对外表达默认不承诺：

- 收入增长。
- 降本比例。
- 获客结果。
- 客资数量。
- 签单数量。
- 成交率提升。
- 招聘成功。
- 融资成功。
- 组织转型结果。
- 员工一定使用。
- AI 替代人。
- 系统零错误。
- 自动化稳定运行。
- 数据绝对安全。
- 本地部署。
- 多部门长期落地。
- 第三方平台永久可用。
- 爆款内容。
- 平台流量。
- GMV 或 ROI。
- 未经人工审核的自动发布质量。
- 无人值守 Agent 长期稳定运行。

可承诺的是过程和交付物：

- 按约定完成诊断。
- 给出流程拆解。
- 输出 AI 落地路径图、SOP 卡或试点定义。
- 标出可尝试和不建议自动化的节点。
- 写清人工审核点。
- 给出下一步实验建议。
- 按范围整理资料。

## 7. 交付责任分层

报价前必须判断本次服务属于哪一类交付。

| 类型 | 定义 | 报价方式 | 风险处理 |
| --- | --- | --- | --- |
| 自己交付 | 售前判断、流程拆解、资料结构、小实验设计等自己能完成的服务 | 可直接报价 | 自己承担交付质量 |
| 合作交付 | 工作流搭建、前端封装、行业深度方案、内训规模化等需要他人参与的服务 | 先拆分范围，再报价 | 写清合作方职责和验收 |
| 暂不触碰 | 高敏数据、复杂私有化、多系统集成、长期代运营、效果承诺等 | 不报价或只报需求诊断 | 明确拒绝或转介绍 |

合作交付不能按自己单人服务的方式报价。

合作方未确认时，只能报价：

- 需求诊断。
- 试点定义。
- 资料盘点。
- 合作方案梳理。

不能直接报价完整交付。

资源方或合作方参与时，报价还要额外写清：

- 谁负责获客和客户关系维护。
- 谁负责售前访谈和策略诊断。
- 谁负责执行交付。
- 客户向谁付款，谁开票。
- 尾款和延期回款由谁承担风险。
- 售后问题由谁响应。
- 复购和二次需求归谁跟进。

如果 B 端客户审批和回款周期不确定，不能把尾款当成确定现金流安排。小额诊断、工作坊和样板验证优先争取预付或阶段付款。

## 8. 服务边界模板

### 8.1 诊断服务边界

包含：

- 一次售前访谈。
- 一条流程或一批资料分析。
- 一份简版诊断结论。
- 一次交付说明。

不包含：

- 现场培训。
- 系统搭建。
- 多部门访谈。
- 长期答疑。
- 客户内部推动。

### 8.2 工作坊边界

包含：

- 课前需求确认。
- 一次主题工作坊。
- 现场实操材料。
- 工作坊产出整理。

不包含：

- 员工长期辅导。
- 课后无限答疑。
- 内部制度建设。
- 系统上线。

### 8.3 资料整理边界

包含：

- 资料盘点。
- 结构整理。
- 命名 / 标签建议。
- 模板建议。

不包含：

- 逐条业务审核。
- 法务审核。
- 财务审计。
- 隐私合规审查。
- 系统迁移。

### 8.4 维护和新增需求边界

如服务包含维护期，必须写清维护和新增需求的区别。

维护可包括：

- 已交付内容的错误修正。
- 约定范围内的小调整。
- 对客户使用问题的有限答疑。
- 第三方工具轻微变化后的说明修正。

新增需求包括：

- 新场景。
- 新字段。
- 新系统对接。
- 新角色权限。
- 新报表。
- 新工具替换。
- 新部门推广。
- 原范围外的数据清洗和迁移。

新增需求必须另行报价，不能混入免费维护。

## 9. 让步规则

可以让步：

- 缩小范围。
- 缩短时长。
- 减少资料量。
- 减少复盘次数。
- 降低定制程度。
- 换取可脱敏案例和反馈。

不建议让步：

- 不写边界。
- 免费输出完整方案。
- 无限答疑。
- 低价接复杂项目。
- 为了成交承诺结果。
- 把首次低价变成长期基准价。

## 10. 报价记录字段

每次报价后记录：

- 日期。
- 客户类型。
- 服务类型。
- 报价金额。
- 包含事项。
- 不包含事项。
- 报价前置条件是否满足。
- 哪些前置成本已计入报价。
- SOW / SOP / SLA 是否写清。
- 客户反应。
- 主要顾虑。
- 是否成交。
- 如果未成交，原因是什么。
- 是否需要调整产品或话术。
- 是否涉及合作方。
- 是否有超出当前边界的需求。
- 是否能形成复用资产。

## 11. 待验证问题

后续通过真实报价验证：

- `999-1999` 元诊断是否太低或太高。
- 客户是否能理解“免费诊断不输出完整方案”。
- 资料整理是否更容易收费。
- 工作坊是否能作为诊断后的升级。
- 哪些客户愿意按月付费。
- 哪些边界最容易被客户突破。
- 哪些能力适合合作交付，哪些合作会显著增加管理成本。
- 哪个引流品能带来真实样本而不拖垮交付。
- 利润品是否能形成复购或升级。
- 明星品是否能提高客户认知和价格锚点。
