# GitHub 开源项目验证 Loop v0.1

> 状态：draft
> 版本：0.1.0
> owner：CEO / Orchestrator
> last_updated：2026-07-15
> 适用：`墨予镜企业AI服务` 的长期开源项目储备

## 1. 目的

把“发现一个看起来不错的 GitHub 项目”变成有证据的储备，而不是链接收藏。

每轮只验证一个项目。通过后才能进入可用储备；失败、超时或只完成资料阅读的项目仍保留，但必须标出卡点。

## 2. 进入条件

项目至少满足以下一项，才值得投入验证时间：

- 能支持企业 AI 落地、个人 AI 工作系统、能力包或行业方案包。
- 能帮助理解真实交付所需的流程、数据、权限、测试、可观测性或失败处理。
- 有明确许可证、近期维护迹象、可读的使用说明或最小示例。

以下项目默认不进入当前轮：纯概念展示、无许可证、只依赖营销截图、明显要求真实客户数据才能启动的项目。

## 3. 验证流程

### 1. 定位

记录仓库链接、许可、主要语言、维护状态、对应的服务线和具体使用场景。先写清“它能帮助验证什么”，再下载。

### 2. 风险分层

先判断是否会触及外部对象：

| 类型 | 允许动作 | 禁止动作 |
| --- | --- | --- |
| 纯本地 SDK / CLI | 下载、安装、官方最小示例 | 无 |
| 模型、数据库、Docker | 使用测试密钥、临时数据、本地容器 | 接入客户真实数据 |
| 邮件、社媒、爬取、浏览器自动化 | dry-run、mock（模拟）或 sandbox（隔离环境） | 真实发送、登录客户账号、批量抓取 |
| 财务、支付、生产系统 | 只读资料与 mock | 任何真实执行 |

出现未明确的外部副作用时，立即停止在本地验证阶段，不能用“试一下”代替授权。

### 3. 最小运行

按优先级选择最小动作：

1. 官方测试命令。
2. 官方 quickstart（快速开始）或无密钥示例。
3. 已发布 SDK 的导入、安装和最小调用。
4. 只能启动完整系统时，记录运行前置条件和失败点，不伪造通过。

完整仓库下载受网络影响时，可以验证其已发布 SDK；记录验证对象是 SDK，不把它写成“完整仓库已跑通”。

### 4. 判断

| 等级 | 判定 |
| --- | --- |
| A | 本机下载和安装成功，官方测试或最小示例得到预期结果。 |
| B | 有方向价值，但下载、安装或最小运行未完成。 |
| C | 只完成资料观察，未做本机运行。 |

所有 A 级结论必须同时写明未验证部分，例如真实模型、数据库、浏览器权限、完整测试或生产部署。

### 5. 留痕和复用

将结果追加到 `internal-research/GitHub-AI开源项目储备与验证记录.md`，至少包含：

```text
项目与链接：
服务关联：
验证日期和环境：
执行命令：
通过的证据：
失败、警告和未验证部分：
储备等级：
可借鉴的服务方法：
下一次验证动作：
```

只有多个项目或真实客户样本反复支持的结论，才升级为 `system/`、`sops/` 或 `capabilities/` 的稳定规则。

## 4. 停止条件

满足任一条件就结束本轮，并如实记录：

- 得到 A / B / C 的明确结论。
- 发现许可证、数据、权限或对外发送风险。
- 依赖安装、运行或测试失败，且已留下错误与环境信息。
- 下载持续受限，转用 SDK 或资料验证后仍不能继续。

每轮的完成标志是“结论已写入”，不是“又多收藏了一个链接”。
