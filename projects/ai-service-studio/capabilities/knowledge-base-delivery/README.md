本文件是内部能力基线，不是对外技术宣传页，也不是固定技术选型清单。

它回答三件事：当前可独立交付什么、为完成知识库 PoC 需要验证什么、哪些条件出现时必须引入合作方。

## 1. 当前服务范围

当前知识库服务按以下阶段推进：

```text
资料治理
  -> 一个场景的知识库 PoC
  -> 扩展治理或生产设计
```

技术工作始终服务于场景、资料责任、人工兜底与验收；不以平台名称、模型名称或向量数据库作为服务入口。

## 2. 能力分层

| 能力层 | 已可独立交付 | 下一步需要实操验证 | 需要合作交付 |
| --- | --- | --- | --- |
| 场景与资料治理 | 场景访谈、资料盘点、分类、准入、版本与责任人规则 | 用真实或脱敏样本完成一次资料质量抽检 | 跨部门资料整改推动与大规模治理 |
| 文档解析与加工 | 判断 OCR、转写、表格清洗和人工校对是否是前置条件 | 对扫描 PDF、表格、长文档各完成一次解析质量对比 | 批量复杂文档解析的质量保障与流水线运维 |
| 检索与问答 PoC | 设计代表资料、测试问题、来源引用、拒答与转人工规则 | 手搭一次基础 RAG：解析、分块、检索、回答、来源回链 | 高可用混合检索、重排、复杂多库路由与性能优化 |
| 评测与错误回流 | 定义测试问题、badcase（失败样例）分类与人工修正流程 | 建立可重复运行的小型评测集，完成一次优化前后对比 | 生产级观测平台、自动回归评测与质量运营后台 |
| 权限与数据边界 | 识别资料权属、敏感范围、资料责任人与最小可见范围 | 在脱敏样本中验证角色隔离与错误拒答 | 源系统 ACL（访问控制列表）继承、SSO（单点登录）、审计与合规评估 |
| 部署与成本 | 说明 PoC 的平台、模型、解析、存储费用归属 | 部署一个可复现的内部样板并记录成本与恢复步骤 | 私有化、企业网络、容灾、高并发与长期运维 |

## 3. 优先学习路径

### P0：能完成资料治理与知识库诊断

先掌握能直接改善当前服务交付的能力：

1. 文档资料治理：分类、命名、元数据、版本、有效期、资料责任人和准入清单。
2. 文档质量判断：识别扫描件、复杂表格、重复版本、历史材料、正式依据和背景材料。
3. 知识库 PoC 定义：把客户需求写成场景、代表资料、测试问题、使用人、验收人、人工兜底和排除项。
4. AI 辅助加工：用 AI 完成候选摘要、标签、FAQ、行动项和模板草稿，但由资料责任人确认后入库。

达到标准：拿到一批脱敏资料后，能在一次访谈和一次盘点中判断它应停在资料治理、可进入 PoC，还是需要合作方生产设计。

### P1：能亲手跑通一个可评测的 RAG 样板

目标不是立刻给客户上线，而是完整理解一个知识库问答为何会好或坏。

建议按顺序练习：

1. 解析：选择一套工具处理 Markdown、PDF、扫描件和表格，并保留原文位置。
2. 分块：比较按标题 / 段落切分与固定长度切分，理解内容被切断时为何会答错。
3. 检索：完成关键词检索与向量检索的对比，再尝试混合检索。
4. 回答：强制输出来源入口；资料不足时必须拒答或转人工。
5. 评测：准备 20 个左右测试问题，记录命中、未命中、错引、版本冲突和拒答是否正确。
6. 回流：修正资料、分块或规则后，重新运行同一批测试问题。

推荐练习项目：使用本项目的一小批公开或脱敏参考资料，做“墨予镜企业 AI 服务知识库问答样板”。它只用于内部学习和评测，不对外宣称生产可用。

达到标准：能解释一个失败样例属于资料缺失、解析错误、版本冲突、检索未命中、回答越界还是问题本身不清楚，并知道先改哪一层。

### P2：具备生产设计与合作判断能力

这层的重点是能判断风险与拆分责任，不要求当前单人独立实现。

- 权限：理解角色、部门、项目或客户隔离为什么必须影响检索阶段，不能只隐藏最终答案。
- 数据：理解脱敏、最小化采集、源系统权属、增量更新和删除 / 下架流程。
- 运行：理解日志、监控、回滚、异常处理、模型与平台变更、成本上限和维护 SLA（服务响应约定）。
- 集成：理解连接器、API、Webhook、MCP（模型上下文协议）分别解决什么问题，以及何时不应接入。
- 合作：能把需求拆成资料治理、PoC、工程实现、安全合规、运维五类工作，并明确客户、自己和合作方的责任。

达到标准：面对“多人使用 + 敏感数据 / 源系统同步 / 自动写入”的需求时，能输出生产设计清单和合作接口，而不是承诺直接上线。

## 4. 当前暂不优先学习

- 在没有真实场景前深入研究多 Agent、GraphRAG（图检索增强生成）或长期记忆框架。
- 为了技术完整性先搭建向量数据库集群、Kubernetes 或高可用架构。
- 把某个平台的配置方法当作可迁移的知识库方法论。
- 在没有评测集和责任人机制时反复调模型或提示词。

这些能力在出现相应客户场景或合作项目时再按需补齐。

## 5. 30 天内部练习闭环

| 周期 | 最小成果 | 验证方式 |
| --- | --- | --- |
| 第 1 周 | 一份资料盘点表与知识库 PoC 准入卡填写样例 | 能明确资料准入、责任人与排除项 |
| 第 2 周 | 一套可复现的解析、分块、检索样板 | 同一资料能返回原文来源入口 |
| 第 3 周 | 20 个测试问题与 badcase 分类表 | 能区分资料、检索、回答与权限问题 |
| 第 4 周 | 一份内部 PoC 复盘与合作边界清单 | 能说明可独立交付、需验证和需合作内容 |

每周应保留：输入资料范围、配置 / 代码位置、运行步骤、测试问题、结果与失败样例。只有实际跑通过的能力，才可从“需要实操验证”升级为“已可独立交付”。

## 6. 对外表达边界

当前可对外表达：可以为一个具体场景做资料治理、知识库诊断与样板 PoC 定义。

当前不对外承诺：固定平台选型、检索准确率、生产级权限安全、私有化部署、全量资料迁移、长期运维或 Agent 自主记忆效果。
