## 1. 总体判断

这份材料最有价值的不是给出一套固定技术选型，而是把知识库重新定义为“上下文供给系统”：资料从源系统进入后，经过解析、治理、检索、引用、人工纠错和持续更新，才可能稳定地为人或 AI 提供可用答案。

这与当前项目的“资料盘点 / 入库前整理 -> 样板验证 -> 扩展或生产治理”路径一致，并补足了两个此前应在售前更明确区分的层面：

- 业务知识库、AI 应用 RAG（检索增强生成）和 Agent 记忆是三种不同对象，不能用同一个“知识库”报价包笼统承接。
- 生产级的难点不在选择向量数据库或模型，而在资料权责、权限继承、版本、评测、错误回流和持续运营。

对当前 `墨予镜企业AI服务`，它支持把“AI 文档 / 知识库前置整理”作为可独立销售的前置服务；知识库问答或内部 Agent 则应以一个真实场景的 PoC（概念验证）或试点承接，不能以“导入资料即可智能问答”承诺效果。

## 2. 可借鉴的业务模式

可采用的服务路径：

```text
一个高频业务场景
  -> 资料与权限诊断
  -> 入库前治理与样板资料包
  -> 带引用的检索 / 问答 PoC
  -> 测试题、人工审核与错误回流
  -> 决定扩展、生产化或停止
```

其中每一步都交付可见对象：

- 诊断：场景说明、使用人与验收人、资料状态、风险与不做清单。
- 治理：资料准入规则、文档分类、元数据字段、版本与责任人清单。
- 样板：限定范围的资料集、问答入口、来源引用、测试问题与已知失败样例。
- 扩展：连接器、增量更新、权限同步、监控、评测和知识运营机制。

这也使客户可以按阶段购买。前期卖“判断能否做、先治理什么”，中期卖“一个场景跑通”，后期再判断是否需要工程合作、私有化或长期运营。

## 3. 产品和服务设定

建议把当前知识库类服务进一步区分为三类交付对象：

| 服务对象 | 客户问题 | 当前可承接交付 | 不应默认包含 |
| --- | --- | --- | --- |
| 人用知识系统 | 资料难找、交接困难、新人上手慢 | 资料盘点、目录 / 标签 / 模板、维护机制、协作入口建议 | RAG、私有化部署、复杂权限改造 |
| AI 问答 / RAG 样板 | 标准答案、FAQ、制度或产品资料难复用 | 代表资料治理、一个检索 / 问答场景、来源引用、测试集、人工审核点 | 全量资料导入、全员上线、准确率或业务结果保证 |
| Agent 记忆 / 上下文 | Agent 需要保存用户偏好、任务状态或时间事件 | 需求澄清、状态数据边界、记忆写入 / 更新 / 删除规则、PoC 定义 | 将历史文档直接当作 Agent 记忆、无人值守的生产系统 |

对外服务名称可继续使用“AI 文档 / 知识库前置整理”或“知识库诊断与样板验证”。避免先卖“企业知识库搭建”，因为该名称会让客户默认包含权限、迁移、系统集成、数据安全和长期运维。

## 4. 获客与销售

这份材料适合用于客户教育，但不适合直接拿技术名词做获客主张。可将其转成下面的售前表达：

```text
知识库项目先不问选哪个平台。
先看一个具体场景：谁需要查什么资料、谁确认口径、资料是否有有效版本、
答错后谁负责修正。这个基础明确后，才知道应该做协作文档、AI 问答，还是系统试点。
```

适合的客户信号：

- 新人反复询问老员工，且标准答案存在于散乱文档或聊天记录中。
- 销售、客服、交付团队经常找不到政策、案例、FAQ 或历史项目材料。
- 客户已经购买过 AI 工具，但因资料脏、答案无引用、权限不清而无法推广。
- 客户能指定使用人、资料责任人和验收人，并愿意先用一小批资料验证。

不宜接入完整交付的信号：

- 要求上传全量历史文件后立即得到“全知全能”助手。
- 没有人能确认哪些资料可作为正式回答依据。
- 需要跨部门权限继承、核心系统写入或高敏数据处理，却没有 IT / 安全责任人参与。

## 5. 售前和需求诊断

在现有资料盘点问题之外，知识库类售前应补问以下项目，并将答案写进方案：

| 判断对象 | 需要确认的问题 | 对方案的影响 |
| --- | --- | --- |
| 检索任务 | 是找原文、查标准答案、全局归纳、多步分析，还是生成动作建议？ | 决定 Wiki、全文检索、基础 RAG、图谱 / Agent 流程，或暂不做 AI |
| 资料质量 | 是否有扫描件、表格、图片、长 PDF、重复或冲突版本？ | 决定是否先做 OCR、解析抽样和人工校对 |
| 权限 | 用户能看什么是否由源系统决定？是否需要部门、项目或客户隔离？ | 生产试点需要权限继承与检索前过滤，不能只在前端隐藏答案 |
| 更新 | 资料多久变化一次？谁发起更新、确认版本、下架旧内容？ | 决定人工维护、定期批处理还是增量同步 |
| 质量 | 哪些问题必须回答正确且附来源？哪些问题应拒答或转人工？ | 决定测试集、引用规则、置信度阈值和兜底流程 |
| 成本与能力 | 客户是否有 IT、数据、安全或运维团队？ | 决定用现有平台、低代码平台、合作交付还是不承接 |

技术选型应放在上述诊断之后。优先遵循：客户已有协作平台时先利用其权限与资料入口；需要证明价值时先做一条场景的样板；只有当检索质量、权限、数据管道或评测成为业务核心时，才讨论自建技术栈。

## 6. 报价、付款和商业边界

报价应按治理与验证阶段，而不是按“模型 / 向量库 / 文档数量”直接报一口价：

- 资料治理诊断：限定资料范围和访谈对象，交付资料状态、准入规则和样板建议。
- 样板知识库 PoC：限定一个场景、代表性资料、测试题数量、使用人数和反馈周期；输出可运行样板与失败清单。
- 扩展 / 生产设计：单列数据接入、权限、日志、审计、评测、运维和项目协调；复杂工程需要合作方及独立 SOW（工作范围说明）。

必须在报价单中单列：资料解析与人工校对是否包含、是否要处理历史去重和版本冲突、是否需要接入源系统、权限规则由谁提供和确认、模型与平台费用由谁承担、上线后的维护期与错误处理范围。

不以单篇材料中的平台价格、性能数据或“一周上线”经验作为报价或交付周期承诺。

## 7. 交付、验收和复购

样板阶段的验收不应写成“AI 很聪明”，而应写成可测试的行为：

- 指定使用人能在目标入口完成约定检索 / 问答任务。
- 约定测试问题能返回有效资料或明确拒答，并显示来源。
- 已知 badcase（失败样例）能被归因为资料缺失、解析问题、版本冲突、检索失败、提示词问题或权限不足。
- 客户指定责任人能完成一次资料补充、版本更新或错误反馈。

复购路径应围绕知识运营，而非无限期“调模型”：定期抽检高频问题、补齐未命中资料、清理过期版本、回顾权限变化、更新测试集。对高风险或高影响回答，保留人工审核或明确转人工入口。

## 8. 合同、数据和合规边界

本材料补强了企业知识库项目的三个边界：

- 权限必须在检索与资料层处理，不能只靠最终回答页面隐藏。
- 模型、平台和连接器的能力、价格、数据驻留与开源协议都需要在项目立项时按客户环境核验。
- Agent 记忆属于动态状态数据，应单独约定写入条件、保留期限、修改 / 删除机制和可见范围，不能默认从客户资料中自动提取。

合同或服务确认单应继续要求客户确认资料权属、可入库范围、版本责任人和权限规则。涉及个人信息、医疗、金融、核心商业资料或跨系统同步时，当前只做方案与脱敏样本验证，生产实施需客户的法务、信息安全和技术责任人共同确认。

## 9. 能力边界判断

当前可直接积累和交付：

- 资料盘点、资料准入、分类、命名、标签、版本和责任人规则。
- 一个限定场景的样板资料包、测试问题与评测口径。
- 对客户现有协作工具或知识库平台的需求诊断和选型建议。
- RAG、知识图谱、Agent 记忆的适用边界说明。

需要合作交付或额外验证：

- 复杂扫描件 / 表格的批量解析质量保障。
- 源系统连接器、增量同步、权限继承、审计日志和企业 SSO（单点登录）。
- 自建 RAG 的混合检索、重排、评测观测与高可用运维。
- 大规模向量数据库、图谱、Agent 记忆基础设施和私有化部署。

## 10. 不适合直接照搬的部分

- 不将材料中的产品对比、Star 数、价格、性能、市场规模和行业趋势对外表述为已核验事实。
- 不把“编排选 Dify、解析选 RAGFlow”等口诀写成固定选型规则；客户资料形态、权限、现有工具、数据驻留和团队能力优先。
- 不把 GraphRAG、Agentic RAG 或 Agent 记忆当成普通资料库的默认升级路径。
- 不把个人本地 Markdown 知识管理方法照搬为企业生产系统；企业项目必须补权限、责任、版本、审计与维护机制。
- 不承诺单人完成企业级全栈实现、数据迁移、长期运维或安全合规背书。

## 16. KB 入库判断

可作为候选 atoms（知识原子）：

- 企业知识库的生产难点集中在资料治理、权限、评测和持续运营，而非单一模型选择。
