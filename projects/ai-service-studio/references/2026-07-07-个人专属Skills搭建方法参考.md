# 个人专属 Skills 搭建方法参考

> 日期：2026-07-07
> 来源：用户粘贴生财有术帖子《花3个月时间，我把10年设计经验沉淀搭建自己专属的Skills，全方位接管我的虚拟电商和公众号内容（附搭建流程）》及评论区
> 原文留存：[个人专属 Skills 搭建方法原文](2026-07-07-个人专属Skills搭建方法-原文.md)
> 项目：知行AI服务
> 用途：把个人经验、知识库、角色档案和高频任务 Skill 化的方法，转成 `ai-service-studio` 的服务设计参考
> 可信状态：来源为用户粘贴材料，未做外部页面二次核验；文中项目结果、账号数据、个人经历和效率提升只作为经验信号，不作为已验证事实

## 1. 总体判断

这篇材料对 `知行AI服务` 的价值，不是“大家都该搭 Skills”，而是提供了一条可交付的方法路径：

```text
个人 / 业务上下文
  -> 高频重复任务
  -> 隐性判断标准
  -> 知识库和素材库
  -> 单一职责 Skill
  -> 真实任务测试和迭代
  -> 半自动化工作流
```

这条路径和当前两条服务线都有关系：

- `AI 工作流诊断`：可以诊断客户哪些工作适合 Skill 化，哪些只适合一次性对话。
- `AI 文档/知识库整理`：可以帮助客户把“我是谁”“业务是什么”“判断标准是什么”整理成 AI 可读取的上下文。

但它不应被包装成“帮你搭一套全自动系统”。当前更适合作为小单中的诊断和结构整理方法。

## 2. 核心观点：Skill 不是技术包，是岗位说明书

原文把 Skills 解释成写给 AI 的“岗位说明书”：

- 这个岗位要做什么。
- 按什么流程做。
- 用什么标准判断好坏。
- 输出到哪里。
- 什么情况需要回退或人工判断。

对 `知行AI服务` 的启发：

客户说“我想用 AI 提效”时，不能直接问他要不要 Prompt 或自动化工具，而要先问：

- 你最常重复做的工作是什么？
- 这件事有没有固定输入和固定输出？
- 你平时怎么判断它做得好不好？
- 哪些部分能标准化，哪些必须由人判断？

如果客户答不出来，说明他现在需要的不是 Skill，而是流程拆解和判断标准整理。

## 3. 为什么别人的 Skill 到自己手里不好用

原文给出两个原因：

### 3.1 任务场景不匹配

市面上的 Skill 多数是通用能力，解决的是最大公约数问题。客户的真实业务往往非常具体，例如某个账号风格、某个产品人群、某种内容结构、某类客服咨询。

对项目的判断：

- 不要向客户售卖通用 Skill 包。
- 更适合卖“把你的一个高频任务拆成可复用 Skill 的诊断和搭建方案”。
- 如果市面上已有成熟工具，例如 PPT、排版、通用封面，不建议客户再定制 Skill。

### 3.2 缺少隐性知识密度

Skill 的价值来自客户自己的经验、审美、判断和踩坑记录，而不是 Prompt 写得花。

可转成服务语言：

```text
我们不是先写提示词，而是先帮你把经验讲清楚：
哪些内容你一眼能判断好坏？
你上次否掉一个方案，是因为什么？
哪些话你绝对不会对客户说？
哪些输出看起来正确，但你知道不能用？
```

这些答案才是定制 Skill 的材料。

## 4. 先让 AI 认识你：角色档案是地基

原文强调，在搭 Skill 前要先写一份“我是谁”。它可以是 `CLAUDE.md`、`AGENTS.md` 或项目档案，本质是让 AI 知道正在为谁、为什么业务、按什么风格工作。

对当前服务的可交付转译：

可设计一个轻量交付物：`AI 协作上下文档案`。

内容可以包括：

- 个人或团队定位。
- 当前业务和目标客户。
- 核心能力和边界。
- 过去经验和典型案例。
- 价值观、表达风格和禁用表达。
- 当前项目目录和材料入口。
- 哪些身份可以混用，哪些身份必须隔离。

这对客户的价值是：以后每次使用 AI，不必从零解释“我是谁”和“我要什么”。

## 5. 不同业务要有不同的“我是谁”

原文给出两个身份拆分：

- 小红书账号使用虚拟 IP / 产品定位档案。
- 公众号和个人品牌使用真实人物档案。

评论区也有人问“每个账号是否单独一套规则”，作者回复是：从同一架构里衍生出来。

对 `知行AI服务` 的启发：

- 可以给客户做一套总架构，但不同账号、业务线、场景要有分档案。
- 不同身份不能混着用，否则 AI 输出会风格错位。
- 对内容型客户尤其重要：企业号、创始人号、产品号、社群号不能共用同一份角色设定。

售前可以新增判断问题：

- 你现在有几个账号或业务场景？
- 它们服务的是同一类人，还是不同人群？
- 哪些表达可以共用，哪些绝对不能串？
- 是否需要区分“真实本人”“品牌人格”“客服身份”“专家身份”？

## 6. 从知识库长出 Skill

原文的小红书案例不是直接写 Skill，而是先有产品知识库，再有选题库、创作规范、关键词库和关键词指南。

这个顺序对项目很重要：

```text
先整理业务材料
再整理判断标准
最后才写 Skill
```

如果客户没有知识库和素材库，直接写 Skill 容易变成空壳。

对 `AI 文档/知识库整理 SOP` 的启发：

- 文档整理不只是归档，也是在为后续 Skill 提供弹药。
- 资料库应区分：产品知识、客户问题、案例素材、禁用表达、关键词、历史数据。
- 每个库都要说明被哪个任务调用，不能只是堆文件。

## 7. 单一职责：一个 Skill 只做一类判断

原文明确反对“全能 Skill”，建议拆成：

- 选题 Skill。
- 创作 Skill。
- 关键词布局 Skill。
- 长文 Skill。
- 一鱼多吃 Skill。

原因是一个 Skill 同时做多件事，会连续做多次判断，每一步都可能偏掉。

对当前项目的交付原则：

- 不帮客户做“大而全 AI 助手”。
- 每个 Skill 只解决一个高频任务。
- 工作流可以串联多个 Skill，但每个 Skill 的输入、输出和人工检查点要清楚。
- 先做最小可用版本，再用真实任务迭代。

## 8. 三步原创 Skill 方法

原文的三步可以直接转成服务诊断框架。

### 8.1 找高频重复任务

判断标准：

- 每天或每周都会做。
- 输入和输出相对固定。
- 有重复流程。
- 客户自己已经有一定经验。

不适合 Skill 化：

- 只做一次的任务。
- 每次差异很大的任务。
- 客户自己还没想清楚判断标准的任务。
- 已有成熟工具解决得更好的任务。

### 8.2 掏出判断标准

可用问题：

- 你平时怎么看这个输出合不合格？
- 你最近一次否掉某个方案，是因为哪里不对？
- 哪些词、结构、承诺、风格是你绝对不接受的？
- 你认为新手最容易错在哪里？
- 哪些地方 AI 可以直接做，哪些地方必须你最后看？

### 8.3 用真实任务测试迭代

第一版 Skill 一定不完美，要拿真实任务跑。

记录：

- 输入材料是什么。
- 输出哪里可用。
- 输出哪里偏了。
- 是规则没写清楚，还是缺少知识库材料。
- 下次要补充哪条标准。

## 9. 人和 AI 的分工

原文里一个清晰分工是：AI 完成 90% 的“对”，人补最后 10% 的“感觉”。例如 P1 封面、正文标题、情绪判断、点击率判断仍由人把关。

对当前项目的表达：

- AI 适合处理结构、批量、复用、初稿和稳定流程。
- 人负责目标判断、审美、情绪、风险、价格和客户关系。
- 交付时要明确人工检查点，避免客户误以为 AI 可以全自动替代。

## 10. 评论区信号

评论区对项目有几个有用信号：

- 有人正在探索知识库和 Skill 结合，说明需求存在，但门槛在架构、流程和大量判断劳动。
- 有人问多个账号是否单独规则，说明“总架构 + 场景分档案”是常见困惑。
- 有人把垂直 Skill 视为个人核心竞争力，说明客户可能愿意为“把自己的经验封装成系统”付费。
- 有人想把公众号流量和内容自动化做成 Skill，说明内容型客户可能是较早需求方。

## 11. 对当前服务线的影响

本次暂不直接改 SOP 或新增服务线。

但这篇材料提示后续可以把现有服务线扩展出一个小型诊断模块：

```text
AI Skill 化适配诊断

输入：
  一个客户高频任务
  3-5 份真实历史样本
  客户的判断标准口述
  当前使用 AI 的失败样例

输出：
  是否适合 Skill 化
  需要先补哪些知识库材料
  推荐拆成几个单一职责 Skill
  哪些环节必须人工把关
  第一版 Skill 的输入 / 输出 / 验收标准
```

这个模块可以先作为 `AI 工作流诊断` 的一个场景，不单独售卖。

## 12. 风险和边界

不能承诺：

- 用 Skill 全面接管客户业务。
- 一次搭建后长期不用维护。
- 复制别人的 Skill 就能跑通客户业务。
- 没有真实经验和素材，也能做出“有自己味道”的输出。

必须说明：

- Skill 依赖客户自己的素材、经验和判断标准。
- 初版需要真实任务测试。
- 不同账号、不同身份、不同业务线需要隔离上下文。
- 维护要基于数据和使用反馈，不宜频繁大改底层骨架。

## 14. KB 入库判断

暂不直接写入 `projects/research-center/kb/`。

可作为后续 KB 原子候选：

- `有效 Skill 来自高频重复任务、具体业务场景和隐性判断标准，而不是通用 Prompt。`
- `AI 协作前应先建立角色和业务上下文档案，否则输出会落回通用表达。`
- `知识库是 Skill 的弹药库；没有业务材料和判断标准，Skill 容易变成空壳。`
- `一套总架构可以衍生多个场景档案，但不同账号和身份不应混用上下文。`

入库条件：后续至少在 2-3 个客户样本、内部项目或其他来源中重复出现，再沉淀为长期知识。
