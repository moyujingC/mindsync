## 2. 企业级知识库的做法：五层模型

综合已有材料与行业共识，企业级知识库的建设可拆为五层。**80% 的工作量在第一层和第五层，不在模型。**

### L1 采集治理（地基）

- 来源盘点：文档从哪来（飞书/Notion/本地文件/聊天记录/工单），谁是资料责任人
- 准入规则：哪些资料有资格进入系统（正式 vs 草稿 vs 历史），去重与版本识别
- 加工流水线：解析（OCR/转写/表格清洗）→ 清洗 → 结构化
- 关键认知：资料治理是独立可售的前置交付，不是"准备工作"

### L2 结构化（决定检索上限）

- 切片策略：按语义/标题/父子结构切分，而非固定长度硬切
- 元数据 schema：每条知识携带来源、版本、有效期、适用范围、责任人字段
- 分类体系（taxonomy）：按业务维度建立受控分类（对项目 B：按课程/流派/议题/流程阶段）
- 受控词表：术语、别名、同义词的标准化（如"曼陀罗绘画"="曼陀罗艺术疗愈"）

### L3 检索（demo 与生产的分水岭）

- 混合检索：BM25 关键词 + 向量语义召回，RRF 融合
- 重排（rerank）：召回 top-20~50 后精排取 top-3~5
- 查询侧：意图识别路由到不同知识分区，必要时查询改写
- 权限感知：检索阶段过滤（pre-filter），不是生成后隐藏——多人使用场景的硬要求

### L4 生成护栏（客服场景的生死线）

- 强制引用溯源：每个答案可回链到具体资料条目
- 拒答策略：资料不足时明确拒答，不编造
- 转人工规则：高风险/低置信/用户明确要求时转出
- 对疗愈场景的加严：AI 不做诊断、不做危机干预，识别危机信号直接转人工/给求助渠道（见[心理咨询初访助理产品参考](../references/2026-07-18-心理咨询初访助理产品参考.md)的伦理边界）

### L5 运营闭环（知识库是活的系统）

- 评测集：20-50 个代表问题，覆盖命中/未命中/错引/拒答是否正确
- badcase 归因：资料缺失 / 解析错误 / 版本冲突 / 检索未命中 / 回答越界 / 问题不清——先归因再修
- 回流机制：未解决问题定期补全知识，过期内容清理
- 关键认知：没有运营机制的知识库三个月后必然腐化

**对项目 B 的意义**：spec 必须以这五层为骨架组织需求，每层都有明确的验收物。第一版允许 L3 简化（单库、无量级压力）、L1 半人工，但 L4 护栏和 L5 评测集不许省——这两层是"企业级"和"玩具"的分界线。

### 2.1 五层模型不等于自研架构

五层模型是"必须存在什么"的验收框架，不是"必须自己实现"的施工图纸。复用开源成果分三种粒度：

| 粒度 | 例子 | 对五层的覆盖 |
| --- | --- | --- |
| 组件级（默认） | 解析 MinerU/Docling、向量库 pgvector/Qdrant、嵌入 BGE-M3 | L1-L3 的零件，无争议必须复用 |
| 框架级（项目 B 主线） | LangGraph/LlamaIndex 组装编排、护栏、状态机 | L3-L5 的骨架，自己组装但不造轮子 |
| 平台级（对照 + FDE 技能） | Dify/RAGFlow/MaxKB 端走 | L1-L3 全包，L4-L5 浅度覆盖 |

选择编排层粒度的依据不是技术偏好，而是目标权重：

- 求职旗舰故事需要能讲清"检索不命中怎么排查、护栏怎么设计、转人工状态机怎么实现"——框架级组装的含金量最高
- 客服 Agent 的差异点（多轮状态机、转人工、疗愈伦理护栏、评测回流）恰好在成品平台定制能力最弱处
- FDE 客户交付则需要平台熟练度（快速上线、业务方可维护）——用 2-3 天的平台对照实验顺带获得，同时给自建版提供质量基准

## 3. 本体论：用不用、什么时候用

### 3.1 概念区分（面试也常考）

| 概念 | 是什么 | 解决的问题 | 成本 |
| --- | --- | --- | --- |
| 分类法（taxonomy） | 树状分类体系 | 资料归置、检索分区、导航 | 低，人工可维护 |
| 受控词表 / 元数据 schema | 术语标准化 + 字段规范 | 同义词归一、检索过滤、治理 | 低 |
| 本体（ontology） | 概念 + 关系 + 约束的形式化建模 | 多跳推理、语义一致性、跨系统对齐 | 高，需专业建模 |
| 知识图谱（knowledge graph） | 本体 + 实例数据的图存储 | 关系查询、图推理、全局归纳 | 高，含构建与维护 |

### 3.2 本体的适用边界

**值得用本体的信号**：领域概念层级复杂且稳定（医疗、法律、金融合规）；需要多跳推理（"A 疗法的禁忌与 B 药物的相互作用"）；需要跨系统语义对齐（多个系统共享同一概念模型）。

**不值得用的信号**：语料以流程、FAQ、话术为主；问题以单点事实查询为主；领域概念体系仍在快速演变；团队没有图谱维护人力。

### 3.3 对项目 B 的决策

**第一版不用本体。** 理由：

1. 客服知识库的主体是 FAQ、流程话术、课程介绍、预约规则——单点查询为主，无多跳推理需求
2. 需要的语义结构用 taxonomy + 元数据 schema + 受控词表即可覆盖（这是"本体论 lite"，也是简历上的正确术语）
3. 本体建模的投入产出比在语料量千级以下时为负

**二期候选：疗愈领域概念图谱。** 疗愈领域有特殊资产——概念体系本身就是产品内容（曼陀罗、议题系列、流派关系），且 aimandala 已有结构化脚本经验。当知识库从"客服问答"扩展到"课程内容生成""个性化学习路径"时，概念图谱从成本变成资产。届时按"实体（流派/技术/议题/课程）→ 关系（属于/适用于/前置）→ 属性"的轻量本体方法建模，不必上 OWL/SPARQL 重型栈。

**对项目 B 的意义**：spec 中 L2 结构化层采用 taxonomy + 受控词表；概念图谱写入 roadmap 二期，与项目 C（AI 课程）的内容底座需求联动评估。

## 4. 客服知识库的端到端操作链（项目 B 操作视图）

把五层模型落到客服 Agent 场景的操作顺序：

```text
1. 语料盘点：课程介绍 / 价格与预约规则 / 常见问答 / 初访信息收集流程 / 转接话术
   → 产出：资料清单 + 责任人 + 准入标记
2. 结构化：按"课程 / 流程 / 价格 / 疗愈概念 / 边界声明"分类；每条带来源与版本
   → 产出：知识条目 schema + 分类树 + 受控词表
3. 检索：单库起步，混合检索（BM25+向量），暂不重排
   → 产出：可查询的索引
4. 护栏：引用溯源、拒答话术、转人工触发词、疗愈伦理红线（不诊断/危机转介）
   → 产出：护栏规则集
5. 评测：20-30 个测试问题（含故意越界问题），badcase 归因表
   → 产出：评测集 v1 + 首轮归因
6. 上线试运行：真实流量接入，每周 badcase 回流
   → 产出：运营节奏（周会看"哪些问题答不上"）
```

技术选型初选假设（待 PoC 验证，不作交付承诺）：

- 嵌入：BGE-M3 或 Qwen3-Embedding（中文场景、开源、可私有化）
- 向量库：pgvector（数据量 <百万级、与业务数据同库）或 Qdrant（独立部署偏好时）
- 检索：BM25 + 向量混合，RRF 融合；rerank 二期再上
- 平台：优先框架自建（LangChain/LlamaIndex 级），因为客服 Agent 的对话状态机与转人工逻辑需要深度定制，成品平台（Dify/RAGFlow）可作为对照实验
- 评测：轻量评测集 + 人工归因起步，RAGAS 类框架二期引入

## 5. 决策结论汇总（spec 的直接输入）

**第一版做**：

1. 五层骨架完整，但 L1 允许半人工、L3 允许单库简化
2. taxonomy + 元数据 schema + 受控词表（不上本体）
3. 护栏四件套：引用溯源、拒答、转人工、疗愈伦理红线
4. 20-30 题评测集 + badcase 归因表（第一版就要有）

**第一版不做**：

1. 本体 / 知识图谱（二期，与项目 C 联动）
2. rerank、多库路由、复杂查询改写（流量验证需要后再加）
3. 权限感知检索（单租户自用场景暂无 ACL 需求；作为 FDE 接单能力单独验证）
4. Agent 长期记忆（与知识库是不同对象，按阶段门复盘结论分开定义）

**遗留待验证**（spec 中标注为开放问题）：

1. 嵌入模型与向量库的最终选型（PoC 对比后定）
2. 框架自建 vs 成品平台（用同一份语料做对照）
3. 权限感知检索的自有实现验证（FDE 接单前置能力，当前无自用场景）
