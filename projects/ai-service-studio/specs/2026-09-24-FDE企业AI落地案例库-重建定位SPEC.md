## 1. 问题与定位

GitHub 上已有企业 AI 落地案例库（guminghao-avi/FDE-case-library，127 条），组织方式是「按公司/行业陈列事实」。2026-09-24 盘点同类项目后确认空位：中文 + 结构化可筛选 + 证据分级 + 面向业务痛点的检索 + 交付模式拆解，这个位置没人占。

本项目自建案例库，切入角度为已确认的合并定位：

- **角度一（企业决策者）**：按「业务痛点」组织案例，每条案例翻译成决策语言——投入、周期、前提条件、失败点、同类企业能否复制。服务对象是中小企业老板和业务负责人，即墨予镜 FDE 服务的潜在客户。
- **角度二（交付者）**：从案例中抽象出「FDE 模式库」——诊断套路、窄场景选择、人机责任划分、评测与上线方法。案例是模式的佐证材料。服务对象是 FDE/AI 落地从业者，同时沉淀墨予镜自己的交付方法论。

对墨予镜的商业价值：案例库是获客资产（老板按痛点检索后自然进入诊断服务），模式库是服务资产（喂给 ai-service-studio 的 SOP 与报价实验）。

## 2. 数据源与取材原则

不复用上游 127 条整理数据（上游案例来源本身是公开的，我们直接回到一手来源自行提取，署名与质量自己把控）。

### 2.1 一手来源池

国内：

- [义道 FDE 案例库](https://fdehub.yidaocaiwu.com/)：24 条署名 FDE 从业者的真实落地案例，带效果数字，最佳中文一手来源
- Datawhale《FDE 案例 100》官方 PDF：100 条脱敏审核案例
- [AI落地案例库 aicases.cn](https://aicases.cn/cases)：国内企业 AI 应用实录，持续更新
- 沙丘社区榜单（AI Agent 最佳实践 TOP20 / 智能体先锋 TOP30）：批量线索，逐条核验后使用
- 大厂工程博客与公开报道：美团、东航×百度、上海银行×蚂蚁数科等单点深度素材

国际：

- Palantir 客户案例页：部署细节披露最多的一手来源
- OpenAI customer stories：效果口径为主，技术细节需配工程博客补齐
- 公司工程博客：Uber / DoorDash / Meta / Bayer / Doctolib 等，深案例主要产出方向
- themanojdesai/genai-llm-ml-case-studies（509 篇 / 127 公司）：只作线索索引，按它给的链接回到一手来源提取
- global-fde/awesome-fde-resources：资源导航，线索池

无协议声明的项目只当线索，不抄内容。

### 2.2 收录标准（质量门，取代数量指标）

不设条数配额，不设国内/国际比例。一条案例进入库中，必须同时满足：

1. **来源可定位**：有一手来源链接（官方案例页、工程博客、审核材料、PDF 页码），来源可被别人复核。
2. **对目标读者有实际价值**：中小企业决策者可参照（同行业/同规模/同痛点），或对 FDE 交付者有模式价值。满足其一即可。

首批规模预期在 40-60 条区间浮动，由质量门决定，不作为验收指标。

### 2.3 分档与分析范围

案例按公开细节分三档，三档都收录，但分析深度不同：

| 档位 | 收录条件 | 分析范围（当前确定） |
| --- | --- | --- |
| **S 级（深度）** | 公开细节足以回答决策五问（投入/周期/前提/失败点/可复制性） | 完整字段：决策五问 + fde_actions + 模式链接，参与模式抽象 |
| **标准级** | 主要方法与场景可理解，但决策五问缺项 | 收录：基础事实字段 + 痛点标签 + 来源。暂不做深分析，后续可升级 S |
| **概览级** | 只有场景与效果口径，细节不足 | 收录为线索卡，页面明确标注「细节不足，仅供参考」。暂不做分析 |

当前确定要做的分析只覆盖 S 级。标准级、概览级的分析是暂定项，后续按使用反馈决定是否升级。

### 2.4 证据口径

国内案例的效果数字绝大多数为来源方自述，无独立审计。每条案例沿用三级标注：公开事实 / 来源方披露 / 编辑分析，页面显式展示。敢给国内案例标证据等级本身是差异化，不回避。

## 3. 数据结构

### 3.1 案例（cases.json）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| detail_tier | string | S / 标准 / 概览（见 2.3） |
| pain_points | string[] | 业务痛点标签，检索主维度。标签集单独维护（见 3.3） |
| decision_info | object | 决策语言：effort / duration / prerequisites / failure_modes / transferability。仅 S 级必填 |
| delivery_pattern | string | 交付模式：诊断型 / 平台型 / 助手型 / 评测型。仅 S 级必填 |
| pattern_links | string[] | 关联的模式 ID（见 3.2）。仅 S 级 |
| fde_actions | string[] | FDE 关键动作，模式抽象的原始材料。仅 S 级 |
| company / industry / problem / solution / human / result / evidence / url | — | 基础事实与来源字段，三档必填 |

effect 类数字按 2.4 口径标注，不做独立审计暗示。

### 3.2 模式（patterns.json）

独立数据文件，角度二的核心产物：

| 字段 | 说明 |
| --- | --- |
| id / name / summary | 模式标识与一句话定义 |
| signals | 适用信号：什么情况下该考虑这个模式 |
| actions | 关键动作序列 |
| anti_patterns | 反模式：什么情况下这个模式会失败 |
| case_refs | 佐证案例 ID 列表（≥2 条才允许立模式） |

模式只从 S 级案例的 fde_actions 高频项统计抽象产生。首版规模 8-12 个模式。

### 3.3 痛点标签集（pain-points.json）

独立维护的受控词表，首版从首批案例的 problem 字段聚类产生，预计 15-25 个标签（如：客服成本 / 文档审核 / 专家知识流失 / 遗留系统维护 / 质检依赖人工 等）。标签集对外公开，接受 issue 投稿修订。

## 4. 页面形态

零依赖静态站（无构建步骤），GitHub Pages 部署：

- 首页：痛点标签检索为主界面（不是行业/公司列表），次要筛选维度为行业、交付模式、档位、证据等级。
- 案例详情：单条独立页面，可分享单条链接；S 级的决策语言块（decision_info）置顶展示；标准/概览级明确标注当前未做深分析。
- 模式详情：单条独立页面，列出佐证案例；案例与模式双向互链。
- 每个页面显式标注档位、证据等级与来源。

## 5. 阶段划分

| 阶段 | 内容 | 出口标准 |
| --- | --- | --- |
| M1 首批数据 | 按 2.2 质量门从一手来源提取首批案例，按 2.3 分档 | 见第 6 节 |
| M2 模式库 v1 | S 级 fde_actions 频率统计 → 模式抽象 → patterns.json | 8-12 个模式，每个 ≥2 佐证案例 |
| M3 页面 | 首页 + 案例详情 + 模式详情，GitHub Pages 上线 | 可公开访问 |
| M4 扩容 | 按同一质量门持续补充新案例，标准级可按需升级 S | 不设目标条数 |

## 6. 验收指标（M1 出口）

1. 首批案例全部满足 2.2 两条收录标准，逐条可指出一手来源链接。
2. 每条 S 级案例：decision_info 五字段完整、delivery_pattern 非空、fde_actions 非空。
3. 每条案例：detail_tier 非空、pain_points 非空、基础事实字段完整。
4. pain-points.json 标签数 15-25 个，每个标签下 ≥2 条案例（不足的标签说明原因）。
5. 每条案例标注证据口径（公开事实/来源方披露/编辑分析），来源方披露的效果数字无独立审计暗示表述。
6. 校验脚本通过：必填字段、标签合法性、ID 唯一、档位与字段必填规则一致。
