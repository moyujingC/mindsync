# 知行AI服务案例库 SPEC

> 项目：[知行AI服务](../PROJECT.md)
> 任务级别：执行落地

## 1. 问题定义

客户需要通过具体案例判断服务是否贴合自己的问题，但项目当前处于验证期：已有不少外部研究和服务设计材料，尚缺少可包装为成熟客户成果的真实交付案例。

如果直接把外部案例改写成“自己的案例”，会造成来源、能力和结果的误导；如果完全不展示案例，又难以把现有能力、演示和研究转成可理解的售前资产。

## 2. 用户与场景

- 潜在客户：想判断“我的流程或资料问题是否适合先做 AI 小实验”的小团队负责人、专业服务者或企业业务负责人。
- 服务提供者：需要快速选择合适案例、明确展示边界，并在真实交付后稳定沉淀复盘的人。
- 使用场景：售前沟通、客户定向展示、交付复盘、内容选题和案例资产维护。

## 3. 本轮范围

- 建立一个项目级案例库入口，按客户问题和案例类型导航。
- 规定真实交付、自用验证、模拟演示、外部参考四类资产的证据与表达边界。
- 提供一张可复用的案例卡模板。
- 把已有外部参考以“外部参考”身份接入索引，不复制或改写为自有案例。

## 4. 不做范围

- 不新增虚构客户案例、虚构数据、虚构截图或虚构客户反馈。
- 不将当前外部参考改写为真实交付案例。
- 不在本轮建设飞书多维表、网站、视觉作品集或客户授权流程。
- 不改变现有服务范围、报价或行业策略。

## 5. 结构选择

案例库采用“按客户问题入口 + 按案例证据类型分层”的结构。

原因：客户先关心自己遇到什么问题；内部维护时则必须先区分证据强度和对外表达权限。仅按行业或仅按服务名会掩盖模拟演示和真实交付之间的差异。

## 6. 验收标准

1. 项目入口能导航到案例库和案例卡模板。
2. 案例库明确四类资产的可说与不可说范围。
3. 所有现有案例引用都保留为“外部参考”，且能定位到来源文件。
4. 模板能记录范围、证据、未验证项、脱敏与授权状态。
5. 对外展示前有可执行的检查清单。

## 7. 风险与后续 handoff

- 风险：案例库仍为空时，容易为了售前压力而过度包装模拟演示。
- 控制：每张案例卡必须填案例类型、证据状态和授权状态；没有证据的结果不写成事实。
- 下一步：首次真实服务完成后，由交付负责人用案例卡模板从复盘记录提炼，并在客户确认展示范围后升级到“真实交付”。
