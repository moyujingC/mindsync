## 1. 架构目标

本架构只支撑“受控知识库 + 有限 Agent 工作流 + 人工接管”三个能力。它先服务 P1/P2，后续再让一镜一梳、内容矩阵和课程项目按隔离空间接入。

```text
渠道适配层（公众号 / 企业微信 / Web 测试台）
    -> 会话编排层（意图、状态机、规则、人工接管）
    -> 知识与工具层（FAQ、RAG、资料包、表单）
    -> 数据与评测层（来源、版本、日志、评测、反馈）
    -> 人工运营层（交接卡、审核、知识发布/回滚）
```

## 2. 模块边界

| 模块 | 责任 | 首轮实现 | 明确不承担 |
| --- | --- | --- | --- |
| 渠道适配层 | 校验公众号/企微回调，转换消息，返回渠道允许的响应 | Web 测试台优先；公众号和企微使用独立适配器 | 不保存跨渠道完整对话 |
| 会话编排层 | 意图分类、状态机、规则优先级、转人工 | 仅支持找服务/谈合作/了解范围/转人工 | 不负责通用闲聊或自主执行 |
| 安全策略层 | 敏感信息提示、越界拦截、固定安全出口 | 规则优先，模型只辅助分类 | 不做心理风险诊断或处置结论 |
| 知识接入层 | 解析、清洗、切分、元数据、发布/下架 | Markdown/PDF/网页转存文本；人工审核后发布 | 不自动把聊天或客户资料入库 |
| 检索与回答层 | 混合检索、来源引用、无依据拒答 | FAQ 优先，向量检索为补充 | 不允许无来源生成服务承诺 |
| 人工运营层 | 交接卡、资料包、审核、知识版本管理 | 最小管理脚本或受控表单 | 不在首轮建设复杂后台 |
| 观测与评测层 | 会话、检索、回答、转人工、人工修正和评测运行记录 | 结构化日志 + 评测命令/脚本 | 不承诺完整 APM（应用性能监控）平台 |

## 3. 数据边界与隔离

### 3.1 逻辑空间

每条记录都必须带 `workspace_id` 和 `knowledge_space_id`。首轮预设三个知识空间：

| 知识空间 | 可放内容 | 禁止内容 |
| --- | --- | --- |
| `moyujing-enterprise-service` | 服务说明、公开文章、FAQ、资料包、表单说明 | 企业客户资料、联系人、完整聊天、报价谈判原文 |
| `yijingyishu-intake-course` | 已审定的课程/服务说明、知情同意、边界、固定安全出口 | 个案记录、身份线索、心理状态推断、危机文本库 |
| `content-operations` | 账号定位、可公开素材、人工批准的选题和模板 | 原始私信、可识别用户反馈、其他账号私有资产 |

向量条目必须同时保存：`source_id`、`source_version`、`knowledge_space_id`、`visibility`、`approved_at`、`expires_at` 和原文定位信息。检索必须先按知识空间过滤，再计算相似度，不能只在最终回答层隐藏资料。

### 3.2 数据分类

| 数据类 | 示例 | 存放/处理规则 |
| --- | --- | --- |
| 已审定知识 | FAQ、公开文章、规则、课程讲义 | 可进入对应向量知识空间，保留来源与版本 |
| 线索交接数据 | 意图、时间、是否加企微、下一步 | 单独保存，不进入向量库和内容系统 |
| 用户提交材料 | 表单、脱敏流程图、课程报名信息 | 仅为当前沟通保留，需明确同意；默认不入库 |
| 敏感/个案数据 | 心理状态、个案、联系人、企业内部资料 | 首轮拒绝接收或仅在受控人工流程处理；禁止嵌入和训练 |
| 聚合洞察 | 经同意的不可回溯主题/频次 | 单独聚合后才可供内容/产品复盘使用 |

## 4. 首轮技术路线

| 层级 | 推荐选择 | 选择原因 | 替换边界 |
| --- | --- | --- |
| 服务端 | FastAPI（Python Web 框架） | 适合 Webhook（事件回调）、异步任务和清晰的 API 合同 | 业务逻辑不得依赖渠道 SDK |
| 数据库 | PostgreSQL + pgvector（向量扩展） | 用一套数据库保存业务状态、知识元数据、嵌入向量和日志 | 通过 repository 接口隔离，可替换独立向量库 |
| 模型接入 | OpenAI 兼容 API 适配层 | 支持更换聊天与嵌入模型，避免在业务代码写死供应商 | 不同模型配置通过环境变量/配置文件注入 |
| 任务处理 | 数据库任务表 + worker | 首轮可追踪解析、嵌入、重建索引和评测任务 | 不先引入消息队列集群 |
| 文件存储 | 本地受控目录或对象存储 | 保存原文件和解析产物，避免只存切片 | 生产前需补权限、加密、生命周期策略 |
| 管理入口 | CLI（命令行工具）或受控内部 Web 页 | 优先证明发布、回滚、评测和观察能力 | 不建设面向客户的后台 |

该技术路线是首轮实施建议，不等同于对外的固定技术选型承诺。真实企业项目应根据数据源、权限、部署网络和维护责任重新设计。

## 5. 关键合同

### 5.1 知识条目发布合同

```text
草稿资料
-> 解析并保留原始来源
-> 人工检查元数据、可见范围和有效期
-> approved
-> 写入向量索引
-> 可检索
-> superseded / withdrawn
```

任何未进入 `approved` 状态的条目不能被生产会话检索。被下架的条目在新会话中立即不可用，历史会话保留当时引用的版本标识。

### 5.2 回答与转人工合同

```text
规则命中（敏感/越界/人工请求） -> 固定回复 + handoff_required
FAQ 命中 -> 已审定固定答案
RAG 命中且证据充分 -> 带来源回答
证据不足/冲突/置信不足 -> 不确定说明 + handoff_required
```

模型不能自主决定报价、项目方案、预约、诊断结论、疗愈建议或知识发布。

### 5.3 最小日志合同

每次交互记录：`event_id`、`workspace_id`、`channel`、`intent`、`policy_action`、`knowledge_version`、`retrieved_source_ids`、`answer_template_or_model_version`、`handoff_reason`、`final_human_status`、`created_at`。日志默认不记录不必要的原始敏感文本。

## 6. 运行与安全风险

| 风险 | 首轮控制措施 | 进入真实外部使用前的门槛 |
| --- | --- | --- |
| 幻觉/错引 | FAQ 优先、来源引用、无依据拒答、固定评测集 | 检索质量和 badcase 复测通过 |
| 资料过期 | 版本、有效期、下架和重建索引 | 明确资料责任人与更新频率 |
| 跨账号/跨用户泄露 | 空间级过滤、分离日志、禁止跨空间记忆 | 权限测试和数据删除演练 |
| 心理疗愈越界 | 规则优先阻断、固定人工出口 | 专业审阅者批准安全内容 |
| 渠道回调不稳定 | Web 测试台先行、幂等事件 ID、失败重试 | 真实渠道签名校验和监控 |
| 成本失控 | 单会话 token 上限、检索 top-k 上限、任务状态记录 | 成本报表与预算阈值 |

## 7. 实现前提与顺序

1. 先定义 P2 的需求规格、知识条目样本和 30 条评测问题。
2. 先在 Web 测试台跑通 P1/P2，保留每次测试的输入、预期、结果和日志证据。
3. 再接公众号或企业微信的一个渠道，验证事件适配与人工交接。
4. P2 稳定后，通过新知识空间接入 P3 或 P4；不复制整套服务。
5. P5 只在已有课程内容、学习状态和人工答疑边界确定后进入实现。

## 8. Handoff

- 给 Engineer：实现 P1/P2 的最小服务端、数据模型、知识导入、检索、会话状态机、日志和 Web 测试台。
- 给 Test / QA：建立 30 条评测集，至少覆盖正常、无依据、版本冲突、越界、人工接管、跨空间拒绝和渠道重试。
- 给 Product Spec Lead：先补 P2 详细 spec；P3-P5 分别在开始前补各自的局部 spec，不能用本文件替代具体需求定义。
