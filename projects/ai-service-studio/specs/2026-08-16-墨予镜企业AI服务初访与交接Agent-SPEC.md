## 1. 用户与问题

| 角色 | 要完成的事 | 当前问题 |
| --- | --- | --- |
| 公众号访客 | 快速判断能否获得 AI 服务支持或讨论合作 | 不知道服务范围，不愿在公众号提交企业资料 |
| 企业微信线索 | 提供最少背景并获得明确下一步 | 重复说明、资料要求不清楚、害怕过早泄露内部信息 |
| 本人（人工服务台） | 判断是否值得进入需求诊断 | 线索信息分散，重复解释服务范围，难以回顾问题和反馈 |

本项目只解决“首次咨询到人工判断”的链路，不解决企业 AI 项目的方案、报价、实施或交付。

## 2. 单一主路径

```text
访客进入公众号/Web 测试台
-> 选择或表达找服务、谈合作、了解范围
-> Agent 说明范围并给出来源；不展开具体诊断
-> 访客自主添加企业微信
-> 企微发送对应资料包与最少信息表
-> 生成交接卡
-> 人工审核：约诊断 / 继续补充 / 暂不匹配
-> 记录最终状态和需补充的 FAQ
```

## 3. 本轮范围

### 3.1 需要实现

1. `find_service`、`discuss_cooperation`、`understand_scope`、`handoff_human` 四种意图。
2. 服务说明、FAQ、资料包和表单说明的结构化知识库与向量检索。
3. 每次回答显示可追溯来源；FAQ 优先于模型自由生成。
4. 企微交接卡的最小字段和人工状态更新。
5. 用户主动要求方案、报价、预约、提交内部资料或表达无法判断的问题时，触发人工接管。
6. 在 Web 测试台完成首轮测试，之后再接一个真实渠道。

### 3.2 明确不做

- 不在公众号收集企业名称、联系人、内部文件、完整流程、密码或完整客户数据。
- 不自动生成项目方案、报价、交付周期和预期效果。
- 不自动预约或保证可安排诊断。
- 不让渠道消息直接写入公共向量知识库。
- 不让系统以“已服务企业客户”或“已验证转化”口径对外表达。

## 4. 初始知识范围

| 知识类 | 首批来源 | 更新责任 | 发布前检查 |
| --- | --- | --- | --- |
| 服务范围与边界 | 项目入口、初访试点设计 | 本人 | 不含效果承诺和未验证能力 |
| FAQ | 真实反复问题或模拟评测中出现的问题 | 本人 | 有固定答案、版本、生效时间 |
| 资料包 | 需求诊断说明、合作说明、信息表 | 本人 | 明确最少信息和脱敏提示 |
| 公开内容 | 已发布且仍有效的墨予镜内容 | 本人 | 链接、发布日期、适用场景、失效日期 |

## 5. 人机边界

| 节点 | Agent 可做 | 人工必须做 |
| --- | --- | --- |
| 服务范围问答 | 解释已审定的范围、步骤和材料要求 | 调整服务边界或承诺能力 |
| 意图识别 | 归类并请用户确认 | 处理模糊、跨范围或高价值线索 |
| 检索回答 | 基于来源给出简短说明 | 解释复杂项目适配性和实际方案 |
| 资料收集 | 提示只填写最少概括信息 | 阅读、保留、判断用户主动提交的材料 |
| 交接 | 生成结构化交接卡 | 确认下一步、约诊断、报价、拒绝或合作决定 |

## 6. 验收标准

1. 两类模拟访客能完成正确导流；系统不会要求敏感企业资料。
2. 范围性问题的回答均附有来源；资料不足时不编造。
3. 至少 10 条请求被正确转人工，包含方案、报价、预约、敏感资料和无依据问题。
4. 人工读取交接卡后，不需查看公众号完整对话即可确定下一步。
5. 所有日志中均可查询意图、规则动作、检索来源、回答版本和最终人工状态。
6. 至少完成一次知识条目更新和同一评测集的更新前后对比。
