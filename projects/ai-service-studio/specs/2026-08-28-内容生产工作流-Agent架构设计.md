## 0. 背景

原《第一篇工作流复盘：从选题到成稿》记录的是《为什么企业 AI 项目总是在 POC 后死掉？》的人工创作过程。随着内容生产规模扩大，需要把这套流程升级为可自动化、可规模化的 Agent 工作流。

本文档基于亦仁关于内容生产 Agent 架构的讨论，将原六阶段人工工作流重新设计为 Agent 驱动的六阶段工作流。

---

## 1. 核心原则

1. **内容生产内部：单 Agent 多 Skill，不是多 Agent 串联**：内容访谈、素材整理、内容单元组装、审阅打磨这几个环节强依赖上下文，应该放在同一个 Agent 内，做成不同 Skill。拆成多个 Agent 会导致上下文断裂、协调成本高。
2. **跨环节：按上下文边界拆分为独立 Agent**：内容生产 Agent 只负责“把选题变成内容单元”。选题、多平台分发、数据监控与内容生产的上下文边界不同，应该独立为 Agent 或 Agent 集合。
3. **选题必须独立成 Agent**：选题需要信息广度、判断力和持续扫描，与内容生产的“深度收敛”是两种能力，必须独立。
4. **分发与生产分离**：多平台分发 Agent 与内容生产 Agent 目标不同、上下文不同、风险等级不同，不能合并。一个平台一个 Agent，一个账号一套 Agent 集合。
4. **“成稿”不是最终文章，而是标准化“内容单元”**：内容单元是中间产物，包含标题、摘要、正文、标签、适用场景，可被不同平台分发 Agent 复用。
5. **内容访谈不是草稿，而是结构化素材提取**：先通过访谈把隐性知识变成结构化素材库，再基于素材库组装内容单元。
6. **数据必须回流**：发布数据沉淀到飞书多维表格，反哺选题 Agent 和内容生产 Agent，形成闭环。

## 2. 内容单元的类型定义

内容生产 Agent 在组装内容单元时，不直接写“小红书笔记”或“公众号文章”，而是先确定**内容类型**。类型决定结构、长度、表达方式，平台只是后续分发的变量。

| 内容类型 | 字数 | 结构 | 适用平台 |
|----------|------|------|----------|
| **深度拆解型** | 5000-8000 字 | 问题定义 → 案例拆解 → 底层逻辑 → 可复制方法 | 公众号、知识星球、长文平台 |
| **观点输出型** | 800-1500 字 | 一个反常识观点 → 3 个论据 → 1 个行动建议 | 朋友圈、即刻、Twitter |
| **案例快报型** | 300-500 字 | 谁做了什么 → 结果如何 → 为什么值得关注 | 社群分享、日报、快讯 |

内容单元的格式标准：

- **可读性**：即使脱离上下文，也能独立理解
- **可拆解性**：每个部分都能被单独提取和使用
- **可组合性**：多个内容单元可以组合成一篇长文或一个系列
- **可追溯性**：每个观点、数据、案例都有来源标注

## 3. 六阶段工作流

### 阶段一：选题 Agent —— 从信息源到选题池

**做什么**

- 独立运行，持续扫描信息源：
  - 行业 RSS、关键词搜索趋势
  - 竞品公众号/小红书/推特动态
  - 用户评论、私信、社群讨论
  - 课程知识库、历史内容数据
- 按预设标准输出选题列表，存入飞书知识库“选题池”
- 每个选题包含：标题方向、用户痛点、竞品覆盖情况、信息源、优先级

**输入**

- 关键词库、用户问题库、竞品内容库、课程知识库
- 历史发布数据（用于优化选题方向）

**输出**

- 飞书多维表格“选题池”：标题方向、用户痛点、竞品覆盖情况、信息源、优先级、建议内容类型

**人工介入点**

- 从选题池里筛选出高质量选题，打上优先级标签
- 保留判断权：Agent 可以找选题、分析选题，但“值不值得写”由人定

---

### 阶段二：内容访谈 Agent —— 从选题到结构化素材库

**做什么**

- 从选题池拉取高优先级选题
- 围绕选题，按固定框架进行“结构化素材提取”
- 输出不是文章，而是结构化的素材库

**素材库结构**

- **背景信息**：时间、场景、人物、条件
- **关键动作**：具体做了什么、顺序是什么
- **踩坑记录**：哪些尝试失败了、为什么
- **数据结果**：效率提升、成本变化、用户反馈
- **核心认知**：做完之后对这件事的理解变化
- **来源标注**：每条素材追溯到原始课程、文档或访谈

**输入**

- 选题池中的高优先级选题
- 课程库、文档库、专家访谈记录

**输出**

- 飞书文档/多维表格“素材库”

**与原人工流程的对应**

- 替代原来的“知识采矿阶段（Agent 集群）”和“卡片整理阶段”
- 输入卡片 ≈ 素材库中的条目；主题卡片 ≈ 素材库的结构化归类

**关键提醒**

- 素材库质量是内容单元质量的天花板
- 严格控制每个 Agent/Skill 的输出数量，避免信息过载
- 不要把 Agent 输出直接当草稿

---

### 阶段三：内容单元组装 Agent —— 从素材库到标准化内容单元

**做什么**

- 读取结构化素材库
- 按“内容单元”格式组装输出
- 内容单元是中间产物，不绑定任何平台

**内容单元格式**

- **标题**：一句话概括核心观点，有冲突感
- **摘要**：3-5 句话说明内容价值
- **正文**：按选题需要的长度展开，以“说透”为准，不设固定字数
- **关键标签**：3-5 个关键词
- **适用场景建议**：适合什么平台、什么人群、什么场景

**输入**

- 结构化素材库
- 账号定位、目标读者、内容类型

**输出**

- 飞书知识库“内容单元库”

**人工介入点**

- 标题和摘要需要人工重点把关
- 确认信息密度和表达力度

**与原人工流程的对应**

- 替代原来的“草稿阶段”和“成稿阶段”
- 原来的“草稿”变成“素材库组装过程”，原来的“成稿”变成“内容单元”

**关键提醒**

- 不要固定字数，素材多就长、素材少就短
- 不要在组装阶段纠结平台适配，那是分发 Agent 的事
- 正文需先堆信息密度，再统一语气、优化衔接、调整节奏

---

### 阶段四：审阅打磨阶段 —— 从内容单元到可发布内容

**做什么**

- 对内容单元进行结构审阅、表达审阅、读者适配审阅
- 控制在 2 轮：
  - 第一轮：结构审阅（检查结构重复、逻辑硬伤、素材重复）
  - 第二轮：成稿综合审阅（表达、读者适配、专业准确性、传播潜力）
- 人工最终审核标题、摘要和金句

**审阅标准**

- 术语密度降到非技术读者可接受
- 加粗金句控制在 3 句以内，且句式错开
- 每个案例都经得起工程推敲
- 引用都能追溯到一手来源，否则用模糊表述
- 结尾给出可截图/可收藏的交付物

**人工介入点**

- 最终审核标题、摘要、金句
- 决定是否发布

**与原人工流程的对应**

- 扩展原来的“成稿与多轮审阅阶段”
- 从 3 轮 13 个 Agent 精简为 2 轮

**关键提醒**

- 结构审阅要提前到内容单元阶段，不要在成稿后再大修结构
- 每次修改要有明确目标，按反馈清单改

---

### 阶段五：多平台分发 Agent 集群 —— 从内容单元到各平台发布

**做什么**

- 每个平台一个独立 Agent，从内容单元库拉取内容
- 按平台规则转换格式：公众号长文、小红书图文、即刻短内容等
- 处理标题、封面、排版、发布时间
- 调用平台 API 或 RPA 发布
- 记录发布结果和链接

**分发 Agent 设计原则**

- 内容生产 Agent 不关心平台规则，分发 Agent 不关心内容创意
- 一个平台一个 Agent，一个账号一套 Agent 集合
- 分发 Agent 是“格式转换器 + 定时发布器”，不需要深度理解内容
- 各平台账号、IP、API Key 隔离，降低风控关联风险

**输入**

- 内容单元库中的已审核内容单元

**输出**

- 各平台发布结果、发布链接、发布时间
- 飞书多维表格“内容数据总表”初始记录

**账号与平台对应示例**

| 账号 | 定位 | 主要平台 | 分发策略 |
|------|------|----------|----------|
| 企业 AI 落地业务账号 | 个人 IP 号 | 公众号、知乎、LinkedIn | 深度拆解型为主 |
| 疗愈师 AI 课账号 | 获客内容号 | 小红书、抖音、视频号 | 观点输出型、案例快报型为主 |

---

### 阶段六：数据回流与迭代 —— 从发布数据到系统优化

**做什么**

- 每个分发 Agent 定时回传数据：阅读量、点赞、评论、转发、收藏、转化
- 数据统一沉淀到飞书多维表格
- 定期由数据监控 Agent 或人工复盘
- 把结论以规则/提示词更新的方式，反哺选题 Agent 和内容生产 Agent

**数据表结构**

- **内容数据总表**：每条记录对应一篇已发布内容，字段包括内容 ID、标题、平台、发布时间、阅读量、点赞、评论、转发、收藏、转化、数据更新时间
- **选题数据汇总表**：按选题方向汇总所有平台数据
- **平台健康度表**：按平台维度汇总，看哪个平台流量稳定、哪个平台在下降

**数据回传时间**

- 小红书：发布后 24 小时数据基本稳定
- 公众号：发布后 48 小时数据基本稳定
- 抖音：发布后 6 小时数据就能看出趋势
- Twitter：发布后 2 小时数据就差不多了

**反馈闭环**

- 选题 Agent 读取选题数据汇总表，调整选题方向
- 内容生产 Agent 读取高表现内容的共同特征，复用到提示词中
- 人工每月一次深度复盘，做方向性调整

## 4. 账号定位：个人 IP 号 vs 获客内容号

根据业务变现方式不同，两个账号应采用不同的 Agent 配置。

| 维度 | 企业 AI 落地业务账号 | 疗愈师 AI 课账号 |
|------|----------------------|------------------|
| 定位 | 个人 IP 号 | 获客内容号 |
| 核心目标 | 建立信任，降低高客单价决策门槛 | 批量获客，提升转化效率 |
| 内容逻辑 | 70% 干货 + 20% 案例 + 10% 个人思考 | 90% 干货 + 10% 转化钩子 |
| 选题方向 | 企业 AI 落地的真实问题、深度拆解 | 疗愈师痛点、AI 工具实操 |
| 内容风格 | 第一人称、真实案例、个人观点 | 信息密集、可复制、低门槛 |
| 分发平台 | 公众号、知乎、LinkedIn 为主 | 小红书、抖音、视频号为主 |
| 私域转化 | 高客单价，AI 培育 + 人工成交 | 低客单价，AI 可完成全链路 |

**关键提醒**：不要两个账号都“既要又要”。个人 IP 号不要批量生产干货，获客内容号不要花太多时间建立个人故事。

## 5. Agent 集合设计总览

基于上下文边界，建议拆分为四个独立的 Agent 集合：

```
┌─────────────────────────────────────────────────────────┐
│                      选题 Agent 集合                      │
│  持续扫描信息源 → 产出选题池 → 人工审核优先级            │
└──────────────────────┬──────────────────────────────────┘
                       │ 选题池
┌──────────────────────▼──────────────────────────────────┐
│                   内容生产 Agent 集合                     │
│  内容访谈 Skill → 内容单元组装 Skill → 审阅打磨 Skill    │
│  （单 Agent 多 Skill，上下文共享）                        │
└──────────────────────┬──────────────────────────────────┘
                       │ 内容单元库
┌──────────────────────▼──────────────────────────────────┐
│                   公域流量 Agent 集合                     │
│  分发 Agent 集群：公众号 / 小红书 / 抖音 / 即刻 / Twitter │
│  （一个平台一个 Agent，一个账号一套集合）                 │
└──────────────────────┬──────────────────────────────────┘
                       │ 发布数据
┌──────────────────────▼──────────────────────────────────┐
│                   数据监控 Agent 集合                     │
│  收集数据 → 沉淀多维表格 → 异常报警 → 反馈优化           │
└─────────────────────────────────────────────────────────┘
```

每个 Agent 集合内部再拆为“决策 Agent”和“执行 Agent”两层：

- **决策 Agent**：负责判断（如选题优先级、高意向用户识别、内容是否通过审阅）
- **执行 Agent**：负责干活（如生成素材库、发布内容、回传数据）

**关于“单 Agent 多 Skill”与“多个 Agent 集合”的关系**

这二者并不矛盾，而是不同层级的切分：

- **内容生产 Agent 集合内部**是“单 Agent 多 Skill”：内容访谈、内容单元组装、审阅打磨共享同一个上下文，避免素材和判断在多个 Agent 之间传递时失真。
- **跨 Agent 集合**是“多个独立 Agent”：内容生产、选题、分发、数据监控的上下文边界不同，必须独立，否则会出现上下文污染和协调成本。

简单说：**强上下文依赖的环节放同一个 Agent 内做 Skill；上下文边界清晰的环节拆成独立 Agent。**

## 6. 共享数据层设计

Agent 集合之间不直接通信，通过共享数据层协作：

| 数据存储 | 用途 | 写入方 | 读取方 |
|----------|------|--------|--------|
| 飞书多维表格“选题池” | 存放候选选题 | 选题 Agent | 内容生产 Agent、人工 |
| 飞书文档/表格“素材库” | 结构化素材 | 内容访谈 Skill | 内容单元组装 Skill |
| 飞书知识库“内容单元库” | 标准化内容单元 | 内容单元组装 Skill | 分发 Agent 集群、人工 |
| 飞书多维表格“内容数据总表” | 发布数据 | 分发 Agent 集群 | 数据监控 Agent、选题 Agent、人工 |
| 飞书多维表格“选题数据汇总表” | 按选题方向聚合数据 | 数据监控 Agent | 选题 Agent、人工 |
| 飞书多维表格“平台健康度表” | 按平台维度聚合数据 | 数据监控 Agent | 人工 |

## 7. 实施节奏建议

不要一次性搭建完整架构。按以下顺序逐步跑通：

**第一步：跑通内容生产 Agent 集合**（进行中）
- ✅ 仓库 `myj-ai-content-agents` 已创建并开源
- ✅ 状态机、SQLite 持久化、CLI 入口已实现
- ✅ 内容单元组装 Skill 已接入 Kimi K3 并跑通
- ✅ 本地 Markdown 知识库、Get笔记 API 已接入
- ⚠️ 内容访谈 Skill 已实现基础版，但素材分类仍较粗糙
- ⚠️ 审阅打磨 Skill 为占位实现，需接入 Eval 和 LLM 审阅
- 选题先以人工通过 CLI 传入为主

**第二步：把选题独立成 Agent**
- 当内容生产跑通后，把选题自动化
- 初期可半自动：选题 Agent 扫描 + 人工审核选题池

**第三步：跑通一个平台的分发 Agent**
- 先选公众号作为首个平台
- 完成从内容单元到发布的完整链路
- 记录发布数据

**第四步：扩展多平台分发 Agent 集群**
- 复制公众号 Agent 的逻辑到小红书、抖音等平台
- 每个平台独立调试

**第五步：建立数据回流闭环**
- 收集发布数据
- 沉淀到飞书多维表格
- 定期复盘，反哺选题和内容生产

## 8. 技术栈与实现状态

本节记录技术栈的已决策结论、已落地实现和剩余待解决问题。

### 8.1 当前约束（已部分落地）

- **运行环境**：本地 Mac
- **Agent 实现**：已选择**轻量自研**，仓库 [`moyujingC/myj-ai-content-agents`](https://github.com/moyujingC/myj-ai-content-agents) 已创建并开源
  - 核心调度、状态机、Skill 抽象、SQLite 持久化均已实现
  - Hermes Agent 不再作为首选方案，仅保留为历史备选参考
- **内容生产大模型**：Kimi K3 已接入 `assembly.py`，支持 JSON mode 输出内容单元
  - 约束：K3 只支持 `temperature=1`，且必须用 `response_format={"type": "json_object"}` 才能稳定返回结构化结果
- **知识库来源**：
  - 本地 Markdown 知识库（MindSync 目录）已接入 `local_markdown.py`
  - Get笔记（biji.com）个人开发者模式已接入 `knowledge/getnote.py`
    - 可读取笔记列表、知识库列表
    - **知识库语义召回接口在个人模式下返回 404，暂未开通**，已自动降级为关键词筛选
    - 企业代授权模式因无 GetSeed 录音卡资质，无法开通
- **分发平台与方式**：
  - 企业 AI 落地业务账号：公众号（官方 API）、小红书（手动发布）
  - 疗愈师 AI 课账号：小红书（手动发布）、抖音（手动发布）
- **自动化程度**：人必须参与审核，不追求全自动
- **人机协作方式**：命令行 CLI + SQLite 状态持久化；飞书集成尚未接入
- **设计倾向**：受课程影响，选择轻量自研，避免框架黑盒
- **DeepSeek Harness**：待安装后评估，当前不绑定核心系统

### 8.2 Agent 实现方案（已决策）

| 方案 | 结论 | 说明 |
|------|------|------|
| **A. 直接用 Hermes Agent** | ❌ 不采用 | Skill 模型与内容单元格式映射不自然，内存占用高，黑盒风险大 |
| **B. 轻量自研 + 少量依赖** | ✅ 采用 | 仓库已创建，核心调度、状态机、Skill 抽象已实现，完全可控 |
| **C. 基于现成框架二创** | ❌ 不采用 | 仍受框架约束，与课程“框架已死”理念不一致 |
| **D. 从头自研所有基础设施** | ❌ 不采用 | 成本过高，使用成熟库处理 HTTP、数据库、配置加载 |

**决策理由**：
- 内容生产工作流的核心是“状态机 + Skill 调度 + 内容单元格式”，自研成本可控
- 依赖库仅用于基础设施（Pydantic、requests、PyYAML、sqlite3、python-dotenv），不引入 Agent 框架黑盒
- 代码结构面向 Codex/Claude Code 协作优化，便于持续迭代

### 8.4 当前技术栈

- **Agent 实现**：Python 自研（`myj-ai-content-agents`）
- **大模型**：Kimi K3（内容组装）；审阅环节可备选 Claude/GPT
- **知识库**：本地 Markdown + Get笔记个人 API
- **数据持久化**：本地 SQLite（`.runtime/` 目录，不提交 Git）
- **配置**：YAML（账号配置）+ `.env`（API Key 等敏感信息）
- **分发**：公众号官方 API；小红书、抖音先手动发布，后续再考虑 RPA
- **Harness 平台**：DeepSeek Harness 作为实验田，不绑定核心系统

### 8.5 已落地实现概览

仓库 [`moyujingC/myj-ai-content-agents`](https://github.com/moyujingC/myj-ai-content-agents) 已实现内容生产 Agent 集合的最小闭环：

#### 8.5.1 核心模型

```python
class ContentUnit(BaseModel):
    id: str
    topic_id: str
    account_id: str
    content_type: ContentType
    title: str = ""
    summary: str = ""
    body: str = ""
    tags: list[str] = []
    usage: dict[str, Any] = {}
    sources: list[SourceItem] = []
    status: str = "created"      # created / interviewing / assembling / reviewing / approved / rework / failed
    round_no: int = 0            # 当前审阅轮数
    max_rounds: int = 3          # 最大审阅轮数
    trace: list[dict] = []       # 状态流转记录
```

#### 8.5.2 状态机

```
created → interviewing → assembling → reviewing → approved
                              ↓            ↓
                           rework      failed
```

- 所有状态流转通过 `ContentUnitStateMachine` 显式校验
- 只有 `reviewing` 状态才能被人工 `approve` 或 `request_rework`
- 达到 `max_rounds` 后不能再请求返工，只能标记为 `failed`

#### 8.5.3 Skill 设计

| Skill | 文件 | 职责 | 状态 |
|-------|------|------|------|
| 内容访谈 | `skills/interview.py` | 从知识库召回素材，输出结构化 `Material` | 已实现基础版，分类规则较粗糙 |
| 内容单元组装 | `skills/assembly.py` | 调用 Kimi K3 生成标题、摘要、正文、标签 | 已实现并跑通 |
| 审阅打磨 | `skills/review.py` | 基础长度/标签检查，等待接入 Eval 和 LLM 审阅 | 占位实现 |

#### 8.5.4 知识库来源

| 来源 | 文件 | 状态 |
|------|------|------|
| 本地 Markdown | `knowledge/local_markdown.py` | 已接入 |
| Get笔记（biji.com） | `knowledge/getnote.py` | 已接入个人模式；语义召回 404，已降级为关键词筛选 |

#### 8.5.5 CLI 入口

```bash
# 运行演示
python -m myj_ai_content_agents.cli demo --account enterprise-ai --stop-at assembling

# 从选题运行
python -m myj_ai_content_agents.cli run \
  --topic "为什么企业 AI 项目总是在 POC 后死掉" \
  --account enterprise-ai \
  --content-type deep-dive \
  --stop-at reviewing

# 人工审核
python -m myj_ai_content_agents.cli review cu-20260829-xxxxxx \
  --reviewer 崔兴 \
  --decision approve \
  --note "标题和摘要已通过，可以发布"

# Eval 检查
python -m myj_ai_content_agents.cli eval cu-20260829-xxxxxx
```

#### 8.5.6 已知问题与限制

1. **内容访谈 Skill 的素材分类较粗糙**：目前用关键词硬规则分类，后续应接入 LLM 做更精准的结构化提取
2. **审阅打磨 Skill 是占位实现**：只做了基础长度检查，尚未接入 Eval 检查清单和 LLM 审阅
3. **Get笔记语义召回不可用**：个人开发者模式下 `POST /api/v1/resource/note/recall` 返回 404，当前降级为拉取笔记列表后做关键词筛选
4. **选题 Agent 尚未实现**：当前选题由人工通过 CLI 传入
5. **分发 Agent 尚未实现**：内容单元生成后需人工复制到各平台发布
6. **数据回流尚未实现**：无发布数据自动回传

### 选题 Agent
- [ ] 是否持续扫描关键词搜索趋势、竞品动态、用户问题？

- [ ] 是否限制了输出数量，避免信息过载？
