## 1. 背景

当前需要建设的不是一组彼此无关的 Demo（演示原型），而是一套由真实自用场景驱动的企业级 Agent 能力组合。它服务两项长期目标：

1. 为上海 AI 产品经理、FDE（Forward Deployed Engineer，前线部署工程/交付型解决方案）和 AI 解决方案岗位提供可核查的项目证据。
2. 为后续承接 FDE 式项目积累场景诊断、知识库建设、Agent 实现、人工兜底和运行复盘能力。

所有场景必须由本人正在运营的账号、服务或课程承担。项目不得伪造企业客户、生产数据、营收、交付效果或资质。

## 2. 问题定义

### 2.1 需要证明的能力

简历和面试需要能展示以下完整链路，而不是只展示模型调用：

```text
业务场景诊断
-> 资料治理与知识库准入
-> RAG 问答/工作流 Agent
-> 权限与数据边界
-> 人工审核或接管
-> 日志、评测、失败回流
-> 版本迭代与运行复盘
```

其中企业级不等同于大规模并发或复杂基础设施。当前阶段的企业级证据是：边界明确、数据可追溯、失败有去向、角色责任可说明、同一测试集可以重复运行。

### 2.2 真实自用需求

| 场景 | 真实使用者 | 当前卡点 | 需要的 Agent 能力 | 约束 |
| --- | --- | --- | --- | --- |
| 墨予镜企业 AI 服务 | 本人及潜在线索 | 公众号咨询需要分流，企微需要人工接住，服务资料和常见问题会重复解释 | 意图识别、受控 RAG、资料包发送、交接卡、人工接管 | 公众号不收企业敏感资料；完整聊天不跨渠道迁移 |
| 一镜一梳初访 | 本人及疗愈/课程用户 | 课程、合作、预约问题需要说明与导流，敏感情形必须停止普通对话 | 边界告知、最小信息收集、固定安全出口、人工接管 | 不做诊断、治疗建议、风险分级或危机结论；严格数据隔离 |
| 多账号内容运营 | 本人 | 多账号定位和工作流不同，素材、选题、草稿、反馈难以复用又不能混用 | 账号隔离的素材检索、工作流编排、人工发布确认、反馈回流 | 不自动发布；原始私信和可识别信息不进入通用内容库 |
| AI 互动图文课程 | 本人及付费学员 | 课程内容、练习和答疑需要形成可重复交付的交互流程 | 课程状态机、课程知识检索、练习反馈草稿、人工升级入口 | 不承诺疗效；不把心理高风险或个案问题交给自动生成 |

## 3. 项目组合与取舍

本轮采用“一套共享底座，三个业务项目”的组合，而不是同时建设四个完整应用。

| 编号 | 项目 | 归属 | 首要价值 | 首轮范围 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| P1 | Agent 与知识库运行底座 | `ai-service-studio` | 建立可复用的资料治理、向量检索、评测、日志和版本能力 | 单租户开发环境，两个隔离知识空间 | 最高 |
| P2 | 墨予镜企业 AI 服务初访与交接 Agent | `ai-service-studio` + `content-matrix` | 真实承接 AI 服务/合作线索；第一份 FDE 作品集主案例 | 公众号意图分流、企业微信交接、受控 RAG、人工接管 | 最高，首个实现 |
| P3 | 一镜一梳初访与课程导流 Agent | `aimandala` + `healing-courses` | 验证高约束行业的安全边界与课程转化流程 | 固定服务说明、课程/合作导流、人工优先接管 | 次高，复用 P1 后实施 |
| P4 | 多账号内容工作流 Agent | `content-matrix` | 用本人日常运营证明多角色、多知识空间和人工审核工作流 | 账号级素材检索、选题/草稿辅助、发布前人工确认 | 第三 |
| P5 | AI 互动图文课程交付 Agent | `healing-courses` 或后续 AI 课程项目 | 将验证过的内容转成可销售、可复用的交互课程 | 一门课程、一个学习路径、一个练习/答疑边界 | 最后 |

`P1` 是技术能力包，不单独包装成产品案例；`P2` 是首个可运行的案例；`P3-P5` 是同一能力包的不同业务验证。这样能避免重复搭建三套知识库和三套 Agent，同时保留账号与用户数据隔离。

## 4. 本轮目标

### 4.1 90 天目标

1. 跑通一个可部署、可观测、可评测的 RAG Agent 样板。
2. 让墨予镜的初访与交接链路在本人和模拟用户测试中完整运行，并为真实线索保留人工接管。
3. 使用同一底座为一镜一梳或内容工作流完成一个第二场景验证。
4. 形成一份面向求职的项目案例：问题、架构、数据边界、评测结果、失败样例和下一轮迭代。

### 4.2 不做范围

- 不先建设通用 SaaS、多租户收费、复杂运营后台或 Agent 市场。
- 不先接入真实企业内部系统、企业数据、SSO（单点登录）或复杂 ACL（访问控制列表）。
- 不做无来源引用的泛聊天机器人。
- 不把敏感疗愈信息、个案记录、完整私信或联系人资料放入向量知识库。
- 不在未完成评测、人工接管和隐私检查前对外宣传“生产可用”或“企业客户案例”。

## 5. 方案比较

| 方案 | 收益 | 代价/问题 | 结论 |
| --- | --- | --- | --- |
| 分别用低代码平台制作多个机器人 | 上线快 | 难以展示检索质量、版本、日志与隔离；能力难迁移 | 可做渠道壳，不作为能力主线 |
| 先建设统一大型知识库平台 | 架构看上去完整 | 没有真实问题会导致资料收集和系统治理拖延 | 不采用 |
| 共享受控运行底座 + 单场景先行 | 每一层都有真实用途，能逐步积累项目证据 | 需要先明确数据合同和评测方法 | 当前采用 |

## 6. 首个项目定义

首个实施项目为：`墨予镜企业 AI 服务初访与交接 Agent`。

它的单一主路径为：

```text
公众号关键词或菜单进入
-> 识别“找服务 / 谈合作 / 了解范围”
-> 仅用已审定知识回答范围性问题
-> 用户自主添加企业微信
-> 企业微信发送资料包并收集最少准备信息
-> 人工审核、约诊断或说明暂不匹配
-> 记录检索、转人工原因和最终状态
```

首批知识库只包含服务说明、FAQ、资料包、表单说明、人工转接规则和经过审核的公开内容。它不包含客户资料，也不承担自动报价、自动方案或自动预约确认。

## 7. 验收标准

### 7.1 P1 运行底座

- 可以导入 Markdown、PDF 或网页转存文本，并保存来源、版本、可见范围和发布日期。
- 可以完成向量检索，并让每个生成回答给出来源条目和版本。
- 没有足够依据时，系统明确拒答或转人工，不编造答案。
- 有至少 30 条可重复运行的评测问题，覆盖正常问答、资料不足、版本冲突、越界输入和敏感信息。
- 能记录一次会话的意图、检索结果、回答版本、转人工原因和人工最终处理状态。

### 7.2 P2 初访与交接

- 两类模拟用户能在不提交敏感企业资料的前提下完成“找服务”或“谈合作”的导流。
- 所有需要具体判断、报价、项目方案或客户资料的对话均转人工。
- 人工仅依靠企微交接卡和用户主动提交的材料，可以判断下一步。
- 演示、日志和复盘均标注为“自用生产试点/模拟测试”，不包含虚构的外部成果。
