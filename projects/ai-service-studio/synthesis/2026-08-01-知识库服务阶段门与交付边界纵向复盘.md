## 1. 本次复盘问题

当前“AI 文档 / 知识库前置整理”已经有资料盘点与三阶段治理边界，但客户口中的“做知识库”可能指协作文档、人用检索、AI 问答、内部 Agent 或生产级企业搜索。本次复盘要回答：

- 如何把这类模糊需求拆成可报价、可验收的服务阶段？
- 哪些条件是进入 AI 问答 PoC（概念验证）的必要条件？
- 哪些能力仍应由合作方承接？
- 当前 system 哪些规则可合并为一条清晰的知识库交付门槛？

## 3. 反复出现的模式

### 3.1 先定义场景与责任，再讨论工具

五份材料都指向同一顺序：先明确谁在什么时刻需要何种答案或动作、资料由谁确认、错误由谁发现和修正，再判断是否需要 RAG（检索增强生成）、工作流或 Agent。技术选型不能替代场景诊断。

### 3.2 资料治理是问答效果的前置条件

资料是否电子化、是否有当前有效版本、是否有正式依据、是否允许入库、是否有人维护，反复被视为交付成败条件。资料盘点不是低价值准备工作，而是独立可售的前置交付。

### 3.3 样板验证必须小而完整

有效的首个知识库样板都应限制为一个场景、一批代表资料、一组测试问题、一个使用入口和一位反馈责任人。样板不是“半套生产系统”，而是验证资料、检索、人工审核和客户投入是否能形成闭环。

### 3.4 生产级边界由治理与运行责任决定

生产级的标志不是接入了向量数据库或 Agent，而是权限、版本、数据来源、日志、评测、错误回流、维护和责任机制已明确。资料量越大、使用者越多、错误影响越大，越不能靠人工临场修补。

### 3.5 交付价值是可用与可维护，不是模型“聪明”

客户能否减少反复询问、在限定任务中找到依据、理解答案来源、提交错误反馈并完成一次更新，比模型演示效果更适合作为验收。后续服务应围绕知识运营，而非无限期调模型。

## 4. 只有单篇支持的信号

- GraphRAG（图检索增强生成）、Agentic RAG（智能体式检索）和 Agent 记忆的具体适用条件：有技术启发，但尚无当前客户样本或工程验证。
- Dify、RAGFlow、向量数据库、嵌入模型等具体产品选型：只能作为调研起点，需按客户数据驻留、已有系统、协议、预算和团队能力复核。
- 权限感知检索的具体实现方式，如 ACL（访问控制列表）同步与检索前过滤：方向明确，但目前缺少自有实现与验证证据。
- 以业务结果为核心的知识库报价上限：仍缺真实付费与交付复盘，不能从参考材料推导价格或 ROI 承诺。

## 5. 互相冲突的判断

### 5.1 “快速上线”与“生产可用”

一线定制材料强调小 demo 尽快让客户看见结果；技术研究强调权限、评测和运维。两者不冲突，但适用层级不同：前者适合脱敏、限定范围的 demo / PoC，后者适合真实用户、真实数据和跨部门使用的试点以上交付。问题在于把前者包装成后者。

### 5.2 “让 AI 自动维护知识”与“资料责任人维护”

自动抽取、归类和建议更新可以降低整理成本，但不能替代资料的业务确认。AI 可做候选加工，资料责任人必须确认准入、版本、适用范围和下架。否则会把未经确认的历史材料放大为正式回答。

### 5.3 “知识库”与“Agent 记忆”

二者都会储存信息，但前者以可追溯的业务资料为主，后者以动态用户状态、偏好或任务事件为主。两者的写入规则、保留期限、删除机制、权限和风险不同；不能用导入文档替代记忆设计，也不应把记忆功能作为普通知识库的默认范围。

## 6. 可以升级为 system 的规则

以下规则已有多篇材料支持，也与现有 system 一致；建议在后续 `system-refactor-from-synthesis` 中收束为明确阶段门：

1. 知识库类需求先分为“人用知识系统”“AI 问答 / RAG 样板”“Agent 记忆 / 上下文”三类对象，不能共用一个笼统报价包。
2. 进入 AI 问答 PoC 前，必须明确一个业务场景、使用人、验收人、代表资料范围、资料责任人、人工兜底方式和测试问题；缺一项时只做诊断或资料治理。
3. 样板验收必须包含来源引用或可追溯资料入口、明确拒答 / 转人工规则，以及至少一轮 badcase 分类与修正。
4. 涉及真实多人使用、跨部门资料、敏感数据、源系统同步或自动写入时，必须重新评估权限继承、数据边界、日志、维护、异常处理和合作方，不得沿用小单或 demo 报价。
5. 知识库维护采用“资料责任人确认 + AI 辅助加工 + 定期评测和错误回流”的机制；不承诺 AI 自动维护后天然正确。

## 7. 暂不升级的候选规则

- 用文档数量直接决定技术架构或报价：资料复杂度、权限和业务风险同样决定工作量。
- 固定平台决策口诀或指定技术栈：必须保留客户环境与实测优先。
- 具体召回率、重排收益、解析效果或上线周期：需用客户样本建立评测基线后再讨论。
- GraphRAG、Agentic RAG、长期记忆产品化：作为研究与 PoC 候选，不进入当前主服务承诺。
- “一周上线”“无需技术团队”等市场表述：未核验且容易掩盖数据治理与运维成本。

## 8. 应删除 / 合并 / 降级的旧 system 内容

当前 system 的方向无明显错误，不建议删除规则；建议在重构时合并分散表达：

- 将 `AI服务产品体系` 的知识库三阶段、demo / POC / 试点 / 生产级分层，以及交付对象地图合并成一张“知识库服务阶段门”表，减少资料阶段与系统阶段分开阅读的成本。
- 将 `获客与售前SOP` 的资料检查表补成可复用的“知识库 PoC 准入卡”，把场景、资料状态、责任人、权限、测试和人工兜底集中在同一处。
- 将 `报价与服务边界` 与 `合同条款清单` 中分散的资料范围、版本、权限、评测、维护内容对齐为同一份范围字段，避免报价承诺和合同责任不一致。
- 将“技术选型”降级为诊断后的方案附录，不作为入口服务或对外卖点。

## 9. 建议进入 kb 的 atoms / wiki

暂不直接写入 KB（知识库）。以下内容已具备跨项目复用价值，可作为候选：

- 企业知识库的交付单元是“场景 + 已确认资料 + 使用与维护责任”，不是文档数量或单个工具。
- 知识库生产化的阶段门是治理、权限、评测、错误回流和运行责任，而不是是否使用 RAG 或 Agent。
- RAG 问答与 Agent 记忆应独立设计资料对象、写入规则、保留期限、删除机制和权限。

进入 KB 前需补充至少一个真实客户 PoC 或内部技术验证，并剥离特定项目的服务阶段和未核验工具事实。

## 10. 下一步 system refactor 建议

建议 handoff 给 `system-refactor-from-synthesis`，范围限定为知识库相关的四个既有 system 文件，不新增大而全的技术栈文档：

1. 在 `AI服务产品体系` 建立“资料治理 -> 知识库 PoC -> 扩展 / 生产设计”的阶段门，并标注三类服务对象。
2. 在 `获客与售前SOP` 增加一页知识库 PoC 准入卡，作为报价前的最小输入。
3. 在 `报价与服务边界` 统一样板 PoC 的范围字段：场景、资料量、测试题、使用人、维护期、平台费用、排除项。
4. 在 `合同条款清单` 对齐资料准入、来源引用、权限确认、错误回流和维护责任。

重构验收标准：客户需求能在 30 分钟售前后被判断为“仅做资料治理 / 可做样板 PoC / 需合作方生产设计 / 暂不承接”四种结果之一；报价、交付物和合同使用相同的范围字段。
