## 1. 本次复盘问题

当前项目已经有产品阶段、售前检查、报价边界和合同条款。此次要判断的不是“是否继续使用 FDE（Forward Deployed Engineer，前线部署工程 / 交付型解决方案）”这个说法，而是把它落到一次可验证交付时，哪些条件必须同时成立：

## 3. 反复出现的模式

### 3.1 售前对象是一条真实工作链，不是一个工具名称

六篇材料都指向同一个起点：客户说“想做 Agent”“想上知识库”“想自动化”时，不能直接把这个词当作需求。先要拿到最近一次真实事件，继而看清流程起止、实际使用人、输入材料、业务规则、当前补救方式和结果接收者。

可复用的诊断链为：

```text
客户原话
  -> 要改善的业务动作
  -> 当前人工流程
  -> 候选 AI 节点
  -> 输入、规则、输出与交付对象
  -> 人工审核、失败发现与下一步动作
```

这意味着“是否懂业务”不是服务方单向证明。业务负责人、实际使用人、资料方和验收人都必须参与，才有可定义的试点。

### 3.2 第一版只验证一个紧邻行动的闭环

材料反复反对一开始就承诺完整 ERP、CRM、企业 Agent 平台或全链路自动化。更可验证的第一版通常只有：一个使用人、一个核心输入、一个有业务标准的处理节点、一个可核对结果，以及结果出现后紧接着的一个动作。

“生成了一份内容”“页面可以打开”都不等于闭环。结果必须在约定时点交给约定角色，并能观察到对方采用、修改、拒绝、转人工、停止或申请扩展中的至少一种行为。

### 3.3 跳级是主要报价和交付风险

六篇材料分别从场景筛选、原型、Agent、现场产品化和业务方自研说明同一风险：demo、PoC、试点、生产级的技术和责任条件不同，不能用低层级成果替代高层级承诺。

| 层级 | 本轮能证明什么 | 不能证明什么 |
| --- | --- | --- |
| demo | 某个流程可能被 AI 辅助，客户可据此讨论需求 | 稳定性、真实使用、效果或生产可用性 |
| PoC | 在约定样本、测试环境和人工审核下可跑通一个假设 | 全量数据、全部异常、组织采用或正式上线 |
| 试点 | 小范围真实使用，有反馈和异常记录 | 全员铺开、长期维护或持续经营结果 |
| 生产级 | 在另行确认的权限、数据、日志、监控、回滚、维护和责任机制下运行 | 不应由普通诊断、工作坊或 demo 自动包含 |

### 3.4 采用证据与工程结果同样需要被设计

FDE 现场闭环、反向 FDE 与 Agent/FDE 三篇材料共同补强了现有边界：验收不应只检查功能和交付物，也要提前约定采用证据。

最小采用证据包括：

- 实际使用人是否在约定场景中使用；
- 结果是否能回溯到输入材料和判断依据；
- 错误、拒绝或异常是否被记录并能转人工；
- 使用人或资料责任人是否能完成一次反馈、修正或更新；
- 客户能否基于该结果决定继续、修改、停止或扩展。

这组证据不等同于“保证提效、成交或 ROI（投资回报）”，而是帮助双方判断下一阶段是否值得发生。

### 3.5 现场定制的价值要回流为复用资产，但不能过早平台化

“业务到 AI 的翻译”、九要素卡、流程图、样板、失败样例、验收口径、资料准入和人工兜底点，在多篇材料中都被视作高价值交付。它们也是下一次服务可复用的资产。

不过，单一客户的特殊字段、流程和系统接入不应马上变成通用产品。先作为内部组件、模板或案例记录，待多个客户独立出现相同问题，再判断是否形成行业包、能力包或产品化功能。

## 5. 互相冲突的判断

### 5.1 快速原型与完整工程治理并不矛盾，但适用层级不同

部分材料强调用低保真原型或小功能快速对齐，另一些材料强调权限、日志、监控、回滚和 SLA（服务级别协议）。它们的冲突来自把不同层级混为一谈。

当前处理：在 demo、PoC 和试点中采用原型先行与小步测试；一旦涉及真实敏感数据、自动写回、自动发送、跨系统操作、长期无人值守或多部门使用，必须切换到生产设计或合作交付，不再沿用“先做出来再说”的节奏。

### 5.2 业务负责人深度参与与服务方交付责任必须同时成立

反向 FDE 材料强调业务方是流程知识的拥有者；FDE 材料强调服务方对落地和采用负责。两者并不表示服务方可把需求、验收或失败责任交回客户。

当前处理：客户负责提供经授权的资料、业务规则、验收判断与反馈；服务方负责将这些条件变为明确的试点范围、样板、验证记录、已知限制和下一步建议。缺少其中任一方，不进入完整试点报价。

### 5.3 现场定制与规模化复用之间要有证据门

材料均支持从真实现场学习，但“每个客户都做新东西”会退化为不可控的人力项目；太早抽象又会让产品脱离真实问题。

当前处理：每次交付后先记录“本客户特有 / 可作为候选模板 / 已有多例支持”三类资产。只有多名客户或多篇独立材料反复支持、且不包含客户私有数据时，才进入能力包或 system 规则。

## 6. 可以升级为 system 的规则

以下规则获得多篇材料支持，并且与当前业务阶段相符。建议在用户确认后交给 `system-refactor-from-synthesis` 实施；本次不直接修改 system。

### 6.1 为试点新增“闭环准入卡”

建议写入 `获客与售前SOP`，并同步到 FDE 售前诊断模板。除既有流程、资料与风险检查外，进入 PoC 或试点报价前还需确认：

| 准入项 | 最低问题 | 缺失时的动作 |
| --- | --- | --- |
| 最近事件 | 最近一次卡住、返工或出错是什么？ | 只做访谈 / 诊断，不定义功能。 |
| 真实材料 | 是否有可授权、可脱敏的代表样本？ | 先做资料盘点或脱敏样本验证。 |
| 业务标准 | 谁判断结果好坏、异常和例外？ | 不进入自动化或试点承诺。 |
| 结果接收者 | 结果在何时给谁，接收者下一步做什么？ | 不把页面或报告当作交付终点。 |
| 采用与反馈 | 谁实际使用，谁记录采用、拒绝、错误和反馈？ | 不进入真实试点。 |

### 6.2 将“采用证据”加入 PoC 与试点验收

建议写入 `报价与服务边界` 与 `合同条款清单`。对于 demo，验收仍是演示完成；对于 PoC 和试点，除交付物外应约定：测试样本、使用人、验收人、反馈期限、异常记录方式和至少一次人工修正或转人工验证。

这不是结果保证，也不把业务经营结果转嫁为服务方承诺。它只防止“完成开发”被误写为“完成采用”。

### 6.3 交付复盘分离四种事实

建议写入 `获客与售前SOP` 的项目复盘要求：

- 工程事实：功能 / 流程是否按约定样本跑通；
- 使用事实：谁实际使用了几次，在什么情境下使用；
- 风险事实：发生了哪些错误、拒绝、绕过、权限或资料问题；
- 商业事实：客户决定继续、修改、停止、扩展还是仅保留观察。

这样可以避免用点赞、演示顺利、预约或一次付费代替采用和复购证据。

### 6.4 建立“现场到资产”的分级回流

建议写入 `AI服务产品体系` 或新增到现有复盘模板：

| 回流级别 | 去向 | 条件 |
| --- | --- | --- |
| 客户私有记录 | 项目记录 | 含客户私有资料、流程或错误细节。 |
| 候选模板 | 内部模板 / references | 已脱敏，能服务下一次相似访谈，但仍只有单例支持。 |
| 当前规则 | system | 多篇材料或多个真实项目反复支持，边界和例外已写清。 |
| 跨项目知识 | research-center KB | 具有跨项目复用价值，且不依赖单一行业、客户或未核验结果。 |

## 7. 暂不升级的候选规则

- 把 FDE 作为对外主身份标签：当前仍更适合描述为“拿一条真实流程做诊断、小样板和试点定义”；FDE 作为内部能力模型即可。
- 用“7 天”作为全部客户的统一实验周期：可作内部节奏提示，但不同流程、资料和使用频率差异很大，不能写成固定交付承诺。
- 用通用场景评分直接决定成交：高频、结构化、可评判、有人工兜底是必要筛选，不足以替代资料、决策链、预算和验收条件。
- 以“反向 FDE”命名服务包：先在真实访谈中验证客户是否理解并愿意为这种参与方式付费。
- 将业务诊断自动生成报告作为标准交付：报告可以辅助整理，但必须由人核对流程、边界、例外和责任人。

## 8. 应删除 / 合并 / 降级的旧 system 内容

本次检查没有发现必须删除的稳定规则。现有 system 已覆盖“从真实流程进入”“demo/PoC/试点/生产级分层”“人工兜底”和“生产级条件”四个主方向。

下一轮重构建议避免继续添加并列的产品名、工具名或行业案例，改为：

1. 将分散在 `AI服务产品体系`、`获客与售前SOP`、`报价与服务边界` 中的试点前置条件对齐为同一张“闭环准入卡”。
2. 将“功能完成”“交付物完成”“真实使用”“经营结果”明确分开，避免同一词“验收”承担四种含义。
3. 将反复出现的行业 Agent、ERP、工作台、自动化示例降为长期方向或合作交付示例，不继续扩大为当前主服务范围。
4. 保留现有 demo / PoC / 试点 / 生产级表，但在 PoC 与试点栏补上“结果接收者、采用证据、反馈责任人”。
