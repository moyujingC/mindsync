# 从办一场聚餐，看懂 Agent、Workflow、Skill、Plugin、MCP

最近聊 AI 的时候，越来越容易遇到一堆英文词：

Agent、Workflow、Skill、Plugin、MCP。

很多人第一次看到，会觉得它们都差不多。

反正最后都是“让 AI 调用一些东西，把事情做完”。

但如果只这样理解，很快就会乱。

因为这几个概念真正的区别，不在于它们最后是不是代码，也不在于它们是不是都能被 AI 调用。

更重要的区别是：

**它们各自封装了什么复杂度，以及决策权放在哪里。**

可以先记一个最短版本：

- Agent（智能体）是主体
- Workflow（工作流）是流程
- Skill（技能）是能力包
- Plugin（插件）是扩展包
- MCP（模型上下文协议）是连接标准

这句话可能还是有点抽象。

我们换一个生活里的例子来讲：办一场朋友聚餐。

## 01

假设你对 AI 说：

“这个周六晚上，帮我组织一场 8 人朋友聚餐，预算人均 150 元，地点尽量靠近静安寺。”

这件事看起来很简单。

但真要办起来，其实包含一堆动作：

- 确认人数
- 了解忌口
- 查餐厅
- 看评分
- 对比距离
- 估算预算
- 订位
- 发通知
- 聚餐前提醒
- 餐厅没位置时换备选方案

这时候，Agent、Workflow、Skill、Plugin、MCP 就会分别扮演不同角色。

## 02

先说 Agent。

Agent 像一个会自己张罗事情的助理。

你只告诉它目标：

“帮我组织一场 8 人聚餐。”

它不会等你一步步命令：

先查餐厅，再问时间，再做预算，再发通知。

它会自己判断：

- 这件事需要哪些步骤？
- 哪些信息还缺？
- 应该先查餐厅，还是先确认时间？
- 如果餐厅满了，要不要换备选？
- 通知应该发给谁？
- 是否需要聚餐前提醒？

所以 Agent 的本质是：目标执行主体。

它封装的是“从目标到结果”的决策复杂度。

你给它目标，它负责理解目标、拆解任务、选择工具、调整策略、处理异常。

这里的决策权主要放在 Agent 运行时。

人不需要提前写死每一步，而是把目标交给 Agent，让它在执行过程中持续判断下一步怎么走。

简单说：

**Agent 回答的问题是：谁来判断并推进这件事？**

## 03

再说 Workflow。

办聚餐其实也可以整理成一套固定流程：

1. 收集人数
2. 确认时间
3. 确认预算
4. 搜索餐厅
5. 筛选候选
6. 发起投票
7. 订位
8. 发通知
9. 聚餐前提醒

这就是 Workflow。

它的重点不是“聪明”，而是稳定、可复用、可追踪。

下次再办聚餐，还可以继续套这套流程。

如果投票没有结果，就进入提醒分支。

如果订位失败，就回到候选餐厅列表重新选择。

所以 Workflow 的本质是：控制流封装。

它封装的是过程复杂度，包括步骤顺序、条件分支、状态流转、重试机制、异常处理和完成标准。

这里的决策权主要放在流程设计阶段。

流程设计者提前规定好步骤和分支，运行时的 Workflow 按规则执行，不会自己发明新目标。

简单说：

**Workflow 回答的问题是：这件事应该按什么步骤走？**

## 04

再说 Skill。

在办聚餐这件事里，有些动作可以沉淀成独立能力。

比如：

- 餐厅筛选 Skill：根据地点、预算、口味、评分筛出候选餐厅
- 预算估算 Skill：根据人数、人均、酒水和服务费估算总价
- 群消息撰写 Skill：把时间、地点、路线、注意事项写成一条清楚通知
- 备选方案 Skill：如果首选餐厅没位置，快速找 3 个替代方案

Skill 和 Workflow 很容易混。

因为一个 Skill 内部也可能有步骤。

比如“餐厅筛选 Skill”内部可能会做：

1. 查静安寺附近餐厅
2. 排除评分过低的
3. 排除人均超预算的
4. 排除距离太远的
5. 按适合聚餐程度排序

但它对外表现为一个能力：

“帮我筛出合适餐厅。”

所以 Skill 的重点不是流程本身，而是把某类任务打包成可复用能力。

它封装的通常包括方法、规则、模板、脚本、检查清单，必要时也会调用工具。

这里的决策权主要沉淀在技能作者的经验里。

Skill 不需要每次重新发明方法，而是把“这类事通常怎么做好”提前封装起来。

简单说：

**Skill 回答的问题是：这类事怎么稳定、重复地做好？**

## 05

再说 Plugin。

如果这个 AI 助理只能聊天，它其实没法真正查餐厅、看地图、发通知。

这时就需要 Plugin。

比如你给系统装了：

- 大众点评插件：查餐厅、评分、人均、营业时间
- 地图插件：查距离、路线、通勤时间
- 日历插件：看大家有没有空
- 微信或邮件插件：发送聚餐通知

插件的重点是把某种外部能力装进系统。

但要注意，Plugin 不一定是最小能力单位。

一个“大众点评插件”里面可能包含多个具体工具：

- 搜索餐厅
- 查看餐厅详情
- 查询空位
- 获取评价
- 获取地址

所以更准确地说：

Plugin 更像扩展包，Tool（工具）才更像具体工具。

很多人会把 Plugin 和 Tool 混用，所以容易误解。

从系统设计角度看，Plugin 解决的是能力如何安装、挂载、分发的问题。

简单说：

**Plugin 回答的问题是：新能力怎么装进来？**

## 06

最后说 MCP。

如果每个插件都有自己的调用方式，系统会变得很乱。

大众点评一套格式，地图一套格式，日历又一套格式。

每接一个新能力，都要单独适配一次。

MCP，全称是 Model Context Protocol，可以简单理解为“模型上下文协议”。

它解决的就是统一接入问题。

你可以把它理解成一种统一插口标准。

不管是地图能力、餐厅能力、日历能力，还是文件系统、数据库、浏览器，只要按同一种协议暴露出来，Agent 就能用相对统一的方式发现和调用。

所以 MCP 本身不是“办聚餐”的能力。

它不负责查餐厅，也不负责订位。

它负责的是：

- 能力如何被发现
- 参数如何描述
- 调用如何发起
- 结果如何返回
- 外部资源如何暴露给模型

这里的决策权不在 MCP 本身。

MCP 只规定连接方式，真正的业务判断仍然发生在 Agent、Workflow、Skill 或具体工具里。

简单说：

**MCP 回答的问题是：外部能力怎么标准化接进来？**

## 07

现在把整个过程串起来。

你说：

“帮我组织一场 8 人朋友聚餐。”

Agent 接到目标后，判断这件事可以分成几块：

- 确认信息
- 搜索餐厅
- 筛选候选
- 订位
- 发通知

于是它决定启动一个“办聚餐 Workflow”。

这个 Workflow 里有几个节点：

1. 调用餐厅筛选 Skill
2. 调用预算估算 Skill
3. 调用订位 Tool
4. 调用群消息撰写 Skill
5. 调用通知发送 Tool

这些 Skill 内部可能会调用多个工具。

比如餐厅筛选 Skill 会调用地图工具、点评工具、搜索工具。

这些工具可能来自不同 Plugin。

而这些工具之所以能被 Agent 统一调用，可能是因为它们通过 MCP 这样的协议接入。

一句话串起来：

**Agent 接目标，Workflow 排步骤，Skill 做专项任务，Plugin 提供外部能力，MCP 负责统一连接。**

## 08

所以，它们不是一条简单的金字塔。

很多文章会把它们画成：

MCP -> Plugin -> Skill -> Workflow -> Agent

这个图有一定帮助，但也容易误导。

因为它们并不完全在同一个维度上。

Agent 是执行主体。

Workflow 是控制结构。

Skill 是能力封装。

Plugin 是扩展分发。

MCP 是连接协议。

真实系统里，它们经常互相嵌套：

- 一个 Agent 可以调用一个 Workflow
- 一个 Workflow 可以调用多个 Skill
- 一个 Skill 内部也可以包含小 Workflow
- 一个 Skill 可以调用多个 Tool
- Tool 可以由 Plugin 提供
- Tool 也可以通过 MCP 暴露
- Plugin 里也可能打包 Skill、Tool、MCP Server

这就是为什么看起来会乱。

它们不是严格上下级，而是不同维度的封装方式。

## 09

如果从软件工程视角看，这些东西也不是几种神秘的新概念。

它们更像 AI 应用开发里的不同组织方式。

传统软件里，我们早就有函数、模块、接口、管道、协议。

这些东西的作用，都是为了把复杂度拆开、封装起来，并让不同部分能稳定协作。

Agent、Workflow、Skill、Plugin、MCP 也是类似逻辑。

只是它们处理的不再只是确定性的代码逻辑。

它们要组织的是一种混合系统：

**确定性程序 + 不确定性模型能力 + 外部工具调用。**

这也是为什么它们容易混淆。

在传统程序里，一个函数的输入输出通常更稳定。

但在 AI 系统里，模型的判断、工具的返回、外部环境的变化，都会影响结果。

所以这些概念不只是为了“复用代码”，还要处理：

- 模型输出的不确定性
- 工具调用的失败和重试
- 多步骤任务的状态追踪
- 人类目标到机器执行之间的语义落差
- 外部系统接入的权限、安全和格式差异

它们不是为了制造新名词，而是因为 AI 应用本身变成了一种更复杂的系统工程。

## 10

最后，再压缩一下。

如果只想记一个最短版本：

- Agent 是会自己想办法的执行者
- Workflow 是预先设计好的流程
- Skill 是打包好的专项能力
- Plugin 是装进系统的扩展包
- MCP 是连接外部能力的统一协议

换成聚餐例子：

- Agent 是帮你张罗聚餐的人
- Workflow 是办聚餐的固定流程
- Skill 是筛餐厅、做预算、写通知这些专项手艺
- Plugin 是大众点评、地图、日历这些外部能力包
- MCP 是让这些外部能力能被统一调用的插口标准

回到最开始的问题：

它们当然都可以由程序实现。

但真正重要的是，它们分别封装了不同类型的复杂度，也把决策权放在了不同位置。

Agent 封装决策复杂度。

Workflow 封装流程复杂度。

Skill 封装复用复杂度。

Plugin 封装扩展复杂度。

MCP 封装接入复杂度。

所以它们不是五个互相替代的概念，而是 AI 应用系统里五种不同的设计角色。

当你不再只看实现形式，而是去问：

它们各自封装了什么？

谁拥有决策权？

谁负责连接和复用？

这些概念之间的边界，就会清楚很多。
