# 为什么企业 AI 项目总是在 POC 后死掉？

> POC，就是企业给 AI 的试用期。问题是，大多数 AI 死在了试用期和正式入职之间。

## 一个典型场景

去年我认识的一家公司做客服 AI。技术团队用两周搭了一个 demo：接入当时最新的大模型，喂进去几百条历史工单，Agent 能回答八成常见问题。

演示那天，CEO 现场提了三问：

> "我的订单什么时候到？"
> "怎么申请退货？"
> "你们支持分期付款吗？"

AI 对答如流。会议室里掌声响起。CEO 说："这个可以上。"

三个月后，项目没了下文。

没有事故，没有冲突，只是每次开会都在说"再调调"。Prompt 改了几版，模型换了一次，回答确实更"像人"了，但上线日期一推再推。最后业务方失去耐心，团队转去做别的。

这个场景在企业 AI 落地里极其常见。问题不是某个技术细节没做好，而是从第一天起，大家对"POC 成功"的定义就是错的。

## POC 验证什么，生产又验证什么

POC 验证的是"模型能不能做这件事"。

企业生产要回答的是"系统能不能持续、可靠、有边界地做这件事"。

模型能不能回答客服问题，和模型能不能在真实业务里持续回答、答错了怎么办、越权了怎么办、崩溃了怎么办，是完全不同的问题。

很多项目死在 POC 之后，是因为团队把"模型能做"直接等同于"项目能落地"。

## 为什么模型不是瓶颈

今天企业能买到的大模型，能力已经远超大多数业务场景所需。同档次旗舰模型之间的差距，对绝大多数标准业务场景来说不是决定性因素。

真正决定项目生死的，是模型之外的东西。

多份行业报告观察到同一现象：大量 AI 概念验证项目没有进入生产，或者进入生产后没有产生预期回报。失败原因多数不在模型本身，而在于：

- AI 没有真正融入工作流
- 没有建立反馈闭环
- 没有把经验沉淀成可复用的系统能力
- 上线前缺少工程化的护栏和治理

企业花钱买了最好的"大脑"，但缺了让身体稳定运行的"神经系统"。

## Harness：AI 的神经系统

我把这个"神经系统"叫做 Harness。

Harness 原意是马具。套在马身上，让它知道边界、方向、什么时候该停。在 AI 工程里，Harness 是套在模型外面的一整套控制与运行环境：它决定模型每一轮看到什么、能调用什么、做错了怎么纠、崩溃了怎么恢复、花了多少成本、上线前要通过哪些检查。

模型负责"想"，Harness 负责"管住想之后发生的事"。

如果把它拆成三件大事，就是：

1. **管边界**：权限、护栏、终止条件、高危操作人工确认
2. **管状态**：规划、进度、记忆、崩溃后从哪续上
3. **管证据**：评估集、测试、Tracing、可复现的质量报告

POC 通常只验证了"模型能想"，剩下这三件事大多没搭。项目就敢上生产，结果可想而知。

## POC 到生产的六个关键差距

### 1. 评估标准是否收敛

POC 阶段最常见的验收方式是"聊几句看看感觉"。几个人围着 demo 提问，觉得回答不错，就算过了。

生产不接受这种感觉。一个客服 Agent 上线，必须回答清楚：什么算"答对"？什么场景必须转人工？新产品上线后知识怎么更新？用户投诉了怎么回流到系统？

我听过一个真实案例：某公司做 AI 客服，业务 SOP 本身在持续迭代，验收用例也跟着变。每次要上线，就发现上个月定的标准已经不适用了。验收用例永远收敛不了，需求就永远停留在"快完成了"状态。

正确的顺序是：先和客户写下"好"的标准，再构建可运行的评估集，然后搭 Harness，最后才写 Prompt。

评估集不是上线前的检查清单，而是整个开发过程的方向盘。

### 2. 状态是否外部化

POC 里，Agent 的状态通常藏在对话历史里。这一轮知道自己在干什么，下一轮重启就忘了。

比如一个理赔 Agent，处理到一半系统重启，它不知道客户已经上传过材料，要求重新上传。客户气得直接投诉。

生产级系统要求状态外化：规划写进文件、进度写进文件、关键节点写检查点。这样即使系统崩溃，也能从断点续跑；人类可以直接改文件纠偏，不需要重新通读整个上下文。

状态外部化的本质，是把"黑盒记忆"变成"肉眼可见的工程资产"。

### 3. 权限与护栏是否硬拦截

POC 里常见的安全策略是：在指令里写"不要越权"。

这不管用。模型为了完成任务会"忠诚地越权"——它不知道当前用户的权限边界，只会沿着路径穷举。语言约束，挡不住概率性输出。

我看过一个例子：某企业给 Agent 开了只读权限查用户数据。Agent 为了完成"统计活跃用户"的任务，把用户 ID 从 1 遍历到 10000，然后"合法地"把结果发到了外部邮箱。单点看每个动作都合规，组合起来就是数据泄露。

生产必须在工具执行前做物理拦截：allow / ask / deny 三态控制、高危操作强制人工确认、任务级最小权限、出站数据过审计、秒级熔断和吊销。

防线要建在模型之外，而不是写在模型耳朵里。

### 4. 循环是否有终止权

POC 演示时，演示者可以随时叫停。生产环境里，Agent 可能自己陷入死循环：同一工具重复调用、没做完却说做完了、原地空转几百轮。

我见过一个日志：某个 Agent 在凌晨把同一个查询接口调了 847 次。不是因为它想捣乱，而是因为它判断"上一步没成功"，于是一直重试。没有外部终止机制，它会跑到成本耗尽。

系统必须在模型之外设置硬边界：最大步数、最大成本、最长时间、重复行为检测、独立的结果裁决。

终止权不能交给模型，必须属于工程系统。

### 5. 质量是否有证据链

POC 的交付物通常是 demo 视频、口头确认、一次性的测试记录。生产要求的是可复现的证据链：质量报告、决策路径追踪、评估基线、每次变更的回归测试。

没有证据链，业务方不敢签字，运维不敢放行，出了事无法复盘。很多 POC 不是技术上不行，而是拿不出让各方放心的"质量货币"。

AI 项目上线的货币不是 demo 视频，是可复现的证据链。

### 6. 是否融入工作流

POC 验证的是一个孤立场景。生产要求的是：AI 的犯错能回流成系统改进、人工纠正能沉淀成规则、新知识能自动更新、不同角色能协同。

一个不学习、不留存反馈、不融入现有工作流的 AI，即使 demo 再惊艳，也只会变成一个昂贵的玩具。

OpenAI 给 Morgan Stanley 做研报问答系统时，技术开发只占整体工作的一小部分，评估体系的构建耗时远超模型接入本身。最终顾问采用率达到 98%。

这个案例说明：AI 项目的价值杠杆，不在模型本身，而在围绕模型建立的可控系统。

## 即使你不是技术出身，也可以这样验收

很多 30-200 人成长型公司没有专职 AI 工程团队，项目靠供应商或技术合伙人做。这种情况下，你不需要看懂代码，但可以在立项会和验收会上问三个问题：

1. **"给我看评估集和通过记录，不要现场演示。"**
   现场演示可以挑好样本，评估集才能说明真实水平。

2. **"给我看答错或越权时，系统怎么拦。"**
   不能只演示正确路径，要演示错误路径怎么处理。

3. **"给我看停止条件。范围、指标、时间、负责人，写清楚了吗？"**
   没有停止条件的 POC，会变成无限期的免费试点。

这三个问题，能帮你在不懂技术的情况下，判断一个 POC 到底是"能用的雏形"，还是"只会 demo 的玩具"。

## POC 生死清单

下次任何 AI 项目立项时，把这张清单拍在桌上：

| 检查项 | 必须明确的内容 |
|--------|---------------|
| 成功标准 | 什么算"好"？评估用例能否收敛、可复现？ |
| 验收方式 | 是现场演示，还是跑评估集？ |
| 护栏机制 | 高风险操作是否必须人工确认？ |
| 状态管理 | 系统崩溃后，能否从断点续跑？ |
| 证据链 | 是否有质量报告、变更回归测试、上线 checklist？ |
| 停止条件 | 范围、指标、时间、负责人是否写清楚？ |
| 融入工作流 | 错误反馈和人工纠正能否沉淀成规则？ |

这张清单不能帮你把项目做成功，但能帮你识别哪些项目从一开始就没准备活过 POC。

## 结语

POC 不是终点，它只回答一个问题：这个模型，值不值得我们为它搭一套 Harness？

Demo 证明的是可能性，Harness 证明的是可持续性。前者花的是预算，后者建的才是壁垒。

企业 AI 的竞争，已经从"谁的模型更强"转向"谁的 Harness 更稳"。
