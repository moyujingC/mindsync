# 为什么会出现 Agent、Workflow、Skill、Plugin、MCP？

上一篇，我们用“办一场聚餐”的例子，讲了 Agent、Workflow、Skill、Plugin、MCP 的区别。

这一篇，想继续追问一个问题：

为什么 AI 应用发展到今天，会逐渐长出这些东西？

理解这些概念，不能只看它们是什么。

更要看它们为什么会出现。

很多技术概念不是凭空发明出来的。它们通常是旧方式解决不了新问题之后，自然长出来的新抽象。

Agent、Workflow、Skill、Plugin、MCP 也是这样。

它们不是为了制造复杂度，而是因为 AI 应用从“聊天演示”走向“真实业务”之后，开始遇到不同层次的问题：

- 只靠一次 prompt，复杂任务不稳定
- 模型只会说，不能访问外部世界
- 工具越来越多，接入方式越来越碎
- 通用 Agent 很灵活，但缺少稳定的领域经验
- 真实业务既有固定流程，也有动态判断

这些问题不断出现，才让不同概念逐渐变得重要。

先说明一点：

这里讲的不是这些词在计算机科学史上的首次出现。

Workflow、Agent、Plugin 这些词，在传统软件工程和 AI 历史里早就存在。

我们这里讨论的是：它们为什么会在大模型应用开发里，重新变成一组重要的工程抽象。

## 01

最早大家使用大模型，主要是把它当成 Chatbot，也就是聊天机器人。

你问一句，它答一句。

比如：

- 帮我写一篇小红书文案
- 帮我总结这段材料
- 帮我翻译这篇文章
- 帮我解释一个概念

这个阶段的核心体验是：

> **AI 很会说。**

它能生成文本、总结文本、改写文本、翻译文本，也能给出建议。

但只要任务稍微复杂一点，问题就来了。

比如你让它：

“帮我做一次完整的小红书月度内容复盘。”

它可能会写得很像样，但未必真的按正确步骤做：

- 有没有先拉数据？
- 有没有区分曝光、互动、转化？
- 有没有对比不同选题类型？
- 有没有找出异常笔记？
- 有没有沉淀下月选题建议？
- 有没有把结论放到固定格式里？

单次 prompt 很容易漏步骤，也很难保证每次都稳定。

这就引出了第一个问题：

> **复杂任务不能只靠一次回答，需要拆成多步。**

## 02

于是，Workflow 开始变重要。

为了解决单次 prompt 不稳定的问题，大家开始把复杂任务拆成多个步骤。

早期可能叫 Prompt Chaining（提示词链）、Chain（链）、Pipeline（流水线），后来更常被放进 Workflow（工作流）的语境里理解。

名字不同，背后的需求是一致的：

不要指望模型一次完成复杂任务，而是把任务拆成多个稳定步骤，让前一步输出成为后一步输入。

比如做内容复盘，可以拆成：

1. 读取数据
2. 清洗字段
3. 计算指标
4. 找异常笔记
5. 按选题类型聚合
6. 生成复盘结论
7. 输出下月建议

这时，AI 不再是“一口气回答”，而是进入一个流程。

Workflow 的价值开始出现：

- 步骤更清楚
- 顺序更稳定
- 中间结果可检查
- 失败节点可重试
- 批量任务可复用

所以 Workflow 的出现，是为了解决这个问题：

> **复杂任务需要稳定、可追踪、可复用的执行过程。**

## 03

但 Workflow 也不是万能的。

它很适合稳定流程，但真实任务不总是固定路径。

有些任务不能提前写死每一步。

比如：

“帮我找 5 个适合我们护肤品牌的小红书近期热点，并判断哪些值得跟。”

这个任务就不太适合完全固定流程。

因为 AI 可能需要根据搜索结果不断调整：

- 搜到的热点是否真的相关？
- 这个热点是不是已经过时？
- 有没有品牌安全风险？
- 要不要继续查用户评论？
- 要不要换关键词？
- 要不要把某个热点排除？

这时就需要一种新的能力：

系统不只是按预设流程执行，而是能根据观察结果决定下一步。

这就是 Agent 开始变重要的原因。

Agent 可以简单理解为智能体。

它不是只负责回答，也不是只按流程走，而是围绕一个目标，自己拆任务、调用工具、观察结果、调整下一步。

所以 Agent 的出现，是为了解决这个问题：

> **真实任务有很多不确定性，系统需要围绕目标动态决定下一步。**

它和 Workflow 的差别在这里：

- Workflow 是“流程先定好，再执行”
- Agent 是“目标先给定，再动态规划和调度”

Agent 不是为了替代 Workflow。

它更适合处理 Workflow 预设不到的部分。

## 04

接下来，Tool 和 Plugin 也开始重要。

无论是 Workflow 还是 Agent，如果只能在模型内部生成文本，都还是有限。

真实业务里，AI 不能只会说，还要能干活。

它需要：

- 查数据库
- 读文件
- 调接口
- 搜网页
- 发邮件
- 创建任务
- 查询库存
- 发布内容
- 调用业务系统

这就是 Tool（工具）和 Plugin（插件）出现的背景。

Tool 更像一个具体可调用能力。

比如“查询笔记数据”“发送邮件”“读取文件”。

Plugin 更像一个扩展包。

它可能包含一组工具、配置、权限和说明。

它们解决的是同一个方向的问题：

> **模型不能只停留在生成文本，它需要调用外部能力，才能参与真实业务。**

没有 Tool，Agent 再聪明也只能纸上谈兵。

没有 Plugin，很多外部能力就很难被打包、安装和分发。

所以 Tool / Plugin 的出现，是让 AI 从“会回答”走向“能操作外部系统”。

## 05

但工具一多，新的问题又来了。

当工具少的时候，手写几个接口还可以接受。

但当 AI 应用开始连接越来越多外部系统时，问题会迅速变复杂：

- 每个平台一套工具格式
- 每个数据源一套接入方式
- 每个应用都要重复适配
- 工具能力难以复用
- 权限和上下文管理容易混乱

这时候，需要的不只是更多工具，而是统一的连接标准。

MCP，全称是 Model Context Protocol，可以理解为模型上下文协议。

它试图解决的问题是：

> **AI 应用如何用统一方式连接外部工具、数据源和上下文。**

你可以把 MCP 理解成一种“通用接口语言”。

它不是具体业务能力。

它不负责写文案，不负责查餐厅，也不负责做复盘。

它负责的是：

- 外部能力如何被发现
- 参数如何描述
- 调用如何发起
- 结果如何返回
- 外部资源如何暴露给模型
- 工具和数据源如何被不同 Agent 或应用复用

如果说 Tool / Plugin 解决的是“AI 怎么接外部世界”，那么 MCP 进一步解决的是：

> **接外部世界这件事，能不能变得更统一、更可复用。**

## 06

有了 Agent、Workflow、Tool、Plugin、MCP 之后，AI 应用已经能做很多事。

但新的问题又出现了：

> **Agent 太通用了。**

一个通用 Agent 可以规划、可以调用工具、可以写代码、可以查资料。

但它未必知道你的组织经验、任务规范、领域方法和交付标准。

比如你让它做“小红书笔记复盘”，它可能每次都要重新理解：

- 复盘看哪些指标？
- 互动率怎么算？
- 什么样的数据算异常？
- 输出格式是什么？
- 哪些结论不能乱下？
- 哪些经验来自过去的业务沉淀？

如果每次都靠长 prompt 重新教一遍，成本很高，也不稳定。

这就是 Skill 开始重要的背景。

Skill 可以简单理解为技能。

它的作用，是把某类高频任务需要的说明、步骤、脚本、模板、资源和经验打包起来，让 Agent 在需要时动态加载。

它解决的是：

> **通用 Agent 缺少稳定的领域经验，需要把组织知识和任务方法沉淀成可复用能力包。**

例如：

- 小红书内容复盘 Skill
- 财报分析 Skill
- 代码审查 Skill
- 简历改写 Skill
- 会议纪要整理 Skill

Skill 和 Tool 不一样。

Tool 是“能做一个动作”。

Skill 是“知道一类任务怎么做”。

Skill 和 Workflow 也不一样。

Workflow 更强调固定流程。

Skill 更强调任务经验和方法封装。

所以 Skill 的出现，是为了让高频任务不再每次从零教 Agent。

## 07

如果从大模型应用的演化看，大致可以这样理解：

第一阶段，AI 先是 Chatbot。

它解决的是回答问题和生成文本。

第二阶段，出现 Workflow。

因为单次 prompt 做复杂任务不稳定，需要拆成多步骤流程。

第三阶段，Agent 变重要。

因为真实任务路径不固定，需要系统边观察边行动。

第四阶段，Tool / Plugin 变重要。

因为模型不能只会说，还要能调用外部系统。

第五阶段，MCP 变重要。

因为工具、数据源、平台接口越来越碎，需要统一接入。

第六阶段，Skill 变重要。

因为通用 Agent 缺少稳定领域经验，需要把任务方法、脚本、资源打包成能力。

但这不是严格的“概念发明时间线”。

因为 Workflow、Agent、Plugin 这些概念很早就存在。

这里说的是：

大模型应用走向真实业务后，重新需要它们来组织复杂系统。

## 08

所以，这些概念分别解决了哪类问题？

可以这样看：

Workflow 解决的是多步骤任务的稳定性。

Agent 解决的是开放目标的动态判断。

Tool / Plugin 解决的是模型连接外部世界。

MCP 解决的是外部能力接入标准化。

Skill 解决的是高频任务经验复用。

这样看，它们就不是一堆互相竞争的概念。

它们分别对应 AI 应用走向真实业务时遇到的不同问题。

## 09

这里还有一个挺有意思的现象。

Agent 火了之后，很多企业实践反而重新强调 Workflow。

原因也简单：

真实业务不只需要“聪明”，还需要稳定。

很多任务并不需要 Agent 自由发挥。

比如：

- 审批流程
- 报销流程
- 内容发布流程
- 月度报表流程
- 客服工单流转
- 数据清洗入库

这些任务的路径清楚、规则明确、异常可枚举。

用 Agent 反而会增加不可控性。

所以更实际的做法是：

- 能用 Workflow 稳定解决的，不要强行上 Agent
- Workflow 覆盖标准路径
- Agent 处理开放目标、异常判断和策略调整
- Skill 沉淀高频任务经验
- Tool / Plugin 提供外部能力
- MCP 做统一连接

不是因为 Agent 不重要。

而是因为真实业务需要分层：

> **确定性的部分下沉到流程，不确定性的部分交给 Agent。**

## 10

把整条线串起来，其实就是 AI 应用从聊天走向真实业务的过程。

一开始，AI 只是会说。

后来，人们发现：

只会说不够，要能按步骤做事，于是有了 Workflow。

固定步骤不够，要能动态判断，于是有了 Agent。

只在文本里判断不够，要能调外部系统，于是有了 Tool / Plugin。

工具太多太散不够，要有统一接入，于是有了 MCP。

通用 Agent 太泛不够，要沉淀组织经验，于是有了 Skill。

所以这些概念不是凭空多出来的。

它们都是 AI 应用“越来越像真实工作系统”之后，逐步长出来的组织方式。

理解一个技术概念，最好的方式不是先背定义，而是看它到底替谁解决了什么麻烦。

新概念不是为了制造复杂度。

而是因为旧抽象已经装不下新的真实工作。
