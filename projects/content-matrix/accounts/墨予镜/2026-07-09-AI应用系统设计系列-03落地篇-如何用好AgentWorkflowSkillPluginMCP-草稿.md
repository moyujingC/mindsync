# AI 应用系统设计系列：如何用好 Agent、Workflow、Skill、Plugin、MCP

这是「AI 应用系统设计」系列的落地篇，建议放在本质篇和背景篇之后阅读。

本质篇先讲清楚这些概念的边界，背景篇再说明它们为什么会在 LLM 应用走向真实业务的过程中变重要。

这一篇回答第三个问题：面对一个真实业务，应该怎样拆解，并选择合适的 AI 能力形态承接它？

在本系列的本质篇里，我们把 `Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 的区别压缩成一句话：

- `Agent` 是主体
- `Workflow` 是流程
- `Skill` 是能力包
- `Plugin` 是扩展包
- `MCP` 是连接标准

但真正难的不是记住这些概念，而是知道什么时候该用哪个。

很多 AI 应用做不好，不是因为技术组件不够多，而是因为业务没有拆清楚。程序本质上是对现实世界的数字化模拟。如果现实业务里的角色、流程、规则、动作、判断和反馈没有被拆明白，后面无论叫 Agent 还是 Workflow，都会变成一团混乱的自动化脚本。

所以，用好这五个概念的前提是：

> 先解构业务，再选择 AI 能力形态。

不是先问“这里要不要上 Agent”，而是先问：

> 现实世界里，这件事到底由哪些角色、动作、规则、工具、判断和反馈构成？

---

## 一、先从现实业务拆起

可以把真实业务拆成几类对象：

| 现实世界里的东西 | 数字化后对应什么 | AI 系统里更接近 |
|---|---|---|
| 人 / 岗位 / 责任主体 | 执行者、决策者、上下文持有者 | `Agent` |
| 标准流程 / SOP | 步骤、状态、分支、验收 | `Workflow` |
| 熟练工的方法 | 可复用能力、模板、经验规则 | `Skill` |
| 外部工具 / 系统 | 可调用能力、API、服务 | `Tool` / `Plugin` |
| 系统间协作规则 | 协议、接口、权限边界 | `MCP` / API |
| 业务判断标准 | 约束、评分、路由规则 | Workflow 条件 / Agent 策略 / Skill 规则 |
| 反馈闭环 | 监控、复盘、重试、迭代 | Agent memory / Workflow state / QA gate |

所以判断顺序应该是：

- 先识别现实中的“谁负责判断”，再考虑 `Agent`
- 先识别现实中的“稳定流程”，再考虑 `Workflow`
- 先识别现实中的“熟练技巧”，再考虑 `Skill`
- 先识别现实中的“外部工具”，再考虑 `Tool / Plugin`
- 先识别现实中的“系统连接边界”，再考虑 `MCP`

一句话总结：

> 不是拿 AI 概念套业务，而是把业务拆成角色、流程、能力、工具、接口和反馈，再选择合适的 AI 组织范式承接它们。

---

## 二、核心原则：确定性下沉，不确定性上浮

用好这套体系，有一个很重要的原则：

> 确定性下沉，不确定性上浮。

也就是说：

- 越稳定、越高频、越标准化的动作，越应该下沉到 `Tool / Skill / Workflow`
- 越开放、越动态、越需要判断的目标，越应该上浮给 `Agent`

不要让 Agent 亲自做所有事。

如果 Agent 每次都从零开始查数据、写内容、发通知、做复盘，它就会退化成一个“大号 Prompt 脚本”。

更好的结构是：

- `Tool` 做单一动作
- `Skill` 做标准任务
- `Workflow` 做固定流程
- `Agent` 做目标拆解、调度、异常处理和策略迭代
- `MCP` 负责把外部能力标准化接入

这样系统才会稳定、可复用、可维护。

## 三、落地演示：小红书种草运营场景

我们用一个具体业务场景来说明：**新消费护肤品牌的小红书种草内容运营**。

这个场景很好，因为它同时包含：

- 标准化执行
- 固定流程
- 经验判断
- 外部工具调用
- 开放增长目标

核心业务目标是：

> 持续产出符合品牌调性的种草内容，提升品牌曝光与产品转化，同时控制内容生产成本。

如果直接说“做一个小红书运营 Agent”，很容易做虚。

更稳的方式，是先按确定性高低拆业务。

---

## 四、业务分层：从确定动作到开放目标

### 1. 原子动作层：100% 标准化

这一层是不可再拆的纯执行动作，输入输出固定，没有业务判断空间。

典型动作包括：

- 查询单篇笔记数据
- 搜索平台热点关键词
- 生成产品素材图
- 检测内容合规性
- 发布笔记
- 回复标准化评论

这一层更接近 `Tool`。

如果这些能力以扩展包形式安装进系统，则可以由 `Plugin` 提供。

### 2. 标准任务层：单任务闭环

这一层是高频出现的完整任务，有明确输入、输出和业务规则。

典型任务包括：

- 单篇笔记效果复盘
- 选题热度校验
- 单篇笔记排版发布
- 周度内容数据统计

这一层适合封装为 `Skill`。

### 3. 固定流程层：多节点串联

这一层是多个任务按顺序组成的流程，路径、分支和异常基本可以提前枚举。

典型流程包括：

- 常规种草笔记生产流程
- 热点选题快速响应流程
- 周度内容复盘流程

这一层适合编排为 `Workflow`。

### 4. 开放目标层：路径动态调整

这一层只有最终目标，没有固定执行路径，需要根据数据和外部环境动态调整。

典型目标包括：

- 完成月度 500 万曝光
- 提升内容种草转化率
- 控制内容生产成本
- 应对突发舆情并调整内容策略

这一层适合交给 `Agent`。

## 五、逐层封装：每一层该怎么落地

### 1. Tool / Plugin：封装原子动作

原子动作的封装原则是：

> 单一职责，只做执行，不掺杂业务判断。

比如：

- 小红书笔记数据查询 Tool
- 平台热点关键词搜索 Tool
- 商品素材图生成 Tool
- 内容合规检测 Tool
- 笔记发布 Tool
- 标准化评论回复 Tool

这里要注意边界。

“查询笔记数据”是 Tool。

“分析笔记数据好不好”不是 Tool，因为它包含业务判断，应该放到 Skill 或 Workflow 里。

Plugin 在这里的角色，是把这些 Tool 作为一组能力装进系统。

比如“小红书运营 Plugin”里可以包含数据查询、内容发布、评论回复等多个 Tool。

### 2. Skill：封装标准任务

Skill 的封装原则是：

> 边界封闭，输入输出明确，内置固定业务规则，能独立交付一个完整任务结果。

比如“单篇笔记效果复盘 Skill”。

它可以这样设计：

- 输入：单篇笔记 ID
- 输出：标准化笔记复盘表
- 内容：曝光、点击率、互动率、转化关键词、问题判断、优化建议
- 内部逻辑：调用笔记数据查询 Tool，按预设复盘维度分析，再输出统一格式结果

它的价值是：

> 不用每次都告诉 AI “复盘要看哪些指标、按什么维度分析、输出什么格式”。

调用一次 Skill，就能得到一个完整复盘结果。

Skill 和 Tool 的边界是：

- Tool 是“动作”
- Skill 是“动作 + 业务规则 + 任务交付”

### 3. Workflow：编排固定流程

Workflow 的封装原则是：

> 只承接全路径可枚举的确定性流程，所有节点、分支和异常规则提前定义。

比如“常规种草笔记生产 Workflow”：

1. 选题抽取：从选题库中按分类规则抽取当日选题
2. 大纲生成：按品牌固定模板生成内容大纲
3. 初稿撰写：遵循品牌话术规范生成初稿
4. 合规校验：调用内容合规检测 Tool
5. 条件分支：校验不通过，返回初稿节点重写，最多重试 2 次
6. 排版配图：调用笔记排版 Skill 和素材图生成 Tool
7. 定时发布：调用笔记发布 Tool
8. 数据归档：发布 7 天后自动同步数据到内容台账

Workflow 的核心价值不是“聪明”，而是稳定、批量、低成本。

Skill 和 Workflow 的边界是：

- Skill 交付一个标准任务结果
- Workflow 编排多个任务和工具，完成一条业务流程

### 4. Agent：承接开放目标

Agent 的封装原则是：

> 只做决策、调度、异常处理和策略迭代，不亲自执行可标准化的重复动作。

比如“小红书种草运营 Agent”。

它的目标可以是：

> 本月完成 500 万笔记总曝光，种草转化率不低于 2%，内容成本控制在 1.5 万以内。

它不应该亲自写每一篇笔记。

它应该做这些事：

- 拆解月度目标，规划内容数量、品类分布和发布节奏
- 调度常规种草笔记生产 Workflow 批量执行日常内容
- 每日监控数据，发现选题下滑后调用笔记复盘 Skill 定位原因
- 调整选题池占比，更新 Workflow 规则
- 发现突发热点、爆量笔记、负面评论集中等情况时，判断是否响应
- 每周输出复盘，把可标准化的新规律沉淀成 Skill 或 Workflow 规则

Agent 和 Workflow 的边界是：

- Workflow 是“给流程，按规则执行”
- Agent 是“给目标，自己判断路径”

Workflow 负责确定性的存量效率。

Agent 负责不确定性的增量优化。

### 5. MCP：统一能力接入标准

MCP（Model Context Protocol，模型上下文协议）的定位不是业务能力，而是连接标准。

它解决的是：

> 外部能力如何被模型系统统一发现、调用和返回结果。

在这个场景里，如果素材图生成、内容合规检测、数据查询等能力都按 MCP 暴露，那么它们就不只服务小红书运营。

同一套能力还可以被：

- 抖音运营 Agent 调用
- 私域运营 Skill 调用
- 内容审核 Workflow 调用
- 品牌素材管理系统调用

所以 MCP 的价值是：

> 一次开发，多处复用，减少不同系统之间重复适配。

但要记住：MCP 不做业务判断。

它只是通用接口语言。

## 六、一次完整的月度运营闭环

现在看一轮完整运行。

月初，运营人员给 Agent 下达目标：

> 本月小红书完成 500 万曝光，转化率不低于 2%，内容成本控制在 1.5 万以内。

Agent 拆解目标，规划出 80 篇常规笔记的生产节奏，调用“常规种草笔记生产 Workflow”批量执行，覆盖基础曝光需求。

日常运行中，Workflow 按固定流程产出内容，调用各个 Skill 和 Tool。Agent 不介入每篇内容，只监控整体数据进度。

月中，平台突然出现热门成分话题。Agent 判断这个话题与品牌产品高度相关，于是调度“热点内容响应 Workflow”，在 2 小时内产出 3 篇对应笔记，抓住流量窗口。

第二周结束，Agent 发现“用户实测类笔记”的转化率低于预期，于是调用“笔记效果复盘 Skill”定位问题，并调整该类笔记的内容模板，更新 Workflow 的撰写规则。

月底，Agent 调用“月度复盘 Skill”输出完整报告，核算目标完成情况，同时提炼出 3 类高转化选题模板，沉淀到 Workflow 的选题库中。

这就是完整闭环：

> Tool 执行动作，Skill 完成任务，Workflow 批量跑流程，Agent 动态调策略，MCP 统一接外部能力。

## 七、可复用的业务拆分方法

遇到任何业务需求，可以按四步拆。

### 第一步：全链路动作梳理

把业务从起点到终点拆成独立动作，颗粒度细到：

> 一个人单次可完成的一件事。

例如内容运营可以拆成：

- 找选题
- 查热度
- 写大纲
- 写初稿
- 配图
- 检查合规
- 发布
- 查看数据
- 复盘表现
- 调整选题库

### 第二步：确定性梯度分层

把动作按确定性分成四层：

- 原子动作层：输入输出固定，没有判断空间
- 标准任务层：单任务闭环，规则固定，交付物明确
- 固定流程层：多任务串联，分支和异常可提前枚举
- 开放目标层：只有最终目标，路径不固定，需要动态判断

### 第三步：标记复用频率

给每个动作标记频率：

- 日更
- 周更
- 月更
- 单次

高频、稳定的动作优先沉淀。

低频、变化大的动作不急着封装。

### 第四步：校验边界

检查相邻层级有没有重叠：

- Tool 里有没有偷偷写业务判断？
- Skill 有没有扩展成大流程？
- Workflow 有没有塞进无法枚举的开放目标？
- Agent 有没有亲自执行大量重复动作？

边界不清，后面系统一定会乱。

## 八、能力匹配速查表

| 能力类型 | 对应业务层级 | 判断标准 | 封装要求 | 边界红线 |
|---|---|---|---|---|
| `Tool` / `Plugin` | 原子动作层 | 单一执行动作，无业务判断 | 单一职责，输入输出标准化 | 不内置业务规则和多步骤流程 |
| `Skill` | 标准任务层 | 可独立交付完整任务结果 | 输入输出明确，内置固定业务规则 | 不处理动态变化的开放需求 |
| `Workflow` | 固定流程层 | 全路径可枚举，分支异常可提前定义 | 节点清晰，可追踪可复盘 | 不承接路径不固定的目标 |
| `Agent` | 开放目标层 | 只有最终目标，需要动态判断 | 目标拆解、调度、异常处理、策略迭代 | 不亲自执行可标准化重复动作 |
| `MCP` | 全层级通用 | 有跨系统复用和统一接入需求 | 统一能力发现、调用、返回格式 | 不提供具体业务能力 |

## 九、几个常见业务场景怎么套

### 内容运营

- Tool / Plugin：内容数据查询、素材生成、合规检测、多平台发布
- Skill：单篇内容复盘、选题热度校验、内容排版优化
- Workflow：常规内容生产流程、周度复盘流程、热点响应流程
- Agent：内容增长运营 Agent，承接曝光、互动、转化目标

### 用户运营

- Tool / Plugin：用户标签查询、触达消息发送、权益发放、数据导出
- Skill：用户画像生成、用户分层打标、单活动复盘
- Workflow：新用户 7 天触达流程、沉睡用户召回流程、活动执行流程
- Agent：用户增长 Agent，承接留存、付费、活跃目标

### 电商运营

- Tool / Plugin：库存查询、订单导出、商品上下架、价格调整
- Skill：单品标题优化、单品数据复盘、售后单审核
- Workflow：商品上新流程、日常订单处理流程、月度对账流程
- Agent：店铺运营 Agent，承接销售额、利润率目标

### 行政办公

- Tool / Plugin：日程查询、会议室预定、邮件发送、文档转换
- Skill：会议纪要整理、差旅行程规划、报销单校验
- Workflow：员工入职流程、会议组织流程、月度报销审批流程
- Agent：行政助理 Agent，承接事务效率和成本控制目标

## 十、落地避坑清单

1. 不要给 Tool / Plugin 添加业务判断逻辑。判断规则应该上移到 Skill、Workflow 或 Agent。
2. 不要把 Skill 做得太细。只能做单一动作的是 Tool，能交付完整任务结果的才是 Skill。
3. 不要把开放目标硬塞进 Workflow。全路径无法枚举时，应交给 Agent。
4. 不要让 Agent 从零执行所有步骤。Agent 应该调度下层能力，而不是替代下层能力。
5. 不要重复开发同类能力。公共能力应尽量用 MCP 或统一 API 暴露。
6. 不要为了炫技强行上 Agent。Workflow 能稳定解决的，就不要增加自主性风险。
7. 不要让 Workflow 节点粒度过粗。高频复用节点应单独沉淀为 Skill。
8. 不要在多层重复封装同一个动作。一个能力只在最合适的层级沉淀一次。

---

## 十一、落地自检 10 题

业务拆分完成后，可以用这 10 个问题检查：

1. 所有 Tool 是否只做单一执行动作？
2. 所有 Skill 是否都能独立交付完整业务结果？
3. 所有 Workflow 的路径、分支、异常是否都能提前枚举？
4. Agent 是否只承接开放目标，而不是亲自执行重复步骤？
5. 公共能力是否有统一接口，方便跨场景复用？
6. 高频复用能力是否已经尽量下沉？
7. 每个能力单元是否只有单一职责？
8. 80% 的日常标准化业务，是否能由 Workflow / Skill 自动完成？
9. Agent 是否主要处理 20% 的不确定性、决策和异常？
10. 所有封装是否贴合真实业务，而不是为了技术概念强行拆分？

---

## 结尾：AI 系统设计，先是业务理解问题

用好 `Agent`、`Workflow`、`Skill`、`Plugin`、`MCP`，本质不是学会几个技术名词，而是学会把现实业务数字化。

程序是对现实世界的模拟。

AI 应用程序则是在模拟现实业务里的角色、流程、判断、工具和反馈。

所以真正的能力不是“会不会做 Agent”，而是：

> 能不能看懂一个业务，把其中稳定的部分沉淀为流程，把高频的经验沉淀为技能，把外部系统沉淀为工具，把开放目标交给 Agent，把跨系统连接交给统一协议。

这就是从业务解构到 AI 系统设计的核心路径。
