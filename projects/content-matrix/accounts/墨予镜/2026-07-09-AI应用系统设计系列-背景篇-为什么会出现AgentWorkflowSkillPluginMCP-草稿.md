# AI 应用系统设计系列：为什么会出现 Agent、Workflow、Skill、Plugin、MCP？

这是「AI 应用系统设计」系列的背景篇。

这一组文章不按“第几篇”来编号，而是按三个问题展开：

- 背景篇：这些概念为什么会出现？
- 本质篇：它们各自封装了什么复杂度？
- 落地篇：真实业务里应该怎么用它们？

这一篇先回答第一个问题：为什么 AI 应用从聊天演示走向真实业务后，会逐渐需要 `Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 这些抽象？

理解 `Agent`、`Workflow`、`Skill`、`Plugin`、`MCP`，还有一个很重要的角度：

> 不只看它们是什么，还要看它们为什么会出现。

很多技术概念不是凭空发明出来的。它们通常是旧方式解决不了新问题之后，自然长出来的新抽象。

`Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 也是这样。

它们不是为了制造复杂度，而是因为 AI 应用从“聊天演示”走向“真实业务”之后，遇到了不同层次的问题：

- 只靠一次 prompt，复杂任务不稳定
- 模型只会说，不能访问外部世界
- 工具越来越多，接入方式越来越碎
- 通用 Agent 很灵活，但缺少稳定的领域经验
- 真实业务既有固定流程，也有动态判断

这些问题不断出现，才让不同概念逐渐变得重要。

需要先说明一点：

> 这里追溯的不是这些词在计算机科学史上的首次出现，而是它们什么时候成为 LLM 应用工程里的主流抽象。

因为 `workflow`、`agent`、`plugin` 这些词，在传统软件工程和 AI 历史里早就存在。

我们这里讨论的是：它们在大模型应用开发中，为什么重新变成核心概念。

---

## 一、Chatbot 阶段：AI 先是“会回答”

最早大家使用大模型，主要是把它当成 `Chatbot`（聊天机器人）。

你问一句，它答一句。

比如：

> 帮我写一篇小红书文案。
> 帮我总结这段材料。
> 帮我翻译这篇文章。
> 帮我解释一个概念。

这个阶段的核心体验是：

> AI 很会说。

它能生成文本、总结文本、改写文本、翻译文本，也能给出建议。

但只要任务稍微复杂一点，问题就来了。

比如你让它：

> 帮我做一次完整的小红书月度内容复盘。

它可能会写得很像样，但未必真的按正确步骤做：

- 有没有先拉数据？
- 有没有区分曝光、互动、转化？
- 有没有对比不同选题类型？
- 有没有找出异常笔记？
- 有没有沉淀下月选题建议？
- 有没有把结论放到固定格式里？

单次 prompt 很容易漏步骤，也很难保证每次都稳定。

这就引出了第一个问题：

> 复杂任务不能只靠一次回答，需要拆成多步。

---

## 二、Prompt Chaining / Workflow：让任务变成稳定多步流程

为了解决单次 prompt 不稳定的问题，大家开始把复杂任务拆成多个步骤。

这就是早期的 `Prompt Chaining`（提示词链）、`Chain`（链）、`Pipeline`（流水线）或后来的 `Workflow`（工作流）思路。

它们的核心都是：

> 不要指望模型一次完成复杂任务，而是把任务拆成多个稳定步骤，让前一步输出成为后一步输入。

比如做内容复盘，可以拆成：

1. 读取数据
2. 清洗字段
3. 计算指标
4. 找异常笔记
5. 按选题类型聚合
6. 生成复盘结论
7. 输出下月建议

这时 AI 不再是“一口气回答”，而是进入一个流程。

`Workflow` 的价值开始出现：

- 步骤更清楚
- 顺序更稳定
- 中间结果可检查
- 失败节点可重试
- 批量任务可复用

所以，`Workflow` 的出现，是为了解决这个问题：

> 复杂任务需要稳定、可追踪、可复用的执行过程。

在 LLM 应用里，workflow 不一定一开始就叫 workflow。早期可能叫 prompt chain、chain、pipeline。名字不同，但背后的工程需求是一致的：**把一次性生成，变成多步骤执行。**

---

## 三、ReAct / Agent：让模型不只是按流程走，还能边想边做

`Workflow` 很适合稳定流程，但真实任务不总是固定路径。

有些任务不能提前写死每一步。

比如：

> 帮我找 5 个适合我们护肤品牌的小红书近期热点，并判断哪些值得跟。

这个任务就不太适合完全固定流程。

因为模型可能需要根据搜索结果不断调整：

- 搜到的热点是否真的相关？
- 这个热点是不是已经过时？
- 有没有品牌安全风险？
- 要不要继续查用户评论？
- 要不要换关键词？
- 要不要把某个热点排除？

这时就需要一种新的能力：

> 模型不只是按预设流程执行，而是能根据观察结果决定下一步。

这就是 `Agent`（智能体）在 LLM 应用里开始变得重要的原因。

2022 年的 ReAct 论文提出让模型交替生成 `reasoning`（推理）和 `acting`（行动），也就是一边想、一边做，并根据外部环境反馈调整后续行动。

后来 AutoGPT 这类项目又把 “autonomous agent”（自主智能体）推到大众视野里：用户给一个目标，系统自己拆任务、调用工具、循环推进。

所以，`Agent` 的出现，是为了解决这个问题：

> 真实任务有很多不确定性，系统需要围绕目标动态决定下一步。

它和 Workflow 的差别在这里：

- Workflow 是“流程先定好，再执行”
- Agent 是“目标先给定，再动态规划和调度”

Agent 不是为了替代 Workflow，而是为了处理 Workflow 预设不到的部分。

---

## 四、Plugin / Tool：让 AI 从“只会说”走向“能接外部世界”

无论是 Workflow 还是 Agent，如果只能在模型内部生成文本，都还是有限。

真实业务里，AI 不能只会说，还要能干活。

它需要：

- 查数据库
- 读文件
- 调接口
- 搜网页
- 发邮件
- 创建任务
- 查询库存
- 发布内容
- 调用业务系统

这就是 `Tool`（工具）和 `Plugin`（插件）开始重要的背景。

2023 年，ChatGPT Plugins 让很多人第一次直观感受到：模型可以连接第三方服务，访问实时信息，执行外部动作。

随后 function calling / tool calling 让开发者能用更工程化的方式，把函数、API、业务能力暴露给模型调用。

这里要区分一下：

- `Tool` 更像一个具体可调用能力，比如“查询笔记数据”“发送邮件”“读取文件”
- `Plugin` 更像一个扩展包，可能包含一组工具、配置、权限和说明

它们解决的是同一个方向的问题：

> 模型不能只停留在生成文本，它需要调用外部能力，才能参与真实业务。

所以，`Tool / Plugin` 的出现，是为了解决这个问题：

> AI 要从“会回答”变成“能操作外部系统”。

没有 Tool，Agent 再聪明也只能纸上谈兵。

没有 Plugin，很多外部能力就很难被打包、安装和分发。

---

## 五、MCP：当工具越来越多，就需要统一接入方式

当工具少的时候，手写几个接口还可以接受。

但当 AI 应用开始连接越来越多外部系统时，问题就出现了：

- 每个平台一套工具格式
- 每个数据源一套接入方式
- 每个应用都要重复适配
- 工具能力难以复用
- 权限和上下文管理容易混乱

这时候，需要的不只是更多工具，而是统一的连接标准。

`MCP`（Model Context Protocol，模型上下文协议）就是在这个背景下出现的。

它试图解决的问题是：

> AI 应用如何用统一方式连接外部工具、数据源和上下文。

你可以把 MCP 理解成一种“通用接口语言”。

它不是具体业务能力。

它不负责写文案，不负责查餐厅，也不负责做复盘。

它负责的是：

- 外部能力如何被发现
- 参数如何描述
- 调用如何发起
- 结果如何返回
- 外部资源如何暴露给模型
- 工具和数据源如何被不同 Agent 或应用复用

所以，`MCP` 的出现，是为了解决这个问题：

> 外部能力越来越多，不能每个系统都重新接一遍，需要标准化连接方式。

如果说 Tool / Plugin 解决的是“AI 怎么接外部世界”，那么 MCP 进一步解决的是：

> 接外部世界这件事，能不能变得更统一、更可复用。

---

## 六、Skill / Agent Skill：让通用 Agent 拥有稳定经验

有了 Agent、Workflow、Tool、MCP 之后，AI 应用已经能做很多事。

但新的问题又出现了：

> Agent 太通用了。

一个通用 Agent 可以规划、可以调用工具、可以写代码、可以查资料。

但它未必知道你的组织经验、任务规范、领域方法和交付标准。

比如你让它做“小红书笔记复盘”，它可能每次都要重新理解：

- 复盘看哪些指标？
- 互动率怎么算？
- 什么样的数据算异常？
- 输出格式是什么？
- 哪些结论不能乱下？
- 哪些经验来自过去的业务沉淀？

如果每次都靠长 prompt 重新教一遍，成本很高，也不稳定。

这就是 `Skill`（技能）开始重要的背景。

`Skill` 或 `Agent Skill` 的核心，是把某类高频任务需要的说明、步骤、脚本、模板、资源和经验打包起来，让 Agent 在需要时动态加载。

它解决的是：

> 通用 Agent 缺少稳定的领域经验，需要把组织知识和任务方法沉淀成可复用能力包。

例如：

- 小红书内容复盘 Skill
- 财报分析 Skill
- 代码审查 Skill
- 简历改写 Skill
- 会议纪要整理 Skill

Skill 和 Tool 不一样。

Tool 是“能做一个动作”。

Skill 是“知道一类任务怎么做”。

Skill 和 Workflow 也不一样。

Workflow 更强调固定流程。

Skill 更强调任务经验和方法封装。

所以，`Skill` 的出现，是为了解决这个问题：

> 高频任务不能每次从零教 Agent，需要把经验沉淀成可复用能力。

---

## 七、这些概念不是严格发明时间线，而是主流化顺序

如果从 LLM 应用开发的演化看，大致可以这样理解：

| 阶段 | 典型概念 | 背景问题 | 核心解法 |
|---|---|---|---|
| 1 | Chatbot | 模型先被用来回答问题和生成文本 | 人问一句，模型答一句 |
| 2 | Prompt chaining / Workflow | 单次 prompt 做复杂任务不稳定 | 把任务拆成多步流程 |
| 3 | ReAct / Agent | 真实任务路径不固定，需要边观察边行动 | 让模型围绕目标动态决策 |
| 4 | Plugin / Tool calling | 模型只能说，不能操作外部系统 | 让模型调用工具和 API |
| 5 | MCP | 工具、数据源、平台接口碎片化 | 用统一协议连接外部能力 |
| 6 | Skill / Agent Skill | 通用 Agent 缺少稳定领域经验 | 把任务方法、脚本、资源打包成能力 |

但这不是严格的“概念发明时间线”。

因为：

- `Workflow` 在业务流程管理里很早就存在
- `Agent` 在经典 AI 里也很早就存在
- `Plugin` 在软件系统里更是常见概念
- `Tool use` 也不是 LLM 之后才有

这里讨论的是：这些概念什么时候在 LLM 应用工程里变成主流抽象。

换句话说：

> 不是这些概念今天才被发明，而是大模型应用走向真实业务后，重新需要它们来组织复杂系统。

---

## 八、它们分别解决了哪类问题？

可以把五个概念放回问题本身看：

| 概念 | 解决的问题 | 一句话理解 |
|---|---|---|
| `Workflow` | 单次 prompt 不稳定，多步骤任务需要可控流程 | 让复杂任务按稳定路径执行 |
| `Agent` | 真实目标路径不固定，需要动态判断 | 让系统能围绕目标自己决定下一步 |
| `Tool / Plugin` | 模型只能生成文本，不能操作外部世界 | 让 AI 能调用外部系统和能力 |
| `MCP` | 工具和数据源接入碎片化 | 让外部能力用统一方式接进来 |
| `Skill` | 通用 Agent 缺少稳定任务经验 | 把高频任务方法沉淀成可复用能力 |

这样看，它们不是一堆互相竞争的概念。

它们分别对应 AI 应用走向真实业务时遇到的不同问题。

---

## 九、为什么企业实践里又开始强调 Workflow？

一个有意思的现象是：Agent 火了之后，很多企业实践反而重新强调 Workflow。

原因很简单：

> 真实业务不只需要“聪明”，还需要稳定。

很多任务并不需要 Agent 自由发挥。

比如：

- 审批流程
- 报销流程
- 内容发布流程
- 月度报表流程
- 客服工单流转
- 数据清洗入库

这些任务的路径清楚、规则明确、异常可枚举。

用 Agent 反而会增加不可控性。

所以更实际的做法是：

- 能用 Workflow 稳定解决的，不要强行上 Agent
- Workflow 覆盖标准路径
- Agent 处理开放目标、异常判断和策略调整
- Skill 沉淀高频任务经验
- Tool / Plugin 提供外部能力
- MCP 做统一连接

这也是为什么后来的工程实践里，会明确区分 workflows 和 agents。

不是因为 Agent 不重要，而是因为真实业务需要分层：

> 确定性的部分下沉到流程，不确定性的部分交给 Agent。

---

## 十、从“会说”到“能干活”，每一步都带来新抽象

把整条线串起来，其实就是 AI 应用从聊天走向真实业务的过程。

一开始，AI 只是会说。

后来，人们发现：

- 只会说不够，要能按步骤做事，于是有了 Workflow
- 固定步骤不够，要能动态判断，于是有了 Agent
- 只在文本里判断不够，要能调外部系统，于是有了 Tool / Plugin
- 工具太多太散不够，要有统一接入，于是有了 MCP
- 通用 Agent 太泛不够，要沉淀组织经验，于是有了 Skill

所以这些概念不是凭空多出来的。

它们都是 AI 应用“越来越像真实工作系统”之后，逐步长出来的组织方式。

---

## 结尾：理解概念，先看它解决了什么麻烦

理解一个技术概念，最好的方式不是先背定义，而是看它到底替谁解决了什么麻烦。

`Workflow` 解决的是多步骤任务的稳定性。

`Agent` 解决的是开放目标的动态判断。

`Tool / Plugin` 解决的是模型连接外部世界。

`MCP` 解决的是外部能力接入标准化。

`Skill` 解决的是高频任务经验复用。

所以，`Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 并不是五个孤立的新名词。

它们是 AI 应用从演示走向真实业务时，为了处理不同问题而形成的一组工程抽象。

或者说：

> 新概念不是为了制造复杂度，而是因为旧抽象已经装不下新的真实工作。
