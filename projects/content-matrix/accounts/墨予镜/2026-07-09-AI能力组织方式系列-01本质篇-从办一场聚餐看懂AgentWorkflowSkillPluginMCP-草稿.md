# AI 能力组织方式系列：从办一场聚餐，看懂 Agent、Workflow、Skill、Plugin、MCP

这是「AI 能力组织方式」系列的入口篇，也就是本质篇。

这一组文章想讲清楚一件事：AI 不只是一个会聊天的模型，它会逐渐被组织成工具、技能、流程、智能体和外部连接。建议按“本质 -> 背景 -> 落地”的顺序阅读：

- 本质篇：先用一个通俗例子看懂五个概念的边界。
- 背景篇：再理解这些概念为什么会在 LLM 应用里变重要。
- 落地篇：最后进入业务解构，讨论真实场景里怎么用好它们。

这一篇先回答第一个问题：`Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 各自封装了什么复杂度，决策权分别放在哪里，为什么真实系统里它们会互相嵌套？

很多人第一次接触 `Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 这些概念时，会觉得它们很像。

因为它们最后都可以落到代码上，都像是“程序在调用程序”。但如果只看实现形式，就会越看越乱。

更准确的理解方式是：

> 它们都可以由程序实现，但真正拉开差异的，是各自封装的复杂度类型，以及决策权的分配方式。

可以先记住一句话：

> `Agent` 是主体，`Workflow` 是流程，`Skill` 是能力包，`Plugin` 是扩展包，`MCP` 是连接标准。

为了更容易理解，我们用一个日常例子来讲：**办一场朋友聚餐**。

---

## 一、先看这个具体任务

假设你对 AI 说：

> “这个周六晚上，帮我组织一场 8 人朋友聚餐，预算人均 150 元，地点尽量靠近静安寺。”

这件事看起来简单，但真正做起来包含很多动作：

- 确认人数
- 了解忌口
- 查餐厅
- 看评分
- 对比距离
- 估算预算
- 订位
- 发通知
- 聚餐前提醒
- 如果餐厅没位置，还要换备选方案

这时，`Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 就会分别扮演不同角色。

在展开之前，可以先看一张总表：

| 概念 | 封装的复杂度 | 决策权主要放在哪里 |
|---|---|---|
| `Agent` | 目标理解、任务拆解、路径选择、异常处理、工具调度 | 放在运行时的 Agent 身上。人给目标，Agent 决定怎么推进 |
| `Workflow` | 步骤顺序、状态流转、条件分支、重试、回退、验收节点 | 放在流程设计者手里。运行时按预设规则走 |
| `Skill` | 某类任务的方法、规则、模板、经验和工具组合 | 放在技能作者沉淀的经验里。调用者只决定是否使用 |
| `Plugin` | 外部能力的安装、暴露、配置、权限和分发方式 | 放在插件提供者和宿主系统的能力边界里 |
| `MCP` | 外部能力如何被发现、描述、调用和返回结果 | 放在协议约定和 MCP server/client 的实现里，本身不做业务决策 |

---

## 二、Agent：负责“把事办成”的执行主体

`Agent`（智能体）像一个会自己张罗事情的助理。

你只告诉它目标：

> “帮我组织一场 8 人聚餐。”

它不会等你一步步命令：

1. 先查餐厅
2. 再问时间
3. 再做预算
4. 再发通知

它会自己判断：

- 这件事需要哪些步骤
- 哪些信息还缺
- 应该先查餐厅还是先确认时间
- 如果餐厅满了，要不要换备选
- 通知应该发给谁
- 是否需要聚餐前提醒

所以 `Agent` 的本质是：**目标执行主体**。

它封装的是“从目标到结果”的决策复杂度。你给它目标，它负责理解目标、拆解任务、选择工具、调整策略、处理异常。

这里的决策权主要放在 Agent 运行时。人类不需要预先写死每一步，而是把目标交给 Agent，让它在执行过程中持续判断下一步怎么走。

简单说：

> `Agent` 回答的问题是：谁来判断并推进这件事？

---

## 三、Workflow：负责“事情怎么流转”的固定流程

办聚餐其实可以整理成一套固定流程：

1. 收集人数
2. 确认时间
3. 确认预算
4. 搜索餐厅
5. 筛选候选
6. 发起投票
7. 订位
8. 发通知
9. 聚餐前提醒

这就是 `Workflow`（工作流）。

它的重点不是“聪明”，而是**稳定、可复用、可追踪**。

下次再办聚餐，还可以继续套这套流程。如果第 6 步投票没有结果，就进入提醒分支。如果第 7 步订位失败，就回到第 5 步重新选候选餐厅。

所以 `Workflow` 的本质是：**控制流封装**。

它封装的是过程复杂度，包括：

- 步骤顺序
- 条件分支
- 状态流转
- 重试机制
- 异常处理
- 完成标准

这里的决策权主要放在流程设计阶段。流程设计者提前规定好步骤和分支，运行时的 Workflow 只是按规则执行，不会自己发明新目标。

简单说：

> `Workflow` 回答的问题是：这件事应该按什么步骤走？

---

## 四、Skill：负责“某类事怎么做好”的能力包

在办聚餐的流程里，有些动作可以沉淀成独立能力。

比如：

- `餐厅筛选 Skill`：根据地点、预算、口味、评分筛出候选餐厅
- `预算估算 Skill`：根据人数、人均、酒水和服务费估算总价
- `群消息撰写 Skill`：把时间、地点、路线、注意事项写成一条清楚的通知
- `备选方案 Skill`：如果首选餐厅没位置，快速找 3 个替代方案

`Skill`（技能）和 `Workflow` 很容易混淆，因为一个 Skill 内部也可能有步骤。

比如“餐厅筛选 Skill”内部可能会做：

1. 查静安寺附近餐厅
2. 排除评分过低的
3. 排除人均超预算的
4. 排除距离太远的
5. 按适合聚餐程度排序

但它对外表现为一个能力：

> “帮我筛出合适餐厅。”

所以 `Skill` 的重点不是流程本身，而是**把某类任务打包成可复用能力**。

它封装的通常包括：

- 固定方法
- 领域规则
- 模板
- 脚本
- 检查清单
- 必要时的工具调用

这里的决策权主要沉淀在技能作者的经验里。Skill 不需要每次重新发明方法，而是把“这类事通常怎么做好”提前封装起来，调用者只需要决定要不要使用这个技能。

简单说：

> `Skill` 回答的问题是：这类事怎么稳定、重复地做好？

---

## 五、Plugin：负责“把外部能力装进系统”的扩展包

如果这个 AI 助理只能聊天，它其实没法真正查餐厅、看地图、发通知。

这时就需要 `Plugin`（插件）。

比如你给系统装了：

- 大众点评插件：查餐厅、评分、人均、营业时间
- 地图插件：查距离、路线、通勤时间
- 日历插件：看大家有没有空
- 微信或邮件插件：发送聚餐通知

插件的重点是：**把某种外部能力装进系统**。

但要注意，`Plugin` 不一定是最小能力单位。

一个“大众点评插件”里面可能包含多个具体工具：

- 搜索餐厅
- 查看餐厅详情
- 查询空位
- 获取评价
- 获取地址

所以更准确地说：

> `Plugin` 更像扩展包，`Tool` 才更像具体工具。

很多人会把 Plugin 和 Tool 混用，所以容易误解。从系统设计角度看，Plugin 解决的是能力如何安装、挂载、分发的问题。

这里的决策权主要放在插件提供者和宿主系统的边界里。插件决定自己暴露哪些能力、需要哪些配置和权限；宿主系统决定它能不能被安装、能访问什么资源。

简单说：

> `Plugin` 回答的问题是：新能力怎么装进来？

---

## 六、MCP：负责“外部能力怎么统一接入”的连接标准

如果每个插件都有自己的调用方式，系统会变得很乱。

大众点评一套格式，地图一套格式，日历又一套格式。每接一个新能力，都要单独适配一次。

`MCP`（Model Context Protocol，模型上下文协议）解决的就是这个问题。

它像一种统一插口标准。

不管是地图能力、餐厅能力、日历能力，还是文件系统、数据库、浏览器，只要按同一种协议暴露出来，Agent 就能用相对统一的方式发现和调用。

所以 `MCP` 本身不是“办聚餐”的能力。它不负责查餐厅，也不负责订位。

它负责的是：

- 能力如何被发现
- 参数如何描述
- 调用如何发起
- 结果如何返回
- 外部资源如何暴露给模型

这里的决策权不在 MCP 本身。MCP 只规定连接方式，真正的业务判断仍然发生在 Agent、Workflow、Skill 或具体工具里。

简单说：

> `MCP` 回答的问题是：外部能力怎么标准化接进来？

---

## 七、五者如何一起工作？

现在把整个过程串起来。

你说：

> “帮我组织一场 8 人朋友聚餐。”

`Agent` 接到目标后，判断这件事可以分成几块：

- 确认信息
- 搜索餐厅
- 筛选候选
- 订位
- 发通知

它决定启动一个“办聚餐 Workflow”。

这个 `Workflow` 里有几个节点：

1. 调用 `餐厅筛选 Skill`
2. 调用 `预算估算 Skill`
3. 调用 `订位 Tool`
4. 调用 `群消息撰写 Skill`
5. 调用 `通知发送 Tool`

这些 Skill 内部可能会调用多个工具。比如 `餐厅筛选 Skill` 会调用地图工具、点评工具、搜索工具。

这些工具可能来自不同 Plugin。而这些工具之所以能被 Agent 统一调用，可能是因为它们通过 MCP 这样的协议接入。

一句话串起来：

> `Agent` 接目标，`Workflow` 排步骤，`Skill` 做专项任务，`Plugin` 提供外部能力，`MCP` 负责统一连接。

---

## 八、它们不是一条简单的金字塔

很多文章会把它们画成一条从底到顶的金字塔：

> `MCP -> Plugin -> Skill -> Workflow -> Agent`

这个图有一定帮助，但也容易误导。

因为它们并不完全在同一个维度上。

更准确的理解是：

| 概念 | 所在维度 | 封装的复杂度 | 决策权分配 |
|---|---|---|---|
| `Agent` | 执行主体 | 目标理解、规划、调度、异常处理 | 决策权在运行时的 Agent |
| `Workflow` | 控制结构 | 步骤、分支、状态、回退、验收 | 决策权在流程设计者 |
| `Skill` | 能力封装 | 方法、规则、模板、经验、工具组合 | 决策权在技能作者沉淀的经验 |
| `Plugin` | 扩展分发 | 安装、挂载、配置、权限、能力暴露 | 决策权在插件边界和宿主平台 |
| `MCP` | 连接协议 | 发现、描述、调用、返回结果的统一约定 | 不做业务决策，决策权在调用方和实现方 |

所以，它们不是严格上下级，而是不同维度的封装方式。

它们可以互相嵌套：

- 一个 Agent 可以调用一个 Workflow
- 一个 Workflow 可以调用多个 Skill
- 一个 Skill 内部可以包含小 Workflow
- 一个 Skill 可以调用多个 Tool
- Tool 可以由 Plugin 提供
- Tool 也可以通过 MCP 暴露
- Plugin 里也可能打包 Skill、Tool、MCP Server

真实系统里，它们经常混在一起出现。这就是为什么看起来会乱。

---

## 九、它们更像 AI 应用开发里的“组织范式”

如果从软件工程视角看，`Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 并不是几种神秘的新东西。

它们更像 AI 应用开发里的不同**组织范式**。

也就是说，它们关注的不是“最后用什么代码实现”，而是：

> “这类复杂度应该怎么组织、封装、复用、连接？”

这和传统程序开发里的很多概念很像。

| 编程里的范式 / 结构 | 解决的问题 | AI 系统里的对应理解 |
|---|---|---|
| 函数 | 把一段逻辑封装成可调用单元 | `Tool` / 小型 `Skill` |
| 类 / 模块 | 把状态、能力、边界组织起来 | `Skill` / `Plugin` |
| 管道 / 流水线 | 把步骤串起来处理 | `Workflow` |
| 事件驱动 | 根据外部事件触发不同动作 | 自动化 / Agent 触发机制 |
| 面向对象里的对象 | 有状态、有职责、能响应消息 | `Agent` 的一部分隐喻 |
| 协议 / 接口 | 统一调用方式，隔离实现差异 | `MCP` |

所以可以这样理解：

> 从软件工程视角看，`Agent`、`Workflow`、`Skill`、`Plugin`、`MCP` 是 AI 应用开发中围绕大模型能力形成的新一代组织范式。它们和函数、模块、接口、设计模式的作用类似，都是为了把复杂度拆开、封装起来，并让不同部分能稳定协作。

但它们和传统编程范式有一个重要区别。

传统编程范式主要组织的是**确定性代码逻辑**。  
而这些 AI 范式组织的是一种混合系统：

> 确定性程序 + 不确定性模型能力 + 外部工具调用。

这也是为什么它们更容易混淆。

在传统程序里，一个函数的输入输出通常更稳定；但在 AI 系统里，模型的判断、工具的返回、外部环境的变化都会影响结果。

因此，AI 应用开发里的这些范式，不只是为了“复用代码”，还要处理：

- 模型输出的不确定性
- 工具调用的失败和重试
- 多步骤任务的状态追踪
- 人类目标到机器执行之间的语义落差
- 外部系统接入的权限、安全和格式差异

这也是为什么我们需要同时区分 `Agent`、`Workflow`、`Skill`、`Plugin` 和 `MCP`。

它们不是为了制造新名词，而是因为 AI 应用本身变成了一种更复杂的系统工程。

## 十、几个常见误区

### 误区一：Plugin 是最小工具

不一定。

很多情况下，最小的是 `Tool`（工具），Plugin 更像能力扩展包。一个 Plugin 里面可以包含多个 Tool，也可以包含配置、资源、说明，甚至一组 Skill。

所以不要简单把 Plugin 理解成“一个小工具”。

### 误区二：MCP 是一种新能力

不是。

`MCP` 是协议，不是业务能力本身。它像 USB 标准，不像 U 盘、键盘或鼠标。

它不提供具体业务功能，而是让不同外部能力能以统一方式接入模型系统。

### 误区三：Skill 和 Workflow 是严格上下级

也不是。

更准确地说：

- `Skill` 偏能力封装
- `Workflow` 偏过程编排

一个 Skill 内部可以有小流程。一个 Workflow 的节点也可以调用 Skill。

它们经常交叉嵌套，不是单向包含关系。

### 误区四：有了 Agent，就不需要 Workflow

这个误解也很常见。

其实 Agent 和 Workflow 更像管理者和标准流程的关系。

对于标准化、高频、稳定的任务，Workflow 更便宜、更可控。对于开放、复杂、变量多的任务，Agent 更灵活。

现实里不是谁替代谁，而是分层协作：

- Workflow 负责稳定部分
- Agent 负责判断、调度和异常处理

---

## 十一、最后再压缩成一句话

如果只想记一个最短版本：

- `Agent` 是会自己想办法的执行者
- `Workflow` 是预先设计好的流程
- `Skill` 是打包好的专项能力
- `Plugin` 是装进系统的扩展包
- `MCP` 是连接外部能力的统一协议

再换成聚餐例子：

- `Agent` 是帮你张罗聚餐的人
- `Workflow` 是办聚餐的固定流程
- `Skill` 是筛餐厅、做预算、写通知这些专项手艺
- `Plugin` 是大众点评、地图、日历这些外部能力包
- `MCP` 是让这些外部能力能被统一调用的插口标准

---

## 结尾：它们的本质都是复杂度封装

回到最开始的问题：它们当然都可以由程序实现。

但真正重要的是：它们分别封装了不同类型的复杂度，也把决策权放在了不同位置。

- `Agent` 封装决策复杂度
- `Workflow` 封装流程复杂度
- `Skill` 封装复用复杂度
- `Plugin` 封装扩展复杂度
- `MCP` 封装接入复杂度

也可以换一种说法：

- `Agent` 把决策权放在运行时
- `Workflow` 把决策权放在设计时
- `Skill` 把决策权放在经验封装里
- `Plugin` 把决策权放在能力边界里
- `MCP` 把决策权放在协议约定和具体实现里

所以它们不是五个互相替代的概念，而是 AI 应用系统里五种不同的设计角色。

当你不再只看实现形式，而是问“它们各自封装了什么、谁拥有决策权、谁负责连接和复用”，这些概念之间的边界就会清楚很多。
