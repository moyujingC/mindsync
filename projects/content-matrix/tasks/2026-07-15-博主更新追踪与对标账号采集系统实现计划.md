# 博主更新追踪与对标账号采集系统实现计划

## 1. 实现目标

把 `博主账号 -> 定时检查 -> 新内容入库 -> 飞书呈现` 跑成一个可验证的 MVP。

当前优先交付运营可用的监控链路，而不是一次性做满三平台、评论区和复杂分析。

## 2. 推荐目录

建议后续在 `projects/content-matrix/tools/influencer-tracker/` 下实现：

```text
projects/content-matrix/tools/influencer-tracker/
  README.md
  config/
    feishu.example.json
    sources.example.json
  src/
    cli/
    feishu/
    platforms/
      douyin/
      xiaohongshu/
      bilibili/
    jobs/
    analysis/
    storage/
  logs/
```

说明：

- `feishu/`：飞书多维表格读写封装。
- `platforms/`：平台适配器，每个平台只输出统一结构。
- `jobs/`：每日检查、手动回溯、评论采集等任务。
- `analysis/`：主题归纳、需求分类和选题建议。
- `storage/`：本地缓存、去重索引和运行日志。

## 3. 里程碑

### M0. 飞书表结构落地

目标：

- 创建或确认飞书多维表格
- 建立四张表：博主账号、内容更新、评论样本、洞察与选题
- 获取 base ID、table ID、字段 ID

交付物：

- `config/feishu.example.json`
- 字段映射说明
- 一条人工测试博主记录

### M1. 飞书读写适配层

目标：

- 能读取启用状态的博主账号
- 能创建内容更新记录
- 能更新博主最近检查状态
- 能按内容唯一键查询已存在记录

验收：

- 使用本地 fixture（测试样例数据）模拟一条内容
- 写入飞书后再次运行不重复写入

### M2. 平台适配器骨架

目标：

- 定义统一内容结构 `NormalizedContent`
- 定义统一账号结构 `TrackedCreator`
- 为抖音、小红书、B站各保留适配器入口
- 先选一个平台完成 L1 元数据采集

建议统一字段：

```json
{
  "platform": "bilibili",
  "creatorExternalId": "123",
  "contentExternalId": "BV...",
  "url": "https://...",
  "title": "标题",
  "description": "简介",
  "publishedAt": "2026-07-15T09:00:00+08:00",
  "contentType": "video",
  "metrics": {
    "likeCount": 0,
    "commentCount": 0,
    "favoriteCount": 0,
    "shareCount": 0
  },
  "raw": {}
}
```

### M3. 手动检查任务

目标：

- 提供命令行入口
- 支持检查全部启用博主
- 支持只检查某个平台
- 支持 dry-run（试运行，不写飞书）

建议命令：

```bash
node src/cli/check-updates.mjs --platform bilibili --dry-run
node src/cli/check-updates.mjs --all
```

### M4. 每日定时任务

目标：

- 支持本地 cron 或后续接入 Automation Platform
- 每天定时执行一次检查
- 生成运行日志
- 失败不阻断其他账号检查

验收：

- 单个账号失败时，其他账号仍继续检查
- 失败账号回写状态和原因

### M5. 对标账号批量回溯

目标：

- 支持对一个账号抓取最近 N 条内容
- 写入内容更新表
- 标记采集模式为 `backfill`

建议命令：

```bash
node src/cli/backfill-creator.mjs --platform bilibili --creator-id 123 --limit 50
```

### M6. 评论区与需求分析

目标：

- 评论采集与内容采集分离
- 评论写入评论样本表
- 生成基础需求标签
- 关联到洞察与选题表

这一阶段需要单独做合规和频率评审，不应混入 M1-M4 的 MVP。

## 4. 技术决策

### 4.1 先用脚本服务，不先做前端

飞书多维表格已经承担界面。第一版不需要再做一个前端控制台。

### 4.2 适配器先统一输出，不统一采集方式

不同平台可用的数据入口不同，先要求输出字段一致，不强行要求内部采集方式一致。

### 4.3 先做幂等，再做分析

幂等（idempotency，重复运行结果不重复）是采集系统的底线。没有去重和状态回写前，不进入评论分析。

### 4.4 保留原始 raw 字段

每条内容保留平台原始返回的最小必要片段，便于排查字段变化。

## 5. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 平台反爬或页面结构变化 | 适配器独立，失败回写，不影响其他平台 |
| 飞书字段名变化 | 使用字段 ID 映射，不只依赖字段名 |
| 重复写入 | 内容唯一键强制去重 |
| 评论区数据敏感 | 评论单独开关、脱敏保存、单独验收 |
| 数据不完整 | 每个平台记录能力级别和缺失字段 |

## 6. 下一步执行顺序

1. 确认飞书多维表格是否已创建
2. 建立字段映射配置样例
3. 实现飞书读写层
4. 先选一个平台跑通 L1 元数据采集
5. 接入手动检查命令
6. 再接每日定时任务

## 7. MVP 实现记录

> 更新时间：2026-07-15

已完成第一版本地 MVP：

- 工具目录：`projects/content-matrix/tools/influencer-tracker/`
- 命令入口：`src/cli/check-updates.mjs`

当前已跑通：

```bash

npm run check
npm run validate:feishu
npm run run:daily
npm run generate:topics
```

当前实现能力：

- 从本地 JSON 读取博主清单。
- 只处理 `启用` 状态账号。
- 通过 B 站 RSS 适配器标准化内容。
- 生成稳定内容唯一键。
- 支持 `dry-run`，默认不写飞书。
- 支持本地去重存储，非 `dry-run` 时持久化。
- 保留飞书多维表格读写客户端和字段映射。
- 支持飞书配置结构校验，先检查 base、table 和字段映射是否齐全。
- 支持只读飞书验表，能读取真实表字段并对照配置检查字段名是否存在。
- 支持日常运行包装命令，按日期写入 JSON 运行报告，便于后续接 cron 或 Automation Platform。
- 支持从运行报告生成待人工审核的选题候选，开始连接 `采集 -> 选题` 链路。
- 支持创建飞书多维表格表结构的 bootstrap 命令，会创建 `博主账号`、`内容更新`、`评论样本`、`洞察与选题` 四张表，并输出采集器可用的配置。

当前未完成：

- 真实飞书表字段验证。
- 真实飞书建表执行。当前本机没有飞书 CLI / 环境变量凭据，需提供 `appId`、`appSecret`、`baseAppToken` 后执行。
- 真实 B 站 RSSHub / 其他数据源稳定性验证。
- 抖音、小红书适配器。
- 每日定时任务接入。
- 评论区采集和需求分析。
