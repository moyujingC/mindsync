## 2. 当前定下的边界

系统属于 `内容矩阵` 的内容情报能力。

第一版目标是：

- 在飞书维护关注博主
- 每日检查博主是否更新
- 新内容写入飞书
- 支持后续对标账号回溯采集
- 为选题、市场需求调研和评论区需求归纳提供结构化输入

第一版不直接追求：

- 三个平台全部一次性跑通
- 评论区深度采集
- 绕过平台风控
- 自动内容发布
- 复杂前端工作台

## 3. 推荐 MVP 路线

建议下一步按这个顺序执行：

1. 先创建飞书多维表格和四张表
2. 配置 base ID、table ID、字段 ID
3. 写飞书读写层
4. 先选一个平台跑通 L1 元数据采集
5. 跑通手动检查命令
6. 再接每日定时任务

## 4. 待确认事项

进入代码实现前，需要人工确认：

1. 飞书多维表格是否已经创建
2. 第一优先平台是哪一个：抖音、小红书、B站
3. 是否允许使用登录态或只采集公开页面
4. 每天检查时间和频率
5. 评论区采集是否进入第二阶段

## 5. 当前风险

主要风险：

- 平台公开页面结构经常变化
- 抖音、小红书的采集稳定性和合规边界更敏感
- 评论区采集容易扩大数据和合规风险
- 如果没有稳定唯一键，会造成重复写入

当前处理方式：

- 先做适配器分层
- 先保证飞书写入和幂等
- 评论区单独开关、单独验收
- 每个平台记录能力级别和缺失字段
