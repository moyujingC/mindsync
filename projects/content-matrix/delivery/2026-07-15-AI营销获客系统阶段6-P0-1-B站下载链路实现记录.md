# AI营销获客系统阶段 6 P0-1 B站下载链路实现记录

本文记录 `ai-boshu-crawler` 能力迁移的第一步是怎么实现的，方便后面继续做 `转写 -> 评论 -> enrich`，也方便以后复用同样的迭代套路。

## 1. 这一步解决什么问题

在原来的 `influencer-tracker` 里，B站能力主要停留在：

```text
RSS 发现更新
-> 标准化内容元数据
-> 写内容更新表
```

这足够做“有没有更新”的追踪，但不够做更深的内容研究。

要进入后面的选题和需求分析，至少需要先把内容素材沉淀到本地：

```text
发现视频
-> 建本地 artifact（产物）目录
-> 保存元数据和简介
-> 可选地下载真实视频
```

所以这一步不是直接做“完整下载器”，而是先把下载工作流骨架搭起来。

## 2. 这一步怎么实现

### 2.1 新增的模块

新增 4 个文件：

- `src/platforms/bilibili/download.mjs`
- `src/jobs/download-bilibili.mjs`
- `src/cli/download-bilibili.mjs`
- `tests/download-bilibili.test.mjs`

职责拆分如下：

- `platforms/bilibili/download.mjs`
  负责单条内容的 artifact 目录写入、manifest 生成，以及具体下载器适配。
- `jobs/download-bilibili.mjs`
  负责“取最新几条内容，然后逐条生成 artifact”。
- `cli/download-bilibili.mjs`
  负责命令行参数和本地运行入口。
- `tests/download-bilibili.test.mjs`
  负责验证最小闭环。

### 2.2 工作流逻辑

当前执行逻辑是：

```text
creator（博主配置）
-> fetchBilibiliContents（从 RSS 拉标准化内容）
-> downloadLatestBilibili（选最新 N 条）
-> downloadBilibiliArtifact（给每条内容建目录）
-> 写 metadata / description / manifest
-> 如果启用真实下载，再调用 downloader
```

输出目录统一放在：

```text
logs/downloads/bilibili/<账号>/<内容ID>/
```

### 2.3 当前产物

每条内容最少会写出：

- `metadata.json`
- `description.txt`
- `download-manifest.json`

如果启用真实下载，还会多出：

- `video.*`

### 2.4 为什么改成“默认 metadata-only”

第一版实现时，默认下载器直接把 `content.url` 当成视频地址抓取。

这个做法有问题：

- B站内容 URL 通常是网页地址，不是最终视频流地址。
- 直接 `fetch` 很容易把 HTML（网页源码）保存成 `.mp4`。
- 这样看起来像“下载成功”，其实是伪成功。

所以这一步后来收紧成两种模式：

1. `metadata-only`
   只落本地目录和基础文件，不做真实下载。
2. `yt-dlp`
   显式指定后，才调用 `yt-dlp` 去做真实视频下载。

这样做的好处是：

- 默认行为更安全，不会产生误导性的假视频文件。
- 测试更稳定，不依赖外部下载器。
- 真正下载时，也保留了独立适配器入口，后续可替换成别的下载方案。

## 3. 命令怎么用

只生成本地 artifact，不下载真实视频：

```bash
node src/cli/download-bilibili.mjs --creator-id sample-bilibili-rss --limit 1
```

启用 `yt-dlp` 真实下载：

```bash
node src/cli/download-bilibili.mjs \
  --creator-id sample-bilibili-rss \
  --limit 1 \
  --download-mode yt-dlp
```

## 4. 这一步的验证方式

这一步用了两层验证：

### 4.1 单元测试

新增测试覆盖了两种情况：

1. 自定义 downloader 时，会写出 `downloaded` 状态。
2. `metadata-only` 模式下，不会伪造视频文件路径。

### 4.2 本地命令验证

至少验证：

```bash
npm test
npm run download:bili
```

其中 `npm run download:bili` 默认走 `metadata-only`，主要验证目录、元数据和 manifest 是否能正确落盘。

## 5. 当前边界

这一步还不是完整的“B站真实下载能力”，当前边界很明确：

- 还没有下载封面。
- 还没有把下载结果回写飞书。
- 还没有抽音频和转写。
- 还没有接评论抓取。
- 真实下载目前依赖本机 `yt-dlp`。

换句话说，这一步完成的是：

```text
下载链路骨架
```

不是：

```text
完整内容研究链路
```

## 6. 对后续阶段的帮助

这一步完成后，后面几个阶段就有了稳定入口：

1. P0-2 转写链路可以直接读取 `artifactDir` 里的视频文件。
2. P0-3 评论抓取可以直接复用同一条内容目录和 manifest。
3. P0-4 manifest 细化时，可以把下载、转写、评论统一成相同格式。

## 7. 复用方法

以后如果迁移别的平台，建议继续沿用这个顺序：

1. 先保留现有“发现内容”的适配器。
2. 单独增加 `download` 模块，而不是把下载逻辑塞进采集逻辑。
3. 先落 artifact 目录，再落真实下载。
4. 先支持 `metadata-only`，再接真实下载器。
5. 先让 manifest 可读，再做后续分析链路。
