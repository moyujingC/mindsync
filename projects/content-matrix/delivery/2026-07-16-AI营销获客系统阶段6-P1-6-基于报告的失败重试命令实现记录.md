# AI营销获客系统阶段 6 P1-6 基于报告的失败重试命令实现记录

本文记录 P1-6，也就是基于上一轮批量写入报告，只重试失败 enrichment 文件。

## 1. 这一步解决什么问题

P1-5 已经能把坏的 `enrichment.json` 隔离到报告的 `failed` 项里。

但当用户修复坏文件后，如果只能重新跑整个目录，会有两个问题：

- 成本高：目录越大，重复扫描越多。
- 操作不精确：用户只是想补救失败文件，不想重新处理所有内容。

所以这一步新增独立 retry 命令，输入上一轮报告，只读取其中失败项。

## 2. 当前实现

新增 job：

```text
writeFailedEnrichmentInsightsToFeishu(reportPath)
-> read previous report
-> extract items where status == failed
-> take enrichmentPath list
-> reuse enrichment path writer
-> write retry report
```

新增 CLI：

```bash
node src/cli/retry-failed-enrichment-insights.mjs \
  --report logs/enrichment-writes/2026-07-16.json \
  --retry-report logs/enrichment-writes/2026-07-16-retry.json
```

真实写飞书时追加：

```bash
--feishu config/feishu.local.json --mark-processed
```

## 3. 复用方式

这一步没有复制一套批量写入逻辑，而是把原来的目录批量处理抽成内部复用函数：

```text
writeEnrichmentPathsToFeishu(enrichmentPaths)
```

现在两条链路共用同一套逻辑：

- 目录批量：先 `findEnrichmentFiles(rootDir)`，再按路径列表处理。
- 失败重试：先从报告提取 failed 路径，再按路径列表处理。

这样后续去重、飞书写入、报告结构、`markProcessed` 回写保持一致。

## 4. 报告变化

retry 报告会保留：

- `retrySourceReportPath`：本次重试来自哪一份失败报告。
- `retryCount`：本次准备重试多少个失败文件。

如果上一轮报告没有 failed 项，会生成空报告：

```json
{
  "retryCount": 0,
  "enrichmentCount": 0,
  "inputCount": 0,
  "items": []
}
```

## 5. 验证方式

新增测试覆盖：

- 报告里同时有 `failed` 和 `written` 项时，只重试 `failed` 对应的 `enrichmentPath`。
- 重试报告会记录 `retrySourceReportPath`。
- 没有 `failed` 项时返回空结果，不触发飞书写入。

已验证：

```bash
npm test
```

结果：

```text
tests 74
pass 74
fail 0
```
