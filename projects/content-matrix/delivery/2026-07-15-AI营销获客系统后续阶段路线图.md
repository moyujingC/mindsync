后续不要直接追求“全平台全自动”。优先顺序是：

```text
飞书工作台稳定 -> 真实采集源扩展 -> 洞察选题入库 -> 内容生产闭环 -> 自动化运维
```

## 阶段 1：飞书工作台收口

### 目标

把当前 MVP 从“能跑通”提升到“每天可用”。

当前已经能写入 `内容更新`，但还需要让飞书成为可靠工作台，而不是只做数据落点。

### 主要任务

1. 去重改为优先查飞书
   - 当前主要依赖本地 `logs/content-store.feishu.json`。
   - 后续应先查飞书 `内容更新` 表的 `内容唯一键`。
   - 本地 store 只做缓存和运行加速。

2. 完善 `博主账号` 表字段
   - 账号类型：同行 / 对标 / 需求样本 / 灵感源 / 竞品。
   - 关注目的：选题 / 市场需求 / 竞品研究 / 表达学习 / 评论洞察。
   - 关联业务线：墨予镜 / 一镜一梳 / 知行AI服务。
   - 优先级：高 / 中 / 低。
   - 备注。

3. 完善 `内容更新` 表字段
   - 采集模式：daily / backfill / manual。
   - 是否进入选题池。
   - 原始数据摘要。
   - 采集失败原因。

4. 固定日常操作方式
   - `run-daily` 作为日常入口。
   - 每次运行写报告。
   - 失败账号标记为 `需人工处理`。

### 交付物

- 更新后的飞书字段结构。
- 采集器支持飞书去重。
- `run-daily` 真实飞书模式验证记录。
- 一份每日运行 SOP。

### 验收标准

1. 连续运行两次不会重复写入同一内容。
2. 删除本地 store 后，再运行仍不会因本地缓存缺失而重复写入飞书已有内容。
3. `博主账号` 中暂停账号不会被采集。
4. 失败账号会回写失败原因。

### 不做范围

- 不做评论采集。
- 不做抖音 / 小红书自动采集。
- 不做自动发布内容。

## 阶段 2：真实采集源扩展

### 目标

从当前 B 站样例和本地 RSS fixture，扩展到真实可用的数据输入。

### 主要任务

1. B 站真实 RSS
   - 支持 `数据源类型 = rss`。
   - 支持 RSSHub 或其他稳定 RSS。
   - 失败时记录状态，不无限重试。

2. 对标账号回溯采集
   - 新增 `backfill-creator` 命令。
   - 支持 `--limit` 和 `--since`。
   - 写入 `内容更新` 时标记 `采集模式 = backfill`。

3. 小红书 / 抖音半自动导入
   - 先不硬爬。
   - 支持人工粘贴链接、标题、正文、互动数到 JSON 或飞书。
   - 采集器负责标准化和去重。

4. 数据源状态管理
   - 每个账号记录 `数据源类型` 和 `数据源地址`。
   - 支持 `rss`、`rss-file`、`manual`。

### 交付物

- B 站真实 RSS 采集验证记录。
- `backfill-creator` 命令。
- 小红书 / 抖音人工导入模板。
- 数据源字段说明。

### 验收标准

1. 至少 3 个 B 站真实账号可被日常检查。
2. 一个对标账号可回溯最近 20-50 条内容。
3. 小红书 / 抖音至少能通过人工导入进入统一内容表。
4. 所有内容都有稳定 `内容唯一键`。

### 不做范围

- 不绕过平台风控。
- 不做大规模爬取。
- 不承诺平台覆盖完整性。

## 阶段 3：洞察与选题入库

### 目标

把系统从“采集工具”推进到“营销获客工作台”。

当前已经能本地生成选题候选，但还没有写入飞书 `洞察与选题` 表。

### 主要任务

1. 选题候选写入飞书
   - 将 `generate-topic-candidates` 输出写入 `洞察与选题`。
   - 状态默认 `待处理` 或 `待人工审核`。
   - 记录来源内容唯一键。

2. 增强候选字段
   - 目标读者。
   - 用户问题。
   - 服务方向。
   - 证据摘要。
   - CTA。
   - 建议动作。

3. 人工审核闭环
   - 人工在飞书里标记：已转选题 / 暂存 / 忽略。
   - 对 `知行AI服务` 有价值的选题，进入内容生产链路。

4. 与 `ai-service-studio` 对齐
   - 服务方向必须能映射到：
     - AI 工作流诊断
     - AI 文档 / 知识库整理
     - 企业 AI 落地 / FDE
     - 内容生产系统

### 交付物

- 选题候选写入飞书命令。
- `洞察与选题` 字段更新。
- 选题审核 SOP。
- 与 `ai-service-studio` 的服务方向映射表。

### 验收标准

1. 一次 `run-daily` 后，可生成并写入选题候选。
2. 每条候选都有来源内容链接。
3. 每条候选默认需要人工审核。
4. 至少 10 条候选中能筛出 3 条可进入内容草稿。

### 不做范围

- 不自动判断最终选题。
- 不自动生成发布稿。
- 不把评论或标题直接当市场结论。

## 阶段 4：内容生产闭环

### 目标

打通：

```text
洞察与选题 -> 草稿 brief -> 成稿 -> 配图 -> 排版 -> 发布准备
```

当前 `内容视觉工坊` 已经有草稿、配图、排版等能力，本阶段要把上游选题接进去。

### 主要任务

1. 生成草稿 brief
   - 输入：飞书 `洞察与选题` 中已审核选题。
   - 输出：目标读者、问题、证据、服务指向、内容角度、CTA。

2. 接成稿编辑链路
   - 生成草稿后进入已有成稿编辑流程。
   - 保留人工审核。
   - 避免 AI 腔和未经验证的服务承诺。

3. 接视觉链路
   - 根据成稿生成配图建议。
   - 接 `内容视觉工坊` 的图片、封面、排版能力。

4. 发布反馈记录
   - 记录发布平台、链接、发布时间。
   - 手动或半自动记录评论、私信、咨询、样本沟通。

### 交付物

- 选题到 brief 命令或脚本。
- 内容生产 handoff 模板。
- 发布反馈记录格式。
- 至少 3 条从飞书选题生成的内容草稿。

### 验收标准

1. 选题能生成结构化 brief。
2. brief 能进入现有成稿 / 配图 / 排版链路。
3. 发布后的反馈能回写到飞书或 `ai-service-studio`。
4. 至少 1 条内容带来真实外部反馈。

### 不做范围

- 不自动发布。
- 不自动私信。
- 不承诺内容带来成交。

## 阶段 5：自动化运维与复盘

### 目标

让系统进入稳定日常运行，而不是靠临时手动命令。

### 主要任务

1. 定时运行
   - 先接本地 cron。
   - 后续接 Automation Platform。
   - 每天固定时间执行 `run-daily`。

2. 运行报告
   - 保留 JSON 报告。
   - 生成每日摘要。
   - 记录新增内容数、失败账号、候选选题数。

3. 失败处理
   - 连续失败账号标记为 `需人工处理`。
   - 数据源失效时暂停采集。
   - 输出失败原因。

4. 周复盘
   - 每周统计：
     - 新增内容数。
     - 进入选题池数量。
     - 发布内容数量。
     - 外部反馈数量。
     - 进入样本沟通数量。

### 交付物

- cron 配置或 Automation Platform 配置。
- 每日摘要脚本。
- 周复盘模板。
- 失败账号处理 SOP。

### 验收标准

1. 连续 7 天自动运行。
2. 每天有运行报告。
3. 失败不会中断所有账号。
4. 周复盘能回答：哪些市场信号真正推进了 `知行AI服务` 获客。

### 不做范围

- 不做无人监管自动化。
- 不自动做销售判断。
- 不把所有评论都长期保存为个人画像。

## 总体优先级

推荐顺序：

1. 阶段 1：飞书工作台收口。
2. 阶段 3：洞察与选题入库。
3. 阶段 2：真实采集源扩展。
4. 阶段 4：内容生产闭环。
5. 阶段 5：自动化运维与复盘。

理由：

- 先把飞书主库和去重稳定下来，避免后续数据污染。
- 先让采集结果进入选题表，系统才真正服务获客。
- 平台扩展可以并行探索，但不应阻塞核心闭环。

## 下一次具体执行建议

下一次优先做：

```text
飞书去重 + 选题候选写入飞书
```

这一步完成后，系统会从：

```text
飞书博主账号 -> 内容更新
```

升级为：

```text
飞书博主账号 -> 内容更新 -> 洞察与选题
```

这是从采集工具到营销获客工作台的关键跃迁。
