# AI营销获客系统阶段 6 P0-4 manifest 统一实现记录

本文记录 `ai-boshu-crawler` 能力迁移第四步，也就是把下载、转写、评论三条链路的 manifest（运行清单）统一起来。

## 1. 为什么要做这一步

前面三步虽然都跑通了，但 manifest 还是分散写的：

- 下载自己写一个 JSON
- 转写自己写一个 JSON
- 评论还没有 manifest

这样后面做运维审计时，很难统一读。

所以这一步的目标不是“做大平台”，而是先把契约统一。

## 2. 这一步做了什么

新增：

- `src/utils/manifest.mjs`

这个工具先提供两类能力：

1. 统一写 manifest
2. 汇总 artifact 目录里的 manifest 覆盖情况

## 3. 统一后的 manifest 长什么样

当前统一结构：

```json
{
  "version": 1,
  "job": "download",
  "status": "ok",
  "generatedAt": "2026-07-16T00:00:00.000Z",
  "input": {},
  "output": {},
  "error": {
    "message": "..."
  }
}
```

好处是后面不管是哪条 job，都可以按同一方式读：

- 谁生成的
- 成功还是失败
- 输入是什么
- 输出是什么
- 出错原因是什么

## 4. 当前接入了哪些 job

这一步先接了三个：

1. `download`
2. `transcribe`
3. `comments`

其中：

- `download-manifest.json` 现在走统一写法
- `transcribe-manifest.json` 现在走统一写法
- `comments-manifest.json` 现在首次补上

## 5. 评论 manifest 是怎么接的

评论链路以前只有返回结果，没有 artifact 级别记录。

这一步增加了：

```bash
--artifact-dir <目录>
```

如果传入这个目录，就会在里面写：

- `comments-manifest.json`

这样同一条内容后面就能形成一组完整产物：

```text
download-manifest.json
transcribe-manifest.json
comments-manifest.json
```

## 6. ops-audit 这一步怎么升级

这一步没有重写整个 `ops-audit`，而是先加了最小增强：

- 原来继续看 `runs/` 目录
- 现在额外统计 artifact manifest 覆盖情况

新增输出：

- artifact 数量
- download manifest 数量
- transcribe manifest 数量
- comments manifest 数量
- enrich manifest 数量

这样后面运维上就能更快看出：

- 只是“日常任务跑了”
- 还是“下载 / 转写 / 评论链路真的留下了结构化证据”

## 7. 当前边界

这一步还是“统一 manifest 契约”，不是完整观测系统。

当前还没做：

- enrich manifest
- 按日期索引 manifest
- manifest 聚合报表
- failure review 直接读取 manifest

## 8. 当前验证方式

这一步增加了三类测试：

1. `writeJobManifest` 的统一结构测试
2. `comments-manifest.json` 写入测试
3. `ops-audit` 的 manifest 覆盖统计测试

## 9. 对下一步的帮助

这一步完成后，后面几个方向都更容易推进：

1. P1-1 enrich 可以直接沿用相同 manifest 契约。
2. `ops-audit` 后续可以逐步从“看 run report”升级成“看 job evidence”。
3. 失败复盘可以按 job 分类，不必再靠猜测。

## 10. 复用建议

以后新增 job，建议统一按这个顺序：

1. 先定义 input / output
2. 再决定成功状态和失败状态
3. 用统一 manifest 工具落盘
4. 最后再把它接进 ops 审计
