# AI 营销获客系统阶段 3-4 实现记录

本文记录第二轮后续阶段实现：

```text
洞察与选题去重 + 已审核选题生成 brief
```

对应路线图中的：

- 阶段 3：洞察与选题入库。
- 阶段 4：内容生产闭环。

## 本轮目标

上一轮已经把选题候选写入飞书 `洞察与选题` 表。本轮解决两个问题：

1. 重复执行同一份运行报告时，不能反复写入同一来源的候选。
2. 人工审核后的选题需要能交给后续成稿、配图、排版链路，而不是停在飞书表里。

## 实现步骤

### 1. 洞察候选去重

改动位置：

- `projects/content-matrix/tools/influencer-tracker/src/jobs/write-topic-candidates.mjs`
- `projects/content-matrix/tools/influencer-tracker/src/feishu/client.mjs`

实现方式：

1. 写入 `洞察与选题` 前，先读取飞书现有洞察记录。
2. 将飞书记录映射成内部 `insight` 对象。
3. 用下面的组合生成去重 key：

```text
来源内容 + 洞察类型
```

4. 新候选写入前也生成同样 key。
5. 如果飞书里已经存在同 key，跳过该候选，并在结果里记录 `duplicateCount`。

设计取舍：

- 当前不用标题去重，因为标题可能因模板调整变化。
- 当前不用独立 `candidateId` 字段，因为飞书表还没有这个字段。
- `来源内容 + 洞察类型` 对 MVP 足够稳定。后续如要更强去重，可给 `洞察与选题` 增加 `候选唯一键` 字段。

### 2. 已审核选题生成 brief

改动位置：

- `projects/content-matrix/tools/influencer-tracker/src/analysis/content-brief.mjs`
- `projects/content-matrix/tools/influencer-tracker/src/jobs/build-briefs.mjs`
- `projects/content-matrix/tools/influencer-tracker/src/cli/build-briefs.mjs`

实现方式：

1. 新增 `build-briefs` 命令，从飞书 `洞察与选题` 表读取记录。
2. 默认只筛选：

```text
状态 = 已转选题
```

3. 每条已审核洞察生成一份 Markdown brief。
4. brief 默认输出到：

```text
logs/briefs/
```

5. brief 包含：
   - 适用账号。
   - 目标读者。
   - 用户问题。
   - 证据摘要。
   - 内容角度。
   - 建议结构。
   - CTA。
   - 交接注意。

CLI 用法：

```bash
node src/cli/build-briefs.mjs --feishu config/feishu.local.json
```

如果要临时导出全部洞察，可用：

```bash
node src/cli/build-briefs.mjs --feishu config/feishu.local.json --all
```

设计取舍：

- 默认只处理 `已转选题`，避免未审核候选直接进入生产。
- `--all` 只用于调试或批量导出，不作为日常生产入口。
- brief 是交接稿，不是最终成稿，仍要求人工打开来源内容复核。

## 当前系统状态

现在系统已经跑通：

```text
飞书博主账号
-> 内容更新
-> 远端去重
-> 运行报告
-> 选题候选
-> 洞察与选题
-> 候选去重
-> 已审核选题
-> Markdown brief
```

这一步把系统从“选题池”推进到了“内容生产交接入口”。

## 残留风险

1. 飞书 `洞察与选题` 还没有 `候选唯一键` 字段，去重规则仍是组合推断。
2. brief 生成只是规则模板，不是完整写作策略。
3. 当前没有把 brief 自动交给成稿、配图、排版脚本。
4. 真实业务上仍需要人工审核来源内容和评论区，不能把单条内容直接当市场需求结论。

## 下一步建议

下一步优先做：

```text
brief -> 草稿入口 + 飞书状态回写
```

目标：

- 让 `已转选题` 生成 brief 后，可标记为 `已生成brief` 或类似状态。
- 将 brief 接到已有草稿 / 成稿流程。
- 保留人工审核点，避免自动生成发布稿。
