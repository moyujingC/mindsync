# AI 营销获客系统阶段 5 周复盘与失败处理实现记录

本文记录路线图阶段 5 的第二轮实现：

```text
每日运行日志 -> 周复盘
每日运行日志 -> 连续失败账号复核
```

## 本轮目标

上一轮已经有了每日摘要，但系统还缺两块运维能力：

1. 周视角统计。
2. 连续失败账号的人工处理入口。

这一轮就是把这两块补上。

## 实现步骤

### 1. 新增 weekly-review job

改动位置：

- `projects/content-matrix/tools/influencer-tracker/src/jobs/weekly-review.mjs`
- `projects/content-matrix/tools/influencer-tracker/src/cli/weekly-review.mjs`

实现方式：

1. 按开始日期和结束日期枚举一周日期。
2. 逐天读取 `logs/runs/YYYY-MM-DD/*.json`。
3. 读取对应日期的 `logs/topic-candidates/*.json`。
4. 扫描账号目录一周内生成的 `brief / 草稿 / 成稿` 文件。
5. 输出周复盘 Markdown 到：

```text
logs/weekly-reviews/<end-date>.md
```

当前周复盘能回答：

- 这一周跑了多少次。
- 新增了多少内容。
- 产生了多少选题候选。
- 产出了多少 brief / 草稿 / 成稿骨架。
- 哪些账号本周出现过失败。

### 2. 新增 failure-review job

改动位置：

- `projects/content-matrix/tools/influencer-tracker/src/jobs/failure-review.mjs`
- `projects/content-matrix/tools/influencer-tracker/src/cli/failure-review.mjs`

实现方式：

1. 回看最近 N 天的运行报告。
2. 以账号为单位统计“连续失败次数”。
3. 当连续失败次数达到阈值时，生成待人工处理清单。
4. 输出 Markdown 到：

```text
logs/failure-reviews/<date>.md
```

这样做的原因很直接：

- 不因为一次临时波动就误判账号失效。
- 先形成“人工复核名单”，再决定是否回写飞书。

### 3. 支持可选飞书回写

`failure-review` 支持：

```bash
--feishu config/feishu.local.json --mark-status
```

启用后会把达到阈值的账号回写为：

```text
最近状态 = 需人工处理
失败原因 = 连续失败 N 次：<最后一次错误>
```

这里没有直接做“自动停用”。

原因：

- 现阶段账号数量不大，误停用比漏标记更危险。
- `需人工处理` 更适合作为阶段 5 的第一版失败处理机制。

## 命令

周复盘：

```bash
node src/cli/weekly-review.mjs --start-date 2026-07-09 --end-date 2026-07-15
```

或：

```bash
npm run weekly:review
```

失败账号复核：

```bash
node src/cli/failure-review.mjs --date 2026-07-15 --lookback-days 7 --threshold 3
```

如果需要回写飞书：

```bash
node src/cli/failure-review.mjs \
  --date 2026-07-15 \
  --lookback-days 7 \
  --threshold 3 \
  --feishu config/feishu.local.json \
  --mark-status
```

## 残留风险

1. 还没有接本地 cron 或 Automation Platform。
2. 周复盘仍基于本地日志和账号目录，不包含发布后的真实私信、咨询和成交反馈。
3. `需人工处理` 还不是完整 SOP，只是第一版识别和回写入口。

## 下一步建议

下一步优先做：

```text
cron / Automation Platform 接入文档 + 失败处理 SOP 固化
```

原因：

- 现在运维报告已经成型。
- 下一步应该把“能手动跑”升级成“能按节奏稳定跑”。
