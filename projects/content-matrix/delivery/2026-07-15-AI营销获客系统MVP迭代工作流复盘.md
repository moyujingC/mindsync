# AI 营销获客系统 MVP 迭代工作流复盘

这份文档记录本次从想法到可运行 MVP 的完整迭代路径，方便以后复用到其他“本地工具 + 飞书多维表格 + AI 工作流”的项目。

## 1. 起点：先判断它不是单点工具

最初需求是：

- 关注一批博主。
- 每天检查抖音、小红书、B站是否更新。
- 有更新就采集数据。
- 支持对标账号批量采集。
- 用评论区归纳用户需求。

第一轮判断时，先把它落成 `博主更新追踪与对标账号采集系统`。这个判断能让范围变清楚，但仍然偏“采集工具”。

随后进一步收束为：

```text
市场需求调研 -> 选题判断 -> 草稿 -> 成稿 -> 配图 -> 排版 -> 发布 -> 反馈记录 -> ai-service-studio 获客依据
```

这个升级很关键。它把系统从“监控别人有没有更新”改成“服务 AI 服务获客的营销系统”。

复用规则：

- 如果一个工具的输出会影响业务获客、销售、产品验证，就不要只按工具定义。
- 先写清它服务哪个业务闭环。
- 上游采集只是模块，不是系统本身。

## 2. 先补 artifact，再写代码

本次先补了四类 artifact：

- `spec`：产品定义和飞书表结构。
- `task`：实现计划和里程碑。
- `qa`：验收基线。
- `delivery`：阶段交付说明。

随后新增总定义：

- `AI营销获客系统总定义`

这样做的好处：

- 明确飞书是运营主界面，本地 Markdown 是系统规则主库。
- 明确第一版不做评论区采集、不绕过平台风控。
- 明确 B 站先作为首个平台，抖音和小红书后置。
- 明确每一步验收口径，避免写完代码后不知道怎么算完成。

复用规则：

- 新能力如果会进入长期工作流，先补最小 artifact。
- artifact 不求长，但必须写清：目标、边界、数据流、验收标准。

## 3. MVP 先做本地可测，不先依赖外部平台

第一版工具目录：

```text
projects/content-matrix/tools/influencer-tracker/
```

先实现：

- 本地 JSON 博主清单。
- B 站 RSS 适配器。
- 本地 RSS fixture。
- dry-run。
- 本地去重。
- 单元测试。

这里没有一开始就接真实抖音、小红书，也没有一开始就依赖真实 RSSHub。

原因：

- 平台公开页面容易风控。
- RSSHub 或外网请求可能不稳定。
- 如果第一步就依赖外部平台，很难判断是代码错、权限错、网络错还是平台拦截。

本地 fixture 的作用：

- 保证 `npm test` 和 `npm run check` 随时可重复。
- 保证任何人拉代码后可以先理解数据结构和运行结果。
- 后续换真实数据源时，不影响核心编排逻辑。

复用规则：

- 任何采集类 MVP，先做本地 fixture。
- 第一版必须有 `dry-run`。
- 外部接口不稳定时，先把内部数据流跑通。

## 4. 先把飞书接入拆成两层

最初实现的是 Open API app secret 模式：

- `FeishuBitableClient`
- `config/feishu.example.json`
- `validate-config`
- `inspect-feishu`

这个方向适合后续服务器或长期自动化，但需要 `appId / appSecret / baseAppToken`。

用户随后提供了更适合本地协作的方式：

```bash
npx -y @larksuite/cli@latest
```

于是补了第二条接入路径：

- `LarkCliBitableClient`
- `config/feishu.lark-cli.local.example.json`
- 复用本机 `lark-cli` 用户登录态

这一步让工具可以用用户个人飞书身份读写表格，不需要另建服务端凭据。

复用规则：

- 本地个人工作台优先用 `lark-cli --as user`。
- 服务器自动化再考虑 app secret 或 bot 身份。
- 两种客户端应共用同一个业务接口：`listRecords / createRecords / updateRecord`。

## 5. 飞书表格也应由 Agent 创建

用户指出：“创建飞书多维表格不是你的事吗”。

这个反馈是正确的。

随后改为由 Agent 执行：

1. 检查 `lark-cli` 是否可用。
2. 检查 `whoami` 和 `doctor`。
3. 使用 `base +base-create --dry-run` 预览创建请求。
4. 使用 `base +base-create --as user` 创建 Base 和第一张表。
5. 使用 `base +table-create` 追加其他表。
6. 使用 `base +record-batch-create` 写入样例记录。
7. 使用采集器真实写入 `内容更新`。

最终创建结果：

- Base：`AI营销获客系统`
- URL：`https://ocn8icdz3ez3.feishu.cn/base/L2ghbMSJiaJrJKsUNMTcMLxInMb`
- `博主账号`：`tblShoJENEvdH1m6`
- `内容更新`：`tbl30niUryp9Sgp8`
- `评论样本`：`tbl2NTi3iiKXjliG`
- `洞察与选题`：`tblcgq7lKn2mXE6p`

复用规则：

- 如果已有 CLI 登录态，就不要让用户手工建表。
- 写操作前先 `--dry-run`。
- 创建成功后必须记录 base token、table id 和 URL。
- local 配置不提交，结构样例可以提交。

## 6. 真实写入前先做只读和样例验证

真实飞书接入分成几步：

1. `validate-config`
   - 只检查本地配置结构。
   - 不访问飞书。

2. `inspect-feishu`
   - 访问飞书。
   - 只读字段。
   - 检查配置字段名是否存在。

3. `record-batch-create`
   - 先写 1 条样例博主。

4. `check-updates --dry-run --feishu`
   - 从飞书读取博主。
   - 不写内容表。

5. `check-updates --feishu`
   - 真实写入内容表。

本次验证结果：

- 已从 `博主账号` 读取样例账号。
- 已使用本地 RSS fixture 生成 2 条内容。
- 已写入 `内容更新` 表 2 条记录。

复用规则：

- 真实写入前必须有只读验表。
- 写入前先写样例记录。
- 真实写入后立即用 list 命令核对。

## 7. 处理外部数据源不稳定

真实 B 站公开页面和 API 容易遇到验证码、412、fetch failed。

本次处理方式：

- 不绕过风控。
- 不把失败伪装成成功。
- 给 `博主账号` 增加：
  - `数据源类型`
  - `数据源地址`
- 支持：
  - `rss`
  - `rss-file`

这样同一条博主记录可以在真实 RSS 和本地 fixture 之间切换。

复用规则：

- 平台采集不要一开始硬爬。
- 先允许人工配置数据源。
- 每个账号应该能记录自己的数据源类型和数据源地址。

## 8. 从采集推进到选题候选

采集工具如果只写入内容表，还不算营销获客系统。

因此继续补了：

- `run-daily`
  - 每日运行包装。
  - 生成 JSON 运行报告。

- `generate-topic-candidates`
  - 从运行报告提取新增内容。
  - 生成待人工审核的选题候选。
  - 初步推断服务方向：
    - `AI 工作流诊断`
    - `AI 文档 / 知识库整理`
    - `内容生产系统`
    - `企业 AI 落地 / FDE`

当前选题候选仍是规则初筛，不是最终洞察。

复用规则：

- 自动化输出默认应是 `待人工审核`。
- 不把规则推断包装成市场结论。
- 下一步应写入飞书 `洞察与选题` 表，而不是长期停留在本地 JSON。

## 10. 本次踩坑

### 10.1 不应把建表交还给用户

一开始把“创建飞书多维表格”列成用户待办，这是不完整交付。

修正：

- Agent 应先检查本机工具和授权。
- 如果有权限，直接创建。
- 如果缺权限，明确卡在哪个授权项，而不是泛泛说“你去建表”。

### 10.2 Open API 和 lark-cli 是两条不同接入路径

Open API app secret 适合服务端自动化。

`lark-cli --as user` 适合本机个人工作流。

修正：

- 保留两种客户端。
- 对采集任务暴露同一接口。

### 10.3 lark-cli record-list 输出不是普通 records 列表

`record-list` 返回：

- `fields`
- `data`
- `record_id_list`

而不是 `{ fields: {...} }` 结构。

修正：

- 在 `LarkCliBitableClient` 中把矩阵转成统一 record 结构。

### 10.4 字段类型会被 CLI 转换

例如 `url` 字段实际可能以 text 形式出现。

修正：

- 写入层不要强依赖复杂 URL 对象。
- `lark-cli` 模式按 happy path 写字符串。

### 10.5 运行产物不能提交

`run-daily` 和 `generate-topic-candidates` 会生成日志。

修正：

- `logs/` 加入 `.gitignore`。
- local 配置也加入 `.gitignore`。

## 11. 下次复用模板

类似项目可以按这条顺序推进：

1. 把口头需求改写成业务闭环。
2. 补最小 `spec / task / qa / delivery`。
3. 做本地 fixture。
4. 做 dry-run。
5. 做本地测试。
6. 接飞书配置校验。
7. 接飞书只读验表。
8. 用 `lark-cli --as user` 创建 Base 和表。
9. 写入样例记录。
10. 跑通真实读取。
11. 跑通真实写入。
12. 补运行报告。
13. 补选题 / 洞察候选。
14. 记录真实 base URL、table ID、验证命令和踩坑。

## 12. 下一步建议

本系统下一步应优先做：

1. 选题候选写入飞书 `洞察与选题` 表。
2. 去重改成优先查飞书 `内容唯一键`，本地 store 只做缓存。
3. 增加 `backfill-creator`，支持对标账号回溯。
4. 增加人工导入小红书 / 抖音链接的半自动流程。
5. 再评估真实评论区采集。
