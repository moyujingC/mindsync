# AI营销获客系统阶段 6 P0-3 B站评论入库实现记录

本文记录 `ai-boshu-crawler` 能力迁移第三步，也就是：

```text
评论样本
-> 标准化
-> 去重
-> 写评论样本表
```

## 1. 这一步解决什么问题

前两步解决的是：

- 有没有新内容
- 能不能拿到内容文本

但真正做市场需求调研时，最直接的信号很多来自评论区。

所以这一步先不做复杂分析，而是先把评论作为结构化样本入库。

## 2. 当前实现策略

这一步先做最小、可验证、可幂等的链路：

```text
fixture 评论输入
-> 标准化 comment 对象
-> 生成 commentUniqueKey
-> 去重
-> dry-run / 飞书写入
```

这里故意没有把“真实网络抓取”一起塞进来。

原因是：

- 抓取方式后面还可能变化。
- 先把评论对象和入库契约定稳，更利于后续替换抓取源。
- 这样测试也更稳定。

## 3. 新增了什么

新增文件：

- `src/jobs/sync-bilibili-comments.mjs`
- `src/cli/sync-bilibili-comments.mjs`
- `tests/sync-bilibili-comments.test.mjs`
- `fixtures/bilibili-comments.example.json`

同时补齐了：

- `config/feishu.example.json` 的 `comments` 表配置
- Feishu 评论字段映射
- `lark-cli` 写入字段排序

## 4. 评论对象怎么定义

当前最小字段：

- `commentUniqueKey`
- `contentUniqueKey`
- `commentText`
- `commentedAt`
- `likeCount`
- `userHandle`
- `demandType`
- `sentiment`
- `insightStatus`

其中最重要的是 `commentUniqueKey`。

当前规则：

```text
<platform>:<contentUniqueKey>:<commentId>
```

这样后面重复跑时，能稳定去重。

## 5. 当前命令怎么跑

本地 dry-run：

```bash
node src/cli/sync-bilibili-comments.mjs \
  --input fixtures/bilibili-comments.example.json \
  --dry-run
```

或者直接：

```bash
npm run comments:bili
```

真实飞书写入：

```bash
node src/cli/sync-bilibili-comments.mjs \
  --input fixtures/bilibili-comments.example.json \
  --feishu config/feishu.local.json
```

## 6. 这一步做了哪些幂等处理

当前会在真实飞书模式下先读取 `评论样本` 表里的 `评论唯一键`。

如果同一条评论已经存在：

- 不重复写入
- 计入 `duplicateCount`

这和内容入库的幂等思路保持一致。

## 7. 当前验证方式

测试覆盖了三层：

1. 评论标准化后，能生成稳定 comment key。
2. 评论字段能正确映射到飞书表结构。
3. 重复运行时，已存在评论不会重复写入。

## 8. 当前边界

这一步还是“评论入库”，不是“评论洞察系统”。

当前还没做：

- 真实 B站评论 API / 页面抓取
- 翻页抓取
- 热评 / 全量评论策略
- 评论自动打标签
- 评论直接转洞察

## 9. 对后面的帮助

这一步做完后，后面就能继续往前推：

1. P0-4 manifest 公共抽象，可以把评论 job 也纳入统一运行记录。
2. P1-1 enrich 可以同时读取 transcript 和 comments。
3. 后面做需求洞察时，可以直接从评论样本表筛选高频问题。

## 10. 复用建议

后面迁其他平台时，建议继续沿用这套顺序：

1. 先把评论对象标准化。
2. 先把去重键定稳。
3. 先跑 dry-run。
4. 最后再替换成真实抓取源。
