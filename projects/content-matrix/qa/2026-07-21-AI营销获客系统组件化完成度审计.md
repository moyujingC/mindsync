## 本次真实联调

在不写入飞书或本地台账的条件下执行：

```bash
TIKHUB_API_KEY='[redacted]' npm run research:run -- \
  --template enterprise_ai_service \
  --mode search \
  --platform xiaohongshu \
  --keyword '企业 AI 工作流' \
  --limit 1 \
  --dry-run
```

首次搜索探针结果：TikHub 返回 `402`，错误为“check account balance or endpoint entitlement”。充值前该 Key 未具备接口的可用余额或套餐权限；当时使用 `--dry-run`，没有写入飞书、研究台账或本地去重库。

2026-07-21 又以同一凭据运行只读详情探针：

```bash
TIKHUB_API_KEY='[redacted]' npm run preflight:readiness -- \
  --feishu config/feishu.local.json \
  --probe \
  --platform xiaohongshu \
  --share-url 'https://www.xiaohongshu.com/explore/6853a16c000000001c032269'
```

结果：`tikhubKey: true`、飞书配置校验通过，但详情接口同样返回 `402`。该探针不写飞书、研究台账或本地去重库；当时外部阻塞可确认是 TikHub 小红书详情/搜索接口的余额或套餐权限，不是本机 Key 缺失或飞书配置错误。

充值后真实联调结果：小红书详情探针返回成功。旧分享链接的业务数据为空，因此未用于写入；随后以关键词“企业 AI 工作流”运行真实搜索和评论采样。真实响应新增一层 `code/success/data` 包装，搜索内容位于 `data.items[].note`，且指标字段使用 `comments_count`、`collected_count` 等名称，已在标准化组件中兼容。

先以 `--dry-run --limit 1 --comment-limit 1` 验证：返回 1 条内容、1 条评论、2 次 TikHub 调用，`outputPath: null` 且飞书未同步。再运行请求 ID 为 `research-2026-07-21-enterprise-ai-search-001` 的真实研究写入：飞书“研究请求”记录创建成功；只读复核确认博主、内容、评论和研究请求四表均命中对应的外部 ID、唯一键或请求 ID。候选状态仍为“待人工审核”，未自动转草稿、发布或服务结论。

同日完成抖音关键词“企业 AI 工作流”的真实联调。搜索响应顶层 `data` 为卡片数组，视频对象在 `aweme_info`；标准化组件已兼容该包装，并在入库前移除分享链接查询参数。默认评论端点 `/api/v1/douyin/app/v3/fetch_video_comments` 以当前 `POST { content_id, cursor }` 合同实际返回 HTTP 405。为避免猜测接口并重复消耗调用额度，研究请求提供 `--no-comments` 显式覆盖模板的评论默认值。使用该降级模式写入请求 `research-2026-07-21-enterprise-ai-douyin-search-001` 后，只读复核确认飞书博主、内容和研究请求表均已命中；内容唯一键为 `douyin:7660701321988803867`。该请求无评论样本，候选保持“线索 / 假设 / 待人工审核”，不得作为评论需求结论。

公众号和视频号关键词搜索也已按 TikHub OpenAPI 的真实合同完成联调。公众号使用 `POST /api/v1/wechat_search/v2/fetch_search` 及 `business_type: article`；视频号使用 `POST /api/v1/wechat_search/v2/fetch_search_videos`。公众号结果位于 `data.results.data[].items[]`，视频号结果位于 `data.results.data[].subBoxes[].items[]`，两种包装、游标和标题高亮均已在标准化层覆盖。受控写入请求分别为 `research-2026-07-21-enterprise-ai-wechat-mp-search-001` 与 `research-2026-07-21-enterprise-ai-wechat-channels-search-001`；飞书内容表和研究请求表均已按唯一键或请求 ID 只读复核。搜索响应只提供来源显示名，不提供账号追踪所需的公众号 `gh_username` 或视频号 `finder username`，因此没有创建博主账号记录，也不将来源显示名伪装为账号标识。

后续检查 TikHub OpenAPI 发现，微信详情、账号和评论不能沿用通用 `content_id`/`creator_id` 参数：公众号详情和评论都必须 `POST` 并传文章链接，账号列表必须传 `gh_username`；视频号详情必须传短链接、数字 `object_id` 或短期 `export_id`，账号列表必须传 `finder username`，评论必须传数字 `object_id`。客户端已按该合同改为显式请求体和输入校验，搜索页的显示名、非数字 `docID` 不会触发无效调用。该改动已由 140 项自动化回归覆盖；因当前样本没有这些正式输入，详情、账号与评论尚未执行真实请求。

## 恢复条件与下一步

1. 向 TikHub 官方文档或支持确认抖音评论的正确路径、方法和请求字段；取得合同后再做一次受控 `dry-run`、字段校验和评论入飞书验证。
2. 为小红书补详情、账号列表和评论的脱敏真实合同样本，运行 `validate:tikhub-contracts` 使四类覆盖通过；复核旧分享链接为空的原因。
3. 用有效文章链接、公众号 `gh_username`、视频号数字 `object_id` 或短链接和 `finder username`，为公众号和视频号补详情、账号和评论的真实合同；搜索响应不具备这些输入时不猜测。
4. 人工确认 `research-2026-07-21-enterprise-ai-search-001` 的候选是否进入选题；若进入，生成草稿、完成真实发布并填写反馈记录。
5. 累积 3-5 轮真实闭环后，再评估每周 Agent Loop。
