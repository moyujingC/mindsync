# 内容视觉工坊 V2.8 主链路收束方案

## 1. 背景

- 项目：内容视觉工坊 V2
- 当前阶段：从多能力原型收束为可验证主闭环
- 上游输入：
  - V2.7 Skill Architecture
  - V2.7 Skill Dependency Matrix
  - V2.7 Skill State Inventory
  - 当前产品判断：先验证“文章到知识卡”，不继续横向扩展页面和能力

V2 当前不是底座错误，而是主线过散。已有代码、接口、状态和页面都能复用，下一步不新开完整 V3，先在 V2 里做一次 V2.8 主链路收束。

V2.8 的目标不是把 V2.7 里所有 skill 做完，而是把产品从“很多能力的集合”收束成一个能跑通、能验证、能复用的 AI 内容产品闭环。

## 2. 问题定义

- 用户是谁：
  - 中文内容创作者
  - 需要把一篇成稿快速拆成可发布的知识卡图组的人
  - 也包括未来通过 agent 调用同一套能力的自动化工作流

- 用户卡点是什么：
  - 文章已经有了，但不知道如何稳定拆成 3-5 张知识卡
  - AI 拆解结果看起来像“自动生成”，用户不知道为什么这样拆
  - 用户想修改卡片标题和摘要，但不希望重新推倒整篇文章
  - 图片生成失败、旧结果过期、单卡重生成等状态不够清楚
  - 页面很多，但用户难以判断下一步应该点什么

- 为什么现在解决：
  - 当前系统已经具备真实导入、拆解、知识卡生成和部分状态记录
  - 继续做封面、金句卡、正文配图、公众号排版，会继续稀释主闭环
  - 先把一条主链路跑稳，才能判断后续是继续 V2.9 扩展，还是开 V3 做干净版重构

## 3. V2.8 唯一主线

当前唯一主线固定为：

`导入一篇文章 -> AI 拆解出 3-5 张知识卡计划 -> 用户确认 / 修改 -> 生成知识卡图片 -> 用户选择 / 重生成 -> 导出`

这条主线必须满足：

1. 用户能导入一篇完整文章。
2. 系统能拆出 3-5 张知识卡计划。
3. 用户能看懂每张卡为什么被拆出来。
4. 用户能修改卡片标题和摘要。
5. 用户能生成至少 1 张知识卡图片。
6. 用户能对单张卡重生成，而不是只能全量重来。
7. 用户能看懂失败原因和 stale 状态。
8. 用户能导出已选择的知识卡结果。

## 4. 能力分级

### 4.1 主链路能力

| 能力 | V2.8 状态 | 说明 |
| --- | --- | --- |
| `article_ingest` | 主链路 | 负责文章导入、标题和正文确认 |
| `content_planning` | 主链路 | 负责拆出 3-5 张知识卡计划 |
| `knowledge_card_generation` | 主链路 | 负责知识卡图片生成、单卡重生成、结果绑定 |
| `distribution_packaging` | 主链路 | 负责导出已确认的知识卡结果 |
| `theme_mounting` | 支撑主链路 | 只保留必要风格选择，不扩展风格资产深层管理 |
| `activity_logging` | 支撑主链路 | 只记录主链路事件，不扩展完整审计页 |

### 4.2 暂缓能力

| 能力 | V2.8 状态 | 暂缓原因 |
| --- | --- | --- |
| `quote_selection` | 暂缓 | 金句卡不进入本轮闭环 |
| `quote_card_generation` | 暂缓 | 会分散知识卡主链路 |
| `cover_generation` | 暂缓 | 封面不是“文章到知识卡”闭环的必要步骤 |
| `inline_illustration_generation` | 暂缓 | 正文配图依赖公众号排版，本轮不做 |
| `wechat_layout_rendering` | 暂缓 | 公众号排版先保持可用，不继续加深 |

### 4.3 未来能力

| 能力 | 未来恢复条件 |
| --- | --- |
| 金句卡 | 知识卡闭环稳定后，再作为第二条导出资产链 |
| 封面 | 知识卡导出稳定后，再接入“公众号发布包” |
| 正文配图 | 公众号排版链恢复时再做 |
| 风格资产深度管理 | 当知识卡风格选择和复用成为真实瓶颈时再做 |
| 同步记录扩展 | 当多轮生成和多人/agent 协作需要审计时再做 |

本轮判断标准：

- 如果一个功能不能服务“文章到知识卡”闭环，本轮不做。
- 如果一个页面不能让用户更好确认、修改、生成或导出，本轮不优化。

## 5. 方案比较

| 方案 | 做法 | 代价 | 判断 |
| --- | --- | --- | --- |
| 新开 V3 | 重建目录、重做工作台、重写主链路 | 容易变成高质量重来，旧问题可能复现 | 暂不采用 |
| V2.7 继续横向补齐 | 继续补封面、配图、公众号排版、风格资产 | 每条链都有价值，但没有一个闭环足够稳 | 停止推进 |
| V2.8 主链路收束 | 在 V2 基础上冻结横向能力，只验证文章到知识卡 | 需要暂时接受其他页面“不够完整” | 当前采用 |

当前推荐方案：

在 V2 里做 V2.8 收束，不新开完整 V3。

推荐原因：

- V2 已经有真实代码、真实接口和状态基础。
- 当前问题是主线散，不是方向错。
- 先做减法版产品验证，能避免把重构当成逃离复杂度。
- V2.8 验证后，如果代码结构确实拖不动，再开 V3 更稳。

## 6. 工作台信息架构

V2.8 的工作台不再按页面能力堆叠，而按用户完成主链路所需确认动作组织。

### 6.1 左侧：文章输入和拆解参数

目标：

- 让用户确认“系统正在处理哪篇文章”。

包含：

- 文章标题
- 正文输入 / Markdown 导入
- 字数、段落数、标题层级摘要
- 拆解参数：
  - 卡片数量：3-5 张
  - 拆解策略：默认自动

必要状态：

- 未导入文章
- 已导入但未拆解
- 文章变更后，旧拆解计划 stale
- 文章解析失败

### 6.2 中间：AI 拆解计划和用户确认

目标：

- 让用户看懂 AI 为什么这样拆，并能改计划。

包含：

- 3-5 张知识卡计划
- 每张卡：
  - 标题
  - 摘要
  - 来源段落 / 理由
  - 当前确认状态
  - stale 标记
- 用户操作：
  - 修改卡片标题
  - 修改卡片摘要
  - 确认单卡
  - 重新拆解整篇文章

必要状态：

- 拆解中
- 拆解失败
- 拆解成功但未确认
- 用户已修改，图片结果需重生成

### 6.3 右侧：生成结果、重生成、导出

目标：

- 让用户对每张卡完成“生成 -> 选择 -> 重生成 -> 导出”。

包含：

- 每张卡的生成结果
- 当前选中图片
- 单卡重生成
- 全部已确认卡生成
- 失败原因
- 导出入口

必要状态：

- 未生成
- 生成中
- 单卡失败
- 部分成功
- 已生成但内容 stale
- 已选择可导出

### 6.4 底部或侧栏：任务状态 / 历史记录 / stale 提醒

目标：

- 让用户理解当前系统是否可继续操作。

包含：

- 当前主链路进度
- 最近事件：
  - 导入文章
  - 完成拆解
  - 修改卡片
  - 生成成功 / 失败
  - 导出
- stale 汇总：
  - 哪些旧图还在
  - 哪些旧图不再匹配当前卡片

## 7. 四个核心 Skill Contract

### 7.1 `article_ingest`

| 字段 | Contract |
| --- | --- |
| 目标 | 把一篇文章导入为稳定输入 |
| 输入 | Markdown 文本、粘贴正文、标题 |
| 输出 | `currentArticle`，包含 `title`、`body`、`sourceMeta` |
| 触发者 | 用户 |
| 是否需要用户确认 | 需要，至少确认标题和正文存在 |
| 失败展示 | 显示导入失败原因，例如空正文、解析失败 |
| stale 条件 | 无。它是上游真理源，变化会让下游 stale |
| 消费者 | `content_planning` |

### 7.2 `content_planning`

| 字段 | Contract |
| --- | --- |
| 目标 | 把文章拆成 3-5 张知识卡计划 |
| 输入 | `currentArticle.title`、`currentArticle.body`、卡片数量范围、拆解策略 |
| 输出 | `cardPlan[]`，每项包含标题、摘要、来源依据、解释理由 |
| 触发者 | 用户点击拆解，或文章导入后用户确认触发 |
| 是否需要用户确认 | 需要。生成图片前必须确认或修改卡片计划 |
| 失败展示 | 显示拆解失败原因，保留文章输入，不清空工作台 |
| stale 条件 | 标题变化、正文变化、拆解参数变化 |
| 消费者 | `knowledge_card_generation` |

### 7.3 `knowledge_card_generation`

| 字段 | Contract |
| --- | --- |
| 目标 | 为已确认的卡片计划生成知识卡图片 |
| 输入 | `cardPlan[i]`、当前风格、尺寸预设 |
| 输出 | `imageResult`，绑定到 `cardPlanItem.id` 或稳定指纹 |
| 触发者 | 用户点击生成单卡 / 生成全部已确认卡 |
| 是否需要用户确认 | 需要。未确认卡片不默认生成 |
| 失败展示 | 单卡显示失败原因，不阻塞其他卡片 |
| stale 条件 | 卡片标题变化、卡片摘要变化、风格变化、拆解 revision 变化 |
| 消费者 | `distribution_packaging` |

### 7.4 `distribution_packaging`

| 字段 | Contract |
| --- | --- |
| 目标 | 导出用户选择的知识卡结果 |
| 输入 | 已生成且被选择的图片结果 |
| 输出 | 下载文件、图片包、导出记录 |
| 触发者 | 用户 |
| 是否需要用户确认 | 需要，至少确认导出哪些图片 |
| 失败展示 | 显示导出失败原因，保留已生成图片 |
| stale 条件 | 上游图片或卡片内容变化后，需要重新导出 |
| 消费者 | 用户，未来也可被 agent 调用 |

## 8. 预留 Agent 接口

V2.8 不实现完整 agent，但要把能力接口写成未来可调用的形式。

建议保留三个能力函数边界：

```ts
planArticleCards(article) -> cardPlan
generateKnowledgeCard(cardPlanItem, style) -> imageResult
exportCardPack(selectedImages) -> package
```

设计原则：

- UI 和未来 agent 使用同一套状态。
- UI 和未来 agent 复用同一套能力 contract。
- 本轮不做 agent 调度器，不做多步自动执行。
- 本轮只保证能力边界清楚，未来能接。

## 9. 第一条纵切面

V2.8 第一轮实现只做一个最小纵切面：

`导入文章 -> 拆解计划 -> 生成 1 张知识卡 -> 导出`

### 9.1 先 mock

先用假数据跑通完整交互：

1. 导入一篇文章。
2. 生成 3 张模拟知识卡计划。
3. 用户修改第一张卡标题和摘要。
4. 生成第一张模拟图片结果。
5. 导出第一张图片。

验收重点：

- 用户路径顺不顺。
- stale 提醒是否看得懂。
- 单卡生成和导出是否足够明确。

### 9.2 再接真实 `content_planning`

替换模拟拆解为真实 AI 拆解。

验收重点：

- 拆解结果稳定输出 3-5 张。
- 每张卡有可读的拆解理由。
- 用户能在生成前修改。

### 9.3 再接真实 `knowledge_card_generation`

替换模拟图片为真实知识卡生成。

验收重点：

- 单卡失败不影响其他卡。
- 单卡重生成能保留历史。
- 修改卡片后旧图会 stale。

### 9.4 最后补导出

导出先只支持已选择知识卡图片。

验收重点：

- 用户知道导出了哪些图。
- stale 图片不能默认混入“当前有效导出”。
- 导出失败不会清空结果。

## 10. 本轮明确不做

V2.8 不做：

- 新开 V3 目录
- 新增完整页面
- 金句卡生成
- 封面生成深化
- 正文配图生成深化
- 公众号排版深化
- 风格资产页深度管理
- 同步记录页扩展审计能力
- 完整 agent 调度器
- 同时改 UI、prompt、接口和状态模型

允许保留：

- 现有入口
- 现有历史结果展示
- 现有页面最小可用能力

但这些不是本轮优化对象。

## 11. 验收标准

V2.8 主链路验收标准：

1. 用户能导入一篇 `墨予镜` 成稿。
2. 系统能拆出 3-5 张知识卡计划。
3. 用户能看懂每张卡的标题、摘要和拆解理由。
4. 用户能修改至少一张卡的标题和摘要。
5. 系统能生成至少 1 张知识卡图片。
6. 用户能对单张卡重生成。
7. 修改卡片后，旧图片会显示 stale，而不是伪装成当前有效结果。
8. 生成失败时，错误显示在对应卡片上，不让用户以为整个工作台坏了。
9. 用户能导出已选择的知识卡图片。
10. 金句卡、封面、正文配图、公众号排版不会抢占主链路操作层级。

## 12. 下一步 Handoff

建议下一步交给 Engineer。

实现顺序：

1. 按本方案冻结导航和页面优先级。
2. 重排工作台为左中右主链路结构。
3. 用 mock 数据跑通第一条纵切面。
4. 接真实 `content_planning`。
5. 接真实 `knowledge_card_generation`。
6. 补最小 `distribution_packaging`。

每次实现前只回答四个问题：

1. 这次改动是否服务“文章到知识卡”？
2. 它属于四个核心 skill 里的哪一个？
3. 用户是否因此更容易确认、修改、生成或导出？
4. 它的 stale 条件是什么？

如果回答不清，本轮不做。
