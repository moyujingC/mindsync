# 内容工作流系统重做 Framing SPEC

## 1. V1/V2 闲置根因诊断（已验证与修正）

handoff 的初步诊断（"先造了工具，而工作流本身从未被手动跑通过"）**成立，但需修正一处、补充两条**。

### 1.1 确认成立：发布链路从未被跑通

- 2026-06-06 至 07-22，[墨予镜账号目录](../accounts/墨予镜/)积压 10+ 篇成稿（含配图版与公众号成品 HTML），但 [feedback/](../accounts/墨予镜/feedback/) 为空，账号至今未起号。
- 2026-07-21 至 07-30 约 50 个 commits 全部投入采集/情报侧（TikHub、链接收件箱、Hermes、Creator Worker、评分筛选、历史回溯），同期发布侧产出为零。
- [内容方法验证实验闭环实现记录](../delivery/2026-07-30-内容方法验证实验闭环实现记录.md) 明确记录：回流表"未写入模拟发布数据；当前表保持空白"。

### 1.2 修正：不是"每一步都和真实动作对不上"

TikHub 采集、链接收件、视频文字稿均有真实验收记录，确实被使用过。更准确的诊断是：**"情报→选题"段被过度验证，"选题→成稿→发布→回流"段从未闭环**。系统优化的是输入端，瓶颈一直在输出端。

### 1.3 补充根因 A：账号定位反复重构，以"再设计一轮"替代"先发一条"

6 月（个人 AI 工作系统）→ 7 月（AI 营销获客）→ 8-01（企业 FDE）三次重定位，每次都触发新一轮 spec 与选题设计，发布被无限推迟。定位不稳定导致选题标准与工具需求同步摇摆。

### 1.4 补充根因 B：工作台底座运维成本与单人使用规模不匹配

7 月下旬大量 fix commits 是路由错乱、环境隔离、限流重试等系统运维问题。链路（iPhone 快捷指令→飞书→采集→评分→研究→选题）离"今天发一条小红书"太远，注意力被系统运维吃掉。

### 1.5 对视觉工坊 V1/V2 的具体结论

配图、排版、金句卡是真实痛点，但它服务"已有成稿之后的加工环节"；瓶颈在没有持续产出的成稿流。**工具建在了链路中段，而链路两端（持续写作、真实发布）从未跑通。**

### 1.6 由此推出的重做原则

1. 第一里程碑内**不允许任何采集/情报类工具开发**——该段已过剩。
2. 工具边界只围绕一个问题切："哪个环节正在阻止本周发出第一条内容？"
3. 飞书工作台降级为可选；默认起点是"仓库文件 + Claude Code skills + 手动发布"。
4. 回流表沿用 [2026-07-30 实验闭环规格](./2026-07-30-内容方法验证实验闭环规格.md) 的最小字段合同（设计本身无问题，问题是从未被填过），第一天手动填写。

## 2. 试点账号与工作流阶段定义（开放问题 1-2，已决策）

**试点账号：墨予镜。** 依据：

- 离"能持续产出的内容源"最近：选题源已收敛到「基于 ai-service-studio 纵向复盘与既有资料做判断、讲观察」的路线（首篇公众号主文《企业上AI，第一步从来不是选工具》已打磨至润色版 v2），另有存量成稿与写作规则。
- 与项目 B/C 联动最强：墨予镜是企业 AI 服务获客入口，起号后直接为项目 B（客服 Agent）提供真实流量。
- 唯一有最新定位 spec 的账号（[2026-08-01 企业 FDE 定位](./2026-08-01-墨予镜-企业FDE账号定位-SPEC.md)）。

**平台策略：小红书首发 + 公众号同步。** 小红书承担冷启动触达与快速反馈；公众号同步发深度长文作服务承接。同一批选题双平台复用，边际成本低。

### 2.1 六阶段在里程碑 1 的形态

| 阶段 | 里程碑 1 形态 | 载体 | 是否进自建工具 |
| --- | --- | --- | --- |
| 情报 | 手动刷 + 存量采集组件按需调用 | 手动 + influencer-tracker（存量，不新建） | 否 |
| 选题 | AI 辅助 | 选题提案 + 周复盘会话 | 否 |
| 草稿 | AI 辅助 | Claude Code skills + 账号写作规则 | 否 |
| 成稿 | 手动确认 + skill 打磨；封面配图手动 | 账号目录 markdown | 否（候选，见 §4 触发器） |
| 发布 | 手动 | 平台后台 + 发布 checklist | 否（平台无可用 API，合规上不自动发布） |
| 数据回流 | 手动填写 | 仓库回流表 + 周复盘 | 否 |

### 2.2 质量门（企业级标准的落点）

- **成稿→发布**：对照 [FDE 定位 spec](./2026-08-01-墨予镜-企业FDE账号定位-SPEC.md) 的"可说/暂不说"边界、账号写作规则（先正面给判断）、内容治理合规（不承诺效果、不伪造案例）逐项检查后才可发布。
- **发布→回流**：每条发布当天在回流表建行；无记录视为未发布。
- **周复盘**：每周一次，复盘结论必须落到"下周选题调什么"，只改一个主要变量。

## 3. 第一里程碑定义

**目标：两周内（2026-08-17 至 08-31）墨予镜发出第一批内容。**

通过标准：

1. 小红书 ≥3 条、公众号 ≥1 条真实发布（合计 ≥5 条）。
2. 每条发布在回流表有完整记录（含观察期数据）。
3. 第一周结束完成一次复盘，并产出第二轮选题调整（写明依据哪条回流信号）。
4. 全程未新建任何采集/情报类工具；任何工具开发需求以"触发器证据"形式记录，不直接开工。

首周发布组合：公众号主文 1 篇（《企业上AI，第一步从来不是选工具》，已打磨至润色版 v2）+ 小红书 2 条。

## 4. 工具边界定义（开放问题 3，已决策）

**默认偏见：能不进工具的不进工具。里程碑 1 预建工具数为零。**

里程碑 1 的全部能力由三层承接：

1. **手动**：发布、配图初版、回流表填写、情报浏览。
2. **Claude Code skills**：选题生成、草稿、成稿打磨、复盘（复用账号写作规则与存量编辑 skill）。
3. **存量工具（只调用，不开发）**：influencer-tracker 采集组件按需使用。

**工具开发触发器（唯一例外通道）**：某阶段手动跑通 ≥2 次、且被周复盘识别为"最痛环节"后，才允许为该阶段立项工具。当前候选首位是小红书图文卡制作（高频重复动作），但必须先手动发出第一批卡片证明它是瓶颈。

每个工具任务开工前必须回答："它服务的阶段是否已手动跑通过？"答不上就先手动跑。

## 5. 数据回流表字段定义（第一天启用，手动填写）

载体：仓库内 markdown 表（`accounts/墨予镜/feedback/2026-08-发布回流表.md`），不用飞书。字段沿用 7-30 规格最小合同，按单账号试点尺度简化：

| 字段 | 填写时机 | 说明 |
| --- | --- | --- |
| 发布日期 | 发布当天 | |
| 平台 | 发布当天 | 小红书 / 公众号 |
| 标题 | 发布当天 | |
| 内容形态 | 发布当天 | 图文卡 / 深度长文 |
| 选题来源 | 发布前 | 纵向复盘核心判断 / 复盘调整 / 自发 |
| 选题假设 | 发布前 | 为什么写这条、预期吸引谁 |
| 目标动作 | 发布前 | 收藏 / 评论 / 私信 / 关注，只选一个 |
| 链接 | 发布当天 | |
| 观察截至 | 发布当天 | 与同批内容保持可比窗口（建议 7 天） |
| 曝光/播放、点赞、收藏、评论、转发、私信 | 观察截至时 | 平台可见累计事实；没有留空，不填零 |
| 有效反馈 | 观察截至时 | 可复查的人工事实：评论原话、私信内容（脱敏） |
| 人工结论 | 复盘时 | 待观察 / 保留 / 调整 / 无效 |
| 下周调整 | 复盘时 | 只改一个变量：选题来源、表达角度或 CTA |
