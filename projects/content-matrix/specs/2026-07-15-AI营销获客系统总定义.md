# AI 营销获客系统总定义

## 1. 系统定位

这套系统不是单独的“博主更新追踪”，也不是单独的“内容生产工具”。

它是一套服务 `知行AI服务` 的 AI 营销获客系统，负责从市场需求信号中产生选题，再把选题推进到草稿、成稿、配图、排版、发布和反馈回流。

一句话定义：

```text
市场需求调研 -> 选题判断 -> 内容生产 -> 多平台发布 -> 反馈记录 -> 服务获客依据
```

这里的 AI 营销获客，不是承诺自动涨粉、自动成交或自动转化，而是用 AI 把市场信号、内容生产和服务验证连接起来，让每一篇内容都有来源、目标读者、服务指向和反馈记录。

## 2. 服务的业务目标

系统优先服务 `知行AI服务` 的早期获客和市场验证。

它要解决的问题是：

- 不再凭感觉决定写什么。
- 不再只看同行热闹，而是提取真实需求信号。
- 不再把内容生产停在草稿或想法阶段。
- 不再让发布后的反馈丢失。
- 不再把 AI 服务获客建立在空泛概念上。

对 `ai-service-studio` 的价值是：

- 市场需求调研有来源。
- 服务切口有证据。
- 选题能对应具体客户痛点。
- 内容能引导到低压力沟通、样本访谈或服务诊断。
- 发布反馈能反向修正服务 SOP、话术和报价边界。

## 3. 端到端链路

```mermaid

  A["市场信号采集"] --> B["需求归纳"]
  B --> C["选题池"]
  C --> D["草稿生成"]

  E --> F["配图与视觉资产"]
  F --> G["排版与草稿箱"]

  K --> B
```

## 4. 模块定义

### 4.1 市场信号采集层

对应已定义的：

- [博主更新追踪与对标账号采集系统](./2026-07-15-博主更新追踪与对标账号采集系统产品定义.md)

职责：

- 跟踪抖音、小红书、B站上的目标博主和对标账号。
- 采集内容元数据、正文、互动数据和可用评论样本。
- 把内容更新、评论样本和洞察写入飞书多维表格。
- 为选题和市场需求判断提供证据。

### 4.2 需求归纳层

职责：

- 从内容和评论中归纳重复出现的问题。
- 区分“用户好奇”“用户痛点”“用户愿意付费解决的问题”。
- 标记需求适合哪个业务线：
  - `知行AI服务`
  - `墨予镜`
  - `一镜一梳`
  - 其他后续账号或产品

示例需求类型：

- 工作流混乱
- 资料散乱
- 内容生产不稳定
- 私域承接弱
- 客户跟进靠人工记忆
- 团队不知道 AI 应该先落在哪条流程

### 4.3 选题池

职责：

- 把需求信号转成可发布的内容选题。
- 给每个选题记录来源证据。
- 判断选题服务哪个客户类型和哪条服务入口。

每个选题至少包含：

```text
目标读者：
真实问题：
来源证据：
服务指向：
发布平台：
内容形态：
下一步 CTA：
```

CTA（Call To Action，行动召唤）可以是：

- 评论区留言
- 私信一个关键词
- 提供一条流程
- 提供一批脱敏资料
- 约 20-30 分钟样本沟通
- 进入 AI 工作流诊断

### 4.4 内容生产层

对应已经跑通或正在建设的能力：

- 草稿到成稿
- 成稿编辑
- 配图
- 公众号排版
- 小红书 / 公众号 / 其他平台发布准备

职责：

- 把选题推进到可发布内容。
- 保留人审，不直接把 AI 生成稿当最终稿。
- 让内容口径符合账号定位和服务边界。

要求：

- 每篇内容写清服务指向。
- 不使用未验证案例包装自己。
- 不承诺收入增长、获客结果或 AI 转型成功。
- 对 `知行AI服务` 的内容，优先落到具体流程、资料、样本和小实验。

### 4.5 发布与反馈层

职责：

- 记录内容发布平台、链接、发布时间。
- 记录互动、评论、私信、转发和潜在线索。
- 把可用反馈回写到飞书和 `ai-service-studio` 记录。

反馈不能只看数据高低，还要看是否出现服务信号：

- 有人提出真实流程问题。
- 有人愿意提供资料样本。
- 有人询问能否帮忙诊断。
- 有人问价格。
- 有人提出反对意见或不信任点。

### 4.6 获客与服务验证层

对应 `projects/ai-service-studio/`：

- [最快启动最小闭环](../../ai-service-studio/system/最快启动最小闭环-v0.1.md)
- [零案例获客与模拟案例打样](../../ai-service-studio/system/零案例获客与模拟案例打样-v0.1.md)
- [获客与售前 SOP](../../ai-service-studio/system/获客与售前SOP-v0.1.md)
- [样本沟通记录](../../ai-service-studio/records/样本沟通记录.md)

职责：

- 把内容反馈转成真实外部动作。
- 记录样本沟通、报价、拒绝、成交和交付复盘。
- 用真实反馈修正服务定义，而不是只优化内容表达。

## 5. 数据主库边界

| 信息类型 | 主库 | 说明 |
| --- | --- | --- |
| 博主清单、内容更新、评论样本、洞察选题 | 飞书多维表格 | 日常筛选、协作、标记状态 |
| 系统定义、链路规则、验收标准 | 本地 Markdown | 需要版本、追溯和 Codex 读取 |
| 正式内容草稿、成稿、发布资产 | `projects/content-matrix/` | 按账号和内容资产治理 |
| AI 服务 SOP、报价、售前、复盘 | `projects/ai-service-studio/` | 服务业务系统主库 |
| 真实客户沟通与反馈 | `projects/ai-service-studio/records/` | 不混入内容素材目录 |

## 6. MVP 优先级

第一阶段不追求完整自动化。

优先跑通：

1. 飞书里有市场信号和博主更新。
2. 每周能产出一批有证据的选题。
3. 每个选题能对应 `知行AI服务` 的一个客户痛点或服务切口。
4. 每周至少发布 1-3 条服务相关内容。
5. 发布后记录反馈。
6. 出现服务信号时，进入样本沟通记录。

## 7. 不做范围

第一阶段不做：

- 自动承诺获客结果。
- 自动私信、自动评论、自动成交。
- 绕过平台权限采集数据。
- 大规模无节制爬取。
- 把未验证的市场信号写成确定结论。
- 把模拟案例包装成真实客户案例。

## 8. 验收口径

这套系统不是看“自动化程度”验收，而是看是否形成业务闭环。

最小验收：

1. 至少有 10 个被追踪的市场信号来源。
2. 至少形成 10 条带证据的候选选题。
3. 至少发布 3 条与 `知行AI服务` 相关的内容。
4. 每条内容都有来源证据和服务指向。
5. 至少记录 1 条真实外部反馈。
6. 如果出现私信、咨询或样本沟通，能进入 `ai-service-studio` 的记录系统。

## 9. 当前判断

`博主更新追踪` 是这套系统的上游模块。

完整系统应继续向下打通：

```text
采集 -> 洞察 -> 选题 -> 内容 -> 发布 -> 反馈 -> 获客 -> 服务验证
```

只有走到外部反馈和样本沟通，才算真正服务 `ai-service-studio`。停在采集、选题或草稿阶段，仍然只是准备工作。
