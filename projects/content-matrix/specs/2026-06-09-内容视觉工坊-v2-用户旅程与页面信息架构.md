# 内容视觉工坊 v2 用户旅程与页面信息架构

## 1. 这次重设计要解决什么

当前版本已经证明两件事：

1. 公众号排版这条链路是成立的
2. 如果把所有能力都堆在同一个工作台页面里，信息密度会过高，心智负担会迅速上升

所以这次不是继续往当前首页叠功能，而是先重新整理整个产品的信息架构。

目标不是“让每个功能都能出现”，而是让每条关键链路都能被清楚地使用。

## 2. 核心设计原则

### 2.1 不同任务阶段要拆开

当前实际已经存在三类完全不同的任务：

- 内容生产
- 图片生成
- 公众号排版打磨
- 风格资产沉淀

它们不应该继续混在一个页面里。

### 2.2 封面要有中间确认层

封面不能从“长文输入”直接跳到“文生图”。

必须存在：

- 提示词草案
- 人工确认
- 手动编辑
- 再进入出图

### 2.3 公众号排版样式不再以 JSON 为主入口

对于当前用户，更真实的工作流不是“导出 JSON -> 改 JSON -> 再导入”，而是：

1. 在微信编辑器里调好样式
2. 复制富文本
3. 粘贴进工具
4. 保存为命名样式基准

所以公众号排版样式的导入方式，应以富文本回贴为主。

### 2.4 公众号封面与转发封面是一套系统

前台不需要把它们做成两套风格入口。

正确做法是：

- 用户只定义一套“公众号封面风格”
- 系统内部自动产出：
  - 列表大封面
  - 转发小封面

### 2.5 通用文生图能力要独立出来

这个工具未来不只服务公众号。

既然已经接了文生图模型，后续像作品集网站配图、品牌图、概念图这类需求，也应该能直接使用。

所以“通用出图”不能永远挂在公众号链路下面。

### 2.6 金句卡要被单独定义

金句卡不应被混成“普通知识卡片”。

它更适合作为一条独立能力，处在：

- 内容提炼链路
- 卡片生成链路

之间。

正确做法是：

1. 先从文章中提炼候选金句
2. 由用户确认要做成卡片的句子
3. AI 生成底图
4. 程序再叠加：
   - 金句文字
   - 账号名
   - 二维码

这样可以避免：

- AI 直接出字时出现错字
- 文字样式不可控
- 二维码变形
- 同一账号下卡片不统一

## 3. 主要用户旅程

## 3.1 旅程 A：长文 -> 图片 -> 公众号排版

这是当前最核心的链路。

### 用户目标

给一篇已经写好的公众号文章，同时完成：

- 图片生成
- 公众号正文排版

### 路径

1. 进入工作台
2. 上传 Markdown 或粘贴正文
3. 勾选本次要生成的内容：
   - 知识卡片
   - 金句卡
   - 公众号封面
   - 正文配图
   - 公众号排版
4. 系统先生成中间方案：
   - 卡片拆解
   - 候选金句
   - 封面提示词
   - 正文配图建议
5. 用户确认或修改中间方案
6. 系统出图
7. 进入公众号排版页
8. 复制到公众号编辑器
9. 如有需要，在公众号编辑器里继续微调
10. 回贴并保存为排版基准

### 这个旅程说明什么

图片生成和公众号排版不是一个页面里的同一层任务。

它们共享同一篇原稿，但不共享同一个操作界面。

## 3.2 旅程 B：长文 -> 金句卡

### 用户目标

从一篇长文里提炼出几句值得传播的核心表达，并做成可单独传播的金句卡。

### 路径

1. 进入工作台
2. 导入文章
3. 勾选“生成金句卡”
4. 系统先给出候选金句列表
5. 用户勾选或修改金句
6. 系统为每张金句卡生成底图
7. 程序叠加：
   - 金句文字
   - 账号标识
   - 二维码
8. 导出最终 PNG

### 这个旅程说明什么

金句卡不是“知识卡片的精简版”。

它是一条更轻、更偏传播的内容链路，适合：

- 公众号正文插卡
- 带二维码传播
- 朋友圈或社群转发
- 小红书单张内容

## 3.3 旅程 C：只做封面

### 用户目标

快速做一套公众号封面，或者只做一个小红书封面。

### 路径

1. 进入封面工作流
2. 选择提示词来源：
   - 从长文生成
   - 手动填写
   - 基于已有提示词修改
3. 选择封面类型：
   - 公众号封面系统
   - 小红书封面
4. 系统先产出提示词草案
5. 用户查看、修改、重生提示词
6. 确认后再进入文生图
7. 保存结果

### 这个旅程说明什么

封面是入口图，不适合被设计成“一键直接出图”的黑盒流程。

它需要一个明确的中间确认层。

## 3.4 旅程 D：只做公众号排版

### 用户目标

把一篇文章整理成公众号可粘贴的富文本，并持续打磨排版风格。

### 路径

1. 进入公众号排版页
2. 导入 Markdown 或已有正文
3. 选择标题映射规则：
   - `# -> 一级标题`
   - `## -> 一级标题`
4. 系统生成公众号富文本
5. 用户预览
6. 复制到公众号编辑器
7. 用户在公众号编辑器里微调样式
8. 再把编辑器里的富文本复制回来
9. 点击“保存”
10. 存成命名样式基准

### 这个旅程说明什么

公众号排版页的核心动作，应该非常克制：

- 粘贴
- 保存
- 预览
- 复制

而不是继续把 JSON 导入导出暴露成主操作。

## 3.5 旅程 E：通用文生图

### 用户目标

不依赖公众号正文，直接做图。

例如：

- 作品集网站配图
- 品牌概念图
- 首页气氛图
- 单张知识图卡

### 路径

1. 进入通用出图页
2. 输入提示词
3. 选择风格
4. 选择参考图
5. 选择尺寸
6. 出图
7. 保存到素材库

### 这个旅程说明什么

通用出图应该成为独立能力，而不是公众号工作台的附属操作。

## 4. 页面信息架构

## 4.1 页面一：工作台

### 页面目标

发起一次“从内容到图片”的任务。

### 页面保留内容

- 原稿导入
- 输出类型选择
- 图片生成目标选择
- 卡片拆解结果
- 候选金句结果
- 提示词草案入口
- 图片结果总览

### 页面不再承担

- 公众号排版精调
- 富文本样式回贴
- 风格资产长期管理

### 这个页面更像什么

一个任务发起页，而不是万能控制台。

## 4.2 页面二：公众号排版

### 页面目标

专门处理公众号正文排版与样式打磨。

### 页面模块

- 标题映射规则选择
- 当前排版基准显示
- 排版预览
- 复制公众号正文
- 微信编辑器回贴区
- 保存当前富文本样本

### 这个页面的两个主按钮

- 粘贴
- 保存

这两个动作就是排版样式导入的真正入口。

## 4.3 页面三：风格资产

### 页面目标

统一管理所有风格资产，而不是在工作台里夹带查看。

### 页面模块

- 图片风格库
- 排版样式样本
- 金句卡模板
- 参考图分组
- 默认基准样式

### 这里应支持什么

- 为公众号排版基准命名
- 查看当前命名样式，例如 `蓝雾静读版`
- 后续再新增其他命名样式
- 管理金句卡模板

## 4.4 页面四：通用出图

### 页面目标

面向非公众号场景直接出图。

### 页面模块

- 手动提示词输入
- 参考图输入
- 风格选择
- 尺寸选择
- 出图结果

### 典型用途

- 作品集网站配图
- 落地页视觉图
- 通用概念图

## 4.5 页面五：同步记录

### 页面目标

记录历史生成和后续同步行为。

### 页面模块

- 历史图片生成记录
- 历史样式保存记录
- 后续公众号草稿同步记录

## 5. 封面链路重设计

## 5.1 产品定义

公众号封面与转发封面归为一套封面系统。

前台只暴露一个入口：

- 公众号封面

后台自动知道这套系统要产出：

- 列表页大封面
- 转发小封面

## 5.2 封面工作流

### 提示词来源

- 从长文生成
- 手动填写
- 基于现有提示词重写

### 中间确认层

在真正进入文生图前，用户必须能：

- 查看提示词
- 修改提示词
- 重新生成提示词

### 之后再出图

这一步才真正调文生图模型。

## 6. 金句卡链路定义

## 6.1 产品定义

金句卡是一种更轻的传播卡，不追求像知识卡片那样信息完整。

它的核心目标是：

- 单句成立
- 可单独转发
- 可挂二维码
- 可作为公众号正文中的插卡

## 6.2 系统职责

系统应拆成两层：

### A. 金句提炼层

- 从长文中提炼候选金句
- 允许用户勾选和修改

### B. 卡片生成层

- AI 只负责底图
- 程序负责叠文字和二维码

## 6.3 与知识卡片的区别

### 知识卡片

- 信息完整
- 一张图可以单独成立
- 更适合收藏、学习、转发

### 金句卡

- 信息极简
- 只有一句核心表达
- 更适合传播、插卡、转化

## 7. 公众号排版风格导入方式

## 7.1 旧方式的问题

旧方式是：

- 导出 JSON
- 编辑 JSON
- 导入 JSON

这更适合工程调参，不适合当前用户的真实工作流。

## 7.2 新方式

公众号排版样式的主入口应该改为：

1. 在微信编辑器里调好
2. 复制富文本
3. 粘贴到工具
4. 保存为命名样式

## 7.3 当前建议命名

已确认的默认样式基准命名为：

- `蓝雾静读版`

后续可以继续扩展：

- `蓝雾静读版 v2`
- `蓝雾静读版 · 长文版`
- `蓝雾静读版 · 短文版`

## 8. 当前版本迁移建议

## 8.1 保留

- 当前已经打通的图片生成链路
- 当前公众号回贴解析能力
- 当前保存样式样本能力
- 当前新排版链路里的 HTML 预览与复制

## 8.2 迁移

- 把风格资产相关模块迁到风格资产页
- 把公众号排版相关模块迁到公众号排版页
- 把金句卡从知识卡片逻辑里拆出来
- 工作台只保留任务发起和结果总览

## 8.3 暂缓

- JSON 作为主要排版样式编辑入口
- 复杂草稿箱自动同步
- 多账号多权限系统
- 高自由度可视化编辑器

## 9. 下一步实现顺序

建议按下面顺序推进：

1. 先把页面级导航结构定下来
2. 把工作台、公众号排版、风格资产拆成三个正式页面
3. 把金句卡链路拆成独立输出
4. 把封面提示词确认层单独做出来
5. 再补通用出图页

## 10. 结论

`内容视觉工坊 v2` 不应继续沿着“一个工作台塞下所有功能”的方向扩展。

正确方向是：

- 工作台负责任务发起
- 公众号排版负责样式打磨
- 风格资产负责长期管理
- 金句卡负责轻传播卡片链路
- 通用出图负责跨场景生成

这样才不会随着能力增加，把整个产品变成一个越来越重、越来越难用的大面板。
