## 1. 问题定义

当前问题不是“有没有一份方法文档”，而是：

1. 方法真值源写在 `sources/` 里，但实现层没有始终按它收口。
2. 生成链路曾经混入旧容器、旧 prompt preview、旧 projection 和旧 QA 样本，导致 AI 容易把历史实现当成当前方法。
3. 过程交付物没有被强制化，导致最终报告能产出，但中间链路不可追溯或可追溯性不足。

本规格要解决的是把“方法”变成“可执行合同”，让实现层、测试层和 QA 层都只承认同一条 stage 00-16 链路。

## 2. 正式边界

本项目的知识与方法边界固定为：

1. `projects/aimandala/docs/sources/知识库构建/三圈五行流派解读方法与步骤.md`
   - 这是单一方法真值源。
   - 它定义 stage 00-16 的顺序、输入、输出和禁止项。
2. `projects/aimandala/docs/specs/2026-05-10-三圈五行流派解读方法实施规格.md`
   - 这是实现合同。
   - 它定义系统必须如何承接方法真值源。
3. `projects/aimandala/docs/qa/2026-05-10-三圈五行流派解读方法实施QA基线.md`
   - 这是 QA 质量门。
   - 它定义样稿和中间过程必须如何被验证。

原则上：

- `sources` 负责“应该怎么解读”
- `specs` 负责“程序要怎么实现”
- `qa` 负责“是否真的实现到了”

## 3. 目标行为

系统在生成 Lite / Pro 报告时，必须满足以下行为：

1. 只接受 `stage_process_package` 作为正式生成输入。
2. `stage_process_package` 只包含 stage 00-12 的过程交付物、命中知识条目和写作输入。
3. Lite / Pro 正文只能在已有 stage 证据上做整合，不允许重新看图、重新查知识库或重选主轴。
4. 每份 QA 样稿必须同时保留：
   - 最终报告
   - 中间过程版本
   - 过程链摘要
   - 对应的验证记录
5. 旧链路、旧 prompt skeleton、旧报告骨架、旧样本不得成为默认运行路径；已确认废弃的旧内容应从 active 工作区删除。

## 4. 实现合同

### 4.1 输入合同

正式输入必须满足：

- `stage-00-input-context` 到 `stage-12-healing-direction-and-report-branching` 可被追溯
- `process_contract` 明确方法来源、目标报告类型、token 策略和禁止输入项
- `knowledge_refs` 只写具体知识条目，不写执行规范
- `prompt_refs` 只用于说明执行过程，不充当知识依据

### 4.2 输出合同

正式输出必须包含：

- `stage_process_package`
- Lite / Pro 结构化报告
- 最终用户可见正文
- 调试与 QA 所需的过程痕迹

### 4.3 运行时合同

运行时必须遵守：

- 第 03 / 04 步优先负责视觉证据和直断互验
- 第 05 - 09 步默认不调用大模型
- 第 10 - 12 步可以合并为一次文字大模型调用
- 第 13 / 14 步分别按 Lite / Pro prompt 生成正文
- 第 15 步只负责可视化资产生成
- 第 16 步只负责质检和组装

### 4.4 SDD / TDD / Harness Engineering

重要实现必须遵守：

1. 先定义目标行为和边界。
2. 再定义最小可验证合同。
3. 再写测试锁定合同。
4. 最后才允许修改实现。

对本链路的最低要求是：

- SDD：明确每个 stage 的输入、输出和禁止项
- TDD：先有能证明 contract 的测试，再改实现
- Harness Engineering：把 stage 交付物、QA 样稿和最终报告打通成可回放链路

## 5. 非目标

本规格不做以下事情：

1. 不重写原始知识内容。
2. 不把 `sources` 改成产品功能 spec 的替代目录。
3. 不恢复任何旧报告默认链路。
4. 不允许最终报告直接吞掉完整 Markdown 真值源。
5. 不在最终阶段补新判断或新知识。

## 6. 验收标准

本规格通过时，应满足以下条件：

1. 代码层正式生成入口只消费 `stage_process_package`。
2. 测试层能验证 stage 交付物存在且顺序正确。
3. QA 层能保存中间过程版本，而不只保存最终报告。
4. active 文档不会把旧链路写成当前方法。
5. 已确认废弃的旧样本、旧链路归档和旧报告生成文档已从 active 工作区删除。

## 7. 交付物

本规格对应的最小交付闭环是：

1. 实现层收口到 stage-based 输入。
2. QA 基线确认过程链保留。
3. 旧样本和旧链路清理。
4. 新增或更新验证记录。

## 8. 后续建议

下一步应该补一份配套的 `qa basis`，把本规格中的合同转成可执行验证矩阵，然后再补一份 delivery 说明，形成完整闭环。
