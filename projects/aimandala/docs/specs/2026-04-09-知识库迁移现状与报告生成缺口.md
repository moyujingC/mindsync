## 1. 目的

本文件专门回答一个这两天已经被反复碰到的问题：

- 为什么当前 `Lite / Pro` 的报告样稿看起来和我们的解读流派、知识库关系不大

这份文档不讨论页面入口，也不继续讨论报告产品矩阵，而是收束下面 4 个判断：

1. 当前知识库到底迁到了什么程度
2. 当前报告生成链路真实依赖的是什么
3. 这会对 `Lite / Pro` 的内容质量造成什么影响
4. 如果要让报告真正体现流派，下一步最少缺哪几层接入

## 2. 当前结论

当前更准确的判断不是“知识库完全不存在”，而是：

1. `Lite / Pro` 的页面链路、prompt 壳、字段结构和结果页壳已经存在
2. 报告生成也已经有一条可运行的最小主链路
3. `V2 knowledge` 包已经迁入当前后端，并开始进入 orchestrator、prompt context 和 `Layer 0`
4. 三圈颜色提取也已经重新接回当前后端，可对有效图片生成真实三圈颜色结果
5. 但这条主链路当前还不是“完整知识库驱动”
4. 它更接近：
   - `模板 + 已迁入的 V2 知识包 + 已恢复的三圈颜色提取 + 仍保留的 fallback/placeholder + prompt 壳`
   - 驱动的一条迁移中链路

因此，当前报告可以用于：

1. 看页面结构
2. 看字段契约
3. 看 `Lite / Pro` 的基础层级差异
4. 看 loading / result / history 的交付壳

但当前报告还不适合用于：

1. 验证流派是否已经真正进入生成主链路
2. 验证知识库主题是否已经稳定生效
3. 验证“这份报告像不像我们自己”

## 4. 这对当前 `Lite / Pro` 样稿意味着什么

## 4.1 现在能看的是什么

当前看 `Lite / Pro` 样稿，主要是在看下面几件事：

1. `Lite` 是否更轻、更快、更低压
2. `Pro` 是否更完整、更结构化
3. 字段和段落骨架是否合理
4. 页面最终怎么呈现这些字段

这些是当前样稿仍然有价值的地方。

## 4.2 现在看不了的是什么

当前样稿还不能有效回答下面这些问题：

1. 这份报告是否已经体现我们的解读流派
2. 这份报告是否真正用到了主题知识库
3. `general / father_relationship / mother_relationship / intimate_relationship / parent_child_relationship / wealth_career / health_wellness / personal_growth`
   - 是否已经被不同主题知识稳定拉开
4. 画作中的具体画面特征是否已经真正被知识规则解释过

因此，如果此时直接评价：

- “这份 `Lite / Pro` 像不像最终产品”

很容易把两个问题混在一起：

1. 当前文案骨架是否合理
2. 当前底层知识能力是否已经接通

## 4.3 为什么会出现“看起来不像我们”的感觉

当前最核心的原因，是报告底层还没有形成：

- `画面特征 -> 三圈结构 -> 知识库规则 -> 主题解释 -> 报告输出`

这条完整链路。

所以现在更容易出现的情况是：

1. 报告有结构
2. 报告有语气
3. 报告有一些固定判断壳
4. 但报告还缺少真正属于我们自己的解释来源

这就是用户会明显感到：

- “有报告形状，但不是我们的报告”

的根本原因。

## 5. 当前最明显的生成缺口

当前至少还有下面 5 层缺口。

## 5.1 `Layer 0` 还不是正式知识层

现在的 `Layer 0` 仍然更像迁移期占位层。

真正需要的 `Layer 0` 应至少回答：

1. 画面里命中了哪些流派解释对象
2. 三圈中的颜色 / 节奏 / 结构如何落到规则层
3. 候选失衡为什么是这些，而不是固定默认值

## 5.2 主题系统还没有真正变成主题知识系统

现在“主题”更多是：

- 一个前台选择项
- 一个 prompt 变量
- 一个模板标签

它还没有稳定变成：

- 一套真正影响解释路径、证据组织和现实连接方式的知识输入

## 5.3 意图和过程感受仍主要停留在弱提示层

虽然 prompt 和 spec 都反复要求吃进：

1. 创作前意图
2. 创作时感受

但在当前代码路径里，它们更接近：

- 文案提示增强项

而不是：

- 真正改变分析结论的核心输入层

## 5.4 blueprint 解决了“怎么说”，但还没解决“为什么这样说”

当前模板层已经能帮助我们统一：

1. 结构
2. 段落
3. 语气
4. 缺省建议

但它无法替代：

1. 证据来源
2. 流派判断
3. 知识映射

所以它更像“表达层”，不是“知识层”。

## 5.5 `general` 主题当前尤其容易显得空泛

因为 `general` 本来就比专题主题更依赖：

1. 真实画面判断
2. 多维知识汇总
3. 明确的主线收束

在知识层还没接稳时，`general` 往往最容易退化成：

- 一份结构还行、但解释来源偏弱的通用报告

## 6. 当前阶段应该如何正确使用这些样稿

当前更适合把 `Lite / Pro` 样稿当成：

1. 结果页字段与结构打样
2. 语气与层级差异打样
3. 页面信息密度打样
4. 后续知识库接入后的承载壳

当前不适合把它们当成：

1. 最终解读质量证明
2. 最终流派命中率证明
3. 知识库已迁移完成的证据

## 7. 下一步最值得先补的 4 件事

## 7.1 先补一份“知识库接线清单”

先回答：

1. 原有知识库到底有哪些目录和对象
2. 哪些已经进入 `mindsync`
3. 哪些已经进入但还没接线
4. 哪些字段已经开始使用，哪些还停留在 placeholder

## 7.2 再定义正式 `Layer 0` 合同

要先写清：

1. 正式 `Layer 0` 应该有哪些字段
2. 哪些字段来自三圈检测
3. 哪些字段来自知识库查询
4. 哪些字段来自规则映射

否则后面即使接知识库，也容易继续退回 placeholder。

## 7.3 把 `theme_context` 从“输入摘要”升级成“知识上下文”

也就是把当前：

- 主题名 + 意图 + 感受 + 半径

升级成：

- 主题知识摘要 + 当前命中的解释焦点 + 该主题下的现实场景路径

## 7.4 最后再重做 `Lite / Pro` 样稿验证

等上面 3 件事成立后，再重新拿：

1. `mandala-test-01`
2. `mandala-test-02`

去验证 `Lite / Pro`，那时看的才会是：

- 这份报告到底像不像我们自己的系统

而不是：

- 这份模板壳是否还算顺

## 8. 当前阶段收束结论

基于以上判断，当前建议先收束到下面 6 个结论：

1. 当前 `Lite / Pro` 的问题不只是文案问题，而是底层知识链路只接上了前半段
2. 当前系统已经有报告生成壳，也已经迁入 `V2 knowledge` 与三圈颜色提取，但还不是完整知识库驱动的正式生成系统
3. 当前最关键的断层发生在：
   - `knowledge -> Layer 0 -> theme_context -> report generation`
   - 这条链上
4. 当前样稿仍可用于评估页面结构和层级差异，但不能代表最终解读质量
5. 如果继续只改结果文案，不补知识层，报告仍会持续显得“不像我们自己”
6. 后续更值得优先补的是知识库迁移与接线，而不是继续手工润色假样稿
