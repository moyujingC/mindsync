## 1. 文档目的

本文定义 Aimandala 当前 MVP 上线前的范围、验收口径和 Go / No-Go 判断标准。

本文不是完整产品重定义，不覆盖 `ToC-MVP-产品规范.md` 的项目主线；它只收束当前上线窗口：Lite / Pro 升级关系、支付权限、报告生成、曼曼 followup、异常兜底、smoke test 和后续 UI 最后一轮优化的进入条件。

## 2. 用户与场景

### 2.1 目标用户

当前 MVP 面向 To C 用户：

- 用户已经画了一幅曼陀罗，想获得一份温和、可阅读的自我观察报告。
- 用户愿意先以 Lite 低门槛体验，再根据报告感受决定是否升级 Pro。
- 用户在读报告时可能不理解某些段落，希望围绕本次画作和本次报告继续追问。

### 2.2 用户当前卡点

上线前需要避免用户在以下位置失控：

1. 不知道 Lite / Pro 分别是什么。
2. 不知道自己支付了什么、支付后能看到什么。
3. 支付后权益未同步，用户不知道是否重复付款。
4. Lite 报告像半成品，Pro 升级像硬性索费。
5. Pro 报告只是 Lite 加长版，缺少升级价值。
6. followup 变成泛心理咨询、长期陪伴或重大决策建议。
7. 上传、生成、支付、followup 出错时没有下一步。
8. 上线后出现用户问题，团队无法查清支付、报告和 followup 状态。

## 3. 本轮要解决的问题

当前上线窗口要解决的问题是：

> 一个真实用户能从进入、上传、查看 Lite、升级 Pro、查看 Pro、围绕报告继续追问，到遇到异常时都有明确反馈；同时产品边界、内容边界、技术边界都能被解释和验证。

这意味着 MVP 上线不是追求所有功能完成，而是保证付费交付主链路可用、可解释、可排障。

## 4. 当前继承口径

### 4.1 Lite / Pro 关系

以 `2026-05-29-Lite-Pro版本关系与内容边界决策.md` 为准：

- Lite 价格：9.9 元。
- Pro 是 Lite 的升级，不提供独立购买入口。
- Pro 升级价：29 元。
- 用户必须先完成对应画作的 Lite 体验，才能触发 Pro 升级。
- Lite 是完整轻量交付，不是 Pro 的残缺预览。
- Pro 承接 Lite 结论，提供推导层和深度层。

### 4.2 曼曼 followup 关系

以 `2026-05-30-曼曼-avatar报告陪读与追问-handoff.md` 和 `2026-05-30-曼曼-report-followup-真实模型-smoke-验证记录.md` 为准：

- 曼曼是 Aimandala 的 AI 报告陪读 avatar。
- 曼曼只围绕本次画作和本次报告回答追问。
- 曼曼不是真实疗愈师、心理咨询师、医疗服务提供者、财务顾问或长期陪伴者。
- followup 第一阶段不做多报告对比、长期观察、人工转接、长期人格画像或主题计划。

### 4.3 UI 关系

UI 最后一轮优化在 MVP 底座稳定后启动。

UI 本轮目标不是重新做品牌视觉，而是把上传、Lite、Pro、支付、followup、异常状态串成用户能理解的闭环。

## 5. 本轮必须上线前完成

### 5.1 主流程闭环

用户至少能完整走通：

1. 进入 Aimandala 入口。
2. 上传 / 提交曼陀罗画作和必要信息。
3. 生成并查看 Lite 报告。
4. 理解 Lite 是轻量完整报告。
5. 在 Lite 报告中看到 Pro 升级入口。
6. 完成 Pro 升级支付。
7. 查看 Pro 报告。
8. 围绕 Pro 报告继续提问。
9. 失败时知道下一步。

验收标准：

- 主路径至少用真实或近真实样例完整跑通一次。
- 刷新 / 重新进入后关键权益和报告状态不丢。
- 用户不会卡在“付了钱去哪看报告”。

### 5.2 Lite / Pro 权限

必须保证：

- 未购买 Lite 的用户不能查看 Lite 正文。
- 未升级 Pro 的用户不能查看 Pro 完整内容。
- 已购买 Lite 的用户可查看对应 Lite 报告。
- 已升级 Pro 的用户可查看对应 Pro 报告和允许范围内的 followup。
- Pro 购买前必须校验对应画作已完成 Lite 购买。
- 权限判断不能只依赖前端状态。

验收标准：

- 覆盖未支付、Lite 已支付、Pro 已升级、支付失败、支付取消、已购买再次进入。
- 不出现未付费看到 Pro。
- 不出现已付费用户权益丢失。

### 5.3 支付状态正确

必须覆盖：

- Lite 支付成功。
- Lite 支付失败 / 取消。
- Pro 升级支付成功。
- Pro 升级支付失败 / 取消。
- 支付成功但权益同步中。
- 重复点击支付。
- 已购买后再次进入。

验收标准：

- 金额展示清楚：Lite 9.9 元，Pro 升级再付 29 元。
- 支付成功后能进入正确报告或明确的生成 / 同步状态。
- 支付失败不会错误解锁。
- 支付同步中不诱导重复支付。
- 已购买用户不再看到重复付款主按钮。

### 5.4 报告生成稳定

必须保证：

- Lite 报告可稳定生成和展示。
- Pro 报告可基于同一画作和 Lite 前置结果继续生成。
- Lite / Pro 报告结构符合当前内容边界。
- 报告生成失败有明确兜底。

验收标准：

- 至少 5–10 个真实 / 半真实样例完成 Lite / Pro 人工阅读。
- Lite 读起来是完整轻量交付。
- Pro 比 Lite 有明确推导深度和行动建议。
- 不出现明显模板拼接、空泛堆叠或与画作无关的报告。

### 5.5 Followup 基本可用

MVP 阶段 followup 只需要支持本次报告追问：

- 解释报告段落。
- 解释画面线索和报告判断之间的关系。
- 把报告建议转成更具体的小行动。
- 处理“我觉得这部分不准”。
- 对超出范围的问题温和拉回。

必须收束：

- 医疗 / 心理诊断。
- 危机干预替代。
- 投资、财务、关系、职业等重大现实决策。
- 长期人格画像。
- 跨报告总结。
- 长期记忆 / 长期陪伴。
- 与报告无关的闲聊。

验收标准：

- followup 回答能绑定本次报告上下文。
- context missing 不生成无依据回答。
- report_id mismatch 返回错误，不串报告。
- 不重新生成完整报告。
- 不变成泛心理咨询。
- 边界问题能被 pre-check、post-check 或产品回应拦截。

### 5.6 内容安全边界

报告和 followup 都必须遵守：

- 不做医疗诊断。
- 不做心理疾病判断。
- 不做财务、投资、职业或关系决策替代。
- 不做未来预测。
- 不制造依赖。
- 不承诺疗效。
- 不恐吓用户。
- 不用“只有升级才能真正理解自己”之类焦虑转化文案。

推荐表达：

- “可能反映……”
- “可以作为一个观察角度……”
- “如果你对这句话有共鸣……”
- “这份报告用于自我观察，不构成医疗、心理诊断或治疗建议。”

验收标准：

- 报告和 followup 的安全声明一致。
- 真实模型 smoke 中不出现诊断、恐吓、依赖诱导或治疗承诺。
- 越界输入不会进入普通报告追问回答。

### 5.7 异常兜底

必须覆盖：

- 图片上传失败。
- 图片格式不支持 / 图片过大。
- 必填信息缺失。
- Lite 生成失败。
- Pro 生成失败。
- 模型返回异常。
- 生成时间过长。
- 网络中断。
- 支付失败。
- 支付取消。
- 支付成功但权益同步中。
- 权限状态异常。
- followup 空输入 / 过长输入 / 生成失败 / 超出范围。

每个异常提示至少回答：

1. 发生了什么。
2. 用户的钱、报告或数据是否安全。
3. 下一步可以怎么做。

验收标准：

- 不出现白屏。
- 不直接暴露技术错误。
- 不让用户付费后无处可去。
- 不诱导重复支付。

### 5.8 Smoke test 记录

上线前必须留下可追溯验证记录。

至少包括：

- 主流程 smoke。
- Lite / Pro 权限与支付 smoke。
- Lite / Pro 报告内容 smoke。
- followup 真实模型 smoke。
- 异常状态 smoke。

验收标准：

- 每一轮 smoke 有输入、结果、结论和残留风险。
- 失败项明确标记阻塞 / 非阻塞。
- Go / No-Go review 能引用这些记录作判断。

## 6. 可以上线后补

以下内容不阻塞 MVP 上线，但应记录为后续迭代：

1. 完整后台。
2. 精细化数据分析。
3. 更多 followup 轮次策略。
4. 更丰富的报告视觉设计。
5. 多版本 AB 测试。
6. 自动化内容评估。
7. 更完整的用户画像沉淀。
8. 结构化引用增强。
9. `out_of_scope` / `answer_type` 分类。
10. 更完整的人工排障后台界面。

## 7. MVP 阶段不建议做

以下内容不进入当前 MVP：

1. 复杂会员体系。
2. 多套餐并行。
3. Pro 独立购买入口。
4. 大规模个性化运营。
5. 过深的心理咨询式对话。
6. 自动危机干预。
7. 没有人工兜底的高风险情绪服务。
8. 多报告对比。
9. 长期观察和长期记忆。
10. 21 天 / 主题计划自动生成。
11. 人工疗愈师转接。
12. 社区分享。
13. 用户画像页。
14. 复杂历史报告管理。

## 8. 方案比较与取舍

### 8.1 上线前先补底座，再做 UI 最终优化

| 方案 | 好处 | 代价 | 判断 |
|---|---|---|---|
| 先做 UI 最终精修 | 视觉推进快，容易看到成果 | 权限、支付、followup 边界变化会导致返工 | 不采用 |
| 先完成 MVP 底座，再做 UI 收口 | UI 基于稳定边界优化，返工少 | 前期视觉变化较慢 | 采用 |

结论：UI 最后一轮优化必须等 MVP 范围、权限、支付、报告结构、followup 边界和异常状态清单稳定后启动。

### 8.2 Pro 独立购买 vs Lite 后升级

| 方案 | 好处 | 代价 | 判断 |
|---|---|---|---|
| Lite / Pro 独立购买 | 入口简单 | 用户首次决策压力大，Pro 价值缺少体验铺垫 | 不采用 |
| Lite → Pro 升级 | 首次门槛低，Pro 转化基于体验 | 要求 Lite 必须完整，Pro 引导不能像硬索费 | 采用 |

结论：Pro 只能作为 Lite 升级，不提供独立购买入口。

### 8.3 Followup 做报告追问 vs 泛心理咨询聊天

| 方案 | 好处 | 代价 | 判断 |
|---|---|---|---|
| 泛心理咨询聊天 | 用户可聊得更多 | 风险高、边界不清、依赖诱导风险大 | 不采用 |
| 单报告追问 | 范围清楚，和报告交付强相关 | 能力看起来克制 | 采用 |

结论：followup 第一阶段只围绕本次画作和本次报告。

## 9. UI 最后一轮优化进入条件

只有完成以下条件后，才进入 Figma Make UI 最后一轮优化：

1. MVP 范围已冻结。
2. Lite / Pro 权限规则已验证。
3. 支付状态已验证。
4. Lite / Pro 报告结构已确认。
5. followup 能力边界已确认。
6. 异常状态清单和兜底文案已确认。
7. 至少一轮 smoke test 已记录。
8. Go / No-Go review 已给出 Go 或 Conditional Go。

UI 最后一轮优化要产出：

- 首页 / 入口页。
- 上传页。
- 报告生成中。
- Lite 报告页。
- Pro 升级页。
- 支付成功 / 权益同步中。
- Pro 报告页。
- Followup 对话区。
- 主要错误态。
- 主要空态。

UI 验收重点：

- 用户知道自己在哪一步。
- 用户知道 Lite / Pro 是什么。
- 用户知道自己支付了什么。
- 用户知道支付成功后去哪看。
- 用户知道报告生成中不是卡死。
- 用户知道 followup 是围绕报告追问。
- 失败状态都有下一步。
- 没有医疗诊断、恐吓或过度承诺表达。

## 10. Go / No-Go 标准

### 10.1 Go

满足以下条件可以上线：

1. 主流程完整走通。
2. 支付和权限无阻断问题。
3. 报告质量达到最低可交付标准。
4. followup 不越界、不跑飞。
5. 异常状态有明确提示。
6. smoke test 有记录。
7. 已知问题不影响用户付费和交付。
8. 人工排障能查清支付、报告和 followup 基本状态。

### 10.2 Conditional Go

满足上线主条件，但存在非阻塞风险时，可以 Conditional Go。

允许的非阻塞风险示例：

- 个别 UI 文案还可继续润色，但不影响理解。
- followup 引用段落不够精确，但回答仍基于报告。
- `out_of_scope` 分类不够细，但用户侧已被温和拉回。
- 数据分析不完整，但支付和报告排障信息可查。

Conditional Go 必须附带：

- 风险清单。
- 监控方式。
- 回退条件。
- 上线后修复 owner。

### 10.3 No-Go

出现以下任一情况不能上线：

1. 用户付费后可能看不到内容。
2. 未付费用户可能看到 Pro。
3. 支付状态可能错乱。
4. 已付费用户可能被诱导重复付款。
5. 报告存在明显诊断、恐吓、攻击性表达。
6. followup 会脱离报告乱答。
7. followup 会进入心理咨询、长期陪伴、投资建议或重大决策替代。
8. 真实模型调用未验证。
9. 失败状态白屏或无提示。
10. 上线后无法判断用户是否真的付费或报告是否真的生成。

## 11. 最小人工排障要求

MVP 不要求完整后台，但上线前必须能人工查到：

- 用户是否付费。
- 用户买的是 Lite 还是已升级 Pro。
- 支付是否成功。
- 报告是否生成成功。
- 报告 ID。
- followup 会话或请求 ID。
- 模型调用是否失败。
- 失败原因大致分类。

必须能人工处理：

- 支付成功但权益未同步。
- 报告生成失败。
- 用户找不到报告。
- followup 报错。
- 用户投诉报告内容异常。

## 12. 后续 handoff

### 12.1 交给 Architect

需要产出：

- Lite / Pro 权限与支付状态主路径技术边界。
- ReportFollowupContextStore 主路径接入方案。
- 结构化引用与 `out_of_scope` 分类方案。
- 异常状态与错误码边界。

### 12.2 交给 Engineer

需要完成：

- 主流程闭环实现。
- Lite / Pro 权限校验。
- 支付状态接入与同步兜底。
- Lite / Pro 报告生成主路径稳定。
- `/api/report-followups` 接入 report_id + context 主路径。
- 异常兜底与基础排障信息。

### 12.3 交给 Test / QA

需要产出：

- 主流程验收记录。
- Lite / Pro 权限与支付验收表。
- Lite / Pro 报告内容 smoke test 记录。
- Followup MVP 验收记录。
- 异常状态清单与 smoke test 记录。
- Go / No-Go Review。

### 12.4 交给 UI / UX

进入条件满足后，基于本文第 9 节做 Figma Make 最后一轮优化。

UI / UX 不负责重新打开 Lite / Pro 商业边界，不负责把 followup 扩成心理咨询聊天产品。

## 13. 当前下一步

建议按以下顺序推进：

1. 基于本文创建 `MVP 主流程验收表`。
2. 创建 `Lite / Pro 权限与支付验收表`。
3. 创建 `Lite / Pro 报告内容 Smoke Test 记录`。
4. 创建 `Followup MVP 验收记录`，并复用已有真实模型 smoke 结果。
5. 创建 `MVP 异常状态清单与兜底文案`。
6. 汇总为 `MVP 上线 Go / No-Go Review`。
7. Go 或 Conditional Go 后，再进入 Figma Make UI 最后一轮优化。
