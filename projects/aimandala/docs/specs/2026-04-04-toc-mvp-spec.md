## 1. 背景

`AI-Mandala / 一镜一梳` 已经在旧仓库中形成可运行的产品主线，但当前结构同时混有：

- To C 主产品
- To B / Studio
- `V2` 生产能力
- `V3` 实验线
- 部署、运维和历史治理材料

当前需要先把真正仍要继续开发的 To C 主线，迁成 `mindsync` 中一条清晰、可治理、可持续演进的产品线。

这份 spec 只服务这一目标，不试图一次定义整个历史仓库的全部能力。

## 2. 问题定义

当前需要解决的问题不是“如何把所有曼陀罗相关资产都迁进来”，而是：

1. 如何保留 To C 主产品当前已经被验证的核心体验。
2. 如何把 `V2` 生产主线从旧仓库中剥离出来，形成可继续开发的最小闭环。
3. 如何在前端渠道会继续增长的前提下，避免 Web、小程序、App 各写一套业务逻辑。

如果这一步不先收口，继续开发只会重复旧问题：

- 主线边界不清
- 实验线和生产线混在一起
- 多渠道前端逻辑逐步复制粘贴

## 3. 本轮目标用户

当前 MVP 只聚焦 To C 用户：

- 希望通过上传自己的曼陀罗绘画，获得一版结构化、可阅读的心理洞察
- 更适合个人觉察、轻疗愈和自我理解场景
- 愿意先体验 Lite，再视情况升级到更深内容

本轮不覆盖：

- 疗愈师工作台用户
- B 端机构使用者
- 内部运营或知识库维护用户

## 4. 核心产品场景

当前 MVP 只覆盖一条 To C 主路径：

1. 用户进入手机端 Web 产品。
2. 用户上传曼陀罗图片，并补充少量必要描述。
3. 系统完成三圈检测与 Lite 解读生成。
4. 用户查看 Lite 报告。
5. 用户决定是否升级到 Pro。
6. 若升级成功，系统在复用 Lite 前置数据的基础上生成 Pro 报告。

这条路径的核心不是“内容越多越好”，而是：

- 用户能完成上传到报告的闭环
- Lite 到 Pro 的升级逻辑清楚
- 当前主线能被验证、维护和继续迭代

## 5. 本轮目标

这一版 To C MVP 只验证四件事：

1. To C 主产品能在新工作区中形成一条清晰可执行的产品边界。
2. `V2` 生产链路可以作为当前正式实现主线继续承接。
3. 手机端 Web 可以作为当前用户端主入口继续开发。
4. 前端架构能够为后续小程序与 App 留出共享业务逻辑的演进空间。

## 6. 本轮不做

- 不把 To B / Studio 纳入当前 MVP 范围
- 不把 `V3` 实验线接入当前正式主线
- 不在本轮定义完整小程序版和 App 版交付
- 不处理完整部署收口、云端运维和内部工具治理
- 不把所有历史产品文档都直接提升为当前正式约束

## 7. 产品方案

当前 To C MVP 保持旧主线的核心产品结构，但在新工作区中重新收口为更清晰的正式边界。

### 7.1 当前产品层级

当前只承接 To C 主产品中最接近真实用户路径的内容：

1. Lite
   - 面向首次体验用户
   - 输出基础解读报告
2. Pro
   - 面向愿意继续深入的用户
   - 基于 Lite 前置数据生成更深内容

`明镜轻咨询` 等更强服务化内容，在当前这份 To C MVP 中只作为上游背景存在，不作为本轮实现范围。

### 7.2 核心能力

当前 MVP 必须具备的核心能力：

1. 图像上传
2. 三圈检测
3. Lite 报告生成
4. Pro 升级与生成
5. 报告读取与历史记录查看

### 7.3 当前正式 API 主线

当前以 `V2` 为正式 API 主线。

优先围绕以下接口组织用户路径：

1. `POST /api/v2/interpretations`
2. `POST /api/v2/interpretations/{interpretation_id}/upgrade`
3. `GET /api/v2/interpretations/{interpretation_id}/report`
4. `GET /api/v2/users/{user_id}/interpretations`

`V3` 当前明确不作为正式主线的一部分。

## 8. 用户流程

当前 To C MVP 默认按 6 步推进：

1. `upload`
   - 用户上传图片并补充必要描述
2. `detect`
   - 系统执行三圈检测，必要时允许用户确认或修正
3. `lite-generating`
   - 系统生成 Lite
4. `lite-ready`
   - 用户查看 Lite 报告
5. `upgrade`
   - 用户发起升级并完成支付或确认
6. `pro-ready`
   - 用户查看 Pro 报告

各步输入输出：

- `upload`
  - 输入：图片 + 主题 + 可选描述
  - 输出：可进入检测的前置输入
- `detect`
  - 输入：图片
  - 输出：三圈检测结果与确认后的几何参数
- `lite-generating`
  - 输入：已确认输入
  - 输出：Lite 报告数据
- `lite-ready`
  - 输入：Lite 报告
  - 输出：用户查看与升级决策
- `upgrade`
  - 输入：已有 Lite 结果 + 升级请求
  - 输出：Pro 生成前置状态
- `pro-ready`
  - 输入：Pro 报告
  - 输出：完整 To C 解读结果

## 9. 前端渠道策略

当前 To C 用户端采用分阶段渠道策略：

1. 当前主入口
   - 手机端 Web
2. 后续渠道
   - 小程序
   - 原生 App

但这不意味着三个渠道各自维护一整套前端逻辑。

当前默认前端策略是：

1. 共享内核
   - `shared/core`
   - `shared/api`
   - `shared/types`
2. 渠道实现
   - `mobile-web`
   - `miniapp`
   - `native-app`

默认要求：

- 共享业务决策、状态机、类型定义和 API service
- 不强行共享页面组件、路由和平台能力

## 10. 成功判定

本轮成功不以迁了多少文件衡量，而以以下结果衡量：

1. 团队能基于同一份 To C spec 讨论范围，不再混入 To B / `V3`。
2. 当前 To C 主路径足够清楚，可以直接写技术方案和 QA 清单。
3. `mobile-web` 当前主入口与未来多渠道扩展关系已经明确。
4. 前端共享内核与渠道实现的边界已经正式写入系统，而不是停留在口头判断。

## 11. 关键 trade-off

1. 先恢复 To C 主线开发，不先迁完整产品矩阵。
2. 先承接 `V2` 生产主线，不先扩展 `V3`。
3. 先把 mobile-web 跑顺，不先同时做小程序和 App。
4. 先共享业务逻辑与 API 层，不先追求跨渠道 UI 统一。

## 12. 验收标准

1. 存在一条清晰的 To C 用户主路径定义。
2. 文档中明确写出当前正式 API 主线是 `V2`。
3. 文档中明确写出当前不纳入 To B / Studio / `V3`。
4. 文档中明确写出当前用户端主入口是手机端 Web。
5. 文档中明确写出前端采用“共享内核 + 渠道实现”的演进策略。

## 13. 默认决策

基于当前阶段的最小实现原则，本轮先采用以下默认决策：

1. `mobile-web` 作为当前唯一正式用户端入口。
2. 小程序与原生 App 先只保留结构兼容性，不进入本轮实现。
3. Lite 与 Pro 的产品闭环继续沿用 `V2` 升级模式。
4. 前端共享内核优先沉淀为业务流程、API service 与类型定义。
5. 渠道差异先限制在 UI、路由、上传、支付、登录等平台适配层。

## 14. 依赖与风险

依赖：

- 后续技术方案明确 `toC/app/backend` 与 `toC/app/frontend` 的真实迁移落点
- QA 文档明确 To C 主路径的人工验证清单
- 文档继续梳理旧仓库中哪些约束仍然有效

风险：

- 旧仓库历史文档过多，容易把参考文档误当当前约束
- mobile-web 当前实现里仍有设计壳代码与正式逻辑混杂
- 如果共享内核边界不够严格，后续小程序与 App 仍会复制逻辑
- 如果过早预建过多渠道空壳，反而会让当前 To C 主线失焦
