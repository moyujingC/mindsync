## 1. 目的

本文件用于统一定义 `Pro` 的内容骨架与字段接口，不再把 `全面解读` 和 `专题解读` 拆成两套看起来彼此独立的 schema。

这里要回答的是：

1. `Pro` 共享哪些正文主骨架
2. `全面解读` 与 `专题解读` 在哪里分叉
3. 页面渲染与生成侧该如何共用同一套接口

## 2. 设计原则

`Pro` 的结构应同时满足下面 5 条原则：

1. `先命中，后展开`
   - 第一段先让用户觉得“这说中了我”
2. `先依据，后判断`
   - 不能只有结论，没有来源
3. `共享主骨架，模式再分流`
   - 两种解读方向先共用核心结构，再进入差异段
4. `现实连接必须成立`
   - 不能只停在分析层
5. `结尾只给一个主路径`
   - 不把报告写成训练计划

## 3. Pro 的共享主骨架

无论是 `全面解读` 还是 `专题解读`，当前都建议共享下面 `6` 个主内容块：

1. `标题`
2. `开头命中`
3. `画面依据`
4. `核心解释`
5. `模式命名`
6. `现实连接与下一步`

## 4. 两种方向的差异块

## 4.1 全面解读的差异块

`全面解读` 额外强调：

1. 当前整体状态
2. 主要拉扯如何形成
3. 这次最值得带走的一个主判断

## 4.2 专题解读的差异块

`专题解读` 额外强调：

1. 为什么是这个主题
2. 该主题里的核心矛盾
3. `触发 -> 自动反应 -> 强化结果` 的问题闭环

## 5. Canonical 内容结构

当前建议把 `Pro` 的 canonical 内容结构定义为：

```yaml
pro_report:
  mode: overall | topic
  topic: general | relationship | boundary | emotion | expression | career
  title: string
  opening_hit: string
  visual_evidence:
    summary: string
    anchors: string[]
  core_interpretation:
    current_state: string
    explanation_chain: string
    key_tension: string
  pattern_naming:
    pattern_name: string
    pattern_description: string
    protective_logic: string
  reality_connection:
    typical_scene: string
    current_impact: string
  next_step:
    direction: string
    action: string
  overall_view:
    main_judgment: string
    state_summary: string
    reading_focus: string
  topic_focus:
    why_this_topic: string
    recurring_loop:
      trigger: string
      automatic_response: string
      reinforcing_result: string
    topic_scene: string
  bridge:
    followup_option: string
    why_continue: string
```

说明：

1. `overall_view` 只在 `mode = overall` 时必填
2. `topic_focus` 只在 `mode = topic` 时必填
3. 其余字段为 `Pro` 的共享主结构

## 6. 字段定义

## 6.1 title

### 作用

- 给整份报告定一个主轴

### 要求

1. 有明确状态感
2. 不要只追求诗性
3. 能让用户大概知道这份报告在讲什么

## 6.2 opening_hit

### 作用

- 承担“被看见”任务

### 要求

1. 第一段就建立命中感
2. 2-3 句即可
3. 不要一上来就是摘要表或方法论

## 6.3 visual_evidence

### 作用

- 承担“为什么这样判断”的证据任务

### 子字段

- `summary`
- `anchors`

### 要求

1. 要把画面与判断连起来
2. 不能只是罗列图像元素

## 6.4 core_interpretation

### 作用

- 承担“被解释”任务

### 子字段

- `current_state`
- `explanation_chain`
- `key_tension`

### 要求

1. 解释链必须可复述
2. `key_tension` 要帮助用户看清主要拉扯

## 6.5 pattern_naming

### 作用

- 承担“被命名”任务

### 子字段

- `pattern_name`
- `pattern_description`
- `protective_logic`

### 要求

1. 命名要通俗
2. 重点是帮助用户从模糊进入清楚

## 6.6 reality_connection

### 作用

- 承担“被连接”任务

### 子字段

- `typical_scene`
- `current_impact`

### 要求

1. 必须落回现实生活
2. 场景要足够具体，不要停在抽象词

## 6.7 next_step

### 作用

- 承担“被指引”任务

### 子字段

- `direction`
- `action`

### 要求

1. 只给一个主路径
2. 不能泛泛而谈

## 6.8 overall_view

### 作用

- 只服务 `全面解读`

### 子字段

- `main_judgment`
- `state_summary`
- `reading_focus`

### 要求

1. 帮用户快速看清这次整体状态
2. 不要发散成多个平行主题

## 6.9 topic_focus

### 作用

- 只服务 `专题解读`

### 子字段

- `why_this_topic`
- `recurring_loop`
- `topic_scene`

### 要求

1. 要证明“为什么是这个主题”
2. 要形成最小问题闭环
3. 主题存在时，正文必须真的更聚焦

## 6.10 bridge

### 作用

- 为结果页的后续承接预留接口
- 当前应只承接已经存在的 `MVP` 页面动作

### 子字段

- `followup_option`
- `why_continue`

### 要求

1. 长期方向上，`全面解读` 可以更自然地收束到某个值得继续展开的主题
2. 当前 `MVP` 里，两种模式都应优先服务 `再画一幅` 这一主动作
3. `开始 AI 对话`、`查看历史记录` 只作为辅助动作，不应写成主承接
4. 不写入 `主题方案`、`Journey` 或其他尚未落地的未来模块

## 7. 当前阶段收束建议

基于以上定义，当前建议先收束到下面 5 个判断：

1. `Pro` 必须共用一套母 schema，再按 `mode` 分叉
2. `全面解读` 与 `专题解读` 的差异应体现在正文结构里，而不是只换标题
3. `Pro` 的价值核心是完整解释链、模式命名与现实连接
4. `Pro` 的结尾应优先给主路径，而不是堆很多行动提示
5. 后续 prompt、schema、结果页都应统一回到这份文档校验
