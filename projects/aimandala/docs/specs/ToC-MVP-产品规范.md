## 1. 背景

`AI-Mandala / 一镜一梳` 已经在旧仓库中形成可运行的 To C 产品主线。当前需要把仍要继续开发和上线的 To C 主线，收束成 `mindsync` 中一条清晰、可治理、可验证的产品线。

这份 spec 只服务 To C MVP，不试图定义历史仓库的全部能力。

当前 MVP 上线判断以 [MVP-当前上线口径.md](MVP-当前上线口径.md) 为第一入口。

## 2. 问题定义

当前要解决的问题是：

1. 保留 To C 主产品当前已经可接受的核心报告体验。
2. 把 `V2` 生产主线作为当前正式实现主线继续承接。
3. 保证手机端 Web 主路径可跑通，并为后续小程序与 App 保留共享业务逻辑边界。
4. 避免历史 Lite / Pro 过程性文档继续干扰当前 MVP 上线判断。

## 3. 本轮目标用户

当前 MVP 只聚焦 To C 用户：

- 希望通过上传自己的曼陀罗绘画，获得一份温和、可阅读的自我观察报告。
- 愿意先以较低门槛完成 Lite 体验。
- 如报告体验有价值，再决定是否升级 Pro。
- 读报告时可能希望围绕本次报告继续追问。

本轮不覆盖：

- 疗愈师工作台用户。
- B 端机构使用者。
- 内部运营或知识库维护用户。

## 4. 核心产品场景

当前 MVP 只覆盖一条 To C 主路径：

1. 用户进入手机端 Web 产品。
2. 用户上传曼陀罗图片，并补充少量必要描述。
3. 系统生成 Lite 报告。
4. 用户查看 Lite 报告。
5. 用户如愿意继续深入，可从 Lite 报告中的入口升级 Pro。
6. Pro 支付成功后，用户查看对应 Pro 权益内容。
7. 用户可围绕当前报告向曼曼继续追问。

这条路径的验收重点不是重新定义报告结构，而是：

- 用户能完成上传到报告的闭环。
- Lite / Pro 权益关系清楚。
- 支付和权限不会错乱。
- 报告与追问不越界。
- 失败状态不失控。

## 5. 本轮目标

这一版 To C MVP 只验证：

1. 手机端 Web 主路径能作为当前用户端主入口继续开发。
2. 当前报告版本可作为 MVP 接受版本。
3. Lite / Pro 付费权益和升级路径可控。
4. 曼曼 followup 只围绕本次报告追问。
5. 前端架构为后续多渠道保留共享业务逻辑边界。

## 6. 本轮不做

- 不把 To B / Studio 纳入当前 MVP 范围。
- 不把 `V3` 实验线接入当前正式主线。
- 不在本轮定义完整小程序版和 App 版交付。
- 不处理完整后台、精细化数据分析和复杂运营系统。
- 不重新打开 Lite / Pro 报告结构设计。
- 不把历史内容边界、固定字数或固定模块当作当前上线验收依据。

## 7. 产品方案

### 7.1 当前产品层级

当前只承接 To C 主产品中最接近真实用户路径的内容：

1. `一镜 Lite 版`
   - 面向首次体验用户。
   - 当前入口价格：9.9 元。
   - 作为 MVP 的入口报告体验。
2. `一梳 Pro 版`
   - 只能从 Lite 后升级。
   - 当前升级价：29 元。
   - 不提供独立购买入口。

### 7.2 当前购买关系

当前正式口径：

1. Pro 是 Lite 的升级，不是独立购买产品。
2. 用户必须先完成对应画作的 Lite 购买 / 查看，才能触发 Pro 升级入口。
3. 前端不提供独立 Pro 购买入口。
4. 后端必须校验 Pro 购买资格，不能只依赖前端状态。
5. 已购买用户重新进入时，应恢复对应权益，不能诱导重复付款。

### 7.3 核心能力

当前 MVP 必须具备：

1. 图像上传。
2. 必要信息提交。
3. Lite 报告生成与查看。
4. Pro 升级支付与权益恢复。
5. Pro 权益内容查看。
6. 报告读取与历史记录查看。
7. 曼曼 report-bound followup。

### 7.4 当前正式 API 主线

当前以 `V2` 为正式 API 主线。

优先围绕以下接口组织用户路径：

1. `POST /api/v2/interpretations`
2. `POST /api/v2/interpretations/{interpretation_id}/upgrade`
3. `GET /api/v2/interpretations/{interpretation_id}/report`
4. `GET /api/v2/users/{user_id}/interpretations`

`V3` 当前明确不作为正式主线的一部分。

## 8. 用户流程

当前 To C MVP 默认按下面路径推进：

1. `upload`
   - 用户上传图片并补充必要描述。
2. `lite-generating`
   - 系统进入 Lite 报告生成状态。
3. `lite-ready`
   - 用户查看 Lite 报告。
4. `pro-upgrade`
   - 用户从 Lite 报告中的升级入口发起 Pro 升级。
5. `pro-generating / pro-ready`
   - Pro 权益确认后，用户查看 Pro 权益内容。
6. `followup`
   - 用户围绕本次报告继续追问。
7. `history`
   - 用户可在历史记录中再次打开已有报告。

当前页面状态与页面文案的总映射，如与本文冲突，以 [MVP-当前上线口径.md](MVP-当前上线口径.md) 为准。

## 9. 前端渠道策略

当前 To C 用户端采用分阶段渠道策略：

1. 当前主入口：手机端 Web。
2. 后续渠道：小程序、原生 App。

默认前端策略：

1. 共享内核
   - `shared/core`
   - `shared/api`
   - `shared/types`
2. 渠道实现
   - `mobile-web`
   - `miniapp`
   - `native-app`

默认要求：

- 共享业务决策、状态机、类型定义和 API service。
- 不强行共享页面组件、路由和平台能力。

## 10. 成功判定

本轮成功不以文档或功能数量衡量，而以以下结果衡量：

1. 用户能完成手机端 Web 主路径。
2. Lite / Pro 权益和支付状态正确。
3. 当前报告版本可交付且不越界。
4. 曼曼 followup 不脱离本次报告，不进入长期陪伴或高风险建议。
5. 关键失败状态不白屏。
6. 团队能基于当前上线口径讨论范围，不再被历史过程文档带偏。

## 11. 关键 trade-off

1. 先保留当前可接受报告版本，不重新打开报告结构设计。
2. 先跑通 mobile-web，不同时做完整小程序和 App。
3. 先保留共享业务逻辑和 API 层，不追求跨渠道 UI 统一。
4. 先做最小上线检查，不扩张完整后台、复杂 analytics 或会员体系。

## 12. 验收标准

1. 存在一条清晰的 To C 用户主路径定义。
2. 文档中明确写出当前正式 API 主线是 `V2`。
3. 文档中明确写出 Pro 只能从 Lite 后升级，不提供独立购买入口。
4. 文档中明确写出当前不纳入 To B / Studio / `V3`。
5. 文档中明确写出当前用户端主入口是手机端 Web。
6. 文档中明确写出前端采用“共享内核 + 渠道实现”的演进策略。
7. 文档中明确写出当前上线以 `MVP-当前上线口径.md` 为准。

## 13. 默认决策

1. `mobile-web` 作为当前唯一正式用户端入口。
2. 小程序与原生 App 先只保留结构兼容性，不进入本轮实现。
3. Pro 只能从 Lite 报告后升级。
4. 前端共享内核优先沉淀为业务流程、API service 与类型定义。
5. 渠道差异先限制在 UI、路由、上传、支付、登录等平台适配层。
6. 当前不再以历史 Lite / Pro 内容结构作为上线验收依据。

## 14. 依赖与风险

依赖：

- 后续技术方案明确 `toC/app/backend` 与 `toC/app/frontend` 的真实落点。
- QA 文档明确 To C 主路径的最小人工验证清单。
- 当前上线口径持续作为默认入口。

风险：

- 旧仓库历史文档过多，容易把参考文档误当当前约束。
- mobile-web 当前实现里仍有设计壳代码与正式逻辑混杂。
- 如果共享内核边界不够严格，后续小程序与 App 仍会复制逻辑。
- 如果过早预建过多渠道空壳，会让当前 To C 主线失焦。
