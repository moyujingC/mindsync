## 1. 目的

这份文档专门回答下面两个问题：

1. 当前 `V2` 知识库真正值得优化的地方是什么
2. 如果它要长期演进，应该长成什么样，而不是继续停留在“旧仓库知识包 + 迁移期编排器”的状态

这里说的 `V2` 知识库，指的是从旧版 `AI-Mandala` 迁入的产品内嵌知识库：

- `projects/aimandala/toC/app/backend/app/core/knowledge/`

它不是 `研究中心` 的知识沉淀系统，也不是公司级长期知识库。

## 2. 当前判断

当前 `V2` 知识库的真实状态可以概括为：

1. 它已经是 To C 当前主链路的一部分，而不是纯历史代码。
2. 它保留了旧版产品中最重要的领域知识资产：
   - 五行
   - 三圈
   - 颜色含义
   - 主题特化
   - 失衡类型
   - 疗愈建议
3. 它当前仍主要以 Python 常量、字典和函数的方式存在。
4. 它已经开始进入 `orchestrator_v2 -> Layer 0 -> theme_context -> Lite / Pro 报告` 这条链路。
5. 它还没有成为一个边界清晰、可验证、可维护、可演进的正式知识系统。

更准确地说，当前系统里存在的不是“知识库缺失”，而是“知识资产、知识查询、规则判断、叙事拼装和 fallback 机制被揉在一起”。

## 3. 现状优点

在谈优化前，先明确当前版本保留了什么价值。

### 3.1 它不是空壳

当前 `core/knowledge/` 已经具备较完整的领域资产骨架，至少覆盖：

1. 五行基础属性与颜色映射
2. 三圈结构和圈层解释
3. 主题特化配置
4. 失衡类型定义与 To C / To B 支持边界
5. 通用查询入口 `KnowledgeQueryEngine`

这意味着长期方案不应该从零重建，而应以“保留旧资产价值、重构资产组织方式”为主。

### 3.2 它已经经过生产语义验证

虽然当前迁入链路仍是迁移期实现，但这套知识包本身来自旧版产品，不是纸面假设。

因此它和 `研究中心` 的知识库有一个关键区别：

- `研究中心/kb`
  - 更偏方法、研究和跨项目知识
- `V2 knowledge`
  - 是直接驱动一镜一梳解释结果的产品知识域

### 3.3 它已经暴露了真实演进方向

旧仓库中未迁入的 `knowledge_v3` 与 `knowledge_base_v3` 至少说明了一点：

- 团队已经意识到“把知识继续写死在 Python 模块里”不是长期解

但旧版 `V3` 的做法也暴露出另一点：

- 直接上“一条很重的全新知识库 + 质检体系 + 新 API”，对当前迁移中的 To C 主线来说太重

因此长期架构应该吸收它的方向，但不能照搬它的重量。

## 4. 当前最值得优化的地方

### 4.1 知识资产和运行时代码耦合过深

当前知识内容主要直接写在：

- `five_elements.py`
- `three_circles.py`
- `color_meanings.py`
- `themes/*.py`
- `imbalance_types.py`

这会带来 4 个问题：

1. 改知识内容必须改代码
2. 内容评审和代码评审混在一起
3. 很难做结构化校验、差异比较和批量审查
4. 未来很难给知识资产建立编辑、审核和版本化入口

### 4.2 查询层不是正式的知识服务层

`KnowledgeQueryEngine` 现在更像一个“函数封装 + fallback 容器”，而不是正式知识服务。

它当前缺少的不是接口数量，而是下面这些能力：

1. 统一的知识实体 ID
2. 明确的查询契约
3. 结果证据链
4. 命中来源与 fallback 可观察性
5. 资产版本与 schema 版本

当前虽然 `QueryResult` 有 `source` 和 `fallback_used`，但这些信息没有被稳定提升为后续编排和验证的正式输入。

### 4.3 `Layer 0` 合同不够清晰

当前 `Layer0Raw` 承担的是：

1. 颜色分析聚合
2. 三圈主导信息
3. 五行分布
4. 失衡候选
5. 主题摘要

但它还没有明确区分下面三类信息：

1. 视觉事实
   - 从图片分析得到
2. 知识命中
   - 从知识库查询得到
3. 规则推导
   - 从事实和知识组合推出来

这会导致后面 `Lite / Pro` 叙事层很难回答：

- 这句话到底是来自图片、来自规则、还是来自模板兜底

### 4.4 编排器承担了过多知识职责

`orchestrator_v2.py` 当前同时做了下面几类事：

1. 调知识引擎
2. 做五行聚合
3. 做失衡候选推断
4. 做主题摘要拼装
5. 做故事角度提取
6. 做知识文本清洗
7. 做报告内容 fallback

这意味着知识系统的边界没有稳定停在知识层，而是一路蔓延到编排器内部。

直接结果就是：

1. 编排器过重
2. 知识改动容易牵动报告逻辑
3. 很难单独验证知识层正确性
4. 未来换报告结构时容易误伤知识逻辑

### 4.5 主题系统是“配置集合”，还不是“主题解释系统”

当前 `themes/*.py` 解决的是“每个主题有一套大字典”，但没有把主题真正抽成正式能力层。

现在的主题更多还是：

1. 一个主题名
2. 一组 `core_issues`
3. 一组 element/circle 解释数据
4. 一组模板角度

缺的是真正可复用的主题能力：

1. 主题焦点收束
2. 主题下的规则优先级
3. 主题证据组织方式
4. 主题差异化验证

### 4.6 fallback 机制太“能跑”，但不够“可治理”

当前系统大量使用 fallback，这是迁移期合理策略，但长期风险也很明显：

1. fallback 很容易掩盖真实知识缺口
2. 上游缺数据，下游仍能产报告
3. 最终看到的是“报告能出”，而不是“知识链路已完整”

长期上应该保留 fallback，但必须做到：

1. fallback 可见
2. fallback 可统计
3. fallback 可分级
4. fallback 不再和正式知识命中混为一谈

### 4.7 知识质量校验能力仍偏薄

当前测试里已经有：

- `test_v2_knowledge.py`

但它更多是 smoke test，不足以覆盖知识库真正需要的质量门：

1. 主题覆盖完整性
2. 失衡映射完整性
3. 元素/颜色/圈层组合合法性
4. 主题数据字段完整性
5. fallback 命中率
6. 关键样本的稳定输出差异

### 4.8 当前旧版 `V3` 方向正确，但粒度和落地方式都过重

旧仓库 `knowledge_v3` 已经做了两件有价值的事：

1. 开始把知识数据从 Python 代码中抽出来
2. 引入质量与审核元数据

但它的问题也很明显：

1. 直接引入新的知识模型和新 API
2. 数据文件粒度过细
3. 缺少平滑接入当前 `V2` 主链路的适配层
4. 没有先把 `Layer 0` 和查询契约收清楚

所以它更适合作为“长期方向参考”，不适合作为“当前直接切换方案”。

## 5. 长期架构目标

长期要达到的，不是“再做一个 V3 文件夹”，而是建立一套清楚的知识系统分层：

1. 知识资产层
   - 存什么
2. 知识构建与质检层
   - 怎么验
3. 知识运行时层
   - 怎么查
4. 解释装配层
   - 怎么把知识变成 `Layer 0`
5. 叙事生成层
   - 怎么把 `Layer 0` 变成报告

一句话说：

- 先把“知识为什么成立”收清楚，再去优化“报告怎么说出来”

## 6. 长期架构原则

### 6.1 产品内闭环优先，能力抽象后置

这套知识库首先服务：

- `一镜一梳` To C 主线

在它没有在产品内跑顺前，不要急着把它平台化成公司通用能力。

### 6.2 资产外置优先于 API 版本升级

真正该先升级的不是：

- `/api/v3/*`

而是：

- 知识资产从代码常量中外置出来
- 知识查询契约先收清楚

### 6.3 结构化证据先于文案优化

必须先明确：

1. 看到了什么视觉事实
2. 命中了什么知识对象
3. 推出了什么规则结论

然后再决定：

- 报告怎么组织和表达

### 6.4 构建期校验优先于运行时猜测

长期应优先在构建时发现：

1. 缺字段
2. 缺映射
3. 重复定义
4. 无法命中的主题条目

而不是等运行时靠 fallback 抹平问题。

### 6.5 兼容迁移，不做一次性重写

当前已有 V2 主链路、旧版资产和迁移中的编排器。

所以长期方案应该采用：

1. 先加适配层
2. 再抽资产
3. 再替换调用点
4. 最后再讨论新版本 API

## 7. 目标分层

建议长期收束成下面五层。

### 7.1 知识资产层

职责：

1. 保存正式领域知识
2. 保存知识元数据
3. 保存审核状态和版本信息

建议内容分类：

1. `elements`
   - 五行基础定义
2. `circles`
   - 三圈基础定义
3. `colors`
   - 颜色与色调解释
4. `themes`
   - 主题配置与主题差异化解释
5. `rules`
   - 失衡、相生相克、命中规则
6. `healing`
   - 疗愈建议模板
7. `narrative`
   - 叙事提示和报告桥接模板

### 7.2 知识构建与质检层

职责：

1. 读取资产文件
2. 做 schema 校验
3. 做完整性校验
4. 产出运行时索引
5. 产出质量报告

这一层应该显式回答：

1. 某个主题缺哪些字段
2. 某个规则引用了不存在的知识对象没有
3. 当前 pack 与上一个 pack 的差异是什么
4. 哪些条目仍是 draft，哪些已可进入 runtime

### 7.3 知识运行时层

职责：

1. 提供正式查询接口
2. 屏蔽资产文件格式
3. 提供证据化结果，而不是只返回文本块

建议最小服务：

1. `ElementService`
2. `CircleService`
3. `ThemeService`
4. `ImbalanceRuleService`
5. `HealingService`
6. `NarrativeHintService`
7. `KnowledgeRepository`

### 7.4 解释装配层

职责：

1. 接收视觉事实
2. 查询知识对象
3. 形成正式 `Layer 0`

这一层应该输出：

1. `visual_facts`
2. `knowledge_hits`
3. `derived_signals`
4. `theme_context`
5. `quality_flags`
6. `fallback_flags`

也就是说，长期的 `Layer 0` 不应只是“知识库原始查询结果”，而应是：

- 一份结构化解释证据包

### 7.5 叙事生成层

职责：

1. 消费正式 `Layer 0`
2. 生成 `Lite / Pro` 上游草稿
3. 严格区分“知识结论”和“叙事组织”

长期上，叙事生成层不应该再直接自己拼接主题知识细节，而应只消费上游已装配好的：

1. 主题焦点
2. 主导信号
3. 证据摘要
4. 风险提示
5. 适用叙事角度

## 9. 长期核心契约

### 9.1 Knowledge Asset 契约

每个正式知识条目至少应带：

1. `id`
2. `type`
3. `version`
4. `status`
5. `source`
6. `review_status`
7. `payload`
8. `relations`

### 9.2 Query Result 契约

长期返回值不应只是字符串，而应至少带：

1. `value`
2. `entity_id`
3. `source_pack`
4. `fallback_level`
5. `evidence`
6. `warnings`

### 9.3 Layer 0 契约

长期 `Layer 0` 至少应拆成：

1. `visual_facts`
2. `knowledge_hits`
3. `rule_evaluations`
4. `theme_projection`
5. `imbalance_candidates`
6. `quality_flags`
7. `fallback_summary`

只有这样，后面才可能真正回答：

- 这份报告为什么这样生成

## 10. 推荐演进路线

### Phase 0：先把当前 V2 收口成可观察系统

目标：

- 不改知识内容，先把边界和缺口看清

建议动作：

1. 写 `Layer 0` 正式合同
2. 补知识命中与 fallback 统计字段
3. 为关键主题、失衡、三圈主导补覆盖测试
4. 明确 `orchestrator_v2` 中哪些逻辑属于“知识装配”，准备后移

### Phase 1：先加适配层，不急着抽空旧包

目标：

- 让旧版 `core/knowledge/` 先通过一个正式 repository/service 层被访问

建议动作：

1. 新增 `KnowledgeRepository`
2. 新增 `legacy_v2_python_pack` 适配器
3. 让 `orchestrator_v2` 改为调用 service，而不是直接碰知识细节

这一阶段结束后，当前知识内容仍可全部留在 Python 中，但系统边界已经开始变清楚。

### Phase 2：把高价值资产从 Python 常量外置

目标：

- 先抽“变化频率高、需要评审、主题差异大的内容”

优先建议外置：

1. 主题配置
2. 主题摘要与核心议题
3. 失衡规则
4. 疗愈建议
5. 叙事提示模板

相对可以晚一点抽的内容：

1. 五行基础常量
2. 三圈基础定义

### Phase 3：建立构建与质检层

目标：

- 让知识包从“文件集合”变成“可验证产物”

建议动作：

1. 建 schema 校验
2. 建完整性检查
3. 产出 build 索引
4. 产出 diff 报告
5. 产出 fallback 热点报告

### Phase 4：重构 `Layer 0 -> theme_context -> report generation`

目标：

- 让知识层真正主导解释路径，而不是继续停在 prompt 提示层

建议动作：

1. 用正式 `Layer 0` 替换迁移期 placeholder 语义
2. 让 `theme_context` 基于主题投影结果生成
3. 让 `Lite / Pro` 草稿读取结构化证据，而不是自己再拼知识文本

### Phase 5：再决定是否需要新的 API 版本

只有当下面 3 件事都成立，才值得讨论正式 `V3 API`：

1. 资产已外置
2. runtime 已稳定
3. `Layer 0` 与报告链路已完成解耦

否则“先开新 API”只会把旧问题从目录 A 搬到目录 B。

## 11. 对旧版 `V3` 的取舍建议

建议吸收的部分：

1. 数据外置方向
2. 审核和质量元数据
3. 质检报告意识

当前不建议直接采纳的部分：

1. 立即重开完整 `V3 API`
2. 一上来就引入过细颗粒度的数据拆分
3. 把六维质检体系作为当前主链路前置阻塞

更合理的做法是：

- 先把当前 `V2` 资产做成“可验证的 pack + 可查询的 service + 可解释的 Layer 0”

再逐步把质量元数据和更复杂的理论体系接进来。

## 12. 当前最值得马上做的 8 个动作

如果只看近期优先级，我建议先做下面 8 件事：

1. 明确正式 `Layer 0` 字段合同。
2. 从 `orchestrator_v2` 中抽出 `layer0_assembler`。
3. 为 `knowledge query -> evidence -> fallback` 建正式返回结构。
4. 给主题系统建立统一 manifest 和 ID。
5. 给失衡规则建立可验证映射，而不是只靠散落字典。
6. 给知识命中率、fallback 命中率补测试和日志。
7. 先把主题/规则/疗愈建议外置成 pack。
8. 把旧版 `knowledge_v3` 的质量元数据设计收编到 build 层，而不是直接重启 V3 主线。

## 13. 一句话结论

当前 `V2` 知识库最需要优化的，不是继续补几段解释文案，而是把：

- 旧版迁移来的知识资产
- 当前运行时查询逻辑
- `Layer 0` 解释证据
- `Lite / Pro` 叙事生成

这四层彻底拆开。

长期最合理的路线不是“再开一套更重的 V3”，而是先把 `V2` 收束成：

- `知识资产包 + 构建质检层 + 查询服务层 + Layer 0 装配层 + 叙事生成层`

这样它才会从“还能跑的旧资产”变成“可长期维护的产品知识系统”。
