## 1. 目的

本文件专门回答：

- `议题聚焦报告` 的正文到底由哪些内容块组成
- 这些内容块各自承担什么任务
- 生成侧应该输出哪些结构化字段
- 当前如果要为主题化报告预留实现接口，建议怎么定义 canonical 结构

这份文档不是页面视觉稿，也不是 prompt 文案本身。

它是：

- 内容结构定义
- structured schema 前置定义
- 页面渲染与生成实现之间的共同接口说明

## 2. 继承的上游结论

本文件继承以下前提：

1. `议题聚焦报告` 是 `问题向理解型报告`
2. 它的核心用户任务是：
   - 主题确认
   - 画面依据与议题判断连接
   - 核心拉扯说明
   - 现实场景解释
   - 议题向下一步
3. 它的最小内容骨架是：
   - 当前议题下的命中句
   - 画面为何指向该议题
   - 该议题里的核心拉扯
   - 现实中的典型场景
   - 一个议题向下一步

## 3. 本轮做什么 / 不做什么

### 3.1 本轮做什么

本轮明确：

- 内容块定义
- 字段层级
- 字段命名建议
- 每个字段的生成要求
- 为主题化实现预留统一接口

### 3.2 本轮不做什么

本轮不直接定义：

- 最终对外文案语气
- 最终 UI 排版
- 具体价格
- 各主题知识库的详细内容建设方案
- 主题方案的具体字段定义

## 4. 结构设计原则

议题聚焦报告的结构，不应只是“把主题词插入通用报告”。

当前建议遵循以下 5 条原则：

1. `先确认主题成立`
   - 开头必须说明为什么这份报告与这个问题有关
2. `依据必须指向议题`
   - 不是先假设主题，再去补解释
3. `围绕一个问题持续收束`
   - 不应在中途发散成泛人格分析
4. `场景必须具体`
   - 至少有一个现实高相似度场景
5. `下一步必须是议题向动作`
   - 不能退回通用建议

## 5. 当前建议的内容块

当前建议将 `议题聚焦报告` 拆成 `6` 个主内容块与 `2` 个辅助内容块。

### 5.1 六个主内容块

1. `标题`
   - 给整份议题报告定一个问题轴
2. `当前议题下的命中句`
   - 先说清为什么这份报告和该主题有关
3. `画面为何指向该议题`
   - 说明判断依据
4. `该议题里的核心拉扯`
   - 帮用户看清问题里的核心矛盾
5. `现实中的典型场景与重复方式`
   - 说明它在生活里如何反复发生
6. `一个议题向下一步`
   - 让用户知道在这个主题里最先做什么

### 5.2 两个辅助内容块

1. `输入线索利用`
   - 更强地使用主题、意图、过程感受
2. `主题方案入口`
   - 作为更自然的后续承接

## 6. Canonical 内容结构

当前建议把 `议题聚焦报告` 的 canonical 内容结构定义为：

```yaml
issue_focus_report:
  title: string
  issue_opening:
    issue_name: string
    hit_sentence: string
    why_this_issue: string
  issue_evidence:
    summary: string
    anchors: string[]
    input_signals:
      theme: string
      intention: string
      feeling: string
  core_tension:
    visible_conflict: string
    hidden_need: string
    protective_move: string
  scene_connection:
    typical_scene: string
    recurring_moment: string
    current_impact: string
  repeat_mechanism:
    trigger: string
    automatic_response: string
    reinforcing_result: string
  next_step:
    direction: string
    action: string
    followup_option: string
  theme_plan_bridge:
    suitable_path: string
    why_continue: string
```

说明：

- 这是一份“产品语义结构”
- 后续主题化实现与页面渲染都应尽量向这份结构靠拢

## 7. 字段定义

## 7.1 title

### 作用

- 让用户快速知道这份报告聚焦的是哪个问题轴

### 要求

- 不能过于泛
- 要带出明确议题感

## 7.2 issue_opening

### 作用

- 承担“主题确认”任务

### 子字段

- `issue_name`
- `hit_sentence`
- `why_this_issue`

### 要求

- 第一段就要说清楚为什么是这个主题
- 不允许到正文中段用户还不确定这份报告在讲什么问题

## 7.3 issue_evidence

### 作用

- 承担“为什么会判断成这个议题”的证据任务

### 子字段

- `summary`
- `anchors`
- `input_signals`

### 要求

- 必须把画面依据与主题输入连起来
- 若意图或感受存在，应在这里真正参与判断

## 7.4 core_tension

### 作用

- 承担“该议题里的核心拉扯”任务

### 子字段

- `visible_conflict`
- `hidden_need`
- `protective_move`

### 要求

- 要让用户看懂自己在该议题里为什么会摇摆
- 不能只写结果，不写内在矛盾

## 7.5 scene_connection

### 作用

- 承担“落回现实场景”任务

### 子字段

- `typical_scene`
- `recurring_moment`
- `current_impact`

### 要求

- 场景必须具体
- 不能只停在抽象描述

## 7.6 repeat_mechanism

### 作用

- 承担“为什么它会反复发生”任务

### 子字段

- `trigger`
- `automatic_response`
- `reinforcing_result`

### 要求

- 要有最小闭环
- 让用户看到问题为何持续自我加强

## 7.7 next_step

### 作用

- 承担“议题向下一步”任务

### 子字段

- `direction`
- `action`
- `followup_option`

### 要求

- 必须围绕该议题成立
- 不能退回通用建议

## 7.8 theme_plan_bridge

### 作用

- 为 `主题方案` 承接预留接口

### 子字段

- `suitable_path`
- `why_continue`

### 要求

- 只做轻桥接
- 不能把整份报告写成方案预告

## 8. 当前阶段收束建议

基于以上定义，当前建议先收束到下面 4 个判断：

1. 议题聚焦报告必须先证明“这个问题为什么成立”
2. 它的中段核心不是泛分析，而是问题矛盾与现实场景
3. 它需要一条最小的“触发 -> 自动反应 -> 强化结果”闭环
4. 它的结尾应优先承接 `主题方案` 或 `Journey 报告`
