## 1. 问题定义

当前 `Paperclip` 面板中的 workflow 区域，默认按 workflow 展开全部历史 run。

这会带来 3 个直接问题：

1. 用户在看 `ci / deploy / nightly-smoke` 时，首屏首先看到的是一长串历史红绿记录，而不是“当前是否健康”。
2. 较早提交上的失败 run 会长期保留为红色视觉噪音，即使这些失败已经被后续绿色 run 覆盖，也仍像“待处理问题”一样占据注意力。
3. CI/CD 在 GitHub 中更接近“最近几次是否健康”的判断对象，但在 Paperclip 中被误表现成“所有历史失败都需要补修的债务清单”。

用户真实关注点更接近：

- 最近几条是不是绿的
- 当前分支 / 当前发布链路是不是通的
- 当前有没有持续性红灯值得处理

而不是：

- 把过去每一次失败都当成当前待办

## 2. 目标

本规则要把 `Paperclip` 面板中的 CI/CD 视图改造成与 GitHub 更一致的判断模型：

1. 默认先回答“现在健康吗”
2. 历史 run 默认作为追溯材料，而不是首屏待办
3. 只有当前主链仍受阻，或同类失败连续发生，旧红灯才继续升级为当前问题

## 3. 非目标

本轮不做：

1. 不要求删除真实 run history
2. 不要求取消失败同步到 Paperclip issue
3. 不要求重写 GitHub Actions 或 self-hosted runner 架构
4. 不把所有历史 issue 批量关闭成“看起来全绿”

## 4. 核心判断模型

### 4.1 workflow 面板的默认对象

workflow 面板默认展示的对象不应是“所有历史 run”。

它应优先展示两层：

1. workflow 当前状态摘要
2. 最近窗口内的 run 样本

推荐默认窗口：

- `recent_window = 最近 5 次 run`

如果空间更紧，可退化为：

- `recent_window = 最近 3 次 run`

### 4.2 当前状态摘要的计算规则

每条 workflow 在首屏只应暴露一个当前状态摘要：

- `healthy`
  - 最近一次 terminal run 为绿色
  - 最近窗口内没有形成连续失败
- `failing`
  - 最近一次 terminal run 为红色
- `degraded`
  - 最近窗口内存在红绿交替或告警态，需要关注但不一定阻塞
- `running`
  - 当前有 run 正在执行
- `blocked`
  - 当前 run 因 runner、权限、workspace drift 等无法进入有效执行

这里的 terminal run 指：

- `success`
- `failure`
- `cancelled`
- 其他已经结束且可判定结果的状态

### 4.3 历史红灯何时不再算当前问题

满足下面任一条件时，历史失败默认不再作为当前待处理对象：

1. 同一 workflow 在更新的提交上已经出现成功 run
2. 同一分支同一 job 的失败已被更近一次绿色 run 覆盖
3. 对应 commit-summary 父任务已进入 `done`
4. 当前主分支 / 发布分支不再被该失败阻塞

这类 run 仍可保留在历史明细中，但不应继续在首屏以“当前红灯”语义占位。

### 4.4 历史红灯何时仍应保留为当前问题

旧失败只有在下面情况才应继续升级为当前信号：

1. 同类失败在最近窗口内连续发生，形成 `持续红灯`
2. 当前最新 run 仍然失败
3. 当前最新 run 虽未失败，但处于 `blocked` 或 `queued timeout`
4. 该失败对应的是当前发布门，例如：
   - `main -> dev` 最近一次 deploy 失败，且尚无后续成功 deploy 覆盖
   - `release -> prod` 最近一次 deploy / smoke 失败，且尚无后续成功 run 覆盖
5. 该失败已被显式提升为需要持续处理的 Paperclip issue

## 5. workflow 视图结构

### 5.1 第一层：workflow 摘要

`ci / deploy / nightly-smoke / auto-repair` 每一项首屏只显示：

- 当前状态图标
- workflow 名称
- 最近一次 terminal run 编号
- 最近一次 terminal run 时间
- 最近窗口内的趋势摘要

趋势摘要推荐写法：

- `最近 5 次：4 绿 1 红`
- `最近 5 次：1 红 4 灰`
- `最近 3 次：连续 2 次失败`

### 5.2 第二层：最近窗口

展开 workflow 后，默认只显示最近窗口内的 runs，而不是全部历史。

推荐展示顺序：

1. 当前运行中的 run
2. 最近一次 terminal run
3. 其余最近窗口内的 runs

### 5.3 第三层：历史记录

历史 run 必须进入单独的折叠层，例如：

- `查看更早记录`
- `历史 run`

默认收起，不进入首屏判断。

## 6. 与 Paperclip issue 的关系

### 6.1 run history 和 issue 不是同一个对象

run history 是事实流。

Paperclip issue 是协作对象。

两者必须分开理解：

1. run 失败，不等于永远有一个当前待处理问题
2. 只有失败仍影响当前主链，或被升级为持续问题时，才应继续占据协作首屏

### 6.2 commit-summary 的正确语义

`commit-summary` 父任务已经接近正确模型：

- 它只汇总某次提交下的失败项
- 后续更近提交成功后，这个父任务应进入“已被覆盖或已恢复”的收束语义

因此 workflow 面板不应再用“所有历史 run 都红着挂在那里”的方式，重复制造第二份待办。

## 7. GitHub 对齐原则

如果 GitHub 与 Paperclip 展示发生冲突，当前规则优先向 GitHub 的操作心智对齐：

1. CI/CD 首先是“当前健康度面板”
2. 历史 run 首先是“审计与追溯材料”
3. 持续性故障才是“当前待处理问题”

## 8. 验收标准

完成改造后，用户应能在 5 秒内回答下面问题：

1. `ci` 现在是不是绿的
2. `deploy` 当前是不是可放行
3. 最近一次失败是不是已经被后续绿色覆盖
4. 哪一类问题是当前真的还需要处理的

如果用户还需要在十几条旧红灯里人工判断“哪些其实已经没事了”，则说明该视图仍未达标。
