## 1. 目的

本文件专门把当前 `To C MVP` 已经收好的页面与状态，统一汇总成一张总表。

它重点回答：

1. 当前主链路到底有哪些页面状态
2. 每个状态的用户任务是什么
3. 每个状态下一步会去哪里
4. 当后续文档越来越多时，应该先以哪张表为总入口

## 2. 当前适用范围

本表当前覆盖：

1. `upload`
2. `detect`
3. `report-choice`
4. `selected-generating`
5. `selected-ready`
6. `history`
7. `existing`
8. 主链路异常与回退状态

当前不覆盖：

1. `Journey`
2. To B / Studio
3. 运营后台
4. 更未来的陪伴产品

## 3. 当前最重要的收束判断

本轮先收束到下面 8 个判断：

1. 当前主链路已经不是“先 Lite 再 Pro”
2. 当前主链路是“上传 -> 识别 -> Lite/Pro 选择 -> loading -> 对应结果页”
3. `Lite / Pro` 的分流当前由用户自己选，不是系统推荐
4. 结果页 CTA 规则只在结果页生效，不前置到选择页或 loading 页
5. `history` 是回看入口，不是新一轮分流入口
6. `existing` 是复用语义，不是异常报错
7. 异常状态的任务是恢复流程，不是继续销售
8. 后续页面改动都应先回到这张总表校验

## 4. 页面状态总表

| 状态 id | 页面 / 状态名称 | 当前用户任务 | 主要输入 | 主要输出 | 下一步 |
|---|---|---|---|---|---|
| `upload` | 上传页 | 上传作品，补充基础描述，可选主题 | 图片、简单背景、主题 | 可进入三圈识别的输入 | `detect` |
| `detect` | 三圈识别 | 完成作品识别，必要时确认或修正 | 图片 | 识别结果与几何参数 | `report-choice` |
| `report-choice` | Lite / Pro 选择页 | 用户自己选择这次要用 `Lite` 还是 `Pro` | 已识别作品、基础信息、可选主题 | 所选报告层级 | `selected-generating` |
| `selected-generating` | Lite / Pro loading 页 | 等待对应报告生成 | 所选报告层级 | 对应 `Lite` 或 `Pro` 报告数据 | `selected-ready` |
| `selected-ready` | Lite / Pro 结果页 | 阅读结果并执行页面内后续动作 | 已生成报告 | 结果页 CTA 与辅助动作 | `upload` / `history` / 当前页内动作 |
| `history` | 历史记录页 | 回看已有记录 | 用户已有报告列表 | 打开某条已有 `Lite` 或 `Pro` 记录 | `selected-ready` |
| `existing` | 已有记录复用提示 | 理解这次已有对应记录并直接复用 | 当前输入命中已有记录 | 打开已有记录或重生 | `selected-ready` 或当前链路重试 |

## 5. 页面职责拆分

## 5.1 上传页

上传页只负责：

1. 进入主链路
2. 收集最少必要输入
3. 让用户知道后面会先识别，再进入选择页

上传页不负责：

1. 推荐 `Lite / Pro`
2. 展示结果页 CTA
3. 讲复杂价格逻辑

## 5.2 识别页

识别页只负责：

1. 完成三圈识别
2. 让用户理解当前还没开始解读生成

识别页不负责：

1. 提前生成报告
2. 直接跳结果页

## 5.3 Lite / Pro 选择页

选择页只负责：

1. 解释 `Lite` 和 `Pro` 的差异
2. 露出价格
3. 让用户自己做选择

选择页不负责：

1. 黑盒推荐
2. 再插入新的中间页
3. 结果页 CTA

## 5.4 loading 页

loading 页只负责：

1. 承接等待
2. 明确当前正在生成哪一种报告
3. 生成完成后直接跳结果页

loading 页不负责：

1. 再次分流
2. 继续销售
3. 提前出现结果页按钮

## 5.5 结果页

结果页只负责：

1. 完成交付
2. 承接当前可走通的 CTA
3. 提供页面内辅助动作

结果页不负责：

1. 推出未来产品货架
2. 重写选择页逻辑

## 5.6 history / existing

history 与 `existing` 只负责：

1. 回看已有结果
2. 复用已有记录
3. 避免无提示重复生成

history 与 `existing` 不负责：

1. 重新分流
2. 强推升级
3. 加入未来入口

## 6. 当前主链路状态转移

当前建议的最小状态转移如下：

1. `upload -> detect`
2. `detect -> report-choice`
3. `report-choice -> selected-generating`
4. `selected-generating -> selected-ready`
5. `selected-ready -> upload`
6. `selected-ready -> history`
7. `history -> selected-ready`
8. `existing -> selected-ready`

## 7. 当前异常与回退状态转移

当前建议的最小回退关系如下：

1. `upload` 失败
   - 留在 `upload`
2. `detect` 失败
   - 回到 `upload` 或识别前一层
3. `report-choice` 加载失败
   - 重试 `report-choice` 或返回 `upload`
4. `selected-generating` 失败
   - 返回 `report-choice`
5. `selected-generating` 超时
   - 继续等待或返回 `report-choice`
6. 命中 `existing`
   - 直接打开已有 `Lite` 或 `Pro`

## 9. 当前最需要避免的写法

当前最需要避免下面 8 种情况：

1. 把当前主链路重新写回“先 Lite 再 Pro”
2. 把选择页写成推荐页
3. 把 loading 页写成结果页前的销售页
4. 把 history 写成升级入口
5. 把 `existing` 写成错误态
6. 让异常页承担产品分流任务
7. 不同文档里写出不同价格口径
8. 不同文档里写出不同下一步跳转

## 10. 当前阶段收束结论

基于以上总表，当前建议先收束到下面 5 个判断：

1. 当前主链路已经可以用一张状态表完整描述
2. 各页面的职责边界已经相对清楚，不应再混写
3. 后续任何页面改动，都应先回到这张总表核对状态与跳转
4. QA 与 spec 都应以这张总表作为总入口之一
5. 如果未来流程再改，应优先先改这张总表，再改分文档
