## 1. 目的

本文件专门回答：

- `Journey 报告` 的正文到底由哪些内容块组成
- 这些内容块各自承担什么任务
- 生成侧应该输出哪些结构化字段
- 当前如果要兼容现有 `pro_v1.6` 链路，建议怎么映射

这份文档不是页面视觉稿，也不是 prompt 文案本身。

它是：

- 内容结构定义
- structured schema 前置定义
- 页面渲染与生成实现之间的共同接口说明

## 2. 继承的上游结论

本文件继承以下前提：

1. `Journey 报告` 是 `基于多次历史画作的深度机制型分析报告`
2. 它的核心用户任务是：
   - 更深层主判断
   - 机制递进
   - 重复模式解释
   - 优先级判断
   - 后续方向承接
3. 它的最小内容骨架是：
   - 深层主判断
   - 历史画作总览
   - 结构化执行摘要
   - 机制拆解
   - 根源递进
   - 优先级判断
   - 后续方向

## 3. 本轮做什么 / 不做什么

### 3.1 本轮做什么

本轮明确：

- 内容块定义
- 字段层级
- 字段命名建议
- 每个字段的生成要求
- 当前兼容实现映射

### 3.2 本轮不做什么

本轮不直接定义：

- 最终对外文案语气
- 最终 UI 排版
- 具体价格
- 21 天定制方案的详细内容结构
- 长期 AI 陪伴的详细产品结构

## 4. 结构设计原则

Journey 报告的结构，不应只是“更长”，而应真正体现深度质变。

当前建议遵循以下 6 条原则：

1. `先确认历史序列成立`
   - 必须先有多次画作，才能进入 Journey
2. `先给更深层主判断`
   - 开头要让用户知道“这次多看见了什么”
3. `先总览，再递进`
   - 先给执行摘要，再进入拆解
4. `机制必须连成链`
   - 不能只有很多段分析，缺少因果递进
5. `根源要分层，不要混写`
   - 表层、深层、核心位置必须可区分
6. `结尾给优先级，不给空口号`
   - 不能只是“更爱自己”“更觉察自己”

## 5. 当前建议的内容块

当前建议将 `Journey 报告` 拆成 `7` 个主内容块与 `2` 个辅助内容块。

### 5.1 七个主内容块

1. `标题`
   - 给整份深层报告定一个主轴
2. `深层主判断`
   - 告诉用户这次多看见了什么
3. `历史画作总览`
   - 先确认反复出现的时间性线索
4. `结构化执行摘要`
   - 用高压缩度总结整份报告核心
5. `机制拆解`
   - 解释状态、模式、保护、代价如何运作
6. `根源递进`
   - 把问题从表层现象推进到更深层位置
7. `优先级与后续方向`
   - 告诉用户现在先处理什么，以及之后往哪走

### 5.2 两个辅助内容块

1. `三圈与微观证据`
   - 用于承载画面结构证据
2. `分阶段建议`
   - 作为后续推进提示，但不能代替 program 本身

## 6. Canonical 内容结构

当前建议把 `Journey 报告` 的 canonical 内容结构定义为：

```yaml
deep_pattern_report:
  title: string
  history_overview:
    series_summary: string
    repeated_signals: string[]
    contrast_points: string[]
  deep_judgment:
    opening: string
    deeper_shift: string
    bridge: string
  executive_summary:
    energy_essence: string
    core_pattern: string
    key_stuck_point: string
    priority_direction: string
    healing_axis: string
  evidence_chain:
    cross_work_summary: string
    recurring_anchors: string[]
    turning_points: string[]
  mechanism_breakdown:
    current_state: string
    sustaining_loop: string
    protective_logic: string
    current_cost: string
    life_manifestation: string
  root_progression:
    surface: string
    deeper_pattern: string
    core_belief: string
  priority_decision:
    what_first: string
    why_now: string
    if_ignored: string
  next_path:
    immediate_direction: string
    practical_action: string
    followup_option: string
  phased_support:
    - phase: string
      focus: string
      practice: string
```

说明：

- 这是一份“产品语义结构”
- 不等于当前必须一步到位改完所有代码
- 但后续 prompt / schema / 页面应尽量向这份 canonical 结构靠拢

## 7. 字段定义

## 7.1 title

### 作用

- 让用户快速进入整份深层报告的主轴

### 要求

- 要比自我理解报告更稳
- 不能只是文艺短句
- 要能暗示“这次看到的是更深一层”

## 7.2 deep_judgment

### 作用

- 承担“更深层主判断”任务

### 子字段

- `opening`
  - 第一击命中
- `deeper_shift`
  - 点出这次比主报告多看见了什么
- `bridge`
  - 过渡到后文

### 要求

- 必须先被看见，再进入深度分析
- 不能一上来像摘要表

## 7.3 executive_summary

### 作用

- 承担“先总览后拆解”任务

### 子字段

- `energy_essence`
- `core_pattern`
- `key_stuck_point`
- `priority_direction`
- `healing_axis`

### 要求

- 读完后用户应能抓住整份报告主轴
- 每个字段都要有信息增量，不能同义改写

## 7.4 evidence_chain

### 作用

- 承担“为什么会这么判断”的证据任务

### 子字段

- `cross_work_summary`
- `recurring_anchors`
- `turning_points`

### 要求

- 证据必须支持跨时间机制分析
- 不能只是单幅画面的描述堆叠

## 7.5 mechanism_breakdown

### 作用

- 承担“机制如何运作”的核心任务

### 子字段

- `current_state`
- `sustaining_loop`
- `protective_logic`
- `current_cost`
- `life_manifestation`

### 要求

- 要把状态、保护、代价和现实表现串起来
- 至少有一条完整运作回路

## 7.6 root_progression

### 作用

- 承担“根源递进”任务

### 子字段

- `surface`
- `deeper_pattern`
- `core_belief`

### 要求

- 三层必须递进
- 不能把表层现象直接当作核心信念

## 7.7 priority_decision

### 作用

- 承担“优先级判断”任务

### 子字段

- `what_first`
- `why_now`
- `if_ignored`

### 要求

- 要帮用户收束，而不是继续扩散
- 不能停留在“都很重要”

## 7.8 next_path

### 作用

- 承担“后续方向承接”任务

### 子字段

- `immediate_direction`
- `practical_action`
- `followup_option`

### 要求

- 既要有当下可做的一步
- 也要给出更长路径方向

## 7.9 phased_support

### 作用

- 提供辅助性的阶段推进建议

### 要求

- 只能作为延伸
- 不能把整份报告写成 program

## 8. 当前兼容实现映射建议

当前如需兼容 `pro_v1.6`，建议先做以下映射：

| canonical 字段 | 当前可兼容来源 |
|---|---|
| `deep_judgment` | `first_impression` |
| `executive_summary` | `core_insight_table` |
| `history_overview` | `待历史画作序列能力补齐` |
| `evidence_chain.recurring_anchors` | `待历史画作对照能力补齐` |
| `mechanism_breakdown` | `imbalance_confirmed` |
| `root_progression` | `root_cause` |
| `phased_support` | `healing_suggestions` |

说明：

1. 当前 `pro_v1.6` 已具备部分 Journey 报告骨架
2. 但字段仍更接近“深度通用解读”
3. 后续应把字段语义从“章节名”继续收束到“任务名”

## 9. 当前阶段收束建议

基于以上定义，当前建议先收束到下面 4 个判断：

1. Journey 报告必须有一条稳定的 `证据 -> 机制 -> 根源 -> 优先级` 主线
2. 它不能再被定义为“更长版本”
3. 它需要比当前 `Pro` 原型更清楚地区分执行摘要、机制拆解和根源递进
4. 它的结尾应优先服务后续承接，而不是只留下一段漂亮结语
