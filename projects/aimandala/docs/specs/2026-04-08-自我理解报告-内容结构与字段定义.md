## 1. 目的

本文件专门回答：

- `自我理解报告` 的正文到底由哪些内容块组成
- 这些内容块各自承担什么任务
- 生成侧应该输出哪些结构化字段
- 当前如果要兼容现有 `lite_v1.6` 链路，建议怎么映射

这份文档不是页面视觉稿，也不是 prompt 文案本身。

它是：

- 内容结构定义
- structured schema 前置定义
- 页面渲染与生成实现之间的共同接口说明

## 2. 继承的上游结论

本文件继承以下前提：

1. `自我理解报告` 是 `核心理解型报告`
2. 它的核心用户任务是：
   - 被看见
   - 被解释
   - 被命名
   - 被连接
   - 被指引
3. 它的最小内容骨架是：
   - 整体命中句
   - 画面依据
   - 状态解释
   - 模式命名
   - 现实连接
   - 一个下一步

## 3. 本轮做什么 / 不做什么

### 3.1 本轮做什么

本轮明确：

- 内容块定义
- 字段层级
- 字段命名建议
- 每个字段的生成要求
- 当前兼容实现映射

### 3.2 本轮不做什么

本轮不直接定义：

- 最终对外文案语气
- 最终 UI 排版
- 具体价格
- 最终主题分流策略
- Journey 报告或议题聚焦报告的字段定义

## 4. 结构设计原则

自我理解报告的结构，不应只是“看起来丰富”，而应服务五个用户任务。

当前建议遵循以下 5 条原则：

1. `先命中，后展开`
   - 开头必须快，不要先铺垫方法论
2. `先依据，后结论`
   - 不能只有判断，没有来源
3. `先整理，后延伸`
   - 先把用户当前状态整理清楚，再考虑扩展阅读
4. `一条主线，不要散`
   - 各段要能串成同一条理解链
5. `结尾只给一个下一步`
   - 不要把报告写成训练计划

## 5. 当前建议的内容块

当前建议将 `自我理解报告` 拆成 `6` 个主内容块与 `2` 个辅助内容块。

### 5.1 六个主内容块

1. `标题`
   - 让用户快速进入这份报告的主状态
2. `整体命中`
   - 第一时间建立“这说中了我”的感觉
3. `画面依据`
   - 说明为什么会这样理解
4. `状态解释`
   - 解释用户当前处在什么状态
5. `模式命名`
   - 帮用户把模糊感整理成结构
6. `现实连接与下一步`
   - 把内在状态落到现实，并给出一个可继续的方向

### 5.2 两个辅助内容块

1. `主题洞察`
   - 当主题不是“整体”时，帮助报告聚焦阅读角度
2. `日常小觉察`
   - 作为低压行动承接，不可喧宾夺主

## 6. Canonical 内容结构

当前建议把 `自我理解报告` 的 canonical 内容结构定义为：

```yaml
self_understanding_report:
  title: string
  opening_hit: string
  visual_evidence:
    summary: string
    anchors: string[]
  state_interpretation:
    current_state: string
    emotional_tension: string
    explanation_chain: string
  pattern_naming:
    pattern_name: string
    pattern_description: string
    protective_logic: string
  reality_connection:
    life_dimension: string
    typical_scene: string
    current_impact: string
  next_step:
    direction: string
    action: string
  theme_insights:
    scene: string
    impact: string
    awareness: string
  daily_awareness:
    - day: number
      title: string
      content: string
```

说明：

- 这是一份“产品语义结构”
- 不等于当前必须一步到位改完所有代码
- 但后续 prompt / schema / 页面应尽量向这份 canonical 结构靠拢

## 7. 字段定义

## 7.1 title

### 作用

- 给整份报告定一个主轴

### 要求

- 3-8 个字为宜
- 有画面感
- 能点出当前状态主线
- 不要过度悬浮或纯诗化

### 失败信号

- 看完标题还不知道大概在讲什么

## 7.2 opening_hit

### 作用

- 承担“被看见”任务

### 要求

- 第一段即建立命中感
- 2-3 句即可
- 不能太长
- 不能全是形容词堆积

### 必须回答的问题

- 你现在大概处在什么状态
- 为什么这份报告值得继续读下去

## 7.3 visual_evidence

### 作用

- 承担“被解释”的起点

### 子字段

- `summary`
  - 一段完整说明
- `anchors`
  - 2-4 个最关键的画面锚点

### 要求

- 不能只是罗列元素
- 要把画面特征和理解方向连起来

### 示例语义

- 哪些地方让我们判断你是在收束、试探、扩张、保护、拉扯

## 7.4 state_interpretation

### 作用

- 解释用户当前的核心状态

### 子字段

- `current_state`
  - 当前最主要的状态判断
- `emotional_tension`
  - 当前最主要的内在拉扯
- `explanation_chain`
  - 画面依据如何导向这个判断

### 要求

- 不能只有结论
- `explanation_chain` 必须能复述“为什么这么判断”

## 7.5 pattern_naming

### 作用

- 承担“被命名”任务

### 子字段

- `pattern_name`
  - 一个通俗但清楚的命名
- `pattern_description`
  - 说明这种模式是什么
- `protective_logic`
  - 说明这种模式为什么会形成

### 要求

- 不追求术语感
- 重点是帮助用户从模糊进入清楚

## 7.6 reality_connection

### 作用

- 承担“被连接”任务

### 子字段

- `life_dimension`
  - 关系 / 情绪 / 表达 / 事业阶段 / 整体状态
- `typical_scene`
  - 典型场景
- `current_impact`
  - 当前影响

### 要求

- 必须落在现实生活
- 不要只停在抽象描述

## 7.7 next_step

### 作用

- 承担“被指引”任务

### 子字段

- `direction`
  - 接下来应该把注意力放在哪里
- `action`
  - 一个低压、可执行、今天就能开始的动作

### 要求

- 只给一个主方向
- 不要变成长训练计划

## 7.8 theme_insights

### 作用

- 把主题输入变成正文的一部分

### 子字段

- `scene`
  - 该主题下的典型场景
- `impact`
  - 该主题下的具体影响
- `awareness`
  - 该主题下的一个觉察点

### 要求

- 当主题不为 `整体` 时，这块必须明显存在
- 不能只是把主题原样复述一遍

## 7.9 daily_awareness

### 作用

- 提供轻量行动承接

### 子字段

- `day`
- `title`
- `content`

### 要求

- 建议 3 条
- 每条都应与本次报告主状态相关
- 不能写成通用鸡汤建议

## 8. 当前建议的页面阅读顺序

虽然本文件不直接定义 UI，但为了避免字段顺序与阅读顺序错位，当前建议页面主顺序为：

1. `title`
2. `opening_hit`
3. `visual_evidence.summary`
4. `state_interpretation.current_state`
5. `state_interpretation.emotional_tension`
6. `pattern_naming.pattern_name + pattern_description`
7. `reality_connection.typical_scene + current_impact`
8. `next_step.direction + action`
9. `theme_insights`
10. `daily_awareness`

说明：

- `theme_insights` 和 `daily_awareness` 都是辅助块
- 它们不应抢走主结构的位置

## 9. 当前兼容实现映射

为了兼容现有 `lite_v1.6` 链路，当前建议先做一层映射，而不是立即推翻现有字段名。

## 9.1 当前实现中的现成字段

当前已有字段包括：

- `title`
- `overall_impression`
- `visual_elements`
- `emotion_portrait`
- `story`
- `theme_scene`
- `theme_impact`
- `theme_awareness`
- `three_awareness`
- `pro_teaser`

这些字段可以先作为迁移壳使用。

## 9.2 建议映射关系

| canonical 字段 | 当前兼容字段 | 当前说明 |
|---|---|---|
| `title` | `title` | 可直接复用 |
| `opening_hit` | `overall_impression` | 可先承接“整体命中” |
| `visual_evidence.summary` | `visual_elements` | 可先承接“画面依据” |
| `state_interpretation.current_state` | `emotion_portrait` 前半段 | 当前可临时借位 |
| `state_interpretation.emotional_tension` | `story.contradiction` | 可先承接“核心拉扯” |
| `state_interpretation.explanation_chain` | `story.base` + `visual_elements` | 当前需要组合理解 |
| `pattern_naming.pattern_name` | `story.pattern` 标题层语义 | 当前无独立字段，后续建议新增 |

| `pattern_naming.protective_logic` | `story.defense` | 可先承接 |

## 9.3 当前不建议继续强化的旧字段

以下字段在自我理解报告语境下不建议继续作为主结构强化：

- `story.light`
  - 可以保留，但不必再把“六段故事”当成唯一框架
- `pro_teaser`
  - 它是分流字段，不应主导报告结构
- `six_insights_rendered`
  - 更适合作为兼容层，而不是未来主结构
- `experiment_rendered`
  - 在自我理解报告里不应再占据核心位置

## 10. Prompt / Schema 建议

如果后续进入 prompt 或 schema 重写，当前建议：

### 10.1 短期

- 继续沿用当前 `lite_v1.6` 外壳
- 但 prompt 内容按 `自我理解报告` 语义重写
- 让模型输出更接近本文件的 canonical 结构
- 这里的 `lite_v1.6` 只表示迁移期兼容壳，不代表商品层 `Lite` 仍等于 `自我理解报告`

### 10.2 中期

- 新增一份专属 schema，例如：
  - `self_understanding_report_v1.yaml`
- 不再借用 `Lite` 作为语义名称

### 10.3 长期

- 页面结构、schema、prompt、结果页分流都统一回到 `自我理解报告` 这个真实产品定义

## 11. 验收标准

一版成立的字段定义，至少应满足：

1. 内容块和用户任务一一对应
2. 结构足够稳定，能接 prompt 和页面
3. 当前实现可以找到兼容映射
4. 后续可逐步去掉旧 `Lite` 语义依赖

## 12. 下一步建议

基于本文件，后续最适合继续推进的是：

1. 把当前 `lite_v1.6` prompt 与 schema 改写成 `自我理解报告` 语义
2. 补一份 `自我理解报告` 结果页结构 spec
3. 开始定义 `议题聚焦报告` 的内容结构与字段定义
