## 1. 目的

本文件专门定义：

- `议题聚焦报告` 到底是什么
- 它主要服务谁
- 它要帮用户完成什么任务
- 它和 `自我理解报告`、`Journey 报告` 的边界在哪里
- 它当前最小可交付版本应长什么样

这份文档是新报告矩阵下第二份主报告展开 spec。

当前默认判断是：

- `议题聚焦报告` 不应被理解为一个独立价格层
- 它更适合作为 `Pro` 商品层里的主题向版本

因此，后续若要继续推进：

- 主题入口分流
- 主题化报告结构
- 主题方案承接逻辑
- 报告矩阵定价与升级路径

都应优先回到本文件校验。

## 2. 本轮任务级别

本轮属于：

- `局部实验中的主干定义`

更具体地说，是：

- 在已确认的四类报告矩阵内，优先展开最有商业潜力的第二类主报告

它不是：

- 对整个项目定位的重写
- 对全部主题系统的最终实现定义
- 对所有报告类型的最终 UI 结论

## 3. 继承的上游结论

本文件明确继承以下判断，不重复改写：

1. `一镜一梳` 的报告产品本质是 `理解产品`
2. 报告的一级任务是：
   - 被看见
   - 被解释
   - 被命名
   - 被连接
   - 被指引
3. 报告长期不应再按 `Lite / Pro` 作为唯一主框架
4. 当前建议的报告矩阵包含：
   - 当下映照报告
   - 自我理解报告
   - 议题聚焦报告
   - Journey 报告
5. `议题聚焦报告` 当前更适合作为 `Pro` 的主题向版本
6. 它与 `自我理解报告` 的同价，更应理解为同属 `Pro`

## 4. 本轮允许变化 / 禁止变化

### 4.1 本轮允许变化

本轮允许继续定义：

- 议题聚焦报告的目标用户
- 议题聚焦报告的适用主题范围
- 议题聚焦报告的最小内容结构
- 议题聚焦报告与其他报告的边界
- 议题聚焦报告结果页的后续承接原则

### 4.2 本轮禁止变化

本轮不在这里改写：

- 整个项目的目标用户
- 整个产品矩阵
- 所有主题的完整知识库结构
- 主题方案与 21 天定制方案的具体产品定义
- 最终商业化结账策略

## 5. 产品定位

`议题聚焦报告` 的一句话定义是：

- 围绕一个已经明确的现实主题，把“这张画为什么会指向这个问题”讲清楚

它的本质是：

- `问题向理解型报告`

它不是：

- 泛泛讲“你是谁”的通用报告
- 低压情绪安放卡片
- 更长的自我理解报告
- 深层根源剖析方案
- 连续训练计划

## 6. 核心目标用户

### 6.1 第一优先用户

- `议题解决型`

她的典型心态是：

- “我不是泛泛地想看自己，我就是卡在关系里。”
- “我想知道为什么边界这件事总会反复出问题。”
- “我想知道这张画和我当前这个现实问题到底有什么关系。”

### 6.2 第二优先用户

- `自我理解型` 中已经把问题收束到单一主题的那部分用户

她的典型心态是：

- “我大概知道自己怎么了，但我更想搞清楚这件事为什么发生在关系/表达/事业上。”

### 6.3 可兼容用户

- `情绪安放型` 中问题已收束、但仍需要低压理解的人

她的典型心态是：

- “我现在最影响我的不是全部人生，而是最近某个主题一直在消耗我。”

### 6.4 不优先服务的用户

以下用户不应默认由议题聚焦报告主承接：

1. 还处在泛模糊状态、并未聚焦到具体主题的用户
   - 更适合 `自我理解报告`
2. 只想先被轻轻接住、不适合问题导向阅读的用户
   - 更适合 `当下映照报告`
3. 已明确想看更深机制、根源与优先级的高意愿用户
   - 更适合 `Journey 报告`
4. 高复杂度支持型用户
   - 不应由 AI 报告主承接

## 7. 用户任务定义

议题聚焦报告最核心要完成的，不是“把某个主题讲得很多”，而是完成下面五件事。

### 7.1 让我确认这份报告真的在说这个问题

用户任务：

- “我想先确认，这份报告讲的不是泛泛的我，而就是我现在卡住的这个主题。”

对应要求：

- 开头必须快速点中该主题
- 第一屏就要让用户知道“这份报告为什么和这个问题有关”

### 7.2 让我知道为什么这张画会指向这个议题

用户任务：

- “我不只想听结论，我想知道为什么会判断成关系/边界/事业问题。”

对应要求：

- 必须有“画面依据 -> 议题判断”的解释链
- 不能只是先假设主题成立，再在后面补文字

### 7.3 让我看清这个议题里的核心拉扯

用户任务：

- “我想知道，在这个问题里，到底是哪两股力量在拉扯我。”

对应要求：

- 报告必须说明该议题里的核心矛盾
- 不能只给笼统的人格描述

### 7.4 让我知道它在现实里怎么反复发生

用户任务：

- “我想知道，这件事为什么总在具体场景里一次次重演。”

对应要求：

- 必须落回现实场景
- 至少给出一个高相似度的典型情境
- 需要解释它为什么会反复出现

### 7.5 让我知道在这个议题里下一步先做什么

用户任务：

- “我不想只看懂问题，我想知道在这个主题里最先该动哪一下。”

对应要求：

- 只给一个围绕该议题的下一步
- 不能退回泛建议
- 要为后续承接 `主题方案` 留出接口

## 8. 议题聚焦报告的独特价值

相对于其他三类报告，议题聚焦报告最独特的地方不是：

- 最长
- 最深
- 最便宜
- 最通用

而是：

- 它最擅长把“一个已经明确的问题”讲准、讲实、讲到现实里

它的独特价值在于：

1. 比 `自我理解报告` 更聚焦
2. 比 `当下映照报告` 更问题导向
3. 比 `Journey 报告` 更贴近当前现实议题，而不是先去挖最深层机制
4. 它最适合成为 `主题方案` 的前置理解层

## 9. 与其他报告的边界

### 9.1 与当下映照报告的边界

当下映照报告：

- 更偏“先接住、先确认当下状态”

议题聚焦报告：

- 更偏“围绕一个问题看清楚它为什么会反复发生”

关键差异是：

- 议题聚焦报告必须比当下映照报告多出明确的主题判断与场景解释

### 9.2 与自我理解报告的边界

自我理解报告：

- 更回答“我到底怎么了”

议题聚焦报告：

- 更回答“为什么这件事会在这个主题里反复发生”

关键差异是：

- 自我理解报告先整理整个人当前状态
- 议题聚焦报告先收束一个问题，再围绕该问题展开解释

因此：

- 议题聚焦报告不是自我理解报告的删减版
- 自我理解报告也不是议题聚焦报告的前置必经站

### 9.3 与 Journey 报告的边界

Journey 报告：

- 更回答“为什么我总会这样，以及当前先处理哪一层”

议题聚焦报告：

- 更回答“为什么这个问题会在这个主题里不断发生”

关键差异是：

- 议题聚焦报告可以解释重复，但不必递进到最深根源层次
- Journey 报告必须比它多出机制深度、根源递进和优先级判断

## 10. 适用主题范围

当前优先适合承接为议题聚焦报告的主题包括：

1. `关系`
2. `边界`
3. `情绪稳定`
4. `表达`
5. `事业阶段`

当前前台主题与知识库主题映射时，应优先考虑：

1. `father_relationship`
2. `mother_relationship`
3. `intimate_relationship`
4. `parent_child_relationship`
5. `wealth_career`
6. `health_wellness`
7. `personal_growth`

当前不建议：

- 在 `general` 主题下直接默认进入议题聚焦报告

因为：

- `general` 更适合自我理解报告先完成一次全局整理

## 11. 输入利用逻辑

议题聚焦报告当前默认应吃四层输入：

1. `主题`
   - 这是议题聚焦报告成立的前提输入
2. `绘画前意图`
   - 用于判断用户最关心的问题方向
3. `绘画过程中的感受`
   - 用于补充该议题下的情绪张力
4. `画作本身`
   - 仍然是最核心判断依据

与自我理解报告相比，它最需要强化的不是：

- 更多画面描述

而是：

- 更强地把 `主题 / 意图 / 过程感受 / 画面结果` 串成同一个问题解释链

## 12. 最小可交付版本

当前建议 `议题聚焦报告` 的最小可交付单元为：

1. 只承接一组明确主题
2. 每份报告至少同时满足下面 5 条：
   - 主题判断明确
   - 画面依据清楚
   - 核心拉扯能命名
   - 典型场景足够具体
   - 下一步围绕该议题成立
3. 结果页至少支持一个后续动作：
   - 进入 `主题方案`
   - 进入 `Journey 报告`
   - 或返回同主题再画一幅

## 13. 结果页承接原则

议题聚焦报告的结果页，不应只是“分析完结束”。

它最适合承接的后续方向是：

1. `进入主题方案`
   - 当用户已经从“理解问题”进入“愿意开始改变”
2. `进入 Journey 报告`
   - 当用户已经觉得“问题背后还有更深一层”，且已经有多次历史画作
3. `围绕同一主题再画一幅`
   - 当用户还不急着继续付费，但想继续观察变化

当前不建议它的结果页优先承接：

- 回到过于泛的自我理解报告

因为这会让用户感觉又退回去了。

## 14. 与当前迁移期原型的关系

在迁移期语境下，当前最接近议题聚焦报告的，是：

- 当前 `Pro` 原型中的一部分主题化解读能力

但旧 `Pro` 原型并不能直接等于议题聚焦报告。

原因是：

1. 旧 `Pro` 原型更偏深度通用分析
2. 议题聚焦报告要求更强的主题判断与场景聚焦
3. 它不应只是“更长的主题版 Lite”

因此，迁移期更合理的理解应是：

- 现有 `Pro` 只是一部分过渡承载壳
- 真正成立的议题聚焦报告仍需要单独定义

## 15. 当前阶段最重要的收束结论

基于以上定义，当前建议先收束到下面 5 个判断：

1. `议题聚焦报告` 不是单独价格层，而是 `Pro` 的主题向版本
2. 它的成立前提是主题明确，而不是“任何输入都能硬聚焦”
3. 它最核心的价值是“问题解释力”，不是“更多内容”
4. 它最自然的后续承接是 `主题方案` 与 `Journey 报告`
5. 它与 `自我理解报告` 的同价，本质上来自它们同属 `Pro`

## 16. 本轮做什么 / 不做什么

### 16.1 本轮做什么

本轮先明确：

- 议题聚焦报告的产品定位
- 议题聚焦报告的目标用户
- 议题聚焦报告的任务与边界
- 议题聚焦报告的适用主题范围
- 议题聚焦报告的最小可交付版本

### 16.2 本轮不做什么

本轮暂不直接定义：

- 具体 structured 字段
- 最终 prompt 结构
- 各个主题的知识库展开方式
- 页面 UI 稿
- 最终入口排序与运营策略

## 17. 后续建议

基于本轮定义，后续最适合继续补的文档应是：

1. `议题聚焦报告` 内容结构与字段定义
2. `Journey 报告` 产品定义
3. `四类报告矩阵下的入口与结果页分流策略`

如果只允许先做一篇，当前最值得优先展开的是：

- `议题聚焦报告` 内容结构与字段定义

因为：

1. 产品边界已经清楚
2. 下一步最需要把“问题向理解”翻译成可生成、可渲染的结构
3. 它会直接影响后续主题入口与报告生成实现
