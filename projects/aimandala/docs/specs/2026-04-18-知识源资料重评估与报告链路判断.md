## 1. 目的

这份文档用于替代此前旧迁移缺口叙事的判断口径。

从 `2026-04-18` 起，关于 `aimandala` 报告链路是否遵从原始解读流派，默认不再从“旧仓迁了多少”来讨论，而是直接基于：

- 已迁入 workspace 的知识源资料
- 当前正式依据的分层
- 源资料到运行时资产的映射
- 当前报告生成链路实际消费到的 runtime 位置

来重新评估。

## 2. 重评估后的总判断

当前更准确的判断是：

1. 原始流派资料已经正式进入当前 workspace，不再需要依赖旧仓绝对路径理解来源。
2. 当前问题的重点已经不是“知识库有没有迁进来”，而是“迁入后的知识在运行时被如何压缩、改写和投影”。
3. 当前 `Lite / Pro` 报告链路已经消费到部分 `V2 knowledge runtime` 资产，但还没有完整保留原始流派中的中间判断结构。
4. 因此，“现在的报告不像我们的流派”更可能是保真链路问题，而不是知识资料缺失问题。

一句话说：

- 现在要查的是“知识如何失真”，不是“知识是否存在”。

## 3. 当前正式评估基线

后续讨论报告保真、知识漂移或链路整改时，默认基线固定为这三层：

### 3.1 源资料层

入口固定为：

- [../sources/知识库构建/README.md](../sources/知识库构建/README.md)
- [../sources/知识库构建/最小必读知识源清单.md](../sources/知识库构建/最小必读知识源清单.md)
- [../sources/知识库构建/当前正式依据与使用说明.md](../sources/知识库构建/当前正式依据与使用说明.md)

这层回答：

- 我们的流派原文是什么
- 哪些资料当前算正式依据
- 哪些只是支撑参考或历史样本

### 3.2 运行时层

入口固定为：

- [../sources/知识库构建/V2运行时映射清单.md](../sources/知识库构建/V2运行时映射清单.md)

这层回答：

- 原始资料当前落在了哪些 `pack`、`build`、`knowledge_runtime`、`core/knowledge` 位置
- 哪些部分仍然被压缩
- 哪些部分只是被部分消费

### 3.3 报告链路层

默认结合：

- [../architecture/报告生成分层与信息流说明.md](../architecture/报告生成分层与信息流说明.md)
- [../architecture/V2知识库长期架构方案.md](../architecture/V2知识库长期架构方案.md)

这层回答：

- 当前报告生成到底在哪些环节消费知识
- 哪些环节仍主要依赖 projection、模板和叙事压缩
- 长期应该把哪些中间结构显式化

## 4. 为什么当前报告容易偏离流派

基于现有资料，当前偏离主要来自这几类压缩：

1. 原始流派中的“四步法”“三元结构”“主题 × 圈层 × 状态”没有完整保留为运行时中间层。
2. `Layer 0` 仍偏向聚合结果层，没有清楚拆出“视觉事实 / 知识命中 / 规则推导”。
3. narrative 与 prompt 上游仍在消费 projection 结果，而不是直接消费可追溯的原始解释结构。
4. fallback 仍然存在且可出报告，这会掩盖“知识命中不足”和“结构被压平”的真实位置。

所以当前最容易出现的情况是：

- 报告有结构
- 报告能成文
- 报告也能带一点知识痕迹
- 但报告并不能稳定呈现原始流派的判断路径

## 5. 当前应如何重新看待“报告生成缺口”

旧的“迁移缺口”说法现在应拆成下面三类问题分别判断：

### 5.1 保真缺口

回答：

- 原始流派里的结构有没有被 runtime 完整保留

重点看：

- 四步法
- 三元论
- 20 种失衡类型
- 主题特化中的圈层和状态解释链

### 5.2 消费缺口

回答：

- runtime 资产虽然存在，但当前报告链路有没有真的消费到

重点看：

- `Layer 0`
- theme context
- narrative context
- `knowledge_skeleton`

### 5.3 治理缺口

回答：

- 当前哪些内容算正式依据，哪些只是历史样本或理论支撑

重点看：

- [../sources/知识库构建/当前正式依据与使用说明.md](../sources/知识库构建/当前正式依据与使用说明.md)

这样处理后，就不会再把“资料未迁入”“链路未消费”“结构被压缩”混成一个问题。

## 6. 当前推荐的排查顺序

如果后续要继续做报告链路整改，默认顺序应是：

1. 先读 [../sources/知识库构建/最小必读知识源清单.md](../sources/知识库构建/最小必读知识源清单.md)
2. 再读 [../sources/知识库构建/当前正式依据与使用说明.md](../sources/知识库构建/当前正式依据与使用说明.md)
3. 然后对照 [../sources/知识库构建/V2运行时映射清单.md](../sources/知识库构建/V2运行时映射清单.md)
4. 最后再进入 [../architecture/报告生成分层与信息流说明.md](../architecture/报告生成分层与信息流说明.md) 和 [../architecture/V2知识库长期架构方案.md](../architecture/V2知识库长期架构方案.md)

默认不要再把已经删除的旧文档当成判断入口。

## 7. 当前结论的使用边界

这份文档当前只回答：

- 现在该用什么口径重看这件事
- “不像我们的流派”大概率卡在什么层
- 后续继续整改时应先比对哪几层

它当前不直接替代：

- 产品定义文档
- 长期架构设计文档
- runtime 细节实现说明

这些仍分别由 `specs`、`architecture` 与运行时资产目录负责。
