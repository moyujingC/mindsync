## 1. 背景

当前 `aimandala` 的知识源资料已经正式迁入 workspace，旧的“知识库还没进来多少”不再是主问题。

当前真正的问题已经收束为：

1. 原始流派资料进入 runtime 时被压缩、改写或拆散。
2. `Layer 0 -> theme_context -> narrative projection -> report contract` 这条链路没有完整保留原始流派中的中间判断结构。
3. 报告可以生成，但主要段落还不能稳定回答“这句话来自哪条知识链”。

因此本轮不再做“迁移说明补丁”，而是正式启动一轮 `源资料 -> runtime -> prompt/skeleton -> Lite/Pro 报告合同` 的保真重构。

## 2. 本轮目标

本轮总目标固定为：

1. 让 `docs/sources/知识库构建/` 中的当前正式依据，成为这条链路唯一正式知识来源入口。
2. 把 `Layer 0` 收成正式证据层，而不是聚合占位层。
3. 让 narrative、prompt 和 report skeleton 改为消费结构化证据，而不是继续消费压平后的 projection 摘要。
4. 允许同步调整 Lite / Pro 报告合同和前端承接方式，让最终报告具备可追溯来源。
5. 为后续分批实现建立 `Spec -> Architecture -> Task -> QA -> Delivery` 的正式治理闭环。
6. `Lite / Pro` 的产品语义固定按“独立产品”收口，不再把 `Pro` 定义为 `Lite` 升级版。

## 3. 当前适用范围

### 3.1 本轮覆盖

本轮覆盖以下五段链路：

1. `Source Basis`
   - 仅限 [../sources/知识库构建/当前正式依据与使用说明.md](../sources/知识库构建/当前正式依据与使用说明.md) 中 `A. 当前正式依据`
2. `Runtime Evidence`
   - `Layer0Raw`
   - `Layer0Assembler`
   - 失衡、主题、疗愈等 runtime service 的证据化输出
3. `Narrative Plan`
   - `NarrativeContextService`
   - `theme_context`
   - `knowledge_skeleton`
4. `Report Assembly`
   - Lite / Pro 草稿与最终报告装配
5. `Report Contract`
   - `report_contracts`
   - debug payload
   - 前端消费类型与渲染逻辑

### 3.2 本轮不覆盖

本轮默认不覆盖：

1. 公司级知识库治理
2. `company/knowledge-base/` 的结构重做
3. To B、Studio 或 `V3` 实验级 API
4. 不相关的页面入口、支付链路和宿主灰度机制

## 4. 当前正式判断

本轮采用下面这组固定判断，不在实现阶段重新争论：

1. 原始知识资料已进入 workspace，当前问题不是“有没有资料”，而是“资料如何失真”。
2. 当前压缩主要发生在：
   - `Layer 0`
   - `NarrativeContextService`
   - `ReportPromptPreviewBuilder`
   - `report_contracts`
3. 当前 `Lite / Pro` 报告的问题更偏“保真缺口”和“消费缺口”，而不是简单的“文案不够像”。
4. 本轮默认允许调整结果合同，但必须同轮收口后端、前端和 debug payload，不维持长期双合同。

## 5. 目标行为

本轮完成后，目标行为应满足：

1. 每个主要报告段落都能追到至少一条结构化证据链，或显式标记为 fallback。
2. `Layer 0` 必须明确区分：
   - `visual_facts`
   - `knowledge_hits`
   - `rule_evaluations`
   - `theme_projection`
   - `fidelity_flags / fallback_summary`
3. narrative 层不再自己重新拍脑袋生成主题摘要，而是装配证据层和规则层。
4. Lite / Pro 结果结构不再只暴露压平后的纯文本块，而要暴露可追溯的段落来源。
5. debug payload 必须可直接用于 drift / fidelity 检查。
6. `Lite` 必须包含独立轻疗愈区块，`Pro` 必须保留更深的完整疗愈方案。

## 6. 对外合同方向

本轮对外合同固定按下面口径收束：

1. `Lite / Pro` 结果合同允许调整。
2. 合同调整必须在同一轮同步更新：
   - 后端 `report_contracts`
   - 前端 API 类型
   - 前端结果页渲染
   - debug 展示
3. 若实现中需要过渡字段，只能作为临时兼容层，必须在 `Delivery` 中明确去留。

本轮新合同方向至少包括：

1. 主结果区分：
   - 结构化证据导出内容
   - narrative 装配内容
   - fallback 兜底内容
2. debug payload 显式提供：
   - `evidence_trace`
   - `rule_trace`
   - `fallback_summary`
   - `fidelity_flags`

## 7. 非目标

本轮明确不是为了：

1. 继续补“迁移阶段说明”
2. 把原始镜像目录整体当成运行时真理源
3. 在没有正式 spec / architecture / task / qa 的情况下直接改代码
4. 把这轮工作降级成只有文档、没有后续实现的评估项目

## 8. 成功标准

本轮总成功标准固定为：

1. 新的正式母文档链已经建立：
   - `Spec`
   - `Architecture`
   - `Task`
   - `QA basis`
   - `Delivery`
2. 后续实现批次按母计划拆成 `Batch A-D`，且每批进入实现前都单独有子计划。
3. 自动化与样本验证口径已经在 QA 中提前定义，不允许实现后临时补口径。
4. 最终交付时，至少能用固定样本证明：
   - 主题差异被稳定拉开
   - fallback 可见、可统计、可定位
   - 主要报告段落可以追溯来源
