## 0. 更正（v0.1.0 → v0.2.0）

**本文档 §4.1 的命名规范与既有设计冲突，以既有设计为准。**

`knowledge-base.md` §3.2「知识单元结构」已经定义了 ID 与版本字段，本文档写作时未纳入核查：

```yaml
id: wealth.self_worth.low_deservingness   # 点分语义 ID
type: issue_clause
layer: L3                                  # 五层知识体系
state_id: S-001
version: 0.1.0
status: case_verified                      # ai_draft / source_supported_draft / case_verified / reviewed
relay_risk: low                            # 转述风险分级
risk_level: safe
source_ref: ["...", "case-003"]
```

因此三处修正：

1. **ID 格式改为点分语义 ID**，与既有 `wealth.self_worth.low_deservingness` 一致，例如 `mandala.color.yellow_earth`、`mandala.pattern.white_split`、`mandala.imbalance.water_floods_fire`。§4.1 的 `<域码>-<两位序号>`（`C-01`）**降级为可选的短别名**，仅用于报告内引用显示（`〔来源: mandala.color.yellow_earth〕` 对来访者可见时过长）。原文「不做语义编码」的理由（「颜色名将来会改」）只对中文颜色名成立，对英文 slug 不成立——此处判断有误。
2. **版本治理不是从零开始**：`version` / `status` / `source_ref` 三个字段已在知识单元结构里设计。缺的是**实现**（写入知识库文件 + 被代码读取 + 进 `run.json`）。
3. **防泄漏已经设计过**：`knowledge-base.md` §3.2 A1 已规定「按 `source_ref` 机读过滤；考 case-X 时检索范围排除所有 `source: case-X` 的知识单元（提炼 ≠ 原文，泄漏间接但存在）」。**`_reference_case()` 的问题不是缺少防线，是硬编码注入绕过了这道防线。**

## 1. 背景

d191 已端到端跑通，报告出两版：`report.md`（干净版）与 `report.sourced.md`（溯源版）。溯源当前用「文件 + 章节号」（如 `visual-signal-map.md §4.1`）实现，有两个已知限制：章节号会漂、颜色来源偏粗。

本文档先核查实跑数据，再定 ID 体系的粒度、命名与覆盖范围。

## 3. 溯源格式评审结论

**格式：判定为对，保留。**

- `〔来源: ...〕` 挂在**句尾**、与 claim 一一对应，是正确的粒度。
- 不建议挂段级（一段里多个判断分不清哪个有依据），也不建议挂词级（标记淹没正文，干净版与溯源版无法从同一份产物切出）。
- 干净版/溯源版「一次生成、正则切两份」的做法保留，不改成两次生成（两次生成会让两版结论不一致）。

**优先级判定：先修层级断裂，再修引用塌缩。**

理由：塌缩只让溯源变糊，仍能定位到小节；层级断裂让 8 条判断（17%）**完全无法被检查**——报告里根本没有那句话，你不知道它是从 S-002 来的还是编的。

**注意：层级断裂不是 ID 体系能修的。** `S-002` 已经是稳定 ID，且 claims 里已经正确引用了 `ontology.md §4.1 根因层状态（S-002 安全感不足）`。它丢在报告生成环节。这个问题单独立项，不进本 ID 体系。

**注意：覆盖率不能用 claims 当分母算。** 当前「47/47 有来源」是循环论证——分母是 claim 自己。正确的分母是**报告里的判断句**，按那个算，解读正文覆盖尚可，「调整方案」整段为 0。

## 4. ID 体系设计

### 4.1 命名规范

**格式：`<域码>-<两位序号>`**

| 域码 | 含义 | 来源文件 |
|---|---|---|
| `C` | 颜色规则 | `visual-signal-map.md` §4.1 + §4.1.2 |
| `CP` | 组合模式 | `combination-patterns.md` §2.x |
| `IM` | 失衡模式 | `mandala-5e.md` §4.2 |
| `T` | 议题 | `topics.md` §3.x |
| `S` | 状态 | `ontology.md` §4.1（**沿用现有 S-001..S-023**） |

**编号规则：**

- 按文档现有行序连续编号，**不做语义编码**。不写 `C-PINK` 这类名字——颜色名将来会改，序号不会。
- 序号在域内唯一、不复用、不回收。删除一条规则时保留空号，不做重编（重编等于让所有历史 run 的引用失效）。
- ID 写在规则所在行上（表格加一列，或小节标题后），使 ID 与该行成为一体。

**不要新增的前缀：**

- 不要 `R-5E-*`。`R-` 在现有库中已承载三种含义（案例候选规则 `R-002`、AI 规则 `R-AI-001`、`R-022`），再加一个是第四种。
- 不要 `VS-*` 包一层。文件名已在引用中可见，域码只需区分判断单位。

### 4.2 粒度规则

> **判据：一条规则发一个 ID，当且仅当「单独引用它时，读者能据此做一次独立的判断」。**

| 发 ID | 不发 ID |
|---|---|
| 颜色映射表的**一行**（一个颜色名） | 章节（`§4.1`） |
| 一个失衡模式 | 小节标题本身 |
| 一个组合模式 | 文档 |
| 一个状态、一个议题 | 流程说明、定位说明 |

**明确的反对项：不要给章节发 ID。** 章节是导航单位，不是判断单位。给章节发 ID 等于把粗粒度固化成正式结构，将来更难拆。

### 4.3 覆盖范围

**本轮只做颜色域 `C`，不动其他域。** 一轮只动一个域，做完能重跑，再动下一个。

依据：47 条 claim 中，颜色 18 + 视觉 13 + 组合 3 = 34 条（72%）依赖颜色与画面信号；且 `§4.1` 一个引用独占 22 个标记中的 16 个。修这个域，覆盖率和精度立刻可见。

颜色域清单：§4.1 表 14 行（标准五色 6 + 过渡色 8）→ `C-01`..`C-14`；§4.1.2 表外 3 行（灰/金/银）→ `C-15`..`C-17`。

### 4.5 已有 ID 的处理

| 现有 ID | 处理 | 理由 |
|---|---|---|
| `S-001`..`S-023` | **纳入**，仅从引用串中去掉冗余的 `§4.1` | 已是判断单位，引用里同时写 `§4.1` + `S-002` 是重复 |
| `F-001` 五行体系 | **不动，不纳入** | 它是文档定位引用，不是判断规则 |
| `R-AI-001/002/003` | **不动**（本轮不改名） | 改名前要同步 `visual-signal-map.md` 正文引用；收益为零。加 ID 的收益来自**没有 ID 的地方**，不来自已有 ID 的地方 |
| `R-002` / `R-003` / … | **不纳入正式 ID** | 它们是「案例里待晋升的候选」，状态还不是规则。给候选发正式 ID 会让候选与正式混淆。晋升时才分配正式 ID，并在候选处标注「已晋升为 IM-xx」 |

## 7. 明确不做

- 不给章节发 ID。
- 不改 `R-AI-*` / `F-*` 的现有命名。
- 不给案例候选规则 `R-*` 发正式 ID。
- 不引入 UUID / 内容 hash 作为规则 ID（人不可读、无法手写、diff 不可读）。
- 不做全量域（本轮只做 `C`）。
- 不改「一次生成、正则切两版」的产出方式。

## 8. 遗留问题（本轮不解决，单独立项）

1. **层级断裂（优先级高于本 ID 体系）**：state 5 条 + topic 3 条在报告中 0 标记、0 状态名。
   **根因已定位（三处叠加，均为小改动）：**
   - a. `_build_claims()`（`stage35.py:474`）对 `state_hypotheses` / `topic_hypotheses` 两组**不生成人话句子**，直接把 `state_id` / `topic` 当作 `claim.text` → text 的取值就是裸的 `S-002` / `情绪模式`。而 `_build_color_claims` / `_build_visual_claims` 都会拼出完整句子。
   - b. `_report_signals()` 因此输出 `- S-002　[来源: ontology.md §4.1 根因层状态（S-002 安全感不足）; …]`；而报告 prompt 写作要求第 3 条明确写着「不要提『程序、标记线、claim、证据门、观察 ID』这些工程术语——你是疗愈师，不是系统」→ 模型看到裸 ID，合法地把整行丢掉。
   - c. **`state-explanation.md`（含 S-001..S-023 的完整解读材料：是什么 / 形成原因 / 常见表现 / 生活影响）不在 `KNOWLEDGE_FILES` 的 8 个文件里**，所以状态层的人话材料从未进入 prompt——即使不禁 ID，模型也无话可写。
   **修法**：① 把 `state-explanation.md` 加入注入清单（或至少加入状态候选的 `knowledge_refs`）；② `_build_claims()` 为 state/topic 两组拼人话句子，不再直接把 ID 当 text；③ 重跑看报告里是否出现状态层叙述与对应来源标记。
   **ID 体系修不了这个问题**——`S-002` 已经是稳定 ID，且 claims 里已正确引用。
2. **「调整方案」段 0 标记**：该段 4 条不在 47 条 claim 里，正文与 `case-004.md` 逐字重合（74 字连续，含「每天 7 张 / 14 张」）。→ 删除该段，或为它补 claim 与来源。
3. **报告丢掉 3/4 引用**：claims 侧 80 次 → 报告 22 个标记。需查 `_report_signals()` 到报告 prompt 的传递是否被截断（如 token 上限、prompt 长度）。
