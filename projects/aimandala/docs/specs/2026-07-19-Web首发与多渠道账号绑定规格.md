## 1. 决策与目标

当前首发渠道固定为手机端 Web App（Web 应用），不以小程序为上线前置条件。

Web 首发采用手机号验证码登录。后续接入微信网页、小程序或其他微信生态入口时，必须把微信身份绑定到同一个内部主账号，确保报告、订单和权益跨渠道连续可见。

本规格解决两个问题：

1. Web 用户完成付费后，刷新、重新登录或后续使用微信入口时，仍能找回自己的报告和权益。
2. 同一人通过手机号和微信进入时，不会产生两个无法合并的账号。

## 2. 当前范围

### 2.1 Web 首发

首发 Web App 支持：

1. 手机号验证码登录。
2. 登录后查看本人上传、订单、权益、报告和本次报告追问记录。
3. 退出当前设备登录。
4. 使用有效登录态恢复历史报告与对应权益。

首发不支持：

1. 用户名加密码注册或登录。
2. 以 URL 参数、浏览器本地存储或前端传入的 `userId` 作为可信身份。
3. 匿名账号购买后再依赖匿名标识找回权益。
4. 小程序上线、微信登录按钮或微信支付作为 Web 首发前置条件。

### 2.2 后续微信生态

后续微信网页、小程序等渠道可接入微信身份，但不创建独立的“微信账号体系”。

优先使用 UnionID（同一微信开放平台主体下跨应用一致的用户标识）绑定内部主账号；若当前微信能力暂时无法稳定提供 UnionID，则以已验证手机号完成跨渠道绑定，待具备条件后再补充 UnionID。

OpenID（单个微信应用内的用户标识）只能作为该应用内身份记录，不能单独作为跨 Web 和小程序合并账号的依据。

## 3. 账号与数据模型

系统必须以内部 `user_id` 作为唯一主账号标识。手机号、微信 UnionID、微信 OpenID、订单号和报告 ID 均不是主账号。

```text
User（内部主账号）
├─ PhoneIdentity（已验证手机号）
├─ WeChatIdentity（UnionID；可附带各应用 OpenID）
├─ Session（设备登录态）
├─ Upload（用户上传画作）
├─ Report（报告）
├─ Order（订单）
└─ Entitlement（按报告授予的 Lite / Pro 权益）
```

约束：

1. 每个手机号在有效状态下只能绑定一个 `user_id`。
2. 每个 UnionID 只能绑定一个 `user_id`。
3. 每条 Upload、Report、Order、Entitlement 和 Followup Context 都必须保存所属 `user_id`。
4. 报告、Pro 权益和追问上下文仍须绑定具体 `report_id`，不得在同一用户的不同画作之间复用。
5. 访问控制以服务端从登录态解析出的 `user_id` 为准，不能相信客户端请求中的用户身份字段。

## 4. 注册、登录与会话

### 4.1 手机号验证码登录

用户输入手机号并完成验证码验证后：

1. 若手机号已绑定内部账号，服务端登录该 `user_id`。
2. 若手机号未绑定内部账号，服务端创建 `User` 与 `PhoneIdentity`，再登录该 `user_id`。
3. 服务端签发短期 access token（访问令牌）和可撤销的 refresh token（续期令牌）。
4. Web 端不得把长期可用令牌或可伪造的用户身份写入 URL 或 localStorage（浏览器本地存储）。
5. 退出登录后，当前设备的 refresh token 失效。

验证码必须设置有效期、单手机号与单 IP 限流、错误次数上限和审计记录。验证码明文不得持久化保存或写入日志。

### 4.2 微信身份绑定

用户从微信入口进入时，服务端完成微信授权码校验后再获得 UnionID / OpenID，前端传入的 OpenID、UnionID、手机号或 `userId` 都不得直接被信任。

绑定规则：

1. 微信身份未绑定，且用户已登录 Web 账号：在当前登录态下确认绑定到该 `user_id`。
2. 微信身份已绑定当前 `user_id`：直接登录或继续当前账号。
3. 微信身份已绑定其他 `user_id`：拒绝静默覆盖；要求用户完成手机号验证后进入人工可审计的合并流程。
4. 用户先用微信进入、后验证手机号：若手机号已绑定账号，走账号合并流程；若未绑定，给当前 `user_id` 添加手机号身份。

### 4.3 账号合并

账号合并只能在服务端执行，并要求用户同时证明两个身份：例如当前有效微信登录态加手机号验证码。

合并前必须检查两边没有未决退款、拒付、支付争议或高风险状态。合并后应保留全部有效的报告、订单与权益，并写入不可修改的审计记录，至少记录源账号、目标账号、验证方式、操作者、时间与结果。

自动合并的唯一允许情形是服务端已证明两个身份归属同一内部账号；不能仅凭显示名、设备、IP 或前端字段自动合并。

## 5. 授权与隐私边界

所有下列接口都必须先验证登录态，再验证资源的 `user_id` 所有权：

1. 图片上传与读取。
2. 报告创建、列表、详情、重试和下载。
3. Lite / Pro 订单、支付结果和权益查询。
4. 报告追问及其上下文。
5. 账号绑定、解绑、合并、退出和删除请求。

客户端只可提交服务端签发的 upload ID 或受控 storage key，不能提交任意服务器本地 `image_path`。图片访问使用短期签名链接或等价受控下载能力；不得把公开对象 URL 当作永久访问控制。

用户应能在产品中看到隐私政策、数据保留说明和删除申请入口。删除流程至少要明确画作、报告、会话、订单法定留存与模型调用审计记录的分别处理方式。

## 6. 与支付和 Pro 的关系

本规格不改变现有 Lite / Pro 定价与购买关系：Lite 为 9.9 元，Pro 仅能基于同一报告的 Lite 权益再付 29 元升级。

订单与权益必须关联 `user_id + report_id`。支付回调只能由服务端验证并更新权益；前端支付成功页面、查询参数或客户端回调不得直接解锁 Lite 或 Pro 内容。

如果项目后续决定以 Lite-only 进行封闭内测，应仅关闭 Pro 的售卖入口，不改变本规格的账号归属和授权模型。

## 7. 验收标准

以下任一失败均阻塞上线：

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AUTH-P0-01 | 手机号首次登录 | 创建单一内部账号，验证码不泄露，登录态可用 |
| AUTH-P0-02 | 已有手机号登录 | 回到原 `user_id`，历史报告和权益完整可见 |
| AUTH-P0-03 | 换设备登录 | 验证手机号后能找回本人已购报告；未登录不可读取 |
| AUTH-P0-04 | 跨用户报告访问 | 用户 A 不能列表、读取、追问、下载或支付操作用户 B 的报告 |
| AUTH-P0-05 | 客户端身份伪造 | 修改 URL、localStorage、请求体中的 `userId`、OpenID 或 report ID 不得获得他人资源 |
| AUTH-P0-06 | 微信绑定 | 同一人完成验证后，Web 与微信入口显示同一报告、订单和权益 |
| AUTH-P0-07 | 冲突绑定 | 已绑定到其他账号的微信身份不会静默覆盖或创建重复权益 |
| AUTH-P0-08 | 账号合并 | 同时完成两侧身份验证后才能合并；保留记录并写入审计日志 |
| AUTH-P0-09 | 登录态失效与退出 | 退出或 token 失效后，受保护接口返回未登录，刷新令牌不能继续使用 |
| AUTH-P0-10 | 上传授权 | 用户不能用任意服务器路径创建报告，也不能读取其他用户画作 |

还需覆盖验证码频率限制、错误次数限制、重复支付回调、订单与权益恢复、上传格式与大小限制、删除申请和审计查询。

## 8. 实现前提与下一步

进入实现前，Architect 必须产出账号、会话、资源所有权、订单权益和微信绑定的技术边界，包括数据迁移方案、令牌存储策略、回调验签、审计与删除策略。

Engineer 应先为跨用户越权、身份伪造、会话撤销、绑定冲突和支付权益恢复写失败测试，再实现接口和前端接线。

Test / QA 应以本规格第 7 节建立上线前安全回归矩阵；任一 AUTH-P0 失败时，产品维持 No-Go。
