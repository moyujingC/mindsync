## 1. 问题定义

截至 `2026-04-26`，`aimandala` 当前任务面已经同时混有两类对象：

1. 历史 automation 任务
2. 历史普通人工任务

这些旧任务的共同问题不是“都还值得继续追”，而是：

1. 它们大量产生于旧模板、旧 execution routing（执行分流）口径或旧运行窗口
2. 其中很多任务已经失去继续投入判断成本的价值
3. 旧任务持续占据面板、block（阻塞）视图和巡检视图，会掩盖真正需要观察的新任务生成行为

当前真正想达成的目标已经改变：

1. 不再追逐历史任务逐条清账
2. 只要求从新基线开始，新产生的任务按新的模板语义和宿主机路由规则运行
3. 把旧任务统一视为历史噪音，一次性收口

因此，本规格固定把问题改写为：

1. 不是继续修旧任务
2. 而是进行一次“历史任务全量关闭 + 新基线切换”

## 2. 目标

本规格的目标固定为：

1. 定义“旧任务”的统一关闭范围
2. 定义新基线时间点
3. 定义极少数例外保留规则
4. 明确后续只观察新基线之后产生的新任务
5. 明确旧任务全量关闭不等于运行规则已经正确，真正的后续主线应先满足普通任务在本地 Mac 自动执行

## 3. 非目标

本规格不做：

1. 不逐条复盘历史任务技术细节
2. 不把关闭旧任务误解释为 heartbeat gate（门禁）问题已经解决
3. 不批量补 `executionWorkspaceId`
4. 不修改 `check-paperclip-execution-health.mjs`
5. 不修改 `audit-paperclip-workspace-materialization.mjs`
6. 不修改 `diagnose-paperclip-server-automation-materialization.mjs`
7. 不在本规格中直接定义模板代码实现细节

## 4. 新基线定义

### 4.1 基线时间

新基线固定定义为：

1. `2026-04-26 00:00 Asia/Shanghai`

解释：

1. 在这个时间点之前创建的任务，默认都属于历史任务
2. 在这个时间点之后创建的任务，才进入新的观察窗口

### 4.2 基线后的观察对象

从新基线开始，默认只观察：

1. 新生成的 automation 任务
2. 新生成的普通人工任务
3. 普通任务本地 Mac 自动执行链路上的新样本

默认不再把基线前的旧任务持续带入当前判断。

## 5. 历史任务关闭范围

### 5.1 默认关闭范围

新基线前的下列任务默认全部关闭：

1. 历史 automation 任务
2. 历史普通人工任务
3. 历史 review 任务
4. 历史 blocked 任务
5. 历史 in progress / in review 但已不再继续跟进的任务

这里明确不再区分：

1. automation 与普通任务
2. parent / child（父子任务）
3. 执行任务、审阅任务、文档任务

只要属于历史窗口且未被明确列入保留名单，默认全部收口。

### 5.2 统一关闭口径

历史任务关闭时，comment（评论）口径应统一为：

1. 历史任务基线重置
2. 不再继续追踪旧窗口任务
3. 后续以 `2026-04-26` 新基线后产生的新任务为准
4. 若该问题仍然成立，应由新模板 / 新执行规则重新生成新的任务，而不是继续复用旧任务

通俗讲：

1. 旧任务不是被证明“已经解决”
2. 而是被明确“停止追历史”

### 5.3 默认终态选择

当前 `Paperclip` 在本仓实际稳定使用的任务终态口径，优先可依赖的是：

1. `done`
2. `blocked`
3. `in_review`

因此本规格固定默认：

1. 历史任务批量收口时，统一使用 `done`
2. 不使用任务态 `archived` 作为本轮默认执行口径
3. “这不是技术问题已解决”这层语义，必须通过统一 comment 明确补出，而不是寄希望于状态名表达

原因：

1. 仓库现有运行链、脚本和文档口径对 `done` 的支持最稳定
2. 当前没有足够证据表明任务态 `archived` 已是生产可依赖主路径
3. 若继续悬空终态选择，会把执行判断再次留给实现者

## 6. 例外规则

### 6.1 默认例外策略

本规格允许存在极少数例外保留任务，但默认数量应收敛到最少。

建议默认规则：

1. 未被显式点名保留的旧任务，全部关闭
2. 只有被明确列入“保留名单”的任务可以继续存在

### 6.2 例外名单的上限

为避免重新把历史任务面做脏，例外名单默认应限制为：

1. `0` 到 `5` 条

如果超过这个数量，说明策略已经偏回“继续追历史旧账”，不符合本规格目标。

### 6.3 例外任务的条件

只有满足下面任一条件，旧任务才允许留在保留名单：

1. 你明确指定必须继续跟进
2. 它是当前唯一外部协同锚点，短期内不能换新任务
3. 它承载了当前必须保留的人工决策上下文，且无法安全迁移到新任务

## 7. 新基线后的治理规则

### 7.1 主线不再是旧任务修复

从新基线开始，主线固定为：

1. 只修“新任务生成规则”
2. 不再修“历史任务状态”

### 7.2 新任务治理优先级

新基线后的治理顺序固定为：

1. 先满足普通任务在本地 Mac 自动执行
2. 再继续收 automation 模板语义修复

进一步展开为：

1. `manual-review-required + local_manual_review`
   - 先由你的当前这台 Mac 自动 claim / checkout / 执行 / 回写
   - 这是新基线后的普通任务主链
2. `automation-execution + server_automation`
   - 继续由 automation 服务器承接
   - 其模板语义修复排在普通任务本地自动执行之后

通俗讲：

1. 先把普通任务“别再卡在服务器上、能在本地 Mac 自动跑起来”这件事做实
2. 再继续治理 automation 任务模板语义

### 7.3 关闭旧任务与修新模板的先后

正确顺序固定为：

1. 先明确新模板语义与宿主机路由规则
2. 先满足普通任务在本地 Mac 自动执行
3. 再批量关闭旧任务
4. 之后只观察新任务

禁止倒置为：

1. 先关旧任务
2. 但不修新规则
3. 结果让系统继续生成一批新的错任务，且普通任务仍然不能在本地 Mac 自动执行

## 8. 验收标准

本规格通过至少满足：

1. 明确把 `2026-04-26 00:00 Asia/Shanghai` 定义为新基线
2. 明确历史 automation 与历史普通任务都在默认关闭范围内
3. 明确旧任务关闭不代表旧问题已技术解决
4. 明确历史任务批量收口默认终态使用 `done`
5. 明确例外保留名单应极少且必须显式指定
6. 明确新基线后的第一主线是“普通任务先在本地 Mac 自动执行”，不是“历史任务逐条清账”
