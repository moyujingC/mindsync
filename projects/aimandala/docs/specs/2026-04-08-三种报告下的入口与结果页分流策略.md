## 1. 目的

本文件专门回答一个现在必须收束的问题：

- 在三种报告已经成立之后，用户入口到底该怎么设计，结果页又该怎么承接，才能不让用户感到混乱

这份文档重点不是继续定义三种报告本身，而是定义：

1. 用户在前台到底看见什么
2. 系统在后台到底怎么判断
3. 上传页、解读方式确认页、生成页、结果页之间应该如何分工
4. 什么情况下应继续留在当前报告
5. 什么情况下应在结果页引导下一类报告

它不是：

- 最终 UI 稿
- 最终技术实现文档
- 最终运营投放文案
- 最终支付页文案

它是：

- 报告矩阵下的入口规则 spec
- 结果页分流规则 spec
- 用户可见层与系统内部层的边界说明

## 2. 继承的上游结论

本文件明确继承以下判断，不重复改写：

1. 当前产品真相就是 `Lite / Pro / Journey`
2. `Lite` 与 `Pro` 都支持：
   - `全面解读`
   - `专题解读`
3. 如果用户没有选主题，`Lite` 与 `Pro` 都默认进入 `全面解读`
4. `Journey` 只在有多次历史画作时才成立
5. 用户在第一次进入时，不应被迫理解完整的内部实现逻辑

## 3. 当前最重要的收束判断

本轮先收束到下面 8 个判断：

1. 上传页不直接要求用户先理解完整报告矩阵
2. 上传页先让用户表达 `这次最想重点看什么`
3. 用户选择的是 `阅读焦点`，不是最终结论
4. 上传后应进入一层明面的 `解读方式确认页`
5. `解读方式确认页` 必须告诉用户：
   - 这次推荐哪种 `商品层解读方式`
   - 为什么是这个方式
   - 价格与风格差异大概是什么
   - 如果不想走这条，也可以改选什么
6. 第一层明面分流应优先发生在 `Lite / Pro`
7. `Pro` 内部可以有 `全面解读` 与 `专题解读` 两种解读方向
8. `Journey` 不属于单次上传后的直接选项，只有在存在多次历史画作时才应被推荐

## 4. 用户可见层 vs 系统内部层

## 4.1 用户可见层

用户在前台当前不需要一上来就理解的概念：

- 三种报告的完整内部实现细节
- `Pro` 内部是如何决定全面解读或专题解读
- 内部分流判定逻辑

用户在前台第一步只需要完成两件事：

1. 上传这张画
2. 选择这次更想重点看什么

但在上传之后，用户应继续看见一层明确说明：

1. 这次系统为什么推荐 `Lite` 或 `Pro`
2. 这种解读方式会更偏什么风格
3. 如果她更想看另一种，也可以切换

因此，当前更建议用户看见的是：

- `阅读焦点`
- `主题方向`
- `这次更想被看见的部分`

而不应该一开始就直接看见：

- `你要购买哪类报告`
- `你现在属于哪个内部产品`

## 4.2 系统内部层

系统内部仍然需要保留的概念：

1. 当前实际生成的是哪一种报告
2. 用户当前承载力更适合轻入口还是主报告
3. 当前输入是否已经收束到明确主题
4. 用户是否已经具备进入更深机制层的条件

但这里要补一条关键原则：

- `内部判断` 可以存在
- `分流结果` 不能完全隐藏

也就是说：

- `阅读焦点` 是第一步用户可见交互语言
- `Lite / Pro / Journey` 是用户最终会理解到的报告产品
- `全面解读 / 专题解读` 是 `Lite` 与 `Pro` 内部的解读方式
- 真正不能直接暴露的，是复杂的内部判定过程，而不是最终分流结果

这三层必须区分，不应混写：

1. 用户先表达什么
2. 系统据此如何判断
3. 最终向用户推荐什么

## 5. 上传页与解读方式确认页规则

## 5.1 上传页的核心任务

上传页最核心的任务不是教育用户理解三种报告，而是帮助用户低成本进入：

1. 上传作品
2. 说出这次最想重点看什么
3. 感到这次解读和自己当下有关

上传页完成后，不建议直接生成结果，而应进入：

- `解读方式确认页`

## 5.2 上传页建议使用的交互语言

当前更建议上传页使用的语言是：

- `这次你更想重点看什么`
- `如果你愿意，也可以选一个你最近最在意的方向`
- `你可以选全面看看，也可以选一个当前更在意的主题`

当前不建议上传页直接使用的语言是：

- `请选择报告类型`
- `请选择全面解读 / 专题解读`
- `请选择基础版 / 深度版`

## 5.3 上传页建议保留的焦点类型

当前建议上传页只呈现有限的阅读焦点：

1. `general`
   - 更像“先整体看看我现在是什么状态”
2. `relationship`
3. `boundary`
4. `emotion`
5. `expression`
6. `career`

这些是：

- 用户阅读焦点

不是：

- 最终对用户公开的产品线命名

## 5.4 解读方式确认页应如何解释 Lite / Pro

当前更建议这页优先告诉用户：

1. `Lite`
   - 更轻、更快、更像先看清当前状态的一次低压解读
2. `Pro`
   - 更完整、更深入、更像一次正式解读

如果系统推荐 `Lite` 或 `Pro`，再继续说明它这次会更偏：

1. `全面解读`
2. `专题解读`

## 5.5 解读方式确认页的作用

解读方式确认页的存在，不是为了把用户重新丢进选择题，而是为了完成三件事：

1. 让分流发生在明面上
2. 让用户理解为什么这次会是这种解读风格
3. 避免用户对不同次解读风格差异产生黑盒困惑

它要回答的核心问题是：

- `为什么我这次更适合这样看`

而不是：

- `请你自己研究这些内部区别再决定`

## 5.6 解读方式确认页建议结构

当前建议这页只保留非常轻量的结构：

1. `本次推荐`
   - 例如：这次更适合从 `Lite` 开始
   - 或：这次更适合进入 `Pro`
2. `推荐原因`
   - 例如：你当前填写的内容更像想先看清整体状态，而不是只围绕单一议题展开
3. `风格说明`
   - 例如：这一类解读会更偏整体状态、核心拉扯和现实连接
4. `可改选项`
   - 最多再给 `1-2` 个可切换方式，而不是全量货架
5. `价格提示`
   - 让用户知道这是更轻的 `Lite` 还是更完整的 `Pro`

## 5.7 解读方式确认页不建议做成什么

当前不建议把这页做成：

1. 三种报告完整对照表
2. 复杂套餐页
3. 价格货架页
4. 需要用户重新学习一次产品体系的页面

## 6. 第一份报告的默认落点

## 6.1 默认规则

当前建议的默认规则是：

- 第一份进入确认页后，先优先推荐 `Lite` 或 `Pro`

原因不是因为它“最中间”，而是因为：

1. 它最适合大多数第一次认真想看懂自己的用户
2. 它最容易同时完成 `被看见`、`被解释`、`被命名`、`被连接`、`被指引`
3. 它最适合作为后续所有结果页分流的中枢
4. 它比直接让用户选专题解读更不容易让初次用户感到“被框进一个问题”

## 6.2 `general` 的解释

当用户选择 `general` 时，更适合理解为：

- 她想先整体看懂自己当前状态

因此：

- `general` 默认最适合被推荐为：
  - `Lite / 全面解读`
  - 或 `Pro / 全面解读`

因为这会把原本应该在确认页解释的东西，过早硬塞给用户。

## 6.3 具体主题的解释

当用户选择某个具体主题时，更合理的理解是：

- 她这次希望阅读更偏向这个方向

这意味着：

1. 确认页可以更高概率推荐：
   - `Lite / 专题解读`
   - 或 `Pro / 专题解读`
2. 如果仍推荐 `Pro / 全面解读`，也可以明确说明它会带当前主题视角
3. 结果页可以优先承接同主题的后续路径

但不意味着：

- 这一次一定只能是 `专题解读`

当前更建议在确认页明说：

- 你这次的关注点更偏某个主题
- 因此你可以选择：
  - 先看 `Lite / 专题解读`
  - 或直接进入 `Pro / 专题解读`

## 7. 什么情况下应优先推荐 Lite

虽然第一份进入确认页后用户可能期待完整解读，但仍应保留一个更轻的可解释例外：

- 当用户明显不适合高密度理解时，系统应明确推荐 `Lite`

## 7.1 适合优先推荐 Lite 的信号

当至少出现下面几类信号时，应考虑优先推荐 `Lite`：

1. 用户明显只想先被接住
2. 输入语言显示承载力较低
3. 当前状态明显较乱，不适合高密度解释
4. 用户对分析感有明确抗拒
5. 这是第一次接触报告，且更像试探式进入

## 7.2 Lite 的前台处理原则

即使系统判断更适合 `Lite`，前台也不建议强调：

- `因为你现在不适合读完整报告`

更合适的处理方式应是，在确认页明确说明：

- 这次更适合先从一份更轻、更快的当下解读开始
- 等你想继续看清楚时，再进入更完整的理解报告

也就是说：

- `Lite` 更像对当下状态和当前承载力的匹配
- 不应被用户感受到是在“被降级”

## 8. 什么情况下在结果页引导 Pro 的专题解读

`Pro / 专题解读` 当前不适合在上传页直接硬分成独立商品，但可以在 `Pro` 推荐中被明确说明是这次更贴合当前主题的解读方式。

## 8.1 适合引导 Pro 专题解读的信号

当结果页已经能确认下面判断时，可优先引导 `Pro / 专题解读`：

1. 用户当前卡点已经明显收束到单一主题
2. 用户最在意的是某个现实问题，而不是整体看懂自己
3. 当前报告里某个主题的命中感明显高于其他部分
4. 用户读完后更自然会问：
   - “那关系里为什么总这样？”
   - “那边界这件事到底怎么回事？”
   - “那我在表达上为什么总卡住？”

## 8.2 Pro 专题解读的结果页表述原则

当前建议用下面这类语言承接：

- `如果你想沿着这个主题继续看清楚，可以继续看这一部分`
- `如果你更想把这个问题讲透，我们可以只围绕这个主题继续展开`

当前不建议直接让用户感到：

- 她刚刚其实“选错了报告”
- 她被系统重新改派到了另一条线路

因此更合理的承接是：

- 当前这份报告先完成当前这一轮理解
- 下一步再进入专题理解

## 9. 什么情况下在结果页引导 Journey 报告

`Journey` 的位置不应是单次上传后的主入口。

它只应在下面条件成立时被明确解释：

1. 用户已经有多次历史画作
2. 系统确实能做跨时间对照分析

## 9.1 适合引导 Journey 报告的信号

当出现下面判断时，可优先引导 `Journey`：

1. 用户已经有多次历史画作
2. 用户已经被命中，但仍明显觉得“不够”
3. 用户更想知道“为什么我总会这样”
4. 当前问题已经不只是单点议题，而像跨时间重复模式

## 9.2 Journey 的结果页表述原则

当前更建议用下面这类承接语言：

- `如果你想继续看见更深一层的重复模式，可以继续往下看`
- `如果你已经不只想知道现在怎么了，而想知道为什么总会这样，可以继续深入`

当前不建议把它写成：

- `升级到更贵版本`
- `解锁完整版报告`

因为这会把用户重新拉回旧的 `Lite / Pro` 认知。

## 10. 三种报告的结果页承接方向

当前建议的主承接方向如下：

| 当前报告 | 更适合承接什么 | 说明 |
|---|---|---|
| Lite | `Pro` / `陪你画` / `再画一幅` | 先从轻解读走向更完整理解，不急着推深 |
| Pro / 全面解读 | `Pro / 专题解读` / `陪你画` / `多次画作后进入 Journey` | 当某个主题逐渐收束时，可以继续往专题方向走 |
| Pro / 专题解读 | `主题方案` / `同主题再画一幅` / `多次画作后进入 Journey` | 更适合继续往专题行动走 |
| Journey 报告 | `21 天定制方案` / `长期 AI 陪伴` / `优先级动作` | 更适合进入连续路径，而不是再回到浅层报告 |

## 11. 结果页 CTA 优先级

## 11.1 总原则

结果页的目标不是一次性把所有后续产品都摆出来，而是：

1. 先完成这份报告本身的交付
2. 只给一个最自然的主动作
3. 允许再保留一个更轻的次动作

## 11.2 当前建议规则

当前建议每个结果页最多保留：

1. `1` 个主 CTA
2. `1` 个次 CTA

推荐顺序如下：

1. 主 CTA
   - 指向当前最自然的下一步理解或行动
2. 次 CTA
   - 指向更轻的继续陪伴、再画一幅或延后决策

## 11.3 当前不建议事项

当前不建议结果页出现以下情况：

1. 同时并列展示 `3` 个以上强 CTA
2. 一边引导 `Pro / 专题解读`，一边引导 Journey，一边又推活动，权重都一样
3. 把所有报告类型直接摆成菜单让用户重新选
4. 把结果页写成“产品货架”

## 12. 可执行分流判断表

| 场景 | 用户可见输入 | 系统内部判断 | 当前输出 / 承接建议 |
|---|---|---|---|
| 初次进入，想整体看看 | `general` | 先判断更适合 Lite 还是 Pro | 确认页推荐 `Lite / 全面解读` 或 `Pro / 全面解读` |
| 初次进入，选了具体主题，但还在泛模糊状态 | `relationship` / `boundary` / `career` 等 | 主题作为阅读焦点，但不一定需要完整专题分析 | 确认页推荐 `Lite / 专题解读` 或 `Pro / 专题解读` |
| 初次进入，明显只想先被接住 | 任意焦点 | 承载力不足 | 确认页推荐 `Lite`，并说明为什么更适合先轻一点 |
| 已读 Pro 全面解读，明确还想继续看某一主题 | 结果页行为 / 明确表达 | 主题已收束 | 引导 `Pro / 专题解读` |
| 已读 Pro，明确想看更深机制，且已有多次历史画作 | 结果页行为 / 明确表达 | 深度意愿成立且输入条件满足 | 引导 `Journey` |
| 已读 Journey 报告，想继续推进 | 结果页行为 / 明确表达 | 进入连续路径 | 引导 `21 天定制方案` 或 `长期 AI 陪伴` |

## 13. 当前阶段最重要的避免事项

当前最需要避免重新滑回下面 6 种写法：

1. `选主题 = 自动进入另一种完全不同等级的报告`
2. 上传后系统默默分流，却不给用户解释
3. 上传页直接要求用户理解很多内部报告差异
4. 把 `Journey 报告` 写成“完整版”
5. 把 `Lite` 写成“缩水版”
6. 让用户以为单次一幅画也能直接得出长期稳定模式

因为这些写法都会把已经收束好的三种报告结构，重新拉回：

- 轻版 / 重版
- 入门版 / 升级版
- 用户必须先理解产品线再开始使用

这类旧逻辑。

## 14. 当前阶段最值得继续补的下一份文档

基于本文件，后续最值得继续补的文档应是：

1. 上传页阅读焦点文案与交互结构 spec
2. 结果页 CTA 结构与分流组件 spec
3. 分流规则对应的技术字段与判定逻辑 spec

如果只允许先做一份，当前最值得优先继续的是：

- `上传页阅读焦点文案与交互结构 spec`

因为：

1. 当前最大的用户困惑风险首先发生在入口
2. 只要推荐页语言不稳，用户就会把风格差异理解成黑盒波动
3. 它会直接影响后续结果页、支付页和生成逻辑的统一表达
