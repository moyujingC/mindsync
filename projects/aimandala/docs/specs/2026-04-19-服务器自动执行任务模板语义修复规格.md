## 1. 问题定义

`aimandala` 已经完成 execution routing（执行分流）的服务器侧去拒绝化，并通过 diagnosis（诊断）脚本确认：

1. 当前 automation 节点上的真实基线已滚动为：
   - `serverAutomationBlocking = 35`
   - `historicalDoneWorkspaceDrift = 8`
   - `localExecutionRouting = 3`
2. `strict gate` 当前仍然只由活跃 `server_automation` 驱动
3. `local_manual_review` 已成功从服务器主阻断链中分离

本轮 diagnosis 的关键发现不是：

1. 服务器 worktree（工作树）根目录配置错误
2. execution workspace 实体普遍持久化失败
3. isolated workspaces（隔离工作区）实例总开关仍未开启

而是：

1. `35` 条活跃 `serverAutomationBlocking` 中，`33` 条落在 `routing_metadata_or_source_anomalies`
2. 这些异常高度集中在 4 类 `source` 模板：
   - `build-failure`: `13`
   - `infra-runner-failure`: `9`
   - `deploy-or-smoke-failure`: `7`
   - `ci-test-failure`: `4`
3. `localExecutionRouting` 中的 `MIN-137` 与 `MIN-133` 说明：
   - `automation-summary` / `commit-summary` 这类摘要任务当前被明确建模为
     - `task_class: manual-review-required`
     - `execution_route: local_manual_review`
   - 它们不是服务器自动执行任务，只是控制面协调或人工收口任务
4. `MIN-119` 说明：
   - 纯人工文档整理任务也可能在后续绑定 execution workspace 时错误落进服务器 worktree

因此，下一阶段的主问题已经收敛为：

1. 任务模板的语义合同还没有和新的双执行宿主机模型彻底闭合
2. 服务器真正需要自动执行的 task（任务）模板，与控制面摘要 / 汇总 / 人工审核类模板仍然混层
3. 在模板语义未闭合前，继续批量补绑 `executionWorkspaceId` 只会掩盖根因

## 2. 目标

本规格的目标不是恢复 heartbeat 绿色，而是先把“什么任务应该是 `server_automation`，什么任务只是控制面摘要 / 人工审核任务”写成稳定合同。

本轮固定要达成：

1. 明确 `automation-summary` 与真正 `server_automation` task 的边界
2. 明确 4 类 `source` 模板各自应生成什么 `task_class / execution_route / description` 头部
3. 先收模板语义，不先收 execution workspace 绑定
4. 为下一轮 Task / QA / 实施提供唯一正式入口

## 3. 非目标

本规格不做：

1. 不修改 `PaperclipAI` 源码
2. 不修改 heartbeat strict gate 规则
3. 不批量补 `executionWorkspaceId`
4. 不批量 patch issue 状态
5. 不修改现有 `localExecutionRouting` 为服务器可写执行
6. 不把 `automation-summary` 类任务重新解释成服务器自动修复任务

## 4. 核心规则

### 4.1 两类任务必须彻底分开

从本规格生效起，服务器侧模板必须固定区分两类任务：

1. 真正的自动执行任务
   - `task_class: automation-execution`
   - `execution_route: server_automation`
   - 允许进入 execution workspace（执行工作区）
   - 允许被 heartbeat / health 视为服务器阻断对象
2. 控制面摘要 / 人工审核任务
   - `task_class: manual-review-required`
   - `execution_route: local_manual_review`
   - 不允许进入服务器可写执行链
   - 即使名字里带 `ci`、`heartbeat`、`summary`，也不等于自动执行任务

### 4.2 `automation-summary` 的正式边界

`automation-summary` 固定解释为：

1. commit-summary（提交摘要）
2. workflow-summary（流程汇总）
3. review / epic（审阅型 / 史诗型）父任务
4. 只负责收口信息、状态和人工判断

它们的固定合同是：

1. `task_class: manual-review-required`
2. `execution_route: local_manual_review`
3. 不进入服务器可写执行链
4. 不应被后续流程误绑到 `/opt/automation/worktrees`

这条规则对下面样本已被真实验证：

1. `MIN-137`
   - `title: Runner-Heartbeat`
   - `source: automation-summary`
   - `workflow: runner-heartbeat`
   - 仍然是 `manual-review-required + local_manual_review`
2. `MIN-133`
   - `title: #31`
   - `source: automation-summary`
   - `workflow: ci`
   - 仍然是 `manual-review-required + local_manual_review`

通俗讲：

1. 名字像自动化任务，不代表它就是自动执行任务
2. “摘要任务”与“实际修复任务”必须是两层对象

### 4.3 4 类 source 模板的修复优先级

下一阶段模板语义修复优先级固定为：

1. `infra-runner-failure`
2. `build-failure`
3. `deploy-or-smoke-failure`
4. `ci-test-failure`

排序依据：

1. `infra-runner-failure`
   - 有 `MIN-137` 这种高价值错层样本
   - 说明 runner / heartbeat 相关任务最容易和摘要任务混层
2. `build-failure`
   - 数量最大，共 `13` 条
3. `deploy-or-smoke-failure` 与 `ci-test-failure`
   - 仍然是独立模板桶，但规模次之

### 4.4 四类模板必须收口的字段

下一阶段修复时，这 4 类模板必须统一收口下面字段：

1. `task_class`
2. `execution_route`
3. `source`
4. `type`
5. `description` 头部字段顺序与最小字段集

要求：

1. 同一 `source` 下的 description 头部格式必须稳定
2. 必须让脚本只靠显式元数据就能判断它是否属于 `server_automation`
3. 不再依赖“看标题像不像自动化任务”做主判断

### 4.5 任务模板与运行态边界

在模板语义未修好之前，运行态问题按下面方式解释：

1. `serverAutomationBlocking`
   - 先视为模板语义和自动执行链未闭合的结果
2. `localExecutionRouting`
   - 先视为摘要任务或人工任务被错误绑进服务器 worktree

本阶段禁止倒置因果：

1. 不能先把 worktree 绑定修好，再假设模板自然会正确
2. 不能因为任务名像自动化，就把它提格为 `server_automation`

## 5. 当前基线与样本证据

本规格固定继承下面远端事实：

1. 当前基线：
   - `35 / 8 / 3`
2. diagnosis 分桶：
   - `routing_metadata_or_source_anomalies = 33`
   - `issue_binding_missing_after_execution_trace = 2`
3. `MIN-137` / `MIN-133`
   - 都属于 `automation-summary`
   - 都明确标成 `manual-review-required + local_manual_review`
4. `MIN-119`
   - 是典型纯人工任务
   - 被标成 `local_manual_review` 完全合理
   - 问题在后续 workspace 绑定跑偏，不在模板本身模糊

## 6. 验收标准

本规格通过至少满足：

1. 明确 `automation-summary` 不是服务器自动执行任务
2. 明确 4 类 `source` 模板的修复优先级
3. 明确下一阶段先修模板语义，不先修 heartbeat gate
4. 明确下一阶段不先批量补绑 execution workspace
5. 让后续实现者无需再决定：
   - `Runner-Heartbeat` 这类摘要任务到底是不是 `server_automation`
   - `automation-summary` 是否还能进入服务器可写执行链
   - 下一轮是否应先去做批量 workspace 补绑
