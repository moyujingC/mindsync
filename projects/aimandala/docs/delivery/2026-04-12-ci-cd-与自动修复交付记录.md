## 2. 当前状态入口

本轮之后，默认从三层看状态：

1. GitHub PR / commit checks 和 workflow run history
2. `aimandala-smoke.mjs` 对应的 dev / prod 健康检查
3. Paperclip 中由聚合键收口的 CI/CD 问题单

同时，Paperclip 面板中的 CI/CD 问题单按如下状态语义运行：

- `todo`
  - CI / 构建失败已进入待处理队列，但尚未进入自动修复闭环
- `in_progress`
  - 已命中 auto-repair 白名单，自动修复正在隔离分支尝试修复或已尝试但仍待人工接手
- `in_review`
  - 自动修复已产出修复分支或 Draft PR，等待人工审阅
- `done`
  - 对应同类失败已恢复为绿色，问题单完成收束
- `blocked`
  - 已明确属于基础设施、凭证、工作区漂移或外部人工动作阻塞，不能继续假装处于执行中

同时补充一层 commit 级收束语义：

- 同一提交的 `ci` 先创建一个父任务
- 同一提交下各 job 的失败项作为子任务挂在该父任务下
- 父任务显示名默认对齐 GitHub workflow run 编号，例如 `#24`
- 子任务显示名默认对齐 GitHub job 名，例如 `frontend-quality`、`deploy-dev`
- 标题中不再额外写 `成功 / 失败 / 汇总` 等结果描述
- 子任务聚合键带上 `sha`，避免不同提交继续复用同一条旧单

## 3. 未完成但已留好入口

1. GitHub 仓库 secrets / vars 仍需人工配置：
   - `AIMANDALA_DEV_*`
   - `AIMANDALA_PROD_*`
   - `PAPERCLIP_API_BASE`
   - `PAPERCLIP_API_KEY`
   - `PAPERCLIP_ENGINEER_AGENT_ID`
   - `AIMANDALA_AUTO_REPAIR_COMMAND`
2. self-hosted runner 仍需在线注册
3. `check-runner-heartbeat.mjs` 与 `check-paperclip-execution-health.mjs` 仍需部署到 heartbeat timer

本轮补充交付：

4. `.github/workflows/aimandala-deploy.yml` 的 `Prepare SSH Key` 已补上最小防御性处理：
   - secret 缺失校验
   - `CRLF` 归一化
   - raw multiline / base64 双格式兼容
   - `ssh-keygen -y -f` 私钥有效性检查

这意味着下一次 `deploy-dev` 或 `deploy-prod` 再失败时，日志会更快区分：

- secret 没配
- 私钥内容损坏
- `ssh-keyscan` 或目标主机连通性异常

## 4. 当前残留风险

1. GitHub Actions YAML 尚未在线实跑，因此现阶段结论以本地脚本验证为主
2. auto-repair 能力当前是“受控框架已具备”，但是否真正改代码，取决于外部修复命令是否配置
3. runner watchdog 需要额外主机或自动化入口，单靠 runner 本机无法覆盖“整机宕机”
4. 当前环境没有 `actionlint`，因此尚未做 GitHub Actions 语义级 lint
5. 执行健康巡检虽然已补入口，但线上是否真正拦住“running 无回写”仍需在 automation 节点联调验证
