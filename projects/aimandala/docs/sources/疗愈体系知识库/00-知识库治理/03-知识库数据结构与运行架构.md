# 知识库数据结构与运行架构

> 状态：draft
> 版本：0.1.0
> date：2026-05-14
> owner：CEO / Knowledge Base / Architect
> source_of_truth：当前目录/00-知识库治理/03-知识库数据结构与运行架构.md

本文定义疗愈体系知识库的数据结构、材料组织方式、RAG 使用方式、切块原则和后续技术栈方向。

## 1. 应用场景

疗愈体系知识库至少要支撑三类当前能力：

1. 生成解读报告。
2. 回答用户围绕解读报告提出的追问。
3. 生成定制化疗愈建议。

后续还可能增加更多应用：

4. AI 在分析画面后，先向用户提出补充问题，再结合用户回答生成更精准的解读报告。
5. 基于某个议题生成课程、训练营、陪伴方案或练习手册。
6. 基于疗愈路径生成内容选题、社群引导材料或衍生产品素材。

因此，疗愈体系知识库不能只做成一组给人看的 Markdown 文档。它需要同时服务人工维护和机器运行。

## 2. 总体分层

疗愈体系知识库建议分成四层：

```text
source index layer     来源索引层
llm wiki layer         自然语言知识层
structured layer       机器可读的结构化知识
runtime layer          产品运行时实际调用的数据
```

### 2.1 Source Index Layer

`source index layer` 是来源索引层，记录研究母库、专家手册、案例源、课程材料和外部资料在本知识库中的引用关系。

这里的重点是“可追溯”，不是直接给产品调用，也不是重复保存来源正文。来源正文优先维护在 `projects/research-center/kb` 或已迁入的来源文件中。

### 2.2 LLM Wiki Layer

`LLM wiki layer` 可以理解为“给人和大模型共同阅读的自然语言知识库”。

它接近 Karpathy 提到的 `LLM Wiki` 思路：把来源材料按自己的框架整理成清晰、稳定、可阅读的 Markdown 文档，让 AI 协作时有一个高质量的自然语言上下文。

这里存放：

- 议题体系说明。
- 议题体系说明。
- 流派知识整理。
- 疗愈方案材料。
- 应用适配规范。

这一层的作用是：

- 给人维护和审核。
- 给 AI 协作时读取和理解。
- 承接专家经验、案例表达和理论框架。
- 为后续结构化提供稳定来源。

但它不应直接等同于最终运行时。

### 2.3 Structured Layer

`structured layer` 是结构化知识层，后续建议用 YAML / JSON 表达。

它把 Markdown 中的内容拆成可检索、可组合、可追溯的知识单元。

### 2.4 Runtime Layer

`runtime layer` 是运行时知识包。

它面向产品能力，包括：

- 生成报告时按主题和画面信号取知识。
- 用户追问时检索相关条款。
- 生成疗愈方案时取对应建议。
- 记录每段生成内容引用了哪些知识条款。

运行时不应直接依赖整篇 Markdown，而应依赖经过校验的 `JSON pack`、索引和检索结果。

## 3. 核心知识对象

本知识库的基本单位不应是“文件”，而应是“知识单元”。

建议至少包含以下对象类型：

- `domain`：议题域，例如财富、亲密关系、事业、健康。
- `issue_clause`：议题条款，例如配得感不足、情绪型漏财、求认可式赚钱。
- `visual_signal`：画面信号，例如外圈红色多、土不成片、金克木。
- `mapping_rule`：画面信号到议题条款的映射规则。
- `report_block`：报告段落素材或生成指引。
- `followup_answer`：追问回答素材。
- `healing_intervention`：疗愈建议，例如蓝色清理、腹式呼吸、感恩日记。
- `course_block`：课程、训练营、练习手册或陪伴方案的内容素材。
- `source_ref`：来源引用。

## 4. 知识单元字段建议

一个最小知识单元可以这样设计：

```yaml
id: wealth.self_worth.low_deservingness
version: 0.1.0
status: draft
domain: wealth
type: issue_clause
title: 配得感不足
summary: 用户在财富议题中觉得自己不值得拥有更多。
applies_to:
  - report_generation
  - followup_qa
  - healing_plan
content:
  explanation: 用户可能把财富结果和自我价值绑定在一起。
  typical_signals:
    - 需要不断证明自己才敢收钱。
    - 拿到结果后仍然不满意。
  healing_direction:
    - 建立稳定的自我价值感。
    - 区分价值创造和自我证明。
evidence:
  source_refs:
    - 20-疗愈体系/10-议题层/01-财富议题体系框架.md#配得感不足
mapping:
  visual_signals:
    - metal_excess
    - weak_earth
safety:
  avoid:
    - 不写成财务承诺。
    - 不写成心理诊断。
```

字段设计要满足三件事：

- 能被检索。
- 能被组合。
- 能追溯来源。

## 5. 材料组织原则

本知识库的组织逻辑不是“把所有材料堆进一个 wiki”，而是按知识生产流程组织：

```text
研究母库 / 来源索引 / 培训材料 / 案例源
        ↓
LLM Wiki 自然语言知识层
        ↓
20-疗愈体系 / 10-议题层
        ↓
20-疗愈体系 / 30-疗愈方案层
        ↑
20-疗愈体系 / 20-流派层 / 曼陀罗
        ↓
30-应用适配 / 报告 / 追问 / 课程 / 交互生成规范
        ↓
runtime pack
```

关键原则：

- 议题层是语义中心，不是画面映射。
- 先建设议题本身，再做画面映射。
- 画面信息不能直接等同于最终结论。
- 画面信息应先变成 `visual_signal`，再映射到 `issue_clause`。

## 6. RAG 使用方式

本知识库需要使用 RAG，但不能只做普通的 `LLM wiki`。

`RAG` 是 `Retrieval-Augmented Generation`，中文可以理解为“检索增强生成”。它的作用是：LLM 在生成回答前，先从知识库检索相关材料，再基于检索结果生成内容。

本知识库适合使用：

```text
结构化知识库 + RAG 检索 + 映射规则 + LLM 生成
```

而不是：

```text
把所有文档丢进 wiki，让 LLM 自己查
```

原因是本知识库的推理链路有结构：

```text
画面特征 → 画面信号 → 议题条款 → 报告表达 → 疗愈建议
```

普通 wiki 式检索容易把上下文找出来，但不保证映射关系正确。

## 7. RAG 切块原则

本知识库需要切块，但不能按普通字数切块。

不推荐：

- 每 500 字切一段。
- 每 1000 token 切一段。
- 机械按 Markdown 标题切。

推荐按知识单元切块：

- 一个议题条款一个 chunk。
- 一个画面信号一个 chunk。
- 一个五行关系一个 chunk。
- 一个疗愈建议一个 chunk。
- 一个案例中的“一圈解读”或“调整方案”一个 chunk。

每个 chunk 都要带元数据：

```yaml
id: wealth.leak_money.outer_red
type: visual_signal
domain: wealth
scenario:
  - report_generation
  - followup_qa
source: 20-疗愈体系/20-流派层/10-曼陀罗/10-画面语言/11-新手解读6式.md
version: 0.1.0
```

长条款内部可以继续拆成子 chunk：

- `explanation`：解释。
- `evidence`：依据。
- `report_language`：报告表达。
- `healing_direction`：疗愈方向。
- `case_excerpt`：案例片段。

## 8. 检索策略

不同场景应使用不同检索策略。

### 8.1 生成解读报告

输入可能包括：

- 用户主题。
- 画面观察结果。
- 三圈信息。
- 颜色、形状、五行生克信号。

检索顺序建议：

1. 按主题过滤 `domain`。
2. 按画面信号找 `visual_signal`。
3. 通过 `mapping_rule` 找相关 `issue_clause`。
4. 取 `report_block` 和 `healing_intervention`。
5. 生成报告。

### 8.2 回答用户追问

输入包括：

- 用户问题。
- 原报告中的相关段落。
- 当前会话上下文。

检索顺序建议：

1. 找到原报告相关判断。
2. 检索对应议题条款。
3. 检索对应画面信号和解释依据。
4. 生成回答，并保持和原报告一致。

### 8.3 生成疗愈方案

输入包括：

- 用户当前议题。
- 已识别卡点。
- 用户可接受的练习方式。
- 风险和禁忌。

检索顺序建议：

1. 取对应 `issue_clause`。
2. 取对应 `healing_intervention`。
3. 按强度、周期、用户状态筛选。
4. 生成可执行方案。

### 8.4 AI 追问用户

如果画面信息不足或存在多个可能解释，AI 可以先向用户提问。

提问应服务于区分议题条款，例如：

- 这个问题更像财富压力，还是关系压力？
- 你最近花钱更多是因为开心奖励自己，还是因为情绪低落想安抚自己？
- 你想赚钱更多是为了自由、创造，还是为了逃离某种关系或环境？

用户回答后，再选择更准确的 `issue_clause` 和 `healing_intervention`。

## 9. 版本迭代

本知识库不需要一次性完成。

建议按 pack 版本迭代：

```text
1.0.0-alpha.1  财富议题 + 基础画面映射 + 报告组织规范
1.0.0-alpha.2  个人成长 / 自我价值议题
1.0.0-alpha.3  亲密关系议题
1.0.0-beta.1   疗愈方案库增强 + 追问问答增强
1.0.0          第一版稳定知识包
```

每次版本更新应记录：

- 新增了哪些知识单元。
- 修改了哪些知识单元。
- 废弃了哪些知识单元。
- 哪些报告能力受影响。
- 哪些测试案例需要重新验证。

## 10. 技术栈建议

### 10.1 当前阶段

当前阶段建议保持轻量：

- Markdown：维护知识源。
- YAML frontmatter：维护文档元信息。
- YAML / JSON：维护知识单元。
- JSON Schema：校验数据结构。
- Python：构建、校验、转换知识包。

### 10.2 产品化阶段

进入产品化后建议：

- JSON pack：运行时知识包。
- SQLite 或 Postgres：存结构化条款。
- pgvector 或等价向量库：支持语义检索。
- Embedding：把知识单元向量化。
- FastAPI：提供知识检索和生成接口。
- LLM API：生成报告、追问回答和疗愈方案。

### 10.3 后续增强

后续可以增加：

- Rule engine：处理画面信号到议题条款的权重。
- Eval set：用案例测试报告质量。
- Trace：记录每段生成内容引用了哪些知识单元。
- Pack diff：比较不同版本知识包的变化。

当前阶段不必一次性创建所有目录。建议先把数据结构和构建规则写清楚，再逐步建立 `runtime/`。

## 12. 当前结论

本知识库应采用：

```text
Markdown 源资料
  → 结构化知识单元
  → 语义 chunk
  → RAG 检索
  → 映射规则
  → LLM 生成
```

它不是普通 wiki，也不是只靠 prompt 的知识库。

它应是一个可版本化、可检索、可追溯、可运行的知识系统。
