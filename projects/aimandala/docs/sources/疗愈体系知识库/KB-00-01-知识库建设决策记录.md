本文沉淀疗愈体系知识库建设过程中的关键讨论结论，作为后续整理资料、设计数据结构、实现 RAG、生成报告、生成疗愈方案和开发衍生产品时的决策依据。

## 1. 建设目标

疗愈体系知识库从头建设。外部来源材料只有在被重新整理、标注来源、确认适合进入本知识库后，才可以成为正式知识源。

本知识库的上层边界是“疗愈体系”，不是某一个单一应用。曼陀罗解读是当前第一条落地链路，后续同一套议题、条款和疗愈路径可以继续用于课程、训练营、陪伴方案、内容产品和其他衍生产品。

这样做的原因是：知识库需要保持清晰边界，避免未经整理的材料自动进入 AI 协作、内容生成、知识整理或报告规则设计过程。

当前至少服务三类产品场景：

1. 生成解读报告。
2. 回答用户围绕解读报告提出的追问。
3. 生成定制化疗愈方案。
4. 支撑课程、练习、陪伴方案和内容产品的后续开发。

后续还可能支持一种更主动的交互：AI 在分析画面后，先向用户提出补充问题，再结合用户回答生成更精准的解读报告。

## 2. 知识库形态

本知识库不应只做成给人看的 wiki，也不应只靠 prompt 保存知识。

推荐形态是：

```text
Markdown 源资料
  → LLM Wiki 自然语言知识层
  → 结构化知识单元
  → 可检索 chunk
  → RAG 检索
  → 映射规则
  → LLM 生成
```

其中：

- `Markdown` 用于人工维护、阅读、审核和追溯。
- `结构化知识单元` 用 YAML / JSON 表达，让机器能稳定读取。
- `chunk` 是 RAG 检索时的最小材料块。
- `映射规则` 用来连接画面信号和议题条款。
- `LLM` 负责把检索出的材料组织成报告、追问回答和疗愈建议。

这里的 `RAG` 是 `Retrieval-Augmented Generation`，可以理解为“检索增强生成”：AI 在回答前，先从知识库中找出相关材料，再基于这些材料生成内容。

## 3. 议题层先行

本知识库的议题层不能只从 11 个案例中反推出完整体系。

11 个原始案例有价值，因为它们来自真实解读经验，可以帮助我们学习：

- 疗愈师如何组织报告。
- 个案中常见的表达方式。
- 某些议题在实际解读中的呈现。
- 报告语言如何从观察走向解释和建议。

但 11 个案例数量有限，不能代表完整议题。比如财富议题不能只由这些案例中出现过的财富表达构成。

更合理的顺序是：

1. 先不考虑画面因素，建立议题本身的框架体系。
2. 用心理学流派、疗愈流派、培训材料和专题资料填充议题内容。
3. 用 11 个案例校验报告语言、案例表达和部分高频模式。
4. 再把画面信息映射到议题条款。

也就是说，`KB-03` 议题层应先回答“这个议题本身是什么”，`KB-01` 和 `KB-02` 后续再回答“哪些画面信号可能指向这个议题条款”。

## 4. 材料组织方式

本知识库的材料应按知识生产链路组织：

```text
参考文献 / 培训材料 / 原始案例
        ↓
KB-03 议题层
        ↓
KB-04 疗愈方案层
        ↑
KB-01 画面层 → KB-02 映射层
        ↓
KB-05 报告、追问、交互规范
        ↓
runtime pack
```

各层职责如下：

| 层级 | 职责 |
|------|------|
| `KB-01` 画面层 | 描述画面上能观察到什么，例如三圈、颜色、形状、位置关系。 |
| `KB-02` 映射层 | 把画面特征整理成可解释的画面信号，例如五行关系、圈层失衡、高频组合。 |
| `KB-03` 议题层 | 建立财富、关系、事业、健康、自我价值等议题的完整知识框架。 |
| `KB-04` 疗愈方案层 | 沉淀颜色处方、绘画练习、冥想、日常行动等干预方案。 |
| `KB-05` 执行规范层 | 定义报告结构、追问回答、沟通边界和生成规范。 |
| `参考文献` | 保存来源说明、培训材料、案例源和外部理论依据。 |
| `runtime` | 后续保存机器运行时使用的 schema、unit、pack、index 和 eval。 |

## 5. 数据结构

本知识库的基本单位不应是整篇文档，而应是“知识单元”。

建议的对象类型包括：

| 对象 | 含义 |
|------|------|
| `domain` | 议题域，例如财富、亲密关系、事业、健康。 |
| `issue_clause` | 议题条款，例如配得感不足、匮乏感、安全感不足。 |
| `visual_signal` | 画面信号，例如外圈红色多、土不成片、金克木。 |
| `mapping_rule` | 画面信号到议题条款的映射规则。 |
| `report_block` | 报告段落素材或生成指引。 |
| `followup_answer` | 追问回答素材或回答策略。 |
| `healing_intervention` | 疗愈建议，例如呼吸练习、颜色清理、书写练习。 |
| `source_ref` | 来源引用，用来追溯知识来自哪个文档、案例或培训材料。 |

一个知识单元至少要能回答：

- 它是什么？
- 适用于哪个场景？
- 来自哪里？
- 能被哪些画面信号触发？
- 生成报告时可以怎么表达？
- 生成疗愈方案时可以给出什么建议？
- 有哪些安全边界？

## 6. RAG 和切块

本知识库需要 RAG，但不能只把整批 Markdown 丢进向量库。

普通 wiki 式 RAG 容易做到“找相关文字”，但不保证推理链条正确。本知识库的链条更像：

```text
画面特征 → 画面信号 → 议题条款 → 报告表达 → 疗愈建议
```

因此，切块方式应按知识单元切，而不是按固定字数切。

推荐切块方式：

- 一个议题条款一个 chunk。
- 一个画面信号一个 chunk。
- 一个五行关系一个 chunk。
- 一个疗愈建议一个 chunk。
- 一个案例中的“一圈解读”“整体解读”或“调整方案”一个 chunk。

每个 chunk 都应带元数据，例如：

```yaml
id: wealth.self_worth.low_deservingness
type: issue_clause
domain: wealth
scenario:
  - report_generation
  - followup_qa
  - healing_plan
source: KB-03-01-财富议题体系框架.md
version: 0.1.0
status: draft
```

如果一个条款很长，可以继续拆成子块：

- `explanation`：解释。
- `evidence`：依据。
- `report_language`：报告表达。
- `healing_direction`：疗愈方向。
- `case_excerpt`：案例片段。

## 7. 三个场景的调用方式

### 7.1 生成解读报告

输入通常包括用户主题、画面观察结果、颜色、形状、圈层和五行关系。

建议链路：

```text
用户主题
  → 过滤 domain
  → 识别 visual_signal
  → 通过 mapping_rule 找 issue_clause
  → 取 report_block 和 healing_intervention
  → 生成报告
```

### 7.2 回答用户追问

输入通常包括用户问题、原报告段落和会话上下文。

建议链路：

```text
用户追问
  → 定位原报告相关判断
  → 取对应 issue_clause
  → 补充 visual_signal 和 source_ref
  → 生成一致、可解释的回答
```

追问回答要和原报告保持一致，不能因为重新检索到别的材料就推翻前文判断。

### 7.3 生成定制化疗愈方案

输入通常包括已识别议题、卡点、用户状态、可接受练习方式和风险边界。

建议链路：

```text
issue_clause
  → healing_intervention
  → 按强度、周期、适用人群筛选
  → 生成可执行方案
```

疗愈建议不能写成医疗诊断、财务承诺或确定性因果判断。

## 8. 技术栈方向

当前阶段保持轻量：

- `Markdown`：维护源资料。
- `YAML frontmatter`：维护文档元信息。
- `YAML / JSON`：维护结构化知识单元。
- `JSON Schema`：校验知识单元字段。
- `Python`：构建、校验、转换知识包。

产品化阶段再引入：

- `JSON pack`：运行时知识包。
- `SQLite` 或 `Postgres`：保存结构化条款。
- `pgvector` 或向量库：支持语义检索。
- `Embedding`（向量表示）：把知识单元转成可检索向量。
- `FastAPI`：提供检索和生成接口。
- `LLM API`：生成报告、追问回答和疗愈方案。

后续增强能力：

- `rule engine`（规则引擎）：处理画面信号到议题条款的权重。
- `eval set`（评估集）：用案例测试生成质量。
- `trace`（引用追踪）：记录每段生成内容引用了哪些知识单元。
- `pack diff`：比较不同版本知识包的变化。

## 9. 迭代方式

本知识库不需要一次性建设完成，应按版本逐步扩展。

建议每次迭代都记录：

- 新增了哪些知识单元。
- 修改了哪些知识单元。
- 废弃了哪些知识单元。
- 哪些报告能力受影响。
- 哪些测试案例需要重新验证。

建议初始迭代顺序：

| 版本 | 目标 |
|------|------|
| `1.0.0-alpha.1` | 财富议题、基础画面映射、报告组织规范。 |
| `1.0.0-alpha.2` | 个人成长 / 自我价值议题。 |
| `1.0.0-alpha.3` | 亲密关系议题。 |
| `1.0.0-beta.1` | 疗愈方案库增强 + 追问问答增强。 |
| `1.0.0` | 第一版稳定知识包。 |

## 10. 当前执行原则

当前阶段先做四件事：

1. 保持知识库边界清晰，来源资料只做人工迁移。
2. 继续用“原文保真重组”的方式拆解专家手册，保留一线经验表达。
3. 优先把 `KB-03` 议题层建扎实，不让少量案例定义完整议题。
4. 在文档稳定后，再逐步建立 `runtime/schemas`、`runtime/units` 和 RAG 索引。
