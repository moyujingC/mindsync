## 1. 背景

Aimandala 当前的报告生成正在经历一次“旧链保留，新链重建”的过渡期。

此前 legacy report pipeline（旧报告流水线）里混杂了：

- stage package（阶段包）
- prompt builder（提示词构造器）
- draft assembler（草稿拼装器）
- placeholder renderer（占位文案渲染器）
- LLM runtime（大语言模型运行层）

问题是这些层相互改写，容易出现：

1. 模型输出被后处理再次重写
2. placeholder 文案混入最终用户报告
3. 内部标签、开发态兜底语句进入成品
4. 局部修 prompt 之后，又被旧 renderer 覆盖

因此当前正式方向是新增 `mandala_interpretation_agent` 作为旁路重建链路。

旧链保留在代码树和历史资料中，便于：

- 回滚
- 对照
- 理解旧 API / 旧测试为什么仍然失败

但它不再是新报告链的设计基线。

## 2. 当前目标

当前解读智能层的 MVP 只聚焦一个智能体：

1. `Mandala Interpretation Agent`（曼陀罗解读智能体）

下一阶段才考虑：

1. `Report QA Agent`（报告追问智能体）

MVP 阶段的关键要求是：

- 新智能体能生成 Lite / Pro 报告
- 生成过程保留足够多的中间交付物，方便人工审阅
- 同时写出 `Report Context Package`，为未来追问能力保留上下文

## 4. 总体结构

```text
图片 + 用户输入 + 三圈边界
   ↓
Input Collector（输入收集器）
   ↓
Knowledge Pack Builder（知识包构建器）
   ↓
Mandala Interpretation Agent（曼陀罗解读智能体）
   ↓
Artifact Store（交付物存储）
   ├─ agent_input.json
   ├─ knowledge_pack.json
   ├─ agent_output.json
   ├─ interpretation_artifacts.json
   ├─ stage_outputs.json
   ├─ execution_trace.json
   ├─ final_report.json
   ├─ final_report.md
   ├─ report_context_package.json
   └─ quality_gate.json
   ↓
Post-MVP:
Report QA Agent（报告追问智能体）
```

## 5. 方法层与执行层

当前方法真值源固定是：

- [../sources/知识库构建/三圈五行流派解读方法与步骤.md](../sources/知识库构建/三圈五行流派解读方法与步骤.md)

实现层采用“两层结构”：

1. 方法层
   - 保留 16 个 `stage-*`
2. 执行层
   - 压缩成 5 个 execution block

这可以通俗理解成：

- `stage-*` 像完整工序清单，方便回看每一步发生了什么
- execution block 像把相近工序打包成 5 个程序执行段，方便工程实现

### 5.1 Block 1：输入与边界锁定

覆盖：

- `stage-00-input-context`
- `stage-01-user-input-context`
- `stage-02-circle-boundary-decision`

特点：

- 不调用模型
- 固定本次运行的图片、主题、用户输入和三圈边界

### 5.2 Block 2：视觉观察与直断互验

覆盖：

- `stage-03-visual-evidence`
- `stage-04-direct-judgment-high-hit-check`

特点：

- 调用视觉模型
- 输出三圈 visual units（视觉单元）和直断命中情况
- 当前质量门会卡住缺少 visual units 的结果

### 5.3 Block 3：逐圈规则推导

覆盖：

- `stage-05-per-circle-color-shape-element-sensing`
- `stage-06-per-circle-element-generation-control`
- `stage-07-per-circle-imbalance-patterns`
- `stage-08-energy-flow-diagnosis`
- `stage-09-evidence-consolidation`

特点：

- 默认不调用模型
- 主要依赖知识包和程序规则完成逐圈推导

### 5.4 Block 4：解读主轴与写作输入整理

覆盖：

- `stage-10-core-thesis-selection`
- `stage-11-user-facing-framing`
- `stage-12-healing-direction-and-report-branching`

特点：

- 调用文字模型
- 在已有证据基础上选主轴，整理用户可读表达

### 5.5 Block 5：报告生成与质检

覆盖：

- `stage-13-lite-report-draft`
- `stage-14-pro-report-draft`
- `stage-15-visual-assets`
- `stage-16-final-report-assembly`

特点：

- 生成 Lite / Pro 文本产物
- MVP 阶段 `stage-15` 只输出可视化模块定义，不生成真实图片
- `stage-16` 执行文本泄漏检查、证据覆盖检查和上下文包完整性检查

## 6. 关键模块边界

### 6.1 Input Collector

负责：

- 统一读取图片输入
- 归一化主题、用户输入和边界参数
- 形成稳定的 agent input（智能体输入）

不负责：

- 解读推理
- 报告写作

### 6.2 Knowledge Pack Builder

负责：

- 从正式知识源抽取当前运行所需的精简知识
- 组装为结构化 knowledge pack（知识包）

不负责：

- 直接把整份 Markdown 原文塞进 prompt
- 携带 secret（密钥）或环境变量

### 6.3 Mandala Interpretation Agent

负责：

- 组织 5 个 execution block 的执行
- 输出 16 个 `stage-*`
- 产出 Lite / Pro 报告
- 产出中间交付物
- 产出上下文包

不负责：

- 支付、订单和登录
- 历史列表改造
- 多轮追问

### 6.4 Quality Gate

当前至少检查：

1. JSON 是否可解析
2. 必要文件是否齐全
3. 16 个 `stage-*` 是否齐全
4. 三圈 visual units 是否齐全
5. `evidence_map` 是否为空
6. 最终用户报告是否泄漏内部词
7. `Report Context Package` 是否缺关键字段

### 6.5 Artifact Store

负责把运行结果写成一组可审阅文件。

这一步很重要，因为当前阶段不是直接上线，而是先让：

- 工程侧看结构是否稳定
- QA 看质量门是否有效
- 产品 / 内容侧看报告是否像最终用户能读的东西

## 7. 当前输入输出合同

当前最小输入内容包括：

- 图片路径或存储 key
- 主题与主题标签
- 创作前意图
- 创作时感受
- 三圈边界
- 报告模式：Lite / Pro
- 输出语言与语气要求

当前最小输出文件包括：

- `agent_input.json`
- `knowledge_pack.json`
- `agent_output.json`
- `interpretation_artifacts.json`
- `stage_outputs.json`
- `execution_trace.json`
- `final_report.json`
- `final_report.md`
- `report_context_package.json`
- `quality_gate.json`

## 8. 与现有主链的关系

当前要特别注意这件事：

- 新智能体已经有离线原型
- 现有 API 默认主链还没有正式切过去

所以现在的正确说法是：

1. `mandala_interpretation_agent` 是新报告链的 active architecture（当前生效架构）
2. 它在实现上还处于“离线原型已落地，在线接入待推进”的状态
3. 旧链相关代码仍会影响现有单测和 API 行为，但不再是新设计依据

## 9. Post-MVP 方向

下一阶段才考虑新增：

1. `Report QA Agent`
2. 基于 `Report Context Package` 的追问回答
3. Lite / Pro 权限控制
4. 追问历史上下文
5. 报告依据引用展示

在这之前，不应把“追问智能体”写成当前已落地能力。
