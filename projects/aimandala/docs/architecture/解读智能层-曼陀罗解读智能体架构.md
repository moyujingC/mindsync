## 1. 背景

当前报告生成链路由 stage package、prompt builder、draft assembler、placeholder renderer、LLM runtime 和 report contract 多层共同完成。最近的真实模型跑数显示，报告质量问题主要来自链路混合：

- 模型输出会被 draft assembler 和 placeholder renderer 再加工
- 用户可见文案仍有一部分来自 placeholder（占位）生成器
- 内部标签、stage 判断和开发态兜底句会进入最终报告
- 继续局部修 prompt 或局部修 stage，仍会被旧 renderer 改写

后续报告生成新增一条旁路的解读智能层。旧链路保留为回滚和对照样本，不再承担报告质量升级。

## 2. 架构目标

`解读智能层` 包含两个智能体：

1. `曼陀罗解读智能体`
2. `报告追问智能体`

MVP 阶段先实现 `曼陀罗解读智能体`。MVP 上线后，下一阶段实现 `报告追问智能体`。

MVP 不实现追问能力，但 `曼陀罗解读智能体` 要在生成报告时同步保存 `Report Context Package`（报告上下文包）。后续追问智能体基于这份上下文回答问题。

## 3. 阶段范围

### 3.1 MVP 要做

- 新增 `Mandala Reading Agent`（曼陀罗解读智能体）运行时
- 生成 Lite / Pro 报告
- 读取画作、三圈边界、主题、用户输入和精简知识包
- 输出中间解读交付物
- 输出结构化报告 JSON
- 输出报告 Markdown
- 输出 `Report Context Package`
- 输出自检结果和质量门结果
- 先通过离线 fixture runner 验证，再以 feature flag（功能开关）接入 API

### 3.2 MVP 不做

- 不实现 `Report QA Agent`（报告追问智能体）
- 不删除旧报告生成链路
- 不重构上传、支付、订单、用户身份和历史记录主链
- 不把完整 Markdown 真值源直接塞进模型上下文
- 不让旧 placeholder renderer 继续参与新链路的最终报告生成

### 3.3 Post-MVP 要做

- 新增 `Report QA Agent`（报告追问智能体）
- 基于 MVP 产出的 `Report Context Package` 回答用户追问
- 处理 Lite / Pro 权限边界
- 处理追问历史上下文
- 返回报告依据引用和边界提醒

## 4. 总体结构

```text
图片 + 用户输入 + 三圈边界
   ↓
Input Collector（输入收集器）
   ↓
Knowledge Pack Builder（知识包构建器）
   ↓
Mandala Reading Agent（曼陀罗解读智能体）
   ↓
Report Artifacts（报告交付物）
   ├─ interpretation_artifacts.json
   ├─ final_report.json
   ├─ final_report.md
   ├─ report_context_package.json
   └─ quality_gate.json
   ↓
Post-MVP:
Report QA Agent（报告追问智能体）
```

## 5. 方法 stage 与 MVP 执行块

完整解读链路以 [三圈五行流派解读方法与步骤.md](../sources/知识库构建/三圈五行流派解读方法与步骤.md) 为准。

MVP 运行时保留 16 个 `stage-*` 作为方法交付物和 QA 追溯结构，同时把执行过程压缩成 5 个 execution block（执行块）。执行块只影响程序如何组织运行，不改变方法顺序。

```text
方法层：16 个 stage
执行层：5 个 MVP block
```

### 5.1 Block 1：输入与边界锁定

覆盖：

- `stage-00-input-context`
- `stage-01-user-input-context`
- `stage-02-circle-boundary-decision`

执行方式：

- 不调用模型
- 固定运行上下文、用户输入、主题和三圈边界
- 输出后续步骤共用的基础上下文

### 5.2 Block 2：视觉观察与直断互验

覆盖：

- `stage-03-visual-evidence`
- `stage-04-direct-judgment-high-hit-check`

执行方式：

- 调用视觉模型
- 用程序规则做直断模式校验
- 只记录可见证据、命中项、冲突项和不确定项

### 5.3 Block 3：逐圈规则推导

覆盖：

- `stage-05-per-circle-color-shape-element-sensing`
- `stage-06-per-circle-element-generation-control`
- `stage-07-per-circle-imbalance-patterns`
- `stage-08-energy-flow-diagnosis`
- `stage-09-evidence-consolidation`

执行方式：

- 默认不调用模型
- 使用运行时知识包和程序规则完成颜色、形状、五行、生克、失衡、能量流动和证据池整合
- 保留每个判断对应的证据和知识引用

### 5.4 Block 4：解读主轴与写作输入整理

覆盖：

- `stage-10-core-thesis-selection`
- `stage-11-user-facing-framing`
- `stage-12-healing-direction-and-report-branching`

执行方式：

- 一次文字模型调用
- 在已有证据之间选择解读主轴
- 生成用户可见表达框架、术语解释、疗愈方向和 Lite / Pro 写作输入

### 5.5 Block 5：报告生成与交付质检

覆盖：

- `stage-13-lite-report-draft`
- `stage-14-pro-report-draft`
- `stage-15-visual-assets`
- `stage-16-final-report-assembly`

执行方式：

- 按需生成 Lite 或 Pro 报告
- MVP 阶段 `stage-15` 只输出可视化模块定义，不生成真实图片
- `stage-16` 执行文本质量门、证据覆盖检查和最终组装

## 6. 模块边界

### 6.1 Input Collector

输入收集器只负责收集和归一化运行输入，不做解读。

输入来源包括：

- 图片本地路径或存储 key
- 三圈边界
- 用户主题
- 创作前意图
- 创作时感受
- 报告版本：Lite / Pro
- 用户购买权限

范围外：

- 五行判断
- 主题解释
- 报告文案生成

### 6.2 Knowledge Pack Builder

知识包构建器负责把正式知识源压缩成模型可用的精简知识包。

知识包内容：

- 方法摘要
- 三圈含义摘要
- 颜色到五行的映射规则
- 形状与画面线索规则
- 主题知识摘要
- 失衡类型摘要
- 疗愈建议边界

禁止放入知识包：

- 完整 Markdown 真值源
- 旧报告骨架、旧 prompt skeleton、旧容器
- private env、API key 或运行时 secret

### 6.3 Mandala Reading Agent

曼陀罗解读智能体是 MVP 阶段的主生成链路。

它负责：

- 观察画作
- 结合三圈边界理解内圈、中圈、外圈
- 结合五行规则形成解释
- 结合主题和用户输入确定解读主轴
- 生成 Lite / Pro 报告
- 输出可审阅的中间解读交付物
- 输出给追问智能体复用的报告上下文包
- 保留 16 个 `stage-*` 交付物，方便 QA 回看完整方法链

范围外：

- 支付和订单
- 上传存储
- 用户身份
- 报告生成后的多轮追问

### 6.4 Report Artifact Store

报告交付物存储负责保存智能体输出。

MVP 至少保存：

- `agent_input.json`
- `knowledge_pack.json`
- `agent_output.json`
- `interpretation_artifacts.json`
- `final_report.json`
- `final_report.md`
- `report_context_package.json`
- `quality_gate.json`

### 6.5 Quality Gate

质量门负责判断报告能否进入用户可见状态。它检查的是最终用户可见报告和面向用户的摘要，不检查供 QA 使用的 `stage_outputs` 键名。

MVP 至少检查：

- JSON 结构完整
- Markdown 非空
- Lite / Pro 字段完整
- 不包含内部标签泄漏
- 不包含开发态语言
- 不包含 placeholder 兜底句
- 不包含 forbidden input 标记
- 报告主判断能回到中间解读交付物

典型禁止文本包括：

- `stage-`
- `transition-overload`
- `待完整 stage 证据确认`
- `需要进一步确认`
- `应由 stage`
- `回到画面证据`
- `placeholder`
- `legacy`

## 10. 与旧链路的关系

### 10.1 旧链路冻结

旧报告链路保留为：

- 回滚路径
- 对照样本
- 历史记录兼容路径

旧链路不再承担报告质量升级。

### 10.2 新链路旁路接入

接入 API 前，先用离线 runner 验证。

建议新增：

```text
app/core/reading_intelligence/
  __init__.py
  contracts.py
  input_collector.py
  knowledge_pack_builder.py
  mandala_reading_agent.py
  quality_gate.py
  artifact_store.py

scripts/run_mandala_reading_agent_fixture.py
```

旁路接入时使用 feature flag：

```text
AIMANDALA_REPORT_GENERATION_RUNTIME=legacy | mandala_reading_agent
```

### 10.3 旧 placeholder renderer 边界

新链路不再调用：

- `ReportPlaceholderAssembler`
- `report_pipeline_output_components.py` 中的 `_build_lite_*`
- `report_pipeline_output_components.py` 中的 `_build_pro_*`

这些旧组件仅保留给 legacy fallback 和历史调试入口。

## 11. 实现阶段

### Phase 0：架构收口

- 建立本架构文档
- 明确 MVP / Post-MVP 边界
- 明确旧链路冻结策略
- 明确 16 个方法 stage 和 5 个执行块的分工

### Phase 1：离线原型

- 新增 `reading_intelligence` 模块
- 新增 contracts
- 新增 fixture runner
- 使用真实模型跑 3-5 个 fixture
- 输出完整审阅产物
- 输出 16 个 `stage-*` 交付物
- 输出 5 个 execution block 的运行 trace

### Phase 2：质量门

- 增加 forbidden language gate
- 增加 internal label leak gate
- 增加 empty / generic report gate
- 增加 evidence coverage gate

### Phase 3：旁路接入

- 在 API 层增加 runtime 选择
- 默认仍走 legacy
- 本地和灰度环境允许切到 `mandala_reading_agent`

### Phase 4：MVP 切换

- 通过 fixture 审阅
- 通过真实模型 smoke
- 通过 Lite / Pro 验收
- 默认切到 `mandala_reading_agent`

### Phase 5：Post-MVP 报告追问智能体

- 新增 `Report QA Agent`
- 使用 `Report Context Package`
- 支持 Lite / Pro 权限边界
- 支持多轮追问

## 12. 关键风险

### 12.1 单智能体上下文过大

知识包过大会增加泛化和漏读风险。MVP 限制知识包大小，只给当前任务需要的规则。

### 12.2 只写 Markdown 导致追问返工

MVP 如果只保存最终 Markdown，Post-MVP 追问智能体会缺少依据。MVP 阶段要保存 `Report Context Package`。

### 12.3 新旧链路混用

新链路禁止把 LLM 输出送回旧 placeholder renderer。这个混用方式会复现当前质量问题。

### 12.4 质量门过弱

只检查 JSON parse 不能阻止空泛报告上线。质量门要检查内部标签、占位句、开发态语言和证据覆盖。

### 12.5 执行块替代方法 stage

5 个 execution block 只是运行组织方式。如果实现时丢掉 16 个 `stage-*` 交付物，QA 会失去方法追溯入口，后续报告追问智能体也会缺少依据。

## 14. Handoff 给 Test / QA

Test / QA 下一步定义解读智能层的验收口径。

最小验收场景：

- Lite 报告没有内部标签泄漏
- Pro 报告不出现开发态占位句
- 报告能具体引用画面观察
- 报告能解释三圈与五行关系
- 报告能关联用户主题
- 16 个 `stage-*` 交付物可以追溯到方法真值源
- 5 个 execution block 没有替代或删减方法 stage
- `Report Context Package` 足够支持下一阶段追问
- 真实模型失败时不会静默生成伪报告
