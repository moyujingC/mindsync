## 1. 目标

本方案只回答一个问题：

- 在不把知识源资料混入公司级知识库的前提下，如何把 `aimandala` 的报告生成链路重构成一条 `evidence-first` 的正式运行时链路

这里的 `evidence-first` 指：

- 先保留结构化证据
- 再做规则推导
- 再做 narrative 装配
- 最后才形成 Lite / Pro 报告合同

而不是继续走：

- projection 文本先行
- 再把文本反向塞回报告

## 2. 当前问题

当前链路的主要问题不是没有知识，而是知识在进入报告前被层层压平：

1. `Layer 0` 已经开始具备证据化字段，但仍混有聚合摘要和 fallback 占位。
2. `ImbalanceService` 仍偏 dominance rule，无法充分承接原始 20 种失衡体系。
3. `NarrativeContextService` 仍把知识进一步压成 narrative projection。
4. `ReportPromptPreviewBuilder` 的 `knowledge_skeleton` 仍更接近 projection-first 结构。
5. 最终 `report_contracts` 没有把证据来源和 fallback 语义稳定暴露给前端与 QA。

## 3. 目标分层

本轮固定采用下面五段链路：

1. `Source Basis`
2. `Runtime Evidence`
3. `Narrative Plan`
4. `Report Assembly`
5. `Report Contract`

### 3.1 Source Basis

唯一正式来源固定为：

- [../sources/知识库构建/当前正式依据与使用说明.md](/Users/xinran/.codex/worktrees/0aa2/mindsync/projects/aimandala/docs/sources/知识库构建/当前正式依据与使用说明.md) 中 `A. 当前正式依据`

这层不直接给 report contract 供数据，只负责界定：

1. 哪些资料可以定义当前行为
2. 哪些资料只作理论支撑
3. 哪些资料只能作历史样本

### 3.2 Runtime Evidence

这层是本轮重构的第一主战场。

目标是让 `Layer 0` 成为真正的证据层，最少固定包含：

1. `visual_facts`
   - 视觉检测事实
   - 三圈边界
   - 颜色与形状识别
2. `knowledge_hits`
   - 命中的主题、圈层、颜色、形状、疗愈和规则条目
3. `rule_evaluations`
   - 失衡判断
   - 主题映射
   - 三元状态和四步法中间判断
4. `theme_projection`
   - 主题下对后续 narrative 真正可消费的结构化投影
5. `fidelity_flags`
   - 保真警告
   - 压缩点标记
6. `fallback_summary`
   - fallback 是否发生
   - 发生在哪层
   - 对输出造成什么影响

这层不再承担“直接帮报告写段落”的职责。

### 3.3 Narrative Plan

这层的职责是把证据层装配成可生成报告的叙事计划，而不是重新推导知识。

这层允许产出：

1. 主题视角下的叙事排序
2. Lite / Pro 不同深度下的段落规划
3. 疗愈、洞察和主题建议的组织顺序

这层不允许：

1. 绕开 evidence 直接造结论
2. 把 fallback 和正式命中混在一起
3. 用 narrative 模板替代规则判断

### 3.4 Report Assembly

这层负责把 `Narrative Plan` 组装成 Lite / Pro 草稿和最终报告。

要求是：

1. Lite / Pro 草稿结构来自同一条 evidence-first 链
2. Lite 和 Pro 的差异体现在深度、证据展开、规则解释和疗愈层次，不靠纯文案切分
3. 组装阶段可以润色表达，但不能改写证据结论

当前新增固定口径：

1. `Lite` 输出独立轻疗愈区块
2. `Lite` 中的 `Pro` 入口按独立产品语义表达
3. `Pro` 输出完整疗愈方案，不再被产品语义误读为 `Lite` 的续篇

### 3.5 Report Contract

这层负责输出给前端和 debug 侧真正消费的合同。

本轮固定要求：

1. 结果合同允许调整
2. debug payload 必须稳定承接 trace 信息
3. 前端拿到合同后，不需要再猜“哪些段落可靠、哪些是兜底”

## 4. 关键接口约束

### 4.1 Layer 0 约束

`Layer0Raw` 后续要被视为正式接口，而不是内部临时结构。

它必须满足：

1. 同时可服务 orchestration、prompt、report 和 QA
2. 任何主要字段都能回答“它是视觉事实、知识命中还是规则推导”
3. fallback 不能只体现在 warning 文本里，必须结构化

### 4.2 Narrative 约束

`NarrativeContextService` 与等价服务后续只能消费：

1. evidence
2. rule evaluations
3. theme projection

不能继续把：

- theme narrative asset
- 通用模板
- fallback 提示

拼成一个新的“伪知识层”。

### 4.3 Contract 约束

`report_contracts` 后续必须显式区分：

1. 用户主结果
2. trace / debug 信息
3. fallback / fidelity 信息

不允许把 trace 信息只留在调试台，主结果却无法校验来源。

## 5. 分批实现边界

### 5.1 Batch A

负责：

- `Layer0Assembler`
- `ImbalanceService`
- 主题与运行时 evidence 映射

不负责：

- 前端结果合同

### 5.2 Batch B

负责：

- `NarrativeContextService`
- `ReportPromptPreviewBuilder`
- `knowledge_skeleton`

不负责：

- 前端渲染

### 5.3 Batch C

负责：

- `report_contracts`
- 前端 API 类型
- 结果页与 debug 面板承接

### 5.4 Batch D

负责：

- golden / fixture / drift 验证
- README 索引与交付收口

## 6. 风险与默认策略

本轮默认采用下面策略：

1. 不做长期双合同维护。
2. 允许临时兼容字段，但只能跨同一轮实现窗口存在。
3. fallback 保留，但必须被治理，不再允许隐形兜底。
4. 旧 `V2` 资产继续保留为输入来源，不从零重写 pack。
