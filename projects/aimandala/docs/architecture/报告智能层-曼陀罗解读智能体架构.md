## 1. 背景

当前报告生成链路由 stage package、prompt builder、draft assembler、placeholder renderer、LLM runtime 和 report contract 多层共同完成。实际运行后暴露出一个核心问题：

- 模型输出不是最终报告的唯一来源
- 大量用户可见文案仍来自 placeholder（占位）生成器
- 内部标签、stage 判断和开发态兜底句容易泄漏到最终报告
- Lite / Pro 报告质量很难通过局部修 prompt 或局部修 stage 得到根本改善

因此，后续报告生成不再继续把旧链路作为质量提升对象，而是新增一条旁路的报告智能层。

## 2. 架构目标

新增 `报告智能层`，包含两个智能体能力：

1. `曼陀罗解读智能体`
2. `报告追问智能体`

MVP 阶段只实现 `曼陀罗解读智能体`。MVP 上线后，紧接着实现 `报告追问智能体`。

虽然 MVP 不实现追问能力，但 `曼陀罗解读智能体` 必须在生成报告时同步产出 `Report Context Package`（报告上下文包），作为后续追问智能体的正式输入。

## 3. 阶段范围

### 3.1 MVP 要做

- 新增 `Mandala Reading Agent`（曼陀罗解读智能体）运行时
- 支持 Lite / Pro 报告生成
- 读取画作、三圈边界、主题、用户输入和精简知识包
- 输出中间解读交付物
- 输出最终报告结构化 JSON
- 输出最终报告 Markdown
- 输出 `Report Context Package`
- 输出自检结果和质量门结果
- 先通过离线 fixture runner 验证，再以 feature flag（功能开关）旁路接入正式 API

### 3.2 MVP 不做

- 不实现 `Report QA Agent`（报告追问智能体）
- 不删除旧报告生成链路
- 不重构上传、支付、订单、用户身份和历史记录主链
- 不把完整 Markdown 真值源直接塞进模型上下文
- 不让旧 placeholder renderer 继续参与新链路的最终报告生成

### 3.3 Post-MVP 要做

- 新增 `Report QA Agent`（报告追问智能体）
- 使用 MVP 产出的 `Report Context Package` 回答用户追问
- 支持 Lite / Pro 权限边界
- 支持追问历史上下文
- 支持报告依据引用和边界提醒

## 4. 总体结构

```text
图片 + 用户输入 + 三圈边界
   ↓
Input Collector（输入收集器）
   ↓
Knowledge Pack Builder（知识包构建器）
   ↓
Mandala Reading Agent（曼陀罗解读智能体）
   ↓
Report Artifacts（报告交付物）
   ├─ interpretation_artifacts.json
   ├─ final_report.json
   ├─ final_report.md
   ├─ report_context_package.json
   └─ quality_gate.json
   ↓
Post-MVP:
Report QA Agent（报告追问智能体）
```

## 5. 模块边界

### 5.1 Input Collector

输入收集器只负责收集和归一化运行输入，不做解读。

输入来源包括：

- 图片本地路径或存储 key
- 三圈边界
- 用户主题
- 创作前意图
- 创作时感受
- 报告版本：Lite / Pro
- 用户购买权限

它不负责：

- 不做五行判断
- 不做主题解释
- 不生成报告文案

### 5.2 Knowledge Pack Builder

知识包构建器负责把正式知识源压缩成模型可用的精简知识包。

它可以包含：

- 方法摘要
- 三圈含义摘要
- 颜色到五行的映射规则
- 形状与画面线索规则
- 主题知识摘要
- 失衡类型摘要
- 疗愈建议边界

它不允许：

- 不把完整 Markdown 真值源塞进 prompt
- 不把旧报告骨架、旧 prompt skeleton、旧容器交给智能体
- 不把 private env、API key 或运行时 secret 放入上下文

### 5.3 Mandala Reading Agent

曼陀罗解读智能体是 MVP 的核心能力。

它负责：

- 观察画作
- 结合三圈边界理解内圈、中圈、外圈
- 结合五行规则形成解释
- 结合主题和用户输入确定核心主轴
- 生成 Lite / Pro 报告
- 产出可审阅的中间解读交付物
- 产出给追问智能体复用的报告上下文包

它不负责：

- 不处理支付和订单
- 不处理上传存储
- 不管理用户身份
- 不回答报告生成后的多轮追问

### 5.4 Report Artifact Store

报告交付物存储负责保存智能体输出。

MVP 至少保存：

- `agent_input.json`
- `knowledge_pack.json`
- `agent_output.json`
- `interpretation_artifacts.json`
- `final_report.json`
- `final_report.md`
- `report_context_package.json`
- `quality_gate.json`

### 5.5 Quality Gate

质量门负责判断报告能否进入用户可见状态。

MVP 至少检查：

- JSON 结构完整
- Markdown 非空
- Lite / Pro 字段完整
- 不包含内部标签泄漏
- 不包含开发态语言
- 不包含 placeholder 兜底句
- 不包含 forbidden input 标记
- 报告核心判断能回到中间解读交付物

典型禁止文本包括：

- `stage-`
- `transition-overload`
- `待完整 stage 证据确认`
- `需要进一步确认`
- `应由 stage`
- `回到画面证据`
- `placeholder`
- `legacy`

## 9. 与旧链路的关系

### 9.1 旧链路冻结

旧报告链路保留为：

- 回滚路径
- 对照样本
- 历史记录兼容路径

不再把旧链路作为报告质量提升主对象。

### 9.2 新链路旁路接入

正式接入前，先用离线 runner 验证。

建议新增：

```text
app/core/report_intelligence/
  __init__.py
  contracts.py
  input_collector.py
  knowledge_pack_builder.py
  mandala_reading_agent.py
  quality_gate.py
  artifact_store.py

scripts/run_mandala_reading_agent_fixture.py
```

旁路接入时使用 feature flag：

```text
AIMANDALA_REPORT_GENERATION_RUNTIME=legacy | mandala_reading_agent
```

### 9.3 旧 placeholder renderer 边界

新链路不再调用：

- `ReportPlaceholderAssembler`
- `report_pipeline_output_components.py` 中的 `_build_lite_*`
- `report_pipeline_output_components.py` 中的 `_build_pro_*`

这些旧组件只允许继续作为 legacy fallback 或历史调试入口。

## 10. 实现阶段

### Phase 0：架构收口

- 建立本架构文档
- 明确 MVP / Post-MVP 边界
- 明确旧链路冻结策略

### Phase 1：离线原型

- 新增 `report_intelligence` 模块
- 新增 contracts
- 新增 fixture runner
- 使用真实模型跑 3-5 个 fixture
- 输出完整审阅产物

### Phase 2：质量门

- 增加 forbidden language gate
- 增加 internal label leak gate
- 增加 empty / generic report gate
- 增加 evidence coverage gate

### Phase 3：旁路接入

- 在 API 层增加 runtime 选择
- 默认仍走 legacy
- 本地和灰度环境允许切到 `mandala_reading_agent`

### Phase 4：MVP 切换

- 通过 fixture 审阅
- 通过真实模型 smoke
- 通过 Lite / Pro 验收
- 默认切到 `mandala_reading_agent`

### Phase 5：Post-MVP 报告追问智能体

- 新增 `Report QA Agent`
- 使用 `Report Context Package`
- 支持 Lite / Pro 权限边界
- 支持多轮追问

## 11. 关键风险

### 11.1 单智能体上下文过大

如果知识包过大，模型容易泛化或忽略约束。MVP 必须限制知识包大小，只给任务必要规则。

### 11.2 只写 Markdown 导致追问返工

如果 MVP 只保存最终 Markdown，Post-MVP 追问智能体会缺少依据。必须保存 `Report Context Package`。

### 11.3 新旧链路混用

新链路不能再把 LLM 输出送回旧 placeholder renderer。否则会复现当前质量问题。

### 11.4 质量门过弱

如果只检查 JSON 是否能 parse，无法阻止空泛报告上线。质量门必须检查内部标签、占位句、开发态语言和证据覆盖。

## 12. Handoff 给 Engineer

Engineer 下一步应先实现离线原型，不直接接正式 API。

最小实现输入：

- 本文档
- `docs/sources/知识库构建/三圈五行流派解读方法与步骤.md`
- 现有 fixture 图片
- 现有 LLM runtime

最小实现输出：

- `report_intelligence` 模块骨架
- fixture runner
- 单个 fixture 的真实模型产物
- `agent_input.json`
- `knowledge_pack.json`
- `agent_output.json`
- `final_report.md`
- `report_context_package.json`
- `quality_gate.json`

## 13. Handoff 给 Test / QA

Test / QA 下一步应定义报告智能层的验收口径。

最小验收场景：

- Lite 报告没有内部标签泄漏
- Pro 报告不出现开发态占位句
- 报告能具体引用画面观察
- 报告能解释三圈与五行关系
- 报告能关联用户主题
- `Report Context Package` 足够支持下一阶段追问
- 真实模型失败时不会静默生成伪报告
