## 1. 背景

`/report/lite` 与 `/report/pro` 正在 Figma Make 中快速迭代。当前已经明确：

- Lite / Pro 是同一套报告体系的不同深度版本。
- 报告页要像结构化模板，不应是一整篇随意排版的长文章。
- Pro 追问要借鉴 AI 师傅 / MarkdownFlow 的段落级互动方式：默认只露出轻量「追问」按钮，点击后展开输入，提交后在当前段落下方出现回答。
- 追问内容需要和原报告正文有视觉区分；如果用户围绕同一段追问很多轮，中间追问记录需要能整体折叠。

本文件回答一个问题：后续报告结构、模块顺序、追问位置和互动样式会高频变化时，技术方案应如何支撑。

## 2. 当前判断

当前方向可以继续推进，但不能把 Figma Make 生成的页面代码直接当长期架构。

设计原型适合探索：

- 模块顺序
- Lite / Pro 的视觉差异
- 追问按钮、输入框、思考中、回答态
- 折叠区、补充解读卡、底部操作

长期实现需要收口成：

```text
final_report / report_document 结构化数据
  ↓
report template renderer
  ↓
Lite / Pro 页面与模块组件
  ↓
followup anchor + followup thread
```

`final_report_md` 可以继续保留为调试、导出、回归对照和低保真 fallback，但不应作为前端主渲染源。前端主渲染源应是结构化 `final_report`，或由后端适配出的 `report_document`。

## 3. 技术边界

### 3.1 模块边界

报告链路拆成五层：

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| 报告生成层 | 产出 Lite / Pro 的内容结构、正文、追问锚点 | 页面样式、折叠交互 |
| 报告适配层 | 把现有 `final_report` / `final_report_md` 转成 `ReportDocument` | 重新写报告内容 |
| 报告渲染层 | 根据 `module.type` 选择对应 React 组件 | 解析不稳定自然语言标题 |
| 追问状态层 | 管理模块内追问展开、输入、发送、回答、折叠 | 决定报告主结构 |
| 导出分享层 | 从同一份 `ReportDocument` 生成图片、分享页、PDF 或 Markdown | 维护另一套报告内容 |

### 3.2 数据边界

长期 canonical 数据应是 `ReportDocument`：

```ts
type ReportDocument = {
  schemaVersion: "report.document.v1";
  reportId: string;
  reportMode: "lite" | "pro";
  templateId: "mandala.report.lite.v1" | "mandala.report.pro.v1";
  templateVersion: string;
  title: string;
  generatedAt: string;
  subject: {
    theme: string;
    themeLabel: string;
    imageUrl?: string;
  };
  header: ReportHeader;
  modules: ReportModule[];
  actions: ReportAction[];
};
```

`schemaVersion` 描述数据合同版本，`templateVersion` 描述当前 UI 模板版本。两者需要分开：

- 数据合同变了，影响前后端解析和历史报告兼容。
- UI 模板变了，通常只影响展示、模块样式和交互组织。

### 3.3 模块类型

MVP 阶段先支持这些模块类型：

```ts
type ReportModule =
  | SummaryModule
  | ImpressionModule
  | InsightListModule
  | DeepReadingModule
  | ThreeCirclesModule
  | FormationReasonModule
  | PracticeSuggestionModule
  | UpgradePromptModule
  | FooterActionModule;
```

每个模块至少包含：

```ts
type BaseModule = {
  id: string;
  type: string;
  order: number;
  title: string;
  subtitle?: string;
  display?: {
    initiallyCollapsed?: boolean;
    collapsible?: boolean;
    density?: "compact" | "standard";
  };
  followup?: FollowupAnchor;
};
```

模块内正文可以继续是富文本字段，但富文本只在模块内部使用，不负责定义模块边界。

## 4. 追问架构

### 4.1 追问锚点

追问不是全局聊天入口，而是挂在报告模块或段落上的上下文动作。

```ts
type FollowupAnchor = {
  anchorId: string;
  moduleId: string;
  scope: "module" | "paragraph" | "whole_report";
  label: "追问";
  contextExcerpt: string;
  suggestedPlaceholder: "请输入你想追问的问题";
  threadId?: string;
};
```

前端发送追问时必须带：

- `reportId`
- `reportMode`
- `schemaVersion`
- `moduleId`
- `anchorId`
- `question`
- 当前模块的 `contextExcerpt`
- 必要时带 `visual_draft` / `final_report` 的引用，而不是只带整段 Markdown

这样后端才能知道用户是在围绕哪一段报告继续问。

### 4.2 追问线程

用户可能围绕同一段问多轮。追问记录不应混进原报告正文，而应作为当前模块下的 `FollowupThread` 渲染：

```ts
type FollowupThread = {
  threadId: string;
  anchorId: string;
  moduleId: string;
  turns: FollowupTurn[];
  display: {
    state: "collapsed" | "expanded" | "input" | "thinking" | "answered";
    collapseAfterTurns: number;
    summaryWhenCollapsed?: string;
  };
};
```

折叠策略：

- 默认只显示「追问」小胶囊按钮。
- 用户点击后展开一行输入。
- 提交后显示用户问题、思考中、回答卡片和继续输入框。
- 同一锚点超过 2 轮问答后，历史问答整体折叠成「已追问 3 次，展开查看」。
- 最新一轮默认展开，历史轮次默认折叠。
- 折叠区视觉上使用“补充解读 / 追问记录”样式，不使用原报告正文卡片样式。

### 4.3 视觉区分

报告正文和追问内容必须有明确区分：

| 区域 | 视觉语义 |
| --- | --- |
| 报告正文模块 | 米色内容区、结构化模块、稳定报告内容 |
| 追问按钮 | 小胶囊、靠右、低权重、图标 +「追问」 |
| 输入区 | 浅色嵌入条，36-40px 高，不像常驻聊天框 |
| 用户问题 | 小型右侧气泡，作为用户补充问题 |
| AI 回答 | 「补充解读」卡片，轻描边或左侧金色细条 |
| 历史追问折叠 | 一行摘要，不展开时不占正文阅读空间 |

## 5. Figma Make 与正式实现的关系

Figma Make 继续用于探索页面形态，但同步到正式代码时要做一次映射：

| Figma 原型元素 | 正式实现落点 |
| --- | --- |
| 报告头部 | `ReportHeader` + `ReportHeaderView` |
| Lite / Pro 标识 | `reportMode` + `templateId` |
| 结构化模块卡片 | `ReportModule` + 对应 module component |
| 段落级追问按钮 | `FollowupAnchor` + `FollowupInline` |
| 思考中 / 回答态 | `FollowupThread.display.state` |
| 折叠追问记录 | `FollowupThread.display.collapseAfterTurns` |
| 保存 / 重新上传 | `ReportAction[]` |

原则：

- 不直接把 Figma 页面拆成长期业务逻辑。
- 可以复用 Figma 里的视觉组件和 CSS 语言。
- 组件命名要回到报告模板语义，而不是停留在原型布局命名。

## 6. 迁移路径

### Phase 1：定义合同，不改主链

- 新增前端 `ReportDocument` / `ReportModule` 类型。
- 新增后端或前端 adapter，把现有 `final_report` / `final_report_md` 转成 `ReportDocument`。
- 保留现有 `final_report_md` 渲染 fallback。
- 不要求一次性改完 Lite / Pro 页面。

### Phase 2：Pro 页面先接入模板渲染

- Pro 页面使用 `ReportDocument.modules` 渲染主体模块。
- 段落级追问使用 `FollowupAnchor`。
- 追问输入、回答、折叠只作为模块内扩展区，不改变报告正文。

### Phase 3：Lite / Pro 共用 renderer

- Lite 和 Pro 共享 `ReportRenderer`。
- 差异由 `templateId`、`reportMode`、`modules` 和 `actions` 控制。
- 升级 Pro、继续追问、保存报告等操作都从结构化 action 渲染。

### Phase 4：后端直出结构化报告

- prompt 输出要求从“Markdown 主输出”调整为“结构化 JSON 主输出 + Markdown 导出”。
- 质量门同时检查 `ReportDocument` 和 Markdown fallback。
- 历史报告按 `schemaVersion` 做 adapter，不强行重写旧数据。

## 7. 风险

1. 如果继续以 Markdown heading 解析作为主渲染方案，模块边界会被文案变化打破。
2. 如果 Figma Code 直接进入正式运行时，后续会形成页面级硬编码，Lite / Pro 复用困难。
3. 如果追问没有 `moduleId` / `anchorId`，后端只能拿整份报告回答，无法稳定做到“围绕这一段继续问”。
4. 如果追问记录混在报告正文里，用户会分不清哪些是原始报告，哪些是后续互动生成内容。
5. 如果不做 `schemaVersion`，历史报告会在模板升级后出现展示兼容风险。

## 8. 实现前提

进入实现前需要确认：

- 最新 Figma Make 代码已经同步到 `projects/aimandala/FigmaCode`，或明确不以 FigmaCode 为本轮实现来源。
- Lite / Pro 当前上线口径已经更新，尤其是 Pro 是否对外开放、是否收费、是否允许追问。
- 后端 `final_report` 当前真实结构样本至少提供 Lite / Pro 各 1 份。
- 追问 API 是否能接收 `moduleId` / `anchorId`；如果不能，先加兼容字段。

## 9. Handoff

### 给 Engineer

优先实现：

1. `ReportDocument` 类型与 adapter。
2. `ReportRenderer`：`module.type -> component` 的映射。
3. `FollowupInline`：段落级追问按钮、输入、思考中、回答态。
4. `FollowupThreadCollapse`：超过 2 轮后的折叠摘要。

暂不实现：

- 完整 MarkdownFlow 语法解析器。
- 通用课程互动系统。
- 全局常驻聊天窗口。
- 历史报告批量迁移。

### 给 Test / QA

验证重点：

1. Lite / Pro 都能从同一份 `ReportDocument` 模型渲染。
2. 模块顺序变化不需要改页面主逻辑。
3. 追问按钮点击前不显示输入框。
4. 提交问题后，回答显示在当前模块下方，而不是报告底部。
5. 同一锚点多轮追问后，历史问答可以折叠。
6. 原报告正文与追问回答在视觉上能一眼区分。
7. `final_report_md` fallback 仍可用于旧数据和调试。

## 10. 当前结论

支持高频迭代的关键，不是继续加页面状态，而是把报告当成版本化结构数据来渲染。

当前建议是：

- `final_report` / `ReportDocument` 做主数据。
- `final_report_md` 做 fallback、导出和回归证据。
- Lite / Pro 共享 renderer。
- 追问作为模块内锚点和线程，不混入报告正文。
- 折叠逻辑属于追问线程层，不属于报告正文层。
