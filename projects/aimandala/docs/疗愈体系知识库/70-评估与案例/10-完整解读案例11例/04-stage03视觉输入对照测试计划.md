# stage-03 视觉输入对照测试计划

> 状态：draft
> 适用范围：11 个完整解读案例的 stage-03 视觉识别评估
> 目标：判断视觉模型在“三圈边界识别”上更适合使用半径参数、三圈标记图，还是组合输入。

## 当前输入方式

当前 `run_case_visual_stage03.py` 会把用户原画作和三圈标记图一起传给视觉模型。

脚本会读取每个案例的两张图：

- `case-xxx-mandala.*`：用户原画作，作为第一张图传给视觉模型。
- `case-xxx-mandala-3q.*`：疗愈师三圈标记图，作为第二张图传给视觉模型，只用于辅助确认三圈边界。

当前传给模型的圈层信息是归一化半径：

```json
{
  "inner_radius": 35,
  "middle_radius": 65,
  "radius_unit": "normalized_percent",
  "source": "manual_case_review_default"
}
```

因此当前识别效果实际来自：

- 原画作视觉输入
- 三圈标记图的边界辅助
- 文本中的内圈、中圈半径提示
- prompt 对圈层观察方式的要求

## 待测试问题

需要验证的问题不是“哪种方式理论上更好”，而是哪种方式在真实案例里错误更少。

重点观察 5 类错误：

- 圈层归属错误：把内圈元素放到中圈，或把中圈元素放到外圈。
- 标记线污染：把疗愈师蓝色/红色/其他标记线当成画作颜色。
- 留白漏判：漏掉切分、包围或隔开元素的留白。
- 形状抽象错误：把块状、点状、花瓣、三角、矩形、波纹等识别错。
- 相邻关系缺失：没有说明元素之间是否接触、被留白隔开、被包围或形成层级。

## 对照组设计

### A 组：原画作 + 半径参数

输入：

- 只传用户原画作。
- 在 prompt 中提供内圈、中圈半径。

优点：

- 不会受到疗愈师标记线颜色污染。
- 更接近真实产品中的用户上传场景。

风险：

- 模型需要自己把半径文字提示映射到画面区域，圈层边界可能不稳定。
- 对复杂画面容易把跨边界元素归错圈。

### B 组：三圈标记图

输入：

- 传带三圈标记线的图片。
- prompt 明确说明标记线只用于边界，不属于画作。

优点：

- 圈层边界更直观，模型更容易知道内圈、中圈、外圈范围。

风险：

- 视觉模型可能仍被标记线颜色影响，把标记线当作画作元素。
- 如果标记线覆盖了画作细节，会影响颜色、形状和留白识别。

### C 组：原画作 + 标记图衍生边界数据

输入：

- 仍只传用户原画作。
- 由人工或程序从标记图/前端标圈结果生成更精确的边界数据。

优点：

- 保留原画作的干净视觉输入。
- 比固定 `35/65` 半径更贴近具体案例。

风险：

- 需要先建立边界数据生成方式。
- 如果边界数据不够明确，模型仍可能理解偏差。

## 初步判断

更稳的产品方向应优先测试 A 组和 C 组。

B 组可以作为评估对照，但不宜直接作为正式运行方案。原因是用户已经多次指出模型会受到三圈标记线颜色影响。视觉模型对“这条线只是辅助线，不要识别为画作内容”的遵守能力并不稳定。

如果 C 组能做到边界数据足够清楚，它最适合正式产品：

- 用户仍上传原画作。
- 前端手动确认三圈边界。
- 后端把边界作为结构化数据传入 stage-03。
- 视觉模型只看干净原图，并按边界数据分层观察。

## 验收口径

每个案例按以下项目人工判定 pass/fail：

- 三圈元素归属是否基本正确。
- 是否排除模板黑线。
- 是否排除疗愈师标记线。
- 是否记录圈内重要留白。
- 留白是否写清楚切分、包围、隔开关系。
- 关键颜色是否正确，例如红色渐变不能写成粉色，浅蓝圆形不能写成白色留白。
- 关键形状是否正确，例如方块、三角、花瓣、点状、矩形、波纹不能混淆。
- 相邻关系是否足够支持后续五行生克判断。

## 下一步

先用新 prompt 跑 B 组，复核 case-001 到 case-011 的错误类型。

如果 B 组仍频繁出现标记线污染，再回到 A 组或实现 C 组对照。优先实现 C 组，因为它更接近正式产品形态。
