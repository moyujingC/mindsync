# 疗愈体系知识库系统评估与优化

> 状态：current
> 日期：2026-05-28
> 方法：4-agent 并行评估 + 主控整合
> owner：CEO / Knowledge Base
> source_of_truth：70-评估与案例/06-agent集群系统评估与优化-2026-05-28.md

本文评估 `projects/research-center/kb` 上游研究母库到 `projects/aimandala/docs/疗愈体系知识库/` 下游产品知识库的完整链路。

## 1. 总体结论

系统骨架已经成立，当前等级为 `B+`：

- 上游 `sources -> atoms -> wiki` 已形成研究母库。
- 下游 `05-参考来源索引 -> 20-疗愈体系 -> 30-应用适配 -> 60-运行时知识包` 已形成产品知识链路。
- 最大问题不再是“没有目录”，而是“哪些内容可运行、可对外、可追溯”的状态口径不一致。

当前最应先修的是运行时质量门：

1. 主题可调用状态必须统一。
2. 来源状态必须从文档级推进到条目级。
3. 高风险内容必须有硬路由。
4. 报告段落需要能追到画面信号、议题条款和来源。

## 2. 链路现状

```text
research-center/kb/sources/healing
  -> research-center/kb/atoms/healing
  -> research-center/kb/wiki/healing
  -> 疗愈体系知识库/05-参考来源索引
  -> 疗愈体系知识库/20-疗愈体系
  -> 疗愈体系知识库/30-应用适配/10-aimandala
  -> 疗愈体系知识库/60-运行时知识包
```

上游研究母库的强项：

- 来源目录普遍有来源登记、章节索引、来源评估、跨来源对照。
- atoms 数量已覆盖 ACT、CBT、创伤、家庭系统、财富、关系、身体、内在小孩等主题。
- 高风险边界意识较强，例如创伤、医学、灵性因果、财务承诺都有禁用提醒。

下游产品知识库的强项：

- 能区分来源索引、议题层、流派层、疗愈方案层、应用适配和运行时包。
- 财富关系主题链路较完整，亲密关系链路已具备内部测试基础。
- 三库交叉索引已经开始约束疗愈建议，避免直接从信号表复制建议。

## 3. 主要断点

| 断点 | 影响 | 处理方向 |
|------|------|----------|
| 上游清单和真实处理状态不一致 | Agent 会误判来源成熟度 | 建来源状态同步表 |
| 下游主题可调用状态不一致 | 模板存在会被误认为可对外 | 运行时包设主题状态分级 |
| 文档级 review 多，条目级 review 少 | 无法审计具体报告句子 | 增加条目级质量门字段 |
| 三库建议缺逐条来源状态 | 疗愈建议可能越界 | 先补会进入报告的建议 |
| 示例材料含待补图/待审核内容 | 未审核示范可能进入运行时 | 默认排除未审核示范 |
| 运行时策略口径混杂 | Markdown 直读和已弃用的结构化方案被混用 | 当前统一为受控 Markdown 包 |

## 4. 运行时状态分级

当前统一采用：

| 状态 | 含义 | 默认动作 |
|------|------|----------|
| `public_candidate` | 可进入对外候选报告 | 可生成 Lite，需抽检 |
| `internal_test` | 内部测试可用 | 不对外开放 |
| `framework_only` | 只作背景线索 | 不生成独立主题报告 |
| `blocked_draft` | 阻断草稿 | 必须拦截 |

当前建议：

- 财富：`public_candidate`
- 亲密关系、父亲关系、母亲关系、亲子关系、人际关系：`internal_test`
- 个人成长与自我价值：`framework_only`
- 事业 / 发展、健康 / 身体：`blocked_draft`

## 5. 质量门

进入运行时最低字段：

| 字段 | 说明 |
|------|------|
| `entry_id` | 条目 ID |
| `entry_type` | 画面信号、议题条款、映射规则、报告段落、练习、来源引用 |
| `source_refs` | 上游 source、atom、wiki、案例或下游来源索引路径 |
| `source_status` | `ai_draft`、`source_supported_draft`、`case_verified`、`reviewed` |
| `review_status` | `draft`、`review_pending`、`approved_for_internal`、`approved_for_public` |
| `risk_level` | `low`、`medium`、`high` |
| `runtime_permission` | `allow`、`allow_with_warning`、`block` |
| `fallback_action` | 被拦截后的追问、降级或外部支持动作 |

进入正式报告还需要：

- `matched_visual_signals`
- `matched_issue_clauses`
- `emergent_topics`
- `confidence_level`
- `blocked_reasons`
- 段落级 `trace`

## 6. 风险路由

| 风险类型 | 默认动作 |
|----------|----------|
| 自杀、自伤、活不下去 | 停止报告生成，提示外部专业支持 |
| 严重创伤具体事件 | 停止深度解读，只给稳定化和外部支持 |
| 医疗症状、疾病、孕期、癫痫等 | 不做医学判断，建议医疗专业支持 |
| 债务危机、破产、严重财务风险 | 不给财务承诺、投资建议或结果保证 |
| 关系暴力、控制、现实安全威胁 | 不做关系修复承诺，优先安全支持 |

风险路由优先于主题路由和 Lite / Pro 分流。

## 7. P0 / P1 / P2

### P0

1. 统一运行时策略为受控 Markdown 包，删除已弃用的运行时口径。
2. 在运行时包中维护主题可调用状态表。
3. 修正 Lite / Pro 字段边界：`user_segment` 是用户类型，`report_version` 是报告版本。
4. 建立条目级质量门字段，先覆盖运行时会输出的内容。
5. 建立高风险路由表，阻断诊断、医疗、财务承诺、创伤暴露和现实安全风险。

### P1

1. 建上游到下游来源状态同步表，字段包含来源目录、atoms 数量、wiki、review 状态、可产品化等级、禁用场景。
2. 为财富关系主题建第一版 runtime registry（运行时注册表），连接 `visual_signal_id -> issue_clause_id -> report_block -> source_status`。
3. 三库逐条补来源状态，优先补会进入报告的建议。
4. 议题本体补 `atom_id/source_ref`，优先健康身体、人际关系、事业发展。
5. 建案例审核统一表：案例编号、画面特征、解读结论、人工审核状态。

### P2

1. 做只读检查脚本：链接完整性、条款 ID、一致性、来源状态、Lite / Pro 字段混用、示范可用性。
2. 清理 `.DS_Store` 等非知识文件。
3. 对应用模板编号做长期命名规范，主题增多后改为目录化结构。

- 更新 `60-运行时知识包/10-aimandala-解读报告生成最小包.md`：增加主题状态表、必填中间字段、质量门、风险路由、示范材料过滤和 Lite / Pro 分流规则。
- 更新 `30-应用适配/10-aimandala/03-解读报告生成最小规则.md`：修正 `user_segment` 与 `report_version` 混用。

## 9. Readiness 判断

是否 ready 进入稳定运行时：否。

是否 ready 进入内部测试：有条件通过。

条件：

- 只开放财富关系主题作为对外候选。
- 其他主题只做内部测试或背景线索。
- 报告生成必须带质量门字段和段落级 trace。
- 高风险输入必须先走风险路由。
