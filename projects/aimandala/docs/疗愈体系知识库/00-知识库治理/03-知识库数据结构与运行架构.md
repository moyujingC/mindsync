本文定义疗愈体系知识库的数据结构、材料组织方式、运行时读取方式和质量门。

## 1. 应用场景

疗愈体系知识库至少要支撑三类当前能力：

1. 生成解读报告。
2. 回答用户围绕解读报告提出的追问。
3. 生成定制化疗愈建议。

后续还可能增加更多应用：

4. AI 在分析画面后，先向用户提出补充问题，再结合用户回答生成更精准的解读报告。
5. 基于某个议题生成课程、训练营、陪伴方案或练习手册。
6. 基于疗愈路径生成内容选题、社群引导材料或衍生产品素材。

因此，疗愈体系知识库不能只做成一组给人看的 Markdown 文档。它需要同时服务人工维护和机器运行。

## 2. 总体分层

疗愈体系知识库当前分成三层：

```text
source index layer     来源索引层
llm wiki layer         自然语言知识层
runtime layer          当前产品运行时读取的受控 Markdown 包
```

### 2.1 Source Index Layer

`source index layer` 是来源索引层，记录研究母库、专家手册、案例源、课程材料和外部资料在本知识库中的引用关系。

这里的重点是“可追溯”，不是直接给产品调用，也不是重复保存来源正文。来源正文优先维护在 `projects/research-center/kb` 或已迁入的来源文件中。

### 2.2 LLM Wiki Layer

`LLM wiki layer` 可以理解为“给人和大模型共同阅读的自然语言知识库”。

它接近 Karpathy 提到的 `LLM Wiki` 思路：把来源材料按自己的框架整理成清晰、稳定、可阅读的 Markdown 文档，让 AI 协作时有一个高质量的自然语言上下文。

这里存放：

- 议题体系说明。
- 议题体系说明。
- 流派知识整理。
- 疗愈方案材料。
- 应用适配规范。

这一层的作用是：

- 给人维护和审核。
- 给 AI 协作时读取和理解。
- 承接专家经验、案例表达和理论框架。
- 为后续运行时包提供稳定来源。

但它不应直接等同于最终运行时。只有经过运行时包列入依赖、补齐状态字段并通过质量门的内容，才允许进入报告生成链路。


### 2.4 Runtime Layer

`runtime layer` 是运行时知识包。

它面向产品能力，包括：

- 生成报告时按主题和画面信号取知识。
- 用户追问时检索相关条款。
- 生成疗愈方案时取对应建议。
- 记录每段生成内容引用了哪些知识条款。

当前运行时直接读取经过收束的 Markdown 入口。运行时 Markdown 必须满足：

- 依赖文件明确列出，不能让 Agent 自由泛读整个知识库。
- 每个可输出条目至少能回到来源索引、议题条款、画面信号或三库交叉索引。
- `ai_draft`、`source_needed`、未审核案例和三库交叉索引中的 ❌ 项不得进入对外报告正文。
- 高风险主题先走风险路由，再决定是否继续生成。

## 3. 核心知识对象

本知识库的基本单位不应是“文件”，而应是“知识单元”。

建议至少包含以下对象类型：

- `domain`：议题域，例如财富、亲密关系、事业、健康。
- `issue_clause`：议题条款，例如配得感不足、情绪型漏财、求认可式赚钱。
- `visual_signal`：画面信号，例如外圈红色多、土不成片、金克木。
- `mapping_rule`：画面信号到议题条款的映射规则。
- `report_block`：报告段落素材或生成指引。
- `followup_answer`：追问回答素材。
- `healing_intervention`：疗愈建议，例如蓝色清理、腹式呼吸、感恩日记。
- `course_block`：课程、训练营、练习手册或陪伴方案的内容素材。
- `source_ref`：来源引用。

## 5. 材料组织原则

本知识库的组织逻辑不是“把所有材料堆进一个 wiki”，而是按知识生产流程组织：

```text
研究母库 / 来源索引 / 培训材料 / 案例源
        ↓
LLM Wiki 自然语言知识层
        ↓
20-疗愈体系 / 10-议题层
        ↓
20-疗愈体系 / 30-疗愈方案层
        ↑
20-疗愈体系 / 20-流派层 / 曼陀罗
        ↓
30-应用适配 / 报告 / 追问 / 课程 / 交互生成规范
        ↓
runtime Markdown pack
```

关键原则：

- 议题层是语义中心，不是画面映射。
- 先建设议题本身，再做画面映射。
- 画面信息不能直接等同于最终结论。
- 画面信息应先变成 `visual_signal`，再映射到 `issue_clause`。

## 6. 运行时读取方式

当前阶段使用受控 Markdown 运行时包：

```text
受控 Markdown 包 + 映射规则 + 质量门 + LLM 生成
```

原因是本知识库的推理链路有结构：

```text
画面特征 → 画面信号 → 议题条款 → 报告表达 → 疗愈建议
```

普通 wiki 式读取容易把上下文找出来，但不保证映射关系正确。因此当前用运行时包约束读取顺序和可输出范围。

## 7. Markdown 切块原则

本知识库给 Agent 读取时需要按语义切块，但不能按普通字数切块。

不推荐：

- 每 500 字切一段。
- 每 1000 token 切一段。
- 机械按 Markdown 标题切。

推荐按知识单元切块：

- 一个议题条款一个 chunk。
- 一个画面信号一个 chunk。
- 一个五行关系一个 chunk。
- 一个疗愈建议一个 chunk。
- 一个案例中的“一圈解读”或“调整方案”一个 chunk。

每个可运行切块都要能回到来源路径、适用场景、风险边界和可输出位置。

长条款内部可以继续拆成子 chunk：

- `explanation`：解释。
- `evidence`：依据。
- `report_language`：报告表达。
- `healing_direction`：疗愈方向。
- `case_excerpt`：案例片段。

## 8. 检索策略

不同场景应使用不同检索策略。

### 8.1 生成解读报告

输入可能包括：

- 用户主题。
- 画面观察结果。
- 三圈信息。
- 颜色、形状、五行生克信号。

检索顺序建议：

1. 按主题过滤 `domain`。
2. 按画面信号找 `visual_signal`。
3. 通过 `mapping_rule` 找相关 `issue_clause`。
4. 取 `report_block` 和 `healing_intervention`。
5. 生成报告。

### 8.2 回答用户追问

输入包括：

- 用户问题。
- 原报告中的相关段落。
- 当前会话上下文。

检索顺序建议：

1. 找到原报告相关判断。
2. 检索对应议题条款。
3. 检索对应画面信号和解释依据。
4. 生成回答，并保持和原报告一致。

### 8.3 生成疗愈方案

输入包括：

- 用户当前议题。
- 已识别卡点。
- 用户可接受的练习方式。
- 风险和禁忌。

检索顺序建议：

1. 取对应 `issue_clause`。
2. 取对应 `healing_intervention`。
3. 按强度、周期、用户状态筛选。
4. 生成可执行方案。

### 8.4 AI 追问用户

如果画面信息不足或存在多个可能解释，AI 可以先向用户提问。

提问应服务于区分议题条款，例如：

- 这个问题更像财富压力，还是关系压力？
- 你最近花钱更多是因为开心奖励自己，还是因为情绪低落想安抚自己？
- 你想赚钱更多是为了自由、创造，还是为了逃离某种关系或环境？

用户回答后，再选择更准确的 `issue_clause` 和 `healing_intervention`。

## 9. 版本迭代

本知识库不需要一次性完成。

建议按 pack 版本迭代：

```text
1.0.0-alpha.1  财富关系议题 + 基础画面映射 + 报告组织规范
1.0.0-alpha.2  个人成长 / 自我价值议题
1.0.0-alpha.3  亲密关系议题
1.0.0-beta.1   疗愈方案库增强 + 追问问答增强
1.0.0          第一版稳定知识包
```

每次版本更新应记录：

- 新增了哪些知识单元。
- 修改了哪些知识单元。

### 10.2 后续增强

后续可以增加：

- Rule engine：处理画面信号到议题条款的权重。
- Eval set：用案例测试报告质量。
- Trace：记录每段生成内容引用了哪些知识单元。
- Pack diff：比较不同版本运行时 Markdown 包的变化。

## 12. 当前结论

本知识库应采用：

```text
Markdown 知识文档
  → 受控 Markdown 运行时包
  → 映射规则（翻译层）
  → 质量门与风险路由
  → LLM 生成
```

> **变更（2026-05-28）**：当前阶段采用受控 Markdown 运行时包；已弃用的运行时路线不再作为后续方向写入本架构。

它不是普通 wiki，也不是只靠 prompt 的知识库。

它应是一个可版本化、可检索、可追溯、可运行的知识系统。

## 13. 当前运行时质量门字段

进入运行时包的内容，至少需要能回答这些问题：

| 字段 | 说明 |
|------|------|
| `entry_id` | 条目 ID，可先用人工命名，不强制机器生成 |
| `entry_type` | `visual_signal`、`issue_clause`、`mapping_rule`、`report_block`、`practice`、`source_ref` |
| `source_refs` | 上游 source、atom、wiki、案例或下游来源索引路径 |
| `source_status` | 来源验证状态，见本节定义的四级体系 |
| `review_status` | `draft`、`review_pending`、`approved_for_internal`、`approved_for_public` |
| `risk_level` | `low`、`medium`、`high` |
| `runtime_permission` | `allow`、`allow_with_warning`、`block` |
| `report_sections` | 可进入哪些报告段落 |
| `fallback_action` | 被拦截时如何处理，例如追问、降级、转外部支持 |

### 13.1 来源验证状态（source_status）四级体系

> **变更（2026-05-28）**：统一来源分级体系，补充晋级条件和最终状态。

| 状态 | 含义 | 晋级条件 |
|------|------|----------|
| `ai_draft` | 内容由 AI 生成，尚未完成来源验证 | 无需晋级前置条件 |
| `source_supported_draft` | 已有来源材料支撑初版表达，但仍处于草稿 | 必须补充来源路径、对应章节或条款说明，并说明该来源支持的是概念、机制、表达还是疗愈方向 |
| `case_verified` | 已通过案例验证 | 必须有至少 1 个来源索引文件记录，且该来源与条目内容语义对应 |
| `reviewed` | 已完成人工审核 | 必须有明确 reviewer 指定，且审核意见已记录在来源索引或条目文件 metadata 中 |
| `runtime_ready` | 运行时就绪 | 必须在 `reviewed` 基础上，补充：① 可用/不可用场景；② 安全边界；③ 可映射条款（画面信号）或对应议题条款（议题条款） |

**晋级路径**：

```
ai_draft
  ↓ 补充来源路径 + 对应章节 + 来源支撑类型
source_supported_draft
  ↓ 来源索引记录 + 案例验证
case_verified
  ↓ 明确 reviewer + 审核意见记录
reviewed
  ↓ 补充场景边界 + 安全边界 + 可映射条款/对应议题条款
→ runtime_ready
```

**使用规则**：
- `ai_draft` 状态的内容只能作为内部候选，不得进入对外报告正文。
- `source_supported_draft` 状态的内容可进入内部测试版本报告，但必须保留"来源待验证"标注。
- `case_verified` 状态的内容可用于报告生成。
- `reviewed` 状态的内容可进入正式用户输出。
- `runtime_ready` 状态的内容满足运行时包所有字段要求，可安全进入产品链路。

### 13.2 运行时质量门最小规则

- `runtime_permission = block` 的内容不得进入用户可见报告。
- `risk_level = high` 的内容必须先经过安全边界判断。
- `source_status = ai_draft` 的内容只能作为内部候选，除非所在运行时包明确声明允许内部测试。
- 疗愈建议必须能回到三库交叉索引，且 ❌ 项不得直接输出。

### 13.3 review_status 与 source_status 的关联

| review_status | source_status 最低要求 | 说明 |
|---------------|----------------------|------|
| `draft` | `ai_draft` | 初始状态 |
| `review_pending` | `source_supported_draft` | 进入 review 前必须至少达到来源支撑草稿 |
| `approved_for_internal` | `case_verified` | 内部可用前必须至少通过案例验证 |
| `approved_for_public` | `reviewed` | 对外发布必须完成人工审核 |

> 注：`runtime_ready` 不是 review_status 的晋级，而是 source_status 的最终质量门。review_status 达到 `approved_for_public` 后，如果需要进入运行时包，仍需补充 runtime 专用字段达到 `runtime_ready`。

## 14. 内容进入下游的最低审核标准

> **新增（2026-05-28）**：本节定义内容从上游研究母库进入下游产品化知识库的最低标准。

### 14.1 上游与下游的分工

| 位置 | 定位 | 内容成熟度要求 |
|------|------|--------------|
| `research-center/kb/sources/healing` | 来源本体 | 原始资料保存，允许不同成熟度并存 |
| `research-center/kb/atoms/healing` | 可检查判断 | 最小观点、机制、边界、练习和风险提示，可来源于 AI 辅助整理 |
| `research-center/kb/wiki/healing` | 结构化理解 | 跨来源整理，允许研究态和待验证观点 |
| `疗愈体系知识库/20-疗愈体系` | 产品化知识 | 必须满足本节的最低审核标准 |

### 14.2 进入下游的最低标准

进入下游产品化知识库（`20-疗愈体系`）的内容，默认需要满足以下所有条件：

| 要求 | 说明 | 对应字段 |
|------|------|----------|
| **来源可追溯** | 内容必须有明确的上游来源路径（source、atom、wiki 或下游来源索引文件） | `source_refs` |
| **来源状态可评估** | 内容必须标注当前来源状态，且不得为 `ai_draft`（直接来源为 AI 的内容不允许进入下游） | `source_status` |
| **有边界说明** | 内容必须说明适用场景和不适用场景 | `scope` / `safe_boundary` |
| **有风险提示** | 涉及自杀/自伤、严重创伤、医疗、财务、关系暴力等高风险内容必须标注风险类型和默认动作 | `risk_level`、`runtime_permission` |
| **不包含原始来源正文** | 下游只引用来源位置，不复制大段来源正文 | - |

### 14.3 来源状态与进入下游的对应关系

| `source_status` | 能否进入下游 | 说明 |
|----------------|------------|------|
| `ai_draft` | ❌ 不得进入 | 直接由 AI 生成，无来源验证的内容禁止进入下游 |
| `source_supported_draft` | ✅ 可进入 | 有来源材料支撑即可进入下游，但报告生成时需标注来源待验证 |
| `case_verified` | ✅ 可进入 | 已有案例验证的内容优先进入下游 |
| `reviewed` | ✅ 可进入 | 人工审核通过的内容可进入正式产品链路 |
| `runtime_ready` | ✅ 可进入 | 满足所有运行时字段要求，可安全进入产品链路 |

### 14.4 各层级的来源要求

| 下游层级 | 最低来源状态要求 | 说明 |
|---------|----------------|------|
| `10-议题层/议题本体` | `source_supported_draft` | 每个议题条款必须有来源支撑 |
| `10-议题层/浮现机制` | `source_supported_draft` | 浮现机制必须有来源或案例支撑 |
| `20-流派层/曼陀罗` | `source_supported_draft` | 信号和解读规则必须有手册来源或案例验证 |
| `30-疗愈方案层` | `source_supported_draft` | 疗愈建议必须有来源支撑或案例验证 |
| `60-运行时知识包` | `reviewed`（或 `runtime_ready`） | 运行时包必须通过人工审核才能打包 |

### 14.5 审核标准速查

进入下游时，逐项检查：

- [ ] 是否有 `source_refs`（来源路径）
- [ ] `source_status` 是否 ≥ `source_supported_draft`
- [ ] 是否有明确的边界说明（适用/不适用）
- [ ] 是否涉及高风险内容，如有则是否已标注 `risk_level` 和 `runtime_permission`
- [ ] 是否复制了大段来源正文，如有则需要删除并改为引用

全部通过后方可进入下游知识库。

## 15. 上游来源更新的下游影响传播机制

> **新增（2026-05-28）**：本节定义上游来源更新时，如何追踪和传播影响到下游知识库。

### 15.1 追踪原则

上游来源（`research-center/kb/sources/healing`）更新时，不自动触发下游知识库的同步更新。但应建立影响追踪机制，确保下游知识库在必要时能够回溯和更新。

### 15.2 影响传播链路

```
上游来源更新
  → 标记更新时间
  → 查找受影响的下游来源索引文件（05-参考来源索引/）
  → 查找引用该来源的议题本体、流派知识或疗愈方案
  → 评估是否需要同步更新下游内容
  → 如需更新，按以下优先级处理：
      1. 议题层条款（影响报告生成）
      2. 画面信号映射（影响翻译链路）
      3. 疗愈方案（影响方案生成）
```

### 15.3 来源索引的影响追踪

每个来源索引文件（`05-参考来源索引/`）应记录：

| 字段 | 说明 |
|------|------|
| 上游来源路径 | `research-center/kb/sources/healing/` 中的对应来源 |
| 入库日期 | 该来源首次入库的日期 |
| 最后同步日期 | 该来源与下游内容最后一次同步的日期 |
| 受影响文件 | 引用该来源的下游文件列表 |
| 同步状态 | `synced`、`pending_review`、`needs_update`、`stale` |

来源索引文件格式建议：

```yaml
source_index:
  upstream_path: projects/research-center/kb/sources/healing/对财富说是/
  upstream_last_updated: 2026-05-20
  last_synced: 2026-05-25
  sync_status: pending_review  # 来源有新章节未同步
  affected_files:
    - 20-疗愈体系/10-议题层/10-议题本体/30-现实/01-财富关系.md
    - 20-疗愈体系/10-议题层/20-浮现机制/02-安全感与匮乏感.md
  notes: 第8-10章尚未回填至议题本体
```

### 15.4 使用规则

1. 上游来源更新后，维护者在来源索引文件中更新 `upstream_last_updated` 和 `sync_status`。
2. `sync_status = pending_review` 或 `needs_update` 时，应在 30 天内完成下游内容同步评估。
3. 如果来源更新导致下游条款内容发生实质变化（如条款被删除、核心观点改变），需要更新对应条款的 `source_refs` 中的章节引用，并提升 `source_status`。
4. 如果来源更新导致新的疗愈方向或风险提示，需要同步更新议题本体和风险路由表。

### 15.5 定期检查机制

建议每季度做一次来源同步检查：

- 检查上游来源是否有新增章节或更新版本
- 核对来源索引的 `sync_status` 字段
- 优先处理 `stale` 状态的来源索引

## 14. 当前风险路由

| 风险类型 | 默认动作 | 输出边界 |
|----------|----------|----------|
| 自杀、自伤、活不下去 | 停止报告生成，提示外部专业支持 | 不输出画面分析结论 |
| 严重创伤具体事件 | 停止深度解读，转稳定化与外部支持 | 不做成因解释或暴露式练习 |
| 医疗症状、疾病、孕期、癫痫等 | 不做医学判断，建议医疗专业支持 | 只保留低风险观察和身体觉察 |
| 债务危机、破产、严重财务风险 | 不给财务承诺或投资建议 | 只做情绪承接和下一步求助建议 |
| 关系暴力、控制、现实安全威胁 | 不做关系修复承诺 | 优先安全计划和外部支持 |

风险路由优先于所有报告生成规则。
