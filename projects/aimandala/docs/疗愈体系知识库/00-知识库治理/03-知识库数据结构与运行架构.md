本文定义疗愈体系知识库的数据结构、材料组织方式、运行时读取方式和质量门。

## 1. 应用场景

疗愈体系知识库至少要支撑三类当前能力：

1. 生成解读报告。
2. 回答用户围绕解读报告提出的追问。
3. 生成定制化疗愈建议。

后续还可能增加更多应用：

4. AI 在分析画面后，先向用户提出补充问题，再结合用户回答生成更精准的解读报告。
5. 基于某个议题生成课程、训练营、陪伴方案或练习手册。
6. 基于疗愈路径生成内容选题、社群引导材料或衍生产品素材。

因此，疗愈体系知识库不能只做成一组给人看的 Markdown 文档。它需要同时服务人工维护和机器运行。

## 2. 总体分层

疗愈体系知识库当前分成三层：

```text
source index layer     来源索引层
llm wiki layer         自然语言知识层
runtime layer          当前产品运行时读取的受控 Markdown 包
```

### 2.1 Source Index Layer

`source index layer` 是来源索引层，记录研究母库、专家手册、案例源、课程材料和外部资料在本知识库中的引用关系。

这里的重点是“可追溯”，不是直接给产品调用，也不是重复保存来源正文。来源正文优先维护在 `projects/research-center/kb` 或已迁入的来源文件中。

### 2.2 LLM Wiki Layer

`LLM wiki layer` 可以理解为“给人和大模型共同阅读的自然语言知识库”。

它接近 Karpathy 提到的 `LLM Wiki` 思路：把来源材料按自己的框架整理成清晰、稳定、可阅读的 Markdown 文档，让 AI 协作时有一个高质量的自然语言上下文。

这里存放：

- 议题体系说明。
- 议题体系说明。
- 流派知识整理。
- 疗愈方案材料。
- 应用适配规范。

这一层的作用是：

- 给人维护和审核。
- 给 AI 协作时读取和理解。
- 承接专家经验、案例表达和理论框架。
- 为后续运行时包提供稳定来源。

但它不应直接等同于最终运行时。只有经过运行时包列入依赖、补齐状态字段并通过质量门的内容，才允许进入报告生成链路。


### 2.4 Runtime Layer

`runtime layer` 是运行时知识包。

它面向产品能力，包括：

- 生成报告时按主题和画面信号取知识。
- 用户追问时检索相关条款。
- 生成疗愈方案时取对应建议。
- 记录每段生成内容引用了哪些知识条款。

当前运行时直接读取经过收束的 Markdown 入口。运行时 Markdown 必须满足：

- 依赖文件明确列出，不能让 Agent 自由泛读整个知识库。
- 每个可输出条目至少能回到来源索引、议题条款、画面信号或三库交叉索引。
- `ai_draft`、`source_needed`、未审核案例和三库交叉索引中的 ❌ 项不得进入对外报告正文。
- 高风险主题先走风险路由，再决定是否继续生成。

## 3. 核心知识对象

本知识库的基本单位不应是“文件”，而应是“知识单元”。

建议至少包含以下对象类型：

- `domain`：议题域，例如财富、亲密关系、事业、健康。
- `issue_clause`：议题条款，例如配得感不足、情绪型漏财、求认可式赚钱。
- `visual_signal`：画面信号，例如外圈红色多、土不成片、金克木。
- `mapping_rule`：画面信号到议题条款的映射规则。
- `report_block`：报告段落素材或生成指引。
- `followup_answer`：追问回答素材。
- `healing_intervention`：疗愈建议，例如蓝色清理、腹式呼吸、感恩日记。
- `course_block`：课程、训练营、练习手册或陪伴方案的内容素材。
- `source_ref`：来源引用。

## 5. 材料组织原则

本知识库的组织逻辑不是“把所有材料堆进一个 wiki”，而是按知识生产流程组织：

```text
研究母库 / 来源索引 / 培训材料 / 案例源
        ↓
LLM Wiki 自然语言知识层
        ↓
20-疗愈体系 / 10-议题层
        ↓
20-疗愈体系 / 30-疗愈方案层
        ↑
20-疗愈体系 / 20-流派层 / 曼陀罗
        ↓
30-应用适配 / 报告 / 追问 / 课程 / 交互生成规范
        ↓
runtime Markdown pack
```

关键原则：

- 议题层是语义中心，不是画面映射。
- 先建设议题本身，再做画面映射。
- 画面信息不能直接等同于最终结论。
- 画面信息应先变成 `visual_signal`，再映射到 `issue_clause`。

## 6. 运行时读取方式

当前阶段使用受控 Markdown 运行时包：

```text
受控 Markdown 包 + 映射规则 + 质量门 + LLM 生成
```

原因是本知识库的推理链路有结构：

```text
画面特征 → 画面信号 → 议题条款 → 报告表达 → 疗愈建议
```

普通 wiki 式读取容易把上下文找出来，但不保证映射关系正确。因此当前用运行时包约束读取顺序和可输出范围。

## 7. Markdown 切块原则

本知识库给 Agent 读取时需要按语义切块，但不能按普通字数切块。

不推荐：

- 每 500 字切一段。
- 每 1000 token 切一段。
- 机械按 Markdown 标题切。

推荐按知识单元切块：

- 一个议题条款一个 chunk。
- 一个画面信号一个 chunk。
- 一个五行关系一个 chunk。
- 一个疗愈建议一个 chunk。
- 一个案例中的“一圈解读”或“调整方案”一个 chunk。

每个可运行切块都要能回到来源路径、适用场景、风险边界和可输出位置。

长条款内部可以继续拆成子 chunk：

- `explanation`：解释。
- `evidence`：依据。
- `report_language`：报告表达。
- `healing_direction`：疗愈方向。
- `case_excerpt`：案例片段。

## 8. 检索策略

不同场景应使用不同检索策略。

### 8.1 生成解读报告

输入可能包括：

- 用户主题。
- 画面观察结果。
- 三圈信息。
- 颜色、形状、五行生克信号。

检索顺序建议：

1. 按主题过滤 `domain`。
2. 按画面信号找 `visual_signal`。
3. 通过 `mapping_rule` 找相关 `issue_clause`。
4. 取 `report_block` 和 `healing_intervention`。
5. 生成报告。

### 8.2 回答用户追问

输入包括：

- 用户问题。
- 原报告中的相关段落。
- 当前会话上下文。

检索顺序建议：

1. 找到原报告相关判断。
2. 检索对应议题条款。
3. 检索对应画面信号和解释依据。
4. 生成回答，并保持和原报告一致。

### 8.3 生成疗愈方案

输入包括：

- 用户当前议题。
- 已识别卡点。
- 用户可接受的练习方式。
- 风险和禁忌。

检索顺序建议：

1. 取对应 `issue_clause`。
2. 取对应 `healing_intervention`。
3. 按强度、周期、用户状态筛选。
4. 生成可执行方案。

### 8.4 AI 追问用户

如果画面信息不足或存在多个可能解释，AI 可以先向用户提问。

提问应服务于区分议题条款，例如：

- 这个问题更像财富压力，还是关系压力？
- 你最近花钱更多是因为开心奖励自己，还是因为情绪低落想安抚自己？
- 你想赚钱更多是为了自由、创造，还是为了逃离某种关系或环境？

用户回答后，再选择更准确的 `issue_clause` 和 `healing_intervention`。

## 9. 版本迭代

本知识库不需要一次性完成。

建议按 pack 版本迭代：

```text
1.0.0-alpha.1  财富议题 + 基础画面映射 + 报告组织规范
1.0.0-alpha.2  个人成长 / 自我价值议题
1.0.0-alpha.3  亲密关系议题
1.0.0-beta.1   疗愈方案库增强 + 追问问答增强
1.0.0          第一版稳定知识包
```

每次版本更新应记录：

- 新增了哪些知识单元。
- 修改了哪些知识单元。

### 10.2 后续增强

后续可以增加：

- Rule engine：处理画面信号到议题条款的权重。
- Eval set：用案例测试报告质量。
- Trace：记录每段生成内容引用了哪些知识单元。
- Pack diff：比较不同版本运行时 Markdown 包的变化。

## 12. 当前结论

本知识库应采用：

```text
Markdown 知识文档
  → 受控 Markdown 运行时包
  → 映射规则（翻译层）
  → 质量门与风险路由
  → LLM 生成
```

> **变更（2026-05-28）**：当前阶段采用受控 Markdown 运行时包；已弃用的运行时路线不再作为后续方向写入本架构。

它不是普通 wiki，也不是只靠 prompt 的知识库。

它应是一个可版本化、可检索、可追溯、可运行的知识系统。

## 13. 当前运行时质量门字段

进入运行时包的内容，至少需要能回答这些问题：

| 字段 | 说明 |
|------|------|
| `entry_id` | 条目 ID，可先用人工命名，不强制机器生成 |
| `entry_type` | `visual_signal`、`issue_clause`、`mapping_rule`、`report_block`、`practice`、`source_ref` |
| `source_refs` | 上游 source、atom、wiki、案例或下游来源索引路径 |
| `source_status` | `ai_draft`、`source_supported_draft`、`case_verified`、`reviewed` |
| `review_status` | `draft`、`review_pending`、`approved_for_internal`、`approved_for_public` |
| `risk_level` | `low`、`medium`、`high` |
| `runtime_permission` | `allow`、`allow_with_warning`、`block` |
| `report_sections` | 可进入哪些报告段落 |
| `fallback_action` | 被拦截时如何处理，例如追问、降级、转外部支持 |

最小规则：

- `runtime_permission = block` 的内容不得进入用户可见报告。
- `risk_level = high` 的内容必须先经过安全边界判断。
- `source_status = ai_draft` 的内容只能作为内部候选，除非所在运行时包明确声明允许内部测试。
- 疗愈建议必须能回到三库交叉索引，且 ❌ 项不得直接输出。

## 14. 当前风险路由

| 风险类型 | 默认动作 | 输出边界 |
|----------|----------|----------|
| 自杀、自伤、活不下去 | 停止报告生成，提示外部专业支持 | 不输出画面分析结论 |
| 严重创伤具体事件 | 停止深度解读，转稳定化与外部支持 | 不做成因解释或暴露式练习 |
| 医疗症状、疾病、孕期、癫痫等 | 不做医学判断，建议医疗专业支持 | 只保留低风险观察和身体觉察 |
| 债务危机、破产、严重财务风险 | 不给财务承诺或投资建议 | 只做情绪承接和下一步求助建议 |
| 关系暴力、控制、现实安全威胁 | 不做关系修复承诺 | 优先安全计划和外部支持 |

风险路由优先于所有报告生成规则。
