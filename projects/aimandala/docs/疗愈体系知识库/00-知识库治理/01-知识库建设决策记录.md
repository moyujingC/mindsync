## 1. 建设目标

疗愈体系知识库从头建设。外部来源材料只有在被重新整理、标注来源、确认适合进入本知识库后，才可以成为正式知识源。

本知识库的上层边界是“疗愈体系”，不是某一个单一应用。曼陀罗解读是当前第一条落地链路，后续同一套议题、条款和疗愈路径可以继续用于课程、训练营、陪伴方案、内容产品和其他衍生产品。

这样做的原因是：知识库需要保持清晰边界，避免未经整理的材料自动进入 AI 协作、内容生成、知识整理或报告规则设计过程。

当前至少服务三类产品场景：

1. 生成解读报告。
2. 回答用户围绕解读报告提出的追问。
3. 生成定制化疗愈方案。
4. 支撑课程、练习、陪伴方案和内容产品的后续开发。

后续还可能支持一种更主动的交互：AI 在分析画面后，先向用户提出补充问题，再结合用户回答生成更精准的解读报告。

## 3. 议题层先行

本知识库的议题层不能只从 11 个案例中反推出完整体系。

11 个原始案例有价值，因为它们来自真实解读经验，可以帮助我们学习：

- 疗愈师如何组织报告。
- 个案中常见的表达方式。
- 某些议题在实际解读中的呈现。
- 报告语言如何从观察走向解释和建议。

但 11 个案例数量有限，不能代表完整议题。比如财富关系议题不能只由这些案例中出现过的财富表达构成。

更合理的顺序是：

1. 先不考虑画面因素，建立议题本身的框架体系。
2. 用心理学流派、疗愈流派、培训材料和专题资料填充议题内容。
3. 用 11 个案例校验报告语言、案例表达和部分高频模式。
4. 再把画面信息映射到议题条款。

也就是说，`20-疗愈体系/10-议题层` 应先回答“这个议题本身是什么”，曼陀罗流派下的画面语言和五行色彩材料后续再回答“哪些画面信号可能指向这个议题条款”。

## 4. 材料组织方式

本知识库的材料应按知识生产链路组织：

```text
研究母库 / 来源索引 / 培训材料 / 原始案例
        ↓
20-疗愈体系 / 10-议题层
        ↓
20-疗愈体系 / 30-疗愈方案层
        ↑
20-疗愈体系 / 20-流派层 / 曼陀罗
        ↓
30-应用适配 / aimandala
        ↓
runtime pack
```

各层职责如下：

| 层级 | 职责 |
|------|------|
| `05-参考来源索引` | 保存来源位置、入库用途、审核状态和影响文件，不重复维护来源正文。 |
| `20-疗愈体系/10-议题层` | 建立财富、关系、事业、健康、自我价值等议题的完整知识框架。 |
| `20-疗愈体系/20-流派层` | 沉淀心理学流派、疗愈流派、曼陀罗等专业解释框架。 |
| `20-疗愈体系/30-疗愈方案层` | 沉淀练习、觉察问题、书写任务、身体练习、冥想和行动建议。 |
| `30-应用适配` | 定义具体产品如何使用疗愈体系知识，例如报告结构、追问回答、沟通边界和生成规范。 |
| `runtime` | 后续保存机器运行时使用的 schema、unit、pack、index 和 eval。 |

## 6. RAG 和切块

本知识库需要 RAG，但不能只把整批 Markdown 丢进向量库。

普通 wiki 式 RAG 容易做到“找相关文字”，但不保证推理链条正确。本知识库的链条更像：

```text
画面特征 → 画面信号 → 议题条款 → 报告表达 → 疗愈建议
```

因此，切块方式应按知识单元切，而不是按固定字数切。

推荐切块方式：

- 一个议题条款一个 chunk。
- 一个画面信号一个 chunk。
- 一个五行关系一个 chunk。
- 一个疗愈建议一个 chunk。
- 一个案例中的“一圈解读”“整体解读”或“调整方案”一个 chunk。

每个 chunk 都应带元数据，例如：

```yaml
id: wealth.self_worth.low_deservingness
type: issue_clause
domain: wealth
scenario:
  - report_generation
  - followup_qa
  - healing_plan
source: 20-疗愈体系/10-议题层/10-议题本体/30-现实/01-财富关系.md
version: 0.1.0
status: draft
```

如果一个条款很长，可以继续拆成子块：

- `explanation`：解释。
- `evidence`：依据。
- `report_language`：报告表达。
- `healing_direction`：疗愈方向。
- `case_excerpt`：案例片段。

## 7. 三个场景的调用方式

### 7.1 生成解读报告

输入通常包括用户主题、画面观察结果、颜色、形状、圈层和五行关系。

建议链路：

```text
用户主题
  → 过滤 domain
  → 识别 visual_signal
  → 通过 mapping_rule 找 issue_clause
  → 取 report_block 和 healing_intervention
  → 生成报告
```

### 7.2 回答用户追问

输入通常包括用户问题、原报告段落和会话上下文。

建议链路：

```text
用户追问
  → 定位原报告相关判断
  → 取对应 issue_clause
  → 补充 visual_signal 和 source_ref
  → 生成一致、可解释的回答
```

追问回答要和原报告保持一致，不能因为重新检索到别的材料就推翻前文判断。

### 7.3 生成定制化疗愈方案

输入通常包括已识别议题、卡点、用户状态、可接受练习方式和风险边界。

建议链路：

```text
issue_clause
  → healing_intervention
  → 按强度、周期、适用人群筛选
  → 生成可执行方案
```

疗愈建议不能写成医疗诊断、财务承诺或确定性因果判断。

## 9. 迭代方式

本知识库不需要一次性建设完成，应按版本逐步扩展。

建议每次迭代都记录：

- 新增了哪些知识单元。
- 修改了哪些知识单元。
- 废弃了哪些知识单元。
- 哪些报告能力受影响。
- 哪些测试案例需要重新验证。

建议初始迭代顺序：

| 版本 | 目标 |
|------|------|
| `1.0.0-alpha.1` | 财富关系议题、基础画面映射、报告组织规范。 |
| `1.0.0-alpha.2` | 个人成长 / 自我价值议题。 |
| `1.0.0-alpha.3` | 亲密关系议题。 |
| `1.0.0-beta.1` | 疗愈方案库增强 + 追问问答增强。 |
| `1.0.0` | 第一版稳定知识包。 |

## 10. 当前执行原则

当前阶段先做四件事：

1. 保持知识库边界清晰，来源资料只做人工迁移。
2. 继续用“原文保真重组”的方式拆解专家手册，保留一线经验表达。
3. 优先把 `20-疗愈体系/10-议题层` 建扎实，不让少量案例定义完整议题。
4. 在文档稳定后，再逐步建立 `runtime/schemas`、`runtime/units` 和 RAG 索引。

## 11. 历史运行时资产处理原则

旧运行时资产只作为迁移参考和保真对照，不再作为本知识库的新建设目标。

后续新增报告、追问和疗愈方案能力时，应优先进入本知识库的自然语言知识层、结构化知识单元层和新的运行时入口。旧运行时资产后续可按迁移进度逐步清理，不在新版入口文件中反复引用。

## 12. 知识状态分级体系

> **变更（2026-05-28）**：本节原定义的 `model_scaffold` / `source_supported` / `cross_source_validated` 三级体系已废弃，统一迁移至 03-运行架构第13节定义的四级体系。本节保留历史决策说明，供理解当时设计意图。

### 历史决策（原 v0.2.0）

原体系定义了三类状态：

| 状态 | 含义 | 使用边界 |
|------|------|----------|
| `model_scaffold` | 由现有框架和大模型辅助整理出的草稿结构 | 可用于产品试写和结构验证，不可视为来源结论。 |
| `source_supported` | 已有明确来源材料支持 | 可进入报告生成，但表达应保留来源范围和不确定性。 |
| `cross_source_validated` | 已被多个来源支持或交叉校验 | 可作为较稳定的疗愈体系条款。 |

晋级条件：
- `model_scaffold` → `source_supported`：必须补充来源路径、对应章节或条款说明。
- `source_supported` → `cross_source_validated`：必须至少记录两个不同来源的支持关系。

### 当前体系（v0.3.0）

现统一使用 03-运行架构第13节定义的四级体系：

| 状态 | 含义 | 使用边界 |
|------|------|----------|
| `ai_draft` | 内容由 AI 生成，尚未完成来源验证 | 只能作为内部候选，不得进入对外报告正文。 |
| `source_supported_draft` | 已有来源材料支撑初版表达，但仍处于草稿 | 可进入内部测试。 |
| `case_verified` | 已通过案例验证 | 可用于报告生成。 |
| `reviewed` | 已完成人工审核 | 可进入正式用户输出。 |

晋级条件详见 03-运行架构第13节。最终可运行状态为 `runtime_ready`（需补齐边界字段和风险路由）。

**各层级的状态使用规范**：
- 议题本体、流派知识、疗愈方案层：使用 03-运行架构的四级体系。
- 画面信号：使用画面信号审核流程的状态，同时通过晋级路径最终归入 `runtime_ready`。
- 运行时包打包：必须达到 `reviewed` 级别；`runtime_ready` 为可选目标状态。

**废弃状态**：本知识库中不再使用 `model_scaffold`、`source_supported`、`cross_source_validated` 作为状态值。历史文件中的这些状态值应随文件更新逐步替换为新体系对应值。
