## 概述

## 第五阶段：颜色与形状知识库补充完善

### 5.1 补充背景

**颜色测试报告**: `05_知识库与芷默文章对比测试报告.md`

**发现的问题**:
- **颜色方面**: 通过严格对比芷默老师的颜色解读文章，发现知识库存在以下缺失：
  - 颜色特质描述角度差异（侧重心理状态 vs 行为表现）
  - 缺少色阶的"强弱"分级描述
  - 部分颜色特质未完整记录
  - 24色/36色彩铅覆盖不完整
- **形状方面**: 缺乏三圈解读、曼陀罗特有形状、形状组合解读

### 5.2 关键决策

在补充过程中，对速查表和手册的差异进行了用户决策：

| 决策项 | 选项 | 决策结果 | 说明 |
|--------|------|---------|------|
| 粉色定义 | A速查表/B手册/C融合 | **C融合** | 心理角度(爱的辛苦)+行为角度(被动害怕担当)+疗愈方向 |
| 紫色归属 | A固定火/B灵活 | **B灵活** | 可归为弱火或木属性，以解读者感觉为准 |
| 外圈红色 | 采纳/不采纳 | **采纳** | 成片红色=漏财/入不敷出；零碎红色=爱美/爱打扮 |
| 命名规范 | 深正淡/深重轻/其他 | **深中浅** | 统一使用深/中/浅三级命名 |
| 色阶数量 | 两级/三级 | **三级** | 每种主要颜色补充深/中/浅三级色阶 |

### 5.3 颜色补充内容

**第一部分：新增颜色定义（24/36色覆盖）**

| 新增颜色 | 元素 | 色阶定位 | 核心含义 | 与现有颜色区别 |
|----------|------|---------|---------|---------------|
| **桃红** | 火 | 弱火偏中 | 渴望被爱，愿意适度付出，但仍依赖 | 比粉红略暖、带微橙调，比粉红主动一点 |
| **玫瑰红** | 火或木 | 弱火带紫 | 灵性+浪漫，有幻想倾向，贵气但可能不接地气 | 介于粉红和紫色之间，偏紫的红 |
| **橘黄** | 火 | 中火 | 温暖付出，照顾者，有掌控欲但比橙色柔和 | 橙色的一种，偏黄的橘色，更温暖 |

**第二部分：颜色别名映射体系（COLOR_ALIASES）**

建立24色/36色彩铅完整映射：
- 红色系：朱红、大红、深红、暗红、酒红、橘红 → 红色
- 黄色系：柠檬黄、淡黄、中黄、土黄、深黄、咖啡黄 → 黄色
- 绿色系：草绿、深绿、墨绿、翠绿、青绿、淡绿、嫩绿、浅绿 → 绿色
- 蓝色系：天蓝、湖蓝、钴蓝、深蓝、普蓝、群青 → 蓝色
- 紫色系：紫罗兰、青莲 → 紫色
- 棕色系：棕色、褐色、茶色 → 黄色（按深黄色处理）

**第三部分：色阶细分补充**

| 颜色 | 深 | 中 | 浅 |
|------|----|----|----|
| **红色** | 压抑的红，淤堵的红，有伤痛；破坏性、毁灭性 | 喜悦热情但不稳定 | 失落的红，力量不足，依赖 |
| **黄色** | 沉重、内敛、自卑；被动等待、期待被爱 | 接纳承担、老黄牛 | 明亮、轻松、温和 |
| **绿色** | 深沉固执、边界封闭 | 放松疗愈、有清晰边界 | 新生放松、边界建立中 |
| **蓝色** | 沉稳静谧、情绪暗涌 | 智慧生发、爱学习 | 温柔清新、优柔寡断 |
| **紫色** | 浓重紫、自我封闭、不好接近 | 直觉型、时断时续 | 萌芽型、希望被关注 |

## 第六阶段：四步方法论重构与知识库文档化 (2026-03-05 ~ 2026-03-06)

### 6.1 背景与目标

在前五阶段基础上，对知识库进行方法论层面的重构，建立标准化的四步解读流程，并创建完整的 Markdown 文档体系供 RAG 检索使用。

### 6.2 关键决策与重构

#### 决策一：四步解读方法论

**旧架构** (分层式):
- 初级/中级/高级三层体系
- 复杂且难以执行

**新架构** (四步法):
```
Step 1: 直断（快速筛查）
Step 2: 颜色分析（逐圈详细）
Step 3: 形状分析（整体+触发式）
Step 4: 生克分析（圈级关系）
```

**决策依据**: 通过分析11个完整案例，发现实际解读流程更符合四步逻辑，且颜色是主要维度，形状是辅助维度。

#### 决策二：三圈能量循环模型

**新增内容**:
- **正向流动**: 内圈(意识) → 中圈(能量) → 外圈(物质) → 反馈 → 内圈
- **反向流动**: 外圈→中圈（压力倒灌）、中圈→内圈（情绪反噬）
- **跳跃流动**: 内圈→外圈（意识直接显化，缺乏情感缓冲）

**能量质量评估四维度**:
- 通畅度（意识-情绪-行为一致性）
- 速度（从意识到显化的转化速度）
- 强度（各圈能量饱满程度）
- 方向（正向/反向/跳跃/分散）

#### 决策三：颜色含义融合版

**策略**: 将手册原文的丰富描述与结构化数据结合

**数据结构**:
```python
COLOR_MEANINGS = {
    "木": {
        "element": "木",
        "nature": "生长、向上、独立",
        "shades": {
            "深绿": {
                "state": "太过",
                "core_meaning": "内在有伤痛或忧郁，无法释放，固执己见",
                "keywords": ["伤痛", "忧郁", "固执", "自视甚高"],
                "circles": {
                    "内圈": {
                        "interpretation": "手册原文...",
                        "manifestations": [...],
                        "healing": "..."
                    }
                }
            }
        }
    }
}
```

## 第八阶段：疗愈方案定位澄清与2B/2C差异化设计 (2026-03-07)

### 8.1 背景与问题

在第七阶段完成后，疗愈方案 (`healing_programs.py`) 的数据结构已完整，但产品定位仍存在混淆：

**问题一：名称误导**
- "21天疗愈营"容易被误解为固定节奏、群体参与的训练营
- 用户可能期待标准课程表，而非个性化方案

**问题二：方案性质不清**
- 2C和2B的疗愈方案差异未明确区分
- 代码实现为"固定模板"，但产品设计应为"动态定制"

### 8.2 关键决策

#### 决策一：2C灵犀Pro方案定位

**正确定位**：**21天一对一曼陀罗疗愈方案**

| 维度 | 错误理解 | 正确定位 |
|------|----------|----------|
| **名称** | ~~21天疗愈营~~ | 21天一对一曼陀罗疗愈方案 |
| **性质** | 固定课程 | AI动态定制 |
| **交互** | 跟随固定任务 | 画作驱动，每次建议基于画作变化 |
| **绘画频率** | 误以为每天都要画 | Day1/7/14/21，每周一幅 |

**流程设计**：
```
Day 1:  开营画 → AI解读 → 生成 Week 1 定制建议
Day 7:  周中画 → AI对比变化 → 调整 Week 2 建议
Day 14: 周中画 → AI追踪趋势 → 优化 Week 3 建议
Day 21: 结业画 → AI总结变化 → 生成完整报告
```

**日常任务**：
- 音频引导：5-10分钟
- 书写练习：3-5分钟
- 小行动：5-10分钟
- 总时长：每日不超过20分钟

#### 决策二：2B明镜轻咨询方案定位

**方案来源**：智牧老师《曼陀罗解读手册》第四章11个完整案例

**核心方法**：**清理 → 显化** 两阶段深度疗愈

| 阶段 | 绘画方式 | 颜色使用 | 频率 |
|------|----------|----------|------|
| **清理期** | 单色清理画 | 黑色(恐惧)、蓝色(固化)、红色(愤怒)、黄色(委屈)、绿色(失衡) | 每天7-21张 |
| **显化期** | 彩色订单画 | 根据显化目标选择颜色 | 每周1张 |

**清理颜色对照**（来自手册案例）：
| 颜色 | 清理对象 | 适用情况 |
|------|----------|----------|
| 黑色 | 恐惧、不安全感 | 童年创伤、被忽视/虐待经历 |
| 蓝色 | 灵活性、固化思维 | 思维僵化、难以接受变化 |
| 红色 | 心力不足、愤怒 | 缺乏动力、压抑的愤怒 |
| 黄色 | 委屈 | 付出不被认可、老黄牛模式 |
| 绿色 | 平静、平衡 | 情绪失衡、需要恢复平静 |

**11个案例主题**：
| 案例 | 主题 | 核心方法 |
|------|------|----------|
| 案例1 | 个人成长 | 五行感知法 |
| 案例2-11 | 财富/情感/事业/成长组合 | 五行感知+相生相克法 |

#### 决策三：2C与2B方案对比

| 维度 | 2C 灵犀Pro | 2B 明镜轻咨询 |

## 第九阶段：主题个性化数据架构重构 (2026-03-08)

### 9.1 背景与问题

在第八阶段完成后，Prompt体系存在架构性问题：

**问题一：数据冗余**
- Lite版和Pro版的主题Addon（`addons/lite/*.md`, `addons/pro/*.md`）重复定义相同的主题个性化内容
- 6个洞察角度、失衡类型解读、实验建议等散落在多个Markdown文件中
- 修改一个主题需要同步修改多个文件，容易遗漏

**问题二：缺乏统一数据源**
- 颜色含义有 `color_meanings.py` 作为单一数据源
- 但主题个性化内容（洞察角度、失衡解读等）没有统一的API支持
- Prompt模板直接包含大量主题个性化文本，难以维护

**问题三：版本不一致风险**
- Lite和Pro对同一主题的解读可能出现偏差
- 新增主题时需要同时维护两套Addon文件

### 9.2 架构重构方案

#### 9.2.1 新架构设计

```
┌─────────────────────────────────────────────────────────────┐
│  Prompt层（轻量模板）                                         │
│  ├── prompt-lite-base.md（极简，使用 {{ theme_context }} 占位符）│
│  └── prompt-pro-base.md（详细，使用 {{ theme_context }} 占位符）│
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  PromptBuilder._build_theme_context()                        │
│  - 根据版本（Lite/Pro）动态构建主题上下文                       │
│  - Lite版：隐藏失衡类型名称，只给描述                           │
│  - Pro版：给出完整的失衡类型解读                               │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  知识库API层：app/core/knowledge/themes/                      │
├─────────────────────────────────────────────────────────────┤
│  7个主题文件：                                                │
│  ├── intimate_relationship.py                                │
│  ├── wealth_career.py                                        │
│  ├── personal_growth.py                                      │
│  ├── health_wellness.py                                      │
│  ├── father_relationship.py                                  │
│  ├── mother_relationship.py                                  │
│  └── parent_child_relationship.py                            │
│                                                              │
│  每个主题包含统一数据结构：                                    │
│  ├── THEME_CONFIG              # 主题基础配置                │
│  ├── COLOR_MEANINGS            # 颜色含义（原有）             │
│  ├── INTERACTIONS              # 相生相克（原有）             │
│  ├── HEALING_PRESCRIPTIONS     # 疗愈方案（原有）             │
│  ├── INSIGHT_TEMPLATES         # 6个洞察角度模板 ← 新增      │
│  ├── IMBALANCE_MAPPINGS        # 10种失衡类型映射 ← 新增     │
│  └── 导出函数（实验模板、Pro引导等）← 新增                   │
└─────────────────────────────────────────────────────────────┘
```

```python
def _build_theme_context(self, theme: str, version: ReportVersion) -> str:
    """
    构建主题上下文（从知识库API动态获取）

    流程：
    1. 获取主题配置（核心议题）
    2. 获取6个洞察模板
    3. 获取失衡类型映射（Lite版隐藏名称，Pro版显示完整）
    4. 获取实验建议模板（Lite版）
    5. 获取Pro引导文案（Lite版）
    """
```

### 9.4 收益与优势

#### 9.4.1 维护性提升

| 指标 | 重构前 | 重构后 |
|------|--------|--------|
| 主题数据存储位置 | 分散在14+个Markdown文件 | 集中在7个Python文件 |
| 修改一处主题数据 | 需同步修改2+个文件 | 修改1个文件即可 |
| 新增主题 | 需创建Lite+Pro两个Addon | 只需添加1个Python模块 |
| 类型安全 | 无 | TypedDict支持 |

#### 9.4.2 架构优势

1. **单一数据源**：主题个性化数据与颜色含义一样，统一存储在Python知识库中
2. **版本一致性**：Lite和Pro使用同一套主题数据，通过 `_build_theme_context()` 根据版本格式化输出
3. **动态注入**：Prompt模板只保留基础框架，主题数据由Builder动态注入
4. **可扩展性**：新增主题只需添加一个Python文件，无需修改Prompt模板
