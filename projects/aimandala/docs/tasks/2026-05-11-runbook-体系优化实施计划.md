## 1. 问题定义

`aimandala` 当前不是缺少 runbook，而是 runbook 的使用方式存在结构性失配，已经影响“程序按预期链路实现”的稳定性。

当前至少存在四类问题：

1. 入口分散
   - `runbook` 类文件仍散落在 `docs/runbooks/`、`docs/tasks/` 和部分 README 中
   - 读者很难一眼区分“当前正式入口”和“历史参考”
2. 状态混杂
   - 一些 `historical-reference` 文件仍在索引里以高优先级出现
   - 一些旧 phase 方案虽然已废弃，但仍容易被误当成当前主路径
3. 抽象层次不齐
   - 有些文件是入口导航页
   - 有些是人工操作手册
   - 有些规则其实已经下沉到脚本 / gate
   - 但当前索引没有显式区分这些层次
4. 文档与控制层映射不清
   - 已经存在 `guard`、`finalizer`、`execution health check` 等控制层机制
   - 但 runbook 没有稳定说明“哪部分只是手册，哪部分已经被程序强制执行”

## 2. 目标

本轮优化只做 runbook 体系收口，不直接改业务实现链路。

本轮要固定下面五条结果：

1. `docs/runbooks/README.md` 成为唯一默认 runbook 入口
2. 当前入口和历史参考入口显式分开
3. 每条关键 runbook 都能看出：
   - 它是入口页、人工手册，还是带控制层映射的正式 runbook
4. `docs/tasks/README.md` 不再把 runbook 类文件混作默认任务入口
5. `runbook` 与 `control layer` 的边界被写清：
   - runbook 负责流程
   - script / gate / guard / finalizer 负责执行约束

## 3. 非目标

本轮不做：

1. 不直接改 `Paperclip` 或 `aimandala` 业务代码
2. 不重写每一份历史 runbook 正文
3. 不迁移所有旧文件路径
4. 不把所有手册立刻脚本化
5. 不宣称仅靠改文档就能解决执行失配

## 4. 实施范围

本轮固定只收口下面几类资产：

1. `projects/aimandala/docs/runbooks/README.md`
2. `projects/aimandala/docs/tasks/README.md`
3. 与 runbook 体系直接相关的新 task / QA artifact
4. 必要时补 runbook 分类口径与控制层映射说明

## 5. 实施步骤

### 5.1 入口收口

1. 统一声明 `docs/runbooks/README.md` 为 runbook 正式入口
2. 显式区分：
   - current runbooks
   - historical-reference runbooks
   - tasks 目录中的 runbook-like 文件

### 5.2 类型分层

在 runbook 入口中固定三种类型：

1. 入口页 / index
2. manual runbook
3. control-backed runbook

定义口径：

1. 入口页
   - 负责导航，不直接承载完整操作合同
2. manual runbook
   - 定义进入条件、判断树、步骤、禁止动作、升级路径
   - 但仍主要依赖人工执行
3. control-backed runbook
   - 除了手册本身，还明确映射到脚本、gate、guard、finalizer 或 health check
   - 其中一部分规则已被程序强制执行

### 5.3 当前主链与历史链隔离

至少要在入口层明确：

1. `本地人工接手-runbook.md`
   - 只保留为旧 phase 2 历史参考
2. `本地-Mac-自动执行器-runbook.md`
   - 已从 `historical-reference` 修正为当前 control-backed runbook
   - 应作为普通任务自动在本地 Mac 上跑的正式操作入口
   - 不应再与旧 phase 2 handoff 模型混用
3. `aimandala-pr-质量门-runbook.md`
   - 当前仍在 `docs/tasks/`
   - 应在入口说明里明确它是 runbook-like delivery 手册，而不是任务计划

### 5.4 控制层映射补充

当前入口至少要对下面几类控制层资产建立映射：

1. `shared/tools/ci/server-automation-guard.mjs`
2. `shared/tools/ci/server-automation-finalizer.mjs`
3. `shared/tools/ci/check-paperclip-execution-health.mjs`
4. `shared/tools/ci/server-automation-run.sh`
5. 相关 smoke / verification 入口

目的不是复制脚本说明，而是明确：

1. 哪些规则只在文档里
2. 哪些规则已经由程序兜底
3. 哪些失配还停留在“手册知道，但系统没拦住”

## 6. 交付物

本轮最小交付物固定为：

1. 当前 task 文档
2. 对应 QA basis
3. 更新后的 `docs/runbooks/README.md`
4. 更新后的 `docs/tasks/README.md`

## 7. 验收口径

本轮完成至少应满足：

1. runbook 默认入口只剩一个
2. 当前主入口与历史参考入口不再混排
3. runbook 与 task 的边界更清楚
4. runbook 与 control layer 的关系被明确写出
5. 新入口能帮助后续定位：
   - 应先改文档
   - 还是应直接补脚本 / gate

## 8. 后续 handoff

本轮完成后，下一阶段再继续判断：

1. 哪些单篇 runbook 需要按统一模板重写
2. 哪些高频手册步骤该下沉成脚本或 gate
3. 哪些历史 runbook 应彻底迁出默认阅读路径
