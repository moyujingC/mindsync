## 1. 本轮目标

本轮不是单个 patch，而是一条正式重构主线。

总目标固定为：

1. 把源资料驱动链路从“迁移中可跑”推进到“正式可追溯”
2. 让 runtime、prompt/skeleton 和报告合同统一按 evidence-first 工作
3. 用分批实现的方式把重大重构拆开，避免一次性大爆炸

## 2. 执行纪律

从本文档起，后续执行必须遵守：

1. 先有 `spec + architecture + task + qa basis`
2. 每个批次进入实现前必须再开一轮计划模式
3. 每批实现完成后必须执行自动化验证
4. 每批完成后必须补对应 `verification record / delivery`
5. 有改动后及时提交，不把同一轮治理和实现改动长期堆在工作区

## 3. 批次拆分

### 3.1 Batch A：源资料到 runtime evidence 保真重构

目标：

1. 把 `Layer 0` 收成正式证据层
2. 把四步法、三元结构、失衡判断进入 runtime 中间层
3. 补齐 fidelity / fallback 结构化标记

默认涉及：

- `Layer0Raw`
- `Layer0Assembler`
- `ImbalanceService`
- 主题与运行时映射逻辑

通过条件：

1. `Layer 0` 能稳定区分 `visual_facts / knowledge_hits / rule_evaluations`
2. fallback 和 fidelity 可结构化暴露
3. 相关单测与 fixture 样本通过

### 3.2 Batch B：Narrative Plan 与 prompt/skeleton 重构

目标：

1. narrative 只消费 evidence 和 rule 层
2. `knowledge_skeleton` 不再以 projection-first 组织
3. theme context 能显式带出结构化来源

默认涉及：

- `NarrativeContextService`
- `ReportPromptPreviewBuilder`
- prompt preview / skeleton 相关逻辑

通过条件：

1. prompt 上游可明确看到 evidence trace
2. 不再需要用 narrative 层补假知识
3. 相关后端测试与 debug 样本通过

### 3.3 Batch C：Lite / Pro 报告合同与前端承接重构

目标：

1. 新结果合同真实落地
2. 前后端同轮承接，不留长期双合同
3. debug payload 支持 fidelity / trace 检查

默认涉及：

- `report_contracts`
- frontend shared types
- 结果页消费
- debug 面板

通过条件：

1. Lite / Pro 新合同与前端渲染同步通过
2. debug payload 可直接支撑 QA
3. 前端测试和合同回归通过

### 3.4 Batch D：回归、样本验证与治理收口

目标：

1. 固定 golden / fixture / drift 检查
2. 把 README、QA、Delivery、历史状态收口
3. 形成这一轮的正式交付链

通过条件：

1. 至少 4 组固定样本通过
2. README 默认入口已切到新母文档
3. 最终 delivery 能说明剩余风险和 handoff

## 4. 每批必备 artifact

每个批次进入实现前必须补齐：

1. 子计划
2. 子 QA 基线或等价 QA 章节
3. 预期自动化命令
4. 风险和回退边界

每个批次完成后必须补齐：

1. 验证记录
2. 交付记录或交付章节
3. git 提交

## 5. 当前顺序

本轮顺序固定为：

1. 先完成这批母文档和入口索引
2. 再进入 `Batch A` 的子计划
3. 之后按 `A -> B -> C -> D` 推进

默认不允许跳过 `A / B`，直接改 `report_contracts` 或前端结果页。

## 6. 当前不做

本轮默认不做：

1. 一次性把所有历史文档全部清洗到最新路径
2. 重做 `pack schema`
3. 同时推进不相关的产品链路需求
4. 在没有子计划的情况下先写实现再回补 artifact
