## 1. 本轮结论

当前系统状态可以概括为一句话：

`仓库侧治理能力已明显提升，但 automation / GitHub 凭证层仍未恢复到真正可运营状态。`

基于 `MIN-12`、`MIN-13`、`MIN-14`、`MIN-15`、`MIN-16` 的连续样本，本轮正式结论写死如下：

1. `MIN-15` 与 `MIN-16` 都不是代码失败，而是同一条 `runner-heartbeat` 链路上的基础设施阻塞
2. `MIN-16` 已能细化到 `credential_missing`，说明新的故障分类和评论模板已经开始生效
3. 当前最直接阻塞点不是仓库实现缺口，而是 `paperclip-heartbeat` 使用的 GitHub token 缺少 `repository self-hosted runners` 读取权限
4. `MIN-12`、`MIN-13`、`MIN-14` 仍保留旧标题和旧语义，说明系统处于新旧治理并存的过渡期
5. `MIN-14` 已出现“已修复”评论但状态仍是 `todo`，说明控制面仍存在状态、最新评论和执行结论不一致的问题

本轮目标不是继续在 issue 评论里零散补说明，而是把这批样本收束为正式治理整改 artifact。

## 2. 当前样本判断

### 2.1 `MIN-12` 到 `MIN-16` 的过渡期口径

- `MIN-12`
  - 旧诊断粗粒度样本
  - 主题是 `infra-runner-failure`
  - 线程后期已明确真实阻塞点是 heartbeat token 权限不足，但标题和结构仍是旧口径
- `MIN-13`
  - 旧口径下的代码修复样本
  - 已有本地修复和交付回写，但仍受在线凭证和复跑条件阻塞
- `MIN-14`
  - 旧口径下的代码修复样本
  - 已出现“已修复”评论，但状态没有同步收口，暴露控制面一致性问题
- `MIN-15`
  - 新治理初版样本
  - 已切换到三态 emoji 标题和执行基线展示
  - 仍把阻塞泛化为 `infra_missing`
- `MIN-16`
  - 当前最接近目标态的样本
  - 已切换到三态 emoji 标题
  - 已细化 `blocked_reason=credential_missing`
  - 已把“当前判断 / 已做动作 / 下一步动作 / 谁来解除阻塞”写入标准评论模板

### 2.2 本轮正式判断

从本轮开始，下面规则作为当前正式判断：

1. `queued` 超时优先归类为 `infra-runner-failure`
2. 若 heartbeat 无法读取 runner 元数据并返回 `403` 或 `accessDenied=true`，优先归类为 `credential_missing`
3. 若 runner 未注册、未在线或 labels 不匹配，归类为 `infra_missing`
4. 若 issue 描述中的执行基线与目标分支 / sha 明显不一致，必须继续标记 `workspace_drift`
5. 不允许再把上述问题混写成“构建失败”

## 3. 整改目标

### 3.1 第一层：恢复运行底座

第一优先级是恢复 `automation` 节点与 GitHub runner 观测链路：

1. 更新 `paperclip-heartbeat` 使用的 GitHub token，补齐 `repository self-hosted runners` 读取权限
2. 在 `automation` 节点重新执行 `shared/tools/ci/runner-doctor.sh`
3. 验证以下服务全部正常：
   - `mindsync-ci-runner.service`
   - `paperclip-heartbeat.service`
   - `paperclip-heartbeat.timer`
4. 至少让一条真实 `ci` workflow 从 `queued` 被 `mindsync-ci` runner 实际拾取并完成

本层未完成前，不应把系统表述为“已恢复可运营”。

### 3.2 第二层：修正控制面一致性

本轮同步收口下面 4 个治理要求：

1. 后续新 issue 继续严格使用三态 emoji、`blocked_reason`、执行基线、标准评论模板
2. issue 状态、最新评论、执行基线三者必须一致；若不一致，视为控制面不可信
3. 若任务线程已出现“已修复”或“已回写”评论，但状态仍停在 `todo` 或与评论结论不符，heartbeat 必须补一次状态修正或诊断评论
4. `queued` 超时、凭证缺失、runner 离线、workspace drift 必须各自保留独立语义，不能再混成同一个错误桶

### 3.3 第三层：统一过渡期样本口径

本轮不做全量旧 issue 批量迁移，但必须把 `MIN-12` 到 `MIN-16` 作为正式样本留档。

目的有两个：

1. 以后回看这批问题时，能看出系统是如何从旧口径演进到新口径的
2. 后续新增治理逻辑时，有明确样本可对照，而不是继续散落在评论线程中

## 4. 本轮执行纪律

### 4.1 做什么

- 新增本轮正式 `task / qa / delivery`
- 把 `MIN-12` 到 `MIN-16` 的现状和治理结论写入正式文档
- 把运行底座恢复动作、控制面一致性要求和过渡期样本说明收束为当前可执行计划

### 4.2 不做什么

- 不批量迁移所有旧 issue
- 不改 Paperclip 前端 UI
- 不把本轮问题重写为新的大而全平台方案
- 不把 `automation` 节点权限缺口误写成仓库代码缺陷

## 5. 通过条件

### 5.1 运行底座

- heartbeat token 不再触发 `accessDenied=true`
- `runner-doctor.sh` 能返回可判定结果
- 至少一条真实 `ci` run 被 `mindsync-ci` runner 拾取并跑完

### 5.2 控制面

- 新 issue 继续使用三态标题与标准评论模板
- `credential_missing`、`infra_missing`、`workspace_drift` 能在 issue 层面被稳定区分
- 已出现“已修复”评论但状态未收口的任务，会被 heartbeat 继续补诊断或状态修正

### 5.3 文档治理

- 本轮正式 `task / qa / delivery` 已落盘
- `MIN-12` 到 `MIN-16` 已作为过渡期样本进入正式文档
