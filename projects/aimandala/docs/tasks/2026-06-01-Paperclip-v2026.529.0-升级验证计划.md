## 1. 问题定义

`2026-06-01` 的版本判断已经把 `Paperclip` 推荐目标版本更新为 `v2026.529.0`。

当前 `aimandala` 项目级已验证基线仍是 `v2026.416.0`。这不是安全紧急问题，但已经形成新的版本治理差距：

1. 推荐目标版本高于已验证运行基线
2. 治理文档已改为“官方优先、本地兜底”，但运行时尚未完成对应验证
3. 升级前必须验证自定义部署、执行边界与本地治理语义不会被破坏

## 2. 目标行为

完成一次面向 `v2026.529.0` 的计划内升级验证，并给出明确结论：

1. 可以升级运行实例
2. 暂缓升级并记录阻断原因
3. 需要先补某个治理、部署或运行时前置项

本任务不直接要求自动升级远端 `Paperclip`。升级动作必须在验证口径明确后执行。

## 3. 范围

本任务覆盖：

- `Paperclip` 主仓版本核验
- `v2026.529.0` release 内容对当前部署的影响确认
- 数据库 migration（迁移）风险确认
- `execution workspace`（执行工作区）materialization（实例化）与 finalize（收尾）验证
- `server_automation` 与 `local_manual_review` 分流验证
- `codex_local` / `claude_local` / `pi_local` 最小唤醒和环境探测
- structured interactions（结构化交互）、document locks（文档锁）与 inline annotations（内联批注）最小验证
- 升级后文档口径与版本基线回写

本任务不覆盖：

- 启用 Modal sandbox provider
- 启用新的 cloud adapter
- 正式接入上游 secrets provider / vault
- 重构本地执行器
- 解除 `PAPERCLIP_SERVER_AUTOMATION_FREEZE=1`

## 4. 验收标准

升级验证通过需同时满足：

1. `Paperclip` 服务端可明确核验为 `v2026.529.0`
2. `/api/health` 返回正常
3. 数据库 migration 完成且无启动卡死
4. `aimandala` 新 issue 能正确生成 `executionWorkspaceId` 或 `currentExecutionWorkspace`
5. `server_automation` 任务只进入 `/opt/automation/worktrees`
6. `manual-review-required + local_manual_review` 不落入服务器可写路径
7. `/opt/automation/app/mindsync` 与 `/opt/automation/app/mindsync-heartbeat` 保持 observe-only，不被真实任务写脏
8. `codex_local` / `claude_local` / `pi_local` 的 Test environment 或等价最小探测通过
9. comment 回写仍包含可信的 `adapter` 与 `host` 语义
10. accepted plan 在 review / accept 后不重复分解子任务
11. blocker 未解除时，下游 issue 不提前唤醒；finalize 后再触发 dependent issue wake（依赖任务唤醒）
12. 至少完成一轮最小 document lock + inline annotation 验证
13. 若升级通过，runbook 中“项目已验证基线”同步更新为 `v2026.529.0`

## 5. 边界情况

需要特别观察：

- migration 成功但旧 issue 缺少 execution workspace 绑定
- project policy 显示启用 isolated workspace，但 issue 没有 materialize
- finalize 正常但宿主机 worktree 状态未收敛
- retry / recovery 新能力把本应本地执行的任务重新唤醒到服务器
- `codex_local` 重新暴露未在 `Paperclip` 明确批准的外部 connector
- structured interactions 与本地 `review:*` 语义解释出现冲突
- document lock / inline annotation 可用，但当前交付链路仍继续退回 comment 审稿

## 6. 执行计划

### 6.1 升级前核验

1. 记录当前运行版本、commit、tag 和容器镜像构建来源
2. 记录当前数据库备份或回滚方式
3. 检查主镜像区、巡检区、worktrees 是否干净
4. 跑现有 execution health strict gate
5. 记录当前 `codex_local` / `claude_local` / `pi_local` 面板状态
6. 核验当前 `Paperclip` 目标文档口径是否已切到 `v2026.529.0`

### 6.2 升级验证

1. 在受控窗口切到 `v2026.529.0`
2. 重建并启动 `paperclip` 容器
3. 观察 migration 和启动日志
4. 验证 `/api/health`
5. 执行最小 issue / workspace / adapter 探测
6. 执行 structured interaction、document lock、annotation 最小探测
7. 跑 heartbeat 与 execution health check

### 6.3 升级后收尾

1. 若验证通过，更新项目已验证基线
2. 若验证失败，记录阻断原因和回滚状态
3. 将结论回写到 deployment runbook
4. 如发现上游原生能力仍无法覆盖关键场景，再单独开任务评估本地兜底增强

## 8. 风险与回滚

- 风险：migration 无法回滚
  - 处理：升级前必须确认数据库备份或快照
- 风险：recovery / productivity review 自动创建新 issue，影响现有状态流
  - 处理：先观察，不直接把新能力纳入正式任务流
- 风险：execution workspace materialization 仍有漂移
  - 处理：按现有 `execution_workspace_policy_not_materialized` 口径阻断
- 风险：adapter 环境探测通过但真实任务路径错误
  - 处理：必须增加最小真实 issue 验证，不只看 Test environment
- 风险：review / document 新能力存在，但团队继续沿用旧交互习惯
  - 处理：升级验证里必须加入至少一轮真实交互样例

4. 残留风险
