## 1. 背景

当前 `Web MVP` 已明确不是“默认 Lite 体验”，而是：

1. `upload`
2. `detect`
3. `report-choice`
4. 用户主动选择 `Lite / Pro`
5. 进入对应版本的 loading 与结果页

同时，历史记录当前仍保留一个过时实现：

- history 列表项会直接推导 `reportVariant`
- reopen 时直接进入某个单一报告

这与当前产品认知不一致，也与“报告类型必须显式传递”的实现纪律不一致。

## 2. 本轮目标

本轮同时收束两件事：

1. 前端报告读取链路显式化
2. history / reopen 改为“记录详情页 -> 版本选择 -> 报告页”

本轮不是重做产品流程，也不是修改后端持久化模型。

## 3. 本轮要做

### 3.1 显式报告类型

- `getInterpretationReport(interpretationId, reportType)` 中 `reportType` 改为必填
- `refreshMobileWebReport(interpretationId, reportType, currentState?)` 中 `reportType` 改为必填
- 所有前端调用点都必须显式传 `lite` 或 `pro`
- 不保留“省略 reportType 让后端自己决定”的调用方式

### 3.2 历史记录详情页

- 新增 `history-record-detail` 路由 / 页面 / descriptor
- 该页面只服务 `history / reopen`
- 页面展示：
  - 当前画作记录基础信息
  - 已购版本 / 可查看版本
  - `upgrade_history` 派生的版本演进信息
  - 打开 Lite / 打开 Pro 的明确动作

### 3.3 history 行为调整

- history 列表项不再直接打开某个报告版本
- history 点击记录后统一进入 `history-record-detail`
- 当只有 `Lite` 时，详情页默认聚焦 Lite
- 当同时拥有 `Lite + Pro` 时，详情页同时露出两个入口
- 若 `Pro` 仍在生成中，详情页显示进度信息，并允许进入对应 loading / 进度态

## 4. 本轮不做

- 不修改 `/api/v2/miniapp/*`
- 不引入微信 session / 支付 / native host
- 不把 `report-choice` 复用成历史详情页
- 不重构后端为“一幅画多条独立版本记录”
- 不处理手机端人工验收，只继续保留该缺口

## 5. 当前实现默认

- `report-choice` 继续只服务新解读流程
- `history-record-detail` 是新的历史 reopen 承接页
- `InterpretationVersion` 当前继续作为前端第一版 `reportType`
- 若现有 `InterpretationRecordResponse` 不够支撑详情页，可做最小向后兼容字段加法
