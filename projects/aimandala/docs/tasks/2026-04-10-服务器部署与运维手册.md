## 1. 目的

这份手册用于收口 `aimandala / 一镜一梳` 当前三台腾讯云服务器的职责、目录、服务、部署方式与日常运维命令，避免后续继续依赖聊天记录回忆现场。

## 2. 当前服务器分工

当前采用三台服务器分工：

- 自动化节点：`automation`
- 开发测试机：`main`
- 正式发布机：`release`

当前确定策略：

1. 本地开发完成后，先提交到 GitHub
2. `automation` 节点承接 Paperclip、runner、smoke、auto-fix
3. 开发测试机从远程仓库拉取 `main`
4. 接近发布时，再从 `main` 收口到 `release`
5. 正式发布机后续只承接 `release`

## 3. 自动化节点（新增）

- 承接 Paperclip UI/API
- 承接 `mindsync-ci` runner
- 承接 `ci / deploy / nightly-smoke / auto-repair`

- 正式站点

- 单 runner
- 串行执行
- Paperclip 常驻

## 7. 开发测试机当前服务清单

### 7.1 后端服务

- systemd 名称：`aimandala-main-backend`
- 启动命令：

```bash
/opt/aimandala-main/backend/venv/bin/uvicorn app.api.main:app --host 0.0.0.0 --port 8000
```

- 核心环境变量：

```bash
PYTHONPATH=/opt/aimandala-main/app/mindsync/projects/aimandala/toC/app/backend
AIMANDALA_LLM_BACKEND=noop
AIMANDALA_UPLOAD_BACKEND=local
```

说明：

- 开发测试机允许继续使用 `noop + local` 作为联调兜底
- 这不是 `release` 口径，不能把开发机默认值误当正式发布配置

### 7.2 前端静态站点

当前正式入口是 `nginx` 提供的静态目录：

- 站点目录：`/var/www/dev-web.jingshu.cc`
- 入口端口：`80`

同时保留了一个临时 Python 静态服务用于排障：

- systemd 名称：`dev-web-8001`
- 端口：`8001`

说明：

- 日常访问优先走 `80`
- `8001` 只作为临时调试保留
- 后续若确认不再需要，可停用 `dev-web-8001`

### 7.3 nginx

当前 `nginx` 配置思路：

- `/`：前端静态站点 + SPA fallback
- `/api/`：反代到 `127.0.0.1:8000`
- `/health`：反代到 `127.0.0.1:8000/health`

## 8. 当前一键部署方式

开发测试机当前一键部署脚本：

```bash

```

1. 拉取 `origin/main`

## 9. GitHub Actions CI/CD 约定

当前仓库内已增加 4 条 workflow：

- `/Users/xinran/Downloads/dev/mindsync/.github/workflows/aimandala-ci.yml`
- `/Users/xinran/Downloads/dev/mindsync/.github/workflows/aimandala-deploy.yml`
- `/Users/xinran/Downloads/dev/mindsync/.github/workflows/aimandala-nightly-smoke.yml`
- `/Users/xinran/Downloads/dev/mindsync/.github/workflows/aimandala-auto-repair.yml`

当前约定：

1. `ci`
   - PR 到 `main`、以及 `main / release` push 时运行
   - 在 self-hosted runner 上跑：
     - 前端 `vitest`
     - `typecheck`
     - `vite build`
     - 后端 `pytest`
     - knowledge 验证脚本
2. `deploy`
   - `main -> dev`
   - `release -> prod`
3. `nightly-smoke`
   - 定时跑 dev / prod 基础烟测
   - 手动触发时可切到 `deep`
4. `auto-repair`
   - 只在 `ci` 失败时进入
   - 默认只对白名单测试 / 构建失败尝试隔离分支修复

### 9.1 self-hosted runner

当前 runner 角色固定为：

- 名称：`mindsync-ci`
- 标签：
  - `self-hosted`
  - `linux`
  - `mindsync-ci`
  - `aimandala`

runner 的安装说明见：

- `/Users/xinran/Downloads/dev/mindsync/projects/aimandala/deploy/github-runner/README.md`

### 9.2 必需 Secrets / Vars

需要在 GitHub 仓库中至少配置：

- `AIMANDALA_DEV_HOST`
- `AIMANDALA_DEV_USER`
- `AIMANDALA_DEV_SSH_KEY`
- `AIMANDALA_PROD_HOST`
- `AIMANDALA_PROD_USER`
- `AIMANDALA_PROD_SSH_KEY`
- `PAPERCLIP_API_BASE`
- `PAPERCLIP_API_KEY`
- `PAPERCLIP_ENGINEER_AGENT_ID`

如需启用自动修复，还需要配置 repo variable：

- `AIMANDALA_AUTO_REPAIR_COMMAND`
- `AIMANDALA_AUTO_REPAIR_PUSH`
- `AIMANDALA_AUTO_REPAIR_CREATE_PR`

### 9.3 当前说明

- Actions 只负责触发、检查和回写，不把服务器现场当权威源
- 开发机仍走 `/opt/aimandala-main/scripts/deploy-main.sh`
- 正式机仍走 `docker compose build && docker compose up -d`
- Paperclip 失败任务按聚合键收口，避免同一失败每次都新建单
- 自动修复只允许在隔离分支里修改可白名单文件范围

### 9.4 runner watchdog

仅靠 GitHub workflow 本身无法覆盖“runner 整机宕机”。

因此当前默认还需要在**非 runner 主机**定时执行：

```bash
node /Users/xinran/Downloads/dev/mindsync/shared/tools/ci/check-runner-heartbeat.mjs \
  --repository moyujingC/mindsync \
  --workflow-file aimandala-ci.yml \
  --branch main
```

## 10. 当前需要记住的约束

1. 服务器上的代码不是权威源，GitHub 仓库才是权威源
2. 开发测试机只跟 `main`
3. 正式机未来只跟 `release`
4. 未经确认，不要在服务器上直接改业务代码并长期保留
5. 若必须临时改服务器文件，应尽快回写到仓库
6. 正式机当前前端若重新 build，必须确保 `VITE_AIMANDALA_API_BASE_URL=https://web-api.jingshu.cc`
7. 正式机必须确保 `AIMANDALA_LLM_BACKEND=openai_compatible`
8. 正式机必须确保 `AIMANDALA_UPLOAD_BACKEND=cos`
9. 正式机必须确保 `AIMANDALA_ENABLE_DEBUG_WORKBENCH=0`
10. auto-repair 不允许直接修改 `main / release`
11. deploy / smoke 失败默认只建 Paperclip 风险任务，不自动改线上
