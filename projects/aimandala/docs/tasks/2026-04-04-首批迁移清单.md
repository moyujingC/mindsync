### 7.1 当前已确认的 `toC/` 内部结构

旧仓库的 To C 主线同时包含：

1. 后端：`app/api + app/core + app/infrastructure`
2. 前端：`app/ui`

因此当前已经确认 `toC/` 采用下面的显式拆分：

```text
toC/
  app/
    backend/
    frontend/
  domain/
  tests/
  data/
```

当前我倾向于要拆，因为否则前后端很快会重新挤在一个入口里。
这一步现在已经作为工作区默认结构落地。

其中 `frontend/` 后续建议优先长成：

```text
frontend/
  shared/
    core/
    api/
    types/
  mobile-web/
  miniapp/
  native-app/
```

这样做的原因是旧仓库里已经有明确的多端前端复用设计：

- `core/`
  - 共享业务逻辑、状态机、纯函数流程
- `api/`
  - 共享 API service 和请求适配
- `types/`
  - 共享类型定义

渠道层只负责：

- 页面组件
- 路由
- 平台 API
- 支付、上传、登录等端侧适配

当前不急着预建所有空目录，但后续迁移和命名应默认兼容这条演进路径。

## 8. 建议执行顺序

1. 先写一份新的 To C MVP spec，而不是直接复制旧 PRD。
2. 再迁 `V2` API 主线和 Lite 主流程相关实现到 `toC/app/backend/`。
3. 迁 To C 前端时，优先区分“共享前端内核”和“移动端 Web 渠道实现”。
4. 再决定小程序与 App 版何时进入工作区。
5. 最后补测试、样本和 delivery 记录。

## 9. 当前结论

如果只以“恢复 To C 主线开发”为目标，旧仓库里真正需要首批迁入的内容并不算太多。

最重要的不是迁得快，而是先把下面这条边界守住：

`先迁 To C + V2 主线，不把 studio / ToB / V3 / 内部运维一起带进来。`
