## 1. 当前判断

截至当前这轮迁移，下面几项已经基本收口：

- mobile-web 上传 / loading / report / history 的最小真实联调主路径
- Lite / Pro 的最小 `create / status / report / upgrade` 闭环
- 浏览器本地文件 -> 后端上传 -> 运行时 `uploadAsset` 契约
- COS 真实上传接入
- Lite / Pro 报告的大部分固定内容模板化

这意味着下一阶段不该再把精力主要花在“继续清理报告模板硬编码”上，而应回到真正阻塞“迁移完成”的主功能。

## 2. 剩余主功能

### P0. 正式 Lite 生成链路替换迁移期占位内容

当前状态：

- Lite 已能真实创建、轮询、读取
- 但内容仍是迁移期规则驱动 + 模板驱动版本

完成标准：

- Lite 报告不再以迁移期占位逻辑为主
- 至少接回旧主线里当前仍有约束力的正式生成逻辑或 Prompt 编排主干

### P0. 正式 Pro 生成链路替换迁移期占位内容

当前状态：

- Pro `upgrade` 已能真实写入并读取
- 但内容仍不是旧主线完整正式 Pro 生成结果

完成标准：

- Pro 报告的失衡判断、根源分析、建议生成不再主要依赖当前迁移期占位拼装
- 能稳定覆盖当前产品定义中的 Pro 正式输出

### P0. 上传后图片生命周期治理

当前状态：

- `local` / `cos` 都已可用
- 当前仍保留本地临时文件，但已补齐最小生命周期元数据：
- 上传响应已返回 `image_local_expires_at`
- `create` 已透传并落库 `image_url / storage_backend / storage_key / image_local_expires_at`

完成标准：

- 明确图片保留时长、清理策略和运行时依赖路径
- 明确 `image_path / image_url / storage_key / image_local_expires_at` 的长期契约

### P1. structured schema 单独收口

当前状态：

- Lite / Pro 报告字段已经 richer
- 但 schema 仍主要散在 `orchestrator_v2.py`、前端结构映射和 types 里

完成标准：

- 后端 structured schema 有单独、清晰的定义入口
- 前端渲染顺序与字段契约不再隐式分散维护

### P1. 部署前配置与运行说明收口

当前状态：

- COS 已接入
- 腾讯云部署、备案域名、正式环境变量口径还没统一收成部署说明
- 已补充部署模板草案：`/Users/xinran/Downloads/dev/mindsync/projects/aimandala/docs/tasks/2026-04-05-腾讯云部署环境模板.md`
- 已补充腾讯云单机样例：`/Users/xinran/Downloads/dev/mindsync/projects/aimandala/deploy/tencent-cloud/`

完成标准：

- 给出最小可执行的生产部署配置清单
- 明确域名、COS、上传公开地址、后端环境变量、前端 API 地址的最终约束

## 3. 当前建议执行顺序

建议按下面顺序继续：

1. 正式 Lite 生成链路
2. 正式 Pro 生成链路
3. 图片生命周期治理
4. structured schema 收口
5. 部署说明收口

## 4. 当前不建议优先的事项

当前不建议再优先做：

- 继续为了“把所有文案都挪出代码”而细拆模板
- To B / Studio / V3 迁移
- 提前做大规模部署自动化
- 把 mobile-web 多端路由体系一次性重做

## 5. 收口结论

如果目标是“尽快把迁移完成”，当前真正的主阻塞已经不是页面交互，也不是报告模板层，而是：

1. Lite 正式内容链路
2. Pro 正式内容链路
3. 上传后图片的长期治理

后续建议围绕这三件事继续推进。
