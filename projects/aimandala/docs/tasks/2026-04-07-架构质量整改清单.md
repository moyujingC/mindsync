## 4. 架构上最该先拆的两个点

### 点一：先拆后端 `LayeredOrchestrator` 的“结构 schema + 报告装配”职责

为什么先拆这个：

1. 它已经同时承担检测、记录准备、Lite/Pro 生成、structured 组装、prompt preview、schema 校验和 safety 包装。
2. 现在改报告结构需要同时动后端、前端和类型，说明 schema 还不是独立边界。
3. 后续一旦正式 Lite / Pro 链路迁回，这个文件会继续变大，而不是自然变小。

本轮建议拆法：

1. 先不拆“生成链路”本身，先拆“结构契约”。
2. 新增一层独立入口，例如：
   - `app/core/pipeline/report_schema.py`
   - 或 `app/core/pipeline/report_contracts/`
3. 把下面三类内容从 `orchestrator_v2.py` 中移出去：
   - Lite / Pro structured schema 定义
   - prompt schema 校验
   - report response 组装规则

本轮完成标准：

1. 前后端对接 structured 报告时，有单独的后端权威入口。
2. `orchestrator_v2.py` 不再既是“生成器”又是“schema registry”又是“render assembler”。
3. 以后改报告字段时，可以先改一份明确契约，而不是顺着多个 helper 找。

### 点二：先拆 `mobile-web` 的“正式运行时”与“浏览器预览调试壳”

为什么先拆这个：

1. 当前 `browser-shell.tsx` 和 `runtime.tsx` 都很厚，而且都在处理上传兜底、轮询、历史回流、路由装配、preview/runtime 切换。
2. 现在 preview 壳很有用，但它已经开始和正式运行时共享过多页面级职责。
3. 如果不先拆，后面真实路由框架接入时，会继续把调试逻辑、宿主逻辑和产品逻辑混在一起。

本轮建议拆法：

1. 明确三层边界：
   - `shared/`: 业务语义与契约
   - `runtime/`: 正式 route -> loader -> app 装配
   - `preview-shell/`: 本地浏览器调试、fixture、联调辅助控件
2. 不再让 `mobile-web/index.ts` 对外整体 re-export `../shared`。
3. 把 preview 专属的状态标签、调试控件、fixture 回退说明集中到调试宿主层。

本轮完成标准：

1. 关闭 preview 后，正式运行时链路可以单独理解和维护。
2. `browser-shell.tsx` 不再承担正式产品语义。
3. 后续接真实路由框架时，替换的是宿主层，而不是整套页面流程。
