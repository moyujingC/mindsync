## 1. 当前状态

MVP 阶段已冻结服务器端自动写仓库能力。

当前确认：

1. `paperclip-heartbeat.timer`：`disabled / inactive`
2. `automation-maintenance.timer`：`disabled / inactive`
3. `paperclip-automation.service`：`active`
4. `Engineer`：`PAPERCLIP_SERVER_AUTOMATION_FREEZE=1`
5. `Test / QA`：`PAPERCLIP_SERVER_AUTOMATION_FREEZE=1`

这表示控制面仍可用，但服务器端自动写入链路不应继续执行。

## 2. 仍存在的历史现场

冻结只能阻止新增自动写入，不能清理历史脏状态。

当前远端仍存在：

### 2.1 `/opt/automation/app/mindsync`

```text
 M projects/aimandala/deploy/paperclip-automation/docker-compose.paperclip.yml
 M shared/tools/sync-paperclip-claude-local-model.sh
```

判断：

- 这是 observe-only checkout（只读观察工作区）里的历史脏状态
- 恢复任何自动巡检或升级前必须先分类

### 2.2 `/opt/paperclip/app/paperclip`

```text
canary/v2026.411.0-canary.7-3-ga692e37f-dirty
 M Dockerfile
 M packages/adapters/claude-local/src/server/test.ts
 M scripts/docker-entrypoint.sh
 M server/src/__tests__/claude-local-adapter-environment.test.ts
?? Users/
```

判断：

- 当前 Paperclip 主仓仍是 dirty canary
- 不能在这个状态下直接升级到 `v2026.428.0`
- 必须先决定这些改动是转正、备份，还是丢弃后重建

## 3. 恢复前必须完成

恢复服务器端任何自动写入前，必须完成：

1. 盘点 `/opt/automation/app/mindsync` 两个脏改的来源和保留价值
2. 盘点 `/opt/paperclip/app/paperclip` dirty canary 改动的来源和保留价值
3. 决定每个脏改的处理方式：
   - 转正进仓
   - 备份留档
   - 丢弃
   - 重建 checkout
4. 让 `/opt/automation/app/mindsync` 回到可解释状态
5. 让 `/opt/automation/app/mindsync-heartbeat` 同步到包含 `paperclip-multi-project-heartbeat.mjs` 的版本
6. 让只读 heartbeat 能以 `--apply 0 --strict 1` 成功运行
7. 让 execution health strict gate 通过
8. 用户明确批准临时解除 `PAPERCLIP_SERVER_AUTOMATION_FREEZE=1`

## 4. 当前不应做

当前不应：

1. 直接 `git pull` 远端脏 checkout
2. 直接 `git reset --hard`
3. 直接恢复 `paperclip-heartbeat.timer`
4. 直接恢复 `automation-maintenance.timer`
5. 直接升级 Paperclip 到 `v2026.428.0`
6. 直接让服务器端 agent 自动修复仓库

这些动作都可能掩盖现场或重新制造脏工作区。

## 5. 下一步建议

下一步应进入 observe-only checkout 治理：

1. 按 [2026-05-03-observe-only-checkout-治理实施计划.md](./2026-05-03-observe-only-checkout-治理实施计划.md) 盘点和归类
2. 先处理 `/opt/automation/app/mindsync`
3. 再处理 `/opt/paperclip/app/paperclip`
4. 最后再决定是否恢复只读 heartbeat

服务器端自动写入能力不作为 MVP 主链恢复目标。
