本轮输入已经明确：当前要推进的不是泛化“测试优化”，而是一轮围绕 `Web MVP` 上线前主链路的质量收口。

## 2. 范围

### 2.1 本轮要做

1. 先定义一轮上线前主链路验证与风险收口任务
2. 基于验证结果判断哪些问题需要进入修复
3. 收口与本轮直接相关的 `tasks / qa / delivery` 文档链

### 2.2 本轮不做

1. 不扩大成全面产品重定义
2. 不扩大成全仓文档重整
3. 不在未完成验证前预先列出大规模优化清单
4. 不把 `specs / architecture` 一并纳入本轮文档治理默认范围

## 3. 任务拆解

### 3.1 子任务 A：上线前主链路验证基线收口

- owner：`Test / QA`
- 需要产出：
  - 本轮主链路验证范围
  - 风险检查清单
  - 验证记录入口
- 完成标志：
  - 能明确回答“当前上线前还有哪些主链路风险”

### 3.2 子任务 B：验证后修复判定与必要修复

- owner：`Engineer`
- 前置条件：
  - 先有 QA 风险与验证结论
- 需要产出：
  - 需要立即修复的问题清单
  - 必要时的修复任务或修复交付
- 完成标志：
  - 能明确区分“上线前必须修”与“可后置”

### 3.3 子任务 C：文档收口

- owner：CEO / Orchestrator 或单独路由
- 需要产出：
  - 与本轮直接相关的 `tasks / qa / delivery` 缺失补齐
  - 当前入口文档的必要收口
- 完成标志：
  - 当前窗口 artifact 链可交接、可追溯

## 4. 风险

1. 如果没有先做验证范围收口，任务容易重新滑回泛化“优化”。
2. 如果先开大量修复任务，容易把上线收口变成无边界重构。
3. 如果把文档治理范围放大，容易打断当前主线推进。
4. 如果本轮不由 CEO 先收成一个总任务，下游 owner 可能会各自理解，导致再次混线。

## 5. 验证准备

进入执行前，至少要先明确：

1. 本轮主链路验证覆盖哪些页面、动作和风险点
2. 哪类问题一旦发现，应直接视为上线前阻塞
3. 哪类问题可以记录但不阻塞当前窗口
4. 文档收口至少要补哪些 artifact，才算形成可交接链路
