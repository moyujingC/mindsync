## 1. 决策作用范围

本决策只定义当前 MVP 的 Lite / Pro 版本关系、购买关系和升级边界。

本决策不再定义 Lite / Pro 的固定报告结构、固定字数、固定段落模块或固定内容层级。当前报告版本已作为 MVP 可接受版本，内容上线判断以 [MVP-当前上线口径.md](../specs/MVP-当前上线口径.md) 为准。

## 2. 版本关系

结论：**Pro 是 Lite 的升级，不能独立购买。**

用户路径：

```text
用户完成 Lite -> 查看 Lite 报告 -> 如愿意继续深入，触发 Pro 升级 -> 支付成功后查看 Pro 权益内容
```

这意味着：

1. 前端不提供独立 Pro 购买入口。
2. 后端在创建 Pro 升级订单前，必须校验用户已拥有对应画作的 Lite 权益。
3. 历史用户重新打开已有 Lite 报告时，也只能通过升级入口获得 Pro。
4. Pro 权益只绑定对应报告 / 画作，不允许跨 report_id 复用。

## 3. 定价

| 版本 | 当前价格 | 说明 |
|---|---|---|
| Lite | 9.9 元 | 当前入口价格 |
| Pro 升级 | 29 元 | 只能在 Lite 后升级 |
| Pro 独立购买 | 不提供 | 前端无独立入口，后端也不得创建有效独立订单 |

如果后续重新设计价格，应单独开新决策，不从历史价格讨论自动继承。

## 4. Lite 成立条件

Lite 必须是用户可接受的入口体验，不应表现成残缺、错误或空白交付。

当前不再要求 Lite 符合历史固定结构。上线前只检查：

1. 用户能正常看到报告内容。
2. 报告内容非空、可读。
3. 报告与本次画作 / 用户输入有关。
4. 报告不出现诊断、恐吓、治疗承诺、投资建议、未来预测或依赖诱导。
5. 报告结尾的 Pro 引导不制造焦虑，不暗示“不升级就无法理解自己”。

## 5. Pro 成立条件

Pro 必须是当前产品承诺的升级权益内容。

当前不再要求 Pro 符合历史固定结构。上线前只检查：

1. Pro 权益只对已升级用户展示。
2. Pro 内容非空、可读。
3. Pro 内容与本次画作 / 报告有关。
4. Pro 不出现诊断、恐吓、治疗承诺、投资建议、未来预测或依赖诱导。
5. Pro 支付成功后可恢复权益，不诱导重复付款。

## 6. 升级入口原则

Pro 升级入口应满足：

1. 只在用户已拥有对应 Lite 权益后出现。
2. 明确说明升级的是当前这份报告 / 画作。
3. 明确显示升级价 29 元。
4. 不使用焦虑转化文案。
5. 不打断用户阅读，不强制弹出，不阻断 Lite 报告完整阅读。

可用表达：

- “想继续看这份报告的更多内容，可以升级 Pro。”
- “Pro 会基于当前这幅画继续展开。”
- “升级 Pro · 29 元”。

避免表达：

- “你需要 Pro 才能真正了解自己。”
- “不升级就看不到关键问题。”
- “你的问题可能很严重。”

## 7. 权限与支付约束

必须满足：

1. 未购买 Lite 的用户不能查看 Lite 正文。
2. 未升级 Pro 的用户不能查看 Pro 权益内容。
3. 支付失败或取消不得解锁权益。
4. 支付成功但同步中时，应提示用户不要重复支付。
5. 已购买用户再次进入时，应恢复对应权益。
6. report_id / user_id 不匹配时，不得泄露报告内容、支付状态或 followup context。
7. 权限判断以后端为准，不能只依赖前端状态。

## 8. 不再保留的历史口径

以下历史口径已从当前决策删除，不再作为 MVP 上线依据：

1. Lite / Pro 独立购买。
2. 进门时让用户自行选择 Lite 或 Pro。
3. Pro 独立价格作为当前执行价。
4. Lite / Pro 固定报告层级。
5. Lite / Pro 固定字数范围。
6. 固定报告段落模块、根源层级或推导层级。

如果后续需要重新定义 Lite / Pro 内容差异，应重新分析并产出新 spec。
