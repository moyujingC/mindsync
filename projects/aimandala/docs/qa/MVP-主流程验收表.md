## 1. 验收对象

本表验收 Aimandala MVP 用户主流程：

```text
入口 -> 上传 / 提交 -> Lite 生成 -> Lite 报告 -> Pro 升级 -> 支付 -> Pro 报告 -> followup -> 刷新 / 重新进入 -> 异常兜底
```

本表只覆盖上线前主流程质量门，不替代专项验收表。支付权限、报告内容、followup 边界和异常文案仍需要分别形成专项记录。

## 2. 原始期望

用户能完成一次真实付费体验：

1. 进入产品后知道这是曼陀罗画作自我观察报告。
2. 能提交画作和必要信息。
3. 能获得 Lite 报告。
4. 能理解 Lite 是完整轻量交付。
5. 能在 Lite 报告中看到 Pro 升级价值。
6. 能完成 Pro 升级支付。
7. 能查看 Pro 报告。
8. 能围绕 Pro 报告向曼曼继续提问。
9. 任何失败状态都有可理解提示和下一步。

## 3. 本表结论口径

每个用例使用以下结论：

| 结论 | 含义 |
|---|---|
| pass | 实际结果符合预期，无阻塞问题 |
| warn | 用户侧可继续完成主流程，但存在需记录的非阻塞风险 |
| fail | 主流程被阻断，或存在支付 / 权限 / 安全高风险 |
| not_run | 尚未执行 |

主流程总评：

- **通过**：P0 全部 pass，P1 不影响付费与报告交付。
- **有条件通过**：P0 全部 pass，但有 P1 warn，需要记录 owner 和修复计划。
- **不通过**：任一 P0 fail。

## 9. 退回条件

出现以下任一情况，本主流程验收直接不通过：

1. 用户无法从入口走到 Lite 报告。
2. Lite 已付费但报告不可查看。
3. 未完成 Lite 的用户可以直接购买或查看 Pro。
4. Pro 支付成功后无法查看 Pro 或无法恢复权益。
5. 支付失败或取消后错误解锁 Pro。
6. 已付费用户被诱导重复支付。
7. 刷新 / 重新进入后丢失权益或报告。
8. followup 串报告、串用户或在 context missing 时生成无依据回答。
9. 报告或 followup 出现医疗诊断、恐吓、治疗承诺、长期依赖诱导。
10. 关键失败状态白屏或只显示技术错误。
