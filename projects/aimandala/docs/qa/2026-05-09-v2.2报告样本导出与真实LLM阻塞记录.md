## 人工初看

当前样本已经比早期“纯字段拼接”更进一步：

- 有开头命中感。
- 有画面依据区。
- 有三圈、颜色、五行、能量流动和卡点的过程链。
- Lite / Pro 能区分轻量判断和深层结构。
- QA 可以从最终报告倒查到每个中间过程。

但当前样本还没有达到最终报告标准：

- 用户可见报告仍有明显结构化拼接痕迹。
- 部分句子重复，例如“旧节奏尚未完全退场、新节奏又开始拉扯”多次出现。
- Pro 的“核心洞察表格”“根因链”仍像工程化产物，不像完整解读师表达。
- 部分术语虽然可接受，但解释还不够顺滑。
- 画面依据区还没有完全按“这个颜色/形状在这个位置如何形成关系”的自然观察方式展开。

因此，本轮样本适合作为 v2.2 知识链路与过程链基线，不适合作为最终用户可见文案。

## 真实 LLM 尝试结果

尝试命令：

```bash
# 先加载本机私有 env，不把 env 文件路径和密钥写入仓库文档
PYTHONPATH=projects/aimandala/toC/app/backend \
python3 projects/aimandala/toC/app/backend/scripts/export_knowledge_fixture_golden.py \
  --fixture-id toc-mvp-fixture-003 \
  --build-selector candidate:v2.2-theme-md \
  --version lite \
  --output-dir projects/aimandala/docs/qa/report-samples/2026-05-09-v22-markdown-runtime-llm-real-chain
```

失败结果：

```text
RuntimeError: chat_generation_failed_blocking:lite:empty_response
```

排查结果：

- 当前私有 env 中存在视觉评测相关 key。
- 当前私有 env 中没有 `AIMANDALA_LLM_BASE_URL`、`AIMANDALA_LLM_API_KEY`、`AIMANDALA_LLM_MODEL` 这组文字模型配置。
- 后端因此走 legacy GLM 默认文本模型，而不是 MVP 决策中的 `deepseek-v4-pro`。
- 最小 GLM 文本请求可成功返回 JSON，说明接口本身可用。
- 完整 Lite 报告长 prompt 生成返回空，不能作为真实报告样本。

## 追加诊断：Layer0 与报告文本生成分离

新增诊断脚本：

`projects/aimandala/toC/app/backend/scripts/diagnose_report_llm_generation.py`

诊断目标：

- 不跑完整导出，只定位 Lite / Pro 真实文字模型生成失败点。
- 保留 `last_error_detail`、`last_attempt_trace`、`chat_trace`、`prompt_chars`。
- 只写脱敏后的 endpoint / model / status，不写 API key。

本轮新增两份诊断证据：

- `projects/aimandala/docs/qa/report-samples/2026-05-09-v22-markdown-runtime-glm-real-chain/lite-diagnose.json`
- `projects/aimandala/docs/qa/report-samples/2026-05-09-v22-markdown-runtime-glm-real-chain/lite-diagnose-with-qwen-vision.json`

第一份诊断把 GLM 文本模型同时作为默认 vision 任务模型使用，结果在 Layer0 视觉证据阶段失败：

```text
layer0_generation_failed_blocking:layer0_vision_request_failed
HTTP 400 / model=glm-4
```

这个结果说明：真实链路里必须显式区分 `chat` 和 `vision` 两类模型配置。不能只设置默认 `AIMANDALA_LLM_MODEL=glm-4`，否则 Layer0 视觉证据会误用文本模型。

第二份诊断显式设置：

- `chat`: GLM `glm-4`
- `vision`: Qwen `qwen-vl-max-latest`
- `vision_fallback`: 豆包 `ep-20260316095322-94wf5`

结果 Layer0 视觉证据通过，但 Lite 文字生成失败：

```text
chat_generation_failed_blocking:lite:empty_response
HTTP 400 / model=glm-4
prompt_chars=1002282
prompt_preview_truncated=true
```

这说明当前主要阻塞已经不是 v2.2 知识库运行时，也不是 Layer0 视觉证据链，而是 Lite 报告文字生成 prompt 过大。当前单次 Lite prompt 约 100 万字符，已明显超出常规 chat-completions（聊天补全接口）稳定输入范围。模型返回 400 后，运行时把空响应归类为 `chat_generation_failed_blocking:lite:empty_response`。

因此，后续不能继续只换模型重试。即使换成 DeepSeek，也应该先重构报告生成输入：

- 不把完整 Layer0 / 全量知识投影直接塞进最终报告 prompt。
- 先生成或选择一份 compact interpretation packet（压缩后的解读包）。
- Lite / Pro 报告 prompt 只读取必要字段、命中的知识条目、视觉摘要和主题上下文。
- Pro 可以拆成多个小步骤生成，再做最终整合，避免一次请求承担全部知识、推理和成文。

## 当前阻塞

要生成真正可评估的真实文字模型报告，需要同时处理两件事。

第一，补齐本地 / staging 文字模型环境变量：

```bash
AIMANDALA_LLM_BACKEND=openai_compatible
AIMANDALA_LLM_BASE_URL=<text-openai-compatible-url>
AIMANDALA_LLM_API_KEY=<text-api-key>
AIMANDALA_LLM_MODEL=deepseek-v4-pro
AIMANDALA_LLM_CHAT_MODEL=deepseek-v4-pro
```

如果经 RelayHub，则 `AIMANDALA_LLM_BASE_URL` 应指向 `prod-relay/aimandala` 的 OpenAI-compatible 入口。

第二，重构报告生成 prompt 输入。当前 v2.2 prompt 尺寸已经达到 `prompt_chars=1002282`，这不是正常的单次报告生成输入规模。即使文字模型配置正确，也不能把这个尺寸当作可接受方案。

## 下一步建议

1. 先实现 compact interpretation packet，把 Stage 00-12 的流水线结果压缩成最终报告所需的最小输入。
2. 再让 Lite / Pro prompt 读取 compact packet，而不是读取完整 Layer0 和全量知识投影。
3. 补本地私有文字模型 env，不把视觉评测 env 当成报告文字模型 env。
4. 用 `deepseek-v4-pro` 跑 `toc-mvp-fixture-003` 的 Lite / Pro 各一份真实报告。
5. 对比本轮确定性样本、真实 DeepSeek 样本和旧版报告，确认报告重建重点。
6. 如果真实 DeepSeek 仍不稳定，需要继续拆分 Lite / Pro 生成步骤或放宽 JSON 合同，再继续文案优化。
