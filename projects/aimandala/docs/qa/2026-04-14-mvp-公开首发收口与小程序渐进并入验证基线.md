## 1. 验证对象

本次验证对象包括三部分：

1. `Web MVP` 公开首发前的质量门
2. 小程序 worktree 渐进并入 `main` 的批次验证规则
3. 本轮文档治理补漏是否形成最小闭环

## 2. 目标行为

### 2.1 Web MVP

- 固定样本不再命中 fallback
- Web 主链路自动化与 smoke 可重复通过
- 手机端人工主路径完整可走通
- 当前公开入口文档与实际阶段门一致

### 2.2 小程序渐进并入

- 未来并入按固定批次进行，而不是整支直并
- 每一批的验证口径明确，不影响当前 Web 主链

### 2.3 Artifact 治理

- 本轮存在正式 `task`
- 本轮存在正式 `qa basis`
- 本轮存在正式 `delivery`
- 目录 README 不再把明显历史材料当默认入口

## 3. 质量门

### 3.1 自动化

必须全部通过：

```bash
pytest -q projects/aimandala/toC/app/backend/tests/unit
npm --prefix projects/aimandala/toC/app/frontend test
npm --prefix projects/aimandala/toC/app/frontend run typecheck
npm --prefix projects/aimandala/toC/app/frontend run build:mobile-web
python3 projects/aimandala/toC/app/backend/scripts/validate_knowledge_workbench.py
python3 projects/aimandala/toC/app/backend/scripts/run_knowledge_evals.py --build-selector current
```

### 3.2 指标

`run_knowledge_evals.py --build-selector current` 必须满足：

- `fixture_fallback_count = 0`
- `structured_missing_count = 0`
- `regression_flag_count = 0`

`warning` 样本允许命中，但应为预期命中，不应表现为异常噪音。

## 4. Smoke 与人工验收

### 4.1 Smoke

必须记录：

- `dev` basic smoke
- `prod` basic smoke
- `prod` 深烟测

### 4.2 人工主路径

必须至少覆盖一次：

1. `upload`
2. `detect`
3. `report-choice`
4. `lite/pro`
5. `history`
6. `reopen`

## 5. 小程序渐进并入验证矩阵

### 5.1 批次 1-2

- `frontend test`
- `typecheck`
- `build:mobile-web`
- `mobile-web` 页面行为不退化
- 批次 1 不引入微信、小程序宿主、支付、session exchange
- 批次 2 的 shared UI 不依赖路由、上传、支付、登录

### 5.2 批次 3

- `miniapp` 预览壳静态渲染
- 不引入真实微信运行时依赖
- 不影响当前 Web 主链
- 不改当前公开产品口径

### 5.3 批次 4

- `backend unit / contract tests`
- `/api/v2/miniapp/*` 只做向后兼容加法
- 不影响当前 Web 主链
- 需要有清晰开关或环境边界说明

### 5.4 批次 5

- 单独灰度验证
- 单独 `verification / delivery`
- 不纳入当前 Web 首发放行条件
- 必须单独补 `spec / task / qa / delivery`

## 6. Artifact 治理检查点

在进入代码实现前，先完成以下检查：

- 本轮重要工作是否已有 `task`
- 是否已有对应 `qa basis`
- README 默认入口是否指向当前有效材料
- 是否仍存在明显错误的 `depends_on`
- 当前准备纳入默认入口的文档，其状态是否合理

## 7. 当前不在本轮验证范围

- 小程序真实微信 live 能力
- 全量旧文档重分级
- 全量旧 spec 重写
