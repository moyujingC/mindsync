## 1. 验证对象

本基线服务于“报告链路保真重构”整条主线，不是单个 patch 的临时验证清单。

它验证的是：

1. 源资料是否被正确消费为 runtime evidence
2. narrative / prompt 是否真正消费了 evidence，而不是继续消费 projection
3. Lite / Pro 合同与前端承接是否同轮收口
4. fallback 和 drift 是否变得可见、可统计、可定位

## 2. 总体通过门槛

本轮总通过门槛固定为：

1. 不能再出现“主要报告段落无法说明来自哪条知识链”的情况
2. `Layer 0` 必须稳定区分：
   - `visual_facts`
   - `knowledge_hits`
   - `rule_evaluations`
3. Lite / Pro 的主题差异必须通过固定主题样本稳定拉开
4. fallback 允许存在，但必须结构化可见
5. 新结果合同和前端渲染必须同轮通过，不允许后端先漂、前端滞后

## 3. 验证矩阵

### 3.1 后端自动化

每个批次至少覆盖：

1. `Layer0Assembler`
2. `ImbalanceService`
3. `NarrativeContextService`
4. `ReportPromptPreviewBuilder`
5. `report_contracts`
6. orchestrator / pipeline 回归

### 3.2 前端自动化

至少覆盖：

1. 新报告合同类型
2. 结果页渲染逻辑
3. debug 面板对 trace / fallback / fidelity 的展示

### 3.3 样本与 golden

固定至少维护 4 组链路：

1. 四步法样本
2. 一个主题特化样本
3. 一个颜色 / 形状样本
4. 一个疗愈 / 失衡样本

### 3.4 drift / fidelity 检查

至少检查：

1. 主要报告段落是否能追到 evidence trace
2. 是否存在隐形 fallback
3. fidelity flag 是否与实际压缩点一致

## 4. 批次级验证重点

### 4.1 Batch A

重点验证：

1. `Layer 0` 新结构是否完整
2. 四步法 / 三元结构 / 失衡中间判断是否进入 evidence 层
3. fallback 是否结构化暴露

### 4.2 Batch B

重点验证：

1. `knowledge_skeleton` 是否由 evidence 生成
2. theme context 是否不再依赖 projection-first 摘要
3. narrative plan 是否没有伪造新知识层

### 4.3 Batch C

重点验证：

1. 新结果合同是否被前端完整承接
2. debug payload 是否能直接做 trace 检查
3. Lite / Pro 结果差异是否真实来自深度变化，而不是临时文案差异

### 4.4 Batch D

重点验证：

1. 固定样本是否通过
2. README 和交付链是否收口
3. 剩余 fallback / drift 风险是否被明确记录

## 5. 默认验证方式

后续每批应至少执行：

1. 对应后端单测
2. 对应前端测试
3. 固定 fixture / golden 检查
4. 必要的脚本或 debug 验证

如果本批只改文档、不改代码，应至少执行：

1. 仓库内引用有效性检查
2. 入口索引检查
3. 不再依赖旧路径的搜索检查

## 6. veto 条件

出现以下任一项，本轮或该批次不得判定通过：

1. 主结果大段内容无法追溯来源
2. `Layer 0` 仍混淆 evidence 与 summary
3. 主题样本拉不开差异
4. fallback 发生但未被结构化标记
5. 新合同已改但前端未同步通过

## 7. 当前说明

本基线是这轮重构的总 QA 入口。

后续每一批仍应补：

1. 具体执行记录
2. 自动化输出摘要
3. 样本观察项
4. 是否允许进入下一批
