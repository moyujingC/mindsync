## 1. 核验结论

当前仍不满足升级到 `v2026.529.0` 的前置条件。

原因不是 `Paperclip` 服务不可用，而是升级前治理状态仍存在阻断：

1. 当前运行代码仍是 dirty canary（脏的预发布基线）
2. `paperclip-heartbeat.service` 当前持续失败
3. execution health strict gate（执行健康严格门禁）仍检出活跃阻断项
4. 主镜像区和 `Paperclip` 主仓 checkout 都不是干净状态

因此本轮结论仍是：暂缓升级，先修复巡检入口、workspace materialization（工作区实例化）阻断和 checkout 脏状态；随后再按 `v2026.529.0` 目标重新进入受控验证。

## 2. 本轮与旧 `v2026.428.0` 核验记录的关系

这份文件不是否定旧记录，而是接替旧记录成为当前默认入口。

相比旧 `v2026.428.0` 核验，本轮新增关注点包括：

1. structured interactions（结构化交互）
2. document locks（文档锁）与 inline annotations（内联批注）
3. accepted-plan exact-once decomposition（计划只分解一次）
4. workspace finalize gates（工作区收尾闸门）

在前置阻断仍未解除前，这些新增项暂不进入真实升级验证，只先作为后续必须验证的检查项保留。

## 3. 当前阻断摘要

截至当前仓内已记录状态，主要阻断仍是：

1. 远端 `Paperclip` 主仓为 dirty canary
2. heartbeat 服务缺少关键脚本，无法稳定运行
3. strict gate 检出 `execution_workspace_policy_not_materialized`
4. observe-only checkout（只读观察工作区）不干净

这些阻断在进入 `v2026.529.0` 升级窗口前必须先清掉，否则即使切到新版本，也无法证明问题是升级引起还是旧基线残留。

## 4. 升级前必须补齐的最小前置项

### 4.1 must

1. 修复 `/opt/automation/app/mindsync-heartbeat` 缺少 heartbeat 脚本的问题
2. 让 `paperclip-heartbeat.service` 恢复成功运行
3. 处理 strict gate 当前活跃阻断项
4. 清理或正式解释 `/opt/automation/app/mindsync` 的脏改
5. 清理或正式解释 `/opt/paperclip/app/paperclip` 的 dirty canary 状态

### 4.2 should

1. 显式记录可恢复的数据库备份文件
2. 对 local execution routing 历史样本做分类，区分历史残留与当前仍会误路由的问题
3. 再次执行 adapter 最小探测，确认 `codex_local` / `claude_local` / `pi_local` 不只是 `idle`，而是真的可执行

## 5. 进入 `v2026.529.0` 验证后必须新增的检查项

1. 至少一轮 structured interaction 验证
2. 至少一轮 document lock + inline annotation 验证
3. accepted plan 不重复分解子任务
4. blocker 未解除前不提前唤醒 dependents
5. finalize 后的 workspace 状态与宿主机 worktree 状态一致

## 6. 当前结论

当前不建议进入 `v2026.529.0` 运行时升级。

下一步应先完成：

1. heartbeat 修复
2. strict gate 清障
3. dirty checkout 处理
4. 再重新跑一次升级前核验
