## 1. 这份文档要解决什么问题

当前 `一镜一梳` 在实现层看起来像一个固定的“上传图片 -> 生成解读报告”产品。

但从项目定位、旧仓库产品文档和多智能体设计来看，它的真实目标更接近：

- 一个围绕曼陀罗创作、解读、对话陪伴与疗愈实践展开的平台
- 一条长期的疗愈旅程，而不是一次性报告生成工具

这份文档的作用，是先把平台级定义写清楚，避免后续继续把当前 To C MVP 主路径误写成整个产品的最终形态。

## 2. 平台重新定义

`一镜一梳` 不再被定义为“AI 曼陀罗解读工具”，而应重新定义为：

**一个以曼陀罗为核心媒介的数字疗愈平台。**

平台的核心目标不是尽快生成一份报告，而是帮助用户完成以下连续过程：

1. 看见自己
2. 表达自己
3. 理解自己
4. 陪伴自己
5. 调整自己
6. 持续成长

因此：

- `解读` 是平台中的第一核心能力，但不是平台本身
- `报告` 是平台中的一种输出，但不是唯一中心对象
- `上传主路径` 是当前 MVP 入口，但不是未来唯一入口

## 3. 平台的核心价值主张

平台级价值主张建议收束为三句话：

1. 帮助用户通过曼陀罗看见当下状态
2. 帮助用户把一次解读延伸为持续的陪伴与练习
3. 帮助用户把“内容消费”变成“旅程参与”

与此对应，平台的长期能力不应只围绕“多出几页报告”，而应围绕：

- 觉察
- 解读
- 对话
- 引导
- 实践
- 复盘

## 4. 平台的核心对象

如果按平台来设计，核心对象不应只有 `interpretation`。

建议平台级核心对象至少包括：

1. `User`
   - 用户及其长期旅程归属
2. `MandalaWork`
   - 用户的一次创作作品或一次上传作品
3. `Interpretation`
   - 对作品的结构化解读结果
4. `Conversation`
   - 围绕作品、报告或情绪状态展开的连续对话
5. `HealingPlan`
   - 个性化练习、节奏安排与跟进计划
6. `HealingJourney`
   - 把作品、解读、对话、计划和进展串起来的上位对象

建议把 `HealingJourney` 视为平台级第一对象；其他对象是旅程中的节点或产物。

## 5. 平台级用户任务

从平台视角，用户不是只想“买一份解读”。

更完整的用户任务可拆成五类：

1. 我想知道我现在处于什么状态
2. 我想理解这幅作品在表达什么
3. 我想有人陪我继续聊下去
4. 我想知道接下来可以做什么练习
5. 我想持续记录自己的变化

这意味着平台必须支持的不是单一“交易流”，而是至少五种任务流。

## 6. 平台的能力边界

建议把平台能力明确拆成五个能力域：

### 6.1 Interpretation

负责：

- 上传作品
- 图像分析
- 三圈检测
- Lite / Pro 解读生成
- 报告查看与历史记录

这是当前最成熟、最接近上线的能力域。

### 6.2 Healing Conversation

负责：

- 围绕报告内容继续追问
- 情绪支持和温和陪伴
- 结合知识库进行解释
- 风险识别与安全提示

这对应旧仓库中最先落地的 `HealingAgent` 思路。

### 6.3 Drawing Guidance

负责：

- 引导用户开始绘画
- 陪伴用户边画边觉察
- 提供实时提示和反馈
- 承接“陪你画”场景

### 6.4 Healing Planning

负责：

- 基于当前状态生成练习建议
- 组织 7 天 / 21 天实践计划
- 提醒、反馈、复盘与再调整

### 6.5 Journey Orchestration

负责：

- 判断用户当前更适合进入哪个能力域
- 把解读、对话、计划、回访串成一条旅程
- 决定平台首页与历史页如何组织内容入口

## 7. 当前 MVP 与平台愿景的关系

当前 To C MVP 仍然有效，但它必须被重新解释为：

- `Interpretation` 能力域的第一个正式用户入口
- 平台的“第一步”，而不是平台全部

当前 MVP 默认覆盖：

1. 上传作品
2. 三圈检测
3. 生成 Lite 报告
4. 查看历史记录
5. 进入 Pro 报告
6. 围绕当前 Pro 报告继续进行 AI 问答

当前 MVP 明确不覆盖：

1. 独立的长期对话陪伴入口
2. 绘画过程引导
3. 个性化疗愈计划
4. 完整的疗愈旅程主页

这些不是被否定，而是被推迟到后续阶段。

## 8. 当前不应再写死的产品结论

为了避免把平台重新做窄，下面这些结论当前都不应再被写成“永久真理”：

1. 用户必须先上传，再进入平台
2. 用户第一次体验只能先走 Lite，再看 Pro
3. 报告页是平台最核心页面
4. 历史页只是报告列表
5. 平台首页只是营销 Landing 页
6. 一切能力都必须从解读入口开始

这些都可以是当前 MVP 的默认路径，但不应成为平台的最终定义。

## 9. 平台首页应承接什么

如果按平台视角重做首页，它不应只是“劝用户开始上传”的单一漏斗页。

平台首页未来至少应具备四类入口：

1. 解读我的作品
2. 跟我一起画
3. 和我聊聊
4. 开始疗愈计划

同时首页还应能展示：

- 最近一次旅程节点
- 最近一次作品或报告
- 当前建议的下一步动作
- 历史进展摘要

## 10. 平台的商业边界

当前阶段不在这份文档中重写完整商业模式，但要先明确边界：

- `Lite / Pro` 只是当前 `Interpretation` 能力域下的交易层设计
- 未来平台可能存在：
  - 单次购买
  - 计划订阅
  - 人工陪伴服务
  - 疗愈师协作服务

因此定价模型不应主导平台架构；它应挂在能力域或服务层之上，而不是反过来定义整个平台。

## 11. 对前端设计的直接约束

这份平台定位对前端有四条直接约束：

1. `mobile-web` 不能被当成产品本体，只能是一个渠道实现
2. 当前页面层不能继续承担平台级业务定义
3. 前端共享层必须围绕“旅程与能力对象”设计，而不是围绕当前几页 UI 设计
4. 当前 UI 即使继续还原旧版，也只能作为 `Interpretation` 能力域的渠道皮肤

## 12. 待决问题

本轮先不拍板，但后续必须单独确认：

1. 平台首页是否先承接多入口，还是先维持解读入口为主
2. `HealingJourney` 是否在后端成为显式对象
3. `Conversation` 与 `HealingPlan` 是否作为第二阶段正式能力域进入 Monorepo 主线
4. To B / 疗愈师协作能力是否属于同一平台对象，还是未来拆分为新对象

## 13. 当前建议

建议从现在开始统一口径：

- 对外：`一镜一梳` 是曼陀罗疗愈平台
- 对内：当前上线主线是该平台的 `Interpretation MVP`，其中 `Pro` 报告内置 AI 问答
- 对实现：先做清晰的能力分层，再决定每个渠道如何承接

## 14. 这份草案不覆盖什么

这份文档不直接回答：

- 多智能体如何落代码
- 前后端目录如何重排
- 当前页面怎样改版
- Lite / Pro 具体如何收费

这些内容分别交给后续的架构草案、演进路线草案和实现方案处理。
