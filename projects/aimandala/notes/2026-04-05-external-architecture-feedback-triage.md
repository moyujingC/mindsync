## 1. 结论先行

这批外部建议总体质量是高的，但**不能整包并入当前执行范围**。

当前建议采用下面的处理原则：

1. 与现有共识一致、且能降低后续返工的建议，吸收进 handoff
2. 会明显扩大当前 MVP 范围的建议，保留为后续阶段讨论
3. 会诱发过度工程化的建议，只保留原则，不立即落为结构或工程任务

一句话取舍：

**吸收“边界澄清”和“最小护栏”，暂缓“新增大能力域”和“基础设施先行”。**

## 2. 建议采纳的部分

### 2.1 旅程层与编排能力的边界澄清

这条建议值得采纳。

当前建议明确为：

1. `旅程层`
   - 定义旅程阶段
   - 定义状态含义
   - 定义阶段间的语义跃迁规则
2. `Journey orchestration`
   - 基于旅程规则做下一步推荐
   - 负责最小跳转判断
   - 属于执行与编排层，而不是纯语义定义层

这样可以避免“旅程”既像模型又像调度器的混淆。

### 2.2 能力域间交互协议

这条建议值得采纳，但当前只做最小版。

当前最需要明确的不是完整协议体系，而是：

1. `Interpretation` 如何把报告上下文交给 `Pro report chat`
2. 未来 `Conversation` 独立后，如何继续复用当前报告上下文
3. 上下文对象最少包含哪些字段

当前建议只先定义：

1. 报告摘要
2. 当前作品摘要
3. 本次解读摘要
4. 可引用的关键段落或主题标签

先不要扩展成完整跨能力总线。

### 2.3 Journey 最小对象提前落地

这条建议可以采纳，但要加限制。

可采纳的部分是：

1. 尽早形成 `Journey` 的最小对象草案
2. 避免后续 Conversation 接入时重新命名和重做语义边界

限制条件是：

1. 当前先允许它停留在文档和应用层对象
2. 不要求立刻变成后端持久化数据库大对象
3. 不因此触发大规模接口改造

### 2.4 MVP 阶段轻量埋点

这条建议值得采纳。

当前若成本可控，建议只做最小埋点：

1. 报告页停留时长
2. AI 问答入口点击率
3. 提问发起率
4. 报告分享或升级相关点击

目的不是建设分析平台，而是帮助判断：

1. `Pro report chat` 是否真有使用价值
2. 后续 `Conversation` 是否值得独立成长

## 3. 建议暂缓的部分

### 3.1 新增三大能力域

外部建议提出：

1. 安全与风险管控能力域
2. 用户成长沉淀能力域
3. 平台运营能力域

这些方向本身合理，但**当前不建议作为正式 capability 域并入主结构**。

原因：

1. 当前最紧迫目标仍然是 `Interpretation MVP` 上线
2. 这些更像跨域支撑能力或运营能力，不是用户当前直接感知的主能力入口
3. 现在把它们都命名成一级能力域，会让平台图过早膨胀

当前更稳妥的做法是：

1. 把 `安全与风险管控` 视为跨能力横切约束
2. 把 `成长沉淀` 视为后续数据与用户资产层议题
3. 把 `平台运营` 视为后台或运营体系议题

它们都重要，但不应抢占当前 capability 结构的中心位置。

### 3.2 Conversation 并行启动

这个建议方向可以理解，但当前不建议把它变成并行工程线。

当前更稳妥的口径是：

1. `Conversation` 的产品边界可以提前设计
2. 但实现优先级仍晚于 `Interpretation MVP` 收口
3. 当前 AI 问答先作为 `Pro` 报告内置能力落地

否则很容易把当前 MVP 再次拉散。

### 3.3 商业化灰度能力

这个建议应暂缓。

原因很简单：

1. 当前最核心的是产品闭环和体验可上线
2. 价格分层和地域灰度是后续增长优化议题
3. 现在提前设计容易把交易系统复杂度拉高

## 4. 当前不建议直接采纳的部分

### 4.1 立刻引入 V2 / V3 并行接口策略

“保留 V2，新增 V3 并行防腐层”是成熟系统里常见做法，但当前不建议直接变成既定路线。

原因：

1. 当前代码规模和上线阶段还不足以证明必须上版本并行策略
2. 如果没有明确兼容压力，版本化很容易先带来额外维护成本
3. 当前更需要的是清晰边界，而不一定是新 API 版本号

当前更稳妥的原则是：

1. 保持现有线上契约稳定
2. 新边界先在内部模块和应用层抽象
3. 只有当外部契约真的需要分叉时，再决定是否引入 `V3`

### 4.2 在报告页加入“未来能力预告”

这条建议不一定错，但当前不建议作为默认动作写进架构口径。

原因：

1. 这属于产品策略与转化文案问题
2. 它不应该反向驱动当前架构设计
3. 如果体验尚未稳定，过早预告未来能力可能增加认知噪音

## 5. 对待决问题的当前建议答案

### 5.1 平台首页是否先承接多入口

当前建议：

1. 先维持解读入口为主
2. 当前不急着做多入口平台首页

### 5.2 HealingJourney 是否成为显式对象

当前建议：

1. 是，先形成最小显式对象
2. 但先停留在文档和应用层
3. 暂不要求立刻成为重型后端核心实体

### 5.3 Conversation 与 HealingPlan 是否进入主线

当前建议：

1. `Conversation` 先作为下一阶段正式能力设计对象
2. `HealingPlan` 继续放在再下一阶段

### 5.4 To B / 疗愈师协作是否纳入当前平台对象

当前建议：

1. 先不纳入当前 To C 主线平台定义
2. 待 To C 主链路稳定后再评估是否拆成新对象

## 6. 这次外部建议真正带来的补强

如果要把这批建议压成对当前最有价值的三点，应该是：

1. 更明确地区分旅程语义层与编排执行层
2. 尽早定义 `Interpretation -> Pro report chat -> Conversation` 的上下文接缝
3. 用最轻量的埋点验证 AI 问答是否值得长成独立能力

## 7. 从 Claude Code 架构可吸收的部分

Claude Code 的 `skills/` 架构对当前项目确实有启发，但当前建议只吸收它的**组织思想**，不吸收它的**完整插件机制**。

### 7.1 建议吸收

当前建议吸收三点：

1. `Capability Registry`
   - 作为能力清单和能力入口的统一注册表
   - 用来回答“当前有哪些能力、哪些已启用、哪些可进入”
2. 配置与实现适度分离
   - 能力元信息可以独立描述
   - 但当前只需要最小元信息，不需要完整插件配置体系
3. 能力边界独立
   - `Interpretation / Conversation / Planning / Drawing` 应保持独立边界
   - 便于未来按能力演进，而不是绑死在某个页面流里

### 7.2 当前不建议吸收

当前不建议直接引入下面这些做法：

1. 插件系统化
   - 当前 capability 不是插件 marketplace
   - 不需要生命周期管理、动态发现、版本兼容治理
2. 软链接能力包
   - 用符号链接复用外部能力包会增加仓库理解和调试复杂度
   - 当前复用优先通过普通模块抽取，而不是文件系统技巧
3. 每个能力都配完整 `capability.config.json`
   - 当前如果上完整配置驱动，维护成本会超过收益
   - 先保留轻量 metadata 即可
4. 统一 `initialize/execute/health` 插件接口
   - 这个抽象对成熟插件平台合理
   - 但对当前 MVP 来说过早，会把不同能力硬拉到同一执行模型

### 7.3 当前更合适的落地方式

如果要落地 Claude Code 启发，建议只落到下面这个力度：

1. 保留 `CapabilityRegistry` 作为应用层对象
2. 每个 capability 当前只声明最小 metadata：
   - `id`
   - `status`
   - `availableChannels`
   - `requires`
   - `canEnter(snapshot)`
3. 复用研究或共享能力时，优先走普通代码模块依赖
4. 等 `Conversation` 真正独立、能力数量明显增加后，再评估是否需要插件化

一句话口径：

**借鉴注册表，不借鉴插件平台。**

## 8. 当前建议同步到 handoff 的口径

下一位继续工作时，可以默认采用下面的补充口径：

1. 当前主线不变，仍是 `Interpretation MVP`
2. 外部建议已吸收为“边界更清晰、护栏更明确”
3. Claude Code 的启示当前只吸收 `Capability Registry` 思路，不引入插件系统、软链接能力包或完整配置驱动
4. 当前不因为这些建议而扩大 capability 数量或重做基础设施
