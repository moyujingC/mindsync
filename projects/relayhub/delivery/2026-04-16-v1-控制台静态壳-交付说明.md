这份文档用于把 `RelayHub` 控制台静态壳首轮实现结果交给下一棒实现者。

它回答三件事：

1. 本轮已经落了什么
2. 还没有落什么
3. 下一阶段应从哪里继续

## 1. 本轮已交付内容

已新增前端工作区：

- `projects/relayhub/console/`

当前实现内容包括：

- `React + Vite + TypeScript` 独立前端骨架
- 顶层布局壳与 9 个一级导航入口
- 4 个核心页面：
  - `Dashboard`
  - `Environments`
  - `Providers`
  - `Eval`
- 5 个占位页：
  - `Routes`
  - `Usage`
  - `Policies`
  - `Runs`
  - `Settings`
- 覆盖正常 / 异常 / 无数据 / 越界风险 / 已生成建议的本地 fixtures

## 2. 本轮明确保持不做

当前仍未实现：

- 真实 Relay API client
- 真实鉴权
- 真实数据库
- 真实配置编辑
- 真实路由保存与发布
- 真实 benchmark 调度

也就是说，当前交付物是“内部运营台静态壳”，不是“真实控制面”。

## 3. 当前代码结构

当前前端结构已落为：

- `console/src/components/`
  - 共用布局、分区、状态块、空态
- `console/src/fixtures/`
  - 本地假数据与状态样本
- `console/src/pages/`
  - 核心页面与占位页
- `console/src/styles.css`
  - 统一视觉变量与页面样式

## 4. 下一阶段建议切入点

下一棒默认不要再讨论：

- 控制台落在哪个目录
- 第一版先做哪些页面
- 前端用什么技术路线

下一阶段建议直接从下面顺序继续：

1. 把 fixtures 抽象成更稳定的 view model
2. 为 `Environments` 详情 tabs、`Eval` 子页和 `Providers` 详情补独立 URL
3. 接入只读 mock API 或本地 JSON server
4. 再决定真实控制台后端契约

## 5. handoff 提醒

下一棒继续实现时，必须保持以下硬边界不被改写：

- `RelayHub` 是公司级 capability，不挂到单一产品前端
- `dev-relay` 可接第三方中转
- 心理疗愈生产版只允许国产模型
- 第三方中转不进入心理疗愈生产用户数据主链路
- 控制台 v1 仍是内部运营台，不是公开产品台，也不是可写控制面

## 6. 一句话结论

当前已经把控制台“放哪里、先做哪些页面、用什么前端路线”这三件事落成正式代码与交付物，下一棒可以直接进入静态壳深化或只读数据接入，而不需要再回到项目边界讨论。
