这份文档定义 `RelayHub` 在进入实现前必须对齐的目标行为、验收标准和最小验证口径。

当前还没有代码实现，因此本文件优先定义人工验证基线，而不是自动化测试细节。

## 1. 目标行为

v1 应满足以下目标行为：

1. 公司内存在唯一正式的 capability 对象定义
2. 公司侧入口、项目工作区入口和正式 artifact 之间能形成稳定 handoff
3. `dev-relay`、`prod-relay/<product>`、`eval-sidecar` 三类运行形态边界清晰
4. 心理疗愈应用生产版 provider 约束被明确写成硬边界
5. 部署职责在本地、automation、production 三层之间明确分离

## 2. 验收标准

### 2.1 文档完整性

必须满足：

- 注册表中存在 `RelayHub` 的唯一正式对象记录
- 公司侧入口和项目工作区入口互相可达
- 项目工作区中存在 `PROJECT`、`spec`、`task`、`qa` 四类正式 artifact

### 2.2 运行形态边界

必须满足：

- `spec` 中明确写出 `dev-relay`、`prod-relay/<product>`、`eval-sidecar`
- `spec` 中明确区分开发版、生产版和评测版的用途
- `task` 中没有把生产策略与开发实验混写

### 2.3 provider 约束

必须满足：

- 开发版允许第三方中转
- 心理疗愈应用生产版只允许国产模型
- 第三方中转不进入该生产版的用户数据主链路

### 2.4 隐私与日志约束

必须满足：

- 生产版不默认记录敏感正文
- 生产版不把 prompt / response 自动发送到日志、监控或错误上报平台
- 文档中明确禁止把开发版观测策略直接复用于生产

### 2.5 部署分层

必须满足：

- 本地只承担开发、调试、实验
- `4G / 4核` automation 节点承担旁路评测、探活、日报与健康检查
- `4G / 8核` 生产机承担公司级主 Relay 和生产版 relay

## 3. 环境与部署验证口径

在进入实现前，至少要有人工核对以下问题：

1. 现有服务器分工是否与文档一致
2. automation 节点是否仍然承担大量 Paperclip、runner、CI 任务
3. 将主 Relay 放到 automation 节点是否会扩大故障域
4. 将评测 sidecar 与主 Relay 分离是否已经成为明确决策

这些问题在当前阶段以文档校验为主，不要求代码验证。

## 4. 关键边界测试

后续进入实现前，至少要准备下面这些边界测试用例：

### 4.1 开发版

- 能接第三方中转
- 能接国产模型
- 能为 `Claude Code`、`Codex` 提供统一入口
- 能记录 usage、延迟、错误和 streaming 完整性指标

### 4.2 生产版

- 若配置包含第三方中转，应视为违反生产边界
- 若默认记录正文，应视为违反隐私边界
- 若将开发版 provider 白名单复用到生产，应视为违反生产边界

### 4.3 评测 sidecar

- sidecar 故障不应阻断主 Relay 正常存在
- 评分板、日报和探活职责不应与主 API 进程耦合

## 5. 当前质量门结论

在当前阶段，只有同时满足下面条件，才允许进入实现：

- 正式 capability 已注册
- `spec`、`task`、`qa basis` 已建立
- 开发版与生产版 provider 边界已写清
- 隐私与日志约束已写清
- 本地 / automation / production 的职责分层已写清

若任一条件未满足，不应直接开始 provider 适配或服务实现。
