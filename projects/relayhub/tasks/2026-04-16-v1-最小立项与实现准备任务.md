这份文档用于把 `RelayHub` 从正式立项推进到可进入实现的最小准备状态。

本轮目标不是编码，而是明确第一阶段先做什么、不做什么，以及后续实现顺序如何安排。

## 1. 当前阶段目标

第一阶段先完成：

- capability 正式注册
- 公司侧入口建立
- 项目工作区骨架建立
- `spec`、`task`、`qa basis` 建立
- 对开发版、生产版、评测版的边界说法一致

第一阶段不做：

- 直接进入 provider 接入实现
- 直接搭建公司级主 Relay 服务
- 在无 QA 口径前做缓存、自动切流或复杂优化

## 2. 先落地哪些 artifact

在进入实现前，必须先有：

1. 公司级 capability 注册
2. 公司侧项目入口
3. 项目工作区入口
4. 正式 `spec`
5. 正式 `implementation plan`
6. 正式 `qa basis`

没有这些 artifact，不进入任何正式实现任务。

## 3. 第一版最小工作包

### 3.1 capability 注册

完成标准：

- `company/项目注册表.yaml` 中存在唯一正式对象记录
- 公司侧和项目工作区入口路径完整一致

### 3.2 项目骨架

完成标准：

- 项目工作区存在 `PROJECT.md`
- `specs/`、`tasks/`、`qa/`、`delivery/`、`notes/` 已建立
- README 或入口文档完整

### 3.3 共享底座边界定义

完成标准：

- `spec` 中明确共享底座只承接 provider 抽象、统一入口、基础鉴权、基础 metrics 和运行模式切换
- 未把复杂缓存、复杂切流、管理后台提前纳入 v1 必做项

### 3.4 `dev-relay` 目标

完成标准：

- 明确服务 `Claude Code`、`Codex`
- 明确可接第三方中转、国产模型和少量免费国外 API
- 明确第一版目标是“中转站比较与续费决策”

### 3.5 `prod-relay` 硬约束

完成标准：

- 明确心理疗愈应用生产版只允许国产模型
- 明确第三方中转不进入生产用户数据主链路
- 明确正文敏感数据不默认落日志

### 3.6 `eval-sidecar` 边界

完成标准：

- 明确旁路评测、日报、探活、评分板由 sidecar 承担
- 明确不把复杂评测逻辑耦合到生产 API 主进程

## 4. 后续实现顺序

在当前 artifact 完整后，后续实现按下面顺序推进：

1. 文档与目录骨架固定
2. provider 抽象层
3. 基础观测能力
4. `dev-relay` 最小闭环
5. `prod-relay/<product>` 最小闭环
6. `eval-sidecar`

这样做的原因是：

- 先把边界写清，避免一开始把开发版和生产版耦合
- 先用 `dev-relay` 验证 provider 抽象和观测能力
- 再把已稳定的共用骨架带入产品生产版

## 5. 当前 handoff 要求

当该任务交给下一棒实现角色时，至少要带上：

- 当前 `spec`
- 当前 `qa basis`
- 生产版 provider 硬约束
- 部署分层结论
- 当前明确不做事项

如果上述任何一项缺失，不应直接开始实现。

## 6. 一句话结论

`RelayHub` v1 的第一阶段，不是“马上开始写一个 relay”，而是先把 capability、边界、阶段顺序和质量门正式固定下来，再进入实现。
