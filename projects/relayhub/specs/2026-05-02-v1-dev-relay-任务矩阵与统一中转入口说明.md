## 1. 本轮目标

把 `dev-relay` 从“只服务 Claude Code / Codex 两条演示链路”，推进成“个人开发线常用大模型任务的统一中转入口”。

目标不是把所有模型请求都混成一个大口子，而是把“任务”变成正式的一等对象：

- 任务决定默认协议面
- 任务决定默认绑定模型入口
- 客户端继续走自己熟悉的原生协议
- 切模型动作统一收口到 RelayHub 控制面

一句话说，就是：

- 以后改模型，优先改 `RelayHub -> 任务绑定`
- 不再要求每个客户端各自改 `base URL / model / provider`

## 2. 当前 `dev-relay` 要覆盖的真实任务

本轮按你当前真实开发工作流，把常用大模型任务收成下面这组内建任务：

1. `task-claude-code`
   - 面向 `Claude Code`
   - 主协议：`POST /v1/messages`（Anthropic 协议，Anthropic 是 Claude 背后的公司）
2. `task-codex-repo`
   - 面向 `Codex`
   - 主协议：`POST /v1/responses`（OpenAI Responses，新一代统一响应接口）
3. `task-dev-frontend`
   - 面向前端改 UI、页面结构、交互细节、样式整理
   - 默认建议走 Claude 型任务
4. `task-dev-backend`
   - 面向后端接口、服务端逻辑、脚本接线、运维小闭环
   - 默认建议走 Codex / OpenAI-compatible（OpenAI 兼容）任务
5. `task-dev-test-fix`
   - 面向测试修复、回归补丁、fixture 收口
   - 默认建议走 Codex / OpenAI-compatible 任务
6. `task-dev-docs`
   - 面向 spec、runbook、交付说明、文档整理
   - 默认建议走 Claude 型任务
7. `task-dev-research`
   - 面向技术调研、方案比较、研究总结、迁移分析
   - 默认建议走 Claude 型任务

这里的“穷举”口径不是数学意义上的无穷枚举，而是针对你这条 `dev-relay` 线当前真实会反复使用的任务做正式收口。

## 3. 统一中转 API 的固定口径

### 3.1 Anthropic 面

用于 Claude 生态客户端：

- `POST /v1/messages`
- `POST /v1/messages/count_tokens`

适合：

- `task-claude-code`
- `task-dev-frontend`
- `task-dev-docs`
- `task-dev-research`

### 3.2 OpenAI Responses 面

用于 Codex 和更偏仓库实现的任务：

- `GET /v1/models`
- `POST /v1/responses`

适合：

- `task-codex-repo`
- `task-dev-backend`
- `task-dev-test-fix`

### 3.3 OpenAI Chat Completions 面

用于通用 OpenAI-compatible SDK、脚本、临时工具：

- `POST /chat/completions`
- `POST /v1/chat/completions`

适合：

- 需要兼容老 SDK 的开发脚本
- 需要显式用任务别名切路由的通用工具请求

## 4. 路由键口径

本轮新增固定路由键：

- `relayhub-task-claude-code`
- `relayhub-task-codex-repo`
- `relayhub-task-dev-frontend`
- `relayhub-task-dev-backend`
- `relayhub-task-dev-test-fix`
- `relayhub-task-dev-docs`
- `relayhub-task-dev-research`

规则是：

- 请求体里的 `model`
- 不再只是“真模型名”
- 也可以是 `relayhub-task-*` 这种任务别名

当客户端传：

- `model = relayhub-task-dev-docs`

`dev-relay` 应做的事情是：

1. 先把它识别成 `task-dev-docs`
2. 去控制面读取该任务当前绑定的模型入口
3. 用绑定入口里的真实 `modelId`
4. 再发给上游

这样做之后：

- 客户端只认任务别名
- RelayHub 决定真实模型

## 5. 为什么要按任务而不是按客户端切

因为“客户端”只是壳，“任务”才是真实切模型的依据。

例如：

- `Claude Code` 里既可能做前端改动，也可能做文档整理
- `Codex` 里既可能做后端修复，也可能做测试收口

如果以后只按客户端切：

- 你会得到“整个 Claude 都换模型”
- 但你真正要的是“前端保持 Claude 型，测试修复切到更适合批量试错的入口”

所以本轮固定原则是：

- 路由决策优先挂在任务上
- 客户端只是进入这些任务的不同协议门面

## 6. 本轮不做

本轮明确不做：

- 自动从 prompt 内容猜任务
- 自动 fallback（故障自动切备用模型）
- 为每个任务都额外做一套独立 URL
- 把控制面任务切换和客户端环境注入完全自动同步

当前先把“任务矩阵 + 别名路由 + 控制面绑定”跑通。

## 7. 一句话结论

从这轮开始，`dev-relay` 的正式目标不是“给某个工具临时配个中转”，而是：

- 把你开发线里常用的大模型任务收成正式任务矩阵
- 把客户端继续留在各自原生协议
- 把“换模型”统一收口到 RelayHub 的任务绑定
