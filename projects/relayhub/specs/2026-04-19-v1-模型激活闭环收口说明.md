## 1. 本轮目标

本轮固定聚焦 `模型激活闭环`。

目标不是继续扩治理壳，也不是新增部署或运行时抽象，而是把模型库里的主路径收口为：

1. 识别优先激活候选
2. 补齐最小配置与 API Key
3. 显式测试连接
4. 明确知道成功、失败、失败原因和下一步
5. 激活成功后进入任务绑定

## 2. 页面职责

`/models` 继续作为默认入口。

本页第一任务固定为“激活一个可用模型”，而不是泛化管理全部模型元数据。

页面首屏需要先回答：

- 哪些模型已经可直接绑定任务
- 哪些模型还缺 API Key
- 哪些模型已配置但还没测试连接
- 哪些模型最近测试失败，需要先修正配置

`系统预置` 的定位固定为“优先激活候选”，不在本轮重做大规模目录策展。

## 3. 激活流程口径

模型激活流程固定为：

1. 选择预置模型或新增自定义模型
2. 填写名称、Provider、Base URL、模型标识
3. 填写或更新 API Key
4. 保存配置
5. 显式点击“测试连接”
6. 查看激活结果与下一步

关键约束：

- 保存配置不等于激活成功
- 只有测试连接通过才进入 `active`
- 测试失败必须说明失败原因和建议动作
- 不做自动续费、自动余额、自动 benchmark 或自动健康探测

## 4. control-plane 最小语义

保留现有 `POST /models/:id/test` 路由，不新增新路由。

在当前 `ModelEntry` 返回结构上补最小测试结果语义：

- `lastTestResult`
- `lastTestCode`
- `lastTestMessage`

测试结果至少覆盖：

- 缺少 API Key
- Base URL 非法
- 上游不可达
- 测试通过

状态集合保持不变：

- `preset-unconfigured`
- `configured-pending-test`
- `active`
- `test-failed`
- `disabled`

mock control-plane 与 server control-plane 必须保持同一结果语义。

## 5. 与主路径的关系

模型激活成功后，下一步自然进入任务库绑定默认模型。

任务库、运行记录、统计模块在本轮只承担被动衔接角色，不作为主要改造对象。

`purchaseUrl` 继续沿用现有字段，但在界面上必须更明确地服务“先购买 / 充值，再回来激活”这一真实路径。
