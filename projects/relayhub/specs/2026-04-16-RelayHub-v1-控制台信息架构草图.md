这份文档用于把 `RelayHub` 的后台控制台从“概念页面”收束成一套可实现的信息架构草图。

它只定义：

- 控制台应该有哪些模块
- 开发版、生产版、评测版如何在界面上分开
- 首页与二级页面默认回答什么问题

它不提前定义：

- 具体视觉风格
- 最终组件库
- API 字段级细节
- 权限系统实现

## 1. 设计目标

控制台不是单纯 API 文档页，也不是只展示 usage 的看板。

v1 控制台至少要同时支持三类工作：

1. 个人开发版 relay 的上游比较与使用观察
2. 产品生产版 relay 的 provider 治理、策略确认和风险边界查看
3. 旁路 eval 的结果查看、评分板和优化建议承接

因此，控制台首页必须回答的不是“系统有没有启动”，而是：

- 现在有哪些环境在跑
- 哪些 provider 正常、哪些异常
- 哪些中转值得续费
- 哪些生产任务适合切到更便宜国产模型
- 当前有没有越界风险或配置风险

## 2. 顶层信息结构

v1 控制台建议采用“单控制台，多工作区”的结构，而不是把所有能力堆进一个混合页面。

顶层结构建议如下：

```text
Dashboard
Environments
Providers
Routes
Usage
Eval
Policies
Runs
Settings
```

其中：

- `Dashboard`
  - 回答当前系统状态和最重要决策结论
- `Environments`
  - 明确区分 `dev-relay`、`prod-relay/<product>`、`eval-sidecar`
- `Providers`
  - 看上游接入、健康度、透明度和可用性
- `Routes`
  - 看模型到 provider 的映射与任务分流
- `Usage`
  - 看 tokens、延迟、错误和成本
- `Eval`
  - 看评分板、比较结果和优化建议
- `Policies`
  - 看生产边界、隐私约束和 provider 白名单
- `Runs`
  - 看 benchmark、日报、探活、旁路评测执行记录
- `Settings`
  - 看环境级配置入口与只读系统信息

## 3. 核心分区原则

### 3.1 环境先于 provider

控制台不应让用户先从 provider 列表进入系统。

因为这个项目最重要的边界不是“接了哪些模型”，而是“当前是在什么运行模式下看这些模型”。

因此 v1 默认先按环境分：

- `开发版`
- `生产版`
- `评测版`

然后在每个环境下再看 provider、路由、usage 和 eval。

### 3.2 开发版与生产版必须显式分离

控制台里不能让人产生“开发版和生产版只是同一个表的两个筛选条件”这种错觉。

必须显式体现：

- `dev-relay`
  - 可接第三方中转
  - 主要目标是比较和续费决策
- `prod-relay/<product>`
  - 只接允许的生产 provider
  - 当前心理疗愈生产版只允许国产模型

也就是说，生产版看到的界面重点应该是：

- provider 白名单
- 任务类型映射
- 风险与策略边界

而开发版看到的重点应该是：

- provider 比较
- 中转透明度
- coding-agent 兼容性

### 3.3 评测不是主导航附属页，而是一级模块

这个项目不是普通网关。

所以 `Eval` 不能只躲在某个 provider 详情页里，而应作为一级模块存在，独立承接：

- 评分板
- 比较任务
- 日报
- 优化建议

## 4. 首页 Dashboard 草图

首页建议分成 5 个区域。

### 4.1 环境总览卡片

展示：

- `dev-relay` 当前状态
- `prod-relay/<product>` 当前状态
- `eval-sidecar` 当前状态

每张卡片至少显示：

- 当前模式
- provider 数量
- 最近 24 小时请求量
- 成功率
- 最近异常状态

### 4.2 决策摘要

这是首页最重要区域。

建议直接给出两类结论：

- `中转站续费建议`
- `国产模型替代建议`

示例表达：

- “开发版当前最稳的中转是 X，适合作为 Claude Code 主用上游”
- “心理疗愈摘要任务可切到国产模型 Y，预计降低成本 Z%”

### 4.3 风险提示

集中展示：

- 生产版是否存在越界 provider
- 某环境是否误开正文日志
- automation 与 production 是否出现职责混叠
- 某 provider 是否长时间异常

### 4.4 运行指标摘要

展示：

- 总请求数
- 总 token
- 平均延迟
- P95 延迟
- 错误率
- 估算成本

### 4.5 最近运行记录

展示：

- 最近 benchmark
- 最近日报
- 最近探活
- 最近失败的评测 run

## 5. Environments 模块

`Environments` 是 v1 的导航枢纽。

页面建议展示 3 类环境卡片：

- `开发版`
- `生产版`
- `评测版`

点进每个环境后的详情页结构建议统一为：

```text
Overview
Providers
Routes
Usage
Policies
Recent Runs
```

这样可以保持心智一致，但每个环境显示的重点不同。

### 5.1 开发版详情页重点

- 当前接了哪些第三方中转
- 哪些模型最适合 Claude Code / Codex
- usage 和 latency 差异
- 哪些 provider 缺 usage 透明度

### 5.2 生产版详情页重点

- 当前产品
- 当前允许的国产模型
- 当前任务类型分流
- 风险提示
- 成本与成功率摘要

### 5.3 评测版详情页重点

- 最近跑了哪些比较任务
- 哪些 run 成功 / 失败
- 最新评分板结论

## 6. Providers 模块

`Providers` 不是“模型市场页”，而是“上游治理页”。

provider 列表建议至少展示：

- 名称
- 类型：
  - 第三方中转
  - 国产模型
  - 免费国外 API
- 可用环境
- 健康状态
- usage 透明度
- 最近错误率
- 最近 P95 延迟

provider 详情页建议分 4 块：

- 基本信息
- 支持的模型
- 最近 24 小时运行指标
- 当前适用建议

这里“适用建议”非常重要，应该给出类似：

- 适合作为 Claude Code 主用
- 适合作为低成本备选
- 不建议进入生产

## 7. Routes 模块

`Routes` 用来回答“什么任务会走到哪里”。

这是连接模型选择与生产治理的关键页面。

v1 建议包含两种视图：

- `模型路由视图`
  - 模型名 -> provider
- `任务路由视图`
  - 任务类型 -> 模型 / provider

### 7.1 开发版路线重点

- `Claude Code`
- `Codex`
- 实验型测试入口

### 7.2 生产版路线重点

围绕任务类型展示：

- 主对话
- 摘要
- 结构化提取
- 风险识别
- 标签分类

生产版路线页必须显式显示：

- 是否仅国产模型
- 是否存在越界配置风险

## 8. Usage 模块

`Usage` 是观测面，不是决策面。

它主要承接：

- 请求量
- token 用量
- latency
- TTFT
- 错误率
- 成本

建议有 3 个默认视角：

- 按环境
- 按 provider
- 按任务类型

这样它既能服务开发版对比，也能服务生产版降本。

## 9. Eval 模块

`Eval` 是这个控制台区别于普通网关的核心模块。

建议拆成 4 个子页：

- `Scoreboard`
- `Comparisons`
- `Recommendations`
- `Reports`

### 9.1 Scoreboard

按环境和任务类型展示评分。

至少区分：

- 编码代理任务
- 心理疗愈业务任务

### 9.2 Comparisons

用于看某次模型 / provider 对比的细节。

例如：

- 中转站 A vs 中转站 B
- 国产模型 A vs 国产模型 B
- 国外模型经中转 vs 国产模型

### 9.3 Recommendations

直接显示建议，而不是只显示指标。

建议至少分两类：

- 中转站续费建议
- 任务级替代建议

### 9.4 Reports

承接日报、周报和阶段性结论。

## 10. Policies 模块

`Policies` 是生产边界的显式化页面。

这是 Manus 原型里大概率没有被做深、但对你最关键的一块。

v1 建议包含：

- provider 白名单
- 环境边界
- 日志策略
- 正文采集策略
- 敏感数据约束

对当前心理疗愈生产版，页面上必须明确显示：

- 只允许国产模型
- 不允许第三方中转
- 不默认记录用户正文

## 11. Runs 模块

`Runs` 用来承接“评测 sidecar 做了什么”。

这里统一看：

- benchmark 运行记录
- 探活执行记录
- 日报生成记录
- 失败任务记录

它的作用是让 `eval-sidecar` 的工作变得可追溯，而不是只在日志系统里才能查。

## 12. v1 不做的控制台能力

v1 控制台不做：

- 面向外部用户的公开 portal
- 复杂权限与多租户设计
- 可视化拖拽路由编排
- 在线 prompt 编辑器
- 大而全的 provider marketplace
- 一上来就做复杂 BI 报表系统

## 13. 一句话结论

`RelayHub` 的 v1 控制台，本质上应该是一个“环境优先、边界清晰、决策导向”的内部工作台。

它不是普通 API 中转后台，也不是单纯 dashboard。

它要把开发版比较、生产版治理和旁路评测三件事放进同一套信息结构里，但绝不能把它们混成同一个页面心智。
