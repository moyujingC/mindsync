## 〇、一句话总结

**八门课在一个问题上高度共识：2026 年 AI 岗的筛选入口是"你能不能讲清楚一个带评估闭环的 Agent 项目"；而 myj-healer-bench 恰好就是一个评估闭环项目本身——但课程同时给了两条硬约束：必须被外部一线用户验证过，以及疗愈/心理场景的"好"必须由人来定义、不能交给模型自评。**

## 一、市场门槛的整体判断（课程共识）

1. **招聘市场已从"你会不会用 AI"转向"你能不能讲清楚一个 Agent 项目"**。普通 demo、套壳 API 的玩具项目已经打不动面试官；面试官看四样：真实场景、复杂链路、评估指标、失败处理。（Agent 面试课·开篇词 00；极客内参·Agent 面试 02）
2. **考察重心从"执行"变成"判断"**。执行 AI 能替你做，判断不能。面试官三层追问：是什么 → 为什么 → 变了会怎样；"第三层只有真懂系统的人答得上"。（极客内参·Agent 面试 02）
3. **"没有评测的 Agent 都是玄学 / 只是玩具"**。Demo 看结果，生产看轨迹；"如果你直接问大模型'我这个回答好不好'，它甚至会奉承你"。（极客内参·玩转Agent应用开发 02、企业AI实战 02/03）
4. **评测是岗位筛选入口，不是加分项**：美团 JD 要求"Agent 测评标准输出经验"；AI lab 面试 "how do you know it works" 是头号筛子，**eval 答不出 = 直接拒**；take-home 常考"搭 RAG + eval harness"。（极客内参·Agent 面试 02；HA7CH·dachang-fde-interview）
5. **评估投入抗模型换代**："模型会换，Harness 会重构，评估那把尺子得一直在。""Big Model 派和 Big Harness 派有一个共同的前提：都得先有评估集。"（FDE 业务落地实战 11）——这是对 healer-bench 项目最有利的结构性判断：**benchmark 是少数不会被下一代模型废掉的投资**。

### 没有竞争力的项目的五个死因（Agent 面试课·直播回放）

1. 业务场景过于简单（"这用 Workflow 就能解决，为什么要搞 Agent？"）
2. 只有技术组件，没有运行机制
3. 只有 Happy Path，没有异常处理
4. 无法解释 Agent 为什么这样决策
5. **没有评估与反馈闭环**——"你只要说'这个地方做得很好'，面试官一定会追问：'你怎么知道？'"

## 二、一个求职项目"算数"的硬标准（课程共识综合）

按课程反复出现的判据，一个能打动招聘方的项目需要同时满足：

### 2.1 内容层

| # | 标准 | 来源 |
|---|---|---|
| 1 | 真实场景 + 复杂链路（多步骤才能解决的场景；面试官一听就知道要分很多步） | Agent 面试课·10 |
| 2 | 解决真问题（"技术链路成立，不代表产品成立"）；进场产出是"经过现场验证的真问题"清单 | 极客内参·FDE 01、AI产品 03 |
| 3 | 异常处理能力：失败回溯、兜底降级、根因点 ≠ 失败点 | Agent 面试课·10 |
| 4 | 端到端（真实输入→处理→可见输出，本人主导，零依赖），"宁可窄，不能断" | HA7CH·fde-diagnosis |
| 5 | **被外部一线用户验证过**（硬地板：内部同事用过 ≠ 被验证；无外部验证，FDE 评分封顶） | HA7CH·fde-diagnosis |
| 6 | 留下可复用资产，且能带它进入下一个场景（"第二客户是不是更容易"是真假 FDE 的分水岭） | FDE 业务落地实战 13/02 |

### 2.2 证据层（评估与数据）

| # | 标准 | 来源 |
|---|---|---|
| 7 | 评估与反馈闭环是简历**必选**项，不能只写"用了 LLM-as-a-Judge"，要形成"离线评估→线上监控→异常样本沉淀→归因→定向优化→灰度验证"闭环 | Agent 面试课·加餐-简历篇 |
| 8 | 每组数字都要扛得住四问：怎么采集？怎么计算？当前数值？是否合理？绝对值+相对值双报 | Agent 面试课·04、直播回放、24 |
| 9 | 指标从"用户为什么用这个 Agent"反推；目标/过程/护栏三组指标同时看；防指标被模型刷歪 | Agent 面试课·23 |
| 10 | 用数据证明优化有效："面试之前，至少准备几组自己能解释清楚的核心指标"，最好有优化前后对比 | Agent 面试课·24 |
| 11 | 评估集是"方向盘"不是验收工序：**写第一条提示词之前，先定义什么叫"好"**；没有评估标准的"快速迭代"只是凭感觉改代码 | FDE 业务落地实战 11；极客内参·FDE 01 |
| 12 | 执行与评判必须分离（模型自评会给自己好评；judge 与被测不同源） | 生产级 Agent 排雷 01；AGI PM 指南 04 |

### 2.3 表达层（简历与面试）

- 简历项目终极三问："你发现了什么业务或技术问题？你设计了什么机制解决它？结果改善到什么程度？"（Agent 面试课·加餐-简历篇）
- 写作公式："解决方案的关键技术词汇 + 改进优化 + 最终数据"，绝对值+相对值双报
- 项目名称要"业务场景 + 核心能力 + 平台定位"，避免"AI 智能平台"这类宽泛名
- 主线剧情法：把要展示的技术判断都织进一个足够复杂的具体业务场景（Agent 面试课·10）
- v0/v1/v2 版本叙事：v0 解释为什么需要优化，v1 分阶段改好，v2 讲下一步（高职级反而要深讲 v2）（Agent 面试课·04）
- 没做过的别吹成做完的："完整方案 10 分，先讲落地的 8 分，剩 2 分作为下一步优化"（直播回放）
- **边界提醒**：课程讲师自己承认方法有"包装"成分，但划了红线——"碰到真正懂行、具备打假能力的面试官，数字、badcase、评测集必须真实可演示"（Agent 面试课·直播回放）

## 三、评测方法论全集（可直接搬进 healer-bench 的部分）

这是三门课+FDE 课交叉验证后最完整的"benchmark 设计教科书"：

### 3.1 评估集骨架：三类评估集（多课独立提出，措辞几乎一致）

1. **黄金场景集**：客户/用户最核心的场景，什么是对什么是错必须足够清楚，答案唯一、可程序逐字判定；不能出现"最近一周"等会漂移的说法。接近满分才允许上线，每次迭代不许倒退。
2. **异常场景集**：真实使用中的长尾怪情况；来源：真实回流 + **双环境互挑错**（同一任务跑在两个 harness 里，分叉处就是脆弱场景）。上线前扛不住 = 上不了生产。
3. **安全对抗集**：故意设套（诱导越权、诱导泄密、提示注入）。**只要有一条不通过就停止上线，红线不能被别的东西稀释。**

来源：极客内参·FDE 01；FDE 业务落地实战 11；生产级 Agent 排雷 13；Agent 设计模式之美 21/22。

### 3.2 分数纪律

- **三集分开算，不许算平均分**（FDE 11）
- **棘轮原则（Ratchet）**：分数每上一个台阶就成为新地板，任何改动不许把分数打回地板以下；"这次先上了再说"永远不会被批准（FDE 11）
- **"考不过就改考卷"是 AI 项目最容易发生、最难被发现的腐化**——改期望值必须慎重，改动必须 diff 可见、单独评审（FDE 11；Harness 课 20 的 Benchmark CI 可工程化防这个）

### 3.3 判定方法分层（确定性优先）

```
确定性脚本（有标准答案）→ LLM-as-Judge（开放任务）→ Agent-as-Judge（评轨迹）
        ↑ 优先用                          ↑ 必须校准，与人工判断一致性
```

- 三级裁判体系 + 多裁判多视角；**聚合前先归一化**（"9600 元"="9,600"）；**允许 verdict=None**——诚实地无法裁决，优于硬投出赢家（设计模式之美 19/17）
- 离线评估的合理组合：**测试集负责稳定回归，LLM Judge 负责语义化评估，专家负责校准，用户反馈/A-B 负责验证线上真实效果**（Agent 面试课·23）
- 测试集三大来源：手写（早期）、AI 生成+人工监督、**线上案例回流**（最有价值）；要考虑覆盖率（23）
- **影子测试**：真实流量走老版，复制一份给新版，judge 自动比对，通过才切流（企业AI实战 04）
- **Quality Gate 发布门禁**：检索命中率低于阈值或工具误用率高于阈值就不允许发布（企业AI实战 02）
- **judge 自身要被评测**：judge 的一致性/与人工裁决的符合率要进报告；"换模型换领域要重跑评估"（排雷 06）
- 用最强模型当标杆：最好模型+最简单提示词能达到 90%，场景才成立；做不到就是外围系统问题（AI产品 02）

### 3.4 指标体系设计

- **分桶报告，禁止一个总分**：按任务类型分桶建立自己的基线 SLO（设计模式之美 16/18）——对疗愈类至少分：日常陪伴/情绪疏导/危机干预/信息咨询
- **多维指标**：最终成功率 + 子目标完成率 + 延迟 + 成本 + 工具调用准确率 + **轨迹效率**（3 步修好 vs 20 步修好，只有轨迹评估能区分）（Harness 课 20）
- 完整指标清单参考 31 项可观测性指标：任务成功率、用户纠正率、约束违反率、证据覆盖率（过低=幻觉风险）、无依据结论率、上下文利用率、Replan 成功率……按业务特点选核心（Agent 面试课·24）
- **成本是正式评估维度**：单位验证成功成本（token/美元）必须披露——"The model spends; the harness budgets"（设计模式之美 19；Harness 课 18）
- 业务指标三问：用户为什么来？觉得好用会做什么？觉得蠢会做什么？（Agent 面试课·23）

### 3.5 可信性工程（benchmark 本身要被信任）

- **SWE-bench 范式**：真实任务 + 客观断言 + 隔离环境（Docker）+ Fail-to-Pass 判据 + 不产生回归；TestCase/TestResult 全部 schema 化（Harness 课 20）
- **防污染防过拟合**：SWE-bench-Live 动态更新测试集防记忆刷分；注明数据切分日期（Harness 课 20）
- **golden questions 回归**：发布前用"业务上最容易出错的关键问题"做回归（设计模式之美 13）
- **消融实验证明区分度**：固定刺激、逐层加装能力，证明每个评分维度确实在测它声称测的东西——"这是 benchmark README/论文最有说服力的证据形式"（设计模式之美 21/22）
- **badcase 闭环六层结构**：失败边界→分类 taxonomy→证据包→根因四段（不写"模型太粗心"）→召回触发器→审查状态机；"同一个坑只踩一次"（设计模式之美 15；Agent 面试课·23）
- **四笔账的报告结构**：状态账（终态通过率）/ 动作账（轨迹）/ 效果账（用户可感知结果）/ 证据账（判定依据可回放）——终态通过率单独不构成证据（设计模式之美 21）

## 四、三条岗位轨道的能力侧重（同一项目，三种讲法）

| 轨道 | 项目要证明的核心 | 面试考察点 | 对标课程 |
|---|---|---|---|
| **AI 产品经理** | 想法→Demo→上线→留存的全链路；"Demo 就是 PRD"；评测、迭代与数据飞轮是壁垒（"真正的壁垒不是第一版，是持续迭代的能力"）；6D 流程中 Design（什么算好）与 Detect（建评测集找 badcase） | 用数字向上表达的话术模板；"打动客户三条硬标准：Demo 解决问题 / 竞品对比在客户自身问题上胜出 / 快速个性化" | AGI PM 指南 02/03/04；极客内参·AI产品 01/03 |
| **AI 应用工程师** | 生产级工程能力：七道关（Loop 控制/工具契约/上下文与记忆/规划/权限安全/韧性成本/测试闭环）；"上线六项检查清单"（评估过线、真实规模性能成本、安全权限、留痕可审计、回滚预案、运营交接） | 架构判断 + 异常处理 + "改版后是否退化"六问 | 排雷课全册；Harness 课；设计模式之美 |

## 五、疗愈/心理/陪伴场景的专门推论（课程空白 + 红线）

**如实说明：八门课均无论述疗愈/心理/陪伴类 AI 的专门标准**，最接近的是两处：

1. **Agent 面试课·直播回放的专门警告**："情感陪伴类 Agent 可设计情绪改变率或情绪向好率，不过**这类指标怎样安全、准确地采集和评测，需要更加谨慎，尤其涉及心理健康场景时不能随便下结论**。"——同一章还给出关键对照：同一个指标在不同业务方向可能相反（客服聊 20 轮=没解决问题；陪伴聊 20 轮=成功）。
2. **医疗（强监管行业）案例的迁移**：坦帕综合医院败血症筛查——"在最受监管的行业，治理本身就是产品，就是核心竞争力"；系统只负责标记、专职团队负责处置（人工检查点）；警报发给谁决定了它是救命工具还是背景噪音。（FDE 业务落地实战 12/17）

**由此直接推出的 healer-bench 设计推论**（课程未明说，但标准一致指向）：

- 疗愈类"好"的三层定义：**系统层**（三集分数）/ **行为层**（真实使用行为，不看主管自评——"客户可能因为礼貌说产品不错，行为不会说谎"）/ **红线层**（危机场景零漏报）
- **安全对抗集在疗愈场景应有医疗案例同等的"红线"地位**：自伤/他伤风险识别一票否决
- **主观维度（共情、陪伴质量）必须有人类锚点**：结构化 rubric + 专家校准集；judge 模型与被测不同源；这是"不能随便下结论"的工程化解法——**这个空白本身就是项目的立项理由**
- 陪伴型 Agent 长会话评测要考**记忆连续性**（跨会话记得用户偏好是陪伴质量的一部分）；长对话历史中埋关键信息（此前透露的风险信号），测上下文稀释下的召回——疗愈场景特有的高价值测试手法

## 六、对 myj-healer-bench 的设计启示清单

综合三份报告，项目要做到"课程及格线"至少需要：

### 必须（MVP 门槛）

1. **三类评估集 + 分桶报告**：黄金/异常/安全对抗，疗愈四桶（陪伴/疏导/危机/咨询），禁止一个总分
2. **红线一票否决**：危机识别（自伤/他伤/转介）作为安全对抗集，不过线即不合格
3. **确定性判定优先**：能写脚本的不用 judge；judge 必须评判分离 + 人工校准 + 一致性报告
4. **schema 化 + 版本化 + 可复现**：TestCase/TestResult 结构、git 管理、隔离运行、固定模型参数
5. **棘轮原则 + Benchmark CI**：每次任务集/judge prompt 变更自动回归，改考卷 diff 可见
6. **badcase 回流机制**：发布后的错误案例归档为 V2 用例库
7. **外部验证**（HA7CH 硬地板）：至少一批真实疗愈师/心理咨询师/真实用户参与共建或评审"什么算好"——这也直接回应课程说的"请客户出题"而非"建好了给客户看"
8. **成本披露**：每个被测模型报单位成本

### 加分（拉开差距）

9. **消融实验**证明每个评分维度测的是它声称测的东西
10. **四笔账报告**（状态/动作/效果/证据）
11. **与墨予镜的联动**：墨予镜疗愈陪伴助手作为首个被测对象 + 真实使用数据的回流来源——一个项目同时讲出"构建 benchmark"和"用 benchmark 驱动产品迭代"两条故事线
12. **"情绪向好率"类指标的严谨化方案**：作为项目的技术亮点正面回应面试课的警告
13. GitHub 公开运营（issue=Echo 落点、PR=Delta 交付单元的协作语言）

### 要主动避开的坑

- ❌ 只有评测集、没有运行机制说明（死因 2）；只有 Happy Path、不测异常（死因 3）
- ❌ 数字经不起四问（采集/计算/数值/合理性）
- ❌ 自评自夸（"陪伴质量很好"而没有证据链）
- ❌ 场景太简单（单轮问答——"面试官会直接带入 RAG 一次搞定"）
- ❌ 疗愈场景的伦理红线：不能让 benchmark 自己变成"随便给心理健康下结论"的东西——这会被懂行的面试官一票否决

---

## 七、待与用户对齐的开放问题

1. 目标岗位轨道的最终取舍（PM 线 vs FDE 线 vs 双线叙事）——影响项目的包装主线
2. 外部验证的入口：有没有疗愈师/咨询师资源可以共建评估集？
3. 与墨予镜的关系：拆出来独立，还是作为其评测子系统？
4. "情绪向好率"等主观指标的采集方式（涉及真实用户情绪数据，伦理边界要先定）
5. MVP 时间预算
